## 着手順を変える二つの事実

### Unity は別ブランチに実装がある

`git log --all` と `git branch --all --contains 98384ba9` で、`feature/remove-unity-gateway` と同名の remote ref を確認した。`98384ba9` は38ファイルを変更し、起動口と gateway を削除している。同ブランチの `docs/issues/unity_gateway_removal.md` には隔離起動・回帰検査の結果と、まはーが v0.3.12 へ入れず develop 経由の次版へ送ると決めた記録がある。

これは**別ブランチの実装・検証記録の確認**であり、現在の HEAD へ統合済み／出荷済みとの判定ではない。こちらで同じ削除を作り直さず、その変更を取り込む担当との整合を確認する。都市間 API 子プロセスと SDS の残りまで直ったとは扱わない。枝の切替・マージ・外部への連絡はしていない。

### Memopedia 操作によるコア記憶への影響は現在のコードにも残る

画面 `MemoryRecall.tsx` の「Memopedia 全削除」は DELETE `/{persona_id}/memopedia/pages` → `delete_all_memopedia_pages` → `clear_all_pages` へ繋がる。インポートは `clear=true` → `import_json(clear_existing=True)`。`sai_memory/memopedia/core.py` の双方は root と chronicle を除外し、core を除外しない。

同ファイルの `export_json` は core の行も出すが metadata は運ばず、`import_json` はその行を metadata なしで作る。`sai_memory/core_memory.py` の読み取りは metadata の `core_id` を整数へ変換する。これらの接続を今回ソースで再確認した。前の追加調査には型エラーの隔離再現がある。製品の発話まで必ず止まるとはまだ言えず、既存 head の据え置きで表面化しない場合もある。

## 最初の対象への提案

**Memopedia の一括削除・書き出し・取り込みが、コア記憶や Chronicle を巻き込まないこと**を最初に扱う (FLOW-11 / FLOW-13)。正常な操作による記憶の喪失という影響があり、既存裁定から守る対象が定まり、入口と保存先が特定できているため。さらに同じ表の差分通知も調べ、コア記憶を別の種類の出来事として伝える混入を同じ責務の問題として点検する。

最初に Opus へ渡すのは [設計・隔離再現の依頼案](../../handoff/2026-09-13_memopedia_boundary_design_opus_brief.md)。元の実験を使い、**対象範囲、UI/APIからの再現、保存後の読み取り、修正の置き場所と検査**まで揃える。返却後に Astra が根拠を確認し、その具体案を実装へ渡す。今回のコード修正を開始したという記録ではない。

以後の順序案:

1. 上記の Memopedia 操作の影響範囲。
2. メディア URI の読み出し境界 (FLOW-06/16) と、別作業の Unity 撤去を踏まえた都市間・SDS 起動停止 (FLOW-25/30)。それぞれ独立した対象として扱う。LAN 直の利用は閉じない。
