## 変わること — 一例

**いま**: 利用者が「Memopedia 全削除」を押す。画面は「Memopedia: 4件のページを削除しました」
と出す ([実測](repro/exp1_delete_all_result.json))。消えた 4 件の内訳は、手帳のページ 1 件と
テーマ 1 件、そして**コア記憶 2 件**。コア記憶は 1 件ずつ消せば戻せるのに、この経路だけ
戻せない形で消える。

**直した後**: 同じ操作で「2件のページを削除しました」。手帳のページとテーマだけが消え、
コア記憶はそのまま残る。画面の文言 (「データを一括削除します」) は書き換えない —
実際の方が文言に合う。

## 推奨する具体案

**カテゴリの役割表に「手帳の一括操作の対象か」を 1 行足し、全経路がそこを引く。**

`CATEGORY_DEFS` (`sai_memory/memopedia/storage.py:29-51`) は既に
「全フラグはここが唯一の真実の源」と宣言し、`in_tree` など 5 つの役割を持つ。そこに 1 つ足す。
コア記憶と Chronicle は既に `in_tree=False` (木に出ない) で分かれているので、**同じ線を
削除にも使うだけ**。新しい概念を作らない。

**守りは「実際に消す場所」に置く。** 2026-08-19 の Chronicle の手当て (`58d57c37`) は、
入口に検査を置く試みを三巡失敗した末に「入口の検査は境界の保証ではない。守りたい結果は
実際に DELETE を発行する場所で検査する」と結論している (`storage.py:756-764`)。
コア記憶にだけその守りが無い。入口は画面の他にスクリプト 3 本もあるので、最下層に置く。

## 実装対象 (4 段、詳細は design.md §9)

1. 役割表 + 一括操作 3 つ + 物理削除 → 全削除・書き出し・取り込みの 3 つの壊れ方が同時に止まる
2. 本人への差分通知 → ペルソナが自分のコア記憶を「手帳の新しいページ」として知らされなくなる
3. 取り込みの順序と告知 → 「取り込んだつもりが全消し」が閉じる
4. 既に壊れた記憶の救済 → 1〜3 の後でないと、直した先からまた壊れる

## 検証の結果

画面のボタンが叩くのと同じ API から、隔離環境で実測した。**4 つとも再現した**:
全削除でコア記憶が物理削除される / 書き出しに混ざる / 取り込むと一覧が丸ごと読めなくなる /
置き換え取り込みが全消しで終わって「成功」と返る。

調査した既存検査では、この四つの被害を防ぐ組み合わせが見つからなかった。
実測したのは変更前の3ファイル93件の成功までで、修正後の既存検査への影響は未検証。
追加する検査の置き場所と判定は [verification.md](verification.md)。

未検証: 実際の HTTP・画面の操作・バックエンドの起動・ペルソナの発話。すべて関数の直接呼び出し。

## Astra が最初に判断する一点

**既に壊れた記憶の救済 (design.md §7) を、予防と同じ変更に入れるか、分けるか。**

予防 (§3〜§6) は迷う余地が無い。判断が要るのは救済のほう。書き出し → 取り込みを既に
踏んだペルソナには、`metadata` の無いコア記憶の行が残っていて、その 1 件が一覧全体を
落としている。**合成データでは壊れた行の本文と番号らしい表題が残ったが、表題から正規IDを復元できるとは限らない**。番号の衝突も機械では決めず、推測で振り直さない。

**私は分けることを推す。** 救済は「現に壊れているペルソナがいるか」に依存し、それを知るには
まはーの本番データを見る必要がある (今回は触っていない)。かつ、壊れた行を利用者に見せて
取り除かせるには画面側の手当ても要るので、予防とは別の作業になる。
**予防を先に入れないと、救済した先からまた壊れる**ので、順序は動かない。

なお「記憶の検索にコア記憶が混ざる」は**今回も次回も直さない**。一見すると同じ根に見えるが、
移行時の記録 (`docs/intent/concept_consolidation.md:199`) に「`Memopedia.search` には
現れる〔**望ましい**〕」と明記されていた。同じ行に一括削除の記述は無い —
**検索は検討されて残され、削除は検討されていない。** ここが「同じ形に見えて別」の境目。

まはーへ上げる新しい質問はゼロ。

## 守った境界

- 製品コード・既存テスト・CI・既存文書・メモリを**一行も変更していない**。書き込みはこのフォルダのみ
- 他の担当の未コミット変更 (`review_progress.md` / 依頼書) を巻き戻していない
- 本番ペルソナ・本番データに触れていない。LLM を呼んでいない。バックエンドを起動していない
- git の切替・stash・reset・コミット・マージ・公開をしていない
- 隔離は毎回 `SAIVERSE_HOME` が本番を指していないことを実行時に検査した上で行った
