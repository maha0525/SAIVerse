# 手帳の一括操作が、手帳以外の記憶を巻き込まないようにする — 設計

2026-09-13 / 開始時 HEAD `19ea2010` (ブランチ `codex/product-normalization`)
入力: [依頼書](../../handoff/2026-09-13_memopedia_boundary_design_opus_brief.md)

観測と再現は [verification.md](verification.md)、要約は [README.md](README.md)。

2026-09-14: [Astraレビュー](astra_review.md)で、§6の失敗時の扱いと§8の通常データの往復を補完対象とした。§7の救済は別変更へ分ける。以下は補完前の設計で、採用部分と残作業はレビューを参照する。

## 0. この設計が実装するもの — 新しい判断は作らない

**正常な姿は、まはーの規範を適用した統合文書に記録されている。**
[normal_behavior.md](../2026-09-12_normal_behavior_consolidation/normal_behavior.md) FLOW-13 (`:579`):

> 手帳のページを全部消す操作は、コア記憶を巻き込まない。(中略)
> 訊いて選ばせるのでもなく、**あらすじと同じように除外する**

同 FLOW-13 の「いま要る判断」は **「無し」** (`:612-614`)。
つまりこれは、書かれた姿を実装へ落とす設計であって、新しい選択肢を並べる設計ではない。

**この操作ではコア記憶を対象から外す。** まはーの原文は「ユーザー操作の結果はその影響範囲をユーザーの期待と合わせる」。三分類とFLOW-13の具体的な除外は、統合担当がその規範を各操作へ適用した記述である。今回の手帳操作ではコア記憶を巻き込まず、専用の入口で扱う。この適用を「確認を求めてよいのは利用者が用意したものだけ」という一般規則には広げない。

## 1. 守る対象 — 同じ場所に、4 種類の記憶が同居している

`memopedia_pages` は名前に反して「手帳のページの表」ではない。**4 種の記憶の物理的な置き場**。

| 種別 | 何か | ペルソナから見た参照 | 1 件ずつ消す口 |
|---|---|---|---|
| 手帳のページ (`people` / `terms` / `plans` / `events`) | 利用者とペルソナが手帳として書く | `m:N` | 消える (戻せない) |
| テーマ (`theme`) | 旧 Note の後継。手帳の木に並ぶ | `m:N` | 同上 |
| **コア記憶** (`core`) | ペルソナ本人が刻んだ、常に携えている記憶 | `c:N` | **ごみ箱行き (戻せる)** |
| **Chronicle** (`chronicle`) | 時間の地図 | `ch:N` | **拒否される (409)** |

**同居したのは置き場所だけで、概念は統合していない。** コア記憶と Chronicle を
`memopedia_pages` へ移した 2026-07-11 の作業は、`docs/intent/concept_consolidation.md:199`
(P3a) と `:207` (P3b) に記録があり、どちらも「**API 完全維持**」と書いている。
移行後もコア記憶は自分の関数群と `c:N` の参照を保ち、Chronicle も同じ。
**同じ表にあることは、同じ操作対象である根拠にならない。**

### 1.1 一括操作の対象はどれか

**対象は、手帳の木に並ぶ 5 カテゴリ (`people` / `terms` / `plans` / `events` / `theme`)。
`core` と `chronicle` は対象外。**

テーマを対象に含める根拠は二つ。`sai_memory/theme_pages.py` の冒頭が
「テーマページは通常の Memopedia ページと同じ扱い」「参照は m:N (memopedia の通常
short_id) — コア記憶の `c:N` / Chronicle の `ch:N` のような専用参照子は持たない」と
明記していること。そしてカテゴリ定義で `in_tree=True` (木に出る) なので、利用者が
手帳を見たときに実際に並んでいること。**画面で手帳として見えているものが対象**、が
この線の意味。

`core` と `chronicle` はどちらも `in_tree=False` で、木に出ない。利用者は手帳の画面で
その存在を見ていない。見ていないものが「手帳の全削除」で消えるのが、今の食い違い。

### 1.2 種別を一意に決める列は存在しない

`category` は親から継承され (`sai_memory/memopedia/core.py:396`)、ページの親を付け替える
処理は Chronicle を拒むがコア記憶を拒まない (`sai_memory/memopedia/storage.py:1358-1408`)。
`id` の `root_` 接頭辞は根だけを守り、その子を守らない。つまり **DB の列だけを見て
「これはコア記憶だ」と確実に言える方法が無い**。

だから守りは **カテゴリの役割** に置き、しかも**実際に消す場所**で見る (§3)。
そうすれば、コア記憶が `root_core` の外へ動かされていても、カテゴリで判定するので守られる。
配置がずれること自体を防ぐ (親の付け替えがコア記憶を拒む) のは別の手当てで、今回は扱わない
— 守りを消す場所に置くので、ずれていても物理削除からは守られる。

## 2. いま実際に何が起きるか

すべて隔離環境で、画面のボタンが叩くのと同じ API から実測した (詳細と数字は
[verification.md](verification.md))。

1. **手帳の全削除で、生きているコア記憶が物理削除される。** ごみ箱にも入らない。
   逆に、既にごみ箱にあるコア記憶は残る。**結果が反転している。**
   exp1の応答は `success: true` / `deleted_count: 4` で、通常ページ1件・テーマ1件・コア記憶2件が消えた。
2. **書き出しにコア記憶が混ざる。** しかも `metadata` を運ばないので、
   何番目の記憶か (`core_id`)・実会話の写しか (`kind`)・利用者が確認済みか (`confirmed`)
   が全部落ちる。
3. **その書き出しを取り込むと、コア記憶が 1 件も読めなくなる。** 壊れた行が 1 件できると、
   一覧を組む処理が `TypeError` で止まる。並び順の都合で壊れた行が先頭に来るため、
   無事な行も 1 件も返らない。
4. **取り込みのつもりが全消しになる場合がある。** 「既存を置き換える」を選ぶと、
   先に全部消してから中身を見に行く。中身が全部はじかれる入力 (Chronicle 時代の
   古い書き出しファイルなど) だと、消しただけで終わって
   `success: true` / `imported_count: 0` が返る。
5. **ペルソナ本人に、自分のコア記憶が「手帳の新しいページ」として知らされる。**
   最近の更新を本人へ伝える処理にカテゴリの条件が無く、全行が対象
   (`sea/head_pipeline/sections/memopedia_index.py:283-297`)。
   取り込み直後は作成時刻が振り直されるので、全ページが「作成されました」として届く。

### 2.1 壊れた後、利用者は自力で直せない (実測)

- コア記憶の画面は 500 を受けて黙って捨て、**「まだコア記憶はありません。」**と表示する。
  同じ画面に出る合計字数は別の集計なので生きており、「合計 N 字」と「まだありません」が
  並ぶ。利用者は全部消えたと読む。
- 壊れた行は手帳の木にも出ない (`core` は木に出ないため)。**見つける手段が無い。**
- きれいにする唯一の方法が「手帳の全削除」。それを押すと、無事なコア記憶も
  戻せない形で一緒に消える。

**壊した操作の後始末が、もっと大きく壊すことでしかできない。**

### 2.2 読み手が受ける影響

コア記憶の一覧が読めなくなると、次が同時に起きる:

- ペルソナの頭を組む処理は例外を握らない設計で、**据え置きの頭があれば古いまま喋り続け、
  無ければそのモデルで一言も喋れなくなる**。これは「コア記憶ゼロの本人」を捏造しない
  ための意図的な作り (`sea/head_pipeline/sections/core_memory.py:107-116`) であって、
  正しい。**壊す側を直すべきで、この fail-closed を緩めてはいけない。**
- 退場のときの記憶の整理が毎回止まる。利用者には一時障害の文面が毎回出る。
- 記憶を読むスペルが失敗し、**例外の文がそのままペルソナの文脈に入る**。

据え置きは失敗のたびに再利用されるので、**操作と症状の間に無期限の遅れが入りうる**。
利用者が原因と結果を結びつける見込みはほぼ無い。

## 3. 修正 — 対象範囲の判定を 1 箇所に置く

### 3.1 役割はカテゴリ定義に足す (新しい概念を作らない)

`sai_memory/memopedia/storage.py:29-51` の `CATEGORY_DEFS` は、docstring で
**「カテゴリ定義。全フラグはここが唯一の真実の源。」**と宣言していて、既に
`in_tree` / `hide_when_empty` / `extractable` / `writable` / `metabolizable` の 5 つの役割を
持つ。引く側は `category_keys(role)` (`:54-63`) を呼ぶ。

ここに **「手帳の一括操作の対象か」を 1 つ足す**。`people` / `terms` / `plans` / `events` /
`theme` が真、`core` / `chronicle` が偽。

この形を選ぶ理由:

- **新しい語彙を増やさない。** 役割フラグという既存の仕組みの中に収まる。
- **カテゴリが増えたときに漏れない。** いまの条件は `category == "chronicle"` という
  **除外するものを名指しする否定形**で書かれていて、種別が増えるたびに同じ漏れが起きる
  (コア記憶がまさにそれ)。役割表は肯定形で「対象はこれ」と書く。
  同じ教訓は `tests/test_body_to_fragment_ops.py:419-422` の docstring にも既にある。
- 表示の区別 (`in_tree`) は既にコア記憶と Chronicle を分けている。**同じ線を削除にも使う**
  だけで、新しい線を引くわけではない。

### 3.2 守りは「実際に消す場所」に置く — 完成した前例がそのまま使える

Chronicle の守りは 2026-08-19 (コミット `58d57c37` に同梱) に
`sai_memory/memopedia/storage.py:751-773` の `delete_page` へ入った。docstring の原文:

> 入口 (Memopedia core の拒否・import/clear の除外) の検査は境界の保証ではない —
> 「Chronicle を通常ページ配下へ移動 → 一括 clear」の並びで、この関数の**子孫再帰**が
> カテゴリを見ずに物理削除する迂回路が実在した。守りたい結果 (Chronicle 行が
> 消えない) はここ = 実際に DELETE を発行する場所で検査する。

**その迂回路は、コア記憶には今も開いている。** ページの親を付け替える処理
(`storage.py:1358-1408`) は Chronicle を拒むがコア記憶を拒まないので、
「コア記憶を通常ページの下へ移す → 手帳の全削除」で同じ並びが成立する。
入口だけ直しても塞がらない。

**前例の形を三点そのまま倣う**:

1. **既定で拒否し、明示的に許可した呼び出しだけが消せる。** Chronicle は
   `allow_chronicle: bool = False` という引数を持ち、現行の本番コードにこれを
   真で渡す呼び出しは存在しない (正規の一括削除は `delete_page` を通らず自前で書く)。
   コア記憶も同じで、正規の削除はごみ箱行き (`remove_core_memory`) なのでこの関数を通らない。
2. **拒否の単位は、その部分木を飛ばすこと。削除全体は続ける。** 例外で止めない。
   手帳の全削除が、コア記憶があるせいで失敗してはいけない (依頼書の
   「保護の結果 Memopedia の操作自体が使えなくならないこと」)。
   既存の削除は行ごとに個別 commit する非原子の作りなので、全体失敗型は後付けできない
   — これも docstring が明記している。
3. **飛ばしたものは、正しい親の直下へ退避する。** Chronicle は `root_chronicle` 直下へ戻す。
   親が直後に消えても宙づりの参照にならないため。コア記憶なら `root_core` 直下へ戻す。

物理削除を呼ぶのは一括操作の 2 箇所だけで、他の削除口はすべて soft delete なので、
ここに境界を置いても正規の経路は壊れない。

### 3.3 引く場所の一覧

| 場所 | ファイル | いまの条件 | 直した後 |
|---|---|---|---|
| 手帳の全削除 | `sai_memory/memopedia/core.py:1059-1076` | `root_` と `chronicle` | 役割表を引く |
| 書き出し | 同 `:917-966` | 同上 | 同上 |
| 取り込みの削除側 | 同 `:988-1000` | 同上 | 同上 |
| 取り込みの作成側 | 同 `:1025-1032` | `chronicle` だけ弾く | 同上 |
| **物理削除 (最後の砦)** | `sai_memory/memopedia/storage.py:751-799` | `chronicle` だけ拒否 | 同上 |
| 本人への差分通知 | `sea/head_pipeline/sections/memopedia_index.py:283-297` | **条件なし (全行)** | 同上 |

入口は画面だけではない。`scripts/export_memopedia.py --clear` /
`scripts/build_memopedia.py --clear` / `scripts/build_arasuji.py --clear-memopedia` の
3 本も同じ処理を呼ぶ (Chronicle を作るスクリプトからコア記憶が消せる形になっている)。
**入口ごとに書くと 4 箇所に散る。だから最下層に置く。**

## 4. 告知を、実際に起きたことと合わせる

画面は「Memopedia 全削除」「データを一括削除します。この操作は取り消せません。」と告げ、
完了時に「Memopedia: N件のページを削除しました」と出す
(`frontend/src/components/memory/MemoryRecall.tsx:1161, 1117, 1165, 624`)。
コア記憶が対象だとはどこにも書かれていない。

§3 の修正で対象がページだけになるので、**この文言は直さなくても正しくなる**。件数も
手帳のページだけを数えた数になる。文言を書き換えるのではなく、実際を文言に合わせる。

取り込みの応答 (`success: true` / `imported_count: N`) は、いま
「Chronicle だったので作らなかった行」「既に同じ id があった行」「例外で落ちた行」を
黙って数から落としている。**除いた件数と理由を返し、画面に出す** (§5 と繋がる)。

## 5. 旧データ — 既に書き出されたファイルにコア記憶が入っている

この欠陥は今日できたものではないので、**利用者の手元にある書き出しファイルには
既にコア記憶の行が混ざっている**。§3 の修正後、それを取り込むとどうなるかを決める。

**決定: 取り込まない。そして黙って捨てず、何件除いたかを告げる。**

Chronicle が既に同じ扱いを受けている (`core.py:1025-1032` が旧 export の残骸を弾き、
警告を書く)。同じ形をコア記憶にも適用する。違いは一点 — **利用者に見える形で伝える**。
Chronicle の現状はログ 1 行だけで、画面には出ない。取り込みは利用者が意図して行う操作
なので、「あなたのファイルには手帳以外の記憶が N 件入っていました。それは取り込んで
いません」と応答に載せる。

推測で補わない。書き出しファイルの core 行から `core_id` を推定して復元する、といった
ことはしない (§7)。

## 6. 消してから失敗しない

いまの「既存を置き換える」は、**削除 → 取り込み** の順で、しかも 1 件ずつ commit する
(同一トランザクションではない)。だから途中で全部はじかれても巻き戻らない。

**決定: 消す前に、取り込める行が 1 件以上あることを確かめる。**

- 入力を先に検査し、取り込み対象が 0 件なら **何も消さずに拒否する** (エラーとして返す)。
  いまは `success: true` / `imported_count: 0` を返しており、
  利用者は成功したと読む。これは「成功したように見せない」に反する。
- 0 件でない場合も、**どこまで変わったかが判別できる**ように、削除した件数・取り込んだ
  件数・除いた件数と理由を返す。

`pages` が空の入力は、いまでも削除の前に戻るので消えない (実測)。
つまり **「空なら守られるが、中身があって全部はじかれると消える」**という中途半端な形に
なっている。検査を「取り込める行の数」に統一すれば両方が同じ扱いになる。

## 7. 既に壊れてしまった記憶をどう扱うか

書き出し → 取り込みを既に踏んだペルソナには、`metadata` の無いコア記憶の行が残っている。

**合成データで残存を確認したもの**:

- **本文。** `content` はそのまま残っている。
- **番号に関する手掛かり。** 合成データではタイトルに `コア記憶 c:1` の形が残った。ただしこれは表題の文字列で、正規IDを復元できる保証ではない。

**この書き出しファイルからは復元できないもの**:

- 実会話の写しかどうかの印 (`kind`)。これが落ちると、本来書き換えから守られる記憶が
  書き換え可能な扱いに化ける。
- 利用者が確認済みかどうか (`confirmed`)。
- 呼び出し側が付けた由来の情報。

**機械が決めてはいけないもの**:

- **番号の衝突。** 取り込み先に同じ番号の記憶があると、`コア記憶 c:1` が 2 件並ぶ (実測)。
  どちらが本物かは機械には決まらない。**推測で振り直さない。**

**決定: 壊れた行を「読めない行」として黙って飛ばすのではなく、利用者に見える形で
残し、取り除く手段を与える。** いまは一覧が丸ごと落ちるので、無事な記憶まで巻き添えに
なっている。少なくとも **無事な記憶が読めること**を優先し、壊れた行は件数と本文を
利用者に示して、1 件ずつ取り除く (またはごみ箱へ入れる) 操作を提供する。

**ここは §11 の境界と隣り合うので、線を明示する。** 壊れた行を黙って飛ばして
「無事な N 件が全部です」という顔で頭へ渡すのは、fail-closed が防いでいる捏造そのもの
(本人のコア記憶を実際より少なく見せる)。だから飛ばすのではなく、
**「読めた N 件と、読めない M 件がある」を頭を組む側が知る形**にする。
そのうえで発話を止めるかどうかは、救済の実装時に決める判断として残す —
一覧が丸ごと落ちる現状 (無事な記憶まで道連れ) よりは、どちらに倒しても良くなる。

この救済は §3〜§6 の予防とは別の作業で、実装順は最後 (§9)。
**予防を先に入れないと、救済した先からまた壊れる。**

## 8. 同じ根から出ている、今回の範囲外のもの

どれも「種別を Chronicle だけで判定している」という同じ形。**一括操作を直しても残る。**
依頼書が禁じる拡張 (コア記憶の汎用の持ち出し機能、ペルソナの無効化・削除) には
触れないが、次の対象として記録する。

1. **記憶の検索にコア記憶が現れることは、欠陥ではなく当時の意図。** 想起の 3 箇所
   (`sai_memory/unified_recall.py:164-171`, `:203-208`, `:788-794`) と
   検索スペル (`saiverse/memory_atlas.py:741`) は Chronicle だけを除外していて、
   コア記憶は検索に出る。これは移行時に観察として明記されている —
   `docs/intent/concept_consolidation.md:199`「`Memopedia.search` には現れる〔**望ましい**〕」。
   **だから今回は触らない。** 削除の除外と同じ扱いにしてはいけない。
   同じ行に一括削除についての記述は無く、**検索は検討されて残され、削除は検討されていない**。
   これが「同じ形に見えて別」の境目になる。
   残る論点は、検索結果の見せ方が種別を混ぜていること (画面に `Memopedia [core]` と出る)
   だけで、それは表示の話。今回の対象ではない。
2. **物理削除が掃除し残すもの**: ページの埋め込み・編集来歴・机の上の位置。
   特に、短い参照番号 (`m:N`) は物理削除の後に**再利用される**ので、机に残った古い参照が
   別のページを指しうる (経路は確定、実害は未再現)。
3. **取り込みが運ばないもの**: 作成時刻・trunk か・重要印・キーワード・短い参照番号・
   `metadata` 全般。短い参照番号が振り直されるため、本文や会話に書かれた `m:N` がずれる。
   **書き出しは現状バックアップとして成立していない** — その明示も要る。
   **テーマもこれを踏む**: 対象に含める決め (§1.1) なので書き出し・取り込みの対象だが、
   `metadata` が運ばれないため由来の情報 (`origin` / `member_refs`) が往復で落ち、
   取り込み先に `root_theme` が無ければ親のいないページになる (実測)。
   コア記憶と違って読み取りが落ちるわけではないので緊急度は低いが、
   **「書き出しは往復で情報を失う」という同じ欠陥の一部**として扱う。
4. **手帳の一括操作だけが Metabolism と直列化されていない。**
   Chronicle の全削除は取っている (`api/routes/people/arasuji.py:874-884`)。

## 9. 実装順

1. **役割表に 1 行足し、一括操作 3 つと物理削除がそれを引く** (§3)。
   → これだけで「手帳を消してコア記憶が消える」「書き出しに混ざる」「取り込みで壊れる」が
   同時に止めることを狙う。修正後の既存テストへの影響は実装時に検証する (§10)。
2. **本人への差分通知が同じ表を引く** (§3.3 の最終行)。
   → ペルソナが自分のコア記憶を「手帳の新しいページ」として知らされなくなる。
3. **取り込みの順序と告知** (§5, §6)。
   → 取り込みのつもりが全消しになる経路が閉じ、除いた件数が利用者に見える。
4. **既に壊れた記憶の救済** (§7)。
   → 1〜3 が入った後でないと、直した先からまた壊れる。

1〜3 は同じ変更に入れてよい。4 は分けたほうが検証しやすい。

## 10. 検査

**現在、この 4 つを守っている検査は 1 件も無い** (7 通りの綴りで確認)。
一括操作を呼ぶテストは 4 本あるがコア記憶を 1 件も作らず、コア記憶を扱う 9 ファイルは
一括操作を一度も呼ばない。両側から真空だった。

調査した4本の一括操作テストが使うのは `terms` と `people` だけだった。
ただし修正後の既存テストは未実行であり、赤になる検査が無いとは確定していない。
とくに取り込みの確定単位を変える補完案は、既存の呼び出しと失敗時の挙動も検証する。

足す場所と判定は [verification.md](verification.md)。

## 11. 広げない境界

- **コア記憶の持ち出し・取り込みの機能を新しく作らない。** 運べる範囲を広げるのは器の
  新設を伴う別案件 (FLOW-13)。将来の設計は `docs/intent/memory_architecture_v2.md` §9 の領分。
- **ペルソナの無効化・削除へ広げない。** そちらは
  [別の調査](../2026-09-10_persona_removal_recovery/) で扱っている。
- **頭を組むときの fail-closed を緩めない** (§2.2)。読めないときに黙って空にする方が
  被害が大きい。
- **記憶の検索からコア記憶を外さない** (§8-1)。移行時に「望ましい」と明記された意図なので、
  削除の除外と同じ形に見えても欠陥として扱わない。
