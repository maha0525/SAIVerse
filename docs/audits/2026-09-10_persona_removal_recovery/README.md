## 0. この報告への訂正 (2026-09-10、Astra のレビューを受けて調査担当が記録)

全文は [astra_review.md](astra_review.md)。**README を単体で読む人が誤解しないよう、
言い過ぎだった箇所をここに引いておく。**

1. **§2 の「記憶が読める条件は ID が変わらないことただ一つ」は言い過ぎ。**
   同じ報告の実験 3 が反例を出している — 別 ID への JSON 移植でも会話は読める。
   正しくは「**ID と既存の状態を保つ案なら、移し替えに伴う欠落を避けられる**」の範囲。
2. **§3 の比較表で無効化を「完全に使える」と書いたのは、証拠より強い。**
   無効化の機構は存在しないので、これは実験 1・5 からの**推論**であって実測ではない。
   停止から復帰までを通した検証はしていない。
3. **§5 の「休ませるがその役割を完全に代替する」も同じく強い。**
   「利用者が記憶を残したい理由は実質また話すかもしれないから」という読みは、
   調査担当の解釈であって、確かめた事実ではない。
4. **§3 の「起動時にロードしない方式は採ってはいけない」は、設計上の必然ではない。**
   実測が示したのは「配送側が無効を知らないまま読み込みを止めると失敗し続ける」こと。
   **配送側も無効の状態を理解する方式なら、比較の対象になる。**
5. **§5 の画面案の文言が、§6 の推奨と矛盾している。**
   画面に「戻せません」と書きながら、§6 でバックアップを残す (= 復元できる) ことを推した。
   バックアップの範囲と戻し方を決めるまで、この文言は確定できない。
6. **§6 の共有記録について、「全件保存が裁定済み」とまでは言えない。**
   2026-08-25 の裁定が直接に禁じたのは、**誰かが記憶へ転記済みのユーザー発言の取り下げ**。
   削除されたペルソナの発言へ理由を広げるのは筋が通るが、**まだ誰も読んでいない発言まで
   含めて裁定済み、とは言えない。** 削除時に残す共有記録は仕様として明記する必要がある。
7. **findings.md の「手帳の往復でペルソナが喋れなくなる」も強すぎる。**
   発話の準備には、既にある控えを据え置く逃げ道がある。**控えが無いときに止まる**が、
   例外の再現から実際の発話停止までを一続きで実測してはいない。

**再現コードは [repro/](repro/) に置いた** (当初は一時領域にあり、失われる状態だった)。
2026-09-10 に `probe_env.py` からセッション固有のパスを外して再実行を確認済み。

## 1. まはーの質問への直接の回答

> 新規ペルソナを作って memory.db だけ差し替えれば動くか。

**動かない。ただし「動かない」の形が、予想より悪い。**

隔離環境で実際にやってみた結果 ([experiments.md](experiments.md) 実験 2)。
ペルソナ A の memory.db をペルソナ B のフォルダに置いて、B として読み出した:

| B から読もうとしたもの | 結果 |
|---|---|
| 会話の続き (自分のスレッド) | **0 件** |
| 建物での会話履歴 | **0 件** |
| 意味検索での想起 | **A のメッセージが返る** |
| 自動想起 (会話中に働く芯) | **A のメッセージが返る** |
| コア記憶 | **A のものが返る** |
| 手帳のページ | **A のものが返る** |

**B は A の記憶を自分のものとして思い出して喋るのに、会話の続きだけが無い。**

理由は二つの読み方が混ざっているから。会話を続ける経路は、必ず
`f"{persona_id}:{suffix}"` という名前でスレッドを組み立てて探す
(`saiverse_memory/adapter.py:2038`)。B が探すのは `probe_b_...:__persona__` で、
DB の中身は `probe_a_...:__persona__` なので一件も当たらない。

一方、想起の経路は持ち主で絞っていない。`saiverse_memory/adapter.py:1699-1701` に
コメント付きでこう書いてある:

```python
# Disable both thread_id and resource_id filters to search across all threads
search_thread_id = None
search_resource_id = None
```

**これは欠陥ではない。** この設計は「この memory.db はこのペルソナのものである」という
前提の上に立っていて、その前提があるから持ち主で絞る必要が無い。
ファイルを差し替える操作は、その前提を音も立てずに壊す。

コア記憶と手帳はさらに直接的で、これらを保存している `memopedia_pages` には
**持ち主の欄がそもそも無い**。DB を置き換えた瞬間に丸ごと B のものになる。

**証拠の範囲**: 隔離した `SAIVERSE_HOME` と合成ペルソナで、製品と同じ読み書きの関数を
呼んだ実測。本番のペルソナ・データには触れていない。本番規模のデータ量では試していない。

## 2. では何なら成立するのか — 実測でわかった唯一の条件

**記憶が読める条件は「ペルソナ ID が変わらないこと」ただ一つだった。**

対照実験として、開発用の `scripts/clone_persona_to_test_env.py` を合成環境で走らせた
(実験 5)。**ID を変えずにフォルダごと写したら、記憶は完全に読めた** — 会話の続きも、
コア記憶も、開いていたスレッドまで戻った。

この一点が、三つの経路すべての優劣を決めている。

## 3. 三つの経路の比較

### 経路 1: 記憶を残して削除し、後で再利用する

Astra が提案した形。**現状では、残した記憶を使う道がどれも成立しない。**

- **利用者の操作**: 削除するとき「記憶を残す」を選ぶ。後日、新しいペルソナへ載せる。
- **残るもの**: `~/.saiverse/personas/<id>/` のすべて (memory.db 含む) と、
  main DB の 25 テーブルの行。
- **後でできること**: 現状では**ほぼ何もできない**。三つの道を全部試した結果:
  - **memory.db を置くだけ** → 半分だけ動く (上の §1)。
  - **JSON で書き出して移植** → 会話の続きは成立するが、**10 個のテーブルが落ちる**
    (実験 3)。落ちるのは `memopedia_pages` (**コア記憶・手帳・Chronicle の本体**)、
    `clips`、`purpose_tags`、`memory_notes`、`desk_items`、`perception_buffer`、
    `pulse_logs`、`sluice_skipped_spans`、`working_memory`、`memopedia_page_edit_history`。
    書き出しの形式が持てる箱が `threads` / `messages` / `stelis_threads` の三つしかなく、
    残り 28 テーブルには対応する欄が無い。**これは「会話の書き起こしの引っ越し」であって
    「記憶の引っ越し」ではない。**
  - **同じ ID で作り直す** → §4 のとおり別の問題が起きる。
- **必要な変更**:
  - (追加実装) 会話以外の記憶を運ぶ器を、書き出しの形式に足す
  - (追加実装) 削除されたペルソナの記憶を画面から見つける入口。現状は
    スレッド一覧が 404 を返すので**画面からは辿り着けない** (実験 4)。
    取り込みは `ensure_persona_exists` で塞がれている (`api/routes/people/utils.py:69`)
  - (追加実装) 別 ID へ移すときの持ち主の付け替え。移植の機構自体は既にあるが
    (`saiverse_memory/native_export.py:333`)、**画面から呼ぶ手段が無い**
- **未確定事項**: 移した記憶を、移された側のペルソナが「自分の記憶」として扱うのか、
  「他人から受け取った記録」として扱うのか。これは設計倫理の判断で、実装より先に要る。

### 経路 2: 無効化して、同じペルソナを再有効化する

まはーが挙げた代案。**構造にいちばん合っている。**

- **利用者の操作**: 「休ませる」を選ぶ。後日「戻す」を選ぶ。
- **残るもの**: すべて。ID も動かない。
- **後でできること**: **記憶は完全に読める** (ID が変わらないので)。
- **必要な変更**:
  - (既存) ペルソナを起こす経路は `saiverse/pulse_dispatcher.py` の 4 つのメソッドに
    集約されている。製品コードから呼ぶのは 5 か所だけ
    (`manager/runtime.py:627,833` / `saiverse/schedule_manager.py:1176` /
    `builtin_data/phenomena/inject_persona_event.py:152` /
    `saiverse/autonomy_manager.py:328`)。**ここに関所を置けば「喋り出す」系はまとめて塞がる。**
  - (追加実装) 状態を持つ列が要る。**既存のフラグは流用できない**:
    `AUTONOMY_ENABLED` は自律だけを止めて会話もアラームも止めない
    (まはーが 2026-09-10 に正常挙動として確定済み)。`IS_DISPATCHED` は
    都市間移動の凍結で True になれず、拒否条件として死んでいる。
  - (追加実装) `pulse_dispatcher` を通らない 4 つを別に塞ぐ:
    先回り編纂 (`sea/session_lifecycle.py:4320`、独立したスレッドで LLM を呼ぶ)、
    フィード配送、実行台帳の配送、起動時のアップグレード通知。
  - **やってはいけないこと**: 「起動時にロードしない」で無効化を実装すること。
    実験で、アラームが `"persona not found"` で失敗して再試行ループに入るのを観測した。
    削除で既に起きている症状を、意図的に作ることになる。
- **未確定事項**: 休んでいる間に来るはずだった予定・アラームを、戻したときどう扱うか
  (無かったことにするか、まとめて実行するか)。**まはーの判断が要る** (§6)。

### 経路 3: 完全削除する

- **利用者の操作**: 「完全に消す」を選ぶ。
- **今の実装が消すもの**: `ai` 行と `task_book` の 2 つだけ。
- **今の実装が残すもの** (実験 1 で数えた): main DB の **25 テーブル**の行
  (`persona_schedule` を含む) / 私室の Building / ペルソナのフォルダ全部。
  さらに記憶のバックアップは `~/.saiverse/backups/` にあるので、
  フォルダを消しても記憶は残る。
- **必要な変更**: (追加実装) 25 テーブル + Building + フォルダの後始末。
- **未確定事項**: **共有された建物の会話に残る、その人の発言をどうするか。**
  ただしこれは §6 のとおり、既存の裁定でほぼ答えが出ている。

### まとめ

| | 記憶は後で使えるか | 実装の重さ | まはーが決めることの数 |
|---|---|---|---|
| 記憶を残して削除 | **今はほぼ使えない** | 器の新設・画面の新設が要る | 多い (移した記憶の名義まで) |
| 無効化・再有効化 | **完全に使える** | 関所 5 + 別経路 4 + 状態列 1 | 少ない (休止中の予定の扱い) |
| 完全削除 | 使えない (それが目的) | 後始末 25 テーブル + α | 少ない (共有記録は裁定済み) |

**まはーの「完全削除か無効化・再有効化の方が軽い」という見立ては、実測で裏付けられた。**
ただし「軽い」の中身は作業量ではなく、**決めなければならないことの少なさ**だった。

## 4. 「同じ ID で作り直す」を復旧手段に使えない理由

一見すると、削除しても `~/.saiverse/personas/<id>/` は残るので、同じ ID で作り直せば
記憶が戻るように見える。実際、実験で**戻った**。だが復旧手段としては使えない。

**確かめた事実 (実験 1)**:

1. **同じ名前では作り直せない。** 削除しても私室の Building が残るので、
   同じ名前で作ると部屋の名前がぶつかって落ちる。実際に出たエラーは
   `UNIQUE constraint failed: building.CITYID, building.BUILDINGNAME`
   (制約は `database/models.py:226`)。**「ミラを消して、後でミラを戻したい」が、
   そのままでは通らない。**
2. **同じ ID・違う名前なら作り直せる。** ID の重複検査は `ai` テーブルだけを見るので、
   行が消えていれば ID は空く。
3. **そのとき、削除したはずのものが黙って戻る。** 残っていた 25 テーブルの行が
   そのまま新しいペルソナに再結合した。**起床・就寝のアラームも戻る。**
   予定表・エピソード・タスク・カーソル・アドオン設定も同じ。
4. **人格の設定だけは戻らない。** `ai` 行の中身 (システムプロンプト・モデル・役割) は
   新規作成の既定値になる。**「記憶とアラームは戻るのに、人格の設定は初期化される」**
   という組み合わせになる。
5. **私室が二重になる。** 古い部屋が残ったまま、`persona_1_testcity_room` のような
   ペルソナ ID と対応しない名前の新しい部屋ができる。

そもそも**画面から ID を指定してペルソナを作る手段が無い**。
API (`api/routes/world.py:120-124`) は `ai_id` を受け取るが、
ワールドエディタの作成処理 (`WorldEditor.tsx:392`) はそれを送っていない。

## 5. 推奨する削除画面 — 二択にする

**「休ませる」と「完全に消す」の二択を推す。「記憶を残して削除」を選択肢に出さない。**

### 案

```
ミラ を、どうしますか

  ○ 休ませる
      活動を止めます。話しかけても返事をしません。アラームも鳴りません。
      記憶・持ち物・部屋はそのまま残り、いつでも戻せます。

  ○ 完全に消す
      ミラ に関するものを、すべて消します。
      記憶も、書いたものも、戻せません。
      ミラ が他のペルソナと話した記録は、聞いた人の記憶に残るため消しません。

      [ 消す前に、会話の記録を書き出す ]     ← 任意

                                    [ やめる ]  [ 決定 ]
```

### この形を推す理由

**「記憶を残して削除」を出さないのが、この案の芯。**
出してしまうと、残した記憶を後で使う道が現状どこにも無いのに、
利用者には「残した」と告げることになる。§1 と §3 で見たとおり、
差し替えは半分しか動かず、JSON はコア記憶と手帳を落とし、
画面からは削除後の記憶に辿り着けない。**守れない約束を画面に書かない。**

**「休ませる」がその役割を完全に代替する。** 利用者が「記憶を残したい」と思う場面は、
実質「またこの子と話すかもしれない」だと私は考える。それなら休ませる方が確実で、
しかも ID が動かないので記憶が完全に読める。

**「完全に消す」に、消さないものを一行で書く。** 建物の会話に残る発言を消さない理由は、
まはーが 2026-08-25 に既に裁定している (§6)。その理由を利用者にもそのまま伝える。

**書き出しは任意のボタンにする。** 必須にすると、急いで消したい人の邪魔になる。
ボタンの文言を「会話の記録」に限定するのは、実際に会話しか運べないから
(コア記憶と手帳は落ちる)。**運べないものを運べるように見せない。**

## 6. まはーの判断が要る点 (2 件に絞った)

依頼書は「まはーに残る判断を絞る」ことを求めていた。調査の結果、**3 件のうち 1 件は
既存の裁定で解けた**ので、残りは 2 件。

### 解けたもの: 共有された建物の会話に残る発言をどうするか

**まはーが 2026-08-25 に既に裁定している。** `database/building_messages.py:834-838` に、
建物の記録から行を消す唯一の経路の条件として、こう書いてある:

> `ingested_by` が空であること — 一人でも記憶へ転記していたら消さない。
> 消すと、そのペルソナは「聞いた覚えがあるのに記録が無い」状態になり、
> 無言で消えるより悪い (2026-08-25 まはー裁定)

**この理由は、ペルソナ削除にそのまま当てはまる。** 誰かが聞いて記憶に写した発言を
後から消せば、その誰かは「聞いた覚えがあるのに記録が無い」状態になる。
消した相手が削除されたペルソナかどうかで、この理由は変わらない。
したがって**新しい判断を仰ぐ話ではなく、既存の裁定の適用**として扱えると私は考える。

まはーに確認してほしいのは「この裁定をペルソナ削除にも適用してよいか」の一点だけ。

### 判断 1: 休ませている間に来るはずだった予定を、戻したときどうするか

- **材料**: アラーム・起床就寝・時間割は、休止中も行が残る。戻したときに
  「無かったことにする」「まとめて実行する」「次の分から再開する」が選べる。
- **私の推し**: **次の分から再開する。** まとめて実行は、半年休ませたペルソナを戻した
  瞬間に半年ぶんが走ることになり、費用の面でも体験の面でも良くない。

### 判断 2: 「完全に消す」を、どこまで本当に消すか

- **材料**: 今は 25 テーブル + Building + フォルダが残る。全部消す実装は書けるが、
  記憶のバックアップ (`~/.saiverse/backups/`) をどうするかは別の判断になる。
  バックアップまで消すと、操作ミスからの復旧手段が消える。
- **私の推し**: **バックアップは消さない。** 「完全に消す」の説明文に
  「バックアップからの復旧は、しばらくの間は可能です」と書く方が誠実だと考える。

## 7. 調べ残しと限界

- **無効化・再有効化の機構そのものは実験していない。** 機構が存在しないので、
  実験の対象が無い。経路 2 の評価は、実験 1・5 が示した「ID が動かなければ記憶は読める」
  という事実からの帰結として書いた。
- **本物の `PersonaCore` を通した作成・削除は実験していない** (実験 1 はスタブ)。
  ペルソナ登録の中で起きること、移動、Pulse の再開は未検証。
- **画面 (フロントエンド) を操作していない。** 画面の話はすべてソースの読み。
- **本番規模のデータで試していない。** 合成データは各 1〜5 件。
- 入口の網羅性は保証していない。アドオン (X 以外)、フェノメノンのルールの条件、
  Discord ゲートウェイの応答者選定は追えていない。
- 本番ペルソナ・本番データに触れていない。LLM を呼んでいない。
  製品コード・テスト・CI・既存文書を一行も変更していない。
