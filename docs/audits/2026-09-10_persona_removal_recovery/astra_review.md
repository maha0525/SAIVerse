# Astra レビュー — 削除方式を選ぶための証拠と未検証範囲

2026-09-10。README / findings / experiments 全文を読み、Memopedia の書き出し・コア記憶の読み取り・head capture・建物発言の取り下げのソースを限定確認した。実験は再実行していない。以下はレビュー判断であり、まはーによる方式の採用決定ではない。

## 方式への判断

「無効化して同じペルソナを戻す」と「削除する」の二つを具体化する方針を推す。DB の直接差し替えでは読み出し経路間の不一致が実測され、JSON 移植では会話が移る一方、コア記憶・手帳等が運ばれなかった。今の機構をそのまま使って「削除後も記憶を戻せる」と利用者に約束する根拠はない。

無効化案の利点は、同じ ID・設定・記憶・関連データを保持でき、復帰時の再作成や移植を避けられること。停止から復帰までの機能は未実装・未検証であり、報告の「完全に使える」「休ませるが完全に代替する」は現時点の証拠より強い。利用者が記憶を残したい理由が常に再会である、という説明も調査担当の解釈である。

## 報告を使う際の訂正・制約

- 「記憶が読める唯一の条件は ID 不変」は一般化しすぎ。実験 3 自身が別 ID への JSON 移植で会話を読めることを示している。今回の比較で必要なのは、ID と既存状態を維持する案なら移植に伴う欠落を避けられる、という範囲。
- 同一 ID のクローン実験も、少数の会話・コア記憶・現在スレッドを確かめたもの。全記憶の完全性や活動の再開は検証していない。私室参照が null になったことも実験本文にある。
- 「起動時にロードしない方式は禁止」は設計上の必然ではない。既存スケジューラが不在ペルソナを失敗・再試行にすることは根拠になるが、明示的な無効状態を配送側も理解する方式は比較対象にできる。配置するチェックの個数を完全性の証拠にしない。
- 実験スクリプト・生 JSON は成果物に含まれず、コマンドのパスも一時領域のプレースホルダ。実行結果の報告として読めるが、そのまま再実行できる証拠一式ではない。後続実装時に必要な再現コードと合成入力を永続する検証資産として残す。
- 「完全に消す」の画面案は「戻せない」と言い、後段ではバックアップを残して復元可能と説明する案になっている。バックアップの範囲・復元経路を決めるまで文言を確定しない。main DB 全体のバックアップ内の当人のデータと、ペルソナ別記憶バックアップを区別する必要がある。
- 共有記録を保つ既存判断の根拠は、聞かれたユーザー発言の取り下げ禁止というソースコメント。削除された本人の共有記録へ理由を適用するのは筋が通るが、未読の発言も含めて全件保存が裁定済み、とまでは言えない。削除時に残す共有記録を仕様に明記する。

## 別途正常化へ渡す問題

findings C の Memopedia 往復で metadata が失われる問題は、削除方式に関係なく修正対象として優先して扱う候補。現行 export は category 等を出すが metadata を出さず、head の CoreMemorySection は list_core_memories の例外を上位へ送ることを確認した。

ただし「往復すると必ず発話不能」は強すぎる。head のコメントでは既存 snapshot があれば据え置き、なければ required 欠損で LLM を止める。報告の例外再現から製品の発話停止までを一続きに実測した証拠は提示されていない。隔離された往復→コア記憶読み取り→head 構築の再現で条件を確定し、metadata の保存・復元を直す場所と既に壊れたデータの扱いを検討する。

## 次の順序

まず無効化・削除という方式をまはーと決める。その後、無効化中の予定・外部イベント・実行中処理と、削除対象・共有記録・バックアップの扱いを具体化する。Opus には採用方式の実装・隔離検証を渡し、停止・再起動・再有効化・会話再開の一続きで評価する。
