## 2026-09-09: 凍結中の連携は、既存の有効設定があっても起動しない

### 判断の対象

### 決まった正常挙動

凍結中は、通常の製品起動でこれらの待ち受け・子プロセス・外部登録やその維持処理を始めない。既存設定が有効でも起動の例外を設けない。単に既定値を無効へ変え、有効設定なら動く形にはしない。

### この決定で変えない範囲

この判断は、コードや保存済み設定・データの削除、Discord・スマホ利用など提供中の外部アクセスの停止を決定するものではない。実装時は凍結対象の起動経路と終了処理の接点を確認する。

### 確認すべき結果

- 設定なし・有効・無効のいずれでも、凍結対象の起動・待ち受け・登録要求が発生しない。
- 凍結した子プロセスのためのポート解放処理も実行されず、他プロセスを終了しない。
- 凍結対象が起動しない状態で、提供中の機能の起動・終了が成立する。

これは期待する挙動の確定。実装と検証は未実施。

## 2026-09-10: 自律行動と別にキャッシュ維持を選べる方向。ただし活動に含まれる維持と追加呼び出しを分かりやすく伝える

### まはーの回答原文

> うーん……選択肢としてはできたほうがまぁいいかなぁ。見せ方ちゃんと分かりやすくできればそれでいい。自律行動を行う場合はキャッシュの維持は追加の課金なく自律行動に含まれる形で行われるというのは中々伝わりにくい部分だから。

### 回答の範囲

FLOW-20 / FLOW-24: 自律 OFF でも利用者がキャッシュ維持を選べる方向に賛成。分かりやすい見せ方が条件。自律行動そのものに伴って行われるキャッシュ維持と、維持のために別途呼び出す処理・費用の区別を、利用者が理解できるようにする。文言・既定値・移行の具体案まで承認されたとは扱わない。

### 限定した実装確認と、表示案

`sea/session_lifecycle.py:1655` 以降では、成功した呼び出しによって anchor が更新されると、同じペルソナ・モデルの維持予約を置き換える。`schedule_cache_ttl_pulse` は `keep_cache_alive=False` なら専用予約を取り消し、それ以外では TTL 接近時に `run_cache_keepalive` を呼ぶ。`sea/runtime.py:2145` 以降の専用処理は `generate` を呼び、usage を `cache_keepalive` として記録する。したがって、通常の活動に伴う更新と維持専用の追加呼び出しをコード上でも区別できる。一方、自律 ON の設定だけで専用呼び出しが常に不要になるわけではない。活動の間隔・使用モデルによって専用予約が発火する余地がある。課金の実測・自律駆動全体の検証は行っていない。

Astra の表示案（相談用、未承認）: 単なる「キャッシュ維持 ON/OFF」ではなく、次の二つの選択として示す。

- **活動に合わせる**: 会話や自律行動の呼び出しに伴ってキャッシュを更新する。維持専用の呼び出しは追加しない。活動の間が空けば失効しうる。
- **待機中も維持する**: 会話や自律行動の間が空いたときも、維持専用の呼び出しを追加する。その呼び出し分の API 費用が生じる。

これは対応するキャッシュ方式の設定案。プロバイダのキャッシュ保持そのものを無料と約束する表示にはしない。また「活動に合わせる」を選んでも、会話・自律行動のキャッシュ利用まで無効にする意味ではない。既存の自律凍結を解除する決定でもない。

## 2026-09-12: チャット画面のモデル指定は、その部屋のユーザー入力への応答に限る

### まはーの回答原文

### 正常挙動への反映

FLOW-04 / FLOW-01 / FLOW-21: チャット画面のモデル指定は、指定した部屋で、ユーザー入力に応じて発話する場合に適用する。同じ部屋であってもアラーム等による発話には適用しない。別の部屋のモデル指定にも波及させない。Astra が直前に提案した「部屋に限定」へ、まはーが「ユーザー入力への応答に限定」という条件を加えた判断。

例: 部屋 A のチャット画面でモデル X を選び、ユーザーが話しかけると、その応答には X を使う。部屋 A または B のアラーム発話は、チャット画面の X に上書きされず、アラーム等の経路に定めたモデル解決に従う。部屋 B のユーザー入力には、部屋 B 側の指定を使う。

### 正常化時に確かめる境界

既存の `manager.set_model` による全ペルソナの可変モデル更新は、この範囲を満たさない。読み取りプレビューと実際の応答が同じ対象・モデルを解決することも、既存のプレビューの約束に沿って確認する。

限定した追加ソース確認: `saiverse/schedule_manager.py` は `dispatch_schedule_fire` を呼び、`saiverse/pulse_dispatcher.py` の同関数は `ExecutionRequest(type="schedule")` を作る。`sea/pulse_context.py:99` の `aspect_from_pulse_type` は user と schedule をどちらも CONVERSATION とし、同ファイルの `resolve_execution_context` は standard tier を `persona.model` から解決する。したがって CONVERSATION かどうかだけでは、今回の適用範囲を区別できない。起点がユーザー入力かを保持してモデルを選ぶ必要がある。これはソース上の確認であり、本番や隔離環境での挙動検証は未実施。

ユーザーへの応答中に呼ぶ分身・ツール内部処理まで一律に同じモデルへ変える合意ではない。再送・続きの生成・他の入力経路は、元の応答との関係と指定の受け渡しを正常化時に追跡する。個別のモデル切替経路を調べずに、全ての LLM 呼び出しへ指定を広げない。
