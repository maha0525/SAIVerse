# 判断の整理 (decisions)

調査日 2026-09-09 / 対象コミット `25ad75d6` / 流れの本文は [flows.md](flows.md) / 要約は [README.md](README.md)

## これは何

32 本の流れを書く過程で出た「決まっていないこと」を、次の 3 つに分けて整理した文書。
**質問として混ぜていない。**

- **第 1 部: まはーの判断が要る議題** — 既存の決定からは答えが出ず、方針の選択が要るもの。
- **第 2 部: 既存資料から解決できたもの** — 一見未合意に見えて、既存の決定・仕様・issue で答えが出るもの。
  **これらをまはーに決め直させない。**
- **第 3 部: 追加調査で確認すべきもの** — 根拠がありそうだが確かめていないもの。
  **ユーザー判断へ転嫁しない。** 有無が確定するまで議題にしない。

議題は、複数の流れに同じ判断が現れるものを一つに束ねてある。ただし**動機が同じだけで
同じ結論を強制していない** — 操作の副作用や既存の同意が違えば、適切な扱いも違いうる。
その違いが重要な箇所には、束ねた中の差異を明記した。

# 第 1 部: まはーの判断が要る議題

## 議題 1: 意図的に配線していない機能の理由を、どこに、どう書くか

**対象**: `FLOW-15` (Region) / `FLOW-17` (Fixture・Observer) / `FLOW-18` (ゲーム) /
`FLOW-12` (Memopedia の整理) / `FLOW-13` (経験の台帳・7 層ストレージ) / `FLOW-24` (保温・先回りの畳み)

**既存の根拠**: まはー本人が課題として立てている。原文 (2026-09-09):
> 「regionとゲーム、FixtureとObserver、この辺は0.4.0以降のリリースにするために意図的に配線を繋いでない。
> ただ、何も書かれてないのは今みたいに混乱を招くから問題だね。」

**まだ決まらない理由**: 書く場所の候補が複数あり、対象によって適する場所が違う。
コード内のコメント / `docs/intent/` / `roadmap_status.md` / 利用者向け文書 / 画面上の表示。
さらに、**対象が一様ではない**ことが今回分かった —

- Fixture は**一部が既に届いている** (RSS のフィード施設)。未配線なのは汎用 API と Observer の口だけ。
  「Fixture 未実装」と書くと事実に反する。
- ゲームは「見る・戻る」が完成していて「始める」だけが無い。
- 保温と先回りの畳みは、v0.3 の止め具の一覧の**どちらの側にも書かれていない** (止めるとも止めないとも)。

**選択肢による利用上の違い**: 利用者向け文書に書くと「今できないこと」が利用者に伝わるが、
未完成の印象が広がる。コード内だけに書くと利用者の混乱は残る (Fixture では実際に、
利用者向け文書 2 件が使えない機能を案内している)。

**調査担当案 (理由つき)**: リポジトリ内に前例が 2 つあり、私は後者を標準にすることを推す。
1. 凍結の書き方 (`roadmap_status.md` §8 + `landscape.md` §8 + 入口の明示的封鎖 + 検査での固定)
2. `builtin_data/tools/observer_read.py:85-91` の 3 行 — **現状・理由・復帰条件**を並べる形

理由: 3 行の形は「意図か欠陥か」を次に読む人が判別できる最小の情報を持ち、書く場所を選ばない
(コードにも intent にも同じ 3 点を置ける)。今回の調査で担当が判別できなかったのは、
まさにこの 3 点が無かったため。

## 議題 2: 機構が使った数字を、利用者にどう申告するか

**対象**: `FLOW-04` (プレビューの費用・送信量) / `FLOW-08` (束ねの残り回数) /
`FLOW-09` (スルースが飛ばした範囲) / `FLOW-16`・`FLOW-18` (操作が LLM 課金を伴うことの事前告知)

**既存の根拠**: 事故 2 件がどちらもこの形。承認した回数と実際に生まれた本数、
読み戻しが開いた量とスルースへ渡した量。どちらも**両側に検査があり、突き合わせだけが無かった**。

**まだ決まらない理由**: 「突き合わせる」ことは事故から明らかだが、**どこに出すか**が決まっていない。
完了文 / 診断レポート / 画面のバナー / 送信前のプレビュー。出し先によって、
気づく人 (利用者かペルソナか) と気づく時点 (事前か事後か) が変わる。

**束ねた中の差異**:
- `FLOW-08` の束ねの残り回数は、**判定材料が実行時に既に計算されている** (`band_plan_count`)。
  出す先を決めれば実装は小さい。
- `FLOW-09` の飛ばした範囲は、**intent が意識的に第二段の UI へ送っている**。未合意ではなく未着手。
- `FLOW-16`・`FLOW-18` の事前告知は、会話側の Chronicle 確認ダイアログ (`CHAT-19`) と同じ問い。
  こちらは確認ダイアログの既定の議題 (議題 5) とも絡む。

## 議題 3: 機構が書いたもの・消したもの・失ったものを、ペルソナと利用者にどう知らせるか

**対象**: `FLOW-11` (記憶の訂正の通知) / `FLOW-14`・`FLOW-17` (建物ログの聴衆) /
`FLOW-26` (終了時に失われた発言) / `FLOW-09`・`FLOW-10` (想起にシステム通知を含めるか)

**これは SAIVerse の設計倫理に直接触れる議題**なので、機械的な統一で決めない。

**既存の根拠**: コア記憶側には明文がある — 「黙って書き換えず、本人が気づける形にして自己像の尊厳を保つ」。
通知の作法も正しく実装されている (`role="user"` + `<system>` 包み。機構の代筆を本人名義にしていない)。

**まだ決まらない理由**: **同じ扱いが正しいとは限らない**のに、その区別がどの intent にも書かれていない。
- コア記憶は**本人の言葉が入る器**。あらすじ・Memopedia は**機構が書いた要約**。器の性格が違う。
- 現状、ペルソナへ通知するのはコア記憶だけ。あらすじ・Memopedia・生ログの編集や削除には
  通知が一切無い (`push_perception` の grep が 0 件)。**意図的な区別か、隣を忘れたかは静的に決められない。**
- 建物ログの行は「誰が聞いたか」に名前がある行だけがペルソナの記憶へ写る。
  その名簿を**世界が算出するのか、書き手が申告するのか**が決まっていない
  (`add_building_event` の既定は空リストで、渡す書き手と渡さない書き手が同居している)。
- 終了時に消えた発言は、`backend.log` の警告 1 行にしか残らない。3 ヶ月で 32 件の記録がある。
  建物の記録に置けばペルソナの記憶へ写るので、**機構の失敗をペルソナに読ませてよいか**という判断になる。

**選択肢による利用上の違い**: 通知を増やすとペルソナの記憶が機構の事務連絡で埋まる。
通知しないと、ペルソナは自分の記憶が変わったこと・自分の発話が失われたことを知らないまま続く。

**調査担当案**: 私はまず「器の性格による区別」を一文で決めることを推す — 例えば
「本人の言葉の器を触ったときは知らせ、機構が書いた要約を触ったときは知らせない」。
一文が決まれば、上の 4 つは個別に決めなくてもほぼ導出できる。ただし
`FLOW-26` (失われた発話) はこの一文の外にあり、別に決める必要がある。

## 議題 4: 自律行動の境界 — 利用者が仕掛けたアラームは「自律」に含まれるか

**2026-09-10 解決済み**: まはーが「自律 OFF でも設定済みアラームは動く。確認済みの現状でよい」と再確認した。[判断原文と正常挙動](owner_decisions.md) を参照。以下は相談前の初稿を経緯として残したもの。

**対象**: `FLOW-20` (自律の ON/OFF) / `FLOW-21` (アラーム) / `FLOW-24` (画面のない処理全体)

**既存の根拠**: **まはーが既にこの問いを立てている。** `docs/intent/autonomous_behavior_v3.md:154`、
2026-08-19 の方針に「自律行動はさせたくないがアラームだけは設定したい」が **v0.4 の未決**として記録されている。

**現状 (今回確定した事実)**: 実装は「常に鳴る」に倒れている。アラームの実行経路 5 段のどこにも
自律のゲートが無く、v0.3 の止め具にも `AUTONOMY_ENABLED=False` にも止められず、LLM 課金が発生する。
一方、同じく費用の出るキャッシュ保温は `AUTONOMY_ENABLED` で止まる。
**費用の出る 2 つの自動処理が、同じ設定に逆の反応をしている。** この非対称は
`autonomous_behavior_v3.md` §11.1 の「止めるもの / 止めないもの」のどちらの一覧にも書かれていない。

**まだ決まらない理由**: 決定の帰結が既存の欠陥と絡む。「自律 OFF なら鳴らない」を選ぶと、
開発者モードを OFF にしたとき全ペルソナの自律が一括で False になる既知の欠陥
(`docs/issues/developer_mode_off_mass_disables_autonomy.md`、裁定待ち) と組み合わさり、
**利用者が知らないうちにアラームが全部止まる**に化ける。

**選択肢による利用上の違い**:
- 「鳴る」を選ぶ → 現状維持。ただし「自律行動 / 有効（自分から考えて動く）」というスイッチの
  ラベルと実際の効果が食い違ったままになる (v0.3 でこのスイッチが実際に変えるのは保温だけ)。
- 「鳴らない」を選ぶ → 上の欠陥を先に直す必要がある。
- 「アラームは自律とは別の設定にする」→ 画面に設定が増える。

## 議題 5: 確認を出す相手がいないときの既定

**2026-09-10 相談結果**: 一律の yes/no は設けず、各機能の利用場面・操作負担・実装を含めてケースごとに判断する。[まはーの回答原文](owner_decisions.md) を参照。以下の分類のみを根拠に確認動作を統一しない。

**対象**: `FLOW-05` (Playbook 権限 / スペル / あらすじ生成の 3 つの確認ダイアログ)

**現状**: 同じ状況に対して結論が三方向に割れている。
- Playbook を動かす権限 → **拒否**して止まる
- あらすじの生成 → **確認せずに飛ばす**
- 世界に変化を起こすスペル → **自動で承認して実行する**

三つとも、コード内の説明文には同じ動機 (「画面が無いときに止めてしまわないため」) が書いてある。

**まだ決まらない理由**: **動機が同じでも前提が違う**ので、同じ結論を強制できない。担当が挙げた 3 つの差:
1. **副作用の向き** — あらすじは後で編纂し直せるので、飛ばしても失うものが無い。スペルは違う。
2. **既存の同意の有無** — 自律実行 (`auto_mode`) を「事前の同意」と読めるかどうか。
3. **取り消しの効き方** — 外部サービスを叩くスペルだけは、実行後に取り消せない。

**判断材料**: **スペル確認だけが「実行する」側に倒れており、かつ設計文書が見つからない**
(期待の根拠が実装のみ)。他の 2 つには根拠がある。

## 議題 6: 失う操作の作法 — 何が残り、何が見え、何を選べるか

**2026-09-10 ペルソナ管理の方式を確定**: 追加調査後、まはーが「無効化して同じ本人として戻す／削除する」の二本立てを承認した。[決定記録](owner_decisions.md) を参照。予定・イベント、削除対象やバックアップの詳細は引き続き具体化する。他の削除操作にはこの承認を拡張しない。

**対象**: `FLOW-15` (部屋を消す) / `FLOW-16` (アイテムを消す) / `FLOW-23` (ペルソナを消す) /
`FLOW-29` (アドオンのデータを消す) / `FLOW-31` (DB の初期化)

**既存の根拠**: まはーの原則「止めるのではなく、記録し、明示し、選択してもらう」。
**ただしこの原則から個々の挙動は自動的には決まらない。**

**現状の分布** (担当が「記録・明示・選択」の 3 つで測った結果):
- アドオンのデータ削除と DB の初期化は、**「明示」と「選択」は満たしていて「記録」だけが無い** (控えが残らない)。
- ペルソナの削除は、3 つとも薄い。警告は 1 行の確認だけで、残るもの
  (memory.db・スケジュール・イベント記録・私室) の説明が無い。
- 部屋とアイテムの削除は、消えた後に何が壊れるか (会話ログの行き場、死んだ参照) が示されない。

**まだ決まらない理由**: 操作ごとに「取り返しのつかなさ」が違う。ペルソナの記憶を消すことと、
アドオンのトークンを消すことは、同じ重さではない。

**調査担当案**: 私は**ペルソナの削除だけ先に決める**ことを推す。理由は、失うものの重さが他と桁違いで、
かつ現状「消えないものが多い」ために残骸が動き続ける (孤児のアラームが起動のたびに失敗する) から。
なお、消えるものが散在している事実自体は `docs/issues/persona_memory_not_self_contained.md` に
まはーの指摘として既に起票済み。

## 議題 7: 外部に何を開くか

**対象**: `FLOW-30` (Unity / LAN 公開 / Discord / SDS) / `FLOW-31` (ループバック起動の API)

**既存の根拠**: Unity についてはまはーが対処の意向を示している。原文 (2026-09-09):
> 「Unity用のポートヤバいな……。今Unity連携完全に凍結してる状態だし、対処しておいた方が良いな。」

**現状 (今回確定)**: `websockets` は本体の依存なので、通常のセットアップを踏んだ環境では
Unity の待ち受けが**既定で開く**。無認証の接続に全ペルソナの ID と表示名を返す。
`UNITY_GATEWAY_ENABLED` は `.env.example` にも環境変数リファレンスにも無い。

**まだ決まらない理由 (Unity の対処の内容以外)**: **「凍結」の定義に待ち受けの停止が含まれるか**が
決まっていない。同じ判断に Unity・inter-city の子プロセス・SDS 登録の 3 つがぶら下がる。
凍結を「入口を塞ぐ」と定義するなら待ち受けも止める。「機能を使わない」と定義するなら開いたままでもよい。

もう一つ、**ループバック起動の API を誰に開くか**。README が案内する遠隔アクセスが、
この判断の実質的な既定値になっている (今回、門は `--listen-host` で起動すれば効くことが分かったので、
**欠けているのは機構ではなく案内**)。

# 第 2 部: 既存資料から解決できたもの

**これらをまはーに決め直させない。** 一見未合意に見えて、既存の決定・仕様・issue で答えが出る。

1. **「あらすじが何本あれば正常か」の件数規則は要らない。**
   `docs/intent/arasuji_levels.md` の既存の約束 4 本 (レベル別の上限 5,000 字 / 残す量 2,500 字 /
   畳み 1 回の材料上限 5,000 字 / 実行は承認済みの見積もりを超えず積み残しは次回が数え直す) から
   件数は導出でき、**§3-2 自身が「子 7〜15 本」と件数の言葉でその導出を書いている**。
   事故 1 の両欠陥も、件数の契約を持ち出さずに既存の約束の違反として表現できた。
   **残る穴は件数ではなく、「走行終了時に上限を超えたレベルが残っているか」が完了文にも
   診断レポートにも出ないこと** (判定材料は実行時に計算済み)。これは議題 2 に含まれる。
2. **スルースの飛ばしの 10 万字は「根拠なし」ではない。** intent の経緯に
   「本来はモデルのコンテキスト長から導出すべきで、それを環境変数で固定した」と記録がある。
   恒久策の方向も書かれている。
3. **モデル JSON と `.env` の書き込みを壊れない形にすること。**
   `saiverse/provider_configs.py:169-186` に同じ失敗形への判断が理由つきで既にある (一時ファイル + 置換)。
   適用漏れであって未合意ではない。
4. **`CLAUDE.md` の「Setup/Update Script Parity」。** 4 つの入口が `scripts/update_engine.py` に
   集約済みで、文書が古くなっただけ。実装を文書に戻す話ではない。
5. **`roadmap_status.md` のアドオン Phase 表記と Discord の位置づけ。** intent の方が新しい。
6. **スナップショットの制限時間 3600 秒。** 恒久策の方向が issue に既にある。
   加えてこの数値は超えても利用者のデータを失わせない (更新が始まらないだけ) ので、
   「超えると利用者の発言が失われる数値」とは格が違う。
7. **隔離の復元と再起動の作法の不揃い** (`copy2` と `os.replace` の混在、子プロセスの終了処理の有無)。
   同じ機構の中で既に一方が正しい形をしている。揃える案件であって決める案件ではない。
8. **利用者向け説明 (`docs/user-guide/`) が実装から取り残されている件。**
   `memory-view` のタブ表、`chat-options` の件数ベースの設定、`persona-settings` の `ACTIVITY_STATE`、
   `memory-migration` の「放っておいてもあらすじが育つ」、`memopedia` のタブ列挙。
   いずれも**直すべき文書であって、戻すべき仕様ではない**。

# 第 3 部: 追加調査で確認すべきもの

**ユーザー判断へ転嫁しない。** 有無が確定するまで議題に昇格させない。

1. **DB (`building_messages`) が壊れたときの検出・隔離・復旧に相当する仕組みがあるか** (`FLOW-31`)。
   **この流れで最も大きい穴の候補。** 建物ログの隔離機構は、印を立てる関数の呼び出し元が
