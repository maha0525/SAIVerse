# Astra の初回確認と判断整理

2026-09-09。対象は本ディレクトリの初稿。実装開始や仕様の承認を意味しない。

## 確認した範囲

README、flows の索引と訂正、decisions の全文を読んだ。本文は FLOW-01 と FLOW-30 の主要部分を重点確認し、FLOW-01 の応答者選択・送信時の保存と重複抑止を現行コードで参照した。32 本すべての期待と根拠の精読はまだ行っていない。

mapping は機械的に照合した。元台帳の見出しから得た 215 ID と mapping の 215 ID は一致し、欠落・余剰はゼロ。流れの本文見出しは重複なしの 32 本で、mapping が参照する FLOW-ID に本文のないものはなかった。これは対応表の検算であり、期待する挙動の正しさの検証ではない。

## 次の議論に使える点

機能の存在だけでなく、目的から結果までを 32 本へ組み替えたことで、正常化の単位を具体的に検討できる。材料量から導ける件数を新たな合意事項にしないこと、既存仕様・担当提案・未調査を分けることも前進している。

## 判断一覧をそのまま質問にしないための整理

- 議題1の記載場所は、既存の docs 保守規約に沿って担当が配置案を作れる。まはーに必要なのは書く場所の選択ではなく、提供範囲の事実が合っているかの確認。『未完成の印象が広がる』を事実の明示を控える理由にしない。
- 議題2のスルース未通過範囲の UI は、資料自身が未合意ではなく第二段の未着手と記している。新しい判断として尋ねない。実測値の表示場所については、画面と文面の具体案を作ってから相談する。
- 議題3は記憶の編集通知、出来事の聴衆、終了時の発言損失、想起対象という異なる判断を含む。『本人の器か機構の器か』という一文で一括決定できるとはまだ扱えない。実際の操作と、本人・利用者が知るべき変化を個別に示す必要がある。
- 議題4（アラームと自律設定）、議題5（確認相手不在時）、議題6（削除時の扱い）は、利用者が受け取る結果に関わる実質的な相談候補。
- 議題7は『凍結という言葉の定義』より、通常起動で何を立ち上げるか、どこから誰が接続できるかという具体的な挙動で整理する。先行対処四件の順序は既存の会話で了承されている。
- 議題8（検証とリリースの形）は、正常化の進行に沿って検討する後段の仕事。初稿の受領だけで実装を開始しない。

## 初稿の結論で注意する点

1. 『本体 CI がない』に手動テストの記録を示して『機械の強制がない』へ訂正する箇所は、二つの事実を分ける。本体 CI の不存在と手動テストの実施は両立し、後者は前者の反証ではない。前回このセッションでも手動実施の記録は認識していた。
2. FLOW-30 は、明示的な公開設定なら認証が働く設計と、既定のまま README の遠隔アクセス手順を使うと認証が有効にならない経路の両方を記録している。『欠けているのは案内だけ』はまだ修正方針の結論であり、実装変更が不要と決まったわけではない。
3. FLOW-01 の『発言は必ず一度だけ記録される』は、保存失敗による受付拒否と区別する必要がある。現行コードにも保存失敗の分岐がある。『同じ送信IDで二重に受理しない』『受理・未受理を利用者が識別できる』など、対象と条件を明示して期待を精密化する。
4. 同じ FLOW-01 の『全員が順に応答する』は、静的には応答者リストに順に処理を依頼すること。途中の停止や失敗、派遣中ペルソナの除外があるため、全員の返答生成を保証した記述にはしない。

## 正常化の議論への接続

全体の見取り図として使い、各流れを扱う際にその期待・根拠・未合意事項を精読する。初稿全体の無条件承認は求めない。まず先行対処四件について、FLOW-30 と URI 読み出しの関連する流れから、具体的な正常挙動と確認すべき境界を整理する。
