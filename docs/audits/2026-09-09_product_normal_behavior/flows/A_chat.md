## FLOW-01: ペルソナに話しかけて返事を受け取る

**対応する台帳項目**: `CHAT-01`, `CHAT-02`, `CHAT-03`, `CHAT-32`, `CHAT-09`, `CHAT-29`, `MEM-38` の一部

### 1. 誰が何をしたいか

**利用者**が、いま自分がいる部屋のペルソナに話しかけて、返事を受け取りたい。
同時に**ペルソナ**は、その発言を自分の記憶として持ち越したい (次の会話でそれを前提に話せる状態になる)。
運用者としてのまはーは、その一往復に**いくら課金が発生したか**が後から辿れることを求める。

### 2. 始まりから結果までの流れ

1. 利用者が本文 (と添付) を入れて送信 → フロントが送信操作 1 回につき UUID を 1 つ作って
   `POST /api/chat/utter` に載せる (`frontend/src/app/page.tsx:2489-2502`)。
2. 見ている部屋がサーバーの現在地と違えば、**発言より先に入室を確定させる** (FLOW-14 と接続)。
   食い違いが解けなければ 409 で発言そのものを止める (`api/routes/chat.py:1367-1435`)。
3. 発言を DB (`building_messages`) に 1 行として確定させる。同じ UUID が二度届いても 1 行しか入らず、
   二度目は認知を起こさない (`manager/runtime.py:786-796`)。
4. 応答者を決める。**その部屋の在室ペルソナ全員**が、リスト順に**逐次**返事をする
   (`manager/runtime.py:475-505, 780-830`)。ゲーム Region 内では Ruler が先頭に入る。
5. ペルソナごとに、応答前の窓の手当て → コンテキストの組み立て → LLM 呼び出し → 逐次配信。
   応答は NDJSON (1 行 1 イベント) で流れ、`say` / `streaming_chunk` / `activity` などが届く。
6. 発言が保存できた時点で `speak_persisted` が流れる。**画面に本文が出たこと (`streaming_complete`) は
   保存の証拠に数えない** (`manager/runtime.py:44-56`)。
7. 保存先は building_messages + 建物履歴 + 各ペルソナの SAIMemory。次回以降の履歴読み込み
   (`GET /api/chat/history`、5 秒ポーリング) で同じものが読み戻る。

### 3. 期待する結果の初稿

**根拠のある期待** (出典は次節):

- **発言は必ず一度だけ記録される。** 通信の再送や二度押しで同じ発言が二行になることはなく、
  二度目に追加の課金が起きることもない。
- **返事が生まれなかった回も、利用者に必ず何かが返る。** 無言で終わらない。
  応答できる相手が部屋にいなければ「いない」と分かる札 (`no_responder`)、
  相手はいたが返事が出なかったなら別の札 (`no_response`) が返る。
- **画面に本文が出たことと、その発言が残ったことは別々に伝わる。**
  保存が確定した回だけ保存の信号が届き、届かなかった回は「途中で終わった」印が残る側に倒れる。
- **話しかけた部屋と、発言が記録される部屋は必ず一致する。** 別の部屋を見ながら送った発言が、
  利用者の知らない部屋に入ることはない。
- **ペルソナは、その発言を次の会話で前提にできる。** 返事の生成に使った履歴と、
  記憶に残る履歴が別物にならない。

**調査担当の提案** (根拠が実装以外に無い。ここを期待に混ぜていない):

- 在室者全員が順に返事をする以上、**一回の送信で何体ぶんの課金が起きるかを送信前に知れる**べきではないか。
  現状これが見えるのはコンテキストプレビューをわざわざ開いたときだけで、
  「人数分の課金」そのものを説明する画面表示は見つけられなかった (CHAT-32)。
- 「全員が順に応答する」という決まりそのものに、利用者向けの説明も設計文書も見つけられなかった。
  期待の根拠が実装だけなので、**これが望ましい姿かどうかがまだ誰にも決められていない**。

### 6. 中断・失敗・再開

この流れで実際に起きる形は 4 つ:

- **応答者ゼロ / 返事なしで終わる** → 札つきで通知され、FLOW-02 の再送導線へ渡る。
- **見ている部屋とサーバーの現在地が食い違う (409)** → 吹き出しを引っ込め、本文と添付を入力欄へ戻す。
  ただし入力欄に既に添付があるときは戻さない (`frontend/src/app/page.tsx:2536-2557`)。
- **窓を用意できずに応答を見送る** → 利用者 Pulse のときだけ
  「記憶の窓を用意できなかったため、この応答を見送りました。次に話しかけると再試行します。」が出る
  (`sea/runtime.py:195-210`、自分で確認)。FLOW-04 の水位と地続き。
- **通信が切れる** → FLOW-03 へ。

### 7. 次に使う機能・共有する状態

- 発言と返事はそのまま **FLOW-09 (会話しながら記憶が整理される)** の入力になる。
  つまりこの流れの「成功」は、返事が画面に出たことではなく、**次の会話で同じ記憶が読み戻せること**まで含む。
- 部屋の在室者・アイテム (FLOW-14 / FLOW-16) が変わると、次の送信内容が変わる。
  右サイドバーのアイテムの開閉トグルは、**次に送るものを変える操作**であって表示切り替えではない (CHAT-29)。
- 入室契機の移動は **FLOW-14** の台帳実行として確定し、世界側のイベントを起こす。

  → **共通議題**: FLOW-31 (壊れたときの復旧) と共有。
- 上記以外に、この流れで新たにまはーの判断を要する点は見つけていない。

## FLOW-02: 思った返事が来なかったときに立て直す

**対応する台帳項目**: `CHAT-04`, `CHAT-05`, `CHAT-06`, `CHAT-07`

### 1. 誰が何をしたいか

**利用者**が、返事が来なかった・途中で切れた・止めたくなった会話から、
**自分の発言を無駄にせずに立て直したい**。
同時に**ペルソナ**の側では、「聞いた覚えがあるのに記録が無い」状態が作られないことが要る。

### 2. 始まりから結果までの流れ

- **止める**: 生成中に停止ボタン → `POST /api/chat/stop` →
  ユーザーの現在建物にいるペルソナの走行中リクエストを取り消し、建物の停止イベントを立てる
  (`saiverse/saiverse_manager.py:1307-1339`、自分で確認)。
  途中まで喋った発言は「途中で終わった」印つきで確定する。
- **続きを出す**: その印の付いた発言に「続きの生成」ボタン → `POST /api/chat/continue` →
  発言は送り直さず応答だけを起こす。入力欄の席に `<system>` で包んだ機構の指示文を載せる (永続化しない)。
- **やり直す**: 返事が来なかった自分の発言に「再送」→ `POST /api/chat/retry` →
  発言は送り直さず、**最初の 1 体だけ**に応答をやり直させる。
- **取り消す**: 同じ発言に「取り消す」→ `POST /api/chat/withdraw` →
  DB の行を消し、建物履歴からも落とし、本文を入力欄へ返す。LLM は呼ばない。

### 3. 期待する結果の初稿

**根拠のある期待**:

- **追加の推論は必ずボタンの後ろに置かれる。** 止めた後・返事が来なかった後に、
  利用者が押していない課金が勝手に起きない。
- **「読まれた後は取り消せない。」** 取り消せるかどうかは、ペルソナがもう読んだかで決まる。
  読まれた後に消せてしまうと、ペルソナ側に「聞いた覚えがあるのに記録が無い」状態が生まれる。
- **断られた理由が利用者に区別できる形で返る。** 「記録が無い」と「履歴を読めなかった」を
  同じ言葉にしない (`manager/runtime.py:1021-1046`)。取り消しの拒否理由は 4 種
  (`already_heard` / `not_found` / `wrong_role` / `unavailable`) に分かれ、それぞれ日本語の説明がある。
- **既に返事が付いた発言を、やり直しで二重に燃やさない。** API と生成直前の 2 段で門番が引かれ、
  判定できないとき (DB を読めない) は通さない側に倒れる (fail-closed、503)。
- **取り消せなかったからといって、再送まで一緒に消えない。** 取り消しが「もう読まれた」で断られても、
  応答を得る唯一の手段である再送は残る (`frontend/src/app/page.tsx:139-148` のコメントに明記、自分で確認)。

**調査担当の提案**:

- **停止ボタンの巻き添えを、利用者に見える形で説明すべきではないか。**
  停止は建物単位なので、同じ部屋で走っている無関係な自律 Pulse も一緒に止まり、
  記録には「ユーザーが止めた」と残る。これはコード内で自覚的に書かれているが
  (`manager/runtime.py:1112-1118`、自分で確認)、画面には一切出ない。
- **「再送」「取り消す」が押せる状態は、ブラウザを再読み込みしても保たれるべきではないか。**
  現状はこの二つのボタンの根拠がブラウザの中だけにある (下記 5 節)。

### 4. 根拠

- **ユーザー原文**: コード内に裁定日つきの言及が 3 件ある — 「追加の推論はすべてボタンの後ろに置く
  (2026-08-25 まはー裁定)」「読まれた後は取り消せない (2026-08-25 まはー裁定)」
  「2026-08-27 / 2026-08-28 まはー裁定」(停止時の吹き出しの畳み方)。
  **いずれも一字一句の引用ではないため、原文未確認**として扱う。
- **既存の仕様文書**: `docs/issues/user_utterance_path_failure_inventory.md`、
  `docs/issues/archive/retry_api_has_no_server_side_eligibility_check.md`。
  後者は `tests/test_generation_stage_signals.py` の docstring §J に設計元として明記されている (自分で確認)。
- **利用者向け説明**: `docs/user-guide/` に停止・再送・取り消し・続きの生成の説明は見つけられなかった
  (`chat-options.md` 全文を読み、`docs/user-guide/` を「再送 / 取り消 / 停止」で grep した。
  当たったのは `persona-settings.md` と `world-view.md` で、いずれもこの 4 操作の説明ではない)。
- **調査担当の提案**: 上記 3 節の後半 2 点。

### 5. 現状との差

- **既知の不一致 (自分で確認)**: **「返事が来なかった」印がブラウザ再読み込みで消える。**
  「途中で終わった」印 (`interrupted`) はサーバーの `metadata["_interrupted"]` に永続化され、
  履歴 API の `ChatMessage.interrupted` として返る (`api/routes/chat.py:64-66`)。
  一方 `needsRetry` / `retryUseless` / `withdrawBlocked` はフロントの `ChatMessage` 型にしか無く
  (`frontend/src/app/page.tsx:137-148`)、サーバーの応答モデルには存在しない。
  つまり**再読み込みすると「再送」「取り消す」が消え、「続きの生成」だけが残る**。
  サーバー側には同じ判定材料 (`/chat/message-outcome` の `has_reply`) があるが、履歴取得では使っていない。
- **静的な疑い**: 停止の巻き添え (無関係な自律 Pulse が「ユーザーが止めた」として記録される) は
  コードの読みで確認したが、実際にどのくらいの頻度で起きるかは追えていない。
- **まだ追跡していない境界**: `CancellationToken` の伝播先 (LLM クライアントのストリーム切断まで)。
  `database/building_messages.withdraw_building_message_in_db` の「読んだ」の定義。
  `history_manager.update_building_message` の実挙動。
- **検査の欠落**: `/chat/withdraw` を通すテストを特定できていない
  (`tests/` を `withdraw_user_message` / `/chat/withdraw` で grep したが、当たったのは
  `test_arasuji_absorption.py` の無関係な「撤去」だけ、自分で確認)。
  取り消せる / 取り消せないの判定は記憶の整合性に直結するので、ここは印象として重い。
  継続・再送の側にはサーバー側の厚いテストがある (`tests/test_user_utterance_durability.py`,
  `tests/test_generation_stage_signals.py`)。

### 6. 中断・失敗・再開

- **停止 → 本文が一文字も出ていない回**: サーバー履歴に残らないので、フロントが吹き出しをその場で畳む。
  そのうえで「返事が来なかった」扱いにする。
- **取り消しが断られた回**: 何も起きていないので、消えるのは「取り消す」ボタンだけ。
- **再送が 409 (already_replied)**: ボタンを戻さず履歴を読み直す。
- **やり直しても結果が変わらない回** (`no_responder` / `already_replied`): 再送ボタンを落とす。
  ただし取り消しは残す — 誰も読んでいない発言を消す手段まで奪わないため。

### 7. 次に使う機能・共有する状態

- 「続きの生成」は FLOW-01 と同じ Pulse の道を通るので、FLOW-04 (送る量) と FLOW-09 (記憶の整理) を
  そのまま起こす。**ここでの局所的な成功 = 続きが画面に出たこと、ではない。**
- 取り消しは building_messages の行を消すので、FLOW-09 の編纂対象からも消える。
  取り消し可能な範囲が「読まれる前」に限られているのは、この波及を止めるためでもある。

### 8. 決める必要がある点

- **失敗の印 (再送・取り消しが押せる状態) を、どこが持つべきか。**
  現状はブラウザだけが持っていて、再読み込みで失われる。サーバーは同じ事実を答えられる立場にある。
  → **共通議題**: FLOW-03 と同じ判断の面。統合担当がまとめる。
- **停止の巻き添え (同じ部屋の自律 Pulse も止まり、「ユーザーが止めた」と記録される) を許すか、
  記録の名義を分けるか、画面で説明するか。** 現状はコード内でだけ自覚されていて、
  まはーの「止めるのではなく記録し、明示し、選択してもらう」に照らすと、記録も明示もされていない。
  ただし**この原則から自動的に結論が出るとは扱わない** — 停止は利用者自身が選んだ操作なので、
  他の障害時の既定とは事情が違う。

## FLOW-03: 通信が切れた会話を復旧する

**対応する台帳項目**: `CHAT-08`, `CHAT-31`, `CHAT-26`

### 1. 誰が何をしたいか

**利用者**が、送信の途中で通信が切れたときに、
**自分の発言が届いたのか届かなかったのかを知り、届いていなければ本文と添付を取り戻したい**。

### 2. 始まりから結果までの流れ

1. ストリーム読み取り中、15 秒間データが来なければ接続を死んだものとして扱う
   (サーバーは 2 秒ごとに `ping` を流すので 7 倍の余裕、という根拠がコメントにある)。
2. 「結果イベントがゼロのまま正常終了した」回も切断と断定する (`frontend/src/app/page.tsx:2294`)。
3. 顛末が分からない回は、フロントが自動で `GET /api/chat/message-outcome?client_message_id=...` を叩く。
   読み取りのみで LLM は呼ばない。
4. 返る値は三値:
   - `found` かつ返事あり → 履歴を読み直して「通信は切れたが発言は届いていて返事も付いている」と案内。
   - `found` かつ返事なし → FLOW-02 の再送導線へ合流。
   - `not_found` → 吹き出しを引っ込め、本文と添付を入力欄へ返す。添付は下書き分と戻り分の両方を残し、
     id で重複を弾く (`frontend/src/app/page.tsx:2354-2364`)。
   - `unknown` / 問い合わせ自体の失敗 → 「発言が届いたかどうかは分かりません」と正直に出す。

### 3. 期待する結果の初稿

**根拠のある期待**:

- **「分からない」を「起きなかった」に潰さない。** 照会できないときは `unknown` のまま返り、
  画面もそう言う。届いたことにも届かなかったことにもしない。
- **届かなかった発言は、本文も添付も手元に戻る。** 打ち直しにならない。
  戻すときに、その間に利用者が入力欄へ足した下書きを潰さない。
- **中継 (Next の :3000 → :8000) 越しでも、待ち続けて固まらない。**
  バックエンドが死んだことをブラウザが知らされない経路があるので、画面側に締切がある。
- **読み手が去っても、ペルソナの生成は止まらない。** 画面を閉じたことを理由に認知を打ち切らない
  (`manager/runtime.py:1107-1118`、自分で確認 — 2026-08-26 に一度入れて撤回した経緯がコメントにある)。

**調査担当の提案**:

- 復旧の入口が**自動でしか開かない**。利用者が後から「さっきのあれ、届いた?」と自分で確かめる導線は
  見つけられなかった。再読み込みすると印が消える (FLOW-02 §5) こととあわせると、
  **タブを閉じた後に顛末を調べ直す手段が無い**ように読める。これは提案であって、
  そういう手段が要ると決まっているわけではない。

### 4. 根拠

- **ユーザー原文**: 見つけられなかった。
- **既存の仕様文書**: `docs/issues/archive/unknown_send_outcome_has_no_recovery_path.md`。
  `tests/test_generation_stage_signals.py` の docstring §I が
  「`client_message_id` で発言の保存結果を問い合わせる読み取りの口。**「分からない」を潰さない。**」と
  設計元として明記している (自分で確認)。ここは設計意図が文書とテストの両方に残っている珍しい箇所。
- **利用者向け説明**: `docs/user-guide/` に切断時の案内の記述は見つけられなかった。
- **実測の記録**: 「2026-08-28 実測: バックエンド直結の読み手は即座にエラーを受けるが、
  中継経由の読み手は done もエラーも受けず永遠に待つ」がコメントにある。**原典は未確認。**
- **調査担当の提案**: 上記 3 節の後半。

### 5. 現状との差

- **台帳の訂正 (自分で確認)**: 台帳 CHAT-08 は「既存テスト: **見つからない**。API 側もフロント側も」と
  書いているが、**API 側にはある**。`tests/test_generation_stage_signals.py` が
  `lookup_client_message_outcome` の三値を実 SQLite で通し (`:326-346`)、
  `get_message_outcome` の口を直接呼んで `found` / `not_found` / `unknown` を固定している
  (`:364-388`)。特に `test_message_outcome_endpoint_does_not_flatten_unknown` は
  「照会できないときに unknown を潰さない」をそのまま検査している。
  **無いのは画面側の復旧分岐** (本文と添付の戻し、id での重複弾き、15 秒の心拍締切) のテストで、
  これはフロントにテスト基盤が無いことの帰結。
- **既知の不一致**: 無し。文書とコードの食い違いはこの流れでは見つけていない。
- **静的な疑い**: 「結果イベントゼロの正常終了を切断と断定する」判定は、
  サーバー側の「届いた」に数えるイベント集合 (`manager/runtime.py:57-77`) の鏡が
  フロント (`frontend/src/app/page.tsx:1621`) に**二重定義**されていることに依存している。
  サーバー側のコメントが「鏡も同じコミットで揃えること」と依頼しているだけで、機械の担保が無い。
  ずれると「届いたのに切断と判定する」側に倒れうる (コードの読みからの推定、実行では確かめていない)。
- **まだ追跡していない境界**: Next の rewrite / proxy 設定 (`frontend/next.config.ts`) の実挙動。

### 6. 中断・失敗・再開

- **照会そのものが失敗する**: `unknown` と同じ扱いで、正直に「分かりません」と出る。
- **切断後にペルソナが返事を書き終える**: 生成は止まっていないので、返事は保存される。
  次の履歴読み込みで現れる。
- **同じブラウザで複数タブを開いている**: 最終操作時刻を BroadcastChannel で共有し、
  最新のタブだけがアイコンを出す (CHAT-26)。**別ブラウザ・別端末は同期できないので
  両方がアクティブになりうる** — これはコードに「意図的な仕様」と明記されている。

### 7. 次に使う機能・共有する状態

- `found` かつ返事なしの分岐は、そのまま FLOW-02 の再送導線に合流する。
  つまり FLOW-02 と FLOW-03 は**同じ「立て直す」目的の、原因違いの二つの入口**。
- 戻された添付は FLOW-06 の入力に戻る。**ただし添付から作られた Item は別の話** (FLOW-06 §5 参照)。

### 8. 決める必要がある点

- **失敗の印をサーバーが持つべきか** (FLOW-02 と同じ論点)。→ **共通議題**。
  この流れの側から見ると、サーバーは既に `has_reply` を答えられるので、
  「持てないから持っていない」のではなく「履歴取得で使っていない」だけに見える。
- サーバー側の「届いた」イベント集合とフロントの鏡が二重定義であることは、
  **未合意ではなく設計の負債**として扱うのが妥当だと考える (統合担当の判断に委ねる)。

## FLOW-04: 送る中身と量とモデルを決めてから送る

**対応する台帳項目**: `CHAT-11`, `CHAT-12`, `CHAT-13`, `CHAT-14`, `CHAT-15`, `MEM-38`

### 1. 誰が何をしたいか

**利用者**が、送信ボタンを押す前に「**いま何が・どれだけ・どのモデルへ送られ、いくらかかるか**」を見て、
必要なら量とモデルを調整したい。
**まはー (運用者として)** は、この画面の数字が実際に送られるものと食い違わないことを求めている
(「プレビューが嘘にならないの原則」が `api/routes/people/context_status.py:5-8` に明記されている)。

### 2. 始まりから結果までの流れ

- **中身を見る**: 「+」メニュー → コンテキストプレビュー → `POST /api/chat/preview`。
  応答可能なペルソナごとに、節ごとの内訳・推定入力トークン・推定費用の幅
  (キャッシュ全ヒット時〜全書き込み時) と、各メッセージの本文が出る。LLM は呼ばず履歴にも書かない。
- **量を見る**: チャットオプション →「データ送信量の管理」→ `GET /api/people/{id}/context-status`
  (1 回だけ、ポーリングしない)。読み取り専用で行を一切書かない。
- **モデルを選ぶ**: チャットオプションの「モデル」欄 → `POST /api/config/model`。
- **キャッシュの残りを見る**: `GET /api/people/{id}/cache-status` を 2 秒ごとにポーリング。
- **画像の枚数を絞る**: 「画像埋め込み上限」→ `POST /api/config/max-image-embeds`。

### 3. 期待する結果の初稿

#### 3-1. 数値の契約 — どの数値が何の量を数え、誰に何を約束しているか

**この節は根拠のある期待。** すべて `saiverse/model_configs.py:203-262` と
`docs/intent/arasuji_levels.md` §9 を自分で開いて確かめた。

|---|---|---|---|---|

**この主語の分け方には、まはーの裁定と原文が残っている** (根拠として最も強い):

- 「**上限 = 実際に送る合計**」「**残す量 = 会話の行の量**」は `docs/intent/arasuji_levels.md` §9

**帰結として画面に出る約束**: 合計が上限を超えているのに会話の行が残す量以下 = 「畳めるものが無い」。

- **プレビューが嘘にならない。** プレビューに出る量・費用と、実際に送られるものが食い違わない。

- **モデル切替の追い越し**: `client_id` + `seq` の世代ガードで古い要求を 409 にする。

### 7. 次に使う機能・共有する状態

  *費用の設定* であると同時に *記憶が畳まれる契機* でもある。

### 8. 決める必要がある点

  文書の更新漏れ。決めることがあるとすれば「利用者に水位の主語をどこまで説明するか」だけ。
- **モデル欄の効き先 (メモリ上の全ペルソナ / 非永続) を利用者にどう見せるか。** 未合意。
  現状は画面にも利用者向け説明にも範囲が書かれていない。
- **費用の見せ方の粒度を揃えるか** (プレビュー = 金額の幅 / Chronicle 確認 = 呼び出し回数)。

## FLOW-06: 会話にファイルを渡し、それが世界の物になる

**対応する台帳項目**: `CHAT-10`, `WORLD-29`, `WORLD-30`, `WORLD-31`, `WORLD-32`

### 1. 誰が何をしたいか

**利用者**が、画像・文書・音声・動画をペルソナに見せて、それについて話したい。
**ペルソナ**の側は、渡されたものを自分の部屋にある物として認識し、後から参照できることが要る。

### 2. 始まりから結果までの流れ

1. 「+」メニューかドラッグ&ドロップでファイルを選ぶ。
2. `~/.saiverse/{image,documents,audio,video}/{YYYYMMDD_HHMMSS}_{uuid4}.{ext}` に保存する。
   **保存ファイル名はサーバーが生成する**ので、利用者側のファイル名は拡張子の判定にしか使わない。
3. 対応する **Item を現在の建物に作る**。文書・音声・動画は `is_open=True` (= AI のコンテキストに含める) で作られる。
   建物ログに「User Upload」の note 行も残る。
4. 中身の概要生成が走る場合がある (画像・音声・動画は既定でバックグラウンド。
   グローバル設定「添付したメディアの内容を自動想起に使う」が ON のときだけ同期実行され、
   送信が数秒待たされる)。PDF は先頭 5 ページのテキスト抽出、文書の要約は先頭 200 文字の切り出し (LLM 不使用)。
5. 発言と一緒に LLM へ渡る。以後は部屋のアイテムとして残り、`saiverse://` URI でペルソナから参照される。

### 3. 期待する結果の初稿

**根拠のある期待**:

- **ペルソナが添付を見て話せる。** 渡したものが `saiverse://` URI 経由で参照できる状態になる
  (`docs/user-guide/items-and-files.md` §チャットへのファイル添付)。
- **上限を超えたファイルで、壊れた状態が残らない。** 上限超過は 413 で、
  読み込みは上限+1 バイトで止め、書きかけのファイルは消される (`api/file_safety.py:44-77`)。
- **ファイル名でディレクトリの外に出られない。** `safe_filename` がパス構文
  (`.` `..` `/` `\` `:` NUL) を 400 で弾く。
- **発言が拒否されたら、作った Item は片付く。** 位置競合 (409) で発言が通らなかったとき、
  作成済みの Item を削除し、建物履歴に撤去の補記を追記する。
  **元の「User uploaded ...」の記録は消さない** (`api/routes/chat.py:915-959`)。
- **ffmpeg が無い環境では、黙って劣化せず 503 で断る。**

**調査担当の提案**:

- **添付が「部屋に置かれ続ける永続アイテム」になることが、利用者向け説明に書かれていない。**
  `docs/user-guide/items-and-files.md` は URI で参照されることは書くが、
  部屋に残ること・既定で開いていること・後から手で消す必要があることを書いていない (台帳 WORLD-31)。
  これは説明の穴か、設計の意図かがまだ分からない。
- **動画 90 秒 / 音声 300 秒の上限が、超えて初めてエラーで分かる。**
  事前に画面へ出ていない (CHAT-10)。

### 4. 根拠

  添付を消す UI 経路 (ワールドエディタのアイテム削除以外は見つかっていない)。
- **検査の状況**: `tests/test_api_file_boundaries.py` (5 件) が上限超過の 413、部分ファイルの削除、
  ファイル名・拡張子の検査、許可ルート外の拒否を実ファイルで通す。
  `tests/test_attachment_paths.py` (10 件超) が保存先が `SAIVERSE_HOME` 配下になること、
  URI が同じファイルへ再解決することを通す。
  **`resolve_media_uri` にパス構文を渡す検査は見つかっていない** (正常系の再解決だけ)。

### 6. 中断・失敗・再開

- **上限超過**: 413。書きかけのファイルは消える。
- **動画 90 秒 / 音声 300 秒の超過**: ffmpeg 正規化時に打ち切られ、400 の詳細つきエラーになる。
- **PDF のテキスト抽出に失敗**: 「(PDF text extraction failed)」で続行する。
- **位置競合で発言が拒否された**: Item を削除し撤去の補記を追記する。
  **保存済みファイル自体は消さない** — ここは「消さない」を選んでいる。
- **添付処理が想定外の例外を出した**: `None` を返して黙って落ちる (上記 §5)。

### 7. 次に使う機能・共有する状態

- 添付は FLOW-16 (物を作り、持ち、使う) の Item になり、FLOW-14 の部屋の様子に載る。
  **つまり一度渡したファイルは、以後ずっと FLOW-04 の「送る合計」を押し上げる。**
  部屋のアイテムが溜まり続ける問題は `docs/issues/room_items_uncapped.md` に起票済みで、
  アイフィの部屋 58 個で部屋の様子が 35,000 字超という実測が記録されている (台帳 WORLD-31)。
  知覚の上限 60,000 字 (FLOW-04) に対して無視できない大きさ。
- 概要生成が同期実行されるモードでは LLM を呼ぶので、**添付が課金の契機になる**。
- `saiverse://` の解決は FLOW-05 のスペル (`resolve_uri`) と同じ入口を共有する。

### 8. 決める必要がある点

- **添付が部屋に残り続けることを、利用者向け説明に書くか、機構として上限を設けるか。**
  → **共通議題**: FLOW-04 (送る量) と FLOW-16 (物) にまたがる。
  `docs/issues/room_items_uncapped.md` が既に起票されているので、**未合意ではなく設計待ち**として扱うのが妥当。
- **読み出し側のパス検査 (`resolve_media_uri`) は、未合意ではなく修正対象**だと考える。
  アップロード側に同じ検査が既にある以上、「読み出しには要らない」という決定があったとは読めない。
  ただし実行して再現していないので `要追加確認` (再現の確認が先)。**まはーの判断へ転嫁しない。**
- **添付が黙って落ちる経路 (`RuntimeError` 以外の例外)** も同様に、
  まはーの「止めるのではなく記録し、明示し、選択してもらう」に照らせば
  「黙って落ちる」は明らかに外れて見えるが、**この原則から個々の障害時の挙動が自動的に決まるとは扱わない** —
  ここは「利用者に何を出すか」の設計判断が要る。
- 動画 90 秒 / 音声 300 秒の上限を事前に画面へ出すかは未合意。
  ただし**この数値そのものを決め直す必要があるとは扱わない** —
  超えると利用者のファイルが拒否されるだけで、失われるものは無いため
  (FLOW-04 の水位のように、超えると利用者の発言が畳まれる数値とは格が違う)。

## 群 A 全体から、統合担当へ渡す横断の観察

1. **この 6 つの流れは「一往復の会話」で全部繋がっている。**
   FLOW-05 のスペル結果は FLOW-04 の合計を押し上げ、FLOW-06 の添付は部屋のアイテムとして
   同じ合計に乗り続け、FLOW-04 の上限超過が FLOW-09 の記憶の整理を起こす。
   **どれか一つの流れの中で成功しても、それは製品の成功ではない。**
2. **「利用者に見せる数字」と「機構が実際に使った数字」を突き合わせる検査が、この領域に一つも無い。**
   CHAT-11 (プレビューの費用) / CHAT-12 (送信量) / CHAT-19 (Chronicle の呼び出し回数) の 3 つが
   数字を見せる面で、事故 2 件はどちらもその突き合わせの不在から出ている (台帳 §5 の結論と一致した)。
3. **フロントにテスト基盤が無いことが、この領域の検査の穴のほぼ全部を説明する。**
   ただし**検査が無いことは不具合の証明ではない**ので、期待の初稿とは別欄に置いた。
