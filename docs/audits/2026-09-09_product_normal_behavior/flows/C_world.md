## FLOW-14: 部屋を移動し、その場の相手や物を認識して会話する

**対応する台帳項目**: `WORLD-11`, `WORLD-12`, `WORLD-13`, `WORLD-14`, `WORLD-15`, `WORLD-16`, `WORLD-17`, `PERS-04`, `PERS-13`, `PERS-28`

### 1. 誰が何をしたいか

- **利用者** — 部屋を選んで中を見て、そこにいる相手に話しかけたい。ペルソナを呼んだり自室へ帰したりしたい。
- **ペルソナ** — 自分がいま**どこにいて、誰と居合わせていて、その部屋に何があるか**を、自分の知覚として正しく持ちたい。
- **運用者** — 在室の記録が一つに定まっていて、同じペルソナが二つの部屋に同時に居ることがない状態を保ちたい。

### 2. 始まりから結果までの流れ

1. 左サイドバーの場所一覧か街マップで部屋をクリックする。これは**閲覧**で、サーバー上の現在地は動かない
   (`frontend/src/components/Sidebar.tsx:239-254` は `/api/user/move` を呼ばない)。
2. 実際の入室は 2 つの入口から起きる。①街マップからの明示移動・ペルソナ作成ウィザード・チュートリアルが呼ぶ
   `POST /api/user/move`、②閲覧中の別の部屋で発言したときに `POST /api/chat/utter` が行う発言契機入室
   (`api/routes/user.py:94-150`, `api/routes/chat.py:1333-1400`)。
3. ペルソナ側の移動は 5 つの入口 (召喚 / 解散 / ワールドエディタ / ペルソナ自身の `move_persona` / ゲームのパーティー追従)
   があるが、すべて `OccupancyManager.move_entity` の 1 本に集まる (`saiverse/occupancy_manager.py:213-236` の docstring が
   「呼び出し側は位置属性を書き換えてはならない」と明記)。
4. 移動要求は判定順に並んだ門を通る (`saiverse/occupancy_manager.py`)。行き先の存在 → 隔離中か → Region の入口トポロジーと
   entry policy → game Region の入場ゲート → 定員 → DB の CAS 仲裁。
5. 通ると、位置の遷移・退室/入室の建物ログ 2 本・実行台帳の applied・後処理の outbox が**単一トランザクション**で確定する。
6. 確定後、記録は 3 系統に分かれる。
   - **建物ログの host 行 2 本** — 退室元と入室先。`heard_by` は移動後の在室者。`metadata.event.type = "occupancy"`。
   - **ペルソナ記憶への転記はしない** — 転記側 (`builtin_data/tools/get_building_messages.py:251-260`) が
     `event.type == "occupancy"` の行と `entity_type == "user"` の行を既読マークだけ付けて捨てる。
   - **知覚バッファへの投入** — `move.post_dynamic_state` outbox → `DynamicStateManager.on_building_entered`
     (`saiverse/dynamic_state.py:86-260`) が、①移動した本人へ移動の事実 (`only_sections={"building","building_occupants"}`)、
     ②同じ部屋に既にいる他ペルソナ全員へこの入室、③本人へ**部屋の様子の束**を配送する。
7. 消費は各ペルソナの次の Pulse。滞在中は Pulse の頭で `_detect_room_state_changes`
   (`sea/head_pipeline/integration.py:811`) が部屋の様子の束を照合し、変わった分だけを知覚へ積む。

### 3. 期待する結果の初稿

**根拠のある期待**

- **(a)** 部屋を選ぶ操作は「閲覧」であって移動ではなく、実際の入室は発言の瞬間に原子的に起きる。
- **(b)** 移動が成立したとき、位置・在室ログ・建物ログ・後処理は全部成立するか全部成立しないかのどちらかで、
  途中の姿が残らない。commit 後に「失敗しました」を返さない。
- **(c)** 移動が拒否されたとき、利用者は理由を日本語で受け取る。競合したときは 409 とあわせて**サーバーが確定した現在地**を
  受け取れるので、自分がどこにいるかを取り戻せる。
- **(d)** ペルソナは、いまいる部屋の様子を常にコンテキストに持っている。起動直後でも、長い滞在の後でも、記憶の整理の後でも。
  部屋の報告は変わった事実だけを運び、変わらなければ「変わっていません」の一行になる。
- **(e)** 入室は居合わせる全員に届く。移動した本人には「移動の事実」が、既に居た側には「この入室」が届く。
  消費は各自の次の Pulse で、本人が Pulse を打つまで待つ (主観時間が止まっている間の知覚は詰まって待つ、という時間モデル)。
- **(f)** 入口のある空間 (Region) には、外から内部の部屋へ直接入れない。入口を経由して入る。
  入口そのものは常時開放で、鍵は入口→内部の境界でだけ効く。

**調査担当の提案 (根拠のある期待と混ぜない)**

- **(g)** 建物ログに書かれた出来事の**聴衆 (`heard_by`) は「その時その部屋に居合わせた者」という世界の事実**であって、
  行を書く側が任意に決めてよい値ではないのではないか。
  この提案の材料として一番近いのは `docs/intent/arasuji_levels.md` §7-1 のまはー裁定
  (「本人の提示に立った行は、すべて編纂の材料と被覆に入る。意味・種類による仕分けはしない」) で、
  これは**届いた後は種類で選り分けない**ことを確定している。裏返すと、選別が起きてよい唯一の場所は
  「そもそもその出来事が本人に届いたか = 居合わせたか」になる。ただし「`heard_by` を居合わせから導出すべき」と
  書いた文書は見つからなかったので、これは提案として立てる。
- **(h)** 入退室そのものがペルソナの記憶に文として残らない現状は、設計として一貫している。
  部屋の様子の差分が同じことを語るので、二重に語らせない形になっている。
  ただしこれが「意図した無記載」であることは `get_building_messages.py:235-251` のコード内コメント以外に書かれていない。
  ペルソナの記憶に何を残さないかは、コメントではなく設計文書に書かれるべき性質の決定ではないか。

## FLOW-15: 世界を作り変える

**対応する台帳項目**: `WORLD-01`〜`WORLD-10`, `WORLD-18`, `WORLD-19`

### 1. 誰が何をしたいか

- **利用者 (世界の作者)** — 街を作り、部屋を作り、マップに並べ、いらなくなったら消したい。
- **ペルソナ** — 自分が新しく作られた部屋を使えて、その部屋の会話が自分の記憶に正しく繋がる状態でいたい。
- **運用者** — 世界の識別子が動かないこと、消す操作で戻らないものが黙って消えないことを保ちたい。

### 2. 始まりから結果までの流れ

1. ワールドエディタ (City / Building / ペルソナ / Blueprint / ツール / アイテム / Playbook の 7 タブ)、
   左サイドバーの「場所」の ＋ ボタン、街マップの編集モード、そしてペルソナ自身の `create_building_playbook` が入口。
2. City の作成は slug (識別子) と表示名を分けて受け取り、slug の文字種・大文字小文字を畳んだ重複・ポート重複・
   IANA タイムゾーンを検査する (`manager/admin.py:229-295`)。slug は作成時にしか決められない。
3. Building の作成は `POST /api/world/buildings` → `manager.create_building` → `_reload_buildings()` で
   in-memory の buildings / building_map / capacities / occupants が即時更新される
   (`saiverse/saiverse_manager.py:1821-1882`)。
4. 街マップの編集モードで座標をドラッグして一括保存する (`PUT /api/world/buildings/positions`)。
   背景画像は City スコープと Region スコープの 2 つの宛先を、表示中のスコープで切り替える。
5. 削除は事前検査を通ったときだけ通る。City は「最後の 1 件でない・稼働中でない・Building が残っていない・
   占有ログが残っていない」の 4 条件 (`manager/admin.py:352-383`)。Building は「seed 由来でない・AI が在室していない・
   ユーザーが在室していない」の 3 条件 (`:461-508`)。
6. **Region は読む側だけが動いている。** 折り畳み表示と入口 Building から内部マップへ潜る経路は UI から使えるが、
   Region を作る・編集する・削除する・Building を所属させる 4 ルートを呼ぶフロントエンドのコードが無く、
   ワールドエディタに Region タブも無い (`frontend/src/components/settings/WorldEditor.tsx:498-506` の 7 タブを私が開いて確かめた)。

### 3. 期待する結果の初稿

**根拠のある期待**

- **(a)** 街の識別子は作った後は変わらない。表示名はいつでも変えられて、街マップの見出しからも編集できる。
  表示名が空なら識別子が代わりに見える。
- **(b)** 部屋を作ったら、再起動を待たずにその場で使える。
- **(c)** 消す操作は、消したら戻らないものを事前に守る。会話が入っている部屋、人が居る部屋、最後の街は消せない。
- **(d)** Region は入口を必ず持ち、入口は親スコープに属し、入口自体は常時開放される。
  この 3 つが揃うことで「マップ上に到達経路が常に存在する」ことが保証される。
- **(e)** **Region の作成・編集・削除・所属変更が画面から到達できないのは、v0.4.0 以降のリリースへ回すための
  意図的な未配線である。** 読む側 (折り畳み・潜り) だけが先に動いていることも、その意図の一部として読む。

**調査担当の提案**

- **(f)** 「まだ配線していない」という状態は、**利用者にも将来の保守側にも読める形で、どこか 1 箇所に正本として書かれるべき**。
  現在は 4 つの文書がそれぞれ違うことを書いていて (5 節参照)、どれも「意図」を運んでいない。
  実際、今回の棚卸しで担当が「凍結とも開発者専用とも書かれていない、ただ到達できない状態」としか記述できなかったことが、
  その実例になっている (まはー本人の判断)。
- **(g)** 部屋を消したときに会話ログをどう扱うかは、利用者から見て答えが要る問いなのに、

## FLOW-16: 物を作り、持ち、使う

### 1. 誰が何をしたいか

- **運用者** — 利用者のファイルが、置かれるべき場所にだけ置かれ、読まれるべき人にだけ読まれる状態を保ちたい。

### 2. 始まりから結果までの流れ

1. アイテムはワールドエディタのアイテムタブから作る (`POST /api/world/items`)。
   説明を空にして file_path を渡すと、picture は `ensure_image_summary`、document は `ensure_document_summary` が

2. 所有者は world / building / persona / bag のいずれか。既定は `world` で、world 所有のアイテムは

3. 右サイドバーのアイテムをクリックすると中身が開く (`GET /api/info/item/{item_id}`)。
   document は本文、picture は画像 (`thumb=1` なら WebP サムネイル)、bag は中身の一覧。
   本文は同じモーダルから編集して上書きできる (`PUT /api/info/item/{id}/content`、版管理もバックアップも無い)。
4. 目のアイコンで `is_open` を反転すると、その部屋のペルソナのコンテキストに中身が載る

5. ペルソナ側は `item_move` / `item_view` / `item_annotate` の 3 スペルで拾う・置く・使う・見る・書き込む。
   結果は `item_location` 行の付け替えと、本人への `record_persona_event`、
   同室の他ペルソナへの `broadcast_item_event`、そして建物ログの note 行 (`heard_by` は空)。
6. アイテムやファイルは `saiverse://` URI で指せる。解決の入口は `GET /api/uri/resolve` と、
   ペルソナの `resolve_uri` スペル、フロントの `ContentViewerModal`。

### 3. 期待する結果の初稿

**根拠のある期待**

  **Close はユーザーの意思表示なので、機構が本文を再掲してその意思を裏切らない。**
- **(b)** 物が現れたら全文で、消えたら名前の一行で、開かれたら「(開かれた)」の出来事行と開いて初めて見える部分だけが、
  ペルソナに届く。同じ内容が二枚並ぶことは構造的に無い。
- **(c)** 文字と絵がはぐれない。「絵がある」と読めるとき、その絵が見える。
- **(d)** ペルソナの持ち物は移動に付いてくるが、部屋の性質ではないので部屋の様子の束には載らない。
- **(e)** `docs/reference/saiverse-uri.md` の表に載っている URI の形は、載っているとおりに答える。

**利用者のファイルは誰が読めるべきか (この設問への初稿)**

これは新しく決めることではなく、**製品が既に持っている 2 つの約束から導ける**と考える。

- 製品は「参照する主体によって読めるものが違う」という立場を既に取っている。
  ペルソナスコープの URI (message / memopedia / chronicle) は本人の記憶だけを返し、
  他人が引くと「他ペルソナの記憶は参照できません」で拒否する (`saiverse/uri_resolver.py:227-231`)。
- 製品は「利用者のファイルが置かれる場所」も既に定めている。アップロードは保存先とファイル名をサーバーが決め、
  クライアントのファイル名は拡張子の判定にしか使わない。パス構文を含むファイル名は 400、
  許可ルートの外は 403 (`api/file_safety.py:32-77`, `saiverse/file_policy.py:9-25`)。

したがって**正常な姿は「読む側も同じ境界に立つ」** — `saiverse://` の各族が指せる範囲は、
その族に割り当てられた保管場所の中だけであるべきで、URI に書かれた文字列がその外を指せてはならない。
これは既存の決定で表せるので、**未合意事項ではない**。

  item 参照にも同種の手当てが要るのではないか。

> **この流れは、まはーの原文により v0.4.0 以降へ回すための意図的な未配線と確定している。**
> 以下で「API はあるが画面から到達できない」と書く箇所は、欠陥ではなく**その意図の現れ**として読む。

### 1. 誰が何をしたいか

- **利用者** — 部屋に設置物を置き、センサーや外部の情報源を結び、その値を見たい。
- **ペルソナ** — 自分がいる部屋に何が設置されていて、その最新の値が何かを、部屋の様子の一部として知りたい。
  値が閾値を超えたら、それを出来事として受け取りたい。
- **運用者 (将来の想定利用者)** — ウェアラブルのコンパニオンアプリなど、外部のアプリから観測値を送り込みたい。

### 2. 始まりから結果までの流れ

1. Fixture (持ち運べない設置物) を Building に置く。`POST /api/observer/fixture` の upsert と 2 つの GET がある
   (`api/routes/observer.py:120-175`)。**更新も削除も API に無い。**
2. Observer (定期実行能力を持つ Fixture) を結ぶ。`POST /api/observer/config` の upsert のみ
   (`api/routes/observer.py:182-200`)。**取得も一覧も更新も削除も無い。**
3. `EXEC_KIND` が `tool` / `playbook` の Observer は、起動時の `observer_manager.start_pull_observers()`
   (`saiverse/saiverse_manager.py:530`) で EventScheduler に相乗りし、`INTERVAL_SEC` ごとに実行される。
   `push` の Observer は外部アプリが `POST /api/observer/{id}/push` を叩く (Bearer token 認証)。
4. どちらの経路も `record_metrics` に集まり、`observer_metrics` へ時系列で溜め、
   `fixture.STATE_JSON` に最新値をキャッシュする。
5. 直後に `_evaluate_notify_rules` (`saiverse/observer_manager.py:656-705`) が `NOTIFY_RULES_JSON` の
   `above` / `below` を判定し、当たったら `_notify_building` (`:707-728`) が Fixture の設置 Building へ
   host 行を挿入する。
6. 出口は 3 つ。**①利用者の画面** — 右サイドバーの「設置物」欄と設置物モーダル (`GET /api/info/details` の
   `state_json` を表で描く)。**②API** — `/api/observer/{id}/latest` と `/history/{metric}`。
   **③ペルソナ** — 部屋の様子の束の `fixture:<FIXTURE_ID>` パッケージ。

### 3. 期待する結果の初稿

**根拠のある期待**

- **(a)** Observer は環境側の設備であって主体ではない。観測と通知だけを行い、
  観測結果に対する判断・対応はペルソナ側の仕事。
- **(b)** 通知は既存の Building event のパイプラインに乗せる。Observer 独自の通知経路は作らない。
- **(c)** 実行は既存の `EventScheduler` に相乗りし、固定間隔 sleep ループを新設しない。Scheduler を塞がない。
- **(d)** ペルソナは、部屋にある設置物の名前・種別・説明と**最新観測値**を、部屋の様子の一部として受け取る。
  この経路は現在も生きている — `builtin_data/tools/get_visual_context.py:660-700` の `_render_fixture` が
  `STATE_JSON` を「最新観測値: key=値」の行として描き、`room_state_packages.md` §3 の族の表にも
  `fixture:<FIXTURE_ID>` が正式な一族として載っている。**私はこの関数を開いて確かめた。**
- **(e)** **設置物と定期観測を画面から作れないのは、v0.4.0 以降のリリースへ回すための意図的な未配線である。**

**調査担当の提案**

- **(f)** 閾値通知は「その部屋のペルソナに知らせる」ことを目的にした機構なので、
  届き先が空のままでは目的を果たさない。期待 (b) の「既存パイプラインに乗せる」は、
  乗せた先が届くことを前提にしている。FLOW-14 の共通議題 (聴衆を誰が決めるか) と同じ根の問い。
- **(g)** 配線するときには、**作った Observer を止める手段**が要る。現在は upsert しか無く、
  `ENABLED` を落とすには DB を直接触るしかない読みになる。

## FLOW-18: 世界の出来事が自動で何かを起こす

**対応する台帳項目**: `WORLD-39`, `WORLD-40`, `WORLD-20`, `WORLD-21`, `WORLD-41`

### 1. 誰が何をしたいか

- **利用者 (開発者モードで)** — 「こういう出来事が起きたら、こうする」を自分で決めたい。
- **ペルソナ** — 世界で起きた出来事を、自分に向けられた出来事として受け取りたい。
- **利用者 (ゲームの参加者として)** — Ruler (GM ペルソナ) が運営するゲームに参加し、
  その進行が自動で世界に反映されるのを体験したい。

### 2. 始まりから結果までの流れ

1. **ルールを作る** — 左サイドバー → システム → フェノメノン (開発者モードのときだけ導線が出る)。
   `/phenomena` 画面が `GET/POST/PUT/DELETE /api/phenomena/rules` を叩く。
   トリガー種別とフェノメノン名は登録済みのものだけを受け付け、JSON 欄には構文検査がある。
2. **発火する** — 世界の出来事が `SAIVerseManager._emit_trigger(TriggerType, data)` を呼ぶ。
3. **照合する** — `PhenomenonManager.emit` がトリガー種別一致 + `ENABLED` のルールを優先度順に引き、
   `CONDITION_JSON` の各キーを完全一致で照合する (値が null なら何でも通る)。
4. **引数を解決する** — `ARGUMENT_MAPPING_JSON` の `$trigger.<field>` をイベントの値に置き換える。
   それ以外はリテラル。
5. **実行する** — `PHENOMENON_REGISTRY` から実装を引いて呼ぶ (同期、または非同期ワーカー)。
   組み込みは `example_log` と `inject_persona_event` の 2 本 + 3 層読み込みで拡張されたもの。
6. **`inject_persona_event` の場合** — `record_persona_event` で `persona_event_log` に記録し、
   `pulse_dispatcher` へ schedule 優先度の実行を投げる。**ここで Pulse が起き、LLM 課金が発生しうる。**
7. **ゲーム (Region) の側** — `GameLifecycleService` の状態機械 (phase: playing / paused / …)。
   参加者が Region の外へ出ると自動ポーズ、全員が戻ると自動再開 (`on_entity_moved`)。
   phase 遷移とシーン変更は建物ログの host 行として流れる。

### 3. 期待する結果の初稿

**根拠のある期待**

- **(a)** Phenomena は世界側からのイベント入口で、世界の出来事とペルソナの行動を繋ぐ。
- **(b)** ゲームの進行は、参加者の移動という世界の出来事に自動で反応する。参加者が外へ出れば止まり、
  全員が戻れば再開する。
- **(c)** ゲームの phase 遷移とシーン変更は、**参加者と Ruler の記憶に届く**。
  `_emit_game_event` (`saiverse/game_lifecycle.py:481-527`) が `heard_by` に参加者リストと `ruler_id` を
  明示的に渡している。**私はこの関数を開いて確かめた。**
  → これは FLOW-14 の共通議題に対する、**「聴衆を渡している側」の実例**。
- **(d)** ゲームを画面から始められないのは、v0.4.0 以降のリリースへ回すための意図的な未配線である。

**調査担当の提案**

- **(e)** ルール作成画面が差し出すトリガーの選択肢は、**この世界で実際に起こりうる出来事**に限られるべきではないか。
  起こらないものを選べると、利用者は「作ったのに動かない」を自分の設定ミスとして探し続ける。
  CLAUDE.md の「把握可能性は設計制約」に照らすと、画面が嘘の選択肢を出すことは設計の側の負債。

### 6. 中断・失敗・再開 (この流れに実際に関わるもの)
