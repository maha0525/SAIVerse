# 群 E — 画面のない処理 (FLOW-24〜26)

対象コミット: `25ad75d6` (ブランチ `feature/chronicle-coverage-gaps`、これが HEAD)。
前回の棚卸しは `7d7214be` 時点なので、その後の 5 コミット (スルースと Chronicle の
レビュー消し込み) を踏まえて確認し直した箇所には、その旨を書いてある。

この群は画面を持たない。だから各流れの「結果」は、**利用者の請求書・ペルソナの記憶・
次に開いたときの世界の状態**という形で現れる。以下ではその形で書く。

## FLOW-24: 見ていない間にペルソナが動く

**対応する台帳項目**: `AUTO-01`, `AUTO-02`, `AUTO-03`, `AUTO-04`, `AUTO-07`, `AUTO-08`,
`AUTO-09`, `AUTO-10`, `AUTO-11`, `AUTO-13`, `AUTO-14`, `AUTO-31`

### 1. 誰が何をしたいか

結果を受け取る主体は三者いる。

- **利用者** — アプリを起動したまま画面を離れているとき、世界が勝手に壊れていないでほしい。
  そして自分が見ていない間に API の料金が発生するなら、**何のために・どれくらい・どうすれば
  止められるか**を知りたい。
- **ペルソナ** — 見られていない間も自分の時間が続いていて、次に話しかけられたときに
  その間のことを持っている。
- **リポジトリオーナー (まはー)** — 「v0.3 に判断点は一つも無い」と言い切れる状態で出荷する。

**v0.3 の線引きを最初に置く。** 「ペルソナが自分から考えて動く」駆動は、v0.3 では
**意図的に出荷していない**。`saiverse/autonomy_wiring.py:91` の定数
`AUTONOMOUS_DRIVING_SHIPPED = False` がそれで、唯一の判定関数 `is_autonomy_on()` が
この定数の間は常に False を返す。**これは壊れているのではなく、v0.3 の意図された姿である。**
以下は「v0.3 の姿」と「v0.4 で運転を配線したときの姿」を分けて書く。

### 2. 始まりから結果までの流れ

#### (a) v0.3 で実際に背景で走るもの

`SAIVerseManager.start()` (`saiverse/saiverse_manager.py:495-569`) が立てる順に並べると:

1. 実行台帳の起動時回復 (同期) → 60 秒周期の掃除 tick (`AUTO-12`。FLOW-25 で扱う)
2. ScheduleManager (アラーム) / PhenomenonManager / IntegrationManager を起動
3. EventScheduler の配車スレッドを起動 — 以降、時刻予約が発火し始める
4. pull 型 Observer の周期実行を登録 (`AUTO-10`)
5. フィード取得 — **起動直後に 1 回**、以後は既定 1800 秒周期 (`AUTO-11`)
6. 冷えたウィンドウの見張りを 600 秒周期で予約 (`AUTO-14`)
7. 止め具が掛かっている事実を INFO ログに 1 回だけ出し、各ペルソナの
   `ensure_autonomy_for()` を呼ぶ — **v0.3 では AutonomyManager が 1 本も立たない**
8. `server_start` トリガを発火 (`AUTO-09`)

これに加えて、会話が起きるたびに二つの予約が積まれる。

- **会話の沈黙タイマー** (`AUTO-07`、既定 30 分) — 発火しても会話状態を落とすだけで、
  LLM は呼ばない。
- **キャッシュの保温** (`AUTO-13`) — LLM 呼び出しが成功するたびに、TTL の残りが
  3 割になる時刻へ予約が積まれる。

#### (b) LLM の課金が起きる経路は、v0.3 では 3 系統ある

止め具は「駆動するか」の判定にだけ効く。次の 3 つはその判定を通らない。
**目的が違うので、扱いも一括にはできない。** それぞれ分けて書く。

| 経路 | 何のために動くか | 誰の何が変わるか |
|---|---|---|
| **アラーム** (`AUTO-05`、FLOW-21 が主担当) | 利用者が画面で作った予定の時刻にペルソナが喋る | ペルソナが発言し、記憶に残り、課金が発生する |
| **キャッシュの保温** (`AUTO-13`) | 次に利用者が話しかけたときの料金を安くする | 応答は捨てられ、記憶には何も残らない。課金だけが発生する |
| **冷えたウィンドウの先回り畳み** (`AUTO-14`) | 溜まった会話をあらすじに畳む作業を、キャッシュが冷えている今のうちに済ませる | ペルソナの記憶が整理される。課金が発生する |

**アラーム** — `saiverse/schedule_manager.py` の発火経路に `is_autonomy_on` の呼び出しは
1 件も無い (grep 済み)。判断点 Playbook (`judgment_day_open` / `judgment_day_close`) を
指定したものだけが `handle_scheduled_judgment` へ迂回し、そこで止め具に当たって止まる
(`schedule_manager.py:1130-1150`)。それ以外のアラームは v0.3 でも普通に鳴る。

**キャッシュの保温** — 発火側のゲートは `sea/runtime.py:1994` の
`if not bool(getattr(persona, "autonomy_enabled", False))` で、`is_autonomy_on` を
通っていない。予約が立つのはモデルのキャッシュ方式が `explicit` のときだけで
(`sea/session_lifecycle.py:1564`)、`builtin_data/models/` の 142 個のモデル定義のうち
`explicit` は **Anthropic の Claude 系 11 個だけ**だった。その既定 TTL は `5m` で、
`get_anchor_validity_seconds` は `5m` を 300 秒と読む (`session_lifecycle.py:851-869`)。
発火は `TTL × (1 - 0.3)` なので **210 秒後**、成功すると anchor を touch し直して
次の保温がまた予約される (`sea/runtime.py:2183-2192`) — つまり連鎖が続く。
連鎖が止まるのは、呼び出し失敗・anchor 失効・非 explicit への変更・自律 OFF のいずれか。

**冷えたウィンドウの先回り畳み** — 600 秒ごとに全ペルソナを巡回する。検査は読みだけで
LLM を呼ばず、条件が成立したペルソナだけを daemon スレッドへ逃がして編纂を走らせる
(`sea/session_lifecycle.py:4333-4354`)。条件は 4 つ揃ったときだけで、そのうち 2 つは
**利用者が画面で切れるトグル**だった (`cold_precompaction_status`、`:4356-4410`) —
「Chronicle 自動生成」と「自律行動中も記憶整理（Chronicle生成）を行う」の両方が有効で、
かつ全 anchor が冷え切っていて、かつ提示ウィンドウが (残す量 + 上限) の中間を
超えているとき。

### 3. 期待する結果の初稿

**根拠のある期待**

1. **v0.3 では、ペルソナが自分の判断で動き出すことは一度も起きない。** 起床・就寝・
   セッション終了・イベント到着の 4 つの判断点、見張り、時間割のコマは 1 回も発火しない。
2. **実イベント (外部からの出来事) は落ちない。** 判断点を経由しなくなるだけで、
   v0.2 と同じ直接応答の経路で応対する (`AUTO-08`)。
3. **会話・記憶の整理・手帳・沈黙タイマーは止まらない。** 止め具は「自分から考えて動くか」
   にだけ効き、会話の相手をすることには効かない。
4. **背景で通っていない処理があるなら、利用者に分かる状態で明示され、後から通せる。**
   これはスルースの被覆について 2026-09-08 にまはーが出した制約条件で、原文が残っている。

**調査担当の提案 (根拠のある期待と混ぜないこと)**

5. **「見ていない間に課金が起きる処理」は、利用者が一覧で見られるべきではないか。** 現状、
   保温の使用量は使用状況ページに `cache_keepalive` という英字の識別子のまま出る
   (`api/routes/usage.py:290-297` の表示名辞書には `persona_speak` と
   `memory_weave_generate` の 2 件しか登録が無く、未登録のカテゴリは識別子がそのまま
   表示される)。記録は残っているので、必要なのは新しい機構ではなく**表示名と説明**である、
   というのが私の見立て。
6. **止め具の「止めるもの / 止めないもの」の一覧に、保温と先回り畳みを書き足すべきではないか。**
   どちらも現在はどちらの側にも書かれていない (下の §5 参照)。

### 5. 現状との差

**既知の不一致**

1. **保温が自律ゲートを通っていない (intent の主張とコードの食い違い)。**
   `autonomous_behavior_v3.md` §11.1 は「ライフの設定が無い世界で ON/OFF の差が実際に
   出るのは**一箇所だけ** (実イベントへの応対)」と書く。しかし `sea/runtime.py:1994` は
   駆動 (LLM 呼び出し) の判定でありながら `persona.autonomy_enabled` を直読みしている。
   したがって差が出るのは 2 箇所である。前回の棚卸し §3-1 と同じ指摘で、`25ad75d6` 時点でも
   コードは変わっていないことを確認した。
2. **「v0.3 では自律の ON/OFF を切り替える手段が無い」という記述が、実装と食い違う。**
   `autonomy_wiring.py:76-79` の注記と intent §11.1 はどちらも「v0.3 ではその切り替え UI を
   隠したので、新しいユーザーの世界は『既定で自律 ON、OFF にする手段が無い』状態になる」と
   書く。しかし **グローバル設定 → ワールドエディタの AI 編集にそのスイッチがある**
   (`frontend/src/components/settings/WorldEditor.tsx:655-663`、ラベルは「自律行動 /
   有効（自分から考えて動く）」)。保存経路 (`manager/admin.py:1331`) は稼働中のペルソナの
   `autonomy_enabled` も同時に書き換える。
   **利用者から見た帰結**: v0.3 においてこのスイッチが実際に変える唯一のものは、
   キャッシュの保温が走るかどうかである。他はすべて定数の止め具が先に止めている。
   つまり「自分から考えて動く」というラベルのスイッチが、実際には「見ていない間に
   キャッシュ代を払い続けるか」のスイッチとして働いている。
3. **`docs/user-guide/persona-settings.md` が現状を説明していない。** この文書は
   「アクティビティ状態（`ACTIVITY_STATE`）」の 4 値 (Active / Idle / Sleep / Stop) を
   表で説明しているが、この列は 2026-07-14 に解体されて DB から落ちている
   (`database/models.py:133` のコメントに経緯がある)。また「自律行動マネージャー」
   「応答待ち Track 自動 pause 閾値」を挙げる一方で、**v0.3 で実際に背景の課金を左右する
   3 つのスイッチ (自律行動 ON/OFF・キャッシュ維持・自律行動中も記憶整理) のうち
   2 つを載せていない**。利用者が「見ていない間に何が動くのか」を調べにいく先が、
   いま存在しない概念を説明している。
4. **Observer の playbook 実行は、文書が動くものとして書き、実装は debug ログだけで終わる。**
   `docs/intent/observer.md:128/:235` と `saiverse/observer_manager.py:590-591` の食い違い。
   前回の棚卸し §3-3 と同じ。まはーの「意図的に配線を繋いでいない」の一件に当たる。

**静的な疑い (コードを読む限りそう見えるが、実行して確かめていない)**

5. **Observer の周期実行は DB エラーで永久に止まる。** `_execute_pull`
   (`saiverse/observer_manager.py:577-592`) は `self.manager.SessionLocal()` を `try` の
   **外**で呼び、`try` の中身は `finally: db.close()` しか持たない。したがって
   `SessionLocal()` や `db.query(...)` の例外は `schedule_periodic` の wrapper へ届き、
   その wrapper は「callback が例外を投げたら再 schedule しない」契約
   (`saiverse/event_scheduler.py:283-299`) を持つ。利用者から見ると、その観測が
   ログ 1 行だけ残して黙って止まり、再起動するまで戻らない。
6. **Pulse の待ちキューの上限 (10 件) は、数値そのものより「捨てたことが記録と食い違う」
   ことの方が効く。** 詳しくは §8 の「決める必要がある点」に書いた。

**まだ追跡していない境界**

- 実イベント (`inject_persona_event`) を実際に撃つ Phenomenon ルールが標準構成に
  存在するかは、DB の `phenomenon_rule` 行に依存するので静的には決まらない。同梱の
  外部統合実装はゼロ (`saiverse/integrations/` は `base.py` のみ) なので、既定の
  インストールでは撃つ者がいない可能性が高いが、**未確認**。
- 保温 1 回の実際の課金額。キャッシュのヒット率と窓の大きさ次第なので、静的には出せない。
- 先回り畳みの中身 (`run_cold_precompaction` → Metabolism の全経路) は記憶領域 (FLOW-09) の担当。

### 6. 中断・失敗・再開

この流れに実際に関わるものだけを書く。

- **予約はすべてプロセス内のメモリにある。** EventScheduler は heap をメモリに持つので、
  再起動すると保温・沈黙タイマー・先回り畳みの予約はすべて消える。再確立は個別の経路が
  担う (アラームと Observer とフィードは起動時に登録し直す。保温と沈黙タイマーは
  次の会話が張り直す)。
- **会話の沈黙タイマーの再確立は、v0.3 では常に何もしないで終わる。** 前回の棚卸しは
  `rearm_conversation_timeout_on_load` の読み元を「未確認」としていたが、
  `saiverse/user_conversation.py:540-553` の docstring に決着が書いてあった —
  「会話状態はプロセス内のメモリが持つので、再起動した時点でどのペルソナも
  『会話していない』。張り直すべき待ちが構造上存在しない」。**この境界は解決済み。**
- **周期処理が例外で止まったときの扱いが 3 通りに分かれている。** 実行台帳の掃除 tick は
  各ステップを個別に try で包んで周期を守る (`execution_ledger_wiring.py`)。先回り畳みの
  tick は `finally` の中で次回を積むので例外でも続く (`session_lifecycle.py:4353-4354`)。
  Observer だけがこの手当てを持たない (上の §5-5)。
- **失敗が利用者に届く道が無い。** 上の 3 つのどれが止まっても、残るのはログ 1 行だけで、
  画面には何も出ない。

### 7. 次に使う機能・共有する状態

- **FLOW-21 (アラーム)** — アラームは v0.3 で唯一「ペルソナが自分から喋る」出荷済みの
  経路なので、この流れと表裏になる。止め具との関係の未決 (§8-1) は共通議題。
- **FLOW-09 (会話しながら記憶が自動で整理される)** — 先回り畳みは Metabolism の
  引き金の一つで、その先はすべて FLOW-09 の担当。
- **FLOW-22 (費用と使用量を把握する)** — 保温・先回り畳み・アラームの課金はすべて
  `LLMUsageLog` に category 付きで記帳される。「見ていない間の課金」が利用者に届くのは
  この画面だけなので、表示名の欠落 (§3-5) はこちらの流れの問題でもある。**共通議題**。
- **FLOW-17 (設置物と定期観測)** — Observer の設定と閲覧はそちら。この流れが扱うのは
  「登録された観測が周期で回るか」だけ。
- **FLOW-25 / FLOW-26** — 予約がメモリにしか無いという性質は、起動と終了の両方に効く。

### 8. 決める必要がある点

1. **アラームは「自律行動」なのか。** — **未合意 (共通議題: FLOW-21)**
   `autonomous_behavior_v3.md` §11 が「未決」と明記したまま、実装は「アラームは常に鳴る」に
   倒れている。裁定の記録は見つからなかった。利用者から見た争点は「自律行動を無効にした
   ペルソナのアラームは鳴るべきか」で、ワールドエディタのスイッチのラベル
   (「自分から考えて動く」) の意味に直結する。

2. **キャッシュの保温は、止め具のどちら側に置くか。** — **未合意**
   目的からすると保温は「利用者の次の一言を安くする」ための費用であり、ペルソナが
   自分から動くことではない。しかし `cache_lifecycle_control.md` §8.5 は保温を
   **自律側の機構**として設計しており、会話 UI 側には意図的に自動延長を置いていない。
   つまり「保温は自律の領域である」という設計上の位置づけと、「v0.3 では自律を出荷して
   いない」という線引きが正面から当たっている。決めるべきは数値ではなく、
   **保温をどちらの領域の費用と見なすか**である。
   なお「記録・明示・選択」の三つは、保温についてはすでに次の状態にある —
   記録は済んでいる (`category="cache_keepalive"` で使用量に記帳、`sea/runtime.py:2165`)、
   選択もできる (ペルソナ設定の「キャッシュ維持」を OFF にできる)。
   足りないのは明示だけで、それは §3-5 の表示名の話に落ちる。

3. **先回り畳みについて、まはーの判断が要るかどうか。** — **要追加確認、判断は不要の見込み**
   目的は費用の最適化で、`arasuji_levels.md` §14-1 が「編纂の総作業量は畳む時期によらず
   不変」と根拠を書いている。利用者側のスイッチも 2 つある。止め具の「止めないもの」に
   ある「Metabolism のスルース」に含まれると読めば、現状は intent と整合する。
   **ただし** UI のラベルが「**自律行動中も**記憶整理を行う」で、v0.3 に自律稼働は
   存在しないので、利用者はこのスイッチを「自分には関係ない」と読む。ラベルと説明文を
   v0.3 の実態 (= 画面を見ていない間の巡回) に合わせるかどうかは、文言の判断としてまはーに要る。

4. **Pulse の待ちキューの上限 10 件。** — **数値は未合意ではない。記録の食い違いが本題。**
   まず到達しうるかを確かめた。キューに入るのは `on_blocked == "wait"` の種別だけで、
   それは **`schedule` (アラーム) だけ**だった (`sea/pulse_controller.py:48-72`)。
   ユーザー発話と自律 Pulse は待たずに捨てられる。したがって 10 件に届く状況は
   「1 体のペルソナに対して、そのペルソナが塞がっている間にアラームが 11 回鳴る」場合に
   限られる。アラームは秒単位の間隔で作れる (`schedule_manager.py:961-970` が
   「N 秒ごと」を文面化する) ので、短い間隔のアラームを作った利用者では到達しうる。
   **本題は数値ではなく、超えたときの扱いである。**
   - 捨てられるのは**いちばん古い**要求で、記録は `LOGGER.error` の 1 行だけ、
     利用者への通知は無い (`pulse_controller.py:418-430`)。
   - 一方 ScheduleManager は、キューに入った時点でその発火を `accepted` (前進) と
     分類する。理由は「schedule は on_blocked="wait" — queued は queue に残っていて
     消えないため」と明記されている (`schedule_manager.py:1041-1058`)。
   - **その前提はキュー上限では成立しない。** 捨てられたアラームは「届いた」と記帳された
     まま二度と鳴らず、再試行も来ない。終了処理中も同じで、キューに残った要求は
     `_process_queue` が繰り上げを拒んで破棄される (`pulse_controller.py:607-633`)。
   決めるべきは「10 を何件にするか」ではなく、**捨てた事実を台帳と利用者へどう返すか**。
   これは静的な読みなので、実機で 11 件が積まれる状況の再現は `要追加確認`。

5. **止め具の「止めるもの / 止めないもの」の一覧に、保温と先回り畳みを書き足すか。** —
   **未合意 (文書側の宿題)**
   現在どちらも一覧のどちらの側にも書かれていない。まはーの「何も書かれてないのは
   今みたいに混乱を招くから問題だね」がそのまま当たる。

6. **Observer の周期が DB エラーで永久に止まること。** — **不具合の疑い。まはーの判断は不要。**
   同じ危険への手当てが実行台帳の掃除 tick には入っており (`execution_ledger_wiring.py` が
   `schedule_periodic` の「例外で永久停止」契約への対処だと明記している)、Observer にだけ
   無い。同じ理由が当てはまる隣を直す話であって、決める余地は無いと見ている。

   **EventScheduler 停止 (待っていた予約は破棄)** → PhenomenonManager 停止 →
   全ペルソナのセッションメタ保存 (`saiverse/saiverse_manager.py:1100-1175`)

**①を最初に置く理由がコメントに書かれている** (`main.py:566-570`) — 途中まで喋った本文を
確定させて記憶へ書く後始末は生成スレッドの中で走るので、MCP や llama-server を先に
壊すと、壊れた道具の上で後始末が走る。

#### 8 秒が何の締め切りなのかを正確に書く

**8 秒は「LLM が答え終わるまでの待ち時間」ではない。** `PulseController.shutdown`
(`sea/pulse_controller.py:191-275`) は、まず走行中の全要求に取り消しを刻み、そのうえで
**後始末が終わって台帳から席が消えるまで**を最大 8 秒待つ。後始末の中身は
`_settle_placeholder_on_beat_death` (`sea/runtime_llm.py:3389-`) で、次の 4 つを揃える
(同 `:2008-2027` の説明):

1. 下書き行を本文で確定させる (消滅を防ぐ本体)
2. 「言い切っていない」印を画面へ渡す
3. 言いかけた本文を本人の記憶へ書く (建物の記録には残るのに本人だけが覚えていない、を防ぐ)
4. 中断があった事実を建物の記録へ置く (`host` 役で、入退室の通知と同じ道)

**締め切りを過ぎたら何が起きるか。** WARNING を出して先へ進む。確定しなかった下書き行は
`content` が空のまま DB に残り、**履歴 API も取り込みも空の行を除外するので、画面にも
記憶にも出ない = 発言が丸ごと消える**。この形の消失は
`docs/issues/orphaned_streaming_placeholder_cleanup.md` に記録があり、
2026-05-19〜08-26 の 3 ヶ月で 32 件が実際に起きていた。

### 3. 期待する結果の初稿

**根拠のある期待**

1. **言いかけた発言は、言いかけたまま残る。** 中身が空の行として消えるのではなく、
   途中までの本文が確定し、「言い切っていない」印が付き、本人の記憶にも入り、
   建物の記録には中断があった事実が置かれる。これは既に実装され、
   `docs/issues/orphaned_streaming_placeholder_cleanup.md` が
   「node() は未確定の下書き行を残して終わらない」を不変条件として掲げている。
2. **機構が足した注記を、本人の言葉として書かない。** 中断の通告は `host` 役で建物の
   記録へ置き、取り込み側が `user` + `<system>` へ組み替えてから各ペルソナへ配る。
   「本人の発言そのものには一切手を入れない。機構が足した注記は、ペルソナが自分の文体として
   模倣し始めるため、独立した一行として後ろに置く」(`sea/runtime_llm.py:2029-2030`)。
3. **後始末を最初に走らせる。** 道具を壊す前に締める。
4. **既に残っている空の行は消さない。** 2026-08-26 のまはー裁定で「そのまま残す」と決まり、
   代わりに「空の発言として読み込まれたり UI に出たりしないこと」を保つ、と整理されている
   (`docs/issues/orphaned_streaming_placeholder_cleanup.md`)。

**調査担当の提案 (根拠のある期待と混ぜないこと)**

5. **締め切りに間に合わなかったことは、利用者かペルソナのどちらかに届くべきではないか。**
   現状の唯一の痕跡は backend.log の WARNING 1 行で、次に開いたときには何も残らない。
   §8-1 に書く。

### 6. 中断・失敗・再開

- **終了処理は一度だけ走る** (`shutdown_called` の二重実行ガード)。FastAPI の lifespan には
  終了処理を置かない、と明記されている (「二本目を作ると順序が絡む」)。
- **待っていた予約は破棄される。** EventScheduler の停止で、保温・沈黙タイマー・
  先回り畳み・Observer・フィードの予約が一括で消える。再確立は次の起動 (FLOW-25) が担う。
- **待ちキューに残っていたアラームは破棄される。** `_process_queue` は終了処理中なら
  繰り上げを拒む (`sea/pulse_controller.py:607-633`)。FLOW-24 §8-4 に書いた
  「台帳は `accepted` と記帳している」との食い違いは、ここでも同じ形で出る。**共通議題**。
- **llama-server は「idle と証明できたときだけ」止める** (`AUTO-30`)。証明できない
  (`unknown`) ものは決して止めない。終了時は `shutdown_all()` で一括して止める。
- **次の起動で、空の下書き行を掃く処理は無い。** 候補として検討されたが採られなかった
  (issue の「直し方の候補」3)。既存の行は履歴 API と取り込みの両方が content 空を
  除外するので、画面にも記憶にも現れない。

### 7. 次に使う機能・共有する状態

### 8. 決める必要がある点

1. **アプリを閉じたとき、締め切りに間に合わなかった発言をどう扱うか。** — **未合意**
   これは「8 秒を何秒にするか」ではない。仕組みはすでに、間に合った回については
   十分に丁寧である — 途中までの本文を確定し、言い切っていない印を付け、本人の記憶へ書き、
   建物には中断があった事実を置く。**間に合わなかった回だけが、その全部を受け取れずに
   消える。** そして消えたことは backend.log の WARNING 1 行にしか残らず、次に開いた
   利用者にもペルソナにも届かない。
   まはーの原則「止めるのではなく、記録し、明示し、選択してもらう」を当てるなら、
   ここで足りないのは**明示**である。ただし何をどこに出すかは判断が要る —
   建物の記録に置けば、それはペルソナの記憶へ写る (2026-08-23 の裁定により、
   建物ログの `host` 行はペルソナの記憶へ自動で写る)。つまり「機構の失敗を
   ペルソナに読ませてよいか」という問いになる。**これはまはーの判断が要る。**
   なお 8 秒という数値そのものは、決め直す必要が薄いと見ている。締め切りが効くのは
   プロバイダが固まった回だけで、そこでは 8 秒を 30 秒にしても結果は同じ
   (待たされる時間が延びるだけ) になる可能性が高い。**ただしこれは静的な読みで、
   実測していない (`要追加確認`)。**

2. **スルースの飛ばしの閾値を、モデルのコンテキスト長から導出する形に戻すか。** —
   **未合意 (ただし論点は数値ではない)**
   `sluice_coverage_gaps.md` の経緯が「intent からの差分」として明示的に記録している
   ので、これは「出典の無い定数」ではなく「意図的に単純化した代役」である。
   決めるべきは 10 万という数字ではなく、**モデルごとに違う容量を 1 つの固定値で
   代表させ続けるか**。利用体験への効き方は明確で、閾値を超えた回はスルースを飛ばし、
   飛ばした範囲は `sluice_skipped_spans` に記録される。記録が書けなければ退場を止める
   (fail-closed)。**つまり「記録」の脚はすでに立っている。**
   立っていないのは「明示」と「選択」で、それは第二段 (期間を選べる UI) の宿題として
   同じ設計書に書かれている — **したがってこれは未合意ではなく、着手待ちである。**

3. **Metabolism の 3 つの弁 (600 秒 / defer-to-hot / 1.5 倍) を画面に出すか。** —
   **要追加確認**
   3 つとも env でしか変えられず、画面には出ない。ただし利用者が触りたくなる場面が
   実在するかを確かめていない (レート制限に当たった利用者が 600 秒を短くしたいと
   思うか、など)。まはーの判断へ回す前に、そこを確かめるべきだと考えている。

4. **Chronicle の束ねの「1 呼び出し 3 件」について。** — **判断は不要と見ている**
   守る対象 (承認・課金見込みを実行が超えない) が明示されており、利用者には承認件数が
   見えている。`7d7214be` が呼び直しの欠陥を直したので、承認した件数は実行されるように
   なった。残るのは完了報告が内訳を言うかどうかで、それは
   `chronicle_coverage_gaps.md` の新設項目として既に挙がっている。

5. **`manager.shutdown()` の最後の保存が、途中の失敗で飛ぶこと。** —
   **不具合の疑い。まはーの判断は不要と見ている。**
   同じ形の手当て (各ステップを個別に try で包む) が実行台帳の掃除 tick には入っている。
   ただし §5-2 に書いたとおり、失われるものの大きさを確かめていないので、
   優先度の判断には `要追加確認` が残る。
