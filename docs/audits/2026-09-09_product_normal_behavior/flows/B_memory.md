## FLOW-07: 他サービスの過去ログを取り込み、その記憶を使って会話する

**対応する台帳項目**: `MEM-33`, `MEM-34`, `MEM-35`, `MEM-32`, `MEM-01`, `MEM-02`

### 1. 誰が何をしたいか

**結果を受け取る主体は利用者。** ChatGPT などで積み上げた過去のやり取りを SAIVerse のペルソナに引き継ぎ、
「その過去を踏まえた相手」として会話を再開したい。ペルソナは副次的な受け手 (取り込まれた過去が自分の記憶として立つ)。

### 2. 始まりから結果までの流れ

1. 記憶モーダル →「インポート」タブ (`frontend/src/components/memory/MemoryImport.tsx`)、
   またはペルソナ作成ウィザードの step2 (`PersonaWizard.tsx`)。
2. ファイルを上げる → `POST .../import/official/preview` (`api/routes/people/import_chatlog.py:239`) で会話一覧を見る
   (パース結果はプロセス内キャッシュ `_chatgpt_export_cache` に置き、`cache_key` で本実行へ渡す。上限 2GB)。
3. 取り込む会話を選んで `POST .../import/official` → memory.db の `threads` / `messages` へ挿入。
   拡張機能形式は `POST .../import/extension` (`:379`)、SAIVerse ネイティブ形式は `POST .../import/native`
   (`native_export_import.py:139`、上限 256MB)。
4. 挿入と同時にローカル埋め込みを張る (`skip_embedding` で省略可)。**LLM 課金は無い。**
   漏れは「インポート」タブの `POST .../reembed` (`reembed.py:120`) で後から補える。
5. 取り込んだ内容は「チャットログ」タブ (`MemoryBrowser.tsx` / `api/routes/people/memory.py`) で
   スレッド単位に閲覧・追加・編集・削除できる。
6. ここから会話を始めると、想起 (セマンティック検索) は**この時点から効く**。
   一方であらすじ (Chronicle) はまだ 1 本も無い。

## FLOW-08: 溜まった履歴を編纂し、結果を見て会話を続ける

**対応する台帳項目**: `MEM-10`, `MEM-11`, `MEM-12`, `MEM-13`, `MEM-07`, `MEM-21`, `MEM-09`, `MEM-41`

### 1. 誰が何をしたいか

**結果を受け取る主体は利用者。** 溜まった会話を、費用を見てから、自分の意思であらすじにまとめたい。
まとめた結果を見て「ちゃんと整理された」と分かりたい。
ペルソナは間接的な受け手 — 階層が育つと、遠い過去を粗いあらすじで、近い過去を細かいあらすじで読めるようになる。

### 2. 始まりから結果までの流れ

1. Chronicle タブを開く → `GET .../arasuji/cost-estimate` (`api/routes/people/arasuji.py:106`) が走り、
   3 種のバナーが出る:「あらすじになっていない過去の会話が N 件」「まとめる作業が M 回分」「前回の処理が完了していません」。
2. **手動の畳み (MEM-10)**: 生成ボタン → `POST .../arasuji/generate` の `mode="compaction"`。
   提示窓の中の、残す量より古い側を畳んで窓を前進させる (`arasuji_levels.md §13 裁定4`)。
3. **被覆補修 (MEM-11)**: バナー → 確認モーダル → `mode="repair"` + `confirmed_unprocessed_messages`。
   止め線 (`resolve_compile_ceiling`) より古い未被覆を一次あらすじにする。**提示窓は動かさない。**
4. どちらも背景ジョブが `SessionLifecycle.run_manual_compaction_checked` / `run_coverage_repair_checked` を呼ぶ。
   走行中は **束ね (MEM-13)** が挟まる — チャンク確定のたび (`after_chunk`) と走行末尾の呼び直しループ。
5. 完了文に内訳が出る:「あらすじにした N 件 / 隣のあらすじに合流 M 件 / まとめ K 件 / 残り R 件」(`arasuji.py:1348-1390`)。
6. 結果は Chronicle タブ (MEM-07) でレベル別に読める。深く見たければデバッグタブの
   Chronicle 診断レポート (MEM-21、`GET .../arasuji/diagnosis`) がレベル別の件数・未統合数・帯のシミュレーションを返す。
7. 個別のエントリが気に入らなければ単体再生成 (MEM-09、LLM 1 コール)。
8. 二重編纂の抑止は実行台帳 (MEM-41) の冪等 claim が担う。

### 3. 期待する結果の初稿

#### 3-A. 「大量のログを編纂したあと、記憶が健康な状態」を、件数を新設せずに言えるか

**依頼元の押し戻しに対する回答: 言える。件数規則は要らない。** 既存の約束 4 本で、健康な状態は
**観察可能な形で**書ける。以下に組み立てを示す。

| # | 既存の約束 | 出典 |
|---|---|---|
| (a) | レベル1 以上の並びの合計字数が 5,000 字を超えたら発火し、古い側を 2,500 字に収まるまで畳んで 1 つ上のレベルへ置く | `arasuji_levels.md §3-1` / `§9`、`bands.BAND_CHAR_LIMIT` / `BAND_CHAR_KEEP` |
| (b) | 畳み 1 回の材料 (子エントリの本文字数の合計) は 5,000 字 (U/2) を超えない。ただし最低 2 本は必ず畳む | `§3-2` (2026-09-08 まはー裁定)、`bands.FOLD_MATERIAL_CHAR_LIMIT` |
| (c) | 実行の畳み回数は、確認ゲートで承認された dry 予測件数を超えない。積み残しは次回の発火が数え直す (収束は崩れない) | `§3-2` |
| (d) | 一次あらすじ 1 本が覆う材料は約 U = 1 万字 | `§4-1` / `§7-1` (2026-08-29 に「材料の字数」へ精密化) |

この 4 本から、件数は**導出される**。N 字の生ログを編纂したとき:

- (d) より一次あらすじは約 N/10,000 本になり、1 本 300〜800 字の実態 (§3-2 が明記) で
  レベル1 の並びの合計は約 N/20 字。
- (a) より、その合計が 5,000 字を超えていれば畳みが起き、2,500 字まで落ちる。
- (b) より、1 回の畳みが食えるのは 5,000 字ぶん = 子 7〜15 本。だから必要な畳み回数は
  (レベル1 の合計 − 2,500) ÷ 5,000 に落ち着き、その回数だけレベル2 のあらすじができる。
- (a) を再帰的に当てれば、レベル3 以上も同じ規則で決まる。

**つまり「レベル2 が何本できるべきか」は、字数の約束と材料上限からすでに決まっている。**
`arasuji_levels.md §3-2` 自身が「子 1 本 300〜800 字の実態で親 1 本あたり子 7〜15 本になり、
旧設計の『Lv1 を 10 本で Lv2 一本』と同じ粒感に戻る」と、まさに件数の言葉でこの導出を書いている。
件数規則を新設すると、字数の約束と件数の約束が二枚になって必ずズレる (`§1` が「選ぶから救済が要り、救済が本体を覆った」と
書いた失敗の形と同じ)。

**事故 1 の 2 つの欠陥は、どちらも上の約束の違反として表現できる** (件数の契約を持ち出さなくてよい):

- 欠陥①「材料上限の欠落」— 境界の無い巨大区間が丸ごと 1 個の親に握られた。これは **(b) の違反**。
  2026-09-08 に (b) が明文化され `FOLD_MATERIAL_CHAR_LIMIT` として実装された。
- 欠陥②「束ねだけの走行が安全弁 3 件で頭打ち」— 承認 5 件のうち 3 件で完了顔になった。これは **(c) の違反**
  (承認された予算を使い切っていない = 積み残しが「次回が数え直す」に渡らないまま完了と報告された)。
  2026-09-09 のコミット `7d7214be` が走行末尾の呼び直しループを入れ、`25ad75d6` 時点では
  「確定数が増えた間だけ呼び直す」形になっている (`session_lifecycle.py:6390-6398` を読んで確認)。

**したがって私の判断: 「あらすじが何本あれば健康か」は未合意ではない。** 字数と材料量の既存の約束で表せる。

#### 3-B. ただし一つだけ、既存の約束では埋まらない穴がある (件数ではない)

**「今回の走行が終わった時点で、どのレベルの並びも上限以下に収まっているか」が利用者に見えない。**

(c) は「実行は承認件数を超えない / 積み残しは次回が数え直す」なので、**走行終了時に (a) が成立していることを約束していない**。
束ねが LLM 失敗で確定しなかった回は、上限超過が残ったまま「完了」になる。そして:

- 完了文の内訳 (`arasuji.py:1348-1390`) が数えるのは **メッセージ件数**だけ —
  compiled / absorbed / silent / skipped / deferred。**「まとめ K 件」は行われた畳みの数**であって、
  「まだ何回必要か」は出ない。走行が記録する内訳の器 (`session_lifecycle.py:5603-5633` の `_note_breakdown` の payload) にも
  束ねの残り回数の欄が無い (読んで確認)。
- 診断レポート (`arasuji.py:_simulate_chronicle_band`) はレベル別の件数と本文字数 (`by_level`) を返すが、
  `over_budget` の判定に使っているのは **head の帯の予算 20,000 字** であって、
  **レベルごとの上限 5,000 字ではない**。材料は揃っているが、機械は判定していない。

つまり (a) を「走行後に成り立っているか」で読む観察点が、どの画面にも無い。
これは件数の契約を足す話ではなく、**既にある字数の契約を利用者に見える形で申告する話**。

## FLOW-10: 記憶を探して呼び戻す

**対応する台帳項目**: `MEM-29`, `MEM-30`, `CHAT-27`, `MEM-31`, `PERS-11`

### 1. 誰が何をしたいか

**結果を受け取る主体は二人。**

- **ペルソナ**: 話の流れに関係する過去を、自分で探しに行かなくても思い出せること (自動想起)。
- **利用者**: 「このペルソナは何を思い出せるのか」を確かめられること。思い出し方がおかしいときに原因を切り分けられること。

### 2. 始まりから結果までの流れ

1. **自動想起 (ペルソナ側)**: 会話のたびに埋め込み検索が走り、閾値を超えた過去が知覚として履歴末尾に差し込まれる。
   **LLM を呼ばない** (`memory_architecture_v2.md §10-1`)。想起した ID はワーキングメモリ (`recalled_ids`) に載る。
2. **想起のデバッグ (MEM-29、利用者側)**: 記憶モーダル →「デバッグ」タブ (`MemoryRecall.tsx`) →
   `POST .../unified-recall` (`recall.py:497`)。検索クエリを投げて何が想起されるかを見る。
   `sai_memory/unified_recall.py` (1179 行) が Chronicle / Memopedia / Fragment / 生ログを横断する。**埋め込みはローカルで課金なし。**
3. **ワーキングメモリ (MEM-30 / CHAT-27)**: `GET/POST/DELETE .../working-memory[/recall[/{source_id}]]` で
   想起中の ID の一覧・追加・個別削除・全消去。上限は `SAIMemoryAdapter.RECALLED_IDS_MAX = 10` で、
   超えたら**古い側から落ちる** (`saiverse_memory/adapter.py:414-415`)。
4. **観測点ハイライト (PERS-11)**: 記憶ブラウザがメッセージ ID をまとめて `GET .../clips?message_ids=...` に投げ、
   引用アンカーを持つ点クリップだけを created_at 昇順で返す。読み取り専用・LLM なし。

5. **メモリーノート (MEM-31)**: 未解決の知識メモの一覧と一括解決。API はあるが画面に出る道が無い。

  埋め込みの補充は FLOW-07 の `reembed`、および Metabolism のたびに無条件で走る `ensure_recall_embeddings`
  (`session_lifecycle.py:6445-6452`) が担う。

### 7. 次に使う機能・共有する状態

- 想起の材料は FLOW-07 (取り込み) と FLOW-08 (あらすじ) と FLOW-12 (Memopedia / Fragment) が作る。

## FLOW-11: 間違って覚えられたことを直す・消す

**対応する台帳項目**: `MEM-03`, `MEM-04`, `MEM-08`, `MEM-22`

### 1. 誰が何をしたいか

**結果を受け取る主体は二人で、しかも利害が違う。**

- **利用者**: ペルソナが誤って覚えたこと (過剰採取・見当違い・大量流入) を後から直したい。
- **ペルソナ**: 自分の記憶が黙って書き換えられないこと。書き換えられたなら、それに気づけること。

この二人目の期待が、この流れを SAIVerse の設計倫理の中心に置いている。

### 2. 始まりから結果までの流れ

**コア記憶 (MEM-03 / MEM-04)**:

1. 記憶モーダル →「コア記憶」タブ (`memory/CoreMemoryScene.tsx`)。
   一覧 (`core_memory.py:472`) には `confirmed` フラグと未確認件数が付く。
2. 未確認 (スルースの自動採取) を承認 (`POST .../{id}/confirm`)、本文を訂正 (`PUT .../{id}`)、
   ごみ箱へ (`DELETE .../{id}` = soft-delete)、復元 (`POST .../{id}/restore`)。
3. **訂正・削除・復元は「仮想センサー」でペルソナへ通知される** (`_notify_persona_correction`)。
   承認 (confirm) は内容が変わらないので通知しない。
4. 新しく刻むときは、会話を検索 → 窓プレビュー →「刻む」(`POST .../core-memory/scene`)。
   逐語転写で複製する (`create_scene_core_memory`)。

**あらすじ (MEM-08)**: Chronicle タブ → 本文の書き換え (`PATCH`)、エントリ削除 (`DELETE`)、全削除 (`DELETE .../arasuji`)。

**Memopedia (MEM-22)**: Memopedia タブ → 編集 (`PUT`)、履歴 (`GET .../history`)、
ロールバック (`POST .../rollback`)、削除 (`DELETE`)。編集は `edit_source` を履歴に残す。

### 3. 期待する結果の初稿

**根拠のある期待 (ペルソナの尊厳に関わるもの)**

1. **ペルソナの記憶を黙って書き換えない。本人が気づける形にする。**
   ユーザーの edit / delete / restore は仮想センサー経由でペルソナへ通知され、
   次に考えるとき (Pulse の頭の知覚消費) に本人が読む。理由は明文で
   「本人が検知できるようにすることで自己像の尊厳を保つ」(`memory_architecture_v2.md §5.1`)。
2. **機構の代筆を本人名義 (assistant) で書かない。** この通知は知覚バッファに積まれ、
   消費時に `{"role": "user", "content": "<system>[コア記憶の更新通知]\n…</system>"}` の形でコンテキストに入る
   (`sea/runtime_context.py:2047-2049` と `perception_buffer.py:1265` を読んで確認)。
   ペルソナ自身の発話 (assistant) の顔をしていない。
3. **場面の記憶 (scene) を本人には直させない。ユーザーだけが直せる。**
   scene は実会話の写しなので、本人が直すことは写しの改変 = 捏造にあたる
   (`autonomous_behavior_v3.md §13.3`、2026-08-22 裁定)。禁じているのはペルソナ側の口すべてで、
   スルースにも `memory_write` スペルにも同じ規則が効く。最後の保証は書き込みを作る場所
   (`sai_memory.core_memory.update_core_memory` が既定で拒む) が持ち、
   **メモリタブの導線が写しを直せる唯一の口**。実装のコメントもそう書いている
   (`core_memory.py:626-633`「ユーザーによる訂正は捏造ではなく外からの修正なので、ここが唯一の直せる導線として開いている」)。
4. **本人名義のテキストを切り詰めない。** scene の提示は先頭 80 字に刻まれているが、
   `v3 §13.3` は「これは分量の都合であって歯止めではない」と明記する。
   同族の規律として `§13.2.1` は手帳について「一件の本文は絶対に途中で切らない (メモも約束も、切ればそれは本人の言葉の改変)。
   省略の単位は件数だけ」と書いている。
5. **削除は物理削除でなく soft-delete。** 自動採取の誤りやユーザーの誤削除を後から復元できる
   (`memory_architecture_v2.md §5.1`)。削除された内容は通知にも載る (head から消えるものを本人が知れるように)。
6. **通知が会話文脈を埋めない。** 一括操作 (ごみ箱整理・連続修正) でも、同じコア記憶への複数操作は
   `reduce_key` で最新 1 件に集約され、同一 Pulse の全知覚が 1 メッセージにまとまる
   (`memory_architecture_v2.md §5.1` の「通知過多問題と恒久対応 (2026-07-09)」、`perception_buffer.md` Phase 1a)。
7. **Memopedia の編集は履歴を残し、ロールバックできる** (`docs/user-guide/memopedia.md §履歴ボタン`)。

**調査担当の提案 (根拠のある期待と混ぜない)**

- **あらすじと Memopedia の編集・削除は、現状ペルソナに通知されない** (下の §5)。
  この非対称に理由があるかどうかが、この流れで一番はっきりさせるべき点だと考える。
  コア記憶とあらすじには、通知の要否を分けうる違いが実際にある —
  コア記憶は「本人が刻んだ・本人の言葉の器」で、あらすじは「機構が要約として書いたもの」。
  だから同じ扱いが正しいとは限らない。**ただしその区別がどこにも書かれていない**ので、
  意図なのか隣を忘れたのかを静的には決められない。

### 6. 中断・失敗・再開

- **通知の push が失敗しても API 応答を妨げない** — WARNING に落として続行する

### 7. 次に使う機能・共有する状態

- 訂正されたコア記憶は `confirmed=1` になり、次の head に反映される (反映は Metabolism 時のみ、
  `memory_architecture_v2.md §5`)。

- **通知はペルソナの知覚バッファに積まれ、FLOW-09 の Pulse の頭で消費される。**
  消費された通知は保存行として残り、`§7-1` (2026-08-29 裁定) により**編纂の材料と被覆に入る** —
  つまり「ユーザーが私のコア記憶を書き換えた」という出来事も、いずれあらすじの一部になる。
  これは裁定どおりの動き (「本人が見ている以上、機構の通知も本人の経験の一部」)。

  1. **あらすじ・Memopedia・生ログの編集と削除を、ペルソナに通知すべきか。**
