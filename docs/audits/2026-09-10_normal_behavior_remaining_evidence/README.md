## 2. 直す対象 — 判断ではなく実装の話 (8 件)

**まはーの決定を待たずに直せる。** 上から重い順。

1. **⚠️ 本番の画面が、Tailscale の外にも開いている。**
   `frontend/package.json` の `dev` は `-H 0.0.0.0` (= 全部のネットワーク口で待ち受ける) を明示していて、
   `main.py:716-717` が案内しているのはその `npm run dev`。本番用の `next start` も測ると同じだった。
   実測で **Tailscale のアドレス / 物理 LAN のアドレス / WSL の仮想アダプタの 3 つすべてで接続を受けた**。
   ファイアウォールも node.exe 宛の受信を Private/Public 両方で許可している。
   フロントを通ればバックエンドの API に無認証で届く。
   **まはーが決めた「Tailscale の中は信頼する」は有効。実装がその範囲に収まっていない。**
   (別マシンからの実到達は未測定)
2. **バックアップの失敗が、利用者に告げられない。**
   `README.md:35` は「起動するたびにコピー・保存されます」と約束しているが、
   `database/backup.py:204-205` はどんな失敗もログ 1 行にして先へ進む。
   **止めないのは妥当。告げないのが問題。** まはー自身の「記録し、明示し、選択してもらう」の、
   記録だけがあって明示が無い形。
3. **建物の会話記録の破損に、検出も復旧も無い。**
   壊れの定義を持つコードは旧形式のファイル用の 1 つだけで**呼び出し元ゼロ**。
   読み出し側は壊れた JSON を警告なしで既定値へ落とす。整合性の検査は
   live の DB ではなくバックアップのコピーにしか走らない。
   撤去 (2026-05-20) のとき同時起票の issue が「DB 側の復旧は別文書で」と書いたが、その文書は無い。
4. **アラームが、実行される前に「完了」と記帳される。**
   実測: 会話中のペルソナに 12 件積むと **10 回しか鳴らないのに 12 件が「完了」**。
   終了処理では **3 件中 0 回しか鳴らないのに 3 件が「完了」**。画面には「(完了)」と出る。
   **新発見ではない** — `docs/issues/event_delivery_reachability_gaps.md` ①④ が
   2026-07-31 に「頻度・実害の観測待ち」と書いていた。今回その観測を出した。
   issue に無いのは終了処理の経路だけで、それは 2026-08-29 に増えた後発の同族。
5. **アドオン有効化の失敗が、4 つの登録のうち 3 つで画面に出ない。**
   全部失敗させても応答に手がかりが無く、DB は「有効」のまま残る。
   **前段の「画面に出ない」は MCP については誤り** — 分類つきの説明と再試行ボタンが既にある。
   問題は導線 (折り畳みが既定で、開くまで取得もバッジも走らない)。
6. **モデル管理の画面に、プロバイダ側にある告知が無い。**
   同じ食い違い (変更が動いているペルソナに届かない) がモデル定義の編集でも起きる。
   実測済み。**既に下された判断の適用漏れ。**
7. **出来事の受信箱を、誰も開けていない。**
   書き込む処理と、起動時に読み込む処理はある。**読み出す関数の呼び出し元がリポジトリ全体でゼロ**
   (`fetch_pending_events` / `archive_events`)。行は「未処理」のまま溜まり続け、
   起動のたびに全部メモリへ読み直される。
8. **アイテム操作の記録が、その部屋に居るペルソナに届かない。**
   受け手を渡さずに書かれた行は記憶に一度も入らず、読み位置は跨いで前進する (実測)。
   ただし**物の増減そのものは「部屋の様子」の照合で届いている**。
   届いていないのは**行為者が誰か**と**閾値を超えたという語り**の 2 つに絞られた。
