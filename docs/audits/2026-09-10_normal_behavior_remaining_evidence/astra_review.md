## 要約をそのまま引き継がない点

1. **判断候補の件数と中身が揃っていない。** README の 5 件目は day_report、decision_candidates の 5 件目は発話損失で、day_report は既存議題への合流扱い。findings B12 は復旧単位、B45 は LAN 利用の範囲も判断候補としている。「残り 5 件で全部」とは報告しない。
2. **待ち受けの実測は製品 UI の稼働実験ではない。** repro は Next の呼び出しと同じ形の Node の HTTP ソケットを一時ポートで起動したもの。製品設定・Next ソースの追跡と合わせて全 interface 待ち受けの根拠になるが、本番 UI/API を別端末から開けた証拠ではない。README の「本番の画面が外にも開いている」はこの限定を添える。ループバックだけに変えればスマホ利用も壊れるので、それを即時の修正指示にはしない。
3. **利用者の送信は、保存前の失敗まで無損失ではない。** 詳細の段階表が保存前の損失を明記している。期待を「受理した発言が永続化され、未受理は判別できる」として扱い、送信操作だけで保存を保証しない。
4. **終了実験は永続層の比較。** A3 は確定済み／未確定の行を製品保存関数で作り、履歴・取り込みと同じフィルタ等で比較する。実際の 8 秒超過・生成スレッド・終了処理の一続きの実験ではない。既存の主張どおり未確定行が見えないという証拠として受け取る。
5. **部屋とアイテムの拒否条件が違うだけでは欠陥ではない。** 「部屋には拒否条件があるのでアイテムにも足す」は却下する。所有関係、世界状態、参照の整合と利用者の意図で判断する。入退室履歴も、削除対象の性質が違う操作を同じ SQL に揃えることが目的ではない。
6. **Memopedia の夜間報告は、生成する関数があることと通常起動で毎晩稼働することを分ける。** 本調査以前の資料には v0.3 で編纂を止めた記述がある。UI 訂正が差分で届くという今回の結論は使えるが、「2 系統が稼働中」を配線・凍結条件の確認なしで言い切らない。

## 五つの判断候補の扱い

| 候補 | Astra が整理する扱い |
|---|---|
| 1 あらすじの手動変更・削除 | 生ログと合わせ「利用者が本人の記憶を直す目的と、本人への知らせ方」として相談候補を具体化。通常編纂の件数通知を復活させる話にしない |
| 2 生ログの手動削除 | 1 と関連するが、「削除されたことも記憶に残したくない」用途があるかで期待が変わる。本人への訂正通知という既存の意味を尊重しつつ、削除目的を確認する本当の判断として扱う |
| 3 通知に行為者を書くか | 独立した全通知の統一投票にしない。手動訂正を知らせる目的が決まれば、判明している行為者・変更を正確に表す。差分検知だけで不明な行為者を推測して書かない |
| 4 目の前の物の操作の行為者 | 出来事の受け手への配達漏れとして、既存の世界の認識と名義を保つ方針に照合する。場にいない人への全知通知や、部屋の差分から行為者を推測する設計はしない。仕様詳細と実際の受信の確認は残るが、一から好みを尋ねない |
| 5 終了時の発話損失の通知 | 「失う前提で誰に知らせるか」の選択へ直行しない。既存の中断本文・中断した事実の保全という約束に対し、保存が間に合わない経路の不足を正常化対象として整理する。クラッシュ等で回収できない残余と通常終了を分け、通知の具体策は回収・再開経路の検討後に置く |

既存 issue に、中断を本人が認識できるかがまはーの問いとして記録され、その配達修正・実機確認がある。「機構の失敗を本人に知らせることは未決」だけで候補 5 を白紙に戻すと、既存の目的を落とす。

**同日追加回答で境界を訂正**: Astra が関連するあらすじ・コア記憶まで内容を消すことを正常化の要件として広げた点は不採用。関連情報の残り方と影響を利用者へ説明し、追加で変更した方がよいものは提案して選んでもらう。非通知は関連データの自動削除の承認ではない。参照追跡の目的を「追加削除を当然の要件として実現する」から「利用者が操作範囲と結果を理解し、選択できるようにする」へ訂正する。
