# Issue: Chronicle タブが最新エントリを表示しない (一覧 API の 500 件切り詰め)

**ステータス**: 🟡 検証待ち — 修正実装済み (`a537441`)。残りは**まはーの実機確認**
**優先度**: high (ユーザーから見ると「最近の記憶があらすじになっていない」ように見える — 実データは無事)
**作成日**: 2026-07-29
**関連**: `api/routes/people/arasuji.py list_arasuji_entries`, `frontend/src/components/memory/ArasujiViewer.tsx`
**統合**: 同じバグが同日に二重起票されていた (`arasuji_list_limit_hides_newest.md`)。発見経緯を本 issue へ統合し、あちらは [archive](archive/arasuji_list_limit_hides_newest.md) へ移した (2026-07-30)

## 症状

同じ壁に、二つの入口から当たっていた。

- メモリーモーダルの Chronicle タブで、エリスの最新エントリが **7/21 で止まって見えた**。実際には 7/22〜7/29 のエントリ 13 件が memory.db に存在し、コンテキストプレビュー (head のあらすじ枠) には出ていた。
- 記憶修復 (削除・再生成) の直後に一覧を開いても**顔ぶれが削除前と変わらず**、「操作が反映されていない」ように見えた。

## 原因 (特定済み)

一覧 API `/api/people/{id}/arasuji` は `ORDER BY level DESC, start_time ASC LIMIT 500` (limit 既定 500、フロントは limit を渡さない)。上位レベル → 各レベル内は**古い順**という並びなので、総エントリ数が 500 を超えると、並びの**末尾 = レベル1 の最新エントリ**から黙って切り落とされる。新しい記憶ほど見えない窓になっていた。

`?level=1` を指定する経路 (`get_entries_by_level`) には上限が無く、そちらでは全件見えていた — これが「一覧だけおかしい」形になった理由。

検算 (2026-07-29 エリス実測): 総数 513 件 (L1=464, L2=45, L3=4)。500 件に切ると L1 は 451 件になり、返る L1 の最新 end_time は 2026-07-21 10:11 — まはーの観察と一致。切り落とされた 13 件がちょうど 7/22 以降。

エリスが 500 件を跨いだのは 2026-07-29 の一括再編纂 (歪み世代の修復) の直後で、それまで顕在化しなかった。実運用のエントリ数は増える一方なので、放置すれば常時この状態になる。

## 実害

- 記憶の操作 (削除・再生成・編纂) の結果を UI で確認できない。実際に「削除が行われていないのでは」という誤認を生んだ。
- 「新しいものから欠ける」形の静かな切り詰めが最悪 (memory: 上限は実害の根拠がある時だけ・全文到達手段とセット)。

## 修正 (`a537441`、2026-07-29)

一覧 API を「新しい側を SQL の `ORDER BY start_time DESC + LIMIT` で取得し、表示順 (昇順) へ反転」に変更した。limit が DB からの読み取り量も抑える (Codex 再レビュー反映)。

- **上位レベル (L2+) は隠さない**契約。件数が log で有界な全体像の骨格なので全件返す。隠す対象は L1 だけ。
- 切り詰めが起きたら `hidden_oldest` / `total_available` を応答で明示し、フロントに切り詰めバナーを出す (ライト/ダーク両対応)。
- COUNT と行フェッチは同じ読み取りトランザクションで行う (別スナップショットだと並行編纂の insert で `hidden_oldest` がずれ、「黙った切り詰め」が再発する — Codex 三巡目)。
- `limit` は 1〜5000 で検証。`level` 指定時も同じ「古い側から隠す」契約を適用する。

**残 = 実機検証**: エリス 513 件の最新 (7/29) が Chronicle タブに見えること。

## 発見の経緯

2026-07-29 の同じ夜に、独立した二つの作業から同じ壁に当たり、別々に起票されていた。

1. **エリスの記憶修復** — 歪み世代 101 件削除 → 新方式で 8 件再生成した直後、UI 一覧が削除前と同じ顔ぶれのままに見えた。API 応答の突き合わせで、変更が全て 500 件上限の外側 (並びの尻尾) で起きていたことを確認。
2. **「編纂タイミングが意図と違う」調査** (arasuji_levels §13) — その過程で Chronicle タブの最新が 7/21 で止まっていることに気づき、原因を特定。修正は §13 実装と独立に可能と判断した。
