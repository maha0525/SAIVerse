# Issue: Chronicle タブが最新エントリを表示しない (一覧 API の 500 件切り詰め)

**ステータス**: 未解決 (2026-07-29 起票)
**優先度**: high (ユーザーから見ると「最近の記憶があらすじになっていない」ように見える — 実データは無事)
**関連**: `api/routes/people/arasuji.py list_arasuji_entries`, `frontend/src/components/memory/ArasujiViewer.tsx`

## 症状

メモリーモーダルの Chronicle タブで、エリスの最新エントリが 7/21 で止まって見えた。実際には 7/22〜7/29 のエントリ 13 件が memory.db に存在し、コンテキストプレビュー (head のあらすじ枠) には出ていた。

## 原因 (特定済み)

一覧 API `/api/people/{id}/arasuji` は `ORDER BY level DESC, start_time ASC LIMIT 500` (limit 既定 500、フロントは limit を渡さない)。総エントリ数が 500 を超えると、並びの**末尾 = レベル1 の最新エントリ**から黙って切り落とされる。

検算 (2026-07-29 エリス実測): 総数 513 件 (L1=464, L2=45, L3=4)。500 件に切ると L1 は 451 件になり、返る L1 の最新 end_time は 2026-07-21 10:11 — まはーの観察と一致。切り落とされた 13 件がちょうど 7/22 以降。

エリスが 500 件を跨いだのは 2026-07-29 の一括再編纂 (歪み世代の修復) の直後で、それまで顕在化しなかった。

## 修正方向

「新しいものから欠ける」形の静かな切り詰めが最悪 (memory: 上限は実害の根拠がある時だけ・全文到達手段とセット)。ページング導入か、切るなら古い側から + 総数と切り詰めの明示。実装時に UI 側の表示順・レベル絞り込みとの整合も確認する。

## ログ

- 2026-07-29: 「編纂タイミングが意図と違う」調査 (arasuji_levels §13) の過程で発見・原因特定。修正は §13 実装と独立に可能。
- 2026-07-29 (同日): 実装済み・実機検証待ち。一覧 API を「新しい側を SQL LIMIT で取得して表示順へ反転」に変更 (limit が DB 読み取り量も抑える — Codex 再レビュー反映)。上位レベル (L2+) は隠さない契約。切り詰め時は `hidden_oldest` / `total_available` を応答で明示し、フロントにバナー表示 (ライト/ダーク両対応)。limit は 1〜5000 で検証。
