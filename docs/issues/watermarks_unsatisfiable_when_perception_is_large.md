# 知覚が多いと「残す量」と「整理を始める量」を両方満たせる状態が無い

**ステータス**: 設計中 — 2026-09-04 まはー提起。同日夕の議論で範囲が広がった (下の §2026-09-04 の議論)。方向はおおむね揃い、細部と数字が裁定待ち
**深刻度**: 中 — v0.3.7 では整理が何もせず、送る合計が整理を始める量を超えたまま続く。文脈長の小さいローカルモデルでは、応答の失敗に進みうる
**起票**: 2026-09-04
**関連**: [protection_quota_consumed_by_perception_blocks.md](protection_quota_consumed_by_perception_blocks.md) (残す量の主語を会話の行に限った経緯) / [metabolism.md](../concepts/metabolism.md) / PR #280 (水位の全体設定)

## 問題

2026-09-03 の裁定で、「残す量」(畳んだ後に残す直近の会話) は会話の行だけで数え、「整理を始める量」は実際に送る合計 (会話の行 + 送信直前に差し込む知覚ブロック) で数えることにした。二つの主語が違うので、知覚が多いと、会話をどれだけ畳んでも合計が整理を始める量を下回らない状況がある。

具体例: 残す量 18,000 / 整理を始める量 26,000 の設定で、部屋の様子が 10,000 字乗っていると、会話を 18,000 まで畳んでも合計は 28,000。

いまの v0.3.7 の動き: 整理は「畳めるものが無い」と判断して何もしない (`SessionLifecycle._note_perception_over_budget` が WARNING を 1 回、context-status に `perception_over_budget`)。会話は守られるが、送る合計は上限を超えたまま。

## 前提となる事実

知覚ブロックが提示から下りるのは、その期間を覆うあらすじの記録が作られて、そのブロックが材料として付記されたときだけ (`sea/runtime_context.py::list_presented_perception_blocks`、`sai_memory/arasuji/executor.py` の付記)。会話を畳むと畳んだ期間の知覚は一緒に下りるが、守っている直近の会話の期間に乗っている知覚は、会話を守るかぎり下ろせない。

## 案 (メティス、2026-09-04 昼時点)

> 2026-09-04 夕の議論で修正・拡張された。この節は原形のまま残す — 現在の形は下の §2026-09-04 の議論。

**推す案: 知覚に自分の上限を持たせる。**

- 提示に乗せる未処理の知覚ブロックの合計に上限を置く。超えたら古いブロックから提示に乗せない。台帳 (`perception_batches`) からは消さないので、その期間のあらすじが作られるときに材料として拾われる。失うのは「古い部屋の様子を送り続けること」だけ。
- 水位の保存時 (モデル定義・全体設定の両方) の検査に「整理を始める量 − 残す量 > 知覚の上限」を足す。これで「会話を残す量まで畳めば必ず整理を始める量を下回る」が設定の時点で保証される。
- 知覚の上限の値は、まず組み込みの固定値で始める。

代案 1: いまのまま (何もしない + 旗)。ローカルモデルで文脈長を超える道が残る。
代案 2: 整理を始める量も会話の行だけで数える。主語が揃って分かりやすいが、9/2 の「上限は実際に送る量」の裁定を戻すことになり、送る量に歯止めが無くなる。

## 既定値の見直し (同時に裁定してほしい)

残す量が会話だけになったので、組み込み既定 (最初に読み込む文字数 40,000 / 残す量 100,000 / 整理を始める量 200,000) は大きすぎる。叩き台は 20,000 / 40,000 / 120,000。残す量 40,000 字は日本語の会話で百数十往復ほど。上限との差 80,000 は、知覚の上限を引いても畳みを「たまに・まとめて」に保てる幅。場所は `saiverse/model_configs.py` の `BUILTIN_METABOLISM_*_CHARS` (PR #280 のフロントにも同じ数が写っている: `GlobalSettingsModal.tsx` の `wmBuiltin`)。

## 2026-09-04 の議論 (昼の案への修正と、供給側への拡張)

昼の案をまはーとレビューして、三つの欠けが見つかった。いずれも方向は同日中に揃った。

### 裁定済み (まはー)

1. **省略には痕跡が必須。** 知覚ブロックを提示から下ろすとき、その位置に「省略された何かがあった」ことが分かる機構名義の一行を残す (連続して下ろした区間は一行に束ねる)。黙って消すのは「そこに何も無かった」という記録の嘘 — あらすじの畳みが跡地に digest を置くのと同じ原則。昼の案 (「提示に乗せない」だけで跡地を考えていない) はこの点で不合格だった。
2. **スペルの付与通知はスキーマ込みで渡す。** head のスペル一覧は説明 + 引数スキーマを描画する (`sea/head_pipeline/sections/spell_list.py::_render_entry`) が、head はキャッシュ保護で Metabolism まで凍結される。だから移動直後のペルソナにとって付与通知が唯一の情報源なのに、現状は名前一行だけ = 冗長ではなく**不足**。「部屋単位で一行に集約」案は逆方向で却下。
3. **部屋の様子の重複を「最新だけ残す」で消してはならない** — 提示の途中の行を消すのはキャッシュの前方一致の破壊 (知覚上限を一個ずつ下ろす案と同型の欠陥)。代わりに: 再訪時、前回の全文がまだ提示に見えているなら**差分だけ**を末尾に積む。前回の全文があらすじ付記で提示から下りるとき、その内容を「見えている中で最古の同部屋エントリ」へ**移管**する (差分の土台を失わない)。移管の書き換えは付記 = 編纂と同時に起きるので、キャッシュの壊れは既存の発火に相乗りし、新しい壊れ時点を作らない。
4. **アイテム説明の全文提示は維持する。** 一発が巨大になる根っこは部屋の表面に見えるアイテム数に上限が無いこと — これは別件として検討 (ideas 帳 2026-09-04)。
5. **低水位 (`metabolism_low_chars`) は廃止する。** 現役の役割は「anchor が無いときの初期読み込み量」だけだが、発話直前の最終防衛ライン (§15-5) が材料のあるかぎり窓を残す量まで埋め直すので、この値が効く場面が実質無い (新規ペルソナでも意味が無い — まはー)。初期読み込みは残す量を流用し、水位は「残す量」と「整理を始める量」の二つになる。
6. **既定値は残す量 40,000 / 上限 120,000。** (2026-09-04 まはー裁定。「ひとまず入れて、会話して体感をチェックする」— 数字は実機の体感で見直しうる。)
7. **でかい一発の Pulse 終端要約は保留 (GO せず)。** 供給側の修理で判明した通り、でかいものの主産地は「見え続けることに意味がある型」(アイテム・スペル) か「門で発火を止める型」(想起) で、「でかい × 使い捨て」という要約が正解になる型はまだ観測されていない。供給側の修理後に実台帳の分布を測ってから、型ごとの opt-in として再検討する。それまで「単独で知覚の上限を超える一個」は旗を立てて超過を許す (v0.3.7 の `perception_over_budget` と同じ正直な形)。
8. **スペル結果など機構名義の行は残す量の勘定から外す** (2026-09-04 まはー裁定)。残す量が守るのは会話の連続性で、スペル結果の大きさで会話が削られてはならない — 知覚ブロックを外した 2026-09-03 裁定と同じ理屈の同族適用。機構名義 = tags に `MECHANISM_TAGS` (`handy_tool` / `spell` / `event_message`) を持つ保存行で、ペルソナ本人の発話 (唱えの行を含む) は該当しない。機構行は畳みの対象範囲には含まれたまま (畳まれる期間の行として一緒に下がる) — 数えないだけ。実測 (2026-09-04 エリス): 表示 44,006 字のうちスペル結果 3 件 18,010 字が生で「会話」に入り、残す量 4 万の保護枠の 4 割超を消費していた。
9. **上限 (整理を始める量) は生の合計のままスペル結果を含む** (2026-09-04 まはー裁定)。整理をトリガーする文字数にはスペル結果を組み込む — 現状の `message_chars` (実際に送る合計) が既に満たしており、上限側は変更なし。
10. **送信量の内訳表示にスペル結果を独立の行として出す** (2026-09-04 まはー裁定)。context-status の内訳を三分割 (会話 `stored_chars` / スペル結果 `mechanism_chars` / 部屋の様子 `injected_perception_chars`) にし、チャットオプションの表示は「うち会話 A・スペル結果 B・部屋の様子 C」(B=0 なら非表示)。合計 (`presented_chars`) は生のまま不変。

### 方向は出たが細部が未裁定

- **知覚の合計上限は二水位にする** (メティス案): 超えたら一個ずつではなく下の水位まで**まとめて**下ろす。下ろす境界は一方向にだけ進む一つの値として持つ (隠したブロックが復活してちらつかない)。一個ずつ下ろすと、知覚が多い環境で新着のたびに窓の前方が書き換わり、ほぼ全文が毎回定価の読み直しになる — 「窓の並びが変わるのは Metabolism のとき、たまに・まとめて」の不変条件 (intent cached_head_architecture) に反する。
- **想起の門の再配線** (メティス提案): 入室時の過去会話想起は、本来 `should_recall_persona` (直近 20 メッセージに相手がいたら想起しない) という再会判定を持つ (`persona/history_manager.py`)。だが実際に動いている繋ぎ実装 `_inject_persona_recall_on_enter` (`sea/head_pipeline/integration.py`) はこの門を呼ばず、occupant_entered ラベルに無条件で発火する — ずっと会話中の相手にも移動のたびに最大 6 件 × 2,000 字 + Memopedia ページが積まれる。門の配線 + 見出しの ID を名前に直す (`[想起: 1との過去の会話]` の「1」はユーザー ID の生値)。
- **保存時検査には余裕が要る**: 「整理を始める量 − 残す量 > 知覚の上限」は等号ぎりぎりでは成立しない。畳んだ後の会話は端数 (材料 U 未満の畳み残し) と関節寄せで残す量ちょうどには収まらない。→ 2026-09-05 に叩き台 1万字 (`WATERMARK_HEADROOM_CHARS`) で実装。**数字はまはーの裁定待ち**。副作用として「整理をはじめる量 − 残す量 ≤ 1万字」の設定は、知覚の上限をいくら下げても保存できなくなる (余裕が固定値のため)。
- **読み戻し・床の「埋める深さ」は生字数のまま** (裁定 8 の実装で意図的に残した境界): 読み足す量の見積もり (`plan_reopen` の gain、`get_history_before_anchor` の max_chars) は読み戻す行の生字数で数えるので、範囲にスペル結果が混ざると会話の充填が残す量にやや届かない (大きいスペルを含む fold は予算に収まらず開き直し自体が見送られる形もある — Codex 一巡目 high #1 も同じ箇所)。方向は畳み過ぎ側ではなく埋め不足側 (安全)。裁定 8 の前はスペル結果が会話として保護枠を食っていたので、実効の会話量が旧挙動より減る向きの変化ではない。どの fold を開くかの設計判断を含むため、直すかどうかは実機の体感を見てから。
- **機構行が会話より先に積もった窓は、会話が残す量を超えるまで畳みが動かない** (裁定 8 の帰結。Codex 一巡目 high #2): 会話ゼロで機構行だけが上限を超えた窓では、保護境界が全行を覆って畳めるものが無く、合計が上限を超えたまま旗 (`perception_over_budget`、警告は 1 度だけ) で流れる — 裁定 7 の「旗を立てて超過を許す」正直な形と同族。会話が積もれば畳みが再開し、古い機構行は畳まれる期間と一緒に下がる。恒久の解は知覚の二水位上限の波で「機構行にも同種の上限を与えるか」を一緒に裁定する。

### 供給側の事実 (このセッションでコード確認済み)

まはーが実物の知覚ブロック 2 件 (エリス) を提示し、冗長の発生源を特定した。

- 部屋の様子: 移動のたびに全アイテムの説明つき全文が積まれる (`saiverse/dynamic_state.py` の surroundings push)。reduce の鍵なし。
- スペル増減: head の差分検知が 1 スペル 1 ラベルで出す (17 スペルの部屋なら 17 行 × 行き帰り)。鍵なし。
- 集約規則は「同一 (kind, reduce_key) の最新だけ残す」の一本 (`sai_memory/perception_buffer.py::reduce_perceptions`) で、鍵なしの型は全件残る — 行って戻るだけで全部が二重になる。
- 「役割・指示」ブロックの発生元だけは未特定 (同じ差分通知の仲間と推測、未確認)。
