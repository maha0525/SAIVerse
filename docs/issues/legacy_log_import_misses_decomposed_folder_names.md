# 過去ログの取り込みが、濁点を含む部屋名の log.json を見つけられない (macOS)

**状態**: 実装済み・検証待ち (2026-09-02 実装。報告者の macOS 環境での再確認が残る)
**起票**: 2026-09-02 (v0.3.1 利用者からの「移せませんでした のお知らせが消えない」報告を、診断ツールで特定)
**関連**: `saiverse/legacy_log_import.py` `find_log_files` / `_scan_one_building`、`docs/intent/building_memory_unified.md`

## 症状

「部屋『○○』の古い会話 N 件を新しい保存先へ移そうとしましたが、移せませんでした」
のお知らせが、再起動しても消えない。ユーザーには押せるボタンも無く、対処のしようがない。

起動ログにはエラーも例外も出ない。出るのはこれだけ:

```
[legacy-log] 1 部屋に古い会話が残っているので、いま移します: リビング_city_a
対象 log.json: 0 件                              ← ファイルを 1 つも見つけていない
[legacy-log] リビング_city_a: 古い会話 0 件を移しました
[legacy-log] 1 部屋で古い会話を移しきれませんでした: リビング_city_a
```

**「移せていない」と「対象 0 件」が同時に成立している。** 検算はファイルを読めて
1179 件と数えているのに、取り込みは同じファイルを見つけられない。

## 実測 (2026-09-02、報告者の環境)

macOS (Darwin 25.5.0) / SAIVerse 0.3.1 / Python 3.12.10。同じ起動での対比:

| 部屋 | 濁点・半濁点 | 結果 |
|---|---|---|
| アイテム倉庫_city_a | なし | 8 件を取り込み成功 |
| user_room_city_a | なし (ASCII) | 102 件を取り込み成功 |
| 寝室_city_a | なし | 1214 件を取り込み成功 |
| mizuki_city_a_room | なし (ASCII) | 1344 件を取り込み成功 |
| ひな_city_a_room | なし | 572 件を取り込み成功 |
| **リビング_city_a** | **「ビ」「グ」にあり** | **対象 0 件、毎起動アラート** |

対象の部屋: ファイル 1179 件 / DB 26 件 / 欠け 597 件。

報告者から受け取った診断結果のバイト列を調べたところ、DB 側の BUILDINGID は
**合成済みの 1 文字**だった (`ビ` = U+30D3)。

## 原因

**同じ部屋を探す規則が 2 箇所にあり、片方だけが名前の書き方の違いで落ちる。**

macOS はファイル名の濁点・半濁点を「ヒ + 濁点」の 2 文字へ分解して保存する (NFD)。
一方 DB の BUILDINGID は、アプリが受け取った合成済みの 1 文字 (NFC) のまま入る。

- **検算** (`_scan_one_building`): パスを組み立てて `exists()` で開く
  → macOS のファイルシステムは NFC と NFD を**同じ名前として扱う**ので、**見つかる**
- **取り込み** (`find_log_files`): ディレクトリを一覧し、`building_dir.name != building_filter`
  で突き合わせる → **Python の文字列比較は NFC と NFD を別物と判定**するので、**0 件**

濁点・半濁点を含む部屋名を持つ macOS ユーザーは、全員この症状になる。

## 直したこと

`find_log_files` を、名前を指定されたときは一覧を引かずに**パスとして組み立てて開く**
形へ変更した。検算側と同じ解決方法に揃えたので、「片方だけ見つかる」状態が構造的に
起きなくなる。

一覧との照合をやめた分、名前が親フォルダの外へ出ないことを `_child_by_name` で
確かめる (照合していた頃は、一覧に載る名前しか通らないので構造上ありえなかった)。

テスト: `tests/test_legacy_log_find_files_naming.py`。macOS のファイル名正規化は
他の OS で再現できないため、固定したのは**名前を指定されたときに一覧を引かない**
という構造の方。

## なぜ作り込んだか (3 つの原因)

1. **技術的な原因**: ファイルシステムは名前を正規化して同一視するが、プログラムの
   文字列比較は同一視しない。この非対称の上に「一覧の名前と突き合わせる」を置いた。
2. **判断の失敗**: 検算と取り込みで「同じ部屋を指す」ことが要なのに、探し方を別々に
   書いた。2026-08-16 に「欠けの判定規則」は両者で揃えたが (message_id 突き合わせ)、
   **その手前の「どのファイルを見るか」が揃っていないことに気づかなかった。**
   揃えた規則の隣に、揃っていない規則が残っていた。
3. **過程の条件**: 開発と検証が Windows と Linux だけで、ファイル名の正規化が効く
   環境が無かった。日本語の Building ID は本番 DB に実在する
   ([building_id_no_charset_constraint](archive/building_id_no_charset_constraint.md)
   で「既存は放置」と裁定済み) のに、その組み合わせを踏む環境が手元に無かった。

**転移テスト**: 「ファイルシステムが同一視する差 (大文字小文字・Unicode 正規化・
末尾の空白) を、プログラム側の文字列比較で判定してはいけない」は、この事案の外にも
効く。実際、同じ形が Windows でも起きる — City フォルダ名と CITY_SLUG の大文字小文字
が食い違うと、まったく同じ「0 件で空振りしながらアラートだけ出る」状態になる
(診断ツールの検証で再現済み)。

## 残っている穴

**Linux では検算側も落ちる。** Linux のファイルシステムは正規化を同一視しないため、
NFD のフォルダ名 + NFC の BUILDINGID では `_scan_one_building` の `exists()` も
False になる。その部屋は「log.json が無い部屋」として扱われ、**アラートすら出ずに
黙って取り込まれない**。macOS からファイルを移してきた環境などで起こりうる。

今回は報告のあった macOS の症状を直すところまで。実例が出たら、名前の正規化を
突き合わせて解決する形を検討する。
