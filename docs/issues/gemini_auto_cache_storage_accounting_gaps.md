# Issue: Gemini 自動キャッシュの保存料金の記録に、二つの穴がある

**ステータス**: 🔲 未着手（未解決 — `docs/issues/` 直下にある）
**優先度**: low（記録上の料金がずれるだけで、実際の請求や会話の挙動は変わらない）
**作成日**: 2026-10-11
**関連**: `llm_clients/gemini.py`（`_auto_cache_wrap` / `_auto_cache_cleanup` / `_store_usage` / `_pending_cache_storage`）、`saiverse/usage_tracker.py`（`record_cache_storage`）、`docs/intent/cache_lifecycle_control.md` §3.5 / v0.13

## 何が起きているか

継続キャッシュ（§3.5）の敵対レビュー（2026-10-11）で、継続キャッシュの料金の記録に二つの欠陥が見つかり、継続キャッシュの側は直した。同じ形が自動キャッシュにも残っている。

1. **早く消したキャッシュに、寿命いっぱいの保存料金が付いたまま。** 料金の記録は「作ったときに寿命 (TTL) の全額を記録し、早く消したら残りを負の記録で差し引く」という予約席の約束になっている（`record_cache_storage` の docstring）。しかし自動キャッシュは応答の直後に消す（保持秒数 0 のとき）のに、差し引く記録を入れていない。保持秒数 0 では保険の TTL 300 秒で作るので、記録上は毎回およそ 300 秒分の保存料金が付き、実際（数秒〜十数秒）より大きく見える。
2. **保存料金の控えが、クライアント全体で一つの置き場を共有している。** `_pending_cache_storage` に控えを置き、あとで使用量の記録が来たときにくっつけている。生成が失敗した、または使用量が返らなかった回は、作ったキャッシュの保存料金が記録から漏れる。同じクライアントで要求が重なると、別の要求の記録にくっつく可能性もある（ペルソナの返事は Beat の関所で一人ずつ進むので、重なりは起きにくい）。

## 直し方の方向

- 1 は、キャッシュを消した時点で残りの秒数分の負の記録を入れる（継続キャッシュでは `record_cache_storage_refund` を足した）。自動キャッシュの削除の経路はどのペルソナの要求かを知らないので、ペルソナ別の集計に載せるには、作成時に要求側の情報を控えておく必要がある。
- 2 は、作った瞬間にその要求の情報（ペルソナ・建物）で記録する形にそろえる（継続キャッシュの同期作成はこの形に変えた）。
