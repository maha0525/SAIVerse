# v0.2.29 の update.bat は git pull の直後に静かに死ぬ — 依存更新が一切走らない

**発見**: 2026-08-30 (段 3: update.bat 経路の実機検証、隔離複製リポジトリ)
**状態**: 🔲 未解決 (実装済み・実機検証待ち) — 欠陥そのものはリリース済みの v0.2.29 側 update.bat にあり直せないが、**新しい start.bat / start.sh が起動前に「更新が仕上がっているか」を検査して、ずれていれば自動で仕上げる**ようにした (2026-09-01)。リリースノートに一文が載り、v0.2.29 複製での実機検証が通るまでこの issue は閉じない。
**深刻度**: P1 相当 — 全 v0.2.29 ユーザーのアップグレード初回が「コードだけ新しく、依存が古い」中途半端な状態で止まる。ただし 2 回目の実行で完全に自己回復する (実機確認済み)。

## 実測 (2026-08-30、v0.2.29 複製 + 隔離プロファイルで実走)

v0.2.29 の update.bat を実行すると:

1. `git pull` は成功し、コードは新リリースへ fast-forward される。
2. その直後、実在しない stash の案内 (「Your local changes are saved in git stash. Run 'git stash pop'」) を出して **exit 0 で終了**する。
3. pip install / database migrate / playbook import / npm install は**一切実行されない**。

## 原因

cmd のブロック解析の欠陥。v0.2.29 の update.bat には
`echo [OK] Code updated (local changes stashed)` という行があり、echo 引数内の
括弧が `if !errorlevel! neq 0 ( ... ) else ( ... )` のブロック構造を壊す。
最小再現 (`parse_test.bat`) で、errorlevel=0 でも stash ブロック内の echo が
外へ漏れて実行され、以降のフローが崩壊することを確認した。
pull 成否に関係なく、この bat は毎回コード更新だけで打ち切られる。

## ユーザーへの実害と回復手順

- 1 回目の update.bat 後に start.bat を叩くと、v0.3 で増えた依存
  (mcp / feedparser / cryptography / curl-cffi / imageio-ffmpeg など) が venv に
  無く、backend が ModuleNotFoundError で落ちる。
- **update.bat をもう一度実行すれば完全回復する**: 1 回目の pull でコードは
  v0.3.0 になっているため、2 回目は新しい update.bat → `scripts/update_engine.py
  --manual` が走り、スナップショット退避 → pip → npm ci まで正しく完了する
  (隔離複製で実機確認済み)。
- ただしこの回復は、v0.3.0 に次の 2 修正が入っていることが前提:
  - `dc9650cb` — snapshot.py の sys.path shim (無いと 2 回目がスナップショット段で
    ModuleNotFoundError 中断)
  - `302680e6` — requirements.txt の ASCII 化 (無いと日本語 Windows で pip 段が
    UnicodeDecodeError 中断)

## 対処: 起動時の「更新の仕上げ」自己回復 (2026-09-01 実装)

「update.bat を 2 回」の案内をユーザーに背負わせる代わりに、**起動側が中途半端な
更新を見つけて自分で仕上げる**ようにした。1 回目の pull で新しい start.bat 自体は
ユーザーのディスクに届いているので、そこに検査を置けば旧 update.bat の欠陥を
迂回できる。同時に「中途半端な更新のまま起動する」事故クラスごと塞がる。

**印 (`.update_complete`)**: リポジトリ直下に置き、その checkout が
「コード・Python パッケージ・フロントエンドパッケージを揃えて仕上げた」時点の
状態を JSON で書く。`scripts/update_engine.py` は**変異フェーズに入る時点で印を
消し** (`git pull` が成功した直後、依存更新を始める前)、**全段が成功した終了点だけ**で
書き直す。こうすると「途中で死んだら印は必ず無い」が構造として成立し、次回起動は
必ず印なし経路の実在照合を通る。消すのを最初にやる理由は、pip が途中で失敗して
ロールバックまで失敗した場合にある。コードだけが旧リビジョンへ戻ると指紋が古い印と
一致してしまい、パッケージが半端なまま次回起動が 0 (起動可) で素通りしてしまう。
印の削除自体に失敗したときは警告を出して更新を続ける — 更新をそこで止める理由には
ならず、代償は「その更新が失敗したとき、次回起動が古い印を信じうる」だけ。
既存の自己更新の状態ファイル
(`.update_config.json` / `self_update.log`) と同じ場所・同じ .gitignore 節に置いた。
checkout ごとの状態なので `~/.saiverse/` ではなくリポジトリ直下が正しい器
(1 つの SAIVERSE_HOME を 2 つの checkout が共有しても壊れない)。
**.gitignore に入っていることが必須** — 更新エンジンは追跡ファイルに手元の変更が
あると更新を拒否するため、印を一度でもコミットしてしまうと書き換わるたびに更新自体が
できなくなる (印を書くときの一時ファイルも同じ理由で `.update_complete*` として
無視させている)。なお v0.3.6 からは未追跡ファイルは検査対象外なので、無視漏れ
そのものは更新を止めない — 止めるのは追跡されてしまった場合だけ。

印の中身は 3 つ: `version` (VERSION ファイルの文字列)、`requirements_sha256`、
`package_lock_sha256`。**VERSION だけでは足りない** — リリース間のコミットは
VERSION を据え置いたまま `requirements.txt` や `frontend/package-lock.json` を
動かせるので、VERSION 一致だけで「仕上がっている」と言うと、pip が一度も走って
いない checkout に完了の印が立つ。逆にコミット SHA は**鍵にしない**: 開発機では
毎 pull で「何も変わらない pip 実行」を要求する過剰反応になる。
印は一時ファイルに書いてから `os.replace` で差し替える (書きかけの印が残らない)。
書き込みに失敗しても更新自体は失敗にしない — 更新は実際に成功しているので
失敗と報告するのは嘘になる。代償は「次回起動で不要な仕上げが 1 回走る」だけ。
なお v0.3.0 開発中の旧形式 (VERSION 文字列 1 行) の印は「不一致」として扱われ、
仕上げが 1 回走って新形式で書き直される (冪等なので無害)。

**検査 (`python scripts/update_engine.py --check-complete`)**: 判定は Python 側に
寄せ、bat / sh は終了コードで分岐するだけにした。

| 終了コード | 意味 | 起動側の動作 |
|---|---|---|
| 0 | コードと導入済みパッケージが揃っている | そのまま起動 |
| 10 | 更新が途中で死んでいる | `--manual` で仕上げてから起動。仕上げに失敗したら**起動しない** |
| 11 | 判定できなかった (VERSION が読めない、解析できない requirements 行がある等) | 警告だけ出して起動 |
| その他 (検査自体が落ちた) | 判定できなかった | 警告だけ出して起動 (11 と同じ扱い) |

判定の中身:

- 印が現在の指紋 (VERSION + 2 つの sha256) と一致 → 0。
- 印があって不一致 → 10 (更新が途中で死んだ、rollback 後、または依存表が動いた)。
- **印が無い** → 印の仕組み以前のインストール (= v0.2.x からの更新) か、印を消した人。
  ここで「新規セットアップだろう」と決め打ちすると、まさに救いたい v0.2.29
  ユーザーが素通りしてしまう。そこで**実際に壊れる物**を見る (下記)。

印が無いときに見るもの:

1. `frontend/node_modules` があるか。無ければ 10 (npm が一度も走っていない)。
   存在確認だけで、package-lock.json との突き合わせまではしない —
   それは npm の仕事で、ここで防ぎたいのは「npm が走らなかった」中断更新。
2. `requirements.txt` の各行を `packaging.requirements.Requirement` で解析し、
   環境マーカー (`; sys_platform == "win32"` 等) を**評価**して当環境に要る行だけを
   検査する。`importlib.metadata` の導入済みバージョンに**バージョン制約も適用**する
   ので、「名前はあるが古い」も欠落として拾う。`name @ url` 形式は名前で検査する。
   欠けていれば 10。
3. `-` で始まるオプション行は、**無害と分かっているものだけを無視する**。
   無視してよいのは取得元やビルド方法を変えるだけで導入対象を増やさないもので、
   `--index-url` / `--extra-index-url` / `--trusted-host` / `--find-links` /
   `--no-binary` / `--only-binary` / `--prefer-binary` / `--pre` / `--hash` /
   `--require-hashes` を許可リストに置いている (`-r` / `--requirement` は
   従来どおり 1 段だけ辿る)。それ以外はすべて「解析できなかった行」に数える。
   特に `-e` / `--editable` はこの検査が決して照合できない配布物を導入するし、
   `-c` / `--constraint` はどのバージョンなら満たしたことになるかを変える。
   未知のオプションも同じ扱いにする — 導入対象を増やすかどうかがここでは決められず、
   誤った「欠落ゼロ」を完了の印として刻むわけにいかないため。
4. 欠落ゼロでも、**解析できなかった行が 1 つでもあれば 11** (印は書かない)。
   「見られなかった行がある」まま完了の印を書くと、検査していないことを検査済みと
   主張する嘘の印になる。`packaging` が読めずに素朴解析へ縮退したときも同じ 11。
5. すべて揃っていれば印を書いて 0。`requirements.txt` 自体や導入済みパッケージの
   一覧が読めない (= 一切照合できない) ときだけは、従来どおり印を書かずに 0 を返して
   次回もう一度見る。

この「印が無いときは実際に壊れる物で判定する」一段があるおかげで、印を持たない
v0.2.29 ユーザーが `start.bat` を叩くだけで自動回復し、開発機のように印が無くても
依存が揃っている環境は素通りする。照合コストは実測 0.18 秒で、しかも印が無い
初回だけ走る (印があるときは 0.001 秒未満)。

**bat 実装の注意**: この issue の原因そのもの (echo 引数の括弧が if ブロックを壊す)
を踏まないよう、検査ブロックは `if errorlevel N goto :label` の平坦な分岐だけで
書き、ブロック内 echo に括弧を入れず、遅延展開も使っていない。分岐は
`if errorlevel 11` → `10` → `1` の降順で並べる (cmd の `if errorlevel N` は「N 以上」の
意味なので、降順でないと 11 が 10 の枝に落ちる)。想定外の終了コード (1〜9 や 12 以上)
は sh と同じく「判定できなかった」扱いで警告して起動する。8 通りの終了コード
(0 / 10 → 成功 / 10 → 失敗 / 11 / 1 / 2 / 9 / 12) で分岐を実走確認済み。

回復の前提は従来どおり `dc9650cb` と `302680e6` が入っていること (下記)。
