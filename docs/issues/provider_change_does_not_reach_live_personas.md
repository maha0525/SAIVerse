# プロバイダを変更しても、すでに動いているペルソナには届かない

**起票**: 2026-08-05（資格情報の層束縛の改修中に発見。Codex 八巡目の指摘）
**状態**: 未着手
**関連**: `persona/core.py`（`_llm_client` / `_lightweight_llm_client` のキャッシュ）、`saiverse/provider_configs.py`、`api/routes/providers.py`

## 何が起きるか

UI からプロバイダの接続先や API キー環境変数名を変えて保存すると、設定の一覧とモデル側の解決結果はその場で更新される。しかし **`PersonaCore` は最初に喋ったときに作った LLM クライアントを持ち続ける**ため、そのペルソナは再起動まで**変更前の接続先へ送り続ける**。

条件は「過去に会話したことがあるか」ではなく、**今動いているプロセスの中でそのクライアントを既に作ったかどうか**。だから、以前は会話していても今回の起動後にまだ喋っていなければ新しい設定で動く。

さらに `PersonaCore` は通常用 (`_llm_client`) と軽量用 (`_lightweight_llm_client`) を別々に作って別々に持つ。片方だけ生成済みという状態がありうるので、**同じペルソナの中で新旧の接続が混ざる**こともある。

まだクライアントを作っていないペルソナは新しい設定で作る。つまり同じプロセスの中で、新しい接続先を使うペルソナと古い接続先を使うペルソナが混在する。

プロバイダを**削除**した場合も同じで、すでにクライアントを持っているペルソナは削除後も旧い接続へ送れてしまう。

## なぜ厄介か

API は「保存に成功した」と返すので、利用者は反映されたと考える。ところが実際に喋らせてみると挙動が変わらない。しかも「変わるペルソナ」と「変わらないペルソナ」が同居するため、原因が設定ミスに見える。

## 直すなら

プロバイダの保存・削除・再読込のときに、管理下の `PersonaCore` が持つ通常クライアントと軽量クライアントを破棄して作り直す。**走行中のリクエストとの競合**を扱う必要があるのが本体で、単に `None` を代入するだけでは、応答生成の途中でクライアントが差し替わる事故が起きうる。

ライブ更新を保証しない設計にするなら、その旨を API の契約として明示し、UI にも「変更は再起動後に全ペルソナへ反映されます」と出す。現状は intent 不変条件 11 に「反映の範囲を約束しすぎない」として書いてあるだけで、UI には何も出ていない。

## 今回の改修との関係

2026-08-05 以前は、`api_key_env` を持つ同梱プロバイダを UI から編集すること自体が必ず 400 で失敗していたため、この不整合はほとんど表に出なかった。編集が通るようになったことで初めて現実の問題になった。
