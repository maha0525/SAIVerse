# 読み戻しが「あらすじの途中まで」遡ろうとして、一歩も動かない

**ステータス**: 検証待ち — 再実装・レビュー消し込み完了 (下の §レビューの残余)。まはーの実機でエリスの窓に読み戻しが入ることの確認待ち
**深刻度**: 高 — 会話が残す量を下回っても、畳んだ会話が二度と窓へ戻らない。最終防衛ライン (生のまま読み足す方) だけが毎回働く状態になる
**発見**: 2026-09-04 (エリスの実機で、同日のスペル結果の裁定を入れた直後に露出)

## 症状

会話の行が残す量を下回っているのに、読み戻し (畳んだあらすじを開き直して窓へ会話を戻す機構) が毎回「何もしない」で終わる。ログはこう出る:

```
[metabolism] refill planned nothing (persona=eris_city_a model=gemini-3.8-flash-paid
rows=24029 target=40000): rung 1 is broken (4 source id(s) missing from the presentable history)
```

## 実測 (エリス、2026-09-04 22:28 の本番窓を読み取り専用で再現)

| 量 | 値 |
|---|---|
| 会話の行 | 24,029 字 |
| 残す量 | 40,000 字 → 不足 15,971 字 |
| 読み戻しの予算 | 15,971 字 (= 残す量 − 会話の行) |
| 予算で実際に遡れた範囲 | **14 行 / 16,366 字 / 8-31 09:00 〜 9-01 18:58 (約 1 日分)** |
| その範囲を覆う一次あらすじ | short=648 (8-30 23:08 〜 9-01 18:58、材料 18 件) |
| 材料のうち予算の外にあった数 | **4 件** |

予算の外にあった 4 件:

| id (先頭) | 内容 | 字数 | 印 (line_role) |
|---|---|---|---|
| 7fc2c04e | まはーの発話「えりす……ぎゅ……」 | 9 | main_line |
| c7874e7e | エリスの返事 | 1,137 | main_line |
| 790f4482 | 8/31 09:00 のスケジュール通知 | 130 | **なし (NULL)** |
| be23347c | スペル結果 (Elyth タイムライン) | **6,555** | main_line |

## 原因

**予算 (文字数) で履歴を切ってから、その範囲を覆うあらすじを探している。** あらすじは分割できない単位なので、予算が単位の途中で切れると「材料が揃わない」と判定され、読み戻しは一歩も進めない。

いまの順序 (`sea/session_lifecycle.py::_plan_window_refill` → `sea/window_refill.py::plan_rewind_explained`):

1. 不足分を計算する (残す量 − 会話の行 = 15,971)
2. **その字数ぶん履歴を遡って読む** ← ここが誤り
3. 読めた範囲を覆うあらすじを探し、重なるものを併合して「段」を作る
4. 段の材料が読めた範囲からはみ出していたら `broken` と判定して打ち切る (`window_refill.py:409`)

さらに 2 の予算消費は**生の字数**で数えるので、スペル結果 (1 件 6,000 字級) が予算の大半を食う。上の実測では 16,366 字のうち会話は 1 日分しか含まれず、あらすじ 1 件ぶんの期間 (3 日) にまるで届いていない。

## 裁定 (まはー、2026-09-04)

**「会話が足りないと言ってあらすじの途中まで遡ろうとしているのがおかしい。そんなことはできないのだから、足りないなら一番新しいあらすじを開くしかない。」**

正しい順序 = 上の 2 と 3 を入れ替える:

1. 起点より古い側にある**一番新しいあらすじ (段) を先に決める**
2. **その段の材料が全部入るまで**履歴を読む (読む量は段が決める。予算では切らない)
3. 段を丸ごと開く
4. まだ会話が残す量に届かなければ、次の段へ進んで繰り返す

補足の裁定:

- 段を開いた結果、会話が**残す量を超えるのは問題ない** — 残す量は下限であって上限ではない。
- 段を開くと**上限 (整理を始める量) を超える**場合は、同日の裁定「記憶を削るくらいなら予算超過を受け入れる」に従って開く (旗を立てる)。
- **「できない」で止まって、その先の結末を決めない設計をしないこと。** まはーの言葉: 「じゃあそこのあらすじどうするつもりなの、っていう最終的な部分を一切決めずに保留して仕事放棄してるだけの超無責任な処理じゃん。こんなことはしてほしくない。」これは個別の例外ケースの扱いの話ではなく、**設計の態度そのものへの裁定**。実装では「打ち切る」経路を残すなら、その先に何が起きるかまで書く。

## 裁定の確定 (まはー、2026-09-05 — 設計はここで閉じた)

現状の全分岐を洗った資料 (分岐地図) のレビューで、9/4 の裁定が拡張されて確定した。

**芯: 窓の会話文が目標量 (残す量) を下回っていたら、あらすじがどこにあるかを問わず — 窓の中で畳まれているものも、起点をまたいでいるものも、起点より古い側のものも — いちばん新しいあらすじから順に丸ごと開く。会話文が目標量に達したら終了。**

個別の裁定:

1. **読み戻しは全種の Pulse で走る**。会話の Pulse 限定を外す — 自律→会話と連続したとき、自律側で窓が手当てされないと会話側で窓が変わり、キャッシュヒットしなくなる。
2. **「起点をまたぐ圧縮区間」の特別扱い (前段) を廃止する**。開くべきは常にいちばん新しいあらすじで、またいでいるかどうかは判断に使わない。「開く」の中身が場所で変わる (窓の中の畳みは生表示への切り替えだけ、またぎ・起点より古い側は起点も動かす) のは実装の都合であって、判断には使わない。なお、またぐ区間は必ず対応するあらすじを持つ (あらすじで畳んだ記録だから区間がある) ので、「いちばん新しいあらすじから開く」が自然に拾う — 別の掬い取りは不要。
3. **「開くと残す量を超えるなら開かない」(plan_reopen の天井) は誤りとして撤去する**。残す量を超えるためにやっている処理。
4. **「予算」という概念を廃止する**。残す量は目標量であり、読む範囲を字数で切らない。達したかどうかの物差しは常に会話文 (stored_message_chars) — スペル結果などの機構行を見ない。
5. **材料に読めない行があるあらすじでも止まらない** (broken 停止の撤去)。壊れているかどうかに関係なく、読める行を全部生で戻して進む。
6. **ループの終了条件は「会話文が目標量に達したら終了、達していなければ次のあらすじへ」だけ**。
7. **上限超過時に「古いものから外して測り直す」検算は廃止する** — 足りないから開いているのだから原理的に不要。合計が上限を超えたら WARNING と context-status で見えるようにするだけで、開いた結果は保つ。
8. **最終防衛ラインは現状のまま**。目標量まで生で読み足す設計で正しく、あらすじの単位は適用しない (適用したら最終ラインの意味がない)。部分的な二重提示の受容も既定どおり。
9. **あらすじに覆われていない行 (編纂対象なのにどのあらすじにも入っていない行) も一緒に生で戻す**。「むしろそういう行を読めないのはバグ」。「編纂なしで忘れた過去を復活させない」という 7/30 由来の守りは撤去 — **なにも忘れないのが SAIVerse の基本思想**で、「忘れた過去」という概念自体が世界前提と食い違う (最終防衛ラインはあらすじに関係なく生で読むので、守りとして機能してもいなかった)。

用語の裁定: rung / ladder の直訳「段」「梯子」は用語として不可 (2026-09-05)。新しいコード・文書は「あらすじ」の語彙で書く — 開く単位は「あらすじ」、併合が要る文脈は「重なるあらすじはまとめて開く」と中身を言う。

実装後の宿題: 7/30 のレビュー由来の守りの棚卸し → [audit_20260730_review_guards.md](audit_20260730_review_guards.md)

## 実装の方針 (9/5 設計確定後)

- `sea/runtime.py`: 読み戻しの `pulse_type in (None, "user")` ゲートを外し、最終防衛ラインと同じく全種の Pulse で走らせる。
- `_plan_window_refill` (`sea/session_lifecycle.py`): 三段構え (またぐ区間の前段 → 窓内を開く → 予算で引き戻す) を一本化する。「開ける対象」= 窓の圧縮区間 (digest 表示中のもの) + 起点より古い側の一次あらすじを新しい順に並べ、一つずつ丸ごと開いては提示を組み直して会話文を測り、目標量に達したら終了。
- 古い側のあらすじの取得は「予算分読んでから覆いを探す」のではなく、**あらすじを先に選んでから、その材料の行を読む** (材料の最古の行から起点までを読む形は `get_history_from_anchor` の流用が利く)。
- 材料を共有する・範囲が重なるあらすじをまとめて一枚の圧縮区間として開く併合は残す (同じ行が二つの区間に属すると digest が二重になるため)。既存の窓の区間との併合 (absorbed_existing) も残す。
- `plan_rewind` の停止条件群 (broken / 予算超過 / 覆われていない行) と、検算の「外す」ループは撤去。読めない行は飛ばして読める行だけ戻す。
- 旧設計 (予算切り・broken 停止・会話 Pulse 限定) を仕様として固定しているテストは、新設計の仕様に書き換える。

## レビューの残余 (2026-09-05 実装後、Codex 3 件の裁定)

再実装への Codex レビューは high 1・medium 2。medium の一つ (テストの偽物照会が実物と違う物差しで「新しい」を選ぶ) は修正した。残り 2 件は経路を最後まで辿った上で**既知の境界として受容** — 理由ごとここに残す。

1. **[high] 厳格モードが digest 解決の失敗まで貫通していない**: 提示の組み立て (`apply_folds`) は digest の解決に失敗した区間を生表示に倒す (fail-open)。厳格モードの計画はその生表示を測るので、DB の一時障害の間は「開くものが無い」と誤判定しうる。**受容の理由**: この生表示は測定だけでなく**実際にペルソナへ送られる提示そのもの**なので、「測った窓と喋る窓が食い違う」ことはなく、床の不変条件 (会話が痩せたまま喋らない) は破れない。書き込みも区間の記録を消さない (未変更の記録をそのまま書き戻す)。実害は「その Pulse で開き損ねる」だけで、読み戻しは全 Pulse で走るため次の Pulse が自己修復する。挙動自体は 7/30 実装から既存で、この差分の退行ではない。厳格を `apply_folds` まで通す改修は提示層全体に触るので、この変更には含めない。
2. **[medium] 開くあらすじの照会が、開くたびに再実行される (最悪 O(K²))**: 実データの規模 (一次あらすじ 1 件 ≈ 数千字、開く数 K は数件〜十数件) では問題にならない。病的な形は「材料が全滅したあらすじが大量にあり、全部 skip し続ける」場合で、skip の記録は Pulse を跨いで持たないため毎 Pulse 同じ走査をやり直す — ただし材料の行が消える運用 (行の削除) は SAIVerse ではほぼ無い。実データで遅延が観測されたら「候補を一括で引いて計画側で消費する」形に直す。

二巡目 (テスト修正後) は high 1・medium 2。処置:

3. **[high] 作業セッションの入口 (`sea/work_session.py`) が読み戻しを通らない**: 半分本物。作業セッションは会話へ発話せず窓の帳簿も動かさないので、指摘のうち「不足した窓のまま発話できる」「次の会話 Pulse でキャッシュ不一致」は成立しない。本物の半分は「痩せた窓のまま作業する」— 作業セッションは 2026-07-23 以降メインの会話履歴を文脈に含むため。「会話かどうかで可否を変えない」(裁定 1) の精神で読み戻しの呼び出しを配線した (失敗は握って続行)。**最終防衛ライン (unmet で見送る) は張らないで確定** (2026-09-05 まはー「作業セッション対応のために労力を割かなくていい」)。⚠️ そもそも作業セッション自体が退役済みの疑いがある — まはー「作業コマも生活コマも無くなった」。呼び出し元がコードに現存することは生存の証明にならない。生死の念入りな調査は別件 [work_session_liveness_audit.md](work_session_liveness_audit.md)。配線は調査の結論まで残す (呼ばれなければ走らず、害はない)。
4. **[medium] テストの偽物照会が実物の絞り込み (thread_id / created_at 第二キー / NULL の並び) を写していない**: 偽物は計画部の順序論理の試験具で、スレッドの意味論はそこで使わない。代わりに**実 DB のヘルパテスト側**を、別スレッド除外・end_time 同値の第二キー・NULL の並び・level 絞りまで固定する形に拡張した。
5. **[medium] 「窓の中を先に、古い側を後に」は場所ごとの二段階であって単一の新しさ順ではない**: 却下。開く順序の物差しは entry の end_time ではなく「開いて窓に**戻る中身**の位置」— 窓の圧縮区間が戻す中身は必ず起点より新しく、古い側のあらすじが戻す中身は必ず起点より古い (窓側の材料は既に生で見えている) ので、1a → 1b の順は中身の物差しでは常に新しい順。1a 内も「覆う提示中の最新行」降順。古い側同士は読みが起点まで連続なので、選択順が戻る中身を変えることはない (より古くから読む = 包含するだけ)。この論証は `openable_folds_newest_first` の docstring にもある。

三巡目 (作業セッション配線後) は high 1・medium 1。処置:

6. **[high] 計画のあらすじ照会が SAIMemory の `_db_lock` の外で走る**: 却下 (既知の境界として記録)。実測 `sqlite3.threadsafety = 3` (直列化モード — 単一接続の並行使用は C ライブラリ水準で安全) + `check_same_thread=False` で、接続レベルの破壊は起きない。裸の conn 照会は旧実装 (`get_entries_covering_messages` / `filter_chronicle_eligible_ids`) と最終防衛ライン (`_floor_coverage_folds`) から続く本ファイルの既存の書き方でもある。計画→書き込みの隙間の整合は設計上 CAS (起点の一致検査) の仕事で、読みにロックを足してもその隙間は閉じない。残余: 起点を動かさずに圧縮区間だけを書き換える並行操作 (あらすじの手動削除の道連れ等、API スレッド) が計画の読みと書きの間に入ると、古い区間記録を書き戻しうる — 結果は digest 解決失敗 → 生表示 (fail-open) で、次の畳みが引き当て直す。稀・自己修復のため受容。
7. **[medium] 覆いの照会 (`get_entries_covering_messages`) が行数ぶんの `?` を生成し、SQLite の変数上限で失敗しうる**: **採用・修正**。上限はビルド設定次第で、SQLite の既定は 32,766 (この開発機の CPython 同梱ビルドは実測 250,000 — 250,001 個で `too many SQL variables` を実測)。エンドユーザー環境の Python がどちら側かは選べず、`sea/coverage_repair.py` も同じ照会を 400 件刻みで防御済み = 実在の脅威として扱われている。旧実装は予算で読む行数が頭打ちだったが、新実装は「あらすじの材料から起点まで」を無制限に読むため、起点前に大量の行を持つペルソナ (ログ取り込み・未被覆の大穴 = §16 の補修対象層) で踏みうる。予算撤去が生んだ真水の新規露出。照会を 500 件ずつのチャンク分割 (同ファイルの `get_oldest_present_message_id` と同じ型) に直した。

## この日に判明した別の事実 — 印 (line_role) は仕分けの仕事をしていない

調査の途中で「印が無い行があるから読めないのだ」と誤診し、その過程で印の実態が分かった。**今回の欠陥とは無関係だが、別の裁定材料になるので記録する。**

- `saiverse_memory/adapter.py:2840` (`_payload_passes_context_filter`) は、**`line_role` が NULL の行を `main_line` とみなす**。だから印が無い行も窓に載るし、実際にスケジュール通知は本番のリクエストに入っている (まはーの観測どおり)。
- エリスの全 9,890 行の内訳:

  | line_role | scope | 件数 |
  |---|---|---|
  | (NULL) | committed | 8,787 |
  | main_line | committed | 1,045 |
  | main_line | discardable | 38 |
  | sub_line | volatile | 20 |

- **除外されるべきもの (sub_line) は全部 `volatile`** で、その中身は画像生成と部屋移動の子プレイブックの往復だけ。つまり仕分けは実質 `scope` が担っていて、`required_line_roles=["main_line"]` は追加の仕事をしていない。
- 印が無い 8,787 件の内訳は会話 7,339 件が主で、ほかに 2026-02 頃の調査の内部思考など数十件。すべて `committed` で、今も本線として読まれている。
- 印が付かない経路が現存する: `sea/runtime.py:328` のスケジュール発火の枝が `add_to_persona_only` で保存していて、`line_role` を渡していない (毎日 9:00 に 1 件増える)。

まはーの問い「そもそも本線の印なんざ要らないのでは」は、**このデータの範囲では成立している**。廃止するか、印を付ける経路を揃えるかは別件として裁定が要る。
