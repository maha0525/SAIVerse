# 最新ではない ZIP から導入すると、中身は古い版のまま、更新もできなくなる

**状態**: 検証待ち (2026-10-02 に直し、PR #343 で develop に入った。次の版に載る。本物の setup.bat をまっさらな Windows で最初から通すことは未確認のまま残る)。発見は 2026-10-02 (v0.3.19 の発行当日、クリーンな Windows での ZIP インストールのテストを準備しているときに、まはーの「最新版をダウンロードしたのでは、アップデート先が無い」という指摘から見つかった)。
**深刻度**: P2 — 新しい版が出たあとで、手元に残っていた古い ZIP から setup.bat を実行した利用者は、古い版のまま動き、update.bat も画面の「Update」ボタンも「手元に変更がある」と断って更新できない。最新の ZIP をダウンロードしてすぐ導入する利用者には起きない

## 何が起きるか (時間順)

1. 利用者が、ある版 (例: v0.3.18) の ZIP をダウンロードして解凍する。
2. そのあとで新しい版 (例: v0.3.19) が発行される。
3. 利用者が setup.bat を実行する。setup.bat は、ZIP を解凍したフォルダを Git の管理下に置くために、`git init` → `git fetch origin` → `git reset origin/main` を実行する (`setup.bat` の「9b. Initialize git repository」)。
4. `git reset origin/main` は、Git の記録上の現在地を main の最新 (v0.3.19) に合わせるが、フォルダの中のファイルは書き換えない。その結果、Git は「このフォルダは v0.3.19 だ」と記録しているのに、ファイルの中身は v0.3.18 のままになる。
5. Git から見ると、v0.3.18 と v0.3.19 のあいだで変わったファイルが全部「利用者が手元で書き換えたファイル」に見える。
6. update.bat や画面の「Update」ボタンは、更新の前に「手元に変更があるか」を調べ (`scripts/update_engine.py` の `assert_git_update_ready`)、変更があると更新を始めずに断る。Git の記録の上ではもう最新なので、更新する先も無い。

## 確かめたこと (2026-10-02、作業用フォルダでの再現)

- v0.3.18 のタグから ZIP と同じ中身を作り (`git archive`、リリースの自動処理と同じコマンド)、setup.bat と同じ順で `git init` → `git fetch` → `git branch -M main` → `git reset origin/main` を実行した。そのあと `VERSION` は 0.3.18 のまま、Git の現在地は v0.3.19 のマージコミットになり、`git status --porcelain --untracked-files=no` は 87 件の変更を返した。
- 同じ手順を v0.3.19 のタグから作った中身で実行すると、変更は 0 件だった。最新の ZIP から導入する道は、この問題を踏まない。

実際の ZIP と実際の setup.bat では、まだ確かめていない (再現は同じ Git のコマンドを手で実行したもの)。

## 誰が踏むか

- ZIP をダウンロードしてから setup.bat を実行するまでのあいだに、新しい版が発行された利用者。
- GitHub の画面でブランチを develop などに切り替えてから「Code → Download ZIP」で落とした利用者。このときは、ZIP の中身が main のどの版とも一致しない。ブランチを切り替えずに落とした ZIP は、既定のブランチである main の中身になるので、最新の ZIP と同じくこの問題を踏まない (README は「Code」ボタンからの落とし方も案内している)。

## 直したこと (2026-10-02、まはー指示「先に直すべきとこ直してもう準備しといて」)

Git を初期化する処理を `scripts/init_git_repo.py` に移し、setup.bat と setup.sh の両方から呼ぶ形にした。守る約束は一つで、**終わったとき、Git が記録している版のファイルと、フォルダの中のファイルが一致している**こと。

- Git の記録は、フォルダの中身と同じ版に合わせる。フォルダの版は `VERSION` ファイルで分かり、発行済みの版には同じ名前のタグ (`v0.3.18` など) がある。新しい版は、ふつうの更新として先に残るので、update.bat で上げられる。導入の最後に「新しい版がある。update.bat で上げられる」と知らせる。
- 使うタグは、main の履歴に含まれるものだけにする。アーリーアクセス版のタグは main の履歴の外にあり、そこを記録すると main の最新へ早送りできなくなるため。
- 合うタグが無い中身 (ブランチを切り替えて落とした開発中の ZIP など) は、これまでどおり main の最新を記録する。
- どの場合も、最後にファイルと記録が一致しているかを確かめる (更新プログラムが更新の前に調べるのと同じ問い)。一致しないときは、SAIVerse は動くが更新は断られることと、最新の ZIP の場所を、導入の画面でその場で知らせる。フォルダの中のファイルは書き換えない。
- あわせて、`git init` の直後で止まった導入 (ダウンロード中のネットワーク切れなど) を、もう一度 setup を実行すれば続きから仕上がるようにした。これまでは `.git` フォルダがあるだけで「初期化済み」と扱っていたので、一度止まると更新できないフォルダが残っていた。

### 確かめたこと

- 本物の Git を使ったテスト 10 件 (`tests/test_init_git_repo.py`): 古い ZIP から入れても記録がその版になり、変更 0 件で、次の版へ早送りできる / 最新の ZIP / どの版でもない中身は警告になり、ファイルは書き換わらない / 手元で書き換えたファイルがあるときの警告 / main の履歴の外のタグは使わない / 途中で止まった導入の再開 / 初期化済みのフォルダには触らない / 以前の導入で詰まったフォルダには、Git の記録を動かさずに状況を知らせる / setup.bat と setup.sh が同じスクリプトを呼ぶ。
- 本物のファイル一式での通し: 作業用フォルダに「修正入りの版 0.3.20 と、その次の版 0.3.21 が出ている」架空の配布元を作り、リリースの自動処理と同じコマンドで 0.3.20 の ZIP を作って解凍し、setup が実行するのと同じ一行を実行した。記録は v0.3.20、変更 0 件、「新しい版がある」の知らせが出た。そのフォルダ自身の更新プログラムの検査 (`assert_git_update_ready`) を通り、0.3.21 へ早送りできた。

### レビュー (2026-10-02、ローカルのレビューモデルで一巡)

指摘 8 件の裏を取った。

- 採用 4 件: (1) すでに Git の管理下にあるフォルダでは、ファイルと記録が一致しているかを確かめずに「OK」と出していた。以前の導入で詰まったフォルダ (記録は最新、ファイルは古い) でもう一度 setup を実行した人に、何も伝わらない。確かめて、一致しないときは状況と抜け道を知らせるようにした。開発者の作業中のフォルダかもしれないので、Git の記録は動かさない。(2) ダウンロードの進み具合が画面に出なくなっていた。回線が遅いと、止まったように見える。ダウンロードだけは Git 自身の表示をそのまま出すようにした。(3) 「両方のスクリプトが同じ処理を呼ぶ」ことを確かめるテストが、コメントに名前が書いてあるだけで通る作りだった。コメントを除いた行で、実際に呼んでいることを確かめるようにした。(4) 記録を置いた直後にウィンドウを閉じると、更新元の設定が入らないまま「初期化済み」と扱われる隙間があった。更新元の設定を先に書き、記録を置く操作を最後の一手にした。
- 裏取りで解消 3 件: 「ZIP がタグより後のコミットから作られていたら、最新の ZIP でも毎回警告になる」は、リリースの自動処理 (`.github/workflows/release.yml`) がタグを打ったコミットそのものから ZIP を作ることを確かめて解消。「setup.bat の後ろの処理が、このスクリプトの終了コードを読んで分岐がずれないか」は、後ろの処理が読むのは直前の自分のコマンドの結果だけであることを確かめて解消。「ダウンロードのあと main の最新が参照できない環境があるのでは」は、参照先を作る設定を `git remote add` が書くので解消。
- 採ったが実害は無かった 1 件: 名前を変えたファイルが件数に二重に数えられる可能性。この処理のあとでは起きない形だが、数え方を一行一件に改めた。

### 確かめていないこと

- 本物の setup.bat を、Git の入っていない Windows で最初から最後まで通すこと。修正は、修正を載せた版の ZIP にしか入らないので、発行後にクリーンな Windows (Windows サンドボックス) で確かめる。
- macOS / Linux での setup.sh の通し。スクリプトの本体は両方で同じ Python だが、setup.sh から呼ぶ一行は構文の検査 (`bash -n`) しかしていない。

### この修正が届かない人

- 修正は setup.bat / setup.sh と一緒に ZIP に入る。**修正を載せた版より前の ZIP には入っていない**ので、古い ZIP を手元に持っている人が、新しい版が出たあとでそれを導入すると、これまでと同じ状態になる。
- すでにこの状態になっている利用者のフォルダも、更新できないので修正を受け取れない。抜け道は、最新の ZIP を落として新しいフォルダで setup を実行すること (ペルソナの記憶や設定はフォルダの外の `~/.saiverse` にあるので残る。API キーを入れた `.env` はフォルダの中にあるので、古いフォルダから写す)。報告が来たら、この手順を案内する。
