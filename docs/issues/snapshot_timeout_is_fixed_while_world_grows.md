# スナップショットの制限時間が固定値で、世界の成長に追い越される

**ステータス: 暫定措置済み・恒久策は未着手** (2026-09-02 起票。同日、制限時間を 900 秒 → 3600 秒へ引き上げる暫定措置を実施)

## 問題

コード更新の前に取る世界のスナップショット (`scripts/snapshot.py save`) には、呼び出し側
(`scripts/update_engine.py` の `create_pre_update_snapshot`) が制限時間を課している。この
制限時間が **世界の大きさと無関係な固定値** である一方、スナップショットの所要時間は
**世界の大きさに比例して伸びる**。

比例するのは、この処理が対象ファイルを二度なぞるため:

1. 全ファイルの sha256 を計算してマニフェストを作る
2. 改めて全ファイルを ZIP へ圧縮する

したがって世界が育てば、固定値はいつか必ず追い越される。

## 実際に起きたこと (2026-09-02)

まはーの環境で `start.bat` が起動不能になった。

`.update_complete` (更新が完了したことを記録するファイル) が旧形式のまま残っていたため
毎回「更新が中断されている」と判定され、その続きとして pre-update スナップショットが走る。
ところが `~/.saiverse/` が 76GB あり、除外対象が `backups` と `snapshots` だけだったので、
再生成可能な `llama_cache/` (16GB) まで含めた 24.4GB が sha256 と ZIP 圧縮の対象になっていた。
900 秒では終わらず、毎回 15 分待たされて失敗する。**利用者が自力で抜けられない**状態だった。

同日の修正 (コミット `73d3fe53`) で `llama_cache/` を除外し、対象は 8.9GB (-63%) に落ちた。
その上で制限時間を 3600 秒へ引き上げた。

## なぜ暫定なのか

引き上げは「いま追い越されている」状態を解消するだけで、**構造は変えていない**。世界が
育てば同じことが起きる。まはー自身の言葉で「最適な答えが見つからないけど、15 分はわりと
超えうると思うから」——つまり 60 分もまた、根拠のある数字ではない。

一方、制限時間を単に撤廃するのも採れない。本当に固まった場合に無限に待つことになり、
`start.bat` から呼ばれる以上、利用者は手動介入の機会を持たない。

## 恒久策の案 (未着手)

**「完了したか」ではなく「生きているか」で判定する形へ変える。**

現在 `snapshot.py` は収集ファイル数を報告した後、ZIP 書き込みの間ずっと黙っている。
外からは「進んでいる」と「固まっている」の区別がつかない。ここを変える:

- `snapshot.py` 側: 処理した量を定期的に標準出力へ出す
- `update_engine.py` 側: `subprocess.run` の一括待ちをやめ、出力を逐次読みながら
  「一定時間ぶん進捗が出なかったら死んだと判断する」

こうすると、世界が何 GB でも進んでいる限り待ち、本当に固まった場合は世界の大きさと
無関係に数分で気づける。世界と無関係な固定値が設計から消える。

代償は実装が増えること (進捗の出力と、逐次読み取りへの書き換え)。
