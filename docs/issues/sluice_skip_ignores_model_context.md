# モデルを切り替えると、上限の小さいモデルが記憶の整理から抜け出せなくなる (スルースを飛ばす判定が、実際に送る量を見ていない)

**起票**: 2026-09-17 (うるさんの報告「普段は Gemma 4、たまに Qwen や 4o。4o に切り替えたら弾かれて会話できない」、まはー経由)
**状態**: 実装中 — 修正方針はまはーの GO 済み (2026-09-17)
**関連**: [sluice_coverage_gaps.md](../intent/sluice_coverage_gaps.md) (第一段 A「冷たいときはスルースを飛ばす」— 本件はその判定の穴)、`sea/sluice.py` (`_call_sluice_llm` / `get_max_span_chars` / 後から通す採取)、`sea/session_lifecycle.py` (`_run_metabolism_locked` のスルースの節)、`api/routes/people/sluice.py`、`saiverse/token_estimator.py`

## 症状

うるさんのペルソナで、OpenRouter 経由の GPT-4o (2024-11-20、コンテキスト長 128,000 トークン) に切り替えると会話が成立しない。v0.3.11 から続き、v0.3.13 でも同じ。

- 会話のエラー: `maximum context length is 128000 tokens` / `requested about 311900 tokens`。
- 「データ送信量の管理」の表示: 4o を選ぶと 290,404 字 (会話 260,058 / スペル結果 25,547 / 部屋の様子 4,799)。同じペルソナで Gemma 4 を選ぶと 73,073 字。
- 4o で「溜まった会話をあらすじにまとめる」を実行すると、あらすじの生成は成功し、その後のスルースが同じ 400 で失敗する。backend ログは `chronicle_status=ok` / `sluice_status=failed`。畳みは適用されず、送る会話は減らない。
- Qwen では、同程度に履歴が溜まった状態でも畳みが成功した。

## 原因 (コードの読解で確定)

v0.3.11 で、スルースに入りきらない量のときはスルースを走らせず、読めていない範囲を記録して畳みを進める判定を入れた (sluice_coverage_gaps 第一段 A)。うるさんのログは `sluice_status=failed` で、飛ばしたときの `skipped_cold` になっていない。つまりこの判定が「入る」と答えて、スルースを走らせている。

判定が測っているのは、パンマーカー (スルースが最後に読んだ位置の印) から、いまモデルに送っている会話の末尾までの字数だけで、それを固定の 100,000 字 (`SAIVERSE_SLUICE_MAX_SPAN_CHARS`) と比べている。一方、スルースが LLM に実際に送るのは、そのモデルに普段送っている会話の範囲まるごと (先頭の自己定義や部屋の様子を含む) と、スルースの指示文である。

モデルの切り替えがこの差を大きくする。時間順に追うと次のとおり。

1. パンマーカーはペルソナに一つだけで、どのモデルのスルースが読んでも進む。うるさんは普段 Gemma 4 で話しているので、印は最近の位置にある (飛ばしが起きていないログが、その裏付けになる)。
2. 送る会話の範囲 (起点と、あらすじに置き換えた区間) は、モデルごとに別々に持っている。4o の範囲は 290,404 字ある。
3. 4o で話しかけると、応答の前に整理が走る。あらすじの生成は範囲を刻んで行うので成功する。
4. スルースを飛ばすかの判定は、印から末尾までの少しだけを測るので「入る」になる。
5. スルースは 4o の範囲まるごと (約 31 万トークン) を送り、128,000 を超えて 400 になる。
6. スルースが失敗した回は畳みを適用しない決まりなので、範囲が減らない。次に話しかけても 3 から同じことが繰り返され、4o は自力で抜け出せない。

intent の第一段 A は「閾値はモデルのコンテキスト長から導く (実装時に確定)」と書いていた。実装で「環境変数の固定値」に変えたことは intent の経緯に差分 (1) として残っており、その差分がこの穴になった。

### まだ確かめていないこと

同じペルソナで 4o の範囲だけが Gemma 4 の 4 倍ある理由は確かめていない。コードで確かめた事実は二つある。あらすじへの置き換えはモデルごとに持つので、Gemma 4 で畳んだ区間は 4o の範囲では置き換わらない。冷えたモデルの起点が前へ進めるのは、「まだどのあらすじにも入っていない最初の会話」(編纂の最前線) までだけである。ここから、うるさんの記憶のどこかにあらすじの抜けがあり、4o の起点がそこで止まっている可能性がある。確定にはうるさんのデータが要るが、下の修正は範囲の大きさの理由によらず 4o を自力で回復させるので、直すのに必要な情報ではない。

## 決定 (2026-09-17 まはー GO)

メティスの修正方針に、まはーが「了解、それでいい！対応よろしく！」と GO を出した。方針は次のとおり。

- スルースを走らせるかの判定に、「スルースが実際に送る中身が、そのモデルに入るか」を加える。測るのは、送る会話を組み立て終わった直後で、LLM を呼ぶ直前の実物である。
- 字数からトークン数への換算は、日本語を安全側に見て 1 字 ≒ 1 トークンとし、出力の枠も差し引く。
- 入らなかったら、既存の飛ばしとまったく同じ扱いにする。スルースは走らせず、読めていないまま畳まれる範囲を記録し、畳みは進める。
- 固定の 100,000 字の判定は残す。あちらは 429 (送信量の制限) を避ける役で、目的が別だから。
- うるさんが提案した「別の大きいモデルで代わりに畳む」は採らない。定常のスルースは会話を送っているモデルのまま読む前提で組まれており、モデルを差し替えると畳む範囲とスルースが読む範囲がずれる。別のモデルで通したい願いは、sluice_coverage_gaps の「後から通す」(決定 3: 後から通す操作はモデルが通常の会話と違ってよい) の方で叶う。

## 設計

### 1. 送る中身の見積もり (`sea/sluice.py`)

- 見積もりは、文字 1 字を 1 トークン、画像 1 枚を `saiverse/token_estimator.py` の `estimate_image_tokens(provider)`、メッセージ 1 通ごとに 4 トークンとして足す。文字は、`content` が文字列ならその長さ、部品の列ならテキスト部品の長さを数える。画像は、部品の列の画像部品と `metadata.media` の画像を数える (`estimate_messages_tokens` と同じ数え方)。
- 上限は、そのモデルのコンテキスト長の 9 割から、スルースの出力の枠 (`_MAX_OUTPUT_TOKENS`) を引いた値である。
- 既存の `estimate_messages_tokens` をそのまま使わないのは、日本語 1 字を 1.5 トークンと数えるからである。うるさんの実測 (GPT-4o で、送った 290,404 字に先頭の自己定義を足して約 311,900 トークン) では 1 字 ≒ 1 トークンで、1.5 で数えると、普段の大きさの範囲 (上限 60,000 字の水位 + 先頭の自己定義) でも、128,000 トークンのモデルでスルースが飛ばされうる。
- モデルの設定が見つからずコンテキスト長が引けないときは、判定をせずに従来どおり走らせ、WARNING を残す。

### 2. 定常のスルース (整理の中のスルース)

- `_call_sluice_llm` で、実際に使うモデル (構造化出力の都合で差し替わった後のモデル) が決まった後、`generate` の前に見積もりと上限を比べる。超えていたら LLM を呼ばず、専用の例外を送出する。
- `_run_metabolism_locked` はその例外を、既存の量による飛ばしと同じ扱いにする。スルースの状態を `skipped_cold` にし、読めていないまま畳まれる範囲 (印より後ろで、今回の畳みの対象に入っているメッセージ) を記録し、畳みを進める。レート制限の小休止は置かない。ログは既存の飛ばしと区別できる文面にする (モデル名・見積もり・上限を含める)。
- 範囲の記録が空 (畳まれる古い側を、すでに別のモデルのスルースが読み終えている) なら、記録は書かずに畳みを進める。これは既存の飛ばしと同じ規則である。

### 3. 後から通す採取 (同じ欠陥の隣)

後から通すジョブ (`run_sluice_capture`、API `POST /api/people/{id}/sluice/capture`) は、会話を固定の 100,000 字ごとに刻んで、指定のモデル (省略時は本人のモデル) に送る。上限の小さいモデルを指定すると、同じ理由で 400 になる。

- 刻む大きさを、固定の 100,000 字と「そのモデルに入る量」の小さい方にする。入る量は、会話以外の部分 (本人モードの前置きと指示文、機構モードの指示文) を見積もって上限から引き、メッセージ 1 通ごとに写しの書式が足す分も数えて決める。
- 見積もり (`dry=True`) と実行は、同じモデルと同じモードで同じ刻み方を使う。表示と実走が違う数を言わない。
- LLM を呼ぶ直前にも、定常のスルースと同じ比較をする。1 通だけで入らないメッセージがある場合はここで止まり、ジョブは「選んだモデルには一度に送れない長さの会話が含まれている。コンテキスト長の大きいモデルを選んで再実行してほしい」という失敗を返す。

## 検証の旅

- 単体: 見積もりの数え方 (文字列・部品の列・画像) / 定常のスルースで、上限を超える組み立てなら LLM を呼ばず飛ばし、範囲を記録して畳みを進めること / 上限内なら従来どおり走ること / 印が畳みの対象より後ろにあるとき記録が空で畳みが進むこと / 後から通すジョブで、小さいモデルの刻みが上限内に収まり、見積もりと実行の刻み数が一致すること / 1 通だけで入らないときのジョブの失敗の文面。
- 隔離環境: 合成ペルソナに、コンテキスト長の小さいモデル定義と、印より前に大きく溜まった会話の範囲を作る。そのモデルで話しかけ、mock LLM で「スルースが飛ばされる → 畳まれる → 送る範囲が残す量まで縮む → 返事が返る」までを通し、ログと送る量の表示を読む。
- 実機: うるさんに修正版で 4o に切り替えてもらい、会話が成立することを確かめてもらう。

## 経緯

- 2026-09-17: うるさんの報告を受け、コードを読んで原因を確定した。修正方針をまはーに示し、GO を得て実装に入った。調査の途中で、後から通すジョブにも同じ欠陥 (刻む大きさがモデルの上限を見ていない) があるのを見つけ、同じ変更に含めた。
