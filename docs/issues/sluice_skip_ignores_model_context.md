# モデルを切り替えると、上限の小さいモデルが記憶の整理から抜け出せなくなる (スルースを飛ばす判定が、実際に送る量を見ていない)

**起票**: 2026-09-17 (うるさんの報告「普段は Gemma 4、たまに Qwen や 4o。4o に切り替えたら弾かれて会話できない」、まはー経由)
**状態**: 検証待ち — 修正方針はまはーの GO 済み (2026-09-17)。レビュー三巡を経て、まはーの判断でレビューを終えた。隔離環境の実経路の確認は合格。残るのは PR のまはー確認と、うるさんの環境での確認
**関連**: [sluice_coverage_gaps.md](../intent/sluice_coverage_gaps.md) (第一段 A「冷たいときはスルースを飛ばす」— 本件はその判定の穴)、`sea/sluice.py` (`_call_sluice_llm` / `get_max_span_chars` / 後から通す採取)、`sea/session_lifecycle.py` (`_run_metabolism_locked` のスルースの節)、`api/routes/people/sluice.py`、`saiverse/token_estimator.py`

## 症状

うるさんのペルソナで、OpenRouter 経由の GPT-4o (2024-11-20、コンテキスト長 128,000 トークン) に切り替えると会話が成立しない。v0.3.11 から続き、v0.3.13 でも同じ。

- 会話のエラー: `maximum context length is 128000 tokens` / `requested about 311900 tokens`。
- 「データ送信量の管理」の表示: 4o を選ぶと 290,404 字 (会話 260,058 / スペル結果 25,547 / 部屋の様子 4,799)。同じペルソナで Gemma 4 を選ぶと 73,073 字。
- 4o で「溜まった会話をあらすじにまとめる」を実行すると、あらすじの生成は成功し、その後のスルースが同じ 400 で失敗する。backend ログは `chronicle_status=ok` / `sluice_status=failed`。畳みは適用されず、送る会話は減らない。
- Qwen では、同程度に履歴が溜まった状態でも畳みが成功した。

## 原因 (コードの読解で確定)

v0.3.11 で、スルースに入りきらない量のときはスルースを走らせず、読めていない範囲を記録して畳みを進める判定を入れた (sluice_coverage_gaps 第一段 A)。うるさんのログは `sluice_status=failed` で、飛ばしたときの `skipped_cold` になっていない。つまりこの判定が「入る」と答えて、スルースを走らせている。

判定が測っているのは、パンマーカー (スルースが最後に読んだ位置の印) から、いまモデルに送っている会話の末尾までの字数だけで、それを固定の 100,000 字 (`SAIVERSE_SLUICE_MAX_SPAN_CHARS`) と比べている。一方、スルースが LLM に実際に送るのは、そのモデルに普段送っている会話の範囲まるごと (先頭の自己定義や部屋の様子を含む) と、スルースの指示文である。

モデルの切り替えがこの差を大きくする。時間順に追うと次のとおり。

1. パンマーカーはペルソナに一つだけで、どのモデルのスルースが読んでも進む。うるさんは普段 Gemma 4 で話しているので、印は最近の位置にある (飛ばしが起きていないログが、その裏付けになる)。
2. 送る会話の範囲 (起点と、あらすじに置き換えた区間) は、モデルごとに別々に持っている。4o の範囲は 290,404 字ある。
3. 4o で話しかけると、応答の前に整理が走る。あらすじの生成は範囲を刻んで行うので成功する。
4. スルースを飛ばすかの判定は、印から末尾までの少しだけを測るので「入る」になる。
5. スルースは 4o の範囲まるごと (約 31 万トークン) を送り、128,000 を超えて 400 になる。
6. スルースが失敗した回は畳みを適用しない決まりなので、範囲が減らない。次に話しかけても 3 から同じことが繰り返され、4o は自力で抜け出せない。

intent の第一段 A は「閾値はモデルのコンテキスト長から導く (実装時に確定)」と書いていた。実装で「環境変数の固定値」に変えたことは intent の経緯に差分 (1) として残っており、その差分がこの穴になった。

### まだ確かめていないこと

同じペルソナで 4o の範囲だけが Gemma 4 の 4 倍ある理由は確かめていない。コードで確かめた事実は二つある。あらすじへの置き換えはモデルごとに持つので、Gemma 4 で畳んだ区間は 4o の範囲では置き換わらない。冷えたモデルの起点が前へ進めるのは、「まだどのあらすじにも入っていない最初の会話」(編纂の最前線) までだけである。ここから、うるさんの記憶のどこかにあらすじの抜けがあり、4o の起点がそこで止まっている可能性がある。確定にはうるさんのデータが要るが、下の修正は範囲の大きさの理由によらず 4o を自力で回復させるので、直すのに必要な情報ではない。

## 決定 (2026-09-17 まはー GO)

メティスの修正方針に、まはーが「了解、それでいい！対応よろしく！」と GO を出した。方針は次のとおり。

- スルースを走らせるかの判定に、「スルースが実際に送る中身が、そのモデルに入るか」を加える。測るのは、送る会話を組み立て終わった直後で、LLM を呼ぶ直前の実物である。
- 字数からトークン数への換算は、日本語を安全側に見て 1 字 ≒ 1 トークンとし、出力の枠も差し引く。
- 入らなかったら、既存の飛ばしとまったく同じ扱いにする。スルースは走らせず、読めていないまま畳まれる範囲を記録し、畳みは進める。
- 固定の 100,000 字の判定は残す。あちらは 429 (送信量の制限) を避ける役で、目的が別だから。
- うるさんが提案した「別の大きいモデルで代わりに畳む」は採らない。定常のスルースは会話を送っているモデルのまま読む前提で組まれており、モデルを差し替えると畳む範囲とスルースが読む範囲がずれる。別のモデルで通したい願いは、sluice_coverage_gaps の「後から通す」(決定 3: 後から通す操作はモデルが通常の会話と違ってよい) の方で叶う。

## 設計

### 1. 送る中身の見積もり (`sea/sluice.py`)

- 見積もりは、文字 1 字を 1 トークン、メッセージ 1 通ごとに 4 トークンとして足す。文字は、`content` が文字列ならその長さ、部品の列ならテキスト部品の長さを数える。`generate` に渡す答えの形の指定 (`response_schema`) も、`json.dumps(指定, ensure_ascii=False)` の字数を 1 字 1 トークンとして足す。どのクライアントでも指定は入力として送られるからである (OpenAI 互換の json_object モードは指定の全文を system メッセージとして足す)。
- 画像・音声・動画は、LLM クライアントが実際に送る形で数える。クライアントは画像を全部は埋め込まず、直近の数枚だけを埋め込み、埋め込まない画像は `[画像: URI] 要約` の注記に置き換える。全部を埋め込みとして数えると、画像の多いペルソナでは普段の大きさの会話でもスルースが飛ばされる (検収で見つけた。例: 画像 100 枚 × 765 トークン)。反対に注記を数えないと、実物より小さく数えてしまう (レビュー第一巡で見つけた)。数え方は次のとおり。
  - 埋め込む画像は、1 枚を `saiverse/token_estimator.py` の `estimate_image_tokens(provider)` で数える。
  - 部屋の様子のメッセージ (`__visual_context__`) の画像は、埋め込みの上限の枚数を使わず、枠の内側として扱う。
  - それ以外の画像は、新しいメッセージから順に、埋め込みの上限の枚数までが枠の内側になる。上限の決め方と、どの役割のメッセージの画像を埋め込むか、注記にするか、送らないかはクライアントごとに違い、`sea/sluice.py` の `_media_rules` がクライアントのコードで確かめた対応を持つ。上限は、OpenAI 互換がモデル設定の `max_image_embeds` → `SAIVERSE_OPENAI_ATTACHMENT_LIMIT`、Anthropic がモデル設定 → `SAIVERSE_ANTHROPIC_ATTACHMENT_LIMIT`、Gemini と xAI がモデル設定を読まず環境変数だけで決まり、環境変数が無ければ `SAIVERSE_ATTACHMENT_LIMIT`、それも無ければ 4 になる。役割については、OpenAI 互換と Anthropic は枠の内側の user の画像だけを埋め込み、それ以外を注記にする (Anthropic は system の画像を送らず、その画像は枠も使わない)。Gemini は system 以外の画像を、役割によらず枠の内側なら埋め込み、枠の外なら注記にする。xAI は user の画像だけを埋め込みか注記にし、ほかの役割の画像は送らない。画像に対応しないモデルでは、OpenAI 互換と Anthropic は画像を全部注記にし、Gemini と xAI は画像も注記も送らない。Ollama は画像を送らない。
  - 音声・動画は、対応しないクライアントが注記に置き換える。Gemini 以外のクライアントは全部の役割で注記にし、Gemini はモデル設定が非対応のときに system 以外で注記にする。
  - 画像・音声・動画の項目は、クライアントと同じ関数 (`saiverse/media_utils.py` の `iter_image_media` / `iter_audio_media` / `iter_video_media`) で集める。これらはファイルが実在しない項目を落とし、どのクライアントも同じ関数の結果から枠を数えて埋め込みか注記を作るので、落ちた項目は見積もりでも実物でも数えず、枠も使わない。
  - 注記 1 件は、書式の固定部分 16 字 + URI の字数 + 要約の字数として数える。URI はクライアントが載せるのと同じ項目の `uri` (元の URI、無ければファイルの場所)。要約の字数は、クライアントが注記を作るときに最初に読む保存済みの要約 (`get_media_summary`) があればその実際の字数で数える。「300文字以内」は要約を作るときの指示で、保存済みの要約は切り詰めずに注記に載るからである (レビュー第二巡の 2)。保存済みの要約が無ければ、クライアントがその場で作る要約の指示の上限の 300 字で数える。見積もりでは要約を生成しない。
- 上限は、そのモデルのコンテキスト長の 9 割から、応答の枠を引いた値である。応答の枠は、スルースの出力の上限 (`_MAX_OUTPUT_TOKENS`、4,096) と、実際に使うクライアントがリクエストに載せる応答の上限の大きい方である。プロバイダは入力と応答の上限の合計をコンテキスト長と比べるからである。クライアントは `response_token_limit()` で自分が送る上限を答える。Anthropic は `max_tokens` (既定 4,096、adaptive thinking で 16,000、モデル設定や思考の予算でさらに大きい)、OpenAI 互換は `max_tokens` / `max_completion_tokens`、Codex は `max_output_tokens`、Ollama は `num_predict` を答える。per-call の出力上限を守る Gemini と、上限を送らない xAI は答えを持たず、そのときは 4,096 を引く。
- 既存の `estimate_messages_tokens` をそのまま使わないのは、日本語 1 字を 1.5 トークンと数えるからである。うるさんの実測 (GPT-4o で、送った 290,404 字に先頭の自己定義を足して約 311,900 トークン) では 1 字 ≒ 1 トークンで、1.5 で数えると、普段の大きさの範囲 (上限 60,000 字の水位 + 先頭の自己定義) でも、128,000 トークンのモデルでスルースが飛ばされうる。
- モデルの設定が見つからずコンテキスト長が引けないときは、判定をせずに従来どおり走らせ、WARNING を残す。

### 2. 定常のスルース (整理の中のスルース)

- `_call_sluice_llm` で、実際に使うモデル (構造化出力の都合で差し替わった後のモデル) とクライアントが決まった後、`generate` の前に見積もりと上限を比べる。応答の枠はそのクライアントが送る上限で引き、答えの形の指定 (`_RESPONSE_SCHEMA`) も見積もりに数える。超えていたら LLM を呼ばず、専用の例外を送出する。
- `_run_metabolism_locked` はその例外を、既存の量による飛ばしと同じ扱いにする。スルースの状態を `skipped_cold` にし、読めていないまま畳まれる範囲 (印より後ろで、今回の畳みの対象に入っているメッセージ) を記録し、畳みを進める。レート制限の小休止は置かない。ログは既存の飛ばしと区別できる文面にする (モデル名・見積もり・上限・引いた応答の枠を含める)。
- 範囲の記録が空 (畳まれる古い側を、すでに別のモデルのスルースが読み終えている) なら、記録は書かずに畳みを進める。これは既存の飛ばしと同じ規則である。

### 3. 後から通す採取 (同じ欠陥の隣)

後から通すジョブ (`run_sluice_capture`、API `POST /api/people/{id}/sluice/capture`) は、会話を固定の 100,000 字ごとに刻んで、指定のモデル (省略時は本人のモデル) に送る。上限の小さいモデルを指定すると、同じ理由で 400 になる。

- 刻む大きさを、固定の 100,000 字と「そのモデルに入る量」の小さい方にする。入る量は、会話以外の部分 (本人モードの前置きと指示文と `_RESPONSE_SCHEMA`、機構モードの指示文と `_CANDIDATE_SCHEMA`) を見積もって上限から引き、メッセージ 1 通ごとに写しの書式が足す分も数えて決める。
- 実行 (`run_sluice_capture`) の刻みの見積もりはチャンクごとに行い、使うモデルとクライアントは、そのチャンクの LLM 呼び出しと同じ `runtime.select_llm_client(..., needs_structured_output=True)` で決める (`sea/sluice.py` の `_select_capture_llm` に一本化した)。この口は接続を作るが、直後に同じ接続で送るので構わない。構造化出力に対応しないモデルは軽量モデルへ差し替わるので、刻みは差し替わった後のモデルのコンテキスト長と、そのクライアントの応答の上限で決まる。
- 見積もり (`dry=True`、`plan_sluice_capture`) は LLM ゼロ・書き込みゼロの約束を守り、接続を作らない・llama.cpp のサーバーを起動しない・疎通を確かめない・ファイルやディレクトリを作らない (レビュー第二巡の 1)。使うモデルは、`select_llm_client` と同じ規則を接続を作らずに引く `runtime.resolve_llm_model(..., needs_structured_output=True)` で決める (`sea/sluice.py` の `_resolve_capture_model`)。規則が二箇所に分かれて食い違わないよう、`select_llm_client` もモデルは同じ関数 (`sea/runtime.py` の `_decide_base_llm_model` と `_structured_output_model`) で決め、接続の作成とサーバーの起動だけを自分で行う。
- 見積もりと実行は、同じモデルの決め方と同じモードで同じ刻み方を使う。ただし見積もりの刻み数は、見積もった時点の数である。実行の刻みの方が細かくなりうる理由は二つある。一つは、本人モードでは採取でコア記憶や手帳が増えると指示文が伸び、実行はチャンクごとにその時点の状態で刻み直すことである (状態が変わらなければ一致する)。もう一つは、dry は接続を作らないので応答の枠を 4,096 で数えることである。応答の枠が大きいクライアント (Anthropic、`max_tokens` を送る OpenAI 互換) では、実行の刻みが dry より細かくなりうる。runtime の無い呼び出し (lifecycle を渡さない `plan_sluice_capture`) は、差し替え前のモデルで見積もる。API の dry は lifecycle を渡している。
- LLM を呼ぶ直前にも、定常のスルースと同じ比較をする。1 通だけで入らないメッセージがある場合と、会話以外の部分 (本人モードのコア記憶・手帳の一覧を含む指示文) だけで入る量を使い切っている場合はここで止まり、ジョブは「選んだモデルでは、一度に送れる量に収まりませんでした。コンテキスト長の大きいモデルを選んで再実行してください。」という失敗を返す。どちらの場合にも当てはまる文面にしてある。

## レビューの裁定

### 第一巡 (2026-09-17 — ローカルレビュー + Codex adversarial review)

見積もりは近似で、実際に送られる中身とは必ず差が出る。差が出たときの害は向きで違う。見積もりが実物より**大きい**と、入るはずの回にスルースが飛ばされる (読めていない範囲は記録され、後から通せる)。見積もりが実物より**小さい**と、判定を通ったスルースがプロバイダに拒まれて失敗し、畳みが止まり、うるさんの症状 (上限の小さいモデルが抜け出せない) に戻る。だから、実物より小さく数えてしまう**系統的な**原因は見積もりに入れる。境界付近の小さな揺れはコンテキスト長の 1 割の余白で受ける。

採用する指摘:

1. **応答の枠が 4,096 固定になっている** (Codex high、事実を確認)。per-call の出力上限 (`max_output_tokens`) を守るクライアントは Gemini だけで、Anthropic はクライアントが持つ上限 (既定 4,096、adaptive thinking で 16,000、モデル設定や思考の予算でさらに大きい) を、OpenAI 互換はモデルのパラメータ (`max_tokens` / `max_completion_tokens`、たとえば OpenRouter の 4o は既定 8,000) を送る。プロバイダは入力と応答の枠の合計をコンテキスト長と比べるので、応答の枠は**実際に使うクライアントが送る上限**を引く。持ち主はクライアントなので、クライアントが「自分が送る応答の上限」を答える口を持ち、スルースはそれと 4,096 の大きい方を引く。
2. **答えの形の指定 (response_schema) を数えていない** (ローカルレビュー low・Codex high、事実を確認)。スルースの指定は約 2,500 字、機構モードの候補の指定は約 1,000 字。どのクライアントでも入力として消費される (OpenAI 互換の `json_object` モードは system メッセージとして全文を足す) ので、指定の JSON の字数を見積もりに足す。
3. **送らない画像・音声・動画の注記を数えていない** (Codex high の一部、事実を確認)。直近の上限枚数を超えた画像と、user 以外のメッセージの画像は、クライアントが `[画像: URI] 要約` の注記に置き換える。画像非対応のモデルでは全部が注記になる。音声・動画に対応しないクライアントは要約の注記を足す。要約は 300 字以内で作られる (`saiverse/media_summary.py`) ので、埋め込まない 1 件ごとに URI の長さ + 要約の最大 300 字 + 書式の分を数える。画像の多いペルソナでは、この分が 1 割の余白を超えうる。
4. **後から通すジョブの刻みが、構造化出力の都合で差し替わる前のモデルで見積もられている** (Codex high、事実を確認)。刻みの見積もり (dry を含む) も、LLM を呼ぶ直前と同じ `select_llm_client(..., needs_structured_output=True)` で実際のモデルを決めてから行う。

採らない指摘と理由:

- **欠損したファイルの画像も数えてしまう** (Codex high の一部): 事実だが、向きは「多めに数える」側で、多く数えても埋め込みの上限枚数 × 1 枚の見積もり (数千トークン) までに収まる。見積もりのためにファイルを読みに行く費用に見合わない。
- **全クライアントの最終 payload の組み立てを共有化して、それを測る** (Codex の処方): 事実 1〜3 は、クライアントの規則を見積もりに写すことと、応答の上限をクライアントに答えさせることで塞がる。組み立ての共有化は全クライアントの作り替えになり、本件の範囲を超える。見積もりとクライアントの規則が将来ずれる危険は残るので、テストでクライアントの実物と見積もりを突き合わせる (既存の `scan_message_metadata` との突き合わせと同じ形)。

三件とも「上限の境界付近で、実物より小さく数える余地がある」という指摘で、第一巡 (応答の枠・答えの形の指定・注記という系統的な数え漏れ) と第二巡 (dry の副作用という退行) に比べて、的が見積もりの芯から余白の内側の精度へ移った。

採らない指摘と理由:

- **Ollama の `num_predict=-1` (応答の上限なし) を 4,096 として扱っている** (Codex high): 事実だが、この指摘の害は「プロバイダが入力と応答の上限の合計で拒む」ことを前提にしている。Ollama は応答の上限の値でリクエストを拒まず、コンテキストを超える入力は切り詰めて扱う (メティスの知識で、この場では Ollama の公式文書と突き合わせていない)。上限の小さいモデルが抜け出せなくなる症状 (拒まれて畳みが止まる) には結びつかない。
- **保存されていない要約が、作られたときに 300 字を超えうる** (Codex medium): 事実だが、要約はそれを注記に使う最初の返事の呼び出しで作られて保存されるので、スルースの見積もりの時点で保存されていない要約は多くない見込み (推測で、実データで数えてはいない)。指示を超えた分は 1 割の余白で受ける。要約を作る側で 300 字に切り詰める直し方は、ペルソナが読む注記の文面を途中で切ることになり、見積もりのために読み物の質を削る向きなので、本件では採らない。
