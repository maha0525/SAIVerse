# Issue: 自動想起のキーワードの抽出で、語ごとに全メッセージを読み直しているため、返事の前に数秒かかる

**ステータス**: 🟣 検証待ち (修正を実装した。まはーの本番環境で、コンテキストの組み立て (返事の前の準備) の時間を確かめる)
**優先度**: medium
**作成日**: 2026-11-22
**関連**: [記憶の検索用のベクトルの保存形式を変える](../intent/vector_binary_storage.md) / [「通信が途中で切れました」と 500 がまとまって出る件](chat_stream_cut_and_relay_500_on_backend_stall.md)

## 何が起きるか

ペルソナが返事を書きはじめる前に、自動想起 (会話に関係のある記憶を探して、ペルソナに見せる処理) が走る。その最初のほうで、記憶を字面で探すためのキーワードを選ぶ (`sea/auto_recall.py` の `_extract_recall_keywords`)。この文書では、この処理を「キーワードの抽出」と呼ぶ。

キーワードの候補は、ユーザーの発言と、その回に新しく見えたもの (部屋の様子や通知の本文) から、カタカナ・漢字・英数字の連なりを全部抜き出したもの。候補の語ごとに、その語がペルソナの全メッセージのうち何件に出てくるかを数え、1〜50 件の語のうち件数が少ない 4 語をキーワードにする。

件数は、語ごとに `SELECT COUNT(*) FROM messages WHERE content LIKE '%語%'` で数えている。この数え方では、1 語につき `messages` の全行の本文を読み込む。候補が 60 語あれば、全メッセージを 60 回読むことになる。

## 測ったこと (2026-11-22、まはーの本番環境の `backend.log`)

- 更新後の最初の会話 (メッセージが約 4.5 万件のペルソナ) で、コンテキストの組み立ては 8.27 秒。そのうちキーワードの抽出が 5.98 秒、記憶の検索が 1.20 秒、記憶を見せるかの判定が 0.73 秒だった。この回の候補は 60 語以上だった。
- 2026 年 11 月の会話 117 回 (全ペルソナ) で、履歴の読み込みが終わってからキーワードの行が出るまでの時間を調べた。5 秒以上かかった回が 38 回あり、最長は 16 秒 (104 語以上) だった。ログに出た語の数で割ると、1 語あたり約 0.07 秒になる。
- 候補が 20 語以下の回は、1 秒以内に収まっている。候補は、ユーザーの発言に加えて、その回に新しく見えたものの本文からも抜き出すので、本文が長い回ほど多くなる (これはコードから読み取ったことで、回ごとの内訳は調べていない)。

ログに出る語の数は、落とした語と選んだ 4 語の合計なので、実際の候補の数はこれと同じか、これより多い。

## 直し方の案

選ばれるキーワードを変えずに、数え方だけを軽くできる。案は次の 3 つで、1 つ目を採った (「対応」)。

- 全部の候補を、`messages` を一回読むだけで数える (一つの SQL の中で、語ごとの件数を同時に数える)。
- 51 件見つかった時点で数えるのをやめる。必要なのは「1〜50 件かどうか」だけで、ありふれた語の正確な件数は使っていない。ログに出している件数は「51 件以上」に変わる。
- 語から行を引ける索引を作る。保存するデータが増え、既存のペルソナには作り直しが要る。

## 対応 (2026-11-22)

`messages` の全行の本文を一回だけ読み、全部の候補の語をまとめて数える形にした (`sea/auto_recall.py` の `_count_messages_containing`)。数え方は `LIKE` と同じで、語が本文の一部として含まれるかを探し、半角の英字 (ASCII) の大文字と小文字だけを区別しない。選ばれるキーワードは変わらない。

確かめたこと。

- まはーの本番環境の 3 人のペルソナの `memory.db` を読み取り専用で開き、2026 年 11 月のログに出た 1,513 語すべてで、件数が変更の前と一致した。
- 更新後の最初の会話と同じ 60 語の数え上げは、同じペルソナの `memory.db` (メッセージ 10,727 行、本文の合計 16 MB) で、変更の前が 2.25 秒、変更の後が 0.41 秒だった。これは単独で測った値で、本番環境の会話の中で測った値 (変更の前は 5.98 秒) ではない。
- 一つの SQL の中で語ごとの件数を同時に数える形も測った。1.04 秒で、採った形より遅かった。

確かめていないこと。

- 本番環境の会話の中での所要時間。更新のあとに、`backend.log` の `[auto_recall] timing` の行の `keywords=` で確かめる。
- 本番環境で測った 5.98 秒が、単独で測った 2.25 秒の 2.7 倍だった理由。

変更の前と違う点が一つある。本文の途中に NUL 文字 (文字コード 0 の特殊な制御文字) がある行では、変更前の `LIKE` を使った検索では NUL 文字より後ろが対象にならなかったが、変更後は本文の最後まで対象になる。まはーの本番環境の 3 人のペルソナの `memory.db` には、NUL 文字を含む行は無かった。
