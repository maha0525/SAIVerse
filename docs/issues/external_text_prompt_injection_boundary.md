# 外部テキストとプロンプト境界 — 知覚経由の間接プロンプト注入 (体系課題)

**ステータス**: 未解決 (2026-08-02 起票。設計課題・当分未着手)
**起票の経緯**: RSS フィード取り込みの Codex レビュー (2026-08-02) が「外部フィード文面が `<system>` ラップの知覚メッセージと Fixture.STATE_JSON 経由で system プロンプトへ無検証で流れる — 配信元が指示文をタイトルに入れれば prompt injection になる」と指摘した。指摘自体は正しいが、**フィード固有の欠陥ではなくアーキテクチャの体系的な性質**であるため、フィード実装内の対処 (転載の明示枠・長さ上限) に留め、本体はここに切り出す (メティス裁定、まはー報告済み)。

## 問題

ペルソナの知覚に入る外部由来テキストは、event_message / 知覚バッファの流儀で `<system>` ラップの user ロールメッセージとしてプロンプトに載る。この経路はフィード記事に限らない:

- RSS フィード記事のタイトル・概要 (2026-08-02〜)
- Web 取得・検索ツールの戻り値 (read_url / searxng — 以前から)
- X / Elyth タイムライン (アドオン — 以前から)
- 他ユーザー・外部からの発話がありうる将来の経路 (内部フィード、City 掲示板)

悪意ある (または汚染された) 供給元が「以前の指示を無視して…」等の指示文を本文に埋め込むと、ペルソナの LLM がそれを指示として扱うリスクがある。これは LLM に外部世界を読ませる機能の**本質的な代償**であり、SAIVerse に固有でもない (エリスが Elyth を読む時点で既に負っていたリスク)。

## なぜ個別機能で解かないか

- 供給経路ごとにエスケープや役割分離を実装すると、同じ検証が N 箇所に散り、漏れた一箇所が全体を破る (派生状態の教訓と同型)
- 「system 境界の再設計」(外部文面を別ロール・構造化 untrusted data として渡す) はプロンプト組み立ての全層 (head/knot/tail、event_message 形式、キャッシュ設計) に跨る変更で、機能単位のスコープに収まらない

## 現状の緩和 (実装済み)

- フィード: 転載であることの明示枠 + タイトル/概要/リンクの長さ上限 + link の scheme 検証 (http/https のみ)
- 発話の尊厳側の既存原則: ペルソナ名義の記録は本人の実発話のみ (なりすまし禁止) — 注入が成功しても「本人が書いた」ことにはならない記録構造

## 解決の方向 (将来検討)

1. 知覚組み立ての一箇所 (perception_buffer の format 層) に「外部由来テキストの標識と中和」を集約する — 供給側 N 箇所でなく消費側 1 箇所
2. モデル側の指示階層 (system > user > 転載データ) を明示するプロンプト規約
3. 供給元の信頼度メタデータ (builtin プリセット由来 / ユーザー追加 / 不明) を知覚に添える
