# Issue: DB を丸ごと作り直す移行が、プログラムの管理外の表を中身ごと消す

**ステータス**: 未着手 (2026-09-11 起票。現時点で分かっている実害は無い)
**優先度**: medium (データが黙って消える型の穴。いまは該当する表が見当たらないが、同じ形の変更をすると実害になる)
**作成日**: 2026-09-11
**関連**:
- `database/migrate.py` の `migrate_database_in_place` — DB を丸ごと作り直す移行
- `database/migrate.py` の `_drop_empty_legacy_note_tables` — 管理から外したあとも中身が残る表の先例 (note 系 4 表)
- `hotfix/v0.3.12` の `database/migrate.py` の `KNOWN_COLUMN_DROPS` — 廃止した列をその場で落として、作り直しを避ける仕組み
- [persona_media_summary_models_unused.md](persona_media_summary_models_unused.md) — この穴が見つかったレビューの対象

## 何が起きるか

`migrate_database_in_place` は、元の DB ファイルをバックアップ (`〜.bak`) へ移し、新しいファイルに `database/models.py` の `Base.metadata` にある表だけを作って、その表の行だけを写す (`database/migrate.py` の `Base.metadata.create_all(target_engine)` と、`Base.metadata.sorted_tables` を回すコピー)。元の DB にだけあって `Base.metadata` に無い表は、新しいファイルに作られず、中身ごと消える。消えたことはログに出ない。元のデータは `〜.bak` と、起動時に取られる復元用のバックアップにだけ残る。

## いつ走るか

- 起動時 (`main.py`) に DB の形の差分が見つかり、列を足すだけの軽い方式 (`try_additive_migration`) で片付かないとき。列の削除や改名が差分に含まれると、この方式に落ちる。
- `hotfix/v0.3.12` 以降は、`KNOWN_COLUMN_DROPS` に登録した列は先にその場で落とされるので、その列のためだけにはこの方式に落ちない。ただし、SQLite が 3.35 より古くて列をその場で落とせない環境では、この方式に戻る。
- `python database/migrate.py` を手で実行したとき (差分があるか、`--force` を付けたとき)。

## 実害の見込み (2026-09-11 に確かめた範囲)

- **note 系 4 表** (`note` / `note_page` / `note_message` / `track_open_note`): 2026-07-11 (`ca9815ac`) に `database/models.py` から外され、中身をペルソナごとの記憶へ移し終えて空になったら消す作りになっている。移しているのはペルソナの登録時で、起動時の移行より後に走る。したがって、中身が残っている DB でこの方式が走ると、移す前に消える。ただし、note 表を作ったコミット (`587b2d4b`、2026-04-25) を含む最初のタグは `v0.3.0` で、`v0.3.0` の時点で Note はもう外されていた。直前の `v0.2.29` (2026-06-15) には note 表が無い。配布したどのバージョンにも note 表は入っておらず、この経路で消えうるのは開発用の DB だけだった。
- **アドオンの表**: 手元の二つのアドオンは、表を本体の DB ではなく、アドオン専用の DB ファイル (`~/.saiverse/user_data/addon_data/<アドオン名>/` の下) に作っている。スタックチャンの `vessels.db`、X の `x_reply_log.db`。他のアドオンは確かめていない。
- **まはーの本番 DB**: `Base.metadata` に無い表はゼロだった (2026-09-11、読み取り専用の複製で確認)。

## なぜ直すべきか

note 系の退役は、「管理から外して、表と中身は残し、あとで移してから消す」という形をとった。この形を今後またとると、移し終える前にこの方式が走った DB で、中身が黙って消える。レビューでもテストでも、`Base.metadata` の外の表は見えない。

## 直し方の候補 (未決定)

1. 作り直す前に元の DB の表を並べ、`Base.metadata` に無い表があれば、形と中身をそのまま新しいファイルへ写す。
2. `Base.metadata` に無い表が行を持っていたら、移行を止めて元のファイルに戻し、何が残っているかを知らせる。
3. 表を管理から外すときは、中身を移し終えてから外すことを規則にする。ただし、これを機械で確かめる仕組みは無い。

どれを選ぶかと、回帰テスト (管理外の表に行が入った DB で作り直しを流し、表と行が残る/止まることを確かめる) の形は、着手時に決める。
