# Issue: チャット入力欄で一文字入力するたびに画面全体が再レンダリングされ、iPhone で入力がもたつく

**ステータス**: 🟡 進行中
**優先度**: high
**作成日**: 2026-10-26
**関連**: `frontend/src/app/page.tsx` / [フィードの記事供給の issue](feed_blocks_never_leave_presented_context.md) (同じ報告者・別件)

## 背景

an nin さんから、v0.3.26 環境の iPhone 14 (iOS 27.0.1、Safari から追加した PWA) で、チャット入力欄の文字入力がフリック入力に追いつかないほど重くなるという報告が来た (2026-10-25〜26、Discord)。報告の切り分けが丁寧で、原因の絞り込みにそのまま使えた:

- iPhone の再起動、iPhone 側の Tailscale 切断、部屋のアイテム整理では改善しない。
- 同じ SAIVerse 内のアイテム名の編集欄は通常速度で入力できる。重いのはチャット入力欄だけ。
- 同じ会話・記憶・アイテム量のまま、夜は重く、翌朝は軽い、という揺らぎがある。
- 画像送信などの特別な操作との対応は見つかっていない。

Tailscale を切っても (= サーバーに届かない状態でも) 重いままなので、重さはサーバーや回線ではなく、ブラウザの画面側で発生している。

## 確認した事実 (コードを読んだ結果)

- チャット画面全体が `frontend/src/app/page.tsx` (約 4,500 行) の単一コンポーネントで作られており、入力欄の文字列 `inputValue` が画面全体の状態を保持する変数 (`useState` の `state`) に置かれている。
- そのため一文字打つたびに `setInputValue` で状態が更新され、`page.tsx` 全体が再レンダリングされる。その中の `messages.map` によって、表示中のメッセージ (警告・情報・エラーの通知など、Markdown を通らない種類を除く) で `<ReactMarkdown>` による本文の Markdown 解析が毎回やり直される。メッセージ単位で前回の描画結果を再利用する仕組み (`React.memo`) は入っていない。
- さらにキー入力のたびに入力欄の高さを自動調整する関数 (`adjustTextareaHeight`) が呼ばれ、その中で `height` を一度 `0` にしてから `scrollHeight` を読み取っているため、ブラウザが画面の配置（レイアウト）をその場で即座に計算し直す処理が毎キー発生する。
- この構造では、一文字入力するごとの処理負荷が「表示中のメッセージ数 × 本文量」におおむね比例するはず (コードからの推論で、処理時間の実測はしていない)。履歴は開いた直後 20 通で、会話を続けるほど・過去ログを上へスクロールして読み込むほど増える。
- v0.3.26 はフロントエンドのファイルを変更していない (v0.3.25 と v0.3.26 のタグの間に `frontend/` 配下のコミットが無いことを git log で確認した)。フロントエンドに触れた直近のリリースは v0.3.25 で、内容は Next.js 16.1.6 → 16.4.1 と sharp 0.34.5 → 0.35.5 の更新 (セキュリティ更新) と、`next-env.d.ts` を git の管理から外す整理。この構造自体は以前からある。「最近のアップデート後に起き始めたと思う」(まはーの見立て) をバージョン間の変更内容で説明できる箇所は見つからなかった。

同じ文字入力でもアイテム名の編集欄が軽いのは、入力文字列がモーダル内の小さなコンポーネントの `state` に置かれており、再レンダリングの範囲が画面全体に及ばないためである。報告された「チャット入力欄だけ重く、アイテム名編集欄は軽い」という現象と一致する。

## 揺らぎ (急に重くなり、自然に軽くなる) の原因 — 2026-10-26 夜、報告者の追加観測で絞り込み

当初の仮説は「表示中のメッセージ数の増減」と「iPhone 側の速度低下 (低電力モードや発熱)」の 2 つだったが、報告者が再発時 (10/26 20:52) に取ってくれた観測で両方とも主因から外れた:

- PWA を完全終了して開き直しても改善しない → 開き直せば表示は直近 20 通に戻るため、「使ううちに表示が溜まる」だけでは説明できない。
- 再発時は電池残量 89%・低電力モードオフ → 低電力モード説はこの回に当てはまらない。メモ帳やブラウザの検索欄は軽く、端末全体の速度低下でもない。

代わりに、再発の直前の状況が原因を指した: 20:52 の再発は「AI 側で Web 調査と複数回のページ読み込みが行われていた」最中に始まった。スペルの実行結果 (読み込んだページの本文など) は、ペルソナの発言本文の中に折りたたみブロック (`<details class="spellResult">`、`sea/runtime_llm.py` の `_build_spell_user_only_block`) として丸ごと保存され、チャット表示の Markdown 解析を通る。**表示中が直近 20 通のままでも、その中に Web 調査の結果入りの発言があれば本文量が数十 KB 単位で膨らみ**、一文字ごとの全再解析のコストが跳ね上がる (まはーの仮説、2026-10-26)。この読みなら観測が全部つながる:

- 急な発症 — 結果ブロック入りの発言が表示に入った瞬間に重くなる。
- 開き直し・iPhone 再起動で直らない — 読み直した直近 20 通に同じ発言が含まれ続ける。
- 時間が経つと自然に軽くなる — 開いたままの画面では発言は追記されるだけで表示から外れないが (`fetchHistory` は初回 20 通、以後は追記のみ)、iOS は背面に回った PWA をしばしば終了させるため、次に開いた時は直近 20 通だけを読み直す。その時点で重い発言が直近 20 通の外に出ていれば軽くなり (翌朝の改善)、まだ中にあれば開き直しても重いまま (①「開き直しても軽くならなかった」の観測)。どちらの観測も同じ仕組みで説明できる。
- 画面上は「同じ会話量」に見える — ブロックは折りたたまれていて、量が目に見えない。

修正 (入力欄の分離 + `React.memo` 化) はこの原因にもそのまま効く — 打鍵時の再解析自体が無くなる。リリース後に報告者の実機で裏を取る。

## 対処

1. **入力欄の分離**: 入力欄を `frontend/src/components/ChatInput.tsx` に切り出し、入力文字列をそのコンポーネント内の `state` にする。親 (`page.tsx`) へは「空かどうか」の変化だけを伝え (判定は従来の送信ボタンと同じ `!value.trim()` — 空白だけの入力も空扱い)、親が入力値を読む・書くのは、親画面の再描画を起こさずに子コンポーネントを直接操作する仕組み (`ref`) を使った命令 (`getValue` / `clear` / `restoreText`) で行う。読む側は送信とコンテキストプレビューの 2 箇所、書く側はクリアと本文の復元 3 経路。これでキー入力時の再レンダリングは `ChatInput` の中だけで完結する。
2. **Markdown 解析結果の再利用 (`React.memo` 化)**: メッセージ本文の `<ReactMarkdown>` を、内容が変わらない限り前回の表示結果を再利用するコンポーネント (`React.memo`) で包み、本文が変わらないメッセージの再解析を止める。文字入力以外の再レンダリング (ストリーミング中の追記、ポーリングによる `state` 更新) でも全メッセージの再解析が毎回行われていたため、そちらの負荷軽減にもなる。

**対処で残るもの**: 入力欄自身の高さ自動調整 (`adjustTextareaHeight`) による毎キーのレイアウト再計算は `ChatInput` の中にそのまま残る。報告の重さの主因は再レンダリングと Markdown 再解析の側だと推定しているが (処理時間の実測はしていない)、残った分がどのくらい効くかは配布後の経過で見る。

## 検証 (2026-10-26 実施)

本番と分けた検証環境 (worktree の test_data、API キー無し = LLM 課金ゼロ、合成の会話 60 通を注入) で確認した:

- 60 通の長い Markdown 本文を表示した状態で 156 文字を連続打鍵し、入力が追従した。この間の 50ms を超える処理の引っかかり (longtask) は 2 回 (80ms・73ms) だけで、打鍵のたびに発生はしなかった。入力欄の高さの自動調整 (1 行 36px → 複数行 204px → 送信後 36px) と、送信ボタンの空判定の切り替えも従来どおり動いた。
- 親が入力欄を読み書きする 5 箇所の置き換え先のうち、実機で通したのは 3 つ: 送信 (`getValue`+`clear` — Ctrl+Enter で送信、入力欄が空に戻り発言が表示された) / 取り消しの成功 (`restoreText` — `/api/chat/withdraw` 200 で本文 156 文字が入力欄へ戻った) / コンテキストプレビュー (`getValue` — `/api/chat/preview` の要求本文に打鍵した全文が載っていることを捕捉した)。残り 2 つ (送信失敗時・送れたか分からなかった発言の照会が not_found のときの復元) は実機では再現させず、同じ `restoreText` を呼ぶことのコード確認まで。
- `cd frontend && npm test` 緑、`npm run build` 成功。
- 検証中にブラウザのコンソールへ出た 500/502 は、バックエンド起動完了前の中継エラーで、バックエンド側のログの非 200 はアイコンの 404 が 1 件だけだった。
