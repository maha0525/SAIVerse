# アイテムの作成が失敗すると、保存済みのメディアファイルが孤児で残る

**起票**: 2026-09-12 (アイテム表示上限のレビュー三巡目で指摘、出自は従来からの形)
**状態**: 未解決 — 文書の限定的な後始末は develop に取り込み済み。画像の返却を変える方針は未確定

## 起票時の現象 (2026-09-12)

文書・画像の作成は「本文/画像ファイルを保存 → DB にアイテムを登録」の順で進む。登録側が失敗する (DB 例外、または 2026-09-12 に入った置き場所の実在検査での拒否) と、保存済みのファイルがどのアイテムからも辿れないままディスクに残る。

- 文書 (document_create 経路) は 2026-09-12 に、置き場所の検査をファイル保存より前へ動かして、拒否での孤児は塞いだ。**DB 例外での孤児は従来どおり残る。**
- 画像 (image_generator → create_picture_item 経路) は、生成した画像を保存してから登録するので、登録失敗で画像ファイルが残る。生成には API 課金も伴う。

## 起票時の対応方針

登録失敗時に保存済みファイルを削除する後始末を、作成経路の失敗処理に一体で入れる。頻度は低い (健全な世界では置き場所は常に実在し、DB 例外もまれ) ので、単独の掃除案件として扱う。

## 実装範囲と残る判断 (2026-10-02)

[所有権の intent](../intent/media_registration_cleanup.md) を追加し、**生成文書の commit 前の失敗だけ**を後始末する。作成側が排他的に作った本文と要約サイドカーだけを控え、DB の add/flush・置き場所の再検査・要約処理等で失敗したときに削除する。既存ファイルと、後始末の検査時に差し替え・ハードリンク共有が判明したパスは削除しない。対象は公開前の UUID 文書だけで、検査と unlink の間で外部プロセスが同名パスを差し替える競合を原子的に防ぐ仕組みではない。削除できない場合はログに残し、元の例外を隠さない。

DB は明示的に flush してから commit を試す。**commit 呼び出しが始まった後の例外は、成功か不成功かを断定せずファイルを保持する。** commit 後のキャッシュ更新・部屋更新・通知失敗も保持する。既存の孤児の一括掃除やプロセス強制終了時の掃除は含まない。

### 画像を同じ後始末に載せない理由

起票時は「どの Item からも辿れない」を「孤児」と扱っていたが、実際の呼び手を確認すると別の参照が残る。

- `builtin_data/tools/image_generator.py:769-816`: 生成結果を保存して snippet と `metadata.media` を用意する。`create_picture_item` の例外は `800-803` で握り、`816` で **画像 path・metadata・履歴用 snippet を返す**。Item 登録が失敗しても、生成画像そのものはツール成果物として到達できる。
- `api/routes/chat.py:_store_image_attachment / _store_document_attachment / _store_audio_attachment / _store_video_attachment`: 登録失敗後も URI/path を返し、同ファイルの `send_message` (`1020-1072`) が画像・文書・音声・動画を会話 metadata に組み込む。複数添付の一つだけ登録失敗した場合にも、他の添付を含めて削除しない。
- `api/routes/chat.py:_register_uploaded_video_by_uri`: 前のアップロードで保存済みの動画を参照する。登録側にはそのファイルの所有権がない。
- `manager/admin.py:create_item` と `create_picture_item` / `create_*_item_for_user`: 呼び手から FILE_PATH を受け取るだけなので、失敗時にそのパスを削除しない。

したがって、既存方針の「登録失敗なら生成画像を削除」をそのまま実装すると、課金済みの返却成果物や会話添付が壊れる。**画像は現在の返却を維持する。登録失敗の伝え方・保存した画像の再登録導線が必要かは別途判断を要する。** 捨てる仕様には変更していない。安全に消せる新規・未公開の画像失敗経路は、現在の登録呼び手からは確認できなかった。
