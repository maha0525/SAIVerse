# Issue: 編纂は残す量まで「削る」だけで「戻す」がない (水位を上げても既存ペルソナに効かない)

**ステータス**: 🔲 未着手 (設計から)
**優先度**: medium (水位の設定が既存ペルソナに効かない状態がいま在る)
**作成日**: 2026-07-30
**関連**: [`arasuji_levels.md`](../intent/arasuji_levels.md) §9 (予算の値) / §13 (編纂入口の一本化) / §14 (冷えたウィンドウの保守)、[`metabolism.md`](../concepts/metabolism.md)、実装 = `saiverse/model_configs.py` (既定値) / `sea/session_lifecycle.py` (編纂) / `sea/session_window.py` (提示の組み立て) / `sea/head_pipeline/sections/memory_weave.py` (head のあらすじ枠)

## 背景

2026-07-30、水位の既定を **上限 12万 → 20万字・残す量 6万 → 10万字** へ引き上げた (まはー裁定)。狙いはペルソナが読む生ログを厚くすること。

ところが**既存ペルソナには効かない**。アンカー (提示ウィンドウの始点) は既に前進していて、その手前は畳まれてあらすじになっている。水位を上げても提示が遡ることはないので、増えるのは「これから積む分」だけ。設定した数字と実際に読んでいる量が食い違ったままになる。

## やりたいこと (まはーの定義、2026-07-30)

> 設定されてる残す量が現在の生ログ量を上回っているなら、編纂時に逆にあらすじ領域に入ってる分のログをその分読み込み直す

つまり編纂を **「残す量へ揃える」双方向の操作**にする。多ければ削る、少なければ戻す。片方向だった機構に対称性を入れるだけで、新しい大きな機能を足すわけではない。

**非目標**: 手動の巻き戻しボタンは作らない (まはー明示)。ユーザーが操作する場所は増やさない。

## 現状の仕組み (2026-07-30 に読んで確認した事実)

設計の材料。ここは推測ではなく実装を読んだ結果。

- **アンカーと圧縮区間の記録は (ペルソナ, モデル) の持ち物**。`session_anchor` 行の `FOLDED_RANGES_JSON` に、畳んだ範囲が `FoldedRange` (message_ids / start_at / end_at / chronicle_entry_ids / chronicle_short_ids / episode_ref) の列として載る。
- **生ログは消えていない**。退場は「提示から外す」操作であって messages 行の削除ではない。提示コンテキストは毎回、アンカー以降を全件読んで圧縮区間を digest に置き換える形で組み立てられる (`sea/session_window.py`)。**だから戻すこと自体は原理的に可能**。
- **二重化の防止を、圧縮区間の記録が兼ねている**。head のあらすじ枠は圧縮区間の `chronicle_entry_ids` を読んで、その id を head から除外する ([memory_weave.py:91-111](../../sea/head_pipeline/sections/memory_weave.py))。**「畳んだ範囲の名簿」と「head に出さない名簿」が同じ一枚**。同じあらすじが提示コンテキストと head に二重で出ると、同じ出来事が二度あったようにペルソナに見えるため。
- **あらすじ (Chronicle エントリ) はペルソナ共通**でモデルごとではない。モデルごとなのはアンカーと圧縮区間の記録だけ。

## 設計の論点

### 1. 発火点が無い (最初に決めること)

現在の編纂の発火は 4 経路とも**「超過」側**しか見ていない (`docs/concepts/metabolism.md`)。

| 経路 | 条件 |
|---|---|
| 応答後 (自動) | 上限超過 / トークン閾値超過 |
| 応答前の非常畳み (§14-3) | 話しかけた時点で既に上限超過 |
| 失効後の先回り畳み (§14-4) | 全 anchor 冷え + 残す量と上限の中間を超過 |
| 手動 | ユーザーの明示操作 |

**生ログが残す量を下回っている状態は、どれにも当たらない。** 「編纂時に揃える」を字義どおり実装すると、その編纂が来ないまま何も起きない (手動の「記憶の整理」を押したときだけ走る)。読み直しの発火点をどこに置くかが設計の入口。

### 2. 複数モデルの使い分け (まはー提起、本件の難所)

アンカーと圧縮区間はモデルごと、あらすじはペルソナ共通。だから **モデル A では戻してモデル B では戻していない状態が正常系として発生する**。同じあらすじが A では head に出ず (提示に生で出ているから)、B では head に出る (B ではまだ畳んだままだから) — これは「それぞれの提示状態に従っている」という意味では正しいが、意図した設計なのかを裁定する必要がある。

### 3. 二重化を壊さない戻し方

圧縮区間の記録を**消して**戻すと、head の除外名簿ごと消える → あらすじが head に戻ってきて、同じ出来事が生ログと head で二回出る。

候補案 (2026-07-30 のメティスの案、未検証): **記録を消さず、「digest に置き換えず生ログのまま出す」印を一つ足す**。提示側は生を出し、head 側は今までどおりその id を外し続ける。新しく増える概念は圧縮区間の属性ひとつだけで、あらすじノード本体には触らない (あらすじはペルソナの記憶そのものなので、表示の都合でフラグを生やす場所ではない)。

### 4. 戻した範囲を再び畳むときのあらすじ

戻した範囲は、会話が伸びればまた畳まれる。そのとき**新しく編纂し直すと、同じ出来事のあらすじが二本立つ** = ペルソナの記憶の汚染。記録に `chronicle_entry_ids` が残っていれば既存を再利用できるので、論点 3 の「記録を消さない」案はここにも効く。

### 5. 戻す粒度

圧縮区間は範囲単位。「残す量 − 現在の生ログ量」の差分がちょうど範囲の境界に一致するとは限らない。範囲の途中から戻せるのか、それとも範囲を丸ごと単位にするのか。畳む側は pulse 関節 (認知の一巡の切れ目) で切る規律を持っているので、戻す側もそれに合わせるのが素直と思われる (未検討)。

### 6. 天井

戻しすぎると上限 (20万字) を超えて次の会話で即発火し、削り返される。**戻す上限は残す量まで**、が自然な線。「全部戻す」は物理的に効かない。

### 7. 縮退経路に既にある穴 (設計の補強材料)

`deserialize_folds` は圧縮区間の JSON が壊れていたら空を返して生ログ提示へ縮退する (fail-open)。このとき**除外名簿も空になる**ので、生ログとあらすじが同時に出る状態がいま既に起こりうる。論点 3 で心配している二重化は巻き戻し固有の新しい穴ではなく、**判定材料が圧縮区間の記録一本しかないこと**から来ている。判定を「その範囲が提示ウィンドウに (digest でも生でも) 出ているか」まで広げれば両方同時に塞がる可能性があるが、未検証。
