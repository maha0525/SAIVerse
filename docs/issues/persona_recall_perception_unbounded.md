# 再会の想起が個人ページ全文を知覚に積み、編纂が止まると無限に堆積する

**ステータス**: 🔲 未解決 (設計中) — v0.3.9 の主案件。対処の方向はまはーの裁定待ち
**深刻度**: 高 — 「部屋の様子」の送信量がユーザーの制御できない形で肥大し、上限を恒常的に超える。会話は守られるが、送信量 (= API 費用) が膨らみ続ける
**発見**: 2026-09-05 (のろけゆきさんの報告。まはーが「再会の機構が食いつぶしてない?」と機構を言い当て、コードで裏付けた)
**関連**: [watermarks_unsatisfiable_when_perception_is_large.md](watermarks_unsatisfiable_when_perception_is_large.md) (知覚の二水位上限の設計はこちら側。本件は供給源の一つの身の丈直し) / `sea/head_pipeline/integration.py` `_inject_persona_recall_on_enter` / `persona/history_manager.py` `recall_conversation_with`

## 症状 (のろけゆきさんの実測、v0.3.7 相当)

> 現在 222,566文字（読み戻し後）（うち会話 40,398・部屋の様子 182,168）
> 残す量 100,000文字 ／ 上限 200,000文字
> 部屋の様子だけで上限を超えています。

- 部屋に画像も部屋プロンプトもほとんど無いのに「部屋の様子」が 18 万字
- ペルソナを移動しても減らず、**部屋の移動をすると溜まっていく**
- 同じ部屋に滞在していてもペルソナごとに文字数が違う (会話頻度が低いペルソナは約 2 万字)
- Twitter 程度の一往復で表示が約 5 万字増えることがある

## 機構 (2026-09-05 にコードで確定)

三つの仕様の組み合わせで、どれか一つでは起きない。

1. **再会の想起が大きい** — 誰か (ペルソナ**またはユーザー**、2026-07-11 裁定で拡大) が部屋に入ってくるたび、`_inject_persona_recall_on_enter` が「相手との過去会話 最大 6 件 (各 2,000 字まで) + **相手の Memopedia 個人ページの全文 (上限なし)**」を知覚バッファへ push する。実装コメントに「**Note システム完成までの繋ぎ実装**」と明記されたまま本番を走っている。ユーザーの個人ページは肥大しやすい (同コードのコメントが自認)。
2. **知覚は編纂まで下りない** — 提示から下ろす唯一の手段は退場付記の印 (`annexed_entry_id`)。`sea/runtime_context.py::list_presented_perception_blocks` の組成規則に明記。「退場したものは必ず編纂されている」不変条件の知覚版で、これ自体は設計どおり。
3. **編纂が止まる環境が存在した** — 旧既定 (残す量 100,000) では会話 4 万字は畳める側に入らず、編纂が一度も発火しない。よって知覚が一枚も下りない。

結果: 入室のたびに**同じ個人ページの全文コピーが一枚ずつ積み重なる**。18 万字の中身は重複コピーの山 (推定 — 実データでの内訳確認は未実施)。観測「ペルソナごとに違う」は相手との歴史の厚さ、「会話頻度が低い子は小さい」は歴史の薄さ、「一往復で 5 万字」はユーザー入室時のユーザーページ全文、でそれぞれ説明がつく。

## v0.3.8 での部分改善 (リリース済み)

既定値が残す量 40,000/上限 120,000 になり、会話 4 万字級の環境では編纂が動き出す → 畳まれた期間の知覚は下り始める。**ただし入室のたびに全文が積まれる構造 (機構 1) は残る**ので、行き来が頻繁な世界では守られる直近期間の中だけでも再び膨らみうる。

## 対処の選択肢 (裁定待ち)

- **A. 重複の抑止**: 同じ相手の再会知覚が未編纂のまま残っていたら、新しい push で**置き換える** (積み重ねない)。堆積の悪循環を直接断つ。個人ページの鮮度も上がる (常に最新の一枚)。
- **B. 身の丈直し**: 個人ページは全文でなく上限付き (導入部 N 字など) にする。過去会話 6 件×2,000 字も見直し。「全文への到達手段とセット」の原則 ([feedback_no_mechanical_truncation_design]) との整合を設計で決める必要がある。
- **C. 知覚の合計上限**: 超えたら古い知覚から提示に乗せない (台帳の既存案件、watermarks issue 側)。本件の個別対処と独立に効く安全網。
- **D. 恒久解へ前倒し**: 繋ぎ実装をやめ、想起用タグ + 手帳 (v3 §12〜§13 で具体形確定済み、台帳「想起用タグ + Track の役割縮小」) に乗せ替える。範囲が大きい。

私 (メティス) の見立て: A は単独で即効性があり副作用が小さい。C は別案件として並走。B は A の後に実測を見て判断、D は v3 の進行に任せる。
