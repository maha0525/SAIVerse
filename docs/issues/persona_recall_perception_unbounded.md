# 再会の想起と部屋の様子が知覚を無限に堆積させる (本番実測 18 万字)

**ステータス**: 🔲 未解決 (検証待ち) — v0.3.9 の 6 件 (供給側 3 + 上限系 3) とレビュー 4 巡の消し込みまで実装済み、フルスイート 5,553 件緑。残 = まはーの実機検証と、数字の裁定 3 点 (知覚の既定 上 60,000/下 40,000・保存時検査の余裕 10,000・`perception_high_chars: null` のオプトアウトが保存時検査を素通しする穴)
**深刻度**: 高 — 「部屋の様子」の送信量がユーザーの制御できない形で肥大し、上限を恒常的に超える。会話は守られるが送信量 (= API 費用) が膨らみ続ける
**発見**: 2026-09-05 (のろけゆきさんの報告。まはーが「再会の機構が食いつぶしてない?」と機構を言い当てた)
**関連**: [watermarks_unsatisfiable_when_perception_is_large.md](watermarks_unsatisfiable_when_perception_is_large.md) (裁定の正史) / `sea/head_pipeline/integration.py` `_inject_persona_recall_on_enter` / `persona/history_manager.py` `recall_conversation_with` / `should_recall_persona`

## 症状 (のろけゆきさんの実測、v0.3.7 相当)

> 現在 222,566文字（読み戻し後）（うち会話 40,398・部屋の様子 182,168）
> 残す量 100,000文字 ／ 上限 200,000文字
> 部屋の様子だけで上限を超えています。

- 部屋に画像も部屋プロンプトもほとんど無いのに「部屋の様子」が 18 万字
- ペルソナを移動しても減らず、**部屋の移動をすると溜まっていく**
- 同じ部屋に滞在していてもペルソナごとに文字数が違う (会話頻度が低いペルソナは約 2 万字)
- Twitter 程度の一往復で表示が約 5 万字増えることがある

## 機構 (2026-09-05 にコードで確認)

三つの仕様の組み合わせで、どれか一つでは起きない。

1. **再会の想起が大きく、門が配線されていない** — 誰か (ペルソナ**またはユーザー**、2026-07-11 裁定で拡大) が部屋に入ってくるたび、`_inject_persona_recall_on_enter` が「相手との過去会話 最大 6 件 (各 2,000 字まで) + **相手の Memopedia 個人ページの全文 (上限なし)**」を知覚バッファへ push する。本来の再会判定 `should_recall_persona` (直近 20 メッセージに相手がいたら想起しない) は**この繋ぎ実装からは呼ばれていない** (前日 9/4 に特定済み、watermarks issue §想起の門の再配線)。
2. **知覚は編纂まで下りない** — 提示から下ろす唯一の手段は退場付記の印 (`annexed_entry_id`)。「退場したものは必ず編纂されている」不変条件の知覚版で、これ自体は設計どおり。
3. **編纂が止まる環境が存在した** — 旧既定 (残す量 100,000) では会話 4 万字は畳める側に入らず、編纂が一度も発火しない。よって知覚が一枚も下りない。

結果: 入室のたびに**同じ個人ページの全文コピーが一枚ずつ積み重なる**。観測「ペルソナごとに違う」は相手との歴史の厚さ、「会話頻度が低い子は小さい」は歴史の薄さ、「一往復で 5 万字」はユーザー入室時のユーザーページ全文、でそれぞれ説明がつく。

## v0.3.8 での部分改善 (リリース済み)

既定値が残す量 40,000/上限 120,000 になり、会話 4 万字級の環境では編纂が動き出す → 畳まれた期間の知覚は下り始める。**ただし入室のたびに全文が積まれる構造 (機構 1) は残る**。

## 対処 (裁定済み — 2026-09-04、watermarks issue §「2026-09-04 の議論」)

対処案は本 issue では立てない。前日に同じ供給側の議論が行われ、まはーの裁定まで済んでいる。v0.3.9 で実装するのは:

1. **想起の門の再配線 + 名前解決** — 既存の `should_recall_persona` を繋ぎ実装に配線し、ずっと会話中の相手への移動ごとの再想起を止める。想起見出しの ID 生値 (`[想起: 1との過去の会話]`) を名前に直す。
2. **スペル増減通知はスキーマ込みで渡す** — 集約で行数を削る方向は誤り (「使えるようになったスペルはスキーマ込みで渡さないといけない」)。
3. **部屋の様子は差分 + 移管** — 「最新だけ残す」型の置き換えは**禁止** (提示の途中の行を消す = キャッシュの前方一致の破壊)。再訪時、前回の全文がまだ提示に見えているなら**差分だけ**を末尾に積む。前回の全文が編纂付記で提示から下りるとき、その内容を「見えている中で最古の同部屋エントリ」へ**移管**する — 書き換えが編纂という既存の壊れ時点に相乗りし、新しいキャッシュの壊れを作らない。
4. **知覚の合計上限**は watermarks issue 本体の実装対象 (安全網として独立)。
