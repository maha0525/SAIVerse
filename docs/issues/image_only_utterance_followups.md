# Issue: 画像だけの発言を届けるようにした後に残った、添付まわりの欠陥

**ステータス**: 🔲 未着手
**優先度**: medium
**作成日**: 2026-10-14
**関連**: ブランチ `feature/xai-image-only-user` (画像だけの発言を受付で断らず、ペルソナの記憶まで届ける修正)。Codex の敵対レビュー (2026-10-14) の指摘のうち、その修正より前からあった欠陥。

## 背景

2026-10-14 まで、チャット画面で文章を書かずに画像だけを送ると「入力が空でした」と出て、発言がどのペルソナにも届いていなかった。この修正で、受付・ペルソナの記憶への取り込み・各 LLM クライアントの組み立てが、本文が空でも添付があれば発言を残すようになった。

修正のレビューで、次の四つが見つかった。どれも修正より前からある欠陥で、画像に本文が付いている発言でも起きる。画像だけの発言が届くようになったことで、目に見えやすくなったものもある。修正の範囲 (発言を届けること) と別の設計判断が要るので、ここに残す。

## 残っている欠陥

### 1. 画像の中身が、記憶の要約・知識の抽出・意味の検索に入らない

画像だけの発言は、本文 `""` のままペルソナの記憶 (SAIMemory) に入る。記憶を後で使う機構は本文だけを材料にしているので、この発言は材料にならない。

- Chronicle の要約 (`sai_memory/arasuji/generator.py`)、知識の抽出 (`sai_memory/memory/entity_extractor.py`)、Stelis の要約 (`sea/runtime.py`) は、本文が空のメッセージを飛ばす。
- 記憶の書き込み (`saiverse_memory/adapter.py` の `_append_message`) は、本文が空だと検索用の埋め込みベクトルを作らない。
- 結果として、提示ウィンドウから畳まれた後は、要約にも検索にも画像の内容が残らない。ペルソナの返事 (本文がある) は残るので、会話の流れが完全に消えるわけではない。

本文付きの画像でも、画像の中身が要約や検索に入らない点は同じ。直すなら、画像の説明 (`ensure_image_summary` が作る `.summary.txt`) を、ユーザーやペルソナ本人の本文を書き換えずに、機構の材料として要約・検索に渡す形を設計する必要がある。

### 2. 画像ファイルが消えていると、保存済みの説明も一緒に消える

`saiverse/media_utils.py` の `iter_image_media` は、ファイルが存在しない画像を最初から外す。画像の説明が `.summary.txt` や metadata の `summary` に残っていても使われない。画面からの添付には `item_name` があるので、`_enrich_history_with_attachments` が「添付アイテム作成: 画像「名前」」の文を足し、発言そのものは残る。名前の無い古い記録の画像だけの発言は、発言ごと送られなくなる。

### 3. 取り下げると、添付が手元に戻らない

まだ誰も読んでいない発言を取り下げると (`withdraw_user_message`、`database/building_messages.py` の `withdraw_building_message_in_db`)、記録の行を消して本文だけを返す。画面は本文を入力欄に戻すが、添付は戻らない。本文付きの画像なら画像だけが失われ、画像だけの発言なら発言全体が手元から消える。直すなら、取り下げで本文と添付の情報を一緒に返し、画面の添付欄まで戻す。再送で画像の Item を二重に作らないことも確かめる。

### 4. 同じ画像の説明を、二箇所が同時に作って二重に課金しうる

画像を受け取ると、受付 (`api/routes/chat.py`) が文脈付きの説明 (`generate_contextual_image_description`) を裏で作り始める。その完了前に、画像非対応のモデルの組み立てが説明を求めると、`ensure_image_summary` が別に作り始める。二つは同じ「生成中」の管理 (`_generating_paths`) に入っていないので、LLM の呼び出しが二回になり、同じ `.summary.txt` を後から書いた方が上書きする。画像非対応のモデル (OpenAI 互換・Anthropic・Gemini・xAI のどれでも、モデル設定で `supports_images` が偽のもの) で起きる。builtin のモデルはどれも画像に対応しているので、利用者が自分で足したモデルでだけ起きる。

## 解決案候補

- 1 は、記憶の設計 (`docs/intent/memory_architecture_v2.md`) の話になる。画像の説明を機構名義の材料として持たせるか、画像を要約・検索の対象外のままにするかを決めるところから。
- 2 は、ファイルが無いときも保存済みの説明があればそれを使い、それも無ければ「画像を読めなかった」ことを機構の文で残す。
- 3 は、取り下げの戻り値と画面の入力欄の両方を直す。
- 4 は、文脈付きの説明の生成も `_generating_paths` に参加させ、生成中なら待って結果を共有する。説明を作る依頼の中で再び説明を求める再帰 (`__skip_image_summary__` で防いでいる) と、待ちが絡まないことを確かめる。
