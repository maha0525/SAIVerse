# on_event 判断に冪等キーが無く、同じ刺激の再配送が二重応対になりうる

**発見**: 2026-08-14（Track 撤廃 順序① の消し込みに対する Codex adversarial-review 二巡目 high）
**状態**: 未着手（設計判断がまはー待ち — 下の「決めてほしいこと」）
**関連**: [judgment_seat_contention_and_event_loss.md](judgment_seat_contention_and_event_loss.md)（席の競合制御。①〜⑤）、`saiverse/autonomy_wiring.py` の `_judgment_idempotency_key`

## 芯

判断点には「同じ判断を二度走らせない」ための冪等キーがあり、day_open / day_close は日付や節目から安定したキーを作れる。**on_event（外部イベントの到着・別行動中のユーザー発話）だけはキーが `None`** で、発火のたびに新しい台帳の席を取る。

per-persona のロックは**順番に並べるだけ**で、同じものを二度処理するのを止めない。したがって同じイベント / 同じ発話がもう一度届くと（配送元の再送、ユーザーの操作、ゲートウェイの再接続など）、判断が二度走り、両方が engage_now を選べば**応対も二度**走る。

## なぜ今すぐ直せないか

冪等キーには「同じ刺激だ」と言い切れる **安定した ID** が要る。いまその ID を持っている場所が無い:

- 外部イベント（`inject_persona_event`）— 呼び出し元が渡すのは本文テキストだけ。フィード記事・Discord メッセージ・現象など供給源ごとに ID の有無も形も違う
- ユーザー発話 — building history のメッセージ行に相当するものはあるが、仲裁の入口までは運ばれていない

本文のハッシュで代用すると、**同じ文面の別の発話**（「うん」「ありがとう」）が同一視されて二通目が黙殺される。これは二重応対より静かで、気づけない害になる。

## 決めてほしいこと

1. 刺激の ID を**供給源に発行させる**か（各 producer が durable な receipt id を付ける = 正しいが、供給源すべてに手が入る）、**受信側で一括発行**するか（`inject_persona_event` / 発話取り込みの入口で採番 = 変更は 1 箇所だが、再送を「別の刺激」と数えてしまう経路が残る）。
2. 冪等の窓をどう置くか（同一 ID は永久に一度きり／一定時間内だけ一度きり）。会話は同じ相手と何度も起きるので、永久の一意性は「同じ質問を後日また聞く」を弾きうる。

## いま起きていないこと（誤解を避けるため）

- **席の二重取り**（同時に同じ判断が二本走る）は塞がっている（同 issue ①、prepared 限定 CAS）。ここで残っているのは「**別々の席を取った二回の発火**」で、機構としては正常に二回処理している。
- 回復 tick の refire は既存の席を使うので、この経路では二重にならない。
