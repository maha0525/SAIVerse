# 刺激（イベント・ユーザー発話）に永続 ID が無く、同一性を必要とする機構が全部そこで止まる

**発見**: 2026-08-14（Track 撤廃 順序① の消し込みに対する Codex adversarial-review 二巡目 high。三巡目で**同じ欠落が 4 つの別の顔で再出**したため、issue の範囲を「冪等キー」から「刺激の永続 ID そのもの」へ広げた）
**状態**: 実装済み・実機検証待ち (2026-10-09 段 1 — 下の「実装 (2026-10-09 段 1)」。検証は v0.4 実装計画の段 1 の隔離環境の検証と同じ便で行う)。旧状態: 設計確定・実装待ち (2026-10-09 まはー決定)。**2026-08-14 まはー裁定: Track 撤廃 順序① はこの近似のまま実機検証へ進める**（下の「近似のまま進めた裁定」）
**関連**: [judgment_seat_contention_and_event_loss.md](judgment_seat_contention_and_event_loss.md)（席の競合制御。①〜⑤）、`saiverse/autonomy_wiring.py` の `_judgment_idempotency_key`

## 芯

判断点には「同じ判断を二度走らせない」ための冪等キーがあり、day_open / day_close は日付や節目から安定したキーを作れる。**on_event（外部イベントの到着・別行動中のユーザー発話）だけはキーが `None`** で、発火のたびに新しい台帳の席を取る。

per-persona のロックは**順番に並べるだけ**で、同じものを二度処理するのを止めない。したがって同じイベント / 同じ発話がもう一度届くと（配送元の再送、ユーザーの操作、ゲートウェイの再接続など）、判断が二度走り、両方が engage_now を選べば**応対も二度**走る。

## なぜ今すぐ直せないか

冪等キーには「同じ刺激だ」と言い切れる **安定した ID** が要る。いまその ID を持っている場所が無い:

- 外部イベント（`inject_persona_event`）— 呼び出し元が渡すのは本文テキストだけ。フィード記事・Discord メッセージ・現象など供給源ごとに ID の有無も形も違う
- ユーザー発話 — building history のメッセージ行に相当するものはあるが、仲裁の入口までは運ばれていない

本文のハッシュで代用すると、**同じ文面の別の発話**（「うん」「ありがとう」）が同一視されて二通目が黙殺される。これは二重応対より静かで、気づけない害になる。

## 決まったこと (2026-10-09 まはー決定)

1. **刺激の ID は全供給源に一意な ID を義務として持たせる。** 刺激の入口それぞれ (現象の封筒 `phenomena/triggers.py` TriggerEvent / ユーザー発話の取り込み / Discord の受け口) で欄を必須にし、供給源それぞれが自分の永続 ID (フィード記事の ID・Discord のメッセージ ID・発話のメッセージ行の ID 等) を書く。受け取り口での代理採番は採らない — 再送を「別の刺激」と数える経路が残るため。v0.3→v0.4 は大きく変えるブランチなので、供給源全部に手を入れる方を取る。
2. **照合の記録は、行ごとに受け取った時刻を持ち、保持期間を過ぎた行だけを個別に消す。** 記録全体を丸ごと消す瞬間を作らない (掃除と供給が前後しても新しい行が残る形)。古さの判定は実時間。本文のハッシュでの同一視はしない (「うん」「ありがとう」の別発話を黙殺するため)。

## 実装 (2026-10-09 段 1、コミット 8663242b)

刺激の入口三系統のそれぞれで、供給源の永続 ID を必須にした。**現象の封筒** (`phenomena/triggers.py` の `TriggerEvent`) は `stimulus_id` が既定値なしの必須欄になり、入口の `inject_persona_event` は ID の無い封筒を ERROR で落とす。同じ入口が、イベントの記録 (persona_event_log) と判断経由・直接応対のどちらの経路よりも前に、受領の照合 (`saiverse/stimulus_receipt.py`、テーブル `stimulus_receipt`) で同じ (ペルソナ, 刺激 ID) の二度目を止める。照合の記録は行ごとに実時間の受領時刻を持ち、保持期間 (7 日) を過ぎた行だけを受領のたびに個別に消す。**ユーザー発話**は building_messages のメッセージ行の ID (`msg:<message_id>`) を刺激の ID とし、再送は保存の段の `client_message_id` の一意制約が止める (受領の照合は通さない)。別の活動中に届いた発話に ID が無いとき (配線の誤り) は、ERROR を残して仲裁を経ずに直接会話を始める — ユーザーの呼びかけを黙殺しないため。**Discord** は受け口の引数の食い違い ([issue](discord_gateway_human_message_signature_mismatch.md)) を直したうえで、メッセージ ID を `client_message_id = "discord:<id>"` として保存まで運ぶ。on_event の冪等キーは `{persona}:{stimulus_id}` (`saiverse/autonomy_wiring.py` の `_judgment_idempotency_key`) で、受領記録の書き込みが DB 障害で転んだときの二段目の歯止めも兼ねる。下の「4 つの顔」のうち、この便で塞いだのは冪等キー。残りの三つ (回収の重複判定の粒度・回収 activate の競合・claim 失敗時の黙殺) はユーザー発話の仲裁の顔で、仲裁は「別の活動中か」を答える器が無い今の v0.4 では発火しない (`saiverse/user_conversation.py` のコメントのとおり、ID の配線だけを通してある)。仲裁を残すかとその作り直しは v0.4 計画の段 2 (Pulse 並列の表、未決 10) で決めるので、三つはそこで ID を使って扱う。

## 決めてほしいこと (決着済み — 上の「決まったこと」が答え)

1. 刺激の ID を**供給源に発行させる**か（各 producer が durable な receipt id を付ける = 正しいが、供給源すべてに手が入る）、**受信側で一括発行**するか（`inject_persona_event` / 発話取り込みの入口で採番 = 変更は 1 箇所だが、再送を「別の刺激」と数えてしまう経路が残る）。
2. 冪等の窓をどう置くか（同一 ID は永久に一度きり／一定時間内だけ一度きり）。会話は同じ相手と何度も起きるので、永久の一意性は「同じ質問を後日また聞く」を弾きうる。

## 同じ欠落が出てくる 4 つの顔（2026-08-14 三巡目）

三巡目のレビュー指摘 6 件のうち 4 件は、角度が違うだけで**同じものが無い**と言っている。個別に塞ごうとしても、どれも「その刺激だ」と言い切れる ID が無いところで止まる。

| 顔 | 何が起きるか | ID があればどう解けるか |
|---|---|---|
| 冪等キー（本 issue の元の題） | 同じ刺激の再配送が別の台帳席として二重に処理される | 刺激 ID を `on_event` の冪等キーにする |
| 回収の重複判定の粒度 | 「この会話区間に assistant 応答が一件でもあるか」でしか見られないので、**先行発話への応答**を対象発話への応答と誤認して、回収が黙殺されうる | 「その発話に対する応答が出たか」を receipt で照合する |
| 回収 activate の TOCTOU | 応答済み判定と activate が非原子的。判定の直後に通常経路が応答すると二重応対 | 「その発話の receipt がまだ無いときだけ activate」の条件付き遷移にできる |
| claim 失敗時の黙殺 | 台帳 claim が例外だと `indeterminate` = 応答しない。行が作られていなければ誰も拾わず、その発話は永久に失われる | 発話 receipt を先に永続化しておけば、claim が転んでも後から拾い直せる |

**つまり順序が逆にできない。** 上 3 つは receipt が無いと「正しく直したつもり」の実装しか書けず、いま入っている歯止め（区間単位の証跡・条件付き close）はその近似でしかない。

## 近似のまま進めた裁定（2026-08-14、まはー）

**Track 撤廃 順序① は、この永続 ID が無いまま実機検証へ進める。** レビュー（Codex 3 巡）は「指摘が今回の実装範囲を外れた根っこまで到達した」時点で完了とし、receipt の設計と実装は別セッションで扱う。

**了解の上で受け入れているリスク**（見落としではない）:

- 別行動中に立て続けに 2 回話しかけると、1 回目の応答が出た後に 2 回目の仲裁が回収された場合、回収側は「この会話区間に応答がある」と読んで **2 回目を黙殺しうる**。
- 同じイベント / 同じ発話が再配送されると、別の台帳席として二重に処理されうる。

前者を受け入れられる根拠は**復旧可能性**: 黙殺されてももう一度話しかければ通常経路で応答する（永久に失われるのは claim 例外の稀な並びだけ）。逆に receipt 設計を先に入れると順序①の実機検証が丸ごと止まる。

**次にこの issue を開く人へ**: 上のリスクは既知で、意図的に残されている。「近似の歯止めが誤動作した」という観測が来ても、それは新しい発見ではなく**この裁定の想定内**。直す先は歯止めの微調整ではなく、永続 ID の設計そのもの。

## いま起きていないこと（誤解を避けるため）

- **席の二重取り**（同時に同じ判断が二本走る）は塞がっている（同 issue ①、prepared 限定 CAS）。ここで残っているのは「**別々の席を取った二回の発火**」で、機構としては正常に二回処理している。
- 回復 tick の refire は既存の席を使うので、この経路では二重にならない。
