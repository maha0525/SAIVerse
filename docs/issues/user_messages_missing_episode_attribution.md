## 事実 (2026-07-28 実測、eris_city_a 読み取り専用)

- **user メッセージ 4,578 件のうち、エピソード帰属 (`origin_episode`) を持つものは 0 件。** assistant は 141 / 4,657 件、system は 39 / 267 件が帰属あり (エピソード機構の稼働開始以降のもの)。
- 原因はコードで特定済み。帰属タグを付ける処理は**ペルソナ自身の発言の保存経路にしか無い** (`sea/runtime.py` `_store_memory` — 保存時にそのペルソナの開いているエピソードを引いて刻む)。user 発言が通る経路 — 集会所履歴からの転記 `auto_ingest_building_messages` (`builtin_data/tools/get_building_messages.py`) — には**タグ付けが存在しない**。
- 帰結として、Chronicle の列に取り残される豆粒 (恒等転写の極小あらすじ) 26 件は**全件**が無帰属メッセージ (会話の第一声の user 発言かスケジュール起動文) で、**全件**が会話本体とは別の回の編纂で生まれている。会話本体が退場した回に、無帰属メッセージは畳む範囲に入れてもらえず置き去りにされ、後の回に単独で畳まれて生ログのまま列に立つ。

## なぜ問題か

1. **「出来事」という記録の単位が会話の片側しか含んでいない。** まはーと過ごした出来事の記録に、まはーの言葉が構造上一切入らない。エピソードを原子として扱う全機構 (編纂 §4-2「エピソードは分割しない」、退場「開いているエピソードは単独で畳む」、pulse 関節細分、episode_read による再訪) が、片側だけの原子の上に立っている。
2. **豆粒の量産ライン。** 恒等転写 (1,000 字未満は生ログのまま置く) は稀な端数のための受け皿だったが、無帰属の第一声が毎会話・毎スケジュール起動で供給されるため量産になっている。束ね側で観測された病理 (ch:504/505 の永久残留、治療の肥大) の供給源。
3. **これから悪化する。** エピソード機構は稼働開始から日が浅く、依存する機構 (再訪・digest 転写・Track 連携) は増える方向。穴が古くなるほど既存データの修復判断が重くなる。

## 修正方針の候補 (まはー裁定待ち)

1. **転記経路にタグ付けを足す** (本筋と思われる): `auto_ingest_building_messages` の転記時に、`_store_memory` と同じ「開いているエピソードを引いて刻む」を行う。ただし「誰のエピソードに入れるか」の設計判断がある — 転記先ペルソナの開いているエピソードでよいか (会話相手が複数いる建物では?)。
2. **既存データの扱い**: 遡って帰属を付ける (バックフィル) か、これからの分だけか。バックフィルする場合、時間範囲でエピソードに内包される user 発言に付ける形が考えられるが、境界 (エピソード開始直前の第一声こそが問題の本体) の扱いを決める必要がある。
3. 既に生まれてしまった豆粒 26 件の後始末は、束ね側の再設計 (豆粒への比率適用の見直し — 治療再設計ハンドオフ参照) が回収する見込みなので、本 issue の範囲外。
