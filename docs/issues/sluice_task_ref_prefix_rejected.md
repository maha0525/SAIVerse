# Issue: スルースの約束の update が、一覧どおりに書いた task_ref を弾く

**ステータス**: 🟠 実装中
**優先度**: high (ユーザー報告。約束の書き直しが構造的に全滅する)
**作成日**: 2026-09-27
**報告**: noble_piglet_59694 さん (Discord、2026-09-24)。v0.3.14 と当日の develop で確認済みとの報告。
**関連**: `sea/sluice.py` (`_format_task_line` / `_apply_promises` / promises スキーマの `task_ref`)

## 症状

ペルソナのスルース (記憶整理のときに約束や手帳を書き取る仕組み) で、既存の約束の書き直し (update) が「約束 update をスキップ: task_ref='task:74b3bbe2-…' は一覧にありません。」と弾かれ続ける。報告者の環境では 9/22〜9/24 に同じ約束の書き直しが 4 回続けてスキップされた。崩れていないきれいな番号でも弾かれており、弾かれた理由が本人 (ペルソナ) に分からないため、番号を推測で書き換えて試す行動 (`task:74b3…-placeholder-match-fix`) まで起きていた。

## 原因 (コードで確認済み)

ペルソナに見せる約束の一覧は `_format_task_line` が `[task:ID]` の形で書く (sea/sluice.py:959)。プロンプト本文も「その task の ID を task_ref にして update を使えます」と案内している。

一方、適用側の `_apply_promises` は `task_ref not in offered_tasks` で照合する (sea/sluice.py:1721) が、`offered_tasks` の鍵は生の task_id (`task:` なしの UUID、sea/sluice.py:2613) で、前に付いた `task:` を外していない。つまり**ペルソナが一覧に見えたとおり `task:〜` と写すと必ず弾かれる**。コア記憶の `core:N` は `_parse_ref` が接頭辞を外して受けるのに、約束だけ扱いが違う。

既存テストは task_ref に `task:` なしの生 ID を渡しているため、テストではこの欠陥が見えない。

## 直す方向

1. `_apply_promises` で task_ref の先頭の `task:` を外してから照合する。生 ID もそのまま受け続ける — これはコア記憶の `core:N` (そのままの写し以外を棄却) より受理が広い、意図的な違い。理由は、台帳に記録済みの過去の応答が再適用されること (sea/sluice.py:2888) と既存テストとの互換。
2. promises スキーマの `task_ref` の説明と、プロンプトの案内文を「同梱の一覧の task:ID をそのまま写す」に揃える (提示した語をそのまま写させる点はコア記憶と同じ流儀)。
3. テストに「`task:` 付きで update が通る」「生 ID でも通る」「後ろにゴミが付いた ref は弾かれる」を追加する。

### 残る食い違い (この修正では触らない、記録のみ)

参照文法の正典 (docs/intent/reference_addressing.md) では `task:N` は目的の木 (persona_task) の short_id を指す語で、タスク帳の UUID ではない。スルースの一覧が `[task:<uuid>]` と表示するのは正典制定より前からある食い違いで、ペルソナがこの表記を `memory_read` 等へ持ち出すと「目的ノードが見つかりません」になる。本修正はスルースの応答欄という閉じた輪の中の照合を直すだけで、表記の統一 (タスク帳の一件に別の語を与えるか、表示を変えるか) は別の判断として残る。

## 併発していた別の崩れ (このイシューでは直さない)

報告 4 回のうち 3 回で、task_ref の中に `,content':'` から後ろの本文までがくっつく崩れも出ていた (中身の文章が番号の欄に流れ込む形)。これはモデルの出力の崩れで、接頭辞の修正が入れば正しい形の写しは通るようになる。崩れた ref は照合で弾かれるのが正しい挙動 (推測で救済すると別の約束を書き換えかねない) なので、受理は広げない。頻発が続くようなら別イシューとして観察する。

## 約束を「やり終えた」にする口が無い件 (報告の三点目、v0.4 の設計枠)

報告者の指摘どおり、約束を閉じる操作 (`saiverse/task_book.py` の `complete_entry` / `withdraw_entry`) はスペルにも UI にも繋がっていない。これは欠陥ではなく、時期が決まっている空白:

- スルースの応答スキーマに close を置かないのは意図的 (docs/intent/autonomous_behavior_v3.md §13.1 — アクティビティの closed について「定常の一手に閉じる口があると『なんとなく閉じる』が起きる」。v1 で Track が一発で閉じられまくった教訓)。タスク帳側も、完遂で閉じるのは運転の層 (同 §9 の「完遂で閉じるキュー」) の仕事で、v0.4 で設計される。
- UI からの書き込み (訂正・削除の類) は「v0.3 は読むだけ。訂正の口は v0.4 で、手帳の器の作り直しとタスク帳の CAS との整合を決めてから開ける」と裁定済み (同 §13.2.1、2026-08-23)。「やり終えた」にする操作がこの「訂正」に含まれるかは文言上は未確定だが、同じ整合の問題を持つので、私は同じ v0.4 の枠で扱うのが自然と考える。前倒しするかはまはーの判断。
