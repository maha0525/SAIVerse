# Issue: 表示中の建物が削除されたとき、引っ越し先が無いと画面が詰む

**ステータス**: 🟣 検証待ち (修正は v0.3.16 で発行済み。まはーの実機確認待ち。2026-10-01 に台帳と揃えた — それまでの表記は「🔧 実装中」)
**優先度**: medium
**作成日**: 2026-09-28
**関連**: `frontend/src/app/page.tsx` (building-deleted イベントの復旧処理) / `manager/admin.py` `delete_building`

## 背景

世界の編集 (WorldEditor) で建物を削除すると、メイン画面へ `building-deleted` イベントが飛ぶ。
表示中の建物が削除された場合、メイン画面の復旧処理は「建物一覧 (`/api/user/buildings`) を
取って、先頭の建物へ移動する」という作りになっている。この処理には三つの抜けがある。

1. 建物一覧が**空**だと、何もせずに終わる。
2. 建物一覧の**取得に失敗**しても、何もせずに終わる (catch は console.error のみ)。
3. 引っ越し (`/api/user/move`) が**失敗**しても、何もせずに終わる。

どの場合も画面は削除済みの建物を表示し続け、履歴取得・発言先も存在しない建物 ID を
使い続けて詰む。

発見の経緯: 2026-09-28 の監査第二弾 (feature/audit-safety-phase2) の Codex レビュー三巡目が、
隣接する修正のついでに指摘した。その束とは無関係の既存欠陥として切り出した。

## 調査で確定した前提 (2026-09-28)

- 削除 API (`manager/admin.py` `delete_building`) には既に三つの柵がある:
  シード建物 (`user_room_` 等の接頭辞) は削除不可 / AI 在室なら拒否 /
  **ユーザー在室 (DB の `User.CURRENT_BUILDINGID`) なら拒否**。
- メイン画面の建物切り替えは閲覧モード (C-1) で、サーバー上の現在地は発言時 (C-2,
  `/chat/utter`) まで動かない。つまり「自分がいない建物を表示して、それを削除する」は
  **一台の画面でも普通に起きる**。これが復旧処理の主な発火経路。
- 削除が成功した時点で、サーバー上のユーザー現在地は削除された建物ではないことが
  柵により保証されている (現在地そのものが壊れることはない)。壊れるのは表示だけ。
- 「建物ゼロの City」は既に存在しうる正規の状態: City 新規作成 (`manager/admin.py`
  `create_city`) は City の行だけ作り、建物を作らない。ユーザーが作った建物には
  シード接頭辞が無いので、全部消せばゼロに戻る。city_a はシード建物が消せないので
  ゼロにならない。

## 裁定 (2026-09-28 まはー)

対応は **(1) フロント側の手当てのみ**。API 側に「最後の建物の削除を拒否する」柵は
足さない (建物ゼロは City 誕生時の正規状態であり、削除だけ拒否しても状態としての
ゼロは消せないため)。

## 対応内容

`building-deleted` の復旧処理で、引っ越し先が見つからないとき「削除済みの建物を表示し
続ける」のをやめ、選択中建物を null にして操作不能状態を画面に明示する。

- 一覧が空: 「この世界には建物がありません」の案内を本文エリアに表示し、入力欄を無効化。
- 一覧取得失敗・引っ越し失敗: 「表示していた建物は削除された。別の建物を選んで」の案内を
  表示し、入力欄を無効化。サイドバー・マップから建物を選ぶと解除される。
- 一覧が取れて空でないときの既存挙動 (先頭の建物へ移動) は変えない。

## スコープ外として記録する観察

- 復旧処理の「先頭の建物へサーバー移動 (`/api/user/move`)」は、閲覧モード (C-1) の
  設計から見ると過剰の可能性がある (削除後もサーバー現在地は有効なので、表示の
  切り替えだけで足りるかもしれない)。既存挙動として今回は触らない。
- 建物ゼロの City を実際に起動したときの挙動は未検証。

## 実装 (2026-09-28)

- `frontend/src/app/page.tsx`: 表示先を失った状態 `lostBuildingNotice`
  (`'empty' | 'error'`) を導入。復旧処理の三つの抜け (空・取得失敗・移動失敗) で
  この状態に入り、選択中建物を null にして案内を表示、入力欄と送信を無効化する。
  建物を再び表示できる各経路 (サイドバー・マップ・起動時 status・サーバー発移動・
  復旧成功) で解除する。
- 再接続処理の補修 (検収で見つけた隣の穴): 表示先が無いまま再接続すると、引数なしの
  履歴取得がサーバーの現在地の履歴を案内の画面へ流し込んでいた。再接続時に表示先が
  無ければ、先にサーバーの現在地を採用してから読み込む形にした。建物の削除は
  「反映には再起動が必要」と案内される操作なので、削除→再起動は現実的な並び。
- `frontend/src/i18n/messages.json`: `app.page.text095`〜`text097` を追加。
- `frontend/src/app/page.module.css`: 案内ボックスのスタイル (ダーク・ライト両対応)。
