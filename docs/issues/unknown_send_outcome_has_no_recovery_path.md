# Issue: 発言が届いたか分からないまま終わったとき、復旧する手段が無い

**ステータス**: 🔲 未着手 — 設計から。**v0.3 の門の内 (2026-08-29 まはー裁定、gate §2-18)**
**優先度**: high — ユーザーが手で打ち直すと、同じ発言がペルソナの記憶に二度残る
**作成日**: 2026-08-28
**出自**: [user_utterance_path_failure_inventory](archive/user_utterance_path_failure_inventory.md) の
Codex レビュー 1 巡目 (2026-08-26) が指摘し、補修では塞げないとして切り出した 4 件のうちの 1 つ。
出口 7 (顛末が確定していない) の実装で、通知までは作ったが復旧までは作れなかった部分。

---

## 共通の根 — 「どの生成の、どの段階の話か」を運ぶものが無い

切り出した 4 件は別々の顔をしているが、**一つのストリームについて「これはどの生成のことで、
いまどの段階まで進んだのか」を運ぶ仕組みが無い**という同じ欠落から出ている。

- この issue (未知の送信結果から復旧できない) は**どの段階まで進んだか**が運べていない。
  発言がサーバーに残ったのかどうかを、後から尋ねる手段が無い。
- [保存できたことを表す信号が無い](stream_completion_is_not_proof_of_persistence.md) も段階の話で、
  画面に出たところまでなのか DB に残ったところまでなのかを受け手が区別できない。
- [retry がサーバー側で再送可能性を見ていない](retry_api_has_no_server_side_eligibility_check.md)
  も段階の話で、**その発言が既に応答を得たのかどうか**を発言自身が持っていない。
- [ストリームの表示に識別子が無い](streaming_events_have_no_identity_in_the_ui.md) は
  **どの生成の話か**が運べていない。断片がどのペルソナのどの Pulse のものかを、画面側が照合しない。

4 件を別々に補修すると、同じ判断が経路ごとに別の場所へ書き分けられる (この inventory の
レビュー 3 巡で繰り返し出た型)。**設計するときは 4 件を一つの束として扱う**のが安全で、
どれか 1 件だけを先に直す場合も、残り 3 件がその決めごとに乗れるかを見てから決める。

---

## 何が起きているか (コードで確認した事実)

- `frontend/src/app/page.tsx:2231-2246` — ストリームが結果を一つも見ないまま切れたとき、
  サーバーから発言 id を受け取る `user_message_id` イベントがまだ来ていなければ
  (`!landedMessageId`)、`unknown_outcome` の案内を出す。文言は「通信が途中で切れました。
  発言が届いたかどうかは分かりません。履歴を確認してください。」
- そのとき `markRetryable` は呼ばない。**呼びたくても対象の message_id が無い。**
  この案内にはボタンが付かない。
- 文言そのものは正しい。ここで再送ボタンを出すと、実は届いていた場合に同じ発言が二度載る —
  それは「再送」の口 (`/api/chat/retry`) が防ごうとしているものそのもの。

## ユーザーから見て何が起きるか

自分の発言が届いたかどうか分からない状態で、画面には「履歴を確認してください」とだけ出る。
確認して見つからなければ、**入力欄に手で打ち直す**ことになる。

サーバーには冪等性の仕組みがあるが、この場面では効かない。

- 送信 1 回につき UUID (`client_message_id`) を採番し (`frontend/src/app/page.tsx:2342-2353`)、
  `building_messages.client_message_id` は UNIQUE 制約と索引を持ち
  (`database/models.py:857,869,872`)、重複した挿入は既存行を返す
  (`database/building_messages.py:428-437`)。
- **しかしこれは「同じ id で送り直したら二重にならない」であって、「届いたかを尋ねる」ではない。**
  ユーザーが手で打ち直せば新しい UUID が振られるので、冪等性は素通りする。二重になった発言は
  そのままペルソナの記憶へ入る。

これは §2-17 (会話の終わり方) を v0.3 の門の内へ入れた理由そのもの —
「ユーザーは応答を得るために要らない発言をもう一度書かされ、その行がペルソナの履歴に永久に残る」。
出口 7 だけ、その穴が塞がっていない。

## なぜ補修で塞げないか

画面の側には材料が無い。ブラウザは「届いたかどうか」を知らないまま切れており、知っているのは
サーバーだけ。**尋ねる口を作らない限り、フロントで分岐を足しても推測にしかならない。**

## 直すのに要るもの (設計の入口)

**`client_message_id` で保存結果を問い合わせる読み取りの口**。データは既にある (列も UNIQUE 制約も
索引もある) ので、新しい列やマイグレーションは要らない。論点は三つ。

1. **返す形**。「その id の発言は残っている (サーバー側の message_id はこれ)」「残っていない」
   「分からない」の三値。三つ目を潰さないこと — 潰すと、いま正直に言えている出口 7 が嘘をつく側へ
   戻る。
2. **誰が起こすか**。問い合わせ自体は LLM を使わないので自動でよいはずだが、そこから先
   (応答のやり直し) は追加の推論が走るので、**ボタンの後ろに置く**という 2026-08-25 の裁定が効く。
   自動で問い合わせて導線だけ出す形が素直に見えるが、裁定の対象に当たるかは確認が要る。
3. **合流先**。発言が残っていて応答が無ければ既存の「再送」(`/api/chat/retry`) へ、残っていなければ
   入力欄への差し戻し (出口 4) へ。どちらも実装済みなので、この issue で作るのは問い合わせの口と
   分岐だけになる。

## 設計裁定 (2026-08-29、実装前確定)

上の論点三つへの答え:

1. **返す形は三値** — 「残っている (サーバー側 message_id と、その発言より後にペルソナの発言が
   あるか has_reply を添える)」「残っていない」「分からない (照会失敗)」。三つ目を潰さない。
   has_reply の判定は J (retry 門番) と**同じ関数を共有**する — まはー裁定の一比較
   (その発言以後に assistant ロールの発言があるか)。
2. **問い合わせは自動で起こす** — LLM ゼロの読み取りなので、2026-08-25 裁定 (追加の推論は
   ボタンの後ろ) の対象外。推論が走る操作 (再送・やり直し) は従来どおりボタンの後ろ。
3. **合流**: 残っている∧応答なし → 既存の再送導線 / 残っている∧応答あり → 「届いていました」の
   案内 + 履歴の再取得 / 残っていない → 既存の入力欄差し戻し / 分からない → 現行の正直な文言のまま。
