# Issue: スルースの実行台帳 unknown に、エンドユーザーが捌ける口が無い

**ステータス**: 🔲 未着手 (2026-08-19 起票。まはー「それユーザーどうやって捌くんすか — 別途考えよう」)
**優先度**: v0.3 リリース前に方針だけ決めたい (発生は稀だが、起きると一般ユーザーには原因不明の恒久停止に見える)
**関連**: [`../intent/execution_ledger.md`](../intent/execution_ledger.md) / [`../intent/autonomous_behavior_v3.md`](../intent/autonomous_behavior_v3.md) §13.3

## 何が起きるか

スルース (退場の関所の採取) は実行台帳に乗った (2026-08-19、束 3)。台帳の大原則「unknown (実行したか不明) は人の裁定まで自動再実行しない」に従うため、**スルースの LLM 実行中にプロセスが死ぬと、そのペルソナの記憶の退場 (Metabolism の anchor 前進) が、台帳の unknown 行を人が裁くまで止まり続ける**。

- 開発者は `scripts/inspect_world.py` や台帳の list_unknown で裁ける
- **一般ユーザーには見える口が無い** — 「記憶の整理を見送りました」が毎回出続けるだけで、原因も回復手段も提示されない。提示コンテキストは肥え続ける (退場が止まるだけで会話は動く)

## 考える論点 (別途)

1. **UI の口**: unknown 行の存在をユーザーに見せ、「再実行してよい / 破棄する」を選ばせる面をどこに置くか (ペルソナ設定? 通知?)
2. **自動裁定の余地**: スルースは「適用前に mark_failed される設計 = LLM 呼び出しの副作用は課金だけ」なので、unknown の実害は二重課金のみ。台帳の大原則を破らずに「この kind は自動再実行可」の宣言を kind 側に持たせられるか (歯止めの条件は目的から導く — 守りたいのは二重の不可逆適用であって、二重課金は許容かもしれない)
3. 同じ問いは将来、台帳に乗る他の kind (Playbook 投げっぱなし等) にも来る — スルース個別でなく kind の属性として設計する

## 暫定の運用 (v0.3 検証時)

実機検証の手順書に「スルース中にプロセスを殺したら、退場が止まる。回復は inspect_world / 台帳の unknown 裁定」を書き添える。
