# サーバー側文言 (FastAPI detail 等) のローカライズ未配線と構造化

**起票**: 2026-09-14 (Claude 監査指摘 3 の切り出し、まはー合意)  
**状態**: 未着手 (UI 画面のローカライズと City/ペルソナ言語設定を先行して完了、本件は独立課題として分離)  
**関連**: `frontend/src/i18n/api.ts` (`apiFetch`)、`frontend/src/i18n/messages.json`、`api/` 配下の各エンドポイント、`docs/intent/localization.md`

## 症状と現状

1. `frontend/src/i18n/messages.json` には、サーバー側由来の文言（エラー文や操作結果など）に対応する辞書キーが約 433 件定義されている。
2. 一方、バックエンド側（FastAPI エンドポイント群）は現在、`HTTPException(status_code=404, detail="ペルソナが見つかりません")` のように日本語文字列を直接返している。
3. フロントエンドの `apiFetch` (`frontend/src/i18n/api.ts`) には、サーバーが `{"$ui": "key", "params": {...}}` 形式のオブジェクトを返したときに辞書から言語に応じた文言を解決する仕組みが既に実装されている。
4. しかしサーバー側がプレーンテキストの日本語を返しているため、画面言語を英語に切り替えても、サーバー起因のエラーメッセージやトーストは日本語のまま表示される。

## 方針と設計

`docs/intent/localization.md` に掲げた不変条件に沿って、段階的に配線を行う。

- **不変条件**: サーバー側は自然言語の完成文を持たず、文言キーとパラメータのみを返す。文の構築はフロントエンド側の辞書が行う。
- **実装手順**:
  1. バックエンドに UI メッセージ返却用のヘルパー（例: `ui_detail(key: str, **params)`）を用意し、FastAPI の `HTTPException(detail=...)` に構造化辞書を載せる。
  2. `api/` 配下のエンドポイント（約 94 箇所）で日本語直書きになっている `detail` を順次ヘルパー呼び出しへ置き換える。
  3. `messages.json` に登録済みの 433 件のキーと照合し、過不足を解消する。
  4. 画面側でエラー文言が正しく英語／日本語に切り替わることをテストで検証する。
