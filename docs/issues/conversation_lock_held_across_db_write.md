# 会話ロックを持ったまま DB へ書いていて、単一の発火スレッドが止まる

**状態**: 未解決 (2026-08-22 起票)。**裁定待ち** — 直すかどうか、直すならどこへ動かすかが決まっていない。

関連: [`saiverse/user_conversation.py`](../../saiverse/user_conversation.py) / [`saiverse/autonomy_wiring.py`](../../saiverse/autonomy_wiring.py) / [`saiverse/event_scheduler.py`](../../saiverse/event_scheduler.py)
出自: v0.3 形の層の掃討フェーズ、ローカル LLM レビューの指摘 2 (2026-08-22)。同じレビューの指摘 1 (応答中に古いタイマーが会話を閉じる) は原因が特定できたためその場で修正済み。

## 何が起きるか

**あるペルソナの会話を閉じる処理が遅れると、他の全ペルソナの時限処理がその間ずっと止まる。**

具体的には、ペルソナ A の沈黙タイマーが発火して会話を閉じる最中に DB が詰まると、その 10 秒なら 10 秒のあいだ、ペルソナ B の沈黙タイマーも、C の予定の発火も、まとめて後ろへずれる。ユーザーから見ると「B の会話が時間を過ぎても閉じない」「予定の時刻に何も起きない」という形で出る。

加えて、同じ 10 秒のあいだ A へ話しかけたユーザーの応答も待たされる (開始経路が同じロックを取るため)。

## なぜそうなるか (確認した事実)

三つが噛み合っている。いずれも現物を読んで確認した。

1. **沈黙タイマーの callback を実行するスレッドは 1 本だけ。**
   `event_scheduler.py:99` で `threading.Thread` を 1 つだけ立て、その 1 本が全ペルソナ・全種類の予約を順番に捌く。
2. **その callback はロックの外で実行される。**
   `event_scheduler.py:357` に「Lock を抜けた状態で callback を実行」とあり、実装もそうなっている。だから callback は他のロックを取りに行って待つことができる。
3. **会話の終了処理は、会話ロックを持ったまま DB へ書く。**
   `autonomy_wiring.py:817` で `conversation_lock` を取り、その中で `clear_open_conversation` → `_write_transition_line` → `cancel_conversation_timeout` を順に実行する。真ん中の `_write_transition_line` は `manager.add_building_event` を呼び、その実体は `manager/history.py:118` の `insert_building_message` — SQLite への実際の書き込みである。

つまり **単一の発火スレッドが、DB 書き込みの完了を待つあいだ、他の予約を一つも進められない**。

開始経路 (`user_conversation.py:730`) にも同じ構造がある。ただしこちらは発火スレッド上ではないので、波及するのは「そのペルソナへの同時発話」までに留まる。

## この構造が意図的でない根拠

同じモジュールの `user_conversation.py:192-197` が、まさにこの危険を名指しで戒めている。

> ⚠ ロックは**応答 (Pulse) を含まない**。Pulse は LLM 呼び出しを含む長い処理で、それをロックの中に置くと、EventScheduler の dispatch スレッド (沈黙タイマーの callback を同期実行する) が LLM の後ろで待たされ、他ペルソナの予約まで止まる。

戒めは Pulse (LLM 呼び出し) にだけ適用され、DB 書き込みには適用されていない。DB 書き込みは LLM ほど長くないので見逃されたのだと思われるが、止まる理由は同じである。

## なぜその場で直さなかったか (裁定が要る点)

素朴な直し方は「遷移の一行の書き込みをロックの外へ出す」だが、**それは別の並びを開く可能性がある**。

ロックの中で `clear` → `一行を書く` → `cancel` を一続きにやっているのは、途中で別の会話が開く隙間を作らないためである (`autonomy_wiring.py:814-816` のコメントが「照合してから落とすまでの間に別経路が閉じて新しい会話を開く窓を無くす」と明記している)。書き込みだけを外へ出すと、

- 会話 A を閉じた直後・一行を書く前に会話 B が開き、**B が開いている状態で A の終了の一行が書かれる**
- 一行の書き込みが失敗した場合の扱い (いまは WARNING で握って会話は閉じる) をロック外でどう保つか

といった点を決め直す必要がある。判断が割れるため、その場の修正にせず起票した。

## 選択肢 (未裁定)

- **A: 何もしない。** DB 書き込みは通常ミリ秒で終わり、実害の観測もまだ無い。「起きてから直す」
- **B: 書き込みを予約して、ロックを抜けてから実行する。** ロックの中では書く内容を確定させるだけにし、実際の書き込みはロックの外で行う。順序は保たれるが、失敗時の扱いを決め直す必要がある
- **C: 発火スレッドを 1 本から増やす。** 根を「単一スレッド」の側で断つ。影響範囲は EventScheduler 全体に及ぶので、本件より大きい判断になる

## 実機で見ること (実害の有無を先に測るなら)

沈黙タイマーの発火が集中する時間帯に、`[user-conv]` の「会話が閉じた」ログと、他ペルソナの予約の発火時刻のずれを突き合わせる。ずれが観測できなければ選択肢 A の根拠になる。
