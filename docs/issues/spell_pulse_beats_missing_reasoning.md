# スペル入りの複数 Beat の Pulse で、思考がチャット UI に表示されない

**ステータス: 実装済み・検証待ち (2026-09-19 起票 / 同日実装)**

## 症状 (まはーの実機観測、2026-09-19)

スペルを使う複数 Beat の Pulse で、思考部分がチャット UI に表示されない。
「単に思考をすっ飛ばして喋っている」のと区別がつかない。

## 実測 (eris_city_a の memory.db、読み取り専用で確認済み)

チャット UI の思考表示は、発言の保存時に metadata へ添えられた思考 (`reasoning`)
を画面が畳んで見せる作り (`api/routes/chat.py` の履歴復元)。直近ターンの実測:

| ターン | 形 | reasoning |
|---|---|---|
| 2026-09-18 21:29 (お風呂上がり) | 1 拍 | あり (196 字) |
| 2026-09-18 19:03 (ただいま) | 1 拍 | あり (327 字) |
| 2026-09-19 02:36 / 02:42 (ネコの話) | 1 拍 | あり (211 / 202 字) |
| **2026-09-19 09:00 (Elyth を見に行くスペル入り)** | **2 拍** | **1 拍目・2 拍目とも無し** |
| 2026-09-18 12:45 / 2026-09-19 02:45 | 1 拍 | 無し (別件の可能性、下の未解明点) |

## 原因 (一次特定)

事故ではなく、スペル経路が思考を記録に添えないまま温存されてきた。
`sea/runtime_llm.py:5206` に明記がある:

> spell 経路は従来から reasoning を載せていない（＝ 既存挙動を維持）。

つまりスペル経路の成立時から思考を運ばない実装で、その後の改修 (Beat ごとの
吹き出し分割など) でも「既存挙動の維持」として引き継がれてきた。

実害は表示だけではない: **記録に残らない以上、「生成されたのに捨てられた」のか
「そもそも思考しなかった」のかを後から誰も判別できない。**

## 調査結果 (2026-09-19、コード全経路の洗い出し)

**1. 思考は毎周モデルから届いている。runtime が拾っていないだけ (= 受け取って
捨てている)。** スペルループ (`sea/runtime_llm.py` `_run_spell_loop`) は周ごとの
LLM 呼び出しの後に使用量だけを回収し (`consume_usage`)、思考 (`consume_reasoning`)
は一度も取り出さない。クライアント側 (Gemini) は thought part を受け取って
バッファに格納しているが、次の周の呼び出しの頭でバッファごと上書き消去される。
回収されるのは周 1 の思考だけで、その取り出し点はループに入る前にある。
なお周 2 以降の思考も**生成中の実況としては画面へ流れている**
(`streaming_thinking` イベント) — どの記録にも残らないので、確定・再読込で消える。

**2. 発言を保存する経路は 16 本あり、思考の添え方が非対称。** 添えるのは
通常 1 拍系 (ストリーミング/非ストリーミング/SPEAK/SAY ノード) と
**非ストリーミングのスペル締め**のみ。添えないのは: スペルの中間 Beat
(建物 `_close_streaming_beat` / 記憶 `_store_memory`)、**ストリーミングの
スペル締め** (`runtime_llm.py:5206` の「従来から載せていない」)、native tool +
スペル (`:4759`)、早期 emit、中断の確定、死亡補填。同じスペル締めでも
ストリーミングだけ落とす非対称がある。

**3. 自律ターンは常に非ストリーミングなので、スペル入りでも締めに思考が載る
作りになっている。落ちるのはユーザーとの会話 (ストリーミング) だけ。**

**4. スペル無し 1 拍で思考が無かった 2 ターン (2026-09-18 12:45、2026-09-19
02:45) は、中断説を実測で否定した** (`_interrupted` 印なし)。両行とも metadata の
キー集合が {aspect, audience, llm_tokens, predecessor_message_id, tags} だった。

**4-a. その書き手を特定した (2026-09-19、実装時の調査)。別経路ではなく、
思考を運ぶ普通の 1 拍と同じ書き手だった。** 特定の根拠は 3 つ:

- 1 拍の発言を記憶へ書くのは `_finalize_beat` → `_store_beat_memory`
  (`sea/runtime_llm.py`)。この関数は metadata に思考と「言い切っていない」印しか
  入れず、どちらも無ければ `metadata=None` で `_store_memory` を呼ぶ。残る
  {aspect, audience, llm_tokens, predecessor_message_id, tags} は `_store_memory`
  自身が付ける欄で、**この署名は「思考が空だった 1 拍」そのもの**。
  `llm_usage` はもともと記憶側には入らない (建物の記録だけが持つ) ので、
  この行に無いのは異常ではない。
- 実測 (memory.db、読み取り専用): 同じ書き手を通った直近の 1 拍は、思考の有無で
  しか差が無い (`spell_seq` が NULL、`tags` は `playbook:track_user_conversation`
  のみ、`paired_action_text` なし)。スペルループの記憶書き込みは `spell_seq` と
  `conversation` タグが付くので、署名で区別できる。
- 建物側 (`saiverse.db` の `building_messages`、読み取り専用) でも同じ 2 ターンに
  `reasoning` が無い。建物と記憶の両方に無い = **その呼び出しがそもそも思考を
  返さなかった**回で、縮めた写しではない。

よってこの 2 ターンは本件の修正対象外 (直す欠陥が無い)。スペル入りの 2 拍
(2026-09-19 09:00) だけが本件の症状。

関連 intent (Beat の境界・quick_spell の終端・下書き行の確定) のどれも思考の
運搬には触れていない — スペル経路が思考を運ばないのは設計の裁定ではなく、
記録の無い惰性で通ってきたもの。

## 修正方針 (まはー GO 済み、2026-09-19 実装)

1. スペルの周回ごとに、使用量と同じ位置で思考も回収し、「次の Beat へ持ち越す」
   台帳 (使用量が既にやっている形) に載せて、**その Beat の建物の確定と記憶の
   書き込みの両方に添える**。
2. ストリーミングのスペル締めに思考を渡し、非ストリーミング側と対称にする。
   native tool + スペル、早期 emit も同じ扱い。
3. 中断の確定・死亡補填は対象外のまま (思考が確定していない場面)。
4. UI は建物履歴の metadata を読む既存の仕組みのままで表示が戻る想定。
   生成中の実況 (streaming_thinking) は現状どおり。
5. 上の 4 (思考を運ばない書き手の署名で書かれた 1 拍ターン) の書き手を特定し、
   同族なら同じ修正に含める。

## 実装の要点 (2026-09-19)

変えたのは `sea/runtime_llm.py` の 1 ファイル。運び方は使用量と同じ形に揃えた。

1. **周ごとの回収**: スペルループが再呼び出しの直後、使用量を回収するのと同じ
   位置で思考も回収する。回収した値は「次の Beat へ持ち越す」器に入り、
   その周の記録に載る (使用量の `pending_llm_usage` と同じ寿命)。
   ループの前に済ませた呼び出しの思考は、呼び出し元が引数で渡す。
2. **Beat が思考を持つ**: 1 Beat の本文を表す器 (`BeatSegment`) が、自分の
   使用量と並べて自分の思考を持つようになった。**どの Beat にどの周の思考が
   付くか**の対応づけはここで決まる。
3. **添え先は建物と記憶の両方**: 中間 Beat は下書き行の確定 (建物) と周ごとの
   記憶の書き込みの両方へ、締めの Beat は呼び出し元が組む metadata へ。
   ストリーミング / 非ストリーミング / native tool の 3 経路すべてで同じ形に
   揃えた (以前はストリーミングの締めだけが落としていた)。
   早期 emit (スペル実行と音声合成を並行させるために先に出す吹き出し) にも
   同じ思考を添える。
4. **空の周はキーを入れない**: 思考を返さなかった呼び出しの Beat には
   `reasoning` キー自体を入れない (既存の「空を空として落とす」流儀)。
5. **state の思考は毎回の呼び出しで置き換える**: 後段の memorize が読む state の
   思考は、LLM 呼び出しのたびに**置き換える** (足すのではなく)。思考があれば書き、
   空なら消す。空を空として確定しないと、思考を返さなかった呼び出しの Beat に
   前の呼び出しの思考が居残って誤帰属する — スペルの締めが思考なしで返った回
   (周 1 の思考が締めの発言に付く) も、同じ Pulse 内で別ノードの呼び出しが続く回も
   同じ形。格納の関数は 1 本 (`_store_reasoning_in_state`) で、スペルの有無で
   扱いを変えない。
6. **触っていない境界**: 中断の確定・Beat 死亡補填・MEMORIZE ノード。
   止められた回の思考は「その本文を言い切らせた思考」ではないため。
7. **受容した見た目 (2026-09-19 裁定)**: スペルの前の語りを先に出す吹き出し
   (早期 emit、自律ターン限定) と、その続きの 1 拍目の吹き出しには、
   **同じ呼び出しの思考が同じ値で並ぶ**。どちらもその呼び出しが生んだ本文
   なので事実としては正しい。実機で冗長に感じたら、先頭側だけに寄せる。

回帰は `tests/test_beat_segment_records.py` の第 8 節
(周ごとの対応づけ / 非ストリーミングの対称性 / 空の周 / 締めの Beat /
中断の確定は載せないまま) と第 9 節 (途中の Beat と早期 emit の say イベントの
トップレベルに思考が載る / 空の周は載らない)。state の置き換え意味論は
`tests/test_runtime_llm_helpers.py` と `tests/test_beat_finalize.py`
(前の呼び出しの思考が memorize / dual-write の両方に居残らない)。

  Beat ごとのメタデータの帰属の契約 (`archive/pulse_beats_merge_into_single_record.md`

- 2026-09-19 (敵対レビュー 2 巡目): 2 件を消し込んだ。① **途中の拍の思考が生の画面に
  出ない** — 画面の say 処理は `event.reasoning` (トップレベル) しか読まず
  `metadata.reasoning` を見ないので、中間 Beat と早期 emit の思考は記憶には残るのに
  画面には出ていなかった。締めの Beat と同じくトップレベルにも載せて揃えた
  (記録側は元から正しく、画面への載せ方だけの修正)。② **前の呼び出しの思考の居残り** —
  state への格納が「空を無視」だったため、思考を返さなかった呼び出しの Beat に前の
  呼び出しの思考が付きうる形が、スペル無しの経路に残っていた。スペル専用にしていた
  置き換え用の関数を廃し、格納を 1 本の置き換え意味論に統一して世代境界を一本化した。
- 2026-09-19 (敵対レビュー 3 巡目): 同族の残りを 1 件消し込んだ — **作業セッション
  (ペルソナの一人作業、`sea/work_session.py`) の初回 Beat と締めの生ログ**。周回の
  仕組みは会話と共有しているのに、初回の呼び出しの思考を回収せず、締めの書き込みにも
  渡していなかったため、「中間の周だけ思考付き」のちぐはぐな生ログになっていた。
  会話経路と同じ受け渡し (初回は回収して周回へ、締めは最終周の分を添える) に揃えた
  (回帰は `tests/test_work_session.py` の 2 本)。
- 2026-09-19 (同型の 3 例目、消し込み時に発見して修正): ストリーミングのスペル経路の
  中間 Beat が画面へ送る確定の say イベント (`_close_streaming_beat`、下書き行が
  作れなかった回の退避も) も、思考を metadata にだけ持ちトップレベルには持たなかった。
  この経路の生成中は `streaming_thinking` の実況が流れるが、Beat の切れ目の
  `streaming_discard` が実況ごと吹き出しを捨てるため、確定後の吹き出しから思考が
  消えていた — **ユーザーとの会話の本線経路で、まはーが最初に観測した症状の生の姿**。
  ①と同じくトップレベルにも載せて修正 (回帰は
  `tests/test_beat_segment_records.py` の streaming say イベントの 2 本)。
