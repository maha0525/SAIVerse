# スペル入りの複数 Beat の Pulse で、思考がチャット UI に表示されない

**ステータス: 調査中 (2026-09-19 起票)**

## 症状 (まはーの実機観測、2026-09-19)

スペルを使う複数 Beat の Pulse で、思考部分がチャット UI に表示されない。
「単に思考をすっ飛ばして喋っている」のと区別がつかない。

## 実測 (eris_city_a の memory.db、読み取り専用で確認済み)

チャット UI の思考表示は、発言の保存時に metadata へ添えられた思考 (`reasoning`)
を画面が畳んで見せる作り (`api/routes/chat.py` の履歴復元)。直近ターンの実測:

| ターン | 形 | reasoning |
|---|---|---|
| 2026-09-18 21:29 (お風呂上がり) | 1 拍 | あり (196 字) |
| 2026-09-18 19:03 (ただいま) | 1 拍 | あり (327 字) |
| 2026-09-19 02:36 / 02:42 (ネコの話) | 1 拍 | あり (211 / 202 字) |
| **2026-09-19 09:00 (Elyth を見に行くスペル入り)** | **2 拍** | **1 拍目・2 拍目とも無し** |
| 2026-09-18 12:45 / 2026-09-19 02:45 | 1 拍 | 無し (別件の可能性、下の未解明点) |

## 原因 (一次特定)

事故ではなく、スペル経路が思考を記録に添えないまま温存されてきた。
`sea/runtime_llm.py:5206` に明記がある:

> spell 経路は従来から reasoning を載せていない（＝ 既存挙動を維持）。

つまりスペル経路の成立時から思考を運ばない実装で、その後の改修 (Beat ごとの
吹き出し分割など) でも「既存挙動の維持」として引き継がれてきた。

実害は表示だけではない: **記録に残らない以上、「生成されたのに捨てられた」のか
「そもそも思考しなかった」のかを後から誰も判別できない。**

## 調査結果 (2026-09-19、コード全経路の洗い出し)

**1. 思考は毎周モデルから届いている。runtime が拾っていないだけ (= 受け取って
捨てている)。** スペルループ (`sea/runtime_llm.py` `_run_spell_loop`) は周ごとの
LLM 呼び出しの後に使用量だけを回収し (`consume_usage`)、思考 (`consume_reasoning`)
は一度も取り出さない。クライアント側 (Gemini) は thought part を受け取って
バッファに格納しているが、次の周の呼び出しの頭でバッファごと上書き消去される。
回収されるのは周 1 の思考だけで、その取り出し点はループに入る前にある。
なお周 2 以降の思考も**生成中の実況としては画面へ流れている**
(`streaming_thinking` イベント) — どの記録にも残らないので、確定・再読込で消える。

**2. 発言を保存する経路は 16 本あり、思考の添え方が非対称。** 添えるのは
通常 1 拍系 (ストリーミング/非ストリーミング/SPEAK/SAY ノード) と
**非ストリーミングのスペル締め**のみ。添えないのは: スペルの中間 Beat
(建物 `_close_streaming_beat` / 記憶 `_store_memory`)、**ストリーミングの
スペル締め** (`runtime_llm.py:5206` の「従来から載せていない」)、native tool +
スペル (`:4759`)、早期 emit、中断の確定、死亡補填。同じスペル締めでも
ストリーミングだけ落とす非対称がある。

**3. 自律ターンは常に非ストリーミングなので、スペル入りでも締めに思考が載る
作りになっている。落ちるのはユーザーとの会話 (ストリーミング) だけ。**

**4. スペル無し 1 拍で思考が無かった 2 ターン (2026-09-18 12:45、2026-09-19
02:45) は、中断説を実測で否定した** (`_interrupted` 印なし)。両行とも metadata の
キー集合が {aspect, audience, llm_tokens, predecessor_message_id, tags} で、
思考を運ばない書き手 (スペルループの記憶書き込みと同じ署名) を通っている。
どの経路がこの署名で 1 拍の発言を書くのかの特定は修正作業の中で行う。
UI が読むのは建物履歴の metadata なので、これらのターンが画面でどう見えて
いたかは建物側の記録で別途確認する。

関連 intent (Beat の境界・quick_spell の終端・下書き行の確定) のどれも思考の
運搬には触れていない — スペル経路が思考を運ばないのは設計の裁定ではなく、
記録の無い惰性で通ってきたもの。

## 修正方針 (案、まはーの GO 待ち)

1. スペルの周回ごとに、使用量と同じ位置で思考も回収し、「次の Beat へ持ち越す」
   台帳 (使用量が既にやっている形) に載せて、**その Beat の建物の確定と記憶の
   書き込みの両方に添える**。
2. ストリーミングのスペル締めに思考を渡し、非ストリーミング側と対称にする。
   native tool + スペル、早期 emit も同じ扱い。
3. 中断の確定・死亡補填は対象外のまま (思考が確定していない場面)。
4. UI は建物履歴の metadata を読む既存の仕組みのままで表示が戻る想定。
   生成中の実況 (streaming_thinking) は現状どおり。
5. 上の 4 (思考を運ばない書き手の署名で書かれた 1 拍ターン) の書き手を特定し、
   同族なら同じ修正に含める。
