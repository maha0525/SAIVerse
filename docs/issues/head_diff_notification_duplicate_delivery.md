# 部屋や持ち物の変化の知らせが、ペルソナに二回届くことがある

**ステータス**: 🔲 未解決 (2026-09-26 まはー判断: ケース 1 と 4 は直す、ケース 2・3 は受け入れて明記。ケース 1 と 4 は実装済みでレビュー中)
**深刻度**: 低〜中 — 実害は「同じ知らせを二回読む」ことで、知らせが消えることはない。四つのケースのうち、本番で起こりうるのはケース 1・2・4

**現在の状態 (2026-09-26)**:
- **直した**: ケース 1 (同時に調べた二つの処理が同じ変化を二回積む) とケース 4 (再起動後、読み込まれていないモデルの組の B が古いまま残る)。「比べる → 台帳に積む → B を進める」はペルソナ単位の通知ロックの中で一続きになり、B を進めるときは DB にだけある組も進める。
- **受け入れた残り**: ケース 2 (B の保存だけ失敗した後、その B が DB から読まれると一回重複する — 再起動のほか、DB にだけある組の保存が失敗した後にそのモデルへ切り替えたときも。後者は Codex 三巡目の指摘で、同じ失敗の別の現れとして受け入れに含めた)、ケース 3 (台帳なしの経路の部分失敗。本番では通らない)、ツールの書き込みから知らせまでの間に差分検知が先に来た回 (同じ出来事が二通りで届く)、新しいモデルの組が初めて撮られる瞬間との隙間 (再起動の直後に一回遅れて届く)。詳細は各節。

## 前提: 変化の知らせはどう届くか

ペルソナの周り (部屋に誰がいるか、持ち物、使えるスペル……) が変わると、SAIVerse は「〜さんが入室しました」「〜がインベントリに加わりました」のような知らせを作って、ペルソナの知覚に積む。ペルソナは次に考えるとき (Pulse) にそれを読む。

何を知らせればよいかは、「最後に知らせた時点の状態」と「いまの状態」を比べて決める。前者はコード上の名前が `last_notified` で、intent (C8) では **B** と呼んでいるので、この文書も B と書く。知らせを届けたら、B を「いまの状態」へ進める。こうして同じ変化を二度知らせないようにしている。

届け方は、実行台帳 (`execution_ledger` = 失敗しても再配送できるように、送る荷物を先に DB に記録しておく仕組み) の送り出し待ちの列に知らせを積む形。本番では台帳は必ずある (`saiverse/saiverse_manager.py:208` で常に作られる)。台帳が無いテスト用の環境だけ、知覚へ直接積む経路 (以下「台帳なしの経路」) を通る。

修正前は、「比べる → 台帳に積む → B を進める」の三つの手順が、途中で別の処理が割り込めない一続きの処理になっていなかった。以下の節は、起票時に確かめた四つのケース (ケース 4 はレビューで追加) を、修正前の挙動として記録したもの。

## ケース 1: 二つの処理が同時に同じ変化を見つけると、二回積まれる (本番で起こりうる)

**起きる場面**: ペルソナ P が考え始める瞬間 (Pulse の頭で変化を調べる) と、別のペルソナ Q が P のいる部屋へ入ってくる瞬間が重なったとき。Q が入室すると、SAIVerse は部屋にいる全員について変化を調べる (`saiverse/dynamic_state.py:148-161`)。

**なぜ起きるか**: P の Pulse は、P の思考を一本に並べるロック (Beat ロック) を持って走る。一方、Q の入室にともなって P のぶんの変化を調べる処理は、P の Beat ロックを取らない。この処理は Q の移動の配送として、Q 側のスレッドで走る。P の Pulse と Q の入室の処理の双方が同じ古い B から「Q さんが入室しました」を見つけ、それぞれ台帳に積み、それぞれ B を進める。台帳への登録には重複を防ぐ鍵 (`idempotency_key`) が無く (`sea/head_pipeline/integration.py:449`)、知覚側の重複排除は送り出し待ちの行ごとなので (`saiverse_memory/adapter.py:968`)、別々に積まれた二行はどちらも届く。

**裏取り**: 隔離したテスト (一時ファイルの SQLite + 合成の Section。本番のペルソナ・DB には触れていない。テストはリポジトリに入れていない一時のもの) で、二つのスレッドが変化を調べ終えてから台帳へ進むように揃えると、「Bが入室しました」が送り出し待ちに二行積まれた。

**同じ型の別の場所**: ツールの成功時に出す知らせ (`sea/head_pipeline/notify.py` — 記憶を書いたときの「コア記憶を更新しました」など) も、同じ時刻に別の処理が同じ Section の変化を調べると、ツール側の知らせと変化の知らせの両方が届く。こちらは文面が違う (ツール側は Section の全文を添える) ので、ペルソナから見ると「同じ出来事を二通りに知らされる」形になる。[beat_execution_context.md](../intent/beat_execution_context.md) §3.3 が「B を進めて二重通知を防ぐ」と約束している部分が、同時実行のときだけ破れている。

## ケース 2: B の保存だけが失敗して再起動すると、同じ知らせがもう一度届く (本番で起こりうるが、起きる場面は狭い)

**起きる場面**: 知らせを台帳に積む書き込みは成功し、直後の B の保存 (`sea/head_pipeline/pipeline.py:834` `_persist_last_notified`) だけが失敗し、B が保存し直される前にプロセスが再起動したとき。

**なぜ起きるか**: 知らせは台帳に残っている (再起動後も届く) のに、DB 上の B は古いまま。再起動後に古い B を読み込み、同じ変化をもう一度見つけて積む。

**失敗を無視しているのは、過去に記録された判断**: B を保存する関数 (`sea/head_pipeline/store.py:196`) の説明に「B の永続化失敗は fail-closed の対象外 (restart 後の再通知重複は自己限定的で、人格の欠損ではない)」と書かれている。出典は [2026-07-21 の引き継ぎ文書](../handoff/2026-07-21_w6_head_fail_closed_handoff.md) の「引き受ける残差」で、その文書の設計の節は「確定設計 (Fable 裁定)」となっている。docs/ の中に、この判断をまはーと合意した記録は見つからなかった。

**起きる場面が狭い理由**: B の保存が一度失敗しても、その後に同じペルソナで何か知らせが届けば、そのときに最新の B が全モデルの行へまとめて保存される (保存の直前に、メモリ上の最新の B を読み直すため)。head を撮り直したときも、そのモデルの行については最新の B が保存される。重複が出るのは、保存失敗のあと、そのペルソナに次の知らせが届く前に再起動した場合だけ。また台帳と B は同じ `saiverse.db` に書くので、台帳の書き込みが通った直後に B の書き込みだけ落ちるのは、一時的なロック待ちの失敗くらいしか考えにくい。

**裏取り**: 隔離したテストで B の保存だけを失敗させ、新しい pipeline に保存済みの状態を読み直させると (再起動の再現)、「Bが入室しました」が二回積まれた。

## ケース 3: 台帳なしの経路で一部の知らせだけ失敗すると、成功した分がもう一度届く (本番では通らない)

**起きる場面**: 台帳が無い環境で、知らせが複数あり、一つ目は積めて二つ目で失敗したとき (`sea/head_pipeline/integration.py:545-567`)。

**なぜ起きるか**: 一つでも失敗したら B を進めないので、次に調べたとき一つ目も含めて全部積み直す。

**本番への影響は無い**: 本番の manager は必ず台帳を持つので、この経路はテスト用の環境でしか通らない。C8 は台帳なしの経路について「次回の再検出に委ねる (at-least-once)」と書いていて、実装側の説明 (`integration.py:520-522`) には「push 済みラベルの再通知はあり得る」と明記してある。

**裏取り**: 隔離したテストで二つ目の積み込みだけ失敗させると、「Bが入室しました」が二回、「Cが入室しました」が一回届いた。

## ケース 4: 再起動のあと、読み込まれていないモデルの記録が古い B のまま残る (Codex のレビューで発見、2026-09-26 まはー判断で直す)

**起きる場面**: モデルを切り替えて使ったことのあるペルソナで、再起動のあと。B はペルソナとモデルの組ごとに DB に保存されていて、再起動後はそのときに使うモデルの組だけが DB から読み込まれる (`integration.ensure_snapshot` → `pipeline.load_from_store`)。知らせを届けたときに B を進めるのは、読み込まれている組だけ (`pipeline.advance_last_notified` が見るのはメモリ上の組だけ)。

**なぜ起きるか**: 再起動後、たとえば標準モデルの組だけが読み込まれた状態で「Q さんが入室しました」を届けると、標準モデルの組の B だけが進む。別のモデルの組は DB 上で古い B のまま残り、そのあとそのモデルでペルソナが考えるときに読み込まれて、同じ変化をもう一度見つけて届ける。保存の失敗が無くても起き、再起動のたびに、まだ読み込まれていない組の数だけ起こりうる。

**ケース 1 の修正とは別の原因**: ケース 1 の修正 (同時に調べる処理を並べる) では防げない。ケース 2 (保存失敗の直後の再起動) とも別で、C8 と perception_buffer §4.5 に書いた「例外は保存失敗を挟む再起動だけ」は、この形がある限り正確ではない。

**直し方 (まはー判断で採用)**: B を進めるときに、メモリ上の組に加えて、DB に保存されている同じペルソナの別モデルの組の B も、その Section の分だけ進める。あわせて、DB から組を読み込む処理も同じ通知ロックの中で行う — B を進めている途中に古い組が読み込まれて、進める前の B がメモリに入るのを防ぐため。

**残るごく狭い隙間 (受け入れ)**: B を進める処理が「メモリ上の組」を確定してから DB の他の行を進めるまでの間に、まだどこにも記録の無いモデルで初めて head が撮られると、そのモデルの新しい行の B が、撮ったばかりの値より少し古い「届けた時点の値」で上書きされることがある。メモリ上の B は正しいままで次の保存で書き戻るので、影響が出るのはこの隙間の直後に再起動した場合だけ。そのときも同じ知らせの二重ではなく、そのモデルで「撮った時点で知っていたことにした変化」が一回遅れて届く形になる。

## 直し方 (2026-09-26 まはー判断: 三つとも下の推奨どおり)

ケース 1 は下の提案どおりに実装した (`HeadPipeline.notify_lock_for`、回帰テスト `tests/test_head_diff_notify_serialization.py`)。ケース 2 は C8 と perception_buffer §4.5 に「再起動をまたぐときは、まれに一回重複する」を明記した。ケース 3 は既存の記述のまま。

**ロックでは閉じない形が一つ残る**: ツールが記憶などを書いてから、ツール側の知らせを出すまでのわずかな間に、別の処理の差分検知が先に同じ変化を見つけることがある。その場合は変化の知らせが先に届き、そのあとツール側の知らせも届く。ツール側の知らせは「何をしたか」と Section の全文を添える別の文面で、B を見ずに必ず出す作りなので、ロックの順番を揃えても防げない。ツールの書き込みそのものを同じロックに入れれば閉じられるが、ツールごとに書き込みの場所が違うので、変更がツール全体に広がる。起きるのはツールの書き込みと知らせの間の数ミリ秒に別のペルソナの入室が重なった回だけで、届くのは同じ出来事の二通りの言い方なので、今回は直さない。

以下は判断前に書いた提案 (記録として残す)。

**提案 (判断前)**

### ケース 1 — 直す (推奨)

ペルソナごとに「変化を調べて知らせを積む処理」を一本に並べるロックを置き、その中で「比べる → 台帳に積む → B を進める」を行う。後から来た処理は、前の処理が B を進め終わってから比べるので、同じ変化はもう見つからない。

- **ロックの中では配らない**: 台帳は、積んだ直後にその場で配る (`mark_applied(deliver=True)` が同じスレッドで配送まで行う)。配送は台帳全体で一本のロック (`_delivery_lock`) を取り、Q の入室の処理はそのロックを握ったまま P の変化を調べに来る。新しいロックを握ったまま配送に入ると、「Q の配送は P のロックを待ち、P は配送のロックを待つ」で固まる。だからロックの中では台帳に積むだけにして (`deliver=False`)、ロックを離してから配る。ロックを取る順序は「配送のロック → 新しいロック」の一方向だけにし、`pipeline.py:92` にある既存のロック順序の規約に書き足す。
- **ロックの単位はペルソナ**: B を進めるときはそのペルソナの全モデル分を進めるので、ロックもモデルではなくペルソナ単位にする。
- **三か所で使う**: 変化の知らせ (台帳の経路と台帳なしの経路の両方) と、ツールの成功時に出す知らせ (`notify.py`)。`notify.py` は Section の撮影もロックの中に入れる — 外で撮ると、古い撮影で B を進める余地が残る。
- **Beat ロックは使わない**: Beat ロックはその Beat が終わるまで握られるので、Q の入室の処理が P の思考の終わりまで止まってしまう。しかも配送のロックを握った状態で P の Beat ロックを取ると、Beat ロックの入口の検査が失敗する (`beat_gate.py:131-132`)。
- **プロセスの中のロックで足りる理由**: ペルソナは自分の City のプロセスにしか読み込まれない (`manager/persona.py:128` が所属 City で絞る)。同じペルソナの変化を二つのプロセスが調べることはないので、プロセスの中で並べれば足りる。Beat ロックも同じ前提に立っている。
- **重複を防ぐ鍵の案は採らない**: 台帳の登録に「どの変化か」から作った鍵を付ける案も考えたが、同じ人が出て行ってまた入ってきたときの正当な二回目の知らせまで消してしまう。部屋の様子の重複の issue ([entry_delivery_retry_duplicates_room_perception.md](entry_delivery_retry_duplicates_room_perception.md)) は鍵での解決を向いているが、あちらは「同じ配送の再試行」を一つにまとめる話で、鍵を配送 ID から作れる。こちらは別々の処理が同時に同じ変化を見つける話なので、配送 ID が二つあり、鍵では一つにならない。

### ケース 2 — 受け入れて文書に明記する (推奨)、または保存の再試行を足す

- **推奨: 受け入れる。** 重複は一回きりで、知らせが消えるわけではない。台帳と B を一つの書き込みにまとめれば完全に塞げるが、台帳と head の二つの仕組みを一つの書き込みで結ぶことになり、どちらの仕組みも単独では説明できなくなる。起きる場面の狭さに対して、その複雑さは見合わないと私は考える。受け入れる場合は、C8 と perception_buffer §4.5 (「どれで走っても正しく動く（基準 snapshot が進むので冪等）」) の両方に、「再起動をまたぐときは、まれに一回重複する」と書き足す。
- **代案: 再試行を足す。** B の保存に失敗したら「未保存」の印を付け、そのペルソナの次の Pulse の前に保存し直す。Pulse の前に head の保存を確かめる処理 (`ensure_persisted`) は既にあるが、見ているのは head の版だけなので、B の保存し直しは新しく足すことになる。起きる場面は「次の知らせが届くまで」から「次の Pulse まで」に縮むが、ゼロにはならない。

### ケース 3 — 受け入れる (推奨)

本番で通らない経路で、C8 と実装の説明に既に「少なくとも一回 (再通知はあり得る)」と書いてある。今回は直さない。
