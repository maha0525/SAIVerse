# 編纂まわりの並行性（pending の原子的 claim / 候補生成のスナップショット）

**状態**: 未着手（2026-08-05 に Codex レビューで発見・裏取り済み。輪の根治とは別件として切り出し）

## 症状（未観測・構造上の穴）

実機で観測された事故ではない。コードの形から可能な経路として指摘され、確認したもの。

## 何が起きうるか

`run_pending_plans`（`sai_memory/curation_ops.py`）は pending 一覧をロックの外で取得し、実行中を示す状態へ**原子的に取得（claim）していない**。起動側の `judgment_finalize` は pending が見えるたび背景スレッドを起こす。したがって、就寝判断の finalize が二度走る、あるいは再試行が重なると、同じプランを 2 つのスレッドが掴める。

そうなると次が起きる。

- merge: 消える側の本文が残す側へ二重に連結される
- split: 既存の子ページへ同じ段落が二重に追記される（2026-08-05 に「同名なら追記」を入れたので、この経路は今後増える）
- 完了したプランの状態を、もう一方のスレッドが failed で上書きする

## もう一つの顔: 候補生成が一貫したスナップショットでない

同じ「編纂まわりの並行性」の束。`detect_curation_candidates`（`saiverse/curation.py`）は、候補ページの一覧と木の形の索引を**別々の SELECT** で取る。その間にページの追加・親子移動が挟まると、木の形が古いまま統合候補が作られうる——「消える側は実際のページを親にも子にも持たない」という健全性規則が、古い形の上で判定される。

実行側は健全性を再判定しない設計（まはー裁定）なので、その候補が承認されればそのまま実行される。

窓は 2 つの SELECT の間で、書き手は Metabolism（entity_extractor の追記）と UI 操作。塞ぐには候補生成を adapter の共有ロックか単一 read transaction で包む必要があり、`detect_curation_candidates` が生の `conn` を受け取る現在の契約を変えることになる。

## 直す方向（案）

`pending -> running` を条件付き UPDATE で claim し、状態更新も CAS にする。`enqueue_plan` の check-then-insert にも一意制約か同一トランザクションを入れる。

関連する既存の知見: 実行台帳（`docs/intent/execution_ledger.md`）で「採番と公開は同一ロック区間」「CAS は書き込み時仲裁」を扱っており、同じ型の問題。設計をそちらに合わせられるはず。

## なぜ今やらないか

[編纂が同名ページを増やす輪](curation_duplicate_pages_loop.md) の修正中に発見したが、輪とは独立した既存の欠陥で、直すには claim プロトコルの設計判断が要る。スコープを混ぜない。
