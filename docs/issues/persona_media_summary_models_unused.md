## 何が起きているか

ペルソナ設定画面で要約モデルを選ぶと、値はサーバーに送られて DB の AI テーブルに保存され、起動時にペルソナ本体 (PersonaCore) の `vision_model` / `audio_model` / `video_model` に読み込まれる。ところが、この三つの属性の値を読むコードは、リポジトリのどこにも無い。

添付された画像・音声・動画の要約に使うモデルは、`saiverse/media_summary.py` の中で決まる。参照されるのはグローバル設定と、組み込みの既定モデルだけ。グローバル設定の値は画面の「モデルロール」タブで選ぶもので、実体は環境変数 `SAIVERSE_IMAGE_SUMMARY_MODEL` / `SAIVERSE_AUDIO_SUMMARY_MODEL` / `SAIVERSE_VIDEO_SUMMARY_MODEL`。そのため、ペルソナ設定で何を選んでも、要約の挙動は変わらない。一方で、ペルソナ設定の欄の空の選択肢には「グローバル設定を使用」と書いてあったので、何か選べばグローバル設定より優先されるように見えた。

`LIGHTWEIGHT_VISION_MODEL` は DB の列だけがあり、画面にも API にも出たことがない。

四つの列の値を読んでいたのは、テスト環境へペルソナを複製するスクリプトだけだった。値をテスト環境へ写し、その値が指すモデル定義ファイルも一緒に複製していた。要約の処理からは読まれていない。

## ペルソナの設定を要約に使う案を採らなかった理由

要約の文章は、元のファイルの隣に `〜.summary.txt` として 1 つだけ置かれ、どのペルソナもそれを読む。音声・動画の要約は、一度できたら作り直されない。画像の要約は、チャットに画像を添付したときや、グローバル設定の「アイテム概要の一括生成」を実行したときに、上書きされることがある。どちらの場合も、ファイルごとに 1 つであることは変わらない。

- **画像**: チャットに画像を添付したとき、一緒に送った文か直前のペルソナの発言があれば、添付の直後に、グローバル設定のモデルで画像の説明文が作られる (`api/routes/chat.py` の画像添付の保存処理)。この文は、アイテムの説明にも、要約 (`〜.summary.txt`) にも使われる。このとき参照されるモデルの設定はグローバル設定だけで、どのペルソナの設定も関わらない (直前のペルソナの発言は、内容の手がかりとして渡される)。
- **音声・動画**: 既定では、添付の時点では要約を作らない (グローバル設定の「添付したメディアの内容を自動想起に使う」が ON のときだけ作る)。要約が作られるのは、音声・動画を直接扱えないモデルで話しているペルソナの処理の中で、そのファイルが最初に必要になったとき。ここでペルソナの設定を使えば、その一回には効く。
- **どちらでも**: ペルソナの設定が効くのは、そのファイルの要約を最初に作ったときだけで、できた要約は他のペルソナも読む。ペルソナごとに確実に効かせるには要約をペルソナごとに分けて持つ必要があり、同じファイルの要約のための LLM 呼び出しが人数分かかる。画面に出るアイテムの説明と、ペルソナが読む要約も食い違う。
- **既存の設計**: 音声・動画の設計文書は、同じファイルが複数の会話・複数のペルソナで使われても要約の生成は 1 回で済むことを、守るべき条件 (C3) にしている。[docs/intent/stackchan_vessel.md](../intent/stackchan_vessel.md) では、Gemini 以外のペルソナ向けの書き起こしが必要になった場合も、ファイル単位の要約は変えず、ペルソナ単位の経路を別に設ける方針とされている。
- **ミラとテリス**: 二人の値は画像を扱えないモデルなので、ペルソナの設定を使い始めた瞬間から、二人の処理で作ろうとする画像の要約が失敗する。

## 決めたこと (2026-09-11、まはー)

まはーに次の二案を示した。

- (a) 要約に使うモデルを、ペルソナの設定、グローバル設定、組み込みの既定モデルの順に決めるようにつなぐ。
- (b) 使われていない欄と列を、画面・API・DB から外す。利用者から見ると、ペルソナ設定から三つの欄が消え、要約の挙動は誰についても変わらない。既存データでは、ミラとテリスの値が消える。DB から列を消すと、次の起動時の自動移行が DB を丸ごと作り直す方式になる、と添えた。
- `LIGHTWEIGHT_VISION_MODEL` は、(a) と (b) のどちらでも外すことを提案した。

まはーの返答 (原文のまま): 「うん、了解(b)でいこう。効いてないのは全く知らなかった。LIGHTWEGHT_VISIONについては外すで問題ないよ。」

決めた内容: ペルソナ設定の三つの欄と四つの列を、画面・API・DB から削除する。要約に使うモデルは、グローバル設定だけで選ぶ。ペルソナごとに別の要約モデルが要る場面が出てきたら、そのときに、要約を誰の分として持つかから設計し直す。

載せるバージョンについて、v0.3.12 に入れる案と次の版に回す案を示し、まはーが次の版を選んだ。まはーの返答 (原文のまま): 「次で！0.3.12はもう出してしまいたいから。」

## 既存データと移行

- 四つの列の値は、移行で消える。どの値も読まれていなかったので、挙動は変わらない。
- 載せるのは v0.3.12 の次の版。v0.3.12 には、廃止した列を `ALTER TABLE DROP COLUMN` でその場で落とす仕組み (`database/migrate.py` の `KNOWN_COLUMN_DROPS`、2026-09-09 に `user_settings` の二つの列のために追加) が入っている。v0.3.12 が develop に戻ったあとで、四つの列をこの一覧に登録してから PR にする。登録すれば、更新後の最初の起動で DB を丸ごと作り直さずに済む。
- 登録しないまま develop に入れると、次の起動時の自動移行は、列を足すだけの軽い方式 (`try_additive_migration`) では済まず、DB を丸ごと作り直す方式 (`migrate_database_in_place`) になる。この方式には二つの注意がある。
  - 2026-08-29 に、Windows で起動が落ちる不具合 (WinError 32) を起こしたことがある。その後、ファイルを移動する前に共有の DB 接続を手放す手当てが入っている。
  - プログラムの管理外の表を中身ごと消す穴がある ([full_rewrite_migration_drops_unmanaged_tables.md](full_rewrite_migration_drops_unmanaged_tables.md))。登録しても、SQLite が 3.35 より古い環境では、この方式に戻る。
- リリースのときに、バージョンごとの更新処理 (`saiverse/upgrade_handlers.py`) へ何もしない処理を足す場合、既存の例に倣って説明に「データ移行なし」と書くと、このバージョンについては正確でない。更新処理の中で何もしなくても、起動時の自動移行で列が消えるため。
- 読まれない列の削除は、後の片付けにまとめて先送りした例 (`METABOLISM_ANCHORS`、`persona_task.note_id`、`MEMOPEDIA_INDEX_LIMIT`) と、すぐに削除した例 (2026-07-14 の `ACTIVITY_STATE` と `SLEEP_ON_CACHE_EXPIRE`、2026-09-04 の `METABOLISM_LOW_CHARS`、v0.3.12 で削除した知覚の上限用の二つの列) の両方がある。今回は、画面に効かない欄を出していたことが問題なので、欄と一緒に列も削除する。

## 三つの原因

- **技術的な直接の原因**: 5/18 の設計文書ではペルソナ単位の読み込みが設計されていたが、環境変数から先だけを実装した時点で完了とされ、先送りは改訂履歴にだけ書かれた。その後、6/21 に画面の欄が、6/23 に保存の処理が足されたが、要約処理のコードは変わらなかった。
- **判断の誤り**: 「保存した値をもう一度取り出せる」ことを、設定が完成した証拠として扱った。6/23 の修正は保存時のエラー (TypeError) が消えたところで止まり、8/12 に足されたテストでも、保存した値をもう一度取り出せることだけが検査された。選んだ値で挙動が変わるかを確かめた変更は一つも無い。
- **それを通した条件**: 保存される設定値について、その値を読むコードがあるかを確かめる仕組みが無い。加えて、設計文書の本文が、先送りした設計を実装済みの書き方のまま残していたので、後から読んだ人には、ペルソナの値が使われる前提に見えた。

**同じ形の前例** (別の仕組みで起きた、値を読むコードの無い設定): `SLEEP_ON_CACHE_EXPIRE` (自律行動。DB の列だけがあって本体のコードから読まれず、2026-07-14 に削除) と、自律会話モードの画面の切り替えと `global_auto_enabled` (値を読むコードが無く、2026-09-01 に削除)。どちらも `docs/overview/landscape.md` §9 の表に載っている。三件とも、「保存と読み込みの処理の外に、値を読むコードがあるか」を確かめていれば見つかる形をしている。同じ形でまだ残っているものに、AI テーブルの `MEMOPEDIA_INDEX_LIMIT` (2026-07-14 から、読むコードが無いまま列だけ残してある。画面と API には出ていない) がある。

**この変更で入れる再発防止**: 無い (削除だけ)。設定の列ごとに値を読むコードがあるかを確かめる自動テストは考えられるが、形はまだ決めていない。現時点では、この文書の記録にとどまる。
