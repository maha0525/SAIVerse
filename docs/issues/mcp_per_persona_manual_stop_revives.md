# per_persona の MCP サーバーは手動停止しても次の Pulse で自動復活する

**ステータス**: 未着手 (低優先度 — まはー裁定 2026-08-10: 停止機能をほぼ使わないため実用上の実害が浮上しない)

## 何が起きるか

アドオン管理 UI から per_persona スコープの MCP サーバーを手動停止しても、そのペルソナが次に Pulse を打った時点で接続が張り直される。ペルソナが活動している間は、停止が数分しか持たない。

現状 per_persona スコープを使っているのは Elyth アドオン (`saiverse-elyth-addon__elyth`) 一つ。

## なぜそうなるか (仕様の帰結であって配線ミスではない)

`docs/intent/mcp_addon_integration.md` §I で、ツール一覧の真実を「そのペルソナ自身の鍵で張った生きた接続」に置いた。Pulse の頭は「接続が無ければ張る」ので、停止という状態を覚えていない限り、次の Pulse が張り直す。

旧設計 (起動時に一度だけ検出し、接続は最初のツール呼び出しで作る) では、手動停止は「次にそのペルソナがツールを呼ぶまで」持った。停止の寿命が「ツール呼び出しまで」から「次の Pulse まで」に縮んだのがこの差。

現在の案内は「止めたければアドオンを無効化する」(無効化はサーバー定義ごと降ろすので、取得の対象から外れる)。

## 何を決める必要があるか

「一時的に止める」に意味を与えるなら、停止は接続の有無ではなく**意図として記録**する必要がある (停止フラグを持ち、Pulse 頭の取得がそれを尊重し、UI から解除できる)。器の候補は失敗記録 (`_failed_instances`) と参照カウント (`_refs`) の隣。

決める前に問うべきこと:

- そもそも per_persona サーバーの「一時停止」に用途があるか (デバッグ時の切り離し? 課金の一時停止?)。用途が無いなら、UI から per_persona の手動停止ボタンを外す方が正直で、機構を増やさない。
- 停止の寿命は誰が決めるか (無期限 / 次の起動まで / 時限)。無期限ならアドオン無効化と何が違うのかを説明できる必要がある。

## 実害の見立て (2026-08-10)

- 停止が効かないことによる **外部への予期しない送信は無い** — 接続を張れるのは鍵が解決できるペルソナだけで、鍵が消えていれば `connect()` の関所が止める。
- 停止が効かないことによる **課金**: Elyth 側の API 呼び出しはペルソナがツールを呼んだときだけ発生する。接続の維持自体に課金は無い (remote HTTP の接続確立と `tools/list` のみ)。
- よって残るのは「UI の停止ボタンが期待どおり効かない」という体験の齟齬。
