## 症状

実機 `aifi_city_a` の Memopedia に「AI研究と技術的検証」というページが 3 枚できていた（まはー発見 2026-08-05）。同名の重複は他にもあり、生存ページで 6 種・余剰 7 枚。

## 何が起きていたか（実データ）

同名ページは実際には **5 枚**作られていた。すべて毎晩 2 時の編纂（`edit_source=curation`）による。

| ページ | 生成日 | 生成経路 |
|---|---|---|
| m:624 | 07-16 | 「まはー」ページ（m:25）の分割 |
| m:633 | 07-17 | 同上（08-01 に m:624 へ統合され閉架） |
| m:640 | 07-18 | 同上（08-02 に m:624 へ統合され閉架） |
| m:667 | 07-25 | 同上（08-05 に m:624 へ統合され閉架） |
| m:668 | 08-03 | **m:624 自身の分割**（親と同名の子） |

輪の形:

1. 人物ページが肥大する（entity_extractor の追記、および下記 3 の吸い戻し）
2. 肥大検知で分割される。LLM は**既存の子ページを一切知らされない**まま、目の前の文章だけで分類軸を立てる（[`curation_ops.py` の `plan_split` プロンプト](../../sai_memory/curation_ops.py)）
3. 同じ人物についての文章なら、内容が違っても立つ軸は同じになる。分割は子を**新規作成しかしない**ので同名ページが横に増える
4. 類似検知の「タイトル包含」で、分割の子が親や別の人物ページへ吸い戻される（子の名前は必ず親の名前を含むので構造的に毎回起きる）。親が再び肥大して 2 へ戻る
5. 同名の重複を統合すると残す側が太り、5,000 字を超えて分割候補になる。中身が単一テーマだと LLM は自分と同じ名前の子を 1 枚だけ作る（m:668）

**重複ページの中身は互いに別物だった**（共通行ゼロ）。「同じ文章を再分割していた」のではなく、**違う文章から同じ軸が立っていた**。したがって統合は重複の解消ではなく、別の話を同じ名前の袋に入れる操作になっていた。

## 三つの原因

- **技術的原因**: 分割が既存の子ページを見ておらず、新規作成の経路しか持たない。統合の候補生成が操作後の状態（結果の文字数・木の形）を見ていない
- **判断の失敗**: 2026-07-14/15 に同型の事故（m:34 が全ブロックを 1 枚の子へ流し、毎晩入れ子が深くなる）を修正した際、**LLM の応答の質を上げる方向**（`child_pages` 先行宣言）で対処し、同名の子を作れてしまう構造自体は残した。質の改善は保証にならない
- **系の条件**: 保存則（本文が失われない）の機械検証はあるが、**操作が棚を改善したかを見る検査が無い**。保存則が成立している限り「完了」と報告されるため、輪が回っていること自体が通知から見えなかった（7/14 の事故と同じ盲点）

## 裁定された規則

正典は [`concept_consolidation.md`](../intent/concept_consolidation.md) の「編纂の健全性規則（まはー裁定 2026-08-05）」。要約:

- 統合で消える側になれるのは、実際のページを親にも子にも持たないページだけ
- 統合した結果が肥大するなら候補にしない
- 分割候補のページは統合の候補から外す
- 同じ残す側を使う統合は一晩 1 件
- 分割で作る子の名前が既存の兄弟と同じなら、新規作成せず追記
- 分割で作る子の名前が親と同じなら、その子は作らない（子 0 枚の分割は失敗でなく「変更なし」）
- fold（過小ページを親へ畳む）は機構ごと撤去

### 追加巡（2026-08-06、Sol・コミット後の一巡）

**統合が吸収側の Fragment を想起不能にしていた（high、修正済み）**: `execute_merge` は本文の連結とキーワード・metadata の和集合だけで、Fragment の付け替えを持たないまま吸収側を soft-delete していた。Fragment の想起可視性は親ページの生存に従う（`unified_recall._FRAGMENT_VISIBILITY_*`）ため、吸収側の Fragment は DB に残ったまま keyword / embedding 検索から恒久的に消える。intent（本文→Fragment）は当初から「統合＝Fragment の所属替え」と書いており、コードが追いついていなかった。統合トランザクション内で `entity_id` を survivor へ付け替え、旧親タイトル込みで生成されていた embedding は削除して再生成経路（`embed_memopedia_fragments`）へ載せる形で修正。統合後も Fragment が通常想起に出る回帰テストを追加した。なお本番 aifi は編纂を巻き戻し済みのため、この穴による実害は残っていない。

## 同じ穴を持っていた別経路 → 削除済み

`scripts/maintain_memopedia.py` の `run_split_large` は編纂とは**別の分割実装**で、`create_page` を直接呼ぶため同名の子を作れた（今回の規則が届かない）。さらに、この経路は LLM に子ページの**本文そのものを生成させていた**（`sec["content"]` をそのまま保存）——2026-07-11 に確立した本文保存則（編纂は本文を生成しない、移動と結合のみ）に違反する。

- 4 操作すべてに後継があるか役目を終えている: split-large / merge-similar → 編纂（P4-a）／group-shallow → P4-b 命名／fix-markdown → 過去のバグ（literal `\n` の混入）の後始末で、**全ペルソナ 3,214 ページを検査して書き換え対象 0 枚**

## 残っている宿題
