# スペル結果・部屋の様子は生まれる時点の文量が多すぎる

**ステータス**: 未着手 — 2026-09-09 まはー提起
**深刻度**: 中 — 送る量の膨張の供給側の根。入った後の節約（intent presented_context_reduction）だけでは、生まれる量そのものは減らない
**起票**: 2026-09-09
**関連**: [presented_context_reduction.md](../intent/presented_context_reduction.md)（入った後の節約 — 本件はその手前、入る前の絞り）/ [room_items_uncapped.md](room_items_uncapped.md)（アイテム個数上限 — 隣接の別裁定）/ [watermarks_unsatisfiable_when_perception_is_large.md](watermarks_unsatisfiable_when_perception_is_large.md)（供給側の事実の初回調査 2026-09-04）

## 問題

送る量の絞り込みの議論（2026-09-09）でまはーが指摘した、コンテキストに**入る前**の問題。スペル結果や部屋の様子は、生まれる時点の文量がそもそも大きい。

- スペル結果は切り詰め無しの全文が機構名義の行として保存される。実測: 3 件で 18,010 字（2026-09-04 エリス）。
- 部屋の様子は「アイテムの説明つき全文 + 画像」が単位。再訪の差分化（2026-09-05 実装）で再訪分は縮んだが、初訪・全文の単位の大きさは変わっていない。

コンテキストに入った後の節約（intent 側）とは**完全に別に**、供給側の文量を絞る調整が要る（まはー 2026-09-09）。

## 方向の種（未裁定）

- アイテム個数上限（room_items_uncapped、新 feature ブランチの裁定済み）は供給側の絞りの隣接裁定で、入れば部屋の様子の単位が直接減る。
- スペル結果の上限や要約は、「黙って切り詰めない・縮めたことが分かるように示す」原則（2026-09-04 裁定の系譜）との整合を設計してから。2026-09-09 まはー裁定: 「今回はどうしようもない、今は何もできない。後回しで」— presented_context_reduction のリリースには含めず、本 issue が持つ。
