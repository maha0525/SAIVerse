## Beat の一生 (ストリーミング会話の場合)

会話の応答を作る Beat は、時間軸で見ると七つの区間を順に通る。コード位置は
`sea/runtime_llm.py` の `lg_llm_node`。

| 区間 | 何をしている時間か | 目印 |
|---|---|---|
| A 順番待ち | Pulse がキューにいて、Beat がまだ始まっていない | `PulseController` |
| B 支度 | node に入り、プロンプトを組み立てている。下書き行はまだ無い | node 頭の取り消し点 (`:3150`) |
| C 思考 | LLM ストリームの前半。reasoning が流れ、本文はまだ一文字も無い | 下書き行は発番済み (`:3892`) |
| D 本文 | LLM ストリームの後半。本文の断片が画面と音声へ流れている | `_consume_pipeline_stream` |
| E 完了処理の入り口 | ストリームは流れきり、スペルラウンドを回している | `_run_spell_loop` (`:4027`) |
| F 確定後の隙間 | 下書き行は本文で確定済み。だが記憶への書き込み (memorize) はまだ | `:4207` 確定 → `:4439` `_finalize_beat` |
| G Beat 完了後 | 記憶まで書き終え、次のノードへ | — |

## 区間 × 原因の表

「画面」「建物の記録」「本人の記憶」「再開手段」の四つがどうなるかを、原因別に並べる。
✅ = 設計どおりに揃う。🕳️ = 穴。コードを読んで確認した事実には (コード確認)、
実機で見た事実には (実機確認) を付ける。無印の推測は残していない。

### 原因 1: ユーザーの停止

| 区間 | 何が起こるか | 判定 |
|---|---|---|
| A・B | 何も書かれていないので、何も残らない。画面は静かに止まる | ✅ 消えるものが無い |
| C 思考中 | 下書き行は空文字で確定 (発言消滅は防がれる)。通告・印・記憶は無し (8/26 裁定「一言も出ないうちに止められた回は何も語らない」のとおり)。**ただし画面には思考の吹き出しが浮いたまま残り、リロードすると消える。そして再開手段が無い** — 本文ゼロなので「続きの生成」は成立せず、ユーザーの吹き出しに「再送」も出ない | 🕳️ **穴 1** (実機確認 2026-08-27) |
| D 本文中 | 部分文で確定 + 印 + 記憶 + 通告 + その場で「続きの生成」 | ✅ (実機確認 2026-08-27) |
| E 完了処理の入り口 | スペルラウンドの頭で取り消しが立ち、Beat の出口の後始末が D と同じ形に揃える | ✅ (2026-08-27 実装。単体テストのみ、実機は未) |
| F 確定後の隙間 | この区間に停止の割り込み点が無い (次の取り消し点は次ノードの頭で、記憶の書き込みはその前に終わる)。発言は完全に残る | ✅ (コード確認) |

### 原因 2: 例外 (LLM エラー等) で Beat が死ぬ

| 区間 | 何が起こるか | 判定 |
|---|---|---|
| A・B | 何も書かれていない。エラーはイベントで画面に届き、ダイアログ + ユーザーの吹き出しに「再送」 | ✅ (束 2 の出口 3) |
| C 思考中 | 下書き行は空文字で確定 (静かに)。その後エラーイベントが届いて「再送」が出る。浮いた吹き出しの問題は停止と同じ | ✅ 再開手段はある (コード確認) |
| D 本文中 | 途中経過の器から部分文を回収して確定 + 印 + 記憶 + 原因を書かない通告。エラーイベントも別に届く | ✅ (2026-08-27 実装。狙って踏めないため実機は未) |
| E 完了処理の入り口 | D と同じ。ただし**スペルの retry 中の途中死**だけは、retry 分の部分文が spell loop の降格契約に吸われて記録に残らない (既知・[orphaned_streaming_placeholder_cleanup](orphaned_streaming_placeholder_cleanup.md) の 2 巡目見送り) | ⚠️ 既知の限定 |
| F 確定後の隙間 | **確定済みなので出口の後始末はスキップされ、memorize はまだ走っていない。建物の記録には全文が残るのに、本人の記憶には残らない** — 「世界には刻まれたのに本人だけが覚えていない」が、逆向きの窓でまだ開いている。窓は狭い (確定からの数十行: 完了イベント送出・メタデータ組み立て・`_finalize_beat` 冒頭) | 🕳️ **穴 3** (コード確認) |

## 別経路 — 上の表に乗らないもの

### tool-streaming 経路 (ツールを持つ playbook の応答)

この経路には下書き行が無く、停止フラグ (`cancelled_during_stream`, `:3449`) を立てた後、
**誰もそのフラグを読まない** (コード確認)。停止で break した後の流れはそのまま続き、
途中までの本文が `_emit_say` で**言い切った発言として**記録される — 印なし・通告なし・
「続きの生成」なし。ユーザーは止めたのに、発言は完成の顔で世界と記憶に載る。
pipeline 経路の「印が無い」(既知) より一段悪い: **停止の意図そのものが握り潰される**。
実機では未確認 (まはーが踏んだのは pipeline 経路のみ)。 → 🕳️ **穴 2**

### 非ストリーミング経路 (response_schema 付き / streaming 無効)

「途中まで」という概念が無く、本文は全部か無かのどちらか。停止してもブロッキングの
LLM 呼び出しは打ち切れず、完走後に次の取り消し点まで進む。**取り消し点に届く前に
say と memorize を通るのか、その場合 cancelled 後のイベントを画面が捨てて「発言が
世界に残るのに画面に出ない」形になるのか — ここは未確認** (コードを最後まで辿って
いない)。 → ❓ **要確認 4**

### 下書き行の発番自体が失敗した回との複合

`_emit_speak_start` が失敗して下書き行が無いまま本文が流れ、その途中で Beat が死ぬと、
出口の後始末は対象を持たず (msg_id 無し)、正常完了時の救済 (`_emit_say` フォールバック
`:4227`) にも届かない — 流れた本文が失われる。発番失敗自体が稀 (ログに ERROR が残る)
なので優先度は低い。 → 🕳️ **穴 5** (コード確認・稀)

## 穴の一覧 (裁定待ち)

1. **思考中の停止は、出口 5 の顔をした出口 3** — 「ユーザーが止めた」(出口 5) の扱いで
   静かに閉じるが、実態は「応答がまだ生まれていない」(出口 3) と同じで、部分文が無い。
   出口 5 の操作 (続きの生成) は成立せず、出口 3 の操作 (再送) も出ない。**再開手段の
   不在は 8/26 裁定の射程外** (裁定は記録に何を書くかの話だった)。加えて、思考の
   吹き出しが浮いたまま残り、リロードで黙って消える — 見かけと実態の食い違い。
2. **tool-streaming の停止が握り潰される** — 部分文が言い切りとして確定する。
3. **確定後の隙間の例外で、記憶だけ欠ける** — 窓は狭いが、開いていることはコードで確認。
4. **非ストリーミングの停止の挙動が未確認** — 辿り切っていないことを辿り切っていないと書く。
5. **発番失敗との複合** — 稀。記録のみ。
