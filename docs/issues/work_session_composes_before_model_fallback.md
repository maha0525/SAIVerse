# 作業セッションが、実行 model の確定前に model 依存の組成を済ませてしまう

**ステータス**: 🔲 未解決 (起票のみ — 発生は劣化経路限定、修正は独立案件)
**深刻度**: 中〜低 — 発火条件が「軽量 LLM クライアントの生成失敗」という設定破損系の劣化経路に限られる
**発見**: 2026-09-06、部屋の様子のパッケージ再設計の Codex レビュー三巡目。**この再設計が作った穴ではない** — 読み戻し (per-model の窓・水位) の頃からある既存の順序で、2026-09-06 に MCP 更新と部屋の検知へ model の配線を増やしたことで影響面が広がって見えた
**関連**: [room_state_packages.md](../intent/room_state_packages.md) (v0.3.9 の再設計 — 本 issue はその束の外)

## 何が起きるか

作業セッション (`sea/work_session.py`) は、読み戻し (`maybe_run_window_refill`)・MCP 更新・コンテキスト組成 (`_prepare_context`) を `execution_context.model_key` (軽量 model) で実行した**後**に、LLM クライアントの選択 (`select_llm_client`) を呼ぶ。クライアントの選択には失敗時の切り替えがあり (`sea/runtime.py:619-632` 付近)、軽量クライアントの生成に失敗すると `persona.llm_client` / `persona.model` (通常 model) へ落ちる。

この切り替えが起きた回は、**組成に使った model と実際に呼ぶ model が食い違う**: 窓 (anchor)・記憶整理の水位・MCP の既読通知・部屋の様子の検知 (2026-09-06 以降) は軽量 model の身分で決まっているのに、送信は通常 model として行われる。per-model の状態 (窓の起点・既読) が別 model の名義で進む。

## 原因の構造

「組成 → クライアント確定 (失敗なら別 model へ)」の順序そのもの。組成が model 依存になった時点 (読み戻しの per-model 化) からこの形で、後から model 依存の処理が増えるたびに影響面が広がる。

## 修正の方向 (着手時に設計)

- クライアント/model の選択と失敗時の切り替えを**先に確定**してから、model 依存の組成 (読み戻し・MCP 更新・組成・部屋の検知) を実行する。
- 順序を変えられない事情があれば、切り替え発生時に model 依存の組成をやり直す。
- テスト: 軽量クライアントの生成失敗を注入し、全入口が切り替え後の model を受け取ること。
