# Issue: NaN や無限大を含むベクトルが、検査を通り抜けて検索に出なくなる

**ステータス**: 🔴 未着手
**優先度**: low
**作成日**: 2026-11-22
**関連**: [記憶の検索用のベクトルの保存形式を変える](../intent/vector_binary_storage.md)

## 背景

記憶の検索用のベクトルの保存形式を変える変更 ([設計の文書](../intent/vector_binary_storage.md)) の敵対レビュー (Codex、七巡目) で見つかった。Codex は、この欠陥が変更の前からあることを確かめている。

## 何が起きるか

保存されたベクトルの中に、NaN (数として表せない値) や無限大が一つでも入っていると、次のようになる。

- 起動時の検査と、再計算の完了の判定は、値の型と長さだけを見る。そのため、この行を「正常なベクトル」と判定する。再計算の警告は出ず、再計算をしても作り直されない。
- 検索では、この行の類似度が NaN になる。NaN はどのしきい値との比較でも成り立たないので、その記憶は思い出されない。

変更の前 (JSON 形式) も、検査は配列の長さだけを見ていたので、同じことが起きていた。JSON 形式の `[NaN, 1.0]` のような行は、変換のときに数値の配列として受け入れられ、同じ値を持つバイト列形式の行になる。

## 起きる条件

埋め込みモデルが NaN や無限大を出力したとき、または `memory.db` を外から書き換えたときに限られる。通常の動作でこの値が保存された例は、確認されていない。

## 直すなら

- 保存するとき (`sai_memory/vector_codec.py` の `encode_vector`) と、変換するとき (`sai_memory/embedding_migration.py` の `convert_json_vectors`) に、有限でない値を含むベクトルを受け付けない。
- 既に保存されている行は、値を読まないと判定できない。SQLite の中の型と長さだけでは見分けられないので、起動時の検査に入れると、全行の値を読むことになる (4.5 万行で約 0.2 秒の読み込みが、起動のたびに増える)。検査に入れるか、再計算のときだけ調べるかを決める必要がある。

## 今回直さなかった理由

保存形式の変更が約束しているのは、「検索の結果が変更の前と変わらないこと」と「変更で新しく記憶が検索に出なくなる経路を作らないこと」。この欠陥は変更の前からあり、変更で悪化していない。敵対レビューは巡を重ねるたびに守る範囲を広げる指摘を出すので、変更の前からある欠陥は、ここに記録して別に扱う。
