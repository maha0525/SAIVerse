# 会話コンテキストの文字数勘定が、送信直前に差し込まれる行を数えていない

**状態**: 実装済み・検証待ち (2026-09-02 実装。実機 (エリス) での数字合わせが残る)
**起票**: 2026-09-02 (v0.3.2 リリース直後。konoe さんの「畳んでもコンテキストが減らない」報告の根本原因調査で発見)

## 症状

ペルソナ設定の「整理を始める文字数 / 整理後に残す文字数」が数えている窓と、実際に LLM へ送られる会話履歴が大きく乖離する。

本番エリスでの実測 (2026-09-02、context-status とコンテキストプレビューを同時刻で突き合わせ):

| | 字数 |
|---|---|
| 勘定 (presented_chars = 水位判定・整理・データ送信量の管理の表示が使う値) | 149,856 字 |
| 実際に送られる履歴 (プレビューの history セクション、166 通) | 209,031 字 |
| 差 | **+59,175 字 (実送信は勘定の 1.4 倍)** |

差の内訳 (実測):
- 部屋の様子 (消費済み知覚バッチ、W14): 47,827 字 (3 通、最大 1 通 19,859 字)
- [システム通知] 等の差し込み・整形分: 約 11,300 字 (出どころの行単位の内訳は未確定)
- 時刻アンカー: 49 字

履歴全体の種類別内訳 (エリス、参考):

| 種類 | 通数 | 字数 | 割合 |
|---|---|---|---|
| スペル結果 | 16 | 73,624 | 35% |
| ペルソナの発言 | 71 | 64,814 | 31% |
| 部屋の様子 (知覚) | 3 | 47,827 | 22% |
| その他のシステム通知など | 35 | 19,381 | 9% |
| ユーザーの発言 | 40 | 3,336 | 1% |

## 由来 (意図した設計ではない)

文字数の勘定 (`sea/eviction_plan.py::message_chars` が数える提示ウィンドウ) は**保存済みの本線メッセージ**から組まれる。一方、知覚バッチは保存行を作らず (perception_buffer.md §10.1)、`sea/runtime_context.py` の `_merge_consumed_perceptions` が**送信直前に履歴へ差し込む**。差し込む場所が数える場所より後ろにあるため、数える係の目に一度も入らない — 「報告文は 0 字換算」と誰かが決めた設計ではなく、配管の並びの結果。

帰結として:
1. 「データ送信量の管理」は実送信より小さい数字を表示する (透明性の看板に対して嘘)。
2. 整理 (畳み) が減らせるのは勘定内の会話だけで、報告文の山は畳んでも残る。ユーザーが「残す文字数」を下げても送信量がほとんど減らない — konoe さん報告 (v0.3.1、畳み成功後も Conversation History 187K トークン) の説明になる (konoe さんの構成の実測は診断拡充後の再提出待ち)。

## まはー裁定 (2026-09-02)

> 整理を始める文字数を設定する目的は、送るトークンを多くしすぎないため。その意味で同じ 1 トークンを会話か報告文かで分ける意味はない。区別が意味を持つのはあらすじを作るところだけ (報告文は生成時の提示で省略され得るので、材料の量として別に見る必要がある)。通常の会話文脈で別々に見る必要はなく、まして 0 字換算はあり得ない。

**方針: 水位判定・整理の発火・「データ送信量の管理」の表示が使う文字数勘定を、「実際に送る中身の合計」に揃える。**

## 設計の追い掛け (実装時に必ず検証)

- 報告文を勘定に入れると水位超過の発火が増える。そのとき**整理が報告文も実際に減らせる**ことが要る — 減らせないと「発火し続けるのに目標に届かない」空回りになる。仕組み上は「あらすじがその期間を覆うと知覚バッチに退場付記 (annexed_entry_id) が付いて提示から下りる」形だが、**手動整理 (畳み) の経路でこの印が付くかは未検証**。
- §15 読み戻し (refill) の目標量も同じ勘定を使うため、勘定の変更は読み戻し量にも波及する。両側を同じ物差しに揃えること。
- 差分の約 11,300 字 (通知・整形分) の出どころを行単位で確定させ、数えるべきものと数えなくてよいもの (例: 揮発の時刻アンカー 49 字) の線を引く。

## 実装 (2026-09-02)

- **組成の一点化**: 知覚ブロックを組む規則 (未付記バッチの取得・Chronicle 無効ペルソナの窓絞り・`<system>` 包み・metadata) を `sea/runtime_context.py::list_presented_perception_blocks` へ切り出し、時系列マージを `merge_perception_blocks` に分けた。送信経路 (`_merge_consumed_perceptions`) はこの二つを繋ぐだけになり、**測る側も同じ関数を呼ぶ**。ブロックの目印 (`__consumed_perception__`) は純関数モジュール側 (`sea/eviction_plan.py::CONSUMED_PERCEPTION_KEY` / `is_injected_perception`) が持つ。
- **測る側**: `SessionLifecycle` に `perception_blocks_for` / `presented_with_perceptions` / `presented_chars` を追加し、発火判定 (`maybe_run_metabolism`)、§15 読み戻しの不足判定と最終検算 (`_plan_window_refill`)、退場計画の入力 (`_run_metabolism_locked` の `plan_eviction`) を「保存行 + 知覚ブロック」に揃えた。取得失敗は知覚ぶん 0 へ縮退 (WARN)。
- **退場計画**: `plan_eviction` は知覚ブロック入りの列を受け取り、ブロックは**重さだけ**参加する。関節 (`_joint_units`) では直前の保存行の単位へ接着し (先頭のぶんは後続の最初の単位へ吸収)、chunk の境目にはならない。`Fold` には保存行だけが入り、`projected_chars` は畳んだ範囲のブロック字数も「消える側」に数える (あらすじ確定と同一 tx で付記印が付き提示から下りるため)。保存行を含まない束は閉じない。
- **表示**: `/api/people/{id}/context-status` の `presented_chars` を合計 (= 実送信) にし、内訳の `stored_chars` と `injected_perception_chars` を追加した。`fold_ready` の下見も本走行と同じ組成の列で計画する。
- **同族の消し込み (2026-09-02、同日の続きのラウンド)**: 生の提示字数で水位を測っていた残り 5 箇所も「保存行 + 知覚ブロック」へ揃えた。判定の目的が『送信量の水位』である箇所だけを置き換え、『材料の量』(U 判定の `material_message_chars`) と『畳める保存行があるか』は据え置いている。

  | 箇所 | この比較の目的 | 判断 |
  |---|---|---|
  | `_manual_compaction_status` (手動整理の門) | ユーザーが押したボタンで畳む値打ちがあるか = 送信量の水位 | 置き換え。走行側 (`plan_eviction`) が既に合計で測っているので、据え置くと門と本走行が別の答えを出す |
  | `maybe_run_emergency_precompaction` (§14-3) | 巨大なコンテキストを送ってしまう前に止めるか = 送信量の水位 | 置き換え。機構の目的そのものが実送信量なので、保存行で測ると存在意義が壊れる |
  | `cold_precompaction_status` (§14-4) | 中間値 ((target+high)/2) を越えたか = 送信量の水位 | 置き換え。本走行 `run_cold_precompaction` はロック内でこの関数を呼び直す構造なので対は自動的に揃う (ログの字数も同じ物差しへ) |
  | `_refold_raw_view_plan` (§15-3 印戻しの継続判定) | 印戻しだけで残す量に収まったか = 送信量の水位 | 置き換え。印戻しは保存行しか動かさないので、ブロック字数は起点基準で一度引いて定数として足す。下見 `preview_planning_window` も同じ関数を通るので対は自動的に揃う |
  | `_run_metabolism_locked` の印戻し後の早期完了判定 | 編纂なしで完了してよいか = 送信量の水位 | 置き換え。据え置くと「整理しました」を返した直後に発火判定 (合計で測る) がまた発火する |
  | `plan_tail_rewind` の `fold_needed` / 退場境界 (`remaining`) | 引き戻した窓が上限を超えるか・どこまで退場すれば残す量に届くか = 送信量の水位 | 置き換え。走査する列も本走行と同じマージ済みの列にした。見積もり側 `estimate_tail_rewind_fold` は同じ関数を通るので対は自動的に揃う |
  | `plan_tail_rewind` の `est_material` | 編纂の LLM コール見込み = **材料の量** | 据え置き (計算式)。ただし走査する列が合計側に変わったぶん、ブロックも本走行の `material_message_chars` と同じ扱い (機構名義の一行へ縮む) で寄与する |
  | `plan_eviction` 内部の `material_message_chars` (U 到達判定) | 一次あらすじの標準被覆 U に達したか = **材料の量** | 据え置き (2026-08-29 裁定のまま) |
