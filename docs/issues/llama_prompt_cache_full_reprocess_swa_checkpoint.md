# Gemma4 でプロンプトキャッシュが毎ターン全損する (SWA + チェックポイント位置)

**状態**: 未解決 (2026-08-07 起票)。**道を決める前の調査段階** — 有力そうな案はあるが、採否を決めるだけの材料がまだ無い。

関連: [`llm_clients/llama_cache.py`](../../llm_clients/llama_cache.py) / fork = `temp/llama-fork` (branch `codex/turboquant-multimodal-slot-save`) / 同ファイルの別欠陥 = [`llama_cache_control_requests_unauthenticated.md`](llama_cache_control_requests_unauthenticated.md), [`llama_cached_client_state_delegation_missing.md`](llama_cached_client_state_delegation_missing.md)

## 現象

`llama-cpp-cuda-gemma4-31b-abliterated` で同じペルソナに二度話しかけると、二度目もプロンプト全体を頭から読み直す。75123 トークンの読み直しに **119 秒** かかっており、応答までの待ち時間の大半がこれ。

## 測った数字 (2026-08-07、ミラの連続 2 ターン)

llama-server 側とアプリ側の両方から測っていて、二つが一致している。

| | |
|---|---|
| 前回のプロンプト | 75123 トークン / 142636 文字 |
| 前回の生成後、キャッシュにあったもの | 75820 トークン |
| **今回のプロンプトと一致した長さ** | **71655 トークン (94.5%)** |
| 文字で数えた一致 | 135763 / 142636 文字 (95.2%) |
| 一致しなかった末尾 | 3468 トークン / 6873 文字 |

**94.5% 当たっているのに 0 から読み直している**、というのがこの issue の芯。

## なぜ全部読み直しになるか

四つの事実が噛み合って起きている。一つずつ独立に確認した。

### 1. SAIVerse が毎ターン、履歴の末尾とユーザー発言の間にブロックを差し込んでいる

`llm_io.log` の連続する 2 リクエストを突き合わせて確認した。プロンプトの末尾はこうなっている。

```
... 履歴 ... [直前のペルソナの返答]     ← ここまでは前回と一致
[<system> ## リアルタイム情報 / 現在時刻: 02:46]     59 文字
[<system> ふと浮かんだ記憶: ...]                    6806 文字
[ユーザー発言]
```

**この 2 ブロックは次のターンでは履歴から消える。** 次回は同じ位置にユーザー発言が来て、その後にペルソナの返答が続き、さらに後ろに新しい現在時刻と新しい想起が差し込まれる。

しかも大きさが毎回違う。このターンは想起が 6806 文字、次のターンは 910 文字だった。だから後ろにあるものの位置が必ずずれる。

⚠️ **SAIVerse のどのコードがこの差し込みをしているかは未特定**。プロンプトの構造を実データで確認しただけで、組み立て側は読んでいない。

### 2. Gemma4 は途中位置から再開できない

Gemma4 は SWA (sliding window attention) を使う。ログに `n_swa = 1024` と出ている。この作りでは、大半の層が直近 1024 トークンぶんの置き場しか持たず、そこを使い回す。75820 トークンまで進んだ時点で、その層に残っているのは末尾 1024 トークンぶんだけになる。

ある地点の状態は「頭から順に流した結果」としてしか存在しないので、71655 の時点の状態が欲しければ頭から流すしかない。

> 「層の大半が窓」は Gemma3 世代の一般的な構成からの**推測**で、Gemma4 31B について層数と内訳を確認したわけではない。後述の `--swa-full` が数十GB を要求した事実とは整合する。

### 3. その頭からの流し直しを避ける仕組みは、位置を llama.cpp が決め打ちしている

llama.cpp には**文脈チェックポイント** (context checkpoint) がある。「この地点の窓の層はこうなっていた」というスナップショットで、これがあれば頭から流さずにその地点へ復帰できる。まはーの fork の slot cache 機能は、これを sidecar ファイルに保存・復元している (`saved/restored N context checkpoints from sidecar`)。

**問題は、作る位置がコードに直接書かれていて、設定では動かせないこと。**

- 作る位置 = 「最後のユーザー発言の直前」と「末尾から 4 トークン」「末尾から 4 + n_ubatch トークン」 → `tools/server/server-context.cpp:3535-3548`
- それ以外の途中位置では明示的に作らない → 同 `3584-3587`
- 生成本体 → 同 `2386` (`create_checkpoint`)

次に来るプロンプトは今回のプロンプトの末尾に足しただけのもの、という前提で書かれている。

### 4. 差し込みのせいで、必要な再開位置がチェックポイントより手前になる

実際に作られたのは 73575 番目と 73583 番目 (各 425 MiB)。必要だったのは 71655 番目。**1920 トークン後ろすぎる**。

使えるかどうかの判定は `チェックポイントの開始位置 < 再開位置 − n_swa` (同 `3280`, `3339-3345`)。70631 = 71655 − 1024 より手前のチェックポイントが無いので不成立。結果 `do_reset` が立って頭から読み直しになり、**復元したばかりの 425 MiB × 2 はその場で捨てられた** (同 `3372` の掃除ループ)。

つまり llama.cpp は「ユーザー発言の直前」に置いたつもりで、実際には「差し込みの直後」に置いていた。

## 試した対策と結果

| 手 | 結果 |
|---|---|
| `--swa-full` (窓の層にも全トークンぶんの置き場を持たせる) | ❌ **RAM 側に数十GB 溢れて実用不能** (まはー実測 2026-08-07)。VRAM に収まらず溢れた |
| `-ctxcp` / `--ctx-checkpoints` を増やす | ❌ 効かない。上限は既定 32、最小間隔 256 だが、**位置が末尾付近に限定されている**ので数を増やしても手前には作られない (コードで確認済み、上記 3) |

なお同じ `.bat` にある `--mtmd-batch-max-tokens 1` は、画像 2 枚のときにサーバーが落ちる別件の回避策で、本件とは無関係。

## 検討する道 (まだどれも採用していない)

1. **fork にチェックポイント位置を指定する機能を足す** (まはーの所感、有力候補)。位置指定の口ができれば、差し込みの直前を狙える。fork の slot cache 実装 (`c8e7584a9`) が既に checkpoint を sidecar で保存・復元しているので、手を入れる領域は隣接している。
2. **SAIVerse 側で差し込みの扱いを変える**。差し込みを履歴に残せばプロンプトは追記のみになり、既存のチェックポイントがそのまま効く。ただし想起が最大 6806 文字/ターン積もるので、80k の文脈が 20 ターン程度で埋まる。単独では成立しない。
3. **想起ブロックを小さくする**。910 文字程度 (約 480 トークン) のターンなら、既存のチェックポイントの射程に入る可能性がある。ただし計算上そうなるという話で、実際に効いた回を観測したわけではない。

**まはーの方針 (2026-08-07)**: 「たぶんチェックポイント位置を指定できるような機能を追加する感じで fork に手を入れるのが検討すべき策になるかと思うけど、llama.cpp と Gemma の仕様調査もしつついろんな道探ってみるのが先かな」

## 先に調べること

1. SAIVerse のどのコードが `<system>` ブロック (現在時刻・想起) を差し込んでいるか。**未特定**。
2. Gemma4 31B の層構成と、`--swa-full` が数十GB を要求した内訳。上記 2 の推測を事実に変える。
3. upstream (ggml-org/llama.cpp) にチェックポイント位置の可変化に関する議論や PR があるか。
4. 位置を指定できるようにした場合、fork の sidecar 保存・復元と噛み合うか。
