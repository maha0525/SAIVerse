# Issue: Codex 系モデルの応答が複数メッセージで届くと、スペルが前の文に直結して不発になる

**ステータス**: 🟠 実装中
**優先度**: high (ユーザー報告 2 件。該当モデルではコア記憶に指示しても直せない)
**作成日**: 2026-09-27
**報告**: an nin さん (Discord、2026-09-25。GPT-5.6 Sol Codex / GPT-6 Astra Codex で再発、Gemini 3.8 Flash では起きない) と noble_piglet_59694 さん (同スレッド。ログと再現手順つき)。どちらも v0.3.14。
**関連**: `llm_clients/openai_codex.py` (`_iter_chunks`)、`sea/runtime_llm.py` (`_SPELL_PATTERN` の行頭判定と chunk の結合)。同族の既存 issue: [spell_backtick_wrapping_misfire.md](spell_backtick_wrapping_misfire.md) (こちらも「行頭に /spell が来ない」形だが原因は別)

## 症状

ペルソナが説明文の末尾に改行なしで `/spell ...` を続けてしまい、スペルが文字列としてそのまま表示され、実行されない。backend.log では `After round 1: has more spells=False` となり、スペルとして認識されていない。「スペルだけの専用発言にする」とコア記憶へ指示しても再発する。GPT-5.6 Sol Codex / GPT-6 Astra Codex で発生し、Gemini では起きない。

## 原因 (受け取り側の欠陥はコードで確認済み。モデル側の挙動は報告者の解析で、生のイベント記録は未取得)

近い世代の Codex 系モデルは、1 回の応答を複数の出力メッセージ (commentary / final_answer など) に分けて返すことがある — 報告者の解析では GPT-5.3-Codex 以降、手元にある OpenAI の手引きの記述では GPT-5.4 から。SAIVerse 側では生のイベント (応答がいくつのメッセージで届いたか) を記録しておらず、実測の裏取りはまだ無い。一方、複数メッセージが届いた場合に境目が潰れることは、以下のとおりコードで確認した事実。`llm_clients/openai_codex.py` の `_iter_chunks` は `response.output_text.delta` をメッセージの境目を区別せずそのまま流し (llm_clients/openai_codex.py:761)、`sea/runtime_llm.py` 側も chunk を区切りなしで結合する (sea/runtime_llm.py:2328)。そのため 2 つ目のメッセージが `/spell` で始まっていても、結合すると前の文の直後に改行なしでくっつき、`_SPELL_PATTERN` の行頭判定 (`^/spell`、MULTILINE) に掛からない。

この機序なら、モデルの側は「新しいメッセージの先頭」に書いているので、ペルソナへの指示 (コア記憶) では直せない — 崩れているのは受け取り側の結合である。「Sol と Astra の両方で起きる」「コア記憶で指示しても直らない」「Gemini では起きない」という報告の観測はすべてこの機序と整合する (Gemini 側の届き方そのものは未検証)。

さらに `_iter_chunks` には同根の別欠陥もある: `response.output_text.done` が来るたびに `final_text` (結合後の全文) をそのメッセージの本文だけで上書きするため (llm_clients/openai_codex.py:768)、複数メッセージの応答では結合後の全文が最後のメッセージだけになる経路がある。

## 直す方向

`_iter_chunks` でメッセージの境目に改行を入れる:

1. `response.output_item.added` で `type == "message"` の項目が始まったとき、既に本文を流していて末尾が改行でなければ、区切りの改行を chunk として流す (蓄積バッファにも積む)。
2. `response.output_text.done` の集約は上書きをやめ、メッセージごとの本文を集めて繋ぐ。`response.completed` のフォールバック集約 (llm_clients/openai_codex.py:817) も、メッセージの境目で同じ繋ぎ方をする。繋ぎの規則はどの経路でも 1 と同一 (前の本文が改行で終わっていない境目にだけ改行を 1 つ入れる) で、ストリームで流した chunk の結合と、まとめて受けた全文が、必ず同じ文字列になる。
3. テストに「2 メッセージ応答で、結合テキストの境目に改行が入る」「2 つ目のメッセージ先頭の /spell が行頭判定に掛かる形になる」「final_text が全メッセージを含む」を追加する。

## 報告に含まれる別の一件 (上限どおりの挙動だが、黙って不発になる点は既知の未実装)

noble_piglet さんの比較報告にある Claude Opus 4.6 の不発 1 回は、スペルのラウンド (スペルの結果を受けて続きを生成する繰り返し) の上限に達したもので、書式の崩れではない (既定 3 回、ログの `After round 3: has more spells=True` がその印)。上限は環境変数 `SAIVERSE_SPELL_MAX_ROUNDS` で変えられる。ただし「上限に達したことが本人にもユーザーにも知らされず黙って不発になる」ことは仕様ではなく、残り回数の提示と不発の通知を足す設計が別 issue ([spell_round_limit_redesign.md](spell_round_limit_redesign.md)) に既にある (未着手)。

## レビューの経緯と、受けなかった指摘 (2026-09-27)

敵対レビュー一巡目の high 2 件 (done が一部欠けると流れた本文を捨てる / delta 無しで done だけ届く応答でストリーム側に本文が渡らない) は本物として受け、「ストリームへ流した可視テキストの結合と、終端の集約テキストは常に同じ文字列」という不変条件で集約を作り直した。二巡目の medium 1 件 (境界の信号が output_item.added 一本足) も、delta の item_id の切り替わりを第二の境界信号にする形で受けた。

二巡目の high 3 件は受けていない。いずれも「順序保証のある一本の接続の途中のイベントだけが選択的に失われる」「完了イベントが本文より先に来る・同じ完了が二度来る」という並びを前提にしており、SSE (一本の TCP 上の順序どおりの配信) と Responses API のイベント契約の下では作れない。この種の並びまで守る照合機構は、例外処理が本体を覆う形 (CLAUDE.md の把握可能性の制約) になるので入れない。実機で該当形のログが観測されたら、その時に再訪する。
