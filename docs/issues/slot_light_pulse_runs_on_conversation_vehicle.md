# コマ開始の Pulse が会話 Track の器で走り、独白でなく発話になる (+ track_activate の特殊機構と二重実行)

**ステータス: 実装済み・レビュー待ち** (2026-08-08 起票、同日設計裁定→実装。時間割実機検証 Step 3、ソフィーの出かけるコマの観測から。まはーの発見: 「自律行動中にチャット UI に出る発話ができてるのはおかしい」。設計の正典 = [autonomous_pulse_vehicle.md](../intent/autonomous_pulse_vehicle.md))

**用語注記 (まはー裁定 2026-08-08)**: 従来文書の「軽い一手 (Pulse)」という呼び名は廃止。本書では「**コマ開始の Pulse**」(コマが始まったときに一回だけ走る Pulse) と書く。旧称は既存の intent / コードコメントに残存しており、該当箇所を触る改修時に順次置き換える。

## 観測 (2026-08-08 16:59〜17:00、実ログで確認)

出かけるコマ 1 回の実行が、ニュースアベニューに**発話 3 通** (チャット UI 表示 + TTS 読み上げ) を残した。内訳:

1. コマ開始の Pulse 本体の出力 (記事に触れた良い文面だが、独白でなく発話・まはー宛の文体)
2. ソフィーが唱えた `track_activate` が湧かせた会話 Pulse の出力
3. 完走済みのコマ開始プロンプトが「中断された」として再配達された二重実行の出力

## 構造原因 (三つ、いずれもコードで確認済み)

### ① コマ開始の Pulse の既定の器が会話 Playbook

`day_plan._dispatch_slot_pulse` → `PulseDispatcher.dispatch_schedule_fire` は **meta_playbook 省略 = 既定の `track_user_conversation`** (day_plan.py:5352 の docstring に明記)。会話用 Playbook は応答を Building 履歴へ発話として書く器なので、コマ開始の Pulse の出力は必然的に「発話」になる。チェックリストの想定 (独白が残る) と器が食い違っている。文体がまはー宛になるのも、会話 Track の文脈 (対まはー会話の履歴) の上で生成されるため。

### ② user_conversation 型の特殊機構が健在

Playbook 自体は素朴 (main_line_response + control_body の 2 ノード) だが、**コード側のハンドラに特殊機能が残っている**: `track_activate` スペルの適用で `on_track_activated` (user-conv-handler) が (a) 新しい会話 Pulse を起動、(b) 会話エピソードを開き直し (観測では episode:8)、(c) `wait_response` 30 分タイムアウトを再装填。ペルソナがスペル一つで「会話中」状態 (コマ繰り下げの原因) を自分で作れる。

### ③ 中断復帰の再配達が完走済み Pulse にも発火した疑い

コマ開始の Pulse は 17:00:05 に完走し発話も確定した (`Normal-stream spell+finalize: msg=news_avenue_city_a:2`) のに、17:00:11 に同じプロンプトが「[前回の処理が中断されました] 中断理由: 優先度の高いリクエストを処理しました」の通知つきで再配達され、もう一度実行された。中断復帰 queue が「完走」を認識できていない経路がある可能性 — 要調査 (PulseController の中断判定と track_activate 由来 Pulse の優先度処理の交差点)。

### ④ 席違いのフォールバックが無警告 (まはー指摘 2026-08-08)

meta_playbook 未指定の Pulse は無言で `track_user_conversation` に落ちる (runtime.py の `_choose_playbook` 呼び出し。指定あり+不在のときだけエラーを返す)。未指定はユーザー会話の正規経路と同形のため、フォールバック地点では正常と席違いを区別できない。「auto pulse は必ず meta_playbook 指定」という不変条件は `_choose_playbook` の docstring (散文) にしか存在せず、コードは検査していない — 破られても誰も気づかない。ExecutionRequest は `type="schedule"` を持っているので機械検査は可能: **会話系以外の type で meta_playbook 未指定なら WARN (または拒否)**。①の器の新設と同じ改修面で入れる。

## 裁定と残論点

**着手順のまはー裁定 (2026-08-08)**: ③を単独で直す意味はない — ①②の大元 (器と特殊機構) が間違っており、そこが直れば③を起こした衝突 (会話 Pulse がコマ実行へ割り込む状況) 自体が消える。例外経路の補修より供給源の撤去を先に問う (CLAUDE.md 把握可能性の節と同じ判断)。③は根の再設計後に残っていたら改めて見る。

**①の方向裁定 (2026-08-08 まはー承認)**: 暮らし用の器を**新設しない**。機構が三系統になる案は却下し、**作業セッション運転を唯一の器に統合**する — 出かける/自室で過ごす等の暮らしコマは「**ラウンド予算 1・指示が『ここで過ごしていい』の許可形・締めなし (経験値ノート/終了判断なし)**」のプロファイルとしてセッション運転に乗せる。根拠:

- 機構の形はほぼ同一 (移動 → コンテキスト → ラウンド → 記録)。思想の分離 (暮らしに生産義務を課さない) は指示文面と締めの有無 = **パラメータで表現でき、実行機構の分離を要求しない**
- セッション頭の知覚消費 (2026-08-08 消し込みで実装済み) がそのまま「世界の流れ込み」の入口になる
- ④の「器の明示指定」も自然に満たされ、会話の器の借用が消える
- 将来「自室で記事を数手かけて読む」等の暮らしの膨らみは予算の数字だけで対応できる

発端の議論: 二系統が分かれていた意義は歴史 (作業側が先に器をもらい、暮らし側は要件が軽く見えて借り物で済まされた) 以上に見当たらない、というまはーの「気持ち悪くない？」から。

**残論点**:

- `track_activate` (②) — **方向性 (2026-08-08 まはー提示)**: UI に見える発話の経路自体は必要 (①の統合後、自律行動中に UI へ発話できる経路はここだけになる)。ただし Track の仕組みはもはやそれ用ではない。**発声用スペルを新設し、ユーザー会話 Track から専用機構 (on_track_activated の Pulse 起動・エピソード開き) を段階的に剥がす**。発声スペルは「UI に届く声を出す。それだけ」— 会話エピソードは開かない。エピソードは**まはーが実際に応じた瞬間**に開く (呼びかけて返事がなければそのまま暮らしが続く)。これで「喋る = 会話中になる」の一体化が解け、②の実測連鎖 (下記) の大半が構造ごと消える

  **スペル仕様の設計 (2026-08-08 議論、tell 案で合意方向)**:
  - `tell target=<相手> text=...` — speak (誰にともなく発声) でなく**宛先明示**。まはーの根拠: (a) ペルソナ間会話を見据えると宛先が要る、(b) 通知・未読バッジ (今は実装しない) と相性が良い — 宛先の記録が器として残る、(c) **乱発の抑止**: ペルソナから見て「ユーザーに見えて損なこと」はほぼ無く、見せる/見せないの判断軸では全部見せる側に倒れる。「誰に伝える価値があるか」の問いを毎回強制する含意が、脳死の全発声を構造的に防ぐ
  - target 語彙: 同じ部屋のペルソナ / user / all (部屋全体)。意味論は物理の発声 (部屋の履歴に宛先つき発話として書く)。ペルソナ宛は将来「相手の知覚バッファへ積む」に接続できる (入室配送と同じ口)
  - **会話中の使用**: 宛先で分岐 — 今まさに会話中の相手への tell は no-op + 「返答に書けば届きます」の教育的結果を返す (返答との二重発話を機構で防ぐ)。会話中でも別の相手への tell は許す (同席者への一言は正当)
  - カタログの出し分けはしない (head は persona×model 固定、出し分けは prefix キャッシュを壊す)。見せたまま実行時分岐で捌く
  - **モデル階層の問題と実行形の二案 (2026-08-08 まはー提起)**: ①統合後の自律セッションは worker 系 = 軽量モデルで回りうる。「会話は標準モデル」の鉄則があるのに、テキスト引数の tell を軽量が唱えると軽量の言葉がまはーに届く。
    - **A 案: テキスト引数 + 軽量モデルでは tell 不可** — 禁止が要件と正面衝突する (自律中に喋れる唯一の経路の主用途が軽量文脈。禁止すると「自律中は喋れない」へ逆戻り)
    - **B 案: tell は 1 Beat の Playbook 起動** (`tell target=<相手> gist=<要旨>`) — 軽量が「いま・誰に・何を」の判断を担い、起動された Playbook の LLM ノード (会話 aspect) が実際の言葉を書く。**モデル階層は aspect 導出の既存規則で標準に決まる — 禁止ルールなしで鉄則が構造的に破れない**。届く声も会話ラインの声になる (声の同一性)。コスト = tell 1 回につき標準呼び出し 1 回 (妥当)。Beat の意味論と一致 (正確に 1 Beat、Beat 頭の知覚消費も効く)
    - **裁定 (2026-08-08 まはー): B 案採用**。gist は文脈継承 (起動された Playbook は呼び出し元の文脈を引き継ぐ) があるため言葉の材料としては必須ではないが、「軽量側が何を伝えたくてこの Beat を起動したか」の意図の記録として残す (あったほうがいい)
  - **スペル一発の実測連鎖 (2026-08-08)**: Track running 化 → 会話エピソード開き (機構上「まはーと会話中」に) → 30 分タイムアウト装填 → 会話 Pulse 起動 (LLM 1 回、③の衝突も誘発) → 30 分後にタイムアウトがエピソードを閉じて会話終了判断 (LLM もう 1 回)。まはーには何も届いていないのに世界だけが会話 1 往復ぶんの状態を持った
  - 30 分待機の問題も半分溶ける: 「ペルソナが自分で開いた会話の返事待ち 30 分」は発生しなくなり、残るのは「実際の会話をいつ閉じるか」= [conversation_timeout_eats_short_life_window.md](conversation_timeout_eats_short_life_window.md) の本来の問いだけに純化される
- 統合の設計詳細 (プロファイルの持ち方 = カタログの execution_type 統合か別フィールドか、記録の tag、発話の有無) は intent 起こしで詰める
