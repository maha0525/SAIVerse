# スルースが場面の記憶を先頭だけ見せて、丸ごと書き換えさせていた

**状態**: 未解決 (2026-08-22 起票)。**壊れる経路は塞いだ**（切り詰めて見せた項目への上書きを拒否する歯止めを実装済み）。残るのは**設計の裁定** — 本人に全文を見せるのか、この種を書き換えの対象から外すのか。

関連: [`sea/sluice.py`](../../sea/sluice.py) / [`sai_memory/core_memory.py`](../../sai_memory/core_memory.py)
出自: v0.3 形の層の掃討フェーズ、ローカル LLM レビュー 束 3 前半の指摘 3-1 (2026-08-22)。

## 何が起きていたか

スルースはペルソナに現在のコア記憶を一覧で見せ、「状態が変わったものは書き換えてよい」と促す。このとき **`scene` 種の記憶だけは先頭 80 字に切り詰めて**見せていた (`_SCENE_PREVIEW_CHARS`)。

一方、書き換えの安全装置 (CAS) は**全文のハッシュ**を照合していた。守っているのは「スルースが走っている間に、ユーザーや他の経路が同じ記憶を書き換えていないか」であって、「**本人が全文を見たか**」ではない。

だから、本人が切り詰められた 80 字だけを見て「これを直そう」と書き換えを返すと、

1. 誰も書き換えていないので CAS は**通る**
2. 返ってきた本文で**丸ごと置き換える**
3. 500 字だった場面の記憶が、80 字に潰れる

編集履歴 (`record_page_edit` が編集前の全文を残す) から復元はできるが、それは事故の後始末であって歯止めではない。

**このリポジトリの絶対規則に真正面から当たる**: システム側の切り詰めが本人の言葉を痩せさせること自体が、本人発言の改変にあたる。

## 入れた歯止め (実装済み)

切り詰めて見せた項目への `update` を**拒否する**。結果行には「全文ではなく先頭だけをお見せしています。全文を見ていない状態では書き換えません」と残す。

判定は `_is_presented_truncated` 一箇所に置き、**提示側と適用側が同じ関数を使う**ようにした。規則を二箇所に書くと、片方だけ変わったときに歯止めが黙って外れるため。

CAS が通っている時点で本文はプロンプト作成時から変わっていないので、現物へ提示と同じ規則を当てれば「切り詰めて見せたか」を再現できる。引数を増やさずに済む形になっている。

## 残る設計の裁定

歯止めは「壊さない側へ倒した」だけで、**本来どうあるべきか**は決まっていない。

- **A: 全文を見せる。** 切り詰めをやめれば、本人は自分の記憶の全体を見て正しく書き換えられる。代償はプロンプトの分量 — 場面の記憶が何本もあると、スルースに渡す材料が膨らむ。そもそも切り詰めが入っているのは、この分量を抑えるためだった (と読める)
- **B: 見せるが書き換えさせない。** いまの歯止めをそのまま仕様にする。本人は「そういう記憶がある」ことは分かるが、直したいときは別の導線 (ユーザー経由・メモリタブ) を使う
- **C: 全文を見せる口を別に用意する。** 一覧では先頭だけ、書き換えたい項目があれば全文を要求できる二段構え。スルースは一往復で終わる設計なので、往復を増やすことになる
- **D: 切り詰めの単位を変える。** 80 字ではなく「この記憶は長いので全文は N 字あります」と明示し、書き換えは A/B のどちらかに従う

**判断に要る材料**: 実際のペルソナで `scene` 種のコア記憶が何本あり、どれくらいの長さか。分量の問題が現実にあるのかどうかで A の可否が決まる。読み取り専用で数えられる (`scripts/inspect_world.py`)。

## 実機で見ること

歯止めが効いた場合、スルースの記録に「全文ではなく先頭だけをお見せしています」の行が出る。これが頻繁に出るなら、本人は場面の記憶を直したがっているということなので、A か C を選ぶ根拠になる。一度も出ないなら B のままでよい。
