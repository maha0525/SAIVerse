# Issue: message_id を持たない古い会話は、部分的に取り込まれた状態を検出できない

**ステータス**: 🔲 未着手 (2026-08-16 起票。既知の実例は無い)

## 何が起きるか

古い `log.json` の行の中には `message_id` を持たないものがある (旧形式の移動
イベント等)。取り込みも検算も、この行を**個別に見分けられない**。

そのため両方が同じ逃げ方をしている:

- **取り込み**: `message_id` の無い行は、その部屋に行が 1 つも無いとき
  (= ファイルが唯一の写し) だけ入れる。行があるときは触らない (入れると二重に並ぶ)。
- **検算**: その部屋に行があるときは、`message_id` の無いファイル行を欠けに数えない。

結果として、**過去のどこかで一部だけ取り込まれた部屋**は、残った ID 無しの行が
永久に取り込まれず、検算も「欠け 0」と数える。誰も気づけない。

## 新規発生は塞いである

2026-08-16 に「1 行でも入らなければ部屋を丸ごと巻き戻す」形へ変えたので、今後
この状態が新しく生まれることはない。残っているのは**それ以前に作られた状態**だけ。

## 既知の実例は無い

まはーの環境で、全行が ID 無しの部屋は 3 つ (`ソフィー・ネスト_city_a_room` 4 件 /
`読書の間_city_a` 4 件 / `マユ？_city_a` の 6 件)。いずれも DB の行数がファイルの
件数と一致しており、取り込み済み。部分取り込みの状態にある部屋は見つかっていない。

## 手をつけるなら

`message_id` に頼らない照合が要る。候補:

1. **内容から安定した鍵を作る** — 発話者・時刻・本文を正規化してハッシュ。
   同一内容の行が複数あると衝突するので、ファイル内の出現位置も混ぜる必要がある。
2. **行単位の取り込み台帳を持つ** — 「このファイルの N 行目を取り込んだ」を
   別テーブルに記録する。正確だが、テーブルが 1 つ増える。

どちらも「取り込み済みかどうか」を正確に答えるための機構で、実例が出ていない今は
入れる根拠が薄い。リリース版ユーザーで実際に部分取り込みの部屋が出たら着手する。
