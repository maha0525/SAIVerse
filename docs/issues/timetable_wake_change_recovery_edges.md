# 時間割: 起床設定の日中変更 × 再起動回復の残り縁 2 件

**状態**: 未解決 (2026-08-04 起票、時間割ブランチ Codex 八巡目)。レビュー打ち切り時の残指摘 — どちらも「日中に起床設定を変える + 深夜の再起動 / 一時的な DB 障害」という狭い組み合わせで、実害は記録の捏造ではなく回復の空振り。実機検証と併走で拾う判断 (まはー裁定: 八巡目で打ち切り)。

関連: `docs/intent/timetable_redesign.md` / 五〜七巡目の順序基準一本化 (コミット f276f15 / 6017b5a / 0f60643)

## 経緯 (順序基準一本化の到達点)

五〜七巡目で「時間割の順序・予約の基準」を**当日確定ライフ優先**へ一本化した:

- 保存 / GET / 編成 / 検証: `sort_slots_by_current_basis` + `_template_order_key(plan_date)` (確定ライフ > PersonaSchedule > 暦順)
- 予約の暦日補正: `_resolve_wake_for_plan` (確定ライフの開始 > PersonaSchedule)

八巡目はこの一本化がまだ届いていない 2 経路を指摘した。

## 残り 1: plan_date 無指定の回復が営業日の選択を現行スケジュールで行う

`reschedule_pending_slots(plan_date=None)` (再起動回復 / watchdog) は、まず現行 PersonaSchedule で `effective_plan_date` を計算してから `_resolve_wake_for_plan` を呼ぶ。営業日 D の確定ライフが 23:00〜06:00、設定変更後の現行スケジュールが 07:00〜22:00 のとき、D+1 の 00:30 に再起動すると営業日を D+1 と誤読し、**D の pending コマは検査されず回復 0 件で静かに終わる** (コマは走らないが、偽の記録も残らない)。

**方向**: plan_date と wake を別々に解決せず、確定ライフ (または既存 plan の存在) を候補に含む同一の営業日解決器へ統合する。現在時刻が属する確定ライフの plan_date を選び、その日付と wake を watchdog・起動回復へ渡す。

## 残り 2: ライフ読取の一時失敗を「ライフなし」へ黙って畳む

`_resolve_wake_for_plan` は `get_lives` の例外を `lives=[]` に変換して現行 PersonaSchedule へフォールバックする。一時的な DB ロック等でライフ読取だけが失敗すると、確定ライフ基準を使わずに予約を続行し、`downtime_recovery=True` では本来実行可能な深夜帯コマを grace 超過と誤判定して `skipped` (流れた) に確定しうる。

**方向**: 「ライフが存在しない」と「読めなかった」を分離 (close_outcome の `_RELOAD_FAILED` と同じ三状態化)。読取エラー時は予約も再分類も進めず、未予約のまま次の回復 (watchdog) へ委ねる + WARN。

## 発生条件の見積もり

どちらも前提に「plan/ライフ確定後に PersonaSchedule の起床時刻を変更する」が入る。通常運用 (設定を触らない日) では発火しない。残り 2 は加えて特定タイミングの DB 障害が要る。実機初日の観察対象としては「起床設定を変えた日の翌朝、前日の残りコマの扱い」を見ればよい。
