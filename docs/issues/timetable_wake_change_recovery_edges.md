# 時間割: 起床設定の日中変更 × 再起動回復の残り縁 2 件

## 経緯 (順序基準一本化の到達点)

五〜七巡目で「時間割の順序・予約の基準」を**当日確定ライフ優先**へ一本化した:

- 保存 / GET / 編成 / 検証: `sort_slots_by_current_basis` + `_template_order_key(plan_date)` (確定ライフ > PersonaSchedule > 暦順)

八巡目はこの一本化がまだ届いていない 2 経路を指摘した。2026-08-07 に両方を実装 (下記)。

## 残り 1: plan_date 無指定の回復が営業日の選択を現行スケジュールで行う

`reschedule_pending_slots(plan_date=None)` (再起動回復 / watchdog) は、まず現行 PersonaSchedule で `effective_plan_date` を計算してから `_resolve_wake_for_plan` を呼ぶ。営業日 D の確定ライフが 23:00〜06:00、設定変更後の現行スケジュールが 07:00〜22:00 のとき、D+1 の 00:30 に再起動すると営業日を D+1 と誤読し、**D の pending コマは検査されず回復 0 件で静かに終わる** (コマは走らないが、偽の記録も残らない)。

**方向**: plan_date と wake を別々に解決せず、確定ライフ (または既存 plan の存在) を候補に含む同一の営業日解決器へ統合する。現在時刻が属する確定ライフの plan_date を選び、その日付と wake を watchdog・起動回復へ渡す。

### 実装 (2026-08-07)

`day_plan.resolve_business_day(manager, persona_id, now=None) -> BusinessDay | None` を新設し、営業日と暦日補正の起点 (wake) を**一度に**返す。

- 候補は暦日とその前日の**確定ライフ**。ライフを営業日の暦日に錨として下ろし (跨ぎなら終端は翌暦日)、現在時刻を区間に含むものを選ぶ (`_life_start_covering`)。複数該当時は開始が最も新しいもの = 直近に始まったライフ。
- 含むライフが無ければ従来どおり現行 PersonaSchedule の `effective_plan_date` へ退く (`source="schedule"`、後方互換)。
- 使う側: `reschedule_pending_slots(plan_date=None)` (起動回復) と `watchdog_tick`。watchdog は plan の有無判定・予約途絶検出・再 push をすべてこの営業日で行い、wake も同じ答えを渡す。
- **watchdog の窓・曜日ゲートは、走っている確定ライフがあるときは適用しない**。適用すると解決器へ辿り着く前に tick が打ち切られ、この issue が塞ごうとした穴が watchdog 側に開いたまま残る — 確定ライフ 23:00〜06:00 の最中に設定を 07:00〜22:00 へ変えると、深夜 00:30 は新しい窓の外。次に窓が開く 07:00 にはライフが終わっていて解決器も当日へ退くので、前営業日の予約途絶は**二度と**検出されない (Codex 九巡目 #1)。
- watchdog の day_open 再発火ガードは「見ている営業日が暦日と同じときだけ撃つ」に統一した。旧「深夜帯 (跨ぎの尻尾) では撃たない」は、ライフが無い場合のこの条件と厳密に同値 (`effective_plan_date` が前日を返す条件そのもの) で、ライフが日付を跨いで続いている場合にも自動的に広がる。

**「その日に plan がある」ことは候補の選択に使わなかった** (起票時の方向にあった括弧内の案)。理由: plan は昨日と今日の両方に存在するのが普通で、存在の有無は「いまどちらの日を生きているか」を区別しない。日ごとに記録された時間の基準は確定ライフだけであり、ライフの無い日には基準そのものが存在しない (コマの `start` は "HH:MM" だけで暦日を持たないため、plan から基準は導けない) — その日の唯一の手掛かりは現行スケジュール = 退避先そのもの。

## 残り 2: ライフ読取の一時失敗を「ライフなし」へ黙って畳む

`_resolve_wake_for_plan` は `get_lives` の例外を `lives=[]` に変換して現行 PersonaSchedule へフォールバックする。一時的な DB ロック等でライフ読取だけが失敗すると、確定ライフ基準を使わずに予約を続行し、`downtime_recovery=True` では本来実行可能な深夜帯コマを grace 超過と誤判定して `skipped` (流れた) に確定しうる。

**方向**: 「ライフが存在しない」と「読めなかった」を分離 (close_outcome の `_RELOAD_FAILED` と同じ三状態化)。読取エラー時は予約も再分類も進めず、未予約のまま次の回復 (watchdog) へ委ねる + WARN。

### 実装 (2026-08-07)

`_LIVES_UNREADABLE` (印) と `_load_lives_or_unreadable` を新設し、読み出しの三状態を分離した。

- `_resolve_wake_for_plan`: "HH:MM" (確定ライフ) / None (ライフも PersonaSchedule の起床も無い) / `_LIVES_UNREADABLE` (読めなかった)。
- `schedule_day_plan`: 読めなければ **1 件も push せず** WARN + 0 を返す。押さなければ実行もされず、pending コマの予約途絶として watchdog が拾い直す。
- `reschedule_pending_slots`: 読めなければ push も「流れた」への再分類もせず WARN + 0。
- `watchdog_tick`: 営業日を決められない tick は `{"action": "skip", "reason": "lives unreadable"}` で何もせず次の tick へ委ねる。
- **読取の失敗は例外だけではない**: `load_plan_meta` は不正 JSON を空 dict へ縮退させるため、番兵が例外経路しか見ていないと壊れた台帳が「ライフ未宣言の日」に化け、現行スケジュール基準で別の営業日を駆動する (Codex 九巡目 #2)。営業日の解決だけが `load_plan_meta` / `get_lives` を `strict=True` で読み、不正 JSON・dict でない meta・list でない lives・要素が dict でない lives を読取失敗として扱う。表示・ゲート系の寛容な既定 (空へ縮退) は後方互換のまま — 読み口は一つ、厳しさだけを引数で切り替える。

### 区間として成立しないライフは営業日を名乗れない (十巡目 #2)

`_life_start_covering` は `start == end` のライフを候補から外す。書き手 (`_validate_and_normalize_lives`) が「長さ 0 のライフは無効」として拒否している値を、読み手が `_life_span_minutes` の跨ぎ規約 (`end <= start` は +24h) で**24 時間ライフ**と読み替えていた。壊れた行 (手編集・旧データ) がその日を一日中「走行中のライフ」として名乗り、上の窓・曜日ゲートの解除まで手に入れてしまう — 実際、修正前のコードでは深夜 23:30 (現行設定の窓外) に day_open が撃たれた。候補から外れた日は「ライフが現在時刻を含まない日」と同じ扱いで現行スケジュールへ退く。

**九巡目でこの指摘を一度却下したのは、私の根拠が誤っていた**。「解決器だけ除外すると並び順と基準が割れる」と書いたが、暦日補正の起点 (`_wake_from_lives`) は候補選択と独立に lives[0].start を使うため、割れるのは「どの日か」だけで、それは谷 (どのライフにも属さない時刻) と同じ退避先に落ちる。書ける口が閉じていること (`save_lives` の拒否) も、既存・破損行を守る根拠にはならない。

### 十一巡目の裁定 (いずれも採らず)

いずれも「壊れたライフ行」への追加検証の要求で、**書ける口 (`confirm_life_for_today` → `save_lives`) は 1 日 1 本の正規なライフしか書かない**。判定は「その歯止めの目的から見て必要か」で行った (種類で網をかけない)。

- **strict でライフの `budget_pulses` / `mode` まで検証する案は不採用**。`_life_start_covering` が答えるのは「いまどの営業日を生きているか」であり、その判断に要るのは**区間が成立していること**だけ。予算やモードは支出の話で、区間の妥当性とは別。壊れた予算はコマ発火側で個別に現れる (そこが検知の持ち場)。
- **重なりライフでの「営業日選択と予算記帳の分裂」は成立しない**。`resolve_business_day` が外へ出すのは選んだライフの**日付**だけで、ライフの同一性は輸出しない (起点 wake は候補選択と独立に lives[0].start)。「どれかのライフが現在時刻を含む = 起きている」は、どの一本が含むかに依らない。
- **`source="schedule"` のとき wake をライフから取らない案は不採用** — 採ると七巡目の欠陥が戻る。谷 (ライフが現在時刻を含まない時刻) は日常的に起きる状態で、その日の並びの起点は確定ライフの開始のままでなければ、並び (`day_order_minutes`) と予約の暦日補正が再び割れる。ゲート (いま動くべきか) と暦日補正 (その日の時刻をどの暦日へ写すか) が別の基準を見るのは設計どおり。

### 今回採らなかったもの

- **`_resolve_current_plan_date` の統一は今回のスコープ外** (下記「この修正の後に残るもの」)。十巡目は「活動時間外に有料 keep-alive が継続する」も理由に挙げたが、**これは成立しない** — 指摘の並び (確定ライフ 23:00〜06:00 の深夜 00:30) ではペルソナは自分のライフの中にいるので、keep-alive が許可側に倒れるのは正しい答え。実害は表示 (話しかけやすさ) と判断点パルスの記帳先に限られる。

## 発生条件の見積もり

どちらも前提に「plan/ライフ確定後に PersonaSchedule の起床時刻を変更する」が入る。通常運用 (設定を触らない日) では発火しない。残り 2 は加えて特定タイミングの DB 障害が要る。実機初日の観察対象としては「起床設定を変えた日の翌朝、前日の残りコマの扱い」を見ればよい。

## この修正の後に残るもの (次の候補)

- **`_resolve_current_plan_date` は現行スケジュール基準のまま**。ライフ台帳系 (`is_keepalive_allowed` / `get_life_status_now` / `consume_life_pulse` / `record_judgment_pulse`) はこちらを通る。起床設定を変えた日の深夜帯では「その営業日にライフが無い」と読み、話しかけやすさ表示が未宣言に落ち、判断点パルスが D のライフ台帳へ積まれない。どれも fail-open (温め続ける / 何も表示しない / no-op) なので実害は静かな欠落に留まるが、**予約経路とライフ台帳経路で営業日の答えが割れる**状態は残っている。`resolve_business_day` を fail-open 付きで流用すれば揃う。
- **テストの実時刻依存**: ライフ宣言日の `save_day_plan` は「今〜就寝」へコマを丸めるため、仮想時刻を保存より先に立てないと保存内容が実行時の壁時計に依存する。七巡目の回帰テスト (`test_fire_at_uses_confirmed_lives_wake_not_current_schedule`) が実時刻 08:00 以降の実行で黙って落ちていた (2026-08-07 に修正)。同じ形の潜在的な依存が他のライフ宣言テストにも残りうる。
