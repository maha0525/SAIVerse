# 退場の境目はスペルの群を割らない — 保証の検分と、ツール出力の退場の明文化

**状態**: 🟣 検証待ち (2026-08-24 起票 → 2026-08-25 検分で「守られていない」と確定 → 同日に整列側・退場側へ群の原子性を実装)。残りは実機での退行確認。

関連: `sai_memory/arasuji/` の整列計画 (plan_alignment) / `sea/session_lifecycle.py` の退場と起点前進 / `messages.spell_origin_id` (スペル群の印)
出自: 2026-08-24、退場の実機検分の中でまはーが提起。

## まはーの懸念 (原文の趣旨)

スペルの結果だけが履歴から消えると、「スペルを打った → 何も返ってこず → もう一度自分が喋った」という並びをペルソナが真実として認識してしまう。それは記憶の捏造と同じでまずい。

## 確認済みの事実 (2026-08-24)

- スペルの唱え (assistant 行)・結果 (system 行)・結果を読んだ発話は `spell_origin_id` で一つの群として印が付いている。
- **懸念の並びそのもの (唱えが見えるのに結果が無い) は、退場からは構造的に生じない**。退場は常に窓の古い側から外し、結果は唱えより必ず新しいので、唱えが窓に残っていれば結果も残る。
- 今日のエリスの実機では、群 (唱え dca6546c / 結果 6,210 字 / 発話) が三点セットごと一緒に退場し、境目は群の切れ目に落ちていた。場面の物語は Chronicle のあらすじが引き受けていた (「Elyth で忘却と記憶の議論を読み解き…」)。
- 退場は行ごと窓の外へ出すだけで、省略版のスタブは残さない。スペル結果の生データは Chronicle の被覆に**含まれない** (今日の畳み: 会話 7 通 4,211 字が被覆と完全一致、結果 6,210 字は被覆外)。生の行は memory.db に残る (退場は提示から外れることで、保存の削除ではない)。

## 未確認の穴 (検分の対象)

裏返した形の継ぎ目は理屈の上でありうる: **境目が群の内側に落ちると、「唱えた記憶は退場済みなのに、結果の行だけが窓に残る」** — 出自不明のスペル結果が浮く。

- 整理の境目 (Chronicle の被覆の端 = 起点の前進先・退場計画の端) が、スペル群を割らない保証が整列計画にあるか。
- 気になる符合: 今日の群の行には episode の印 (`origin_episode`) が**付いていなかった** (episode の刻印は 2026-08-22 の束 6c で退役済み。前後の行には episode:86 / episode:87 が付いている)。印の無い区間で整列の境目がどう決まるのかが要検分。今日は群の直後が episode:87 の始まりだったため無事だった可能性がある。

## 方針 (まはー承認 2026-08-24)

1. 「**スペルの群は退場の境目で泣き別れしない**」を設計の不変条件として明文化する。
2. 整列計画・境目の決まり方を読み、この不変条件が機構として守られているかを検分する。
3. 守られていなければ、整列側に群の原子性 (境目候補を `spell_origin_id` の群の外へずらす) を入れ、回帰テストで固定する。
4. あわせて「ツール出力 (スペル結果) の退場のされ方」を明文化する — Chronicle の被覆外で退場することの是非 (スルースは読んでいる・生データは取得し直せる種類、という今日の整理を含めて)。置き場は `docs/intent/chronicle_eviction.md` か `gold_panning.md` の節。

## 検分の結果 (2026-08-25) — 守られていなかった

**結論: 不変条件は機構として守られていない。しかも割れる形は理屈の上だけでなく、本番データに実在している。**

### 1. 境目を決めているのは整列計画ではなく退場計画

方針 2 は「整列計画に保証があるか」を問うていたが、提示と退場を分ける境目を決めているのは `sai_memory/arasuji/alignment.py` ではなく `sea/eviction_plan.py` である。二箇所ある。

- `_protection_boundary()` — 残す量 (`watermarks.target`) を最新側から数えて保護開始位置を出す。境界が pulse の途中に落ちたら、**連続する同一 `pulse_id`** を古い側へ辿ってスナップする。
- `plan_eviction()` の畳みループ — `_pulse_groups()` (連続する同一 `pulse_id`) の切れ目でしか fold を閉じない。

整列計画 (`plan_alignment`) が刻むのはあらすじ 1 個ぶんの被覆範囲で、退場そのものの端ではない。

### 2. episode は最初から境目に効いていなかった

方針 2 が気にしていた「episode の刻印が退役した後の区間で境目がどう決まるか」の答えは、**退役の前後で何も変わっていない**である。`plan_eviction()` は `open_episode_refs` を引数に取るが本文で一度も読んでおらず (「エピソードに畳みを止める権利は無い」= arasuji_levels §4-1)、`episode_ref_of()` の使い道は `Fold.episode_refs` というログ用の記録だけ。境目の材料は昔から `pulse_id` と字数の二つしかない。2026-08-24 の実機で群が無事に一緒に退場したのは、印の有無とは関係のない偶然だった。

### 3. pulse の連続は、本番で実際に切れている

提示ウィンドウは `required_line_roles=["main_line"], required_scopes=["committed"]` で絞られるが、次の二種類はその網を通ってスペル群の内側に割り込む。

- **`event_message` 行** (`role=user`、`line_role` が NULL、`pulse_id` が NULL)。`line_role` NULL は legacy 救済で main_line 扱いになるので通る。中身は「[システム通知] 現在地が『エアの部屋』から『おやすみルーム』に変わりました」など — スペルでペルソナが移動した直後に書かれた通知が、そのスペルの結果行より先に入っている。
- **`scope='committed'` のメタ判断行** (`line_role='meta_judgment'`、`pulse_id` は別の値)。committed なメタ判断は main_line 要求で通す規則がある。

割り込みがあると `_pulse_groups` の連続が切れるので、スナップはそこで止まる。**境目が群の内側に落ちうる = 唱えた記憶が退場済みなのに結果の行だけが窓に残る。** 実測 (読み取り専用の検分): air_city_a は 81 群中 3 群、ruler_region_mistvale は 5 群中 3 群、lucia / nagi / quon は各 1 群が、提示ウィンドウ上で既に分断されている (eris_city_a は 107 群すべて連続)。

### 4. そもそも `spell_origin_id` が計画まで届いていなかった

`saiverse_memory/adapter.py` の `_payload_from_message_locked()` は、SELECT で取得済みの `spell_origin_id` / `spell_seq` を payload に載せていなかった (`pulse_id` や `line_role` は載せている)。退場計画は群の存在を知る材料を持っていなかった。

### 5. 群の起点行の `spell_origin_id` は NULL

最初の唱えの行は、自分の id が他の行の `spell_origin_id` になることで群を作る側なので、自分自身の列は NULL のまま。群を「`spell_origin_id` が入っている行」だけで数えると、先頭の唱えが群から抜け落ちる。実装で必ず踏む非対称。

### 6. 整列側のチャンクの切れ目も、間接的に退場の境目になる

`arasuji_levels.md` §14-2 の「冷えた anchor の前進」は、`get_frontier_anchor_id()` が返す「まだどの一次エントリにも畳まれていない、編纂対象になれる最初のメッセージ」へ起点を進める。整列計画が群の途中でチャンクを閉じていると、この前進先が群の内側に落ちる。だから方針 3 が言う「整列側の原子性」も、遠回りではあるが本当に要る。

## 直したこと (2026-08-25)

- 群の範囲を決める規則を `sai_memory/memory/storage.spell_group_spans()` に一箇所で置いた (起点行の NULL 非対称を含む)。
- `sea/eviction_plan.py` の関節を「pulse の連続」から「pulse の連続と群の範囲を併合した単位」へ広げ、保護境界のスナップと fold の切れ目の両方をその単位の外へ寄せるようにした。単位が窓の先頭から残す量を超える極端な場合だけ従来どおり途中で切るが、その切断が群を割ったときは WARNING を残す。
- `sai_memory/arasuji/alignment.py` の `_plan_run()` が、被覆 U に達しても群の内側ではチャンクを閉じないようにした。
- `_payload_from_message_locked()` に `spell_origin_id` を載せ、`get_messages_for_chronicle()` の SELECT を他の 3 箇所と同じ列構成へ揃えた。
- 回帰テストで固定 (`tests/test_eviction_plan.py` / `tests/test_arasuji_alignment.py` / `tests/test_sai_memory_storage.py`)。

### 残した限界 (承知の上)

- **窓全体が 1 つの関節単位のときだけ、いまも群を割る**。新しい側へ寄せると保護範囲が空になり anchor の指す先が無くなるため、そこだけは素の境界で切って前進を選ぶ。割ったときは WARNING が出るので、黙って起きることはない。
- **旧世代データで、畳み済みの置き換え行 (壁) がスペル群の区間の内側に立っている場合**、併合された単位がまるごと材料から外れて anchor がそこで詰まりうる。現設計の畳みは常に古い側から進み、群も割らずに畳むので、この形は新しくは作られない。実在が分かったら「壁を含む単位は壁の手前で区切って材料にする」扱いを足す。
- `get_messages_for_chronicle()` の SELECT を全列に揃えたぶん、全量編纂の一回あたりの読み込みが増える (実測でエリスは `thought_signature` 1.21MB、air は `paired_action_text` 5.11MB — 本文 5.63MB / 2.42MB と同じ桁)。`Message` の組み立てが列の位置で決まる以上、必要な列だけを選ぶには列一覧と組み立ての二枚目が要るので、規則の一点管理を優先した。

方針 1 と 4 の明文化は [`docs/intent/arasuji_levels.md`](../intent/arasuji_levels.md) §4-3 (手続き) / §7-7 (不変条件) / §7-1 の例外節 (ツール出力の退場) に置いた。**方針 4 が挙げていた `chronicle_eviction.md` は 2026-07-28 に廃止済みで、doc 自身が「設計判断の参照先にしないこと」と書いている**ため、現行の正典である `arasuji_levels.md` に置いた。`gold_panning.md` §3.9 には「スルースが窓をそのまま読むことに、この割り切りが寄りかかっている」という一行の参照だけを足した (内容の二枚目は作らない)。
