# Issue: レビューで繰り返し出る「端の場合」を、起きなくする全体の守りで塞ぐ

**ステータス**: 🔲 未着手
**優先度**: medium
**作成日**: 2026-10-29
**関連**: docs/intent/system_notice_delivery.md (「時刻の境」の「境を守れない場合」ほか)、docs/issues/system_notice_cutover_unsaved_window.md、docs/issues/withdraw_races_transcription.md、saiverse/runtime_marker.py

## 背景

システム通知の追補 (2026-10-29) の作業で、Codex の敵対レビューを 6 巡回した。指摘の多くは、機能の本筋ではなく、「保存先に書けない」「古い版と同時に動く」「途中で落ちる」といった、SAIVerse の動いている環境の前提が崩れたときの話だった。一件ずつ移行のコードに例外処理を足していくと、移行のファイルは 3,700 行を超え、巡のたびに次の端が見つかって収束しなかった。

これらの端は、移行に限らず、どの機能のレビューでも同じ形で出てくる。端が起きる前提そのもの (二つの版が同時に動く、書けない DB のまま動き続ける など) を SAIVerse 全体の仕組みで起きなくすれば、各機能のコードは「その前提は成り立っている」として書けて、次に同じ型の指摘が来たときも「既に全体の守りがある」と線を引ける (2026-10-29 まはーの提案)。

この issue は、その端を列挙し、それぞれを起きなくする全体の守りの案と、今ある仕組みを並べる。今回の追補では、どれも受け入れた残余として intent に線引きしてある。

## 端の一覧と、全体の守りの案

### 1. 同じ SAIVERSE_HOME で、違う版の SAIVerse が同時に動く

- **起きること**: 新しい版の確定の記録や時刻の境を、古い版のプロセスが知らずに書き換える。システム通知の移行では、所有者が確定した行を古い版が変換したり、新しい版の変換の記録を古い版の回復処理が捨てたりしうる (敵対レビュー 5・6 巡目)。
- **今ある仕組み**: `saiverse/runtime_marker.py` の起動時の印。同じ City の二重起動は拒否するが、一つのホームで別の City を動かすことは設計上許していて、印に SAIVerse の版は記録していない。だから違う版の別の City は同時に動ける。
- **守りの案**: 起動時の印に SAIVerse の版を書き、同じホームで稼働中のプロセスが違う版なら起動を拒否する。別の City の並走そのものは今まで通り許す。

### 2. 新しい版で動かした後に、同じ SAIVERSE_HOME で古い版を動かす (版を戻す)

- **起きること**: 1 と同じく、古い版は新しい版の記録を知らずに上書きする。同時でなく順番に動かした場合でも起きる (敵対レビュー 6 巡目)。
- **今ある仕組み**: 無い。
- **守りの案**: 本体 DB に「このデータを最後に書いた版」を残し、それより古い版は起動を拒否する (または読み取りだけで動く)。この守りは、守りを入れた版より後の版から戻すときにしか効かない (既に出した古い版には、拒否するコードが無い)。だから早めに入れるほど効く範囲が広い。

### 3. 本体 DB や保存先 (`backups` など) に書けない・読めない状態で、起動を続ける

- **起きること**: 守りに必要な記録を残せないまま動き続ける。システム通知の移行では、時刻の境を二か所とも保存できなかった起動から、保存できた再起動までのあいだに届いた真似た文が、自動で変換されうる (docs/issues/system_notice_cutover_unsaved_window.md、敵対レビュー 5・6 巡目)。
- **今ある仕組み**: 起動時の変更の前に本体 DB の復元点を取り、取れなければ起動を止める (main.py の `backup_saiverse_db`)。書き込みの可否そのものを確かめて止める検査は無い。
- **守りの案**: 起動の最初に、本体 DB・記憶 DB・`backups` への書き込みと読み戻しを試し、失敗したら起動を止めて画面 (または起動の画面) に理由を出す。動作中に書けなくなった場合の扱い (発言の受け付けを止める・再起動を促す) は別途決める。

### 4. 起動時の処理が途中で落ちる (強制終了・停電)

- **起きること**: 変換は確定したのに記録が残らない、記録だけ残って変換が確定していない、などの食い違い。システム通知の移行では、変換の記録の確定と回復の仕組みを何層も重ねた (敵対レビュー 3〜5 巡目)。
- **今ある仕組み**: 起動時の変更の前の復元点 (3 と同じ)。移行の側は取引と fsync と回の記録で、変換と記録の食い違いを次の起動で決める。
- **守りの案**: 起動時に世界を書き換える処理は、一つの取引の中で終わる形を原則にして、移行ごとの回復処理を持たないで済むようにする。取引に収まらないもの (ファイルの書き出し) は、DB の確定を正とし、ファイルはそこから作り直せるようにする。

### 5. ファイルシステムや OS の差 (ハードリンクが使えない、名前の付け替えが上書きする)

- **起きること**: 上書きしない公開が保証できない。システム通知の移行では、Windows 以外でハードリンクを作れない環境では、時刻の境を記録せず自動の変換を止める形にした (敵対レビュー 3・4 巡目)。
- **今ある仕組み**: 無い (機能ごとに分岐している)。
- **守りの案**: 対応するファイルシステムの条件を決め、セットアップ (または起動) の検査で確かめる。外れていたら知らせる。

### 6. 記憶 DB に、形の崩れた行が入る (metadata が辞書でない など)

- **起きること**: 判定の印を付けられない行が、普通の行として扱われる。システム通知の移行では、こうした行が残る記憶 DB は完了の印を見送り、画面に出す形にした (敵対レビュー 2 巡目)。
- **今ある仕組み**: チャットの送信 API は送り手の metadata の欄を絞る (`api/routes/chat.py` の `_client_metadata`)。記憶の移植など、ほかの書き込みの入口は確かめていない。
- **守りの案**: 記憶 DB に行を書く入口 (adapter の追記・移植の取り込み) で、metadata が辞書の JSON であることを確かめ、違えば書かない。

### 7. 二つの処理が同じ行を同時に扱う (取り下げと転記、削除と転記)

- **起きること**: 取り下げた発言や消した発言が記憶に入る。システム通知の確認の画面の削除と転記の競合は、追補の作業で塞いだ。取り下げと転記の競合は docs/issues/withdraw_races_transcription.md に残してある。
- **今ある仕組み**: 記憶 DB ごとの錠と、ペルソナごとの Beat ロック。本体 DB の行の状態を、記憶への追記と同じ排他で扱う仕組みは無い。
- **守りの案**: 本体 DB の行を「取り込む」「取り下げる」「消す」の三つの操作を、一つの排他 (本体 DB の行の状態の比較つき更新) に寄せる。

### 8. 記憶 DB の行に、どの入口から書かれたかの記録が無い

- **起きること**: 機構が書いた行と、人が書いた行や取り込んだ行を、本文と metadata の形でしか見分けられない。システム通知の移行では、受け入れた端の場合が二つある (2026-10-30、敵対レビュー)。一つ目は、記憶ブラウザの「メッセージを追加」(`api/routes/people/memory.py` の `create_message`) で所有者が機構とそっくりの形の system の行を足すと、その行にも系統の印が付くこと (名義と本文は変わらない)。二つ目は、会話の取り込み (`tools/utilities/chatgpt_importer.py`) が取り込み元の metadata をそのまま写すので、取り込み元が `schedule_id` か `slot_id` を持ち、本文が旧形式の中断の再開文と同じ形の本人の発言は、規則の版 5 がスケジュールの知らせに変えうること。ChatGPT の書き出しはこの名前の項目を持たないので、実際に当たるのは SAIVerse の記録を書き出して取り込み直した場合 (もともと機構が書いた行) に限られる。
- **今ある仕組み**: 建物の会話からの転記 (`building_msg_ref`) と通話の文字起こし (`voice_call` / `voice_transcript`) だけが、行に来歴の印を残す。チャットの送信 API は送り手の metadata の欄を絞る (6 と同じ)。取り込み・記憶ブラウザ・機構の書き込みは、どこから書いたかを残さない。
- **守りの案**: 記憶 DB に行を書く入口ごとに、書いた入口を予約の metadata の鍵に残す (機構・チャット・取り込み・記憶ブラウザ)。取り込みは取り込み元の metadata からその鍵を落としてから自分の値を書く。移行や判定は、この鍵を書き手の証拠に使う。守りを入れる前に書かれた行には効かない。

## 進め方

1 と 3 は効く範囲が広く、ほかの機能のレビューでも同じ型の指摘を止められる。2 は入れた版より後にしか効かないので、早いほど良い。どれも、入れるなら全体の設計として intent を起こしてから実装する。
