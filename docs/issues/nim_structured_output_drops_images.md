# NIM のモデルで構造化出力を使うと、画像がモデルに届かない

**状態**: 検証待ち。修正は develop 向けの PR #306 に出してある。

関連: [`docs/issues/archive/nim_structured_output_drops_request_kwargs.md`](archive/nim_structured_output_drops_request_kwargs.md) (同じ経路で、モデル設定の一部が落ちていた前の件)

## 芯

**同じ NIM のモデルが、構造化出力を頼まれたときだけ画像を送らず、画像の設定も読まない。**

NIM のクライアントは、構造化出力 (返事を決まった形の JSON で受け取る呼び方) だけを SDK を通さない別の経路で送る。スルースの記憶の取り込みはこの呼び方を使うので、NIM のモデルでは記憶の取り込みがこの経路を通る。この経路には欠陥が二つあった。

1. **画像が一枚も埋め込まれなかった。** 会話を送る形に組み立てる関数へ、設定を位置で並べて渡していた。途中の「画像を何枚まで埋め込むか」を一つ飛ばしていたので、後ろの設定が一つずつずれ、「後から来た system メッセージを user に変えるか」の値 (普段は False) が画像の枚数の上限に入っていた。上限 0 枚として扱われ、画像は全部 `[画像: URI] 要約` の文字の注記に置き換わっていた。reasoning の差し戻しの設定も落ちていた。
2. **モデル定義に `max_image_embeds` (画像を何枚まで埋め込むか) を書くと、クライアントが作れなかった。** factory はこの値を NIM のクライアントに渡すのに、受け取る口が無く TypeError になっていた。チャット画面の「名前を付けて保存」はこの値をモデル定義に書くので、UI からも踏める作りだった (コードを辿って確かめただけで、実際に踏んでの再現はしていない)。

## 直し方

- NIM のクライアントが `max_image_embeds` を受け取る。
- OpenAI 互換のクライアントに「このクライアントの設定で会話を組み立てる」メソッドを一つ置き、SDK の経路も NIM の構造化出力の経路も全部そこを通す。設定を呼び出しごとに手で並べていたこと自体が、ずれの原因だったため。
- 会話を組み立てる関数 (OpenAI 互換と Anthropic) は、会話より後ろの設定を名前付きでしか受け取らない。並びを間違えた呼び出しは、黙って通らずに TypeError になる。
- スルースの「送る中身の量の見積もり」は、NIM では定義の上限が効かない前提で数えていた。NIM も OpenAI 互換と同じ規則 (定義の正の整数が環境変数より優先) に揃えた。

## 検出できなかった理由

- 既存のテストはモックで「関数が呼ばれた引数」を見ていて、壊れた並びをそのまま期待値として固定していた。モックはどの順の引数でも受け取るので、値がどの設定に入ったかは誰も見ていなかった。factory でクライアントを作り、実際に送られる HTTP の中身の画像の枚数を数えるテストに置き換えた。
- スルースの見積もりの表は、クライアントのコードを読んで書き写したもので、表のテストは書き写した期待値同士を比べる。クライアント側が変わっても落ちない。factory が作る本物のクライアントに組み立てさせ、埋め込まれた枚数を見積もりと突き合わせるテストを足した。

## 変わること

NIM のモデルでの記憶の取り込みは、画像を実際に送るようになる (既定で直近 4 枚まで)。そのぶん 1 回あたりに送る量は増える。

## 未検証

実際の NIM API には送っていない。送られる中身はテストの中で読んで確かめた。
