# 読み戻し (§15) は目標量を大きく下回るペルソナのほとんどで計画が立たない

**発見**: 2026-08-31 (リリース前掃討 — 読み戻しの本番未発火の原因調査)
**状態**: 🔲 未解決 (観察のみ・診断未着手) — v0.4 の想起・提示チューニングと一緒に見る。リリースは塞がない (読み戻しは救済の最適化で、立たなくても現状維持なだけ)
**深刻度**: P3

## 実測 (2026-08-31、本番 context-status API の preview)

目標量 (target 100,000 字) を下回るペルソナ 10 人のうち、読み戻しの計画
(refill_applied=true) が立つのは **2 人だけ**:

| ペルソナ | presented | 計画 |
|---|---|---|
| air | 6,254 | ✅ 立つ (ただし preview 後も 6,254 — 増分ごく小) |
| testarossa | 94,558 | ✅ 立つ |
| aifi | 21,878 | ✗ (編纂被覆は anchor まで届いているのに立たない) |
| mia / nagi / quon / lucia / aid / mira / navi | 1,681〜99,404 | ✗ |

navi は編纂履歴がほぼ無い (6 項) ので正常な skip。それ以外の 7 人は編纂履歴が
あるのに立たない。

## 仮説 (未検証)

`plan_rewind` (sea/window_refill.py) の梯子は「壊れた段 (提示対象から消えた
source を持つ段) / 既存圧縮区間との交差 / 被覆の無い編纂対象メッセージ」の
どれかに当たると**そこで止まり、段を飛ばして先へは降りない** (設計どおりの
安全側)。長命ペルソナは curation・スルース退場・二重取り込み掃除などで
「source が消えた段」を持ちやすく、最初の段で梯子が止まる形が多発している
可能性がある。また `get_history_before_anchor` の予算打ち切りが、大きく併合
された段の古い側 source を「消えた」と誤認させる可能性もコード上はある
(budget 78k に対し段が数ヶ月幅のとき)。

## やること (v0.4)

- 立たない 7 人について、梯子がどの条件で止まったかを一人ずつ言えるログ
  (skip 理由の DEBUG 出力) を足して診断する。現状 skip は無音で、原因を
  外から区別できない。
- 診断の結果「安全側の設計どおり」なら受容し、誤検知 (予算打ち切り由来など)
  なら直す。
