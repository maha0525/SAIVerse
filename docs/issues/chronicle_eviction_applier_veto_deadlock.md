# 退場の適用側が持つ「計画が知らない拒否権」で、anchor が恒久的に詰まる

**ステータス**: 検証待ち — 2026-07-27 設計確定 (まはー裁定) → 同日実装・回帰緑。残 = 実機検証
**深刻度**: P1 — 起きると anchor が二度と進まず、提示コンテキストが永久に肥大したままになる
**⚠️ 本設計より前から在る経路**: 二段構えの退場計画 (2026-07-25) が入れた欠陥ではなく、変更前も同じ並びで詰まる。ただし [`chronicle_eviction.md`](../intent/chronicle_eviction.md) §5-5 が強制クローズを撤去した根拠を「手詰まりが起きない」と書いていたので、その根拠の範囲を正しく限定するために起票する
**関連**: `sea/session_lifecycle.py` の `_apply_eviction_plan` ・ `sea/eviction_plan.py` ・ [`chronicle_eviction.md`](../intent/chronicle_eviction.md) §2 (下限の強制) / §5-5

## 構造 — 拒否権が計画の外にある

退場は二段階でできている。

1. **計画** (`plan_eviction`、純関数) — どの範囲を畳むかを決める。DB もあらすじも見ない
2. **適用** (`_apply_eviction_plan`) — 計画された範囲を実際に退場させる

適用側には「この fold は退場させない」と拒む条件が二つある。**計画側はその条件を知らない。** だから拒否された fold は次のラウンドでも同じ形で提案され、同じ理由で拒否される。**永久に同じところを回る。**

しかも二段構えの計画は「最後の手段」を一回の Metabolism につき一回しか使わない。その一回を、**拒否されると分かっている先頭の fold が毎回食い潰す**。後ろに畳めるものがあっても手が回らない。

## 顔その1 — あらすじを引けない fold

Chronicle 除外タグ (`handy_tool` / `spell` / `event_message` / `session_digest`) の付いたメッセージは編纂対象から落ちる。だがこれらは `line_role="main_line"` / `scope="committed"` で保存されるので、**提示コンテキストには載る**。

先頭にこの手のメッセージだけの範囲があると、計画はそこを畳もうとするが、あらすじが引けないので適用側が退場を拒む (これは §2 の下限「あらすじの無い範囲を黙って消さない」を守るための正しい規則)。

**確認済みの実測** — 提示コンテキスト `[e0(除外タグ), o0(open, U未満), c0, c1, k0, k1]`、低4万相当の縮小水位で6ラウンド:

```
r0: 計画=[['e0'], ['c0','c1']]  拒否=[['e0']]  anchor 動かず
r1: 計画=[['e0']]               拒否=[['e0']]  anchor 動かず
r2..r5: 同じ (永久)
```

`o0` も永久に畳まれない。

## 顔その2 — digest を引けない既存の圧縮区間

あらすじ本文を引けなくなった圧縮区間は、生ログのまま提示に戻る (fail-open。体験を黙って消さないための正しい規則)。すると計画はそれを普通の材料として束ね直すが、適用側は**既存の圧縮区間と1件でも重なる fold を丸ごと捨てる**ので、同じ束ねに巻き込まれた未畳みのメッセージまで道連れになる。

**確認済みの実測** — 既存の圧縮区間 `[m2,m3]` の digest が引けない状態:

```
r0: 計画=[['m0','m1','m2','m3'], ['m4','m5']]  拒否=[['m0','m1','m2','m3']]  anchor 動かず
r1..r5: 同じ (永久)
```

`m0+m1` だけで U に届かない限り、束ねは必ず `m2` を巻き込むので抜けられない。

## なぜ強制クローズでは救えなかったか

旧 §5-5 の強制クローズは「**計画が完全に空**のとき」しか発火しなかった。上の二つはどちらも計画が空ではない (拒否されるだけ) ので、撤去前も発火していない。**つまりこれは強制クローズ撤去の副作用ではない。**

## 設計の確定 (2026-07-27、まはー裁定)

当初案の「拒否した範囲を次の計画に壁として渡す」(拒否メモリの伝搬) は**採らない** — ラウンドを跨ぐ新しい状態を飼う補修で、無効化の寿命管理が丸ごと付いてくる。二段構造 (計画=純関数 / 適用=DB 持ち) 自体は正しいので残し、壊れている二点を直す。

**顔その1 = 拒否条件をカテゴリでなく目的から書き直す。** 今の条件「あらすじが無い → 見送り」は、目的「編纂されるはずの体験を黙って消さない」(§2 下限) からズレている。全メッセージが Chronicle 除外の fold はあらすじが**永久に**生まれないので、人質に取っても守れるものが無い。Chronicle を切っている persona (disabled) と同じ扱いに落とす — 先頭吸収だけ許し、圧縮区間は作らない。編纂対象を含むのにあらすじが無い fold (LLM 失敗等の一時状態) は従来どおり見送り。

**顔その2 = 死んだ記録の撤去 (発生源 + 安全網の二段)。** 半端な状態「記録は生きているのに指す先のあらすじが無い」を存在させない。

- **発生源**: あらすじエントリの手動削除 (UI) が、それを指す圧縮区間の記録を同じ操作で道連れ削除する。記録は丸ごと外す (複数エントリ持ちから 1 本だけ抜くと、残りの digest が範囲全体の顔をして消したぶんの体験が隠れる)。再生成 (旧 id 削除 → 同じメッセージ集合で新エントリ) は道連れにしない — メモの予備照会 (メッセージ集合での引き直し) が新エントリを引き当てるので、記録は残すのが正しい
- **安全網**: Metabolism 冒頭で「照会は成功したのにエントリが無い」(= 恒久欠落) の記録を捨てる。提示が生ログに倒れる (fail-open) と確定した瞬間に記録も死ぬ — 生死の判定を一箇所に揃える。照会自体の失敗 (一時障害) では捨てない (瞬断のたびに編纂済み範囲が再編纂される事故を防ぐ)

前提の裏取り (2026-07-27 確認): 束ね (chronicle_consolidation) は**一次エントリを消さない** (不変条件5 — 追加のみ、子は `is_consolidated` で列から退くだけ。bands.py に DELETE 経路なし)。エントリが消える経路は手動 UI (削除・再生成) だけなので、道連れとバックアップ復元 (全体が一緒に戻る) を除けば、安全網の出番は DB 破損級の異常系のみ。恒久欠落で記録を捨てた結果 Chronicle に穴が残る問題は、Chronicle 全体の保守管理の課題として本件から切り離す (まはー裁定)。

当初案 2 (最後の手段の枠の数え直し) は不要になった — 拒否される fold が原理的に出なくなるため。案 3 (除外タグを提示に載せない) は引き続き [short_term_to_long_term_memory_filtering](short_term_to_long_term_memory_filtering.md) の管轄 (顔その1 の根)。

## 残る既知の限界

- 除外タグだけの範囲が提示コンテキストの**途中**にある場合は畳めないまま残る (見せる digest が無い)。恒久デッドロックにはならない — 手前が畳まれて先頭に出た時点で吸収される。根治は入口選別 ([short_term_to_long_term_memory_filtering](short_term_to_long_term_memory_filtering.md))
- 複数エントリを指す記録の**一部だけ**が恒久欠落した場合、安全網は発火しない (残りで digest が組めるため fail-open にならず、消えたエントリぶんの体験が置き換えの下に隠れる)。手動削除は道連れが丸ごと外すので UI 経路では起きない。DB 破損級の異常系に限る残余で、Chronicle 全体の整合性点検の課題
- **regenerate の CAS に ms 級の競合窓が残る** (Codex 再々レビューの指摘のうち、処方を採らなかった部分)。swap 前に旧行を完全 id で再取得し、id / parent_id / is_consolidated / content / source_ids が開始時と一致するときだけ差し替え、競合・途中失敗時は新行を親参照ごと取り下げる — ここまでは実装した。残るのは「検査と差し替えが別 commit」である構造そのもので、検査直後の数 ms に別接続の書き込みが割り込む窓は閉じていない。完全に閉じるには storage 層 (1 操作 1 commit 設計) の単一トランザクション化ないし版番号列の導入が要り、手動 UI 操作同士の ms 級競合に対して過大と判断して受容した。同レビューの「staged 状態で不可視に作る」も同じ理由で見送り
- **delete 系が embedding (arasuji_embeddings / memopedia_embeddings) を掃除しない**のは、今回の変更と無関係に全削除経路 (UI 削除含む) が持つ既存の性質。別課題として切り出す
