# Issue: 画面へ流したことを、保存できたことと同じに数えている

**ステータス**: 🔲 未着手 — 設計から
**優先度**: high — 続きの生成のボタンが実態とずれ、どちらへずれても永続データに残骸が出る
**作成日**: 2026-08-28
**出自**: [user_utterance_path_failure_inventory](archive/user_utterance_path_failure_inventory.md) の
Codex レビュー 1 巡目 (2026-08-26) が指摘し、補修では塞げないとして切り出した 4 件のうちの 1 つ。
2 巡目で「私の修正が悪化させていた」件の根も、ここに行き着いた。

---

## 共通の根 — 「どの生成の、どの段階の話か」を運ぶものが無い

切り出した 4 件は別々の顔をしているが、**一つのストリームについて「これはどの生成のことで、
いまどの段階まで進んだのか」を運ぶ仕組みが無い**という同じ欠落から出ている。

- この issue (保存できたことを表す信号が無い) は**どの段階まで進んだか**が運べていない。
  画面に出たところまでなのか、DB に残ったところまでなのかを、受け手が区別できない。
- [未知の送信結果から復旧できない](unknown_send_outcome_has_no_recovery_path.md) も段階の話で、
  **発言がサーバーに残ったのかどうか**を後から尋ねる手段が無い。
- [retry がサーバー側で再送可能性を見ていない](retry_api_has_no_server_side_eligibility_check.md)
  も段階の話で、**その発言が既に応答を得たのかどうか**を発言自身が持っていない。
- [ストリームの表示に識別子が無い](streaming_events_have_no_identity_in_the_ui.md) は
  **どの生成の話か**が運べていない。断片がどのペルソナのどの Pulse のものかを、画面側が照合しない。

4 件を別々に補修すると、同じ判断が経路ごとに別の場所へ書き分けられる (この inventory の
レビュー 3 巡で繰り返し出た型)。**設計するときは 4 件を一つの束として扱う**のが安全で、
どれか 1 件だけを先に直す場合も、残り 3 件がその決めごとに乗れるかを見てから決める。

---

## 何が起きているか (コードで確認した事実)

ペルソナの応答は二段階で世界に残る。まず断片が `streaming_chunk` として画面へ流れ、最後に
`emit_speak_finalize` が下書き行 (placeholder) に本文を流し込んで確定する。
**この二段目の成否を、誰も受け取っていない。**

- `sea/runtime_emitters.py:391-435` — `emit_speak_finalize` は建物履歴の更新・ペルソナ履歴への
  追加・ゲートウェイ配信をまとめて `try` で囲み、`except Exception:` で握ってログに書くだけで戻る。
  戻り値の `building_msg` は `None` のまま返る。しかも `:404-409` の「更新対象の placeholder が
  見つからなかった」場合も同じ `None` へ合流するので、呼び出し元からは
  **成功・保存失敗・対象行なしの三つが区別できない**。
- `sea/runtime_llm.py:4383-4399` — 呼び出し元はその戻り値を受け取らず、直後に
  `pipeline_finalized = True` を立てる。「呼んだ」が「保存できた」として扱われている。
- `manager/runtime.py:130-153` — `_note_speech` は `say` と `streaming_chunk` を見て
  `spoke["value"]` を立てる。どちらも画面へ出すためのイベントで、保存の証拠ではない。
- `sea/runtime_llm.py:4342-4358` — 完了イベント (`streaming_complete`) は finalize より**前**に
  送られる。だから今の完了イベントには、保存された行の id を載せられない。

## ユーザーから見て何が起きるか

`manager/runtime.py:1140-1178` の `continue_persona_message_stream` は、この `spoke` を見て
「続きが生まれた」と判断し、元の発言から中断の印 (`_interrupted`) を降ろす。印を降ろすと、
そのバブルの「続きの生成」ボタンが消える。

- **印を降ろす側へ倒すと**: 続きが保存されていないのにボタンが消える。続きを取る手段が失われ、
  しかもユーザーからは失われたことに気づけない (欠落)。
- **印を残す側へ倒すと**: 続きが保存されているのにボタンが残る。押すと二つ目の続きが生まれ、
  建物の記録とペルソナの記憶に二重に積む (重複)。

現状は後者へ倒してある (`manager/runtime.py:1147-1157` のコメントに理由が書いてある) —
重複は目に見えるが、欠落は気づけないから。**どちらへ倒しても穴が開くのは、判断の材料そのものが
無いため**で、倒し方を変えても穴は移動するだけになる。

到達経路は二つ。**「続きの生成」の最中に読み手が去る** (ブラウザを閉じる・別の建物へ移る) と
重複の側へ落ちる。**finalize の DB 書き込みが失敗する**と欠落の側へ落ちる。後者は
[orphaned_streaming_placeholder_cleanup](orphaned_streaming_placeholder_cleanup.md) の実測
(残骸 32 件はすべて「finalize が呼ばれなかった」形) では観測されていない。

## なぜ補修で塞げないか

塞ぐ先が「判断の分岐」ではなく「判断の材料」だから。どの分岐に手を入れても、材料が
「画面へ流れたか」しかない限り、欠落と重複のどちらかを選ぶことにしかならない。

## 直すのに要るもの (設計の入口)

**保存できたことを表す信号**。論点は少なくとも三つある。

1. **`emit_speak_finalize` が失敗を呼び出し元へ返す形**。戻り値で返すのか例外にするのか、
   「対象行なし」と「保存失敗」を分けるのか。握り潰しを外すと、いま失敗を無視して進んでいる
   経路が全部止まりうるので、止まったときに何を残すかまで決める必要がある。
2. **完了イベントの順序と種類**。いまは finalize より前に流れるので保存された行の id を
   載せられない。単に後ろへ動かすだけでは足りない — 画面は再読込を待たずに「続きの生成」を
   出せなければならない (実機検証④で確定した要件) ので、順序を入れ替えるのか、保存後に
   別のイベントを足すのかを決める。
3. **「喋った」の判定材料の差し替え** (`_note_speech`)。`_OUTCOME_EVENT_TYPES` (ユーザーに
   何かが届いたか) と `_SPEECH_EVENT_TYPES` (ペルソナが言葉を出したか) は別の問いで、
   前者は画面の話なので今のままでよい。**この二つを混ぜないこと** — 混ぜると、エラー通知を
   「喋った」と数える形に戻る。
