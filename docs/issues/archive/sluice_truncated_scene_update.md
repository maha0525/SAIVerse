# スルースが場面の記憶を先頭だけ見せて、丸ごと書き換えさせていた

**状態**: ✅ 完了 (2026-08-22 実装・回帰テスト済み)。歯止めの条件を長さから種類へ移した。

## 実装 (2026-08-22)

`sea/sluice.py` に `_is_scene_memory` を置き、`_apply_ops` の update 拒否条件を `_is_presented_truncated(current)` から `_is_scene_memory(current)` へ変えた (長さ不問)。`remove` は変えていない。結果行は「update 失敗: core:{id} は場面の記憶 (実会話の写し) なので書き換えの対象外です。」。`_is_presented_truncated` は提示側の切り詰め規則だけの役目に戻し、docstring から「適用側の歯止めに使う」を落とした。提示は先頭 80 字のまま。

回帰テスト (`tests/test_sluice.py`): **80 字以下の scene への update も拒否される** (`test_a_short_scene_memory_is_also_rejected` — ここが以前の穴)、80 字超の scene は従来どおり拒否、scene の remove は通る、note 種は長くても書き換えられる、提示側の切り詰めは 80 字のまま (歯止めと提示が別規則になったので、提示が黙って全文提示へ変わらないことを固定)。

**既存テストの仕様を一つ反転した**: `test_a_short_scene_memory_is_still_updatable` は「切り詰めずに見せた scene は直せる」を仕様として固定していた。裁定はこれを穴と判定したので、拒否を期待する形へ書き換えた。

## 裁定 (2026-08-22、まはー + Fable)

**選択肢 B。ただし歯止めの条件を、長さではなく種類 (`kind == "scene"`) で書く。** 実データを数える必要はない。

根拠は `sea/sluice.py` の冒頭に不変条件として既に書かれている一行 — 「scene は参照コピーのみ (ペルソナに書き写させない)」。場面の記憶は実際の会話の写しで、口調のアンカーとして使うもの。本人が「直す」ことは会話の写しを書き換えること、つまり捏造になる。だから**長さに関係なく**書き換えの対象外が本来の姿で、「全文を見せるか」という問いは scene の性質からして立たない。

いまの歯止め (`_is_presented_truncated` = 80 字を超える scene だけ拒否) には、**80 字以下の短い場面はまだ書き換えられる穴**が残っている。「歯止めの条件は目的から導き、種類で書かない」の典型で、目的 (写しを改変させない) から書けば条件は「scene なら update 拒否」の一行になる。

決めたこと:

- `update` の対象から scene を外す (長さ不問)。`remove` は従来どおり (写しを消すことは改変ではない)
- 提示は先頭 80 字のまま (「こういう場面がある」と分かれば足りる)。`_is_presented_truncated` の役目は提示側の切り詰め規則だけに戻す
- 結果行の文言を「core:{id} は場面の記憶 (実会話の写し) なので書き換えの対象外です」に変える
- 回帰テストは「80 字以下の scene への update も拒否される」を含める

## 何が起きていたか

スルースはペルソナに現在のコア記憶を一覧で見せ、「状態が変わったものは書き換えてよい」と促す。このとき **`scene` 種の記憶だけは先頭 80 字に切り詰めて**見せていた (`_SCENE_PREVIEW_CHARS`)。

一方、書き換えの安全装置 (CAS) は**全文のハッシュ**を照合していた。守っているのは「スルースが走っている間に、ユーザーや他の経路が同じ記憶を書き換えていないか」であって、「**本人が全文を見たか**」ではない。

だから、本人が切り詰められた 80 字だけを見て「これを直そう」と書き換えを返すと、

1. 誰も書き換えていないので CAS は**通る**
2. 返ってきた本文で**丸ごと置き換える**
3. 500 字だった場面の記憶が、80 字に潰れる

編集履歴 (`record_page_edit` が編集前の全文を残す) から復元はできるが、それは事故の後始末であって歯止めではない。

**このリポジトリの絶対規則に真正面から当たる**: システム側の切り詰めが本人の言葉を痩せさせること自体が、本人発言の改変にあたる。

## 入れた歯止め (実装済み)

切り詰めて見せた項目への `update` を**拒否する**。結果行には「全文ではなく先頭だけをお見せしています。全文を見ていない状態では書き換えません」と残す。

判定は `_is_presented_truncated` 一箇所に置き、**提示側と適用側が同じ関数を使う**ようにした。規則を二箇所に書くと、片方だけ変わったときに歯止めが黙って外れるため。

CAS が通っている時点で本文はプロンプト作成時から変わっていないので、現物へ提示と同じ規則を当てれば「切り詰めて見せたか」を再現できる。引数を増やさずに済む形になっている。

## 残る設計の裁定

歯止めは「壊さない側へ倒した」だけで、**本来どうあるべきか**は決まっていない。

- **A: 全文を見せる。** 切り詰めをやめれば、本人は自分の記憶の全体を見て正しく書き換えられる。代償はプロンプトの分量 — 場面の記憶が何本もあると、スルースに渡す材料が膨らむ。そもそも切り詰めが入っているのは、この分量を抑えるためだった (と読める)
- **B: 見せるが書き換えさせない。** いまの歯止めをそのまま仕様にする。本人は「そういう記憶がある」ことは分かるが、直したいときは別の導線 (ユーザー経由・メモリタブ) を使う
- **C: 全文を見せる口を別に用意する。** 一覧では先頭だけ、書き換えたい項目があれば全文を要求できる二段構え。スルースは一往復で終わる設計なので、往復を増やすことになる
- **D: 切り詰めの単位を変える。** 80 字ではなく「この記憶は長いので全文は N 字あります」と明示し、書き換えは A/B のどちらかに従う

**判断に要る材料**: 実際のペルソナで `scene` 種のコア記憶が何本あり、どれくらいの長さか。分量の問題が現実にあるのかどうかで A の可否が決まる。読み取り専用で数えられる (`scripts/inspect_world.py`)。

## 実機で見ること

歯止めが効いた場合、スルースの記録に「全文ではなく先頭だけをお見せしています」の行が出る。これが頻繁に出るなら、本人は場面の記憶を直したがっているということなので、A か C を選ぶ根拠になる。一度も出ないなら B のままでよい。
