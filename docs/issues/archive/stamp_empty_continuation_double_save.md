# 504 の継続が空応答のとき、二重保存された部分文に継続コールの数字が乗る

**状態**: ✅ 完了 (2026-08-22 実装・回帰テスト済み)。二重保存そのものを塞いだ。

## 実装 (2026-08-22)

**先に下流を読んだ結果、空文字を返す案は採れなかった**。`_finalize_beat` は空文字なら memorize を飛ばす (`if text and ...`) ので二重保存は消えるが、その手前で `state["last"]` / `state["_messages"]` の assistant 行 / PulseContext / output_key にも空が載る。空の assistant 行が後続の messages へ流れ込む経路は 2026-04-28 のまはー指摘で潰した場所で、そこを開け直すことになる。本人が実際に言ったのは部分文なので、これらには部分文が載るのが正しい。

そこで**戻り値は部分文のまま返し、保存済みの印だけを state に置いて memorize を飛ばす**形にした。印 (`_ALREADY_STORED_STATE_KEY`) の値は保存した本文そのもので、`_finalize_beat` が冒頭で必ず pop して消費し (残すと次の Beat の保存を黙って止める)、本文が一致したときだけ保存を飛ばす。一致で判定するのは、印が古い / 途中で本文が差し替わった (spell の continuation 等) 回に取りこぼさないため。

**隣も塞いだ**: `_finalize_beat` には memorize のほかに important ノードの dual-write という「同じ本文を書く」経路がもう一本ある。片方だけ塞ぐと important ノードの 504 空継続で二重保存が残るので、同じ条件を当てた。

`clear_call_tokens(state)` は裁定どおり呼ぶ。**前駆 (presented ids) は落とさない** — 直前に append した部分文の id は「次に書かれる行が実際に見た最後の永続行」として正しいまま。clear_call_tokens と対で落とす規律は「本文の作り手が変わった区間」のためのもので、ここは作り手が変わったのではなく新しい本文が生まれなかっただけ。

回帰テスト: `tests/test_message_stamp.py` に「空継続 → 部分文の一行だけ + 保存済みの印 + 三つ組が残らない」「継続あり → 印を置かない (二行が正しい)」、`tests/test_beat_finalize.py::AlreadyStoredResponseTest` に「印と一致する本文は memorize も dual-write も飛ばす」「一致しなければ保存する」「印は必ず消費される」。修正を外すと落ちることを両側で確認した。

**既存テストの契約を一つ書き換えた**: `test_empty_continuation_still_clears_the_stale_triple` は「継続コールの三つ組が state に残る」を固定していた (初回の数字を居残らせないため)。行が書かれないと決まった以上残せないので、`test_empty_continuation_leaves_no_triple_behind` へ置き換えた。

## 裁定 (2026-08-22、まはー + Fable)

**選択肢 C (二重保存そのものを直す) を今やる。B (数字だけ落とす) は採らない。**

問題の核は「数字の帰属がずれる」ではなく、**本人の発言が記憶に二回書かれる**こと — 本人が同じ言葉を二度言ったことになる。これは束 5 以前からある欠陥で、刻印が光を当てただけ。そして直す場所は一関数の中に閉じている: 継続が空だったとき `_respeak_after_stream_timeout` (`sea/runtime_llm.py`) が部分文をもう一度戻り値として下流へ渡すのをやめ、「新しい発言は無かった (部分文は保存済み)」と返せばよい。生ログの保存設計には触らない (D は対象外)。

決めたこと:

- 継続が空のとき、部分文を戻り値として返さない。下流の memorize が再保存しない形にする
- 戻り値の形 (空文字か、別の印か) は**下流が「空の発言」をどう扱うかを読んでから**決める — 空文字を返すことで別の救済 (空応答の再試行・エラー表示など) が動くなら、それを踏まない印にする。部分文は `_respeak_after_stream_timeout` に入る前に UI・建物履歴へ emit 済みなので、ユーザーから見える発言は失われない
- 新しい行を書かないと決めたら、state の三つ組を `clear_call_tokens` で落とす (継続コールの数字が次の行に乗らないように — 「欠落は許すが捏造は許さない」)。継続コールの使用量そのものは `_record_llm_usage` で記帳済みなので費用の記録は失われない
- 回帰テストは「504 → 継続が空」で memory.db に同じ本文の行が一行しか無いことを固定する

## 何が起きるか

サーバーが応答の途中で切れた (504) とき、SAIVerse は「続きを話してください」ともう一度呼ぶ。この**継続の呼び出しが空で返った**場合、部分文が二度保存され、**二行目にその部分文を書いていない呼び出しの数字が刻まれる**。

束 5 の芯は「**欠落は許すが捏造は許さない**」なので、これは芯に反する。ただし刻まれるのは数字だけで、本人の言葉は変わらない。

## 具体的な並び (現物で確認済み)

1. 初回のストリームが 504 で切れる → state の三つ組 = 初回コールのもの
2. 部分文を保存 (`_store_memory`) → **一行目: 初回の三つ組** ✓
3. 継続コールを投げる → 空応答
4. `_record_llm_usage` (`runtime_llm.py:446`) が state の三つ組を**継続コールのもので上書き** (入力 > 0、出力 = 0)
5. 空判定 (452 行) で `partial_text` を返す
6. 下流の memorize が同じ部分文をもう一度保存 → **二行目: 継続コールの三つ組** ✗

## 上書きは意図的である (ここが裁定の分かれ目)

446 行の直前のコメントは、空応答でも使用量を通す理由をこう書いている。

> 「**空応答でも必ず通す** — トークンは消費されているし、通さなければ初回コールの三つ組が state に居残って次の生成へ漏れる」

つまり「空でも上書きする」のは**狙ってやっている**。目的は「初回の数字が次の生成へ漏れるのを防ぐ」ことで、それ自体は正しい。

考慮に入っていないのは、**その直後に同じ部分文がもう一度保存される**こと。書き手は「次の生成」を見ていて、「この直後の二重保存」を見ていない。

## 選択肢 (未裁定)

- **A: 何もしない。** 二行目は一行目の重複で、本人の言葉は失われない。数字の帰属だけがずれる
- **B: 空応答のとき、返す直前に三つ組を落とす。** 「この行を書いた呼び出しが確定できない」ので刻印なしへ倒す — 束 5 の他の場面と同じ規律。代償は、UI のキャッシュヒットのドットがその行から消えること (使用量そのものは記帳されているので、費用の記録は失われない)
- **C: 二重保存の方を直す。** そもそも同じ部分文が二度保存されるのが正しいのか。**この二重保存は束 5 以前からある挙動**で、刻印の導入で初めて数字の帰属問題として見えるようになった。根に近いのはこちら
- **D: 二行目を一行目の続きとして扱う。** 保存を一本化し、部分文の行を更新する形にする。影響範囲は C より大きい

**C と D は束 5 の範囲を超える** (生ログの保存の設計に触る)。B は束 5 の中で閉じるが、症状を消すだけで二重保存は残る。

## 実機で見ること

504 は頻繁には起きない。起きたときのログ (`[sea][llm] Re-speak after 504 returned empty response`) を目印に、同じ本文の行が二つ並んでいないか、二行目のドットが出力 0 になっていないかを見る。
