# Pulse の複数 Beat が 1 件の記録に結合され、部屋の帰属と Beat の境界が失われる

**状態**: 完了 (2026-09-12 起票・同日まはー GO、2026-09-13 実装とレビュー 3 巡完了 → 同日の実機確認で表示・音声の 5 件を検出・裁定・修正 → 同日まはーの実機で全件合格。移動先帰属は「移動しながらの発話が移動先の部屋に表示され、移動先の同席者の未読位置より後ろに正しく積まれる」ところまで実データで確認済み)

## 症状 (2026-09-12、まはーの実機観測 2 件)

1. **移動後の発言が元の部屋に残り、元の部屋に残った同席者に読まれる。**
   まはーの部屋にアイフィとエリスがいる状態で、アイフィが Pulse の途中で部屋移動の
   スペルを使って自室へ移動し、続けて自室の片付けスペルを数回使った。移動後の Beat
   (自室の描写・片付けの実況) まで全部が**まはーの部屋の**会話記録 1 件 (3,884 文字)
   として保存され、まはーの部屋に居るエリスがそれを取り込んだ。エリスは「その場に
   いなかったはずの出来事」を見聞きしたことになる。チャット UI にも Pulse 丸ごとが
   まはーの部屋の吹き出しとして残った。

2. **Beat の境界が表示に現れない。**
   エリスの朝の Pulse で、生成の先頭に /spell 行を書き、その後ろに朝の独白を続けた。
   スペルセクション (☆ の折りたたみ) は「/spell 行が書かれた位置」に置かれるため
   本文の先頭へ行き、Beat 1 の残り (独白) と Beat 2 (スペル結果を見た後の発言) が
   何の印もなく連結された。スペルセクションが Beat の境界に見えるのは、ペルソナが
   スペル行を Beat の末尾に書いたときだけの偶然だった。

## 原因

スペルが走った Pulse は、全 Beat の本文を 1 本のテキストに結合して、**1 つの部屋に
1 件だけ**保存する設計 (`docs/intent/voice_tts_pipeline_streaming.md` 不変条件 1、
2026-05-15 確立)。保存先の部屋は 1 つしか選べない:

- ストリーミング表示の経路は、生成開始時に下書き行 (placeholder) を**開始時点の部屋**に
  作り、移動後もわざとその部屋へ確定する (`sea/runtime_llm.py` の 2026-06-11 対処 —
  移動後の部屋を見に行くと更新が空振りして空の下書き行が残る不具合への応急処置)。
  → 全 Beat が**元の部屋**に落ちる (症状 1)。
- ストリーミングを使わない経路は、結合後に現在地を引き直して保存する。
  → 全 Beat が**移動後の部屋**に落ちる (Beat 1 を聞いた元の部屋から発言が消える、
  逆向きの保存先の取り違え)。

どちらの経路も「Beat ごとに部屋へ帰属させる」構造を持っていないことが根本の原因。

## 裁定 (2026-09-12 まはー GO)

**Beat ごとに、部屋の会話記録の別々の 1 件として保存する。** 1 Beat = 1 回の
LLM 生成 = 1 件の記録 = 1 音声ストリーム。

- Beat N の記録は「Beat N の生成が始まった時点でペルソナがいた部屋」に置く。
  スペル実行で移動が起きたら、次の Beat の記録は移動後の部屋に新しく作る。
- 下書き行の確定は「その行を作った部屋」に対して行う (2026-06-11 の不変条件は
  Beat 単位でも維持 — 確定時に部屋を引き直さない)。
- Beat の境界は記録の境界 = 吹き出しの境界になるので、スペルセクションの位置に
  依存せず境界が必ず見える (症状 2 の解消)。「1 Beat = 1 バブル」自体は
  `docs/intent/episode.md` §8 に既にある決定で、本件はその適用 — スペル入りの
  Pulse だけが結合で例外になっていた。
- あわせて、移動イベントの「〜が○○へ移動しました」の行き先の部屋名を
  `saiverse://building/<building_id>` のリンクにし、クリックでその部屋の表示に
  切り替えられるようにする (ユーザーは自動では付いていかないため、続きが
  ある場所への導線が要る — まはー発案)。

## 実装の契約

> この 8 点は、上の裁定 (まはー GO) から私 (メティス) が導いた実装設計。まはーが
> 承認したのは裁定の範囲で、契約の細部は検収と実機で差し戻せる。なお「Beat = 1 回の
> LLM 生成 = スペルループ 1 周」は正典 `docs/intent/beat_execution_context.md` §2.2 の
> 定義どおり。実装内の `BeatExecution` / `_finalize_beat` という名前はループ全体を
> 指していて正典とずれている (既知の命名負債。本件では改名しない)。

1. **記録の分割**: スペルループの各ラウンド (コード上の呼び名。1 ラウンド = 1 Beat)
   の本文 (スペル行の前の文 + スペルの `<user_only>` ブロック + スペル行の後の文) を
   1 件として、その Beat 開始時の部屋に保存する。「スペル行の後の文」とは、同じ
   1 回の生成の中でスペル行より後ろに書かれた文のこと (スペルの結果はまだ見ていない)。
   結果を見た後の発言は次の Beat。最終 Beat (スペル無しの締めの発言) も 1 件。
2. **部屋の解決タイミング**: Beat N+1 の記録先は「Beat N+1 の生成を始める直前」の
   現在地 (= 裁定の言う「Beat の生成が始まった時点でペルソナがいた部屋」)。
   スペル実行と次の生成の間に別の要因で移動が起きても、生成直前の現在地が勝つ。
   下書き行の確定は作成時の部屋に固定。
3. **聞いた人 (heard_by) / 同席者 (with)**: 各 Beat の記録の作成時に、その部屋の
   その時点の在室者から計算する (既存の作成時計算をそのまま使う)。
4. **メタデータの帰属**: 各 Beat の記録は自分のラウンドの LLM 使用量とスペルの
   activity_trace を持つ。~~Pulse 合計 (llm_usage_total = その Pulse の全 LLM 呼び出しの
   合計) は最終 Beat の記録にだけ載せる。~~ ← **2026-09-13 の実機確認で撤回**。
   スペルが走った Pulse では合計の札を出さない (下の「実機確認で出た 4 件」の 2)。
   使用量の数字は吹き出しに出す**表示専用の札**で、課金・使用量の集計は別の記帳
   (usage tracker) が持つ — 記録側の数字を横断集計する消費者を作らないこと
   (作ると Beat 分の llm_usage と二重計上になる)。
5. **UI イベント**: 吹き出しを作る・更新するイベント (streaming_chunk /
   streaming_complete / streaming_discard / say) に `building_id` (その記録が属する
   建物) を載せる。フロントは**閲覧中の建物** (ユーザーが画面で開いている部屋。
   サーバー上の現在地とは別) と一致しないイベントでは吹き出しを作らない
   (見ていない部屋の発言が今の部屋の画面に流れない)。
   抑止するのは吹き出しの生成・更新だけで、「返答が届いたか」の簿記 (サーバーの
   無言検出とフロントの鏡 `SERVER_OUTCOME_EVENT_TYPES`) には触れない。ユーザー宛の
   返答の Beat 1 は必ずユーザーのいる部屋で生成されるので、返答が丸ごと画面から
   消えることはない (消えるのはユーザーが自分で閲覧先を切り替えた場合だけ)。
6. **音声 (voice-tts)**: 1 Beat = 1 message_id = 1 音声ストリーム。Beat の切れ目で
   前の下書き行を finalize (stream close + wav 保存) し、次の Beat は新しい
   message_id で sub-speak (文区切りごとに音声合成へ渡す小分けの依頼) を積み直す。
   既存の「1 message = 1 stream」の機構をそのまま使う。
   **順序保証の追加工事が必要**: hook 配送の直列化 (addon_hooks の order_key) は
   これまで message_id 単位で、1 Pulse = 1 message の世界では Pulse 内の順序が
   全部守られていた。Beat ごとに message_id が変わると、Beat N の close と
   Beat N+1 の最初の sub-speak が別々のキーになり並列配送で追い越しうる
   (2026-05-16 のチャンク並び替え事故と同型)。order_key を pulse_id (無ければ
   message_id) に変えて、同じ Pulse の配送を Beat を跨いで直列化する。
   トレードオフ: 合成の立ち上がりラグが Beat ごとに 1 回になる (従来は Pulse ごとに
   1 回)。Beat の間にはスペル実行の待ちが元々挟まるので受け入れる (2026-09-12 の
   方針提示に「音声は Beat ごとのストリームになる」を含めてまはーが GO。実機で
   気になったら差し戻す)。既知の未解決 issue
   `voice_tts_streaming_audio_bleed.md` (wav の末尾欠け) は message 境界で出るもの
   なので、境界が増える本件で発現面が増えうる — 実機観察の対象に含める。
7. **ペルソナ自身の記憶**: 変更なし (SAIMemory は元から Beat 単位で記録している。
   spell_seq 列がその印)。
8. **移動イベントのリンク**: `OccupancyManager` の退出メッセージの行き先部屋名を
   `<a href="saiverse://building/<id>">部屋名</a>` にする。ペルソナはこのメッセージを
   本文経由では取り込まない (在室の変化は、プロンプト先頭部を組む機構
   (head pipeline) が差分通知として別経路で届ける) ため、ペルソナの知覚は汚れない。フロントは `saiverse://building/` リンクの
   クリックで、サイドバーの部屋クリックと同じ「表示の切り替え」を行う。
   サブパス無しの `saiverse://building/{id}` はこれまで未定義の形 (定義済みは
   `/items` と `/history` だけ)。画面の導線専用の形として
   `docs/reference/saiverse-uri.md` に同じ変更で追記する。ペルソナが発話にこの形を
   書いて解決した場合は、従来どおり「Unknown building path」の整然としたエラーが
   返る (資源の中身は無い) — 解決器の挙動変更なし。
   なお「本文経由では取り込まない」のは自動取り込み (occupancy イベントは読まずに
   済ませる) の話。ペルソナが自分から部屋の履歴を読みに行けば、従来の note-box の
   HTML と同じようにリンク入りの HTML も見える — 既にある道と同じで、新しい種類の
   汚染は増えない。

**取捨 (2026-09-13、三巡目レビューで確認)**: 中間 Beat の保存が失敗した回は、その
本文を建物の会話記録の別の 1 件として退避させる (発言は消さない)。このとき、画面に
出ていた吹き出しは中身の入らなかった下書き行の id を指したまま残るので、その吹き出し
に対する操作 (削除など) は空振りすることがある。同じ本文の吹き出しを 2 つ並べるより
こちらの害が小さいと判断して選んだ、稀な失敗経路の取捨である。

## 検証

- 単体: 2 ラウンドのスペルループで 3 件の記録が正しい順序・正しい部屋・正しい
  heard_by で残る / 移動スペルを挟むと Beat 2 以降が移動先の部屋に落ちる /
  下書き行の確定が作成時の部屋に対して行われる (移動後に引き直さない) /
  quick_spell (「この一言で完了」を宣言する即時スペル) だけのラウンドで締めの生成を
  省略したとき、空の Beat を作らない / ループ途中の失敗で確定済み Beat が残る。
- 実機 (隔離環境 → 本番): 症状 1 の再現手順 (同席者あり・移動スペル入り Pulse) で、
  元の部屋には Beat 1 だけ + リンク付き移動イベント、移動先に Beat 2 以降、
  元の部屋に残った同席者の取り込みが Beat 1 だけであることを確認。
  本番ペルソナで確認する場合は、その操作ごとにまはーの明示承認を得る
  (CLAUDE.md の Production Persona Safety に従う。この文書に手順が書いてあることは
  承認の代わりにならない)。

## 実機確認で出た 5 件 (2026-09-13 まはー観測、同日裁定)

Beat 分割そのもの (部屋への帰属・境界の可視化) は意図どおり動いたが、表示と音声に 5 件
(4 件を観測・裁定した後、同日に音声の 1 件が追加で出た):

1. **顔と名前が毎 Beat に付く。** 裁定: 同じペルソナの吹き出しが続く間は 2 個目以降で
   アバターと名前を省く。間に別の話者・システム通知・部屋の切り替えが挟まったら
   仕切り直して出す (別の部屋に移った先では顔と名前を見せたい — まはー)。
2. **使用量の札が二重に見える。** 各 Beat が自分の分を持ち、最終 Beat に Pulse 合計が
   付く作り (実装の契約 4) だが、合計は前の Beat の分を含むので並べて読むと重複。
   裁定: **合計の札を消して、各吹き出しは自分の分だけ** (2026-09-13)。正確な集計は
   使用量の記帳が別に持つ — 契約 4 の「合計は最終 Beat にだけ載せる」はこの裁定で
   「合計の札は出さない」へ置き換え。
3. **途中の Beat の音声の再再生ボタンが読み込み中の回転のまま押せない。** 最終 Beat は
   押せて、その Beat 分だけ再生される (これは 1 吹き出し = 1 音声の設計どおり)。
   直すのは回転の方 — どの吹き出しも自分の分を再生できる状態がゴール。
4. **「ふと浮かんだ記憶」のセクションが最終 Beat の吹き出しに付く。** 想起が起きたのは
   序盤の生成中なので時系列が逆。浮かんだ瞬間に生成中だった Beat へ付け替える。
5. **(2026-09-13 追加観測) スペルの行より後に書かれた文が、表示はされるのに一音も
   声にならない。** エリスさんの長い朝の挨拶が丸ごと無音になった。裁定: **普通に
   バグなので直す** (まはー)。生成の文を音声へ送る処理が、スペルの行を見つけた
   時点で以降の送出を全部止めていた — Beat 分割の前は「行より後ろは全部
   `<user_only>` に包まれる」が正しかったが、契約 1 で行の後ろの文は可視の本文に
   なったので、その前提は失効していた。

  断られたら従来の確定) を `_withdraw_if_nothing_was_said` に括り出し、
  **同族の三箇所** — 締めの Beat の正常復帰・Beat 出口の後始末・ストリーム中の
  停止 (`cancelled_during_stream`) — から呼ぶ形にした。これに伴い、本文ゼロの
  回に空文字で確定していた従来の挙動 (2026-08-27 の不変条件) は「行ごと取り
  下げる」へ改めた。medium 2 件 (記憶補填の材料に HTML 入りの本文を渡していた /
  中間 Beat の確定が失敗しても `emitted` を立てて発言が孤児になっていた) と
  low 4 件 (締めの Beat の使用量・イベントの名乗りと部屋の出どころ・自分の移動
  の note-box のエスケープ・`_emit_beat_segments` の戻り値) も対応。
- 2026-09-13 (実機確認で出た 4 件の実装): 顔と名前の省略は、吹き出しの持ち主を
  `persona_id` / `_persona_id` の一本化で同定して、直前が同じペルソナなら
  ヘッダを描かない形にした (ライブの `say` の吹き出しに持ち主が入っていなかった
  ので、そこにも名乗りを足した)。使用量は締めの Beat の組み立てを
  `include_total=False` にして合計の札を落とした (スペルなしの単一 Beat の経路は

  アドオンから知らせる本筋の直しは、音声アドオンのリポジトリ側の工事として残る。
  実機での確認はこれから。
- 2026-09-13 (レビュー 3 巡目): high / medium はゼロで、二巡目の消し込みは全部有効と

- 2026-09-13 (実機 5 とその従の直し): スペルの行を音声から外す処理を「見つけた時点で

  唱えごととして読む範囲と同じだけ飛ばす。ストリームが行の途中で終わった回は、その

  あったか) は変えていない — 呼び出し元 2 箇所はどちらも代入するだけで、「音声を
