## 共通の根 — 「どの生成の、どの段階の話か」を運ぶものが無い

切り出した 4 件は別々の顔をしているが、**一つのストリームについて「これはどの生成のことで、
いまどの段階まで進んだのか」を運ぶ仕組みが無い**という同じ欠落から出ている。

- この issue (retry の再送可能性をサーバーが見ていない) は**どの段階まで進んだか**が
  運べていない。その発言が既に応答を得たのかどうかを、発言自身が持っていない。
- [保存できたことを表す信号が無い](stream_completion_is_not_proof_of_persistence.md) も段階の話で、
  画面に出たところまでなのか DB に残ったところまでなのかを受け手が区別できない。
- [未知の送信結果から復旧できない](unknown_send_outcome_has_no_recovery_path.md) も段階の話で、
  発言がサーバーに残ったのかどうかを後から尋ねる手段が無い。
- [ストリームの表示に識別子が無い](streaming_events_have_no_identity_in_the_ui.md) は
  **どの生成の話か**が運べていない。断片がどのペルソナのどの Pulse のものかを、画面側が照合しない。

4 件を別々に補修すると、同じ判断が経路ごとに別の場所へ書き分けられる (この inventory の
レビュー 3 巡で繰り返し出た型)。**設計するときは 4 件を一つの束として扱う**のが安全で、
どれか 1 件だけを先に直す場合も、残り 3 件がその決めごとに乗れるかを見てから決める。

---

## 何が起きているか (コードで確認した事実)

`manager/runtime.py:1179-1229` の `retry_user_message_stream` が確かめるのは三つだけ。

1. 現在地があること (`:1183-1191`)
2. その発言を建物履歴から引けること (`:1194-1215` — 引けなかった場合は `history_unavailable`、
   見つからなかった場合は `message_not_found`)
3. その行の `role` が `"user"` であること (`:1207`)

**その発言が既に応答を得ているかどうかは見ていない。** 見ていないというより、発言の側に
「応答を試みた」「応答が付いた」という状態が無いので、見ようがない。

同時に二本走ることは `PulseController` が止める (ペルソナ単位の排他で、`user` 型は後勝ちに
前を中断する)。止まらないのは**逐次に二度走る**場合で、そちらには関所が無い。

## ユーザーから見て何が起きるか

通常の操作では起きにくい。「再送」ボタンは応答が無かったときに立つ印 (`needsRetry`) で描かれ、
その印はクライアント側の状態だから、普通に一つのタブで使っている限りは押せる場面が限られる。
踏むのは次のような場合になる。

- 古いタブを開いたまま別のタブで会話を進め、古い方に残ったボタンを押した
- 同じ発言への retry が並行して届いた (二重クリックはフロントで弾いているが、API は直接叩ける)

起きると、**既に答えた発言に対してペルソナがもう一度喋る**。両方が建物の記録とペルソナの記憶に
残り、一つの発言に二つの応答が並ぶ。後から片方を消すと記憶と履歴が食い違うので、消せない。

## なぜ補修で塞げないか

サーバー側に「その発言はもう応答を得た」と言える材料が無い。入口で数え上げて弾く形にすると、
古いタブ・API の直接呼び出し・将来増える入口を全部数え切る責任が生まれ、必ず漏れる
(この inventory の束 2 で、同じ理由から「結果を作る場所で一度だけ検査する」形へ寄せた)。

## 直すのに要るもの (設計の入口)

**発言ごとの応答試行状態を永続化して、原子的に claim する仕組み**。論点は三つ。

1. **状態をどこに持つか**。`building_messages` の metadata (JSON) か、専用の列か。metadata は
   JSON なので、条件付き更新 (claim) を一文で書きにくい。取り下げの
   `withdraw_building_message_in_db` が「確かめた時点の `ingested_by` を削除条件に入れる」形で
   同種の問題を解いているので、そこが先例になる。
2. **状態の語彙**。少なくとも「まだ応答が無い」「応答の生成中」「応答が付いた」。
   **「生成中」で止まったまま落ちた場合の回復**まで決めないと、一度落ちると永久にやり直せない
   発言が生まれる。歯止めを作って新しい行き止まりを作るのでは、意味が無い。
3. **[保存できたことを表す信号](stream_completion_is_not_proof_of_persistence.md) と同じものを
   別の角度から見ている**。「応答が付いた」を確定できるのは保存が終わった時点なので、
   **あちらの信号が決まらないと、この状態も正しく進められない**。設計は一緒に行う。
