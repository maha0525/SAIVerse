## 症状 (an nin さんの報告)

記憶整理のたびに「約束 update をスキップ」が 1 回の発言で最大 29 回連続する。同じ task_ref で、理由は「一覧にありません」(v0.3.16 更新後は「変更内容がありません」も混在)。task_ref の後ろに `合?` や `','content':'','x':'`、`告告告` などの文字が付いた崩れも見られた。

## 原因

約束欄 `promises` が、コア記憶側で 2026-08-24 に「危ない形」と結論して作り直した旧型のまま残っていた (同じ理由が当てはまる隣に手術が及んでいなかった)。

1. **必須欄が `op` 一本だけ**で、update なのに変更内容が空の要素が文法上作れる → 「変更内容がありません」。書きたい中身に対応する必須欄が無いため、飛ばした本文が後続の参照欄へ流れ込む崩れも作れる (型の規律 2 の違反形。noble_piglet さんの報告 4 回中 3 回でも併発していた)。
2. **task_ref が UUID (36 文字のランダム英数字) の丸写し**で、長いランダム ID を一字も違わず書き写させるのは LLM が最も崩しやすい形。コア記憶の参照が `core:N` の短い番号なのはまさにこれを避けるため。
3. 崩れた要素は照合で正しく弾かれる (推測で救済すると別の約束を書き換えかねない) が、弾かれ続けるためペルソナの意図した書き直しが構造的に全滅していた。

なお v0.3.16 の接頭辞修正 (PR #322) 自体は効いている — 「一覧にありません」一色だったのが「変更内容がありません」混在に変わったのは、参照の照合を通過して次の関門まで進むようになった証拠。残っていたのは schema の形そのものの問題。

## 実 API での検証 (2026-09-28、まはー承認、合成データのみ)

新 schema (下記) を、過去に壊れた実績のある Gemini 3 系 3 モデル (3.7-flash / 3.6-flash / 3.5-flash-lite) 各 10 回 + Claude Opus 5 系 6 回、本番相当の入力規模 (約 1 万トークン、フィード記事で膨らんだ合成会話) で叩いた。場面は「内容の変更」「期限だけの変更」「期限の撤回」「新規の約束」の 4 種を含む。

- **36/36 で構造は完全に正常。** 参照の崩れ・反復ループ・一覧外参照・本文の流れ込みはゼロ。
- 期限だけの変更は全モデルが content を省略して正しく書いた (content 任意の設計は 2026-09-28 のチャットでのまはー案「promise_updates で content を任意にするんじゃダメなの？」。「書きたいものの置き場 (必須欄) が先頭にあれば、後続の任意欄は事故らない」ことの実証)。
- 軽量モデル (3.5-flash-lite) だけ無害な粗が 2/36: 期限だけの変更に正しい内容を書き添えた回と、期限の無い約束に余分な clear_due を付けた回。後者に備えて適用側は「期限の無い約束への clear_due は、何も変えずに成功として記録する」とした。
- 表記は `task:N` と `promise:N` の両方で同成績。採用は `promise:N` — `task:N` は参照文法の正典 ([reference_addressing.md](../../intent/reference_addressing.md)) で目的の木の short_id を指す別の語なので、同じ字面を約束一覧に使うと本物の衝突になる。この選定はメティスの判断 (2026-09-29 時点でまはーの明示承認は未取得 — PR 確認が承認の場)。なお `promise:N` は参照文法には登録しない、スルースの応答欄の中だけで通じる語 (`act:N` と同じ扱い)。
- 実験スクリプトと生の応答 36 本はセッションのスクラッチパッド (`sluice_promise_probe/`)。実装の schema・プロンプト文言は実験で通した body と機械照合で完全一致 (鍵の並びまで) を確認した。

## 手当て (2026-09-28 実装)

- `promises` を廃止し、**`promise_adds` (content 必須・due 任意) / `promise_updates` (promise_ref 必須・content / due / clear_due 任意)** の二一覧へ。
- 一覧の表示を `[task:<uuid>]` から **`[promise:N]` (その場の連番)** へ。N → task_id の対応表はプロンプトと同じ並びから作り、実行台帳にも凍結する (再適用でも見せた番号と引く先がずれない)。新しいプロンプトでは UUID をペルソナに見せない・書かせない (過去の判断ターン記録に残った `[task:<uuid>]` 一覧はそのまま — 記録は書き換えない)。
- **位置で指す参照の制約 (整合性検査の指摘、v0.4 への引き継ぎ)**: `promise:N` は並びの位置であって安定 ID ではない — 参照文法の正典が「同一性の参照は安定させる」(位置参照 `b:N` を外した Q1 の決定) と定めた型からは外れる。v0.3 では約束を閉じる口が無く一覧は末尾に伸びるだけなので番号はずれないが、**v0.4 で完遂・撤回の口を開けると、過去の記録に残った番号と新しい一覧の番号が別の約束を指しうる** (照合値は「その約束が変わっていないか」しか守らない)。閉じる口の設計時に、安定した短い番号 (short_id) への移行か並びの凍結を必ず一緒に決めること。
- 適用側: 崩れた参照・一覧外の N はその一件だけ捨てて残りは適用する (要素棄却 — 従来どおり救済しない)。期限の無い約束への clear_due は何も変えずに成功として記録する (帰結: 空振りだけの回も「採取あり」に数えられ、判断ターン記録がコンテキストに残る側の扱いになる — 同一内容の追加をスキップして成功に数える既存の前例と同じ)。機構が組み立てる結果の行には `promise:N` ではなく約束の本文を書く (その場限りの番号は後から読む本人に意味を運ばない。本人名義の独白や、記録に写るプロンプト原文の中の番号はそのまま — 本人名義は書き換えない)。
- 記録がどの世代の形式で書かれたかを示す印を `promise2` へ。旧形式 (`promises` を持つ応答) の台帳記録は再利用せず別キーで採り直す (コア記憶の 2026-08-24 の仕組みと同じ)。追加の冪等キーも世代を分ける — 分けないと、採り直しの新しい追加が旧世代の行と同一視されて書かれない (重複の抑止は別にある本文一致の判定が担う)。前段 issue の「生 ID (UUID) もそのまま受け続ける」という決定は、この世代交代で前提 (旧記録の再適用) ごと失効した — 旧記録は再適用されず採り直される。
- 前段 issue の「残る食い違い」のうち**字面の衝突** (スルースの一覧表記が参照文法の `task:N` と同じ字面で別物を指す件) は、`promise:N` への変更で解消した。位置参照であること自体の制約は上の項のとおり v0.4 へ引き継ぐ。

## レビューで塞いだ守りの穴 (2026-09-28〜29 の消し込み)

作り直し本体とは別に、レビューが「壊れた記録・想定外の応答が来たときに守りが静かに外れる」穴を出し、全部塞いだ:

- **ローカル (Flash-Next、13 件中採用 3)**: 番号を振る側と引く側のフィルタ非対称 / 「期限なし」の記録文言が現在を断言する形 / 空振り成功と空 update 失敗の扱い分けの理由をコードに明記。
- **Codex 一巡目 (3 件)**: 照合値 (revision) が None の記録で CAS が実質無効になり古い判断がユーザー編集を上書きできる → 棄却に / 旧欄 (`promises`/`ops`) が混ざった応答で旧欄の中身が黙って消える → 全体棄却の関所を parser に (additionalProperties は Gemini が受けないため schema 側では縛らない) / 期限の記録の破損が「期限なし」と読まれ空振り成功に化ける → 「不明」を区別。
- **Codex 二巡目 (1 件)**: 凍結後に壊れた記録 (欄が null 等) の再適用が「採取ゼロで completed」になり操作が静かに失われる → 再利用前に記録の形を検査し、使えない記録は旧世代と同じ別キーの採り直しへ。採り直し先まで壊れていたら送出して人の裁定へ。
- **Codex 三巡目 (2 件)**: 要素の型が壊れた記録が検査を通過して再適用がクラッシュの無限ループになる → 再読で要素棄却が出た記録も破損扱い / 参照の対応表だけ壊れた記録が要素棄却のまま completed になる → 対応表の破損 (revision が int でない等) は記録ごと採り直しへ。期限・表示本文の破損だけは完全に適用可能なので非致命。

- **Codex 四巡目 (2 件) + 同種の穴を自分で探して 1 件**: 必須欄 (content / promise_ref 等) が null の要素が型検査を素通りし、破損検出の網に掛からない → 入口の検査で要素棄却に / 対応表の鍵の別表記 ("01")・空白だけの task_id・負の revision が破損と判定されない → 書き手が作る正しい表記だけ受理 / (自分で見つけた分) アクティビティ一覧の壊れた鍵が再適用の int() で例外化しクラッシュループ → 約束の対応表と同じ「記録ごと採り直し」へ。
- **Codex 五巡目 (8 件中採用 5)**: アクティビティ一覧の欠落が空扱いに丸まる非対称 / 鍵の別表記の正規化衝突 / task_id の前後空白 / 棄却記録が list でない記録での例外化 / 見た集合が空の記録の再適用 (書き込む側は空を凍結しない決まりなので、読み込む側も空を破損として扱う — 通すと見ていない会話の上を処理済みの印が進んで畳まれる)。

### 五巡目で採らなかった 3 件 (裁定の記録)

- **core_snapshot の欠落を記録ごと採り直しにする案**: 既存の裁定 (第五巡の系譜 —「旧形式の記録は再構成せず、update / remove は要素棄却」) が既にあり、挙動は可視 (判断ターン記録に残る)。この改修のスコープ外の再裁定になるため据え置き。
- **応答の参照と対応表の突き合わせ (部分削除の検出)**: 対応表の一要素だけが消える破損は要素棄却として可視に落ちる。任意深度の破損注入への防御は際限が無く、「操作が静かに失われる・クラッシュループする」形はもう塞いだので、ここで線を引く。
- **span の欠落を破損扱いにする案**: 前提が違う — span_end_id が None の記録は正規の書き手が作る正当な状態 (ID 付きの行が無い窓)。その場合にマーカーが進まないのは凍結前からの仕様で、この改修の退行ではない。
