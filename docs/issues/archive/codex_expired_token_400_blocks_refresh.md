# Issue: ChatGPT ログインの鍵が期限切れになると、Codex のペルソナが 400 エラーで話せなくなる

**ステータス**: ✅ 完了 (2026-11-27。修正は PR #521 で develop に入り、まはーの本番環境で鍵の自動更新と返事を確かめた。v0.3.35 に載る)

**関連**: [設計書 (intent): Codex サブスク認証の自立](../../intent/codex_subscription_auth.md) §9

## 全体と責任

ChatGPT にログインして Codex のモデルを使っている利用者とそのペルソナは、ログインし直さなくても会話が続くことを必要とする。ログインの鍵 (`access_token`、アクセストークン。設定画面と設計書に合わせて、この文書では「鍵」と書く) は発行から 1 時間で期限が切れるので、SAIVerse は期限切れの鍵を、更新用の鍵 (`refresh_token`) で取り直してから送る。処理の流れは「鍵を保存しているファイルから鍵を読む → OpenAI へ送る → 断られたら鍵を更新して送り直す → ペルソナの返事を受け取る」である。鍵の期限が切れているかどうかは、SAIVerse と OpenAI の両方が判定できる。鍵の中に期限 (`exp`) が書いてあるので SAIVerse 自身が読めるし、OpenAI も鍵を確かめて、切れていれば要求を断る。寿命の 1 時間は、まはーの鍵で二回測った値である (2026-11-07 14:50:39 の更新で期限が 15:50:39、2026-11-27 09:31:21 の更新で期限が 10:31:21)。

これまでの仕組みでは、OpenAI から 401 が返ったときにだけ鍵を更新していた。つまり、期限切れかどうかの判定を、OpenAI の返事に付くステータスコード (HTTP の返事に付く番号。401 や 400) ひとつに頼っていた。

## 起きたこと (2026-11-26〜27)

- 2026-11-26、利用者から「昨日から Codex でエラーが出て応答が返らない」と報告が来た。画面のエラーは `Codex backend returned status=400` で、本文は `{"error": {"message": "Bad Request", "type": null, "code": null, "param": null}, "status": 400}` だった。
- 2026-11-27 09:08、まはーの環境でも同じ本文の 400 が出た。このときの鍵は 11/7 15:50 に期限が切れていた。
- 同じ環境の過去のログでは、期限切れの鍵で送ったとき (10/19、10/21、11/7 の三回、いずれも `https://api.openai.com/v1/responses` 宛て) の返事は 401 で、本文は `token_expired` を含み、SAIVerse はそのあと鍵を更新して送り直し、返事が届いていた。
- 切り分け (2026-11-27): 期限切れの鍵で、履歴の無い一言だけの本文を送ると、モデル名を変えても、存在しないモデル名でも、同じ 400 が返った。でたらめな文字列を鍵として送ると 401 が返った。鍵を更新して同じ一言を送ると 200 が返った。変えたのは鍵だけなので、400 の原因は鍵の期限切れだった。
- 会話の中身 (動画・画像・履歴の長さ) とモデル名は無関係だった。報告者のペルソナが挙げた「動画の履歴が原因」という説明は当たっていない。
- 失敗した回に失われたのはペルソナの返事だけで、利用者の発言は記憶に保存されていた。

OpenAI が期限切れの鍵への返事を 401 から 400 に変えた日は分からない。まはーの環境で最後に 401 を見たのは 11/7、報告者の「昨日から」は 11/25 ごろを指す。報告者の環境のログは見ていないので、報告者が同じ原因だという判断は、エラー本文の形が完全に同じという一点に基づく推測のままである。

## 原因

1. **直接の原因**: `OpenAICodexClient._post_with_auth_retry` で、`CodexHTTPError.status_code == 401` のときにだけ鍵を更新する作りになっていた。OpenAI が同じ状況で 400 を返すようになり、鍵の更新が一度も実行されなくなった。
2. **そう決めた判断の誤り**: 期限が切れているかどうかは、鍵に書いてある期限から SAIVerse 自身が判定できた (送る直前に「もう切れている」という警告まで出していた) のに、更新を始める合図を、文書化されていない OpenAI のステータスコードに頼っていた。相手の返事は合図の一つであって、手元で分かる状態の代わりにはならない。
3. **それを通した条件**: 設計書 (intent) の「未検証の境界」(まだ確かめていない点を並べる節) に、期限切れの鍵に OpenAI がどう答えるかが載っていなかった。テストでも「401 が返ったら更新する」場合しか確かめておらず、「期限切れの鍵で 401 以外が返ったとき」を確かめる観点が抜けていた。

## 直し方

目的は一文で言える: **期限切れの鍵を理由に断られた要求を、利用者に失敗として見せない。**

- **送る前**: 鍵の期限を読み、この PC の時計で切れているか残り 60 秒以下なら、送る前に鍵を更新する。OpenAI の返事の形に頼らない。この更新が失敗しても要求は止めず、手元の鍵のまま送る。残りが数十秒ある鍵や、時計が進んでいて切れて見えるだけの鍵は、そのまま通るからである。
- **断られた後**: 401 に加えて、401 以外の 4xx でも、送った鍵が OpenAI の時刻 (返事の `Date` ヘッダー。無ければこの PC の時計) で期限切れだったなら、鍵を更新して一度だけ送り直す。この PC の時計が遅れていて「送る前」の判定をすり抜けた場合を拾う。
- **時計が進んでいる PC で更新を打ち続けないための歯止め**: 最後のログインか更新 (鍵を保存しているファイルの `last_refresh`) から 5 分以内なのに期限切れに見える場合は、送る前の更新をせずにそのまま送る。更新した直後の鍵が期限切れに見えるのは時計が進んでいるときで、この歯止めが無いと要求のたびに更新する。歯止めがあっても、時計が 1 時間より大きく進んでいる PC では 5 分に一度の更新が続く。
- 期限を読めない形の鍵は、従来どおり 401 のときだけ更新する。
- ChatGPT ログイン (`api.openai.com`) と旧方式 (`chatgpt.com/backend-api/codex`) の両方に同じ規則を当てる。

直す場所は `OpenAICodexClient._post_with_auth_retry` とその周辺 (`llm_clients/openai_codex.py`) である。OpenAI へ送る処理はここ一つで、返事を作る呼び出し (`generate` / `generate_stream`) は全部ここを通るので、ここで守れば全部の呼び出しに効く。鍵の更新そのもの (`_refresh_or_pickup_latest`) は変えていない。

## この修正で残るもの

- 鍵の更新そのものが失敗する場合 (更新用の鍵が失効している、ネットワークが切れている): 送る前の更新の失敗では要求を止めず、手元の鍵のまま送る。OpenAI がその鍵を期限切れとして断ったら、もう一度更新を試み、それも失敗したときに「設定画面からログインし直してください」の案内が出る。案内の文面は従来と同じで、従来と違うのは、案内の前に更新を二回試みることである。
- 鍵の更新が走っている間は、停止ボタンを押しても、更新が終わるまで止まらない (通常 1 秒未満、最長 60 秒)。更新を途中で打ち切ると、使い終えた更新用の鍵だけが手元に残ってログインが壊れるので、打ち切れるようにはしていない。更新が終わった時点で停止を確かめ、止められていれば要求は送らない。従来の 401 の流れにも同じ待ちがあった。
- **最後のログインか更新から 5 分以内に保存された鍵は、期限切れに見えても、使える鍵として扱う (「直し方」の「時計が進んでいる PC で更新を打ち続けないための歯止め」。設計書 §9 の規則 3)。** 別のプロセスが、実際に期限の切れた鍵を、`last_refresh` を今の時刻にして保存した場合は、その鍵を一度送って断られ、その要求は失敗する。次の要求では、断られた鍵が保存されたままなので更新が走り、回復する。SAIVerse 自身が `last_refresh` を書くのは、発行されたばかりの鍵を保存するときだけである。だからこの場合が起きうるのは、Codex CLI の `auth.json` に相乗りしていて、CLI が期限切れの鍵と新しい `last_refresh` を一緒に書いたときに限られる (CLI がいつ `last_refresh` を書くかは確かめていない)。
- OpenAI が、期限切れの鍵に 4xx 以外 (5xx、200 の中のエラー、無応答) で答えるようになり、かつこの PC の時計が 60 秒より大きく遅れている場合は、この PC の時計が期限を過ぎるまで失敗する。起きる条件が二つ重なるので、手当てしていない。
- 同じ形 (相手のステータスコードひとつを合図に、手元で分かる状態の回復を始める) が他のクライアントにあるかは、鍵の更新を持つクライアントが Codex だけであることまでしか確かめていない。

## 検証

- 単体テスト (`tests/llm_clients/test_openai_codex_siwc.py`): 実際の通信はせず、テスト用に用意した応答を使って、送る前の更新・断られた後の更新・PC の時計が進んでいる場合と遅れている場合・更新の失敗・送り直しが一度だけであることを確かめる。
- 実際の OpenAI で確かめたのは、「期限切れの鍵は 400」「更新した鍵は 200」の二点 (2026-11-27、修正前のコードの外から一言の本文で)。
- **実際の OpenAI での確認**: 2026-11-27 12:02、まはーの本番環境で、修正を入れて再起動した後の最初の Codex への発話で確かめた。鍵は 1 時間半前に期限が切れていて、`backend.log` には「期限切れなので送る前に更新する」→ 鍵の更新 → 送信 → 返事の順で記録され、400 は出なかった (まはー「OK問題なし！特に再ログインとかせずとも喋れたよ」)。
- **まだ確かめていないこと**: 旧方式の接続先 (`chatgpt.com/backend-api/codex`) が期限切れの鍵に何を返すか。PC の時計がずれている環境での動きは、手元の偽の OpenAI サーバーでだけ確かめた。

## 経緯

- 2026-11-27: 利用者の報告を受けてまはーの環境で再現し、ログの比較と切り分けで原因を確定した。同日に修正を実装した。
- 2026-11-27 (検査で見つかって直したこと): 設計書の整合性を確かめる検査で、「送る前の更新が失敗すると、まだ使える鍵の要求まで止まる」問題が見つかり、失敗しても送る形に変えた。Codex を使った問題点を探すレビューで、次の 3 件の指摘が出た。(1) この PC の時計が 1 時間より大きく進んでいると、同時に来た要求の数だけ更新が走る — 更新の直前にも「最後の更新から 5 分以内か」を見る形に直した。(2) 断られた後に鍵を更新する処理で、送った鍵ではなく保存されている鍵を基準にしていたため、別の要求の処理で先に鍵が更新されていても余分に更新してしまっていた (401 では従来からあった) — 送った鍵そのものではなく、元の鍵に戻せない照合用の値 (ハッシュ値) を控えて照合する形に直した。(3) 鍵の更新の間は停止ボタンが効かない — 途中で打ち切るとログインが壊れるので直さず、「この修正で残るもの」に記録した。
- 2026-11-27 (問題点を探すレビューの二巡目): 2 件。(1) 送った鍵と保存されている鍵の照合を、鍵を保存しているファイルをロック (他の処理と同時に読み書きしないようにする制御)する前の読み取りで行っていて、その読み取りが失敗すると「違う鍵」と扱ってしまう — ファイルをロックした後に照合する形に移した。(2) 5 分以内に保存された鍵を、期限切れに見えても使える鍵として扱うので、実際に期限切れの鍵が新しい `last_refresh` と一緒に保存されていると一度失敗する — 起きうるのが Codex CLI への相乗りの特定の場合に限られ、次の要求で回復するので直さず、「この修正で残るもの」に記録した。
