## Beat の一生 (ストリーミング会話の場合)

会話の応答を作る Beat は、時間軸で見ると七つの区間を順に通る。コード位置は
`sea/runtime_llm.py` の `lg_llm_node`。

| 区間 | 何をしている時間か | 目印 |
|---|---|---|
| A 順番待ち | Pulse がキューにいて、Beat がまだ始まっていない | `PulseController` |
| B 支度 | node に入り、プロンプトを組み立てている。下書き行はまだ無い | node 頭の取り消し点 (`:3150`) |
| C 思考 | LLM ストリームの前半。reasoning が流れ、本文はまだ一文字も無い | 下書き行は発番済み (`:3892`) |
| D 本文 | LLM ストリームの後半。本文の断片が画面と音声へ流れている | `_consume_pipeline_stream` |
| E 完了処理の入り口 | ストリームは流れきり、スペルラウンドを回している | `_run_spell_loop` (`:4027`) |
| F 確定後の隙間 | 下書き行は本文で確定済み。だが記憶への書き込み (memorize) はまだ | `:4207` 確定 → `:4439` `_finalize_beat` |
| G Beat 完了後 | 記憶まで書き終え、次のノードへ | — |

## 区間 × 原因の表

「画面」「建物の記録」「本人の記憶」「再開手段」の四つがどうなるかを、原因別に並べる。
✅ = 設計どおりに揃う。🕳️ = 穴。コードを読んで確認した事実には (コード確認)、
実機で見た事実には (実機確認) を付ける。無印の推測は残していない。

### 原因 1: ユーザーの停止

| 区間 | 何が起こるか | 判定 |
|---|---|---|
| A・B | 何も書かれていないので、何も残らない。画面は静かに止まる | ✅ 消えるものが無い |
| C 思考中 | 下書き行は空文字で確定 (発言消滅は防がれる)。通告・印・記憶は無し (8/26 裁定「一言も出ないうちに止められた回は何も語らない」のとおり)。**ただし画面には思考の吹き出しが浮いたまま残り、リロードすると消える。そして再開手段が無い** — 本文ゼロなので「続きの生成」は成立せず、ユーザーの吹き出しに「再送」も出ない | 🕳️ **穴 1** (実機確認 2026-08-27) |
| D 本文中 | 部分文で確定 + 印 + 記憶 + 通告 + その場で「続きの生成」 | ✅ (実機確認 2026-08-27) |
| E 完了処理の入り口 | スペルラウンドの頭で取り消しが立ち、Beat の出口の後始末が D と同じ形に揃える | ✅ (2026-08-27 実装。単体テストのみ、実機は未) |
| F 確定後の隙間 | この区間に停止の割り込み点が無い (次の取り消し点は次ノードの頭で、記憶の書き込みはその前に終わる)。発言は完全に残る | ✅ (コード確認) |

### 原因 2: 例外 (LLM エラー等) で Beat が死ぬ

| 区間 | 何が起こるか | 判定 |
|---|---|---|
| A・B | 何も書かれていない。エラーはイベントで画面に届き、ダイアログ + ユーザーの吹き出しに「再送」 | ✅ (束 2 の出口 3) |
| C 思考中 | 下書き行は空文字で確定 (静かに)。その後エラーイベントが届いて「再送」が出る。浮いた吹き出しの問題は停止と同じ | ✅ 再開手段はある (コード確認) |
| D 本文中 | 途中経過の器から部分文を回収して確定 + 印 + 記憶 + 原因を書かない通告。エラーイベントも別に届く | ✅ (2026-08-27 実装。狙って踏めないため実機は未) |
| E 完了処理の入り口 | D と同じ。ただし**スペルの retry 中の途中死**だけは、retry 分の部分文が spell loop の降格契約に吸われて記録に残らない (既知・[orphaned_streaming_placeholder_cleanup](orphaned_streaming_placeholder_cleanup.md) の 2 巡目見送り) | ⚠️ 既知の限定 |
| F 確定後の隙間 | **確定済みなので出口の後始末はスキップされ、memorize はまだ走っていない。建物の記録には全文が残るのに、本人の記憶には残らない** — 「世界には刻まれたのに本人だけが覚えていない」が、逆向きの窓でまだ開いている。窓は狭い (確定からの数十行: 完了イベント送出・メタデータ組み立て・`_finalize_beat` 冒頭) | 🕳️ **穴 3** (コード確認) |

## 別経路 — 上の表に乗らないもの

### tool-streaming 経路 (ツールを持つ playbook の応答)

この経路には下書き行が無く、停止フラグ (`cancelled_during_stream`, `:3449`) を立てた後、
**誰もそのフラグを読まない** (コード確認)。停止で break した後の流れはそのまま続き、
途中までの本文が `_emit_say` で**言い切った発言として**記録される — 印なし・通告なし・
「続きの生成」なし。ユーザーは止めたのに、発言は完成の顔で世界と記憶に載る。
pipeline 経路の「印が無い」(既知) より一段悪い: **停止の意図そのものが握り潰される**。
実機では未確認 (まはーが踏んだのは pipeline 経路のみ)。 → 🕳️ **穴 2**

### 非ストリーミング経路 (response_schema 付き / streaming 無効)

「途中まで」という概念が無く、本文は全部か無かのどちらか。停止してもブロッキングの
LLM 呼び出しは打ち切れず、完走後に次の取り消し点まで進む。**取り消し点に届く前に
say と memorize を通るのか、その場合 cancelled 後のイベントを画面が捨てて「発言が
世界に残るのに画面に出ない」形になるのか — ここは未確認** (コードを最後まで辿って
いない)。 → ❓ **要確認 4**

### 下書き行の発番自体が失敗した回との複合

`_emit_speak_start` が失敗して下書き行が無いまま本文が流れ、その途中で Beat が死ぬと、
出口の後始末は対象を持たず (msg_id 無し)、正常完了時の救済 (`_emit_say` フォールバック
`:4227`) にも届かない — 流れた本文が失われる。発番失敗自体が稀 (ログに ERROR が残る)
なので優先度は低い。 → 🕳️ **穴 5** (コード確認・稀)

## 裁定 (2026-08-27 深夜、まはー)

- **穴 3 を最優先で直す。** 洗い出し時の私の順位づけ (穴 1・2 優先) をまはーが正した —
  穴 3 は**唯一、記憶の欠落を作る穴**で、しかも無症状。発生しても誰も気づけず、症状は
  後日「本人が自分の発言を覚えていない」という形でしか出ない。「稀なタイミング × 無症状」は
  32 件の発言消滅と同じプロファイルで、記憶の連続性は UI の再開手段より上位。
  → 直し方: 「建物へ確定したか」と「記憶へ書いたか」の印を分け、Beat の出口で
  「確定済みだが記憶が未了」なら記憶だけ補う。補う材料 (全文) はその場にある。
- **穴 1 は (a) だけ直す** — 本文ゼロの停止で浮いたままになる思考の吹き出しを畳む
  (リロードで消えるものを画面に残さない)。**(b) 再開手段は追加しない** — 停止は
  「この応答は要らない」という意思表示で、直後に再送を勧めるのは矛盾する。応答が
  欲しければ話しかければよく、エラーの回には既に再送が出る。
  - **改訂 (2026-08-28、まはー)**: 実機で (a) を確認した上で「需要を捉えていない」と
    差し戻し。思考中に止める動機はほぼ間違いの訂正 (モデル違い・途中送信) で、発言は
    もうペルソナの記憶に積まれて取り消せない以上、口を全部塞ぐと新しく話しかけるしか
    なくなる。既存の「再送」は送り直しではなく応答だけを求めるボタンなので、エラーで
    返事が生まれなかった回と同じ印を停止にも立てる。「(b) 再開手段は追加しない」の
    元の理屈は本文が出てからの停止 (言いかけの続きを勧めない) の話で、返事ゼロの回に
    まで広げたのが誤り。勝手な再開はしない点は変わらない — 回復はユーザーの一押しの
    後ろに置く。
  - **付記 (同日、まはー)**: 「もう読まれているから取り消せない」も恒久の裁定ではなく、
    「記憶まで安全に操作できる経路を作る暇がまだ無いから、やらない」が正しい位置づけ。
    Claude Code の巻き戻し・ChatGPT の編集/再生成に相当する世界線分岐は、いずれやる
    べき機能として `docs/overview/ideas.md` (既読発言の巻き戻し) に記録した。
- **穴 2 は直さず、地雷として記録して寝かせる。** tool-streaming を通る playbook は
  現存しない (builtin の現役と DB の全 playbook に `available_tools` はゼロ件、
  該当は archive 送りの旧 autonomy 系のみ — 2026-08-27 に読み取りで確認)。
  ツール付きノードを復活させる日に、pipeline と同じ後始末 (途中本文に印を付けて
  残し、続きの生成を出す) へ合流させること。それまでこの経路は**停止を握り潰す**
  (`sea/runtime_llm.py:3449` でフラグを立てた後、誰も読まない)。
- 穴 4 (非ストリーミングの停止の挙動) は未確認のまま残る。穴 5 は記録のみ。

## 実装 (2026-08-27 深夜)

**穴 3 — 記憶の補填** (`sea/runtime_llm.py`):

- memorize の「`_store_memory` 呼び出しの組み立て」を `_store_beat_memory` に抽出し、
  通常の確定 (`_finalize_beat`) と補填が同じ組み立てを共有する (複製すると「死に方で
  記憶の形が変わる」乖離が育つ)。
- 「この Beat の本文は記憶に書かれた」の印 `state["_beat_memorized"]` を新設。
  立てる場所は memorize 成功時・important dual-write 成功時・停止の後始末
  (`_settle_interrupted_utterance`) の記憶書き込み成功時の三つ。Beat の入り口で必ず倒す。
- Beat の出口に `_backfill_memory_on_beat_death` — 「確定済み・記憶未了・記憶に書く
  設計のノード・本文あり」の回だけ、memorize と同じ組み立てで一度書く。
- `_finalize_beat` の呼び出しは except 節の外にあったため、その内部 (memorize 手前) の
  死は補填に届かなかった — 呼び出しを try で包み、補填してから元の例外を通す
  (検収で発見して追加した残り窓)。
- テスト 8 本 (`tests/test_streaming_placeholder_salvage.py`): 確定後死の補填・印に
  よる二重書き防止 (memorize 済み / settle 済み / `_finalize_beat` 内 memorize 済み)・
  memorize 設定なしノードの不発火・`_finalize_beat` 内死の補填。

記憶書き込み完了 23:50:02 → `[shutdown] complete` 23:50:03。**「応答完了を待つ」処理は
存在しない** (main.py の終了は SIGTERM/atexit 経由、uvicorn の猶予は 5 秒) — 終了処理が
各部品を止めている 2 秒の間に生成がちょうど完走した同着で、生成ワーカーは daemon
スレッドなので、生成があと 10 秒長ければ途中で殺されて発言は消えていた見込み。
**強制終了 (taskkill /F) での事故死テストは未実施** — 予想は「下書き行が未確定で残り、
発言は消える」。プロセス内の後始末はプロセスの死には無力で、この領域を受け持つのは
[orphaned_streaming_placeholder_cleanup](orphaned_streaming_placeholder_cleanup.md) の
候補 3 (起動時に残った下書き行を掃いて通告を出す)、未実装。

裏取りの結果、大半は既存の形 — ①待機列 (queued → 台帳 accepted で前進) は元々

#### 裁定 — 帳簿は変更しない (2026-08-29 深夜、まはー)

「取り消しの由来で分類を変える」実装に一度着手したが、まはーが止めて議論からやり
直し、四つの問いの降下で設計ごと覆った。経緯は将来同型の問題を踏む者のために残す。

1. **帳簿は何のためにあるか** — 予定の発火を「消えない・二重に走らない」にする記録。
   複雑さの源は、LLM 実行の取り消せない副作用 (課金・発言) ゆえに「不明」を正直に
   扱う必要にある。語彙は「完走 / 何も起きていない / 不明」の三択で設計されており、
   今回の作業が生んだ第四の状態「途中まで走り、途中までの結果は記録済みと確実に
   分かっている中断」の置き場が無い — 議論が紛糾した根はここ。
2. **「予定」の分解** — 規則 (登録行) / 今日のぶん (occurrence) / 今回の試み (attempt)
   の三層で、帳簿が判定するのは「試みが完走したか」だけ。しかも一回の試み = 1 Pulse
   であり、帳簿が見えるのは「合図を届けた 1 Pulse が完走したか」まで。「散歩が
   果たされたか」は誰も判定していない (できない)。
3. **完了の意味は機械には決められない** — 決定打はソフィーの 0 時リマインドメール:
   意義はメール送信 (Pulse 途中のスペル) にあり、送信後の発言が中断された回を
   「未完了」と分類して再発火させると**メールが二重送信になる**。逆に最後の発言まで
   が本体の予定も、一言でも喋れば用が済む予定もある。完了の意味は登録者の意図の中に
   しかない。
4. **間違い方の非対称** — 誤って再実行すると取り消せない副作用が二重になる (害は
   無制限・非可視)。誤って再実行しないと失われるのは「その回の残り」だけで、しかも
   中断の事実は本人の記憶と画面に残る (本 issue の Ctrl+C 対応がそれを保証した)。
   よって機械が守れる規則は「中断された回を勝手にやり直さない」の一つ。

**結論**: 中断 → 帳簿上「済み」で封印、という現行の挙動は原理として正しく、変更
しない。イレギュラーな停止に対して「途中までを記録し、中断の事実を記録し、本人が
認識できている」なら最小限の最善である (まはーの言葉)。将来の拡張は**登録者が予定
ごとに「失敗時は再実行する」フラグを宣言できるようにする**こと (ideas.md へ記録) —
機械が意味を推測する道は塞いだまま、意味の持ち主だけが例外を開ける。

未確認の尻尾 (記録のみ): 本当の事故死 (taskkill・電源断) では締めの処理が走らず
台帳が prepared のまま残る。回復機構がそれを再発火するなら、そこにも同じ二重送信の
芽がある — どう扱われているかは未調査。
