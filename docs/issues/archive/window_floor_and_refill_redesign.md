# 会話窓の最終防衛ラインと読み戻しの立て直し (2026-09-04)

ステータス: ✅ 完了 (2026-09-04 なかみつさんの実機で、v0.3.7 更新後に会話が窓へ戻ることを確認)。裁定: まはー 2026-09-04 未明。図解: 「読み戻しの立て直し」(Claude artifact 1c5a7f65)。

## 何が起きたか (konoe さん、v0.3.3、2026-09-03)

1. 19:34 / 19:44 JST — 手動の畳み (残す量 18,000): 畳める側の材料が 9,684 字で一束 (U=10,000) に満たず、何もしない。設計どおり。
2. 19:50 — あらすじタブの生成ボタン (`mode=repair`、全量計画)。要約してよい上限 `resolve_compile_ceiling` は**温かい起点の記録**だけを候補にする。最後の返答から 38 分 (TTL 既定 1,200 秒) で全行が冷えていて上限なし → 生きている会話窓 51 件を全部一次あらすじ 2 件にした。**これがバグ。**
3. 同 19:50 — 後始末 `mark_covered_cold_windows` が、冷えた記録 (現役の gemma4 の記録と gemini paid の記録を含む) に圧縮区間の印を書いた。窓が生 51 件からあらすじ 2 枚の表示に変わった。設計どおり (入力が壊れていた)。
4. 20:22 / 20:43 — 冷えた起点の前進 (機構1) が、あらすじの右端 (パンマーカーで頭打ち) まで起点を進めた。窓 = あらすじ B の末尾 3 件を digest で見せる圧縮区間だけ ≈ 945 字。設計どおり。
5. 以後 — 読み戻し `plan_rewind` は「窓に記録済みの圧縮区間に属するメッセージに出会ったら左へ行かない」規則で、起点をまたぐ B (25 件が起点より左) の一歩目で止まる。開き直しだけが効き、B の末尾 3 件が生に戻った。再起動しても同じ。**戻らない原因。**

会話 51 件は memory.db に全部残っている。消えたのは「窓に何を見せるか」の記録の側。

## 三つの原因

- **直接の原因**: 要約の上限が「温かい = 生きている窓」と同一視している。冷えた = 20 分黙っただけで、メンテナンスのボタンは会話を止めてから押すのが普通なので、いちばん普通の使い方でちょうど破れる。
- **判断の失敗**: 読み戻しに置いた守り (またぐ区間に近づかない / 覆われていない会話を跨がない / 見積もりより多ければ全部やめる) は全部「多すぎる」側だけを恐れていて、「ペルソナが自分の会話の記憶が無い状態で喋る」側の恐れを一度も式に書いていなかった。レビュー指摘に一つずつ「迷ったら何もしない」で応え、機構の仕事 (残す量を確保する) に照らして検算していない。
- **通した工程**: 「窓の会話は残す量を下回らない」という契約がテストに無かった。最終検算が「残す量を超えたら捨てる」(目標達成で取り消し) という自己矛盾を持っていても赤にならなかった。

## 不変条件 (最終防衛ライン)

**ペルソナは、窓の会話が残す量を下回った状態で発話しない。埋める材料 (起点より古い会話) があるかぎり。**

## 設計

### 0. 最終防衛ライン (先に入れる。これが入れば残りをどう間違えても被害が出ない)

- 場所: `sea/runtime.py::run_meta_user` の、非常畳み → 読み戻し の直後、`_run_playbook` の直前。ユーザー Pulse だけでなく全 pulse_type に置く (自律の発話も発話。軽量モデルの窓は、そのモデルの水位が無ければ従来どおり skip)。
- 中身 (`SessionLifecycle.ensure_window_floor(persona, building_id, model_key)` を新設):
  1. 水位が無ければ skip。起点を `resolve_metabolism_anchor` で解決 (通常どおり)。窓を撮る。
  2. 窓の**保存行**の字数 (`stored_message_chars`、知覚は数えない) が残す量以上なら skip。
  3. 不足なら、`history_manager.get_history_before_anchor(anchor_id, max_chars=不足分, required_line_roles=["main_line"], required_scopes=["committed"])` で古い方へ生のまま読み足す。材料が無ければ skip。
  4. 新しい起点 = 読み足した最古の行。読み足した範囲を覆う一次あらすじがあれば (`get_entries_covering_messages`)、その範囲を `presented_raw=True` の圧縮区間として記録する (head の除外名簿に載せて二重提示を防ぐ)。覆うものが無い範囲は記録なし (生のまま)。窓に既にある圧縮区間で、読み足した範囲にかかるものは `presented_raw=True` にする。
  5. 書き込みは読み戻しと同じ CAS (`_write_refill`)。head の再 capture も読み戻しと同じ。
  6. 発火したら WARNING `[metabolism] window floor applied ...` と、context-status に `window_floor_applied_at` (最後に発火した時刻、無ければ null)。発火 = 上流 (読み戻し) の失敗の印。
  7. 結果は三値。`skip` = 水位なし / 行が残す量以上 / 起点より古い会話が無い (新規ペルソナなど。正常)。`ok` = 読み足した (古い会話の合計が不足分より少なくても全部読んで ok)。`unmet` = 材料はあるのに例外・DB 書き込み失敗・CAS 不一致が再計画 1 回でも続いた。**unmet ならその Pulse の発話を見送る** (ユーザー Pulse には error イベント、自律 Pulse はログのみ) — 不変条件が発話より優先 (まはー 2026-09-04)。Codex 一巡目の指摘で fail-open だったのを直した。
- テスト `tests/test_window_floor.py`: (a) 起点より古い会話が残す量以上あるとき、フック後の窓の保存行 ≥ 残す量。(b) 読み戻しが None を返す形 (起点をまたぐ圧縮区間) でも (a) が成立。(c) 保存行が残す量以上なら何も書かない。(d) 古い会話が無ければ何も書かない。(e) 覆うあらすじがある範囲は presented_raw の圧縮区間として記録される。

### ① 生成ボタン (全量計画) が要約してよい上限

- `sea/coverage_repair.py::resolve_compile_ceiling` の候補 = 温かい記録 ∪ **ペルソナの現在モデルの記録 (温度不問)**。現在モデルは呼び出し側が `resolve_execution_context(persona, None, state={}).model_key` (runtime.py の非常畳みと同じ導出) で求めて渡す。
- 現在モデルの記録は、候補にする前に `resolve_metabolism_anchor(persona, model_key=現在モデル, persist_advance=...)` を通した位置を使う (冷えた起点の前進を済ませた後の起点)。実走 (`generate_chronicle`) は persist_advance=True、見積もり (`estimate_chronicle_generation_cost` 側) は False。表示と実走が違う数を言わない。
- 記録が一つも無い場合の下限: 現在モデルの水位の残す量ぶん (編纂対象の保存行を新しい側から数えて) は要約しない。上限 = その位置。水位も無ければ従来どおり全域。
- `mark_covered_cold_windows` は触らない。
- テスト: 全行が冷えていても上限 = 現在モデルの起点 / 記録なしなら新しい側の残す量ぶんが残る / 見積もりは行を書かない。

### ② 起点をまたぐ圧縮区間

- `SessionLifecycle._plan_window_refill` に前段を足す: 窓の圧縮区間のうち `message_ids` が `window.raw_ids` の外 (起点より左) に及ぶものを「またぐ区間」とする。あれば、まず起点をその区間の最古の行まで戻し、区間を `presented_raw=True` にする。**予算に関係なく必ず行う** (開こうとしている時点で不足は確定)。
- そのあと残りの予算で従来の `plan_rewind` を続ける。`plan_rewind` からは (a) 「既存区間の領土には踏み込まない」打ち切り (before_messages の切り詰め) と (b) `broken |= sources & already_folded_message_ids` を外す。またぐ区間の `message_ids` は「覆われている」側に数える (forgotten 判定で止まらない)。
- 段の source が窓の既存区間の行と交差するときは、新しい区間を足さずその既存区間へ併合する (行・あらすじ id を広げ presented_raw)。書き込み直前に「各行は高々一つの区間に属する」を検査し、重なりは併合する (Codex 一巡目 #5)。
- 前段の切り位置は「起点の行、または窓の生の行に当たった所」— 起点の行が提示対象外 (scope=discardable、本番の konoe さんの起点がこれ) でも前段が届く。
- テスト: またぐ区間 → 起点が区間の先頭へ、presented_raw、行が戻る。そのあと予算内で古い段も戻る。

### ③ 最終検算が見る線

- `_plan_window_refill` の最終検算は **`watermarks.high` (整理をはじめる)** と比べる。残す量とは比べない。比べる量は上限の契約どおり「実際に送る合計」(`presented_chars`、知覚込み)。

### ④ 上限を超えたときの削り方

- `plan_rewind` の戻り値に、受理した段を新しい順に並べた `steps` (各段: その段まで戻した場合の anchor と圧縮区間) を持たせる。最終検算で超えたら、**いちばん古い段から一段ずつ外して測り直し**、上限の下に入ったところで止める。「全部やめる」は無し。② の前段 (またぐ区間) は外さない (超えるなら WARNING を出し、次の Pulse の非常畳みに任せる)。
- テスト: 超過 → 最古の段だけ外れる / 上限以下なら全部残る / 残す量と比べていない。

### ⑤ 読み戻しが見送る理由のログ

- `_plan_window_refill` が None を返す各経路に INFO: 不足なし / 材料なし (before 空) / 覆うあらすじなし / 段が壊れている (どの段・不足 id 数) / 忘れた過去に当たった / 予算超過。

## レビューで見送った指摘 (既知として記録)

- 非常畳みの水位判定 (`maybe_run_emergency_precompaction`) は知覚ブロックの読みが失敗すると保存行だけで測り、上限以下と判定して Playbook へ進む (Codex 五巡目)。この fail-open は本件より前からの挙動で、影響は「上限超過のまま送る → モデル側のエラー」であり、会話の記憶を失う不変条件とは別。本件では手を入れず、`docs/issues/` の別件として扱う候補。

- 厳格化の範囲 (Codex 七巡目の族の掃討で確定): 起点の記録・圧縮区間・履歴の読みが**書き込み (起点 / 圧縮区間) か、発話 / 全量編纂を通す判断**に流れる箇所は厳格 (床・読み戻し・上限・被覆補修の引き戻し・冷えた窓への印)。据え置いたのは二つ。(a) 発話の文脈を組む経路 (`runtime_context.prepare_context` の起点解決と履歴読み) — 直前の床が同じ Beat ロック内で厳格に検証した後に走るので、縮退の窓は ms 級。(b) 畳み本体 (自動 / 手動 / 非常 / 先回りの `run_metabolism` と `get_presented_window`) — 縮退の向きは「発火しない / 書かない」側だが、壊れた記録を空と見て畳む形は本件より前から残る。どちらも本件の範囲外として記録。

- 発話モデルの入れ替わり (Codex 八巡目): 床は Pulse の冒頭で解決した実行モデルの窓を検証するが、その後の LLM クライアント生成が失敗して別モデルへフォールバックする経路では、検証した窓と実際に喋るモデルの窓が別になりうる。冒頭の解決に失敗した場合は unmet (fail-closed) にしたが、クライアント生成のフォールバックは本件より前からの経路で範囲外。既知として記録。

## 場合分け (① と起点の前進の関係)

- モデルが一つ: 畳みは古い側から順に畳んで先頭を起点が飲み込むので、① が入れば起点より右にあらすじは出来ない。前進は起きない。冷えた窓は 10 分ごとの先回りの畳み (`_cold_window_sweep_tick`) が残す量まで減らすので、ボタンが押される時点で窓は既に減っている。
- モデルが複数: A の畳みが B の窓の中にあらすじを作る。B が目を覚ますと前進で右端まで進み、そのあと読み戻しが段で残す量まで引き戻して圧縮区間 (生表示) として記録する。① はその前進後の起点を使う。
