# 記憶整理 (organize-memory) の UI が長走行でタイムアウト誤報を出す

**ステータス**: 解決済み (2026-07-29 発見 → 2026-09-01 修正)

## 症状

UI の「記憶整理」を押すと、編纂の LLM 呼び出しが多い場合 (実測: 126通 → 8チャンク、63秒) に、フロントが**「サーバーとの通信に失敗しました」**を表示する。実際にはサーバー側の処理は生きていて最後まで完走する — 誤報。

## 何が起きているか

`POST /api/people/{id}/organize-memory` は**同期**で、編纂全体 (チャンクごとの LLM 呼び出し × N + Fragment 抽出 + 束ね) が終わるまでレスポンスを返さない。フロント側のタイムアウト判定 (まはーの言では「雑にタイムアウト判定やってると思う」) がそれより短く、途中で切れて失敗表示になる。

## 実害

- ユーザーが失敗と誤認して**再実行**しかねない。二重編纂は実行台帳の冪等 claim が防ぐが、「失敗した」という誤った体験が残る。
- 完了通知・進捗が無いので、成功したことを知る手段が DB/ログ確認しかない。

## 修正の方向 (案)

1. **ジョブ化** — API の一括生成 (`/arasuji/generate` 系) と同じ非同期ジョブ + ポーリングの形に揃える。進捗 (n/N チャンク) も出せる。既存のジョブ機構の再利用で済む。
2. 次善: フロントのタイムアウトを大幅に延ばし、実行中表示を出す (処理時間は未編纂量に比例するので上限が読めない — 恒久策は 1)。

## 発見の経緯

2026-07-29、エリスの記憶修復 (歪み世代101件の削除) 後の一括再編纂で発生。処理自体は 63 秒で正常完走 (8チャンク、被覆 10,054〜11,493 字 — あらすじのレベル制の初の本番一括編纂として成功)。

## 解決 (2026-09-01)

上の案 1 (ジョブ化) を採った。同期の `POST /api/people/{id}/organize-memory` は**ルートごと削除**し、ペルソナメニューのボタンをあらすじタブと同じ背景ジョブ `POST /api/people/{id}/arasuji/generate` (mode 既定 = compaction) へ乗り換えた。ボタンの名前も「溜まった会話をあらすじにまとめる」に統一している (同日のまはー裁定 — 「整理」は守備範囲が広く読めすぎる)。

- **誤報の根**: 同期ルートが消えたので、フロントが長走行の応答を待つ場面自体が無くなった。押した直後に返るのはジョブの受付だけ。
- **進捗と完了**: あらすじタブ (`ArasujiViewer`) の既存のポーリングが、チャンクごとの進捗・完了メッセージ・エラー案内 (`error_code` 別の対処文) を表示する。DB/ログを見に行く必要は無くなった。
- **残る限界 (実害なしと判断)**: 通知はあらすじタブに出るので、ペルソナメニューから押した場合は「開始しました。進捗は記憶モーダルの「あらすじ」タブで確認できます」の案内を頼りに、ユーザーが自分でタブを開く必要がある。押した場所へ完了を押し返す仕組みは無い。
