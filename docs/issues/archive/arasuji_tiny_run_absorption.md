# 極小 run の単独編纂が捏造あらすじを生む — 隣人吸収 (開き直し) への改修

**発見**: 2026-08-31 (§16 被覆補修の aifi 実機初走行。まはーの観察「1 件だけであらすじが作られるのは異常」から)
**状態**: ✅ **完了 (2026-09-01 実機合格)** — 裁定 8 点 + 改訂 (見送り廃止 → 引き戻し) を全部実装。レビューは Codex 敵対 12 巡 + 最終確認 1 巡 + ローカル LLM 1 巡で、採用消し込み約 35 件・受容残余 15 項 (本文の節)・止め線適用の issue 送り 1 件 ([不確定 commit の復元漏れ](absorption_indeterminate_commit_recovery.md))。テスト: 吸収+再生成 70 件超・フルスイート 4,922 緑。

**実機合格の記録 (2026-09-01 未明、aifi 再補修)**: バックアップ復元 (18:02 JST 時点、補修産物のみが差分であることを機械検算) → 実行台帳の完了 claim を手動退避 (復元は memory.db の外に「台帳の claim」と「§16 の印」の二つの足跡を残す — 学び) → 修正済み補修を実行。見積もり 31 コール $0.14 (旧 129 コール $0.44 — 吸収の効果が値札に出た)。結果: **Lv1 28 本 (22〜55 通、被覆 7,243〜31,525 字、豆粒ゼロ)**、Lv2〜3 の語り直し 26 本 (stale 残ゼロ)、未完了マーカーなし、refill_applied=true。**捏造の再検査**: 昨日 memopedia 645〜647 を発明した現場を覆う新エントリ (55 通合体) は実際の出来事だけを語り、発明番号は不含。world DB の圧縮区間も死んだ参照なし。表示の小瑕疵 2 件は [repair_ui_progress_and_modal_polish](repair_ui_progress_and_modal_polish.md) へ分離。
**深刻度**: P1 — ペルソナの正典記憶への捏造混入が実証済み。補修 (§16) を他ペルソナへ展開する前に直す必要がある

## 事象 (実証済みの捏造)

aifi の被覆補修 (2026-08-31、236 通 / 129 コール) で、材料が極小のチャンクから事実無根のあらすじが生成された。

- 問題のエントリ (0fff5530) の source は入室通知 1 通。材料組成の長さ規則 (§7-1) で **25 字の決定論一行**に畳まれてから LLM に渡った (ログの coverage=25 で確認 — 畳み自体は設計どおり)。
- ところが生成されたあらすじ本文は「memopedia:645、646、647 がそれぞれ複数の子ページへと分割され」と具体的に語る。**この番号は source にも実際の通知にも存在しない** (実際の棚整理通知は 642・643・644。source 全文に "645" は不含 — 機械検索で確認)。
- 生成プロンプトには「これまでの流れ (参考)」として周辺あらすじ最大 20 件 + 意味記憶の文脈が入る (実測 promptTokenCount ≈ 5,000)。直前にコミットされた隣のあらすじが 642〜644 の分割を正しく要約しており、LLM は**参考文脈から借りて続き番号を発明した**と断定できる。「聖域の中で穏やかな日常を共有した」等の根拠のない情緒も付加。
- 同型の豆粒はこの走行で 100 件超 (1 メッセージ・材料数十字のチャンク)。他も「二人は絆を確かめ合う穏やかな時間を分かち合った」型の埋め草を含む。

**機構**: 極小材料 + 分厚い参考文脈 + 「固有名詞や重要な詳細は保持」「具体的に書く」の指示、の組み合わせが捏造機になる。想起再提示への既存のプロンプト柵 (§7-1 のラベルと指示) はこの経路 (参考文脈からの借用) を塞がない — **柵は既に立っていて、破られた**。

## なぜ豆粒 run が生まれるか

計画器 (plan_alignment) は「編纂済みを跨いで束ねない」(偽の隣接の禁止)。aifi の未被覆 236 通は、旧世代の編纂 (機構名義の行を対象外にしていた時代) が残した**歯抜け** — 前後の会話行は 7 月時点で既存あらすじの source になっており、挟まれた機構行・内的思考が 1 通ずつ孤立した。計画器は設計どおりで、入力データの形が原因。

これは補修 (repair) 固有ではない。通常の畳みでも processed 挟み・thread 切れで極小 run は構造的に発生しうる (通常は材料が U 級なので表面化しにくいだけ)。

## 却下済みの対処 (再訪しない)

- **あらすじ席に生メッセージを置く (恒等圧縮)**: 9 字・20 字の豆粒が列を分断した実害で 2026-07 に廃止済み ([undersized issue](chronicle_undersized_lv1_chunks.md))。
- **プロンプトへの柵の増設**: 「書いてはいけないなら文脈を提示する意味がない」(まはー 2026-08-31)。既存の柵が破られた実証もある。

## 方向 (まはー裁定 2026-08-31)

**極小 run に単独の編纂を走らせない。隣接する既存あらすじを開き直し (source の生ログに戻し)、極小 run を吸収して連続範囲で作り直す。**

旧世代の「治療 (隣人への合流)」と思想は同じ。治療は「自動機構としての複雑さが把握可能性を超えた」ことで世代交代時に廃止されたが、本件は**取り残されたメッセージの救出**という手動・保守の文脈であり、却下理由が当てはまらない。ただし旧設計の流用ではなく本件用に考え直す。

### 確定した裁定 (2026-08-31 まはー、同日中に 2 巡で確定)

1. **吸収先は後ろ (新しい側) の隣人**。欠落が壊すのは後続の文脈だから (旧治療と同じ向き)。
2. **単独編纂を止める閾値 X = 0.5U = 材料 5,000 字未満**。5,000 字あれば意味のある概要は作れる。1U 基準だと最悪 2 万字級の合体あらすじができるため、バランスで 0.5U。物差しは材料字数 (U 到達判定と同じ — 2026-08-29 裁定)。
3. **吸収で開き直した Lv1 の上位は、最上位まで連鎖的に再生成する**。据え置きは不可 — 提示に現れる内容が変わらないなら救出の意味が無い (= 記憶が毀損され続ける)。連鎖の深さは実運用で 1 桁レベルなので回数は問題にならない。
4. **連鎖再生成の順序は「時系列に階層をたたみ込む」**。「Lv1 を全部 → Lv2 を全部」の順は不可 — 後半の Lv1 を再生成するとき、生成プロンプトの「これまでの流れ」が引く上位あらすじが古いままになるため。正しくは Lv1 を時系列に処理しながら、**ある Lv2 の被覆範囲から抜ける時点でその Lv2 の下に更新が 1 件でもあれば Lv2 を再生成してから先へ進む**。Lv3 以上も同様に、範囲から抜けるたびに再帰的に。同じ上位を 1 回ずつしか作り直さない節約と、文脈の鮮度の両方が立つ。
5. **適用範囲は再編纂経路のみ** (通常の畳みには入れない)。補修 (API repair) と全量再編纂スクリプトは同じ計画器・同じ生成パイプラインの二つの入口なので、共有の計画層に一度実装すれば両方に効く。通常の畳みの「小粒は最後の手段」(2026-07-25 裁定、`used_last_resort_fold` で観測可能) は既存のまま — 実害が観測されたら広げる。
   - **改訂 (同日夜、まはー裁定): 「見送り (deferred)」の概念は廃止。** 当初の「後ろに隣人が居ない末尾の端数は持ち越す」は覆った — 隣人なしの極小 run にも必ずやるべき作業がある。場合分け: ①後ろに隣人あらすじが居る → 吸収 (本則)。②後ろに何も無く隣が提示窓 (anchor) → **anchor を引き戻して窓の中へ戻す** (LLM 不要の帳簿操作。窓の中にあれば §16-1 の不変条件は満たされる)。③戻すと提示が上限を超える → 戻した上で、未編纂区間 + 窓の古い側を合わせて通常の畳みをする (水位規則の既存動作)。「まだ量が少ないため編纂できません」型の帯表示は前提ごと不要 (実装済みだった分は巻き戻し)。細部 2 点も同夜確定 (まはー承認): ③の畳みは**補修ジョブの中で即座に**行い、費用は実行前のモーダルに含める (次の会話の非常畳みへ黙って送らない)。②の戻し先は**境界を作ってる行** = 止め線になった最古の温かい anchor の行 (温かい行が無ければ最古の冷えた行 — 引き戻し無料。anchor 行が一つも無いペルソナは初会話の bootstrap (§16-3) で自然治癒するため機構を作らない)。なお、この引き戻しは §15 読み戻しの「引き戻し」と同じ動作で、梯子の安全規則 (未被覆を跨がない) は「機構が勝手に過去を復活させない」が目的 — 補修はユーザーの明示操作なので、repair 文脈に限り未被覆の run を窓へ飲み込んでよい。
6. **失敗の可視化**: 連鎖の途中で失敗した場合、「親子のつながりは整合・上位の本文だけ古い」で止まり再実行で続きから直る、を姿勢とする。ただし**再実行が必要なことが誰にも分からない状態を作らない** — Chronicle タブの帯に「前回の処理が完了していません。再実行してください」のステータスを表示する。
7. **冷えた窓への印**: 吸収ジョブの最後に既存の冪等な印書き (`mark_covered_cold_windows`) を再実行する。合体で範囲が広がり窓の境界を跨ぐエントリは印を見送る — §16-2 で受容済みの残余と同じ扱い (次の畳みで自然解消)。検証はしっかり取る (まはー: 「①は OK……たぶん。検証だけしっかり」)。
8. Fragment / embeddings の追随は下表の裁定どおり。

## 受容した残余 (2026-08-31 レビュー消し込みでの裁定 — 直さないと決めたもの)

Codex 敵対レビュー 1 巡 (6 件) + ローカル LLM レビュー 1 巡 (13 観点) の消し込みで、以下は**意図して直さない**と裁定した:

- **引き戻しの fold 上書き競合** (CAS が anchor のみ): 計画→書き込みは ms 級で、regenerate_entry の「手動 UI 操作同士の ms 級競合として受容」(applier_veto_deadlock issue 記録) と同格。§15 共有部品の改造リスクの方が高い。
- **フェーズ 2 部分失敗の二重被覆に自己修復経路が無い**: 「被覆の穴は開けない」側に倒した設計の帰結。二重被覆は提示の除外名簿で実害が薄く、発生も極低確率。
- **巻き戻しの巻き戻し失敗** (repoint 復旧自体の例外): 極低確率の二次障害。WARNING で可視化されるのみ。
- **束ねの dry 計画が合体エントリを見ない / 材料字数の系統的過小 (知覚バッチぶん) / 見積もり時点と実行時点のずれ**: LLM 出力が未知である以上の本質近似。要否判定 (fold_needed・吸収 item 数) は実走と一点共有しており、ずれるのはコール数・字数の概算部分だけ。時点ずれには confirmed_unprocessed_messages の既存の歯止めがある。
- **unresolved_runs (提示中 digest / thread 断絶で開けない稀な形) が帯の件数に残り続ける**: 件数は事実 (未被覆は未被覆)。WARNING で可視化される。
- **上位再生成の指紋が子の本文変更を検出しない** (Codex 二巡目 R6): 「Lv1 の手動編集が上位あらすじを stale にしない」のは吸収以前からの世界全体の既存挙動で、吸収の指紋だけ本文まで厳密化しても増分がない。手動編集を上位へ伝える機構は別の設計判断 (必要になったら独立に起票する)。
- **delete_entry が削除成功後の親帳簿引き直し失敗でも True を返す** (Codex 六巡目 J1): 削除自体は成功しているので True が正直 (failed を返す方が嘘)。失敗は WARNING で可視化され、sweep (全量計画で常時実行) が保険として引き直す。削除ルートの Beat ロック直列化 (J2) で失敗の主因 (並走) 自体も細くなる。
- **flush だけの回に実行台帳の claim が無い** (Codex 十二巡目 Q1 — 却下): 「並行補修で二重課金」の主張は前提が成立しない — 補修は Beat ロックを全区間保持するのでプロセス内の並行は起きず (二重発火は直列化されて二本目が no-op)、プロセス跨ぎ (CLI と本番の同時実行) は「CLI はオフライン保守」の運用前提の外で受容済み。UI 側もボタンの disable が pending/cancelling まで覆う (V1)。

## entry id を参照する帳簿の調査 (2026-08-31、宿題 4 の材料)

「吸収 = 旧エントリ削除 + 合体範囲で新エントリ生成 (別 id)」で影響を受けるものの全量。既存の削除・再生成経路が何を面倒見ているかも併記する。

| 帳簿 | 参照の形 | 既存の削除/再生成での扱い | 吸収での要処置 |
|---|---|---|---|
| 上位あらすじの親子 (Lv2+ の source_ids / 子の parent_id・is_consolidated) | 親の source_ids に子 entry id | `delete_entry_and_update_parent` が親から外す。`regenerate_entry` (Lv1 専用・generate-then-swap・CAS) が親関係を保存 | 裁定 3 の連鎖再生成で親自体を作り直すので、そこで吸収する。**Lv2+ の再生成関数は未存在** — 新規実装 (材料 = 子の content 列) |
| 圧縮区間の記録 (session_anchor の FOLDED_RANGES_JSON、§15/§16 の印) | fold が digest として entry id を参照 | API 削除ルートが `remove_folds_referencing_entry` で道連れ削除 (残すと再畳み拒否の半端が残るため) | 吸収後は新 entry を指す印を書き直すか、次回補修の冪等な再印字 (`mark_covered_cold_windows`) に任せるかを実装時に決める。放置すると冷えた窓で head との二重提示が一時再発する |
| 想起用タグの辺 (recall_edges) | chunk↔page の辺に entry id | 両削除経路が `delete_chunk_page_edges` で同一 tx 削除。新規生成時に新しい辺が記帳される | 既存機構で足りる見込み |
| 知覚バッチの付記印 (perception_buffer の annexed 印) | 「この entry の材料として消費済み」の印 | 削除で返却 (`unmark_batches_annexed`)、再生成で新 id へ付け替え (`reassign_batches_annexed`)。旧バッチは再生成の材料にも入る | `regenerate_entry` の型をそのまま踏襲すれば足りる |
| **Memopedia Fragment (`memopedia_fragments.chronicle_entry_id`)** | 抽出元 Lv1 entry の id。UI の「抽出された知識」表示と、抽出の重複判定キーに使用 | **未処置** — 削除しても再生成しても付け替えられず、旧 id を指したまま宙に浮く (UI 表示から消える。知識自体は残る)。これは既存の再生成ボタンにも元からある欠陥 | **裁定済み (2026-08-31 まはー)**: 元々あった Fragment は消さず**新しい entry へ付け替え**、新エントリからの新規抽出も普通に行う。二重登録は起きてよい — Fragment 抽出はそもそも既存 Fragment を考慮しない設計 (毎回全送は トークン浪費) で、重複は元々の割り切りの範囲 |
| **あらすじ埋め込み (`arasuji_embeddings`)** | entry_id キーの埋め込み (unified recall が使用) | **未処置** — `delete_entry` は消さない (全量整理スクリプト `persona_chronicle_cleanup.py` だけが手で消している)。孤児埋め込みが想起に出る可能性 | **裁定済み (2026-08-31 まはー)**: 削除時の道連れ削除でよい (既存削除経路への横展開も実装時に検討) |
