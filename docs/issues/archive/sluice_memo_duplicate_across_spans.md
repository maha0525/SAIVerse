# スルースの手帳メモだけ、内容ベースの重複防止を持たない

**状態**: ✅ 完了 (2026-08-22 実装・回帰テスト済み)。機械側の重複防止と、供給源を塞ぐ一行の両方を入れた。

## 実装 (2026-08-22)

**機械側の保険**: `pocketbook.find_memo_by_content(conn, activity_id, date, kind, text)` を足し、`sea/sluice.py` の `_apply_memos` が add_memo の直前に照合する。ヒットしたらスキップ (成功扱い、結果行は「既に手帳にあるため採りませんでした」)。照合は書き込みと同じロック・同じトランザクションの中なので、check-then-act の隙間が無く、同じ回の結果に同じメモが二つ入っていた場合も止まる。

⚠ **裁定の三つ組に `kind` を足して四つ組にした (私の判断)**。裁定の文面は「同じ日・同じアクティビティ・同じ本文」だったが、`want` と `did` は同じ本文でも別の記録 (「続きを書きたい」と「続きを書いた」が同じ文面になる回がある)。裁定が三つ組を選んだ理由が「正しい記録を落とさない」ことなので、その理由を `kind` にも適用した形。狭める方向なので、issue が報告した並び (同じ kind の再提案) は変わらず止まる。

**供給源**: `_scope_sentence(span_new_count)` を足し、`_build_sluice_prompt` の手帳の節の先頭に一行入れた。「今回の対象は直近 N 通の会話です。それより前は前回の整理で採取済みです。」/ マーカーが窓に無いときは「今回は手元の会話全体が対象です。」/ 新規ゼロのときは「前回の整理以降、新しいやり取りはありません。」。N は `_count_new_since_marker` = 機械が知る値だけで組む。

⚠ 裁定は「N は `span_ids` の長さ」と書いていたが、`run_sluice` の `span_ids` は**窓全体の id 列**で、担当範囲の通数ではない (それだと「窓全体が対象のとき」との区別が付かない)。意図どおり「マーカー以降の通数」を既存の `_count_new_since_marker` から取る形にした。

⚠ 既知の限界: コンテキスト超過の後退 (§13.5-1) が起きた回は、実際に見せる通数が宣言した N より少なくなる (プロンプトは後退前に一度だけ組むため)。「それより前は採取済み」の部分は後退しても真のままなので、件数だけが概数になる。コードにコメントとして残した。

回帰テスト: `tests/test_sluice.py` に issue の並びの再現 (Metabolism #1 が m0..m4 → 繰り越しで #2 が m5..m6、同じメモを返す → 二行目が書かれない) と、プロンプトの対象範囲の一行 (マーカーあり / なし)。`tests/test_pocketbook_and_edges.py::TestFindMemoByContent` に四つ組の識別 (日付違い・種類違い・活動違い・本文違いはいずれも重複ではない)。修正を外すと再現テストが落ちることを確認した。

## 裁定 (2026-08-22、まはー + Fable)

**選択肢 B (同じ日・同じアクティビティ・同じ本文だけ弾く) を機械側の保険として入れる。加えて、C ではなく「今回の対象範囲を本人に明示する」ことで供給源を塞ぐ。**

重複の供給源は「退場が繰り越された次の回に、本人が採取済みの会話をもう一度読むのに、どこまで採取済みか知らされていない」こと。プロンプト (`_build_sluice_prompt`) を読むと、手帳の節に「この範囲で」とあるのに**その範囲がどこなのか一言も書いていない**。対象範囲の通数はスルースが機械的に計算している (`_compute_span` の span_ids) ので、「今回の対象は直近 N 通。それより前は前回の整理で採取済み」と一行足せば本人は判断できる。既存メモを全部プロンプトに載せる C は、分量が膨らむ割に精度が低いので採らない。

決めたこと:

- `_apply_memos`: 同じ `date`・同じ `activity_id`・同じ本文の生存メモがあればスキップ (成功扱い、結果行に「既に手帳にあるため採りませんでした」と残す)。コア記憶の内容一致ガードと同じ二段構え
- プロンプトの手帳節に対象範囲の一行を足す。span が窓全体 (初回 / マーカー消失) のときは「今回は手元の会話全体が対象」と書く。N は機械が知る値だけで組む (本人の申告は使わない — §13.6 と同じ規律)
- 回帰テストは、この issue の「具体的な並び」(unseen_tail → 次回の同一メモ) を再現して二行目が書かれないことを固定する

## 何が起きうるか

同じ内容の手帳メモが、二度書かれる。

スルースの重複防止は二段ある。

- **コア記憶の add**: 同一本文の生存コア記憶があればスキップする (内容ベース)
- **手帳のメモ**: `idem_key` だけ (`{span 由来の接頭辞}:m{番号}`)

`idem_key` が守るのは「**同じ span の同じ番号**」の再適用だけである。span が変われば別のキーになるので、同じ内容でも通る。

## 具体的な並び (現物で確認済み)

1. Metabolism #1: スルースが範囲 [A..E] を見て、手帳にメモ M を書く (キー `sluice:A..E:m0`)。ところが退場計画に、スルースが見ていない新着 F・G が入っている
2. → `sluice_status = "unseen_tail"`。**採取とマーカー前進は確定し、退場だけを次回へ譲る** (`session_lifecycle.py:2764` のコメントが明記)
3. Metabolism #2: 退場していないので窓には A..G が残っている。マーカーは E まで進んでいるので新しい範囲は [F..G] だが、**プロンプトに載る会話は窓全体 = A..E を含む**
4. 本人が A..E の会話からまた同じメモ M' を返す → キーは `sluice:F..G:m0` → 既存の `sluice:A..E:m0` と別物 → **重複して書かれる**

## なぜコア記憶だけ守られているか (非対称の記録)

`_apply_ops` の docstring は、内容一致ガードを置いた理由をこう書いている。

> 「LLM が既存と同じ内容を再提案したときの抑止 (プロンプトの『既にあるものは再度採らない』の保険) も兼ねる」

つまり **「プロンプトの指示だけに頼らず、機械側でも守る」という判断を明示的にしている**。手帳のメモには、その保険が無い。

しかも条件は手帳のメモの方が**悪い**。プロンプトに載るのはコア記憶・アクティビティ・タスクだけで、**既存の手帳メモは載らない**。本人は「既に書いたか」を確認する手段を持たないまま、「既にあるものは再度採らない」と指示されている。

## なぜその場で直さなかったか (裁定が要る点)

**コア記憶と同じ内容一致ガードを、そのまま持ち込めない。**

コア記憶は事実の記述なので「同一本文 = 重複」でよい。手帳のメモは**日々の記録**で、「今日も小説を書いた」が二日続くのは重複ではなく事実である。日付が違えば別の記録として正しい。単純な内容一致で弾くと、**正しい記録を落とす**方向の実害が出る。

## 選択肢 (未裁定)

- **A: 何もしない。** 発生条件が限定的 (`unseen_tail` で確定した直後の回に限る)。重複しても手帳の一行が二つ並ぶだけで、本人の言葉は失われない
- **B: 同じ日・同じアクティビティ・同じ本文だけを弾く。** 「今日も小説を書いた」を別の日に書くのは通り、同じ日の二重書きだけ止まる。手帳の粒度が日単位 (`date` 列が 'YYYY-MM-DD') なので、この三つ組は自然な単位
- **C: 既存の手帳メモをプロンプトに載せる。** 本人が「既に書いたか」を目で見て判断できるようにする。プロンプトの指示 (「既にあるものは再度採らない」) が初めて実行可能になる。代償は分量 — アクティビティごとに直近何件を載せるかの設計が要る
- **D: 重複を許して、後から畳む。** 手帳の表示側か整理の機会に、同じ日・同じ本文をまとめる

**B と C は排他ではない** — C で本人が判断できるようにし、B を機械側の保険にする形は、コア記憶と同じ二段構えになる。

## 実機で見ること

`unseen_tail` は退場が繰り越されたときだけ立つ。ログの `[sluice] eviction deferred` が出た次の Metabolism で、手帳に同じ日・同じ本文のメモが二行並んでいないかを見る。並ばないなら A のままでよい。
