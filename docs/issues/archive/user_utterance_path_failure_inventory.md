# ユーザー発話から応答完了までの停止点の棚卸し

**ステータス**: 🟡 実装待ち — 洗い出し完了、設計は 2026-08-25 のまはー裁定で確定 (下の「設計の決着」)。
やり直しは v0.3 の門の内側へ引き上げ済み ([v030_release_gate.md](../../overview/v030_release_gate.md) §2-17)。
**出自**: 2026-08-24 に NEBULA の provider を選んで話しかけたら無言だった件 ([user_lane_error_silent_in_ui](../user_lane_error_silent_in_ui.md))。
まはー «今回は LLM サーバー側との接続失敗が原因だったと思うけど、ユーザーが話しかけてから
ペルソナが応答完了するまでっていろんな障壁があるはずでしょ？どこで止まる可能性があって、
そのうちユーザーに原因も対応も分からない形なのがどれか、っていうのの洗い出しからやりたい»

**この文書の役目**: 一件ずつ後追いで起票してきた「無言で止まる」の上流に立ち、経路全体を並べて
**落ちうる場所** と **落ちたとき本人に何が見えるか** を対にする。設計はまだしない — 材料を作る回。

## 判定の語彙

落ちること自体は避けられない。問うのは「落ち方」で、四段に分ける。

| 記号 | 意味 |
|---|---|
| ✅ 分かる | 何が起きたか・どうすればいいかが日本語で本人に届く |
| 🔤 開発者語 | 何か出るが、原因も直し方も一般ユーザーには読めない (英語・内部用語) |
| 🎭 誤誘導 | 何か出るが、**内容が事実と違う方向を指す** — 分かる顔をしているぶん無言より悪いことがある |
| 🕳️ 無言 | 画面に何も出ない。スピナーが消えて終わる |

**同じ失敗が、会話が開いているかどうかで見え方が正反対になる。**

|---|---|---|
| 会話が開いている (継続発話) | `user_conversation.py:833` が `UserUtteranceError` に包んで**上へ送出** → `runtime.py:722-732` の catch-all → `{"type":"error", content:"予期せぬエラーが発生しました。", technical_detail:...}` → フロントが吹き出しに描画 (`page.tsx:1985`) | 🔤 出るには出る。文言は汎用、詳細は英語 |

## 設計の決着 (2026-08-25、まはー裁定)

洗い出しを材料に同日議論して、ここまで決まった。以下は裁定であって見立てではない。

### 1. 残るべき終わり方は 7 通り

数える軸は「エラーの種類」ではなく **ユーザーの次の一手が変わる境目**。

| # | 終わり方 | 発言は残るか | 今あるか |
|---|---|---|---|
| 1 | 応答が返って終わった | 残る | ✅ |
| 2 | 応答が**途中で**終わった | 残る | ⚠️ 起きるが印が無い (完結した短い返事と区別できない) |
| 3 | 発言は届いたが、**応答は生まれなかった** | 残る | 🕳️ **無い — 無言 5 箇所の落ち先はすべてここ** |
| 4 | 発言が**届かなかった** | 残らない | ✅ `persistence_failed` が見本 |
| 5 | ユーザーが止めた | 残る (応答は途中まで) | ✅ `cancelled` |
| 6 | 同じ発言を**既に受け取っていた** | 既に残っている | ✅ `duplicate_command` |
| 7 | **顛末が確定していない** | 分からない | 🕳️ **無い。しかも「送れなかった」と嘘をついている** |

7 は原理的に消せない (ブラウザとサーバーが切れた瞬間、クライアントに確定情報が無い)。
消せないので、**「分かりません」と正直に言う出口を持つ**ことをまはーが裁定した。

### 2. 出口の後ろに「片付け」の一段が付く

「発言しなかったことにしたい」需要は実在する (まはー提起)。ただし **消せるかどうかは好みでは決まらず、
ペルソナが読んだかどうかで決まる**。

| 窓 | 状態 | 片付け |
|---|---|---|
| ① 保存前 | どこにも無い | 自由 |
| ② 保存済み・**まだ誰も読んでいない** | 建物履歴にあるが記憶には無い | **差し戻しを既定にする** (ユーザーは選べる) |
| ③ **読まれた後** | SAIMemory に転記済み | **残すに固定**。「もう聞かれてしまったので取り消せません」と正直に言う |

- ②③ の境目は新設ではなく既存 — `auto_ingest` の `pulse_cursors`
  (`builtin_data/tools/get_building_messages.py:334-372`) が「どこまで読んだか」を持っている。
  **部屋に複数ペルソナがいる場合は全員未読のときだけ ② 扱い**にする (食い違いを作らない側へ倒す)。
- ユーザーの発言は**ユーザーの著作物**なので、「削除」ではなく **入力欄への差し戻し** (手元に返す)。
- ③ で記憶側まで消す案は**採らない** — エラーの後片付けが記憶を書き換える口になるのは危うい。
  記憶の訂正はメモリタブ側の、意図してやる操作に留める。

**ペルソナ側の断片の扱い**:

- 空の placeholder (`content: ""`、`runtime_emitters.py:243-253`) は**常に掃除する**。誰の発言でもない。
- partial の保存は**現状どおり**、そしてその非対称は正しいので明文化する —
  **ユーザーが止めた partial は残す** (「そこで止めた」という事実があり、そこまでは本当に言った) /
  **事故で切れた partial は残さない** (誰の意思でもない残骸)。中断の主語が誰かで決まる。
- 現状の食い違いは直す: いまは画面に partial が残り、世界には空行が残り、リロードで画面の分だけ消える。

### 3. ユーザーの操作は 2 つだけ — `retryable` は要らなくなる

まはーの指摘: **③ が「取り消せない」と言う以上、追加のプロンプト無しで応答をやり直せる機能とセットでないと、
ユーザーはもう一度喋らないと応答を得られない。** そしてやり直しがあれば、**「再送するかどうか」の択自体が消える** —
「続けて喋るか、やり直してください」と言えば済む。

| 出口 | 操作 |
|---|---|
| 1・6 (応答がある) | なし |
| 2・3・5 (発言は残り、応答が足りない) | **やり直し** |
| 4 (発言が残らない) | **送信** (入力欄に戻っている) |
| 7 (不明) | 履歴を見て、どちらか |

よって当初案の「全出口に `retryable` を必須欄で載せる」は**取り下げ**。
発言が残っているかどうかが操作を決めるので、真偽値を別に運ぶ必要がない。

> なお `retryable` はサーバーが既に 4 箇所で送っていて (`manager/runtime.py:566,639,651` /
> `api/routes/chat.py:1122`)、フロントエンドは一度も読んでいない (全文検索で 0 件)。
> 汎用の catch-all (`runtime.py:727-732`) には付いてすらいない。この欄は掃除の対象になる。

### 4. 「やり直し」と「作り直し」は別物

必要な土台が違うので、混ぜない。

- **やり直し** = 応答が無い状態から応答を作る。**枝は増えない** (元の応答が存在しない)
- **作り直し** = 気に入らない応答を別案に置き換える。**枝が増える** (どちらが本流かの記録が要る)

[`memory_continuity_graph.md`](../memory_continuity_graph.md) の「副産物 — 会話の分岐・再生成」が設計しているのは
**作り直し**の方 (新しい thread を開いて分岐位置以前と繋ぐ)。**やり直しは枝を増やさないので、
連続性グラフの決着を待たずに成立する** — これが門の線引きを動かせる根拠。

### 5. 門の線引きを変更 — やり直しを v0.3 の内側へ (まはー裁定)

[`v030_release_gate.md`](../../overview/v030_release_gate.md) §2-14 は「刻印は v0.3、消費は後続」と引いており、
再生成は消費側だった。**やり直しだけを門の内側へ引き上げ、作り直し (分岐) は後続のまま**とする。
③ の出口とやり直しは一つの工事。→ 門 §2-17 として登載。

**土台は既にある**: 会話開始経路の `run_sea_user(persona, building_id, "")`
(`saiverse/user_conversation.py:753-758`) が、まさに「発言はもう履歴にある前提で応答だけを起こす」形。
新機構ではなく、この経路にユーザーが触れる口を付ける工事になる。
製品内の `regenerate` は現状 Chronicle 専用 (`api/routes/people/arasuji.py:717`) で、会話用は無い。

### 実装の前の確認 — 3 点とも決着 (2026-08-25、コードを読んで確認)

**① 窓③ (既読) でやり直したとき、直前のユーザー発言は文脈に載るか → 載る。前提は成立する。**

- 取り込みは user 発言を `add_to_persona_only(entry, memory_first=True)` で **SAIMemory へ書く**
  (`builtin_data/tools/get_building_messages.py:287-302` → `:165-167`)。
- ペルソナの文脈は **SAIMemory の anchor 以降**から組まれる (実機ログ 2026-08-25 19:18:02:
  `Fetching persona history from anchor` → `SAIMemory returned 114 messages from anchor`)。
- 取り込みの目盛り (`pulse_cursors`) は「同じ建物メッセージを二度読まない」ための印であって、
  **文脈の材料ではない**。だから既読でも、その発言は文脈に載っている。やり直しは成立する。

**② 空 placeholder の掃除 → 要るが、害は起票時に書いたより小さい。優先度を下げる。**

- チャット履歴 API が content 空を除外するので **画面には出ない** (`api/routes/chat.py:293-296`)。
- 取り込みも content 空を `consumed` で飛ばすので **誰の記憶にも入らない**
  (`get_building_messages.py:206`)。
- **残るのは `building_histories` と `log.json` の実体だけ**で、掃除する機構は無い。
  害は「ゴミが溜まり、seq 番号を消費する」ことであって、記憶の汚染ではない。
- 訂正: 上の裁定で「常に掃除する」と書いた理由 (誰の発言でもないから) は変わらないが、
  **急いで直す必要はない**。やり直しの工事のついでで足りる。

**③ やり直しの連打 → 完全な二重応答は起きない。ただし別の並びが出る (要裁定)。**

- `PulseController` がペルソナ単位で排他している (`sea/pulse_controller.py:213-218` の `_current`)。
- `user` 型は `same_priority_policy="last"` なので、**後の要求が前を中断して勝つ**
  (`:47-52` と `_should_interrupt` `:275-276`)。`on_blocked="skip"` なので中断された方は再開しない。
  → **応答が二つ生まれることはない。**
- **新しい論点**: 中断された分の partial は、キャンセル経路が確定保存する
  (`sea/runtime_llm.py:3864-3870` — 「placeholder を発番済みのまま抜けると残り続ける」ので finalize する)。
  つまり**やり直しを連打すると、捨てたはずの言いかけが履歴に積もる**。
- これは上の裁定「partial の保存は**中断の主語**で決める」に、**第三の主語**が現れたことを意味する。
  → **この論点は下の「④ 続き」でルールごと差し替わった。**

## ④ 途中終了には「続き」を取る (2026-08-25 まはー方針、ルールの差し替え)

まはー «終わり間際まで生成進んでたらもったいないし、ユーザーが見てたならその発言が勝手に消えるのって
喪失感ない？再送しても同じ発言するとは限らないし……。途中終了に関しては**続きを話させることさえできれば
そっちを取るべき**だと思ってる»

これで、上で立てた「中断の主語で決める」ルールは**単純な一本に置き換わる**。

### 「続き」は既に実装されている (504 限定)

`sea/runtime_llm.py:367-500` の `_respeak_after_stream_timeout` が、まさにこれをやっている:

1. 画面に出す — 「メッセージの生成が予期せず終了しました。ペルソナが再発言を行います。」(`:398-407`)
2. **部分文を SAIMemory へ保存**する (`:411-420`)。刻印は中断した初回コールのものを使う
3. 文脈 + `assistant(部分文)` + `user(<system>あなたの応答がサーバータイムアウトにより途中で
   終了しました。続きがあれば引き続き発言してください。</system>)` で **2 回目のコール** (`:424-430`)
4. 継続分の課金・三つ組を**別々に**記帳する (`:463-469` — 「他人の記帳を自分の事実として刻む」ことを
   避ける配慮が入っている)
5. 継続が空なら部分文のまま返し、二重保存を防ぐ印を置く (`:471-479`)

**つまり「続きを話させる」は新規発明ではなく、この機構の発火条件を広げる工事になる。**

現状の発火条件は `llm_client.consume_stream_error()` が構造化されたストリーム中断を返したときだけ
(`:3829-3841`)。届いていないのは、Pulse 全体が例外で落ちた場合、ユーザーが止めた場合
(`:3825-3827` で明示的に除外)、プロセスが落ちた場合、非ストリーミング経路。

### ルールの差し替え

**旧**: partial を残すかは「中断の主語」で決める (ユーザーが止めた=残す / 事故=残さない / やり直し=?)

**新**: **機構は消さない。消すのはユーザーが消すと言ったときだけ。**

- 途中まで生成された言葉は**常に残す**。もったいないからでも、喪失感を避けるためでもあり、
  何より**続きの材料になる**から。
- 消える契機はただ一つ、**ユーザーが「やり直し」を選んだとき** (= 捨てると言ったとき)。
- この一文は、片付けの裁定 (未読なら差し戻し・既読なら残す) と**同じ形**をしている —
  どちらも「削除の根拠はユーザーの意思だけ」。二つの規則が一本になる。

### 操作は 2 つではなく 3 つ

| 出口 | partial | 操作 |
|---|---|---|
| 2 途中で終わった | 残る | **続き** (やり直しも選べる) |
| 3 応答が生まれなかった | 無い | やり直し |
| 5 ユーザーが止めた | 残る | **続き** (やり直しも選べる) |
| 4 届かなかった | — | 送信 |

「やり直し」は**応答が生まれなかったとき**の操作で、途中終了への答えではない
(まはー: 再送しても同じ発言をするとは限らない)。上で「2・3・5 はやり直し」と書いた表は、これに差し替える。

## ⑤ 続きは自動で打たない — 操作はメッセージバブルのボタンへ (2026-08-25 まはー裁定)

まはー «自動化はちょっと避けたい、**勝手に API 課金が追加で発生する**ことになる。特にキャッシュ使ってない人は
重たい。失敗した場合ユーザーのメッセージバブルには再送ボタン、途中で終わったペルソナのメッセージバブルには
続きの生成ボタンを置く感じがいい気がする。そのうえで、失敗したことについてはちゃんとダイアログか何かで
ユーザーに通知する形。そうすれば**途中終了も、そこでまず処理は終わってよくて、メッセージにフラグつけるだけで
済む**»

### 決まった形

- **ユーザーのメッセージバブル** → 「再送」ボタン
- **途中で終わったペルソナのメッセージバブル** → 「続きの生成」ボタン
- **失敗そのものはダイアログで通知**する (バブルの中に埋めるだけにしない)
- 途中終了の処理は**そこで終わる**。部分文を保存してフラグを立てるだけで、二回目のコールは打たない

**課金は必ずユーザーの一押しの後ろにある** — これが原則。追加の推論が走る操作は、すべてボタンを起点にする。

### 含意 1 — 「言い切っていない」印は、提案ではなく必須要件になった

上の「残る論点」で私が提案していた印は、**ボタンを出す条件そのもの**になった。フラグが立っている
ペルソナのバブルにだけ「続きの生成」が出る。だから印は要る・要らないの話ではなくなり、
どういう名前でどこに持たせるかだけが残る。

### 含意 2 — ユーザーに状態を判断させなくてよくなる

私が組んでいた「発言が残っているかで操作が決まる」は、**ユーザーに状態を理解させる形**だった。
バブルにボタンを置くと、**押す対象がその発言そのもの**なので、ユーザーは判断しなくてよくなる。

- ユーザーのバブルのボタン = 「もう一度応答を得る」。発言が届いていなければ送信、届いていれば
  応答だけのやり直し — **どちらを行うかは機構が決める**。ユーザーからは 1 つのボタン。
- 出口 7 (顛末が不明) でも同じ。「分かりません」と通知したうえで、ボタンは押せる。
  機構が履歴を見て、送信かやり直しかを決める。**ユーザーに履歴を確認させる必要がなくなる。**

### 含意 3 — 既存の 504 自動継続は**撤去する** (2026-08-25 まはー裁定)

まはー «なら取り払ってしまって、手動の続き生成機能に移そう！» — 発火履歴の実測 (下記) がゼロだったことを
受けての裁定。`_respeak_after_stream_timeout` は削除し、504 も他の中断と同じ扱い (部分文を保存して
フラグを立て、そこで処理を終える) に一本化する。続きはユーザーがボタンで起こす。
以下は裁定前の検討の記録。

`_respeak_after_stream_timeout` (`sea/runtime_llm.py:367-500`) は、**いままさに自動で二回目のコールを
打っている**。まはーの言う「勝手な課金」に該当する。

揃えるなら、504 も他の中断と同じ扱いにする — 部分文を保存してフラグを立て、そこで処理を終える。
続きはユーザーがボタンで起こす。そうすると、あの関数の大半 (継続コール、継続分の記帳、空継続の
二重保存防止、`_ALREADY_STORED_STATE_KEY` の印) が**不要になり、コードが減る**。
CLAUDE.md の「例外処理・救済機構が本体を覆い始めたら止まる — 供給源を塞いで機構ごと消せないかを
先に問う」にも合う形。

トレードオフ: **いま自動で復帰していたものが手動になる**。504 は本人の落ち度でない中断なので、
「なぜ自分が押さなければいけないのか」と感じられる可能性はある。ただし課金の同意を上に置くなら
この形になる。

#### 発火履歴の実測 (2026-08-25) — **一度も発火していない**

まはーの問い «その機構の今までの発火履歴ってログに残ってるかな？もし俺が知らないだけでかなり高頻度で
使われてたりすると、UX 損ないそうで怖い» に答えるため、手元のログを全数検索した。

**探した範囲**: `~/.saiverse/user_data/logs/` の全 654 セッション (2026-07-22 〜 08-25)。
うち `backend.log` を持つ 56 セッション (計 243 MB、7 月 12 / 8 月 44) と、`llm_io.log` 56 本。

**結果**:

| 探したもの | 件数 |
|---|---|
| `Triggering re-speak after 504` (機構の起動ログ) | **0** |
| `Stream interrupted by server` (中断の検出ログ) | **0** |
| `Re-speak after 504 returned empty` | **0** |
| `llm_stream_continuation` (継続コールの記帳名、llm_io.log) | **0** |
| 継続プロンプト `続きがあれば引き続き発言` (llm_io.log) | **0** |

**504 自体は 6 回起きているが、機構には届いていない。** 6 件すべて
`google_genai._api_client: Retrying ... as it raised ServerError: 504 DEADLINE_EXCEEDED` の形で、
**Google SDK が自前のリトライで吸収**している (`_request_once` のリトライ = ストリーム中断ではない)。
日付は 08-03 / 08-05 / 08-20 (2) / 08-21 / 08-22。

**構造的な理由**: `consume_stream_error` を実装しているのは `llm_clients/gemini.py` だけ。
Gemini native 以外のプロバイダでは、そもそもこの機構は発火しようがない。

**検索の検算** (0 件が検索の壊れではないことの確認):
同じログ群で `[sea][llm]` が 19,026 件、`504` が 5,932 件ヒットする。
`llm_io.log` は日本語を**生のまま**保存している (`あなた` 963 / `システム` 1,209 / `ペルソナ` 726 件、
`\uXXXX` エスケープは 0 件) ので、日本語プロンプトの検索は有効。

**この検索で答えられないこと**: 654 ディレクトリのうち 598 は `sea_trace.log` しか持たず、
そのセッションの root ログが無い。ただし re-speak のログは `logging.getLogger(__name__)` =
root 伝播で `backend.log` に出るものなので、`sea_trace.log` には元々現れない
(検算: `sea_trace.log` 全 654 本に `[sea]` は 0 件)。よってこの 598 は本件について沈黙している。
また 2026-07-22 より前は手元にログが無い。

**結論**: 手動化で失われる体験は、直近 1 ヶ月の実運用では**観測されていない**。
「一度も発火していない」は「今後も発火しない」ではない (Gemini 側の挙動やモデルが変われば起きうる) が、
起きたときにボタンが出るなら、失われるのは自動性だけ。
**一度も走ったことのない自動復帰機構が本体に居座っている**状態でもあり、
CLAUDE.md の「例外処理・救済機構が本体を覆い始めたら止まる」の典型例にあたる。
→ この結果を受けて、まはーが**撤去**を裁定した (含意 3)。

## 実機検証 ①〜③ (2026-08-26) — 案内の寿命と、果たせない約束

まはーが手順①②③を踏んで出た 4 件。**芯は二つ**あった。

### 芯 1: 「返事が生まれなかった」を一種類に潰していた

実際には二種類ある — **応答できる相手がいない** (やり直しても永久に変わらない) と、
**相手はいたが返事が生まれなかった** (やり直す余地がある)。両方を `no_response` の
一つの札で扱い、画面の補足文は後者の前提だけで書かれていたため、応答者ゼロの部屋で
「発言の『再送』から応答をもう一度求められます」という**その場では絶対に果たせない
約束**が出ていた。

しかも経路によって言うことが違った。①(通常送信)の一番外側の検査は
`responding_personas=0` をログに書き出しながら汎用の文言を出し、②(再送)だけが専用の

だった。「返事が来ていない」と「やり直す余地がある」は別の事実なので、印を
`needsRetry` と `retryUseless` に分けた。消えるのは「再送」だけ。
一つ前の `withdrawBlocked` (読まれた後は取り消せない) と対になる形で、
**一つの印に別々の事実を載せない**という同じ結論に両側から着いた。

**まはーの言葉**: 「応答をもう一度求める、っていう解決策にならない解決策を提示してる
ことに問題がある」。関連する規律は memory の

`feedback_nothing_to_do_is_not_a_failure`。

### 芯 2: 画面の案内に寿命が無かった

ボタンはもう無いのに。

**まはーの裁定 (2026-08-26)**: **何か操作したら案内を消す。時間では消さない。**

> 時間経過で消えたりしたらさすがに問題だけど (読んでない可能性が普通にあるから)、

- **取り消しが別のペルソナの結果まで消していた**。一度の送信で複数のペルソナが並行して
  喋る回があり、`outcome_seen` を全員で共有していたため、あとから来たツール呼び出しだけの
  ペルソナの取り消しが、既に喋った相手の結果まで無かったことにできた。断片を出どころ
  (`persona_id` + `pulse_id`) ごとに持ち、取り消しは同じ出どころのものだけを消す形にした。
  **2 巡目で私が入れた撤回の仕組みが、共有状態の上に乗ったことで生まれた欠陥。**
- **同じことが `spoke` にも起きていた**。ツール呼び出しだけで終わった回に「喋った」が立った
  ままになり、続きの生成の印を降ろしてしまう。`_note_speech` として同じ形に揃えた。
- **MCP が死んだ接続を起動成功として扱っていた**。`call_tool` の失敗で `disconnect()` した
  接続は `_connections` から消えないので、キーの存在だけを見ると「起動済み」と読める。
  兄弟の `register_instance` は最初から `connected` まで見ていた。**同じ判定が経路ごとに
  分裂している**という、より大きな問題の一部。
- **409 の添付復元が、送信中に足した添付を上書きしていた**。手が入っていないときだけ戻す
  ようにした。

#### 直さなかった 1 件と、止める理由

**フロントのストリーム表示にも識別子が無い** (`frontend/page.tsx`) →
[streaming_events_have_no_identity_in_the_ui](../streaming_events_have_no_identity_in_the_ui.md)
(2026-08-28 に独立の issue へ移送)。

**ここで補修を止める。** 3 巡目の指摘は、別々の顔をしているが**一つの構造欠陥**に収束して
いる — 「ストリームに識別子が無く、状態を共有している」。バックエンドは今回その内側に
出どころを持たせたが、フロントを同じ形にするのは表示の設計変更で、`Message` の持ち方から
決め直す話になる。CLAUDE.md の「例外処理・救済機構が本体を覆い始めたら止まる」に当たる。

## 実機検証 ④ (2026-08-26 夜) — 印が画面へ届いていなかった

まはーの観察: 停止すると**発言は残り、二つにも増えていない** (8/26 夜の修正が効いている)。
ただし **「続きの生成」ボタンがその場では出ない。別の部屋を見て戻ると出る。**

つまり印 (`_interrupted`) はサーバー側に正しく立っていて、**画面へ渡す途中で落ちていた**。

### 原因

停止された Beat は、`_run_spell_loop` の spell round の境目で
`ExecutionCancelledException` を投げて抜ける (`backend.log` の
`SEA LangGraph LLM failed: ExecutionCancelledException: Execution interrupted between
spell rounds`)。**印を載せた完了イベントは、その例外より下流にある**ため、決して送られ
なかった。

実装時のコメントには「判定は完了イベントより**前**に置く — 画面は再読込を待たずに
『続きの生成』を出せなければならないので、印を同じイベントに載せて渡す」と書いてあった。
**判定の順序は正しかったが、その完了イベント自体が停止経路では届かないことを確かめて
いなかった。**

### 直した形

停止の後片付け (下書き行の確定) の直後に、印つきの完了イベントをその場で送る。ここは
例外より上流で、worker の `cancelled` イベントよりも前に流れるので、`cancelled` 以降を
捨てる読み手の後片付けにも巻き込まれない。下流の完了イベントは `pipeline_finalized` の
ときは送らない (意味の重複を残さない)。

### 中断を記憶へ残す形 (2026-08-26 まはー裁定)

停止された発言について、**建物の記録にも本人の記憶にも何も残っていなかった**ことが実機で
分かった。決めた形はこう。

**残すもの (途中まで喋ってから止められた回)**

- **言いかけた本文**を、本人の記憶へ「言い切っていない」印つきで書く。建物の記録に残るのに
  本人だけが覚えていない、という食い違いを作らないため。
- **中断があった事実**を、独立した `user` + `<system>` メッセージとして**建物の記録へ**置く。
  文面は `(ユーザーの操作により、ここで発言が中断されました)` まで。

  建物の記録に置くのは、居合わせた他のペルソナにも見せるため。まはー «途中終了ってペルソナの
  口に指立てて制止するような意味合いなわけでしょ。その場にいる別のペルソナはその場を目撃
  してておかしくないんだよ»。不自然な場所で終わった発言が、本人の言い切りなのか外から
  止められたのかを知れる方がよい。本人の記憶へは auto_ingest が配るので直接は書かない
  (直接書くと本人の分だけ二重になる)。

  「続きは求められたら話せる」までは**書かない**。まはー «知っても使い道がない…その文言を
  ペルソナが読むってことは、すでに次の発言を行っている最中なわけでしょ。続き、話したければ
  そこで喋ればいいじゃん»。

**残さないもの (一言も出ないうちに止められた回)**

`PulseController._record_interruption` を撤去した。届く条件が「生成が始まる前に止められた」
= 一言も出ていない回だけで、**707 セッション分のログを数えて実際に通ったのは 1 回**。そして
一言も出ていない回は、ペルソナから見れば「返事が生まれなかった」回と区別がつかない — そちらは
昔から何も書いておらず、中断だけ機構の声を足すと不揃いになる。まはー «無理に特別な機構を
入れるより、自然な形に任せた方がいいか»。

#### 押さえた設計上の制約

- **本人の発言そのものには追記も変更もしない。** 機構が足した注記を、ペルソナが自分の文体と
  して模倣し始める。印を付けたい場面では、発言の後ろに独立したメッセージを置く。
- **`metadata` の印はペルソナから知覚できない。** 画面や機構は読めるが、コンテキストには
  載らない。知らせたい事実はコンテキストに載る形で別に要る。
- **システムからの通告は `user` ロール + `<system>` タグ。** 多くの LLM が途中メッセージの
  `system` ロールを受け付けないため、SAIVerse ではこれが基本形 (`role: "user"` を
  「ユーザー発言の捏造」と読み違えない)。
- **ただし `user` + `<system>` は「取り込みが作る形」で、書き手が作る形ではない。**
  建物の記録へ書くときは **`role: "host"` で平文**。取り込み (`get_building_messages` の
  auto_ingest) が建物名を添えて `user` + `<system>` へ組み替えてから各ペルソナの記憶へ配る。
  入退室の通知が通っているのと同じ道。

  最初この通告を `user` + `<system>` のまま建物の記録へ書き、実機で**まはーのアバターと
  名前の吹き出し**として出た。まはー «さすがに俺の名義で出るのはおかしいぞ»。表示側に
  「user かつ `<system>` タグなら通知として描く」判定を足して塞ごうとしたが、まはー
  «似たような UI 向けシステムメッセージなのに複数種類あるのは、ちゃんと使い分けの理由が
  ない限り許すべきじゃないと思う» — 既存の `host` / `system` に三つ目の形を足すところ
  だった。使い分けの理由はあり (`host` = 建物の記録に載る世界の出来事、`system` = 記憶や
  コンテキストに載る機構のメッセージ)、正しい答えは `host` で書くことだった。表示側の
  追加判定は撤去した。

**tool-streaming 経路 (`sea/runtime_llm.py` の 3168 以降) には印を立てる処理が無い**。
ツールを使う playbook で停止したとき「続きの生成」が出るかは**未確認**。まはーが踏んだのは
pipeline 経路 (ログの `[sea][pipeline] Cancelled mid-stream` が証拠) なので、この回では

→ 2026-08-27 のまはー提起 (思考中の停止が完全な沈黙になる) を受けて、**中断のタイミング軸の

## 実機検証 ⑤ (2026-08-28 未明) — 切断に気づかず、無言のスピナーのまま固まる

まはーが応答の生成中にバックエンドを Ctrl+C で停止 (行儀のいい終了で、生成は完走して
世界と記憶には残った — その経緯は
[beat_interruption_timing_inventory](beat_interruption_timing_inventory.md) の「⑤の変種」)。
**ブラウザ側は、閉じた数秒後も「Streaming...」のスピナーのまま何も出なかった。**

出口 7 の実装が用意している二つの文言 (「接続が途中で切れました」/「発言が届いたか
どうかは判断できません」) は**どちらも出ていない**。つまり不合格の形は「嘘をつく」では
なく「**切れたことに気づかない**」— 復旧の文言まで切断の報せが届いていない。

### 原因の確定 (2026-08-28 未明、隔離再現)

スタブの streaming サーバー (:18000、本番と同じ uvicorn) + 私専用の Next (:3100、中継先を
スタブへ差し替え) + fetch の読み手 2 本 (直結 / 中継経由) で再現した。スタブを終了させると:

- **直結の読み手は、その瞬間にエラーを受けた** (`ERROR: terminated`) — フロントの復旧分岐は
  この形なら働く
- **中継経由の読み手は、done もエラーも受けず沈黙し続けた** (スタブの死から 20 秒以上観察)

つまり犯人は **Next の中継がバックエンドの切断をブラウザへ伝播させない**こと (仮説 2)。
フロントの復旧分岐に切断の報せ自体が届かない。加えてコード読みで、正常終了の顔で閉じた
場合はループが done で抜けて catch を通らず**何も表示しない**穴も確認した (仮説 1 も併存)。

### 直し方 (実装済み 2026-08-28、実機は次のバックエンド停止テストで)

バックエンドはキューが空でも **2 秒ごとに ping を必ず流す** (`manager/runtime.py:903` の
`queue.get(timeout=2.0)` → ping)。この保証を土台に、読み手へ**心拍監視**を付ける —
15 秒何も届かなければ (保証の 7 倍余裕) 切断と判断して既存の復旧分岐へ流す。中継の挙動に
依存しないので、行儀のいい終了・事故死・ネットワーク断のどれでも同じ道で拾える。
併せて「結果もキャンセルも見ないまま正常終了した」場合も異常として同じ分岐へ流す。

## 起票時の見立て (裁定前の記録)

四つの型に畳める。並べ替えると、直す順番の候補にもなる。

1. **内側の握り潰しが外側の網を無効化する** (段 4)。網は既にあるので、握るのをやめるだけで届く。
2. **契約の違う形を流している** (段 2 の生 HTML、段 5 の素の `ValueError`)。器 (`NDJSON イベント` / `LLMError`) は既にあるので、載せ替えるだけ。
3. **何も起きないことが正常終了と区別できない** (段 3 の応答者ゼロ、段 7 の空ストリーム)。
   これだけは新しい概念が要る — 「発言は受理したが応答は生まれなかった」を表す出口。
4. **文言が事実と違う** (段 6 の接続拒否＝タイムアウト表示)。分類を分けるか、文言を両にらみにするか。

1 と 2 は既存の器に載せる工事で、3 は設計の話、4 は文言と分類の話。
