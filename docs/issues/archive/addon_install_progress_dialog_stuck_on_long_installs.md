# 長い導入で、カタログの進捗の小窓が「完了」を受け取れずに回り続ける

**起票**: 2026-10-06 (voice-tts の画面確認で、まはーが実際に踏んだ)
**状態**: 完了 (2026-10-06)。同日に修正して v0.3.22 で発行した — 進捗の無い間も 10 秒ごとに生存信号を流し、切断後は問い合わせで完了に到達し、小窓はいつでも閉じられる。中継越しの切断の再現実験とテストで確認 ([voice_tts_catalog_listing.md](voice_tts_catalog_listing.md))
**関連**: [addon_catalog_management.md](../intent/addon_catalog_management.md) の「導入時の質問と、アドオン専用の Python 環境」

## 何が起きたか

2026-10-06 0 時すぎ、まはーが voice-tts 0.6.0 への更新をカタログから実行した (エンジン三つ全部を選択。ダウンロードは合計で数 GB、約 30 分)。バックエンドは全 step を完了し、アドオンの切り替え・専用環境・答えの保存まで仕上がった (backend.log と `~/.saiverse/addon_install/saiverse-voice-tts/` で確認) のに、ブラウザの進捗の小窓 (AddonInstallProgressDialog) は「更新中」のまま回り続け、完了の表示にならなかった。風呂から戻ったまはーが発見。小窓を手で閉じれば実害は無い。

## 原因 (2026-10-06 に実験で確認)

画面とバックエンドの間の中継 (Next の rewrites) が、**30 秒間なにも流れない接続を黙って切る** (既定の無通信の時間切れ)。進捗は step の出力一行ごとにしか流れないので、pip の大きな取得の無言区間 (実測 571 秒) で確実に切られる。切られた側のブラウザの読み取りは、終わりも失敗も受け取れずに無期限に止まる — これが「エラーも出ずに回り続ける」の正体。中継そのものを通した実験で、30.2 秒での切断と、読み取りが止まったままになることを再現した。10 秒ごとの生存信号 (keepalive) を流すと切られない。

付随して分かったこと: 起票時に「update/confirm の POST が二回」と書いたのは誤り (backend.log には一行だけ。読み違い)。アクセスログは応答の開始時に書かれるので、00:06:12 の 200 は「流し始めた」の意味で矛盾は無い。ただしコードの上では、開発モードの画面の二重実行 (React StrictMode) が確認の要求を二回送れる作りが実在し、さらに**ストリームの切断でアドオンごとの Lock が放れてしまう** (処理は走り続けているのに) 作りだったため、二重実行が重なると同じアドオンの処理が二重に走れた。どちらも今回の修正で塞いだ。

もう一つ: **小窓に閉じる手段が一切ない** (まはーの実機のスクリーンショットで確認)。回り続けると利用者はページの再読み込みしか選べない。

## 直し方の候補

- 小窓が SSE の切断を検知したら、進行中の操作の有無をポーリングで確かめて表示を立て直す (バックエンドには per-addon の Lock と pending の記録があるので、「まだ走っているか」「終わったか」は問い合わせで分かる)。
- あわせて、切断されても処理自体は続いていて壊れないことを文言で伝える。

## 確かめ方

隔離した環境で、重い step (数分かかる pip など) の途中で SSE の接続を落とし (開発者ツールで切断)、小窓が自力で完了へ到達することを見る。
