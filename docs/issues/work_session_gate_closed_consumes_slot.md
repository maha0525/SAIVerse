# 関所閉鎖 (BeatGateClosedError) が未実行の作業コマを消費する

**状態**: 未解決 (2026-07-30 起票、Codex 6巡目レビューの指摘2)。設計裁定待ち — 修正はデイプラン側の再試行設計を伴うため §14 消し込みのスコープ外として分離した。

## 現象

`run_work_session` は Beat ロックの関所 (実行台帳の pending flush) が通らないと `BeatGateClosedError` で始まらない。この例外は汎用の `except Exception` に拾われて `ended_reason='error'` の通常結果になり、デイプランの呼び出し面はそのまま post_session 処理へ進んで **コマ (slot) を done、実行台帳を applied に精算する**。

関所閉鎖は「実行未開始・副作用ゼロ・LLM 課金ゼロ」の失敗で、安全に再発火できるのに、予定された作業が再試行不能のまま消費される。

## 経緯と範囲

- 「error → コマ消費」の精算自体は §14 以前からの挙動 (関所は旧来ループ側の hold にもあった)。
- ただし 2026-07-30 の修正 (Codex 5巡目対応で hold_beat を組成の前へ拡大) により、関所閉鎖は**初回 LLM 課金より前**に起こるのが通常形になった。「何も実行していないのに消費」が明確になった分、再試行可能な扱いに直す価値が上がっている。
- 関所が閉じる状況 = pending 配送が失敗し続けている状態で、それ自体が異常系 (回復処理の領分)。頻度は低い。

## 修正の方向 (裁定待ち)

1. `run_work_session` で `BeatGateClosedError` を汎用 error と分離し、専用の結果 (例: `ended_reason='deferred'`) で返す。
2. デイプラン側 (`day_plan` の slot 発火面) は deferred のとき slot と予算予約を再実行可能状態へ戻し、post_session 判断と done/applied 精算を行わない。
3. 初回関所閉鎖の統合テスト (slot が消費されないこと)。

論点: slot の再武装 (再発火のタイミング・回数上限) の設計。単純な「戻す」だと閉じ続ける関所で無限再試行になるため、リトライ上限か「回復処理が関所を開けたら再開」の連動が要る。
