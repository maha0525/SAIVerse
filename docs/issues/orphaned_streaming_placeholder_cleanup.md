**ステータス**: 🟢 実装済み・検証待ち (2026-08-27 に例外経路も塞いだ。実機での確認が残り)
**優先度**: **high** — ⚠️ **害は「ゴミが溜まる」ではなく「発言そのものが消える」だった**
(下の「§ 起票時の見立ては誤りだった」を参照)

## 直した (2026-08-27) — Beat の出口で一括して受け止める

候補 1 の「300 行を try/finally で囲む」は採らなかった。`lg_llm_node` の node() には
**すべての死に方が通る except 節 (= Beat の出口) が既にあり**、そこへ後始末
`_settle_placeholder_on_beat_death` を差した (`sea/runtime_llm.py`)。囲み直しゼロで、
不変条件は「**node() は未確定の下書き行を残して終わらない**」になる。

- 発番から確定までの間に例外を投げうる箇所は数え上げられない (ストリーム呼び出し、
  spell loop、finalize 経路自身の失敗、asyncio.CancelledError)。入口で数える代わりに、
  出口で「確定していない下書き行が残っていたら確定させる」を保証する
- 後始末の中身は停止経路と同じ `_settle_interrupted_utterance` (旧
  `_settle_cancelled_utterance` を原因つきに拡張)。確定・印・記憶は原因によらず同じで、
  建物への通告の文面だけが変わる — ユーザーの停止なら「(ユーザーの操作により、ここで
  発言が中断されました)」、例外なら「(エラーにより、ここで発言が中断されました)」。
  一言も出ないうちに死んだ回は空文字で確定するだけで、何も語らない (停止と同じ規則)
- spell round の頭の取り消しに個別対応していた内側の except は撤去し、出口へ一本化した。
  通常の確定 3 箇所に「確定済み」の印 (`pipeline_finalized = True`) を立て、確定後の
  例外で二重確定しないようにした
- テスト: `tests/test_streaming_placeholder_salvage.py` (9 本)。LLM 即死・生成後の
  例外・生成直後の停止・タスク破棄・正常完了の一回性を固定

### Codex adversarial review (2026-08-27、1 巡目 5 件) を受けて直した 3 点

1. **ストリーム途中で死んだ回の部分文と連番** (high・裏取りで事実確認) — ストリーム消費中に
   例外が出ると返り値の tuple が届かず、出口の後始末が空文字と古い連番で確定していた
   (final の連番が発火済みの sub-speak と衝突する)。`_consume_pipeline_stream` に途中経過の
   器 (`progress`) を持たせ、受信済み chunk と最新連番を出口から回収するようにした。
   これで「途中で client が例外を投げた回の部分文は救えない」という当初の制限も消えた
2. **schedule / auto の割り込みが「ユーザーの操作により」と通告されていた** (medium・
   裏取りで事実確認) — 取り消しの例外型はユーザー停止と同じなので、型で判定すると機構起点の
   中断にユーザー起点の通告が捏造される。判定を取り消しに刻まれた原因 (`interrupted_by` が
   "user" / "user_stop" か) へ変えた (`_is_user_interruption`)
3. **BaseException 捕捉の範囲** (medium) — `asyncio.CancelledError` に絞った。
   KeyboardInterrupt / SystemExit / GeneratorExit というインタープリタ終了の道筋に
   DB 書き込みの副作用を足さない

### Codex 2 巡目 (2026-08-27、1 件) — 既存挙動と確認して見送り

**spell retry ストリームの途中死で、retry 中に UI/音声へ流れた部分文が記録に残らない**
(high)。指摘の事実関係は裏取りで確認した。ただしこれは**今回の修正前からの挙動**で、
spell loop の「内部エラーは partial へ降格して発言全体を失わない」という既存契約
(retry 前の `text = ""` リセットと `except Exception` の降格、`sea/runtime_llm.py`) が
作る形。下書き行自体は merged text で確定するので、この issue の主問題 (発言が丸ごと
消える) とは別の損失。直すには spell loop のエラー降格契約の再設計 (降格 vs 中断確定)
が要る。今回の diff はこの経路を変えておらず、retry 途中死の sub_seq 回収はむしろ
改善している。残すなら別 issue の器 — 現時点では
[user_utterance_path_failure_inventory.md](user_utterance_path_failure_inventory.md) の
「どの生成のどの段階かを運ぶものが無い」族に属する。

### 採らなかった指摘 (記録)

- **finalize の永続化失敗を成功扱いにする** (high) — `emit_speak_finalize` は永続化エラーを
  内部で握って戻るため、呼び出し元は失敗を検知できず、確定済みの印が立つ。指摘は事実。
  ただし直すには finalize の成否通知と再試行の冪等化という契約の再設計が要り、この失敗が
  起きるのは DB 自体が壊れている場面 (実測 32 件はすべて「finalize が呼ばれなかった」形で、
  「呼んだが DB が失敗した」形は観測されていない)。格に対して装備過剰と判断して見送り。
  起きたら backend.log に `emit_speak_finalize: failed to finalize placeholder` が残る
- **実永続層を通す契約テスト** (medium) — emitter 側は今回の差分で無変更のため、
  モック境界のテスト (runtime._emit_speak_finalize の呼び出し回数と引数) で足りると判断

### 通告の文面 (2026-08-27 決着)

- ユーザー起点 (`interrupted_by` が "user" / "user_stop"):
  「(ユーザーの操作により、ここで発言が中断されました)」(2026-08-26 まはー裁定のまま)
- 非ユーザー起点 (LLM エラー・schedule / auto の割り込み): 原因を書かない
  「(ここで発言が中断されました)」。「エラーにより」と括ると割り込みの回に嘘になる。
  通告の目的は「本人の言い切りではなく外から切られた」を伝えることで、原因の種別は
  必須ではない (まはーが収束判断と併せて委任、推奨案を採用)

## ⚠️ 起票時の見立ては誤りだった (2026-08-26 夜、実機で発覚)

**この文書は当初「害はゴミが溜まることに限られる、優先度 low」と書いていた。両方とも
誤り。** まはーが実機で踏んで分かった。

まはー «生成が終わった瞬間くらいにボタンを押してしまったっぽい。そしたら、記憶の方に
残ってなかった。そして別の部屋見て戻ってきたら、発言は完全に消滅»

### 何を読み違えたか

「`content: ""` の行が残る」を**ゴミが増える**と読んで、**その行に入るはずだった本文が
失われている**と読まなかった。下書き行は本文の器で、確定して初めて中身が入る。確定しな
ければ、ペルソナが実際に喋った内容は**どこにも残らない**。画面に出ないのは、消えた発言が
見えないだけで、無害の証拠ではなかった。

### 「ユーザーの停止は確定が通る」も誤りだった

当初こう書いていた —「中断されても確定は通る経路が用意されている: ユーザーの停止 →
同じく部分文で確定 + `_interrupted`」。**通るのはストリームの途中で止めた場合だけ。**

ストリームが最後まで流れきると `cancelled_during_stream` が立たないので停止の後片付けは
走らず、その直後に spell round の頭で取り消しが見つかると例外で抜けて、通常の確定にも
届かない。**生成し終わった直後に停止を押すと、この隙間に落ちる。**

## 何が起きているか

ペルソナが喋り始めるとき、`emit_speak_start` が **`content: ""` の行を先に建物の記録へ置く**
(`runtime_emitters.py:243-253`)。ストリーミングの断片は画面へ送られるだけでこの行には書かれず、
最後に `emit_speak_finalize` が本文を流し込んで確定する。

中断されても確定は通る経路が用意されている:

- サーバー側のストリーム中断 → 部分文で確定 + `_interrupted` の印 (2026-08-25 実装)
- ユーザーの停止 → 同じく部分文で確定 + `_interrupted`
  (⚠️ **2026-08-26 まではストリームの途中で止めた場合だけだった**。同日夜に全タイミングを
  塞いだ)
- `speak: false` のノード → 空文字で確定

**残っているのは「Beat が例外で丸ごと落ちた場合」だけ。** そのときだけ確定が走らず、
`content: ""` の行が `_streaming_placeholder: True` のまま残る。

## 確定しないと何が失われるか

下書き行は**本文の器**で、確定して初めて中身が入る。確定しなければ、ペルソナが実際に
喋った内容はどこにも残らない。

- **画面には出ない** — 履歴 API が content 空を除外する (`api/routes/chat.py:293-296`)
- **誰の記憶にも入らない** — 取り込みも content 空を `consumed` で飛ばす
  (`builtin_data/tools/get_building_messages.py:206`)
- 残るのは `building_messages` テーブルと `log.json` の**空の行**だけ

⚠️ **この二つを「無害」の根拠にしたのが起票時の誤り。** 画面にも記憶にも出ないのは、
**消えた発言が見えない**というだけで、失われていないことの証明ではない。本文は復元できない。

## なぜ切り出したか

置き場が「placeholder の発番 (`_emit_speak_start`) から finalize までの**約 300 行**」を
try/finally で囲む形になる。システムで最も熱い経路への構造変更で、害の小ささに見合わない。
束 2 を緑で仕上げた時点で、その危険を積む価値が薄いと判断した (まはーへ報告済み)。

## 直し方の候補 (起票時の検討。採ったのは冒頭の「Beat の出口」案 = 実質 1 の変形)

1. pipeline streaming の区間を try/finally で囲み、`pipeline_msg_id` が生きていたら
   空文字で finalize する。**最も直接的だが、囲む範囲が大きい**
   → 2026-08-27: 囲み直す代わりに、node() に既にある except 節 (Beat の出口) へ
   後始末を差した。範囲はむしろ広がり (発番から node 終端まで)、再インデントはゼロ
2. Beat の終わり (`_finalize_beat`) で「発番したが確定していない placeholder」を回収する。
   そのためには placeholder の id を Beat の器へ載せる必要がある
3. 起動時に `_streaming_placeholder: True` のまま残っている行を掃く。
   実行中の Beat の placeholder を誤って消さないよう、起動直後に限る
