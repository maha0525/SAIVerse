# 移動の瞬間に積む通知が、読む時点では嘘や無駄になる

**起票**: 2026-09-07 (まはーの実機報告 — エリスの知覚ダンプ)
**状態**: 実装中 (v0.3.10 の主案件、feature/perception-state-diff)

## 現象 (エリスの知覚に実際に出た列)

エリスが「エリスの部屋 → アイフィの部屋 → エリスの部屋」と往復してから Pulse を打ったとき、知覚に次の四つの問題が出た。

1. **よその部屋の在室通知が、居場所の文脈なしに残る**: アイフィの部屋に移った瞬間の「アイフィ がいます」が、エリスの部屋に戻った後の Pulse にそのまま出た。通知にはどの部屋で見たかの情報が含まれていないため、エリスはアイフィがその場にいるものとして発言してしまった (知覚が嘘になった)。
2. **スペルの「使えなくなりました」と「使えるようになりました」が同じ知覚に対で出る**: Elyth 関連スペルは部屋の往復で失って戻っただけで、差し引き何も変わっていないのに、通知が両方残った。往復のたびに件数が増える。
3. **スペル 1 件ごとに [システム通知] の見出しが付く**: 一度の変化で複数のスペルが変わると、その数だけ別々の通知ブロックになる。見出しが出来事ごとに付くこと自体は前日に確定した「一出来事一ラベル」([issues/archive/perception_event_boundaries_unclear.md](archive/perception_event_boundaries_unclear.md)) のとおりで、問題は「何を一つの出来事と数えるか」の粒度が細かすぎること。
4. **Memopedia も 1 ページごとに別々の通知になる**: 作成 3 件が 3 ブロックで出た (粒度の問題は 3 と同じ)。

## 原因

部屋を移った瞬間に、「前回知らせた状態と今の状態の差分」を計算して移動した本人の知覚バッファへ積んでいる ([dynamic_state.py](../../saiverse/dynamic_state.py) の `on_building_entered`)。バッファに積まれた通知は次の Pulse まで処理が保留されるため、Pulse を打たずに移動を重ねると、途中経過が全部そのまま出る。

「どこまで本人に知らせたか」の記録 (`last_notified`) と、Pulse 開始時の差分計算は既にある。本来はそれだけで「最後に知らせた状態 vs 今」の差分が出せる — 移動時に通知を積む処理が、この記録を途中経過の状態で更新してしまうのが根本原因。移動以外の変化 (アドオンの出し入れなど) は元々 Pulse 開始時の計算に任されており、移動だけが例外的に途中経過を積んでいた。

3・4 は独立の問題で、差分から通知を生成する処理 (`spell_list` / `memopedia_index` の `diff_to_notifications`) が変化 1 件ごとに別ラベルを生成している。

## 直し方 (2026-09-07 まはー承認)

承認の出典: 4 点の提案 (本人向けの積み込み廃止 / 「がいます」廃止 / スペル・Memopedia の束ね) への返答 —「うん、それがいいと思う！退役して部屋の様子にってのも、むしろ本来そうすべきとこだったしすごくいい。対応よろしく、これを0.3.10で！」(2026-09-07)。1・2 の元になった方向づけ (「最後に覚えてた状態と今現在の状態を比較する形にしないと」) と 4 の形 (「更新・作成・削除それぞれで1行ずつにまとめられるでしょ」) は、まはーの報告メッセージ自身にある。

1. **移動の瞬間に本人へ積むのは「移動の事実」だけにする**。在室者・スペルなどの差分は Pulse 開始時の計算に任せる。往復では「最後に知らせた状態」と「今」が一致するので、通知自体が出なくなる (1・2 の根が消える)。移動通知は本物の出来事なので従来どおり移動時に積む — [room_state_packages.md](../intent/room_state_packages.md) §11-1「移動した事実だけは一行の経路で残す (体験の消去はしない)」と §11-2 の経路一行の畳みは無傷に保つ。居合わせた側への「X が入室しました」通知と、部屋の様子の配送もそのまま残す。
2. **「〜がいます」の通知を廃止する**。同席者の情報は部屋の様子に既に含まれていて重複 (v0.3.9 の指示の一本化と同じ型 — まはー「むしろ本来そうすべきとこだった」)。同じ部屋に居るあいだの「入室しました / 退室しました」は本物の出来事なので残す — [room_state_packages.md](../intent/room_state_packages.md) §6-2「到着時は状態 (誰がいる) を、滞在中は出来事を、で二重に語らない」の役割分担どおりで、廃止するのは到着時の状態側だけ。
3. **スペル通知は「使えるようになった」「使えなくなった」の種別ごとに 1 ラベルへ束ねる**。使えるようになった側は、各スペルの引数の説明ごと 1 ラベルに並べる。使えなくなった側は名前の列挙の一行だけ (「もう唱えられない」に引数の形は要らない — 現行の既決定の維持)。一出来事一ラベルの数え方は「一度の差分検知で出た同種の変化 = 一つの出来事」とする (粒度の是正であって、前日の裁定の変更ではない)。
4. **Memopedia 通知は作成・更新・削除それぞれ 1 ラベル (= 1 行) へ束ねる** (例: Memopedia「A」「B」が作成されました)。最大 3 ラベルで、それぞれに [システム通知] の見出しが付く。
5. (実装時に見つけた同族) **能力 (Playbook) の通知も同じ「1 件 1 ラベル」の型だったので、3 と同じ形で種別ごとに束ねた** (`available_playbooks`)。
6. **再会の想起の発火を Pulse 開始時の同席チェックへ移す** (2026-09-07 まはー承認、実機検証で見つかった追加の欠陥への対応)。旧実装は移動の瞬間に入室ラベルを目印として想起を積んでいたため、読まれるのは次の Pulse — その間に本人がさらに移動すると「もう居ない相手との再会」が届いた (1 の「がいます」と同じ型の嘘)。往復のたびに同じ想起が積み重なる欠陥も同じ根。Pulse の頭で「いま実際に同席している相手」を見れば、同じ Pulse が発火して同じ Pulse で消費するので、どちらも構造的に消える。
   - **同席の縁を覚えて、再発火を止める**: 発火の条件が「同席している」という**状態**になったので、そのままでは同席中ずっと門が開きうる — 隣で黙っている相手は直近の文脈に痕跡が無いため、毎 Pulse 過去会話 6 件が積まれる (旧実装は「入室」という一回きりの出来事に紐づいていたのでこの問題が無かった)。プロセス内に「不在から同席へ変わった相手を、その同席の間に想起を試み済みか」の記憶 (persona_id → 相手 ID の集合) を持たせて、出来事発火の性質を復元する。門で抑制された回も、想起本文が空だった回も、push が失敗した回も**試み済み**として記録する (再会の瞬間は一度きり。毎 Pulse 再試行に戻すと同じ欠陥が別の形で残る)。記憶に残すのは「いま同席している試み済みの相手」だけなので、退室すると集合から落ちて次の再会で再武装される。SAIMemory が未 ready の回だけは記憶を触らずに戻る (次の Pulse の頭が新顔としてやり直す)。プロセス再起動でこの記憶は消え、再起動後の最初の Pulse で門を通った相手に想起が一回出る — 旧実装の「入室ごとに一回」と同じ量なので受容する。
   - **旧方式が積んだ想起は回収が捨てる (移行の掃除)**: 新方式の想起には metadata で印 (`{"copresence": true, "occupant_id": …}`) を付け、印の無い `persona_recall` を未消費バッファの回収が遺物として組成から外す ([room_state_packages.md](../intent/room_state_packages.md) §11-2 規則 3(c))。発火点を移しても、旧方式が移動時に積んだ想起はユーザーの知覚バッファに未消費のまま残っていて、次の Pulse で新方式の想起と二重に読まれる (まはーの実機ではエリスに同じ相手の想起が複数枚溜まっていた)。v0.3.9 を使った一般ユーザーの環境にも同じ形で存在するので、掃除を v0.3.10 に同梱する — 手動の掃除は要らず、再起動後の最初の消費で自動的に済む。
   - **発火の位置は建物発言の取り込みの後**: `DynamicStateManager.maybe_inject_event_messages` の中から呼ぶと、同席者の発言の取り込み (`auto_ingest_building_messages`) より前に門が判定してしまい、直前に喋った相手が「久しぶりの相手」に化ける。呼び出しを `sea/runtime.py` の `run_meta_user` へ出し、取り込みの後・知覚の消費の前に置く。もう一つの Pulse root (`sea/work_session.py`) には置かない — 取り込みも世界状態の検知も持たない「指示書に向かうコマ」で、門に見せる会話の文脈がそもそも組まれていない。

7. **配達中に来た配達依頼を、外側の配達が終わったその場で引き継ぐ** (2026-09-07、まはーの実機で「別ペルソナ宛ての入室通知が数十秒遅れる」が確定したことへの対応)。移動の配送の handler は、居合わせた側へ入室通知を積んで配達を頼む。だがその依頼は同じスレッドが配達の鍵を握っているために配れず、そのまま忘れられて 60 秒の回復処理待ちになっていた (実測 38 秒)。退いた依頼の相手を到着順の控えに残し、外側の配達が鍵を離した後に控えが空になるまで順に配る。排出の最中に生まれた依頼も同じ控えに載って続けて片付く。上限 (50 件) で打ち切った残りだけが回復処理送りになる。**特殊分岐は置かない** — 「知覚の場合は」「別ペルソナ宛ての場合は」で分けず、退いた依頼は種類を問わず全部控えへ入れる (同じ persona 宛ての追加行は既存の配り直しループの担当なので、実際に控えに載るのは自分以外の相手への依頼だけになる)。詳細は [execution_ledger.md](../intent/execution_ledger.md) §2.2。
8. **コンテキストプレビューに「Pulse の頭で検知される分」を読み取り専用で合成する** (2026-09-07、まはーの実機で「エリスの退室がプレビューに出ない」が確定したことへの対応)。6 で検知が Pulse の頭へ移った結果、「知覚バッファに溜まっている物」と「話しかけた瞬間にペルソナが読む物」の間に頭の検知ぶんの差が開いた。プレビューの組成時に、実 Pulse の頭と同じ三つの検知 (世界状態の差分 → 部屋の様子の照合 → 同席の想起) を**読み取り専用**で走らせ、結果を仮の未消費項目として実際の未消費の後ろに (= 実 Pulse の到着順で) 合成してから、既存の reduce → 回収 → 消費時描画へ通す。UI は変更しない。
   - **読み取り専用の中身**: 基準 (`last_notified`) を進めない (`flush_diffs(..., advance=False)` の戻りを使うだけで前進を呼ばない) / 知覚バッファに push しない / 実行台帳に行を作らない / 同席想起の「試み済み」の記憶に触れない / head の snapshot も撮らない。部屋の様子は「積むはずの束」だけを映し、置き直し (自己回復) は行わない — 置き直しは提示への書き込みで、しかも未消費の項目を生まないので映すものが無い。
   - **分離の形**: 実配送側の挙動を変えないために、`_detect_room_state_changes` を「照合の計算だけして予定を返す」(`_plan_room_state_change`) と「その戻りを push / 置き直しする」外装に割った。同席想起も同じく `_compose_copresence_recalls`(「試み済み」を更新しないモードつき) と push の外装に割った。プレビューの入口は `sea/head_pipeline/integration.preview_head_perceptions` の一枚。

## 実装メモ (設計の穴 2 点への手当てを含む)

- **2 の廃止は、「B (last_notified) は配送だけが進める」(2026-08-17 まはー裁定、[pipeline.py](../../sea/head_pipeline/pipeline.py) `capture_all` の docstring) への意図的な例外を一つ開ける**: 部屋が変わったとき、「〜がいます」を出さなくても比較の基準は新しい部屋の顔ぶれまで進める必要がある (進めないと基準が古い部屋のまま残り、その後の入退室の差分が出なくなる)。実装は「配送しないラベル」(`NotificationLabel` に deliver フラグを足し、検知はするがペルソナに文としては届けない) を推す — 基準の前進は従来どおり配送確定の流れの中でだけ起き、capture 系が基準を触らない構図は崩れない。不変条件が守っていた実害 (未配送の差分の既読化) について: 部屋を移った時点で旧部屋の未配送の入退室が既読化されるのは「がいます」の現行実装と同一の挙動で、退行ではない。
- **在室者の基準は移動の瞬間に進める** (`only_sections` に `building_occupants` を含める)。ここを Pulse 開始時まで遅らせると、基準が旧部屋の顔ぶれのまま残り、本人が Pulse を打つ前に誰かが同じ部屋へ入ってきた回まで「部屋替え」の比較に化けて、「X が入室しました」が消える (改修前は届いていたので退行。2026-09-07 の Codex 二巡目で発見)。届く文は増えない — 部屋替えの分岐のラベルは全部 deliver=False なので、移動時に走るのは基準合わせだけ。スペル等は対象外のままで、自分のラベルの配送で従来どおり進む。
- **検知した Section の基準は一律に進める**: deliver=False のラベルしか出さない Section (部屋替え時の同席者) にも後段の処理はもう無い (6 で想起の発火点が Pulse の頭へ移った) ので、SAIMemory の readiness で前進を分ける理由が消えた。二分のために足していた `NotificationLabel.section` (`flush_diffs` が出所の名前を刻む) も撤去した。台帳の無い直接経路の「SAIMemory が未 ready なら何も進めない」は、配送する文がある回の既存挙動なのでそのまま残す。
- **再会の想起は発火点ごと移す (6)**: 旧実装 (`_inject_persona_recall_on_enter`) は kind=`occupant_entered` のラベルを目印にしていたので、「〜がいます」を消すとラベルの deliver フラグで発火点を延命する必要があった。実機検証で「もう居ない相手の想起が届く」欠陥が出たため、目印をラベルから外して `inject_copresence_recall(persona, manager, building_id)` へ作り直し、Pulse の頭 (`DynamicStateManager.maybe_inject_event_messages`) で `manager.occupants` のいまの顔ぶれを見る形にした。門 (`HistoryManager.should_recall_persona`)・ユーザーも対象・門の失敗は想起する側に倒す、の規約はそのまま引き継ぐ。deliver=False のラベルと `occupants_baseline` マーカーは基準の前進のために残る。
- どの変更も未消費バッファと通知の生成側だけの話で、提示済みの列 (キャッシュの前方一致) には触れない。

- **ローカルレビュー (Qwopus)**: 指摘ゼロ。唯一の「不明」(push 失敗時の戻り値) は現物確認で問題なし。
- **Codex 一巡目** (high 4): 採用 2 — 空の移動先で基準が進まない / 台帳経路の silent 分岐が未 ready でも基準を進める。却下 2 — outbox DEAD 後の基準 (2026-07-17 S3 の既存設計、本差分は不変更) / 検知→前進の並行窓 (at-least-once として文書化済みの既存設計)。
- **Codex 二巡目** (high 2): 両方採用 — 移動後 Pulse 前の入室が配送なしに化ける退行 (在室者を移動時の検知対象へ戻して修正) / 混在回の基準前進の Section 二分。
- **Codex 三巡目** (high 1 + medium 1): **両方却下** — どちらも再会の想起の配送保証を求める指摘だが、(a) 想起の目印 (部屋替え時の同席者ラベル) は相手と居合わせる部屋替えのたびに再生成されるので「永久に失われる」は成立しない (取りこぼしはその一回ぶん)。(b) 想起が push 失敗・中断で消えうるのは改修前からの挙動で、想起は元々配送保証を持たない繋ぎ実装 (`_inject_persona_recall_on_enter` の docstring)。本差分で悪化していない。(c) 前提の「SAIMemory 未 ready」は実質起動直後の窓だけ。想起の恒久化は Note システム (想起の本体) の設計の話で、本件のスコープ外。
- **まはーの実機検証 (2026-09-07)**: 「もう居ない相手との再会の想起が、移動の後も知覚バッファに残って届く」。1 の「がいます」と同じ型 (移動の瞬間に積んだ知覚が、読む時点で嘘になる) が想起にも残っていた。直し方 6 として、発火点をラベルから Pulse の頭の同席チェックへ移した。三巡目で却下した「想起の配送保証」の議論は、想起が毎 Pulse の頭で組み直されるようになったことで前提ごと解消した。
- **Codex 四巡目** (high 1): 採用 — 発火点を Pulse の頭へ移したことで条件が「同席している」という状態になり、同席中なのに会話していない相手には門が毎 Pulse 開いて過去会話 6 件が積み上がる (状態発火の再発火問題)。直し方 6 の「同席の縁の記憶」で出来事発火の性質を復元し、併せて発火の位置を建物発言の取り込みの後へ動かした (門に直近の発言を見せてから判定する)。

- **Codex 五巡目** (high 1 + medium 2): **3 件とも却下** — いずれも同席想起の例外経路の隅。(a) 取り込み失敗後の想起 = 失敗時に起きるのは会話中の相手への想起一回のノイズで、損失側には倒れない (履歴の痕跡が足りない回は門が開く側に倒れる)。独立の best-effort 二段を成功信号で結合する複雑さに見合わない。(b) SAIMemory 未 ready 中の退室の再武装漏れ = 「想起済みの後に未 ready へ戻る」窓が実運用にほぼ無く、損失は次の再会一回ぶんで恒久ではない。(c) 同席一覧と記憶更新の競合 = 同一ペルソナの Pulse は Beat ロックで直列なので前提が成立しない。残る窓は「目を覚ました瞬間に居た相手が直後に退室」で、これは嘘ではない。三・五巡目と同じく、的が繋ぎ実装の例外経路へ移った時点で本件の検証は収束と判定。

- **まはーの実機検証 (2026-09-07、二件目)**: 再起動後まだ一度も Pulse していないペルソナのコンテキストプレビューが、そのペルソナの per_persona MCP スペル (エリス) を「使えなくなりました」と偽表示した。per_persona のツール一覧は Pulse の頭で本人の接続から取りに行く作りなので、未取得の間は登録簿に無い — [mcp_addon_integration.md](../intent/mcp_addon_integration.md) §I は同じ理由の除外を head の鮮度検査には置いていたが、8 で新設したプレビューの読み取り専用検知 (`preview_head_perceptions` → `flush_diffs` → `SpellListSection.diff_to_notifications`) にはそれが効いておらず、「取っていない」を「消えた」と読んでいた。除外を差分の計算そのものへ配線し、判定 (`_is_unfetched_per_persona_spell`) を鮮度検査と共有した。
