# 移動の瞬間に積む通知が、読む時点では嘘や無駄になる

**起票**: 2026-09-07 (まはーの実機報告 — エリスの知覚ダンプ)
**状態**: 実装中 (v0.3.10 の主案件、feature/perception-state-diff)

## 現象 (エリスの知覚に実際に出た列)

エリスが「エリスの部屋 → アイフィの部屋 → エリスの部屋」と往復してから Pulse を打ったとき、知覚に次の四つの問題が出た。

1. **よその部屋の在室通知が、居場所の文脈なしに残る**: アイフィの部屋に移った瞬間の「アイフィ がいます」が、エリスの部屋に戻った後の Pulse にそのまま出た。通知にはどの部屋で見たかの情報が含まれていないため、エリスはアイフィがその場にいるものとして発言してしまった (知覚が嘘になった)。
2. **スペルの「使えなくなりました」と「使えるようになりました」が同じ知覚に対で出る**: Elyth 関連スペルは部屋の往復で失って戻っただけで、差し引き何も変わっていないのに、通知が両方残った。往復のたびに件数が増える。
3. **スペル 1 件ごとに [システム通知] の見出しが付く**: 一度の変化で複数のスペルが変わると、その数だけ別々の通知ブロックになる。見出しが出来事ごとに付くこと自体は前日に確定した「一出来事一ラベル」([issues/archive/perception_event_boundaries_unclear.md](archive/perception_event_boundaries_unclear.md)) のとおりで、問題は「何を一つの出来事と数えるか」の粒度が細かすぎること。
4. **Memopedia も 1 ページごとに別々の通知になる**: 作成 3 件が 3 ブロックで出た (粒度の問題は 3 と同じ)。

## 原因

部屋を移った瞬間に、「前回知らせた状態と今の状態の差分」を計算して移動した本人の知覚バッファへ積んでいる ([dynamic_state.py](../../saiverse/dynamic_state.py) の `on_building_entered`)。バッファに積まれた通知は次の Pulse まで処理が保留されるため、Pulse を打たずに移動を重ねると、途中経過が全部そのまま出る。

「どこまで本人に知らせたか」の記録 (`last_notified`) と、Pulse 開始時の差分計算は既にある。本来はそれだけで「最後に知らせた状態 vs 今」の差分が出せる — 移動時に通知を積む処理が、この記録を途中経過の状態で更新してしまうのが根本原因。移動以外の変化 (アドオンの出し入れなど) は元々 Pulse 開始時の計算に任されており、移動だけが例外的に途中経過を積んでいた。

3・4 は独立の問題で、差分から通知を生成する処理 (`spell_list` / `memopedia_index` の `diff_to_notifications`) が変化 1 件ごとに別ラベルを生成している。

## 直し方 (2026-09-07 まはー承認)

承認の出典: 4 点の提案 (本人向けの積み込み廃止 / 「がいます」廃止 / スペル・Memopedia の束ね) への返答 —「うん、それがいいと思う！退役して部屋の様子にってのも、むしろ本来そうすべきとこだったしすごくいい。対応よろしく、これを0.3.10で！」(2026-09-07)。1・2 の元になった方向づけ (「最後に覚えてた状態と今現在の状態を比較する形にしないと」) と 4 の形 (「更新・作成・削除それぞれで1行ずつにまとめられるでしょ」) は、まはーの報告メッセージ自身にある。

1. **移動の瞬間に本人へ積むのは「移動の事実」だけにする**。在室者・スペルなどの差分は Pulse 開始時の計算に任せる。往復では「最後に知らせた状態」と「今」が一致するので、通知自体が出なくなる (1・2 の根が消える)。移動通知は本物の出来事なので従来どおり移動時に積む — [room_state_packages.md](../intent/room_state_packages.md) §11-1「移動した事実だけは一行の経路で残す (体験の消去はしない)」と §11-2 の経路一行の畳みは無傷に保つ。居合わせた側への「X が入室しました」通知と、部屋の様子の配送もそのまま残す。
2. **「〜がいます」の通知を廃止する**。同席者の情報は部屋の様子に既に含まれていて重複 (v0.3.9 の指示の一本化と同じ型 — まはー「むしろ本来そうすべきとこだった」)。同じ部屋に居るあいだの「入室しました / 退室しました」は本物の出来事なので残す — [room_state_packages.md](../intent/room_state_packages.md) §6-2「到着時は状態 (誰がいる) を、滞在中は出来事を、で二重に語らない」の役割分担どおりで、廃止するのは到着時の状態側だけ。
3. **スペル通知は「使えるようになった」「使えなくなった」の種別ごとに 1 ラベルへ束ねる**。使えるようになった側は、各スペルの引数の説明ごと 1 ラベルに並べる。使えなくなった側は名前の列挙の一行だけ (「もう唱えられない」に引数の形は要らない — 現行の既決定の維持)。一出来事一ラベルの数え方は「一度の差分検知で出た同種の変化 = 一つの出来事」とする (粒度の是正であって、前日の裁定の変更ではない)。
4. **Memopedia 通知は作成・更新・削除それぞれ 1 ラベル (= 1 行) へ束ねる** (例: Memopedia「A」「B」が作成されました)。最大 3 ラベルで、それぞれに [システム通知] の見出しが付く。
5. (実装時に見つけた同族) **能力 (Playbook) の通知も同じ「1 件 1 ラベル」の型だったので、3 と同じ形で種別ごとに束ねた** (`available_playbooks`)。

## 実装メモ (設計の穴 2 点への手当てを含む)

- **2 の廃止は、「B (last_notified) は配送だけが進める」(2026-08-17 まはー裁定、[pipeline.py](../../sea/head_pipeline/pipeline.py) `capture_all` の docstring) への意図的な例外を一つ開ける**: 部屋が変わったとき、「〜がいます」を出さなくても比較の基準は新しい部屋の顔ぶれまで進める必要がある (進めないと基準が古い部屋のまま残り、その後の入退室の差分が出なくなる)。実装は「配送しないラベル」(`NotificationLabel` に deliver フラグを足し、検知はするがペルソナに文としては届けない) を推す — 基準の前進は従来どおり配送確定の流れの中でだけ起き、capture 系が基準を触らない構図は崩れない。不変条件が守っていた実害 (未配送の差分の既読化) について: 部屋を移った時点で旧部屋の未配送の入退室が既読化されるのは「がいます」の現行実装と同一の挙動で、退行ではない。
- **在室者の基準は移動の瞬間に進める** (`only_sections` に `building_occupants` を含める)。ここを Pulse 開始時まで遅らせると、基準が旧部屋の顔ぶれのまま残り、本人が Pulse を打つ前に誰かが同じ部屋へ入ってきた回まで「部屋替え」の比較に化けて、「X が入室しました」が消える (改修前は届いていたので退行。2026-09-07 の Codex 二巡目で発見)。届く文は増えない — 部屋替えの分岐のラベルは全部 deliver=False なので、移動時に走るのは基準合わせと再会の想起だけ。スペル等は対象外のままで、自分のラベルの配送で従来どおり進む。
- **配送あり・なしが混じる回の基準の前進は Section ごとに分ける**: 文を届けた Section (outbox に載った) はそのまま進め、deliver=False だけの Section は SAIMemory が ready のときだけ進める。一律に進めると、想起を積めなかった回に基準だけ新しい部屋へ動き、その入室が二度と差分に出ない (deliver=False だけの回と同じ倒し方)。どの Section がどのラベルを出したかは `NotificationLabel.section` (`flush_diffs` が出所の名前を刻む) で引く。
- **再会の想起の発火点を保つ**: 入室時に相手との過去会話を思い出す処理 (`_inject_persona_recall_on_enter`) は、kind=`occupant_entered` のラベルを目印に発火している。「〜がいます」を単純に消すと、誰かが居る部屋へ入ったときの想起が発火しなくなる。「配送しないラベル」なら kind と metadata が残るので、想起はそのまま動く (在室者を移動時の検知の対象に残したので、発火点も従来どおり移動の瞬間。消費はどのみち次の Pulse)。
- どの変更も未消費バッファと通知の生成側だけの話で、提示済みの列 (キャッシュの前方一致) には触れない。

## 経緯 (レビューの列)

- **agy 言葉づかい検査 + Opus 整合性検査** (2026-09-07、文書レビューフローの初運用): 言葉づかいの指摘を反映し、整合性検査の A1 (「基準は配送だけが進める」不変条件への例外の明示) と出典の引用を本文へ取り込んだ。
- **ローカルレビュー (Qwopus)**: 指摘ゼロ。唯一の「不明」(push 失敗時の戻り値) は現物確認で問題なし。
- **Codex 一巡目** (high 4): 採用 2 — 空の移動先で基準が進まない / 台帳経路の silent 分岐が未 ready でも基準を進める。却下 2 — outbox DEAD 後の基準 (2026-07-17 S3 の既存設計、本差分は不変更) / 検知→前進の並行窓 (at-least-once として文書化済みの既存設計)。
- **Codex 二巡目** (high 2): 両方採用 — 移動後 Pulse 前の入室が配送なしに化ける退行 (在室者を移動時の検知対象へ戻して修正) / 混在回の基準前進の Section 二分。
- **Codex 三巡目** (high 1 + medium 1): **両方却下** — どちらも再会の想起の配送保証を求める指摘だが、(a) 想起の目印 (部屋替え時の同席者ラベル) は相手と居合わせる部屋替えのたびに再生成されるので「永久に失われる」は成立しない (取りこぼしはその一回ぶん)。(b) 想起が push 失敗・中断で消えうるのは改修前からの挙動で、想起は元々配送保証を持たない繋ぎ実装 (`_inject_persona_recall_on_enter` の docstring)。本差分で悪化していない。(c) 前提の「SAIMemory 未 ready」は実質起動直後の窓だけ。想起の恒久化は Note システム (想起の本体) の設計の話で、本件のスコープ外。
