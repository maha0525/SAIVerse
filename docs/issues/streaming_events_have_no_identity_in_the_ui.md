**ステータス**: 🔲 未着手 — 設計から
**優先度**: medium — サーバー側の記録は正しく、再読込で直る。ただしボタンの誤爆経路が未検証

## 共通の根 — 「どの生成の、どの段階の話か」を運ぶものが無い

切り出した 4 件は別々の顔をしているが、**一つのストリームについて「これはどの生成のことで、
いまどの段階まで進んだのか」を運ぶ仕組みが無い**という同じ欠落から出ている。

- この issue (画面側に識別子が無い) は**どの生成の話か**が運べていない。断片がどのペルソナの
  どの Pulse のものかを、画面側が照合しない。
- [保存できたことを表す信号が無い](stream_completion_is_not_proof_of_persistence.md) は
  **どの段階まで進んだか**の話で、画面に出たところまでなのか DB に残ったところまでなのかを
  受け手が区別できない。
- [未知の送信結果から復旧できない](unknown_send_outcome_has_no_recovery_path.md) も段階の話で、
  発言がサーバーに残ったのかどうかを後から尋ねる手段が無い。
- [retry がサーバー側で再送可能性を見ていない](retry_api_has_no_server_side_eligibility_check.md)
  も段階の話で、その発言が既に応答を得たのかどうかを発言自身が持っていない。

4 件を別々に補修すると、同じ判断が経路ごとに別の場所へ書き分けられる (この inventory の
レビュー 3 巡で繰り返し出た型)。**設計するときは 4 件を一つの束として扱う**のが安全で、
どれか 1 件だけを先に直す場合も、残り 3 件がその決めごとに乗れるかを見てから決める。

---

## 何が起きているか (コードで確認した事実)

- `frontend/src/app/page.tsx` の `streaming_chunk` (`:1899`)、`streaming_discard` (`:1923`)、
  `streaming_complete` (`:1933`) は、いずれも `prev[prev.length - 1]` = メッセージ配列の最後の
  1 件だけを見て、それが `_streaming` なら書き足す・捨てる・確定する。
  **どのペルソナのどの Pulse の断片かは照合しない。**
- 材料は既に手元にある。`Message` 型は `_pulse_id` を持ち (`:160`)、断片を受け取ったときに
  書き込んでもいる (`:1908`, `:1918`)。さらに `activity` の分岐は、確定済みメッセージを
  `_pulse_id` で照合する処理を既に持っている (`:1826-1835`)。
  **ストリームの 3 種だけが、その材料を使っていない。**
- バックエンドは 2026-08-26 のレビュー 3 巡目で出どころを分けた。`manager/runtime.py:82-90` の
  `_stream_key` が `persona_id/pulse_id` を組み立て、断片の印と撤回をその単位で持つ。
  **サーバーとフロントで、同じ判断の粒度が食い違っている状態**になっている。

## ユーザーから見て何が起きるか

部屋に応答できるペルソナが複数いると、一度の送信で並行して喋る回がある。そのとき次のことが
起こりうる。

- 片方の断片が、もう片方の吹き出しへ繋がって表示される
- 片方の `streaming_discard` (ツール呼び出しが見つかったので断片を捨てる合図) が、もう片方の
  吹き出しを消す

**サーバー側の記録は正しい。** 建物の記録もペルソナの記憶も出どころごとに分かれて保存されるので、
画面を再読込すれば正しい形に戻る。

**ただし未検証の経路が一つある。** バブルのボタン (続きの生成 / 再送 / 取り消す) は吹き出しに
紐づく。混線した吹き出しから操作したとき、意図しない発言に対して操作が飛ぶかどうかを
確かめていない。飛ぶなら、表示だけの問題ではなくなる。**この確認が、この issue の最初の一手**。

## なぜ補修で塞げないか

2026-08-26 に補修を止めたのがこの地点で、理由もそれ。「最後の吹き出しを見る」場所は上の 3 箇所
では済まず、`say` や `activity` や `auto_recall` も同じ形を持っている。照合を一つずつ足していくと、
どの分岐が何を見ているかが場所ごとに違う状態が残り、次に触った人が片方だけ直す
(このレビューで繰り返し出た型)。

## 直すのに要るもの (設計の入口)

**`Message` が「どの生成に属するか」をどう持つかを先に決めて、全分岐をその形に揃える**。
論点は三つ。

1. **`_pulse_id` 単独で足りるか**。同じ Pulse の中で複数の吹き出しが生まれる場面
   (spell 経路の `streaming_discard` → `say` の差し替えなど) があるので、ペルソナ id との組が
   要るかを確かめる。サーバーの `_stream_key` は組で持っている。
2. **進行中の吹き出しを引く関数を 1 つにする**。いまは各分岐が `prev[prev.length-1]` を直接
   見ている。引き当ての規則が一箇所にあれば、次に増える分岐も同じ規則に乗る。
3. **サーバーの `_stream_key` と粒度を揃える**。片方だけ変えると、また同じ判断が二箇所に
   分かれる。`_OUTCOME_EVENT_TYPES` の鏡が既にフロントにあり
   (`frontend/src/app/page.tsx:1609`)、「この集合を変えるときは鏡も同じコミットで揃えること」と
   注記されている。同じ扱いをこちらにも要る。
