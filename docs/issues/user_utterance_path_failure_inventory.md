# ユーザー発話から応答完了までの停止点の棚卸し

**ステータス**: 🟡 実装待ち — 洗い出し完了、設計は 2026-08-25 のまはー裁定で確定 (下の「設計の決着」)。
やり直しは v0.3 の門の内側へ引き上げ済み ([v030_release_gate.md](../overview/v030_release_gate.md) §2-17)。
**出自**: 2026-08-24 に NEBULA の provider を選んで話しかけたら無言だった件 ([user_lane_error_silent_in_ui](user_lane_error_silent_in_ui.md))。
まはー «今回は LLM サーバー側との接続失敗が原因だったと思うけど、ユーザーが話しかけてから
ペルソナが応答完了するまでっていろんな障壁があるはずでしょ？どこで止まる可能性があって、
そのうちユーザーに原因も対応も分からない形なのがどれか、っていうのの洗い出しからやりたい»

**この文書の役目**: 一件ずつ後追いで起票してきた「無言で止まる」の上流に立ち、経路全体を並べて
**落ちうる場所** と **落ちたとき本人に何が見えるか** を対にする。設計はまだしない — 材料を作る回。

## 判定の語彙

落ちること自体は避けられない。問うのは「落ち方」で、四段に分ける。

| 記号 | 意味 |
|---|---|
| ✅ 分かる | 何が起きたか・どうすればいいかが日本語で本人に届く |
| 🔤 開発者語 | 何か出るが、原因も直し方も一般ユーザーには読めない (英語・内部用語) |
| 🎭 誤誘導 | 何か出るが、**内容が事実と違う方向を指す** — 分かる顔をしているぶん無言より悪いことがある |
| 🕳️ 無言 | 画面に何も出ない。スピナーが消えて終わる |

### 段 4 — 会話の起動 (ここが 8/24 の現物)

**同じ失敗が、会話が開いているかどうかで見え方が正反対になる。**

| 経路 | 例外の行き先 | 判定 |
|---|---|---|
| 会話が開いている (継続発話) | `user_conversation.py:833` が `UserUtteranceError` に包んで**上へ送出** → `runtime.py:722-732` の catch-all → `{"type":"error", content:"予期せぬエラーが発生しました。", technical_detail:...}` → フロントが吹き出しに描画 (`page.tsx:1985`) | 🔤 出るには出る。文言は汎用、詳細は英語 |
| 会話が開いていない (新規開始) | `user_conversation.py:760-763` が `except Exception: LOGGER.exception(...)` で**握り潰す**。`event_callback` は同じ関数の 739・747 行で手元にあるのに、エラーには使っていない | 🕳️ **catch-all まで届かない。8/24 の無言はこれ** |

芯は「エラー通知が存在しない」ではなく、**外側にはちゃんと網 (catch-all) があるのに、内側の握り潰しがそれを無効化している**こと。
網を足す話ではなく、網より内側で握るのをやめる話になる。

### 段 6 — LLM 呼び出し

| 停止点 | いま何が見えるか | 判定 |
|---|---|---|
| 接続拒否 (サーバーが落ちている・ポートが違う) | `openai_errors.py:31-37` が `APIConnectionError` を **`LLMTimeoutError`** に分類 → 「応答がタイムアウトしました。**サーバーが混雑しているか、リクエストが複雑すぎる**可能性があります」 | 🎭 落ちているサーバーを「混雑」と言い、待てば直ると誤誘導する |

## 設計の決着 (2026-08-25、まはー裁定)

洗い出しを材料に同日議論して、ここまで決まった。以下は裁定であって見立てではない。

### 1. 残るべき終わり方は 7 通り

数える軸は「エラーの種類」ではなく **ユーザーの次の一手が変わる境目**。

| # | 終わり方 | 発言は残るか | 今あるか |
|---|---|---|---|
| 1 | 応答が返って終わった | 残る | ✅ |
| 2 | 応答が**途中で**終わった | 残る | ⚠️ 起きるが印が無い (完結した短い返事と区別できない) |
| 3 | 発言は届いたが、**応答は生まれなかった** | 残る | 🕳️ **無い — 無言 5 箇所の落ち先はすべてここ** |
| 4 | 発言が**届かなかった** | 残らない | ✅ `persistence_failed` が見本 |
| 5 | ユーザーが止めた | 残る (応答は途中まで) | ✅ `cancelled` |
| 6 | 同じ発言を**既に受け取っていた** | 既に残っている | ✅ `duplicate_command` |
| 7 | **顛末が確定していない** | 分からない | 🕳️ **無い。しかも「送れなかった」と嘘をついている** |

7 は原理的に消せない (ブラウザとサーバーが切れた瞬間、クライアントに確定情報が無い)。
消せないので、**「分かりません」と正直に言う出口を持つ**ことをまはーが裁定した。

### 2. 出口の後ろに「片付け」の一段が付く

「発言しなかったことにしたい」需要は実在する (まはー提起)。ただし **消せるかどうかは好みでは決まらず、
ペルソナが読んだかどうかで決まる**。

| 窓 | 状態 | 片付け |
|---|---|---|
| ① 保存前 | どこにも無い | 自由 |
| ② 保存済み・**まだ誰も読んでいない** | 建物履歴にあるが記憶には無い | **差し戻しを既定にする** (ユーザーは選べる) |
| ③ **読まれた後** | SAIMemory に転記済み | **残すに固定**。「もう聞かれてしまったので取り消せません」と正直に言う |

- ②③ の境目は新設ではなく既存 — `auto_ingest` の `pulse_cursors`
  (`builtin_data/tools/get_building_messages.py:334-372`) が「どこまで読んだか」を持っている。
  **部屋に複数ペルソナがいる場合は全員未読のときだけ ② 扱い**にする (食い違いを作らない側へ倒す)。
- ユーザーの発言は**ユーザーの著作物**なので、「削除」ではなく **入力欄への差し戻し** (手元に返す)。
- ③ で記憶側まで消す案は**採らない** — エラーの後片付けが記憶を書き換える口になるのは危うい。
  記憶の訂正はメモリタブ側の、意図してやる操作に留める。

**ペルソナ側の断片の扱い**:

- 空の placeholder (`content: ""`、`runtime_emitters.py:243-253`) は**常に掃除する**。誰の発言でもない。
- partial の保存は**現状どおり**、そしてその非対称は正しいので明文化する —
  **ユーザーが止めた partial は残す** (「そこで止めた」という事実があり、そこまでは本当に言った) /
  **事故で切れた partial は残さない** (誰の意思でもない残骸)。中断の主語が誰かで決まる。
- 現状の食い違いは直す: いまは画面に partial が残り、世界には空行が残り、リロードで画面の分だけ消える。

### 3. ユーザーの操作は 2 つだけ — `retryable` は要らなくなる

まはーの指摘: **③ が「取り消せない」と言う以上、追加のプロンプト無しで応答をやり直せる機能とセットでないと、
ユーザーはもう一度喋らないと応答を得られない。** そしてやり直しがあれば、**「再送するかどうか」の択自体が消える** —
「続けて喋るか、やり直してください」と言えば済む。

| 出口 | 操作 |
|---|---|
| 1・6 (応答がある) | なし |
| 2・3・5 (発言は残り、応答が足りない) | **やり直し** |
| 4 (発言が残らない) | **送信** (入力欄に戻っている) |
| 7 (不明) | 履歴を見て、どちらか |

よって当初案の「全出口に `retryable` を必須欄で載せる」は**取り下げ**。
発言が残っているかどうかが操作を決めるので、真偽値を別に運ぶ必要がない。

> なお `retryable` はサーバーが既に 4 箇所で送っていて (`manager/runtime.py:566,639,651` /
> `api/routes/chat.py:1122`)、フロントエンドは一度も読んでいない (全文検索で 0 件)。
> 汎用の catch-all (`runtime.py:727-732`) には付いてすらいない。この欄は掃除の対象になる。

### 4. 「やり直し」と「作り直し」は別物

必要な土台が違うので、混ぜない。

- **やり直し** = 応答が無い状態から応答を作る。**枝は増えない** (元の応答が存在しない)
- **作り直し** = 気に入らない応答を別案に置き換える。**枝が増える** (どちらが本流かの記録が要る)

[`memory_continuity_graph.md`](memory_continuity_graph.md) の「副産物 — 会話の分岐・再生成」が設計しているのは
**作り直し**の方 (新しい thread を開いて分岐位置以前と繋ぐ)。**やり直しは枝を増やさないので、
連続性グラフの決着を待たずに成立する** — これが門の線引きを動かせる根拠。

### 5. 門の線引きを変更 — やり直しを v0.3 の内側へ (まはー裁定)

[`v030_release_gate.md`](../overview/v030_release_gate.md) §2-14 は「刻印は v0.3、消費は後続」と引いており、
再生成は消費側だった。**やり直しだけを門の内側へ引き上げ、作り直し (分岐) は後続のまま**とする。
③ の出口とやり直しは一つの工事。→ 門 §2-17 として登載。

**土台は既にある**: 会話開始経路の `run_sea_user(persona, building_id, "")`
(`saiverse/user_conversation.py:753-758`) が、まさに「発言はもう履歴にある前提で応答だけを起こす」形。
新機構ではなく、この経路にユーザーが触れる口を付ける工事になる。
製品内の `regenerate` は現状 Chronicle 専用 (`api/routes/people/arasuji.py:717`) で、会話用は無い。

### 実装の前に確かめること (未確認)

「成立するはず」の根拠は経路が在ることまでで、動かして確かめていない。

- 窓③ (既読) でやり直したとき、ペルソナが直前のユーザー発言を文脈に持つか。
  取り込みの目盛りは進んでいるので二度は読まない。SAIMemory には入っているはずだが、head の組み方次第
- やり直しの連打で応答が二重に生まれないか
- 事故で残った空の placeholder 行が、やり直しの前に掃除されるか

## 起票時の見立て (裁定前の記録)

四つの型に畳める。並べ替えると、直す順番の候補にもなる。

1. **内側の握り潰しが外側の網を無効化する** (段 4)。網は既にあるので、握るのをやめるだけで届く。
2. **契約の違う形を流している** (段 2 の生 HTML、段 5 の素の `ValueError`)。器 (`NDJSON イベント` / `LLMError`) は既にあるので、載せ替えるだけ。
3. **何も起きないことが正常終了と区別できない** (段 3 の応答者ゼロ、段 7 の空ストリーム)。
   これだけは新しい概念が要る — 「発言は受理したが応答は生まれなかった」を表す出口。
4. **文言が事実と違う** (段 6 の接続拒否＝タイムアウト表示)。分類を分けるか、文言を両にらみにするか。

1 と 2 は既存の器に載せる工事で、3 は設計の話、4 は文言と分類の話。
