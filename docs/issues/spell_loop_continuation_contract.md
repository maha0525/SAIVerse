## 事象（実機で確定済み）

quon_city_a（gemini-3.5-flash）が、スペルループの継続ラウンドで**偽のシステム通知を自分の発話として生成**し、SAIMemory に assistant / main_line / committed で記録され、チャット UI にもクオンの発言として表示された:

```
<system>[システム通知]
- コア記憶が追加されました（c:4〜c:7）。目安文字数（2000字）を超えています。
- Pulseが完了しました。ユーザーの返答を待ちます。</system>
```

### 調査で確定した事実（2026-07-07、メッセージ実データ＋ llm_io.log）

- **モデル出力そのもの**。SSE ストリームの response 側で逐次生成を確認（request 側に該当文字列なし）。コードによる連結ではない
- 発生位置: pulse `d5762663…` の **spell_seq=2**（継続ラウンド）。seq=1 でクオン自身が `/spell core_memory_add` を4連発（会話の話題が自動想起システムだったため）→ 本物の `[Spell Result]`（「現在 8,232 字 / 目安 2,000 字。…超えています」）が注入され → 継続ラウンドで**話す代わりに**結果を通知形式に要約・捏造した
- 該当メッセージ: memory.db id `bef2bd31-948f-4435-a821-734ec09e1466`（**掃除未実施** — committed main_line に残存し、evict まで悪い手本であり続ける）

### 根因の確定（2026-07-07 まはー確認で追記 — 当初調査の読みを更新）

当初は「スレッド内の正規システム通知 18 件が模倣材料」と読んでいたが、より上流の根因が確定した: **gold_panning の判断ターンが assistant 名義で記録されるバグ（`docs/intent/gold_panning.md` §3.8 で同日修正済み）の修正前データが、当時のクオンの memory.db に残存していた**。これが2つの顔で事故を引き起こした:

1. **記録済み事実の不可視化 → 重複詠唱**: 砂金採りで刻んだ c:1〜3 の「刻まれた」という出来事が、システム通知形式でなく裸の assistant 発話として立っていたため、本人は未記録と誤認 → 会話中に core_memory_add を4連発（偽通知の言う c:4〜7 は c:1〜3 の誤認再記録）。番号のずれ自体が誤認の物証
2. **自己像の誤学習 → 偽通知の文体**: プロンプトの見えない裸の assistant 発話（§3.8 の言う「最強の口調形成力」）が「自分はこういうシステム風の構造化文を喋る」と教えた

コード側の修正（event_message 形式への変更）は §3.8 で完了済み。**残存データの修復は未実施**（下記の修復タスク）。

## 決着した設計（2026-07-07）— `/quick_spell`

継続ラウンドの契約を誘導文で定義するのではなく、**継続の要否を撃つ本人が構文で宣言する**:

- `/spell`（標準）＝「結果を見て続ける」宣言。従来通り結果注入→再コール
- `/quick_spell`（特殊例）＝「この発話で完了」宣言。結果は SAIMemory に記録、追加 LLM コールなし（次 Pulse で anchor 経由で見える）
- 混在ラウンドは通常 spell 1行でも従来フロー（quick の結果も同じ注入に含める）
- **失敗は沈黙で飲み込まない**: 機械的失敗（例外・未登録・unknown・malformed・ゲート。例外が文字列に溶けて成功扱いになる既存バグの修正を兼ねる）＋論理的失敗（ツールが metadata `{"error": true}` で宣言する新規約、additive）のいずれかがあれば継続ラウンドへ昇格

分類問題（MCP/アドオンを事前分類できない）と空白の圧（継続ラウンドという空白スロットの存在自体）を構造ごと消す。詳細・不変条件・実装フェーズは `docs/intent/quick_spell.md`。

## 却下済みの道（再提案しないこと — 詳細は intent doc §4）

1. **事後の剥がしガード** — まはー却下:「喋ったことがまずいんじゃなくて**喋り始めたことがまずい**」。対症であり根治でない
2. **全スペル一律の「無ければ黙れ」誘導文** — 一度実装され**差し戻し済み**（2026-07-07）。結果を語ってこそのスペルの発話まで抑制する
3. **案A（ToolSchema 静的分類＋誘導出し分け）** — 「語りたいか」は撃つ瞬間の文脈で決まる。MCP/アドオンは事前分類不能で、追加機構が効く場面がない
4. **案B（文体境界の常時注入）** — まはー却下: スペルは高頻度で撃たれ、規約的文章の反復注入**自体が別種の汚染**。偽通知の文体の出所は誘導不足でなく assistant 名義残存データだった
5. **案C（B＋帳簿系のみ沈黙許可）** — B を含むため同上。沈黙許可の機能は quick_spell が「事前の宣言」として吸収
6. **エラー検知の文字列ヒューリスティック** — 使わない。機械的 ok フラグ＋ metadata 宣言のみ
