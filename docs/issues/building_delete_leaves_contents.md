# Issue: 建物を消しても中のアイテム・設置物が残り、同じ ID で作った別の部屋に戻ってくる

**ステータス**: 🟠 実装中 (1〜5 はすべて実装済みで、隔離環境での検収と全体のテストまで済み。ローカルレビューと Codex の敵対レビューの最中)
**優先度**: high (ふつうの画面操作だけで、消した部屋の中身と会話が無関係な新しい部屋に混ざる)
**作成日**: 2026-09-29
**関連**: `manager/admin.py::delete_building` / `manager/ids.py::build_identifier` / [`feed_fixture_no_delete_or_edit.md`](feed_fixture_no_delete_or_edit.md) (設置物の削除。この issue の発見元) / [`docs/audits/2026-09-12_normal_behavior_consolidation/normal_behavior.md`](../audits/2026-09-12_normal_behavior_consolidation/normal_behavior.md) の FLOW-15 と「不可逆な操作に共通する規範」

## 症状

ワールドエディタで建物を消すと、建物の行と入退室の記録だけが消える。中に置いてあったアイテムと設置物 (フィードスタンドなど) は、消えた建物を指したまま DB に残る。

残ったものは、ふだんは誰の目にも触れない。ところが**後から作った建物に同じ ID が付くと、残っていたものが全部その新しい建物の中身として戻ってくる**。日本語名の建物は `building_1_city_a` のような「空いている最小の番号」で ID が決まるので、名前も目的も無関係な部屋に同じ ID が付く。英語名の建物も、同じ名前で作り直せば同じ ID になる。

隔離した一時 DB で確かめた再現 (2026-09-29):

1. 「鉄腕の道具店」を作る (ID は `building_1_city_a`)。中にアイテム「古い地図」、フィードスタンド「ニューススタンド」(購読 1 本・記事 1 件)、会話 1 件を置く。
2. 道具店を消す。「削除しました」と返る。
3. 「霧雨の宿亭」を作る。ID は同じ `building_1_city_a` になる。
4. 宿亭の中身を見ると、古い地図・ニューススタンド・その記事・道具店での会話が、全部そのまま宿亭のものとして出てくる。

戻ってきたフィードスタンドは、取得の対象にも戻る (取得の対象を決める `city_feed_fixture_ids` は「今ある建物に属する設置物」を拾うので、建物の行が復活した時点で条件を満たす)。

## 確認した事実 (2026-09-29、develop `0169d02f` 時点)

### 建物の削除が消すもの

`manager/admin.py::delete_building` が消すのは `BuildingOccupancyLog` の行 (その建物の入退室の記録) と `Building` の行の二つだけ。外部キーは宣言されているが、この DB は `PRAGMA foreign_keys` を有効にしていないので、DB が道連れにしたり削除を拒んだりすることもない。確認ダイアログの文言は「この Building を削除しますか？」だけで、何が一緒に消える・残るかを言わない。

### アイテム

- 置き場所の行 (`item_location`、`OWNER_KIND='building'`, `OWNER_ID=<消した建物>`) が残る。アイテム本体 (`item`) も残る。
- 起動時・更新時の読み込み (`manager/items.py::load_items_from_db`) は、この行を `items_by_building[<消した建物>]` に積む。その ID の建物が無いので、どの部屋の様子にも載らず、ペルソナからは見えない。
- ワールドエディタのアイテム一覧は `item` 表をそのまま並べるので、そこには出続ける。ただし開くと持ち主が「消えた建物」のままで、名前などを直して保存すると `update_item` が「Building not found」で弾く。持ち主を別の場所に変えれば保存できる。
- 中身の入ったバッグが建物にあった場合、バッグの中身 (`OWNER_KIND='bag'`) はバッグに付いたまま残る。

### 設置物

- `fixture` の行と、そこにぶら下がる `observer_config` / `observer_metrics` / `feed_subscription` / `feed_item` / `feed_read_cursor` / `feed_fixture_config` が全部残る。
- フィードスタンドは、フィードの取得・配送・古い記事の剪定がすべて `city_feed_fixture_ids` (建物と結合して自分の街のものだけを拾う) で絞られているので、建物が消えている間は止まる。裏返すと、記事も剪定されずに残り続ける。
- `GET /api/observer/fixture/{id}` は街や建物で絞らないので、残った設置物を返す。
- **観測する設置物は止まらない。** 起動時の `ObserverManager.start_pull_observers` は、有効な pull 型の観測設定を建物の有無を見ずに全部予約する。予約されたものは定期的に道具を実行して `observer_metrics` に値を書き続け、通知の条件に当たれば消えた建物の ID で建物の記録 (`building_messages`) へ知らせを書く。ただし観測設定を作る口は API (`POST /api/observer/config`) だけで画面には無いので、今のふつうの使い方では起きない。

### 同じ ID が付く経路

`create_building` の重複検査 (`manager/admin.py`、`build_identifier` の `exists`) は `building` 表だけを見る。消した建物の ID は、残骸がどれだけ残っていても「空いている」と判定される。

### 同じ理由で残る、ほかのもの

建物の ID を持つ表を全部洗った。上の二つ以外に、次が残る。

| 残るもの | 中身 | 今わかっている影響 |
|---|---|---|
| `building_messages` | その部屋で交わされた会話と出来事 | 残すのは既存の裁定どおり (下の「前提になる裁定」)。ただし ID が使い回されると、新しい部屋の過去として出てくる (再現で確認済み) |
| `realtime_spell_binding` (`OWNER_KIND='building'`) | 建物に結びつけたリアルタイムスペル | その建物に居るときだけ読まれるので、建物が消えている間は効かない。ID が使い回されると新しい部屋で効きはじめるはず (未再現) |
| `persona_building_state` / `persona_pulse_cursor` | ペルソナごとの「その部屋の状態の控え」と「その部屋の記録をどこまで読んだか」 | ID が使い回されたとき、新しい部屋を古い部屋の控えと比べて変化の知らせを出す可能性がある (未確認) |
| `playbook.building_id` / `building_tool_link` | 建物専用の Playbook / 使われていない古い表 | 未確認 |
| `~/.saiverse/cities/<city>/buildings/<id>/` | 建物のフォルダ | 未確認 |

## 前提になる裁定

- **FLOW-15 (2026-09-12 の正常挙動の統合)**: 部屋を消しても、そこで交わされた会話の記録は残す。残ることを消す前に伝え、消すかどうかは訊かない。会話は誰かの記憶へ写っている可能性があり、2026-08-25 の裁定が記録の取り下げを禁じているため。
- **不可逆な操作に共通する規範 (2026-09-13 まはー)**: 「ユーザー操作の結果はその影響範囲をユーザーの期待と合わせる。不可逆な操作であるほどこの規範は厳しく守られるべきで、削除はその筆頭」。期待がはっきりしないなら、どちらかへ倒さずに訊く。利用者が用意したものは「これも削除しますか？」と訊き、誰かの記憶へ写った共有の記録は残ることを伝えるだけにする。
- **設置物の削除 (2026-09-29 まはー、feature/fixture-delete-edit)**: 設置物を消すときは、ぶら下がっている記録を同じ transaction で片付ける。

## 裁定 (2026-09-29 まはー)

- **アイテム**: 下の 2 の D (確認ダイアログで「残す / 一緒に消す」を利用者に選ばせる、既定は「残す」) で確定。まはー「そう、ユーザーが選ぶのが一番いい！」
- **ID の使い回し**: 「残骸のある ID を飛ばす」案は採らない。番号が歯抜けになるのを嫌う利用者がいるため。代わりに、残す会話を特殊な ID へ書き換えて、その後の世界の運行に影響しない形にする (まはーの原案は `del.building_2.2026_09_29_18_28_00` のような ID)。具体形は下の 3。
- **ペルソナの記憶の中の機械用の印 (2026-09-29 まはー「OK、書き換えてほしい！」)**: 残す会話を特殊な ID へ移すとき、ペルソナの記憶のファイルの中の機械が読む印 (写した会話の出どころの目印・部屋の様子の控え・知覚をまとめる鍵) も同じ ID へ書き換える。9/11 の付け替えと同じく、書き換える前にペルソナごとに複製を取り、記憶の本文・知覚の文面・添付は変えない。
- **昔の残骸の付け替え (2026-09-29 まはー「消えてる部屋についてならやってもらって大丈夫。他ユーザーさんについても起動時にやって問題ないと思うよ」)**: 建物がもう無いのに元の ID のまま残っている会話などを、起動時に特殊な ID へ付け替える (5)。まはーの環境では、消えた部屋 5 つ (私室の形の ID 3 つを含む、会話計 41 件) が最初の起動で対象になることを、本番を読み取り専用で数えて伝えたうえでの裁定。ほかの利用者の環境でも同じく起動時に行う。
- **順序**: 実装は feature/fixture-delete-edit (設置物の削除) の合流後に始める。同じ場所を触るので、先に develop から切って作業するとコンフリクトする。

## 直す方向

### 1. 設置物 — 建物と一緒に消す (提案)

設置物は必ずどこかの建物に付いている物で (`fixture.BUILDING_ID` は NOT NULL)、アイテムのような「どこにも置かれていない」状態を持たない。建物が消えたら居場所が無いので、ぶら下がる記録ごと消す。確認ダイアログでは「設置物 N 個 (フィードスタンドなど) も一緒に消えます」と伝える。

実装上の注意:

- feature/fixture-delete-edit の `ObserverManager.delete_fixture` は「自分の街の建物に属する設置物」だけを消す (`city_fixture_ids` が建物と結合する)。建物の行を先に消すと対象が見つからなくなるので、**設置物を先に消し、建物の行は最後に消す**。
- 建物の削除と設置物の削除を一つの transaction にしたい。今の `delete_fixture` は自分でセッションを開いて commit するので、行を消す部分をセッションを受け取る関数に切り出し、`delete_fixture` と `delete_building` の両方から呼ぶ形にする。
- pull 型の観測の予約 (`observer:<id>`) は commit の後に取り消す (`delete_fixture` と同じ)。

### 2. アイテム — D で裁定済み

アイテムは利用者が置いた物、利用者が渡した添付、ペルソナが描いた絵や書いた文書で、2026-09-13 の規範の「利用者が用意したもの」に当たる。建物を消す人が中の物も捨てたいのか、物は取っておきたいのかは、建物を消す操作からは決まらない。

選択肢:

- **(推し) D: 確認ダイアログで訊く。** 「中にアイテムが N 個あります」と出し、「どこにも置かれていない状態で残す (ワールドエディタから置き直せる)」と「建物と一緒に消す」を選ばせる。既定は「残す」。規範どおりで、どちらを選んでも利用者の期待と結果がずれない。
- A: 黙って「どこにも置かれていない状態」(`item_location` の行を消した状態。ワールドエディタでは持ち主が world と表示される) に移す。物は失われないが、ワールドエディタの一覧は持ち主を表示しないので、どれが移されたのか利用者から見つけにくい。
- B: 黙って建物と一緒に消す。バッグの中身も入れ子ごと消す必要がある。今の `delete_item` はアイテムの元のファイル (絵や文書) を消さないので、それとも揃える必要がある。取り返しがつかない。
- C: 中にアイテムがある建物は消せないようにする (人が居る部屋と同じ扱い)。安全だが、アイテムを一つずつ動かしてからでないと消せない。2026-09-12 の統合では「拒否条件を部屋とアイテムで揃える話にはしない」と整理されている。

D の「残す」を選んだとき、バッグは中身ごとそのまま残る (バッグの中身はバッグに付いているので、何もしなくてよい)。「消す」を選んだときは、バッグの中身も入れ子の底まで消す。

### 3. ID の使い回し — 残すものを特殊な ID へ付け替える (実装済み)

1 と 2 を直しても、会話の記録 (`building_messages`) は FLOW-15 の裁定どおり残る。付け替えを入れる前は、ID が使い回されると、消した部屋の会話だけが新しい部屋の過去として出てきた。

建物を消すとき、その建物を指して残るものを、二度と使われない特殊な ID `deleted_<元の ID>_<YYYYMMDDHHMMSS>` (ローカル時刻。埋まっていれば `_2`、`_3` …) へ付け替える (`saiverse/building_retirement.py`)。元の ID は完全に空くので、次に作る建物が同じ ID を使っても何も戻ってこず、番号の歯抜けも出ない。

- **付け替えるもの**: 2026-09-11 の部屋 ID の付け替え (`saiverse/building_id_repair.py`、[経緯の issue](building_id_contains_path_separator.md)) の部品をそのまま使う。部屋を指す DB の欄の全部 (会話・ペルソナごとの控えと読んだ位置・部屋専用の Playbook・エピソード・利用記録・私室・Region の入口など)、JSON にまとめた欄 (予定表・通知の控えなど。値の完全一致だけ)、会話のメッセージ ID とアドオンのメタデータ、ペルソナの記憶のファイルの中の機械が読む印 (ペルソナごとに `~/.saiverse/backups/building_retirement/<日時>/` へ複製を取ってから)、部屋のフォルダ (消した建物の City の置き場 `cities/<その City>/buildings/<ID>` と、City の置き場ができる前の `<ホーム>/buildings/<ID>` だけ。別の City の置き場にある同じ名前のフォルダは、その City の持ち物なので動かさない)。記憶の本文・知覚の文面・添付とユーザーが書いた文章は変えない。
- **順番**: `AdminService.delete_building` の中で、(1) 特殊な ID を決めて記録 `cities/<city>/building_id_renames.json` に「予定」(`"kind": "retire"`) を書き、(2) 中身の片付け・建物の行の削除と同じ transaction で DB の参照を書き換えて commit し、(3) 全ペルソナの記憶の印を書き換え、(4) フォルダを移し、(5) 記録を「完了」にする。記録を書けなければ削除ごと止める。削除が巻き戻ったら記録の予定を閉じる。
- **記憶のファイルを SAIVerse が動いている最中に書き換える**: 記憶のファイルは WAL で開かれ、同じプロセスの書き手は `sai_memory.db_locks.lock_for_path` の錠前 (adapter の `_db_lock`) の中で読み書きする (提示の縮みの記帳 `mark_presentation_reductions` も、読んでから書き戻すまでをこの錠前の中で行う)。付け替えは同じ錠前を取ってから読み直し、`BEGIN IMMEDIATE` の中で 1 行ずつ「読んだときの値と同じなら」だけ書き、合わなければそのファイルの書き換えをまるごと巻き戻す。別のプロセスの書き込みとは SQLite の書き込みの鍵と待ち時間 (5 秒) で順番を付ける。同じ DB を別の SAIVerse が使っている間は、(3)(4) を削除の場では行わず、次の起動へ回す。
- **(3)(4) が済まなかったとき**: 削除は済んでいる (DB は commit 済み) ので、利用者には「削除しました」を返す。記録は「予定」のまま残り、その間は建物を作る口のどれも元の ID を使わない (`BuildingIdAvailability`。建物の作成・ペルソナの私室・設計図から作る私室・Region の自動の入口が同じ規則を使う) — 利用者が選んだ ID (手で付けた ID・名前から作った ID・Region ID から決まる入口の ID) は理由つきで断り、機械が選ぶ候補 (連番・私室の ID) は次の候補へ進む。次の起動 (`_retire_deleted_building_ids`) が続きを終えると、元の ID は空く。続きを始める前に元の ID の建物ができていたら (DB を直接触るなど、作る口の外から作られた場合)、新しい建物のものを動かさないよう、続きを止めて警告を出し、記録を「完了」ではなく `abandoned` (付け替えを終えずに止めた) で閉じる。削除が巻き戻ったときの記録は `cancelled` で閉じる。閉じた記録は元の ID を押さえず、続きも行わない。
- **記憶のファイルの場所を決められないペルソナ**: ID が `a//b` のように記憶のファイルの場所を安全に決められないペルソナは、どの起動でも書き換えられないので待たない。警告を出し、そのペルソナの記憶は書き換えずに (3) を済んだものとして数える — 待つと記録が永遠に「予定」のまま残り、元の ID がずっと使えなくなる。記憶のファイルが開けない・複製が取れない・書き換えが途中で止まったときは、次の起動で直りうるので「予定」のまま待つ。9/11 の付け替えは今までどおり待つ。
- **`deleted_` で始まる ID**: 建物を作る口のどれも、この形の ID を新しい建物に付けない (大文字小文字を問わない)。手で付けた ID は断り、名前から作った ID がその形になるとき (名前が「Deleted ...」など) は連番の形 `building_<n>_<city>` にし、私室は次の候補へ進む。
- **古い会話のファイルとの照合の検査はしない**: 9/11 の付け替えは、付け替えの前後で照合の欠けが増える部屋を見送る。古い `log.json` の取り込みは今ある建物にしか走らず、特殊な ID は建物にならないので、特殊な ID の下で照合が使われることは無い。
- **確認の欄**: 変えない。「会話の記録は残る」の文面のまま (残る先が特殊な ID になっただけ)。

### 4. 確認ダイアログ

FLOW-15 が求めている「消す前に何が残るかを伝える」をここで一緒に満たす。出す内容は、会話が残ること (訊かない)、設置物 N 個が一緒に消えること、アイテム N 個の扱い (2 の判断次第)。

### 5. 既にある残骸

利用者の DB には、今までに消した建物の残骸がもう残っている可能性がある。そのままだと、3 を入れる前に作った建物や、3 の検査が会話の記録しか見ない場合に、また戻ってくる。起動時の移行で一度だけ片付ける案:

- 建物が無い設置物は、ぶら下がる記録ごと消す。
- 建物が無いアイテムは、消す前に訊くことができないので、「どこにも置かれていない状態」へ移す (取り返しのつく方に倒す)。
- 建物が無いのに残っている会話などは、3 と同じ付け替えで特殊な ID へ移す (実装済み。建物の行が無いのに `building_messages`・`persona_pulse_cursor`・`persona_building_state`・`playbooks`・`building_tool_link` に残っている ID を見つけ、部屋を指す欄の全部・記憶の印・フォルダを付け替える。利用者の現在地・私室・Region の入口・エピソード・利用記録は、それだけでは見つける根拠にしない。大文字小文字だけ違う建物がある ID は、フォルダを取り違えないよう触らない。フォルダは起動した City の置き場と古い置き場から移し、使った City を記録に書く (どの City の建物だったかは DB に残っていない)。書き換える前に DB の控えを取る。同じ DB を別の SAIVerse が使っている間は見送る)。
- 上の二つ (設置物・アイテム) とリアルタイムスペルの片付けも、「建物が無い」を大文字小文字を畳んで判定する (`shop_a1` を指す行は、建物 `Shop_A1` があれば片付けない)。

### 範囲外で気づいたこと

`delete_building` は、消す建物が誰かの私室 (`AI.PRIVATE_ROOM_ID`) か、利用者が指定した Region の入口 (`Region.ENTRANCE_BUILDING_ID`) かを確かめない (確かめる処理が無いことはコードで確認した。消したときに何が起きるかは未確認)。この issue とは別の欠陥として扱う。3 を入れた後は、消した私室・入口を指すこれらの欄は特殊な ID を指すようになる (同じ ID の新しい部屋を私室・入口と取り違えることは無くなったが、指す先が無いことは変わらない)。

建物を作る口は四つ (`create_building`・ペルソナの私室 `manager/persona.py`・設計図から作る私室 `manager/blueprints.py`・Region の自動の入口 `create_region`) あり、どれも `saiverse/building_retirement.py::BuildingIdAvailability` の同じ規則で ID を確かめる。この規則の外で建物の行が作られた場合 (DB を直接触るなど) は、次の起動の続きが止まり、警告が出て、記録は `abandoned` で閉じる (記憶の印は元の ID のまま残り、新しい部屋を指す)。
