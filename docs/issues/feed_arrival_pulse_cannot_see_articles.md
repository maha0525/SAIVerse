# 出かけるコマでフィード施設に着いても、その Pulse で記事に出会えない

**ステータス: 実装済み・実機検証待ち** (2026-08-08 起票、同日設計裁定→実装 48edbf1 →レビュー指摘の消し込み完了。時間割実機検証中のまはーの疑問「そのBuilding内から始まるPulseじゃないとフィードの中身見えないんじゃ」が的中)

## 症状 (二段)

**① 配送タイミングの構造**: 記事の知覚配送 (`FeedManager.deliver_new_items`) は定期取得サイクル (`_fetch_cycle_worker`、既定 30 分) からしか呼ばれず、**入室トリガーの配送が存在しない**。配送対象は配送時点でその Building にいるペルソナのみ。

- 9:00 に出かけるコマでニューススタンドの Building に到着 → 記事が届くのは早くて次のサイクル
- 出かけるコマの軽い一手 Pulse は到着直後の一回きり → **その Pulse の知覚に記事は無い**
- 滞在がサイクルを跨げば知覚バッファには積まれるが、読まれるのは次の認知機会 (帰宅後のコマ・会話など) — 「スタンドの前で読む」でなく「帰ってから届く」体験になる

**② 設置物欄の見出し表示が未実装疑い**: `feed_manager.update_fixture_display` は Fixture.STATE_JSON の `feed_stand` キーに表示情報 (購読タイトル一覧 + 直近見出し 5 件 + 更新時刻) を書いているが、描画側 `builtin_data/tools/get_visual_context.py` の設置物 (Fixture) 節は STATE_JSON の値を `value_num` / `value_text` 形式 (ObserverManager の観測値形式) でしか拾わない。`feed_stand` の辞書はどちらも持たないため **val=None でスキップされ、何も表示されない**。到着したペルソナに見えるのはスタンドの NAME と DESCRIPTION だけ。

書き手 (feed_manager) は 2026-08-02 夜間分業のエージェント A、読み手 (get_visual_context) は既存コード — 継ぎ目の突き合わせ漏れ。夜間ハンドオフ §2-5 は「visual context に購読タイトル・最新見出しが出ること」を検証項目に挙げており、**実装済みの前提が誤っていた**。

## 直す方向 → 裁定済み (2026-08-08 設計議論、まはー裁定)

**根本原因はフィード側でなくプラットフォーム側**と結論した。議論の経路: 入室配送だけでは「知覚は次の Pulse でしか読まれない」ためスペル移動 (会話中の移動 = いなくなって呼びに行くまで戻らない) に負ける → 「Pulse 中なら手渡し」分岐はその場しのぎで却下 → 「読む行為をスペル化」は無駄なスペルターン 1 回の追加で却下 → **「ラウンド中に世界から本人へ情報が届く正規の通路が、スペル結果テキストしか無い」ことが根本欠陥**。

解 = **知覚バッファの消費点を「Pulse の頭」から「Beat の頭」へ精密化する** (まはー裁定: 「二種類にするのでなく Beat の頭に置き換えるだけ、と考える」)。Beat の頭には既に実行台帳の関所があり、知覚消費が同席する。スペルが世界を変えた帰結は次の Beat の頭で同じラウンドに流れ込む。正典改訂は [perception_buffer.md](../intent/perception_buffer.md) §4.2 / [beat_execution_context.md](../intent/beat_execution_context.md) §2.2 に記録済み。

その上でフィード側の修正は特別扱いゼロの二点に縮む:

1. **入室配送**: `on_building_entered` (dynamic_state) の「移動先の様子」push に相乗りして、フィード施設があれば未読 N 件をカーソル方式で知覚バッファへ。全移動経路 (コマ移動・スペル移動) をこの一点でカバー。既読カーソルが台帳なので定期サイクル配送と重複しない。
2. **設置物欄の描画対応** (②): `feed_stand` キーを get_visual_context が描画できるようにする。

実装順: Beat 頭消費 (プラットフォーム) → フィード二点 → 実機検証再開。

## 実機検証への影響

**起票時 (2026-08-08 午前)**: 統合検証手順 Step 3 の「フィード配送」項目は、当時のままだと**サイクル任せの時間差配送が仕様どおりの挙動** — 出かけるコマの Pulse に記事が無くてもバグではない。visual context の見出し確認は②が直るまで検証不能。

**実装後 (2026-08-08、上の二点 + Beat 頭消費が入った状態)**: どちらの縛りも外れた。到着した Pulse で未読記事が知覚に入り、設置物欄にも購読タイトルと直近見出しが出る — Step 3 のフィード項目は「**到着時に読めるか**」で検証してよい。作業セッション系のコマも、セッションの頭で知覚を消費する (レビュー消し込みで追加)。

## 実機検証の記録 (2026-08-08 夕、ソフィーの出かけるコマ)

**本命経路は端から端まで動作を確認した。** 16:59:58 に出かけるコマ発火 → news_avenue へ移動 → 入室配送 (47NEWS/日経ビジネス/CNN 各 3 件、カーソル前進) → 到着 Pulse の LLM 入力に設置物欄の見出し 5 件と `[フィード]` 記事 (見出し+本文冒頭+リンク) が同居 → 発話が実在記事 (CNN「ローマの暑さ対策広場」) に言及。①②とも実機で解消。

同夜の深掘りで判明した構造事実 (詳細と裁定論点は [slot_light_pulse_runs_on_conversation_vehicle.md](slot_light_pulse_runs_on_conversation_vehicle.md) へ):

1. 出かけるコマ開始の Pulse は既定で会話 Track の Playbook を器に走り、独白でなく**発話** (Building 履歴 + チャット UI + TTS) になった
2. ソフィーが 1 巡目で `track_activate` を唱え、user_conversation 型の特殊ハンドラが会話 Pulse 起動 + 会話エピソード開き直しを実行 (2 通目の発話の正体)
3. 完走済みの出かけプロンプトが「中断された」として再配達され、コマ開始の Pulse が**二重実行**された (3 通目)

記事への言及 (ローマの文) は当初「中断で捨てられた」と誤認したが、**Building 履歴 2 番のスペル畳み込みメッセージの末尾に発言として残っている** (訂正 2026-08-08 夜)。`building_move` 未知スペルの空引数試行はエラー文・リカバリとも正常。
