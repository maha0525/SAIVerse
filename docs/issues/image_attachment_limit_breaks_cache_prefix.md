# Issue: 画像の枚数上限が、新しい画像が来るたびにキャッシュの前方一致を割る

**ステータス**: 🔲 未着手（未解決 — `docs/issues/` 直下にある）
**優先度**: low（音声会話など画像が増えにくい場面では、その回だけ待つ形で済む）
**作成日**: 2026-10-11
**関連**: `llm_clients/utils.py`（`DEFAULT_ATTACHMENT_LIMIT` / `parse_attachment_limit`）、`llm_clients/gemini.py`（`_convert_messages`）、`docs/intent/cache_lifecycle_control.md` §3.5（継続キャッシュ）

## 何が起きているか

LLM に送るとき、画像は新しい順に `DEFAULT_ATTACHMENT_LIMIT` 枚（既定 4。`SAIVERSE_{PROVIDER}_ATTACHMENT_LIMIT` / `SAIVERSE_ATTACHMENT_LIMIT` で変えられる）だけをそのまま送り、それより古い画像は要約の文字（`[画像参照のみ: …] 要約`）に置き換えている。

このため、新しい画像が会話に 1 枚入るたびに、それまで画像として送っていた一番古い 1 枚が文字に変わる。その画像を含むメッセージは会話の前のほうにあるので、そこから後ろが前回送った並びと一致しなくなり、キャッシュ（Anthropic のプロンプトキャッシュ、Gemini の explicit cache と暗黙のキャッシュ）が外れる。

継続キャッシュ（§3.5）では、この回は「一致するキャッシュが無い」例外に落ちて、キャッシュの作成を待つ。

2026-10-14 追記: モデル設定 `cache.persist_realtime_and_recall` を ON にしたモデル（Gemini 4 Argon）では、上限を使わないことにした（送る列の画像をすべて画像のまま送る — `docs/intent/persist_realtime_and_recall.md` §4.2、`llm_clients/utils.ATTACHMENT_LIMIT_OFF_KEY`）。OFF のモデルはこの issue のまま。

## まはーの所感（2026-10-11）

画像の枚数上限は、キャッシュの前方一致を考えると、やらない方が良かった。

## 当面の扱い

上限はそのまま（2026-10-11 まはー判断）。画像が多い使い方で困る場合は、既存の設定 `SAIVERSE_GEMINI_ATTACHMENT_LIMIT` を大きくすれば、コードの変更なしで割れにくくできる（その分、古い画像も画像のまま送られる）。

## 直し方の方向（未決）

- 上限をなくす（送る画像は送信直前に長辺 2048px まで縮めているので、1 枚あたりの量は抑えられている）。
- 上限を残すが、置き換えを一枚ずつではなくまとめて行い、割れる回数を減らす。
- 古い画像を文字に変える代わりに、最初から画像として送り続ける範囲を固定する。

どれを採るかは、画像の多い会話での料金と、各プロバイダのキャッシュへの影響を比べて決める。
