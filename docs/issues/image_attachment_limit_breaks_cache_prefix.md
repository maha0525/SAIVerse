# Issue: 画像の枚数上限が、新しい画像が来るたびにキャッシュの前方一致を割る

**ステータス**: 🟣 検証待ち（実装済み。実機の検証が済むまで `docs/issues/` 直下に置く）
**優先度**: low（音声会話など画像が増えにくい場面では、その回だけ待つ形で済む）
**作成日**: 2026-10-11
**関連**: `llm_clients/utils.py`（`parse_attachment_limit` / `select_embedded_attachment_keys` / `attachment_positions_to_replace` / `parse_attachment_byte_bounds` / `estimate_inline_image_bytes`）、各組み立て側（`llm_clients/gemini.py` の `_convert_messages`、`llm_clients/anthropic_request_builder.py`、`llm_clients/openai_message_preparer.py`、`llm_clients/xai.py`）、送る量の見積もり（`sea/sluice.py` の `_estimate_input_tokens`）、`docs/intent/cache_lifecycle_control.md` §3.5（継続キャッシュ）、`docs/intent/persist_realtime_and_recall.md` §4.2

## 何が起きていたか

LLM に送るとき、画像は新しい順に `DEFAULT_ATTACHMENT_LIMIT` 枚（既定 4。`SAIVERSE_{PROVIDER}_ATTACHMENT_LIMIT` / `SAIVERSE_ATTACHMENT_LIMIT` で変えられる）だけをそのまま送り、それより古い画像は要約の文字（`[画像参照のみ: …] 要約`）に置き換えていた。

このため、新しい画像が会話に 1 枚入るたびに、それまで画像として送っていた一番古い 1 枚が文字に変わる。その画像を含むメッセージは会話の前のほうにあるので、そこから後ろが前回送った並びと一致しなくなり、キャッシュ（Anthropic のプロンプトキャッシュ、Gemini の explicit cache と暗黙のキャッシュ）が外れる。

継続キャッシュ（§3.5）では、この回は「一致するキャッシュが無い」例外に落ちて、キャッシュの作成を待つ。

2026-10-14 追記: モデル設定 `cache.persist_realtime_and_recall` を ON にしたモデル（Gemini 4 Argon）では、上限を使わないことにした（送る列の画像をすべて画像のまま送る — `docs/intent/persist_realtime_and_recall.md` §4.2、`llm_clients/utils.ATTACHMENT_LIMIT_OFF_KEY`）。OFF のモデルはこの issue のまま。

## まはーの所感（2026-10-11）

画像の枚数上限は、キャッシュの前方一致を考えると、やらない方が良かった。

## 採った直し方（2026-10-25 まはー裁定）

「上限をなくす」と「溢れそうなときだけまとめて置き換える」の複合。

- **枚数の上限の既定を廃止**: `parse_attachment_limit` は env を明示しないとき None（枚数では絞らない）を返す。全モデルで画像を画像のまま送り続ける。env（`SAIVERSE_{PROVIDER}_ATTACHMENT_LIMIT` / `SAIVERSE_ATTACHMENT_LIMIT`）、モデル設定の `max_image_embeds`、チャット画面の上書きで枚数を明示したときだけ、従来どおり新しい順にその枚数を送る（そのときは従来どおり前方一致が割れる）。
- **バイトの非常弁**: 埋め込む画像の合計（base64 で約 4/3 倍になるので `ceil(大きさ * 4 / 3)` で見積もる）が**天井**を超える送信でだけ、古い側から合計が**床**以下になるまで画像を要約の文字に置き換える。
  - 天井（既定 12MB）= 1 回の API 送信に埋め込む画像の合計バイト（base64 後の見積もり）の上限。プロバイダの要求サイズ上限（Gemini は 1 回の送信で合計約 20MB、本文・音声・動画も同じ枠を使う）に当たらないための余裕。
  - 床（既定 6MB）= 弁が開いたとき、次に開くまでの間隔を稼ぐために下げておく水準。
  - env `SAIVERSE_{PROVIDER}_ATTACHMENT_BYTE_CEILING` / `SAIVERSE_ATTACHMENT_BYTE_CEILING`（床は `_FLOOR`）で変えられる。
  - `persist_realtime_and_recall` のモデルでも効く（§4.2 の「後ろに足すだけ」の約束の例外。要求サイズ上限に当たると送信そのものが失敗するので、稀な一回のまとめ置き換えを優先する）。

## 仕組み

`llm_clients/utils.select_embedded_attachment_keys` が全組み立て側（Gemini・Anthropic・OpenAI 互換（NIM・Codex を含む）・xAI）の共通の入口で、送る量の見積もり（`sea/sluice.py`）も同じ `attachment_positions_to_replace` を通す。

1. 枚数の上限を明示していれば、それを先に当てる（従来の `compute_allowed_attachment_keys`）。
2. 残った画像のうち、そのクライアントが実際に埋め込むメッセージ（Gemini は system・tool・`tool_calls` を持つメッセージ以外、ほかは user）の画像を古い順に並べ、`attachment_positions_to_replace` で置き換える画像を決める。

置き換える画像の決め方は二段で、列の画像の並びと大きさだけで決まる（覚えておく状態は無い）:

1. それ一枚で天井を超える画像は、弁の手前で必ず文字にする。他の画像の合計には最初から入れない。
2. 残りの画像で「画像が古い順に一枚ずつ会話に入ってきたと見立てて、入るたびに、埋め込む合計が天井を超えたら古い側から床以下まで置き換える」をなぞる。

だから:

- 列の後ろに画像が足されるだけなら、置き換える画像は減らない。一度文字にした画像は画像に戻らない（会話の途中が書き換わったり、天井・床を変えたりしたときは数え直しになる）。
- 弁が開かない送信では、埋め込む並びが後ろに伸びるだけなので、前回の送信が今回の送信の先頭とそのまま一致する。前方一致が割れるのは弁が開いた回だけで、そのとき天井から床までの分（既定でおよそ 6MB 分の画像）をまとめて置き換える。その枚数だけ要約の生成（軽量モデルの課金呼び出し）がまとめて走る（要約は `<画像>.summary.txt` に保存され、以後は使い回す）。
- 再起動しても、同じ列には同じ答えを返す。

`__visual_context__`（部屋・外見の画像）と `__realtime_context__`（毎ターン作り直して末尾近くに置くリアルタイム情報）のメッセージの画像は、非常弁に数えず、常に画像のまま送る。`__skip_image_summary__`（`saiverse/media_summary.py` が画像の要約・説明を作るために送る依頼。`_generate_image_summary` と `generate_contextual_image_description` の両方が付ける）のメッセージの画像も、枚数の上限にも非常弁にも数えず、常に画像のまま送る — 外すと要約のモデルが画像を見ないまま答え、その答え（または「(要約を取得できませんでした)」）が `.summary.txt` に保存されて残るため。リアルタイム情報の画像を数えると、その画像があるターンだけ弁が開き、次のターンで閉じて置き換えた画像が画像に戻る（前方一致が二回割れる）ため。数えない分は、天井とプロバイダの要求サイズ上限の間の余裕が受ける。

あわせて、Gemini の組み立てが「埋め込む画像にも毎回要約を作っていた」のをやめ、文字で送る画像（枚数の上限・非常弁の外、読めない画像）にだけ作るようにした。上限をなくすと、作っていた場合は会話の全部の画像に要約の生成が走るため。

### 仕様から変えた点（実装時の判断）

レビューで決めた二点（2026-10-25）:

- **一枚で天井を超える画像は、その一枚だけを文字にする**: 最初の実装は、天井を超えた時点で先に古い側を床まで置き換え、それでも超えていればその一枚も外していたので、一枚で天井を超える画像が来ると古い画像が全部道連れになった（天井 10・床 5 で大きさ 1, 12 の列なら 2 枚とも文字）。弁の手前でその一枚を文字に振り分け、他の画像の合計に入れない形にした。その画像単体の大きさだけで決まるので、後ろに足すだけなら置き換える画像が減らない性質は保たれる（`tests/llm_clients/test_attachment_byte_valve.py` の単調性のテストに、一枚で天井を超える画像を混ぜて固定した）。
- **要約を作るための送信は弁から外す**: 上の `__skip_image_summary__` の扱い。

裁定時の指示では「置き換えた画像かどうか」をその画像の要約のサイドカー（`.summary.txt`）があるかで判定する案だったが、採らなかった。サイドカーは非常弁以外でも作られる — チャットにアップロードした画像の文脈つきの説明（`api/routes/chat.py` → `generate_contextual_image_description`）、アイテムの説明（`api/routes/world.py`・`manager/items.py`）、そして以前の Gemini の組み立て（埋め込む画像にも要約を作っていた）。サイドカーで判定すると、アップロードした画像の大半が送られた直後から文字になり、「画像を画像のまま送り続ける」が成り立たない。代わりに上の「列の並びと大きさだけで決まる」決め方で、同じ単調性（一度置き換えた画像は画像に戻らない）を持たせた。

## 残課題

- **弁が開いた回は要約の生成がまとめて同期で走る**: 置き換える画像のうち要約がまだ無いものは、その回の組み立ての中で一枚ずつ要約のモデルを呼んで作る（`image_summary_note` / Gemini の `ensure_image_summary`）。既定でおよそ 6MB 分の画像をまとめて置き換えるので、要約の無い画像が多いと、その回の送信は要約の生成が全部終わるまで待たされる。
- **要約の生成に失敗した回は注記の文面が揺れる**: 要約が作れなかった画像の注記は「(要約を取得できませんでした)」（Gemini）か URI だけ（ほかのクライアント）になり、次の回に要約が作れればその要約に変わる。そのメッセージから後ろは前回の送信と一致しなくなる。弁で文字にした画像だけでなく、従来から枚数の上限の外の画像も同じ性質を持つ。

- **音声・動画のバイトは非常弁の対象外**: Gemini は音声・動画も埋め込む（`supports_audio` / `supports_video`）。これらは同じ要求サイズの枠を使うが、非常弁は画像だけを数える。音声・動画の多い会話では、天井と要求サイズ上限の間の余裕を超えうる。
- **既存の `.env` に書かれた `SAIVERSE_ATTACHMENT_LIMIT=4`**: 以前の `.env.example` はこの行を有効なまま持っていて、setup はそれを `.env` に写すので、多くの利用者の `.env` に枚数の上限が明示されている。その環境では、この変更の後も枚数の上限 4 が効き続ける（`.env.example` は今回コメントにした）。既存の `.env` をどうするかは未決。
- **モデル設定の `max_image_embeds`**: 組み込みの OpenRouter のモデル定義（`builtin_data/models/openrouter-*.json`）は `max_image_embeds: 4` を持つので、それらのモデルでは枚数の上限が効き続ける。

## 実機検証

画像の多い会話（Gemini で 20 枚程度）で:

- 枚数の上限を明示していない環境で、全部の画像が画像のまま送られること（`llm_io.log`）と、新しい画像を足した回もキャッシュが当たること。
- 天井を超える量の画像を入れた回に、`[attachment byte valve]` のログが出て古い画像が文字になり、その次の回からキャッシュがまた当たること。
