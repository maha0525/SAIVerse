# 記憶の重いペルソナのパック出力が、画面経由だと約 30 秒で失敗する

- **状態**: 未解決 (2026-10-21 起票。v0.3.23 の次のバージョンの実機検証で発見)
- **関連**: `docs/intent/persona_pack.md` / PR #404

## 現象

ペルソナまるごとパックの出力 (`GET /api/people/{id}/persona-pack`) を**画面経由 (Next.js の
中継、`frontend/next.config.ts` の rewrites) で呼ぶと、ZIP の組み立てに約 30 秒以上かかる
ペルソナでは HTTP 500 になる**。バックエンドへ直接同じ GET を送ると成功する。

実測 (2026-10-21、隔離テスト環境 18010→18000。ペルソナはエリスの移住体 = 記憶 10,471 通・
Memopedia 1,320 ページ・パック 1.47GB):

| 経路 | 結果 |
|---|---|
| バックエンド直 (本番 8000 のエリス本体) | 200、138 秒で 1.47GB |
| 中継越し (テスト環境、二回) | 500、どちらも 30.0 秒ちょうど |
| 中継越しの合流 (POST、処理 65 秒) | 200 — 中継は 30 秒超の POST を通せる |
| 軽いペルソナ (テスタロッサ、12MB) の画面出力 | 成功 (まはー実機、2026-10-21 22:12) |

失敗時の中継のログ: `Failed to proxy http://127.0.0.1:18000/api/people/.../persona-pack
Error: socket hang up { code: 'ECONNRESET' }`。

## 原因 (2026-10-22 特定)

Next.js の中継 (rewrites) は内部の http-proxy に `proxyTimeout || 30000` を渡している
(`next/dist/server/lib/router-utils/proxy-request.js`)。`next.config.ts` の
`experimental.proxyTimeout` を設定しない限り、**バックエンドとの間のソケットが 30 秒
無活動だと接続を破棄する**。パックの出力は ZIP を組み立て終わるまで 1 バイトも返さないので、
組み立てが 30 秒を超える規模でちょうど 30 秒で落ちる。

このタイマーは「リクエスト全体の長さ」ではなく**無活動時間**を測る。上の表で合流 (POST、
処理 65 秒) が通ったのは、1.47GB のアップロード中はソケットが動き続け、送信後の沈黙が
たまたま 30 秒未満だったからで、**保証ではない** — もう少し重いパックなら合流・迎えるも
画面経由で同じ失敗になる。起票時に「中継は 30 秒超の POST を通せる」と書いたのは誤読だった。

## 対処 (同日)

`frontend/next.config.ts` の `experimental.proxyTimeout` を 3,600,000 ms (1 時間) に明示した。
値は無活動の上限なので、死んだバックエンドへの接続を手放す安全弁としての役割は残る
(裏のサーバーが固まったときに画面へエラーが出るまでが、30 秒から最大 1 時間に延びる — その間も
他の操作は通る)。エリス規模 (1.47GB) の画面経由出力の再試験は 200・118 秒で通った。設定を
伸ばしただけで同じ沈黙が通るようになったので、切っていたのが中継側のこのタイマーだったことも
裏が取れた。

**治る範囲の注意 (ローカルレビューの指摘で訂正)**: 治るのは rewrites を通る口 (通常の
`/api/:path*` 全部 — パックの出力・取り込み・チャットログの取り込みなど)。**アドオン系
(`app/api/addon/[...path]` と `api/addon/events`) は Next の Route Handler が先に取って
自前で転送する設計なので、この設定の外** — そちらに「最初のバイトまで 30 秒以上黙る」口が
あれば同じ症状が別の原因で残り得る (アドオンカタログの導入は進捗を流し続ける作りなので
現状は踏まないはず。確認はしていない)。

## 利用者への影響

ZIP の組み立てが 30 秒を超える規模のペルソナ (目安: 記憶が数千通 + 添付が多い) では、
記憶画面の「パックにまとめる」が失敗して見え、パックが得られない。軽いペルソナは問題ない。
出力は読み取り専用なので、失敗してもデータは壊れない。

## 方向の候補 (未裁定)

- 接続を切っている側の設定を伸ばす (原因の持ち主の特定が先)
- 出力をアドオンカタログの導入と同じ「サーバーで作って、あとから取りに行く」形にする
  (組み立て時間が中継の制限と無関係になる。進捗も出せる)
