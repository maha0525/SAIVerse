# Lv1 あらすじの source_ids に重複と孤児参照が残っている (実ユーザー DB で確認)

**状態**: 孤児参照 = 解決 (2026-09-01、補修ジョブ冒頭の sweep を実装) / 重複 source_ids = 未解決 (2026-09-01 起票)
**発見経緯**: v0.3.0 リリース直後のユーザー報告 (コンテキスト超過・Chronicle 生成不能) の調査で、ユーザー提供の Chronicle 診断レポート (persona: konoe_city_a、総メッセージ 60,665 件・Lv1 3,124 件・Lv4 まで統合済み) に以下の異常が出た。

## 事象

診断レポートの「Level 1 source_ids 実態調査」:

- **重複 source_ids: 2,860 件** — 複数の Lv1 エントリが同じメッセージ ID を編纂対象として参照している (実際の合計 62,480 に対しユニーク 59,620)
- **孤児 source_ids: 46 件** — 存在しないメッセージ ID を参照している
- source_count と実際の長さの不一致は 0 件 (この面は正常)

付随観察: 期間が 0 秒 (start_time == end_time が秒単位で同一) の Lv1 エントリが 2026-02-14 前後に連続しており、一括インポート由来とみられる。

## 影響の見立て (未検算)

- 被覆の数え上げ (`_coverage_index`、累積質量ルールの質量) が重複分だけ水増しされ、予算モードの粒度選択が実態よりエントリを「重い」と見る可能性がある
- 「編纂済みか」の判定 (ユニーク source_ids ベース) 自体は DISTINCT で数えているため、重複が二重編纂を直接引き起こしてはいない
- 孤児 46 件は削除済みメッセージへの参照とみられ、実害は薄い可能性が高いが、被覆補修 (§16) の見積もりとの整合は未検算
  - ⚠️ この見立ては誤りだった (2026-09-01 の調査で確定 — 下の「調査結果」を見る)。孤児は被覆計算には効かないが、吸収の再開検査を落として未被覆断片を永久に取り残す。

## 原因の仮説 (起票時。孤児については下の調査結果が上書きした)

v0.2 期の生成・インポート経路の産物の可能性が高い (2026-02 の一括インポート痕跡と時期が重なる)。現行の編纂経路 (整列計画 plan_alignment) は処理済み判定をユニーク source_ids で行うため、現行経路で新たに重複が生まれるかは別途確認が要る。

## 調査結果 (2026-09-01)

### 孤児参照 46 件 — 原因確定・対処済み

**原因**: 記憶ブラウザ (UI) のメッセージ削除 — 個別削除・一括削除・スレッド削除のいずれも、生ログを消すだけで、そのメッセージを指す Lv1 あらすじの `source_ids` を直さない。v0.2 期から存在する経路で、リリース版の通常操作で発生する (壊れた DB の残骸ではない)。

**実害**: 孤児参照そのものは被覆の数え上げには効かない。効くのは**吸収の再開検査**で、隣人 Lv1 の source_ids が一つでも死んでいると `sai_memory/arasuji/absorption.py` の "missing source messages" 警告で開き直しが拒まれ、その隣にある未被覆断片が補修を何度回しても取り残される (本番エリスで確認)。

**対処**: 補修ジョブ冒頭の保守ブロックに `_sweep_dead_message_sources` を追加した (2026-09-01 まはー裁定)。既にあった `_sweep_broken_parents` (「上位あらすじ → 消えた下位あらすじ」の死んだ参照を毎回掃く) と対称の、「Lv1 → 消えたメッセージ」版:

- 処置は `sai_memory/arasuji/storage.py` の `prune_dead_message_sources` — `source_ids` から死んだ id を落とし、`source_count` / `message_count` を実長へ引き直す。**本文 (content) には触らない** (LLM ゼロの帳簿補修)。span も動かさない。
- 材料が全滅した Lv1 は手を付けず WARNING だけ残す (生ログが無い以上開き直せないので、吸収が再開を断るのは正しい)。
- 冪等。発火は `run_absorption` 冒頭と `sea/session_lifecycle.py` の全量計画の保守ブロック (**吸収の計画より前** — 後だと孤児持ちの隣人がその回は開けず、取り残しの解消が毎回 1 巡遅れる)。

### 重複 source_ids 2,860 件 — 未解決 (仮説のまま)

現行の編纂経路 (整列計画 `plan_alignment`) が新規に重複を作る証拠は見つかっていない。付随観察の「期間 0 秒の Lv1 が 2026-02-14 前後に連続」と重なるため、**一括インポートと旧世代カーソルの重なり**が仮説だが未検証。孤児とは別問題として残す。

## 次の一手

1. まはーの手元 DB (エリス等、v0.2 から連続運用) で同じ診断を取り、**重複**が「アップグレード組に共通」か「このユーザー固有」かを切り分ける
2. 現行の編纂経路が重複を新規に作りうるかをコードで検算する
3. 共通なら、修復スクリプト (scripts/arasuji/) 側に重複除去の手を足すかを裁定する
