# 詰まった接続先への再試行が二重に積み、記憶の整理が長時間無言で粘る

**状態**: 未着手 (起票のみ)。

## 芯

LLM 呼び出しの再試行が二段に積んである。外側は SAIVerse 自前の再試行 (`llm_clients/openai_runtime.py` の `call_with_retry`、観測時 3 回)、内側は OpenAI SDK の内蔵再試行 (観測時 3 試行)。接続先が「時間をかけて待たせた末にエラーを返す」型の不調のとき、この二段が掛け算になり、**1 回の呼び出しが最悪 9 試行、待ち時間の合計で数十分粘る**。その間、ユーザーの画面には再試行中であることが一切知らされない。

## 実測 (2026-09-22 深夜、まはーの本番環境)

- 手動の記憶の整理で、Chronicle の生成を NIM の Gemma 4 31B に投げた。
- HTTP の試行はどれも同じ経過をたどった: 接続と送信は一瞬で成功 → **きっかり 5 分沈黙 → NIM のゲートウェイが 504 (Nvcf-Status: errored)** を返す。打ち切りは常に NIM 側の 5 分で、SAIVerse 側の読み取り上限がそれより先に働く場面は観測されなかった。
- SDK が 2 回自動再試行して 3 試行 (計 15 分) を使い切ると、外側の自前再試行が「attempt 1/3 失敗」として**同じ 15 分をもう一周**始めた (backend.log 00:14:42〜00:29:50)。
- その間ずっと、画面は「溜まった会話をあらすじにまとめています…」のまま。まはーは「NIM に接続できていないのでは」と不安なまま数十分待つことになった。実際は接続は成立していて、向こうの処理が詰まっていた——この区別が画面からは付かない。

## 論点

1. **再試行の総量**: 二段の掛け算は意図した設計か。「向こうが時間切れを宣告した」504 を 9 回浴びてから諦めるのは、失敗の確定を数十分遅らせているだけの可能性が高い。
2. **知らせが無い**: 手動整理の進み具合の表示に「接続先の応答待ち」「n 回目の再試行」を映す口が無い。ユーザーから見ると壊れたのと区別が付かない。
3. **総時間の上限が無い**: 1 回の呼び出しが何分まで粘ってよいかを SAIVerse 側が決めておらず、接続先の打ち切り時間に依存している。

## 直し方の候補 (未裁定)

- 再試行をどちらか一段に一本化する (SDK 側の再試行を 0 にして自前で数える、または逆)。
- 手動整理のジョブの進み具合に、LLM 呼び出しの再試行状態を映す。
- 呼び出し 1 回の壁時計時間に上限を置く。
