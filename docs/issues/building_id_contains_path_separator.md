# 部屋 ID に「/」が入った部屋で、過去ログが移らず毎回の起動で警告が出続ける (部屋 ID を付け替えて直す)

**起票**: 2026-09-11 (N さんの報告「久しぶりに起動したら『過去ログが未取込』の警告で画面が埋まった」、まはー経由)
**状態**: 実装中 — v0.3.12 (`hotfix/v0.3.12`) に載せる。設計はまはーの GO 済み
**関連**: `saiverse/legacy_log_import.py` (`find_log_files` / `_scan_one_building` / `_child_by_name`)、`manager/initialization.py`、`manager/ids.py`、[legacy_log_import_misses_decomposed_folder_names.md](legacy_log_import_misses_decomposed_folder_names.md)、[archive/building_id_no_charset_constraint.md](archive/building_id_no_charset_constraint.md)、[building_memory_unified.md](../intent/building_memory_unified.md) の「過去ログ取り込みの自動化と検算」

## 症状

N さんの画面 (v0.3 系) に、赤い警告「過去ログが未取込: 2/28」が出る。警告の中身は「状態: まだ移していない / 古いファイルの件数 23 / 移せていない件数 21 / 移し終わった件数 0 / 新しい会話の件数 0」。この種類の警告は重要度が最高の扱いのため、画面を開くたびに展開された状態で表示される。タイトルを押すと畳めるが、読み込み直すと再び開く。押せるボタンは無い。

23 と 21 の差は、古いファイルの中に同じメッセージ ID を持つ行が 2 組あることによる (起動時の確認処理は、メッセージ ID の集合で件数を数える)。

## 原因 (コードの読解と、隔離した一時フォルダでの再現で確定)

部屋「2/28」の ID は `2/28_city_a` になっている。v0.2 までは部屋 ID に使える文字の制限が無く、ID の生成式 (`name.lower().replace(' ', '_')` + `_` + City) では「/」がそのまま ID に残った。

1. v0.2 では、部屋ごとの会話ファイルが `cities/<city>/buildings/<部屋ID>/log.json` に置かれた。「/」はフォルダの区切り記号なので、実際のファイルは `buildings/2/28_city_a/log.json` という 2 段のフォルダの奥にある。
2. 起動時の確認処理 (`_scan_one_building`) では、同じ組み立て方でパスが作られるため、ファイルが見つかり、不足が 21 件と数えられる。
3. 取り込み処理 (`find_log_files`) では、`_child_by_name` の検査で「/」を含む名前が「親フォルダの外を指すかもしれない名前」として除外されるため、対象が 0 件になる。ログには `Building の識別子が名前として使えません: '2/28_city_a'` が出る。
4. 起動のたびに 2 と 3 が繰り返され、警告が消えない。

2026-09-02 の修正より前 (v0.3.0〜v0.3.2) の取り込み処理は、フォルダ名の一覧と照合していた。一覧には「2」しか出ないため、そちらでも対象は 0 件だった。つまりこの部屋の会話は、v0.3 のどの版でも移らない。

「/」による不具合は、取り込みだけではない (2026-09-11 の調査):

- **`saiverse://building/<ID>/items` と `/history` のリンク**: `parse_sai_uri` ではリンクが「/」で区切られ、`_resolve_building` では先頭の `2` が部屋 ID として使われるため、部屋が見つからない (コードで確認)。画像のリンク (`media_utils`) だけは末尾の `/image` を切り取る読み方なので、ID 全体が正しく読まれる。
- **アドオンのメタデータの取得** (`GET /api/addon/messages/{message_id}/metadata`): メッセージ ID `2/28_city_a:5` に「/」が含まれるため、URL が途中で区切られて取得できない可能性が高い (未試験)。
- **部屋の設定画面の保存・削除** (`/api/world/buildings/{building_id}`): 同じ理由で失敗する可能性が高い (未試験)。

## 決めたこと (2026-09-10〜11、まはー)

- 最初に出した案 (部屋 ID はそのままで、取り込み処理が「/」入りの部屋を読めるようにする) は取り下げた。まはーの問い「2 段のフォルダをそのまま使い続けること自体がまずいのでは」を受けて見直すと、この案は「/」を受け入れる箇所を一つずつ増やす直し方で、古い部屋のためだけの特別扱いがコード全体に散らばる。新しい部屋の ID には、v0.3.0 から「/」が入らない。
- **部屋 ID から「/」を取り除く付け替えを行う。表示名は変えない。**
- 付け替えでペルソナの記憶が分断されないことは、v0.2 のコードで確認した。v0.1.0〜v0.2.29 のどの版でも、記憶への書き込みは部屋 ID で区切ったスレッドに入っていない (`append_building_message` は定義だけがあり、呼び出し元が無い)。会話を記憶へ写すメインの処理 (`persona/history_manager.py` の `_sync_to_memory`) で行に付くのは `conversation` タグだけで、部屋 ID は付かない。
- **メッセージ ID (`message_id`、`部屋ID:番号` の形) も、新しい部屋 ID に切り替える** (まはーの提案。ID の中に「/」を残さない)。アドオンのメタデータの表はメッセージ ID で会話を指しているため、一緒に書き換える。
- **古いファイルでの元のメッセージ ID (`building_messages.legacy_message_id`) は変えない**。起動時の確認処理は、古いファイルの行と DB の行をこの値で突き合わせる。書き換えると古い行がすべて「まだ移していない」と判定され、同じ会話がもう一度移される。この欄を使うのは `legacy_log_import.py` (突き合わせとメタデータの付け替え) と `database/building_messages.py` (書き込み) だけで、URL やリンクには入らない。
- **ペルソナの記憶の中身は書き換えない** — 文章、あらすじ、写した会話の目印 (`building_msg_ref`)、部屋の様子の記録の鍵 (`building:<部屋ID>`)。この方針で受け入れる影響は二つ:
  - 写した会話の目印が読まれるのは、二重転記を防ぐ確認 (`find_message_by_building_ref`) だけ。前回の起動が「記憶に書いた後、部屋の会話に写し終わった印を付ける前」に止まっていて、しかもそれが付け替える部屋の会話だった場合に限り、その一件がペルソナの記憶に二回入る。目印まで書き換える処理を足すほうが、ペルソナの記憶にとって危険が大きいと判断した。
  - 付け替えた部屋に今いるペルソナには、部屋の様子が一度だけ全文で届き直す見込み。
- 実行台帳 (execution ledger) の未配達の作業 (`execution_outbox.PAYLOAD_JSON`) も、値の完全一致で付け替える。実行台帳では「配達内容は実行時点で凍結する」と決まっているが、凍結の対象は本文・タグ・名義・実行時刻で、部屋 ID は宛先の情報にあたる。

## 設計

### 付け替える場所

**DB (saiverse.db) — 部屋を指す欄**

- 部屋そのもの: `building.BUILDINGID`
- ユーザーの現在地 `user.CURRENT_BUILDINGID` / ペルソナの私室の指定 `ai.PRIVATE_ROOM_ID` / 地域の入口の部屋 `region.ENTRANCE_BUILDING_ID`
- 部屋に置かれたアイテムの置き場所 `item_location.OWNER_ID` (`OWNER_KIND='building'`) / 部屋に置いた設備 `fixture.BUILDING_ID` / 部屋に結びつけたリアルタイムスペル `realtime_spell_binding.OWNER_ID` (`OWNER_KIND='building'`)
- 部屋の会話 `building_messages.building_id` と `message_id` (`旧ID:番号` を `新ID:番号` に。番号は変えない) と `event_data` (移動元・移動先の値)
- アドオンのメタデータ `addon_message_metadata.message_id` (付け替えたメッセージ ID に合わせる)
- ペルソナが部屋を「どこまで読んだか」`persona_pulse_cursor.BUILDING_ID` / ペルソナごとの「その部屋を前回どう見たか」の控え `persona_building_state.BUILDING_ID` / 入退室の記録 `building_occupancy_log.BUILDINGID` / 出来事の場所 `episodes.BUILDING_ID` / 費用の記録の部屋欄 `llm_usage_log.BUILDING_ID`
- 使われていない古い表: `building_tool_link.BUILDINGID` / `visiting_ai.building_id` (読む処理は無いが、古い ID を残さない)

**DB — JSON でまとめて保存している欄** (動作の材料として読まれるもの)

- 一日の予定のコマの行き先 `persona_day_plan.slots_json` / 時間割のひな形 `persona_timetable_template.SLOTS_JSON`
- 現象のルールの条件 `phenomenon_rule.CONDITION_JSON` / スケジュールの引数 `persona_schedule.PLAYBOOK_PARAMS`
- 実行台帳の未配達の作業 `execution_outbox.PAYLOAD_JSON`
- 外部イベントの付加情報 `persona_event_log.PAYLOAD` / 地域の状態と設定 `region.STATE_JSON`・`region.CONFIG_JSON`
- アドオンの設定 `addon_config.params_json`・`addon_persona_config.params_json`

JSON の欄で置き換えるのは、文字列の値 (と辞書のキー) が旧 ID と完全に一致するものと、メッセージ ID の形 `旧ID:整数` と完全に一致するものだけ。文章の途中に含まれる ID には触らない。

**ファイル**

- `~/.saiverse/cities/<city>/buildings/<旧ID>/` を `<新ID>/` へ移し、1 段のフォルダに戻す。途中のフォルダ (`2`) は、空になったときだけ消す。
- もっと古い形の置き場 `~/.saiverse/buildings/<旧ID>/` があれば、同じように移す。

### 付け替えないもの

- 古いファイルでの元のメッセージ ID `building_messages.legacy_message_id`
- ペルソナの記憶 (`~/.saiverse/personas/<id>/memory.db`) の中身すべて
- ユーザーが書いた文章 (部屋の指示文など) に含まれる ID
- 提示内容の控え (`session_head_snapshot` など)。組み立て直せる控えで、書き換えるとペルソナに送る内容の先頭部分が変わり、プロンプトキャッシュが効かなくなる

### SAIVerse からは直せないもの

- **Discord 連携の「チャンネルと部屋の対応表」**: DB ではなく、環境変数 `SAIVERSE_GATEWAY_CHANNEL_MAP` (JSON) に書かれている (`discord_gateway/mapping.py`)。SAIVerse の起動環境のこの変数に旧 ID が含まれていたら、警告で「対応表の `旧ID` を `新ID` に書き換えてください」と表示する。
- **アドオンが独自の保存先に部屋 ID を保存している場合**: SAIVerse からは中身を読めない。

### 新しい ID の決め方

- 旧 ID の `/` と `\` を `_` に置き換える。それ以外の文字は変えない (日本語の ID を ASCII にする付け替えはしない — 既存の日本語 ID はそのままと決めてある)。
- 次のどれかに当てはまる間は、末尾に `_2`、`_3` … を足して次の候補を試す:
  - 既存の部屋 ID と、大文字小文字を無視して一致する (Windows のファイルシステムは大文字小文字を区別しないため。`manager/ids.py` の重複検査と同じ扱い)
  - 部屋を指す主な欄 (`building_messages.building_id`、`persona_pulse_cursor.BUILDING_ID`、`persona_building_state.BUILDING_ID`、`building_occupancy_log.BUILDINGID`) で、その ID が既に使われている (削除済みの部屋の行が残っていると、付け替えた部屋に混ざるため)
  - 付け替え先のフォルダが既にある
- 決まった ID が 1 階層のフォルダ名として安全でない場合 (`manager/ids.py` の `is_safe_path_component` で判定 — 末尾のドットや空白、Windows の予約名など)、その部屋は付け替えずに警告を出す。

### いつ、どの順で動くか

- 起動時、`_init_city_config` の直後、部屋を読み込む `_init_buildings` の前に置く。起動のたびに実行されるが、対象が無ければ何もしない。付け替えの後、既存の過去ログの確認処理 (`_check_legacy_building_log_import`) が、新しい 1 段のフォルダから会話を移す。
- バージョンのアップグレード処理 (`main.py` の `run_startup_upgrade`) は SAIVerse の本体を組み立てる前に実行されるため、そこで作られた行 (v0.2 から直接更新する人の「どこまで読んだか」など) も、付け替えの対象に含まれる。
- 対象はこの City の部屋 (`building.CITYID`)。参照の書き換えは、DB 全体に対して行う。
- **多重起動の確認**: 同じ DB を使っている別の SAIVerse が動いている場合は、付け替えない (`saiverse.runtime_marker.another_running_process_owns_db` — `CITY_SLUG` の自動修復と同じ確認)。起動は続け、付け替えを見送ったことを警告に出す。
- **付け替えの前に DB のバックアップを取る** (`database/backup.py` の `backup_saiverse_db`)。バックアップに失敗した場合は付け替えず、警告に出す。
- **順番と、途中で止まったときの再開**:
  1. 付け替えの記録 `~/.saiverse/cities/<city>/building_id_renames.json` に、「旧 ID → 新 ID」を「予定」として書く。
  2. DB を一つのトランザクションで書き換えて commit する。
  3. フォルダを移し、空になった途中のフォルダを消す。
  4. 記録を「完了」にする。記録は消さずに残す (どの ID をどう変えたかの控えとして)。
  - 1 の後で止まった場合: 次の起動では DB にまだ旧 ID があるので、記録の予定をそのまま使ってやり直す。
  - 2 の後で止まった場合: DB は新しい ID、フォルダは古い場所にある。次の起動で記録の「予定」を読み、DB に旧 ID が無く新 ID があることを確かめてから 3 を行う。
  - 3 の途中で止まった場合: 移し終わったフォルダは古い場所に無いので飛ばし、残りを移す。

### 確認処理と取り込み処理の探し方を一本にする

2026-09-02 の修正で「探し方を確認処理と揃えた」と書いたが、実際には取り込み処理だけが `_child_by_name` を通り、確認処理 (`_scan_one_building`) は素のパス結合のままだった。今回、確認処理でも同じ関数で場所を決める。付け替えで「/」入りの ID は無くなるが、残っていた場合 (付け替えを見送ったときなど) は、確認処理でも「部屋 ID がフォルダ名として使えない」として警告 (`check_failed`) に出す。確認処理と取り込み処理の結果が食い違ったまま、警告だけが出続ける状態を作らない。

### 警告とログ

- 付け替えの内容は、毎回起動ログに残す (旧 ID → 新 ID、表ごとの書き換えた行数、移したフォルダ)。
- 画面の警告に出すのは、ユーザーに対応をお願いするときだけ: Discord の対応表に旧 ID が残っているとき、付け替えを見送ったとき (多重起動・バックアップの失敗・安全な ID にできない)、付け替えに失敗したとき。
- 付け替えの後、DB の文字列の欄に旧 ID が残っていないかを数えてログに出す (書き換えはしない。見落とした欄を見つける手がかりにする)。

### 検証の手順

- **単体テスト**: 新しい ID の決め方 (置き換え・大文字小文字・既存の行・既存のフォルダ・安全でない ID) / JSON の完全一致の置き換え (文章中の ID は変えない、辞書のキーも対象) / 各表の書き換え / メッセージ ID とアドオンのメタデータの書き換え / `legacy_message_id` が変わらないこと / 手順 1・2・3 のそれぞれの後で止まった状態からの再開 / 多重起動の確認で見送ること / Discord の対応表の警告。
- **確認処理と取り込み処理の一本化**: 「/」入りの ID が残っていたとき、確認処理が `check_failed` を出し、取り込み処理と食い違わないこと。
- **起動から画面までを一続きに通す確認 (隔離環境)**: 隔離した `SAIVERSE_HOME` に N さんの形 (部屋「2/28」、2 段のフォルダに 23 行の log.json、同じメッセージ ID を持つ行が 2 組、DB の会話 0 行) を作り、起動の実際の経路を通す。付け替え → 取り込み → 警告なし → 部屋の会話が元の順で並ぶ → メッセージ ID が新しい部屋 ID の形、までを出力で読む。
- **実 API での確認 (隔離テスト環境)**: `/api/system/alerts` に過去ログの警告が無い / `/api/chat/history?building_id=2_28_city_a` で会話が見える / `PUT /api/world/buildings/2_28_city_a` が通る。
- まだ確認できない部分: 利用者の実環境 (N さんが更新した後の確認)。

## 似た課題 (今回は手を入れない)

- **ペルソナ ID**: v0.2 の生成式 (`name.lower().replace(' ', '_')` + City、`manager/persona.py` / `manager/blueprints.py`) でも「/」が ID に残った。ペルソナ名に「/」を含む v0.2 のペルソナは、`personas/<ID>/` が 2 段になっている可能性がある。実例の報告は無い。付け替えはペルソナの記憶のフォルダとスレッド名 (`<persona_id>:<suffix>`) に及ぶため、部屋とは別の設計が要る。

## なぜ作り込んだか (三つの原因)

1. **技術的な原因**: 部屋 ID をフォルダ名・URL・リンクの一部としてそのまま使っているのに、v0.3.0 より前は ID に使える文字の制限が無く、「/」が入った。さらに、同じ部屋のファイルを探す規則が、確認処理と取り込み処理の二箇所に分かれていた。
2. **判断の失敗**:
   - 2026-08-09 に ID に使える文字の制限を入れたとき、既存の ID は「数週間の稼働で壊れていない」ことを根拠にそのままにした。この確認は日本語の ID についてだけで、既存の ID の中に、制限を設けた理由 (フォルダ・URL・リンクの一部になる) に実際に反するものが無いかは数えなかった。
   - 2026-09-02 の修正で「探し方を揃えた」と書いたが、取り込み処理にだけ「/」を除外する規則を足し、確認処理は変えなかった。揃えたという記述を、実装と照らし合わせて確認しなかった。
3. **過程の条件**: 区切り記号を含む部屋 ID の実データも、そのテストも無かった。作成時の検査を足すだけで終わる修正には、既存データが制限に反していても気づく仕組みが無い。

**再発防止策の横展開の確認**: 今回の再発防止策は「永続する ID の制限を作成時の検査だけに入れるなら、既存の値が制限の理由に反していないかを起動時に数え、反していれば直すか、画面で知らせる」。この策は、無関係な二つの失敗にも当てはまる — (i) City の識別子 (旧チュートリアルが表示名で上書きした世界は、起動時の `CITY_SLUG` 自動修復で救われている) と、(ii) 上のペルソナ ID (同じ v0.2 の生成式で「/」が入りうる)。今回の対策は文章の規則ではなく、起動時に実行される付け替えと確認処理として置く。
