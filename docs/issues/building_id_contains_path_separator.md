# 部屋 ID に「/」が入った部屋で、過去ログが移らず毎回の起動で警告が出続ける (部屋 ID を付け替えて直す)

**起票**: 2026-09-11 (N さんの報告「久しぶりに起動したら『過去ログが未取込』の警告で画面が埋まった」、まはー経由)
**状態**: 実装中 — v0.3.12 (`hotfix/v0.3.12`) に載せる。設計はすべてまはーの GO 済み
**関連**: `saiverse/legacy_log_import.py` (`find_log_files` / `_scan_one_building` / `_child_by_name`)、`manager/initialization.py`、`manager/ids.py`、[legacy_log_import_misses_decomposed_folder_names.md](legacy_log_import_misses_decomposed_folder_names.md)、[archive/building_id_no_charset_constraint.md](archive/building_id_no_charset_constraint.md)、[building_memory_unified.md](../intent/building_memory_unified.md) の「過去ログ取り込みの自動化と検算」、[room_state_packages.md](../intent/room_state_packages.md)、[execution_ledger.md](../intent/execution_ledger.md)

## 症状

N さんの画面 (v0.3 系) に、赤い警告「過去ログが未取込: 2/28」が出る。警告の中身は「状態: まだ移していない / 古いファイルの件数 23 / 移せていない件数 21 / 移し終わった件数 0 / 新しい会話の件数 0」。この種類の警告は重要度が最高の扱いのため、画面を開くたびに展開された状態で表示される。タイトルを押すと畳めるが、読み込み直すと再び開く。押せるボタンは無い。

23 と 21 の差は、古いファイルの中に同じメッセージ ID を持つ行が 2 組あることによる (起動時の確認処理は、メッセージ ID の集合で件数を数える)。

## 原因 (コードの読解と、隔離した一時フォルダでの再現で確定)

部屋「2/28」の ID は `2/28_city_a` になっている。v0.2 までは部屋 ID に使える文字の制限が無く、ID の生成式 (`name.lower().replace(' ', '_')` + `_` + City) では「/」がそのまま ID に残った。

1. v0.2 では、部屋ごとの会話ファイルが `cities/<city>/buildings/<部屋ID>/log.json` に置かれた。「/」はフォルダの区切り記号なので、実際のファイルは `buildings/2/28_city_a/log.json` という 2 段のフォルダの奥にある。
2. 起動時の確認処理 (`_scan_one_building`) では、同じ組み立て方でパスが作られるため、ファイルが見つかり、不足が 21 件と数えられる。
3. 取り込み処理 (`find_log_files`) では、`_child_by_name` の検査で「/」を含む名前が「親フォルダの外を指すかもしれない名前」として除外されるため、対象が 0 件になる。ログには `Building の識別子が名前として使えません: '2/28_city_a'` が出る。
4. 起動のたびに 2 と 3 が繰り返され、警告が消えない。

2026-09-02 の修正より前 (v0.3.0〜v0.3.2) の取り込み処理は、フォルダ名の一覧と照合していた。一覧には「2」しか出ないため、そちらでも対象は 0 件だった。つまりこの部屋の会話は、v0.3 のどの版でも移らない。

「/」による不具合は、取り込みだけではない (2026-09-11 の調査):

- **`saiverse://building/<ID>/items` と `/history` のリンク**: `parse_sai_uri` ではリンクが「/」で区切られ、`_resolve_building` では先頭の `2` が部屋 ID として使われるため、部屋が見つからない (コードで確認)。画像のリンク (`media_utils`) だけは末尾の `/image` を切り取る読み方なので、ID 全体が正しく読まれる。
- **アドオンのメタデータの取得** (`GET /api/addon/messages/{message_id}/metadata`): メッセージ ID `2/28_city_a:5` に「/」が含まれるため、URL が途中で区切られて取得できない可能性が高い (未試験)。
- **部屋の設定画面の保存・削除** (`/api/world/buildings/{building_id}`): 同じ理由で失敗する可能性が高い (未試験)。

## まはーの発言と決定 (原文つき)

- 最初に書き手 (メティス) が出した案は「部屋 ID はそのままで、取り込み処理が『/』入りの部屋を読めるようにする」だった。これに対するまはーの問い (2026-09-11):「2段のフォルダをそのまま運用し続けること自体、かなりまずそうに思うけどその点はどう？」
- 書き手はこの問いを受けて、「/」を受け入れる箇所を一つずつ増やす直し方は古い部屋のためだけの特別扱いがコード全体に散らばる (新しい部屋の ID には v0.3.0 から「/」が入らない) と判断を改め、**部屋 ID から「/」を取り除く付け替え (表示名は変えない)** を提案した。まはー:「うん、それが良い！」
- 書き手が付け替える場所の一覧を出したところ、まはーの提案:「会話一件ずつの識別番号 — これだけは今後どう使うか分からないしちゃんと新IDに切り替えたほうが良くない…？」→ **メッセージ ID (`message_id`、`部屋ID:番号` の形) も新しい部屋 ID に切り替える**。
- 書き手がこれを受けて示した、古いファイルでの元のメッセージ ID (`legacy_message_id`) は変えないことと、実行台帳の未配達の作業も値の完全一致で付け替えること。まはー:「うん、それはOK！対応お願い！」
- 文書の整合性の検査を受けて書き手が立てた二つの判断 (下の「判断 1・2」) に、まはー:「Ok、どちらもbで！」
  - **判断 1 (b)**: ペルソナの記憶のファイルの中の、機械が読む印 (部屋の様子の記録の「どの部屋か」の印と、写した会話の目印) を新しい ID に書き換える。ペルソナが読む文面は変えない。
  - **判断 2 (b)**: 「/」と「\」だけでなく、フォルダ名や URL を壊す文字もまとめて `_` に置き換える。

### 判断 1 の材料 (決定前に示したもの)

- (a) 書き換えない場合: 付け替えた部屋に v0.3.9 以降にいたペルソナで、部屋の様子の全文が送る内容の一番古い位置に置き直され、古い方も残るので同じ部屋の様子が二枚並ぶ。プロンプトキャッシュはそこから後ろが全部効かなくなる (ペルソナとモデルの組ごとに一回)。写した会話の目印は、まれに一件が二重に記憶に入る。部屋の様子の intent の「同じ内容が二枚並ぶことは構造的に無い」の例外になる。
- (b) 印だけ書き換える場合: 上のことは起きない。起動時にペルソナの記憶のファイルを開けて、旧 ID の印を書き換える処理が入る。前例は `room_state_packages.md` §7-3 (印を打つだけで確定した文面は書き換えない)。
- どちらでも、古い部屋の様子の文面に書かれた画像のリンク (`saiverse://building/<旧ID>/image`) は、付け替え後に開けなくなる。

### 判断 2 の材料 (決定前に示したもの)

- (a) 「/」と「\」だけ: ほかの壊れる文字を含んでいても「/」の無い部屋は、そのまま残る (リンクや URL が壊れたまま、警告も出ない)。
- (b) まとめて置き換える: 仕組みは同じで、対象の部屋が増えるだけ。日本語の ID と、全角の「？」「：」は変えない。実例があるかは確認していない。

## 書き手の判断 (まはーの GO の範囲内で、設計を詰める中で加えたもの)

- 新しい ID の空き判定を、部屋を指すすべての欄に広げる (削除済みの部屋の行が残っていると、付け替えた部屋に混ざるため)。
- 起動時の確認処理と取り込み処理で、部屋のファイルの場所を同じ関数で決める。
- 文書の整合性の検査 (2026-09-11) を受けて加えた訂正:
  - 部屋専用の Playbook の欄 `playbooks.building_id` を付け替える一覧に加えた (漏れていた。一覧にあった `visiting_ai.building_id` は実在しない欄で、書き手の取り違えだった)。
  - 「前回ペルソナに知らせた状態」の控え (`session_head_snapshot.LAST_NOTIFIED_JSON`) の部屋 ID を付け替える。付け替えないと、付け替えた部屋にいるペルソナに「現在地が『2/28』から『2/28』に変わりました」という、起きていない移動の通知が作られる (`sea/head_pipeline/sections/building.py` の差分判定が、部屋 ID の違いで移動と判定する。コードで確認)。ペルソナに送る本文の元 (`SECTIONS_JSON`) は付け替えない。
  - メッセージ ID を書き換える行で `legacy_message_id` が空なら、旧メッセージ ID をそこへ写す。起動時の確認処理と取り込み処理は、古いファイルのメッセージ ID を DB の `message_id` と `legacy_message_id` の両方と突き合わせるので、`message_id` だけで一致していた行 (二重書き込み期に作られた行など) が、書き換え後に「まだ移していない」と判定されないようにするため。今の書き込み処理 (`database/building_messages.py`) は元のメッセージ ID を `legacy_message_id` に写す作りなので、空の行は多くない見込み。
  - 実行台帳の実行の入力 (`execution_ledger.PAYLOAD_JSON`) も、値の完全一致で付け替える一覧に加えた。
  - 実行台帳を付け替える理由の書き方を直した。前の版は「部屋 ID は宛先にあたる」と書いていたが、配達先はペルソナで、部屋の様子の作業では部屋 ID は記録の中身、移動の後処理では「どこからどこへ動いたか」の事実そのものだった。正しくは「同じ部屋を指す識別子の置き換えで、表す事実は変わらない」。

## 設計

### 付け替える場所 — DB (saiverse.db)

**部屋を指す欄** (この一覧が付け替える欄のすべて)

- 部屋そのもの: `building.BUILDINGID`
- ユーザーの現在地 `user.CURRENT_BUILDINGID` / ペルソナの私室の指定 `ai.PRIVATE_ROOM_ID` / 地域の入口の部屋 `region.ENTRANCE_BUILDING_ID`
- 部屋専用の Playbook `playbooks.building_id`
- 部屋に置かれたアイテムの置き場所 `item_location.OWNER_ID` (`OWNER_KIND='building'`) / 部屋に置いた設備 `fixture.BUILDING_ID` / 部屋に結びつけたリアルタイムスペル `realtime_spell_binding.OWNER_ID` (`OWNER_KIND='building'`)
- 部屋の会話 `building_messages.building_id` と `message_id` と `event_data`
- アドオンのメタデータ `addon_message_metadata.message_id`
- ペルソナが部屋を「どこまで読んだか」`persona_pulse_cursor.BUILDING_ID` / 旧式の「その部屋を前回どう見たか」の控え `persona_building_state.BUILDING_ID` / 入退室の記録 `building_occupancy_log.BUILDINGID` / 出来事の場所 `episodes.BUILDING_ID` / 費用の記録の部屋欄 `llm_usage_log.BUILDING_ID`
- 使われていない古い表: `building_tool_link.BUILDINGID` (読む処理は無いが、古い ID を残さない)

**メッセージ ID の書き換え**

- その部屋の `building_messages` の各行で、`message_id` が `旧ID:` で始まるなら、先頭を `新ID:` に置き換える (後ろの番号は、負の数も含めて変えない)。この書き換えで「旧メッセージ ID → 新メッセージ ID」の対応表を作る。
- 書き換える行で `legacy_message_id` が空なら、旧メッセージ ID をそこへ写す。`legacy_message_id` が既にある行は変えない。
- `addon_message_metadata.message_id` は、この対応表と完全に一致するものだけを書き換える。まだ DB に取り込まれていない古いファイル時代のメッセージ ID に付いたメタデータは変えない (取り込み処理が、取り込むときに新しいメッセージ ID へ付け替える)。

**JSON でまとめて保存している欄** (この一覧が対象のすべて)

- 一日の予定のコマの行き先 `persona_day_plan.slots_json` / 時間割のひな形 `persona_timetable_template.SLOTS_JSON`
- 現象のルールの条件 `phenomenon_rule.CONDITION_JSON` / スケジュールの引数 `persona_schedule.PLAYBOOK_PARAMS`
- 実行台帳の未配達の作業 `execution_outbox.PAYLOAD_JSON` / 実行台帳の実行の入力 `execution_ledger.PAYLOAD_JSON`
- 前回ペルソナに知らせた状態 `session_head_snapshot.LAST_NOTIFIED_JSON` / 旧式の控え `persona_building_state.BASELINE_JSON`・`LAST_NOTIFIED_JSON`
- 外部イベントの付加情報 `persona_event_log.PAYLOAD` / 地域の状態と設定 `region.STATE_JSON`・`region.CONFIG_JSON`
- アドオンの設定 `addon_config.params_json`・`addon_persona_config.params_json`
- 部屋の会話の `building_messages.event_data`

JSON の欄で置き換えるのは、文字列の値と辞書のキーのうち、(i) 旧部屋 ID と完全に一致するもの (→ 新部屋 ID)、(ii) 上の対応表の旧メッセージ ID と完全に一致するもの (→ 新メッセージ ID) だけ。文章の途中に含まれる ID には触らない。

### 付け替える場所 — ペルソナの記憶のファイル (判断 1 (b))

対象は DB に登録されているペルソナのうち、`~/.saiverse/personas/<id>/memory.db` があり、下の欄に旧 ID を含む行があるものだけ。書き換えるのは機械が読む印だけで、ペルソナが読む文面 (`perception_buffer.content`、`perception_batches.rendered_text`、`messages.content`) と添付 (`media`) には触らない。

- 未消費の知覚 `perception_buffer.metadata` (JSON): 部屋の様子の記録の鍵 `building:<旧ID>` → `building:<新ID>`、記録の中の束の部屋 ID、移動の知らせの移動元・移動先の ID を、完全一致で置き換える。
- 未消費の知覚 `perception_buffer.reduce_key`: 値が `building:<旧ID>` と完全に一致するなら置き換える (この欄の使われ方は実装時に確認する)。
- 消費済みの知覚 `perception_batches.room_state_json` (JSON): 部屋の様子の記録の鍵と束の部屋 ID を、完全一致で置き換える。
- 記憶の行 `messages.metadata` (JSON) の `building_msg_ref` (写した会話の目印、`<部屋ID>:<メッセージID>` の形): 先頭の `旧ID:` を `新ID:` に、続くメッセージ ID の先頭の `旧ID:` を `新ID:` に置き換える。ほかの項目は変えない。

書き換える前に、そのペルソナの記憶のファイルを `~/.saiverse/backups/building_id_repair/<日時>/<ペルソナ ID の危ない文字を _ にした名前>_memory.db` へ丸ごと複製する (SQLite のバックアップ機能を使い、書き込み途中の状態を写さない)。複製に失敗したペルソナは書き換えず、警告に出す。

ペルソナ ID そのものがフォルダ名として使えないペルソナ (v0.2 の生成式で、ペルソナ名の「/」が ID に残ったもの) の記憶のファイルは、部屋のフォルダと同じやり方で入れ子の場所 (`personas/<a>/<b>/memory.db`) を探して書き換える。場所を安全に決められない ID (空の段・`.`・`..`) のペルソナがいたら、警告を出し、付け替えの記録を「完了」にしない。Windows で作れない文字を含む ID のペルソナには、記憶のファイルが作られていないので、処理済みとして扱う。

どちらの記憶のファイルも、ペルソナの記憶を読み込む前 (SAIVerse の本体の組み立ての途中) に書き換える。

### 付け替える場所 — ファイル

- `~/.saiverse/cities/<city>/buildings/<旧ID>/` を `<新ID>/` へ移し、1 段のフォルダに戻す。途中のフォルダ (`2`) は、空になったときだけ消す。
- もっと古い形の置き場 `~/.saiverse/buildings/<旧ID>/` があれば、同じように移す。

### 付け替えないもの

- 古いファイルでの元のメッセージ ID `building_messages.legacy_message_id` のうち、既に値がある行
- ペルソナに送る本文の元 `session_head_snapshot.SECTIONS_JSON`。書き換えるとペルソナに送る内容の先頭部分が変わり、プロンプトキャッシュが効かなくなる。この欄の見出しには部屋 ID が `(ID: 旧ID)` の形で出るため、次に本文が作り直されるまで、ペルソナには旧 ID が見える
- ペルソナの記憶のファイルの文面と添付、上に挙げた印以外の項目
- ユーザーが書いた文章 (部屋の指示文など) に含まれる ID

### 付け替えで受け入れる影響

- 次に本文が作り直されるまで、ペルソナに送る本文の部屋の見出しに旧 ID が出る。
- ペルソナの記憶の文面の中に書かれた `saiverse://building/<旧ID>/image` のリンクは開けなくなる (今は開ける)。

### 既存の決定との関係 (実装と同じ変更で文書を更新する)

- `building_memory_unified.md` の「過去ログ取り込みの自動化と検算」節は「既存の行は 1 つも動かない (行の seq / message_id は他の記録から参照されている)」と定めている。取り込み処理についてのこの約束は変えないが、部屋 ID の付け替えだけは `message_id` を動かす例外 (参照している側も同時に書き換える) として追記する。同じ文言の説明文 (`saiverse/legacy_log_import.py` の `migrate_building`、`manager/initialization.py` の `_check_legacy_building_log_import`) にも同じ注記を足す。
- `execution_ledger.md` §2.2 と `database/models.py` の `ExecutionOutbox` の説明文 (「配送内容を実行時点で凍結」) に、「部屋 ID の付け替えでは、同じ部屋を指す識別子だけを置き換える (表す事実は変わらない)」例外を一行足す。`saiverse/occupancy_manager.py` の移動の payload の説明文 (「移動時点の事実を凍結する」) にも同じ注記を足す。
- `room_state_packages.md` の §7-3 (印を打つだけで確定した文面は書き換えない) の近くに、「部屋 ID の付け替えでは、記録の鍵と束の部屋 ID を書き換える (文面は書き換えない)」を追記する。
- `legacy_log_import_misses_decomposed_folder_names.md` の「検算側と同じ解決方法に揃えたので、『片方だけ見つかる』状態が構造的に起きなくなる」は、確認処理側が揃っていなかったので誤りだった。同じ変更で訂正を追記する。

### SAIVerse からは直せないもの

- **Discord 連携の「チャンネルと部屋の対応表」**: DB ではなく、環境変数 `SAIVERSE_GATEWAY_CHANNEL_MAP` (JSON) に書かれている (`discord_gateway/mapping.py`)。SAIVerse の起動環境のこの変数に旧 ID が含まれていたら、警告で「対応表の `旧ID` を `新ID` に書き換えてください」と表示する。
- **アドオンが独自の保存先に部屋 ID を保存している場合**: SAIVerse からは中身を読めない。

### 付け替える部屋と新しい ID の決め方 (判断 2 (b))

- **付け替える部屋**: この City の部屋のうち、次の文字の置き換えで ID が変わるもの。
  - フォルダ名に使えない文字 (`manager/ids.py` の `_UNSAFE_PATH_CHARS`): `/` `\` `:` `*` `?` `"` `<` `>` `|`
  - URL の区切りになる文字: `#` `%`
  - 制御文字 (コード 32 未満)
  - 末尾のドットと空白 (Windows がフォルダ名から黙って落とすため)
- **新しい ID**: 上の文字をそれぞれ `_` に置き換える。それ以外の文字は変えない (日本語の ID を ASCII にする付け替えはしない — 既存の日本語 ID はそのままと決めてある。全角の「？」「：」も変えない)。
- 次のどれかに当てはまる間は、末尾に `_2`、`_3` … を足して次の候補を試す:
  - 既存の部屋 ID と、大文字小文字を無視して一致する (Windows のファイルシステムは大文字小文字を区別しないため。`manager/ids.py` の重複検査と同じ扱い)
  - 上の「部屋を指す欄」のどれかで、その ID が既に使われている (削除済みの部屋の行が残っていると、付け替えた部屋に混ざるため)
  - 付け替え先のフォルダが既にある (ただし、この部屋が前にその ID でデータベースに載ったことがある (付け替えの記録に、DB を付け替えた時刻が書いてある) なら、そのフォルダは前の付け替えでこの部屋のフォルダを移したものなので空きとみなす。DB だけをバックアップから戻した後に同じ新しい ID へ付け替え直し、フォルダと部屋をまた揃えるため。記録に「予定」を書いただけで一度も載っていない ID の場所に現れたフォルダは、別の部屋のものかもしれないので空きとみなさない。記録の書き込みが続けて失敗して時刻が残らず、その後に DB だけを戻した場合は、番号を足した ID を選び、前に移したフォルダは新しい ID の場所に残ったまま部屋から外れる)
  - 同じ起動で、先に別の部屋の新しい ID として決めた
- 決まった ID が 1 階層のフォルダ名として安全でない場合 (`manager/ids.py` の `is_safe_path_component` で判定 — Windows の予約名 `CON` などに当たる場合)、その部屋は付け替えずに警告を出す。

### いつ、どの順で動くか

- 起動時、`_init_city_config` の直後、部屋を読み込む `_init_buildings` の前に置く。起動のたびに実行されるが、対象が無ければ何もしない。付け替えの後、既存の過去ログの確認処理 (`_check_legacy_building_log_import`) が、新しい 1 段のフォルダから会話を移す。
- バージョンのアップグレード処理 (`main.py` の `run_startup_upgrade`) は SAIVerse の本体を組み立てる前に実行されるため、そこで作られた行 (v0.2 から直接更新する人の「どこまで読んだか」など) も、付け替えの対象に含まれる。
- 参照の書き換えは、DB 全体とすべてのペルソナの記憶のファイルに対して行う。
- **多重起動の確認**: 同じ DB を使っている別の SAIVerse が動いている場合は、付け替えない (`saiverse.runtime_marker.another_running_process_owns_db` — `CITY_SLUG` の自動修復と同じ確認)。起動は続け、付け替えを見送ったことを警告に出す。
- **付け替えの前に DB のバックアップを取る** (`database/backup.py` の `backup_saiverse_db`)。バックアップに失敗した場合は付け替えず、警告に出す。
- **古い会話との照合が悪くならないことを確かめる**: 部屋ごとに、古いファイルの行のうち DB に見つからない行の数を、DB を書き換える前 (旧 ID) と後 (新 ID、commit の前) で数える。数え方は起動時の確認処理と同じ一つの関数を使う。後の数が前より多い部屋があれば、その回の DB の書き換えを巻き戻し、その部屋だけを外して、残りの部屋でもう一度書き換える。外した部屋は付け替えを見送って警告を出し、次の起動でもまた確かめる。古いファイルは、旧 ID の場所に無ければ新 ID の場所も見る (DB だけをバックアップから戻した後は、フォルダが新 ID の場所に移っているため)。メッセージ ID の書き換えで、古いファイルとの照合に使っていた値が DB から消える形 (`legacy_message_id` に旧メッセージ ID と違う値が入っている行など) を、前提に頼らず検査で止めるため。ただし、外した部屋の古いフォルダが、同じ起動で付け替える別の部屋の古いフォルダの中にある場合は、外側の部屋のフォルダを移すときに内側の部屋のフォルダも一緒に動き、内側の部屋の古い会話は取り込まれなくなる (ファイルは消えずに、外側の部屋の新しいフォルダの中に残る)。フォルダがこう重なるのは、部屋の名前そのものに City の接尾辞と区切り記号の並び (部屋「a/b_city_a/c」の「_city_a/」) が入っているときだけなので、この形には対処しない。
- **順番と、途中で止まったときの再開**:
  1. 付け替えの記録 `~/.saiverse/cities/<city>/building_id_renames.json` に、「旧 ID → 新 ID」を「予定」として書く。
  2. DB を一つのトランザクションで書き換えて commit する。
  3. ペルソナの記憶のファイルの印を、ペルソナごとに (複製を取ってから) 書き換える。
  4. フォルダを移し、空になった途中のフォルダを消す。
  5. 記録を「完了」にする。記録は消さずに残す (どの ID をどう変えたかの控えとして)。
  - 1 の後で止まった場合: 次の起動では DB にまだ旧 ID があるので、記録の予定をそのまま使ってやり直す。
  - 2 の後で止まった場合: 次の起動で記録の「予定」を読み、DB に旧 ID が無く新 ID があることを確かめてから、3 と 4 を行う。3 の書き換えは完全一致の置き換えなので、途中まで済んだペルソナに対してもう一度行っても結果は変わらない。
  - 4 の途中で止まった場合: 移し終わったフォルダは古い場所に無いので飛ばし、残りを移す。

### 元に戻す手順 (付け替えで問題が起きたとき)

1. SAIVerse を止める。
2. 付け替えの直前に取ったバックアップ (`saiverse.db_backup_building_id_repair_*.bak`) で DB を戻す (`database/backup.py` の `restore_saiverse_db_backup`)。
3. 書き換えたペルソナの記憶のファイルを、`~/.saiverse/backups/building_id_repair/<日時>/` の複製で戻す。
4. 付け替えの記録 `building_id_renames.json` の各要素について、フォルダを `<新ID>/` から `<旧ID>/` の場所へ戻す。
5. 記録ファイルから、戻した要素を消す (残すと、次の起動の再開の判定がフォルダを再び移す)。

DB だけを戻すと、ペルソナの記憶のファイルとフォルダが新しい状態のまま残って食い違う。2〜4 は必ずそろえて行う。

### 確認処理と取り込み処理の探し方を一本にする

2026-09-02 の修正で「探し方を確認処理と揃えた」と書いたが、実際には取り込み処理だけが `_child_by_name` を通り、確認処理 (`_scan_one_building`) は素のパス結合のままだった。今回、確認処理でも同じ関数で場所を決める。付け替えで「/」入りの ID は無くなるが、残っていた場合 (付け替えを見送ったときなど) は、確認処理でも「部屋 ID がフォルダ名として使えない」として警告 (`check_failed`) に出す。確認処理と取り込み処理の結果が食い違ったまま、警告だけが出続ける状態を作らない。

部屋を指定しない取り込み (手動の取り込みスクリプト `scripts/migrate_building_logs_to_db.py` で部屋を省いたとき) も、部屋 ID をフォルダ名から取らず、DB に登録された部屋 ID から場所を決める。フォルダ名を部屋 ID に使うと、macOS でフォルダ名が濁点の分解された形のとき、DB の部屋と別の部屋 ID で会話を書き込む。登録されていない部屋のフォルダの古い会話は取り込まない (buildings の直下のフォルダにあるものはログに出す。入れ子のフォルダの奥は調べない — 登録されていない部屋の会話はどのみち取り込まないので、出ないのはログの一行だけ)。

### 警告とログ

- 付け替えの内容は、毎回起動ログに残す (旧 ID → 新 ID、表ごとの書き換えた行数、書き換えたペルソナの記憶のファイルと行数、移したフォルダ)。

## なぜ作り込んだか (三つの原因)

1. **技術的な原因**: 部屋 ID をフォルダ名・URL・リンクの一部としてそのまま使っているのに、v0.3.0 より前は ID に使える文字の制限が無く、「/」が入った。さらに、同じ部屋のファイルを探す規則が、確認処理と取り込み処理の二箇所に分かれていた。
2. **判断の失敗**:
   - 2026-08-09 に ID に使える文字の制限を入れたとき、既存の ID は「数週間の稼働で壊れていない」ことを根拠にそのままにした。この確認は日本語の ID についてだけで、既存の ID の中に、制限を設けた理由 (フォルダ・URL・リンクの一部になる) に実際に反するものが無いかは数えなかった。
   - 2026-09-02 の修正で「探し方を揃えた」と書いたが、取り込み処理にだけ「/」を除外する規則を足し、確認処理は変えなかった。揃えたという記述を、実装と照らし合わせて確認しなかった。
3. **過程の条件**: 区切り記号を含む部屋 ID の実データも、そのテストも無かった。作成時の検査を足すだけで終わる修正には、既存データが制限に反していても気づく仕組みが無い。

**再発防止策の横展開の確認**: 今回の再発防止策は「永続する ID の制限を作成時の検査だけに入れるなら、既存の値が制限の理由に反していないかを起動時に数え、反していれば直すか、画面で知らせる」。この策は、無関係な二つの失敗にも当てはまる — (i) City の識別子 (旧チュートリアルが表示名で上書きした世界は、起動時の `CITY_SLUG` 自動修復で救われている) と、(ii) 上のペルソナ ID (同じ v0.2 の生成式で「/」が入りうる)。今回の対策は文章の規則ではなく、起動時に実行される付け替えと確認処理として置く。
