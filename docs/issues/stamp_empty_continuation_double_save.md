# 504 の継続が空応答のとき、二重保存された部分文に継続コールの数字が乗る

**状態**: 未解決 (2026-08-22 起票)。**裁定待ち** — 直す場所が二つあり、どちらを直すかで意味が変わる。

関連: [`sea/runtime_llm.py`](../../sea/runtime_llm.py) の `_respeak_after_stream_timeout` / [`sea/message_stamp.py`](../../sea/message_stamp.py)
出自: v0.3 形の層の掃討フェーズ、ローカル LLM レビュー 束 5 の指摘 3 (2026-08-22)。同レビューの指摘 1 (子 Playbook の中継で前駆が居残る) は原因が一意だったため修正済み。

## 何が起きるか

サーバーが応答の途中で切れた (504) とき、SAIVerse は「続きを話してください」ともう一度呼ぶ。この**継続の呼び出しが空で返った**場合、部分文が二度保存され、**二行目にその部分文を書いていない呼び出しの数字が刻まれる**。

束 5 の芯は「**欠落は許すが捏造は許さない**」なので、これは芯に反する。ただし刻まれるのは数字だけで、本人の言葉は変わらない。

## 具体的な並び (現物で確認済み)

1. 初回のストリームが 504 で切れる → state の三つ組 = 初回コールのもの
2. 部分文を保存 (`_store_memory`) → **一行目: 初回の三つ組** ✓
3. 継続コールを投げる → 空応答
4. `_record_llm_usage` (`runtime_llm.py:446`) が state の三つ組を**継続コールのもので上書き** (入力 > 0、出力 = 0)
5. 空判定 (452 行) で `partial_text` を返す
6. 下流の memorize が同じ部分文をもう一度保存 → **二行目: 継続コールの三つ組** ✗

## 上書きは意図的である (ここが裁定の分かれ目)

446 行の直前のコメントは、空応答でも使用量を通す理由をこう書いている。

> 「**空応答でも必ず通す** — トークンは消費されているし、通さなければ初回コールの三つ組が state に居残って次の生成へ漏れる」

つまり「空でも上書きする」のは**狙ってやっている**。目的は「初回の数字が次の生成へ漏れるのを防ぐ」ことで、それ自体は正しい。

考慮に入っていないのは、**その直後に同じ部分文がもう一度保存される**こと。書き手は「次の生成」を見ていて、「この直後の二重保存」を見ていない。

## 選択肢 (未裁定)

- **A: 何もしない。** 二行目は一行目の重複で、本人の言葉は失われない。数字の帰属だけがずれる
- **B: 空応答のとき、返す直前に三つ組を落とす。** 「この行を書いた呼び出しが確定できない」ので刻印なしへ倒す — 束 5 の他の場面と同じ規律。代償は、UI のキャッシュヒットのドットがその行から消えること (使用量そのものは記帳されているので、費用の記録は失われない)
- **C: 二重保存の方を直す。** そもそも同じ部分文が二度保存されるのが正しいのか。**この二重保存は束 5 以前からある挙動**で、刻印の導入で初めて数字の帰属問題として見えるようになった。根に近いのはこちら
- **D: 二行目を一行目の続きとして扱う。** 保存を一本化し、部分文の行を更新する形にする。影響範囲は C より大きい

**C と D は束 5 の範囲を超える** (生ログの保存の設計に触る)。B は束 5 の中で閉じるが、症状を消すだけで二重保存は残る。

## 実機で見ること

504 は頻繁には起きない。起きたときのログ (`[sea][llm] Re-speak after 504 returned empty response`) を目印に、同じ本文の行が二つ並んでいないか、二行目のドットが出力 0 になっていないかを見る。
