# ペルソナまるごとパック ストリーミング化 — クラウド継続への引き継ぎ (2026-10-17)

読み手: この続きを別環境 (クラウド) で引き受けるセッション。このリポジトリの外の記録 (作業メモ・スクラッチパッド) は見えない前提で、必要な材料は全部この docs/handoff/ に置いてある。

## 何の作業か

- 機能: **ペルソナまるごとパック** — ペルソナ一体の記憶・プロフィール・手帳・所持品を一つの ZIP として書き出し、別環境で「新しいペルソナとして迎える」「既にいるペルソナに合流させる」機能。設計の正本は `docs/intent/persona_pack.md` (全論点オーナー承認済み)。
- PR: **#404** (feature/persona-archive → develop)。機能本体は実装・レビュー (Codex 敵対 13 巡 + PR 上の再レビュー 3 巡、指摘は全消し込み)・隔離環境での画面検収まで完了している。
- 今の作業: **ストリーミング化** (intent §3 原則 6、2026-10-17 オーナー裁定)。SAIVerse はメモリ 2 GB の VPS でも運用されるため、「パックの中身を一度に全部メモリへ広げない」を v1 の必須要件にした。書き出しは一行ずつ ZIP へ、取り込みは ZIP の JSON を逐次読みしてディスク上の作業用 SQLite に積み、各工程が一行ずつ処理する。ZIP の形式は変えない。

## 済んでいること (コミット済み・push 済み)

実装は束に分けて進め、各束は「対象テスト緑 + ruff 緑 + 差分精読」の検収後にコミットしてある。`git log --oneline` の「ストリーミング化 束Sx」のコミットが対応する。

- **束S1**: `saiverse_memory/persona_pack/json_stream.py` 新設 — JSON 配列を 1 要素ずつ読む読み器 (標準ライブラリのみ、1 要素の上限つき、テスト 44 件)。
- **束S2**: 取り込みのメディアと指紋の丸読み 7 箇所を 1 MiB の分割読みに (`_PackReader.sha256` + キャッシュ)。
- **束S5**: 書き出しに残っていた丸ごと保持を逐次化 (chatgpt_compat は 1 スレッドずつ、addon_message_metadata は 500 件ずつの IN 照合、attachments/index.json は逐次書き)。
- **束S3**: 取り込みの `_load_pack` を作業用 SQLite (`_StagingDB`、ZIP の隣の `<zip名>.<import_id先頭16字>.work.sqlite`、終了時に必ず削除) 経由に。1 要素の上限 `MAX_JSON_ELEMENT_CHARS` (64 Mi 文字) 新設。
- **束S4**: 全体保持が要る工程 (メッセージの正典順ソート・重複判定・seq 判定、ページの番号計画と Chronicle 被覆判定、手帳のソート、切り抜きの計画) を作業用 SQLite の鍵の列・索引・SQL に置換。挙動の不変は、新旧実装の差分比較 (既存テスト由来 135 回 + fuzz 620 回、不一致 0) で確認済み。

設計の背景資料: `docs/handoff/2026-10-17_persona_pack_streaming_survey.md` (実装前の全数調査。各工程の消費パターン・順序依存・テストが内部に依存する箇所の一覧)。

## 残っている作業 (この順で)

### 1. (済) 束S7 — 書き出しの chatgpt_compat に残る「1 スレッドぶんの保持」の解消

クラウド継続のセッションで実装・コミット済み (`git log` の「束S7」)。`chatgpt_compat.write_conversation` が 1 ノードずつ書き、`build_conversation` は削除してテストの参照実装へ移した。`tests/test_persona_pack_memory.py` はスレッド数を固定して 1 スレッドの件数も増やす較正にし、旧実装で落ちる (export 8.3 → 64.0 MiB) ことを確かめてから直した (0.4 → 0.4 MiB)。以下は着手前の発注内容。


束S6 (コミット済み) のピークメモリ計測が見つけた、最後の比例保持。`export.py` の `_iter_conversations` は 1 スレッド (= 1 部屋) の会話メッセージをリストに集めてから `chatgpt_compat.build_conversation` で組み立てる。SAIVerse のスレッドは部屋ごとなので、同じ部屋で長く暮らしたペルソナは 1 スレッドが寿命の大半を占め、実測の増え方 (約 6.7 KiB/件) から 10 万件の部屋で数百 MB になる — 2 GB の機械では致命的。

直し方 (発注側の決定): `chatgpt_compat/conversations.json` の 1 会話 = 1 要素の中身 (mapping の木) を、`json.dumps` で丸ごと作らず**手書きの逐次書きで組み立てる**。mapping は id → ノードの平らな dict で、各ノードの children は次のノードの id 一つだけ (chatgpt_compat.py の `build_conversation` を読んで構造を確かめること)。つまりメッセージを SQL のスレッド内順で読みながら、ノードを一つずつ JSON 文字列として書き出せば、保持は常に前後 1〜2 ノードで済む。検証は「小さいスレッドで、逐次書きの出力を json.loads して `build_conversation` の出力と完全一致」のテストと、`tests/test_persona_pack_memory.py` の較正を「1 スレッドの件数も増やす」形に広げてこの保持が消えたことを実測すること。`write_json_array` は要素を丸ごと dumps する作りなので、この 1 エントリだけは `zf.open(..., "w")` へ直接書く形になる (配列のハンドルを開いている間に別のエントリを書かない制約は維持)。

### 2. (済) 束S6 — 一時置き場・上限の整理・ピークメモリの退行テスト

このローカルセッションで実装・検収・コミット済み (`git log` の「束S6」)。アップロードと書き出しの一時ファイルは `<SAIVERSE_HOME>/tmp/` へ移動済み。上限は `MAX_UNCOMPRESSED_BYTES` (16 GiB、ディスク) と `MAX_JSON_ELEMENT_CHARS` (64 Mi 文字、メモリ) の二本に整理済み (一枚物の JSON には `read_json_document` が同じ要素上限を当てる)。`tests/test_persona_pack_memory.py` が全件保持の書き戻しを機械で検出する。仕様書 `2026-10-17_persona_pack_streaming_s6_spec.md` と調査 (survey) に出てくる廃止済みの定数名は当時の記録なので読み替えること。

## 守ること (CLAUDE.md より特に)

- **本番ペルソナ・本番データ (`~/.saiverse/`) に触れない** (CLAUDE.md の Production Persona Safety。テストは tmp_path の合成 DB だけ)。
- 外部ライブラリを新しく足さない (ストリーミングは標準ライブラリで書く方針)。
- 挙動を変えたら `docs/intent/persona_pack.md` の該当行を同じコミットで更新する。
- コード内のコメント・docstring は識別子と既存用語で書く (新しい日本語の呼び名を作らない)。
- 旧実装の経路を残さない (使われなくなった関数は削除。履歴が保険)。

## 既知の残余 (対応不要・記録のみ)

- 書き出しの messages の `ORDER BY created_at` は索引が無く SQLite の外部ソートに逃げる (一時ファイルの置き場は OS 設定依存)。
- 合流時の取り込み先側の照合に使う id だけの集合は取り込み先の規模に比例するが、id のみで小さい。
- 取り込み結果の「注意」(警告文) は英語のまま — 日本語化するかはオーナー判断待ち。
