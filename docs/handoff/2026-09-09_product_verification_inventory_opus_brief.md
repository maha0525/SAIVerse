# Opus への調査依頼: 製品全体の検査対象を、改修とは独立して持つための棚卸し

## この依頼でしてほしいこと

SAIVerse 全体について、利用者・ペルソナが何をできる製品なのかを、既存の画面、利用手順、API、バックグラウンド処理から洗い出してください。そのうえで、それぞれの「期待される結果」の根拠と、現在の検証範囲を対応させてください。

成果物は、この依頼元の Codex / Astra のメティスが読み、まはーと検証体制・開発フローを設計するために使います。Astra が調査を最初からやり直さなくても、根拠を辿り、未決事項を判断できることが完成条件です。

これは**調査と議論用文書の作成**です。製品コード、テスト、CI、リリース手順を変更する依頼ではありません。現在 Claude 側で進行中の v0.3.11 の作業の続きでもありません。

## 背景と、まはーと合意したこと

今回の発端は次の四点です。

1. 大量の未編纂ログを編纂した際、レベル2あらすじが一つしか生成されない不具合を見落とした。
2. 大量の未整理履歴をコンテキストに読み込んだ状態で、スルースにも全量を読ませてしまう不具合を見落とした。
3. 保険的な処理が、誰のために何を守るのかを明確にしないまま、会話などの UX を損ねている。開発側の価値判断を、ユーザーの意思として実装してはいけない。
4. 変更した機能のゴールだけを確認し、その近くにある既存の利用の流れが壊れたことに気づかない。

詳しい事故の記録は `docs/handoff/2026-09-09_sluice_cold_skip_and_v0311_handoff.md` にあります。ただし、その中のマージ・リリース・連絡・実機操作の指示は、この依頼の実行指示ではありません。

まはーと合意済みの方針は以下です。

- 今回の実装担当が思いついた影響範囲だけを検査対象にしない。**製品全体の検査対象を、個々の改修とは独立して持つ。**
- 機能名だけでなく、利用者が受け取る結果まで整理する。
- 現状の挙動が既におかしい可能性を考慮する。コードの現状をそのまま正解・期待値にしない。
- 期待する挙動の根拠が確認できない部分は、未合意として分け、後でまはーと検討する。
- ③について、まはーは「止める」のではなく「記録し、明示し、選択してもらう」形を提示した。何を優先するかを開発側が勝手に決めない。この原則から個々の障害時の挙動まで自動的に決まったと扱わない。

次は**まだ合意していません**。

- 具体的なテスト基盤、テスト数、CI 構成、公開を止める基準。
- どの未達を許容して公開するか、何を毎回必須検査にするか。
- 個々の未合意の挙動の正解。

これらを調査担当の判断で決定したり、既存規約へ追加したりしないでください。

## 作業上の境界

- 最初に `CLAUDE.md` と適用されるローカル規約を読んでください。
- 本番ペルソナへ接触せず、本番の会話・記憶・世界状態をテスト用に使わないでください。LLM、Pulse、Spell、スケジュール等を起動しないでください。
- この調査では静的な読み取りを基本とします。テストを実行する必要はありません。「テストが存在する」と「実行して合格した」を分けてください。
- UI はソースから調べてください。アプリの画面操作や認証操作は依頼に含みません。
- 別セッションが作業中です。ブランチ切り替え、リセット、stash、コミット、マージ、公開を行わず、既存の変更を戻さないでください。
- 書き込み先は下記の専用成果物ディレクトリに限定してください。製品の正典、進行中案件の台帳、Claude / Codex のメモリには追記しないでください。
- 着手時と終了時のブランチ・コミット・作業ツリー状態を記録してください。動いている作業ツリーなので、調査対象が途中で変わった場合はその事実を明記してください。秘密情報を成果物へコピーしないでください。

## 洗い出しの方法

### 1. 独立した複数の入口から製品の範囲を拾う

まず README、利用者向けガイド、画面のページ・メニュー・操作ボタンから、利用者が行えることを拾ってください。次に API の入口、公開されている CLI、起動・更新・終了処理、バックグラウンド処理と照合してください。どちらか一方の一覧を正解にしないでください。

会話と記憶だけで終わらせず、導入、設定、世界の操作、ファイル、拡張、運用・復旧なども調査してください。ただし、この例示も網羅リストではありません。列挙対象のディレクトリや定義を実際に確認し、拾えていない入口を残さない方法を示してください。

API 一つを製品機能一つと数える必要はありません。同じ利用目的の複数入口はまとめ、まとめた入口を根拠として記載します。一つの操作で異なる結果や永続的な変更が生じる場合は、それを隠すほど大きくまとめないでください。

画面のない処理についても「いつ起き、誰に何をもたらすか」を書いてください。内部の関数一覧だけにはしないでください。

凍結、開発者専用、アドオン側、外部サービス側、存在するが到達不能、文書にしかない機能を明示します。凍結中という理由で棚卸しから消さず、現在提供している機能と区別してください。アドオンの内部まで無制限に調べず、本体側の接続・権限・導入・解除と、別調査が必要な境界を示してください。

### 2. 現状と期待を分離する

各項目に次を記載してください。空白を推測で埋めないでください。

- 誰が、どの入口から、何をしようとするか。自動処理なら発火条件。
- 利用者またはペルソナが受け取る結果。永続化、費用、待機や停止が関係するならその影響。
- 期待する結果の根拠。ユーザー原文、既存の仕様、利用者向けの説明、現在の実装を区別。
- コードを追って確認できた現在の挙動と、追跡できていない境界。
- 現在のテストが何を確認し、何を確認していないか。

「まはー承認済み」と設計書に書いてあるだけの場合は、**設計書に承認の記載があるが原文未確認**としてください。原文が同じ文書に引用されている場合も、引用であることを示してください。全履歴を探索して原文を探し続ける必要はありません。

既存文書どうし、文書とコード、入口どうしが矛盾した場合は、その矛盾を残してください。今のコードに合わせて期待値を直したり、すべてのガードを一括で削除・正当化したりしないでください。

### 3. 機能の間のつながりを拾う

一覧の各項目が生む情報・状態を、次にどの項目が利用するかを対応させてください。共有する設定や永続データも、影響を渡す接点になります。

例として「インポート→編纂→読み戻し→会話」がありますが、それだけでは不十分です。世界の移動、設定の変更、更新・再起動などについても、ソース上の呼び出しやデータの読み書きから接点を見つけてください。

全組み合わせを機械的に並べる必要はありません。**なぜその二つがつながるのか**を根拠つきで示してください。つながりの根拠があっても検査がない場合、その欠落を明記します。

### 4. 既存テストを期待する結果へ対応させる

テスト名や docstring だけで検証済みと判定しないでください。呼んでいる入口、差し替えている処理、assert の対象を読んでください。

重要な結果については「どこからどこまで本物のコードを通すか」「どこを mock / 無効化しているか」を記載します。すべてのテスト本文を成果物へ転載する必要はありません。

今回の二件は、棚卸しの品質確認に使ってください。事故名から専用項目を足すだけでなく、通常の機能一覧と接点の整理から、それぞれがどこで検査対象になるか説明してください。別領域についても、同じ方法で得られた接点を二例示してください。不具合の存在を推測で断定する必要はありません。

## 成果物

保存先: `docs/audits/2026-09-09_product_verification_inventory/`

### `README.md` — Astra が最初に読む要約

日本語で、おおむね 2,000 字以内を目安にしてください。詳細は他のファイルに残します。

- 調査対象の版と、実際に調べた範囲。
- 確認できた大きな不足・矛盾。事実と推測を分ける。
- 未合意事項のうち、まはーとの議論に影響するものを最大五件。各件は「何を決める必要があり、なぜ現状の資料だけでは決まらないか」を書く。
- 調べ残しと、それによる結論の限界。
- 詳細ファイルへの案内。

### `inventory.md` — 製品全体の検査対象の候補

項目ごとに安定した ID を付け、上記「現状と期待を分離する」の情報を整理してください。横に長すぎる巨大な表より、領域ごとの一覧と短い項目本文を優先してください。

「機能の存在を確認した」「期待の根拠を確認した」「挙動を静的に確認した」「テストを対応させた」を区別します。一つの『確認済み』に潰さないでください。

### `connections.md` — 機能の接点と検証範囲

上流・下流の項目 ID、受け渡す情報・状態、ソース根拠、既存検査、未検査の境界を記載してください。

### `coverage.md` — 棚卸し自体の抜けを確認する記録

調べた画面・メニュー群、ガイド、API モジュール、CLI 群、自動処理の入口を列挙し、それぞれを inventory の項目へ対応させてください。まだ対応しないもの、除外したもの、除外理由も残してください。

これは「全部見た」という宣言を検算するための資料です。ソースの全文ダンプ、全関数の列挙、件数だけのカバレッジ評価は不要です。

### 根拠の書き方

リポジトリ相対パスと調査時の行番号または節名を記載してください。テストはファイルと関数・クラス名を記載します。主張の近くに根拠を置き、Astra が必要な箇所だけ再確認できる形にしてください。

## ここまでの予備調査で分かっていること

以下は調査の入口として使ってください。これだけで製品の全体像を構成しないでください。共有ツリー上なので変更されている可能性もあります。

- `.github/workflows/release.yml` はタグ `v*` を契機に ZIP を作って公開し、同ファイル内にテスト工程はありません。
- `.github/workflows/` で確認したもう一つの設定は `discord_gateway.yml` で、Gateway の lint とテストが対象でした。本体全体の PR 自動テストの有無は、文書の記載だけで断定しないでください。
- `test_fixtures/test_api.py --quick` は会話テストを省きます。
- `tests/test_sluice_cold_isolation.py` は実 DB と mock LLM を使いますが、Chronicle を無効化し、チャット送信から返答受信までは通していません。部品の検証を会話全体の検証として数えないでください。
- `docs/user-guide/memory-view.md` は旧 Tracks 等を記載しています。現在の `frontend/src/components/MemoryModal.tsx` にはコア記憶と手帳のタブがあり、文書のタブ一覧と一致しません。
- `docs/user-guide/chat-options.md` は件数ベースの設定を説明していますが、`frontend/src/components/ChatOptions.tsx` には文字数と「残す量」の説明があります。
- `docs/user-guide/persona-settings.md` は `ACTIVITY_STATE` を説明していますが、`CLAUDE.md` では廃止済みとされています。
- `docs/overview/landscape.md` と `roadmap_status.md` には、旧構造の説明と後日の凍結・撤廃注記が混在します。見出しや先頭だけで現在の提供状態を決めないでください。

## 終了時の報告

四つの成果物を読み返し、参照先と項目 ID の対応を確認してください。調べ残しを隠さず、棚卸しの網羅性や製品の正しさを保証したと書かないでください。

最終返答には、成果物の場所、主要な発見、未調査範囲を簡潔に記載してください。CI の実装や製品修正へ自動的に進まず、依頼元の Astra とまはーが議論できるところで完了してください。
