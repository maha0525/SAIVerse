# Handoff: v0.2.29 → v0.3 実機アップグレード検証 (段 1 — 主経路)

**書いた状況**: 2026-08-29 深夜。まはーの「リリース判定で一番やらなきゃいけないのは現行リリースからのバージョンアップが上手くいくか」を受けて、最終リリース (v0.2.29、2026-06-15、= 現 main) の世界を合成で作り、v0.3 候補 (feature/autonomous-behavior-v2) で起動する検証を行った。

## 検証環境 (再現手順)

- `git worktree add C:\Users\shuhe\workspace\saiverse-v0229-upgrade-test v0.2.29`
- v0.2.29 備え付けの隔離テスト環境 (`test_fixtures/setup_test_env.py`、port 18000、`SAIVERSE_HOME`/`SAIVERSE_USER_DATA_DIR` を worktree の `test_data/` へ) で世界を生成

- **無垢なスナップショット**: `test_data_pristine_v0229/` (何度でも跳び直せる)。跳び 1 回目の結果は `test_data_after_hop1/` に保存
- 跳び: メインリポジトリから同じ env で `python main.py test_city`

## 結果の要約

**主経路 (v0.2.29 → v0.3 の一発起動) は、migrate.py の修正 1 件を入れて合格。**

無垢な世界からの一発起動で: スキーマ移行 (CITYNAME→CITY_SLUG 改名 + 全書き換え) → INTERACTION_MODE→AUTONOMY_ENABLED 変換 → 旧建物ログの DB 取り込み (`legacy_log_import`) → ペルソナ記憶 DB に v0.3 の全テーブル (27 枚) 生成、まで自動で完走。旧会話は履歴 API に載り、**会話するとペルソナがアップグレード前の話題 (天体観測) を覚えていた**。会話は現行の track_user_conversation を通り、speak_persisted (当日実装) も流れた。

## 見つけた欠陥と対処

### 1. ✅ 修正済み — 全書き換え移行が Windows で必ず墜落する (起動不能)

破壊的スキーマ差分の移行は DB ファイルの move を要するが、main.py の import 時副作用 (addon ツール登録が addon_config を参照) が共有エンジン (`database/session.py`) の接続プールに接続を 1 本残し、Windows の WinError 32 で move が失敗 → 起動不能。再起動でも直らない。診断スクリプトで「dispose 無しでは main DB への接続 1 本が残る」を直接確認した。

**修正**: `migrate_database_in_place` が move の前に共有エンジンを `dispose()` する (ファイルを動かす当事者に置いた)。修正後、部分移行状態からの復帰と無垢からの一発跳びの両方で合格。

### 2. 🔲 裁定待ち — v0.2 の Playbook 行がゾンビとして残留

37 本の退役 Playbook (meta_user 等) が「ユーザー作」の顔で永久残留する。詳細と対処候補: [`v02_playbook_rows_survive_as_unmanaged_zombies.md`](../issues/v02_playbook_rows_survive_as_unmanaged_zombies.md)。起動と会話は正常なのでリリース遮断ではないが、全アップグレードユーザーに堆積する。

### 3. 観察 — 孤児プロセスが DB を掴んでいると同じ墜落になる

検証中、強制終了で生き残った v0.2.29 の子プロセス (`database.api_server`) が DB を掴み、同じ WinError 32 を起こした。実ユーザーでも異常終了後の孤児は起こり得る。現行のエラーメッセージは「他プロセスが DB を開いていないか確認してください」と正直で、runtime marker の仕組みもあるため、追加対処は今は無し。

## 段 2 — 3 月の本番バックアップからの遠距離跳び (2026-08-29 深夜、合格)

まはーが発掘した `D:\Download\saiverse.zip` (今夜 zip 化された `~/.saiverse` の旧ドライブコピー、中身は 2026-03-13 まで) を使用。もう一つの `SAIVerse (2026-03-15 ver).zip` はリポジトリ形式で world は 2/10 止まり (2 月の user_data 引っ越しの名残) のため不使用。

**手順の要点** (`saiverse-march-upgrade-test\` に展開):
- バックアップは採取時にロック中だったファイル (本体 saiverse.db・大半の memory.db・主要な部屋の log.json) が欠けていた。DB は zip 内の `.bak` バックアップ群から最新を復元配置 (saiverse.db = 3/13 20:36、memory.db はペルソナごとに最新の backup)。
- テストコピーの city ポートを 18000/19000 へずらし、**API キーは全部ダミーで起動** (本物のペルソナデータのコピーに認知を発生させない保険)。会話は一切送っていない。

**結果**: 一発起動で完走。二都市 (city_a + city_b)・16 ペルソナ (0 failed)・建物 28・Playbook 53・使用量ログ 2,961 件を移行。CITY_SLUG 改名 + 表示名復元 + INTERACTION_MODE→AUTONOMY_ENABLED (16 件) も適用。ペルソナ記憶はエリス 594MB / 7,443 メッセージを含め全員 v0.3 スキーマ (29 テーブル) へ移行。モデル失効の fallback 警告ゼロ (3 月のモデル名は現行 config に全部残っている)。

**建物履歴が 0 件になったのはバックアップの欠落** (上記ロック漏れで log.json が主要部屋に無い) であって移行コードの欠陥ではない。残っていた 3 部屋の log.json は DB から削除済みの旧世代の部屋 (図書室→library 改築前の孤児フォルダ) のもので、検算 (`scan_legacy_log_deficits`) が DB の部屋だけを対象にするのは設計どおり。実環境の in-place アップグレードでは log.json は実在し、取り込みは段 1 で実証済み。

## 段 3 — update.bat / self_update.py の経路検証 (2026-08-30 深夜、合格 — 修正 2 件 + issue 1 件)

**環境**: `saiverse-update-bat-test\` に本リポジトリの clone (`repo\`、main ブランチを v0.2.29 に据えて origin の候補ブランチを追跡) + 偽ユーザープロファイル (`profile\`、USERPROFILE/HOME/LOCALAPPDATA/APPDATA/TEMP を差し替え、中身は段 1 の無垢な v0.2.29 世界を実配置 `%USERPROFILE%\.saiverse\` へ合流)。venv は素の新規作成 = **editable install の無い実ユーザー環境を忠実に再現** (これが欠陥 2 を露見させた)。

**実走した旅**: ① v0.2.29 の旧 update.bat → ② (修正後) 新 update.bat = `scripts/update_engine.py --manual` を pull 差分ありで完走 → ③ 更新直後の checkout で `main.py test_city` を起動し、v0.2.29 世界の全書き換え移行 + upgrade handler 7 本 + **[playbook_replacement] 51 行退避→全削除→現行 19 本再取込** + `/api/system/version` 200 (version=0.3.0.dev6, city_name=test_city) まで確認。engine の失敗時ロールバック (`git reset --hard` + 依存修復) も pip 失敗時に実際に発火するのを観測した。

### 見つけた欠陥

1. **🔲 issue 化 — v0.2.29 の update.bat が git pull 直後に静かに死ぬ**: `echo ... (local changes stashed)` の括弧が cmd のブロック解析を壊し、pull 成功でも偽の stash 案内を出して exit 0。pip / migrate / playbook / npm が走らない。リリース済みの過去側なのでコードでは直せず、**リリースノートに「update.bat を 2 回実行」を明記する義務**を [`v0229_update_bat_truncates_after_git_pull.md`](../issues/v0229_update_bat_truncates_after_git_pull.md) に記録。2 回目で完全回復することは実機確認済み。
2. **✅ 修正済み (`dc9650cb`) — 新 update 経路がスナップショット段で全ユーザー必ず墜落**: engine がサブプロセスで呼ぶ `scripts/snapshot.py` に sys.path shim が無く (scripts/ で唯一の欠落)、`from saiverse.runtime_marker import ...` が ModuleNotFoundError。開発機は過去の `pip install -e .` の残骸が import を通すため隠れていた。setup.bat の venv (editable install 無し) では 100% 再現。shim 追加 + `-S` で素の環境を再現する回帰テスト (修正前の赤を実測)。
3. **✅ 修正済み (`302680e6`) — requirements.txt の日本語コメントで日本語 Windows の pip が墜落**: pip は BOM 無しの requirements をロケール (cp932) で decode するため、UTF-8 の日本語コメントで `pip install -r` 自体が UnicodeDecodeError。**update だけでなく setup.bat の新規インストールも死ぬ**、主ユーザー層直撃の欠陥。コメントを英訳して ASCII 化し、requirements*.txt の ASCII 縛りを回帰テストで固定。

### 環境起因で欠陥ではないもの

- Unity Gateway の ws://0.0.0.0:8765 bind 失敗 traceback — 同一機で本番 backend が同ポートを保持していたための衝突。
- 検証 3 回目に pip キャッシュが repo 内 `pip/cache/` に落ちてクリーンツリー検査を汚した — USERPROFILE と LOCALAPPDATA の不整合という harness 側の歪みで、実ユーザー環境では起きない。
