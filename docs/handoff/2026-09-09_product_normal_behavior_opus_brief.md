# Opus への依頼: 製品全体の「正常な姿」の初稿

## 目的と、この仕事の位置

まはーと Codex / Astra のメティスは、SAIVerse 全体について本来の挙動を整理し、現状を正常化したうえで、それを維持する検証・リリースフローを作る方針に合意しました。

進行順序は次のとおりです。

1. **今回の仕事**: 既存の棚卸しを、利用者・ペルソナが受け取る結果を中心とした「正常な姿の初稿」に組み替える。
2. Astra が初稿の根拠と矛盾を読み、まはーとの判断が必要な点を整理する。既存の決定から答えが分かることを、まはーに毎回決め直させない。
3. 一つの利用の流れを選び、詳細の仕様を決め、修正・隔離検証を最後まで行う。
4. 正常化した流れの検査を残し、次の流れへ進む。揃った検査をリリースフローへ組み込む。

今回は 1 までです。元の棚卸しを大規模にやり直す必要はありません。成果物から 2 を開始できる状態にしてください。

外部接続・URI 読み出し・別プロセス強制終了に関わる四件は、別途先行対処する順序として相談済みですが、この依頼に修正を含めません。

## 合意済みの設計方針

- 製品全体の検査対象を、個々の改修担当が思いつく影響範囲とは独立して持つ。
- 現状の実装が既におかしい可能性を考慮する。現在の挙動を、そのまま正常な挙動へ昇格させない。
- 正常化には、不具合の修正と、曖昧な「本来どう動くべきか」の整理の両方を含める。
- 期待する挙動の根拠がない箇所は、未合意として残す。
- 保険的な処理について、まはーは「止める」のではなく「記録し、明示し、選択してもらう」形を提示した。誰のために何を守るか、何を優先するかを開発側が勝手に決めない。個々の操作への適用方法は、根拠なしに決めない。
- 215 項目を一件ずつまはーに承認させる形にしない。共通の判断はまとめ、操作ごとの違いが重要な場合は具体例を添える。

## 作る初稿の粒度

関数や API 一つではなく、**利用者が一つの目的を果たすまでの流れ**を一単位にしてください。自動処理なら、発火から利用者・ペルソナが結果を受け取るまでを一単位にします。

粒度の例:

- 過去ログを取り込み、その記憶を使って会話する。
- 溜まった履歴を編纂し、結果を閲覧して会話を続ける。
- 部屋を移動し、その場の相手や物を認識して会話する。
- モデルや設定を変更し、その設定で利用する。
- 更新・再起動して、保存した状態から利用を再開する。

これは対象を限定する一覧ではありません。会話へ接続しない機能も含め、215 項目を対応させて全体を覆ってください。独立した複数の目的を一つに押し込めず、逆に同じ目的の入口違いだけで細分化しないでください。流れの数にノルマはありません。

## 各流れに書くこと

1. **誰が何をしたいか**。利用者、ペルソナ、運用者など、結果を受け取る主体を明示する。
2. **始まりから結果までの流れ**。操作・自動処理・表示・保存・次の利用を短くつなぐ。
3. **期待する結果の初稿**。「処理が成功する」ではなく、利用者・ペルソナが何を受け取れるかを述べる。観察可能な形で書くが、未合意の数値や制約を作らない。
4. **根拠**。ユーザー発言の引用、既存仕様、利用者向け説明、調査担当の提案を分ける。文書の『承認済み』という記載と、原文の確認を区別する。
5. **現状との差**。既知の不一致、静的な疑い、まだ追跡していない境界を区別する。検査がないことを不具合の証明にしない。
6. **必要な場合の中断・失敗・再開**。何が残り、何が見え、何を選べるべきか。どの流れにも定型の異常条件を大量に貼り付けず、実際の処理・保存・費用・接点から必要なものを選ぶ。
7. **次に使う機能・共有する状態**。他の流れへの接点を明示し、局所の成功を全体の成功として扱わない。
8. **決める必要がある点**。未合意事項がなければ、その旨と根拠を記す。根拠があるのに単に調べていない場合は『要追加確認』とし、ユーザー判断へ転嫁しない。

## 未決事項の整理

複数の流れに同じ判断が現れる場合は、一つの議題へまとめてください。ただし、動機が同じだけで同じ結論を強制しないでください。例えば確認画面を出せないときの扱いは、操作の副作用や既存の同意が違えば、同じ扱いが適切とは限りません。

各議題に、対象の流れ、既存の根拠、まだ決まらない理由、選択肢による具体的な利用上の違いを記載してください。推奨があれば理由つきの調査担当案として区別してください。

議題を増やす前に、既存の決定で解けないかを確認してください。特に次を注意してください。

- 「あらすじが何本あれば正常か」の件数規則を必須にしない。材料量・各階層の字数など既存の約束で期待する結果を表せるかを先に検討する。
- 定数に出典がないだけで、必ずユーザーがその数値を決めるべきとは扱わない。数値が利用体験にどう影響し、どの判断が本当に必要かを示す。
- 文書が古い場合、その文書に合わせて実装を戻すのではなく、後日の決定や現在の仕様との関係を示す。
