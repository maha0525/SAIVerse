## Codex 指摘 5 件 — メティスの裏取りと裁定

### ① [high] create_region の自動入口が ASCII 契約を迂回 — **裏取り済み・直す**

`manager/admin.py` の create_region は `entrance_{region_id}` の Building を直接 `db.add` で作る (L648-661、create_building を通らない)。region_id 自体も自動生成・カスタムとも文字種検証なし。日本語の Region 名で非 ASCII の Building ID が今も生まれる。
**裁定**: 直す。issue の論点 3 (同族点検) を私が「未着手のまま残す」と書いて実際に残した箇所を、Codex が最短距離で突いた。**修正方針**: region_id の自動生成に `_slugify_identifier` + 連番フォールバックを適用し、カスタム region_id にも `_BUILDING_ID_RE` 相当の検証を入れる (entrance_id は region_id 由来なので region 側を塞げば足りる)。日本語 Region 名の回帰テスト追加。

### ② [high] episode 参照の一時失敗で帰属が永久欠落 — **裏取り済み・設計裁定が要る (推奨: fail-open 維持 + WARN 格上げ)**

指摘どおり、`_open_episode_ref` は DB 例外を「開いている出来事なし」と同じ None に畳み、転記は成功として ingested マークまで進む — その行の帰属は再試行されない。
**ただし対抗する設計事情がある**: (a) 転記の本務は知覚の配送で、帰属タグは記録専用の付加。参照失敗で転記を止めると、世界 DB の不調時に**ペルソナがユーザーの言葉を聞けなくなる** (タグ欠け < 会話の沈黙)。(b) `_store_memory` の層0タグ・会話エピソードの開き失敗 (user_conversation_handler) も同じ fail-open の構え — ここだけ fail-closed にすると層0タグの契約が割れる。(c) get_open_episode はキャッシュ持ちで失敗は稀。
**推奨裁定**: fail-open を維持し、例外ログを debug → **WARNING に格上げ**して観測可能にする。fail-closed 化 (参照失敗を `_TranscribeFailed` へ昇格 — 転記機構は再試行設備を持つので実装は安い) を採る場合は「エピソード無し (None 正常)」と「参照失敗」の分離が必須。**最終裁定はまはー / Opus で** — 層0タグ全体の一貫性に関わるため。

### ③ [medium] activity.py の 4 要素アンパック — **裏取り済み・直す (私の見落とし)**

`api/routes/people/activity.py:432` がローカル `_parse_spell_lines` の中で runtime のパーサへ委譲し、**4 要素でアンパック**している。5 要素化で ValueError → L414 の包括 except が握って、ライフビューのスペル詳細が黙って消える。**現に退行している**。
経緯の白状: 最初の族掃きの grep でこのファイルは視界に入っていたが、「ローカル関数を持っている」の一行で対象外と判定し、そのローカル関数の中身 (委譲) を読まなかった。「対象外は結論である。外した理由を検算しろ」の再演。
**修正方針**: 5 要素アンパック (または属性アクセス) へ更新 + 活動 API の回帰テスト (正準形式・quick 形式を含む) を追加。

### ④ [medium] 連番フォールバックの同時作成競合 — **裏取り済み・受容 (記録のみ)**

check-then-insert が非原子なのは事実。ただし (a) 単一ユーザーのローカルアプリで Building 作成は UI 手動操作、(b) 競合時は片方がエラー文字列を受け取り、再試行すれば次の連番で成功する (データ破損なし)、(c) 既存の名前衝突エラーと同型。
**裁定**: 受容し、修正しない (「本番の実害は直す / 手動経路は記録して次へ」の線)。Opus が IntegrityError 捕捉 + 再試行を一行で足せるなら足してよいが、必須としない。

### ⑤ [medium] quick 終端で output_key / state["last"] が空文字 — **裏取り済み・契約の明文化が要る (裁定材料つき)**

指摘の機構は正確。全 quick 終端は `final_continuation=""` を返し、呼び出し側はそれを state の text_key / output_key に入れる。後続ノードが output_key を消費する Playbook では空入力になる。
**設計事情**: continuation に発話本文を入れ直すと、後段 memorize ノードが**同じ本文を二重保存する** (前倒し assistant 記録が既に持っているため)。空文字は重複保存を避ける唯一の値で、intent §3.5 が「空応答 = 正規終端」と選んだ形。会話の主経路 (speak 終端) では実害なし。実害が出るのは「LLM ノード + output_key + 後続の消費ノード」を持つ Playbook で quick を使った場合のみ。
**推奨裁定**: intent §7-1 の残課題として明文化した上で、Opus 消し込みで次のどちらかを選ぶ: (A) output_key を持つノードの quick 終端では発話本文 (text_before + text_after) を continuation に入れ、そのノードの memorize だけ抑止する / (B) 現契約を維持し、head 規約文に「後続処理に本文を渡すノードでは quick を使わない」旨は書かず (プロンプト汚染)、intent の適用範囲外 §3.7 に明記する。**A/B の裁定はまはーへ**。
