## 残課題 (このハンドオフの範囲外、忘れないための記録)

- **ナビの部屋の手動取り込み設計**: 既存 72 行の前に旧 94 件を挿す順序問題。検算バナーが
  毎起動出続けるので、うるさければ優先度を上げる
- **conscious_log の remap 意味論**: リリース版ユーザーでアップグレード前の未読残が
  大きい場合、その分は新着として消化される (既存設計のまま。intent 節に開放点として記載済み)
- 隔離マーカーファイル (`log.json.corrupted_*`) 自体の後始末は不要 (どの機構も参照しなくなった。
  ただし 4/26 事故の法医学的記録として残す)

### まはーの裁定で設計が作り直された

消し込みの報告に対して、まはーが順に指摘した:

1. **「cursor が無かったら全部読む、という既定そのものが問題では」** — F1 を
   「失敗をどう見せるか」の問題として扱っていたのが誤り。取り込みの失敗は
   爆発の口のひとつでしかなく、歯止めは経路ごとでなく値が使われる場所に要る。
2. **「後ろに付ける選択をするユーザーはいない」** — 古い会話の差し込み位置を
   ユーザーに選ばせる案は、実装が楽な方を選択肢の顔で並べていただけ。
3. **「ボタン押したら直るなら、なぜ自動で取り込まない」** — 検算が見つけた
   ものを放置してバナーだけ出す形は却下。
4. **「バナーに遭遇したユーザーはどうすればいいのさ」** — 直せないものを
   毎起動出し続けると全バナーが読み飛ばされ、検算そのものが死ぬ。
5. **「ファイル側を処理すべきだ」** — 確認済みフラグを DB に持つ案は、元を
   放置して元を無視する台帳を増やす形。ファイルを脇へ移せば機構ごと要らない。

### 実装した 5 つ (すべてコミット済み・全体テスト緑)

| # | 内容 |
|---|---|
| 1 | 読んだ位置の記録が無い部屋の既定を 0 (全部未読) → 現在の末尾 (未読なし) へ |
| 2 | 取り込んだ過去ログは 0 未満の seq を持つ。既存行を動かさず時系列どおり前に入る |
| 3 | 毎起動の検算が見つけた漏れを、その場で取り込む |
| 4 | 読めないファイルのバナーに「ファイルを脇へ移す」ボタン (改名して警告を閉じる) |
| 5 | ログとバナーの文面から実装用語を外す |

副産物: 2 の規則により cursor 前進の機構が不要になり、F2 が直した追い越しバグは
構造的に起きなくなった (機構ごと撤去)。3 の途中で「印が残らない部屋を二重取り込み
する」穴を自分で作り、冪等判定を印から message_id の突き合わせへ変えて塞いだ。
