## 1. 実装まで到達した部分 (完了・実機検証待ち)

### 提示が「途中の期間」を黙って落としていた

詳細は [`../issues/chronicle_presentation_gap.md`](../issues/chronicle_presentation_gap.md)。要点:

- `get_episode_context` は予算 (既定2万字) を超えると「昇格閾値を下げて走査ごとやり直す」段を持っていた。2段目以降は粗いレベル優先で選ぶ
- 粗いあらすじを掴むと走査位置が過去へ飛ぶ。**飛び越された範囲は以後どの周回でも候補にならず、警告もログも無しに消える**
- 実測: eris で直近3.7日・一次あらすじ41件、aifi で271日・98件が head から消失。引き金は予算のわずかな超過 (eris 11%・aifi 4.6%) で、超えた瞬間 22,255字→5,901字 (72件→14件) まで落ちる
- 網に掛からなかった理由: 不変条件 §10-4 が「**最古**が落ちない」しか見張っていなかった。**端点の保護は全体の保護ではない**

**直し方**: 走査と圧縮を分離した。

- 走査は「読み残しの最前線」(現在位置以前で end_time が最大の未読ノード) を飛び越えない。昇格制限が穴を強いる場合は制限より穴回避を優先。被覆が部分的に重なるノードを飛び越すときは走査位置をその end_time まで戻す
- 圧縮は読み切ったあと、古い側から「子が全員そろっている親」へ置き換える。**置き換えは被覆範囲を保存する**ので体験が落ちない
- 畳める親が尽きたら超過のまま返して WARNING (削って穴を作らない)
- 旧 ladder (`_PROMOTION_LADDER` / `prefer_coarse`) は撤去

修正後は全ペルソナで「自身も祖先も提示されない一次あらすじ」がゼロ。回帰は `tests/test_episode_context.py::TestNoPresentationGap` (5件)。修正前のコードに同じシナリオを流すと新しい一次あらすじ20件中19件が落ちることを確認済み。

## 2. 見つかった歪み — 束ねの発火条件が提示量を保証していない

### 現状

- **束ねの発火** (`bands.py`): 未束ねの列の**質量**合計が `U × B^k` (一次なら10万字) を超えたら
- **提示の枠** (`context.py`): あらすじの**字数**合計が2万字

この二つを繋ぐのは圧縮率だが、実測で **0.10 〜 1.11 と10倍以上ばらつく**。だから「質量10万字で束ねる」は、あらすじの字数が何字になるかを一切保証しない。

### 数字 (eris 実測、2026-07-26)

未束ねの一次あらすじ50件: 質量 61,495字 / あらすじ字数 13,496字。内訳:

- **LLM 束ね** 23件: 1件あたり 質量2,366字 → 字数245字 (比0.10)
- **恒等圧縮** 27件: 1件あたり 質量**261字** → 字数**290字** (比1.11)

恒等圧縮は覆う量が9分の1なのに、提示枠は LLM 束ねより多く食う。しかも質量をほとんど稼がないので、**束ねの発火点に永久に近づかない**。質量全体の11%しか担っていないのに、提示枠の58%を占めている。

質量10万字 (発火点) まで伸ばしたときのあらすじ字数:

- 本来の姿 (U=1万字級が10件) → 2,458字。枠 (lv1 に使えるのは約15,600字) の16%。余裕
- 今の LLM 束ねだけが並ぶ (42件) → 10,388字。まだ枠内
- **今の比率で恒等圧縮も混ざる (束ね42件+恒等49件) → 24,796字。枠の1.6倍で破綻**

**恒等圧縮を除けば、束ねが発火するまで提示枠は壊れない。** 標準経路の設計は整合していて、壊しているのは例外の方。

### まはーの判断

> イレギュラーを意識して標準のルール作りをすべきではない。イレギュラーにはイレギュラーなりの方法で標準経路に問題が起きないように対処してしかるべき。
>
> (ただし) ユーザーさんがいろいろ操作できる時点であらゆるイレギュラーは起こり得ると思っとくべき。標準のルールに入れないといけないわけじゃないけど、別に入れられるなら入れてもいい。問題は入れることにより無理が出るケースであって、**無理が出ないように設計できるのがベスト**。

なお恒等圧縮だけの問題ではない。**episode を閉じたときに 1001〜9999字で作られる digest** も同じ歪みを持つ (U=1万字に満たないので、質量あたりの提示コストが標準の10倍近い)。

## 3. 質量を導入した理由 (まはーの説明・重要)

> レベル1あらすじ・レベル2あらすじみたいなレベル概念が従来手法だったところ、episode ごとにあらすじを作るとかいろいろと柔軟なやり方を可能にしないといけなくなったがために、処理の際にレベルをそろえにくくなったのが背景にある。例えばエピソードのクローズ時、2000字しかなくてもその episode の digest は作られる。それを今までのレベル1と同じに扱っていいのか、って話だ。だから、**そのチャンクの持つ質量のような概念を導入して、離散的なレベル設定などしなくても平等に取り扱えるようにした**のが質量を参照している理由。

コード側の記述 (handoff D6) は「LLM 出力のブレに依存しない決定論」だが、これは**判定に何を使うかの説明**であって、質量概念を導入した理由そのものではない。

補足事実:

- 判定の時点では子のあらすじ字数は既に確定している (LLM が書き終わった後)。見積もり (`plan_band_overflow`) と実行の一致も保たれる。失われるのは「同じ生ログから作り直したら同じ木ができる」再現性だけ
- **mira と quon は `coverage_chars` を1件も持っていない** (111件・105件とも)。判定は `content長 × 10` の近似で動いている = 既にあらすじ字数から逆算している。eris/air/sophie にも近似で埋めた分がそれぞれ5/5/3件

## 4. 発火をあらすじ字数にすると圧縮回数が発散する (まはーの試算)

**あらすじの字数は階層が上がっても縮まない** (一次も二次も500字前後の固定長)。だから字数だけを基準に切ると、畳んだ結果がまた同じ閾値に届く。何度でも。

まはーの試算 (1メッセージ1000字、2000メッセージ):

- 旧仕様 (質量ベース、レベル3まで) → 圧縮 **3回**
- 字数ベースで「あらすじ + 生ログ9件」を束ね続ける → `1 + (2000-10)/9 ≒` **222回**

**質量が「圧縮回数を有限に保つ」役目を担っていた。** 質量は階層ごとに10倍になるので、有限回で天井に着く。

## 5. 到達した案 — 発火はあらすじ字数、束ねる相手は質量の比率

### ルール

1. **発火**: 未束ねのあらすじの列の**あらすじ字数**合計が閾値 X を超えたら束ねを起こす
2. **束ねる相手の集め方**:
   - 列のいちばん古い1件を候補に入れる
   - 次に古い1件を見て、**候補に加えたとき候補内の質量の最大と最小が10倍以内に収まるか**を確認する
   - 収まるなら加えて繰り返す。収まらないなら加えず、そこまでの候補をまとめて1つのあらすじにする
3. **親の質量 = 子の質量の合計** (保存される性質)

### 具体例

列 (古い順) の質量が `A:300字 B:400字 C:500字 D:2万字 E:3万字` のとき、

- A を候補に (質量 300〜300)
- B を加える → 300〜400、1.3倍 → OK
- C を加える → 300〜500、1.7倍 → OK
- D を加えようとすると 300〜2万で **66倍** → 加えない。ここで終了
- **A・B・C の3件を束ねて1つにする** (質量1,200字)。次回は D から始める

### なぜ比率か (離散的な「階級」を作らない理由)

当初は質量の桁で階級を切り、「同じ階級同士だけ束ねる」案を検討した。だが**階級で線を引くと、線のすぐ両側にいるもの同士が永久に束ねられない** (質量900字と1100字が、桁が違うというだけで相手にならない)。孤立を減らそうとして孤立を作る。

比率で見れば境界で不自然に切れず、かつ「質量20万字の親に261字の小粒を17件足す」(質量が1.02倍にしかならない = 222回の形) は成立しない。まはーが質量を入れた元の狙い——**揃わないものを平等に扱う**——にも、階級を作るより近い。

### この案が同時に満たすもの

- 提示量が確定する (発火があらすじ字数なので)
- 圧縮回数が発散しない (束ねるたび質量が大きく跳ねるので)
- **優先順位を別ロジックで持たなくていい**: 恒等圧縮は質量261字に対し字数290字と効率が最悪なので、恒等圧縮が並ぶ区間ほど早く字数が溜まって発火する。「割に合わないものが先に畳まれる」が自動的に起きる

## 6. 孤立チャンクの回収 (方針は確定・実装未着手)

### 何が起きているか

上位あらすじの時間範囲の**内側**に、後から一次あらすじが生まれることがある (当時編纂され損ねたメッセージが遅れて拾われる)。`bands.py` は上位が覆う範囲の内側のノードを束ね対象から外す (コード内の「壁」) ので、**この孤児は永久に束ねられず列に残り続ける**。

eris の実データ: 4件。short_id 499 (2026-05-26 の出来事・作成は07-22) / 500 (05-27・作成07-22) / 535,536 (07-18・作成07-24)。それぞれ lv2 476 (05-22〜06-12) と lv2 498 (07-10〜07-21) の内側。

### 決まったこと

**孤立チャンクと同じ質量帯まで階層を下りてから合流させ、同じ質量帯同士で束ね直して上まで再生成する。**

手順 (質量20万字のあらすじに、質量数百字の孤立チャンクが挟まっている場合):

1. 質量20万字の親を一段バラす → 質量2万字級が10本 (**この10本は作り直さない**)
2. 孤立チャンクが時系列で入る位置の1本だけ、もう一段バラす → 質量2000字級が10本
3. 孤立チャンクを時系列位置に挿入 → 11本。**ここで初めて質量が同じ帯になる**
4. 11本を束ね直す (LLM 1回)
5. 上の階層を順に作り直す (LLM 1回ずつ)

各段の束ねが全部「質量が近いもの同士」になり、質量はほとんど動かないので**木の形も変わらない**。

**完全伝播する** (上まで全部作り直す)。まはー裁定、理由:

> (上の要約に反映されないと) 掘り返す動機は要約を読んで生まれるのに、要約に載ってないなら掘る理由が生まれない。取りこぼしを構造的には拾ったけど、実質的には届いてない

Claude が挙げた懸念 (①20万字の要約に数百字は影響しない ②あらすじの書き換えはペルソナの記憶の書き換え) への回答:

> ①確かに小さいけど、マジで物による。その恒等圧縮の数回の会話が、当人たちにとってはとても重要ってことだってある。それに、その部分の情報が無いと次以降の文脈がおかしくなってる可能性もある
>
> ②そもそもあらすじを編纂してるのが自動処理だってことを思い出してほしい。書き換えなかったら欠落が生まれる。**欠落がある状態って、それはそれで本人の記憶じゃない。一部嘘になってる**。じゃあそれを書き替えることってのは改竄じゃなくて、**治療**だと思う

**合流先は孤立チャンクの前ではなく後ろのあらすじ** (欠落が壊すのは後続の文脈だから、後ろに入れる方が治療として効く位置に入る)。

**コスト**: アップデートのタイミングでしか発生せず、親子関係はせいぜい5層。孤立チャンクごとに5コール程度、コンテキストもペルソナ会話ほど長くない。十分ペイする。

### 残る代償

治療で巻き込まれた既存のあらすじは**1回余分に圧縮を通る**。回数が有限であることは崩れないが、「取りこぼしを1件回収するために周辺の記憶を一段劣化させる」トレードオフは存在する。孤立チャンクが頻繁に出るなら効いてくるので、**そもそも孤立チャンクを作らない**方が上位の対策。

## 7. Memopedia Fragment の抽出タイミング (原則確定・実装に穴)

### 原則

**生ログが要約に置き換わる瞬間に、一度だけ抽出する。**

「見えている」とは**生ログが見えていること**を指す。あらすじが提示に出ているのは「見えている」に数えない (それを数えたら何も見えなくならない)。見えている間はペルソナが直接読めるので、Memopedia に入れる需要がない。Memopedia は**見えなくなったものへの入口**。

### 現状の実装

- **走る**: 一次あらすじ生成時の LLM 束ね (`CHUNK_LLM_BATCH`) / episode 転写 (`CHUNK_EPISODE_DIGEST`)。自動 Metabolism (`session_lifecycle.py:1872`) でも API 経由でも `batch_callback` が渡っている
- **走らない**:
  - **恒等圧縮** (`CHUNK_IDENTITY`) — コメントの理由は「被覆が小さく抽出 LLM コストに見合わないためスキップ (W4 D4 裁定)」。**恒等圧縮は生ログのままなので、この時点で走らないこと自体は原則に照らして正しい**
  - **`run_band_overflow`** (二次あらすじ以上を作るとき) — 抽出コールバックを受け取る口自体が無い

### 穴

**恒等圧縮が初めて要約に変わる瞬間**——上位に束ねられるときと、孤立チャンクとして合流するとき——に抽出が走らない。その内容は Memopedia に永久に入らない。

なお W4 D4 の裁定理由「被覆が小さいから見合わない」は、まはーが今回否定した論理と同型 (**量を価値の代理にしている**)。

### Fragment 重複を避ける形

- リンクは実在する: `memopedia_fragments.chronicle_entry_id`
- 治療で上位のあらすじを作り直すとき、**そこからは抽出を走らせない**。上位が覆う範囲は既に抽出済みで、新しく足されるのは孤立チャンクの内容だけだから
- 抽出は孤立チャンク側 (= 生ログが初めて要約に変わる側) でだけ走らせる。これなら既存 Fragment に触らないので参照も切れず、追記専用の不変条件も破らない

## 8. 決まっていないこと

1. **発火閾値 X の具体値** — 「未束ねのあらすじ字数合計が何字を超えたら束ねるか」。実測の目安: eris の一次あらすじ列が 13,496字 で突出、他ペルソナは 1,363〜5,187字。5,000字前後に置くと eris だけ発火して他は影響を受けない
2. **比率の閾値** — 10倍と置いたが根拠は薄い。質量の階層が B=10 なので合わせただけ
3. **提示の粒度に質量をどう使うか** — 現在の提示は `MIN_ENTRIES_PER_LEVEL` (離散のレベルを1段ずつ) で粒度を制御している。「遡りながら累積質量を数え、次に選ぶノードに求める質量の下限を累積の1/10に置く」案を出したが未検証。**まはーは実例を見ないと判断できないと保留した**
4. **恒等圧縮ばかりが束ねられたときの挙動** — 質量261字×17件を束ねても質量4,437字にしかならず、標準の一次あらすじ (質量1万字) に追いつくまで数回余分に畳まれる。発散はしないが、もともと情報の薄い生ログに余分な要約が重なる
5. **恒等圧縮そのものを減らす方** — [`chronicle_eviction.md`](../intent/chronicle_eviction.md) の「最後の手段として U 未満も畳む」との関係。上流で潰す方が本筋という認識は共有できているが、あの裁定 (anchor が永久に止まる方が重篤) との折り合いは未検討
6. **不変条件との整合** — 記憶アーキ v2 §10-5「Fragment は追記専用・ID 不変・物理削除しない (ページ削除カスケードを除く)」と、治療によるあらすじ本文の書き換えの関係。治療は id を保ったまま content を更新する形が意味に合うが、そうすると Fragment を消す根拠が無くなる (§7 の「治療側では抽出を走らせない」でひとまず回避できている)
7. **上段 (二次以上のあらすじ) の偽の隣接** — [`chronicle_eviction.md`](../intent/chronicle_eviction.md) §8 の既知の未解決。束ねの連続判定が上の次数の壁しか見ないため、まだあらすじになっていない生ログの期間を跨いで前後が同じ二次あらすじに束ねられうる (§4-5 違反)。本セッションでは触れていない
