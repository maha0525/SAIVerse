## 2. 未解決A（本丸）— 生ログの切れ目を飛び越えて級2が作られる

### 何が起きるか

窓の先頭が畳めない状態（U 未満の open な会話が先頭にいる等）だと、こういう並びになる:

```
[古い期間のあらすじ(級1)] … [anchor] [生ログ A] [畳んだ範囲(級1)] [保護帯の生ログ]
                                       ↑ここだけ、まだあらすじが存在しない
```

級2への束ね（`sai_memory/arasuji/bands.py` の `_select_bundle_run`）が「連続かどうか」を判定する材料は、**上位級ノードが覆っている時間範囲（＝壁、`_walls`）だけ**。壁で列を切る以外は、時系列で隣り合っていれば連続扱いする。

**まだあらすじになっていない生ログの期間は、壁にならない。**

だから「A より古いあらすじ」と「A より新しい、畳んだ範囲のあらすじ」が連続とみなされ、**A を飛び越えて同じ級2に束ねられ得る**。A はまだ生ログで、どのあらすじにも存在しないのに、その前後が一つの粗いあらすじの中で地続きに語られる。

これは experience_structure §4-5「非連続な範囲を一つの digest に束ねない（偽の隣接 = 時系列の嘘）」の違反。

### なぜ今まで起きなかったか

**今回の変更が前提を壊した。** 従来は退場が時系列の一本線で、anchor より古いものは必ず全部あらすじになっていた。「あらすじの列の途中に生ログの切れ目が空く」状態を作れなかったので、壁だけ見る連続判定で足りていた。窓の途中を畳めるようにしたことで、この状態が初めて生まれた。束ね側はその前提で書かれていない。

### 派生（同じ根の、より軽い方）

畳んだ範囲のあらすじは、head の「これまでの出来事」枠から抑止している（同じ話が窓と head に二回出るのを防ぐため）。抑止の書き方が**あらすじの ID を名指しする**形なので、そのあらすじが級2に束ねられると名指しが効かず、級2が head に出て二重化する。

**確認済みの事実**: 級1は束ねられても消えない（`is_consolidated=1` + `parent_id` が付くだけ、`mark_consolidated`）。head の選択処理（`sai_memory/arasuji/context.py` の `_traverse_episode`）は「古い話ほど粗く」の方針で級2を優先して拾う。

**未測定**: 畳んだ範囲が束ねの順番（古い端から）まで生き延びるか。ここは実データを見ないと言えない。

### さらに歪みの指摘（設計として）

畳んだ範囲のあらすじは、**head の枠には出していないのに、級1の帯の一員としては数えられて束ねの圧力に加担している**。「提示していないのに帯を圧迫する」状態。まだ提示面にいるものを上の段へ畳むのは experience_structure §4-1「圧縮は提示面から退場する瞬間に行う」とも噛み合わない。

**畳んだ範囲を帯の勘定にどう置くか（数えるのか、いつ上へ畳むのか）を一切決めていない。** ここが未設計の中心。

## 3. 未解決B — 畳んだ記録が、更新頻度の違う二箇所で共有されている

### 何が起きるか

畳んだ範囲の記録は 2 箇所で使われる。

| 使う場所 | 更新タイミング |
|---|---|
| 窓（提示の本体） | 毎回 DB から読む → **常に最新** |
| head の「これまでの出来事」枠の抑止 | 節目で凍結 → **そのときの値が固まる** |

キャッシュ寿命（20分〜1時間）が切れると `runtime_context.py` の Case 3 に落ちる。そのときの順序:

1. anchor 無効と判定
2. 最小ロードで生ログを低水位ぶん読む ← **畳んだ範囲の置き換えは掛からない**（`apply_window_folds` は anchor 経路でのみ呼ばれる）
3. head を作り直す（`ensure_snapshot` は TTL 超過で `capture_all`）← **このとき、まだ消えていない古い記録を読んで抑止リストを焼き付ける**
4. LLM 呼び出し
5. 成功 → `touch_anchor_after_llm_call` → `update_anchor_for_model` → 新 anchor 書き込み → **ここで初めて記録がクリアされる**

**3 で焼き付けた抑止リストは、5 のクリア後も head に残る**（head の再構築は次の節目まで）。

畳んだ範囲が最小ロードの外（もっと古い側）にあると、その1回の呼び出しで:

- **窓に出ない**（最小ロードの範囲外）
- **head にも出ない**（3 で焼き付けた抑止が生きている）

= その体験が次の節目までどこにも現れない。

### 経緯（重要）

これはレビュー二巡目で見つけた P2-A「anchor が退場経路の外で動くと古い記録が残る」への対処として、`upsert_anchor_entry` で anchor 変更時に記録をクリアする処理を入れた**その結果**。DB 側だけ直して head の凍結側を触っていないので、**クリアという操作自体が二箇所のズレを作る側に働いている**。

まはーの警戒（「この処理が存在してると他の経路を綿密に作っていても丸ごと壊れる可能性」）は当たっている。

### 方向の候補（未決 — 案出しから）

- head 側で畳んだ範囲を参照するのをやめる（抑止を head 以外の場所で実現する）
- 窓と head の同期点を一つにする

どちらも設計判断が要る。即決していない。

## 5. 用語の作り直し（まはー明示指示、実装より先）

**「穴」「級」「窓」— この 3 つを次の実装前に直す。** まはーの指摘: 短い常用漢字を用語に使うと一般語と区別がつかず、地の文で用語かどうか判別できない。説明が分かりにくい原因の一端になっている。

さらに私は説明の中で「穴を塞ぐ / 穴が開く」という比喩まで使い、用語の「穴」と衝突させた。**比喩でも使えない語を用語にしてはいけない**という実例。

| 現行 | 意味 | 実装上の名前 |
|---|---|---|
| 穴 | 提示の途中で digest に置き換えた範囲 | `FoldedRange` / `folded_ranges` |
| 級 | あらすじの粗さの段階 | `level` |
| 窓 | 提示コンテキスト（anchor 以降） | `SessionWindow` / 既存概念の `Session` と重なる |

規律は [[feedback_no_short_common_kanji_as_term]]（固有語・カタカナ・固有性の出る複合語に。まず用語化が要るか疑い、定義済み固有語で足りるならそれが最善）。**改名はまはーが決める** — 候補出しはするが、勝手に確定しない。ドキュメント・コード・コメントの一括置換になるので、決まってから一気にやる。
