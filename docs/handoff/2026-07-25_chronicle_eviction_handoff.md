## 2. 未解決A（本丸）— 生ログの切れ目を飛び越えて二次あらすじが作られる

### 何が起きるか

提示コンテキストの先頭が畳めない状態（U 未満の open な会話が先頭にいる等）だと、こういう並びになる:

```
[古い期間のあらすじ(一次あらすじ)] … [anchor] [生ログ A] [圧縮区間(一次あらすじ)] [保護範囲の生ログ]
                                       ↑ここだけ、まだあらすじが存在しない
```

二次あらすじへの束ね（`sai_memory/arasuji/bands.py` の `_select_bundle_run`）が「連続かどうか」を判定する材料は、**上の次数ノードが覆っている時間範囲（＝壁、`_walls`）だけ**。壁で列を切る以外は、時系列で隣り合っていれば連続扱いする。

**まだあらすじになっていない生ログの期間は、壁にならない。**

だから「A より古いあらすじ」と「A より新しい、圧縮区間のあらすじ」が連続とみなされ、**A を飛び越えて同じ二次あらすじに束ねられ得る**。A はまだ生ログで、どのあらすじにも存在しないのに、その前後が一つの粗いあらすじの中で地続きに語られる。

これは experience_structure §4-5「非連続な範囲を一つの digest に束ねない（偽の隣接 = 時系列の嘘）」の違反。

### なぜ今まで起きなかったか

**今回の変更が前提を壊した。** 従来は退場が時系列の一本線で、anchor より古いものは必ず全部あらすじになっていた。「あらすじの列の途中に生ログの切れ目が空く」状態を作れなかったので、壁だけ見る連続判定で足りていた。提示コンテキストの途中を畳めるようにしたことで、この状態が初めて生まれた。束ね側はその前提で書かれていない。

### 派生（同じ根の、より軽い方）

圧縮区間のあらすじは、head の「これまでの出来事」枠から抑止している（同じ話が提示コンテキストと head に二回出るのを防ぐため）。抑止の書き方が**あらすじの ID を名指しする**形なので、そのあらすじが二次あらすじに束ねられると名指しが効かず、二次あらすじが head に出て二重化する。

**確認済みの事実**: 一次あらすじは束ねられても消えない（`is_consolidated=1` + `parent_id` が付くだけ、`mark_consolidated`）。head の選択処理（`sai_memory/arasuji/context.py` の `_traverse_episode`）は「古い話ほど粗く」の方針で二次あらすじを優先して拾う。

**未測定**: 圧縮区間が束ねの順番（古い端から）まで生き延びるか。ここは実データを見ないと言えない。

> **2026-07-25 追記・訂正**: このメモが書いた「置き換えは再圧縮しない壁なので、圧縮区間を上へ畳む道が無い」は**誤読だった**。experience_structure §4-4 の禁止は「同一レベル」限定で、上の次数への束ねは禁止の例外どころかその機構の本体。圧縮区間の一次あらすじは未束ねのまま一次あらすじの列にいるので、通常の列のあふれで二次あらすじへ束ねられる。壊れているのは提示側が一次あらすじの id を名指しで握っていることで、下の派生（head 抑止が外れる）と同根。§4-4 の本文はこの限定が落ちていたので正典側を修正済み。詳細は intent §8-③。

### さらに歪みの指摘（設計として）

圧縮区間のあらすじは、**head の枠には出していないのに、一次あらすじの列の一員としては数えられて束ねの圧力に加担している**。「提示していないのに列の上限を圧迫する」状態。まだ提示コンテキストにいるものを上の段へ畳むのは experience_structure §4-1「圧縮は提示コンテキストから退場する瞬間に行う」とも噛み合わない。

**圧縮区間を列の上限の勘定にどう置くか（数えるのか、いつ上へ畳むのか）を一切決めていない。** ここが未設計の中心。

## 3. 未解決B — 畳んだ記録が、更新頻度の違う二箇所で共有されている

### 何が起きるか

圧縮区間の記録は 2 箇所で使われる。

| 使う場所 | 更新タイミング |
|---|---|
| 提示コンテキスト（提示の本体） | 毎回 DB から読む → **常に最新** |
| head の「これまでの出来事」枠の抑止 | 節目で凍結 → **そのときの値が固まる** |

キャッシュ寿命（20分〜1時間）が切れると `runtime_context.py` の Case 3 に落ちる。そのときの順序:

1. anchor 無効と判定
2. 最小ロードで生ログを低水位ぶん読む ← **圧縮区間の置き換えは掛からない**（`apply_window_folds` は anchor 経路でのみ呼ばれる）
3. head を作り直す（`ensure_snapshot` は TTL 超過で `capture_all`）← **このとき、まだ消えていない古い記録を読んで抑止リストを焼き付ける**
4. LLM 呼び出し
5. 成功 → `touch_anchor_after_llm_call` → `update_anchor_for_model` → 新 anchor 書き込み → **ここで初めて記録がクリアされる**

**3 で焼き付けた抑止リストは、5 のクリア後も head に残る**（head の再構築は次の節目まで）。

圧縮区間が最小ロードの外（もっと古い側）にあると、その1回の呼び出しで:

- **提示コンテキストに出ない**（最小ロードの範囲外）
- **head にも出ない**（3 で焼き付けた抑止が生きている）

= その体験が次の節目までどこにも現れない。

### 経緯（重要）

これはレビュー二巡目で見つけた P2-A「anchor が退場経路の外で動くと古い記録が残る」への対処として、`upsert_anchor_entry` で anchor 変更時に記録をクリアする処理を入れた**その結果**。DB 側だけ直して head の凍結側を触っていないので、**クリアという操作自体が二箇所のズレを作る側に働いている**。

まはーの警戒（「この処理が存在してると他の経路を綿密に作っていても丸ごと壊れる可能性」）は当たっている。

### 方向の候補（未決 — 案出しから）

- head 側で圧縮区間を参照するのをやめる（抑止を head 以外の場所で実現する）
- 提示コンテキストと head の同期点を一つにする

どちらも設計判断が要る。即決していない。

## 5. 用語の作り直し（2026-07-25 まはー裁定 → 置換実施済み）

短い常用漢字を用語にすると一般語と区別がつかず、地の文で用語かどうか判別できない — まはーの指摘で 4 語を作り直した。私は説明の中で「穴を塞ぐ / 穴が開く」という比喩まで使い、用語の「穴」と衝突させていた。**比喩でも使えない語を用語にしてはいけない**という実例。

| 旧 | 新 | 意味 | 実装上の名前 |
|---|---|---|---|
| 穴 | **圧縮区間** | 提示の途中で digest に置き換えた範囲 | `FoldedRange` / `folded_ranges` |
| 級 | **一次あらすじ / 二次あらすじ**（軸を呼ぶときは「次数」） | あらすじの粗さの段。一段上がると覆う量が 10 倍 | `level` — **改名しない** (Chronicle の metadata キーとして DB に入っている値で、触るのは改名でなくマイグレーション) |
| 窓 | **提示コンテキスト** | anchor 以降の、実際に提示している並び | `SessionWindow` |
| 帯 | **用語を廃止** →「一次あらすじの列」＋「上限」 | 同じ次数のあらすじのうち、まだ上へ束ねられていないものの列 | `bands.py` (モジュール名は据え置き) |

**帯を用語化しない理由が一番重い**: 名前を与えると「それがあって当然の確定した概念だ」という主張が載る。この機構は今後変わりうるので、名前で確定を演出してはいけない（まはー裁定 → [[feedback_naming_asserts_concept_is_settled]]）。私は当初「編纂待ち列」を提案したが自分で取り下げた — 列のあらすじは順番を待っているのではなく head に出て現役で働いているので、待ち行列の語感は状態を誤らせる。

**却下された候補と理由**: 縮尺（数字が上がると粗いのが通常の縮尺と逆で座りが悪い）/ 粗さ（常用語そのもの — 自分の規律違反）/ 被覆桁（意味が届かない）/ 提示面（「面」が何か分からない。既存の定義語だったが、既存だから正しいとは限らない）。

**副産物**: `保護帯` / `退場候補帯` は Chronicle の帯とは無関係な別概念が同じ字を共有していたので、`保護範囲` / `退場候補範囲` に分けた。`同窓即時再試行`・`深夜帯コマ`・`帯域`・`窓プレビュー`・`周辺窓`・`窓集計新聞`・`幾何級数`・`提示面積` は別概念なので置換から除外している。

規律は [[feedback_no_short_common_kanji_as_term]] / [[feedback_naming_asserts_concept_is_settled]]。
