# Opus への追加調査: ペルソナ削除後の再利用と無効化・再有効化

## 今回判断したいこと

正常化の相談で、Astra は「ペルソナを削除するとき、活動を終え、記憶を残すか一緒に消すか利用者が選ぶ」と提案した。まはーは方向性を評価したが、残した memory.db を後から実際に使えるかを疑問視した。「新規ペルソナを作って memory.db だけ差し替えれば動くか」「それが確かでなければ、完全削除か無効化・再有効化の選択の方が軽いのでは」と指摘した。

この判断に必要な成立性を調べる。全体棚卸しの再実行や、製品の実装変更は行わない。

## 入力と既知の範囲

- `docs/audits/2026-09-09_product_normal_behavior/flows/D_persona.md` FLOW-23 と `flows/B_memory.md` FLOW-13。
- 同ディレクトリの `owner_decisions.md`。削除の具体仕様は未決。自律 OFF でもアラームは動くという判断は確定済み。
- `docs/issues/persona_memory_not_self_contained.md`。古い表・概念を含むので、現行の保存先の証拠としてそのまま転記しない。
- `api/routes/people/native_export_import.py` は JSON の復元／移植 API を持つ。`saiverse_memory/native_export.py` の移植処理は persona を含む ID を写像する。これだけで DB 差し替えの可否や全体復元を断定しない。

## 調べる三つの経路

1. **記憶を残して削除し、後で再利用する**: memory.db の直接差し替え、既存 JSON エクスポート／移植のそれぞれで何が戻り、何が戻らないか。同じ ID への復元と別 ID への移植を区別する。削除後の状態から、利用者が辿れる取り出し・取り込み経路が実在するか。会話本文だけでなく Chronicle、Memopedia、コア記憶、添付参照、現在の会話スレッド等の読まれる場所を必要な範囲で追う。本人設定や main DB の状態を含めた再開と、過去ログの再利用を混同しない。
2. **データを保持して無効化し、同じペルソナを再有効化する**: 現行の停止・除外の仕組みでどこまでできるか。起動時ロード、会話応答、アラーム、自律、外部イベントや連携、処理中・待機中の要求から活動が再開しない条件を追う。再有効化で何を再登録するか、停止中の予定・イベントの扱いで判断が必要な箇所を挙げる。フラグを一つ増やせば成立すると仮定しない。
3. **完全削除する**: ペルソナに属する現在のデータと、共有の会話履歴等に残る記録を区別し、何を消す意味にするかを具体化する。残った要求が実行される問題をどう解消できるか。共有記録を連鎖削除する案を無断で採用しない。

## 証拠と制約

適用されるリポジトリ規約を読む。本番起動・本番ペルソナへの接触・実データの差し替え・外部投稿・有料 LLM 呼び出しは禁止。既存の Claude 作業を壊す Git 操作も行わない。

静的追跡だけでは差し替えや移植の可否を判定できない部分は、隔離 SAIVERSE_HOME、合成人格・合成記憶、fake/no-LLM の小さな再現で確認する。実ペルソナのコピーを fixture にしない。実験用コードと報告以外の製品変更はしない。確認できない部分は未検証として残す。

## 成果物

`docs/audits/2026-09-10_persona_removal_recovery/README.md` に、次をまとめる。必要な場合だけ証拠用ファイルを分ける。

- 冒頭に「今 memory.db だけ差し替えて使えるか」への直接の回答と証拠の範囲。
- 三経路の比較: 利用者の操作 → 残るもの → 後でできること → 必要な変更 → 未確定事項。既存機能と追加実装を明記。
- 実験の入力・操作・観測結果と再現方法。保存できたことだけで、再開して読めることまで検証済みにしない。
- 推奨する具体的な削除画面の選択肢を一案。現在の構造を踏まえた理由を示し、まはーに残る判断を絞る。

この報告で Astra とまはーが方式を選び、その後に選んだ方式の実装・検証を依頼できる状態を目標とする。
