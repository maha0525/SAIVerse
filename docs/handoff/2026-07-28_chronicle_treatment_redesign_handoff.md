## 2. 診断 — なぜ ch:504/505 は動かなかったか

当該箇所の列 (数値は `coverage_chars` = そのあらすじが被覆する生ログの字数):

```
[6344] [381] [831] [3042] [130] ...
        ^^^^^ ^^^^^ ch:504 / ch:505
```

旧実装の治療は**群と群の間でしか候補を探していなかった** (`_plan_actions` が `runs` を単位に、`次の run の先頭` を合流先にする形)。

- `381 / 831 / 3042` は比率 10 倍以内なので**同じ群の内側**に収まる
- その群は卒業条件に届かない (`381+831+3042 = 4,254 < 5 × 3,042 = 15,210`)
- 治療は「隣が自分より重いか」を**群の最大メンバー (3,042)** で判定する。隣の群は 130 で軽い → 発火しない

結果、**束ねからも治療からも落ちて永久に残る**。これは「順番待ち」ではなく**構造的な詰まり**だった (前任は最初にまはーへ「次の順番です」と誤って説明した。訂正済み)。

**まはーの指摘 (これが再設計の起点)**: 「そもそもなんで治療に関して群を作用させる必要があるんだ」。

治療は設計上**比率免除**の操作 (`bands.py` の docstring)。にもかかわらず、その比率で引いた区切り (群) を土台にしていた。**免除する前提のルールで引いた線の上に立っていた**のが病巣。

## 4. 本題 — 二つの要求が正面から衝突している

Codex 3 巡の指摘を突き詰めると、治療のアクション構築には**同時に満たせない 2 つの要求**がある。

| | 要求 | 破ったときに起きること |
|---|---|---|
| **R1** | 1 回の合流を小さく保つ | 大量の記憶が一本の要約に潰れる (不可逆) |
| **R2** | 同じ記憶を何度も要約し直さない | 通るたびに劣化する。intent §5-1 の「治療は束ね不能 1 件につき 1 回きり」= 有限性の根拠が壊れる |

**なぜ衝突するか**: ひとつの重いノード (合流先) の周りに軽い欠片が複数集まっているとき、

- 小さく区切る (R1 優先) → 残った欠片が次回また同じ合流先へ寄る → **同じ親が何度も再要約される** (R2 違反)
- まとめて閉じる (R2 優先) → 合流先の周りの欠片を全部飲む → **列全体を 1 アクションが飲む形**が作れる (R1 違反)

前任の 3 巡は、この 2 つの間を往復していただけだった。実測でも両極が出ている:

- R1 側の失敗: エリス実データで **5 日ぶん 58 件が 1 アクション**に化けた (2 回、別の原因で)
- R2 側の失敗: `[16000, 8000, 8000, 8000, 8000, 50]` (U=10,000) で同じ記憶が **4 回連続で再要約**された

**まはーに決めてもらう必要がある分岐**。前任の推しは R1 優先 (再要約の劣化は 1 回ぶんずつだが、大量の記憶を一本に潰すのは取り返しがつかない) だが、その場合「何回まで通してよいか」の線を別に引く必要がある。

## 5. Codex 攻撃レビューの経過

3 巡すべて `adversarial-review --wait --scope working-tree` (companion 1.0.6)。

### 1 巡目 — no-ship (2 件、いずれも修正済み)

1. **[high] 一時的な excluded 境界が卒業可能ノードを束ね不能と誤判定** — 「凍っている」の判定を**場所の種類**で書いていた (最新端だけ)。隣人が後から生まれる場所は 3 つある: 列の最新端 / 未編纂の生ログ (gap) が編纂される位置 / 提示中の圧縮区間 (excluded) が戻る位置。実測で `[4000,3000,4000,4000] + excluded [4000×5]` が、全件可視なら 9 件の正規束ねになるのに除外中は 2 件の治療に化けた
2. **[medium] 存在判定が O(n³)** — 同質量の列で 1,600 件 6 秒。start ごとに「卒業が成立した最遠 end」だけを持ち、前方最大値で一度に展開する形へ (O(n))。**この修正は 2 巡目・3 巡目とも「元の集合と一致・反例なし」で維持可**

### 2 巡目 — no-ship (2 件、いずれも修正したが 3 巡目で別の穴として再発)

1. **[high] 治療親が合流先として繰り返し再要約される** (上記 R2)
2. **[high] excluded/gap の先頭側でも正規窓を先食い** — 前任は「治療は新しい側へ寄せる操作だから先頭群は競合しない」と非対称を正当化したが、Codex に「後付けではないか」と突かれ、**その通りだった**。合流の向きに関係なく**ノード自身が consolidated になる**ので、戻ってきた隣人との将来の正規束ねは同じように失われる

### 3 巡目 — no-ship (**3 件すべて未解決**)

1. **[high] 凍結した端群が合流先として治療に巻き込まれる** (`bands.py:719-743`)
   `frozen_lo` / `frozen_end` は端の群を**候補走査から**外すだけで、**内側のノードの `_treatment_target` が端群を返すこと**を禁止していない。`[excluded 1600×4, 1600, 100, 1]` (U=10,000) が `treatment [1600,100]` を計画した。excluded が戻れば `1600×5` で正規卒業できたはずの端ノードが先に確定する。末尾側も同型。
   → **推奨**: 治療のエッジと `action.items` の**両方**が凍結範囲へ入らないよう制約する

2. **[high] 単調増加列は閉包ガードの前に全体が 1 アクション化する** (`bands.py:738-751`)
   各候補が新しい側の重い隣を選ぶと `linked` が全隣接辺を持ち、**連結成分走査だけで列全体を消費する**。その後の「次が自分の新しい隣へ寄れるなら打ち切り」ガードは、**既に連結された部分には適用されない**。`[10,13,17,...,7728,9738,1]` (U=10,000) で先頭 30 ノードが 1 件の治療になった。
   → **推奨**: 初期 `linked` 成分にも最大子数または最大被覆量の強制上限を設け、上限到達後は分割する

3. **[high] 新しい側へ合流した治療親が次回もう一度治療される** (`bands.py:749-780`)
   閉包が `j+1` 方向にしか伸びないため、合流先が新しい側にある成分の**古い側**に残ったノードを閉じられない。`[100,100,1600,50]` (U=10,000) で 1 回目 `[2 番目の 100, 1600] → 1700`、2 回目 `[先頭 100, 1700] → 1800`。
   → **推奨**: 予測親の**両側**について、隣接ノードが次回その親へ寄るかを固定点まで評価する**双方向閉包**にする

**Codex の Next steps**: 3 反例を回帰テストとして固定 / 凍結範囲を action 構築後にも検証 / 治療アクションへ強制サイズ上限と双方向固定点閉包を導入

## 9. 再開する人へ — 踏まないでほしい轍

前任がこのセッションで**同じ型を 5 回**踏んだ。すべて「**歯止めの条件を目的から導かず、種類 (カテゴリ・構造の形) で書いた**」もの。

1. 治療の発火条件を「群と群の間」という構造の形で書いた → 群の内側に手が届かない (§2)
2. 「凍っている」を「列の最新端」という場所の種類で書いた → gap / excluded の境界を取りこぼす (§5 一巡目)
3. 境界の凍結を末尾だけにして、非対称を後付けで正当化した (§5 二巡目)
4. 先頭側の凍結を「区間の番号 (`seg_no > 0`)」で書いた → 列の先頭の excluded は区間を増やさないので検出できない (自分で気づいて `leading_boundary` へ)
5. 閉包の伸長を「合流後の質量 > 次」だけで書いた → 次のノードが本来どこへ寄りたいかを見ていない (§5 三巡目 -2)

**判定**: 書こうとしている条件が「どういう種類のものか」で書かれていたら止まる。「**その条件は何を達成するためにあるのか**」から導き直す。CLAUDE.md の「Reasoning at whole-system scope」と memory の `feedback_guard_conditions_from_purpose_not_category` が同じことを言っている。

もう一点。**dry 実行を実データに当てて目視すること**を毎回やること。前任が §4 の衝突に気づけたのは、ユニットテストが緑のまま実データで「58 件が 1 アクション」が出たから。合成テストだけでは形が貧しすぎて出ない。
