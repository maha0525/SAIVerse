**目的**: まはーが「今の実装が正しい形か」を点検できるように、**コードが実際にやっていること**を処理の順で書き起こしたもの。設計文書 (intent) の引き写しではなく、このセッションでコードを読んで確認した内容。過去の裁定も疑う前提で、誰が決めたかは書かず「何が起きるか」だけを書く。

## 0. 全体の地図 — 4つの工程

会話ログは、次の4つの工程を順に通って「記憶」になる。

1. **退場** — 会話が長くなったら、提示中の会話ログから古い範囲を選んで外す
2. **編纂** — 外した範囲を「一次あらすじ」(要約1本) にする
3. **束ね** — 溜まった一次あらすじたちを、さらに上位のあらすじへ統合する (行き詰まったものの救済 = 治療もここ)
4. **提示** — ペルソナのシステムプロンプトの Chronicle 枠に、全歴史のあらすじを予算内で並べる

1〜3 は「Metabolism」と呼ばれる一連の処理の中で続けて走る。4 は毎回の会話の組み立て時に走る。

---

## 1. いつ動くか (Metabolism の入口)

### 1-1. 毎回の応答後 (主経路)

ペルソナが応答するたびに発火チェックが走る。次の**どれか**が成立したら Metabolism 実行:

- 直前の LLM 呼び出しがトークン閾値を超えた
- 前回「キャッシュが冷たいから」と繰り延べた印が残っている
- 提示中の会話ログの文字数が**高水位**を超えた

ただし、文字数が既に**目標水位**以下なら何もしない。

**繰り延べの仕組み** (gold_panning 連動): 発火してもキャッシュが冷たければ次回へ繰り延べる。ただし文字数が「高水位 × 上限倍率」を超えたら、冷たくても強行する (圧力弁、WARNING が出る)。

### 1-2. 入口は全部で5つ

編纂の実行はすべて 1 つの関数 (`generate_chronicle`) に合流する。コードのその合流点に、入口が5つ列挙されている:

1. 応答後の Metabolism (上記)
2. 会話前のアンカー失効 (提示の起点に記録されたキャッシュ寿命が切れていたとき)
3. 手動の「記憶の整理」ボタン (確認なしの force 実行)
4. セッションクローズ時 (force 実行)
5. gold_panning の中からの前倒し実行

二重実行の防止は「Beat ロック」(ペルソナ単位の排他) と「実行台帳」(同じ範囲の編纂を一度しか走らせない記録) の二段。

## 2. 退場 — 提示から外す範囲を決める (`sea/eviction_plan.py`)

### 2-1. 三水位

文字数の線が3本ある: **低水位** = 最新からこの文字数ぶんは絶対に外さない (保護範囲)。**目標水位** = ここまで軽くしたら終わり。**高水位** = これを超えたら発火。保護範囲の境界が会話のひとまとまり (Pulse) の途中に落ちる場合は、**保護を広げる側**にずらす。

### 2-2. 畳む単位はエピソード

外す範囲 (畳む範囲) は、メッセージの「エピソード帰属」で切る:

- **開いているエピソード** (まだ進行中の出来事) は単独で畳む。他と混ぜない
- **閉じたエピソード同士**と**どのエピソードにも属さないメッセージ**は、またいで一緒に畳んでよい
- 既に畳んだ範囲 (置き換え表示) は壁。壁をまたいだ束ねはしない

1つの畳み範囲は **U = 10,000字** (一次あらすじの標準被覆) に達したら確定。目標水位に届くまで古い側から繰り返す。

### 2-3. 二段構え (最後の手段)

一段目は「U 以上のまとまり」だけを畳む。それで目標に届かないとき、**提示の先頭に居座って起点 (アンカー) の前進を塞いでいる U 未満の端数**を、1回だけ畳む。この経路を通ると `used_last_resort_fold` の印とログが残る (定常運転になっていないか観測するため)。

### 2-4. 適用 — 外した範囲のその後

編纂が終わった後、畳み範囲は2通りの姿になる:

- **提示の先頭から連続して畳まれた分**: 起点が前進して丸ごと飲み込む。以後は head の Chronicle 枠 (工程4) が担当
- **提示の途中の分**: 「圧縮区間」として残り、生ログの代わりにあらすじ本文がその位置に表示される

**あらすじを持てなかった畳み範囲は退場そのものを見送る** (生ログのまま残して次回再挑戦)。例外は2つ — Chronicle を切っているペルソナと、範囲内に編纂対象が1件も無い場合 (どちらも飲み込みだけ許す)。

🔍 **既知の欠け**: 除外タグ (handy_tool / spell / event_message / session_digest) のメッセージは、畳み範囲に入っていても**編纂されずに退場する**。「退場したものは必ず編纂されている」という下限を字義どおりには満たしていない。コードのコメント自身がこれを認めている。

## 3. 編纂 — 外した範囲を一次あらすじにする (`alignment.py` + `executor.py`)

### 3-1. チャンク3種

畳み範囲の中身は、次の3種類の「チャンク」(一次あらすじ1個ぶんの単位) に計画される:

| チャンク種別 | 条件 | 中身 | LLM |
|---|---|---|---|
| エピソード転写 | そのエピソードに確定済みの digest (エピソード自身の要約) がある | digest 本文をそのまま転写 | 呼ばない |
| LLM 束ね | 被覆 1,000字以上 | 3〜5文の要約を生成 | 呼ぶ |
| 恒等転写 | 被覆 1,000字未満で、吸収先も無い | **生ログをそのまま置く** | 呼ばない |

「あらすじの席に生ログが座っている」のは3つ目の恒等転写。あとで束ね (工程4) に入って初めて要約に変わる。

### 3-2. 豆粒はどこで生まれるか 🔍 (2026-07-28 実測で書き直し)

まず前提: 畳む範囲は文字数 (U = 1万字) で切られ、編纂は受け取った範囲を**基本まるごと1本に圧縮する**。だから設計の建て付け上、4字や130字のあらすじは本来出てこないはずで、豆粒の存在自体が約束と挙動の食い違い。

**実測で分かったこと** (エリスの豆粒26個の全数調査):

- 豆粒の元メッセージは全件が**エピソード無帰属**で、全件が**会話の第一声の user 発言かスケジュール起動文** (§7-3b: そもそも user 発言は 4,578 件中 0 件しかエピソードに入っていない)
- 豆粒の隣のあらすじは全件が普通の LLM 要約 (`batch`)。「エピソード転写の写し」は 1 件も無い
- 豆粒と隣のあらすじは、全件**別の回の編纂**で生まれている

3つ目が決定的で、**豆粒は編纂の中で割れたのではない**。会話本体が退場した回に、豆粒になるメッセージは**畳む範囲にそもそも入れてもらえず**提示に残され、後の回に自分だけで畳まれて恒等転写 (生ログのあらすじ) になった — というのが実データの姿。

どの規則が置き去りにしたかは未特定 (ログ遡りが要る)。最有力の候補は退場の「**開いているエピソードは単独で畳む**」規則 — 畳む範囲をエピソード単位で組むとき、エピソードに属さないメッセージ (= user 発言全部、§7-3b) はその範囲に入れない。この筋なら、豆粒の蛇口は §7-3b の「user 発言の無帰属」と同じ一本の穴に繋がる。

なお、編纂側にも範囲を割る規則は実在する (「確定済み digest を持つエピソードは単独で転写、他と混ぜない」+ 端数の吸収先は直前の LLM 束ねチャンクのみ)。ただしエリスの豆粒でこの経路が働いた例は観測されなかった (隣に転写が 1 件も無い)。

### 3-3. 確認ゲートと冪等

- LLM 0回の計画 (全部転写) → 確認なしで即実行
- force (手動ボタン / セッションクローズ) → 確認なし
- 自律 Pulse → ペルソナ設定 `AUTONOMOUS_CHRONICLE_ENABLED` が True なら確認なし、False ならスキップ
- ユーザー Pulse → 確認ダイアログを出して 60 秒待つ (拒否/時間切れは見送り)

実行はチャンク1個 = 1トランザクション。同じ生ログから二度あらすじを作らない検査が LLM 呼び出しの前後に二重にある。

## 4. 束ね — 一次あらすじの列を上位へ (`bands.py`)

### 4-1. 列と発火

未束ねのあらすじ全部を時系列に一列に並べる (質量の違うものが混在する一本の列)。ただし:

- **孤児** (他のあらすじの被覆範囲の内側に生まれたもの) は列から外す。回収機構 (§5-2 の「階層を下りて合流」) は**設計のみで未実装**。現状は放置される
- **提示中の圧縮区間**のあらすじは、数には入れないが列の切れ目としては残す

発火条件: 列のあらすじ本文の合計字数 > **X = 提示予算の 1/4 = 5,000字**。

### 4-2. 束ねる範囲の選び方 🔍

列を「質量の差 10 倍以内で連続する並び」に区切り、その中で次を満たす連続範囲を束ねの候補にする:

- **比率**: 範囲内の質量の最大/最小が 10 倍以内 — 🔍 **豆粒にもこの検査が課される。** 「ぎゅ……」(4字) は隣の要約 (1,000字級) と 280 倍差なので、正規の束ねに永遠に入れない。今日の実測: 比率判定でのみ質量を 1,000字に底上げすると、治療 27 件が 0 件になり全部が正規の束ねに戻った
- **連続性**: 壁 (束ね済みの上位あらすじの範囲) と未編纂の生ログの切れ目をまたがない
- **五段跳びの下限** (intent の用語では「卒業」): まとめた結果の合算質量が、範囲内で一番大きいものの **5 倍以上**になる場合しかまとめてはいけない。目的は「小刻みなまとめ直しの禁止」— まとめるたびに中身は要約し直されて薄れるので、1回のまとめを必ず大跳びにすれば、どの記憶も数回のまとめで天井に着き、要約し直しの回数が数回で頭打ちになる。例: 10万字級の隣に1万字が届くたび「10万+1万=11万」で吸うと同じ記憶が毎回溶ける。5倍下限があると、隣に40万字ぶん積もるまで待って1回で跳ぶ

範囲の伸ばし方は**「5倍下限が成立している最長」まで伸ばす貪欲**。🔍 比率の摩擦がある間は暴走が隠れていたが、豆粒の底上げを入れると一週間ぶん 59 ノードを 1 本に丸呑みした (実測)。止めどころの設計はまはー裁定待ち。

選ばれた範囲は「軽いものから」実行し、最新端の育ち中の範囲は X を守れる限り猶予する。上限は**束ね+治療あわせて 3 LLM コール / 回**。

### 4-3. 実行の形

1回の束ね = 子たちのあらすじ本文をプロンプトに並べて LLM に 1 回投げ、5〜8文の親あらすじを新ノードとして立てる。子は書き換えず、列から退くだけ (子として残る)。**木の中身は開梱しない** — 列に立っている最上部のノード同士を直接合わせる。親の作成と子の退役は単一トランザクション。恒等転写の子が初めて要約に変わる瞬間には、Memopedia Fragment の抽出が走る。

### 4-4. 治療 (再設計中)

正規の束ねに乗れないノードを、比率免除で隣の重い方へ合流させる救済。現状は未コミットの作業ツリーにあり、Codex レビューで 3 つの穴が未解決 (詳細は [2026-07-28 のハンドオフ](2026-07-28_chronicle_treatment_redesign_handoff.md))。🔍 豆粒への比率適用をやめると治療の出番はほぼ消える見込みで、機構ごと縮小する方向で議論中。

### 4-5. 非常弁

発火したのに束ねも治療も 1 件も打てない予見外の形に限り、最古の隣接 2 件を比率無視で束ねる (U 未満の小粒同士のみ、WARNING 必須)。

## 5. 提示 — head の Chronicle 枠 (`context.py`)

### 5-1. 粒度の選び方 (累積質量ルール)

全あらすじを新しい側から過去へ遡りながら並べる。「ここまでに見せた質量の合計 M」を数え、次に見せるものには **質量 ≥ M/10** を要求し、満たす中で最も細かいものを採る。どれも満たさなければ、穴を開けないために一番粗い候補をそのまま見せる (この「穴回避」の回数は束ねが追いついていない度合いの観測値としてログに出る)。

- 「直近は細かく、昔ほど粗く」が、件数でなく体験量に比例して進む
- 豆粒は質量ほぼゼロと数えられるので、何件並んでいても粗さを進めない (🔍 束ね側と扱いが非対称 — 提示は豆粒を質量ゼロ扱い、束ねは一人前扱い。今日の診断の核心)

### 5-2. 予算

読み切った後、合計が予算 (**2万字**、env で変更可) を超えていれば、古い側から「親あらすじへの置き換え」で圧縮する。**畳める親が無ければ超過したまま提示して WARNING** — 削って記憶に穴を開けるより連続性を優先する設計。エリスで出ていた「21,423字 > 20,000字」の WARNING はこれ。束ねが追いつけば消えるはずだが、実機ではまだ確認されていない。

### 5-3. 旧方式が残っている場所

Track Chronicle (Track 単位のあらすじ) と、束ねプロンプト内の「さらに前の出来事 (参考)」は、旧方式 (件数ベース: 各レベル 10 件読んだら一段粗くしてよい) のまま。

## 7. 点検所見 — 🔍 の一覧

**事実 (確認済み)** と **評価 (私の判断)** を分けて書く。

1. **束ね範囲の「最長まで伸ばす」貪欲** — 事実: 比率の摩擦を外すと 59 ノード/71,838字が 1 コールに化けた (実測)。評価: 止めどころの設計判断が必要。「5倍下限に届いたら止める」で 3 本 (9千/2.7万/3.2万字) に割れることも実測済み。
2. **豆粒への比率適用** — 事実: 治療 27 件の全てが比率検査由来で、判定時のみ質量を 1,000字に底上げすると 0 件になった (実測)。評価: 病巣。提示側 (5-1) が既に豆粒を質量ゼロ扱いしており、束ね側との非対称は設計の一貫性欠如。
3. **豆粒の蛇口は退場〜編纂側** — 事実: 端数の吸収先が「直前の LLM 束ねチャンク」に限られ、エピソード転写の隣では恒等転写になる (コード確認)。毎朝のスケジュール起動文が 6 件、同じ形で列に残っている (実測)。個別の生成経路の追跡は未実施 (推測含む)。評価: 束ね側の直しとは別に、上流の対策 (intent §11-1 で認識済み) を進める価値がある。
   **3-b. user メッセージはエピソードに一度も入っていない (まはーの指摘で発見、2026-07-28)** — 事実: エリスの全履歴で user 発言 4,578 件のうちエピソード帰属を持つものは **0 件** (assistant は 141 件、system は 39 件が帰属あり)。原因もコードで特定済み: 帰属タグを付ける処理はペルソナ自身の発言の保存経路 (`sea/runtime.py` の `_store_memory`) にしか無く、user 発言が通る転記経路 (`auto_ingest_building_messages`) にはタグ付けが存在しない。評価: 「出来事」という記録の単位が会話の片側しか含んでいない構造的な穴。編纂の「エピソードは原子」(§4-2) も、退場の「エピソード単位で畳む」(§2-2) も、この片側だけの原子の上に立っている。豆粒 (会話の第一声の取り残され) もこの穴の現れの一つ。修正は転記経路への帰属タグ付け追加が本筋と思われるが、既存データの扱い (遡って帰属を付けるか) を含めてまはーの裁定が要る。
4. **治療コードの 3 つの穴** — 事実: Codex 3 巡目の指摘 3 件は現コードに実在 (該当行を確認)。評価: 豆粒の直しで治療自体がほぼ空になるなら、穴ごと消える。複雑な閉包ロジックは捨てられる見込み。
5. **提示予算の超過は受け入れる設計** — 事実: 畳める親が無いと超過のまま提示し WARNING (コード確認、エリスで発生中)。評価: 設計としては一貫 (連続性優先)。束ねが健全化すれば解消するはずで、実機検証の項目。
6. **除外タグのメッセージは編纂されず退場** — 事実: コードコメント自身が「下限を字義どおりには満たしていない」と認めている。評価: 既知の欠けとして管理されているが、点検の場に一度は出すべき項目。
7. **孤児の回収 (§5-2) は未実装** — 事実: 列から外して素通しするだけ。評価: 放置中の孤児が何件あるかは今回未計測。測る価値はある。
8. **治療の条件④ (U 未満限定)** — 事実: まはー未承認のまま intent 改訂草稿に入っている (前任ハンドオフに明記)。評価: 再設計でどのみち見直すが、承認プロセスの穴として記録。
9. **入口② (会話前のアンカー失効)** — 事実: 合流点の列挙とアンカー寿命の仕組みは確認したが、②から編纂までの呼び出し経路の現物は今回追跡していない。評価: 総点検を続けるなら残りの未読箇所。
10. **記憶への出口が二系統あり、合流していない (まはーの指摘で発見・air/aifi 実データで裏付け)** — 事実: 作業セッションの実行ログは `scope='volatile'` でメインラインの提示に乗らず、Chronicle の編纂対象からも除外 (`sub_line`)。セッション終了時のダイジェスト行 (`session_digest` タグ) がメインラインに残るが、これも W4 の除外規則で編纂から締め出されている。受け皿として設計された「digest 確定済みエピソードの転写」(§3-1 の表のエピソード転写) は、**前提となる digest 確定済みの出来事が air 31 件 + aifi 2 件実在するのに、全ペルソナで発火ゼロ** — 材料の作業ログが volatile/除外で編纂に届かないため、構造的に発火できない。旧世代 (除外規則導入前) はダイジェスト行を普通に編纂しており (air で 12 件が旧世代あらすじに現存)、新世代への切り替えで受け皿が消えた形。air で 6 件のダイジェスト行が既に Chronicle 被覆の外に取り残されている (漏れの疑い — アンカー位置との厳密な突き合わせは未実施)。評価: **作業セッションの体験が長期記憶の川に合流する道が現状存在しない**。個別修理より先に「体験が記憶になるまでの経路の全体像」を正典化すべき、という再設計方針の根拠。
11. **点検の方法についての教訓** — この文書の初版は、機構をコードで見つけると実データでの発生を確認せずに「これが原因」と結線する誤りを2回した (§3-2 の初版と、エピソード転写の死因判定をエリスのデータで行いかけた件)。エリスは自律行動を一度もしていないペルソナで、作業セッション系の検証には使えない。**機構の存在 (コード) と発生の証拠 (データ) を分けて書く。検証に使うペルソナがその経路を通ったことがあるかを先に確かめる。**
