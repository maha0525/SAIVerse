## 2. Windows で見るところ (退行が無いことの確認)

### 2-1. 過去ログの取り込み — `698a15bf`

`find_log_files` が「ディレクトリを一覧して名前を突き合わせる」形から「パスを
組み立てて開く」形に変わった。**日本語の部屋名でも従来どおり取り込めるか**が
退行チェック。

- 起動ログに `[legacy-log]` の行が出ること。「対象 log.json: N 件」の N が
  0 でないこと (対象の部屋がある場合)
- 過去ログ未取込の部屋があるなら、起動でその場で取り込まれてバナーが消えること
- まはーの環境は取り込み済みなので、**新規に踏む道は無い見込み**。何も出なければ緑

### 2-2. 証明書 — `9de0fd27`

起動時に `saiverse/tls_trust.py` の判定が一度走る。**Windows は OS のストアを
読めるので、何もせずに素通りするのが正しい挙動**。

- 起動ログに `OS の証明書ストアが空でした` が **出ないこと** (出たら退行)
- アドオンカタログが従来どおり開くこと
- (余力があれば) アドオンのインストール、更新通知、お知らせの表示

### 2-3. フィードタブのダークモード — `f9842c88`

**このセッションで唯一、実アプリでの確認が残っている項目。** 検証は実際の CSS を
読み込んだ静的プレビューでライト/ダーク両方を目視したところまでで、アプリ上では
見ていない。

- グローバル設定 → フィード をダークモードで開く
- 購読カードのフィード名が読めること (以前は白地に白文字で消えていた)
- 「施設を追加」の**プルダウンを開いた状態**で候補が読めること
  ← ここが元の issue で「操作不能級」とされた本体。静的プレビューでは開いた
  状態を見ていないので、**ここだけは実アプリでしか判定できない**
- 記事ビューアのパネルが暗いこと
- ライトモードで見た目が変わっていないこと (退行チェック)

### 2-4. 記憶の検索テストの例文 — `274b3a85`

メモリーモーダル → デバッグ → Unified Recall Test の検索クエリ欄の placeholder が
`例: ロンドンへの旅行` になっていること。

### 2-5. 記憶DBの接続 — `cc8dcb0f`

`init_db` の本体を `_init_schema` へ切り出した。**記憶まわり全体の入口**なので、
影響範囲は広いが挙動は変えていない。

- 会話が普通にできること、記憶タブの各画面が開くこと
- ペルソナの新規作成 (新しい memory.db が作られる道)
- 単体では `tests/test_memory_db_connection_leak.py` と、記憶まわり 370 件が緑

## 3. macOS でしか見られないところ (報告者待ち)

Windows 環境では**確認する手段が無い**。報告者の環境で確かめるしかない。

### 3-1. 過去ログが濁点の部屋名で移せない

- **症状**: 「部屋『リビング』の古い会話 597 件を移せませんでした」が再起動しても消えない
- **根因**: macOS はファイル名の濁点を 2 文字へ分解して保存 (NFD)、DB の
  BUILDINGID は合成済みの 1 文字 (NFC)。パスで開けば見つかるがディレクトリ一覧との
  文字列比較では一致せず、取り込みが「対象 0 件」で空振りしていた
- **緑の条件**: 起動でバナーが消え、その部屋の過去の会話が画面に出ること
- issue: [legacy_log_import_misses_decomposed_folder_names](../issues/legacy_log_import_misses_decomposed_folder_names.md)

### 3-2. カタログ・アドオン取得・更新通知・お知らせが全滅

- **症状**: カタログを開くと `CERTIFICATE_VERIFY_FAILED (unable to get local issuer certificate)`
- **根因**: macOS の Python はキーチェーンを読めず、OS のストアから読める証明書が
  **0 個**。urllib 経由の HTTPS が接続先を問わず必ず失敗する
- **緑の条件**: カタログが開くこと。**あわせてアドオンのインストール、更新通知、
  お知らせも戻っているはず** (同じ 4 経路が一度に直る)
- issue: [urllib_https_fails_when_os_trust_store_empty](../issues/urllib_https_fails_when_os_trust_store_empty.md)

### 3-3. Chronicle が開けず、その後 Memopedia が固まる ← **根本原因は未特定**

- **症状**: 2 人のうち 1 人だけ Chronicle が「存在しない」。Chronicle を表示した
  後に Memopedia を開こうとすると読み込みが終わらない
- **直した部分**: 用意の失敗で接続が閉じられず書き込みロックが残る欠陥を、同型
  3 箇所とも塞いだ。順序依存 (Chronicle の後に Memopedia が固まる) はこれで説明がつく
- **直っていない部分**: **その環境で引っ越しが何で倒れているかは未特定。**
  接続リークを塞いだので「後続が巻き添えになる」ことは無くなるが、Chronicle が
  開けないこと自体は直っていない可能性が高い
- issue: [memory_db_connection_leak_on_init_failure](../issues/memory_db_connection_leak_on_init_failure.md)

## 4. 返答待ち (報告者へ送信済み、2026-09-02)

     「開けない」なら説が外れ、原因を探し直す
2. **「読み込みが終わらない」の具体** (何分待ったか / エラーが出るか / 再読み込みで直るか)

### 診断ツール (リポジトリ外)

`saiverse_diagnosis.py` + `SAIVerse-diagnosis.command` (macOS) /
`SAIVerse-diagnosis.bat` (Windows)。読み取り専用で、5 つの節を出す:

【1】街のフォルダ名と識別子の食い違い /【2】部屋ごとの過去ログ突き合わせ (実際に
一時DBへ入れてみて転ぶ行を特定) /【3】起動ログの過去ログ関連 /【4】カタログへの
接続 (OS の証明書 / 同梱 certifi / 相手の証明書の発行元で原因を三択に振り分け) /
【5】ペルソナごとの memory.db (旧形式が残っているか、**複製の上で本体と同じ
引っ越しを実際に走らせて倒れた場所を traceback ごと出す**)。

**まだリポジトリに入れていない** — 今回の症状を追うためのワンオフとして作った。
正式に `scripts/` へ置くかは原因が確定してから。置く場合は【4】の判定文が OS 別に
分岐していることと、`.command` が LF 改行であること (CRLF だと macOS で動かない) に
注意。

## 5. 説明しきれていないこと (次に触る人へ)

正直に書いておく。**「読み込みが終わらない」の体感を、私はまだ説明できていない。**

- SQLite の鍵待ちは既定 5 秒で諦めるので、本来はエラーになって画面に出るはず
- 可能性は ①画面側が繰り返しの失敗を表示せずローディングのまま回っている
  ②引っ越しそのものが重くて実際に何十秒もかかっている — **どちらも未確認**
- 当初「Python 側のロックを握ったまま離していないのでは」と疑ったが**これは外れ**。
  `sai_memory/db_locks.py` の錠前はすべて `with` で取られており、手動 `acquire()` は
  1 箇所も無いことを確認済み

§4 の質問 2 への答えで、ここが埋まるはず。

### 6-3. 設計上の疑問 (別件)

**一覧を見るだけの画面が、なぜ毎回スキーマの用意と引っ越しを走らせるのか。**
Chronicle の API はリクエストのたびに `init_arasuji_tables` (テーブル作成・VIEW
再作成・旧形式からの引っ越し) を通る。引っ越しは一回きりの処理なので、読み取りの
入口に毎回ぶら下げる必要はない。起動時に一度で済ませれば「画面を開くたびに同じ
失敗を繰り返す」構造自体が消える。今回は報告された欠陥の修理までにとどめた。
