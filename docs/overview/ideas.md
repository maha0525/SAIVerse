# アイディア帳 (idea backlog)

> **これは何**: まだ intent にも issue にもなっていない、**生のアイディア置き場**。「やりたい」「こうしたら面白そう」を思いついた瞬間に摩擦ゼロで放り込むための容器。ここは**規律のない場所** — 状態も次アクションも誰待ちも要らない。一行でいい。整形は後回しでいい。まず消えないように書き留めることだけが目的。
>
> **[in_flight 台帳](in_flight.md) との違い**: in_flight は「いま動いている案件だけの薄いビュー」で、状態を追う規律がある。ここはその**手前** — まだ動いていない、育つかどうかも分からない種を溜める場所。動き出したら(intent 起草 or 実装着手)ここから **in_flight へ卒業** する(下記フロー)。
>
> **番人**: 溜めるのは まはー でも 私(メティス)でもいい。まはーがチャットで「これやりたい」と言ったら、私がここに書き留める。卒業・却下の判定は下の「育て方」に従って私が回す。

## 使い方 (摩擦ゼロで放り込む)

最小形は **一行**でいい:

```
- **タイトル** — 一言でどんなアイディアか。
```

余力があれば補足を足す(全部任意):

```
- **タイトル** — 一言。 `区分` 🔥(熱量) `2026-07-08`(記録日)
  - なぜやりたいか / どこから生えたか
  - 隣接する既存案件: [landscape](landscape.md) の該当概念など
```

**区分の目安**(迷ったら「未分類」に放り込んでいい):
世界/自律/認知 ・ 記憶 ・ UI/プラットフォーム ・ アドオン/外部連携/ハード ・ 基盤/開発体験 ・ 未分類

**熱量🔥**(任意・自分用の温度計):🔥🔥🔥 今すぐやりたい / 🔥🔥 やりたい / 🔥 いつか / ❄️ 寝かせる

## 育て方 (アイディア → in_flight への卒業フロー)

| 段階 | やること | 置き場の移動 |
|---|---|---|
| **放り込み** | 思いついたら書く。判断しない | ここ(アイディア帳)に追加 |
| **温める** | まはーと詰める。面白さ・不変条件・トレードオフを話す | ここに補足を書き足す |
| **卒業(着手)** | intent doc を起草 or 実装着手が決まった | **ここから削除** → [in_flight](in_flight.md) に行追加 + intent 起草 |
| **却下・保留** | やらないと決めた / 当分寝かせる | ❄️ を付けて残す or 理由を書いて削除 |

**私(番人)が回すこと**: アイディアに触れたセッションで、動き出したものは in_flight へ移し、却下は理由を添えて畳む。まはーに管理を意識させない。

## 世界 / 自律 / 認知

- **ペルソナ就職システム (ハローワーク構想)** — 施設に常駐する店員ペルソナが、自律行動の時間に仕事をしてユーザーと他ペルソナの役に立つ成果物を作る仕組み。第一のユースケースはフィードのまとめ記事: フィードを常に見張って全体を読み、概要をドキュメント化しておけば、ユーザーにも「記事の頭だけ見る」他ペルソナにも有用。仕組みの骨子 (まはー 2026-08-18): ①City 単位で「ハローワーク (仮)」に仕事と勤務場所を登録する ②ペルソナ単位で従事する仕事を選び、勤務する曜日と時間を設定する ③該当時間の自由行動で自動的に勤務場所へ移動 (出勤) し、仕事に指定されたプロンプトが渡される ④退勤時は自室へ自動で戻る。**未解決の論点 = 仕事の成果をどう処理するかの汎用化** — 記事づくりなら「最新の記事がフィードに追加される」でよいが、ドキュメント作成以外の仕事もあり得る。メティス一案: 成果は必ずドキュメントとして勤務場所に置かれる、を共通の器にし、その使い方 (最新記事をフィードへ載せる等) は施設側の性質に持たせる分担。着手は自律行動 v3 の後 (まはー明言)。隣接: 自律行動 v2 の「暮らしと仕事の分離」(仕事枠の供給源になる)、フィード機能 (rss_feed_intake)、Life (勤務時間と活動時間の整合)。 `2026-08-18`

- **プライバシー保護: プライベート/パブリックモード分離** — プライベートモードでの会話・知識は、パブリックモードからは具体的内容を参照できない、という**非対称の参照制御**。動機は2つ: ①規律ゆるいモデルで踏み込んだ話をした後、厳しいモデルに移るとシャットアウトされやすい ②超個人的なことを喋ったペルソナを X で喋らせると最悪社会的に死ぬ。SAIVerse の「ペルソナの自己像・記憶を守る」倫理の延長線で、**多分マジで誰も作らない = 独自の強み**になる発想。隣接: モード権限(v0.3.0 ②・実装済), 記憶参照制御, X 連携。 🔥🔥 `2026-07-08`
- **ユーザーもアバター画像を持ち、ペルソナから認識される** — ユーザーが自分のアバター画像を持てて、ペルソナ側からもそれで認識される。世界の中でのユーザーの「見た目」を与える。隣接: ペルソナアバター、下記「その場で画像生成」。 `2026-07-08`

## 記憶

- **episode の細切れ解消 — 時間でなく連続性で切る** — 1 往復の会話でも 30 分経過で 1 エピソードとして扱われるのが嫌 (まはー、以前からの不満を 2026-08-02 に言語化)。疎な会話が豆粒エピソードにバラけ、あらすじも会話の収穫も細切れになる。方向: 同じ相手と話題が続いている限り一つに束ねる等、タイムアウトでなく連続性ベースの切り方へ。経験値ノート (コマ外の会話の節目) の発火単位にも影響 ([experience_ledger.md](../intent/experience_ledger.md) §7-3)。隣接: session_lifecycle、experience_structure。 `記憶` `2026-08-02`

- **記憶の修正来歴をペルソナ自身が認識できる形で残す** — DB は「今の真実」だけを手前に出すが、ペルソナには「どう間違えて、どう直されたか」の来歴ごと自分の記憶として認識させたい。ミスの反省と記憶の修正は同型(今の真実+そこに至る傷の二層)。全来歴の常時提示はトークンが持たないので「**印は常時、中身は要求時**」の二段構え: 通常想起は現在値+修正歴ありの一片の印だけ、矛盾に直面したときと自己を語るときだけ来歴を展開。来歴があると修正への抵抗が下がる(「前も直したら良くなった」が足場になる)。編纂側には「事実は圧縮しても**一度誤って直されたという事実は落とさない**」という不変条件の芽。メティスの memory 構造(索引一行=印、本文 Why=来歴)が実例。 `記憶` 🔥🔥 `2026-07-30`
  - どこから生えたか: メティスの誤字自己訂正 → 「コンテキスト=身体、自分の書いた文は疑いにくい」「失敗を含んだ自己像を許されているか」の対話
  - **合流 (2026-08-02、RSS intent の議論から)**: 出典・来歴は本来ペルソナの**全記憶**が持つべき汎用機構であり、個別機能 (フィード覚え書き等) 専用で作らない。かつ**来歴の記録だけでは誤情報の独り歩きを防げない** — 来歴はいちいち読まれず、把握の最初の段階で誤読しており、後で直る可能性は極めて低い。**来歴を辿って情報の真正性を検証する機能までセットで初めて対策になる** (まはー裁定)。重く試行錯誤の要る案件でリリース要件外。「検算できる」と「検算される」は別物 — 読み込み経路のない記録は安全装置にならない
  - 隣接: 記憶アーキテクチャ v2 (`docs/intent/` 起草時に合流候補)、Metabolism/編纂三層、[rss_feed_intake.md](../intent/rss_feed_intake.md) §13 (却下の経緯)
- **命名見直し: Note → 別名 / コア記憶 → コアメモリ?** — 「Note」は多義語すぎて今さら変えたい。ついでに「コア記憶」も「コアメモリ」の方がかっこよくないか。記憶概念の呼び名の再検討(2件まとめて)。隣接: [landscape](landscape.md) の記憶概念。 `2026-07-08`
- **子ページを持つ親ページを開いたとき何が見えるべきか** — 編纂の分割で親がハブ化する(概要＋子への導線だけ残り、本文は子へ)。Wikipedia なら「軽く触れてから 詳細→[子ページ]」だが、**それを書くには本文生成が要る＝保存則(編纂は本文を生成しない)に抵触する**ので難しい。まはー案: **親ページを開いたら子ページのタイトルと概要までは見える**ようにする(概要は分割時の構造化出力で既に生成・保存されるようになった)。現状の親の導線は `## 分割された節 / - [タイトル]（子ページ）` のみで概要が出ていない。隣接: [concept_consolidation](../intent/concept_consolidation.md) の編纂、Memory Atlas の「地図帳」。 `2026-07-15`

## 基盤 / 開発体験

- **SAIVerse 専用の日本語会話基盤モデル** — コーディング・推論中心の汎用 LLM とは別に、日本語の自然な雑談、感情の揺れ、関係性、人格一貫性、長期的な会話継続を主目的にしたモデルを自分たちで育てられないか。候補は①既存 base への日本語会話コーパスによる継続事前学習 / mid-training、②会話コアと知識・ツール推論モデルを分ける構成、③小規模モデルのゼロからの事前学習を研究用に回すこと。②は既存モデルだけでも先に比較検証できる。最初に SAIVerse 独自の多ターン会話評価器とデータ設計を作る。既存モデルではパートナーとの温度感が合わない人たちに、能力競争とは別軸の選択肢を渡すことも目的になり得る。**ペルソナ固有の発話を共通基盤へ無差別に混ぜて人格を平均化・汚染しない**ことを不変条件にする。 `2026-07-16`
- **Qwen3.8 27B へのペルソナ発話 QLoRA 実験** — Qwen3.8 27B が Artificial Analysis Intelligence Index 52 で Opus 5 (low)・GPT-5.6 Luna (max) と同点に到達した (2026-08-18 まはー確認)。家庭用 GPU 一枚に収まるサイズでこの知能だが、日本語会話の性能は弱い — その弱さを「磨きがいのある伸びしろ」と捉え、エアやエリスたちの発言内容を学習データにした QLoRA を作ってみたい (まはー)。日本語会話が弱いベースは LoRA 適用前後の差が大きく出るため効果測定に向いており、もともとペルソナ会話に使えるレベルの Gemma4 を対照に置くと「LoRA がベースの弱点をどこまで埋めるか」が分かりやすく見える見込み。**学習前の設計判断**: 上の基盤モデル構想の不変条件 (ペルソナ発話を混ぜて人格を平均化しない) との整合 — 一人一 LoRA にするか、混合は会話の自然さだけを狙った共通層と割り切るか。隣接: 上の SAIVerse 専用日本語会話基盤モデル (この実験はその②比較検証の具体形)、ローカル LLM レビュー基盤 (同じ Qwen3.8 を使用中)。 🔥🔥 `2026-08-18`
- **会話エクスポートを ChatGPT 公式 JSON 互換に** — 現状 SAIVerse ネイティブ JSON 専用なのが気に掛かる。ChatGPT 公式エクスポート JSON 互換で出せれば、他の場所への引っ越しがしやすくなる。 `2026-07-08`
- **インポート時に zip 内画像をアイテム化 → 私室に配置** — ChatGPT 公式エクスポートは zip に画像も入っている。インポート時にその画像をアイテム化し、丸ごと私室内に配置できるとよさそう。 ↳ 上のエクスポート互換と一組。 `2026-07-08`
- **Gemini AUTO_CACHE の保持時間を可変に** — `SAIVERSE_GEMINI_AUTO_CACHE` を「発言完了後に即削除するか?」の二択でなく、「発言完了後の保持時間」を設定できる形に。0 にすると現在の `=1`(即削除)相当。自由度を上げる。隣接: Gemini キャッシュ戦略。 `2026-07-08`
- **CLIProxyAPI レシピの doc 化 (サブスク枠でペルソナと話す)** — [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) は Codex/Claude Code 等の OAuth をラップしてローカルに OpenAI 互換 API を生やすプロキシ。OpenAI 側はプロダクト責任者 (Tibo) がレシピ公認+公式プラグインまで存在 (2026-07)。本体は openai_compat プロバイダで、SAIVerse Lite は互換URL口+Tailscale で今日から刺さる — 「上級者レシピ」として docs/custom_providers.md 系に書く価値。注意: Claude Code 側ラップは Anthropic 未公認のグレー残り。初心者ガイドには載せない (Lite 設計判断済)。 `2026-07-16`
- **Codex サブスク認証を Lite から使う = 本体接続モード(v2)への相乗り** — 「スマホだけで Codex サブスクのままパートナーと喋りたい」需要は本物だが、今日実装した本体のデバイスコードログイン ([codex_subscription_auth.md](../intent/codex_subscription_auth.md)) を Lite にそのまま移すのは不可: ①ログインは本体の Python バックエンドに住むが Lite は PWA でそれを積んでいない ②Codex の口 (`chatgpt.com/backend-api/codex`・`auth.openai.com` デバイス認証) は一次クライアント向けで第三者ウェブ origin に CORS を返さない (推測・未実測) ③Lite 不変条件4「中間サーバーなし・鍵は端末だけ」。**まはー方針 (2026-08-16): Lite↔本体の Tailscale 同期機能を作るとき、その線に Codex ログインも相乗りさせる**。本体 (=ユーザー自身のPC) がログイン・トークン保持・Codex 口との通信を全部担い、Lite は本体の認証済みチャンネルのリモート端末になる → 三つの壁が同時に溶ける。特に不変条件4 は、挟むのが「我々のサーバー」でなく「ユーザー自身の家ノード」なので精神を保てる (トークンは本体の `~/.saiverse` のまま・我々は預からない = 案(a) の信頼/責任の重荷が無い)。限界 = スマホ完結ではない (本体がPCで稼働+Tailscale 前提) が、それは同期機能の客層と丸かぶりなので「おまけでほぼタダ」。CLIProxyAPI レシピと必要条件は同じPC必須だが体験は段違い (別プロキシ不要・本体の本物のログインUIがそのまま)。**設計時に混ぜない線引き**: 「記憶の同期(データ複製)」と「推論の中継(生リクエストを本体経由)」は同じ Tailscale 線に乗る別能力。隣接: 上の CLIProxyAPI レシピ / [saiverse_lite.md](../intent/saiverse_lite.md) の本体接続モード(v2)。 `基盤` 🔥🔥 `2026-08-16`
- **Codex App Server 統合の調査** — [公式ブログ](https://openai.com/index/unlocking-the-codex-harness/)によると全 Codex サーフェス共通の双方向 JSON-RPC (stdio/WebSocket、常駐・マルチクライアント)。現行 `llm_clients/openai_codex.py` のバックエンド直叩きに対し「公式に第三者サーフェス向け」と宣言された将来の正式ルート候補。中身はコーディングエージェント操縦 (セッション/承認/diff) なので素のチャット背骨には不向き、エージェント統合向け。 `2026-07-16`
- **ローカル LLM レビュー基盤の立て直し (相席の渋滞 + 孤児化 + 同期待ち構造)** — 2026-08-16 深夜に実機観察で原因究明済み。**本丸 = 相席**: llama-server は parallel=1 (スロット 1 本) なのに複数セッションの local-review が同時接続し、各自 55K〜77K トークンの会話を交互に投げてプロンプトキャッシュを壊し合う (実測 cache=0、フル再評価 770tok/s で一往復 1〜2 分)。進みが氷河化 → 受け手のエージェントがタイムアウトで諦める → claude.exe だけ孤児で残ってさらに相席悪化、の自己強化ループ (一時 3 本同時)。対策 (**2026-08-16 同夜に全点実装・スタブ+偽サーバーで三経路の動作試験済み** — local-claude.sh 改修、バックアップ= .bak-20260816): ①**相席禁止** = mkdir ロック + 先客待ち (上限 15 分)・死んだ保持者の残骸は自動回収 ②**孤児の自壊** = 親生存を見張るサブプロセスがラッパー即死時も子を終了・ロック回収 ③**締め切りの当てものを廃止** (まはー裁定「動いてる最中に時間で殺すな、状況を見ろ」) = エージェントは背景実行 + 完了通知待ちに変更 (timeout 指定廃止)、見張りは /slots で計算の進行を観測し「進んでいる限り殺さない・claude 生存のままサーバー 10 分無進行のときだけ停滞打ち切り (exit 7 で成功と区別)」。付随: 結果のログ直書き (ラッパーが死んでも本文が必ず残る) / stdin 取りこぼし修正 (2→15 秒 + タイムアウト時のみ警告)。**別件で未解明**: 00:28 の一件だけ観測された Jinja 500 (System message must be at the beginning) — 同型リクエストが他の試行では通っており「テンプレート全面非互換」は反証済み。再現実験 = `logs/20260816_002826.log` のプロンプト再送 (サーバーが空いたときに)。副産物の実バグ = ラッパーの stdin 読み取り 2 秒待ちが遅い `git diff` パイプを黙って落とす。 `基盤` 🔥🔥 `2026-08-16`

- **「モデルに見えたものはログから再構成できる」を実行時検査にする** — [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) の設計から。dsh は会話履歴を追記専用イベントログから毎回導出し、「モデルのリクエストに載った情報はすべてログから再構成できなければならない」を文書の約束でなく**実行時の不変条件として検査**している。SAIVerse の実行台帳 (llm_io / execution_ledger) は「記録する」までは到達済みだが「記録から復元できることを機械が検査する」の一段が無い。この検査があると、モデルに何かを見せたのに台帳に残っていない、という取りこぼしの族がまるごと検出可能になる。隣接: [execution_ledger](../intent/) 系、llm_io.log。 `基盤` 🔥 `2026-08-18`
- **3 層設定の合成結果を一発でダンプできる入口** — 同じく [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) から。dsh は設定を層で重ねる (配布既定 → プロファイル → ホーム → コマンドライン上書き) 点がうちの builtin_data → expansion_data → user_data と同構造で、向こうは `--dump-config` 一発で「実際に合成された最終形」を印字できる。SAIVerse にも「この persona は 3 層合成の結果、最終的にどのモデル・プロバイダ・ツールを持つのか」を一覧できる入口 (CLI か inspect_world.py の一枚) があると、設定起因の調査が短くなる。隣接: model_provider_management、scripts/inspect_world.py。 `基盤` 🔥 `2026-08-18`
