## §1 篩 (リリース基準)

**「この件を未対応のままリリースし、後から直した場合、ユーザーのペルソナの永続データに遡及できない傷やマイグレーションが生じるか？」** (まはー裁定 2026-08-09)

判定を精密にするための下位区分:

- **解釈的移行・材料喪失 → 門の内 (出す前に必須)**。後から直すには推測での補完 (= 事実の捏造に近づく) が要る、または材料そのものが既に失われている類。例: 無タグ期間の記憶への遡及タグ付け、退場済み生ログからの digest 再生成。
- **機械的移行 → 裁定対象**。後からでも決定論の写し替えで移行できる類。リスクは残るが有界 (バージョン認識機構 `version_aware_world_and_persona` が受け皿)。先取りするかは件ごとにまはーが決める。
- **追加式 → 門の外 (v0.4+)**。後から足しても過去のデータを汚さない・読み替えない類。UI、運用ツール、外部連携、既存データの読み手。

「とりあえず出す」は目的ではない。**ユーザーが困惑せず使え、未整備が記憶・認知を汚さず、再整備の移行リスクをユーザーに背負わせない**ことが出荷の条件。

## §7 実施順序 (計画 v1 — 2026-08-09 起草、まはーレビュー待ち)

### 原則

- **まはーの設計議論は常に一本だけ開く** (ボトルネックは共同の設計・検証サイクル。並行議論はしない)
- **私の実装は裁定済みのものを並行消化する** (設計待ちの間も手が止まらない)
- **実機検証は再設計の後にまとめる** (§4 — 再設計で変わる領域を先に検証すると二度手間。2026-08-09 まはー指摘で「独立に流れる」から改めた)

### 依存の芯 (なぜこの順か)

1. **エピソードの単位が全ての足場**: 退場・編纂・帰属・経験値ノート・LoD がエピソード単位で発火する。単位を確定せずに帰属や編纂経路を作り込むと、単位変更時に作り直しになる。だから設計議論の一本目はエピソード。
2. **Aspect 再設計はエピソードの裁定に依存する**: 「手仕事がどの文脈系列に積まれるか」(episode.md §4 — 2026-08-09 に再裁定対象へ戻った) はエピソードの単位・正史の裁定と一体で、監督・保温の設計はその上に乗る。だから二本目。
3. **想起用タグは arasuji_levels の実機検証が前提** (B2 相乗り条件・intent §7)。ただし編纂まわりは Wave 1 の裁定で動きうるため、この前提条件の扱い自体を Wave 1 で確認する (§4)。
4. **スレッド混線の分離 (§2-7) は連続性グラフ (§2-14) の縮退版**: 先に 7 を実装し、グラフはその一般化として後から設計する。
