# Intent Document: アップデート再起動後処理 (POST_RESTART_UPDATE_STEPS)

**ステータス: 設計中** (2026-10-23 起草。名前はまはーの裁定「アップデート再起動後処理、とかでいい」。工程の通し番号の呼び方「工程番号」もまはーの命名 (2026-10-23))

## 芯 (専門用語なしの数行)

アップデートは再起動で終わる。でも、再起動の後にしかできない作業が時々ある。その作業の一覧と「どこまで済んだか」の記録を持ち、再起動の直後に、足りない分だけを一度実行する。済んだら二度とやらない。最初から揃っている環境では一度もやらない。

## 1. なぜ必要か

アップデートを実行しているのは、**アップデート前のバージョンのプログラム**である (新しいファイルを取ってきても、動いている側は古いまま)。だから「今回のアップデートで初めて足された作業」は、その回のアップデート中には実行されず、新しいコードが動き出す再起動後が最初の機会になる。また、動いている間は差し替えられないファイル (使用中の実行ファイルなど) も、再起動後にしか触れない。

この種の作業を、これまで三回、毎回べつの一回限りの作りで解いてきた:

1. 同梱の Node.js の入れ替え — start.bat が毎回の起動でバージョンを見比べて入れ替える (#413)
2. SearXNG の入れ直し — `installer_revision` という専用の記録で、起動時に一度だけ入れ直す
3. pip 自身の更新と fastembed の削除 — v0.3.24 以前からの初回更新では、古い版のアップデート処理 (`scripts/update_engine.py`) が動くため実行されない ([#415 の Codex P1](https://github.com/maha0525/SAIVerse/pull/415)。v0.3.25 の発行後に発覚)

三つ目を四つ目の個別処理で解く代わりに、この種の作業をまとめて呼び表す概念と一覧を作る (2026-10-23 まはー「再起動後に行うしかない更新処理、を全部まとめて呼び表す概念作ってそいつに対して行うようにすべき」)。

## 2. 利用者に約束すること (不変条件 — 2026-10-23 まはーの三条件)

1. **アップデートの続きとしてしか動かない。** 実行の条件は「古いアップデート処理が書いた、工程番号の無い (または古い) 完了記録ファイル (`.update_complete`) があること」だけ。アップデートしていない環境には、この処理を含むコード自体が存在しない。
2. **正常に 1 回済むまで、で終わる。** 成功した工程番号は `.update_complete` に記録され、以後の起動では工程番号を比べるだけで何も実行しない。失敗した回は工程番号が進まず、次の起動で再挑戦する。
3. **そのバージョン以降に新規導入した環境では 0 回。** セットアップ直後の起動時には、既存の「`.update_complete` が無いときは導入済みの環境を直接確かめる」検証処理が動き、確認が通れば最新の工程番号つきの `.update_complete` が作成される — この再起動後処理は一度も動かない。

加えてこの仕組み自身の約束: **SAIVerse のバージョンは絶対に進めない** (更新ボタンを押していないのにバージョンが変わる事故を作らない)。通信は、各項目が明示的に必要とする分だけ行う。

## 3. 仕組み (出てくる名前と流れ)

- **`POST_RESTART_UPDATE_STEPS`** (`scripts/update_engine.py`) — 工程の一覧。各工程は「工程番号 (1 から増えるだけの通し番号)・何をするか・実行関数」を持つ。**工程は何度実行しても安全な作りにする** (途中で電源が落ちても、次の起動の再実行で壊れないこと)。
- **`post_restart_steps_done`** — 完了記録ファイル (`.update_complete` の JSON) に足す一項目。「どの工程番号まで済んだか」の整数。古い版の `update_engine.py` が書いた `.update_complete` にはこの欄が無く、0 として扱う。
- **`run_post_restart_update_steps`** — backend の起動時 (`main.py`、SearXNG の入れ直しと同じタイミング) に呼ばれ、`.update_complete` の工程番号 < 一覧の最大の工程番号 のときだけ、足りない工程を順に実行して工程番号を進める。**ここを backend の起動処理に置くのは、画面の「Update」ボタンによる自動再起動が `start.bat` を通らないため** — 更新直後の再起動で即座に実行するには、起動する本体側 (`main.py`) から呼ぶ必要がある。
- 工程が失敗したら: 工程番号を進めず、警告をログに残して**起動は続行する** (pip が古いままでも SAIVerse は動くため、この失敗で本体の起動を止めない)。次の起動で再挑戦する。

### 既存の三例との関係

- 最初の工程は **工程番号 1 = pip 自身の更新 + fastembed の削除** (v0.3.26 で追加。v0.3.24 以前から更新してきた環境への対応)。
- 同梱の Node.js (`start.bat` の毎回検査) と SearXNG (`installer_revision`) は**今は移さない**。どちらも動いていて、移し替えはメリットより既存の動作を壊す危険が大きい。次にそれぞれへ手を入れるときに、この一覧へ寄せるかを判断する。

## 4. 変更の置き場所 (なぜここか)

- 一覧と実行関数は `scripts/update_engine.py` に置く — `.update_complete` の読み書き関数 (`read_completion_marker` / `write_completion_marker` / `completion_fingerprint`) がここにあり、「アップデートがどこまで済んだか」の判定処理をこのファイルに集約しているため。
- 呼び出しは `main.py` の起動処理の中 — 理由は上記 (UI ボタンの自動再起動を拾える唯一の場所)。
- `completion_fingerprint` の比較 (`--check-complete`) には**混ぜない**。あちらの不一致は「アップデート処理全体の再実行 (= 手動アップデートと同じで、最新リリースまで進む)」を引き起こすため、工程番号の不足をそこに混ぜると「起動しただけでバージョンが進む」事故になる (2026-10-23 の設計議論でまはーが却下した方式)。

## 5. 検証手順 (本番と分けたコピー環境で、段階ごとに確認)

1. 古い版相当の `.update_complete` (`post_restart_steps_done` の欄無し) を置いて起動 → 工程番号 1 が一度だけ動き、`post_restart_steps_done: 1` が書かれる。
2. もう一度起動 → 何も実行されない (ログに実行の記録が出ない)。
3. `.update_complete` を最新の工程番号つきで新規作成 (セットアップ直後相当) → 一度も動かない。
4. 項目を故意に失敗させて起動 → 起動は完了し、工程番号は進まず、次の起動で再挑戦する。
5. 本物の v0.3.24 の ZIP から更新する通し確認 (リリース前の実機検証で一度)。

## 6. 経緯
