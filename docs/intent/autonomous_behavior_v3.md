## 1. 芯 (一言で)

**ペルソナの一日は、事前に決めた「やること」の台帳と、一定間隔で打たれる標準モデルの Pulse (ティック) で運営される。** 一日の縁 (起床・就寝) から LLM の義務判断が消え、判断は実行の場 (ティックと会話) に寄る。キャッシュの保温はティックの営みそのものが行い、keep-alive 専用の温め直しは最後の保険に退く。

## 2. 前提となる歴史認識 (なぜこの形か)

- **v1 の最大の病理は「何をやるかの規定が無いまま、実行だけが走り続けた」こと。** タスクは、やることが具体的に決まっていればスペルループ一回で普通に終わる。30 秒駆動は不要だった。Track は決める器として曖昧で、一回きりの案件が常設の走路になり、尽きたら新規 Track の創発まで強いていた。
- **v2 の成功は「実行の前に、やることを決める瞬間を置いた」こと。** この芯は変えない。変えるのは決め方 — 毎朝 LLM が時間割を編成する形 (それ自体が創発×後続依存の無監督作業 = v2.5 の診断) をやめ、決定を各々の自然な時点へ分散する。
- **Gemini は自発的にツールへ手が伸びない** (まはー観察 2026-08-12、memory: project_gemini_no_spontaneous_tool_use)。保証が要る行動は、自発に頼らず、スキーマ強制か決定論の配線に載せる。

## 3. 要件 (Wave 2 冒頭で確定、2026-08-12)

1. ユーザーに届く声は標準モデル
2. ライフ中は会話がいつでも温かい — 「話しかけやすい」表示と課金の実態が一致する
3. 作業して暮らした記憶が長期記憶に残る
4. 直前のユーザー会話を**生ログで**覚えている — 自律行動の記録が提示コンテキストを埋め尽くさない (人格の連続性の要請、最重量)
5. 会話の至上性: 即応・往復中の無割り込み・声の混入なし。待ちの備えがその窓の自律予定を全滅させない
6. 席の数と規則は把握できる複雑さに収まる
7. 軽量モデルは、任された仕事の範囲を超える変化を起こさない

## 4. やることの型 — 四類型 + きっかけ

やること (行動の予定) は、やるタイミングの性質で型が分かれる。**型を enum で持たず、時間属性から導出する** (不正な組み合わせを書ける口ごと無くす):

| 型 | 時間属性 | 例 | 表現の器 |
|---|---|---|---|
| アラーム型 | 定時 (その時刻でなければ意味が無い) | 朝の起こしメール・定時連絡 | アラーム (既存の定時スケジュール)。中身は事前に完全確定 (指示書 / Playbook) |
| ルーチン型 | だいたいの位置。**当面「ライフ始め」「ライフ終わり」の二種のみ** (朝/昼の帯は持たない — 途中起床への頑健さを優先) | 朝のフィード確認・夜の日記 | ルーチン (アラームと同じ器 — §4.1) |
| 締め切り型 | 期限 (いつやってもよいが、それまでに) | ユーザーの依頼・帰宅前に仕上げたいもの | タスク帳の一件。失くせないので機械が持つ |
| プール型 | 無し (空き時間に) | 気になることの検索・画像生成の練習 | **システムの表現を持たない** — レパートリー (減らない品書き) + 本人の手帳・記憶 |
| きっかけ型 | 出来事が起きたとき | ユーザーの発話 (最強・常に最優先)・フィード新着・来訪 | 駆動側 (会話機構・判断点) が受ける |

**v1/v2 の失敗の言い直し**: v1 は四類型全部を Track に入れ、v2 は全部を時刻付きのコマに入れた。アラームだけが先に独立し (2026-08-09 裁定「テンプレートと統合しない」)、それは正しかった — 残りも各々の時間属性のまま持つ。

### 4.1 システムが構造として持つ台帳は三つだけ

1. **ルーチン** (アラーム型・ルーチン型 — 正式用語 2026-08-19 まはー裁定): ユーザー合意物。**LLM の出力で直接変わらない — 変更経路はユーザーだけ** (相談は機構ではなく、ただの会話。ペルソナが会話で提案し、ユーザーが UI 等で変える)。**器は一枚・設定 UI は一箇所** — アラームとルーチンの行の中身は「名前 + やる中身 + いつやるかの規則」で同一で、差は時間属性の書き方 (時刻ぴったり or ライフ始め/終わりの位置) だけ。§4 の「型は時間属性から導出」がそのままここにも当てはまる。統一名は**ルーチン**、うち定時のものを**アラーム**と呼ぶ (種別ラベルへ降格 — 時刻厳守の語感を運ぶため残す)。旧 2026-08-09 裁定「アラームは習慣テンプレートと統合しない」は「大きい物を小さい器に押し込むな」の向きで、単純なルーチンをアラームの器に載せる本裁定とは矛盾しない。設計文書で二つをまとめて呼んでいた仮名「繰り返しの定義」は正式用語にしない
2. **タスク帳 — 相手のある一件** (正式用語 2026-08-19 まはー裁定、「締め切り台帳」は廃案): 約束と依頼。失くすことが許されないから機械が持つ。**軸は二本 (2026-08-19 裁定)**: 器を決めるのは**相手の有無** — 相手のいる約束・依頼は、期限が無くてもタスク帳に入る (「ずっと一緒にいようね」型の約束に嘘の期限を発明させないため、**期限 (due) は省略可・省略 = 期限なし**。「永続」と「未定」の区別は持たない — 機械の扱いが同じで、読む消費者がいない)。機械の引き当て (締め切り優先の決定論) に乗るのは**期限のある行だけ**で、期限なしの行は急かされず、空きティックの選択材料として目に入るだけ。現行の統合タスクテーブルを痩せた形に作り直したもので、UI にもこの名で出る。システムタスク (§9-5) もタスク帳の行の亜種。「台帳」を単独の名前にしない — 実行台帳・消費バッチ台帳など開発側の台帳と紛れるため
3. **レパートリー** (減らない品書き): ペルソナ固有の「できる・好きな活動」一覧 (track_retirement の関心の行き先)

**欲求とタスクの区別は廃止** — どちらも「やること」で、差は時間属性 (期限の有無) と**相手の有無** (約束は勝手に消えない・自分のものは薄れたら消してよい) だけ。**減衰機構は持たない** — 選ばれないものはただ選ばれない。見せ方の制限で溢れを防ぎ、消すのは本人の明示かユーザーの掃除。

### 4.2 やること一件が持つ情報

中身 (実行の瞬間に再発明が要らない具体さ) / 時間属性 (定時 or 期限 or 無し) / 繰り返すか / 出自 (どの会話・経験・誰の依頼から) / 相手の有無 / 状態 (ある・やり終えた〔成果物参照〕・取り下げた)。

### 4.3 手帳 — プール型の中身の住処

「気になっていること」は台帳の行ではなく、**本人の手帳** (Memopedia/document のページ) に本人の文章として住む。システムは中身を読まない。机 (memory_open) に開きっぱなしにして、空きティックが想起なしで見る。書き込みの保証は §6 の採取が担う (自発の書き込みには頼らない — Gemini 前提)。

## 5. ティック — 一日の運転

**正式用語 (2026-08-18 まはー裁定)**: 間隔で打たれる一枠 = **ティック**。Beat は「関所 → コンテキスト読み → 1 回の生成 → 記録」の最小行動単位 (beat_execution_context §2.2) の一義に戻り、二語の関係そのものが定義になる — **ティック = 1 Beat を打つ、間隔で来る機会**。

- **ライフ中、標準モデルの Pulse (ティック) が「最後の標準呼び出しから T 分」で打たれる。** T はユーザー設定。均等モード (Anthropic/OpenAI) は物理から T ≦ 50 分。自由モード (Gemini) は任意。事前予測配置は採らない — 予測で省ける無駄は存在しない (間隔を広げる制御はキャッシュ的に禁止・詰める制御は転がし方式でも可能、まはー裁定 2026-08-12)
- **予算 (回数) 設定は T (間隔) 設定に置き換える。** 一日の手数はライフの長さと T から機械的に決まる
- **ティックは 1 Beat (一生成) で閉じる** — スペルは撃ちっぱなしで、結果を積んで続きを生成するラウンドは回さない。帰結は次のティックの頭 (知覚消費・台帳・報告) が読む。⚠️ **この単発で閉じる制御は現行のスペルループに存在しない新設機構** (まはー指摘 2026-08-18 — 現行はスペル結果を積んで続きを回すのが基本形。落とすとティックが会話並みの連鎖 Pulse になり、15〜20 回/日のコスト設計が崩れる)
- **ティックが受け取るのは確定情報** (「このティックは挿絵の続き」) であって、問い (「何をしたいか」) ではない — v1 の病因 2 を踏まない
- **割り付け**: アラームは定時に発火 (ティックの格子に丸めない)。ルーチンはライフ始め/終わりのティックに機械で割当。空きティックは**締め切り優先** (決定論の引き当て) → **システムタスク** (機械からの急ぎでない依頼、§9-5) → 無ければプール (手帳とレパートリーを見て本人が選ぶ — 末端の決定で複利に乗らない、v2.5「コマの中の自由」の継承)
- **継続**: 締め切り型が未完なら台帳に残り続け、次の空きティックが自然に同じ件を引く。「続き」という概念・編集操作は存在しない
- **会話との関係**: アラームは会話中でも鳴る (電話が鳴れば目は逸れる)。**空のティックは会話中は走らない** — 保温は会話自身がしており、待ちも 30 分 < T で切れない。会話終了後、最後の標準呼び出しから T 分で再開
- **重い下請け**: run_playbook を**投げっぱなし**で発注し (身体移動スペルと同型の非同期)、報告は次のティックが読む。発注時に「報告を受けて何をするか」まで決めておく。渡すもの (Playbook・スペル・ループ上限) は発注者が仕事ごとに選ぶ (要件 7 の実現。静的な可否表は持たない — 権限の縛りが欲しくなったらそれはユーザーの権限設定であり、SAIVerse 本体は決めない)
- **締め切りの見張り**: ティックのプロンプトに「期限が近い / 過ぎている」を通知として出すだけ。ティックを足す等の増強は将来の拡張

## 6. 一日の縁 — 判断点の再編

- **起床: 機械の帳簿処理のみ** (ライフ確定・今日のアラーム/ルーチンの割り付け)。LLM の義務なし。時間割の編成・穴埋め・欲求の昇格・減衰は全部消える
- **就寝: 機械の帳簿処理のみ** (ライフ終了・keep-alive 停止・編纂の節目)。ふりかえりの独白・明日へのメモ・欲求の裁定・帰属付けは全部消える
- **朝晩の情緒は義務から習慣へ**: 朝の独白・夜の日記はルーチン型として本人が持てる (持たない人格も合法)。夜の日記用に「やり残し・約束の確認」を含む漏れ検知プリセット (Playbook / 指示書) を builtin で用意する
- ~~残る判断点は「外から何かが届いた直後」だけ: 会話終了と イベント到着~~ → **2026-08-16 改訂: 会話終了判断も退役し、残る判断点はイベント到着ただ一つ** (§13.3)。理由: 会話に切れ目は定義できない — 沈黙 30 分を切れ目とみなす恣意的な運用の上に判断の席を置いていた (まはー指摘)。約束・糸の捕獲は砂金取りへ統合。会話の待ち状態を閉じる処理は機械の帳簿処理として残る (LLM なし)
- **記憶整理 (編纂候補・命名候補のレビュー) は就寝判断から退去** — 自律行動しないペルソナの記憶が二級になる構造的欠陥のため、置き場は記憶側の機構で別途設計 (gate §9 に仕分け行を追加)

## 7. エピソードの解体 (episode.md v1.4 の上書き)

**エピソードという専用の記録行 (テーブル) は持たない。** v1.4 の行が持っていた情報は全て他所に既にある:

| v1.4 のエピソードが持っていたもの | 行き先 |
|---|---|
| どの件の実行か | メッセージへの記録 (書き込み時の目的参照) — 割り付けられたティックは機械で書ける |
| 始まり・終わりの実在イベント | **遷移の一行** (機構名義のシステムメッセージとしてログに実在) — v1.4 の芯「始まりと終わりが実在する」はこの形で生存 |
| 完了・成果物 | 台帳の一件の状態欄 |
| できごと UI の一行 | 表示時にログから導出 (会話・自由時間と同じ扱いに統一)。自由時間の中身は実行スペル・Playbook から表示 (v1 ライフビューの手法の再利用 — ただし §9-9 決着で「本人の言葉が無い隙間だけ」に限定) |
| 読み返し (episode_read) | 目的参照 + 期間でログを引く |
| チャンクの切れ目の目印 | 遷移の一行 |

**自由時間 (空きティック) と会話はもともと記録行を持たない** — 意味づけは §6 の関所タグが運ぶ。実装上、表示や検索のための導出結果の置き場が欲しくなったら、それは概念ではなくキャッシュとして足す。

### 7.1 記憶と想起の完成形

- **書き込み時 (機械)**: 参加者 / 目的参照 (割り付けのあるティック・会話終了判断の捕獲分) / **前駆刻印** (この生成が実際に見ていた最後のメッセージ ID — 同一ライン内の割り込みで「並びでは後ろだが見ていない」を記録する。門 §2-14 決着 2026-08-19、詳細は issues/memory_continuity_graph.md)
- **退場の関所 (Metabolism・gold_panning の席に相乗り)**: 提示から出る直前の範囲を見ながら、構造化出力の一手で ①コア記憶候補の採取 (既存) ②**手帳への採取** (「やりたい・もっと知りたいと思ったことは? 無ければ空」— 空が一級で正常。義務形にしない)。~~③想起用タグの付与~~ → **2026-08-15 訂正: タグは砂金取りの一手ではなく、機構のあらすじ生成コールに相乗りする** (§12-1)。砂金取りはペルソナの視野が広い代わりに畳む範囲の輪郭を正確に知らず、範囲への所属宣言であるタグの書き手として不適
- **不変条件: 提示から出るものは、あらすじ・タグ・採取を済ませてからしか出ない。** タグが要るのは想起でしか届かなくなる素材だけであり、提示に見えている間の未付与は実害ゼロ。保証は二段 — あらすじ・タグ (機構コール) は失敗すると退場が止まる硬い保証、採取 (本人の一手) は失敗しても退場が進む柔らかい保証 (2026-08-15 確認)
- session_digest・恒等転写機構は対象ごと消滅 (セッションが無い。ティックがメインラインに書く本人の言葉がそのまま編纂の材料)

## 12. 暮らしの糸 — 想起の照準の再設定 (2026-08-15 設計議論)

### 12.1 確定裁定

- **想起用タグの書き手は、機構のあらすじ生成コール** (entity_extractor と同一コールへの関与列挙の一欄追加 = 8/2 粒度実験の B2 方式を維持)。砂金取り (本人の一手) 側に載せる案は撤回。理由: ①タグは「このチャンク範囲の中で語られたものは何か」という**範囲への所属宣言**であり、畳む範囲そのものを材料として受け取る機構コールだけが範囲の輪郭を定義上正確に知る (ペルソナに同じ正確さを求めると範囲の再提示 = キャッシュ利点の放棄になる) ②機構コールは「あらすじ生成に失敗したら退場が止まる」硬い保証を既に持ち、タグの不変条件 (§7.1) が自然に乗る (砂金取りは失敗しても退場が進む柔らかい格)。
- **統計を門番にしない**。「関与件数が多いものが自動的に想起対象になる」は保証のない机上論 — **継続的に作業するもの (続きもの) は、本人かユーザーが明示的に立てる・作る**。
- **無差別のタグ (チャンク↔ページ ID の辺) は書き続ける**。役目は選別ではなく**遡りの材料** — 続きものの宣言は遅れて来る (30 日目に立てた糸の、それ以前の経験に年表を組めるのは、辺が既に貼ってあるときだけ。遡及タグ付けは非現実的コストで裁定済み)。

### 12.2 照準 — 何を想起する話なのか

**想起すべき対象は、過去の暮らし。** 時系列的には断絶しているが連続している暮らし (= 糸) を、ペルソナの記憶の中でどう繋ぎ、断絶した過去をそれが見えない現在からいかに再開するか — 人間にはできて AI にはできないことを AI にやらせる話。暮らしの糸でないもの (一度調べただけの知識など) は本件の対象外 — それは能動的な記憶内検索 (Ultramemory・意味検索) の縄張り。

- **創発は放任からは生まれない** (v1 の実証)。LLM は文脈の自然な続きを生成する装置であり、「自由に選んでいい」は機序的に「直近の続きをやれ」と同じ。創発は**システムが文脈を強制的にぶった切り、別の材料を目の前に置く行為**として設計する。v2 の芯「実行の前に決める瞬間を置く」はこの実装だった。
- ただし機械が差し出す内容が機械の発明なら**ペルソナが SAIVerse の操り人形になる** (強く回避)。差し出してよいのは**本人が過去に自分で作った・書いたものだけ** — 著者は常に本人、機械が決めるのはタイミングだけ。
- **head・ビジュアルコンテキスト等の常在提示は意識に上らない** (実測済みの機序)。人間の「ふと目に入る」は、物の常在 × さまよう注意の掛け算で、サンプリングは注意の側がやっている。LLM の注意はさまよわない。

### 12.3 暫定合意の方向 (上手くいかなければ根っこから再考、まはー 2026-08-15)

> **2026-08-16 更新**: 本節のウォークスルーはまはーレビューを通過し、確定形は §13 に置き換わった。特に「誕生の捕獲三席」と「一日の終わりの一問」は、砂金取り一席への統合 (§13.3) で上書きされている。本節は経緯として残す。

- **存在と知覚の分離**: 糸は世界の側に状態として常在し (提示には置かない)、システムが**時々・一本だけ・ティックの尻尾に知覚として**差し込む (「ふと、編みかけのマフラーが目に入った」)。頻度は低く、選び方はわざと直近から離す — 「ふと」の偶然性は乱択が忠実に再現する。
- **糸の記録は片手間では生まれない**: 何かしらのタイミングで、自動機構か本人のどちらかに明示的にやってもらう。誕生の捕獲は三席 (いずれも既存の器):
  1. **会話で生まれた糸** → 会話終了判断 (約束の捕獲スキーマに「続きになりそうなこと・心に残ったこと」の一欄を追加)
  2. **割り付けのティック** → 台帳の一件への参照が機械刻印で最初から付く (意味付け不要)
  3. **自由時間** → **一日の終わりの一問** (ライフ終わりのルーチンの器に置き、中身の一問だけは機構が保証する: 「今日の自由時間、何をしてた?」のスキーマ強制。自由時間の範囲は機械が帳簿で知っており、本人も粗い提示で自分の一日を見えている。生ログが先に畳まれていても本人の自己申告で足りる — 中身への降り口は、どのティックが自由時間だったかの機械刻印が後から貼れる)
- **二度目の紐づけ**: 一日の終わりの一問のプロンプトに機械が**本人の糸の一覧** (小さい・本人が書いたものだけ・古い糸も等しく載る) を添え、「新しい糸か、この中のどれかの続きか」をスキーマで問う — 閉じた語彙で照合問題も直近偏重も出ない。
- **検算の固定点 (まはー設定)**: 「習慣のないペルソナが、たまたま自由時間に小説を書いた。数日後に (続編を書こうかな) と思えて、その時の小説の内容を思い出せる」— これが通れば完璧。最悪ケース (誰の台帳にも手帳にも載っていない、純粋に偶然生まれた糸) なので、これが通れば他は全部通る。

## 13. 手帳とスルース — 確実に通るゲート (2026-08-16 設計議論 — 想起まわりの確定)

小説の固定点 (§12.3) のウォークスルーがまはーのレビューを通過し、以下が確定した。§12.3 の「三席の捕獲」「一日の終わりの一問」はここで一段シンプルな形に置き換えられた。

**正式用語 (2026-08-16 まはー裁定)**: 議論中の仮名「糸」= **アクティビティ** / その器 = **手帳** (英名 pocketbook — diary はペルソナ自身が書く日記と衝突するため回避) / 日付つき一行 = **メモ** (やったメモ / やりたいメモ) / 砂金取り (gold_panning) = **スルース** (Sluice — 水門・洗鉱樋。手作業の一掬いから「全ての水が通る構造物」への性質変化を名前が運ぶ。コードの gold_panning → sluice 改名は v3 実装時)。

### 13.1 手帳 (pocketbook) — アクティビティとメモの統一記録

**レパートリー・旧手帳・アクティビティの記録は同種のものとして一本化する** (まはー裁定「育つ・育たないにかかわらず同種に」)。構造はテーブル二枚:

- **アクティビティ**: ID / 名前 (活動の粒度: 「小説を書く」「絵の練習」) / 状態 (開いてる・閉じた — 閉じるのは本人かユーザーの明示だけ。「眠っている」は保存せず最終メモの日付から導出) / 誕生日と出自
- **メモ**: 所属アクティビティ / 日付 / 種類 (**やった** or **やりたい**) / 本文一行 (本人の言葉 — システムは構造だけ読み、本文は解釈しない) / 期間参照 (やったメモ = その活動のティック・会話の範囲、やりたいメモ = 願いが生まれた範囲。生ログへの降り口)

**粒度は欄の分割で守る**: 捕獲スキーマで「アクティビティの名前 (活動粒度・例つき誘導)」と「今日の中身一行 (具体)」を別欄にする — 詳細を書きたい圧は中身欄が吸い、名前欄が「星を拾う話の小説を書く」で汚れない。二度目以降はアクティビティ一覧の閉語彙が統合方向に働く (同じものを二度発明するのは不自然な続き)。細かすぎるアクティビティが生まれても実害は一覧の一行 — 減衰なし哲学のまま、掃除は本人の明示かユーザー。

**旧概念の行き先**: 品書き (レパートリー) = アクティビティの名前一覧の眺め (メモゼロのアクティビティも並ぶ。キャラ作成時の初期関心は空のアクティビティ) / 旧「手帳」(自由文の願いの置き場) = 全アクティビティのやりたいメモの眺め — 名前は器全体へ昇格した / 年表 = 一本のアクティビティのやったメモの眺め。§4.1 の台帳三つは「ルーチン / タスク帳 / **手帳**」と読み替える (用語は 2026-08-19 裁定)。§4.3 の「台帳の行ではなく本人の文章として住む」は上書き (まはー裁定 2026-08-16「構造化していい? という問いなら Yes」— 機械の消費者 (サンプリング・所属・刻印) が生まれた今、自由文のままだと機械が本文を解釈する羽目になり、メモに割る方が「中身を読まない」の芯を守れる)。

### 13.2 読み口 — ふと目に入る (v0.4)

- 知覚の差し込み: 中断したやったメモと未消化のやりたいメモから、直近を避けた乱択で一本、低頻度でティックの尻尾へ知覚として。**内容の著者は本人・機械が決めるのはタイミングだけ** (操り人形の回避、§12.2)
- **次のティックに降り口の中身 (生ログ) を無条件配達** — 拾ったかの信号を要求しない。拾わなければ配達が捨てられるだけ
- 検算済み: 小説の固定点 (§12.3) が「一日目に糸が生まれ、数日後の差し込み→配達で内容ごと再開」の形で通る

### 13.3 捕獲の一本化 — スルースが「確実に通るゲート」になる

**本人の声の捕獲は、スルースの一手に全部集める** (まはー裁定 2026-08-16)。会話終了判断は退役 (§6・§8)。理由: 会話に切れ目は定義できず、「30 分沈黙 = 会話の終わり」という恣意的な仮定の上の席だった。未確定の約束を拾うリスクは会話終了判断でも同じで、差がない。Metabolism は自律と無関係に全ペルソナで走るため、自律 OFF ペルソナの捕獲が二級になる欠陥 (§9-E の族) も構造ごと消える。

- **スルースの一手が問うもの (洗いざらい)**: ①コア記憶 ops (既存: add/update/remove) ②やりたいメモ (旧・手帳採取の後継) ③**やったメモ / アクティビティ** (機械が帳簿の重ねを添える: 「この範囲にはあなたの自由時間 (ティック n, m) が含まれる」) ④**約束** (タスク帳への追加・更新 — 未確定を拾ったら次の一手で更新すればよい)。アクティビティ一覧・コア記憶現況を同梱 (閉語彙・再提案防止)
- **失敗を許さない格に昇格**: スルースが失敗したら退場を止めて再試行 (あらすじ生成と同格)。従来の「失敗しても退場が進む」は廃止。**価値 (まはー)**: このコストに見合う対価は「**全ての経験が、退場の前に必ず一度、ペルソナ本人の目による構造化出力での解釈・記録を通る**」ことが確定する点
- ライフ終わりのルーチンは純粋に任意の習慣 (日記) に戻る — 捕獲の義務は背負わない
- 標準モデル・温かいキャッシュの一手のまま。判断点 (軽量) から移ることで捕獲の質はむしろ上がり、追加コールはゼロ

### 13.4 v0.3 / v0.4 の割り振り (この節の実装)

### 13.6 スキーマ具体形 (2026-08-18 まはー承認)

§9-1 の決着。置き場・欄の並び・書き手の口まで、実装に渡せる粒度で確定した。

**置き場 = memory.db (SAIMemory、ペルソナごとの SQLite) に新テーブル二枚**。理由: メモの期間参照はメッセージ ID を指すため、メッセージと同じ DB なら参照が壊れず、バックアップ・復元も一体になる。書き手のスルースも Metabolism 内 = memory.db を開いている文脈で走る。

- **activities**: `id` (自動採番) / `name` (活動粒度の名前) / `status` (`open` | `closed`) / `born_at` / `origin` (`sluice` = スルースが立てた | `user` | `initial` = キャラ作成時の初期関心 | `migration` = 既存データの写し替え) / `closed_at` (明示があった日付。開いている間は NULL)。「眠っている」は列にせず最終メモの日付から導出 (§13.1)。
- **memos**: `id` / `activity_id` / `date` (日粒度) / `kind` (`did` | `want`) / `text` (本人の言葉一行 — システムは解釈しない) / `span_start_id`・`span_end_id` (生ログへの降り口 — **本人には書かせず機械が刻印**。スルースの一手が担当した範囲 = 前回のパンマーカーから今回までのメッセージ ID 区間。本人の申告に範囲の正確さを求めない — §12.1 でタグの書き手を機構にしたのと同じ理屈)。
- **導出であって列にしないもの**: 「未消化のやりたいメモ」= 同じアクティビティにそれより後のやったメモが無い / 「中断したやったメモ」も同様に導出。列にすると「消化した」を書く義務が生まれ、書き漏れ = 嘘の列になる。導出は嘘をつけない。

**閉じる口の制限 (v1 の教訓)**: アクティビティの `closed` は「本人かユーザーの明示だけ」(§13.1) — これを構造で保証するため、**スルースの応答スキーマに close 操作を置かない**。定常の一手に閉じる口があると「なんとなく閉じる」が起きる (v1 で Track が一発で閉じられまくった前例)。閉じる口はユーザーの UI 操作と、本人の明示的な行動 (スペル等、v0.4 で設計) だけ。closed_at は機械の消化印ではなく、明示という出来事の日付 (born_at と同じ性質)。

**スルースの応答スキーマ拡張** (現行 `reflection` + `ops` (コア記憶) に追加。Gemini 制約 = フラット・additionalProperties なしは現行と同形式で守れる):

- `want_memos` / `did_memos` — 各要素は三欄: `activity_id` (同梱する一覧 = 閉語彙から選ぶ) / `new_activity_name` (一覧に無いときだけ。活動粒度の例つき誘導を description に書く) / `text` (今日の中身一行)。**「粒度は欄の分割で守る」(§13.1) の実装がこの二欄分離** — 具体を書きたい圧は text が吸う
- `promises` — タスク帳への操作列: `op` (`add` | `update`) / `content` / `due` (**省略可 — 省略 = 期限なし**。期限のない約束に期限を発明させない、2026-08-19 裁定) / `task_ref` (update 対象)。**器はタスク帳で、手帳には入れない** (下記)
- プロンプト同梱物: アクティビティ一覧 (ID + 名前、開いているものだけ) / コア記憶現況 (既存) / 帳簿の重ね (v0.4 から)

**手帳とタスク帳は統一しない (2026-08-17 裁定)**。手帳 = **記録の層** (システムは構造だけ読み本文を解釈しない。メモは閉じない・減衰なし)、締め切り = **運転の層** (機械が due を読んでティックの割り付けが動き、完遂で閉じるキュー)。混ぜると「中身を読まない」の芯が壊れ、単発の約束がアクティビティ一覧を汚す (粒度問題の裏口再輸入)。スルースの振り分けはスキーマ上きれいに割れる: **相手のいる約束・依頼はタスク帳へ (期日は省略可)、自分だけの願いはやりたいメモへ** — 振り分けの軸は期日の有無ではなく相手の有無 (2026-08-19 裁定で精密化)。ただし**現行の統合タスクテーブルはそのまま生き残らない** — v3 で Track 小目標が消え desire 候補は手帳へ写るため、残る仕事は「締め切りの一件」だけ。desire 系列・stage の木・parent_kind を背負った現在形を、痩せたタスク帳へ作り直す (§9-8 移行と合流)。

**B2 欄と辺の格納**: entity_extractor の同一コールに `involved_entities` (この範囲が関与した既存ページの列挙) を一欄追加 — 8/2 実験の B2 方式そのまま、生成後にタイトル→page_id 解決の層を挟む (recall_tags §9.3)。辺は memory.db の新テーブル一枚 **chunk_page_edges** (`chronicle_page_id` / `entity_page_id`) — チャンクも実体も Memopedia ページなので辺はページ ID 同士。役目は選別ではなく遡りの材料 (§12.1)。
