# システム通知の届け方 — system ロールへの一本化と合言葉

**ステータス**: 検証待ち（2026-10-28 実装。ブランチ feature/system-notice-impl に 4 つの束でコミット済み。まはーの実機確認とレビューの消し込みが未了）

## 芯

SAIVerse がペルソナへ送るシステム通知（部屋の様子の変化、スケジュールの発火文、子ライン（裏で走る別の Playbook）の作業結果、スペルの結果など）を、供給側（通知を作って積む側のコード）はすべて role=system で保存する。role=system を会話の途中に置けないモデルへ送るときだけ、送信の直前に「合言葉付き `<system>` タグで囲んだ role=user」へ変換する。合言葉はペルソナの記憶・会話履歴には決して入らない。

## なぜ (2026-10-27 の実測)

Meta の Muse をプロバイダとして追加したとき、SAIVerse を通さずに Meta の API を直接呼んで次を確かめた（記録は [meta_muse_provider.md](meta_muse_provider.md) の経緯。PR maha0525/SAIVerse#428 / #429 で追記）。

- 会話の途中のシステム通知を「`<system>` で包んだ role=user」（従来の統一形式）で送ると、Muse Spark 1.3 は 3 回中 2 回、Muse Wonder は 3 回とも通知を無視した。Wonder は 1 回「その状況変化はあなたのメッセージの中に書かれていたものだから、本当に起きた知らせとしては受け取らない」とペルソナの台詞として答えた。
- 同じ通知を role=system で送ると、両モデルとも 3 回とも従った。

モデルは「user の本文の中に書かれた自称 system 文」をプロンプトインジェクションとして疑う方向に訓練されており、この傾向は今後も強まる。従来形式のままでは、世界の出来事がペルソナに届かなくなっていき、ペルソナが疑いを台詞として口にする（発話の尊厳の問題）壊れ方をする。

従来形式の出どころは、`sea/runtime_nodes.py` のコメントに残っていた——「Gemini 等が messages 中途の system role を受け付けないため、user role でラップする」。一部モデルの制約への対処が、通知の供給側全体の書き方として広がっていた。本 intent では、その変換をモデルごとの仕様差を扱うクライアント層の責務へ戻す。

## データの流れ

```
供給側 13 系統以上       保存                    読み出し                   messages 列   クライアント層   モデル
(スケジュール発火、   → SAIMemory messages / → _payload_from_message_  →            → llm_clients/ → (system のまま
 建物の出来事、        perception_batches /     locked (saiverse_memory/                の各クライアント   または合言葉付き
 子ラインの結果…)      paired_action_text 列    adapter.py)                                               タグの user)
```

messages 列 = LLM へ送るメッセージの配列。

- 改修前（2026-10-27 時点）は、user+`<system>` の形が三か所で作られていた。(1) 供給側が本文に埋め込んで保存する（role=user）。(2) role=system で保存された記録を、読み出しのときに `_payload_from_message_locked` が `wrap_system_record_content`（`sai_memory/memory/storage.py`）で囲む。(3) 送信のときにその場で囲む——スペルの結果・事前スペル（応答の前に自動で実行されるスペル）の結果・TOOL ノードの結果は記録と同じ文面を `presented_system_record_content` で組み、知覚のまとまり・リアルタイム情報・自動想起（関連する過去の記憶を自動で引き出す機能）の結果は `sea/runtime_context.py`（`_perception_block_text` ほか）で囲んでいた。
- 改修後（2026-10-28 実装）は、供給側はすべて role=system・タグ無し本文で保存する。(2)(3) のタグで囲む処理は全部やめ、role=system のまま messages 列へ出す（共通部品は `sai_memory/memory/storage.py` の `system_notice_message`。`wrap_system_record_content` は削除した）。タグで囲むかどうか・どう囲むかの変換はクライアント層（`llm_clients/system_notice.py`）だけで行う。(2)(3) は対で変えないと、送った列と次のターンの復元が食い違い、[persist_realtime_and_recall.md](persist_realtime_and_recall.md) 不変条件 1（前回の送信は今回の送信の先頭そのもの）が壊れるので、同じリリースで両方を変えた。

調査の全件一覧（供給側の一覧、保存形式の分類、各系統の識別用 metadata）: [2026-10-27_system_notice_survey.md](../handoff/2026-10-27_system_notice_survey.md)。

## 不変条件

1. **システム通知の保存形式は role=system、本文はタグ無し。** 本文に `<system>` を埋め込む供給側を新設しない。識別用の metadata の鍵は一つに定義して全系統で揃える。鍵は `__system_notice__`（`sai_memory/memory/storage.py` の `SYSTEM_NOTICE_KEY`）で、値はその通知を作った系統の ASCII snake_case 名（`schedule`、`building_event`、`subline_report` など）にした。`docs/concepts/saimemory.md` の「システム通知には `event_message` タグ必須」の規則はここで合流させ、識別の正は `__system_notice__` とした（既存の tags は残っていて、あらすじの機構名義の判定などは今も tags を読む）。
2. **role=user を role=system へ変換する仕組みを持たない。** 「本文が `<system>` で始まるか」を意味の判定に使う常設コードを置かない（移行の一回だけが例外）。ユーザーや外部の文章がシステム通知に化ける経路は、移行後の世界のどこにも無い。例外は運用者自身の手: 記憶ブラウザの編集 API とインポートスクリプトでは role=system の行を作れるが、それは所有者が自分の世界に行う管理行為として認める。
3. **合言葉はペルソナの記憶・会話履歴・ログ・画面に出さない。** 保存してよいのは head（プロンプト先頭部）の実体 `SessionHeadSnapshot`（(persona_id, model_key) に一つ — [beat_execution_context.md](beat_execution_context.md) §3.1）の `PASSPHRASE` 列だけ。head の作り直しのたびにランダムに生成し直す。head の本文には仮置きの記号（`{{SYSTEM_NOTICE_PASSPHRASE}}`）を書き、実際の値はクライアント層の最終変換でだけ差し込む——SAIVerse 層で messages を写す口（`llm_io.log` を書く `_dump_llm_io`、画面へ返す `/api/chat/preview`）に値が乗らないようにするため。
4. **識別用の metadata はサーバーだけが書ける。** 送り手から届く metadata を選別する処理（`api/routes/chat.py` の `_client_metadata`）は禁止リスト方式で、改修前は `tags` と `with` が素通りしていた（= 既存の識別用 metadata は送り手が偽造できた）。システム通知の識別に使う鍵は「送り手の入力から必ず取り除かれる領域（`__` 始まり）」に置き、あわせて `tags`・`with` も送り手から書けないよう閉じた。X・Discord など外部由来のテキストは本文としてしか入らないことを保つ。
5. **システム通知の時系列上の位置は保たれる。** 変換は元の位置で行う。先頭へ寄せてよいのは head 由来の system（人格指示）だけで、その判定は「先頭に連続しているか」という位置ではなく、head 由来であることを示す metadata（`__head__` = `HEAD_MESSAGE_KEY`。記録には保存しない）で行う（履歴が空のターンでは、冒頭の通知が人格指示と区別できなくなるため）。
6. **同じ head を使い続けている間、同じ記録から組み立てる送信本文は一字も変わらない**（persist_realtime_and_recall.md 不変条件 1 の継承）。一致を取る対象が「保存した本文そのまま」から「クライアント層の変換後の本文」へ移る。合言葉の更新は head の作り直しと同時にだけ行う。
7. **他ペルソナ・ユーザーの発話は role=user のまま。** 世界の中の発話はシステム通知ではないので、role=system 化の対象にしない。

## 設計

### 保存 — 供給側の正規化

全件一覧の 13 系統（本文に `<system>` を埋め込んで保存していた供給側）を、role=system・タグ無し本文 + 識別用の metadata `__system_notice__` での保存に変えた（#13 の添付アイテム作成の注記は保存されていなかったので、提示側で扱った — 下の「移行」の節）。Playbook の MEMORIZE でツールの生の結果をタグ無しの role=user で保存していた Playbook も、`MemorizeNodeDef` の既存の `role` フィールドで role=system に変えた（DB への再 import がリリース手順に要る）。他ペルソナの発話（`名前: 本文`）は role=user のまま変えない。

保存経路の注意: `persona/history_manager.py` の `_sync_to_memory` は、改修前は role=system の行を警告を出さずに読み飛ばしていた（`("skipped", None)` が返る）。スケジュール発火文と建物の出来事はこの経路（`add_to_persona_only`）を通るので、role を変えるだけでは記録が消える。実装では、`__system_notice__` を metadata に持つ role=system の行だけを記憶へ書き、印の無い system 行（入室案内など、機構がその場の状況として積むだけの行）は従来どおり書かない形にした。

### 読み出しと messages 列の組み立て

`_payload_from_message_locked` は、role=system を role=user + タグへ変換するのをやめ、role=system のまま metadata 付きで返す。送信のときにその場で包んでいた箇所（データの流れの (3)。スペル・事前スペル・TOOL・子ラインの報告、知覚のまとまり・部屋の様子、リアルタイム情報・自動想起、時刻の目安・自律行動の記録・あらすじの畳み・keep-alive、作業セッションの指示書・tell・コマの締め、音声通話の host 行など）も role=system の通知として出す。paired_action_text（発話の記録に対で付く指示文の控え）も、保存形式をタグ無しにし、展開のときに role=system の通知として出す。

添付アイテム作成の注記は、ユーザー発言の本文へ連結するのをやめ、発言の直後に独立した role=system の通知（`__system_notice__` = `attachment_note`）として置く（`sea/runtime.py` の `_enrich_history_with_attachments`）。発言の本文はユーザーが言った言葉そのままに残る。

head の自分の姿（self_view）は、タグだけ外して role=user のまま置いた（理由は経緯の 2026-10-28 の項）。

### クライアント層の変換と合言葉

- 判定と変換は `llm_clients/system_notice.py` の一枚にまとめた。会話の途中の role=system を受け取れるかの判定（`accepts_mid_conversation_system`）は、`xai_native` は受け取れる側、`openai_compat` と `nvidia_nim` はモデル設定の `convert_system_to_user` が真なら受け取れない側・それ以外は受け取れる側、それ以外の protocol（`anthropic_native`・`gemini_native`・`openai_codex`・`ollama_compat`・未知の protocol）は受け取れない側にした。
- 会話の途中の role=system をそのまま送れるモデルへは、そのまま送る。Muse は直接呼び出しで実測済み。ただし Meta のプロバイダ定義（`builtin_data/providers/meta.json`）の `default_convert_system_to_user: true` を外す PR #429 は 2026-10-28 時点で未マージで、このブランチでは Muse はタグで囲む側に落ちる。OpenAI と xAI（`llm_clients/xai.py` は途中の system をその場に置く）は仕様上受け付けるが、SAIVerse の messages 列に途中の role=system が現れるのは本 intent が初めてなので、実サービスでの実測は検証計画に残っている。
- 置けないモデルへは、送信の直前に `<system pass="合言葉">本文</system>` の role=user へ元の位置で変換する（`present_system_notices`）:
  - OpenAI 互換（`llm_clients/openai_message_preparer.py`）: head の印を持つ列では `convert_system_to_user` を「途中の system を合言葉付きタグで囲む」の意味で読む（true を宣言している既存モデル定義は、タグで囲む側 = 安全側に落ちる）。head の印を持たない列（要約・判定など、head を組まない呼び出し）は従来の扱いのまま。
  - Gemini（`llm_clients/gemini.py`）・Anthropic（`llm_clients/anthropic_request_builder.py`）・Codex（`llm_clients/openai_codex.py` — instructions へ寄せる）: 先頭の system 欄へまとめるのは head の印を持つ system だけにし、途中の system は合言葉付きタグの role=user へ元の位置で変換する（不変条件 5）。Codex は、この変換（OpenAI 互換と共通の `prepare_openai_messages`）が例外で失敗したら送信を中止する。元の messages のまま送ると、通知が instructions へ寄って位置を失い、伏せ字の無い本文が送られるため。
  - Ollama（`llm_clients/ollama.py`）: チャットテンプレート次第で途中の system が落ちうるので、タグで囲む側に倒した。Ollama は messages を HTTP の本文へそのまま載せるので、送信の直前に各メッセージを API が定義する欄（role / content / images / tool_calls / tool_call_id / name / tool_name）だけの新しい dict へ組み直し、SAIVerse の内部の metadata（思考・出力の分け方・通知の印や本文の写しなど）を一切送らない。通知の画像は metadata にしか無いので、組み直しの前に扱う。タグの中の本文は他のクライアントと同じく「元の本文 + metadata の全部の画像の説明の文」で固定する。画像そのものは、画像に対応するモデルでも送らない — Ollama のクライアントは通常のユーザーの発言の画像も送っていないので、通知の画像・音声・動画も同じく説明の文だけで届く（経緯の 2026-10-28 Codex 6 巡目の欄）。組み直した後の `tool_calls` と、文字列でも部品の並びでもない本文（辞書のまま渡るツールの結果）は、すべての文字列からその送信の合言葉を伏せる（`redact_passphrase_in_value`。head の本文は除く）。
- 画像を持つ通知の扱い: タグで囲む側では、metadata の media を引き継いで role=user のまま画像を埋め込む。そのまま送る側では、system メッセージは文字しか持てないので、画像は説明の文（`llm_clients/system_notice.py` の `system_notice_image_note`）に置き換わり、通知の本文の後ろに足される（OpenAI 互換・xAI とも。本文が空で画像だけの通知も、空のメッセージとして落とさずに説明の文で残す）。説明の文は、記録の metadata の画像の項目に保存済みの要約（`summary`）があれば `[画像: <uri>] <要約>`、無ければ `[画像: <uri>]` だけで、その場で要約を生成しない — 生成する `image_summary_note` を使うと、生成の成否で同じ記録から組む送信本文が変わり、不変条件 6 が割れる。タグで囲む側でも同じ説明の文を使い（OpenAI 互換・Anthropic・Gemini。タグ化した通知は role では見分けられないので、`present_system_notices` が写しに付ける `__system_notice__` で見分ける）、タグの中の本文は、画像・音声・動画を埋め込めたかどうか（対応のモデルか・枚数の上限の内か・ファイルが読めたか）にかかわらず「元の本文 + metadata の全項目の説明の文」で固定する（`system_notice_media_notes`。説明の文は metadata の記述だけから metadata の並びの順に組む）。埋め込めた項目は、説明の文に加えて部品としてタグ付きの本文の後ろに続く。説明と埋め込みが重複するのは受け入れる — 読み込みの成否で同じ記録から組むタグの中の本文が変わると不変条件 6 が割れ、決定性のほうが優先だから。画像のファイルが消えていても、metadata の画像の項目から説明の文を作り、通知ごと消さない。通知に付いた音声・動画も同じ規則で、保存済みの要約か URI だけの `[音声: <uri>]` / `[動画: <uri>]`（`system_notice_media_note`）にし、その場で要約を生成しない（Gemini と、音声・動画を文字に落とす各クライアントの共通の経路 `llm_clients/base.py` の `_inject_unsupported_media_summaries`。後者も metadata の並びの順に全項目を並べるので、ファイルの有無で説明の文の数と順序が変わらない）。この共通の経路は送る直前の前処理なので、一つの送信に一度だけ掛ける — Anthropic の構造化出力のストリームは同期の generate へ委ねるので、委ねる前には掛けない（二度掛けると説明の文が二重になり、同期の送信本文と食い違う）。説明の文は通知の本文の一部なので、タグで囲む側では、クライアントが通知の最終的な本文（元の本文 + 説明の文）を先に組み、その全体を合言葉付きタグで包む（`tag_presented_system_notice`。`present_system_notices` がタグ化した通知の写しの metadata にタグで包む前の本文を残す。この写しは送信の本文には載らない）。閉じタグの後ろに説明の文を足すと、画像だけの通知では証明されたタグの中身が空になり、説明は合言葉の外の普通の user の文章になるため。埋め込む画像・音声・動画は部品なのでタグで包めず、タグ付きの本文の後ろに続く。そのまま送る側では、説明の文は合言葉の変換の後で本文に足されるので、保存済みの要約に現れた合言葉はそこで伏せ、`<system` も無害化する。伏せるのはその送信の head の合言葉だけにする — プロセスが覚えている合言葉の全部で伏せると、別の head の合言葉が登録されただけで同じ記録から組む送信本文が変わり、前方一致が割れる（不変条件 6）。通知以外の発言に、変換の後で足す画像の要約（その場で生成したもの）も、同じくその送信の合言葉で伏せる。
- 変換のとき、通知本文の中に引用で入った `<system` / `</system` は全角の `＜` で始まる文字列にして無害化する。あわせて、通知以外のメッセージ本文と `tool_calls` の引数、それに metadata の `reasoning_details`（前のターンの思考。OpenAI 互換のクライアントが `reasoning_passback_field` で次のリクエストへ送り返す）の思考の文（`text` / `summary`。署名や暗号化された欄は触らない）に現れた合言葉は伏せ字にする（合言葉がモデルの返答に復唱されて記録に残った場合の再利用を防ぐ）。本文が部品の並びのときは、部品をまたいで連結した文字列で伏せる（各クライアントは文字の部品を連結して送るので、部品ごとに伏せると、二つの部品に割った合言葉が素通りして連結で元に戻る）。置換は文字数を変えないので、連結した文字列を元の部品の長さで切り戻し、部品の数・順序と画像などの部品は変えない。この変換は文字列だけを伏せるので、辞書のまま渡ってきたツールの引数・結果は、クライアントが送る形へ変換した後で伏せる: Codex は辞書の引数を JSON の文字列にした後と、辞書の結果や部品を文字列にした後（ツールの結果・ツールの引数・assistant の本文）に、その送信の合言葉で伏せる（system と user は伏せない — head と合言葉付きタグに合言葉が正当に入る）。Gemini は FunctionCall の引数と FunctionResponse の結果を辞書のまま送るので、その中のすべての文字列（辞書の鍵も）を伏せる（`redact_passphrase_in_value`）。
- ログへの非漏洩: 各クライアントは送る形や応答をそれぞれの形でログへ書き、応答に復唱された合言葉は書く側では見分けられない。そこで `present_system_notices` が差し込んだ合言葉をプロセス内で覚えておき（`llm_clients/system_notice.py`）、ログの各ハンドラ（backend / llm_io / error / sea_trace / timeout_diagnostics — `saiverse/logging_config.py` の `_redact_passphrase_filter`）が書き出す直前に、どのログ行（例外の文も含む）からも伏せる。伏せ字はログ行ごとの一致なので、応答の断片を別々の行に書くと、復唱された合言葉が行をまたいで割れて素通りし、行の連結で元に戻る。だから Gemini のストリームは、チャンクごとの本文（SSE の各 payload・チャンク・差分）をログに書かず（大きさなどの要約だけ）、応答の全文を組み立て終わった後の 1 レコードで書く。ツール呼び出しも同じで、OpenAI 互換のストリームの名前と引数の断片は長さだけを書いて結合後の名前と引数を 1 レコードで書き、Gemini のストリームの関数呼び出しはストリームの後で採った一つを 1 レコードで書く。ツールの引数を state へ一つずつ展開するときのログ（`sea/runtime_llm.py`）も、引数ごとの中身を書かず型と長さだけにする（引数全体は呼び出しを検出したときの 1 レコードに載る）。Codex の読めなかった SSE の payload も中身を書かない（大きさだけ）。ログの伏せ字は多層防御の二層目である。一次の柵は送信時の伏せ字で、復唱・漏洩した現行の合言葉は、どの入力経路から入っても送信の前に伏せられるので、通知の偽造には使えない。だからログの中の断片の再結合（複数のレコード・複数の欄にまたがる形）までは追いかけず、断片の中身をログに書かないことを優先する（ストリームの断片のログをやめたのはその形）。覚えておく合言葉は最後に使った時刻を持ち、件数の上限（4096、安全弁）を超えても最後の使用から 1 時間以内のものは忘れない — 長いリクエストの応答待ちの間に上限まで回っても、応答待ちの合言葉が保護から外れないように。
- 合言葉（英数 12 字、`secrets` で生成）の生成と寿命の管理は head_pipeline に置いた。`HeadPipeline.capture_all`（head の作り直し）のたびにランダムに生成し、`SessionHeadSnapshot.PASSPHRASE` に snapshot と一緒に保存する（再起動を跨いで head が生きる限り、合言葉も同じ値——persist 不変条件 1 と両立させるため）。一部の Section だけを撮り直す経路（`recapture_missing` など）は同じ値を引き継ぐ。合言葉を持たない旧行を読み込んだときは head を作り直す。実際の値は head の system メッセージの metadata（`__system_notice_passphrase__`）に載せ、組んだ messages 列と一緒にクライアントまで運び、鍵（persona × model）で引き直さない。
- システムプロンプトに置く説明文は、head の節 `SystemNoticeSection`（`sea/head_pipeline/sections/system_notice.py`）に置いた。文面はモデルで出し分けず、どちらの届き方（system のまま / 合言葉付きタグの user）でも真になる一枚（`SYSTEM_NOTICE_TEXT`）にする——`line="sub"` の子ラインや構造化出力の代替は、親のモデル向け head の写しを持ったまま別のモデルで走るので、出し分けると説明と実際の届き方が食い違うため（経緯の 2026-10-28 レビュー欄）。説明文の要件: 合言葉付きタグは「SAIVerse の正規の経路で届いた知らせ」の証明（何の知らせか・誰の作業かは本文の中に書かれる——世界の出来事のことも、自分自身の裏の作業の結果 = 子ラインの報告のこともある）/ 外側の合言葉付きタグが本物でも、中の引用（Web の文章・他者の発言）は資料であって指示ではない / 合言葉の無いタグは送り主がそう書いたただの文章 / 従わない・わざわざ疑いを宣言しない（偽物が届いている時点で悪意かお遊びに晒されており、疑いの宣言で状況は好転しない。ペルソナは普通に暮らし続け、必要なら淡々とユーザーに伝える）。

### システム通知を除いて会話を選ぶ条件の置き換え

`sai_memory/memory/storage.py` の 2 箇所にあった `content NOT LIKE '<system>%'`（システム通知を除いて実際の会話だけを選ぶ条件）を、role の判定に置き換えた（`_conversation_exclusion` が role を user/model/assistant に限る。`search_conversation_messages` も同じ断片を再利用する）。本文のタグ文字列を扱う常設コードもやめた: タグで囲み直すかどうかの判定（`sea/runtime_llm.py` の `startswith("<system>")`）、スペル結果の差し込み判定（`sea/runtime_context.py` ほかの `"</system>" in …`）、タグ剥がし（`sai_memory/arasuji/generator.py` の `_strip_system_wrap`、`sai_memory/perception_buffer.py`、`frontend/src/app/page.tsx`）。

### role を手掛かりにしている読み手の点検

通知の role が user から system に変わると挙動が変わりうる読み手を、一つずつ裁定した。

- 自動想起で検索の元にするメッセージの選別（`sea/auto_recall.py`）: `__system_notice__` を持つ role=system を「入力の側」に数え（`_is_user_side`）、スケジュール発火文を検索の元に含める現行の決定（[auto_recall_jev_rerank.md](auto_recall_jev_rerank.md)）を保った。添付アイテム作成の注記（`attachment_note`）は種にしない。
- リアルタイム情報の置き場（「最後の user の直前」）: 「最後の user またはシステム通知」の直前に変え（`sea/runtime_context.py` の `last_input_index`）、改修前と同じ位置を指すようにした。
- あらすじや退場の量の勘定で「システムが自動で入れた行」を見分ける判定: 従来の判定（tags）のまま据え置いた（経緯の 2026-10-28 の項）。

### 移行 (database/system_notice_migration.py)

- **置き場と起動**: 移行は `database/system_notice_migration.py` に置いた（当初の案の `database/migrate.py` ではない）。`main.py` が起動のたびに、本体 DB のスキーマ同期の後、バージョンアップグレードと SAIVerseManager の初期化（ペルソナの記憶 DB を開く処理）の前に `run_startup_system_notice_migration` を呼ぶ。
- **一回限りにする仕組み**: ペルソナの記憶 DB は、その DB の `embed_metadata` に完了の印（`system_notice_migration_done`、値は `v<規則の版> <完了時刻>`）を書き、今の版の印があれば何もしない。印の版（`MIGRATION_RULES_VERSION`）は、済んだ DB にも当て直す必要のある規則を足したときに上げる。印の版が古い DB は、その後の版で足した規則だけで走査し直して印を今の版へ書き換える（版 1 の印は版を書く前の形で、値が完了時刻だけ）。版 2 で足したのは 1 の旧世代の個別条件で、版 1 の移行を済ませた DB ではその条件だけを当て直す。変換済みの行はタグで始まらないので素通りし、版 1 で「系統を判定できなかった」として付けた確認待ちの印は、通知に変換した行からだけ外す。版 1 で変換しなかった行は版 1 のレポートと確認待ちの印にあるので、走査し直しでは数え直さない。ただし、確認待ちの印（下の「確認待ちの印」）を付けるべき行があるのに付けられない記憶 DB（`messages` に metadata の列が無い古いスキーマ）には完了の印を立てず、変換だけをコミットする。次の起動では通常の初期化（`init_db`）が列を足しているので、走査し直して確認待ちの印を付け、そのとき完了の印を立てる。本体 DB は印を持たない。変換の条件（タグで始まる・未配送・prepared など）を満たす行は変換すると条件から外れるので、毎起動呼んでも二度目以降は何も書かない。この前提を保つため、剥がした結果がまだ `<system>` で始まる行は剥がさない（下の「剥がし方」）。
- **対象（全数）**:
  1. ペルソナの記憶 DB の `messages` のうち、本文が `<system>` で始まり、**かつ**その系統の識別用 metadata を持つ行。タグを剥がし、role=system + `__system_notice__`（値は系統名）にする（`classify_tagged_message`）。拾う系統は、スルースの採取記録・ライフの境界・記憶整理・知覚（知覚のレンダリングより前の世代）・バージョンアップの知らせ・音声通話・建物の出来事・その他の `event_message` を持つ行・スルースのダイジェスト・Track 切替通知（`track_context`）・Track の Chronicle 挿入（`track_chronicle_insert`）・状況変化（`situation_change`）・スケジュール入力（`with:["system"]`）・子ラインの報告と MEMORIZE（`playbook:` タグ）、それに中断の記録（role=assistant + `interrupted` タグ）。
     系統の印（`with:["system"]`・`event_message` など）を持たない旧世代の正規の通知は、本番 DB の写しへの dry-run レポートから系統を確定し、個別の条件で拾う（`legacy_notice`。上の印で系統が決まる行はそちらが優先）。確定したのはスケジュールの発火文と外部イベント通知の二つで、条件は「role=user・tags が `conversation` だけ・ユーザーの発言の来歴を持たない（下の「来歴の縛り」）・タグの剥がしが成立する・剥がした本文の先頭が `スケジュールの実行時刻です` / `スケジュールが実行されました`（かつ metadata に発火の記録の `schedule_id`）、または `[外部イベント通知]`（かつ metadata の `source` が `external_event`）」の全部。系統はどちらも `schedule` にし、確認待ちの印は付けない。レポートの件数は `messages / schedule(旧世代)` と `messages / external_event(旧世代)` に分けて書き、印で拾った `schedule` と区別する（一つの表記にまとめると、系統ごと 3 件のサンプル枠をスケジュールが埋めて、外部イベントの件数とサンプルが見えなくなる）。
     **来歴の縛り**: `schedule_id` と `source` は送り手（チャットの送信 API）も metadata に書けるので、本文と metadata だけではユーザーが発火文の形を打った発言と区別できない。旧世代の発火文は、ユーザーの入力と同じ記録の経路を通って書かれていたので、書き手を表す列も無い。そこで、ユーザーの発言が持つ来歴の印で縛る。記憶 DB では、建物履歴からの転記の印 `building_msg_ref`（2026-07-21 から転記が必ず刻む。今のコードでユーザーの発言が記憶に入る経路は転記と通話の文字起こしだけ）と、通話の文字起こしの印（`voice_call` / `voice_transcript`）を持つ行を拾わない。本体 DB の `building_messages` では、旧世代の書き手の列（`legacy_seq` / `legacy_message_id`。旧ログの取り込みと、ペルソナ側の番号を持ち込んでいた世代の書き込みだけが埋める）を持ち、画面からの送信の印 `client_message_id` を持たない行だけを拾う（`_written_by_old_writer`）。本番の写しで確かめた分かれ方は、記憶 DB の正規の旧発火文 306 件はどれも転記・通話の印を持たず、転記の印を持つ user 行は 723 件。`building_messages` の正規の旧発火文 171 件は全部が旧世代の列を持って `client_message_id` を持たず、画面から送られた 1039 件は全部 `client_message_id` を持ち、2026-09-06 より後に書かれた行に旧世代の列を持つものは無い。縛った後も、写しの 477 件はそのまま拾う。
     **縛れずに残る範囲**: 旧世代の時期（2025-12〜2026-07）に、送信 API へ手で `schedule_id` などを書いて送った発言は、正規の発火文と列でも metadata でも区別できない（同じ記録の経路を通ったため）。画面はこの時期も今も metadata を送らない。写しでは、`schedule_id` / `source=external_event` を持つ行は全部が発火文の形（中断の再開文が引用した 1 件を除く）で、送り手が書いた形跡は無い。この残余は受容した。書き出しが本文の途中にだけある行（中断の再開文が元の発火文を引用している形）・X の投稿指示（`以下の指示やトピックに基づいて…`）・Memory Recall・メタ判断の文・stackchan などの音声入力の通知は、出自の確度が足りないので拾わず、確認待ちの印のまま残す。
  2. 同じ表の、印の無い role=system 行（スペル・事前スペル・TOOL・Handy Tool・権限拒否・実行エラー・MEMORIZE の結果）。tags から系統を推定して `__system_notice__` を付ける（`classify_unmarked_system_message`）。推定できない行には `__system_notice__` を付けず、確認待ちの印（下の「残すもの」）を付けて、件数をレポートに出す。
  3. `messages.paired_action_text` のうち `<system>` で始まる値。タグを剥がす。
  4. `perception_batches` の kind=`realtime_and_recall` の `rendered_text`。`<system>…</system>` の塊（リアルタイム情報と自動想起）を連結した本文で、旧 `build_turn_realtime_and_recall_message` は片方しか無いターンでもその一つの塊だけで保存したので、塊が一つか二つの行を剥がし、二つなら塊どうしを `\n\n` で繋ぐ。これは提示の最終形（`compose_turn_realtime_and_recall_content`）と一字一致する。kind が違うタグ始まりの行は変換せず、レポートに出す。
  5. 本体 DB の `building_messages` のうち、音声通話の痕跡（role=user + タグ + `event_message` + `voice_call`）と、1 の旧世代の個別条件に当たるスケジュールの発火文・外部イベント通知。今の建物の出来事の行と同じ形（role=host・タグ無し、metadata はそのまま）にする。旧世代の分は、1 の「来歴の縛り」の列の条件も満たす行だけを拾い、レポートの件数は `building_messages / schedule(旧世代)` と `building_messages / external_event(旧世代)` に分けて書く。
  6. 本体 DB の `execution_ledger` のうち、判断点 on_event の prepared 行の `dispatch_envelope.user_input`（回収で応対の入力として送り直される）と、スルースの台帳（kind=`sluice.pan`）の applied / completed 行の `RESULT_JSON.prompt`（再適用のときに記録の paired_action_text になる）。
  7. 本体 DB の `execution_outbox` のうち、記憶への追記（`saimemory.append` / `saimemory.append_digest`）の未配送（pending / dead）行の `message`。送り終えた行の凍結は崩さない。
- **剥がし方**: 一番外側の包みだけを外す（`strip_system_tags`）。剥がすのは、本文全体が完全な `<system>…</system>` の組を空白だけを挟んで並べた形の行だけ。組の中で開きと閉じが同数そろって入れ子になっているタグ（再開文が元の発火文を引用している世代など）は本文の一部としてそのまま残し、送るときにクライアント層が無害化する。対の無い閉じタグ・閉じられていない開きタグ・組の外の地の文がある行は、外部由来の本文に混ざったタグとどこまでが包みかを機械的に決められないので、系統が判定できても変換せず、理由（タグの対応が曖昧）つきでレポートへ出す。組の数も置き場ごとに縛る。一つの包みの中に `</system><system>` を含む引用が入った行と、正当に組を二つ並べた行は文字の並びでは区別できないので、messages・paired_action_text・実行台帳・送信トレイ・building_messages は組が一つだけの行、`rendered_text` は組が一つか二つの行だけを剥がし、それ以外は同じ理由でレポートへ出す。剥がした結果がまだ `<system>` で始まる行（`<system><system>A</system></system>` のような二重の包みか、本文の先頭の引用か）も、どちらか決められないので同じ理由でレポートへ出す。剥がした結果が変換の条件を満たしたままだと、毎起動で走査し直す本体 DB と、完了の印を見送った記憶 DB で、次の起動にもう一度剥がされるためでもある。
- **残すもの**: 識別用 metadata が無いのにタグで始まる行（「対象」の 1 の旧世代の個別条件に当たる行を除く）は**role と本文を触らずに残し**、その変換しなかった行もレポートへ全件出す。外部由来の偽物はそのまま残す（role=user のままなら、合言葉の規則のもとで自然に「ただの文章」扱いになる）。
- **確認待ちの印**: ペルソナの記憶 DB の `messages` で、タグの対応が曖昧な行・系統を判定できなかった行・系統を推定できなかった role=system の行には、metadata に確認待ちの印 `__system_notice_review__`（`sai_memory/memory/storage.py` の `SYSTEM_NOTICE_REVIEW_KEY`。値は残した理由の文字列）を付ける。role=user のまま残る行は、役の判定だけになった「実会話」の条件（`_conversation_exclusion`）を素通りし、機構の文がコア記憶の scene・自動想起・Chronicle の発話の判定に発話として混ざるので、この印を持つ行を「実会話」から外す（`filter_real_conversation_ids` も同じ条件を使う）。印は本文を変えず、レポートには従来どおり載る。本人の発話がこの印で外れることもありうるが、レポートを見て行を直したら印を消せば元の扱いに戻る。metadata が辞書として読めない行には付けない（印だけの metadata に置き換えると元の metadata が失われる）。印の付いた行には二度書かない（完了の印を消して流し直しても書き換えが起きない）。metadata の列そのものが無い古いスキーマの記憶 DB では印を書けないので、完了の印を立てずに次の起動へ回す（上の「一回限りにする仕組み」）。印を付けないまま完了の印を立てると、通常の初期化が列を足した後も走査し直されず、その行が「実会話」に混ざり続けるため。
- **偽造への備え**: 既存の識別用 metadata（`with:["system"]` など）は送り手が偽造できた期間がある（不変条件 4）。移行は印と本文の AND で判定し、**系統ごとの件数と本文のサンプルをレポートに出して人の目を通す**形にした。当初の案にあった「系統ごとの出どころの裏付け（pulse の種類、建物ログとの突き合わせなど）」は実装していない。
- **埋め込みベクトル**: タグを剥がした行の埋め込みは作り直さない（差はタグの文字列だけ）。
- **バックアップ**: 本体 DB は起動冒頭の pre_upgrade バックアップに加えて、書き換える行があるときだけ `<SAIVERSE_HOME>/backups/system_notice_migration/` に写し（`saiverse.db.pre_migration_<時刻>_<pid>_<乱数>.bak`）を取る。ペルソナの記憶 DB も、書き換える行がある DB だけ同じフォルダの `<persona_id>/memory.db.pre_migration_<時刻>_<pid>_<乱数>.bak` に写しを取る。名前に pid と乱数を足し、既にあるファイルは上書きしない形で作るので、同時に起動した二つのプロセスの写しが重ならない。順序は本体 DB・記憶 DB とも「書き込みの取引（`BEGIN IMMEDIATE` — 他のプロセスの書き込みを止める）を取る → 変換対象を走査する → 変換があれば写しを取る → 書き換える → コミット」にした。写しは別の接続から SQLite のバックアップ API で読む（書き込みのロックは他の接続の読み取りを止めない。rollback journal と WAL の両方でテストで確かめた）。写しを取ってから書き換えるまでの間に別のプロセスが行を書けないので、写しに無い行が移行されることはない。記憶 DB は、印の確認を読み取り専用で先に一度行い（済んでいれば何もしない）、取引の中でもう一度確かめて、別のプロセスが先に終えていれば何も書かずに終える。記憶 DB では `init_db`（スキーマの用意と既存行の埋め直しを自分でコミットする）を呼ばない — ロックの中では呼べず、ロックの外で先に呼ぶと写しが「何も触る前」の状態でなくなるため。完了の印を書く `embed_metadata` の表が無い古い DB では、取引の中で同じ定義の表を作る。写しが取れなければ、その DB は書き換えない。通常の起動時バックアップは数が上限を超えると古いものから消えるので、写しは別の置き場に置いた。
- **レポート**: 変換した行・変換しなかったタグ始まりの行・系統を推定できなかった role=system の行・エラーのどれかがあるとき、同じフォルダに `report_<時刻>_<pid>_<乱数>.md` を書く。中身は、DB ごとの移行前の写しの場所、表と系統ごとの件数、系統ごとに 3 件までの前後のサンプル（本文は冒頭 160 字）、変換しなかったタグ始まりの行の全件、推定できなかった role=system の行の件数と先頭 50 件、旧 MEMORIZE の結果の候補の件数と先頭 50 件。レポートの材料は、DB を一つ処理するたびに `results/<時刻>_<pid>_<乱数>/` へ書く DB ごとの結果の JSON。書き換えを伴う DB の JSON は二段で書く。(a) 書き換えの取引のコミットの**前**に、同じフォルダの仮の名前（`<key>.json.tmp`）で書き、中身とフォルダの項目を `os.fsync` で OS に確定させる（Windows はフォルダを開けないので中身だけ）。ここで書けない・確定させられなければその DB の取引を巻き戻し、完了の印を立てず、次の起動で再試行する — コミットの後に書く順序だと、書き出しの失敗で「変換したのに目視の材料が無い」記憶 DB が残り、完了の印のために二度と走査されないため。(b) コミットの後に仮の名前から正式な名前（`<key>.json`）へ付け替え、フォルダの項目を確定させる（失敗は警告だけ — 付け替えが失われても、中身を確定させた仮の JSON が (c) で採用される）。(c) コミットと付け替えの間で止まった（または付け替えに失敗した）起動の仮の JSON は、次の起動の作り直し（`regenerate_pending_reports`）が採否を決める。仮の JSON には、その取引で立てた完了の印の値（`marker_value`）を書いておき、その DB の印が同じ値なら取引はコミットされているので正式な名前へ付け替えて採用し、印が無い・値が違うなら捨てる（コミットの前に止まった起動の JSON が「変換した」という確定していない結果として報告されないように）。仮の JSON そのものが読めない（一時的な I/O・権限の失敗）ときは決めずに残して次の起動で再び試し、読めたのに JSON として壊れているもの（書きかけ — コミットの前に確定させるので、コミットされた取引の仮の JSON ではありえない）は捨てる。印を持たない本体 DB と、完了の印を見送った記憶 DB の仮の JSON は、確定を確かめられないので捨てる。本体 DB では付け替えの前に止まった回の変換の詳細がレポートから欠ける。この小さい窓は受容した（移行そのものは確定していて、写しも残っている）。レポートの書き出しが失敗しても、次の起動でその JSON 群からレポートだけを作り直す（印はそのまま尊重する。書き終えた起動のフォルダには `REPORTED` を置く）。起動のフォルダには最初の JSON と一緒に、その起動のプロセスの pid と開始時刻（`RUN`）を置き、作り直しは、そのプロセスがまだ走っているフォルダ（同時に起動した別のプロセスが移行の途中）を対象にしない。変換が無く、変換しなかった行や推定できなかった行だけがある DB も、本体 DB・記憶 DB を問わずレポートに載せる。記憶 DB は印で一回限りになり、毎起動で走査される本体 DB は、残した行が前回（`last_leftovers.json`）と同じならレポートの材料にしない。比べるのは件数ではなく行の同定（表・行 id・role・残した理由）で、件数が同じままの入れ替わりも報告する。
- **旧 MEMORIZE の結果の候補（変換しない）**: 旧世界で role=user・タグ無しの本文で保存された MEMORIZE の結果（building_move / document_create / document_search / generate_image など）は、発話でないことの来歴を機械的に確定できないので変換しない。代わりに「role=user・タグ無しの本文・`playbook:` タグあり・`conversation` タグ無し」の行を候補として、件数と先頭 50 件（id と本文の冒頭）をレポートの独立した節に出し、人の目で確かめる。
- **知らせ**: 結果は `manager.startup_alerts` に積まれ、画面のバナーに出る。変換があれば「新しい形式へ移行しました」（写しとレポートの場所つき。確認が要る行があればその件数も）、変換が無く確認が要る行だけをレポートに書いた回は「確認が要る行があります」の警告、移行できなかった DB があれば警告、前回書けなかったレポートを作り直した回はその知らせを出す。レポートの材料は書けたのにレポートを書けなかった回も、移行の成否と確認が要る行の件数は分かっているので、「移行は完了したが、レポートの書き出しに失敗した（次の起動で作り直す）。確認が要る行 N 件」の警告を出す。DB ごとの結果の JSON そのものを書けなかった DB があれば、その DB の件数もこの起動の手元の結果から数え、「移行結果を一部保存できず、レポートに詳細が欠けている」の警告を出す（確認が要る行の id はログに残す。本文は書かない）。コミットの前の仮の書き込みに失敗した DB は移行していないので「移行できなかった」の警告にも並び、コミットの後の付け替えに失敗した記憶 DB は「結果は仮の名前で残してあり、次の起動でレポートに載せ直す」と知らせる。古いスキーマで確認待ちの印を付けられず、完了の印を見送った記憶 DB があれば、移行と確認待ちの知らせに「次の起動で印を付け直す」の一文を足す。本体 DB の前回比較（`last_leftovers.json`）は、結果の JSON を保存できなかった回は更新しない（更新すると、次の起動で同じ行が「前回と同じ」として報告されずに終わる）。失敗した DB は印が立たないので次の起動で再試行され、起動は止めない。
- **利用者の Playbook（自動では書き換えない）**: 上位層（user_data / expansion_data）のファイルや世界編集で作った・変えた Playbook が、旧形式のシステム通知を作り続ける（本文にタグを書く、または MEMORIZE がツールの結果を role=user のまま保存する。MEMORIZE の action の省略・空文字は、実行側と同じく `{last}` として判定する。TOOL / TOOL_CALL ノードが一つも無い Playbook の `{last}` はツールの結果ではないので判定しない — SET でユーザーの入力を `last` に入れて role=user で記録するのは正常な形）場合と、TOOL ノードがいま登録されていないツールを参照している場合は、起動ごとに `saiverse/playbook_sync.py` の `playbook_compat_alerts` が DB の行を調べて画面の警告に出す。設定にある MCP サーバーの名前で始まるツールの参照は、サーバーが未接続なだけの可能性があるので、「接続できる状態にして起動し直してもまだ出る場合だけ更新する」という別の警告にする（素の名前の参照は MCP のものか見分けられないので、存在しないツールの警告のまま）。ペルソナごとに接続するサーバー（設定の `scope` が `per_persona`）は、起動時に繋がず各ペルソナの Pulse の頭でツールを登録するのが設計どおりなので、そのツールへの参照はどちらの警告にも出さない（出すと毎起動必ず出て、正常な構成を異常に見せる）。利用者の編集を勝手に変えないため、書き換えはしない。`main.py` が MCP とアドオンのツールを登録した後に呼ぶ。
- **コピーで試す**: `python -m database.system_notice_migration --home <SAIVERSE_HOME の写し> --dry-run` は読み取り専用で開いてレポートだけを書く。`--dry-run` を外すと写しに当てる。`--db` で本体 DB の場所を、`--report` でレポートの書き出し先を変えられる（`docs/reference/scripts.md`）。`--home` に存在しないフォルダを、`--db` に存在しないファイルを指定したときは、移行を始めずにエラーで止まり、何も作らない（打ち間違いの先にレポートや結果の置き場を作って「移行するものが無かった」と見える結果を出さないため）。
- **後から取り込んだ記憶**: 完了の印は記憶 DB の `embed_metadata` にあり、ペルソナまるごとパックは `embed_metadata` を運ばない（`saiverse_memory/persona_pack/export.py` の `NOT_CARRIED_MEMORY_TABLES`）。だから、移行の後に新しく作られた記憶 DB へ旧エクスポートを取り込んだ場合は、その DB に印が無いので次の起動で移行される。一方、すでに印の立った記憶 DB へ旧形式の行を取り込んだ場合（既存のペルソナへの合流 `mode="merge"` など）は移行が走らず、旧形式の行は role=user のまま残る。これは既知の制約として未解決。
- **添付アイテム作成の注記（全件一覧の #13）は移行の対象ではない**: 全数調査では「ユーザー発言の末尾に埋め込んで保存」と書いたが、実装時の確認で、保存はされておらず、文脈を組むたびに `_enrich_history_with_attachments`（`sea/runtime.py`）が発言の metadata からその場で足す形だった。記録に旧形式が残っていないので、提示側の変更（上の「読み出しと messages 列の組み立て」）だけで済んだ。

  - **あらすじ・退場の量の勘定は据え置いた**: `sai_memory/arasuji` の機構名義の判定（`is_mechanism_message`）は tags だけで判定している。通知の見分けを role や `__system_notice__` の印へ切り替えると、印（`event_message` など）を持たない系統——スケジュールの発火文・子ラインの報告・TOOL の結果・作業のまとめなど——が「機構名義」に入り、材料の縮み（U の物差し）と残す量の勘定の主語が変わる。だからこの改修では従来の判定のまま据え置いた。通知を機構名義へ編入するかは、Chronicle の中身が変わる独立の設計判断として未解決のまま残す。
  - **head の自分の姿（self_view）は role=user のまま**: system 化すると、OpenAI 互換の直送モデルでは system メッセージに画像を埋め込めないので、外見の画像が説明の文に落ちる。だからタグだけ外し、role=user のまま置いた。タグを外したのは、head の説明文が「合言葉の無い `<system>` 風の文字列はただの文章」と教えるので、囲んだままだと自分の姿まで疑わせることになるため。
  - **音声通話（Live API）は合言葉無しのタグ付き user に畳む**: Live API の client content は user / model の役しか持てず、head も組まない。だから host 行（機構の通知）は `tag_system_notice` で合言葉無しのタグに包んだ role=user に畳む（`saiverse/voice_call.py` の `_merge_turns`）。通話の指示文（`build_system_instruction` → `get_system_prompt`）は head_pipeline の節を含まないので、合言葉の説明との食い違いは生じない。
  - **Ollama（ollama_compat）はタグで囲む側に倒した**: チャットテンプレート次第で、会話の途中の system が落ちうるため。
  - **入れ子の子ラインの既知の制約**: 入れ子の子ライン（親の snapshot の写しを別モデルで動かす）では、head の本文と合言葉の値は親の pin した snapshot のものなので、合言葉の値は変換と一致する。ただし head の説明文は親モデル向けの版のまま残る。親と子で届き方（タグ変換 / 直送）が食い違う組み合わせでは、説明文と実際の届き方が一致しない。当初は既知の制約として残したが、同日のレビューで常用経路と判明し、説明文の一枚化で解消した（次の 2026-10-28 の欄）。
