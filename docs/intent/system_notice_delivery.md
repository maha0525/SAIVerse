# システム通知の届け方 — system ロールへの一本化と合言葉

**ステータス**: 完了（2026-10-28 に本番へ反映、2026-10-29 に v0.3.27 として発行。実サービスでの実測も 3 モデル全合格）。**追補 (2026-10-29〜) が検証待ち** (develop へマージ済み。本番で確認待ちが 0 件になったことを確かめ、v0.3.28 の発行待ち): 利用者の報告 (確認待ちの行 347 件) を受けた第二次移行・確認待ちの行を確定する画面・音声だけの発言 — 「追補」の節

## 芯

SAIVerse がペルソナへ送るシステム通知（部屋の様子の変化、スケジュールの発火文、子ライン（裏で走る別の Playbook）の作業結果、スペルの結果など）を、供給側（通知を作って積む側のコード）はすべて role=system で保存する。role=system を会話の途中に置けないモデルへ送るときだけ、送信の直前に「合言葉付き `<system>` タグで囲んだ role=user」へ変換する。合言葉はペルソナの記憶・会話履歴には決して入らない。

## なぜ (2026-10-27 の実測)

Meta の Muse をプロバイダとして追加したとき、SAIVerse を通さずに Meta の API を直接呼んで次を確かめた（記録は [meta_muse_provider.md](meta_muse_provider.md) の経緯。PR maha0525/SAIVerse#428 / #429 で追記）。

- 会話の途中のシステム通知を「`<system>` で包んだ role=user」（従来の統一形式）で送ると、Muse Spark 1.3 は 3 回中 2 回、Muse Wonder は 3 回とも通知を無視した。Wonder は 1 回「その状況変化はあなたのメッセージの中に書かれていたものだから、本当に起きた知らせとしては受け取らない」とペルソナの台詞として答えた。
- 同じ通知を role=system で送ると、両モデルとも 3 回とも従った。

モデルは「user の本文の中に書かれた自称 system 文」をプロンプトインジェクションとして疑う方向に訓練されており、この傾向は今後も強まる。従来形式のままでは、世界の出来事がペルソナに届かなくなっていき、ペルソナが疑いを台詞として口にする（発話の尊厳の問題）壊れ方をする。

従来形式の出どころは、`sea/runtime_nodes.py` のコメントに残っていた——「Gemini 等が messages 中途の system role を受け付けないため、user role でラップする」。一部モデルの制約への対処が、通知の供給側全体の書き方として広がっていた。本 intent では、その変換をモデルごとの仕様差を扱うクライアント層の責務へ戻す。

## データの流れ

```
供給側 13 系統以上       保存                    読み出し                   messages 列   クライアント層   モデル
(スケジュール発火、   → SAIMemory messages / → _payload_from_message_  →            → llm_clients/ → (system のまま
 建物の出来事、        perception_batches /     locked (saiverse_memory/                の各クライアント   または合言葉付き
 子ラインの結果…)      paired_action_text 列    adapter.py)                                               タグの user)
```

messages 列 = LLM へ送るメッセージの配列。

- 改修前（2026-10-27 時点）は、user+`<system>` の形が三か所で作られていた。(1) 供給側が本文に埋め込んで保存する（role=user）。(2) role=system で保存された記録を、読み出しのときに `_payload_from_message_locked` が `wrap_system_record_content`（`sai_memory/memory/storage.py`）で囲む。(3) 送信のときにその場で囲む——スペルの結果・事前スペル（応答の前に自動で実行されるスペル）の結果・TOOL ノードの結果は記録と同じ文面を `presented_system_record_content` で組み、知覚のまとまり・リアルタイム情報・自動想起（関連する過去の記憶を自動で引き出す機能）の結果は `sea/runtime_context.py`（`_perception_block_text` ほか）で囲んでいた。
- 改修後（2026-10-28 実装）は、供給側はすべて role=system・タグ無し本文で保存する。(2)(3) のタグで囲む処理は全部やめ、role=system のまま messages 列へ出す（共通部品は `sai_memory/memory/storage.py` の `system_notice_message`。`wrap_system_record_content` は削除した）。タグで囲むかどうか・どう囲むかの変換はクライアント層（`llm_clients/system_notice.py`）だけで行う。(2)(3) は対で変えないと、送った列と次のターンの復元が食い違い、[persist_realtime_and_recall.md](persist_realtime_and_recall.md) 不変条件 1（前回の送信は今回の送信の先頭そのもの）が壊れるので、同じリリースで両方を変えた。

調査の全件一覧（供給側の一覧、保存形式の分類、各系統の識別用 metadata）: [2026-10-27_system_notice_survey.md](../handoff/2026-10-27_system_notice_survey.md)。

## 不変条件

1. **システム通知の保存形式は role=system、本文はタグ無し。** 本文に `<system>` を埋め込む供給側を新設しない。識別用の metadata の鍵は一つに定義して全系統で揃える。鍵は `__system_notice__`（`sai_memory/memory/storage.py` の `SYSTEM_NOTICE_KEY`）で、値はその通知を作った系統の ASCII snake_case 名（`schedule`、`building_event`、`subline_report` など）にした。`docs/concepts/saimemory.md` の「システム通知には `event_message` タグ必須」の規則はここで合流させ、識別の正は `__system_notice__` とした（既存の tags は残っていて、あらすじの機構名義の判定などは今も tags を読む）。
2. **role=user を role=system へ変換する仕組みを持たない。** 「本文が `<system>` で始まるか」を意味の判定に使う常設コードを置かない（起動時の移行だけが例外 — 規則の版を上げた第二次の走査 (「追補」の節) も、この同じ移行の仕組みの中で行う）。ユーザーや外部の文章がシステム通知に化ける経路は、移行後の世界のどこにも無い。例外は運用者自身の手: 記憶ブラウザの編集 API・インポートスクリプト・確認待ちの行を確定する画面（「追補」の節）では role を変えられるが、それは所有者が自分の世界に行う管理行為として認める。
3. **合言葉はペルソナの記憶・会話履歴・ログ・画面に出さない。** 保存してよいのは head（プロンプト先頭部）の実体 `SessionHeadSnapshot`（(persona_id, model_key) に一つ — [beat_execution_context.md](beat_execution_context.md) §3.1）の `PASSPHRASE` 列だけ。head の作り直しのたびにランダムに生成し直す。head の本文には仮置きの記号（`{{SYSTEM_NOTICE_PASSPHRASE}}`）を書き、実際の値はクライアント層の最終変換でだけ差し込む——SAIVerse 層で messages を写す口（`llm_io.log` を書く `_dump_llm_io`、画面へ返す `/api/chat/preview`）に値が乗らないようにするため。
4. **識別用の metadata はサーバーだけが書ける。** 送り手から届く metadata を選別する処理（`api/routes/chat.py` の `_client_metadata`）は禁止リスト方式で、改修前は `tags` と `with` が素通りしていた（= 既存の識別用 metadata は送り手が偽造できた）。システム通知の識別に使う鍵は「送り手の入力から必ず取り除かれる領域（`__` 始まり）」に置き、あわせて `tags`・`with` も送り手から書けないよう閉じた。X・Discord など外部由来のテキストは本文としてしか入らないことを保つ。
5. **システム通知の時系列上の位置は保たれる。** 変換は元の位置で行う。先頭へ寄せてよいのは head 由来の system（人格指示）だけで、その判定は「先頭に連続しているか」という位置ではなく、head 由来であることを示す metadata（`__head__` = `HEAD_MESSAGE_KEY`。記録には保存しない）で行う（履歴が空のターンでは、冒頭の通知が人格指示と区別できなくなるため）。
6. **同じ head を使い続けている間、同じ記録から組み立てる送信本文は一字も変わらない**（persist_realtime_and_recall.md 不変条件 1 の継承）。一致を取る対象が「保存した本文そのまま」から「クライアント層の変換後の本文」へ移る。合言葉の更新は head の作り直しと同時にだけ行う。
7. **他ペルソナ・ユーザーの発話は role=user のまま。** 世界の中の発話はシステム通知ではないので、role=system 化の対象にしない。

## 設計

### 保存 — 供給側の正規化

全件一覧の 13 系統（本文に `<system>` を埋め込んで保存していた供給側）を、role=system・タグ無し本文 + 識別用の metadata `__system_notice__` での保存に変えた（#13 の添付アイテム作成の注記は保存されていなかったので、提示側で扱った — 下の「移行」の節）。Playbook の MEMORIZE でツールの生の結果をタグ無しの role=user で保存していた Playbook も、`MemorizeNodeDef` の既存の `role` フィールドで role=system に変えた（DB への再 import がリリース手順に要る）。他ペルソナの発話（`名前: 本文`）は role=user のまま変えない。

この正規化の時点で、本文にタグを埋め込まずに、印の無い role=system のまま記憶へ書いていた書き手が二つ漏れていた。一つは `builtin_data/tools/thread_switch.py` の `switch_active_thread` で、移動先のスレッドに `[thread switch] moved from <移動元のスレッド>`（`summary` を渡されたときはその本文）を書き、移動元に行があれば、その行への参照 `other_thread_messages` を metadata に持たせる。もう一つは `scripts/import_chatgpt_conversations.py` で、取り込んだ会話の先頭に `[Imported ChatGPT conversation "<題>" (<会話の id>) created <日時>]` を書く。どちらも機構の行なので、2026-10-30 に `system_notice_message` で書く形に直し、系統名はそれぞれ `thread_switch` と `chatgpt_import` にした（`THREAD_SWITCH_NOTICE_KIND`・`CHATGPT_IMPORT_NOTICE_KIND`）。直す前に書かれた行は、移行の規則の版 4 が同じ系統名の印を付ける（「追補」の節の「移行の規則の版 4」）。

同じ形の書き手がもう一つ残っていた。`sea/runtime_nodes.py` の `lg_stelis_start_node` は、Stelis のスレッドを始めるときに、親のスレッドへ本文が空の role=system の行を書き、metadata の `type` を `stelis_anchor`、`stelis_thread_id` を始めた Stelis のスレッドの id にする。読み出し（`sai_memory.memory.storage.compose_message_content`）は、この `type` を見て、Stelis のスレッドの題・開始と終了の時刻・あらすじ・最初と最後の行を本文に組み立てるので、送る列に本文が空の行が出ることはない。この行も 2026-10-30 に `system_notice_message` で書く形に直し、系統名は metadata の `type` と同じ `stelis_anchor` にした（`STELIS_ANCHOR_NOTICE_KIND`）。保存する本文は空のままにした。本番の写しで確認待ちに残っていたほかの二種類の role=system の行は、今のコードにはもう書き手が無い。別の City への移動に失敗したときの案内（`別のCityへの移動に失敗しました。<理由>` と `別のCityへ移動する機能が設定されていません。`）は旧 `persona/mixins/movement.py` の `_handle_movement` が書いていて、2026-06-06 のコミット f915bf22 で削除された。`[要約 <id の先頭 8 文字>] <要約>` の行は旧 `builtin_data/tools/get_since_last_user_conversation.py` の `_save_summary_to_memory` が書いていて、2026-10-28 のコミット 1b9ede25 で削除された。この三種類の過去の行も、移行の規則の版 4 が印を付ける。

保存経路の注意: `persona/history_manager.py` の `_sync_to_memory` は、改修前は role=system の行を警告を出さずに読み飛ばしていた（`("skipped", None)` が返る）。スケジュール発火文と建物の出来事はこの経路（`add_to_persona_only`）を通るので、role を変えるだけでは記録が消える。実装では、`__system_notice__` を metadata に持つ role=system の行だけを記憶へ書き、印の無い system 行（入室案内など、機構がその場の状況として積むだけの行）は従来どおり書かない形にした。

### 読み出しと messages 列の組み立て

`_payload_from_message_locked` は、role=system を role=user + タグへ変換するのをやめ、role=system のまま metadata 付きで返す。送信のときにその場で包んでいた箇所（データの流れの (3)。スペル・事前スペル・TOOL・子ラインの報告、知覚のまとまり・部屋の様子、リアルタイム情報・自動想起、時刻の目安・自律行動の記録・あらすじの畳み・keep-alive、作業セッションの指示書・tell・コマの締め、音声通話の host 行など）も role=system の通知として出す。paired_action_text（発話の記録に対で付く指示文の控え）も、保存形式をタグ無しにし、展開のときに role=system の通知として出す。

添付アイテム作成の注記は、ユーザー発言の本文へ連結するのをやめ、発言の直後に独立した role=system の通知（`__system_notice__` = `attachment_note`）として置く（`sea/runtime.py` の `_enrich_history_with_attachments`）。発言の本文はユーザーが言った言葉そのままに残る。

head の自分の姿（self_view）は、タグだけ外して role=user のまま置いた（理由は経緯の 2026-10-28 の項）。

### クライアント層の変換と合言葉

- 判定と変換は `llm_clients/system_notice.py` の一枚にまとめた。会話の途中の role=system を受け取れるかの判定（`accepts_mid_conversation_system`）は、`xai_native` は受け取れる側、`openai_compat` と `nvidia_nim` はモデル設定の `convert_system_to_user` が真なら受け取れない側・それ以外は受け取れる側、それ以外の protocol（`anthropic_native`・`gemini_native`・`openai_codex`・`ollama_compat`・未知の protocol）は受け取れない側にした。
- 会話の途中の role=system をそのまま送れるモデルへは、そのまま送る。Muse は直接呼び出しで実測済み。ただし Meta のプロバイダ定義（`builtin_data/providers/meta.json`）の `default_convert_system_to_user: true` を外す PR #429 は 2026-10-28 時点で未マージで、このブランチでは Muse はタグで囲む側に落ちる。OpenAI と xAI（`llm_clients/xai.py` は途中の system をその場に置く）は仕様上受け付けるが、SAIVerse の messages 列に途中の role=system が現れるのは本 intent が初めてなので、実サービスでの実測は検証計画に残っている。
- 置けないモデルへは、送信の直前に `<system pass="合言葉">本文</system>` の role=user へ元の位置で変換する（`present_system_notices`）:
  - OpenAI 互換（`llm_clients/openai_message_preparer.py`）: head の印を持つ列では `convert_system_to_user` を「途中の system を合言葉付きタグで囲む」の意味で読む（true を宣言している既存モデル定義は、タグで囲む側 = 安全側に落ちる）。head の印を持たない列（要約・判定など、head を組まない呼び出し）は従来の扱いのまま。
  - Gemini（`llm_clients/gemini.py`）・Anthropic（`llm_clients/anthropic_request_builder.py`）・Codex（`llm_clients/openai_codex.py` — instructions へ寄せる）: 先頭の system 欄へまとめるのは head の印を持つ system だけにし、途中の system は合言葉付きタグの role=user へ元の位置で変換する（不変条件 5）。Codex は、この変換（OpenAI 互換と共通の `prepare_openai_messages`）が例外で失敗したら送信を中止する。元の messages のまま送ると、通知が instructions へ寄って位置を失い、伏せ字の無い本文が送られるため。
  - Ollama（`llm_clients/ollama.py`）: チャットテンプレート次第で途中の system が落ちうるので、タグで囲む側に倒した。Ollama は messages を HTTP の本文へそのまま載せるので、送信の直前に各メッセージを API が定義する欄（role / content / images / tool_calls / tool_call_id / name / tool_name）だけの新しい dict へ組み直し、SAIVerse の内部の metadata（思考・出力の分け方・通知の印や本文の写しなど）を一切送らない。通知の画像は metadata にしか無いので、組み直しの前に扱う。タグの中の本文は他のクライアントと同じく「元の本文 + metadata の全部の画像の説明の文」で固定する。画像そのものは、画像に対応するモデルでも送らない — Ollama のクライアントは通常のユーザーの発言の画像も送っていないので、通知の画像・音声・動画も同じく説明の文だけで届く（経緯の 2026-10-28 Codex 6 巡目の欄）。組み直した後の `tool_calls` と、文字列でも部品の並びでもない本文（辞書のまま渡るツールの結果）は、すべての文字列からその送信の合言葉を伏せる（`redact_passphrase_in_value`。head の本文は除く）。
- 画像を持つ通知の扱い: タグで囲む側では、metadata の media を引き継いで role=user のまま画像を埋め込む。そのまま送る側では、system メッセージは文字しか持てないので、画像は説明の文（`llm_clients/system_notice.py` の `system_notice_image_note`）に置き換わり、通知の本文の後ろに足される（OpenAI 互換・xAI とも。本文が空で画像だけの通知も、空のメッセージとして落とさずに説明の文で残す）。説明の文は、記録の metadata の画像の項目に保存済みの要約（`summary`）があれば `[画像: <uri>] <要約>`、無ければ `[画像: <uri>]` だけで、その場で要約を生成しない — 生成する `image_summary_note` を使うと、生成の成否で同じ記録から組む送信本文が変わり、不変条件 6 が割れる。タグで囲む側でも同じ説明の文を使い（OpenAI 互換・Anthropic・Gemini。タグ化した通知は role では見分けられないので、`present_system_notices` が写しに付ける `__system_notice__` で見分ける）、タグの中の本文は、画像・音声・動画を埋め込めたかどうか（対応のモデルか・枚数の上限の内か・ファイルが読めたか）にかかわらず「元の本文 + metadata の全項目の説明の文」で固定する（`system_notice_media_notes`。説明の文は metadata の記述だけから metadata の並びの順に組む）。埋め込めた項目は、説明の文に加えて部品としてタグ付きの本文の後ろに続く。説明と埋め込みが重複するのは受け入れる — 読み込みの成否で同じ記録から組むタグの中の本文が変わると不変条件 6 が割れ、決定性のほうが優先だから。画像のファイルが消えていても、metadata の画像の項目から説明の文を作り、通知ごと消さない。通知に付いた音声・動画も同じ規則で、保存済みの要約か URI だけの `[音声: <uri>]` / `[動画: <uri>]`（`system_notice_media_note`）にし、その場で要約を生成しない（Gemini と、音声・動画を文字に落とす各クライアントの共通の経路 `llm_clients/base.py` の `_inject_unsupported_media_summaries`。後者も metadata の並びの順に全項目を並べるので、ファイルの有無で説明の文の数と順序が変わらない）。この共通の経路は送る直前の前処理なので、一つの送信に一度だけ掛ける — Anthropic の構造化出力のストリームは同期の generate へ委ねるので、委ねる前には掛けない（二度掛けると説明の文が二重になり、同期の送信本文と食い違う）。説明の文は通知の本文の一部なので、タグで囲む側では、クライアントが通知の最終的な本文（元の本文 + 説明の文）を先に組み、その全体を合言葉付きタグで包む（`tag_presented_system_notice`。`present_system_notices` がタグ化した通知の写しの metadata にタグで包む前の本文を残す。この写しは送信の本文には載らない）。閉じタグの後ろに説明の文を足すと、画像だけの通知では証明されたタグの中身が空になり、説明は合言葉の外の普通の user の文章になるため。埋め込む画像・音声・動画は部品なのでタグで包めず、タグ付きの本文の後ろに続く。そのまま送る側では、説明の文は合言葉の変換の後で本文に足されるので、保存済みの要約に現れた合言葉はそこで伏せ、`<system` も無害化する。伏せるのはその送信の head の合言葉だけにする — プロセスが覚えている合言葉の全部で伏せると、別の head の合言葉が登録されただけで同じ記録から組む送信本文が変わり、前方一致が割れる（不変条件 6）。通知以外の発言に、変換の後で足す画像の要約（その場で生成したもの）も、同じくその送信の合言葉で伏せる。
- 変換のとき、通知本文の中に引用で入った `<system` / `</system` は全角の `＜` で始まる文字列にして無害化する。あわせて、通知以外のメッセージ本文と `tool_calls` の引数、それに metadata の `reasoning_details`（前のターンの思考。OpenAI 互換のクライアントが `reasoning_passback_field` で次のリクエストへ送り返す）の思考の文（`text` / `summary`。署名や暗号化された欄は触らない）に現れた合言葉は伏せ字にする（合言葉がモデルの返答に復唱されて記録に残った場合の再利用を防ぐ）。本文が部品の並びのときは、部品をまたいで連結した文字列で伏せる（各クライアントは文字の部品を連結して送るので、部品ごとに伏せると、二つの部品に割った合言葉が素通りして連結で元に戻る）。置換は文字数を変えないので、連結した文字列を元の部品の長さで切り戻し、部品の数・順序と画像などの部品は変えない。この変換は文字列だけを伏せるので、辞書のまま渡ってきたツールの引数・結果は、クライアントが送る形へ変換した後で伏せる: Codex は辞書の引数を JSON の文字列にした後と、辞書の結果や部品を文字列にした後（ツールの結果・ツールの引数・assistant の本文）に、その送信の合言葉で伏せる（system と user は伏せない — head と合言葉付きタグに合言葉が正当に入る）。Gemini は FunctionCall の引数と FunctionResponse の結果を辞書のまま送るので、その中のすべての文字列（辞書の鍵も）を伏せる（`redact_passphrase_in_value`）。
- ログへの非漏洩: 各クライアントは送る形や応答をそれぞれの形でログへ書き、応答に復唱された合言葉は書く側では見分けられない。そこで `present_system_notices` が差し込んだ合言葉をプロセス内で覚えておき（`llm_clients/system_notice.py`）、ログの各ハンドラ（backend / llm_io / error / sea_trace / timeout_diagnostics — `saiverse/logging_config.py` の `_redact_passphrase_filter`）が書き出す直前に、どのログ行（例外の文も含む）からも伏せる。伏せ字はログ行ごとの一致なので、応答の断片を別々の行に書くと、復唱された合言葉が行をまたいで割れて素通りし、行の連結で元に戻る。だから Gemini のストリームは、チャンクごとの本文（SSE の各 payload・チャンク・差分）をログに書かず（大きさなどの要約だけ）、応答の全文を組み立て終わった後の 1 レコードで書く。ツール呼び出しも同じで、OpenAI 互換のストリームの名前と引数の断片は長さだけを書いて結合後の名前と引数を 1 レコードで書き、Gemini のストリームの関数呼び出しはストリームの後で採った一つを 1 レコードで書く。ツールの引数を state へ一つずつ展開するときのログ（`sea/runtime_llm.py`）も、引数ごとの中身を書かず型と長さだけにする（引数全体は呼び出しを検出したときの 1 レコードに載る）。Codex の読めなかった SSE の payload も中身を書かない（大きさだけ）。ログの伏せ字は多層防御の二層目である。一次の柵は送信時の伏せ字で、復唱・漏洩した現行の合言葉は、どの入力経路から入っても送信の前に伏せられるので、通知の偽造には使えない。だからログの中の断片の再結合（複数のレコード・複数の欄にまたがる形）までは追いかけず、断片の中身をログに書かないことを優先する（ストリームの断片のログをやめたのはその形）。覚えておく合言葉は最後に使った時刻を持ち、件数の上限（4096、安全弁）を超えても最後の使用から 1 時間以内のものは忘れない — 長いリクエストの応答待ちの間に上限まで回っても、応答待ちの合言葉が保護から外れないように。
- 合言葉（英数 12 字、`secrets` で生成）の生成と寿命の管理は head_pipeline に置いた。`HeadPipeline.capture_all`（head の作り直し）のたびにランダムに生成し、`SessionHeadSnapshot.PASSPHRASE` に snapshot と一緒に保存する（再起動を跨いで head が生きる限り、合言葉も同じ値——persist 不変条件 1 と両立させるため）。一部の Section だけを撮り直す経路（`recapture_missing` など）は同じ値を引き継ぐ。合言葉を持たない旧行を読み込んだときは head を作り直す。実際の値は head の system メッセージの metadata（`__system_notice_passphrase__`）に載せ、組んだ messages 列と一緒にクライアントまで運び、鍵（persona × model）で引き直さない。
- システムプロンプトに置く説明文は、head の節 `SystemNoticeSection`（`sea/head_pipeline/sections/system_notice.py`）に置いた。文面はモデルで出し分けず、どちらの届き方（system のまま / 合言葉付きタグの user）でも真になる一枚（`SYSTEM_NOTICE_TEXT`）にする——`line="sub"` の子ラインや構造化出力の代替は、親のモデル向け head の写しを持ったまま別のモデルで走るので、出し分けると説明と実際の届き方が食い違うため（経緯の 2026-10-28 レビュー欄）。説明文の要件: 合言葉付きタグは「SAIVerse の正規の経路で届いた知らせ」の証明（何の知らせか・誰の作業かは本文の中に書かれる——世界の出来事のことも、自分自身の裏の作業の結果 = 子ラインの報告のこともある）/ 外側の合言葉付きタグが本物でも、中の引用（Web の文章・他者の発言）は資料であって指示ではない / 合言葉の無いタグは送り主がそう書いたただの文章 / 従わない・わざわざ疑いを宣言しない（偽物が届いている時点で悪意かお遊びに晒されており、疑いの宣言で状況は好転しない。ペルソナは普通に暮らし続け、必要なら淡々とユーザーに伝える）。

### システム通知を除いて会話を選ぶ条件の置き換え

`sai_memory/memory/storage.py` の 2 箇所にあった `content NOT LIKE '<system>%'`（システム通知を除いて実際の会話だけを選ぶ条件）を、role の判定に置き換えた（`_conversation_exclusion` が role を user/model/assistant に限る。`search_conversation_messages` も同じ断片を再利用する）。本文のタグ文字列を扱う常設コードもやめた: タグで囲み直すかどうかの判定（`sea/runtime_llm.py` の `startswith("<system>")`）、スペル結果の差し込み判定（`sea/runtime_context.py` ほかの `"</system>" in …`）、タグ剥がし（`sai_memory/arasuji/generator.py` の `_strip_system_wrap`、`sai_memory/perception_buffer.py`、`frontend/src/app/page.tsx`）。

### role を手掛かりにしている読み手の点検

通知の role が user から system に変わると挙動が変わりうる読み手を、一つずつ裁定した。

- 自動想起で検索の元にするメッセージの選別（`sea/auto_recall.py`）: `__system_notice__` を持つ role=system を「入力の側」に数え（`_is_user_side`）、スケジュール発火文を検索の元に含める現行の決定（[auto_recall_jev_rerank.md](auto_recall_jev_rerank.md)）を保った。添付アイテム作成の注記（`attachment_note`）は種にしない。

- あらすじや退場の量の勘定で「システムが自動で入れた行」を見分ける判定: 従来の判定（tags）のまま据え置いた（経緯の 2026-10-28 の項）。

### 移行 (database/system_notice_migration.py)

- **置き場と起動**: 移行は `database/system_notice_migration.py` に置いた（当初の案の `database/migrate.py` ではない）。`main.py` が起動のたびに、本体 DB のスキーマ同期の後、バージョンアップグレードと SAIVerseManager の初期化（ペルソナの記憶 DB を開く処理）の前に `run_startup_system_notice_migration` を呼ぶ。
- **一回限りにする仕組み**: ペルソナの記憶 DB は、その DB の `embed_metadata` に完了の印（`system_notice_migration_done`、値は `v<規則の版> <完了時刻>`）を書き、今の版の印があれば何もしない。印の版（`MIGRATION_RULES_VERSION`）は、済んだ DB にも当て直す必要のある規則を足したときに上げる。印の版が古い DB は、その後の版で足した規則だけで走査し直して印を今の版へ書き換える（版 1 の印は版を書く前の形で、値が完了時刻だけ）。版 2 で足したのは 1 の旧世代の個別条件で、版 1 の移行を済ませた DB ではその条件だけを当て直す。変換済みの行はタグで始まらないので素通りし、版 1 で「系統を判定できなかった」として付けた確認待ちの印は、通知に変換した行からだけ外す。版 1 で変換しなかった行は版 1 のレポートと確認待ちの印にあるので、走査し直しでは数え直さない。ただし、確認待ちの印（下の「確認待ちの印」）を付けるべき行があるのに付けられない記憶 DB（`messages` に metadata の列が無い古いスキーマ）には完了の印を立てず、変換だけをコミットする。次の起動では通常の初期化（`init_db`）が列を足しているので、走査し直して確認待ちの印を付け、そのとき完了の印を立てる。本体 DB は印を持たない。変換の条件（タグで始まる・未配送・prepared など）を満たす行は変換すると条件から外れるので、毎起動呼んでも二度目以降は何も書かない。この前提を保つため、剥がした結果がまだ `<system>` で始まる行は剥がさない（下の「剥がし方」）。
- **対象（全数）**:
  1. ペルソナの記憶 DB の `messages` のうち、本文が `<system>` で始まり、**かつ**その系統の識別用 metadata を持つ行。タグを剥がし、role=system + `__system_notice__`（値は系統名）にする（`classify_tagged_message`）。拾う系統は、スルースの採取記録・ライフの境界・記憶整理・知覚（知覚のレンダリングより前の世代）・バージョンアップの知らせ・音声通話・建物の出来事・その他の `event_message` を持つ行・スルースのダイジェスト・Track 切替通知（`track_context`）・Track の Chronicle 挿入（`track_chronicle_insert`）・状況変化（`situation_change`）・スケジュール入力（`with:["system"]`）・子ラインの報告と MEMORIZE（`playbook:` タグ）、それに中断の記録（role=assistant + `interrupted` タグ）。
     系統の印（`with:["system"]`・`event_message` など）を持たない旧世代の正規の通知は、本番 DB の写しへの dry-run レポートから系統を確定し、個別の条件で拾う（`legacy_notice`。上の印で系統が決まる行はそちらが優先）。確定したのはスケジュールの発火文と外部イベント通知の二つで、条件は「role=user・tags が `conversation` だけ・ユーザーの発言の来歴を持たない（下の「来歴の縛り」）・タグの剥がしが成立する・剥がした本文の先頭が `スケジュールの実行時刻です` / `スケジュールが実行されました`（かつ metadata に発火の記録の `schedule_id`）、または `[外部イベント通知]`（かつ metadata の `source` が `external_event`）」の全部。系統はどちらも `schedule` にし、確認待ちの印は付けない。レポートの件数は `messages / schedule(旧世代)` と `messages / external_event(旧世代)` に分けて書き、印で拾った `schedule` と区別する（一つの表記にまとめると、系統ごと 3 件のサンプル枠をスケジュールが埋めて、外部イベントの件数とサンプルが見えなくなる）。
     **来歴の縛り**: `schedule_id` と `source` は送り手（チャットの送信 API）も metadata に書けるので、本文と metadata だけではユーザーが発火文の形を打った発言と区別できない。旧世代の発火文は、ユーザーの入力と同じ記録の経路を通って書かれていたので、書き手を表す列も無い。そこで、ユーザーの発言が持つ来歴の印で縛る。記憶 DB では、建物履歴からの転記の印 `building_msg_ref`（2026-07-21 から転記が必ず刻む。今のコードでユーザーの発言が記憶に入る経路は転記と通話の文字起こしだけ）と、通話の文字起こしの印（`voice_call` / `voice_transcript`）を持つ行を拾わない。本体 DB の `building_messages` では、旧世代の書き手の列（`legacy_seq` / `legacy_message_id`。旧ログの取り込みと、ペルソナ側の番号を持ち込んでいた世代の書き込みだけが埋める）を持ち、画面からの送信の印 `client_message_id` を持たない行だけを拾う（`_written_by_old_writer`）。本番の写しで確かめた分かれ方は、記憶 DB の正規の旧発火文 306 件はどれも転記・通話の印を持たず、転記の印を持つ user 行は 723 件。`building_messages` の正規の旧発火文 171 件は全部が旧世代の列を持って `client_message_id` を持たず、画面から送られた 1039 件は全部 `client_message_id` を持ち、2026-09-06 より後に書かれた行に旧世代の列を持つものは無い。縛った後も、写しの 477 件はそのまま拾う。

- **剥がし方**: 一番外側の包みだけを外す（`strip_system_tags`）。剥がすのは、本文全体が完全な `<system>…</system>` の組を空白だけを挟んで並べた形の行だけ。組の中で開きと閉じが同数そろって入れ子になっているタグ（再開文が元の発火文を引用している世代など）は本文の一部としてそのまま残し、送るときにクライアント層が無害化する。対の無い閉じタグ・閉じられていない開きタグ・組の外の地の文がある行は、外部由来の本文に混ざったタグとどこまでが包みかを機械的に決められないので、系統が判定できても変換せず、理由（タグの対応が曖昧）つきでレポートへ出す。組の数も置き場ごとに縛る。一つの包みの中に `</system><system>` を含む引用が入った行と、正当に組を二つ並べた行は文字の並びでは区別できないので、messages・paired_action_text・実行台帳・送信トレイ・building_messages は組が一つだけの行、`rendered_text` は組が一つか二つの行だけを剥がし、それ以外は同じ理由でレポートへ出す。剥がした結果がまだ `<system>` で始まる行（`<system><system>A</system></system>` のような二重の包みか、本文の先頭の引用か）も、どちらか決められないので同じ理由でレポートへ出す。剥がした結果が変換の条件を満たしたままだと、毎起動で走査し直す本体 DB と、完了の印を見送った記憶 DB で、次の起動にもう一度剥がされるためでもある。
- **残すもの**: 識別用 metadata が無いのにタグで始まる行（「対象」の 1 の旧世代の個別条件に当たる行を除く）は**role と本文を触らずに残し**、その変換しなかった行もレポートへ全件出す。外部由来の偽物はそのまま残す（role=user のままなら、合言葉の規則のもとで自然に「ただの文章」扱いになる）。
- **確認待ちの印**: ペルソナの記憶 DB の `messages` で、タグの対応が曖昧な行・系統を判定できなかった行・系統を推定できなかった role=system の行には、metadata に確認待ちの印 `__system_notice_review__`（`sai_memory/memory/storage.py` の `SYSTEM_NOTICE_REVIEW_KEY`。値は残した理由の文字列）を付ける。role=user のまま残る行は、役の判定だけになった「実会話」の条件（`_conversation_exclusion`）を素通りし、機構の文がコア記憶の scene・自動想起・Chronicle の発話の判定に発話として混ざるので、この印を持つ行を「実会話」から外す（`filter_real_conversation_ids` も同じ条件を使う）。印は本文を変えず、レポートには従来どおり載る。本人の発話がこの印で外れることもありうるが、レポートを見て行を直したら印を消せば元の扱いに戻る。metadata が辞書として読めない行には付けない（印だけの metadata に置き換えると元の metadata が失われる）。そういう行が一つでも残る記憶 DB には完了の印を立てず（理由 `MARKER_HELD_UNREADABLE_METADATA`）、起動のたびに画面の警告 `system_notice_migration_unreadable_metadata` にペルソナごとの件数を出す。完了の印を立てると二度と走査されず、印の付かないその行が実会話として扱われ続けるため（2026-10-29、敵対レビュー 2 巡目の指摘）。印の付いた行には二度書かない（完了の印を消して流し直しても書き換えが起きない）。metadata の列そのものが無い古いスキーマの記憶 DB では印を書けないので、完了の印を立てずに次の起動へ回す（上の「一回限りにする仕組み」）。印を付けないまま完了の印を立てると、通常の初期化が列を足した後も走査し直されず、その行が「実会話」に混ざり続けるため。
- **偽造への備え**: 既存の識別用 metadata（`with:["system"]` など）は送り手が偽造できた期間がある（不変条件 4）。移行は印と本文の AND で判定し、**系統ごとの件数と本文のサンプルをレポートに出して人の目を通す**形にした。当初の案にあった「系統ごとの出どころの裏付け（pulse の種類、建物ログとの突き合わせなど）」は実装していない。

- **バックアップ**: 本体 DB は起動冒頭の pre_upgrade バックアップに加えて、書き換える行があるときだけ `<SAIVERSE_HOME>/backups/system_notice_migration/` に写し（`saiverse.db.pre_migration_<時刻>_<pid>_<乱数>.bak`）を取る。ペルソナの記憶 DB も、書き換える行がある DB だけ同じフォルダの `<persona_id>/memory.db.pre_migration_<時刻>_<pid>_<乱数>.bak` に写しを取る。名前に pid と乱数を足し、既にあるファイルは上書きしない形で作るので、同時に起動した二つのプロセスの写しが重ならない。順序は本体 DB・記憶 DB とも「書き込みの取引（`BEGIN IMMEDIATE` — 他のプロセスの書き込みを止める）を取る → 変換対象を走査する → 変換があれば写しを取る → 書き換える → コミット」にした。写しは別の接続から SQLite のバックアップ API で読む（書き込みのロックは他の接続の読み取りを止めない。rollback journal と WAL の両方でテストで確かめた）。写しを取ってから書き換えるまでの間に別のプロセスが行を書けないので、写しに無い行が移行されることはない。記憶 DB は、印の確認を読み取り専用で先に一度行い（済んでいれば何もしない）、取引の中でもう一度確かめて、別のプロセスが先に終えていれば何も書かずに終える。記憶 DB では `init_db`（スキーマの用意と既存行の埋め直しを自分でコミットする）を呼ばない — ロックの中では呼べず、ロックの外で先に呼ぶと写しが「何も触る前」の状態でなくなるため。完了の印を書く `embed_metadata` の表が無い古い DB では、取引の中で同じ定義の表を作る。写しが取れなければ、その DB は書き換えない。通常の起動時バックアップは数が上限を超えると古いものから消えるので、写しは別の置き場に置いた。

- **旧 MEMORIZE の結果の候補（変換しない）**: 旧世界で role=user・タグ無しの本文で保存された MEMORIZE の結果（building_move / document_create / document_search / generate_image など）は、発話でないことの来歴を機械的に確定できないので変換しない。代わりに「role=user・タグ無しの本文・`playbook:` タグあり・`conversation` タグ無し」の行を候補として、件数と先頭 50 件（id と本文の冒頭）をレポートの独立した節に出し、人の目で確かめる。
- **知らせ**: 結果は `manager.startup_alerts` に積まれ、画面のバナーに出る。変換があれば「新しい形式へ移行しました」（写しとレポートの場所つき。確認が要る行があればその件数も）、変換が無く確認が要る行だけをレポートに書いた回は「確認が要る行があります」の警告、移行できなかった DB があれば警告、前回書けなかったレポートを作り直した回はその知らせを出す。レポートの材料は書けたのにレポートを書けなかった回も、移行の成否と確認が要る行の件数は分かっているので、「移行は完了したが、レポートの書き出しに失敗した（次の起動で作り直す）。確認が要る行 N 件」の警告を出す。DB ごとの結果の JSON そのものを書けなかった DB があれば、その DB の件数もこの起動の手元の結果から数え、「移行結果を一部保存できず、レポートに詳細が欠けている」の警告を出す（確認が要る行の id はログに残す。本文は書かない）。コミットの前の仮の書き込みに失敗した DB は移行していないので「移行できなかった」の警告にも並び、コミットの後の付け替えに失敗した記憶 DB は「結果は仮の名前で残してあり、次の起動でレポートに載せ直す」と知らせる。古いスキーマで確認待ちの印を付けられず、完了の印を見送った記憶 DB があれば、移行と確認待ちの知らせに「次の起動で印を付け直す」の一文を足す。本体 DB の前回比較（`last_leftovers.json`）は、結果の JSON を保存できなかった回は更新しない（更新すると、次の起動で同じ行が「前回と同じ」として報告されずに終わる）。失敗した DB は印が立たないので次の起動で再試行され、起動は止めない。本体 DB に `execution_ledger` の表が無いので変換をコミットしなかった回は、「移行できなかった」の一般の警告には並べず、表が無いことと、表が作られた後の起動で再試行することを伝える専用の警告 `system_notice_migration_commit_record_unavailable` を出す（表が作られるまで毎起動で同じ理由が続くので、理由の分かる文面にする）。
- **利用者の Playbook（自動では書き換えない）**: 上位層（user_data / expansion_data）のファイルや世界編集で作った・変えた Playbook が、旧形式のシステム通知を作り続ける（本文にタグを書く、または MEMORIZE がツールの結果を role=user のまま保存する。MEMORIZE の action の省略・空文字は、実行側と同じく `{last}` として判定する。TOOL / TOOL_CALL ノードが一つも無い Playbook の `{last}` はツールの結果ではないので判定しない — SET でユーザーの入力を `last` に入れて role=user で記録するのは正常な形）場合と、TOOL ノードがいま登録されていないツールを参照している場合は、起動ごとに `saiverse/playbook_sync.py` の `playbook_compat_alerts` が DB の行を調べて画面の警告に出す。設定にある MCP サーバーの名前で始まるツールの参照は、サーバーが未接続なだけの可能性があるので、「接続できる状態にして起動し直してもまだ出る場合だけ更新する」という別の警告にする（素の名前の参照は MCP のものか見分けられないので、存在しないツールの警告のまま）。ペルソナごとに接続するサーバー（設定の `scope` が `per_persona`）は、起動時に繋がず各ペルソナの Pulse の頭でツールを登録するのが設計どおりなので、そのツールへの参照はどちらの警告にも出さない（出すと毎起動必ず出て、正常な構成を異常に見せる）。利用者の編集を勝手に変えないため、書き換えはしない。`main.py` が MCP とアドオンのツールを登録した後に呼ぶ。
- **コピーで試す**: `python -m database.system_notice_migration --home <SAIVERSE_HOME の写し> --dry-run` は読み取り専用で開いてレポートだけを書く。`--dry-run` を外すと写しに当てる。`--db` で本体 DB の場所を、`--report` でレポートの書き出し先を変えられる（`docs/reference/scripts.md`）。`--home` に存在しないフォルダを、`--db` に存在しないファイルを指定したときは、移行を始めずにエラーで止まり、何も作らない（打ち間違いの先にレポートや結果の置き場を作って「移行するものが無かった」と見える結果を出さないため）。
- **後から取り込んだ記憶**: 完了の印は記憶 DB の `embed_metadata` にあり、ペルソナまるごとパックは `embed_metadata` を運ばない（`saiverse_memory/persona_pack/export.py` の `NOT_CARRIED_MEMORY_TABLES`）。だから、移行の後に新しく作られた記憶 DB へ旧エクスポートを取り込んだ場合は、その DB に印が無いので次の起動で移行される。一方、すでに印の立った記憶 DB へ旧形式の行を取り込んだ場合（既存のペルソナへの合流 `mode="merge"` など）は移行が走らず、旧形式の行は role=user のまま残る。これは既知の制約として未解決。
- **添付アイテム作成の注記（全件一覧の #13）は移行の対象ではない**: 全数調査では「ユーザー発言の末尾に埋め込んで保存」と書いたが、実装時の確認で、保存はされておらず、文脈を組むたびに `_enrich_history_with_attachments`（`sea/runtime.py`）が発言の metadata からその場で足す形だった。記録に旧形式が残っていないので、提示側の変更（上の「読み出しと messages 列の組み立て」）だけで済んだ。

### 移行の規則の第二版

完了の印の「規則の版」を上げる。「版の古い DB を足した規則だけで走査し直す」仕組み (経緯 2026-10-28「approve 後の差分レビュー」の (2)) は、今のコードでは版 2 の規則 (`legacy_notice`) 専用の作りになっている — 走査し直しの入口が真偽値 (`legacy_only`) で、しかも `_scan_legacy_rescan` は `classify_tagged_message` が系統を返す行を飛ばすので、新しい規則をそこへ足すと走査し直しがまさにその行を素通りする。だから**「版ごとに足した規則の集合で走査し直す」形への一般化が、実装の仕事の一つ**。あわせて、role=system の行の経路が確認待ちの印を外さない穴 (変換しても `UNKNOWN_SYSTEM_REASON` の印が残り、下の画面の入口が消えなくなる) も塞ぐ。これで、バナーが消えた既存の世界でも、次の更新の起動で追加分だけが自動で変換される。

足す規則は次のとおり (件数はまはーの環境の実測)。**共通の前提: 規則 6 を除き、対象は role=user かつ本文が `<system>` で始まるタグ付きの行だけで、全部に旧世代の規則と同じ来歴の縛り (「移行」の節の同名の条件) を掛ける** — 改修前のチャット送信 API は tags を素通ししていた (不変条件 4 の経緯) ので、「今の API が tags を落とすから縛りは要らない」とは言えない:

1. **tags に `tool` があるもの** → `tool_result`。`classify_unmarked_system_message` (系統の印の無い role=system 行用) には既にある判定を、`classify_tagged_message` (user + タグの行用) にも掛ける。実測 約 80 件 (「Email sent.」「[Memory Recall]…」など)。
2. **tags に `internal` があるもの** → 旧世代の Playbook の指示文・機構の記録 (`playbook_memorize`)。ユーザーの通常の発話は `internal` を持たない前提も、写しの実物で同時に検証する。実測 168 件。
3. **tags に、実在する Playbook 名がそのまま (`playbook:` の接頭辞なしで) 入っているもの** (`novel_writing` など、古い世代の付け方) → `playbook_memorize`。実在の判定はビルトインの Playbook のファイル名と、移行の時点の DB の playbooks 表。`conversation`・`internal`・`tool` など判定に使う一般のタグと同名の Playbook は対象にしない。世界の状態で判定が変わる規則なので、来歴の縛りとの AND を外さない。
4. **本文が「サブプレイブック実行結果」で始まるもの** → `subline_report`。この書き出しは退役した Playbook (builtin_data/playbooks/archive/ の memory_research など) の MEMORIZE が書いたもので、現行コードが見る書き出し (`_SUBLINE_REPORT_PREFIX` = 「サブ Playbook '」) とは別物なので、新しい条件として足す。実測 4 件。
5. **音声入力時の定型案内文**: 本文が定型案内文 (「〈供給元の名前〉から音声入力を受信しました。添付の音声を〜ください。」の形。末尾は供給元と時期で「聞いてください」「聴いて応答してください」に揺れる。名前の部分を任意にした一つの正規表現で判定し、供給元の名前をコードにもテストにも書かない) で、metadata の media に音声があり、metadata の `source` が `_voice` で終わるもの (音声入力を中継するアドオンは `<供給元>_voice` の形で source を書く — stackchan の audio_input_relay.py、Godot の voice_input.py ほかで確認) → **二行に分割する**: 定型文は role=system の通知へ (系統名は実装時に決める)、音声は本文の無い role=user の行へ (下の「音声だけの発言」の今後の形と同じ)。まはーの裁定 (2026-10-29): 「指示の部分はシステムからで、添付されてる音声だけがユーザーから」。行ごと role=system にする案は捨てた — ユーザーの音声の発言が機構の通知の添付物になって不変条件 7 とぶつかり、さらに音声を聴けないモデルへの届き方も変わる (user 行の音声にはその場で生成した要約が付くが、通知の音声は保存済みの要約か場所の表記だけになる — llm_clients/base.py の user 行と通知の分岐) ため、分割をまはーが選んだ (2026-10-29)。実測 104 件 (供給元 3 種)。
6. **系統の印の無い role=system 行**: `classify_unmarked_system_message` に、`perception` タグ → `perception` (実測 65 件) と、`<div class="note-box">` で始まる感情パラメータ変動の知らせ → `emotion_summary` (実測 238 件、全部がこの形) を足す。後者の出どころは、撤去された `persona/mixins/emotion.py` の `_format_emotion_summary` (コミット f915bf22 の親) が role=system で記憶に書いていた文で、その書式の正規表現の全体一致で判定する。他の note-box の文面は出どころを特定していないので足していない。
7. **定型の機構テキスト**: 足さなかった (2026-10-29 の実装で確定)。候補だった「会話を終了した。」などの行は、すべて所有者が別のゲームの記憶を手で移した記録で、リポジトリにもその履歴にも出どころの文面が無い (`git log -S` で確認)。作った側が機構だと言い切れないので、確認の画面で所有者が確定する。

分けた音声だけの role=user の行は、元の行の機構のタグ (`MECHANISM_TAGS`) を持たず、元の line_role が `CHRONICLE_EXCLUDED_LINE_ROLES` に入るなら `main_line` にする。外したものは確認の画面の「通常のユーザー発話に変換」と同じく `__system_notice_review_cleared__` に残し、通知の行の tags と line_role はそのままにする。これで分けた音声の行は実会話に入る (2026-10-29、敵対レビュー 6 巡目の指摘。本番の写しの 104 件には該当が無かった)。規則 5 の二行分割は、分けた音声の行が通知の直後に並ぶこと (同じ created_at で後ろの rowid) を保証できるときだけ行う。同じ created_at で元の行より後ろの rowid の行がどこかにある場合は、分けずに確認待ちとして残す (理由 `SPLIT_POSITION_REASON`)。本番の写しで該当は 0 件。分けた音声の行の id は `storage.add_message` と同じく uuid4 で作り、列は元の行から写す (応答の行だけが持つ paired_action_text・thought_signature などは写さない)。本文が空の行には埋め込みの行を作らない (adapter の既存の作りと同じ)。

規則 5 には来歴の縛りを掛けない (この行はユーザーの音声の発言そのものなので、建物の履歴からの転記の印を持っている) 代わりに、元の発言の行 (本体 DB の `building_messages` の行) が画面からの送信でないことを確かめてから変換する。規則 5 の形 (案内文・音声の `media`・`_voice` で終わる `source`) は、チャットの送信 API の送り手も作れるからである (`source` は送り手が書ける欄で、音声は添付として付けられる)。音声入力を中継するアドオン (stackchan・Godot ほか) は `handle_user_input_stream` を `client_message_id` なしで呼び、画面からの送信は必ず `client_message_id` を付ける (2026-10-29 に各アドオンのコードで確認)。だから、元の行がこの印を持たないと分かった行だけを分割し、印を持つ行 (理由 `VOICE_SENT_FROM_SCREEN_REASON`) と、元の行を一つに決められない行 (見つからない・複数ある・本体 DB を読めない。理由 `VOICE_SOURCE_UNKNOWN_REASON`) は確認待ちにする。元の行は、記憶の行の `building_msg_ref` (2026-07-21 から転記が必ず刻む) で引き、それを持たない古い行は音声の `media` の `uri` が同じ role=user の行で引く (音声のファイル名は受け取るたびに一意に作られる)。`uri` は、本体 DB の各行の metadata を JSON として解釈した `media` のうち `type` が `audio` の項目の値で比べ、生の JSON の文字列では探さない。同じ `uri` がエスケープの違う表現 (`\/` や `\u` の書き方) で保存されていると、文字列の検索では候補から漏れて、元の行が一つに決まったと誤認するからである。候補が複数あれば、これまでどおり確認待ちにする。本体 DB の role=user の行の中に、metadata を読めない行 (JSON として解釈できない・辞書でない・`media` が一覧でない) が一つでもあれば、その起動の `uri` での引き当ては全部「元の行を一つに決められない」(理由 `VOICE_SOURCE_UNKNOWN_REASON`) にする。読めない行の `media` を数えられないので、その行が同じ音声を持つ画面からの送信だった可能性を除けず、読める候補が一つだけでも元の行と決められないからである (2026-10-29、敵対レビュー 3 巡目の指摘。それまでは読めない行を候補から黙って外し、読める候補が一つなら分割していた)。`building_msg_ref` で引く行は、本体 DB の `building_id` と `message_id` の列で引くので、読めない行があっても変わらない。実装は `database/system_notice_migration.py` の `BuildingSourceRows`。本番の写しでは、規則 5 の 104 件はどれも元の行が `client_message_id` を持たず、全件がこれまでどおり変換された (2026-10-29、まはーの承認で入れた条件)。

この条件には承知の上で受け入れた残余がある。チャットの送信 API は `client_message_id` を省略でき、`source` も送り手が書けるので、元の行が `client_message_id` を持たないことは、音声入力を中継するアドオンの発言だという積極的な証拠ではない。送り手が送信 API を意図的に直接叩き、`client_message_id` を付けずに案内文の形と音声を送った偽物は、アドオンの発言と区別できずに変換される。まはーは 2026-10-29 に、この残余 (送信 API を意図的に叩いて作った偽物だけ) を承知でこの形を承認した (敵対レビュー 2 巡目の指摘への裁定)。

### 時刻の境 — 改修の後に届いた行は自動で変換しない

規則は「過去に機構が書いた行」を見分けるためのもので、改修の後にユーザーが送った「規則の形を真似た文」を通知に変えてはならない (まはー 2026-10-29「今回の改修以後のバージョンで、新たにユーザーから真似た文が届いたときに、それ以降の起動やアップデートで勝手にそれをシステムメッセージに改変しないかどうか」)。境が無いと、真似た文が自動で変換される経路が三つあった: 完了の印の無い新しい記憶 DB の全体の走査、規則の版を上げたときの走査し直し、完了の印を見送った後の次の起動の走査し直し。どれも、その時点までに届いた行を規則で判定する。

- **境の時刻**: この環境で新しい形式に切り替わった時刻を一度だけ決めて、`<SAIVERSE_HOME>/backups/system_notice_migration/cutover.json` に記録する (`resolve_cutover`)。全記憶 DB の完了の印の時刻と、この移行が前の起動で書いた記録の時刻のうち、最も早い時刻を使う。移行が書いた記録とは、起動ごとの結果のフォルダの `RUN` に書いた開始時刻、移行前の写し (`*.pre_migration_*.bak`) の更新時刻、`last_leftovers.json` の更新時刻で、どれも v0.3.27 以降の移行が書き換えありで走った起動だけが書く (`_earliest_migration_trace`)。起動ごとの結果のフォルダ (`results/<起動>/`) はコミット 938ec0f8 (2026-10-28) から書かれ、`RUN` はコミット a56380fd (同日) から書かれる。その間の版は `RUN` を書かずに結果の JSON だけを書いたので、`RUN` が無く結果の JSON だけがあるフォルダは、壊れた記録ではなくその版の正当な形式として読む: フォルダ名の先頭の時刻 (`<年月日>_<時分秒>`、その起動の地方時を秒まで) を読めれば、その時刻を UTC と見なして 14 時間を引いた時刻 (ありうる最も早い UTC) を使い (名前はタイムゾーンを持たないので、今の計算機のタイムゾーンでは読まない。2026-10-29、敵対レビュー 4 巡目の指摘)、読めなければフォルダの中の結果の JSON の更新時刻のうち最も早いものを使う (`_legacy_run_folder_started_at`。どちらの時刻も、その起動の開始より早いことはない)。どちらも取れないときだけ、境を決められないものとして扱う (2026-10-29、敵対レビュー 3 巡目の指摘。それまでは `RUN` の無いフォルダを壊れた記録として扱い、その版を一度動かした環境では全部の DB の変換が止まり続けた)。`RUN` を書かない版は発行した版 (v0.3.26 と v0.3.27) のどちらでもないので、この形式のフォルダを持ちうるのは、その間の開発中の版を動かした環境だけである。印だけで決めないのは、v0.3.27 の起動のときに記憶 DB が無かった環境では印がどこにも残らず、古い記憶 DB を消した環境では残った最古の印が実際の切り替えより遅くなるからである。dry-run のレポートは数えない (dry-run は世界を新しい形式で動かしていない)。印も記録もどこにも無いときだけ、その起動で移行を始めた時刻を使う。一度書いた記録は決め直さない。置き場は `backups` の下なので、スナップショットの復元で巻き戻らない。
- **記録の書き方**: `cutover.json` は、中身を OS に確定させた仮のファイルを、上書きしない固いリンクで正式な名前に付けて公開する。固いリンクを作れないファイルシステムでも、正式な名前に直接は書かず、仮のファイルの名前の付け替えで公開する。Windows の付け替えは既存の名前があると失敗するので、先に記録したプロセスの記録を上書きしない。それ以外の OS の付け替えは既存の名前を上書きするので、固いリンクを作れないときは境を記録せず、その起動では何も変換しない (境を決められないときと同じ扱いで、画面に警告を出す)。3 巡目の指摘への手当てとして一度ロックのファイルで公開を排他する形を入れたが、4 巡目でロックの片づけそのものに競合が見つかったので、自前の排他をやめて、固いリンクを作れない珍しいファイルシステムでは自動の変換を諦める形にした (2026-10-29、メティスの判断)。どちらの OS でも、途中で止まって正式な名前に書きかけの記録が残り、次の起動から境を決められなくなることは無い。
- **記録できなかった起動の時刻**: 境を決められなかった起動 (`cutover.json` を書けなかった起動を含む) は何も変換しないが、アプリは起動を続けて新しい形式の行を書く。次の起動がその起動の時刻で境を決め直すと、間に届いた発言が境より前の行として扱われ、規則に当たれば変換される。そこで、境を決められなかった起動は、その起動で決めようとした境の時刻 (決める前に止まったなら、その起動で移行を始めた時刻) を本体 DB の `execution_ledger` に一行だけ残す (`_leave_cutover_attempt`)。KIND は `system_notice_migration.cutover_attempt`、IDEMPOTENCY_KEY は固定の `first`、STATUS は `completed`、時刻と決め方は PAYLOAD_JSON に書く。既にその行があれば書き換えないので、最初に残した時刻が残る。台帳の読み手 (`saiverse/execution_ledger.py` と `saiverse/building_id_repair.py`) は STATUS (と KIND の前方一致) で絞って走査するので、`completed` のこの行は回復の処理の走査に入らない (`system_notice_migration.commit` の行と同じ)。`resolve_cutover` は、この行の時刻も境の候補に含め、最も早い時刻を取る規則のまま決める (決め方 `unrecorded_attempt`)。その起動の時刻は実際の切り替えより早いことはないので、候補に足しても境が実際より早まることはない。本体 DB が無い、`execution_ledger` が無い、本体 DB に書けないときは残さず、今までどおり次の起動の時刻で決め直す。境を決める前の起動で本体 DB を読めないときは、残した時刻を読み落とすと境が遅く決まるので、境を決められないものとして扱う (2026-10-29、敵対レビュー 5 巡目の指摘。それまでは記録できなかった起動の時刻がどこにも残らなかった)。
- **境より後に作られた行**: どの規則に当たっても自動では変換せず、確認待ちにする (理由 `AFTER_CUTOVER_REASON`)。境と同じ秒に作られた行も境より後として扱う。保存先ごとに時刻の精度が違い (本体 DB の `created_at` は秒まで)、同じ秒の中の前後を決められないので、確認待ちの側に倒す (2026-10-29、敵対レビュー 2 巡目の指摘。それまでは同じ秒の行を境より前として扱い、境の直後の行を変換しえた)。新しい形式のコードは `<system>` を書かないので、境より後に機械が直すべき `<system>` の行は無い。例外は記憶 DB の `messages` の role=system の行で、境より後でも規則で判定する (2026-10-30)。移行が role=system の行にするのは系統の印を足すことだけで、名義も本文も書き換えない (本文を剥がす規則は role=user と role=assistant の行にだけ当たる) から。記憶ブラウザの「メッセージを追加」(`api/routes/people/memory.py` の `create_message`) では所有者が role=system の行を足せるので、所有者が機構の書く形とそっくりの system の行を境の後に足すと、その行にも系統の印が付き、自動想起の検索の元に入るかどうかがその系統の扱いに変わる。名義と本文は所有者が書いたまま残るので、この扱いを受け入れて、印の無いまま書かれた機構の行 (本文が空の Stelis の開始の行など、確認の画面では判断しにくい行) を所有者に委ねずに片づける側を取った (2026-10-30 まはー裁定。Codex の敵対レビューの指摘で、最初に書いた理由「ユーザーは role=system の行を送れない」が誤りだったと分かった)。v0.3.27 の後も印の無い role=system の行を書いていた書き手がいた (上の「移行の規則の版 4」)。記憶 DB の `messages` のほか、paired_action_text・perception_batches・本体 DB の building_messages・実行台帳にも同じ境を当てる (印の置き場の無い列は書き換えずにレポートに出す)。例外は旧 log.json の取り込みの行 (`seq < 0`) で、取り込みはこの移行より後に走るので、入った時刻に関係なく境より前として扱う。
- **境を決められなかった起動が残す時刻**: 境の候補を集める途中で決められなくなった起動は、そこまでに読めた候補とその起動の時刻のうち最も早い時刻を、本体 DB の `execution_ledger` (KIND `system_notice_migration.cutover_attempt`、固定の一行) に残す。後の起動がより早い時刻を残そうとしたときだけ書き換え、行の時刻が読めなければ書き換えない (2026-10-29、敵対レビュー 6 巡目の指摘)。
- **境を決められないとき**: 記録を読めない・書けない、記憶 DB の印を読めない、記録が無いときに本体 DB の `execution_ledger` を読めない、移行が前に書いた記録はあるのにその時刻を読めない (`RUN` があって壊れている、`RUN` の無い前の版の形式のフォルダで名前の時刻も JSON の更新時刻も読めないなど) ときは、どの DB も変換せず、画面に警告 `system_notice_migration_cutover_unavailable` を出す。最も早い印や記録を読み落とすと境が遅く決まるからである。
- **境を守れない場合 (2026-10-29、敵対レビュー 6 巡目への裁定、メティスの判断)**: この版を初めて動かした起動で、`cutover.json` と本体 DB の `execution_ledger` の両方に書けなかったときは、その起動の時刻はどこにも残らず、保存先が直った後の起動の時刻が境になる。そのあいだに届いた真似た文は自動で変換されうる。その起動では画面に「境を決められない」警告が出るので、所有者は気づける。本体 DB に書けない状態では SAIVerse そのものがほぼ動かないので、起動を止めて待つ仕組みは足さない (2026-10-29、まはーが受け入れを判断。docs/issues/system_notice_cutover_unsaved_window.md)。また、新しい版で動かした後に同じ SAIVERSE_HOME で古い版を動かす (版を戻す、または二つの版を同時に動かす) 使い方は想定しない — 古い版は新しい版の確定の記録・時刻の境・回の記録を知らないので、所有者の確定を無視して変換したり、変換の記録を捨てたりしうる。こうした端の場合は、移行の中で一つずつ塞ぐのでなく、起きる前提そのものを SAIVerse 全体の守りで起きなくする方針で、docs/issues/edge_conditions_need_system_guards.md に列挙した。
- **残る範囲**: 記憶の行の `created_at` は書いた時刻ではなく発言の時刻なので、記憶の移植 (別の環境の時刻を持ち込む) と記憶の編集 API (古い行の本文や時刻を変える) では境を回り込める。どちらも所有者の操作なので受け入れる。v0.3.27 の起動で移行が何も書かなかった環境 (記憶 DB が無く、本体 DB にも変換や残した行が無かった起動) には印も記録も残らないので、境は次にこの版を動かした起動の時刻になる。`cutover.json` を消すと、印と移行の記録から決め直す。写しや記録の更新時刻は最後に書いた時刻なので、それらも消えていれば決め直した時刻は本来より遅くなりうる。
- 本番の写しの予行では、境は 2026-10-28T05:11:48Z になり、変換の件数は境を入れる前と同じだった (境より後に作られた行に、規則に当たるものは無かった)。敵対レビュー 3 巡目の修正の後の予行 (2026-10-29) でも、境・変換の件数 (記憶 DB で 833 件、うち規則 5 が 104 件) とレポートの中身は変わらなかった。写しの本体 DB では role=user の行 3266 件の metadata がどれも読め (1682 件は空)、写しには起動ごとの結果のフォルダが無く、本体 DB には `execution_ledger` があって変換する行も無かったので、3 巡目で直した四つの挙動はどれもこの写しの結果を変えない。敵対レビュー 5 巡目の修正の後の予行 (2026-10-29) でも、境 (2026-10-28T05:11:48Z、記憶の完了の印から) と変換の件数 (記憶 DB で 833 件、うち規則 5 が 104 件) は変わらず、dry-run は写しの本体 DB の `execution_ledger` に行を書かなかった。

### 確認待ちの行の確定 (利用者の画面)

残った著者不明の行 (例: まはーが別のゲームの記憶を手で移植した行) は、機械が決めずに持ち主が画面で確定する。

- **入口は「確認待ちの印 (`__system_notice_review__`) を持つ行が存在する」という状態に応じて出す。** 起動時のバナーという一度きりの表示に頼らない (まはー 2026-10-29「最初の導線から設計し直す必要がある」)。印が残っている限り画面に入口が出続け、全行の確定で消える。起動時のバナーの文面も、レポートのファイルの場所ではなくこの入口へ誘導する形に直す。実装 (2026-10-29): 確認の画面のサービス `saiverse/system_notice_review.py` が、起動時と確定の操作のたびと、画面が一覧を取り直すたび (一時的に読めなかった記憶が読めるようになったとき、確定する行が無くても警告を外せるように。PR #434 のレビューの指摘) に確認待ちの件数を数え、1 件以上なら警告 `system_notice_review_pending` (バナーの「確認する」から画面を開く) を置き、0 件で外す。移行の側の警告からは確認待ちの件数とレポートの場所を外し、確認待ちだけの回の警告 (`system_notice_migration_review`) とレポートの作り直しの警告 (`system_notice_migration_report_regenerated`) は廃止した (レポートは移行の記録としてファイルに残る)。記憶 DB を読めなかったペルソナがあるときは、確認待ちが 0 件でも警告を外さず、読めなかったペルソナの名前を出す (読めない DB に確認待ちの行が残っているかは分からないため)。画面も、読めなかったペルソナがあれば閉じずに名前と「読み込みをやり直す」を出す。バナーは閉じられるので、設定の「便利機能」にも同じ画面を開く項目を置き、警告がある間だけ出す (2026-10-29、Codex 1 巡目の指摘への対応)。
- 問い (まはーの設計、2026-10-29): 「**これらは正式なシステムメッセージとして残しても良いですか？**」。補足に「v0.3.27 以降のバージョンでは `<system>` で囲んだだけのメッセージはペルソナから偽のシステムメッセージとみなされる可能性があります」と問題をはっきり書く。
- 選択肢は最大 4 つで、**その行の作りで嘘にならない操作だけを出す**: **そのままにする** = 行を変えず、確定の記録だけ残す / **正式に変換** = role=system に変えて系統の印 `owner_confirmed` を付ける (`<system>` タグが本文全体を囲んでいれば剥がす)。role=user や role=assistant の行が添付 (`media` / `images` / `documents`) を持つときは出さず、API の側でも同じ判定で拒否する — 行ごと role=system にすると、発話者の添付が機構の通知の持ち物になる (不変条件 7)。一覧は各行の添付の種類と件数・ファイルの参照を返し、画面に出す / **通常のユーザー発話に変換** = role=user のまま普通の発話に戻す。`<system>` タグが本文全体を囲んでいれば開きと閉じのタグだけを外し (包みの内側の前後の空白・改行は変えない)、そうでなければ本文を一字も変えない。実会話から外す印 (機構のタグ `handy_tool` / `spell` / `event_message` と、line_role の `sub_line` / `meta_judgment` / `nested`) もその行から外して line_role を `main_line` にし、外したものを metadata の `__system_notice_review_cleared__` に残す。**role=user の行にだけ出す** — role=system や role=assistant の行に出すと、機構やペルソナの文がユーザーの名義になる。タグが本文の途中で閉じている role=user の行 (ユーザー本人が本文の途中に `<system>` を打った発言など) にも出す。本人が打ったとおりの本文が、本人の発話の正しい記録だから (2026-10-29 の隔離環境での画面の確認で、実装の最初の定義「タグが剥がせる行にだけ出す」では本人の発話を発話に戻す手段が無いと分かって改めた) / **削除** = 行を消す (確認ダイアログ付き)。建物の履歴から転記された行 (`building_msg_ref` を持つ行) は、消す前に建物の側の取り込み済みの印 (`ingested_by`) を確実にし、付けられなければ消さない — 転記は、建物の側の印の書き込みに失敗した行を記憶の側の `building_msg_ref` の照会で見つけて重複を避けるので、照会先の行を消すと同じ発話が取り込み直されて復活する。転記の側は、記憶へ足す直前に建物の行の `ingested_by` を本体 DB から読み直し、自分の印があれば足さない。転記が建物の履歴を読んだ後に削除が割り込んでも、行は戻らない。複数のペルソナが同じ建物の行へ並行して印を足すときは、読んだ時点の値を更新の条件に入れて読み直す (`mark_ingested`) ので、互いの印を消さない (2026-10-29、Codex 2 巡目)。転記は、読み直しで既に自分の印があって何も足さなかった候補を「追記を試みた」と数えない。数えると次の候補の `building_msg_ref` の照会が省かれ、記憶に追記済みで印だけ無い行を足し直すからである。照会は記憶 DB の錠の中で読み、削除は同じ錠の取引の中で本体 DB の印をコミットしてから記憶の行を消すので、照会が行を見ないときは読み直しが必ず印を見る (2026-10-29、Codex 3 巡目)。
- **確定の記録**: 確認待ちの印を消すだけだと、完了の印の無い DB を走査し直したときにまた印が付いて、所有者の判断が消える。確定した行からは確認待ちの印を消し、代わりに確定の記録 `__system_notice_reviewed__` (`SYSTEM_NOTICE_REVIEWED_KEY`、値は選んだ操作 `keep` / `system` / `user`) を書く。移行は、この鍵を持つ行の印付けと変換を両方とも飛ばす。確認待ちの印が掛けている除外 (会話の手本・想起・あらすじの判定からの除外 — storage.py の `_conversation_exclusion`) は、変換・発話への変換・削除で解ける。「そのままにする」(`keep`) の行は除外したままにする — 偽タグに見える本文のまま残す選択なので、口調の手本や想起に混ぜない側に倒した (2026-10-29、メティスの判断。この扱いの設計は後で見直せるが、所有者が一度「そのままにする」を選んだ行を画面から選び直す操作は第一版には無い)。書き手が決まっていない行 (確認待ちと `keep`。判定は storage.py の `is_author_unsettled` で、`_conversation_exclusion` の SQL の条件と同じ行を選ぶことをテストで固定した) は、あらすじと Memopedia の材料にも発話として渡さない。あらすじでは材料の文を空にするだけで、編纂の対象と被覆 (source_ids) からは外さない — 2026-08-29 の裁定で提示に立った行は被覆に入るので、外すと所有者が後で確定したときに被覆の穴が開き、退場の勘定も変わるため。引き換えに、確認待ちのあいだに編纂されたあらすじは、所有者が後でその行を発話や通知と確定しても、その本文を含まないまま残る。確定のときに編纂し直す経路は第一版には無い (2026-10-29、敵対レビュー 6 巡目の指摘を受けて、この得失を受け入れると判断した。確認待ちの行は画面の警告で知らされ続け、欠けるのは所有者が確定するまでのあいだに編纂された分だけなので)。書き手が決まっていない行は、記憶の検索・想起の候補にも入れない。キーワード検索と意味検索の候補 (storage.py の `get_all_messages_for_search`・`get_embeddings_for_scope`) では順位付けの前に、当たりの周辺の行を広げるとき (`get_messages_around` の `settled_only`) では広げた後に、同じ条件 (`author_settled_sql`) で外す。広げるときは、前後それぞれ指定の件数を正典の順で取ってから外し、外した分を遠くの行で埋めない。当たりを挟む並べ方は、前と後を別々に取って連結し、同じ秒の行の順を `created_at` だけで並べ直さない (`get_window_with_anchor`。2026-10-29、Codex 3 巡目)。対象は Memopedia の検索・`memory_search_brief`・`memory_recall`・`recall_walk`・鮮明想起・`saiverse://` の本文検索で、既に `_conversation_exclusion` を通っている `unified_recall` と scene は元から外れている。ID や時刻を指定した読み出し (`memory_read_around` など) は、普段の履歴と同じく外さない (2026-10-29、Codex 2 巡目)。**外すのは検索の候補と窓の行までで、当たりの行の本文を組み立てるときに別の行を引き込む展開 (`compose_message_content` の `other_thread_messages`、Stelis のスレッドの開始と最新の行) までは追わない** (2026-10-29、Codex 4 巡目の指摘への裁定、メティスの判断)。理由は、書き手の決まっていない行は普段の会話の履歴 (`get_messages_last`) には今も並んでいて、ペルソナはその本文を履歴として読んでいるからである。想起から外すのは、検索で当たった行を「その時ユーザーが言ったこと」として改めて差し出さないための手当てで、本文を見せない柵ではない。読み出しの経路は多く、本文を展開する箇所を一つずつ外す修正は巡ごとに次の箇所が見つかって閉じないので、守る範囲をここで線引きする。
- **キャッシュへの影響**: この画面の操作は、稼働中の任意の時点で履歴の途中の行を書き換えるので、操作のたびにそのペルソナの送信の前方一致がその行から先で割れる。所有者の明示の操作に伴う計画されたコストとして受け入れる (不変条件 6 は「同じ記録から組む本文は揺れない」の約束で、記録そのものを所有者が変える場面には及ばない)。実行中の Pulse と重なったときの排他は、記憶ブラウザの既存の編集 API と同じ扱いに乗せる (実装時に確認)。
- **音声入力の案内文の行の「正式に変換」は二行分割**: 確認待ちの行のうち規則 5 の形の role=user の行 (`is_voice_split_row`) では、「正式に変換」は行ごとの変換ではなく、移行と同じ二行分割 (案内文は系統 `voice_input` の通知、音声は本文の無いユーザーの発言) にする。元の発言の行が画面から送られたかは問わない (所有者が見て決める操作なので)。時刻の境より後に古いアドオンから届いた案内文の行は自動では変換されないので、所有者はこの操作で片づける (2026-10-29、敵対レビュー 7 巡目の指摘)。音声の行を通知の直後に並べられない行には出さない (移行の `SPLIT_POSITION_REASON` と同じ約束)。画面には、正式に変換したときの結果 (案内文はシステムメッセージに、音声はユーザーの発言として残る) を一文で添える。同じ並びの中に二行分割になる行と行ごとの変換になる行が混ざるときは、一括の操作から「正式に変換」を外し、行ごとのボタンでだけ選べるようにする (同じ操作の名前で結果が違う行に、一括で当てない)。移行と確認の画面は `is_voice_split_row`・`voice_split_metadata`・`split_insert_statement`・`split_position_is_free` を共有し、`SAIMemoryAdapter.rewrite_message` は同じ取引の中で一行足せる (`insert_after`)。確定の操作の後は、確認の画面を開いた側が window に `saiverse:system-notice-review-changed` を出し、上部のバナーと設定の入口の両方が警告を取り直す。
- **並べ方 (2026-10-30 に作り直した)**: 一段目はペルソナ、二段目はそのペルソナの中の名義 (role。`model` は `assistant` と同じ並び) で、行は記憶 DB の順に一件ずつ全文で並ぶ。最初の版は本文の書き出し・タグの組・確認待ちの理由で束ね、束ごとに理由の説明を出していたが、本番の画面で、似ているだけの行の束の件数が何を指すのか分からず、理由の説明は所有者の判断 (自分が書いた文ならそのまま、システムの知らせなら正式に変換、覚えが無ければ削除) に関わらなかった (まはー 2026-10-30)。だから理由・タグ・line_role は画面に出さない。代わりに、判断の材料として、各行に作成の日時と「前後を見る」(同じスレッドの前の 3 件と後ろの 3 件を、確認待ちの行も含めて読み取り専用で出す。`GET /api/system/notice-review/context`) を置く。添付がある行の「正式に変換できない」と、二行分割の結果の説明だけは、選んだ操作の結果に関わるので残す。名義ごとの一括の操作は、その並びの全行で選べる操作の共通部分で、どの操作でも対象の件数を確認ダイアログに出す。一覧は各行の role・本文・metadata・created_at・line_role から作るハッシュ (`version`) も返し、確定の操作は書き込みの取引の中で今の行から作ったハッシュと違えば、書き換えずに拒否する (`changed`。画面は一覧を読み直す) — 一覧を開いた後に記憶ブラウザなどで変わった行に、所有者の選択を当てないため。created_at は一覧が表示する日時、line_role は発話への変換が書き換える値なので材料に入れた (2026-10-29、Codex 2 巡目)。
- 第一版の対象は、ペルソナの記憶 DB にある確認待ちの行。本体 DB (building_messages) の変換しなかった行 (まはーの環境で 114 件) を同じ画面に載せるかは、実装時に件数と表示の実害を見て決める。

### 音声だけの発言 (今後の分の供給の修正)

音声入力のときに定型文を本文へ添える処理自体を廃止する。本文が空で音声だけの発言は、本体では既に受け付けられる (manager/runtime.py の `_utterance_is_empty` は本文が空でも `has_attachments` が真なら通し、`saiverse/media_utils.py` の `has_attachments` は音声を添付に数える — 2026-10-29 にコードで確認。v0.3.24 の PR #397 で画像だけの発言を通した同じ判定)。だから本体の改修は要らず、音声入力を中継するアドオン (stackchan・Godot ほか) が定型文の代わりに空の本文で音声のデータだけを送ればよい。どこから届いた音声かを知らせたい場合は、正式なシステム通知を併せて送る — この通知の作り手はアドオンのサーバー側のコード (音声入力を中継するアドオンはどれもバックエンドのプロセスの中で `manager.handle_user_input_stream` を直接呼んでいて、外から送信 API を叩く中継は無い — 2026-10-29 に各アドオンのコードで確認) なので、「識別用の metadata はサーバーだけが書ける」(不変条件 4) の内側に収まる。外部のプログラムが直接通知を作る口は作らない。これで「機構の書いた文がユーザーの名義で残る」余地が根から消える (まはー 2026-10-29「音声だけのユーザー発言にするのは賛成」)。stackchan 0.5.3 で定型文を地の文にした変更は、この修正までの繋ぎ。
