# ユーザーの添付がペルソナに届く道 — 発言が中身を運び、アイテムは閉じて置く

**ステータス**: 検証待ち (2026-11-10 実装、PR #468 で develop に入り、v0.3.30 に載る。実機の確認待ち)

## 芯

ユーザーがチャットに添付したもの (画像・文書・音声・動画) は、**ユーザーの発言 (role=user) が中身を運ぶ**。添付から作るアイテムは四種類とも**閉じた状態**で部屋に置く。中身がペルソナに届く道は、添付した回については発言の一本だけにする。

## なぜ (2026-11-09〜10 の調査)

まはーの観察「動画添付で作られた動画アイテムが、画像と違って最初から open になっている」から調べた。

- 添付からアイテムを作る処理は種類ごとに別の関数で、初期状態がばらばらだった。画像 (`create_picture_item_for_user`) は `state` が空で閉じた扱い。文書 (`create_document_item_for_user`) は `is_open=True`。音声・動画 (`_create_media_item_for_user`、2026-05-18 の `d2f1c740`) は文書の処理を写して `is_open=True`。音声・動画の intent ([media_input_audio_video.md](archive/media_input_audio_video.md)) は「画像と同じ思想」と書いていたのに、実装は文書を手本にした。
- 発言が中身を運ぶかどうかも種類で違った。画像は発言の `metadata["images"]` が、音声・動画は `metadata["media"]` が中身を LLM へ運ぶ。文書は `metadata["documents"]` を読むのが添付の通知 (`_enrich_history_with_attachments` の「添付アイテム作成: ドキュメント「x」」) だけで、本文はどのクライアントも送っていなかった。文書の本文は、open の文書アイテムが部屋の様子に載る道でしか届かなかった。
- その結果、音声・動画は二重に届いていた。2026-10-28 に添付された `erys_avatar.mp4` の送信記録 (`llm_io.log`) では、同じ動画ファイルが発言の `metadata["media"]` と、直後の部屋の様子の通知の `media` の両方に付いていた。Gemini のクライアントはメッセージごとに動画を読み込んで送り、メッセージをまたいだ重複を省かない。
- PDF の添付は、アイテムのファイルが PDF そのものなので、部屋の様子が UTF-8 のテキストとして読もうとして失敗し、open にしても説明文 (抜き出した文字の頭 200 字) しか載らない作りだった (コードから。送信記録では未確認)。

## 届け方の決まり

### 文書の本文は、ユーザーの発言の後ろに付けて送る

- 添付した時点で本文を抜き出し、発言の `metadata["documents"]` の各項目に写す (上限 8000 字)。PDF は全ページから文字を抜き出し、上限に届くまで読む。
- 記録に残る発言の本文は、ユーザーが言った言葉のまま変えない。本文を足すのは、送る直前のクライアント層だけ。全クライアントと `sea/sluice.py` (送る量の見積もり) が通る `llm_clients/system_notice.py` の `present_system_notices` から呼ぶ。
- ペルソナには次の形で届く。

  ```
  (role=user) これ読んでみて

  [添付文書: memo.txt]
  (本文。8000 字まで。切ったときは末尾に「... (以下省略)」)
  ```

- **本文を添付の通知 (role=system) に載せてはならない。** 通知はペルソナに「世界の仕組みからの知らせ」として届くので、ユーザーの文章を載せると、ユーザーの文章がシステムの言葉に化ける ([system_notice_delivery.md](system_notice_delivery.md) 不変条件 2)。2026-11-09 の最初の案はこれを踏んでいて、実装前に取り下げた。
- 本文を写すのは、この変更から後の添付だけ。前からある発言の `metadata["documents"]` には頭の 500 字 (`content_preview`) しか無く、それを送り始めると過去の発言の文面が変わってキャッシュの前方一致が割れるので、古い添付は今のまま送る。

### アイテムは四種類とも閉じて作る

- 添付からアイテムを作る処理は一つの関数にまとめ、初期状態は常に閉じた状態 (`{"is_open": False}`) にする。どの種類も発言が中身を運ぶので、開いて作る理由が無い。
- ペルソナがあとで中身を見直したいときは、自分でアイテムを開く。文書はペルソナが `document_edit` で書き換えうるので、開いたときに見えるのはその時点の版で、発言に付いているのは添付した時点の版になる。

## 不変条件

1. 添付した回に、同じ添付の中身がペルソナへ二度送られない。閉じたアイテムも部屋の様子には説明文 (`description`) で載り、文書の説明文は本文の頭 200 字なので、その 200 字だけは発言の本文と重なる。これはアイテムの説明として受け入れる (閉じた画像が説明文で載るのと同じ扱い)。
2. ユーザーの添付の中身は、ユーザーの発言 (role=user) としてだけ届く。システム通知の本文に載らない。
3. 同じ記録から組む送信本文は一字も変わらない (system_notice_delivery.md 不変条件 6 の継承)。文書の本文は記録の `metadata` の写しだけから組み、ファイルを読みに行かない。
4. 記録に残る発言の本文はユーザーの言葉のまま。

## 影響の範囲と、変わらないもの

- 記録の本文が変わらないので、自動想起の種・Chronicle のあらすじの入力・記憶の検索には文書の本文が入らない (画像の中身が入らないのと同じ扱い)。
- `llm_io.log` と画面の文脈プレビュー (`/api/chat/preview`) は SAIVerse 層の列を写すので、足した本文は出ない。
- 合言葉の伏せ字: 足した本文はユーザーの発言の一部として、`present_system_notices` の既存の伏せ字の処理を通る。

## 検証計画

- 隔離環境 (合成ペルソナ・LLM を呼ばない) で、文書・PDF・画像・音声・動画を添付した発言を作り、各クライアントへ渡る直前の列を読んで、本文が発言の後ろに一度だけ付き、部屋の様子に中身が載らないことを確かめる。
- 古い形の `metadata["documents"]` (本文の写しが無い) の発言から組む列が、変更の前後で一字も変わらないことをテストで固定する。
