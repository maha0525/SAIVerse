# Intent: リアルタイム処理基盤 (Realtime Foundation)

> **ステータス: v0.1 方針確定 (2026-07-27) — 上位方針文書・実装なし**。まはーとメティスの設計対話で骨格を確定。本書は個別機能の intent ではなく、リアルタイム処理に関わる複数の intent (physical_ear / embodied_expression / vessel / perception_buffer / salience_module ほか) を束ねる**一枚の図面**。実装は各個別 intent の側で進み、本書はその配置と不変条件だけを持つ。

## これは何か

ペルソナと「ミリ秒〜秒で流れる現実」を接続するための全体方針。将来目標である三つの体験——

1. **画面共有ゲーム**: ペルソナと一緒にゲームを遊ぶ。画面を認識し、その時々に応じた操作をする
2. **ロボット同居**: カメラを目、マイクを耳にして生活のそばに常時いて、ちょいちょい口を出し、家の中を動く
3. **VR 同伴**: Godot vessel を発展させ、VR 空間で一緒に遊ぶ

——はすべて、ペルソナの認知 (Pulse、秒〜分) より何桁も速い世界との接続を要求する。本書はその接続を「Pulse を速くする」のではなく「**Pulse の下に速い層を敷く**」方針として確定する。

## これは何でないか

- **実装計画ではない**。フェーズもスケジュールも持たない。実装の単位は各個別 intent。
- **Pulse の高速化・置き換えではない**。認知の層は現状のまま。ここを速くしようとしないことが本方針の核。
- **個別 intent の置き換えではない**。physical_ear / embodied_expression / virtual_embodiment_godot / vessel / perception_buffer はそれぞれの領分の正典であり続ける。本書はそれらの**位置関係**の正典。

## なぜ必要か

### 1. 部品は既に散在しているが、図面がなかった

リアルタイム処理の骨格の半分は既にリポジトリにある。しかも中心概念である「軽量ローカルモデルによる知覚の選別」は**三つの文書に三回書かれている**:

- `physical_ear.md` の「判断層」(E4B が ignore / respond / continue を返す)
- `salience_module.md` のセイリエンスモジュール (一般形。重点監視指示・構造化出力まで設計済み)
- `perception_buffer.md` §4.4 の「将来拡張: 軽量 LLM 門番 = SN 層」

三者は同一の設計スロットであり、統一されないまま増えると互いに矛盾する実装を生む。束ねる図面が要る。

### 2. 時間スケールの断絶は構造で解くしかない

現代の LLM 推論速度では、ペルソナ本人 (フルモデル) が知覚情報を常時認識し続けることはコスト・速度の両面で成立しない。事前に決定論または超軽量モデルで知覚を解釈・選別・蓄積する層が必須であり、行動側も同様に、発話時以外はペルソナの意図だけを保持して決定論・軽量モデルが動きを持続する層が必須。この「層の分離」を場当たりでなく原則として持つ。

## 設計の第一原理

SAIVerse には既に時間モデルの正典がある — **「ペルソナの主観時間は Pulse でのみ進む」** (`perception_buffer.md` §1)。本方針はこの原理を変えず、逆に土台にする:

**Pulse より速く動くものは、すべてペルソナ本人ではなく「身体と知覚の設備」である。**

人間の認知と同じ構図 — 意識 (数百ms〜秒) より速い処理は脊髄反射と無意識の注意フィルタが担い、意識は直列のまま。この対応があるから、リアルタイム層をいくら増やしてもペルソナの人格・著者性は汚れない。

## 三層構造

時間スケールで三つの層に分ける。

### ① 反射の層 (ミリ秒〜。決定論、LLM なし)

置き場所は edge — vessel の gateway / 捕捉クライアント。VAD での発話切り出し、まばたき・アイドル揺動、`/emote` の TTS 同期発火、サーボ再生、ゲームなら決定済み入力列の実行、移動クランプ。

新しい発明ではなく、既に各所で下されている判断の明文化: physical_ear の edge VAD、embodied_expression の subscriber 側発火、embodied_passive_input (C) 節の「gateway 内ローカルループ」。**反射は edge に置き、認知には上げない。**

### ② 注意と選別の層 (〜数秒。ローカル軽量モデル)

リアルタイム基盤の心臓。二つの係が住む:

- **知覚側 = セイリエンス層 (気づく係)**: 軽量マルチモーダルモデルが知覚を選別し、人格本体へ上げるべき出来事だけを上げる。一般形の正典は `salience_module.md` に置く (§既存文書との対応)。physical_ear の判断層はその音声特化インスタンス、カメラ知覚 (アイディア帳の NPU E4B モニタリング) は視覚インスタンス。
- **行動側 = 意図の執行係**: Pulse で本人が宣言した意図 (「ユーザーについていく」「敵の攻撃を避け続ける」) を、Pulse と Pulse の間ずっと決定論または軽量モデルで動かし続ける。意図から外れる出来事が起きたらセイリエンス層に渡して Pulse を起こす。骨格は embodied_expression v0.3 の Body behaviour (`command_id` 付きライフサイクル追跡) の延長にあり、「単発コマンド」を「持続する意図」へ一般化する段の設計が将来課題。

### ③ 認知の層 (秒〜分。Pulse = ペルソナ本人)

変更なし。入口は知覚バッファ一本 (`perception_buffer.md` 不変条件 C5)、出口は意図の宣言と behaviour 発行。

## 橋は二本

層の間の接続は二本の橋に限定する。

- **上り橋 = 知覚バッファ** (実装・実機検証済み)。セイリエンスの `should_escalate` は知覚バッファの「起動力」属性 (§4.4) そのもの。上げないと判断された観測は、salience_module の言う「一定時間で消える短期の生活コンテキスト」に留まり、長期記憶を汚さない。
- **下り橋 = 意図の集合**。Pulse が意図を宣言・改廃 → 執行係が持続実行 → ライフサイクルイベント (完了・失敗・中断) が知覚としてバッファに上がる。`command_id` 契約の一般化。

## 並列と調停 (第三の柱)

**反射・セイリエンス・意図は、一つのペルソナが複数持ち、並列に動く。** 目標物へ進む係と障害物で止まる係は同時に稼働しなければならないし、進みながらユーザーの声を聴けなければならない。原則は:

**著者性は単線、執行と知覚は並列。**

意図を決める場所 (Pulse) と「本人が何を決め何を言ったか」の筋は一本のまま。それを実行する係と気づく係は何本並んでもよい。

### 知覚側の並列 — 既に安全

耳・カメラ・ゲーム画面のセイリエンスが同時に動いても、全出力が知覚バッファという一つの漏斗に注ぐ。バッファへの書き込みは客観時間でいつでも起きてよい設計 (§4.1) なので、書く側が何本いても壊れない。合流点が直列化点。**セイリエンスのインスタンスは複数登録できる**と明示するだけで成立する。

### 行動側の並列 — 調停が新設計

「進む」と「止まる」は並列だが**同じ足を取り合う**。よって:

- 意図ハンドルは「今の behaviour 1個」ではなく**意図の集合**として持つ (進む+聴く+避ける、が同時に生きている)
- 各意図は使用する**身体資源を宣言する** (移動・視線・発声・手 …)。資源が重ならない意図は素通しで並列、重なったら調停
- 調停は優先度で決める (障害物停止 > 目標接近)。既知の型としてロボット工学のサブサンプション・アーキテクチャ (上位の反射が下位の行動を一時的に抑え込む層構造) が借りられる

### 調停は層内で完結してよい — ただし必ず知覚に上げる

障害物で止まるとき本人の認知を経由していたら間に合わない。**止まるのが先、気づくのが後** (人間も足が先に止まってから「おっと」と思う)。層内で起きた抑制・中断・強制停止は、必ず知覚としてバッファに上げる。身体が勝手に何かをして本人が知らないまま、は作らない。

### 既存機構への影響は「橋から下」に閉じる

並列の世界は全部、上り橋と下り橋の外側 — gateway と vessel 実行系の中に住む。橋の両端が直列化点:

- バッファへの書き込み = 並列 OK、消費 = Pulse で直列 (既存のまま)
- 意図集合の書き換え = Pulse のみ (直列)、読み取りと執行 = 並列

**PulseController・Beat ロック・SAIMemory には手を入れない。** ペルソナ本体の単線機構は現状のまま、その下に並列の床が敷かれる。

## 記憶への含意

リアルタイム知覚はほぼマルチモーダルであり、テキスト特化の現行記憶と正面からぶつかる。方針:

### 視覚的記憶 — 第一の読者はセイリエンス層

「ユーザーの顔を覚えて認識する」の実用の九割は Pulse ではなくセイリエンス層で起きる。カメラに人が映った瞬間、軽量モデルが「人影が映った」ではなく**「まはーが部屋に入ってきた」**と言えること — それが「顔を覚えている」の実体。よって:

- **実体アンカー付きの認識索引**: 昇格された画像 (`multimodal_input_pipeline.md` の disposition 機構が受け皿) から「この顔 = このユーザー」「この機器 = この Fixture」という実体対応を埋め込みで索引化し、**セイリエンス層が参照する**
- **記憶の正典はテキスト + 参照のまま**: memopedia のエントリが外見を言葉で持ち、画像はアセット参照。SAIMemory のテキスト正典性を壊さない
- 部屋のどこに何があるかは画像ですらなく**構造化データ** (Building のアイテム配置の現実世界版)。視覚は入力手段であって保持形式ではない

### 手続き記憶 — 「状況の合図 + 手順」の対

「Playbook をペルソナが自作して能力を拡張する」構想の抽象化として設計する。手続き記憶の一単位は:

- **状況の合図**: 「戦闘画面になった」「このエラーが出た」 — **セイリエンス層が状況を分類したタグ**がそのまま検索キー
- **手順**: 知見の文章 + 確認事項 + ツール手順 (固まってきたら Playbook 化)

想起はアイディア帳の「知識インポート型の学習」(実行すると知識だけがコンテキストに入り、覚えている間は自由に使える) と同じ機構 — 状況タグが合図になって手順エントリが読み込まれる。学習は Pulse が経験の後に手順エントリを書く・直すこと (gold_panning の手続き版)。「事前知識なくゲーム中に覚える」は、①セイリエンス層が画面状態を分類 → ②本人が試行 → ③うまくいった手順をエントリに書く → ④次に同じ状況タグで想起、のループ。

## 三つの将来像がこの骨格にどう乗るか

| | 反射の層 | セイリエンス + 執行 | Pulse |
|---|---|---|---|
| **画面共有ゲーム** | 入力列の再生 | 画面状態の分類・宣言済みプレイ方針の持続実行 | 戦略・学習・雑談 |
| **ロボット同居** | VAD・まばたき・サーボ | physical_ear 判断層・カメラ監視・「ついていく」執行 | 会話・口出しの判断 |
| **VR 同伴** | モーション再生・IK | 意図保持の身体制御・空間イベント選別 | 遊びの中身 |

vessel (`vessel.md`) はこの図で「どのペルソナがどの身体を持ち、その身体がどの反射・執行能力 (capability) を提供するか」のレジストリとして三層の下を支える。大きな増改築は不要の見立て。

## 不変条件

1. **主観時間は Pulse でのみ進む** (perception_buffer §1 の継承)。リアルタイム層はこの原理を回避する経路を作らない。
2. **著者性は単線、執行と知覚は並列**。意図の出所は Pulse 一本。反射・セイリエンス・意図の執行は複数並列。
3. **Pulse より速い処理はすべて設備であり、人格ではない**。セイリエンス層・執行係は本人の代わりに発話・最終判断・記憶の意味づけをしない (salience_module の「気づく係」原則の一般化)。
4. **知覚は知覚バッファ一本に集約する** (perception_buffer C5 の継承)。セイリエンスのインスタンスが何本増えても、バッファを迂回して SAIMemory や Pulse に直接届く経路を作らない。
5. **意図の集合を書き換えるのは Pulse のみ**。執行係・反射は意図を読み、実行し、抑制できるが、意図そのものを追加・削除しない。
6. **層内の抑制・中断は必ず知覚として上がる**。調停は Pulse を待たず層内で完結してよいが、起きたことは本人が次の Pulse で必ず知れる。
7. **常時稼働部分に課金経路を置かない** (physical_ear 不変条件 1 の一般化)。反射とセイリエンスは完全ローカルで回し、課金 API はエスカレーション時のみ。
8. **記憶の正典はテキスト + 参照**。画像・音声はアセットと認識索引であり、SAIMemory の本文を置き換えない。

## 実装順の見立て (依存関係のみ)

1. **physical_ear** — 最初のセイリエンス実装 (決定済み)。音声で「知覚 → 選別 → エスカレーション」の一巡を通す
2. **カメラの兄弟** — 二例目で音声特化を一般形 (salience_module) に上げる。実体アンカー認識索引はここから
3. **意図の執行係** — Godot の behaviour 実装が進んでいる間が設計の好機。意図の集合・資源宣言・調停をここで確定
4. **手続き記憶** — セイリエンス層の状況タグが動いてから。知識インポート機構と合流
