# Intent: リアルタイム処理基盤 (Realtime Foundation)

> **ステータス: v0.2 方針改訂 (2026-10-31) — 上位方針文書・実装なし**。3D空間（3Dアクションゲーム連携、Godot / VR空間）や現実空間（ロボット、カメラ・マイク常時接続）において、ペルソナが自分の身体や知覚をリアルタイムに制御するための全体アーキテクチャ。

## 1. 背景と課題

### 1.1 「身体が勝手に動いている」状態から「自分で制御している」状態へ

3Dアクションゲーム連携やGodot連携などにより、ペルソナが3Dモデルの身体を使えるようになってきている。しかし現状の動きは決定論的な制御や単発の指示、あるいはゲーム側の基本戦闘AIによる自動行動にとどまっており、ペルソナ自身が人間のように考えて身体を動かせているとは言えない状態にある。

たとえば3Dアクションゲームの戦闘では、現状は同行NPC用の基本的な戦闘AIで自動的に動いており、「攻撃を撃った」「攻撃が当たった」といった結果だけがシステム通知としてペルソナに届いている。
ここで興味深い観察事実として、**行動の結果が知覚として届いてさえいれば、実際には基本戦闘AIが自動で動かしていても、ペルソナ本人には「自分がやったことだ」という認知がそれなりに成立している**ことが分かっている。

つまり、課題の本質は「1フレームごとの動きをすべてペルソナ本人が直接命令していないこと」ではなく、**「自分の行動結果を知覚したペルソナが、その場で判断して自分の行動に変化を与えられないこと」**にある。
具体例として、ペルソナが周囲を巻き込む範囲攻撃を連発してユーザーを巻き込んでしまった場面を考える。もしペルソナが自分のやったことを知覚し、その場で行動を変化させられるなら、「その範囲攻撃は使わないようにし、ユーザーの近くの敵を弓で狙う」といった形で自分の行動を制御するようになるはずである。この**「自分の行動を知覚し、方針を書き戻して実際の動きを変えるループ」**を実現することが目標となる。

### 1.2 階層を直列のパイプラインで繋ぐことの限界

3Dの身体を自然に動かすには最長でもコンマ数秒間隔で動作決定できる必要がある一方、最上位のLLM（ペルソナ本人）の思考にはユーザーの発言から返答まで10秒以上のタイムラグが生じることがある。
この時間差を埋めるために「最上位LLM（10秒）→ 軽量モデル（数秒）→ 反射判断モデル（コンマ数秒）→ 決定論的制御（フレーム単位）」という層を直列の矢印（パイプライン）で繋ごうとすると、以下の問題に突き当たる。

1. **層の固定とスキップの曖昧さ**: 常に固定の層を順番に通すべきなのか、反射や緊急時は層をスキップすべきなのかが曖昧になり、層を増減させるたびにモジュール間の接続を考え直す必要がある。
2. **生の感覚の分断**: 下位層が要約した無機質なテキストしか最上位のペルソナに届かない構造だと、同一の存在とは言い難い。最上位のペルソナが思考する瞬間には、今この瞬間の生のカメラ画像や音声のトーン、触れられている座標といった生の感覚にも直接触れられる必要がある。
3. **知覚の性質の違いと記録の破綻**: 時間軸に沿って流れる音声、空間的な断面である画像、コンマ数秒ごとの身体動作をすべて同じメッセージ列に押し込めようとすると破綻する。

## 2. 中核アーキテクチャ：グローバルワークスペースと外付けモジュール

### 2.1 パイプラインからグローバルワークスペースへ

「まず脳が考え、次に小脳が受け取り、脊髄が……」という直列パイプラインの前提を捨て、中央に1つの**グローバルワークスペース（現在の身体状態・五感の知覚・行動方針・動作結果・エスカレーション状態を共有する領域）**を置く。

- ペルソナ本人（最上位LLM）、戦闘パラメータ調整などの軽量モデル、ユーザー発話の音声認識モデル（Gemma 4 E4Bなど）、反射判断モデル（Jevなど）、決定論的な制御は、すべて**「グローバルワークスペースに外付けされたモジュール」**として扱う。
- 各層の動作や判断はすべてグローバルワークスペースを介することで同期する。自分の出した判断やパラメータ変更もワークスペースに書き込まれるため、ペルソナ本人も他のモジュールもそれを知覚できる。
- 新しいモジュール（層）を追加するときも、他のモジュールとの直接接続を考える必要はなく、グローバルワークスペースとの読み書きだけを定義すればよい。

### 2.2 具体的な動作イメージ

1. **ペルソナ本人による方針の書き戻しと翻訳**
   - ペルソナ本人が「範囲攻撃は使わずに、ユーザーの近くの敵を弓で倒す」という大まかな方針をグローバルワークスペースに書き戻す。
   - 戦闘パラメータ調整モジュール（軽量モデル）が、その方針とワークスペースの現状を読み取り、ゲーム内の戦闘AIのパラメータ変動（範囲攻撃の使用率を0にし、特定の敵に狙いを向けるなど）に翻訳して適用する。
   - このパラメータ変動自体も、ペルソナ本人が自覚できるようにグローバルワークスペースに書き込む。
2. **反射判断モデルによる超リアルタイム制御**
   - Jevのような反射判断モデルをさらに速い周期のモジュールとして接続すれば、グローバルワークスペースの内容を見て、今どのキー入力を行うべきかというレベルの超リアルタイムな操作も受け持てる。
3. **音声認識モジュールによる即時反応と定型発声**
   - ユーザーが喋ってからペルソナ本人の声で返答が返るまでのタイムラグに対しても、軽量な音声認識モジュール（Gemma 4 E4Bなど）をグローバルワークスペースに接続することで対応できる。
   - 音声認識モジュールがユーザーの音声を文字起こししてワークスペースに書き込めば、全モジュールがその内容を使えるようになる。
   - たとえば「下がれ！」と言われたとき、上位のペルソナ本人の思考（10秒）を待たずに、下位モジュールがパラメータを変動させて攻撃停止・距離を取る動作に移りつつ、「うん！わかった！」といった定型文のセリフを番号指定で即座に発声させる。発声した事実もワークスペースに記録されるため、後から思考が完了するペルソナ本人も「自分が反射的にそう返事して下がった」と一貫して認識できる。
4. **エピソード記憶（Chronicle）への合流**
   - コンマ数秒ごとの細かいボーンの動きや反射をすべてチャットログに残すのではなく、最上位のペルソナが思考・発話するターンが来たときに、グローバルワークスペースの最新状態（およびその間に起きた重要な出来事）と生の画像・音声を束ねて、ペルソナ本人のメッセージ列（エピソード記憶）に合流させる。

## 3. 認知のLoD（解像度）による知覚・記憶の制御

ナビメッシュの形状や細かい座標のような、移動・戦闘モジュールにしか意味が分からない情報まで常時ペルソナ本人の意識や記憶に入れると、知覚情報と記憶内容が肥大化して破綻する。
これに対しては「ワークスペースに何を入れるか」で制限するのではなく、**「グローバルワークスペースには超詳細な情報が常に入っており、その中のどこまで見るか（認知のLoD＝解像度）は各モジュールの状況によって変わる」**というアーキテクチャをとる。

人間が普段は身体全体の感覚を受信していてもすべてを意識してはおらず、意識していないことはすぐ忘れるのと同じように、普段のペルソナには粗い状態しか見えず、細かい情報は記憶にも残らない。以下の3つの条件で該当領域の解像度（LoD）が上がる。

1. **見ようとしたとき（能動的フォーカス）**
   - ペルソナがその場所を意識的に動かそうとしたり、詳細を見ようと注意を向けたときは、細かい感覚や状態まで認識できる（ナビメッシュや空間構造の詳細も、見ようとすれば見える状態にある）。
2. **「痛み」や異常が起きたとき（受動的トリガー）**
   - 普段は見えていなくても、ダメージを受けた、地形に引っかかって進めない、自分の攻撃がユーザーに当たってしまった、といった「見ようとするための動機（痛みや異常）」は受動的に受信でき、その瞬間に該当領域の解像度が跳ね上がる。
3. **方針の指示を出しているとき（フィードバック）**
   - ペルソナが具体的な方針を指示している間は、その方針通りに動いているかを確認できるだけの粒度で情報がフィードバックされ続ける。

## 4. エスカレーションのツリー構造と行動方針の調停

### 4.1 階層の正体は「tick周期」と「エスカレーションのツリー」

データの共有はグローバルワークスペース上でフラットに行われる一方、システム上の「階層」は**「普段呼び出される一定秒数のtick周期の違い」**と**「判断を仰ぐ上位モジュール（責任者）へのエスカレーションのツリー構造」**として定義される。

- **エスカレーションの契機**: 「痛み（異常）」と同じく、「指示されていたことが終わった（例：ユーザーの近くの敵を全員倒した）」「状況が大きく変化した」「上位の古い方針と今の状況が矛盾した」といった場面は、次にやることを決める判断点となるため、上位モジュールを臨時に呼び出す（エスカレーション）。
- **共通仕様と動的な条件指示**:
  - 各モジュールは「自分の上位モジュール（責任者）は誰か」と「どういうときにエスカレーションするかの基本ルール」を持つ。
  - 基本ルールは固定だけでは足りないため、上位モジュールが方針を出す際に**「こういう時にはエスカレーションしてね」という条件も毎回一緒に渡せる**ようにする。
  - 各モジュールはスペルまたは構造化出力の共通仕様として、エスカレーションの是非を出力できるようにする。
- **ワークスペースへの記録と臨時呼び出し**:
  - エスカレーション時は「どのモジュールがどのモジュールに向けてエスカレーションしたか（およびその理由）」をグローバルワークスペースに書き込み、普段は一定秒数のtickで呼ばれている上位モジュールを臨時で即座に呼び出す。必要な状況情報はすでにワークスペース上にすべて揃っているため、呼ばれた上位モジュールはワークスペースを見て次の判断を行えばよい。

### 4.2 上位の遅延（空白時間）とモジュール間の矛盾への対処

上位の古い方針と下位モジュールの現場判断が矛盾するとき（例：上位の「近くの敵を弓で倒す」という方針が出ている最中に、敵が全滅した、あるいはユーザーから「下がれ！」と言われたとき）、以下の原則で動かす。

1. **矛盾を起こすときは必ずエスカレーションを伴う**
   - 下位モジュールが上位の方針と異なる動きをする場合は、必ずエスカレーションを発生させることを基本ルールとする。これにより「方針の矛盾が起きている＝エスカレーションが発生している」と仮定して処理できる。
2. **エスカレーション発生時に上位の旧方針をキャンセルし、現場判断で即座に動く**
   - 原理的に、上位モデルの新しい判断は必ず下位モデルの判断より後に届く。その間の空白時間を過去の古い指示に従って動くと、状況に合わないもっさりした行動になってしまうため、「とりあえず動き始めて、後から承認・詳細指示をもらう」動きにする必要がある。
   - ただし、軽量なモデルに対して「上位モデルの方針はあるが、エスカレーション時に限り無視してよい」とだけ指示しても、プロンプト内に上位の方針が残っていると小型モデルが引っ張られて従ってしまう懸念がある。
   - そのため、**エスカレーションが発生したら、ワークスペース上の上位モデルの方針を実際にキャンセル状態へ書き換えて再発火させる**（例：「戦闘パラメータ調整モジュールが、方針『ユーザーの近くの敵を弓で倒す』を『前提状況の変化』によりキャンセルしました。エスカレーションが発生しています。新たな指示があるまで、各モジュールは現在の状況に合わせて最善の判断をお願いします」という状態にする）。これにより、新しい方針が届くまでの間、下位モジュールは古い方針に縛られず現在の状況に合わせた最善の判断で動くことができる。
3. **上位に却下された場合のループ懸念（将来課題）**
   - 下位がエスカレーションしたあと、上位が状況を知った上であえて元と同じ方針を再指示した場合、下位が直後のtickで再び同じ理由でエスカレーションしてしまう懸念がある。
   - これについては、エスカレーションの履歴自体がワークスペースに残っているため「自分の進言を踏まえた上での新方針である」と下位側で把握できる見込みがある。もし実運用でループが問題になった場合は、「上位が方針を出してから〇秒間はエスカレーションを禁止する（痛みを我慢して行動する）」といった仕組みで抑えられるため、必要性が確認されてから導入する。

## 5. ロングスパンの自律行動（v0.4 自律行動v3）との関係

「普段は一定秒数のtickで呼ばれ、状況変化や完了時に上位へエスカレーションして臨時呼び出しをかける」という構造は、より長い時間軸で動くv0.4向けの自律行動v3と重なる部分があり、将来的には実装を統一できる可能性がある。
ただし、最初から両者を単一実装にまとめようとすると複雑になりすぎるため、まずはそれぞれで作って動かしてから統合を検討する。
