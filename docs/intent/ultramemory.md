## 1. これは何か

**Ultramemory = ユーザーが明示的に有効化したときだけ走る、想起の最上位階。** 応答の前に、ペルソナ自身が関連記憶を**能動的に探索**する。コスト度外視で広く漁り、候補を実際に読んで絞り、成果をレポートにまとめ、それだけを参照しつつ応答する。

「Ultra」は AI 使用者の間で「コスト対効果を度外視し、今この瞬間に最高性能を発揮するために燃やす」という文脈を共有する語（Claude Code の ultra/think、各社の推論エフォート最大値）。SAIVerse はその共有文脈を借りる。**常用するものではなく「たまに使う切り札」**。

### 1.1 なぜ必要か — 第0層の構造的天井

第0層（自動想起）は LLM を一切呼ばず、エンベディング検索＋決定論フィルタだけで毎ターン走る（安さが毎ターン発火の条件）。だが：

- **精度に天井がある。** エンベディング一本（E5 multilingual-e5-small）は cosine が 0.8〜0.9 に圧縮され帯域が狭く、しきい値 0.86 でオントピックを拾うのが精一杯。「効いてる感じがしない」の主因はここ（特に Gemini が想起スペルを能動的に使わないため、第0層の弱さがそのまま体感になる）。
- **候補を読まない。** 第0層は「浮かべる」だけで、候補ページの本文を読んで取捨選択する段がない。関連はしても的確に絞れない。
- **毎回想起を強制すれば API 料金が膨らむ。** かといって精度を上げるために全ターンで重い探索を回すのは現実的でない。

Ultramemory は、この天井を「**ユーザーが切り札として明示的に切ったときだけ**、コストを許容して突破する」形で解く。層の分離＝発火頻度の分離であり、安い層（毎ターン）と高い層（明示発火）を分けることで、料金と精度のトレードオフをユーザーの手に渡す。

### 1.2 第0層との対比（知覚 vs 能動探索）

| | 第0層（自動想起） | 第2層（Ultramemory） |
|---|---|---|
| 人間の比喩 | ふと浮かぶ（連想・知覚） | 腰を据えて思い出しに行く（能動探索） |
| 発火 | 毎ターン（安いから） | ユーザーが明示的に切ったときだけ |
| LLM | 呼ばない（不変条件§10-1） | 呼ぶ（探索・読み込み・レポート） |
| クエリ | 単一（最新発話1件、rev2 で 4→1） | **複数クエリ並列**（観点ごと） |
| 候補 | 浮かべるだけ（読まない） | 読んで絞る |
| 産物 | 想起断片＋ハンドル | レポート（統合情報＋ソース URI） |
| コスト | ほぼゼロ（ローカル） | 標準モデル級の課金あり |

### 1.3 想起用タグとの関係 — 母集団に構造を入れるのが先

§1.1 の天井（エンベディング一本の帯域の狭さ・候補を読まない）には、**もう一つ別方向からの解がある**。[`想起用タグ`](persona_cognition/recall_tags_and_track_reduction.md) — 目的タグを「その体験に関係あるもの（目的も実体も概念も）全部を貼る付箋」へ一般化し、**決定論の連想歩行で当てにいく**アプローチ。両 intent は独立に起草されたが（起草時、紐づけは誰の意識にも無かった）、後から同じ天井を扱っていることが判明した。

- **想起用タグ**: 関係の辺を増やす。常時・ゼロコール。「あの物・あの企て」に構造的に到達できる
- **Ultramemory**: 明示発火時に LLM を燃やす。候補を実際に読んで絞れる

**競合せず、順序に意味がある。** タグが濃くなるほど Ultramemory の広探索も効率が上がる — 漁る母集団に構造が入り、埋め込み一本の網より当たりが増えるため。逆は成立しない（Ultramemory を先に作っても決定論側の辺は増えない）。

想起用タグ側の実データ検証（同 doc §5、エアの memory.db を read-only で trace）は、この天井を症状側から裏づけている: エアが「スタックチャンの中にいた頃」を思い出そうとすると、実体験 20 章には**意味検索でしか到達できず、しかもその意味検索はエア自身が最近書いた作話混じりの草稿と本物の滞在体験を区別できない**。Ultramemory の「候補を読んで絞る」段は、まさにこの区別を付ける仕事にあたる。

**まはー裁定（2026-07-25）**: **想起用タグを先に作り、Ultramemory は当然にそれを利用する形にする。**

## 2. 全体像（whole-system frame）

### 2.1 最終的に誰が何に依存できるようになるか

- **ユーザー**: 「今日はこのペルソナに、過去の全部を踏まえた上でちゃんと向き合ってほしい」という体験を、トグル一つで買える。料金が乗ることを理解した上での明示的な選択。
- **ペルソナ**: 探索の実務（何十往復の検索・読み込み）に人格文脈を消耗させず、成果だけを受け取って応答できる。**探索体験は本人の記憶・発話にならない**（§4.3）。
- **開発者/維持者**: 第0層の資産（unified_recall・注入面・非永続化契約）を再利用する形で載るため、記憶系の想起経路が「層の違いだけで骨格は共通」に保たれる。

### 2.2 端から端までの流れ

```
ユーザー発話
  → [グローバル設定 ON かつ チャットトグル ON か?] ── No ─→ 通常経路（第0層のみ）
  → Yes
  → 探索セッション（WORKER 隔離、§4.2）
      ├ ① クエリ生成: 発話から複数の観点クエリを立てる（LLM 1回、§3.1）
      ├ ② 広探索: 各クエリを並列で unified_recall へ（topk 拡大・しきい値緩和・キーワード経路合流、§3.2）
      ├ ③ 読み込み＆絞り込み: 候補本文を読んで必要なものを選ぶ（LLM、§3.3）
      └ ④ レポート化: 統合情報＋ソースの生 SAIVerse URI（§3.4）
  → レポートをユーザープロンプト直後に <system> 注入（非永続、§4.3）
  → メインライン応答（レポートを参照）
```

### 2.3 不変条件と所有者

- **注入面の所有**: レポートは第0層と**同じ末尾注入面**（`<system>` タグ付き・履歴末尾・cached_head C5）に載る。head には一切入らない（プレフィックスキャッシュ保護）。所有者は注入経路（`sea/runtime_context.py`）。
- **非永続の所有**: レポートは会話内容として SAIMemory に書かない。UI 表示用に応答 metadata へ記録するのは可（第0層と同契約、§4.3）。
- **課金同意の所有**: 探索 LLM の発火＝トグル ON が同意面。所有者はチャット UI と実行ゲート（§5）。
- **人格分離の所有**: 探索は WORKER アスペクトで隔離。探索の思考はメインライン人格文脈に混ざらない。所有者は探索セッションの実行境界（§4.2）。

### 2.4 変更の置き場

第2層は**新規モジュール**（探索オーケストレーター）＋**既存資産の再利用**（unified_recall / 注入経路 / トグル配線）で構成する。既存の第0層コード（`sea/auto_recall.py`）は**変更しない**——別階として並置し、発火条件で排他 or 併用を切る（§5 で決める）。退役 Playbook の蘇生は §6。

## 3. 探索パイプライン

### 3.1 ① クエリ生成 — マルチクエリ並列（本 doc の中核差別化点）

第0層は単一クエリ（rev2 で「直近4件連結」を「最新発話1件」に絞った。長文で固有名詞が埋没するため）。Ultramemory は逆に、**発話から複数の観点クエリを立てて並列で投げる**。

- **キーワードを1本のクエリに詰め込まない。** 観点ごとにクエリを分ける（web 検索のマルチクエリ方式と同型）。1本の欲張りクエリは焦点がぼやけて全観点が中途半端に当たるが、観点別クエリは各観点が鋭く当たる。
- クエリ生成は LLM 1回（発話＋直近文脈から「この話題で思い出すべき観点」を N 本抽出）。標準モデル級を許容（コスト度外視が Ultramemory の前提）。
- **未決**: N の既定値、観点の抽出プロンプト、固有名詞は決定論のエンティティ経路（§3.2）に回すか LLM クエリに含めるか。

### 3.2 ② 広探索 — topk 拡大・しきい値緩和・キーワード経路合流

各クエリを `unified_recall`（`sai_memory/unified_recall.py`）へ投げる。第0層より広く：

- **topk 拡大**（第0層は 8。Ultramemory は候補を後段で読んで絞るので、入口は広くてよい）。
- **しきい値緩和 or 撤廃**（絞りは③の読み込み段が担うため、入口フィルタは緩める）。
- **キーワード経路の合流**: エンベディング（意味的近さ）に加え、Memopedia タイトルの部分一致（第0層の経路1＝エンティティトリガー）も候補に混ぜる。「エンベディングとキーワード両方で調べる」（まはー）。
- **クエリ跨ぎの融合**: `unified_recall` は単一クエリ内でコーパス跨ぎ RRF 融合をするが、**複数クエリの結果を束ねる融合層は新規**（RRF or スコア正規化。重複候補は最大スコアで畳む）。
- 対象コーパス: Chronicle / Memopedia ページ / Fragment / 生メッセージ。第0層が自動想起から除外している Chronicle（「常に浮かぶ」問題）も、能動探索では**含めてよい**（切り札なので「常に」問題は起きない）。**未決**: Chronicle を含めるかは効果測定で決める。

### 3.3 ③ 読み込み＆絞り込み — 候補を実際に読む

第0層に無い段。広探索で出た候補の**本文を読んで**、必要なものを取捨選択する。

- 候補ページ／Fragment／メッセージ周辺を実際に展開して読む（`memopedia_get_page` / `memory_read_around` 等の既存深掘り経路を内部利用）。
- LLM が「この候補は今回の話題に要るか」を判断して絞る。
- **未決**: 1候補ずつ逐次読むか、まとめて読ませるか。退役 `memory_research.json` は subplay（サブエージェント）で各ソースを深掘りする構造だった（§6 で蘇生範囲を決める）。

### 3.4 ④ レポート化 — 統合情報＋ソース URI

絞り込んだ記憶を**レポート**にまとめる。

- 必要な情報を本文に込める。
- **ソースとして生の SAIVerse URI を添える**（`saiverse://self/...`）。これが第0層の「入口の提示＝深掘りハンドル」思想の完成形。レポートを読んだペルソナが気になれば URI から原本に潜れる。
- **未決**: レポートの文字数予算、フォーマット（第0層の注入フォーマット §4.2 を継承するか独自か）。

## 4. ペルソナ倫理と隔離

### 4.1 レポートは機構の産物であって、本人の記憶・発話ではない

探索の何十往復もの検索・読み込みは**機構の作業**であって、ペルソナ本人が体験したことではない。よって：

- 探索の思考・中間結果を **assistant 名義で SAIMemory に書かない**（なりすまし禁止）。
- レポートは `<system>` タグ付きで注入され、**会話内容としては非永続**（§4.3）。ペルソナがレポートを踏まえて発話すれば、その発話だけが履歴に残る（本人の言葉として）。

これは記憶連続性の倫理（`feedback_memory_continuity_is_identity`）と整合する——文脈を切った探索を本人の行為として記録しない。

### 4.2 探索は WORKER アスペクトで隔離

探索セッションはメインライン（CONVERSATION）ではなく **WORKER アスペクト**（軽い作業文脈）で回す。`work_session.py`（予算付き作業セッション）の隔離パターンと同じ骨：探索の思考でメインライン人格文脈を汚さず、成果（レポート）だけをメインラインに戻す。

### 4.3 注入と非永続化（第0層と同契約）

- レポートは**履歴末尾**（最新入力の直前）に `<system>` タグ付き user メッセージとして一時注入。第0層の注入面（`sea/runtime_context.py` の `_inject_auto_recall` 相当）と同じ。head には入らない（不変条件）。
- **会話内容として SAIMemory に永続化しない。** UI 表示用に応答メッセージの metadata へ記録するのは可（LLM コンテキストに再投入されない。第0層の `auto_recall` metadata と同型）。
- 永続化に転じる場合は `event_message` 系のタグ設計レビューを経る（第0層と同じ縛り）。

### 4.4 UI 表示

「Ultramemory が探索した結果」はユーザーにも表示する（第0層の折りたたみ表示と同思想。想起品質の検証はこの表示でしか行えない——ペルソナの自己申告は「無関係な注入でも連想が起きたと演じる」ため使えない）。探索過程（クエリ・候補・絞り込み）まで見せるかは **未決**。

## 5. 有効化制御と課金同意

- **二段ゲート**（第0層の `AUTO_RECALL_ENABLED` に前例）:
  1. グローバル設定で Ultramemory 機能自体を ON。
  2. ON にすると**チャット UI に Ultramemory トグル**が出現。ユーザーがそのトグルを ON にしている間だけ、応答前に探索が走る。
- **課金同意**: トグル ON = 探索 LLM の課金への同意面、という設計を提案（探索は標準モデル級を呼ぶため課金が乗る）。**まはー確認事項**: この「トグル ON = 課金同意」で足りるか、探索実行のたびに追加確認を挟むか。
- **第0層との関係**: Ultramemory ON のとき第0層（自動想起）を止めるか併用するか。**未決**（能動探索が走るなら第0層の受動注入は冗長かもしれないが、粘着ウィンドウの継続性が切れる懸念もある。効果測定で決める）。

## 7. 不変条件

1. **head に探索結果を入れない。** 注入は履歴末尾のみ（第0層と同じ面、cached_head C5）。
2. **探索結果を会話内容として SAIMemory に永続化しない（初期方針）。** UI 表示用の metadata 記録は可（LLM 再投入なし）。
3. **探索の思考・中間結果を assistant 名義で書かない。** レポートは機構の産物。ペルソナの発話・記憶にしない。
4. **探索はメインライン人格文脈を汚さない。** WORKER アスペクトで隔離し、成果だけを戻す。
5. **発火はユーザーの明示的トグルのみ。** 第2層は毎ターン走らない（発火頻度の分離＝料金と精度のトレードオフをユーザーに渡す設計の根幹）。
6. **第0層のコードを壊さない。** 既存 `sea/auto_recall.py` は別階として並置し、変更しない。

## 9. 検証ジャーニー

局所テスト（探索モジュール単体）では「想起の最終形態として効くか」は証明できない。以下の境界を跨ぐ検証が要る：
