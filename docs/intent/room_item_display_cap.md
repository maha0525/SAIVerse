# 部屋のアイテムの表示個数の上限と、片付けの道具

**ステータス**: 実装中 — 2026-09-11 起草 → 同日整合性検査 (Opus) の指摘 7 件を反映 → 同日まはーの裁定で全論点確定 (下の「裁定の記録」2026-09-11 第二回)、実装開始
**関連**: [room_items_uncapped.md](../issues/room_items_uncapped.md)（発端の issue — 経緯と却下済みの案）/ [bag_item_has_no_creation_path.md](../issues/bag_item_has_no_creation_path.md)（Bag の作成経路 — 2026-09-01 裁定「アイテム作成の一般経路として設計」。本 intent の設計 5 が引き取る想定）/ [room_state_packages.md](room_state_packages.md)（部屋の様子の組み立てと差分 — 上限の実装点。本 intent の実装時に §7-1 の文言を改訂する）/ [presented_context_reduction.md](presented_context_reduction.md)（隣接 — 送る量の上限。本件はその供給側を減らす一手）

## 一言で

部屋に物が増えても、ペルソナに見える「部屋の様子」には最近使われた物だけが並び、残りは表示から埋もれる — 散らかった部屋では物が見えなくなる、という世界の物理として。埋もれた物にはページをめくるスペルで届き、あわせて、散らからないように片付ける道具 (アイテム作成の一般経路と、その中の Bag) をペルソナと一般ユーザーに渡す。

## 全体像 — 誰に何を約束するか

- **ユーザー**: アイテムが 50 個ある部屋でも、部屋の様子の全文が数万字に膨らんでコンテキストと料金を圧迫することがなくなる (実測: アイフィさんの部屋はアイテム 58 個で 35,000 字超だった)。美術館のように多く見せたい部屋は、Building の設定で枠を広げられる。
- **ペルソナ**: 物は消えない。埋もれるのは表示だけで、スペルでめくれば全部に届く。表示される物の説明は削られない (2026-09-04 裁定の維持)。散らかってきたら、自分で Bag を作って片付けられる。
- **保守**: ページをめくる仕組みは共通の部品になり、手帳などの多くの項目を返すスペルが同じ形の案内でめくれるようになる。

## 裁定の記録 (確定済み)

- **2026-09-01 (まはー、[issue](../issues/bag_item_has_no_creation_path.md))**: ユーザーがアイテムを作る画面の入口は、Bag 専用ではなく**アイテム作成の一般経路**として設計する。
- **2026-09-07 (まはー)**: 上限だけ先に入れない — 片付けの道具とセットで新しい feature ブランチでやる。目安 10 個、超えた分は古いものから見えなくなる (世界の物理)。Building ごとに個数を変えられる形にする (美術館のような部屋のため)。
- **2026-09-04 (まはー)**: 表示される物の説明を削る案は却下 — 減らすのは表面に出る個数であって、見えている物の情報量ではない。
- **2026-09-11 (まはー、この intent 起草直前の会話。一次記録はここ)**: ①どの物を見せるかは**更新が新しい順**。②あふれた物を「見当たらなくなったもの」として通知する必要は全くない — 次に全体を見せるときに見せなければいいだけ。③埋もれた物への道は、手帳のページ分けの仕組みを参考にしたスペル。ページ指定を「1-5」のような範囲でできる形にし、手帳や他の多項目を返すスペルでも使えるよう汎用部品として作る。④Building ごとの個数の設定 (既定 + 部屋ごとの上書き) は起票時の推奨案の形で確定。
- **2026-09-11 第二回 (まはー、改訂版レビュー)**: (1)「ほかに N 個」の一行は**置く** — 総数だけ (カテゴリごとの個数は、カテゴリが増えたとき一行自体が育つので入れない)。文言は「埋もれていて見えません」。(2) めくるスペルの表示名は**「埋もれたアイテムを見る」** (「調べる」は一つの物を入念に調べる語感になるため)。Bag 作成スペルは「入れ物を作る」で確定。(3) アイテム作成の一般経路 (2026-09-01 裁定) はこの束で実装する。(4) **手帳へのページ番号も含める** —「片方だけやる方が後々手間」。切れ目は日付の境目のまま順番の番号を振る。番号が呼ぶたびに少しずれるのは、アイテムのスペルと同じく「固定の索引ではない」として受け入れる。範囲指定の上限 (5 ページ) と、開いた Bag の中身を勘定に入れないことは、推奨のまま採用。

## 設計

### 1. 表示の上限と、どの物を見せるか

- 部屋の様子を組む処理 (`build_room_bundle`) が、**建物に直接置かれているアイテム**のうち「最近触られた順」の上位・上限の個数だけを束 (部屋の様子のひとまとまりのデータ) に載せる。それ以外のアイテムは束に入らない = 部屋の様子に描かれない。
- 「最近触られた」の物差しは**二つの時刻の新しい方**: アイテム自身の更新時刻 (`Item.UPDATED_AT` — 開閉・説明や中身の書き換えで進む) と、置き場所の更新時刻 (`ItemLocation.UPDATED_AT` — 設置・移動・拾得で進む)。片方だけでは「Bag から出して部屋に置いた物」(場所だけ動いた物) が埋もれたままになる。同時刻の並びは `SHORT_ID` の降順で決める。
- **選別と並びは別物**: 上限はどのアイテムを載せるかを決めるだけで、束の中の並び順は現行のまま (キーの昇順 — 差分の照合と指紋が「同じ部屋は同じ束になる」ことを前提にしているため、並びは変えない)。
- 上限の既定は **10 個**。Building の設定で部屋ごとに上書きできる (設計 4)。
- **開いている Bag の中身は勘定に入れない (2026-09-11 第二回裁定で推奨のまま採用)**: 開いた Bag の中身はその Bag の描画の一部として全部見える (現行仕様)。開けているのは見せる意思 — 隠したければ Bag を閉じる、が片付けの操作そのもの。この帰結として、上限の主語は「建物に直接置かれたアイテムの個数」であって「部屋の様子の字数」ではない — 開いた Bag に物を詰めれば様子は大きいまま、は仕様。

### 2. あふれた物の見え方

- 上限で埋もれた物は、部屋の様子に描かれない。**「見当たらなくなったもの」の行も作らない** — 部屋から本当に持ち出された・消えた物 (見えている物に限る) だけが今まで通りそこに出る。
- **差分への伝え方 (置き場所を確定)**: 「上限で外した」という事実は、束そのものに「外した物のキーの一覧」として持たせる。差分の判定は二つの束だけを見比べる作りなので、束の外に別の連絡路は作れない。判定の規則は「前の束にあって今の束に無い物のうち、今の束の『外した一覧』に載っている物は、消えたと言わない」。束の形が変わるので、束の検査と指紋 (`bundle_is_valid` / `canonical_bundle_json`) への影響は実装時にここへ追記する。
- **埋もれている間の出来事は語られない**: 埋もれた物が (見えないまま) 持ち出されても、行は出ない — 見ていない物は消えたことにも気づかない、という物理。埋もれていた物が触られて表面に戻った回は「増えた・変わったもの」として全文で出る — 久しぶりに取り出した物は改めて目に入る。
- **提示の積み上がりとの関係**: ペルソナの見ている部屋は「一番古い全文 + その後の差分」の積み上げなので、埋もれた物の姿は古い全文の中にしばらく残る。それは「前に見た記憶」として自然で、害はない。次に全文を見せ直す回 (部屋に戻った回・整理での置き直し) からは上限までの姿になる — まはーの「次に全体を見せるときに見せなければいいだけ」はこの形で実現する。
- **[room_state_packages.md](room_state_packages.md) §7-1 の改訂を同じ変更で行う**: 「今いる部屋の全体像 (全パッケージの最新の全文相当) が常に見えている」の主語を「上限の範囲の全体像」へ書き直す。二つの正典が反対のことを言う瞬間を作らない。
- **「ほかに N 個」の一行 (2026-09-11 第二回裁定で採用)**: 埋もれた物の存在をペルソナが知る手掛かりとして、機構名義の一行を置く。**束には入れず、様子を文字にするときに添えるだけ** — 束に入れると、埋もれた物の数が変わるたびに「見た目は何も変わっていないのに差分が出る」ことになるため。出力例:

  ```
  （ほかに 48 個のアイテムがありますが、埋もれていて見えません。スペル「埋もれたアイテムを見る」でめくって見られます）
  ```

### 3. 埋もれた物をめくるスペル (ページの共通部品)

- 新しいスペル **「埋もれたアイテムを見る」** を作る: 今いる部屋の全アイテムを、設計 1 と同じ「最近触られた順」でページに分けて出す。
  - 1 ページは **10 件** (表示上限とは独立の定数で、たまたま同じ数)。
  - ページ指定は番号で、`page="2"` の一枚指定と **`page="1-5"` の範囲指定**の両方を受ける。一度に開ける範囲は**最大 5 ページまで** — スペルの返りは会話と一緒に畳まれるまで送る量に残り続けるので、際限なく開ける形にはしない。
  - どのページを出すときも「全 58 件・6 ページ。いま 2 ページ目 (11〜20 件目)」のような全体の案内を必ず添える — 手帳よりも全体把握の必要が高い道具だから。
  - 一件の本文 (説明) は途中で切らない。省略の単位は件数 (ページ) だけ — 手帳と同じ原則。
  - ページの中身は呼んだ瞬間の並びで切る。物が触られると並びが変わるので、同じ番号が次の呼び出しで少し違う中身を指すことはある — 物理的な棚と同じで、固定の索引ではない。
- **ページの仕組みは共通の部品として作る**: 範囲指定 (`"2"` / `"1-5"`) の解釈・切り出し・全体の案内行の生成をモジュールに一本化する。
- **手帳にもページ番号を足す (2026-09-11 第二回裁定)**: 手帳のページの切れ目は現行の「日付の境目」の規則のまま、新しい順に順番の番号を振り、`page` の番号・範囲指定で開けるようにする。現行の日付めくり (`before`) も残す。メモが増えると同じ番号が別の中身を指すことはある — アイテムのスペルと同じ「固定の索引ではない」の受け入れ。

### 4. Building ごとの個数の設定

- Building に列を一つ足す (整数、空欄可)。**空欄 = 既定の 10 個に従う。0 以上の整数 = その個数** (0 は「様子にアイテムを出さない部屋」として有効)。負数は保存時に拒否する。「全部見せたい」部屋は十分大きい数を入れる — 「無制限」の特別な値は作らない。
- 保存画面はワールドエディタの Building 設定。値の変更は次に部屋の様子を組むときから効く (即時の書き換えはしない — 設計 6)。
- DB の列追加は additive なので、migrate は既存 DB に列を足すだけ。

### 5. 片付けの道具 (アイテム作成の一般経路と Bag)

- 現状: Bag は「他の物を入れられるアイテム」の一種として既に存在する。**閉じた** Bag の中身は部屋の様子に出ない (開いた Bag の中身は全部見える)。物を Bag へ移す道具 (item_move) もペルソナに既にある。無いのは **Bag を作る手段** — ワールドエディタからは作れるが、一般ユーザー・ペルソナには経路が無い。
- 追加するもの:
  - **一般ユーザー向け**: 2026-09-01 裁定のとおり、**アイテム作成の一般経路**を画面に作り (Bag もその一種として作れる)、[bag_item_has_no_creation_path.md](../issues/bag_item_has_no_creation_path.md) をこの束で完了させる (2026-09-11 第二回裁定で確定)。
  - **ペルソナ向け**: Bag を作るスペル **「入れ物を作る」** (名前と説明を決めて、今いる部屋に置く)。document_create と同じ型。
- アイフィさんの「自律お片付けデモ」構想との接続: このブランチで作るのは道具まで。自律の片付け行動 (時間割に片付けの時間を置くなど) は v0.4 の自律行動の枠で扱う。

### 6. 差分・キャッシュとの整合

- 上限が変えるのは部屋の様子の**中身**だけで、書き換える**タイミング**は今と同じ (入室・Metabolism などの既存の機会)。新しい書き換えのタイミングは一つも増やさない — 送る内容の先頭からの一致 (キャッシュの前提) が新しく壊れる場所は無い。
- Building 設定の変更も、次に部屋の様子を組むときから効くだけで、その場で提示を書き換えない。

## 不変条件

1. **物は消えない。** 上限が変えるのは表示だけで、DB のアイテム・item_view / `saiverse://item/` での到達・ユーザー画面の一覧は無傷。
2. **表示される物の説明は削らない** (2026-09-04 裁定)。減らすのは個数だけ。
3. **上限で埋もれた物は「見当たらなくなったもの」に出ない** (2026-09-11 裁定)。部屋から実際に持ち出された・消えた「見えていた物」だけがそこに出る。
4. **スペルの一覧は本文を途中で切らない。** 省略の単位は件数 (ページ) だけ — 手帳の原則と同じ。
5. **提示を書き換えるタイミングを増やさない。** 上限も Building 設定の変更も、部屋の様子を組む既存のタイミングに乗るだけ。
6. **束の並び順は変えない** (差分の照合と指紋の前提)。上限が決めるのは載せる物の選別だけ。

## 検証の手順

- **隔離環境** (合成ペルソナ + 15 個以上のアイテム): 部屋の様子が「最近触られた順」の 10 個 (+ 裁定次第で N 個の行) になること / Bag から出して置いた物が表面に現れること (置き場所の時刻の軸の検算) / 古い物を触ると次の様子で表面に戻り、押し出された物に「見当たらなくなったもの」の行が出ないこと / 部屋を離れて戻った回の全文が上限までの姿になること / スペルで `page="2"`・`page="1-3"` が案内行つきで返り、6 ページ超の範囲が断られること / 一般経路から Bag を作り、物を移して閉じると様子が縮むこと。出てきた文面を私が読者として読む。
- **実機** (まはー): アイフィさんの部屋 (58 個・35,000 字超) の縮みの実測。美術館のような部屋での Building 設定の上書き。
