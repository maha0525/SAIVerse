## 1. 核となる時間モデル

**ペルソナの主観時間は Pulse でのみ進む。** ユーザー発話 Pulse も自律 Pulse も、どちらも Pulse の開始が「時間が動く瞬間」。

この一原理から次が従う:

- ペルソナが外界の変化を**知覚できるのは主観時間が動く瞬間＝ Pulse 開始時だけ**であるべき。
- Pulse と Pulse の間（＝主観時間が止まっている間）に客観時間の世界で起きた変化は、ペルソナ本人はまだ知覚していない。**知覚の入口の手前で「詰まって」待つ**だけ。
- 次に Pulse が動くと、詰まっていた知覚が**その一瞬の知覚**としてなだれ込む。

比喩: 喋っていないペルソナは時が止まっている。そこへ向かう知覚情報は、入る直前で queue に詰まる。Pulse で一瞬時間が動くとき、詰まっていたものが一緒に入っていける。

**この待ち行列を「知覚バッファ」と呼ぶ。** 「バッファ」という語自体が、時間経過による溜め込みと消費を暗示している。（実体は揮発ではなく永続ストア。§4.1 参照。）

## 2. これは何か / 何でないか

### これは何か

Pulse と Pulse の間にペルソナ宛てに発生した知覚イベントを、**型付きで溜め込み**（非状態イベントは発生時 push、状態差分は検知タイミングで投入 §4.5）、次の Pulse 開始時に**型ごとに畳み込んで（reduce）1 つのシステムメッセージに統合し、SAIMemory へ書き出して消費する**永続バッファ。消費前はプレビュー・編集の余地を残す。

### これは何でないか

- **自動想起 (auto_recall) の器ではない。** 自動想起は「クエリに応じてその瞬間に浮かぶ」＝主観時間の産物であり、外界起因で詰まる知覚とは性質が逆。かつ SAIMemory に**永続化されない** (`memory_architecture_v2.md` §4.3)。よって知覚バッファには乗せず別枠のまま。(まはー決定 2026-07-09)
- **「既にペルソナに入った情報」の対ユーザー透明性の仕組みではない。** それは §6 の通り別件で、スルース (sluice、旧 gold_panning) のコア記憶自動更新をユーザーにどう見せるか、という並行案件に合流する。
- **会話履歴そのものの置き換えではない。** ただし他ペルソナの発話取り込みは知覚バッファ経路に載せる（§4.4 / §5.3、まはー確定 2026-07-09）——「経路に載せる」のであって、会話内容を通知ラベルに変質させるわけではない。

## 3. 現状マップ（今どこがこの原理から逸脱しているか）

ペルソナが「喋っていない間に情報を得る」経路は現在複数あり、時間モデルへの準拠度がまちまち:

| 経路 | 実装 | Pulse で消費? | 永続化 | 逸脱 |
|---|---|---|---|---|
| 世界状態の差分（入退室 / アイテム / スペル / Memopedia 索引 等） | Cached Head の各 Section `diff_to_notifications` → `inject_diff_notifications` (`sea/head_pipeline/integration.py:139`) | ✅ Pulse 開始時 (`sea/runtime.py:129`, `sea/runtime_context.py:190`) | ✅ event_message 1 通 | **snapshot 差分**であってイベントバッファではない。中間イベントを保持せず B/C 比較で net 差分を出す。状態で表せない一発イベントを表現できない。プレビュー用の常設バッファが無い |
| 入室時の過去会話想起 | `_inject_persona_recall_on_enter` (`integration.py:197`) | △ Pulse だが差分通知の**副作用**として別メッセージ | ✅ 別 event_message | 同一 Pulse なのに**2 通目**を足す（③「同一 Pulse は 1 メッセージ」違反）。enter が畳まれても道連れにできない |
| メタ記憶訂正（ユーザーがコア記憶を edit/delete/restore） | `_notify_persona_correction` (`api/routes/people/core_memory.py`) | ❌ **編集した瞬間**に即書き込み | ✅ 即時 event_message | **時間が止まっているペルソナが即座に記憶を得る**＝時間モデル違反。一括操作で通知スパム（2026-07-09 応急停止済み） |
| 他ペルソナの Building 内発話 | `auto_ingest_building_messages` | ✅ 次 Pulse で取り込み | ✅ 会話として | Pulse 消費だが知覚バッファとは別経路。畳み込み対象外 |
| 自動想起 | `sea/auto_recall.py` | ✅ Pulse | ❌ 非永続 | 別枠でよい（§2）。混同注意 |

**要点**: 「状態差分」は既に *Pulse 消費 + 1 メッセージ + 永続化* をほぼ満たしている（＝まはーが欲しい flush 形に近い）。逸脱しているのは **(a) 一発イベントが別経路で即時 or 別メッセージになっている** ことと、**(b) 中間イベントを溜める常設バッファが無く snapshot 差分で代用しているためプレビューできず、状態で表せない知覚を扱えない** こと。

## 4. 設計: 知覚バッファ

### 4.1 4 つの性質

1. **書き込みは客観時間で、消費とは独立（§4.5）**: 外界の変化・イベントが起きたら（＝発生時 push、または検知タイミングでの状態差分検出）、対応する知覚項目が**永続バッファ**に積まれる。ペルソナはまだ知覚しない。
2. **消費は Pulse 開始時に一括（主観時間の一歩）**: Pulse が起動すると、バッファ内の全項目を型ごとに reduce し、**1 つのシステムメッセージ**にまとめて SAIMemory へ書き出す（＝「その瞬間に知覚した」証跡）。消費後、バッファの該当項目はクリアされる。
3. **未消費の間だけ畳み込める（型付き reduce）**: 各知覚項目は型を持ち、型ごとの reduce 関数で統合・相殺される。畳み込みが許されるのは**まだ消費（知覚）していないから**——一度消費したものは主観時間に入ったので相殺不可。これが不変条件（§7 C2）。
4. **消費前はプレビュー / 編集できる**: バッファは**永続的な常設状態**なので消費前に覗ける。「今このペルソナに話しかけたら、自分のプロンプトに加えて何が知覚されるか」をユーザーが事前に見て、要らない項目を消せる（§6 透明性）。プレビューを開くこと自体が状態差分の検知タイミングになる（§4.5）。

**永続バッファであること（まはー確定 2026-07-09）**: バッファは揮発（in-memory）ではなく永続化する。当初「状態型は snapshot から再導出できるので揮発でよい」と設計していたが、これは Cached Head の「状態は snapshot に持ち差分は Pulse 時に再計算」パターンに引きずられた前提だった。揮発を守ろうとすると透明性（任意タイミング検知）と再起動耐性の両立に冪等同期・型別分担といった複雑さが要る。永続化すればそれらは全て不要になり（再起動耐性は自動、状態型/非状態型の永続化分担も消える）、全知覚が単一の永続バッファに集約される。入退室 / アイテム変更は低頻度で書き込みコストは無視できる。置き場所は SAIMemory の会話履歴とは別の per-persona ストア（未消費のものを会話に混ぜないため。消費時にそこから SAIMemory へ移す）。

### 4.2 消費点 = Pulse（①の決定）→ 2026-08-08 改訂: 消費点 = Beat の頭

- 時間を進めるのは Pulse。ユーザー発話 Pulse も自律 Pulse も消費点になる。(まはー決定 2026-07-09)
- 消費点は現状の `inject_diff_notifications` 呼び出し位置（`run_meta_user` の Pulse 開始 / 応答前 metabolism 後）を継承する。差分注入を「バッファ消費」に置き換える形。
- **消費者は主観時間を進める Pulse すべて**（ユーザー発話 Pulse も自律 Pulse も）。(まはー確定 2026-07-09) サブライン / メタ判断 / 入れ子 Pulse が「主観時間を一歩進める」ものとして消費者に含まれるかは Phase 1 実装時にこの原理から導く。

**→ 2026-08-08 改訂（まはー裁定）: 消費点は Pulse の頭から「Beat の頭」へ精密化する。**

- **Beat** = [beat_execution_context.md](beat_execution_context.md) §2.2 の最小行動単位（「関所 → コンテキスト読み → 1 回の生成 → 記録」の一続き。実体はスペルループ 1 周）。Pulse 開始時の消費は「最初の Beat の頭」の特例に過ぎなくなり、規則は一つのまま: **知覚はどの Beat であれ、その頭で消費される**。「主観時間は Pulse で進む」は「Beat で進む」に置き換わる。
- **動機（発見の経緯）**: ラウンド内スペル（例: 移動スペル）が世界を変えたとき、その帰結（移動先の様子・入室で届く知覚）が「次の Pulse」まで見えなかった。会話中に移動したペルソナは行った先を知覚しないまま Pulse を終え、次に誰かが呼びに行くまで盲目のまま——「行動の最中に世界から本人へ情報が届く正規の通路が、スペル結果テキストしか無い」ことが根本欠陥だった（発見は RSS フィード×出かけるコマの合流点 [issue](../issues/feed_arrival_pulse_cannot_see_articles.md)）。
- **効果**: スペル実行の次の Beat の頭で、行動の帰結（と、それまでに溜まった知覚）が同じラウンドの続きに流れ込む。行動 → 世界が応える → 見える → 続きを考える、が Pulse を跨がず成立する。フィード等の個別機能は知覚バッファに積むだけでよく、届くタイミングの分岐を持たない。
- **不変条件は不変**: 書き込みと消費の分離（§4.5）、型別 reduce と 1 メッセージ統合、消費済みの相殺不可（§7 C2）、プレビュー可能性は全て Beat 単位でもそのまま成り立つ。消費が細かくなるだけで、規則の形は変わらない。
- **実装時に確定する点**: (a) 子ライン（親 Beat の実行スタック内で走る WORKER）は親 Beat の一部（beat_execution_context §3.4）なので、子の生成前に独立の消費点を置かない。(b) ラウンド途中の SAIMemory 書き出しと作業中コンテキストへの挿入の並び（スペル結果の直後）。(c) メディア付き知覚（移動先の様子の内装画像等）のラウンド途中挿入。

### 4.3 型と reduce（③の決定）

知覚項目は型を持ち、型ごとに reduce する。そして**同一 Pulse で消費される全知覚は 1 つのシステムメッセージにまとめて記憶する**。(まはー決定 2026-07-09)

型ごとの reduce 方針（v0.1 叩き台）:

| 型 | reduce | 備考 |
|---|---|---|
| occupant 入退室 | 同一対象の enter と leave が未消費バッファ内に両方あれば**相殺して消える**。片方だけなら net の在/不在変化として残る | まはー案。検知（§4.5）で enter/leave が別々に積まれ、消費時 reduce で畳まれて消える |
| 入室時想起 | 対応する enter が相殺で消えたら道連れで消える。残るなら本文に統合 | 現行の 2 通目別メッセージを廃し、統合フローに畳む |
| メタ記憶訂正 | 同一コア記憶への複数操作を最新状態＋件数に集約（「N 件のコア記憶が更新された」等） | 一括操作のスパムをここで吸収。応急停止の恒久対応 |
| アイテム / スペル / 索引差分 | 現行 Section の diff ロジックを型付き項目として移植 | §5 参照 |

reduce は「型 → マージ関数」の汎用基盤にする。新しい知覚源が増えたら reduce を 1 つ足すだけで済む形にする（横断的関心事の汎用化）。

### 4.4 起動力属性と決定論ディスパッチャ

知覚イベントは「起動力」——主観時間を進める力——を属性として持つ:

- **起動力あり**: 到着した瞬間に Pulse を起動する（到着＝消費が同時＝割り込み / 召喚）。
- **起動力なし**: バッファに溜まり、次に別の起動力イベントで時間が動いたとき一緒に消費される。

これにより「Pulse dispatch（何がペルソナを起こすか）」と「知覚（起きたとき何を知るか）」が、**同じイベントストリームの二つの読み方**に畳まれる。会話取り込みをこの経路に載せられる（＝統合が綺麗になる）核がこれ。

**現状との対応**（`persona_cognition/pulse_dispatch.md` §3.1 / §3.2）:

- 起動力あり = §3.1 の起動契機（ユーザー発話 1a/1b・自律 2a/2b・スケジュール 3・wait_response timeout 5・時間差ツール完了 8・Phenomenon 9）
- 起動力なし = §3.2 のうち 4（他ペルソナ発話）・6（入退室差分）。7（Pulse 中断 / 再開）は PulseController 内部制御で知覚ではないので対象外。

**今回の設計判断のスコープ**（まはー確定 2026-07-09）:

1. 知覚イベントが **フラグ・属性・（必要なら）数値パラメータ** を持てるようにする。
2. それを読んで **決定論的に反応の可否（起動する / 溜める）を決める**ディスパッチャを置く。

**最小実装**: 「**絶対反応する**」フラグを 1 つ用意し、現状 §3.1 で反応している全契機に付与する。フラグが無ければ溜まる（現状 §3.2 相当）。これで**現状挙動を完全保存（リグレッションゼロ）**したまま拡張点だけを開ける。⚠️ **棚卸しで §3.1 の契機を漏らすと「今まで反応してたのに黙る」リグレッションになる**ので、付与漏れに注意。

実際にどんなフラグ体系にするか / AI 同士の会話をどう起動制御するかは**後続**（まはー: 後でよい）。器（属性付き知覚イベント＋決定論ディスパッチャ）だけ今作る。

**将来拡張（軽量 LLM 門番 = SN 層）**: 反応可否の判断を、決定論ルール → 軽量 LLM に育てられる構造にしておく。人間の注意（カクテルパーティ効果）に相当する「割り込みの門番」。これは自己モニタリング（DMN 相当＝既存のメタ判断）とは**別のネットワーク（SN 相当）**であり、標準モデルではなく軽量モデルを使う想定なので **Aspect も別になる**（`persona_aspect_design.md`）。メタ判断とは似て非なるが、判断の骨格（状況を読んで構造化出力で決める）に**流用できる部分はある**。軽量 LLM はコスト増と調整負荷が大きいため、**今は入れず「噛ませられる構造」に留める**。(まはー方針 2026-07-09)

### 4.5 検知は消費と分離する（まはー確定 2026-07-09）

**snapshot の操作とバッファ消費は完全に別物**として扱う。状態差分を検知する操作は、消費（Pulse での flush）とは無関係なタイミングで独立に走る。

- **検知操作**: （前回検知時の基準 snapshot）vs（現在の live 状態）を比較し、差分があれば知覚項目を永続バッファに入れ、基準 snapshot を現在状態で更新する（次の検知で同じ差分を二重に出さないため）。
- **検知タイミング（複数・消費とは独立）**: **プレビューを開いたとき**・**Pulse 起動時**・定期（数分おき）・その他のきっかけ。どれで走っても正しく動く（基準 snapshot が進むので冪等）。
- 非状態イベント（メタ記憶訂正・発話）は「検知」ではなく発生時に直接永続バッファへ push する（差分ではなく一発の事実なので）。

**なぜ分離が必須か**: 「消費時にしか状態差分を検知しない」とすると、状態変化は Pulse が起きて初めて可視化される＝**プレビューできない＝透明性が出ない**（本 doc の大目的に反する）。検知を消費から切り離し、プレビューを検知タイミングの一つにすることで、「今このペルソナに話しかけたら何が知覚されるか」を Pulse 前に見られる。当初 §9-B に「消費時に比較」と書いていたのはこの点で誤りだった（まはー指摘）。

## 5. 既存機構との関係・移行

### 5.1 Cached Head の差分通知との統合

現行は各 Section が `diff_to_notifications(old, new)` で snapshot 差分を出し、`inject_diff_notifications` が 1 メッセージに畳んで注入する。移行の方向（v0.1 案、部分再設計）:

- Section は **head 描画のための snapshot** を持つ責務は維持する（Cached Head の不変条件 C1〜C6 はそのまま）。
- **snapshot 比較（`diff_to_notifications`）は状態型 event の検知器として残す**。ただし (1) 実行タイミングを消費から切り離して**検知タイミング（プレビュー / Pulse / 定期）で走らせ**（§4.5）、(2) 出力先を「直接 SAIMemory へ注入」から「永続バッファへ型付き項目として投入」に変える。これにより状態型も一発イベントと同じ器に入り、reduce とプレビューの対象になる。
- 消費（flush）は Section 横断で 1 箇所（知覚バッファ）に集約し、`inject_diff_notifications` + `_inject_persona_recall_on_enter` + `_notify_persona_correction` の**3 直挿入経路を撤去して 1 本化**する。

（注: 撤去するのは「バッファを迂回する直接注入経路」であって、snapshot 比較そのものではない。snapshot 比較は「検知器」として残り、消費とは独立に走る（§4.5）。検知の実装が型で違う（状態型＝snapshot 比較、非状態型＝発生時 push）のは並存する二経路ではなく、単一の永続バッファへの型別入力。）

### 5.2 凍結概念の一般化

Cached Head が「Metabolism まで snapshot を凍結」、visual_context / memory_weave が「anchor まで凍結」しているのは、**主観時間が止まっている間は外界変化を取り込まない**という同じ原理の個別実装に見える。**凍結＝バッファリング、解凍＝消費**として、これらを知覚バッファの一般形に寄せられる可能性がある（v0.2 以降の検討。本 doc の一次スコープ外だが、設計の指針として明記）。

### 5.3 auto_ingest_building_messages

他ペルソナの発話取り込みは「ペルソナに向けられた発話」であり、通知（知覚ラベル）ではなく会話内容。**この経路も知覚バッファに載せる**（まはー確定 2026-07-09）。発話は起動力属性（§4.4）を持ち、フラグが立てば到着で Pulse 起動（＝ペルソナ同士の自律会話の土台）、立たなければ溜まって次 Pulse で消費される。「経路に載せる」のであって会話内容を通知ラベルに変質させるわけではない——バッファは「通知ラベル型」と「会話発話型」を別型として保持し、reduce と render を型ごとに分ける。

### 5.4 移動時の「移動先の様子」とメディア channel（2026-07-09 実装）

**問題**: head の visual_context Section は移動 (`building_entered`) で refresh しない (cache 保護。`refresh_on_events={APPEARANCE_CHANGED}` のみ)。かつ head のアイテム一覧・内装は visual_context が唯一の描画者 (`building_items.render` は None)。よって移動直後、ペルソナの head は**旧 Building のアイテム/内装のまま**次の Metabolism まで凍結し、唯一の信号「周囲の見え方が変わりました」は中身ゼロ。ペルソナは新しい部屋の様子を正確に知れず、旧部屋のものと誤認しうる (まはー指摘)。

**対応**: head は凍結のまま、tail (知覚バッファ) で新しい景色を届ける。
- **メディア channel**: 知覚バッファに `media` 列 (JSON) を追加。push/list/flush で画像 ref を運び、flush が全知覚のメディアを path 重複排除で集約して event_message の `metadata.media` に載せる (`NotificationLabel.media` / `append_persona_message` の media 対応は既存)。
- **移動時 push**: `on_building_entered` で移動した本人へ `get_visual_context(include_self=False, for_perception=True)` の内容 (他ペルソナ外見画像 + 内装画像 + Building 内アイテム〔**無い時も明示**〕+ Fixture) を kind=`surroundings` で push。self は head と重複するので除外。消費は本人の次 Pulse。
- **入室を既存者へ**: 併せて、`on_building_entered` は居合わせる既存ペルソナ全員にも occupant 検知を push する (新入りに自分の次 Pulse を待たず気づける)。
- **知覚バッファ向けの整形** (2026-07-09): head 記法をそのまま入れるとごちゃつくため:
  - flush の format は **kind グルーピングでなく発生順**。移動を跨いだとき「後から入室した相手が前の部屋にいた」ように見える崩れを防ぐ (連続する world_state だけ 1 見出しにまとめる)。
  - 中身ゼロの **「周囲の見え方が変わりました」フラグは廃止** (`visual_context.diff_to_notifications → []`)。移動時は surroundings が中身を届け、外見変化は head refresh で反映されるため。
  - **`get_visual_context(for_perception=True)`** = バッファ向け記法: 「リアルタイム反映」文言削除 (head は凍結され嘘だったので head 側からも削除) / Building 名を見出しで明示 / 「現在いる」断定回避 (通知後さらに移動しうる) / インベントリ除外 (移動で変わらない) / 「### Building内」見出し省略 / `<system>` 包みなし。head 用 (`for_perception=False`) と記法は分けるが収集ロジックは共通 (処理統一)。
- **既知の限界 (今は未対応・まはー 2026-07-09)**: 2 つ以上の Building の様子が 1 つの知覚バッファに載ると、途中の一時滞在を「消す」戦略が使えない (今いる部屋に相手が来て喋ったように見えうる)。将来、会話を別型で保持し「発話を聞いた時点でバッファ前半を固定」する戦略 (§4.4 会話統合と接続) で、会話が無い移動は省略・会話があれば移動を認識、と両立できる見込み。

## 6. 透明性の二層

まはーの指摘を二つに割る:

- **未消費バッファのプレビュー（本 doc の領分）**: 「今このペルソナに話しかけたら、自分の発話に加えて何が知覚されるか」。バッファが常設・永続で、プレビューを開くこと自体が検知タイミング（§4.5）なので消費前に覗け、要らない項目を編集/抑制できる。ユーザーが**次の消費者になる文脈**でのみ意味を持つ透明性。**自律 Pulse が先に消費した場合、その知覚は既にペルソナに入っているので本 doc の透明性対象ではなく、下の事後表示（別件）へ移る。**(まはー確定 2026-07-09)
  - **置き場所 = `ContextPreviewModal`**（既存の「送信前プロンプト内訳」プレビュー。section 別トークン内訳を出し、`personas[]` でペルソナ単位に切り替わる）。未消費バッファを 1 section として同モーダルに出す。ペルソナ単位で切り替わる UI なので**バッファ粒度は per-persona**（§9-A 確定の根拠）。ペルソナホームからも同プレビューを開けるようにする想定だが、ペルソナホームまわりの実装は別途詰める。(まはー確定 2026-07-09)
- **消費後にペルソナへ入った情報の事後表示（別件・合流）**: ユーザーが最後に喋った後、ペルソナが自律 Pulse 等で知覚・自己更新した情報の透明性。これは「既に時間が動いてペルソナの中に入った情報」の話なので知覚バッファの範囲外。**スルースでペルソナが自発的にコア記憶を更新したとき、ユーザーにどう見せるか**という並行案件（`memory_architecture_v2.md` §5.1 未確認バッジ）と完全に合流する。(まはー整理 2026-07-09)

## 7. 不変条件

- **C1. 知覚は Pulse でのみ発生する**: バッファへの書き込みは Pulse 外でも起きるが、ペルソナが知覚する（＝ SAIMemory に入る）のは Pulse 消費時のみ。Pulse 外で SAIMemory に直接知覚を書く経路を新設しない。
- **C2. 畳み込みは未消費の間だけ**: 消費（知覚）済みの項目は相殺・改変しない。相殺できるのは「ペルソナがまだどちらも見ていない」から。
- **C3. 同一 Pulse の知覚は 1 メッセージ**: 消費時に型別 reduce した結果を 1 つの event_message にまとめて永続化する。同一 Pulse で複数の知覚メッセージを積まない。
- **C4. event_message 規約を継承**: 従来の差分通知と同じく `metadata.tags=['internal','event_message']`・Track 横断メタログ（`origin_track_id=NULL`）で保存し、Chronicle / scene 切り出し / キーワード検索から自動除外する。
- **C5. 知覚は単一の永続バッファに集約する**: バッファを迂回して直接 SAIMemory へ注入する経路を残さない（現行 3 直挿入は撤去）。バッファへの**入力を作る検知アダプタが型で違う**（状態型＝検知タイミングでの snapshot 比較〈§4.5〉、非状態型＝発生時 push）のは、並存する二経路ではなく単一経路への型別入力。snapshot 比較器は「注入経路」ではなく「状態型 event の検知器」として残る。
- **C6. 一つの知覚が SAIMemory に入るのは高々一度**（2026-08-08 追加、Codex レビュー #2）: 消費は「SAIMemory へ書く」→「バッファから削る」の二段で、この二段の間で失敗すると**書き終えた知覚がバッファに残る**（削除自体の失敗 / 二つの commit の間でのプロセス死）。次の消費は event_message に刻まれた知覚 id（`metadata.perception_ids`）と照合し、書き終えている分は書き直さず削除だけやり直す。**「書けたか不明なら残して再試行する」（知覚を落とさない、SEA 監査 S5）は据え置いたまま**、再試行が二度書きになる口だけを塞ぐ。消費点が Beat 単位になって再試行の機会が増えたぶん、この塞ぎが要る。
  - **供給源を先に断つ**: 当時いちばん頻度が高かったのは「行は保存されたのに、後から作る埋め込みが落ちて**保存失敗として返る**」経路だった。派生物（検索用の索引）の失敗を保存の失敗として報告すると、呼び出し側は保存済みの行を書き直しに来る——だから照合で受け止める前に、`SAIMemoryAdapter._append_message` が「行が入ったか」だけで成否を返すよう直した。**照合はその後に残る細い口（削除失敗・プロセス死）のための最後の網**であって、これ一本に頼る設計ではない。
  - **この照合が成り立つ前提**: 消費は Beat の内側でしか呼ばれない（Pulse 頭とスペルループの周の切れ目。どちらも Beat ロックを保持する）ので、同じペルソナの消費同士は割り込まない。消費の呼び出し口を Beat の外や別プロセスへ増やすなら、照合では足りず DB 側の一意制約で場所取りする形が要る。

## 9. 方針確定と残る実装判断

**大原則（まはー 2026-07-09）**: 複数の知覚経路を恒常的に残すのは不健全。最終的に本 doc の仕様（全知覚を知覚バッファに event-push で一本化）へ統一する。ハイブリッドや旧経路は**移行の途中状態としてのみ許容**し、移行完了で撤去する。ただし今回の実装スコープを太らせすぎない。判断基準は「一本化する実装コスト（一度きり）」対「二経路を維持し続けるコスト（恒久）」の比較。

- **A. 永続性 → 永続化で確定**（まはー確定 2026-07-09。当初の「状態型は揮発でよい」案は撤回）: バッファは永続化する。揮発を守ろうとすると透明性（§4.5 の任意タイミング検知）と再起動耐性の両立に冪等同期・型別分担といった複雑さが要るが、永続化すればすべて不要になり（再起動耐性は自動、状態型/非状態型の永続化分担も消える）、全知覚が単一の永続バッファに集約される。書き込みコストは入退室/アイテムの低頻度ゆえ無視できる。詳細は §4.1 の永続バッファ注記。
- **B. 検知と消費の分離 → 検知タイミングは複数**（§4.5。当初「消費時に比較」は透明性を殺すので撤回——まはー指摘 2026-07-09）: 状態差分の検知（snapshot 比較 → バッファ投入 → 基準 snapshot 更新）は、消費（Pulse flush）と独立に、プレビュー / Pulse / 定期などのタイミングで走る。撤去するのは「バッファを迂回して直接 SAIMemory へ注入する 3 経路」であって snapshot 比較器そのものではない（比較器は検知タイミングで走る状態型の検知器として残す）。非状態イベントは発生時に直接バッファへ push。全知覚は単一の永続バッファに集約される（大原則）。
  - **段階**: Phase 1 は非状態イベント（メタ記憶訂正）を発生時 push でバッファに載せ、その直挿入経路を畳む。Phase 2 で状態型の検知（snapshot 比較）を「検知タイミングでバッファ投入」に付け替え、3 直挿入経路を全廃。
- **C. プレビュー先行・編集後回し**（まはー 2026-07-09）: Phase 3 はまず未消費バッファの**閲覧（read-only）**を `ContextPreviewModal` に出す。項目編集（削除 / 抑制 / 本文編集）はその後。

**決定済み**: 消費者＝主観時間を進める Pulse すべて（§4.2）／会話取り込みも経路に載せる（§4.4 / §5.3）／バッファ粒度 = per-persona（§6）／未消費プレビューの置き場 = `ContextPreviewModal`（§6、ペルソナホームからのアクセスは別途）／バッファは永続化（A）／検知は消費と分離しプレビューも検知タイミング（§4.5 / B）。

## 10. 後続 Phase: 知覚レンダリング (= 完了計画書 W14、2026-08-18 設計確定)

[experience_structure.md](experience_structure.md) §7 の原則 (イベント記憶領域への記帳・コンテキストへは翻訳のみ・event_message 直挿しの段階的廃止) の実装形。まはー裁定 2026-08-18: **案A (台帳正準) を採用。畳む判断は新設せず、会話の退場判定に相乗りする** (当初案の「24時間の鮮度窓」は根拠がなく撤回した — 独自の畳みタイミングを発明すると「畳んでいいか」の判断責任が新設され、head にも生テキストにも出ない情報はペルソナに存在しないのと同じになるため)。

### 10.1 存在論

会話ログ (SAIMemory messages) は会話の事実を持つ場所、知覚は知覚台帳が持つ。「その瞬間に知覚した」という証跡は、会話ログの event_message 行ではなく**台帳の消費印**が担う。消費された知覚は messages に行を作らない。

### 10.2 器 — 消費バッチ (2026-08-18 Codex レビューで改訂: 時刻からの再構成をやめる)

消費 (flush) は**消費バッチ**を単一トランザクションで確定する: バッチ行 (一意 id / `consumed_at` / `pulse_id` / `episode_id` / **確定レンダリング済みテキスト** = reduce → format の結果 / メディア / 付記印 `annexed_entry_id` = NULL) を挿入し、消費した項目にバッチ id と `consumed_at` の印を打つ。「その瞬間に知覚した」証跡はこのバッチ行であり、**ペルソナが見た文面そのもの**が消費時に確定・永続化される (後から台帳の生の行を読み直して再構成しない — 再構成は reduce で消えた中間状態を復活させ、秒精度の時刻衝突でグループを混ぜる)。二段 commit の隙間を塞ぐためにあった C6 の照合機構は**機構ごと退役**。消費済み行・バッチ行は削除しない。

### 10.3 提示 — 未付記バッチの時刻順マージ

コンテキスト組み立ての履歴節が、messages と**付記印のないバッチ** (`annexed_entry_id IS NULL`) を時刻順にマージして提示する。バッチはレンダリング済みテキストを `<system>` 包みでそのまま出す — 窓や fold スパンの計算は持たない (**提示から下ろす唯一の手段が付記印**なので、付記されるまで消えない = 下限が提示側でも常に成立し、履歴が空でも未付記バッチは提示される)。Chronicle 無効のペルソナ (「編纂なしで忘れる」を選んだ) だけは、提示中の生ログ窓より古いバッチを会話と同じように忘れる。編纂がバッチに付記印を打ってから退場が適用されるまでの短い間、そのバッチは提示から先に下りる (digest 可視化と同じ節目量子化の一部として受容)。ラウンド中の Beat 頭消費が作業中コンテキストへ断片を差し込む挙動は不変。

### 10.4 退場 — 会話と同じ運命 (fold 相乗り)

Chronicle 編纂がチャンクの digest を確定するとき、対象期間の**未付記バッチ**と legacy event_message 行を digest へ**決定論で** (LLM なしで) 添え、バッチには**digest 確定と同一トランザクションで付記印**を打つ。少量なら全文を恒等転写 (恒等圧縮と同じ — 小さいものは潰さない)、大量なら kind 別集約。期間の割り当ては:

- 付記スパンの敷き詰めは**同一 fold 群 (alignment の run_groups) の中だけ**。群と群の間に生きた提示中の範囲が挟まるとき、そこのバッチは提示に残り、その土地が編纂される回に引き取られる。
- 計画の先頭チャンクは、**既存の編纂被覆の末尾以前の未付記バッチを一括で引き取る** (チャンク skip・付記失敗・関節の取り残しの回収路。転写には発生時刻が付くので、少し後の digest に載っても時系列の嘘にはならない)。
- 付記の失敗は digest を止めず、バッチは未付記のまま**提示に残る** (fail-open — 消える方向には倒れない)。

これで「退場したものは必ず編纂されている」の下限 (experience_structure §4-1) が知覚に通る。legacy event_message 行は同スパンで転写するが付記印を持てないため、チャンク skip 等で転写機会を失った行は従来どおり digest に入らず退場する (W14 以前と同じ挙動・行は DB に残る — 既知の残欠として記録)。

### 10.5 読み口と調整口

- 退場後も台帳に全文が残るので、読み口を付ける: **消費済みバッチ (rendered_text) を unified_recall のキーワード検索対象に含める** (未消費は含めない)。当初「実装時に決める・後回し」としていたが、付記の集約 (件数への畳み) は「全文へ到達する手段とセット」でなければ下限の主張と矛盾するため、W14 本体スコープへ繰り入れた (2026-08-19 Codex 三巡の指摘で確定)。集約の転写も汎用見出しでなく**意味のある本文冒頭を必ず残す**。現行は退場で完全消滅+検索除外なので、**どの時点を切っても見える情報は現行より減らない**。
- kind 別の早畳み (例: 古いフィード記事だけ逐語期間を短く) は**調整口だけ**用意し、既定では発動しない。発動条件は実機観察を見てまはーと決める。

### 10.6 直挿しの移送と対象外

- **移送する** (バッファ迂回の純粋な知覚): 施設移動失敗通知 (`day_plan._record_move_failure`)、アップグレード通知 (`upgrade_handlers`) → `push_perception` へ。
- **対象外**: ①他ペルソナ発話の取り込み (auto_ingest) = 会話内容であって通知でない。Phase 1b/2b (Phase 5 と足並み) の裁定のまま。②機構の報告書系 (ライフ境界通知・編纂の朝報告・スルース記録) = 「機構が何をしたか」の事実の記録で知覚と存在論が違う。event_message 形式のまま残す (ライフ境界通知は消費者確認の上で第二段候補)。③判断の状況文 (paired_action) = 別 issue へ分離。

### 10.7 不変条件の改訂

- C1: 「知覚する＝SAIMemory に入る」→「知覚する＝台帳に消費印が入る」。Pulse (Beat) 外で消費印を打つ経路を新設しない、は不変。
- C3: 「同一 Pulse の知覚は 1 メッセージ」→「同一 Beat の消費は 1 ブロック (マージ提示の 1 挿入)」。
- C4: event_message 規約は legacy 行にのみ残る (新規知覚は行を作らない)。
- C6: 退役 (消費が単一トランザクションになり、二度書きの口が構造ごと消えるため)。
- C2 (未消費の間だけ reduce)・C5 (単一バッファ集約) は不変。
