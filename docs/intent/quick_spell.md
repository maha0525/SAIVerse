## 1. 背景 — 事故と契約の問い

2026-07-07、quon_city_a がスペルループの継続ラウンドで偽のシステム通知
（`<system>[システム通知]…</system>`）を自分の発話として生成し、SAIMemory の
committed main_line に記録される事故が起きた。

調査と議論で確定した因果連鎖（詳細は issue 参照）:

1. **根因はデータ汚染**: gold_panning の判断ターンが assistant 名義で記録される
   バグ（`docs/intent/gold_panning.md` §3.8 で同日修正済み）の**修正前データ**が
   当時のクオンの memory.db に残存していた
2. その残存データが2つの顔で事故を引き起こした:
   - **記録済み事実の不可視化**: 砂金採りで刻んだ c:1〜3 の「刻まれた」という
     出来事がシステム通知形式で本人の記憶に立たず、本人は未記録と誤認 →
     会話中に `/spell core_memory_add` を4連発（重複記録、c:4〜7 として追加）
   - **自己像の誤学習**: プロンプトの見えない裸の assistant 発話として立った
     構造化文が「自分はこういうシステム風の文を喋る」と教えた → 継続ラウンド
     の無指示な空白で偽通知の文体が出た
3. その上で、**継続ラウンドの契約が未定義**という機構側の穴も実在する:
   スペル結果を受けた再 LLM コールに「何を期待し、何を禁じ、いつ黙ってよいか」
   がどこにも定義されていなかった

本ドキュメントは 3 の穴を塞ぐ設計。ただし誘導文でモデルを矯正する方向
（後述の廃案 A〜C）ではなく、**継続の要否を撃つ本人が構文で宣言する**方向で塞ぐ。

## 2. 概念 — 撃ち方が意志の宣言になる

スペルの撃ち方を2つに分ける:

- **`/spell`（従来型・標準）** = 「結果を見て続ける」意志の宣言。
  従来通り、結果が注入され LLM が再呼び出しされる。検索・想起・画像生成など、
  結果を本人が自分の言葉で語ってこそのスペルはこちら
- **`/quick_spell`（簡易型・特殊例）** = 「この発話で完了」の宣言。
  結果は SAIMemory に記録されるが、追加の LLM コールは起きない。
  コア記憶の追記・メモの整理など、結果が完了報告（ACK）でしかない帳簿系操作
  で空白の継続ラウンドを生成しないための道具

この対によって、旧設計案が抱えていた2つの問題が構造ごと消える:

- **分類問題**: 「このスペルの結果を語りたいか」はスペルの静的性質では決まらず、
  撃つ瞬間の文脈で決まる。判断を ToolSchema の分類表でなく撃つ本人に置くこと
  で、事前分類できない MCP / アドオンスペルにも自動で通用する
- **空白の圧**: 継続ラウンドという空白スロット自体が生成されないので、
  そこでの振る舞いを誘導文で矯正する必要がない

**位置づけの原則**: 標準はあくまで `/spell`。quick は「結果を見る必要がないと
確信できるときだけ使える特殊例」として規約文でも提示する。従来 /spell で体験は
成立していたので、quick の乱用（presentation 系を quick で撃って語らずに終わる）
で体験を落とさないことを命名（spell の派生形と一目で分かる）と規約文の両方で守る。

**Beat との接続**: 継続ラウンドは Beat（ペルソナの最小行動単位、命名済み・実装
未型付け）のスロットにあたる。quick_spell は「空 Beat の宣言的省略」であり、
Beat が型付けされる際はこの契約が「Beat をどう終端するか」の仕様の一部になる。

## 3. 機構設計

### 3.1 構文とパーサ

```
/quick_spell name='ツール名' args={'引数名': '値'}
```

`/spell` と完全同形、動詞のみ違い。`_parse_spell_lines` / `_SPELL_PATTERN` 系を
拡張し、パース結果に `quick: bool` を運ぶ。canonical / fuzzy / malformed 救済の
全経路で quick 判定を保持する（fuzzy 救済された quick_spell 行も quick 扱い）。

### 3.2 ラウンド判定 — 全 quick / 混在

- **ラウンド内の全スペル行が quick** → 実行・記録（§3.5）まで従来通り行い、
  **LLM 再呼び出しをスキップしてループ終端**
- **通常 `/spell` が1行でも混在** → 従来通り再呼び出し。quick で撃たれた分の
  結果も同じ注入メッセージに含める（同一発話内で「見える結果 / 見えない結果」
  が割れる不整合を避ける。混在時の quick は「これだけなら継続不要」という
  宣言に格下げされるだけで、実行・記録は同一）

### 3.3 失敗の検知 — 2層

quick の「成功したら黙って完了」を安全にするには、失敗が機械可読であることが
前提になる。失敗を2層に分けて扱う:

**(1) 機械的失敗** — 機構が確実に検知できるもの:
- ツール実行中の例外（現状 `_run_spell_tool_async` が文字列に溶かして返すため
  呼び出し側で成功と区別できない — **既存バグの修正を兼ねる**。修正前は例外死が
  `[Spell Result]` の顔をして注入されていた）
- レジストリ未登録（`Spell 'X' not found in registry`）
- unknown spell / malformed args / モードゲートブロック（これらは既に
  `round_records` の `success=False` で検知済み）

対応: `_run_spell_tool_async` の戻り値を `(result_str, metadata)` から
`(result_str, metadata, ok)` の3要素に変え、例外パス・レジストリ未登録で
`ok=False` を返す。`_run_spell_loop` の `valid_results` はこの `ok` を
`executed`（→ `round_records.success`）に反映する。

**(2) 論理的失敗** — ツールが例外を投げず、丁寧語の失敗文を正常戻り値で返す
ケース（例: 「該当するメモが見つかりませんでした」）。機構からは成功と区別が
つかない。**文字列ヒューリスティックは使わない**（不変条件5）。

対応: 既にサポートされている `(str, dict)` 2-tuple 戻り値の metadata に
`"error": true` を積むことでツール側から失敗を宣言できる規約を追加する。
additive な規約であり、宣言しない既存ツールの挙動は一切変わらない。
quick で撃たれる頻度が高い帳簿系（`core_memory_*` / `note_*` / `track_*` /
`task_*` / memopedia 編集系）から順次宣言を入れる。丁寧語で作り込まれた
エラー文面を例外ダンプに置き換えずに済むのがこの形の利点。

### 3.4 失敗時の昇格

**昇格条件**: 全 quick ラウンドでも、1つでも失敗（機械的 `ok=False` または
metadata `error: true`）があれば、従来と同じ結果注入 → LLM 再呼び出しへ昇格
する。成功したら手放せる、失敗したら起こされる — この非対称が契約の核。

昇格時の注入メッセージには、なぜ quick 宣言に反して応答機会が返ったかを
説明する短い事実文を先頭に付ける（文言は未決事項 §7。方向性:
「/quick_spell で唱えたスペルに失敗があったため、結果を確認できるよう応答機会を
返しています」）。これは失敗時のみ現れる出来事の説明であって、毎ラウンド注入
される規約文ではない（廃案 B の反復注入汚染とは性質が異なる）。

### 3.5 記録と UI

- **SAIMemory**: quick の結果も従来と同じ経路で記録する — 発話（spell 行込み）
  はラウンドの assistant 記録（実行前の前倒しブロック）、結果は
  `combined_results` の system role 記録。誘導文の注入自体が存在しないので
  「誘導は記録ではない」問題も発生しない
- **本人からの見え方**: 結果は次の Pulse で anchor 復元により本人のコンテキスト
  に立つ。quick は「結果が見えなくなる」のではなく「見るのが次の機会になる」
- **UI / 建物履歴**: `full_merged_text`（text_before ＋ ★/×ブロック ＋
  text_after）は従来通り。継続発話が付かないだけ
- **`final_continuation`**: 全 quick 終端時は空文字を返す（空応答は既存機構で
  正規終端 — append も永続化もされない）。発話本文はラウンド内 assistant 記録
  が既に持っているので取りこぼしはない（実装時に `state["last"]` / 後段
  memorize ノードとの整合を確認すること — §7）

### 3.6 システムプロンプト規約（head）

掲示先は `sea/head_pipeline/sections/spell_list.py` の `render()` 固定前文
（「### 使い方」ブロック）。render の静的テキスト変更なので snapshot 構造は
無変更（head テキストが変わる一回だけキャッシュが張り直される。用途別の
出し分けはしない — head は (persona, model) 固定の原則）。

文言たたき台（最終文言は §7）:

> 結果を見て発言を続ける必要がない記録・整理系の操作には `/quick_spell` が
> 使えます（構文は /spell と同じ）。quick_spell は成功するとその発言で完了し、
> 結果はあなたの記憶に記録されます（次の機会に確認できます）。失敗した場合と、
> 通常の /spell と同じ発言に混ざっている場合は、通常通り結果が返ってきます。
> 基本は /spell を使い、quick_spell は結果を確認する必要がないと確信できる
> ときだけ使ってください。

### 3.7 適用範囲外

- **`_execute_pre_spells`（応答前スペル経路）**: 適用外・無変更。ユーザー起動の
  事前実行であり、継続はその Pulse の本応答そのもの — 「完了宣言」が成立しない
- **構造化出力内**: 従来通りスペル自体が使用不可
- **media 転送**: quick 終端では継続コールが無いため metadata の media は LLM に
  渡らない。運用上、画像提示はペルソナが saiverse:// URI を発話に書く形で行われて
  おり media 転送経路は実質使われていない（2026-07-07 まはー確認）ため、機構
  ガード（media 付き結果での強制昇格など）は入れない

### 3.8 メタ判断・自律行動 v2 との関係

- メタ判断 Pulse の `meta_judgment_buffer` への発動 spell ＋結果の記録は quick
  でも同様に行う（記録経路は共通のまま）
- 自律行動 v2 の作業セッション予算（`_run_spell_loop` の `max_rounds`）に対し、
  quick はラウンド予算を消費しない撃ち方になる。帳簿処理で予算を溶かさず、
  語るべき結果にだけラウンドを使える — 予算設計と整合する

## 4. 廃案の記録（再提案しないこと）

1. **事後の剥がしガード**（発話から `<system>` を strip）— まはー却下:
   喋り始めたこと自体が問題で、事後に剥がしても対症でしかない
2. **全スペル一律の「無ければ黙れ」誘導文** — 実装後差し戻し済み(2026-07-07)。
   結果を語ってこそのスペルの発話まで抑制する
3. **案A（ToolSchema にスペル区分を持たせ誘導文を出し分け）** — 「語りたいか」は
   静的性質でなく撃つ瞬間の文脈で決まる。MCP / アドオンは事前分類できず、
   未分類デフォルトの挙動を結局決めることになり追加機構が効く場面がない
4. **案B（継続ラウンド注入への文体境界の常時追加）** — まはー却下: スペルは
   高頻度で撃たれ、規約的文章が繰り返しコンテキストに注入されること**自体が
   別種の汚染**になる。また偽通知の文体の出所は誘導不足でなく assistant 名義
   記録の残存データだった（根因は §1、修正済み）
5. **案C（B ＋帳簿系ラウンドのみ沈黙許可）** — B を含むため同上。沈黙許可の
   機能は quick_spell が「事後の許可」でなく「事前の宣言」として吸収した
6. **エラー検知の文字列ヒューリスティック** — 戻り値文面の嗅ぎ分けはしない。
   機械的 ok フラグと metadata error 宣言のみ（§3.3）

## 5. 不変条件

1. **標準は `/spell`、quick は特殊例** — 規約文・命名でこの位置づけを崩さない。
   quick の使用を促す圧をプロンプトに入れない
2. **失敗を沈黙で飲み込まない** — 全 quick ラウンドでも失敗が1つでもあれば
   必ず継続ラウンドへ昇格して結果を見せる
3. **quick は additive** — quick を使わないペルソナ・既存プレイブック・既存
   ツールの挙動は従来と完全に同一
4. **エラー判定に文字列ヒューリスティックを使わない** — 機械的 ok フラグ
   （例外・未登録・unknown・malformed・ゲート）と metadata `error: true`
   宣言のみを失敗として扱う
5. **誘導文をスペル結果と一緒に SAIMemory へ永続化しない** — 昇格時の説明文
   （§3.4）も注入のみで、記録される `combined_results` には混ぜない
6. **継続ラウンドの空応答は正規終端であり続ける**（既存挙動の保護）
7. **混在ラウンドで結果の可視性を割らない** — 通常 spell が混在したラウンドでは
   quick の結果も同じ注入に含める

## 6. 実装フェーズ（実装セッションへの引き継ぎ手順）

前提: `.venv/Scripts/python.exe` を使用。変更後は `ruff check` と
`python -m pytest tests/` を通すこと。挙動確認は `llm_io.log` /
`sea_trace.log`（`SAIVERSE_SEA_TRACE=1`）で spell_round の有無を観測する。

- **Phase 1 — ok フラグ配線（既存バグ修正を兼ねる・単独コミット可）**:
  `_run_spell_tool_async` を 3-tuple `(result_str, metadata, ok)` 化し、例外
  パス・レジストリ未登録で `ok=False`。`_run_spell_loop` と
  `_execute_pre_spells` の呼び出し側で `executed` に反映（例外死が
  `[Spell Error]` ラベルで注入されるようになる）
- **Phase 2 — パーサ ＋ 終端/昇格ロジック**: `/quick_spell` パース（quick
  フラグの伝搬、fuzzy 救済含む）、全 quick 判定、全成功なら再呼び出しスキップ
  （`final_continuation=""`）、失敗あれば説明文付き注入で従来フローへ昇格。
  `state["last"]` / memorize 整合の確認（§7-1）
- **Phase 3 — head 規約文**: `spell_list.py` `render()` の「### 使い方」に
  §3.6 の文言（まはー最終確認後のもの）を追加。
  `tests/test_head_pipeline_spell_list.py` の期待文字列更新
- **Phase 4 — metadata error 規約**: `docs/developer-guide/`（ツール追加ガイド）
  に規約を記載し、帳簿系ツール（`core_memory_*` / `note_*` / `track_*` /
  `task_*` / memopedia 編集系）の失敗戻りに `{"error": true}` を宣言
- **テスト**: mock LLM で (a) 全 quick 終端＝再呼び出しなし、(b) 混在＝
  再呼び出しあり＋quick 結果も注入に含まれる、(c) 機械的失敗昇格、
  (d) metadata error 昇格、(e) quick 不使用時の完全無変化（回帰)
- **ドキュメント同期**: `docs/overview/landscape.md`（スペル節）、
  `docs/reference/`（該当があれば）、`scripts/gen_reference_docs` 対象に
  ツール変更が含まれる場合は `gen_reference_docs.bat` 実行
