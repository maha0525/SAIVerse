# 型付き判断の共通化 — 答える側 (Jev / 互換の宛先 / 手持ちの軽量モデル) の差し替え

**ステータス: 設計中 (2026-09-19 起草、言葉づかい・整合性の検査済み。まはーの設計レビュー待ち — 名称を含む裁定ポイント 7 つ)**

## これは何か

Jev の実験 (docs/intent/auto_recall_jev_rerank.md) で開けた「**状況と、はい/いいえの
基準付きの質問を渡すと、文章ではなく確率だけが返る**」という呼び出しの形を、
二方向に一般化する設計。

1. **答える側を差し替えられるようにする** — 答えるのが ①TypeSafe 公式の Jev、
   ②Jev の API と同じ作法で話せる別の宛先 (セルフホストの OpenJev など)、
   ③手持ちの普通の軽量モデル (構造化出力で確率を返させる)、のどれでもよい。
2. **想起以外でも同じ呼び出し形を使えるようにする** — 自由記述が要らない
   構造化判断 (ツール選択・自律判断など) の全般が、同じ質問の書き方・同じ
   失敗時の扱いでこの共通の呼び出し形を使える。

まはーの依頼 (2026-09-19): 「Jev の代わりに普通の軽量モデルを使えるようにする」
「Jev の API と互換の別エンドポイントに差し替えられるようにする」「自由記述がない
構造化出力案件全般で Jev 形式を使えるようにする流れになりそうだから汎用的な
仕組みを持ちたい」。

## 全体像 (どこで何が変わるか)

- **影響を受ける人**: 判断の質・速さ・費用の出どころを利用者が選べるようになる。
  TypeSafe 側の障害 (このセッションの実測: 2026-09-19 に公式 API が半日 503 を
  返し続けた)・将来の料金改定・オフライン運用への保険でもある。
- **流れ**: 呼び出す機能 (現在は自動想起の選別層のみ。候補: ツール選択・自律判断)
  → 共通の呼び出し形 → 選ばれた答える側 → 確率が返る → 採否の判断は呼び出した
  機能の側で行う。
- **変えないもの**:
  - **失敗時の扱いは呼び出した機能の側が持つ**。共通層は「使えなかった」を
    一種類の例外で返すだけで、そのターンをどう凌ぐか (自動想起なら従来方式へ
    戻る) は各機能の設計のまま。
  - 会話の返事を待たせる場所で使う前提の作り — 同時本数の上限・実際の経過時間で
    打ち切る締切 — は、答える側によらず同じにする。

## 設計

### 1. 質問の形 — System One の形を「当面の共通語」にする

現在使っているのは Noul (TypeSafe の質問の型のひとつ。はい/いいえの確率を返す)
だけ。質問ごとの ID (qid) に `{instructions, criteria: {true, false}}` を添える
System One の形を、呼び出す機能が書く共通の形とする。①②へはそのまま送り、
③へは共通層の中でプロンプトに変換する — 呼び出す機能は質問を一度書けば、
答える側を知らなくてよい。

**射程の限定**: これは「SAIVerse の構造化判断の正典を外部ベンダーの API の形に
固定する」という決定ではなく、**当面の実装形**。共通語を自前の形に置き直すのは、
System One に無い型が必要になったときに改めて設計する (裁定ポイント 5)。

Choice (選択肢) と Score (数値) の型は、最初の利用者が現れたときに足す
(裁定ポイント 4)。

### 2. 答える側は 3 種

**(A) TypeSafe 公式 (現行)** — `saiverse/typesafe_client.py` がそのまま実体。

**(B) 互換の別の宛先** — 宛先とモデル名を設定で差し替える案:
`TYPESAFE_API_URL` (完全な宛先。既定 `https://api.typesafe.ai/v1/systemone` —
現行コードの定数 `API_URL` と同じ値をそのまま env 化する)、`TYPESAFE_MODEL`
(既定 `jev-latest`)。通信の作法が同じなので、締切・同時上限・キーの伏せ字・
厳格な応答検証といった共通の作りはそのまま使い回す。

- **キーは宛先とペアで扱う**: 宛先が既定 (公式) と完全一致のときだけ
  `TYPESAFE_API_KEY` を送る。**公式以外の宛先へはキーを送らない** (キー無しで
  接続する)。宛先だけ第三者へ向けた設定で公式のキーが流れる事故を防ぐため —
  既存の裁定「信頼は宛先とキーの組で引き継ぐ」(model_provider_management.md
  の provider 照合) と同じ向き。認証付きの互換サーバーが必要になったら、
  そのとき専用のキー設定を設計する (今は作らない)。

**(C) 手持ちの軽量モデル** — 既存のモデル基盤 (`llm_clients`) を使い、状況と
全質問を 1 個のプロンプトに畳んで、構造化出力で確率を返させる変換層。

- モデルの指定は、**モデルの役割の一元表 (`saiverse/model_defaults.py` の
  `MODEL_ROLES`) に「構造化判断」の役割として登録する** — 6 つある役割の 7 個目。
  この表に載ることで、定義の無いモデル名を保存しない検査・画面の警告・
  チュートリアルのプリセットが既存の仕組みのまま効く (役割表の外に独自の
  env を作ると、打ち間違いが誰にも知らされない静かな劣化になる)。
  未指定の既定は軽量モデルの既定と同じ解決 (env → 組み込み既定へ落ちる、
  `LIGHTWEIGHT_MODEL` と同じ道筋)。**ペルソナ個別の軽量モデル設定は関与しない**
  (裁定ポイント 6 — これは決定ではなく提案)。
- **応答スキーマは配列 `[{id, probability}]` で受けて辞書に戻す** — Gemini の
  構造化出力は additionalProperties を使えず、qid が動的な辞書スキーマを
  組めないため (CLAUDE.md の既知の罠)。
- 全 qid が揃わない・0〜1 の外・無限大や数でない値は不成立 (TypeSafe
  クライアントと同じ厳格さ。部分回答を誤って採用しない)。
- 締切は LLM クライアントの timeout に渡したうえで、実際の経過時間でも打ち切る。
  同時本数の上限は (A)(B) と**同じ枠を共有する** (プロセス全体で 4 本 — 利用者
  から見える「混んだターンは判定を通らない」の挙動を答える側で変えない)。

### 3. どれが答えるかの選び方と、費用が黙って発生しない約束

- `SAIVERSE_JUDGMENT_BACKEND` = `typesafe` (既定) / `llm`。互換の宛先は
  `typesafe` のまま `TYPESAFE_API_URL` を変える (プロトコルが同じだから、
  独立した第三の選択肢にはしない)。
- **「使えるか」の判定は共通層の中で行い、二種類を区別する**:
  - **設定ミス** (llm でモデル名がカタログに実在しない、typesafe でキーが無い):
    役割表の既存の検査・警告に乗せて**利用者に見える形で知らせる**。実行時の
    静かなフォールバックには畳まない (既存裁定「指定したモデルが無いとき、
    代わりのモデルで動かさない・黙って別のもので済ませない」と同じ向き)。
  - **実行時の障害** (接続不可・締切超過・不正応答): 従来どおり、そのターンだけ
    呼び出した機能のフォールバックで凌ぐ (WARNING ログ)。
- **既存の約束「キーが無ければ OFF」は破らない**。現行は
  `SAIVERSE_AUTO_RECALL_JEV=1` + `TYPESAFE_API_KEY` の両方が揃って初めて ON
  (environment-vars.md と既存テストが契約として固定)。この約束の例外は、
  **利用者が `SAIVERSE_JUDGMENT_BACKEND=llm` を自分で書いたときだけ** —
  それ自体が「軽量モデルの費用で判定してよい」の明示の意思表示だから。
  トグルだけ立ててキーを消してある既存環境が、更新後に黙って軽量モデルの
  課金を始めることは起きない。
- 機能の ON/OFF は従来どおり各機能の設定が持つ (自動想起なら
  `SAIVERSE_AUTO_RECALL_JEV`)。この env 名は答える側が llm でも据え置くか、
  改名するかは名称の裁定に含める (裁定ポイント 1)。

### 4. 費用の帰属 (答える側 3 種すべて)

判断の費用は、答える側によらず**同じ場所に、同じ帰属の仕方で**見えるべき —
(C) だけ記帳して (A)(B) が見えないと、「答える側を替えたら費用が消えたように
見える」非対称ができる。

- (C) は既存の使用量の記帳 (usage tracker) に、役割表の設定キー名義で載せる
  (「使用量と費用は設定キーに帰属させる」の既存原則のまま)。
- (A)(B) は単価がモデルカタログに無い外部 API なので、同じ記帳に載せるには
  単価の置き場が要る。当面はログ (現行の usage 出力) のみとし、記帳への統合は
  恒久昇格時の宿題として明記する — か、最初から揃えるか (裁定ポイント 2)。

### 5. 置き場と移行

- `saiverse/typesafe_client.py` は (A)(B) の実体として残す (宛先とモデル名の
  env 化のみ)。
- 選択と (C) の変換層を持つ薄いモジュールを 1 つ新設し (名称は裁定ポイント 1)、
  呼び出す機能はそこから確率評価の関数を import する。例外
  `TypeSafeUnavailable` は共通の名前に**改名し切る** (利用箇所は自動想起と
  テストだけと確認済みなので、別名は残さない — 中途半端な混在を作らない)。
- 設定は Jev 実験と同じく当面 env で持つ。恒久機能へ昇格するときに、宛先とキーを
  モデルカタログ (provider_ref) へ載せ替える道を残す — provider type を新設する
  のはその時で、今は作らない (把握可能性: 使い手の居ない器を先に作らない)。
- **env の全体像** (この設計で増えるのは 3 本): 機能の ON/OFF (各機能、既存) /
  答える側の選択 `SAIVERSE_JUDGMENT_BACKEND` (新) / typesafe の接続先
  `TYPESAFE_API_KEY` (既存)・`TYPESAFE_API_URL`・`TYPESAFE_MODEL` (新) /
  llm のモデルは役割表 (env としては役割表の既存の形に乗る)。しきい値等は
  従来どおり各機能側。実装時に environment-vars.md へ「どれを触ると何が
  変わるか」の対応表を一枚で載せる。

### 6. 観測と品質比較

- 判定ログの形 (`[auto_recall][jev] judged N/N ...`) は共通層でも維持し、
  **どの答える側が答えたか**をログに載せる。
- 同じ場面を答える側だけ替えて再現する検証 (隔離環境または読み取り専用の
  合成再現。実 API の課金はその API の実費で、実行は従来どおりの承認の範囲) で、
  Jev と軽量モデルの確率を並べて比較できる — 「Jev でなければ出ない質か」の
  答え合わせが実測でできる。

## 裁定ポイント (まはー)

1. **名称**: 新モジュール名・この intent の名・ログの語・例外の新名・
   (答える側が llm でも据え置くなら) `SAIVERSE_AUTO_RECALL_JEV` の env 名。
   注意が二つ: 「構造化判断」は時間割の書き換え (day_plan) の地の文で既に
   別の意味に使われており、自律行動の「判断点」とも紛れやすい。私の推しは
   **「型付き判断」** (この文書の表題に仮置きした) — 新しい漢字一字の用語
   (「口」「窓」型) は作らない。
2. **費用の帰属**: (C) は記帳に載せる前提として、(A)(B) の TypeSafe 系の費用を
   最初から記帳に統合するか (単価の置き場の設計が要る)、当面ログのみで恒久
   昇格時の宿題にするか。私の推しは後者 (今の実験の規模では 1 ターン 0.01 円
   未満で、器を先に作る価値が薄い)。
3. **公式以外の宛先にはキーを送らない**、で良いか (認証付き互換サーバーは
   必要になったとき専用のキー設定を設計する)。
4. **質問の型の範囲**: Noul (はい/いいえの確率) だけ作る。Choice / Score は
   最初の利用者が現れたときに足す。私の推しはこのまま。
5. **共通語の射程**: System One の質問の形を「当面の共通語」とする限定で
   良いか (SAIVerse の正典として固定するのではなく)。
6. **軽量モデルの答える側は世界側の一本のモデルで良いか**: Jev と同じ形
   (全ペルソナ共通・ペルソナの設定モデルとは無関係)。ペルソナごとの軽量
   モデルで判定させる形は、必要が見えたときの拡張とする。私の推しは一本。
7. **既存の約束の継承**: 「キーが無ければ OFF」の例外を
   `SAIVERSE_JUDGMENT_BACKEND=llm` の明示だけに限る (§3)、で良いか。

  互換の宛先への差し替え・自由記述なしの構造化判断全般への一般化」を要望。
  本 intent を起草。
- 2026-09-19: 言葉づかいの検査 (自作の短い漢字用語「口」「裏側」「器」を役割の

  費用が黙って発生しない約束 (§3)、モデル指定を役割の一元表に載せて設定ミスを
  見える化 (§2C)、公式キーを第三者の宛先へ流さない (§2B)、例外名の別名を
  残さない (§5)、費用の帰属を 3 種すべてで考える (§4)、共通語の射程の限定 (§1)。
