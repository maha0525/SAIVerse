# サーバーの動作中に見つけた警告を、画面の右下に閉じるまで残す

ステータス: 設計中 (2026-11-19 起草。形はまはーが同日に決めた — 下の「まはーが決めたこと」。それ以外はメティスの設計)

## 要点

サーバーが動いている間に見つけた警告やエラーのうち、どの部屋にも結びつかないものを、画面の右下に出す。ユーザーが閉じるまで残し、ブラウザを開いていない間に起きた分も、サーバーを再起動した後も消さない。今サーバーから右下に出していて 5 秒で消えている警告も、ここに移す。ペルソナには届かない。

## 背景

[no_utterance_error_notice.md](no_utterance_error_notice.md) (エラーで発言が生まれなかった回を部屋の記録に残す設計) を詰める中で、部屋に書けない失敗が残った。スケジュールや外部イベントの対象のペルソナが見つからない回、ペルソナの現在地が無い回で、どの部屋の記録にも書けない。

今の画面には、知らせの出し方がいくつもある (2026-11-19 にコードで確認)。

| 出し方 | 中身 | 消え方 |
|---|---|---|
| 上部のお知らせのバナー (`SystemAlertBanner`、`GET /api/system/alerts`、`manager.startup_alerts`) | 起動時の処理で作られる知らせ。アドオンの環境が壊れている、旧ログが読めない、といった続いている状態のほか、「記憶の移行が済みました」のような一回きりの出来事も載る。動作中に中身を差し替える箇所もある (`saiverse/system_notice_review.py`) | 閉じると、その起動のあいだは閉じたまま (閉じた記録はメモリにだけ置く)。次の起動で作り直される |
| 上部のモデル設定の警告のバナー (`startupWarningBanner`、`GET /api/config/startup-warnings`) | ペルソナが話せないモデル設定の警告 ([persona_model_selection.md](persona_model_selection.md) の決まったこと 8) | ページを開くたびに今の設定から作る |
| 右下の数秒で消える知らせ (`frontend/src/app/page.tsx` の `toasts`) | 画面の操作の結果 (「更新が終わりました」、更新の開始の失敗など)。**サーバーからの警告も来ている** — 「記憶の保存に失敗しました。会話内容が記録されていない可能性があります。」(`memorize_failed`、`sea/runtime_llm.py:1548`・`sea/runtime_engine.py:447`・`:607`)、記憶の整理を見送った知らせ (`chronicle_skipped`、`sea/session_lifecycle.py:6489`)、許可の確認が時間切れになった知らせ (`permission_timeout`、`sea/runtime.py:1340`) | 5・8・15 秒で消える。サーバーからの警告は、チャットの返事を少しずつ送る通信 (1 行ずつデータを送る NDJSON 形式) で届くので、そのとき画面を見ていた人にしか届かない |
| チャット欄の警告 (`isWarning`) | 上のチャットの返事の通信で届く警告のうち、右下に出さないもの | 次の操作で消える (`clearTransientNotices`) |
| チャット欄のエラー表示 | 返事が失敗したときの案内 (再送ボタンへの案内つき) | 次の操作で消える |
| お知らせのベル (`/api/system/announcements`) | 配布元が出すお知らせ | ユーザーが既読にする |

この中で、「サーバーが動いている間に見つけた、部屋に結びつかない警告を、見ていない人にも後で必ず届ける」出し方は無い。右下のサーバーからの警告は、読んでいない可能性が普通にあるのに 5 秒で消える。これは 2026-08-26 のまはーの判断 ([user_utterance_path_failure_inventory.md](../issues/archive/user_utterance_path_failure_inventory.md) の「画面の案内に寿命が無かった」の節 — 「時間経過で消えたりしたらさすがに問題だけど (読んでない可能性が普通にあるから)」) に当たる。

## まはーが決めたこと (2026-11-19)

- 「こういう既に起動したサーバーの中で不意に起きる、部屋が確定していない警告やエラーをどう表示すべきか。個人的には、画面右下とかに出せる仕組みが要るんじゃないかと思ってる。」
- メティスの最初の案に「その案で」。ただしその案は、既存の仕組みの説明を三つ間違えていた (右下の知らせはサーバーからは出ていない / 上部のバナーは起動時の状態だけ / 出し方は三つ)。
- 正しい説明で組み直した案に「その案で」。組み直した案の中身は次の四つ。
  1. 右下に、閉じるまで残る知らせを出す。
  2. サーバーが右下に出している 5 秒で消える警告 (`memorize_failed`・`chronicle_skipped`・`permission_timeout`) も、閉じるまで残る知らせに移す。ユーザー自身の操作の確認だけが数秒で消える。
  3. 上部のお知らせのバナーとの分け目は「いつ見つけたか」。起動時の確認で見つけたものは上部、動いている間に見つけたものは右下。
  4. 同じ原因の知らせはまとめて、回数と最後に起きた時刻を出す。

## この設計で保証すること

1. **サーバーが動いている間に見つけた、部屋に結びつかない警告は、画面の右下に出て、ユーザーが閉じるまで残る。** 時間では消えない。
2. **起きた瞬間に出る。ブラウザを開いていなかった間や、接続が切れていた間に起きた分は、次に開いたとき・繋ぎ直したときに出る。**
3. **サーバーを再起動しても消えない。** 閉じるまでは残る。
4. **閉じた知らせは、そのとき開いている別のタブからも消え、どのブラウザで開き直しても出ない。**
5. **同じ原因の知らせは一枚にまとまり、回数と最後に起きた時刻が出る。** 本文と詳細は、最後に起きたときの内容に書き換える。閉じた後にまた起きたら、新しい一枚として出る。閉じた後の発生は、ユーザーにとって新しい出来事だから。
6. **右下の数秒で消える知らせは、ユーザー自身の操作の確認だけになる。** サーバーから来る警告は、全部閉じるまで残る側に移る。
7. **ペルソナには届かない。** 画面だけの知らせで、部屋の記録にもペルソナの記憶にも書かない。
8. **文は画面の言語に合わせて出る。** 文面は画面の文言の表 (`frontend/src/i18n/messages.json`) に置き、サーバーはキーと値だけを送る (`api/ui_messages.py` の `ui_message`)。

### 出力例

ペルソナの現在地が無くて、エリスの 9:00 のスケジュールを実行できなかった回 (文面は原案):

> ⚠ スケジュールを実行できませんでした
> エリスの 9:00 のスケジュールは、エリスの現在地が分からないため、実行されませんでした。
> 3 回目 (最後: 11/21 9:00) [閉じる]

ここで言う「一回」は、一回分の予定 (9:00 のスケジュールの、その日の分) について、自動の再試行をすべて終えて実行を打ち切った時点で数える。毎日 9:00 のスケジュールなら、一日に一回までしか増えない。

## 全体の流れ

```
どこかの処理で、部屋に結びつかない警告を見つける
  → post_runtime_alert(key, level, title, message, details)   ← 新しく作る関数
      → DB の runtime_alerts の表へ書く
         (同じ識別キーでまだ閉じていない行があれば、回数・最後の時刻・本文・詳細を更新する)
      → 常時接続 (/api/addon/events) で、繋がっている全ブラウザへ送る
  → 画面
      ├─ 開いている: 常時接続で受け取り、右下に出す (同じ知らせなら書き換える)
      └─ 開いていなかった / 接続が切れていた:
           開いたとき・繋ぎ直したときに GET /api/system/runtime-alerts で一覧を取り、右下に出す
  → ユーザーが閉じる → POST /api/system/runtime-alerts/{id}/dismiss
      → 閉じた時刻を DB に書く → 常時接続で「閉じた」を送り、ほかのタブからも消す
```

## 仕組み

- **保存**: DB の表を一つ足す (`runtime_alerts`。列は、知らせの番号・まとめるための識別キー (`key`)・重要度 (`warning` / `error`)・見出し・本文・詳細・回数・最初に起きた時刻・最後に起きた時刻・閉じた時刻)。表の定義は `database/models.py` に足し、DB の構造を変える処理は `database/migrate.py` に足して、DB のコピーで試してから当てる。見出しと本文は `ui_message` の形 (文言のキーと値) で保存する。閉じるまで残る以上、アップデートをまたいで古い行が残るので、**この表で使う文言のキーは後から名前を変えない**。
- **書き込み**: `saiverse/runtime_alerts.py` (新しく作る) の `post_runtime_alert` を、どのスレッド (並行して動く処理の流れ) からでも呼べるようにする。スケジュールの処理や処理待ちの列から走る実行は、Web の処理と同じスレッドでは動いていないため。識別キーには「何が・どの対象で・どんな原因で」起きたかを入れる (例: `schedule_unrunnable:2:no_location` — スケジュール 2 が、現在地が無いために走れない)。同じ識別キーでまだ閉じていない行があれば、新しい行を作らずに、回数・最後の時刻・本文・詳細を更新する。
- **常時接続**: サーバーからブラウザへ即座に知らせを送る、つなぎっぱなしの接続 `/api/addon/events` (`saiverse/addon_events.py`) を使う。今はアドオンの知らせ (`type: "addon_event"`) だけを送るのに使われている。ここに `type: "runtime_alert"` (知らせが出た・更新された・閉じられた) も載せる。画面側の受信処理 (`frontend/src/hooks/useAddonEvents.ts`) は今 `addon_event` だけを通しているので、`runtime_alert` を別の処理へ分けて渡す (アドオンの処理 `dispatchClientActions` には流さない)。見出しや本文は `title`・`message` の項目に置く — 画面側で文言のキーを表示用の文へ変換する処理 (`frontend/src/i18n/api.ts` の `decodeUIMessages`) は、`content` と `metadata` の中を変換の対象にしないため。URL はアドオンが使っているので変えない。
  - ブラウザが繋がっていない間に送られた知らせは、この接続では保持されず届かない (`emit_addon_event` は受け手がいなければ何も送らない)。取りこぼした分は、開いたときと繋ぎ直したときの一覧の取得で補う。
  - [building_memory_unified.md](building_memory_unified.md) には「`addon_events` SSE は別目的で、汎用的なクライアントへの push 基盤は別の設計書で扱う」と書かれている (ここでの SSE・push 基盤は、この節で言う常時接続と同じ仕組みを指す)。この設計書が、その「別の設計書」にあたる。あちらの文と、`saiverse/addon_events.py` の説明書き (アドオン専用と書かれている) と、`docs/overview/landscape.md` を同じ変更で直す。
- **API**: `GET /api/system/runtime-alerts` (閉じていない知らせの一覧) と `POST /api/system/runtime-alerts/{id}/dismiss` (閉じる) を `api/routes/system.py` に足す。API と DB の定義を足したら、自動生成のリファレンス (`docs/reference/api-endpoints.md`・`docs/reference/database-schema.md`) を作り直す (`gen_reference_docs.bat`)。
- **画面**: `frontend/src/app/page.tsx` の右下の通知の表示エリア (`toastContainer`) に、閉じるまで残る知らせを並べる。数秒で消える知らせと違い、見出し・重要度・回数と最後の時刻・閉じるボタンを持つ。ダークモードとライトモードの両方の色を用意する。
- **今の 5 秒で消えるサーバーの警告の移し替え**: `memorize_failed`・`chronicle_skipped`・`permission_timeout` を送っている箇所 (上の表) は、チャットの返事の通信 (NDJSON) に `{"type": "warning", "display": "toast"}` を載せるのをやめて、`post_runtime_alert` を呼ぶ形に変える。画面の側で `display === 'toast'` を 5 秒で消える知らせにしている分岐 (`frontend/src/app/page.tsx` の 2843-2849 行付近) は、送り手がいなくなるので消す。

### 上部のお知らせのバナーの仕組みを広げない理由

上部のお知らせのバナー (`manager.startup_alerts`) に、保存と常時接続を足して使う案もある。採らないのは、二つの知らせの作られ方が違うから。上部のバナーの知らせは、起動のたびに起動時の処理が作り直す (状態が続いていれば同じ知らせがまた作られる)。これを DB に保存すると、起動のたびに作り直す分と保存した分が重なる。動作中に見つけた知らせは、一度しか作られないので保存が要る。作られ方が違うものを同じ DB の表に混ぜると、どちらの規則で消すのかが行ごとに変わる。

## 最初の適用対象と、ほかの使い道

- **最初の適用対象**: [no_utterance_error_notice.md](no_utterance_error_notice.md) の、書く部屋が決まらない失敗 — スケジュールや外部イベントの対象のペルソナが見つからない回、現在地が無い回 (`saiverse/schedule_manager.py:1159-1167`)、ユーザーがチャットから話しかけた経路で会話を始める前提 (ペルソナ・建物・返事を作る処理を起こす関数 `run_sea_user`) が揃わない回 (`saiverse/user_conversation.py:702-728`)。
- **移し替え**: 今 5 秒で消えているサーバーの警告三種類 (上の表)。
- **ほかの使い道の候補** (それぞれ今どう見えているかを確かめてから、別の改修で載せる): 裏で走る記憶の整理が詰まって進まない ([llm_retry_stacking_stalls_jobs_silently.md](../issues/llm_retry_stacking_stalls_jobs_silently.md))、外部のサイトの新着記事 (RSS などのフィード) の取得が失敗し続ける、アドオンの機能を提供するために裏で動いている別のプログラム (MCP サーバー) が停止する。

## 見つけたが、この設計では扱わないこと

- 上部のバナーが二本ある (お知らせのバナーと、モデル設定の警告のバナー)。どちらも起動時やページを開いたときに作る知らせで、作り方と閉じ方が違う。まとめるかどうかは別に考える。

## 検証の道筋

- 本番と分けたテスト環境 (SAIVerse のデータを置くフォルダを設定 `SAIVERSE_HOME` で専用のものに替え、テスト用のペルソナを置いた環境) の画面をメティスが開き、次を確かめる。
  1. 画面を開いたまま知らせを起こすと、右下にすぐ出る。
  2. 画面を閉じて知らせを起こし、開き直すと出る。サーバーを止めて起動し直しても出る。
  3. 二つのタブで開いておき、片方で閉じると、もう片方からも消える。開き直しても出ない。
  4. 同じ知らせを 3 回起こすと、一枚のまま「3 回目」になり、本文が最後の内容になる。閉じた後にもう一度起こすと、新しい一枚が出る。
  5. 記憶の保存の失敗 (`memorize_failed`) を起こすと、5 秒で消えずに、右下に閉じるまで残る。画面を見ていなかった回も、後で開くと出る。
  6. ライトモードとダークモードの両方で読める。
- 本番のペルソナでは確かめない。
