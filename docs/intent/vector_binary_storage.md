# 記憶の検索用のベクトルの保存形式を変える

**ステータス: 設計中 (2026-11-21 下書き作成。保存済みのデータを「更新したあとの最初の起動で、起動を待たせて変換する」ことは、まはーの判断待ち)**

## これは何か

SAIVerse では記憶を検索するために、文章を数値の列 (ベクトル) に変換して保存し、検索のときに「意味が近いか」を比べている。このベクトルは、各ペルソナの `memory.db` に JSON の文字列 (`[0.0123, -0.0456, …]`) として保存されている。検索のたびに、保存してある全行を JSON の文字列から数値へ変換し直している。

会話のたびに実行される自動想起 (今の話題に関係する記憶を探して、ペルソナへ送るコンテキストに足す機能) でも、この検索が行われる。そのため、記憶が多いペルソナほど、返事が始まるまでの待ち時間と、そのときに使うメモリが大きくなる。

この変更では、ベクトルを、32 ビットの浮動小数点数をそのまま並べたバイト列として保存する形式に変える。この文書では、今の形式を「JSON 形式」、新しい形式を「バイト列形式」と書く。

利用者から見える変化は三つある。

- 返事が始まるまでの待ち時間が短くなる。
- 返事の前に一時的に使うメモリが小さくなる。
- 更新したあとの最初の起動が、一度だけ長くなる (保存済みのベクトルを変換するため。まはーの判断待ち)。

検索で見つかる記憶の内容は変わらない。`memory.db` のファイルの大きさは、この変更では変わらない (「採らなかった案」のファイルの詰め直しを参照)。

## 測定 (2026-11-21)

開発者のペルソナの一つでは、`message_embeddings` (メッセージのベクトルの表) が 45,503 行あり、ベクトルの文字列の合計は 776 MB だった (`memory.db` 全体は 959 MB)。同じ行数・同じ次元 (768) の作り物の `memory.db` を作り、次のように測った。この文書が、これらの数字の元の記録になる。

| 測ったもの | 所要時間 | プロセスのメモリの最大値 |
|---|---|---|
| 今の読み方 (全行を読み込んでから `json.loads` で変換する) | 9.4 秒 + 類似度の計算 0.7 秒 | 2,339 MB |
| バイト列形式で保存した表を、一行ずつ読んで変換する | 0.19 秒 + 類似度の計算 0.002 秒 | 181 MB |
| JSON 形式のまま、一行ずつ読んで変換する (採らなかった案) | 7.6 秒 + 類似度の計算 0.002 秒 | 180 MB |
| 保存済みの行を、JSON 形式からバイト列形式へ書き換える (一度だけ) | 12 秒 | 111 MB |

- JSON 形式からバイト列形式へ書き換えた前後で、先頭 2,000 行の値は完全に一致した。
- 書き換えたあとの表で「JSON 形式の行が残っているか」を調べる検索は、0.11 秒だった。
- 書き換えたあと、ファイルを詰め直さない状態でも、読み込みは 0.19 秒だった。
- 測ったのは 1 台 (開発者の PC) で、ファイルを作った直後の状態 (ディスクから読み直さなくて済む状態)。ディスクから読む場合は、これより長くかかる。
- 開発者のペルソナの実際の会話のログでは、コンテキストの組み立てに 37 秒かかった回があった。内訳は、前半が 12 秒、記憶の検索の区間が 23 秒。自動想起のキーワードを数える検索 (候補の語ごとに `messages` の全行を調べる) は、同じ `memory.db` で 1 語あたり 0.04 秒で、前半の 12 秒の原因ではなかった。

この読み込みの重さは、[EmbeddingGemma 2 への移行](embedding_gemma2_migration.md) でベクトルが 384 次元から 768 次元になったときに、およそ倍になった。その移行の設計では、読み直しの高速化を「範囲外 (次の段)」としていた。メモリが 2 GB の仮想専用サーバー (VPS) で SAIVerse を動かしている利用者が複数いることも、同じ文書に記録がある。

## この変更で守りたいことと、関わる処理の流れ

- **利用者**にとっては、ペルソナの記憶が増えても、返事までの待ち時間が記憶の量に比例して伸びないことと、返事の前に PC が固まらないことが必要になる。また、更新で記憶が失われないことと、変換の途中で PC が止まっても壊れないことが必要になる。
- **ペルソナ**にとっては、変更の前後で同じ記憶が同じように思い出されることが必要になる。この変更で変わるのは保存形式だけで、記憶の原文にも、どの記憶が選ばれるかにも触れない。
- **開発者**にとっては、ベクトルの保存形式を扱う箇所が一箇所だけであることが必要になる。

ベクトルが作られてから使われるまでの経路は、次のとおり ([調査資料](../handoff/2026-10-12_embedding_consumer_survey.md) に、2026-10-12 時点の各経路のファイルと行がある)。

1. **作る**: メッセージの保存・編集、会話ログの取り込み、Chronicle・Memopedia のページ・Fragment (Memopedia のページに付く、知識の最小単位) のベクトルのまとめての生成、再計算。
2. **保存する**: `memory.db` の 4 つの表 (`message_embeddings`・`arasuji_embeddings`・`memopedia_embeddings`・`memopedia_fragment_embeddings`) と、旧形式の表 `embeddings`。
3. **読む**: 自動想起や記憶の検索画面から呼ばれる `unified_recall`、記憶を探すツールなどから呼ばれる `semantic_recall_groups` と `semantic_recall`、自動想起で記憶の元の会話を抜き出す処理 (`_vivid_source_messages`)。
4. **検査して作り直す**: 文章をベクトルに変換するモデル (埋め込みモデル) が変わったときの検査と再計算 (`sai_memory/embedding_migration.py`)。
5. **持ち出す**: ペルソナまるごとパックと Native エクスポート (会話のスレッドを、付随する情報ごと SAIVerse 独自の形式のファイルへ書き出す機能。取り込みの画面では「Native (SAIVerse)」という名前で出ている形式) の出力データには、ベクトルを含めない (取り込んだ側で作り直す)。そのため、この変更は持ち出しの形式に影響しない。

## 守るべき条件

1. **保存される値は、変換の前後で同じ。** 埋め込みモデルが出力する値は 32 ビットの浮動小数点数で、JSON 形式にはその値が正確に書かれている。バイト列形式にも同じ値をそのまま入れる。
2. **記憶の原文には触れない。** 書き換えるのはベクトルの列だけ。
3. **変換が途中で止まっても、記憶は失われず、会話と記憶の保存は続く。** 残りは次の起動で変換する。まだ変換されていない行は、変換されるまで記憶の検索の対象から外れる。
4. **ベクトルの保存形式を扱う箇所は一箇所だけ。** ベクトルを保存用の値に変える処理と、保存された値をベクトルに戻す処理は、一つのモジュールに置く。ほかの箇所では、保存用の値を直接組み立てたり読み解いたりしない。
5. **「空のベクトル行」の仕組みは変えない。** ベクトルをまだ作っていないメッセージの印として `[]` という文字列を入れる仕組み (`storage.DEFERRED_VECTOR`。「空のベクトル行」は [EmbeddingGemma 2 への移行](embedding_gemma2_migration.md) の §2 の呼び名) は、今のまま残す。
6. **外部ライブラリを増やさない。** 使うのは導入済みの NumPy だけ。

この変更より前のバージョンが、変換のあとの `memory.db` を読めることは、条件に入れない (「採らなかった案」と「経緯」を参照)。

## 設計

### 1. 保存形式

- `vector` 列に、32 ビットの浮動小数点数 (リトルエンディアン) を並べたバイト列を入れる。768 次元で 3,072 バイトになる (JSON 形式は約 17,000 文字)。
- 表の定義は変えない。`vector` 列は `TEXT` と宣言されているが、SQLite は値ごとに型を持つので、同じ列にバイト列 (`BLOB`) を入れられる。測定でも、`TEXT` と宣言した列にバイト列を入れて読めることを確かめた。
- バイト列形式か JSON 形式かは、値の型 (`typeof(vector)`) で見分ける。次元は、バイト列の長さを 4 で割って求める。
- 空のベクトル行は、今までどおり文字列の `[]` のままにする。
- 対象は 4 つの表すべて。メッセージ以外の 3 つの表は小さい (開発者のペルソナで合計 91 MB) が、保存形式を一つに揃えるために一緒に変える。

### 2. 読み書きを一つのモジュールに置く

新しいモジュール `sai_memory/vector_codec.py` に、三つの関数を置く。

- ベクトルを保存用のバイト列に変える関数。
- 保存された値をベクトルに戻す関数。バイト列形式の値だけをベクトルに戻す。空のベクトル行、JSON 形式の値、読み解けない値は「ベクトル無し」として返す。
- 保存された値の次元を返す関数。

`vector` 列の値を直接組み立てたり読み解いたりしている箇所は、テスト以外では次の 5 つのファイルにある (2026-11-21 に検索して確かめた)。この 5 つを、上の関数を使う形に直す。ほかのファイル (`saiverse_memory/adapter.py`、`api/routes/people/`、`scripts/` など) は、この 5 つのファイルの関数を呼んでいるだけなので、直さなくてよい。

- `sai_memory/memory/storage.py` (メッセージのベクトルの書き込みと、`get_embeddings_for_scope`)
- `sai_memory/memory/recall.py` (`semantic_recall` と `semantic_recall_groups`)
- `sai_memory/unified_recall.py` (Chronicle・ページ・Fragment のベクトルの書き込みと、4 つの表の読み込み)
- `sai_memory/embedding_migration.py` (検査と再計算)
- `sea/auto_recall.py` (`_vivid_source_messages`)

値を読み解けなかったときの扱いは、今は経路ごとに違う (検索では行を飛ばす経路と例外になる経路があり、検査では「古いベクトル」として数える)。この変更で、検索ではどの経路でも行を飛ばし、検査では「古いベクトル」として数える、に揃える。値を読み解けなかったことが原因で、`memory.db` を開く処理が失敗することは無いようにする。

### 3. 検索の読み方

- `unified_recall` の 4 つの読み込みと、`get_embeddings_for_scope` は、「行の ID の列」と「全行のベクトルを並べた NumPy の二次元配列」を返す形に変える。読み込みは一行ずつ行い、全行ぶんの文字列や Python のリストを同時にメモリに持たない。
- `unified_recall` と `semantic_recall`・`semantic_recall_groups` では、類似度を、二次元配列の全行に対して一度に計算する。計算の精度は今と同じ 32 ビットで、計算の順序が変わることによる丸めの差 (100 万分の 1 未満) だけが出る。
- `_vivid_source_messages` での類似度の計算は、今のまま (Python の数値での計算) にする。読み込む行が少なく、速くする必要が無いため。
- メッセージの本文は、類似度で上位に残った行のぶんだけ、あとから読む。今は、類似度の計算に使わない本文を、ベクトルの全行ぶん一緒に読んでいる。
- 検索の対象を絞る条件 (実際の会話だけを対象にする条件、除外する ID、次元が合わない行を飛ばす扱い) と、返す結果の形は、今と同じにする。
- 読み込んだ配列を、次の検索のためにメモリに持ち続けることはしない。毎回読んでも 0.19 秒で、持ち続けると、メッセージの追加・編集・削除のたびに配列を合わせ直す仕組みが要るため。

### 4. 保存済みのデータの変換

- **どこで**: ペルソナを起動するときに `memory.db` を開く経路 (`persona/bootstrap.py` の `initialise_memory_adapter`) でだけ変換する。ツールや API から一時的に `memory.db` を開く経路では変換しない。起動時のバックアップと、中断したスレッドの復旧を行う処理と同じ経路になる。
- **順番**: `memory.db` を開く → 変換する → 起動時の検査 (古いベクトルが無いかを調べる既存の検査) → 起動時のバックアップを始める。変換は、検査とバックアップより前に済ませる。変換する前の状態は、前回までの起動で取ったバックアップに残っている。
- **どう変換するか**: 4 つの表から、JSON 形式で、空のベクトル行ではない行を 1,000 行ずつ読み、バイト列形式に書き換えて確定する。これを、残りが無くなるまで繰り返す。書き込みは、ベクトルを書くほかの経路と同じロック (`sai_memory/db_locks.py` の `immediate_transaction`) の中で行い、書き換えるのは「その行がまだ JSON 形式のとき」に限る。
- **変換できない行**: 一つのベクトルとして読めない行 (壊れた値と、一行に複数のベクトルを配列で入れた旧形式の行) は、書き換えずに残す。これらは今の検査でも「古いベクトル」として扱われていて、再計算で作り直される。
- **旧形式の表 `embeddings`**: `memory.db` を開くたびに、この表の行を `message_embeddings` へ写す処理がある。写された行は JSON 形式なので、上の変換の対象に入る。変換が済んだら、旧形式の表の行を消す。消さないと、あとから開いたときに JSON 形式の行がまた写されるため。
- **途中で止まったとき**: 確定済みの行はバイト列形式で、残りは JSON 形式で残る。残りの行は、次の起動で変換されるまで、記憶の検索の対象から外れる。変換がどこまで進んだかの記録は持たない。次の起動で、JSON 形式の行が残っているかを表から調べる (変換済みの 4.5 万行の表で 0.11 秒)。
- **再計算との関係**: 記憶の管理画面や起動時の警告から実行する再計算でも、最初にこの変換を実行する。変換が済んでいない行を、時間のかかる再計算で作り直さないため。この変換では、埋め込みモデルの記録 (`embed_metadata.embed_model`) と、再計算の途中であることを示す記録 (`embed_metadata.embed_migration_in_progress`) を書き換えない。
- **表示**: 変換の間は、どのペルソナの何行を変換しているかを、ログとコンソールに出す。

### 5. 検査と再計算の処理を新しい形式に合わせる

`sai_memory/embedding_migration.py` では、保存されたベクトルの長さをもとに、古い埋め込みモデルのベクトルかどうかを判定している。この長さの取得を、§2 の「次元を返す関数」に置き換える。再計算で書くベクトルはバイト列形式になる。判定の規則は、次の一点を除いて変えない。JSON 形式の行 (空のベクトル行を除く) は、次元に関わらず「古いベクトル」として数える。

### 6. コンテキストの組み立ての所要時間をログに残す

`sea/runtime_context.py` の `prepare_context` (ペルソナへ送るコンテキストを組み立てる処理) の各段階 — 人格と固定の記憶の部分、会話の履歴、リアルタイム情報、自動想起 (候補の収集と反射判断) — にかかった時間を、INFO のログに一行で出す。

これは、この変更の効果を確かめるための計測 (「検証」の 5 と 7) として入れる。今のログでは、コンテキストの組み立てのどこに時間がかかったかが読めない。開発者の環境の 37 秒のうち前半の 12 秒が何の処理なのかも、このログで特定する。

## この変更が済んでも残ること

- **開発者の環境の 37 秒のうち、この変更で縮むと測定から言えるのは、ベクトルの読み込みの約 10 秒ぶん。** 記憶の検索の区間 (23 秒) の残りと、前半の 12 秒は、まだ特定できていない。§6 のログを入れたあとに、開発者の環境のログで特定する。
- **報告のあった利用者の環境でバックエンドが応答しなくなる理由が、メモリ不足かどうかは未確認。** [不具合の記録](../issues/chat_stream_cut_and_relay_500_on_backend_stall.md) で追っている。この変更で、返事の前に 2 GB を超えるメモリを一度に使うことは無くなる。
- **`memory.db` のファイルは小さくならない。** 書き換えで空いた領域はファイルの中に残り、そのあとの記憶の保存で再利用される。
- **変換のあとの `memory.db` は、この変更より前のバージョンでは正しく読めない。** 前のバージョンのコードにバイト列形式の値を読ませると、`sai_memory/embedding_migration.py` の `is_stale_vector` で `UnicodeDecodeError` が起きた (2026-11-21 に、変更前のコードで確かめた)。前のバージョンへ戻すことは支えない。この変更に問題が見つかったときは、バイト列形式を読める新しいバージョンで直す。

## 検証

1. **読み書きの関数**: ベクトルを保存用のバイト列に変えて戻すと、元の値に一致すること。空のベクトル行、JSON 形式の値、読み解けない値が「ベクトル無し」になること。
2. **検索の結果が変わらないこと**: 同じ作り物のデータに対して、変更前の検索と変更後の検索が、同じ ID を同じ順番で返し、類似度の差が 100 万分の 1 未満であること。
3. **変換**: JSON 形式だけの `memory.db`、両方の形式が混ざった `memory.db`、変換の途中で止めた `memory.db` を、ペルソナの起動の経路で開くと、変換できる行が全部バイト列形式になり、値が一致し、空のベクトル行と変換できない行と記憶の原文 (全行のハッシュ) が変わらないこと。変換のあとに、旧形式の表が空になること。
4. **順番と同時書き込み**: 変換が、起動時の検査とバックアップの開始より前に済むこと。変換の途中で別の接続からメッセージを保存しても、保存したベクトルが失われないこと。
5. **本番と分けたテスト環境での通し確認** (本番と別の `SAIVERSE_HOME`、テスト用の架空のペルソナ、テスト用のダミーの LLM): 4.5 万行のベクトルを持つ `memory.db` で起動して変換の所要時間を測り、会話一回のコンテキストの組み立ての時間 (§6 のログ) とプロセスのメモリの最大値を、変更の前後で比べる。
6. **検査と再計算**: 古い次元のベクトルをバイト列形式で混ぜた `memory.db` と、JSON 形式の行が残った `memory.db` と、読み解けない値が入った `memory.db` で、`memory.db` を開く処理が失敗せず、起動時の警告と再計算が動き、再計算のあとに全行がバイト列形式になること。
7. **まはーの本番環境での更新一回** (まはーの操作): 変換の所要時間と、返事が始まるまでの時間。

確かめられないもの。

- 報告のあった利用者の PC で停止が無くなるか。この変更を含むバージョンが出て、利用者が更新したあとに分かる。
- メモリが 2 GB の VPS での動作。開発者の手元に同じ環境が無い。リリースのあとに、VPS で動かしている利用者に、変換の所要時間と返事までの時間を尋ねる。

## 採らなかった案

- **前のバージョンのコードでも読めるように、バイト列を Base64 (バイト列を英数字の文字列で表す標準の方式) の文字列にして保存する。** 前のバージョンのコードは、Base64 の文字列を「古いベクトル」と判定するだけで、エラーにならない。代わりに、読み込みは 0.60 秒 (バイト列形式は 0.19 秒) になる。新しいデータを古いコードが読めることを条件にすると、この先のデータの変更のたびに同じ条件を守り続けることになり、守り切れない。そのため、この条件ごと採らない。
- **変換のあとに、ファイルを詰め直す (`VACUUM`)。** ファイルは 801 MB から 211 MB になり、1.7 秒で済んだ。しかし SQLite の公式の文書は、`VACUUM` で行の番号 (`rowid`) が変わりうるとしている。SAIVerse は、メッセージの `rowid` を、同じ時刻のメッセージの順番を決めるために使い、ほかの表に保存もしている (`sai_memory/perception_buffer.py` の `boundary_rowid`、`api/routes/people/memopedia.py` の `last_message_rowid`)。ペルソナの記憶の並び順を危険にさらしてまで、ファイルを小さくはしない。
- **JSON 形式のまま、一行ずつ読んで変換する。** メモリの最大値は同じだけ下がるが、所要時間は 9.4 秒から 7.6 秒にしかならない。
- **読む側で JSON 形式とバイト列形式の両方を読めるようにして、変換を裏で進める。** 起動を待たせずに済むが、二つの形式を読む処理がずっと残る。変換は 4.5 万行で 12 秒ほどなので、起動のときに済ませる。
- **読み込んだベクトルをメモリに持ち続ける。** 二回目からの読み込みは要らなくなるが、メッセージの追加・編集・削除のたびに、メモリの中身を合わせ直す仕組みが要る。毎回読んでも 0.19 秒なので、採らない。
- **全行と比べるのをやめ、近いものだけを探す索引を作る。** 全行と比べる計算は 4.5 万行で 0.002 秒なので、要らない。
- **検索の対象を最近の記憶に絞る。** ペルソナが思い出せる範囲が変わるので、採らない。
