## 1. 目的 — ユーザーが頼れるようになること

1. **ペルソナ一体の全データを、一つの ZIP として持ち出せる。** 中身は人間が読める JSON ファイルと、画像・添付ファイルそのもので、特定のソフトが無くても開いて読める。
2. **その ZIP を別の環境（新しい PC の SAIVerse、SAIVerse Lite）に取り込めば、同じ子が記憶ごと続きから生きられる。**
3. **他のチャットアプリへも会話を持ち込める。** ZIP 内に ChatGPT のエクスポート形式と互換のコピーを同梱する。

旧来のスレッド単位エクスポートは、`thought_signature`（LLM が返す思考の署名。bytes のまま保存されている）を含むスレッドで JSON 化に失敗して壊れている。修理せず、本機能で置き換える。

## 2. 全体の流れ

```
書き出し元                形式                         取り込み先
────────────            ─────────────                ────────────
本体のエクスポート API →  ZIP (manifest + JSON 群     → 本体のインポート（新規 / 合流）
SAIVerse Lite             + 添付ファイル・画像など)    → SAIVerse Lite
                                                      → 他アプリ（chatgpt_compat/ 経由）
                                                      → 人間（手で開いて読む・確認する）
```

- エクスポートは**読み取り専用の操作**。実行してもペルソナの状態は一切変わらない。
- Lite 側の対応は `saiverse_lite.md` §5 の決まり（形式仕様を docs/reference/ に文書化し、変更は両側同時に更新）に従って別途設計する。Lite が扱わないデータ（extensions/ の中身など）は、Lite が再エクスポートするまで**素通しで保持**し、Lite 経由の往復で黙って欠けさせない。Lite 側の記録 ID が UUID かどうかの確認も Lite 側の作業に含める。

## 3. 設計原則（不変条件）

1. **割り当ての漏れを許さない**: データ地図にある全項目を、実装時に「どのフォルダに入るか / 運ばない（理由つき）」のどちらかに割り当て、その確定表をこの intent に書き戻す。ZIP に入るのはその表に挙げたデータだけに限る。**認証情報（API キー・トークン類）は決して入れない。**
2. **本人名義のテキストは無改変で運ぶ。** 発話・思考・ページ本文を切り詰めたり整形したりしない。
3. **すべての記録に ID と日時を付けて書き出す。** メッセージ・Memopedia ページ・切り抜きには作成時に UUID（重複しない固有 ID）が付いているため、そのまま書き出す。手帳の行（activities / memos）は整数の連番しか持たないので、実装時に UUID 列を足す移行を行う。この ID があることで、最初から §5 の合流が可能になる。
4. **`manifest.json`（目録ファイル）に同梱フォルダの一覧を記載する。** `contents` 欄に同梱フォルダ名を列挙し、インポート側はそこにあるフォルダだけを取り込む。一部のフォルダが無い ZIP も正常に扱えるため、将来「不要なデータのチェックを外してエクスポートする」機能を作る際も、フォルダを減らすだけで形式を変えずに実現できる。
5. **データ形式のルール**: バイナリ値（`thought_signature` 等）は base64 文字列に変換する。日時はタイムゾーン付き ISO 8601 — ただし元データがタイムゾーンを持たない列（`saiverse.db` の DateTime 列）は、UTC と決めつけて書き換えず元の値のまま出す。ZIP 内のファイル参照は常に ZIP の最上位（ルート）からの相対パスで書く。`extensions/saiverse/` の機械的な書き出しは値を変換せず元のまま。JSON 文字列の列（`messages.metadata` など）を展開した値の中に、取り込みが印（`{"__bytes_b64__": ...}` / `{"__raw_text__": ...}`）と読む形の dict — キーが一つだけで、そのキーが `__bytes_b64__`・`__raw_text__`・`__escaped__` のどれか — があれば、書き出しは `{"__escaped__": <その dict>}` に包み、取り込みはそれを印として読まずに元の dict へ戻す（2026-10-17 レビュー指摘で確定 — それまでは利用者のデータの中の同じ形の dict が、往復で文字列や bytes に変わっていた）。`extensions/saiverse/` の書き出しは DB の値（文字列・数値・bytes）をそのまま書き、利用者の dict を出さないので、この包みは要らない。
6. **パックの中身を一度に全部メモリへ広げない（2026-10-17 まはー裁定）。** SAIVerse はメモリ 2 GB の VPS でも運用されており、記録の量はペルソナの寿命とともに際限なく育つ。書き出しは DB から一行ずつ読んで ZIP へ逐次書き、取り込みは ZIP の JSON を先頭から逐次読み解いてディスク上の一時 SQLite（作業用の控え）に行として積み、各工程はそこから一行ずつ取り出して処理する。取り込みの一時 SQLite は ZIP と同じフォルダに `<ZIP のファイル名>.<import_id の先頭 16 字>.work.sqlite` として作り、取り込みの終わりに成功・失敗を問わず消す（ZIP が置けた場所なら展開分の空き容量の見込みも同じ場所で立つため。ペルソナフォルダには置かない — 取り残しが次の書き出しに入り、取り込みでも復元されるため）。積む工程は取り込み先の DB への書き込みを始める前に終え（書き込み前に全部検査する約束を保つため）、取り込み先の DB とは別のファイル・別の接続にする。JSON の配列は 1 要素ずつ読むので、1 要素の大きさの上限（コードの `MAX_JSON_ELEMENT_CHARS`、64 × 1024 × 1024 文字）がメモリの上限になり、上限を超える要素を持つパックは、切り詰めずに書き込み前に断る（原則 2）。メディアのファイルも丸読みせず、分割して写しながら sha256 を計算する。ZIP の形式・フォルダ構成は変えない（この原則は読み書きの実装の話で、形式の話ではない）。一度に保持してよいのは、件数が構造的に有界な一枚物（manifest・profile・私室・active_state 等）と、処理が全体を要する中規模の表（Memopedia のページ木の判定等）だけで、メッセージ・ログ類・辺の表は常に逐次。
   - **上限は二本**（2026-10-17 ストリーミング化の仕上げで整理）: (1) 展開後の合計サイズの上限（コードの `MAX_UNCOMPRESSED_BYTES`、16 GiB。`check_uncompressed_size` が ZIP の宣言のサイズで書き込み前に検査する）はディスクと細工 ZIP への保護で、ディスクには展開されるファイルに加えて、配列の JSON と同程度の大きさの作業用 SQLite も取り込みの間だけ載る。(2) JSON の 1 要素の大きさの上限（`MAX_JSON_ELEMENT_CHARS`）はメモリへの保護で、配列でない一枚物の JSON（manifest・profile・`items/` の二つ）はファイル全体を 1 要素とみなして同じ上限を当てる（コードの `read_json_document`）。以前あった 1 ファイルの展開サイズの上限と JSON の合計の上限は、根拠だった「JSON を丸ごとメモリに読む」が無くなったので廃止した。
   - **一時ファイルの置き場は `<SAIVERSE_HOME>/tmp/`**（2026-10-17 確定）: API が受けたアップロードの ZIP と、書き出しの ZIP を作る一時フォルダは、OS の一時フォルダではなく `<SAIVERSE_HOME>/tmp/` に置く（`api/routes/people/persona_pack.py` の `_temp_root`）。Linux の配布によっては OS の一時フォルダが tmpfs（メモリ上のファイルシステム）で、最大 2 GiB のアップロードと、その隣に作られる作業用 SQLite がメモリを食うため。`tmp` はペルソナフォルダの外で、書き出しが読む範囲（ペルソナフォルダと、共有メディアフォルダ・`user_data/icons` に解決したファイル）にも入らない。**既知の限界**: プロセスが異常終了すると `<SAIVERSE_HOME>/tmp/` に残骸（アップロードの ZIP・作業用 SQLite・書き出しの一時フォルダ）が残りうる。名前は一意に作るので次の取り込み・書き出しの邪魔にはならず、害はディスクの容量だけなので、起動時の掃除は作らない。
   - **実装の現況**（2026-10-17 ストリーミング化の完了時点）: 書き出しは表を一行ずつ読んで ZIP へ逐次書く（`chatgpt_compat/` は 1 スレッドぶんずつ組み立てて書く）。取り込みは JSON を逐次読みして作業用 SQLite に積み、各工程はそこから読む。残っている保持は、件数が有界なもの（所持品・約束・スレッドの数に比例するもの等）と、本文を持たない id だけの集合・対応表で、全行を持つ保持は無い。この性質は `tests/test_persona_pack_memory.py` が、メッセージ件数だけが違う二つの世界のピークメモリを比べて機械で守る。**既知の残余**: (a) `chatgpt_compat/` の 1 スレッドぶんの会話はメモリで組み立てるので、1 スレッドの件数に比例する。SAIVerse のスレッドは部屋ごとなので、同じ部屋で長く暮らしたペルソナでは 1 スレッドが寿命の大半を占めうる（実測で 1 件あたり数 KiB）。(b) 書き出しの messages の `ORDER BY created_at` には索引が無く、SQLite の外部ソートに逃げる（その一時ファイルの置き場は OS の設定に依る）。(c) 取り込み先側の id の集合（合流時の照合など）は取り込み先の規模に比例するが、id だけ。

## 4. 同梱するデータ — ZIP に何を入れるか

方針は「**ペルソナ個人のものは全部入れる。運ばないのは、取り込み先で再生成できる派生データと、取り込み先で作り直される運用状態だけ**」。下の表は全体像で、データ地図の全項目をどこに割り当てたかの確定表は §9 にある（§3-1 の約束の履行）。

| フォルダ | 中身 | 出どころ |
|---|---|---|
| `manifest.json` | 形式名・版・生成元・作成日時・ペルソナ名・contents | — |
| `profile/` | 名前・システムプロンプト・説明文・アイコン画像・モデル設定（モデル名のみ。キーは入れない）・記憶機能の ON/OFF | `saiverse.db`（本体DB）の AI 行 + アイコンファイル |
| `chatlog/` | スレッドと全メッセージ。**messages の全列と metadata を丸ごと**運ぶ（id・時刻・role・話者・タグ・添付参照に加え、同じ秒の中の並び順の鍵 seq、コンテキストへの載せ方を決める scope、pulse_id、Stelis（本筋から切り離して進める子スレッドの仕組み）の情報なども落とさない） | `memory.db` の threads / messages |
| `knowledge/` | Memopedia 全ページ（コア記憶 = core 分類、Chronicle = chronicle 分類もページとしてここに入る） | `memory.db` の memopedia_pages |
| `attachments/` | 添付ファイルそのもの | 共有メディアフォルダのうち、このペルソナの記録が参照しているもの |
| `avatar/` `voice/` | 立ち絵・表情差分・声の設定。**v1 では空** — 実装時に確認した結果、本体に立ち絵の保存場所が無く（screen_avatar は draft）、声の設定はアドオンのペルソナ別設定（addon_persona_config = 認証情報と同じ表）に入る仕組みのため、書き出すものが無い。フォルダの席だけ規格に確保してある（§8） | — |
| `items/` | 所持品・私室（部屋とその中の配置を「持ち物」として記述） | `saiverse.db` + `memory.db` |
| `journal/` | 一日新聞 (day_reports)・手帳 (activities / memos)・約束帳 (task_book。手帳の一欄)・切り抜き (clips)・目的タグ | ペルソナフォルダ + `memory.db` |
| `extensions/saiverse/` | 共通フォルダに写していない SAIVerse 固有の残り全部。机の上 (desk_items。いま開いている記憶の参照なので持ち物ではなくこちら)、Memopedia の編集履歴、フィードの既読位置、通話の録音 (voice_calls/)、ペルソナフォルダの運用ファイルなど | `saiverse.db` + `memory.db` + ペルソナフォルダ |
| `chatgpt_compat/` | 会話の ChatGPT エクスポート互換コピー（ChatGPT 公式エクスポートの conversations.json 相当。会話のやりとりだけを写し、内心の記録や一時的な（履歴に残さない）行は含めない。他アプリ向けで、SAIVerse 側の取り込みでは無視する） | `chatlog/` からの変換 |

**運ばないもの**: 検索用のインデックスと embeddings（意味検索用の数値データ。取り込み後に再生成する）、取り込み先で作り直される運用状態（session_anchor・head_snapshot 系・execution_ledger など、§9 の一覧のとおり）。起草時は知覚バッファも「一時的な作業状態」としてここに入れていたが、これは誤りだった — `sai_memory/perception_buffer.py` の宣言どおり**消費済みの行も削除しない永続台帳（知覚の証跡）**なので、`extensions/saiverse/` で運ぶ（2026-10-17 実装時に訂正）。**建物の会話履歴 (building_messages) は運ばない** — 建物の記録は世界のもので他のペルソナの発話を含み、本人が体験した会話は本人の `memory.db` に本人の記録として既に入っているから（データ地図が「設計判断が要る」とした箇所。2026-10-16 まはー承認）。

## 5. インポート — 新規作成と合流（マージ）

取り込み時にユーザーが選ぶ: **「新しいペルソナとして迎える」**か**「既存のこのペルソナに合流させる」**か。ZIP の中の子と手元の子が同一人物かの判定は自動で行わない — 合流先を選ぶのはユーザーで、同一性の判断は人が行う。

**ID の扱いは旧エクスポートの「移植」の裁定（2026-07-16、native_export.py 冒頭）を継承する。** ペルソナ ID は `ai_stem_街のID` の形で、スレッド ID はその前に付くため、別の環境では一致しない。そこで取り込み時に、ZIP 内の全スレッド ID の前半（ペルソナ ID 部分）を取り込み先ペルソナの ID へ置き換え、元の ID は各メッセージの `metadata.transplanted_from` に由来の記録として残す。

- **新規作成**: 取り込み先の街で新しいペルソナ ID を発番する（名前の部分は ZIP のペルソナ名から。同じ ID が既にあれば番号を足す）。元の ID は上記の由来の記録に残る。新規作成は「空のペルソナへの合流」と同じ手順で動くため、処理経路は一本。
- **スレッドの合流**: ID を置き換えた後、後半（建物 ID などの部分）が一致するスレッドは同じスレッドへ混ざり、一致しないものは別スレッドとして追加される。
- **追記型の記録**（メッセージ・切り抜き・手帳の行）: UUID で照合し、まだ無いものだけを追加する。既にあるものは変更しない。一日新聞は日付名のファイルなので、同じ日付で内容が違えば**両方残す**（別々の環境で別の一日を生きた、どちらも本物の記録だから）。
- **書き換わる記録**（Memopedia ページ）: `updated_at`（最終更新時刻）を比べ、本文が違うときだけ**日時が新しい方を採用する**。Memopedia の updated_at は内容を変えない操作でも進むことがある既知の粗さがあり、まれに、本文を書き換えた側よりも、後から目印（ピン留めや状態フラグなど）だけを切り替えた側（本文は古いまま）が新しいと判定されて採用されることがある。上書きするときは、消える側の本文を取り込み先の `memopedia_page_edit_history`（編集履歴の表、edit_source = `persona_pack_import`）に先に書き残すので、採用されなかった本文も `rollback_page` で戻せる（2026-10-17 実装時に確定 — 起草時の「編集履歴は extensions/ が運ぶから失われない」は合流が extensions/ を取り込まない確定と矛盾していたため、この形に差し替えた）。
  - **上書きは親子の木を壊さない**（2026-10-17 レビュー指摘で確定）: 上書きは親（`parent_id`）も ZIP 側の値にするので、ページごとに採否を決めると、両方の環境でそれぞれ正常な木が混ざって循環することがある（例: 取り込み先が root→A→B、ZIP が root→B→A で、A だけ ZIP 側が新しいと、A の親が B になり B はスキップされて A と B が互いの親になる）。循環したページは一覧の木から消え、削除は終わらない。そこで memory.db の確定の前に、Chronicle・コア記憶・通常のページを含む全ページの親子を検査し（コードの `check_page_tree`）、親を辿って根（親の無いページ）に着かないページを探す。原因が上書きで親を変えたページなら、そのページの親だけを取り込み先の元の値に戻して警告する（本文などの上書きは残す）。それでも残る循環や無い親のうち、この取り込みで入れた・上書きしたページを含むものは、そのページを同じ分類の根の直下に置いて警告する。取り込み前から取り込み先にあった循環や無い親は書き換えず、件数だけ警告する。
- **Chronicle（chronicle 分類のページ）は、合流では「取り込み先のあらすじと重ならない枝」だけを取り込む**（2026-10-17 実装時に確定。当初は全部スキップにしていたが、相手側で生まれた新しい枝まで捨てる必要は無かったので置き換えた。実装は `importer.py` の `plan_chronicle_merge`）。id で照合して、取り込み先に同じ id がある記事は上書きしない（親子の記録を書き換えると取り込み先の木が動くため）。取り込み先に無い記事は、次の規則で取り込むかを決める:
  - **一次あらすじ（Lv1）**: 覆っているメッセージ（source_ids）が、取り込み先の一次あらすじのどれとも一つも重ならないものだけを取り込む。重なる記事は、取り込み先で吸収・差し替え済みの古い記事か、取り込み先のあらすじと同じ会話を二重に覆う記事なので入れない。これで、取り込み先で吸収・差し替えられた記事が戻ってくることも、同じ会話を二本のあらすじが覆うこと（`docs/issues/lv1_source_ids_duplicates_and_orphans.md` の既知課題）も起きない。ZIP の中に同じメッセージを覆う一次あらすじが二本あるときも、ZIP での並び順で先の一本だけを取り込む（取り込むと決めた一次あらすじの source_ids を、後に判定する記事の照合相手に加える。2026-10-17 レビュー指摘で修正）。
  - **上位のあらすじ（Lv2 以上）**: 子が全員「取り込むと決まった記事」か「どちらの環境にも無い記事」（消えた子への参照。既存の掃除 `_sweep_broken_parents` が直す）のときだけ取り込む。取り込み先にある記事を子に持つ上位は入れない — その上位を後で削除すると、子が取り込み先の木から外れて根に戻されるため。
  - **親の付け替え**: 取り込む記事の親が、取り込まない記事や取り込み先と共有の記事のときは、その親の下に付けず、根（`root_chronicle`）の直下に「まだまとめられていない記事」として置く。時間的に取り込み先の上位あらすじに収まる記事は、次のまとめの冒頭で既存の縁組（`bands.reconnect_contained_orphans`）が正規の親に付け直す。新しい縁組の仕組みは作らない。
  - **費用**: 取り込みそのものは LLM を呼ばない。根に置いた記事が増える分、次の補修でまとめ（LLM 課金）が増えることがあるが、その増加分は、全部スキップした場合に相手側の会話を一から編纂し直す費用の一部にすぎない。合流の結果画面に、次の補修で走るまとめの見込み回数（`plan_band_overflow`）と書き直し待ちの上位あらすじの件数を出し、補修を一度実行するよう案内する。
  - **合流の後処理**（`api/routes/people/persona_pack.py`）: 取り込んだ記事が覆う冷えた会話の窓に、補修の完了時と同じ関数（`mark_covered_cold_windows`）で「生ログのまま見せる」印を書く — 後で head が組み直されたとき、同じ出来事が生ログとあらすじの両方に出ないようにするため。印は冷えた行にしか書かないので、まだ温かい窓の中を覆う記事が取り込まれた場合は、次に head が撮り直されたとき同じ出来事が一時的に生ログとあらすじの両方に出うる（arasuji_levels.md §16-2 と同類の残余で、次の畳みで解消される）。合流は、あらすじの生成・補修のジョブが動いている間は断り（409）、会話や Metabolism と同じロック（Beat ロック）の内側で行う。取り込んだ記事の想起用タグの辺（chunk_page_edges）は一緒に入れ、Memopedia の断片（memopedia_fragments）は入れない（ペルソナが編集・削除する記録で、ページ本文との行き来もあり、行単位で混ぜてよいと言い切れないため）。
  - 新規取り込みでは全ページそのまま入る。
- **プロフィール（名前・システムプロンプト等）**: AI 行には更新時刻の列が無く「新しい方」を機械では決められない。取り込み時にユーザーが「プロフィールも ZIP の内容で上書きする」を選べるようにし、**既定は現状維持**とする（2026-10-16 まはー承認）。上書きを選んでも、取り込み先の環境と結びついた列（AIID・HOME_CITYID・PRIVATE_ROOM_ID・PERSONA_ROLE・IS_DISPATCHED と運用状態の列。確定の一覧はコードの `PROFILE_PROTECTED_COLUMNS`）は触らない。上書きで名前が取り込み先と同じ街（HOME_CITYID）の別ペルソナの名前と重なるときは、名前だけ今のまま保ち、警告に載せる（他の列は上書きする）。規則は通常の作成経路（`manager/persona.py` の `_create_persona`）の同名拒否と同じで、大文字小文字を区別しない（2026-10-17 レビュー指摘で確定 — それまでは同名でも上書きしていたので、`update_ai` が共有の名前の表 `persona_map` の同名の項目を取り込み先の AIID で上書きし、既存ペルソナの名前の解決が別のペルソナを返した）。アイコンと外見画像は値のコピーではなく、ファイル実体を取り込み先へ復元してその場所を指す。合流先のペルソナが読み込み済みなら、上書きした値は設定画面の保存と同じ経路（`manager.update_ai`）でサーバーのメモリ上のペルソナへ写す — 名前を変えたときは、同席者名の解決が読む共有の名前の表（`persona_map` / `id_to_name_map`）も `update_ai` が書き換える（2026-10-17 レビュー指摘で確定 — それまでは `update_ai` が改名を表へ写しておらず、設定画面の改名でも次の再起動まで同席者として旧名が出ていた）。スペル不使用モード（`SPELL_ENABLED`）が上書きで変わったときは、通常の保存と同じ切り替え（`AdminService._deliver_spell_toggle`、spell_disabled_mode.md §4-2）を `update_ai` の後に届ける。取り込みは DB を書き終えてから `update_ai` を呼ぶので `update_ai` 自身は旧値を知らず、取り込みの前に読んだ値と比べて判定する（2026-10-17 レビュー指摘で確定 — それまでは届けておらず、head が次の記憶整理か再起動まで旧いモードのままだった）。新規作成のペルソナは取り込みの時点で読み込まれていないので、起動時の head の構築が新しい値を読む。
- **短縮番号 (short_id。`m:3` のような環境ごとの連番。所持品の `item:N` は世界全体の連番で、同じ規則に従う)**: 元の番号が取り込み先の最大値より大きいときはそのまま使う（取り込み先で一度も使われたことのない番号なので、衝突も再利用もない — 空のペルソナへの新規取り込みでは全番号が無傷で残る）。それ以外は取り込み先の採番規則（最大値+1）で振り直し、元の番号は行の metadata に `original_short_id` 等として残す（切り抜きと所持品は metadata の置き場が無く、振り直すと元の番号が残らない。所持品は世界全体の連番なので、既に物のある世界へ迎えるとほぼ振り直しになる）。切り抜き（clips）の `purpose_ref` / `pasted_to` と目的タグ（purpose_tags）の `target_ref` / `purpose_ref` に入った、自分のものを指す短縮番号の参照（`memopedia:N` / `core:N` / `chronicle:N` / `clip:N`。旧 prefix と `saiverse://self/...` の形も。文法は `saiverse/references.py`）は、ZIP のその番号の行が取り込み先で持つ番号に書き換える — 振り直した行なら新しい番号、取り込み先に同じ id の行があればその行の番号。ZIP の行が取り込み先に入らなかった参照（合流の判定で取り込まなかった Chronicle・削除済みのページを指すもの）は、取り込み先で同じ番号の別の行を指しうるので、目的タグは行を入れず、切り抜きはその列を空にする（件数を警告に載せる）。重複の判定（同じ組の目的タグがあるか）は書き換えた後の値で行う（2026-10-17 レビュー指摘で確定 — それまでは元の番号のまま入れていたため、振り直しが起きると目的タグと切り抜きが取り込み先の無関係なページに結び付いていた）。所持品を指す参照（`item:N` / `saiverse://item/N`）も同じ規則で書き換える: 新規作成で登録した所持品は振り直した番号へ、登録しなかった所持品（合流では所持品を取り込まない）は、取り込み先に同じ物（同じパックで以前に登録した物、または元の ID のままの同じ物）があればその番号へ、無ければ取り込まなかった行への参照として扱う（目的タグは入れず、切り抜きの列は空にする）。所持品の番号は本体 DB 側で登録するが、目的タグと切り抜きはペルソナの memory.db 側で先に入るので、番号の決定だけを memory.db 側の取り込みより前に行い、登録の時に本体 DB の確定前の同じトランザクションの中で同じ決定をやり直して照合する — その間に取り込み先の所持品が変わっていたら、取り込み全体を巻き戻す。新規作成が途中で止まったときの印（下の「再開」）には決めた番号を残し、再開の合流はその番号が空いていればそれで登録する（2026-10-17 レビュー指摘で確定 — それまでは所持品の番号を参照の書き換えが扱わず、取り込み先に `item:1` があると、振り直された元の `item:1` を指していた目的タグが取り込み先の別の物に結び付いていた）。止まっている間に取り込み先の別の物がその番号を取っていたら別の番号で登録し、止まった回が確定させた目的タグと切り抜き（ZIP の `tag_id` / `clip_id` で特定する）の参照を、本体 DB の確定の後に登録した番号へ書き換え（コードの `repair_resumed_item_refs`）、それが確定してから印を消す — 書き換えに失敗したら印を残し、同じパックの合流がもう一度書き換える。書き換えた目的タグの組が取り込み先の別の行と同じになったら、同じ付与として書き換えた行を消す。再開の合流が memory.db 側の取り込みもやり直すときは、memory.db を確定する前に印の番号をその回の決定へ書き換え、印の番号が常に memory.db 側の参照が使う番号であるようにする（2026-10-17 レビュー指摘で確定 — それまでは別の番号で登録して警告するだけで、確定済みの参照が旧番号のまま取り込み先の別の物を指していた）。机の上（desk_items。新規作成でだけ入る）の `ref` / `purpose_ref` も同じ規則で取り込み先の番号へ書き換え、番号を振り直しうる種類の参照で対応の分からないもの（ZIP のどの行の番号でもないもの・取り込み先に入らなかった行を指すもの）を持つ行は入れずに警告する — 机が取り込み先の別のページを開くより、開いていない方がよいため（2026-10-17 レビュー指摘で確定 — それまでは完全一致の置き換えしか通らず、初期ページの採番が違う取り込み先では机が別のページを開いていた）。過去の発話の本文に埋まった短縮番号は元の環境の番号のままで、振り直しが起きた分は合流後に別のものを指しうる — 原則 2 のとおり本文の書き換えは行わないため、**既知の限界**として受け入れる。
- **削除は伝わらない**: 片方の環境で消した記録が、もう片方の ZIP から戻ってくることがある（消した印を運ばないため）。Chronicle は作り直しのときに古い行がデータベースから消去される仕組みのため、何もしないと、同じ期間に対して二つの環境それぞれのあらすじが両方残る。これは上の Chronicle の規則（覆うメッセージが取り込み先の一次あらすじと重なる記事は入れない）で防いだ（2026-10-17）。ただし取り込み先で差し替えなしに手で消した記事は、覆っていたメッセージがどのあらすじにも覆われていないので、相手側の ZIP から戻ってくる。逆向き（ZIP 側で消した記録が、取り込み先の生きている記録を消すこと）は起こさない: Memopedia ページの上書きは、ZIP 側が削除済み（is_deleted）の行を入力にせず（スキップ件数に載せる）、上書きしても取り込み先の削除の状態（is_deleted と、コア記憶の metadata の deleted_at）を変えない。合流では、取り込み先に無い ZIP の削除済みのページも足さない（新規作成は §4 のとおり削除済みの行も履歴として全部入れる）（2026-10-17 レビュー指摘で確定 — それまでは「本文が違えば新しい方」の比較が削除済みを除いておらず、元の環境で編集してから消したページが、削除済みの印ごと取り込み先の生きているページを上書きしていた）。
- **手帳の uuid は後付け前の行では環境ごとに違う**: 手帳（activities / memos）の照合に使う uuid は、列を後から足したときに既存の行へ環境ごとに別々の値を振っている。そのため、列を足す前の同じデータベースの複製を二つの環境でそれぞれ起動した場合、同じ行でも uuid が一致せず、合流すると同じ手帳の記録が二重に入ることがある（開いている同名のアクティビティと、idem_key が一致するメモは別の照合で一つにまとまる）。開いている同名のアクティビティへまとめたときは、ZIP の行の uuid と合流先の uuid の対応を取り込み先の memory.db の表 `persona_pack_activity_merges` に残し、アクティビティの照合は「uuid 一致 → この対応 → 開いている同名」の順にする。対応で当たった行は、取り込み先で閉じられていても既にあるものとしてスキップし、再開させない（2026-10-17 レビュー指摘で確定 — それまでは対応が取り込みの最中にしか無く、合流先を閉じた後に同じ ZIP を入れ直すと、空のアクティビティが開いた状態で増え、メモは閉じた側に残って泣き別れた）。一つのアクティビティが複数の元の uuid を吸収しうるので、約束帳の `ORIGIN_TASK_ID` のような列ではなく表に置く。
- **同じ世界に同じパックから二体目を迎えたとき、アドオンがメッセージに付けた値 (addon_message_metadata) は二体目では入らない**: メッセージの ID は取り込みで変わらず、この表はメッセージ ID・アドオン名・キーの組で一意なので、二体目の行は一体目の行と同一とみなされて挿入されない（既知の限界として受け入れる）。
- **合流で混ぜる範囲**: §5 の規則で混ぜるのは `chatlog/`・`knowledge/`・`journal/` と `attachments/` の実体。`profile/` は上書きオプションのみ。`items/` と `extensions/saiverse/` は**新規作成のときだけ取り込み、合流時は取り込まずスキップ件数として報告する** — 机の上や運用記録は取り込み先の現在の状態が正で、機械的に書き出したテーブルの行単位の混合は意味が定義できないため（2026-10-17 実装時に確定）。例外は下の「新規作成が途中で止まったときの再開」だけ。
- **`extensions/saiverse/` の本体 DB の行は、書き出す表だけを、そのペルソナの行として入れる**（2026-10-17 レビュー指摘で確定）: 取り込むのは書き出す側が書く表（コードの `SAIVERSE_DB_TABLE_OWNERS`。§9 の saiverse_db の表と addon_message_metadata）だけで、それ以外の表名の JSON は警告して取り込まない。各行のペルソナ ID の列（PERSONA_ID・AIID・persona_id。表ごとの列はコードの表）は、ZIP の値がなんであれ取り込み先のペルソナ ID にする。子表（タスクのステップと履歴、Track のローカルログ）は、同じ取り込みで取り込み先のペルソナの行として入った親を指す行だけ、addon_message_metadata は取り込み先の memory.db にあるメッセージ宛ての行だけを入れる。手を加えた ZIP の行が、別のペルソナの記録として書き込まれないようにするため。

- **添付の参照に ZIP のパスを残さない**（2026-10-17 レビュー指摘で確定）: 取り込んだメッセージの添付の参照（metadata の images / documents / media）は、ZIP から実体を復元できたものは元の `uri` / `path` を一切引き継がず、復元先のフォルダの種類と実際のファイル名から `uri`（`saiverse://<種類>/<ファイル名>`）と `path` を組み直す（2026-10-17 レビュー指摘で確定 — それまではファイル名が変わったときだけ書き換えていたため、`saiverse://image/../x` のような `uri` が残り、取り込み後の会話のメディア読み込みが共有メディアフォルダの外のファイルを読みえた）。復元できなかったものは `uri` と `path` の両方を空にし、件数を警告に載せる（2026-10-17 レビュー指摘で確定 — それまでは `saiverse://<種類>/<ファイル名>` の形の `uri` を残していたため、添付を同梱しない ZIP では、取り込み先の共有メディアフォルダに同名の別のファイルがあるとそれに解決され、別の画像が本人の記憶として提示されえた）。復元先は、取り込み先に同名のファイルがあっても中身（sha256）が同じときだけ再利用し、違えば `<名前>_<n>` へ避ける。ZIP が書いた元の環境のパスを残すと、取り込み先で再エクスポートしたときに、そのパスにある取り込み先のファイル（本体 DB など）を添付として ZIP に入れてしまうため。書き出す側も、内装画像・所持品と私室の物のファイルは共有メディアフォルダの内側、添付は共有メディアフォルダと `user_data/icons` の内側、アイコンと外見画像は `user_data/icons` と `image/` の内側のものだけを入れる（§9 ゾーン C）。添付の置き場に `user_data/icons` を含めるのは、取り込みが外見画像を `user_data/icons` へ復元し、その子を見た別のペルソナの部屋の様子の記帳や知覚台帳・スペルの結果のメッセージの `media` がその絶対パスを持つため（2026-10-17 レビュー指摘で確定 — それまでは共有メディアフォルダだけを認めていたので、次の書き出しで「過去に見た相手の姿」が拒否されて記録から消えていた）。`user_data/icons` のファイルは `attachments/image/` に入れ、取り込みは共有メディアフォルダ `image/` へ復元して `uri` を `saiverse://image/<ファイル名>` で組み直す。

は取り込み先の運用状態なので書き出さない。取り込みの後の埋め込みの再生成は、今回足した message の件数ではなく、取り込み後の memory.db に残る埋め込み待ちの空のベクトル行の件数（起動時の検査と同じ数え方）で起こす — 再開の合流は足す message が 0 件でも、止まった回が残した空のベクトル行を埋める必要があるため（2026-10-17 レビュー指摘で確定）。画面は失敗時に「同じパックをこのペルソナへ合流で取り込めば残りが入る」と案内する。印は書き出さず、取り込みでもペルソナフォルダへ復元しない。
- **新規作成は作る前にパック全体を検査し、作った後の失敗では作ったものを残さない**（2026-10-17 レビュー指摘で確定）: 新規作成は、ペルソナを作る前に取り込みの書き込み前の検査（壊れた JSON・形の不正・§3 原則 6 の二本の上限 — 展開後の合計サイズと JSON の 1 要素の大きさ。コードの `validate_pack`）をパック全体に通し、弾けるものは何も作らずに断る。作った後で取り込みが丸ごと巻き戻った（ペルソナの memory.db にメッセージが無く、上の印も無い）ときは、ペルソナに加えて作成経路が作った私室（building 行と入室の記録・その部屋の fixture 行）と、利用者とペルソナの結び付き、サーバーのメモリ上の登録（部屋の一覧・自律行動の見回り）も消す。それまではペルソナだけを既存の削除経路で消していて私室が残り、同じパックで入れ直すと部屋の名前が同じ街の私室と重なって作成に失敗していた。
- **取り込みは一度に一つ**（2026-10-17 レビュー指摘で確定）: 合流と新規作成は、ペルソナを問わずサーバーの中で同時に一つだけ走らせ、走っている間に届いた二つ目は 409 で断る（`api/routes/people/persona_pack.py` の `_claim_import`）。取り込みは共有メディアフォルダへ添付を書き、同じ中身のファイルが既にあれば再利用するので、別のペルソナ宛ての取り込みが並走すると、片方がもう片方のまだ確定していないファイルを再利用し、先の取り込みが失敗して自分の書いたファイルを消したとき、後の取り込みの参照が欠けるため。引っ越しは稀な操作なので、全部を一つずつにする遅さは受け入れる。
- 取り込み後に**結果の内訳（何件追加・何件更新・何件スキップ）を表示**し、ユーザーが確認できるようにする。
- 合流を行うと、ペルソナに提示するコンテキストの途中へ過去の記録が差し込まれるため、プロンプトのキャッシュ（先頭からの一致）が一度切れる。引っ越し・合流という一回限りの操作の代償として受け入れる。

なお本機能は、ユーザーが自分の手元に持つファイルから迎える操作であり、2026-09-10 に採用しないと決めた「削除後の記憶の再利用を約束する機能」を作るものではない。

## 6. 互換と移行

- 旧スレッド単位エクスポート（`saiverse_saimemory_v1` 形式）の**書き出しは、UI のボタンと API を本機能で置き換えて廃止**。コマンドラインの `scripts/export_saimemory_native.py` も新形式が入り次第、廃止する。既に書き出された旧ファイルの**取り込み機能は当面残す**。
- 既存の ChatGPT 会話取り込み（`import_chatlog.py`）はそのまま残す。アイディア帳にあった「ChatGPT の ZIP 内画像をアイテム化して私室に配置」は、既存の ChatGPT 取り込み機能側の改良として本件とは別に扱う。

## 7. 検証計画

1. **往復テスト**: テスト用の隔離環境で作ったダミーペルソナをエクスポート → 別の隔離環境へ新規インポート → 再エクスポートし、ZIP の中身が一致すること。`thought_signature` のバイナリデータが base64 変換の往復で壊れないこと。同じ秒に複数スレッドへ書かれた記録の並び順（seq）が保たれること。
2. **合流テスト**: 同じペルソナを二つの環境で別々に動かしてから合流し、追記型の記録が重複せず混ざり、書き換わる記録が新しい方で揃うこと。二度同じ ZIP を取り込んでも結果が変わらないこと。
3. **画面の目視確認**: 取り込み後のペルソナの画面（スレッド・Memopedia・手帳）を開発者が実際に開いて読み、引っ越し前と同じ子として表示されること。
4. **Lite との受け渡し**: Lite で書き出した ZIP を本体へ取り込む一連の動作確認（Lite 側の対応と合わせて）。

## 8. 保留（v1 ではやらない）

- 会話の分岐（再生成の履歴）の表現。チャットログは一本道の時系列で運ぶ。
- 不要な部分を外して書き出す選択エクスポートの UI（データ形式自体は §3-4 の仕組みで対応済み）。
- `avatar/` と `voice/` の中身。本体側に立ち絵の保存場所ができたとき、また声の設定が認証情報と分離して保存されるようになったときに、確保済みの席へ入れる。
