## 0. 三つの概念と、メッセージの刻印

| 概念 | 単位 | 答える問い |
|---|---|---|
| **エピソード** | 意味 | これは**何の出来事**か |
| **チャンク** | 量 | 記憶として**どう畳むか** |
| **エピソードコネクション** | 関係 | **何と繋がっている**か |

- **エピソード**は出来事の記録行。ID（episode:N）・種類・参加者・期間・目的参照を持ち、本文テキストを持たない。二種類ある:
  - **有界エピソード**（コマ・作業セッション）: 開始と完了がシステムのイベントとして実在する出来事。完了する
  - **対話エピソード**（会話）: 会話相手ごとに 1 行。完了しない（§3.3）
- **チャンク**はあらすじの生成と畳みの単位。**規定は [`arasuji_levels.md`](arasuji_levels.md) のまま**（約 U＝1 万字で区切り、切れ目に寄せる、レベル制）。本書による変更は「あらすじ生成時期の前倒し」と「畳みの記録操作化」の 2 点だけ（§4）。呼称は「チャンク」— v1.1 までの「エピソードチャンク」という呼称は撤回した（チャンクはエピソードに従属せず、字数で決まるため）
- **エピソードコネクション**はエピソード間の関係の記録（目的・親子・想起の足跡）。実体は episode_inheritance テーブル（実装済み・消費待ち）
- **メッセージの刻印**: 各メッセージは書き込みの時点で「その場の参加者」「所属する有界エピソード」「目的参照」を記録する。どれも書き込み時に確定している事実で、機械的に書ける
- **エピソードを読む**: エピソード → 刻印が一致するメッセージ列 → そのメッセージ列を覆うチャンクのあらすじ、または生ログ。エピソードの中身は常にこの導出で得る（エピソード行自体はメッセージ集合を持たない）。チャンクは字数で切られているため、**あらすじの文章にはそのエピソード以外の前後の内容も含まれる** — 所属の正確さはメッセージの刻印が保証し、あらすじは前後関係込みの読み物として扱う（まはー許容 2026-08-11）

**判定基準**: ユーザーが夜帰ってきて「今日何してたの？」と眺めるとき、ペルソナの一日がエピソードの列として読め、気になる一つを開くと中の生の過程（間違いや訂正も含めて）まで降りられるか。

## 1. なぜ — 解いた症状

1. **細切れ**: 会話が 30 分無応答のタイマーで別エピソードに割られ、疎な会話のあらすじと収穫が細切れになっていた → 時計の退場（§2-2）と対話エピソード（§3.3）で解消
2. **分裂と二重記述**: 会話と作業の交差でエピソードが割れ、全体を語る digest が断片に貼られて同じ出来事が二回記述された → 旧機構は 7/28 に撤去済み。新設計では「エピソード単位の digest」自体が存在しない（あらすじはチャンク単位・エピソードの概要は導出）ため温床が無い
3. **孤児エピソード**: 押し出された会話を閉じる者が居らず、「会話中」の判定が嘘のままコマが消えた → 会話のエピソードは完了しないので、閉じ忘れという状態が構造から消滅（§3.3。[issue](../issues/open_conversation_orphaned_by_track_displacement.md) は実装後 archive）
4. **無言の退場**: ツール結果・システム通知が編纂の圧力に数えられながら、どのあらすじにも覆われず消えていた → 編纂対象規則（§4.4）
5. **自律行動が世界から見えない**: エピソードは Building で起きているのにチャット UI に現れない → §3.2 の三段露出

## 2. 設計原理

1. **終わりは検出でなく定義**: 会話に終わりの合図は存在しない（ユーザーは終了を宣言せずに離席する）。会話の切れ目はどう置いても実在しない終わりの捏造になるため、置かない
2. **時計は記憶の構造に触れない**: 時間が動かしてよいのは世界側の行動（ペルソナがいつまで返事を待つか）だけ。エピソードの開始・完了・チャンクの区切り・畳みのどこにも、タイマー・暦日・ライフ境界は登場しない
3. **一次生成物はチャンクのあらすじのみ**: エピソードの概要・目的別のあらすじは、覆うあらすじの列の検索で導出する。別のテキストを生成しない
4. **保存と材料化の分離**: memory.db への保存は常に全文。圧縮・省略は編纂材料・コンテキスト搭載・UI 表示の側でだけ行う
5. **ペルソナ名義のテキストは省略しない**（継承）
6. **会話の至上性**（継承）: 畳み・可視化のどれも、進行中のユーザー会話の応答経路に同期処理を割り込ませない

## 3. エピソード（意味の層）

### 3.1 記録の形

`saiverse/episodes.py` の既存行をそのまま使う: kind・participants・building・origin（目的参照 — Track 撤廃後はタスクとレパートリー項目の二種、[track_retirement.md](track_retirement.md) §6）・short_id。目的参照は開始の瞬間にエピソード行へ直接記録する（コマ座標経由の逆引きは廃止 — 確定した瞬間に確定した場所へ書く）。

### 3.2 有界エピソード（コマ・作業セッション）

- **開始**: コマの発火・セッションの起動。**完了**: セッションの締め・コマの終了。時計による完了は無い
- **遷移の一行**（まはー発案 2026-08-11）: 開始・完了を機構名義のシステムメッセージとして知覚の列に立てる — 「習慣テンプレートにより『昼の執筆作業』を開始した」「『昼の執筆作業』が完了した」。これにより、会話の途中に作業が挟まった事実があらすじの材料に時系列どおりの位置で入り、あらすじが経過を正しく記述できる。500 字以下なのでそのまま材料に乗る（§4.4）。既存の切替通知との重複は実装時に棚卸し
- **チャット UI への三段露出**（2026-07-13 裁定の UX。発火点は遷移の一行と同一イベント）:

| 段 | タイミング | 表示 |
|---|---|---|
| 枠の投下 | 開始 | 「エアが〜しているようです」（コマの型から決定論生成） |
| 詳細のライブ | 枠をクリック | 中のパルス・ビートをリアルタイム表示（ライフビューと同データ源） |
| 概要の確定 | 完了 | 枠が概要表示に変わる（概要＝覆うあらすじの導出。未生成ならこの時点で生成 — §4.2） |

- **枠の文面**（基準＝外から分かる粒度。全 6 型確定 — 補完 2 件は 2026-08-11 まはー承認）: 自分を更新する→「考え事をしている」/ 知る→「調べ物をしている」/ 作る→「作業をしている」/ 暮らし→「ゆっくりしている」/ 話す・聞く→「誰かと話したそうにしている」/ 経験する→「出かけようとしている」。kind='conversation' は対象外（発話そのものが履歴に見えている）。work_session は親 slot の型を継承（枠は 1 つ）。型不明は「何かをしている」
- 同じ Building の他ペルソナには開始通知のみ（完了概要は送らない）。ユーザーへの露出はチャット UI 経由のみ（push しない）

### 3.3 対話エピソード（会話相手ごとに 1 行・完了しない）

会話の出来事としての識別は「誰との対話か」以外に正解が無い（原理 1）。だから:

- **会話相手ごとに 1 行**: 初めてその相手と話した時に作られ、以後**完了しない**。関係に終わりが実在しないため、記録にも終わりを書かない
- **中身は導出**: 「エアとの対話」の中身＝参加者の刻印にエアを含むメッセージ列。複数人会話のメッセージは参加者全員分の対話エピソードの導出条件に一致するため、**各相手との対話の両方から参照される**。実体（メッセージ・チャンク・あらすじ）は複製しない
- 会話には**完了・追記先の照合・参加者集合の管理・閉じる処理が存在しない**。これらの検討過程（時計で切る → 圧力で完了 → 相手構成ごとに区切る → エピソードを与えない → 相手ごと永続、の順に検討・棄却）は改訂履歴参照
- 「30 分無応答」はペルソナが返事を待つのをやめて次の行動へ移る世界側のタイマーで、記録には触れない。「いま会話中か」の判定は待ちタイマーの生死で行う
- **経緯**: これは撤廃した永続会話 Track が持っていた「会話記録の常設の器」という役割の、状態機械（running/alert/タイマー/排他）を伴わない形での再配置である（track_retirement 住人 2 — 関係の器は 意図＝レパートリー / 知識＝人物ページの経験の台帳 / 記録＝対話エピソード に三分割）

### 3.4 「完結」の語彙（まはー裁定 2026-08-11）

有界エピソードとチャンクの「済んだ」状態は**完結（complete）**と呼ぶ。完結＝追記不可＋あらすじ生成済み。完結した範囲の生ログは、畳まれるまで提示コンテキストに残ってよい — 「完結している」と「提示から消えている」は別の状態。「閉じる」という語は両者を混同させるため**廃語**。**コード名も complete 系へ改名する**（close_episode → complete_episode、DB 列含む。まはー「メティスは絶対コードの言葉で喋るから」— 文書だけの言い換えは必ず崩れる）。

## 4. チャンク — arasuji_levels 準拠と、変更 2 点

チャンクの区切り・レベル制・水位・畳みの範囲規則は **[`arasuji_levels.md`](arasuji_levels.md) の規定のまま**（約 U＝1 万字・切れ目に寄せる・予算超過で古い側から）。会話の参加者が変わってもチャンクは切らない — 区切りを参加者や有界エピソードの境界に従属させる案は v1.1 で採り、文字数が揃わなくなる（小さいあらすじが量産される）ため撤回した。所属の正確さはメッセージの刻印が担う（§0）。

本書による変更は次の 2 点だけ:

### 4.1 変更 1: あらすじの生成時期の前倒し

あらすじは**チャンクが U に達した時点**（および有界エピソードの完了時点で、その完了までを覆うチャンクを確定して）生成する。畳み（Metabolism）の時点ではなく。理由:

1. 有界エピソードの完了時、チャット UI が概要を即時に必要とする（§3.2 三段目）
2. 変更 2 の前提になる

生成は提示コンテキストに触れないため、会話モデルのキャッシュには影響しない。総作業量は不変（各文字があらすじ生成を通る回数は変わらない — arasuji_levels §14-1 の原理。変わるのは時期のみ）。

### 4.2 変更 2: 畳みを記録操作にする

あらすじが畳みの時点で既に存在するため、畳み＝「この範囲は生ログでなくあらすじで提示する」という記録の書き換えだけになる。LLM 呼び出しなし。実装は arasuji_levels §15-3 の再畳み（印の切り替え）と同じ経路に乗せる。

### 4.3 展開の既定量（旧 7/13 保護リストの廃止）

「進行中＋直近 1＋ユーザー会話を生ログのまま残す」という保護リストは廃止。生ログがどこまで残るかは水位（上限・残す量）と畳みの範囲規則だけが決める — 新しい規則もパラメータも無い。ユーザー会話 20 件保持（user_conversation_preserver）は**退役**（track_retirement 住人 11。会話開始時の生ログの厚みは読み戻し〔arasuji_levels §15〕が字数で保証する）。

### 4.4 編纂対象規則（まはー裁定 2026-08-11）

機構名義のシステムメッセージ（ツール結果・スペル結果・通知・遷移の一行）も編纂対象に入れる:

- **閾値以下（初期値 500 字 — まはーが実機のチャット画面の 1 画面分を実測した値。調整パラメータ）はそのまま材料に入れる**
- **閾値超えは決定論の一行に置き換えて材料に入れる**（「◯◯を実行し、結果 6,213 字を得た」— metadata から機械生成。LLM は使わない: 編纂 LLM がどうせ全体を要約するため二重払いになり、機械生成の一行は捏造しようがない）。結果の内容の記述は、それを見て反応したペルソナの発話（全文で材料に乗る）が担う
- **条件は長さのみ。種類（ツール/通知）では分けない**（目的＝会話の内容があらすじで薄まらないこと、から導出）
- **チャンクの字数勘定は置き換え後のサイズで行う**
- 保存は触らない（原文全文が memory.db に残り、被覆記録に原文のメッセージ ID が入る）
- session_digest（作業ダイジェスト）のみ除外を維持し、生ログ正史の裁定（Wave 2）に従属

### 4.5 材料と参照の分離

あらすじ生成の**材料**（＝被覆・退場の対象）と**参照文脈**（読むだけ・覆わない・退場しない）を分ける。生成の時点で、材料の周囲の内容は生ログかあらすじのどちらかの形で必ず存在する（古い側から順に処理されるため）。現行の生成器が参照文脈をどこまでプロンプトに渡しているかは実装時に確認する。

### 4.6 提示の時系列

エピソードが時間的に重なる（会話の合間に作業が挟まる）ため、「提示の並び順＝時系列」という前提は成立しない。**並び順は開始時刻による整列にすぎず、時間の事実は各あらすじが自分の対象期間**（被覆記録の最初と最後のメッセージ時刻）**を明示することで伝える**。あらすじの本文にも期間の記述を含める（「9 時から 17 時にかけて断続的に」）。

## 5. エピソードコネクション（関係の記録）

- **実体**: episode_inheritance テーブル（有向・層・由来・実装済み）。操作は `saiverse/experience_inheritance.py` に集約。新テーブルは作らない
- **張り方 — 機械的に観測できる事実のみ。LLM 判定なし**:

| 種類 | 記録される瞬間 |
|---|---|
| **目的** | エピソード開始時の目的参照の直接記録（§3.1） |
| **親子** | コマ↔セッションのように、一方が他方から生まれたシステムイベント |
| **想起の足跡** | エピソード M の最中に memory_read でエピソード N を開いた事実を M→N として記録。ANCHOR_REF により特定メッセージ粒度でも指せる |

- 会話の「続き」の記録は不要（対話エピソードは完了しないため、繋ぎ直す場面が無い）
- 記録された関係は次の想起の探索路になる。想起用タグ（意味による検索）と相互補完
- occurrence（同じ会話の別ペルソナ視点の対応）の置き場所は実装設計で確定（§9 確認事項）

## 11. 守るべき不変条件

1. **成果物の接地は不変**: task_done の成果物参照必須・Item 実在検証は一切緩めない
2. **ペルソナ名義のテキストは全文保存**: 圧縮・省略は材料化と表示の側でだけ行う
3. **退場は必ず編纂**: 畳まれる範囲は必ずあらすじ生成済み（§4.1 の前倒しにより構成的に成立）
4. **一次生成物はチャンクのあらすじのみ**: エピソード・目的・相手ごとの概要はすべて導出
5. **実体の非複製**: メッセージ・チャンク・あらすじを複製しない。エピソードの中身は刻印からの導出のみ
6. **時計は記憶の構造に触れない**: 開始・完了・区切り・畳みのどこにもタイマー・暦日・ライフ境界を書かない
7. **見せ方はライフサイクルに従う**: チャット露出は有界エピソードの開始/完了と一対一。表示だけの中間状態を発明しない
8. **会話の至上性**: 応答経路に同期処理を割り込ませない
