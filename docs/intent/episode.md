## ⚡ 2026-08-10 設計議論の到達点（Wave 1 第一夜 — v1.0 改稿で本文へ統合する）

「エピソードの単位と正史」の設計議論で以下が固まった。本文の各節より新しい裁定であり、矛盾する場合はこちらが勝つ:

1. **器と縁の二本立て**: エピソード＝記憶管理の器（有限の塊）。「あの会話・あの作業の続き」という関係は器の中に入れず、**器と器の間の縁**として張る。縁の実体は実装済みの episode_inheritance テーブル（前駆 DAG）— 新テーブル不要。数日跨ぎの会話の続きは「新しい器＋縁」で表す
2. **切れ目に時計を使わない**: 会話に「終わりの合図」は存在しない（検出でなく定義）。エピソードの閉じは ①自然な閉じを持つ種類はそれ（セッションの締め等）②**量**（一本の概要で語り切れる限界。chronicle_eviction の文字数水位と同じ物差し）③**畳みの需要**（Metabolism がその範囲を畳みたくなった瞬間、開きっぱなしの小さい器を閉じる）— の三つだけで決める。深夜 0 時も暦日もライフ境界も規則に登場しない
3. **中断状態の新設**: エピソードは「開いている / 中断中 / 閉じた」の三状態。30 分無応答は「中断」（ペルソナが自由になる世界側の状態）であって「閉じ」ではない。細切れ（1 往復 30 分＝1 エピソード）はこれで解消。**既存の「中断中セッション」（Track の机メモ）は器の中断の既存実装であり、吸収して消す**（机メモ→中断中エピソードのしおり）
4. **再開の判定**: 同じ場所に開いた/中断中の会話の器があり、発話者が参加者の輪（途中参加で育つ）に居れば追記。居なければ新しい器。誤判定は縁が繋ぐので致命傷にならない
5. **孤児エピソード問題（gate §2-6）は条文ごと消える**: 押し出し＝中断、閉じ＝量と需要、閉じ忘れという概念が構造に存在しなくなる（A/B 裁定は不要になった）
6. **前提工事**: 議論が三度 Track に足を取られたため、**Track の撤廃計画を先に確定させた** — [`track_retirement.md`](track_retirement.md)（裁定 3 点決着済み）。目的の参照語彙はタスク＋レパートリー項目の二種になり、origin_ref の多義（座標/親子/目的/Track）は縁の型付き語彙へ解体される

## ⚡ 2026-08-11 設計議論の到達点（Wave 1 第二夜 — 編纂対象規則）

7. **システムメッセージ（機構名義）は編纂対象に入れる**（まはー裁定）。現状はツール結果・スペル結果・システム通知のタグが編纂材料から除外され、Metabolism の圧力には数えられ退場するのに、どのあらすじの被覆にも属さず無言で消えている（「退場は必ず編纂」の下限違反。システムメッセージのみの範囲は「編纂対象なし＝退役してよい」が正規動作として仕様化されていた）。規則:
   - **閾値以下（初期値 500 字）はそのまま材料に入れる**。500 字の由来: まはーが実機のチャット画面で「ちょうど 1 画面に収まるメッセージ」を実測した値 —「一目で読める量なら会話と同じ重みで乗っても薄めない」。調整パラメータ
   - **閾値超えは決定論の一行に圧縮して材料に入れる**（「◯◯を実行し、結果 6,213 字を得た」— metadata から機械生成。LLM は使わない: 編纂 LLM がどうせ全体を要約するのでコスト二重払い、かつ機械の一行は捏造しようがない）。**結果の中身の語りはペルソナの発話が運ぶ**（本人が反応して喋った言葉は全文で材料に乗る）
   - **条件は長さのみ。種類（ツール/通知）で分けない**（目的=会話を薄めないこと、から導出。種類で書くと短いツール結果を潰し、長い通知を素通しする穴が開く）
   - **チャンク切りの勘定は圧縮後サイズ**（現実装は除外が先・チャンク切りが後のため、システムメッセージはチャンク計画に透明だった。圧縮表現で数えることで「チャンクの 1 万字 = 語りの量の 1 万字」になる）
   - **保存は触らない**: memory.db の原文は全文のまま。変換は材料化の瞬間だけ。被覆帳簿には原文のメッセージ ID が入り、あらすじから memory_read で原文へ降りられる
   - session_digest（作業ダイジェスト）はこの規則から除外し、生ログ正史の裁定（Wave 2）に従属させる
8. **生ログ正史（§4 AUTONOMOUS 化）の再裁定は Wave 2 へ**（まはー裁定 2026-08-11）: 「作業セッション自体をどう取り扱うか＝Aspect の件と一緒にしか裁定できない」。作業セッションの記憶が Chronicle へ入る道（gate §2-5）も同時に決まる

## 1. これは何か

エピソード（できごと）に**三つの顔**を与える設計。エピソードの「封筒」（kind＋実体参照＋open/close＋occurrence_id＋層0 タグ）は `saiverse/episodes.py` として実装済み——本書は封筒の**中身の扱い**を定める：

| 顔 | 内容 | 出自 |
|---|---|---|
| **記憶の顔** | 記憶の詳細度（LoD）の制御単位。近い＝生ログ全展開、遠い＝概要 1 本 | A2 |
| **世界の顔** | 他者（ユーザー・他ペルソナ）から見える活動の単位 | B1＋X1 |
| **監査の顔** | 誠実さの検証単位。外部監査役が目標整合を判定し危険マークを付ける | A1 |

三つの顔は同じ一つの実体（エピソード）の面であり、**概要（エピソード Lv1 Chronicle）を共有部品とする**——記憶が畳まれた姿・チャットに表示される終了サマリ・監査役に渡す文脈が、すべて同じ「エピソード単位のまとまり」から出る。

判定基準（試金石）：**ユーザーが夜帰ってきて「今日何してたの？」と眺めるとき、ペルソナの一日がエピソードの列として読め、気になる一つを開くと中の生の過程（間違いや訂正も含めて）まで降りられるか。**

## 2. なぜ必要か — 四つの症状

1. **ダイジェスト正史の二重の誤り（A1）**：作業セッションは生ログを volatile に落とし、締めのダイジェスト 1 件だけを committed にする（v2 intent §4.3）。だがダイジェストは軽量モデル 1 コールの生成物で、**正しさを担保する機構が無い**（機械的に接地されているのは成果物 Item の差分だけ）。検証なき要約を正史にし、検証可能な過程を捨てている——二重に逆
2. **「間違っていた物事は全て忘れるべきなのか」（A1）**：人格は失敗の軌跡でできている（`autonomous_living.md`「人格は経験に宿る」）。ハルシネーションして最終的に直した過程こそ、そのできごとの実質かもしれない
3. **畳み単位が Pulse のまま（A2）**：volatile/committed の線は line/Pulse を作った時代の単位で引かれている。今はエピソードという時間構造があるのに、記憶の詳細度がそれに載っていない
4. **自律行動が世界から見えない（B1/X1）**：エピソードは Building で起きているのに、チャット UI（＝その Building の出来事の履歴）に一切現れない。同室の他ペルソナからも見えない。またチャットバブルは Beat の切れ目を潰して表示しており（スペル前後の発言が 1 バブルに融合）、見せる以前に**見せる単位が型として立っていない**

## 3. 設計原理

1. **接地は検証で、誠実さは監査で**（接地原則の深化）：主張の真実性を「要約時にお願いする」のではなく、**過程を残して外部が検証する**構造に変える。監査から漏れるできごとは許容（100% は狙わない——割り切り済み、まはー裁定）
2. **忘れないが、遠ざける**：間違いも経験として記憶に残る。ただし LoD により、遠いできごとは概要しか自動搭載されない。「消す」のではなく「畳む」
3. **概要は一度だけ作り、三つの顔で使い回す**：エピソード終了時に Lv1 Chronicle を 1 本作り、記憶の畳み表現・チャットの終了サマリ・想起の入口すべてに使う。同じ情報を別々に生成しない
4. **見せ方は封筒に従う**：チャットへの露出はエピソードの open/close/概要というライフサイクルそのままに行う。表示専用の別状態を作らない
5. **ペルソナ名義のテキストは省略しない**（既存原則の継承）：発話・独白の本文は全文が memory.db に残る。切り詰めはコンテキスト搭載時・UI 表示時の表示層の仕事

## 4. 生ログの正史化 — 作業セッションの AUTONOMOUS 化（A1 前半）

> **⚠️ 再裁定対象（まはー 2026-08-09 朝）**: 本節の 2026-07-13 裁定は古い前提（Track 解体・監督役構想より前）に立っている可能性があるため、裁定を見直す。「作業セッションをどの文脈系列に積むか」は Aspect/モデル格 再設計（v0.3.0 の門 §2-1）の設計議論で改めて決める。

### 4.1 何が変わるか

作業セッションのアスペクトを **WORKER（sub_line / volatile / lightweight）から AUTONOMOUS（main_line / committed / lightweight 運転は維持）へ**変更する（まはー裁定）。現状のハードコード点は `sea/work_session.py` L201 `pulse_ctx.push_line(aspect=Aspect.WORKER, track_id=...)`。

| | 現状（WORKER） | 変更後（AUTONOMOUS） |
|---|---|---|
| ライン | サブライン（別 line_id・別キャッシュ） | メインライン（会話と同じ head・同じキャッシュ） |
| 生ログ scope | volatile（メインライン文脈に自動搭載されない） | **committed（正史）** |
| committed | 締めのダイジェスト 1 件のみ | 生ログ全体＋ダイジェスト |
| Task 操作スペル | ❌（mode_spell_permissions: WORKER は Task 操作不可——purpose_seed が撃てない問題の正体） | ⭕（AUTONOMOUS は可。fixes handoff §3-1 が同時に解ける） |
| キャッシュ | セッション中、親 head は完全不変 | セッションのラウンドがメインラインに積まれる |

### 4.2 キャッシュ・コンテキストへの影響（設計上の覚悟）

メインライン積載により、1 セッション（5〜15 ラウンド、ツール往復込み）ぶんのトークンがメインの context を消費する。緩和は三段：

1. **ライフとの整合が主緩和**：ライフ中は生ログが熱いまま積まれる（それが「近い＝詳細」の LoD そのもの）。ライフ終端の Metabolism でエピソード単位に畳まれて概要に置換される（§5）——つまり**積むのは一時的で、畳む機構が対で入る**。A1 単独では成立せず、A2 とセットで初めて成立する設計
2. **ツール往復の搭載形**：発話（ペルソナ名義）は全文。ツール結果は memory.db への**保存は全文**（原理 5）、Metabolism 後の再搭載時は畳み表現に含める（先例: メティス記憶ブリッジの「ツールコールは `<system>N件実行</system>` 圧縮」裁定——保存と搭載を分けてよい）
3. **予算ゲートは既存**：ラウンド上限（コマの budget_rounds）がセッション長の上限を今までどおり抑える

均等モード（ライフ＝Session）では「セッションの生ログがメインラインに積まれる」ことは**キャッシュ 1 本化と同義**であり、WORKER 別ラインが毎セッション別キャッシュを張るコストが消える側面もある（トレードオフは実機の llm_io.log で観測して初期値を調整する）。

### 4.3 WORKER アスペクトの残る用途

WORKER（親に閉じる子セッション、session.md §2.4）は**廃止しない**。ユーザー会話中の分身（会話の裏で走る調べ物等、親 head を汚してはならない文脈）には引き続き WORKER が正しい。変わるのは「自律の時間割から発火する作業セッション」の既定アスペクトのみ。

## 5. できごと単位の LoD（A2）

### 5.1 詳細度の二状態

| 状態 | 距離 | コンテキストへの載り方 |
|---|---|---|
| **展開** | 進行中のエピソード＋直近の閉じたエピソード 1 つ＋ユーザー会話のエピソード | 生ログ全文（メッセージ列そのまま） |
| **畳み** | それ以外の閉じたエピソード | **概要 1 件**（エピソード Lv1 Chronicle、§6）に置換 |

（まはー裁定 2026-07-13: Metabolism 時の読み込み方＝「進行中＋直近 1＋ユーザー会話は残す、それ以外は全て畳む」。）

### 5.2 畳むタイミング＝ライフ終端の Metabolism

即畳みはしない——エピソード終了直後に畳むと、その手前からのキャッシュを道連れにする（まはー自己訂正、gaps doc A2）。畳みは **Metabolism（＝均等モードではライフ終端、life.md §6.3）で一括**して行う。ライフ中の閉じたエピソードは「閉じているが展開されたまま」が正常状態。

### 5.3 畳んだできごとを読む — memory_read への統合

畳まれたエピソードの生データを読む行為は、**既存の `memory_read` スペル（Memory Atlas の統一読みスペル）に統合**する（まはー裁定：「内部的には統合可能。できごとも記憶の一部」）。エピソード参照（`episode:N`、short_id は実装済み）を memory_read の引数語彙に加え、指されたエピソードの構成メッセージを開く。新スペルは作らない。

### 5.4 scope 意味論の整理

- 生ログの scope='volatile' 落とし（WORKER 由来）は §4 で消える。エピソードの畳みは **scope ではなく「エピソード単位の搭載制御」**で表現する——メッセージの所属エピソードが畳まれていれば、そのメッセージは自動搭載されず概要が代わりに載る
- volatile という scope 自体は残る（メタ判断の試行ターン等、本当に使い捨ての文脈用）。「作業の生ログ」がそこから出ていくだけ
- システム通知の長期記憶流入（[short_term_to_long_term_memory_filtering](../issues/short_term_to_long_term_memory_filtering.md)）は、この搭載制御に載る：束C の裁定どおりムダ通知自体を消した上で（life.md §7 で切替通知の氾濫は根治済み）、残る正当な通知はエピソードに属して普通に畳まれる——「入口で止める」特別機構は不要になる方向で解消

## 6. 概要の実体 — エピソード Lv1 Chronicle（三つの顔の共有部品）

### 6.1 生成の仕様

- **エピソード終了次第、即生成**（まはー裁定）。Metabolism を待たない——畳みは遅delayed、概要生成は即時、の別操作（B1 の終了サマリ表示が即時性を要求する）
- **どんなに長いエピソードでも Lv1 一本**にまとめる（まはー裁定。基本そこまで長尺にならない前提）
- 実装の器は既存の ArasujiGenerator（`sai_memory/arasuji/`）の level-1。現行の「未処理メッセージがバッチサイズ溜まったら」という件数 trigger を「エピソードが閉じたら、その範囲を」に変える——[general_chronicle_metabolism_trigger](../issues/general_chronicle_metabolism_trigger.md) の解決形（案 A「押し出し予定 ID を渡す」のエピソード版。「今コンテキストに残っているもののあらすじは不要」の原則はエピソード単位の畳みが引き継ぐ）

### 6.2 Track Chronicle との統合（書き込み側）

Track Chronicle（origin_track_id ごとの分割あらすじ、Metabolism 連動）とエピソード Lv1 Chronicle は「あらすじ」の粒度違いの同類。**エピソード Lv1 を一次生成物とし、目的別のあらすじは『その目的に属するエピソード概要の列』として導出する**方向に統合する——エピソードは層0 で origin_ref（目的参照）を持つので、目的→エピソード列→概要列は SELECT で引ける。Track Chronicle の独立バッチ生成は世代交代で退役候補（実装フェーズで、目的別あらすじの現行読者〔随意想起・head MemoryWeave〕への供給が途切れないことを確認してから）。

### 6.3 head 自動搭載の世代交代（読み込み側）

Track Chronicle の head 搭載（`_get_track_chronicle_context` が `get_running()` の Track のあらすじを MemoryWeave に織る、life.md §7.3 で記録済み）は退役方向。後継の「目的の文脈」供給：

1. **起動時**：コマ/セッションの指示書（title＋机メモ＋配下タスク、実装済み）
2. **再開時**：机メモ（決定論・無料）→ 随意想起（memory_read によるタグ・エピソード鍵の読み、行為として末尾追記）の二段（life_concept_map §9.2 裁定）
3. **常設**：head にはライフ①「常在の自己像」（第一階層の短いメニュー）だけが残る（同 §15）

**なぜ退役して文脈を見失わないのか（根拠）**：head 自動搭載が実際に文脈を運んでいた場面は「**自律 Track が running のままメインラインが繰り返し Pulse する**」場面——つまり v1（track_autonomous の 30 秒連続 Pulse）の世界の産物である。v2 でその場面は構造ごと消えた：

| v2 でペルソナが目的の文脈を必要とする瞬間 | 文脈の運び手（head 搭載に依存しない） |
|---|---|
| セッション/コマの開始 | 指示書（title＋机メモ＋配下タスク） |
| 判断点（起床・会話終了・セッション終了・就寝） | 状況テキスト（Track 一覧・机メモ・実績——③節目の全景として設計済み） |
| ユーザー会話 | 元々 head 搭載の対象外（`_get_track_chronicle_context` は user_conversation を除外していた）——変化なし |
| 会話の中で過去の作業に触れる | 生ログ正史化（§4）で直近はそのまま履歴に居る＋遠い分は随意想起 |

「自動で目の前に置く」から「必要な瞬間に運び込む」への移行であり、v2 の駆動構造（判断は少なく濃く、実行は機械的に）が先に変わったことで、head 常設の必要が後から消えた——という順序。加えて案 Y（life.md §7）後は `get_running()` の意味自体が変質するため、この機構はどのみち読み替えを要していた。

## 7. 監査役と危険マーク（A1 後半）

### 7.1 外部監査役

- **ペルソナの外側**に置く判定役。ペルソナの人格文脈を持たず、**そのエピソード分のコンテキストだけ**を渡して「元の目標と整合しているか」を判定する（まはー裁定。低コスト——エピソード単位で完結・毎エピソード 1 コール程度）
- 発火点：エピソード close 時（Lv1 Chronicle 生成と同じ瞬間に相乗り——同じ材料〔エピソードの構成メッセージ＋目標〕を二つの出力に使う）
- 判定材料の機械的裏付け：成果物の実在（Item 差分）との突き合わせを判定プロンプトに含める（例:「ドキュメントが完成したと報告しているが、このエピソードで作成された Item は 0 件」）
- 監査対象は当面**自律系エピソード（slot / work_session）**。ユーザー会話は対象外（会話はユーザーという抵抗が毎ターン入る——監査の必要が構造的に薄い）

### 7.2 危険マーク

- 監査でハルシネーション／インジェクションが検出されたエピソードに**危険マーク**を付ける（エピソード単位のラベル）
- **メッセージ単位マークは将来許す**（まはー裁定 2026-07-13）：監査が「この 1 メッセージが虚偽／有害」と特定できた場合の個別マーク。設計はエピソードラベルと同じ「マーク＋想起時定型文」の型を粒度違いで適用する。**転用先を最初から視野に入れる**——X（外部 SNS）連携や外部由来メッセージの有害コンテンツ・インジェクション対応は「特定メッセージに危険マークを付けて想起時に警告を挟む」という同型の問題。マーク機構はエピソード専用にせず、**メッセージにも付けられる汎用ラベル**として設計する（初期実装はエピソード単位から）
- **ラベルはメッセージ単位にも降りる**（まはー裁定の「新概念 (ii)」）：エピソードに付いたラベルを、その構成メッセージの想起・表示時に参照できる特性。実装はエピソード行のラベル＋メッセージ→エピソードの所属（層0 で実装済み）の JOIN で足りる見込み——メッセージ側への物理コピーはしない
- **想起時の定型文付加**：危険マーク付きエピソード由来のメッセージが想起・展開されるとき、必ず定型文を付ける——「このメッセージは監査により虚偽の可能性があると判断されました。情報や判断の真正性についてよく注意して閲覧してください。検出理由：【…】」（まはー裁定の文面をそのまま採用）
- マークが無いエピソードは普通に経験として読める。**間違いも（マークされていなければ、あるいはマークごと）記憶に残る**——失敗の軌跡は人格の材料（§3-2）

## 8. 世界への見せ方（B1）

### 8.1 チャット UI への三段露出（まはー裁定の UX をそのまま仕様化）

| 段 | タイミング | 表示 |
|---|---|---|
| **枠の投下** | エピソード open を検知 | 大きめの枠をチャット履歴に投下。最初は「エアが机に向かっているようです」程度の情報だけ（**コマの型（六型）＋ kind から決定論で文生成**——LLM 不要。語彙は下表） |
| **詳細のライブ** | 枠をクリック | エピソードの中のパルス・ビートをリアルタイムで確認できる（展開ビュー。ライフビューのエピソード詳細と同じデータ源） |
| **概要の確定** | エピソード close | 枠が概要表示に変わる。**概要の実体＝§6 の Lv1 Chronicle**（別テキストを作らない——原理 3） |

**枠投下の文面語彙**（まはー提示 2026-07-13。基準＝**外から分かりそうな粒度**——同室の人間に見える程度の情報量で、中身は語らない）：

| コマの型（六型） | 文面（「エアが〜ようです」） |
|---|---|
| 自分を更新する | 考え事をしている |
| 知る | 調べ物をしている |
| 作る | 作業をしている |
| 暮らし（無意味の予算） | ゆっくりしている |
| 話す・聞く | 誰かと話したそうにしている（補完案・要レビュー） |
| 経験する | 出かけようとしている（補完案・要レビュー） |

- kind='conversation' は枠投下の**対象外**（会話は発話そのものが Building 履歴に見えている——枠は不要）
- kind='work_session' は親 slot の型を継承（slot＋work_session は親子畳み込み済みなので枠は 1 つ）
- 型情報が無いエピソードのフォールバック：「何かをしている」
- チャット UI＝「その Building における出来事の履歴」という定義に、自律行動がようやく従う（B1 の症状の解消）
- **同じ Building の他ペルソナには、冒頭の「〜しているようです」イベント通知のみ**送る。終了概要は送らない（まはー裁定：とりあえず無しで進める）
- ユーザーへの露出はチャット UI 経由のみ（通知の push はしない——見に来た人が見える、が正しい距離感）

### 8.2 occurrence（世界的できごと）の扱い

エピソードは 1 ペルソナで閉じる（まはー裁定：前者で進める）。世界側で「同一のできごと」を束ねるアンカーは occurrence_id で、**会話（kind='conversation'）には実装済み**。slot / work_session は 1 ペルソナで完結する活動なので occurrence 不要——**拡張はしない**（将来、共同作業（同じ工房で同じ成果物を触る等）が設計されたときに、その intent が occurrence を広げる）。

- **実装順の依存**: Beat 型化は runtime_llm.py 分割（台帳 🟡 実装待ち）の Phase 1 副産物として得るのが最短。本 intent の表示改修はそれを待って乗る

## 11. 守るべき不変条件

1. **成果物の接地は不変**（v2 intent 継承）：task_done の成果物参照必須・Item 実在検証は本書後も一切緩めない。生ログが正史になることは「主張だけで完了にできる」ことを意味しない
2. **ペルソナ名義のテキストは全文保存**：畳み・圧縮は搭載と表示の制御であり、memory.db の本文を切り詰めない
3. **監査役はペルソナの外**：ペルソナの人格文脈を監査に混ぜない（監査は世界の抵抗であって内なる声ではない）。逆に監査結果の定型文は機構名義（event_message 形式）で入り、ペルソナ発話を騙らない
4. **概要は単一ソース**：エピソードの概要テキストは Lv1 Chronicle 一つ。表示用・記憶用・監査用に別々の要約を生成しない
5. **見せ方はライフサイクルに従う**：チャット露出の状態はエピソードの open/close と一対一。表示だけの中間状態を発明しない
6. **会話の至上性**（継承）：エピソードの畳み・監査・可視化のどれも、進行中のユーザー会話の応答経路に同期処理を割り込ませない
