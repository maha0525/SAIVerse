# アーリーアクセス版の配布 (Early Access Release)

**ステータス**: 🟠 実装中 (v0.3、2026-09-25。v0.1 起草 → 言葉づかい検査と整合性検査で発見 3 件を反映 (v0.2) → 未決 5 点 + 版名をまはー裁定で確定し実装着手)

## 1. これは何のためか

大きな版 (直近では v0.4) を、いきなり全ユーザーへ届けるのではなく、**希望した人にだけ先に届けて不具合を出し切り、落ち着いてから全員に届ける**ための仕組み。

背景は v0.3.0 の反省。一度リリースすると自動アップデートで全ユーザーに即座に届いてしまうため、「出したら初期不具合が全員を直撃する」プレッシャーがリリースを遅らせた。アーリーアクセス版という緩衝材を挟むことで、大きな版を早く外に出せるようになる。

**誰が何に頼れるようになるか**:

- **安定版のユーザー**は、何もしなければアーリーアクセス版が届かないことに頼れる。通知も更新も、いままで通り安定版だけ。
- **アーリーアクセス版に入ったユーザー**は、入る前にワールドの保存 (スナップショット) が取られること、「安定版には当分戻れない」ことを入る瞬間に知らされることに頼れる。
- **まはー**は、大きな版を「まず希望者だけに」出せることに頼れる。

## 2. いまの配り方 (事実の確認、2026-09-25 時点)

- **更新の実体**: ユーザーの手元のフォルダは git で `main` ブランチを向いていて、更新はそのブランチの最新へ進める操作 (`scripts/update_engine.py` — git の fast-forward)。ZIP からインストールした場合も、セットアップが同じ形 (main を追跡する git フォルダ) に整える。
- **「新しい版があります」の通知**: `api/routes/system.py` が GitHub の最新リリース (`releases/latest`) と手元の版を比べて出す。GitHub は**プレリリースの印 (リリース作成時に付けられる「これは正式版ではない」の目印) が付いたリリースを「最新」に数えない**。
- **⚠️ ただし、いまの発行の自動化はこの印を付けない** (整合性検査 2026-09-25 の発見 A)。`.github/workflows/release.yml` は `v` で始まるタグが push されると**印なしの通常リリースを自動で作る**ので、`v0.4.0rc1` のようなタグを何もせずに push すると、その瞬間からアーリーアクセス版が「最新」として全ユーザーの通知と ZIP の配布リンク (`releases/latest/download/`) に載ってしまう。**「安定版ユーザーに誤って届かない」は、自動化がプレリリースの印を付けるようになって初めて成立する** (§3-6)。

## 3. 設計

### 3-1. 配布の線を二本にする

| | ブランチ | 版名とタグ | GitHub リリース |
|---|---|---|---|
| 安定版 | `main` (従来通り) | `0.4.0` / タグ `v0.4.0` | 通常リリース |
| アーリーアクセス版 | `early-access` (新設) | `0.4.0rc1` / タグ `v0.4.0rc1` | **プレリリースの印付き** |

- **版名は `0.4.0rc1` の形にする** (rc = release candidate、N 回目の候補版)。理由: 起動時にワールドを新しい版へ合わせる処理 (アップグレードの鎖) は Python の版名規格 (PEP 440) で版を解析しており、`0.4.0-ea.1` のような独自の形は**受け付けず、その版は起動できない** (発見 B)。`0.4.0rc1` は規格上の正式なプレ版で、`0.4.0rc1 < 0.4.0rc2 < 0.4.0` の並びも規格が保証する。画面に見せる名前は版名とは別に「アーリーアクセス版」と表示してよい。
- **手元がどちらのブランチを向いているか、それだけで受け取る版が決まる**。別の設定値は持たない (設定とブランチがずれる事故を作らないため)。
- `early-access` ブランチには**発行済みのアーリーアクセス版だけ**を置く。開発の日々のコミットは統合ブランチ (v0.4 なら `develop-v0.4`) に積み、発行のたびに `early-access` へ取り込んでタグを打つ。理由: 更新はタグではなくブランチの最新へ進むので、ブランチの先頭は常に「出した状態」でなければならない (main と同じ規律)。

### 3-2. アーリーアクセス版に入るとき (安定版 → EA)

設定画面に切り替えの入口を置く。切り替えは**既存の更新の流れ (`update_engine.py` の run_update) に乗せる** — 独自の道を作ると、更新が持っている安全装置 (下記) を全部作り直すことになるため (発見 D1〜D3)。流れ:

1. **説明と同意**: 「試験中の版で、不具合を先に踏む役になること」「ワールドのデータは新しい形に進み、**次の安定版が追いつくまで安定版には戻れない**こと」を示し、同意を取る。
2. **ワールドの保存**: 切り替えの直前に `scripts/snapshot.py` で **ワールド全体 (DB も記憶も含む `~/.saiverse` 丸ごと) のスナップショット**を取る。戻れない一線を越える前の、唯一の巻き戻し手段になる。既存の更新も毎回これを取っているので、同じ流れに乗せれば自動で満たせる。起動時の DB バックアップ (`SAIVERSE_DB_BACKUP_ON_START`) は**この用途には使えない** — DB 単体しか写さず、10 世代で消え、しかも版の処理を適用した後に走る (発見 E)。切り替え時のスナップショットには専用の名前 (例 `ea_optin_*`) を付け、後から見分けられるようにする。
3. **切り替えの実体**: `git fetch` → 追跡設定つきのローカル `early-access` ブランチを作って切り替え → 依存の更新 → 再起動。切り替え前のブランチ名を記録しておき、途中で失敗したときの巻き戻しは**記録したブランチへ戻す** (今の巻き戻しはブランチ切り替えを知らず、今いるブランチの上で古い状態に戻すだけなので、そのままでは使えない — 発見 D1)。切り替えにも、更新と同じ「git の管理外ファイルを黙って上書きしない」保護 (`--no-overwrite-ignore`) と「手元に変更があれば拒否して該当ファイルを示す」検査を効かせる (発見 D3)。

### 3-3. 安定版に戻るとき (EA → 安定版)

- 戻れるのは「**安定版の最新が、手元のアーリーアクセス版と同じか新しくなったとき**」だけ。DB は前へ進む一方 (migrate に逆向きが無い) なので、古い安定版に戻すとワールドが読めなくなるため。「今より古い版では起動しない」は既存実装が既に守っている (`saiverse/upgrade.py` — 手元の記録より古い版で起動すると拒否)。
- その条件が満たされたら、設定画面に「安定版に戻る」の入口が現れる。実体は `main` への切り替え + 更新で、§3-2 と同じ安全装置を通す。
- 条件が満たされる前に戻りたい場合の答えは「入る前のスナップショットからの復元」で、切り替え時の同意画面に書いておく。ただし**復元はいま CLI (`snapshot.py restore`) しか道が無い** — 画面から復元できる道を作るかは未決 (§6-4)。

### 3-4. 更新チェックをブランチ対応にする

- 手元のブランチが `main` のとき: いままで通り `releases/latest` (プレリリース除外) を見る。**変更なし**。
- 手元のブランチが `early-access` のとき: リリース一覧をプレリリース込みで見て、いちばん新しい版と比べる。
- 版の比較 (`_compare_versions`) は現在ドット区切りの数字として比べるため、`0.4.0rc1` を **`0.4.0` より新しいと逆に判定してしまう** (「0-ea」のような部分を 0 に落とし、余った「1」が桁として足されるため)。アップグレードの鎖と同じ Python の版名規格 (`packaging.Version`) で比べる形に直し、**版の並べ方の基準を一つにする**。

### 3-5. 版の約束 (アップグレードの鎖) — 発行側の規律で守る

アップグレードの鎖 = 起動時にワールドを新しい版へ合わせる処理の列。各処理は「どの版からどの版へ」の一段 (辺) として登録され、途中の版の記録 (`LAST_KNOWN_VERSION`、単一の値) から目的の版まで**途切れず繋がっていないと起動が止まる**。この構造から、次の三つは仕組みが自動で守るものではなく、**発行のたびに守る規律**になる (発見 C):

1. **アーリーアクセス版の最初の辺は、発行時点の最新安定版から張る**。EA 期間中に安定版のホットフィックス (例 0.3.15) が出たら、**次の EA 版で最初の辺の基点をそこへ張り直し、ホットフィックスが足した処理も取り込む** (取り込まないと、EA のワールドではその処理が永遠に走らない)。
2. **正式版 (0.4.0) は、配った全 EA 版の辺をそのまま持ち続ける**。EA のワールドが正式版に上がるとき、そこから先の辺だけを踏む。二重に走らないのは「rc 版 < 正式版」の並びと版の記録が守る。
3. この規律は目視で守れる量ではないので、**鎖の検算テスト** (0.3.x → rc1 → rc2 → 0.4.0 の全経路で、隙間なし・二重適用なし) を発行前の関所として持つ (§7)。

### 3-6. 発行の自動化にプレリリースの印を教える

`.github/workflows/release.yml` を、**版名にプレ版の部分 (rc 等) を含むタグではプレリリースの印付きでリリースを作る**ように直す。これが §2 の「安定版ユーザーに誤って届かない」を成立させる前提で、**この修正が入るまで EA のタグは push しない**。

## 4. 何もしない安定版ユーザーを守る約束 (不変条件)

1. **安定版ユーザーには、何もしなければアーリーアクセス版が一切届かない** (通知にも更新にも ZIP の配布リンクにも現れない)。前提は §3-6。
2. **`early-access` ブランチの先頭は、常に発行済みの状態と一致する** (main と同じ規律)。
3. **アーリーアクセス版への切り替えは、ワールド全体のスナップショットと同意を経ずに起きない**。
4. **手元のブランチが、受け取る版を決める唯一の場所** (別の設定値を持たない)。

## 5. 実装の置き場と順序

- この仕組み自体は **develop (v0.3 系) に実装して、v0.3.x の安定版として先に配る**。v0.4 のアーリーアクセス版が出る日には、全ユーザーの手元に「入る口」が届いている状態にするため。
- `early-access` ブランチの新設と最初のタグは、v0.4 が出せる品質になった時点で行う (この intent の実装範囲には含めない)。

## 6. 裁定済みの論点 (2026-09-25 まはー)

1. **EA 期間中の安定版ホットフィックスの流れ**: main → develop → develop-v0.4 → (次の EA 発行時に) early-access の順に取り込む。EA への発行が一手増えるのは §3-5-1 の規律とセット。
2. **`early-access` への取り込みも PR にして、まはーが確認してからマージする** (配布ブランチは main と同じ扱い)。
3. **切り替え UI はグローバル設定に置く** (アップデートの自動検知や開発者モードと同じ場所。まはー「そこにあるし自然」)。
4. **スナップショットからの復元は画面からできるようにする** (本 intent の実装範囲。復元はサーバーを止めて別プロセスで行う型になる — 詳細は実装時に設計)。プログラマーでない利用者が「入る前に戻る」を自力で実行できることが、同意の実効性の条件。
5. **アーリーアクセス版のリリースノートも従来どおり丁寧に書く** (まはー「サボっても大した短縮にならない」)。
6. **版名は `0.4.0rc1` の形で確定** (§3-1 の理由)。画面の表示は「アーリーアクセス版」。

## 7. 実装後に通す検証

1. 隔離した clone を main に置き、プレリリースの印付きで EA を発行しても、通知が出ない・更新されない・`releases/latest/download/` の ZIP が安定版のままであること (不変条件 1)。
2. 同 clone で切り替え → ワールド全体のスナップショットが実在する → `early-access` の最新に進む → 以後の通知が EA 版を見ること。途中で失敗させたときに、元のブランチへ戻ること (§3-2-3)。
3. EA 版より新しい安定版を発行 → 「安定版に戻る」が現れて main へ戻れること。
4. 版の比較が `0.4.0rc1 < 0.4.0` を正しく並べること (単体テスト)。
5. アップグレードの鎖の検算テスト: 0.3.x → rc1 → rc2 → 0.4.0 の全経路で隙間なし・二重適用なし (§3-5-3)。
6. ZIP からインストールした手元 (セットアップが git フォルダに整えた状態) でも、切り替えが同じ道で通ること。

## 8. 経緯

- 2026-09-25 (裁定): 未決 5 点と版名を確定 (§6)。UI はグローバル設定、リリースノートは丁寧に、他はメティスの見立てどおり。実装は二段 — 第一段 = 仕組み一式 (切り替え・通知・発行の自動化・版の比較・鎖の検算)、第二段 = 画面からの復元。
- 2026-09-25: v0.1 起草。言葉づかい検査 (agy) と整合性検査 (Opus) を実施。整合性検査が重大 3 件 (A: 発行の自動化がプレリリースの印を付けない / B: `-ea.N` の版名は起動時の版解析が受け付けない / C: 鎖の二重適用防止は発行側の規律) と、切り替えを既存の更新の流れに乗せるべき根拠 (D1〜D3: 巻き戻し・追跡設定・管理外ファイルの保護)、スナップショットが正しい保存手段であること (E) を発見。v0.2 に反映。関連する既存の穴として「システムに git が無く同梱の PortableGit だけの環境では、画面からの更新が git を見つけられず断られる可能性」も見つかった (別件、issue 化候補)。
