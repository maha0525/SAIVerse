# エラーで発言が生まれなかった回を、部屋の記録に残す

ステータス: 設計中 (2026-11-19 起草。方向はまはーが同日に決めた — 下の「まはーが決めたこと」。それ以外はメティスの設計で、未決の問いは末尾の「まはーに決めてもらうこと」)

## 要点

ペルソナが喋るはずだった実行が、エラーで一言も発言を残さずに終わったら、その部屋の記録に一行を置く。本文には理由を含まない一文を書き、ペルソナに届ける。原因の詳細は同じ行の `metadata` に置き、画面だけがそれをユーザーに見せる。

## 背景

2026-11-19 の朝、エリス (`eris_city_a`) の 9:00 のスケジュールが実行され、LLM が 400 (`context_length_exceeded`) を返して、エリスは何も喋らなかった。部屋の記録にもエリスの記憶にも何も残らず、起きたことは `backend.log` にしか記録されていなかった。

洗い出しの結果は [no_utterance_errors_are_log_only.md](../issues/no_utterance_errors_are_log_only.md) にある。要点は三つ。

- スケジュールと外部イベント (`inject_persona_event`) の経路は、ほぼすべての失敗がログだけに残る。
- ユーザーがチャット (Web の画面、またはアドオンの音声入力) から話しかけたときは、ブラウザで見ている間だけ、画面にエラー表示が出る (NDJSON のイベントで届く。再送ボタンへの案内つき)。このエラー表示は保存されないので、次の操作や再読込で消え、ペルソナは失敗を知らない。ブラウザで見ていない回 (アドオンの音声入力、画面を閉じた後) はログだけになる。
- ペルソナが忙しい間に来た実行は処理待ちの列に入り、後で別のスレッドで走る。その実行の失敗は、結果を見ている者が誰もいない。

## まはーが決めたこと (2026-11-19)

原文のまま引く。

3. 「ペルソナにはエラーで発言失敗したってことだけ見せて、ユーザーにだけ詳細が見える形の方がよさそうだね。」 — メティスが、[reply_stop_exit.md](reply_stop_exit.md) の「通告の内容」の節の判断 (エラーの中身、特に安全性フィルターの理由をペルソナの記憶に書くと、「自分の発言は禁止内容と判定された」という自己像を植え付ける) を示したことへの返事。

## この設計で保証すること (メティスの設計。問いへの答えで変わりうる)

1. **エラーで発言が生まれなかったら、その部屋の記録に一行が残る。** きっかけ (ユーザーの発言・スケジュール・外部イベント・処理待ちの列から繰り上がった実行) を問わず、ブラウザで見ているかどうかも問わない。例外は下の「この設計の対象外になる失敗」と「判定の限界」に書く。
2. **ペルソナには、失敗したという事実だけが届く。** エラーの種類 (会話の長さの上限超過・利用制限・安全性フィルターなど) は届かない (まはーの決めたこと 3)。ただし、ユーザー自身の操作が原因の回 (サーバーの停止、問い 2) は、中断を知らせる行に「ユーザーの操作により、」と原因が書かれているのと同じく、原因を本文に含める。
3. **行は、部屋に居合わせた全員に届く** (まはーの決定、下の「問いへの答え」の 0)。喋ろうとして喋れなかったことは、同じ部屋にいれば目撃しているはずの出来事で、声が届いたかどうかとは関係がない。周りのペルソナが気づいて助けられる余地を残す。
4. **ユーザーには、原因と詳細が見える。** チャット画面のその行に、何が起きたかが日本語で出る。再読込しても消えない。
5. **一回の実行につき、置かれる行は多くても一行。** 途中まで喋ってから止まった回は、既存の仕組みで、発言の後ろに中断を知らせる行が置かれる。この行は、部屋で起きた出来事を書く行 (`role: "host"`。入退室の知らせなどにも使われている) で、[reply_stop_exit.md](reply_stop_exit.md) では「中断の通告」と呼ばれている。その回には今回の行を追加しない。
6. **エラーではない沈黙には置かない。** ペルソナが外部イベントへの反応の判断で「何もしない」「メモだけ残す」を選んだ回、ユーザーが停止ボタンで止めた回 (`interrupted_by="user_stop"`)、新しい発言や優先度の高い要求に割り込まれた回 (`interrupted_by` が `"user"` など。割り込まれた要求は処理待ちの列に戻って後で走る) がこれにあたる。

### 出力例 (今朝のエリス)

部屋の記録 (画面に出る行):

> (エラーにより、エリスは発言できませんでした)
> 詳細: 会話の長さが、使っているモデル gpt-4o-2024-11-20 の上限を超えました。モデルの返したエラー: This model's maximum context length is 128000 tokens. However, your messages resulted in 159608 tokens.

エリスの記憶に届く形 (取り込み処理 `auto_ingest` が、部屋の名前を先頭に付けて、role=system のシステム通知として記録する):

> [エリスの部屋] (エラーにより、エリスは発言できませんでした)

エリスの記憶では、この行の直前に、9:00 のスケジュールの指示文 (「スケジュールの実行時刻です。」で始まる文) が残っている。スケジュールの指示文は、Playbook が走る前に、role=system のシステム通知として記憶へ書かれるため (`sea/runtime.py:420-436`)。だから次に喋るとき、エリスは「9 時に何かを言おうとして、言えなかった」ことを読める。

詳細の一行目 (「会話の長さが…上限を超えました」) は、今の `LLMError` のエラーの種類からは出てこない。会話の長さの上限超過を表す専用のエラーの種類は無く、今は `InvalidRequestError` の「リクエストが不正です」系の文になる。この種類と文面を足すことも今回の改修に含める (下の「あわせて直す不具合」の 5)。

本文の文面は原案で、後から調整してよい。

## 全体の流れ

```
きっかけ (ユーザー発言 / スケジュール / 外部イベント /
          再起動後に実行の記録から拾い直された外部イベントへの応答)
  → PulseController.submit / submit_user
      ├─ すぐ走る ─────────────────────┐
      └─ 忙しい → 処理待ちの列 → 後で別スレッド ─┤
                                        ▼
  PulseController._execute_unlocked  ← この中で一回だけ確かめる (開始時刻を覚える)
      → _do_execute → run_meta_user
          → (ユーザー発言は既に部屋の記録にある / スケジュールの指示文を記憶へ書く)
          → Playbook → LLM → 失敗
          → settle_reply_stop: 何か保存されていれば、中断を知らせる行を置く (既存)
      ← 結果 (runtime_outcome)・例外・request に新しく足す項目 (発言できなかった理由) が戻る
      → この実行の開始より後に、このペルソナの発言が保存されたかを確かめる
        保存が無く、エラーで終わっていたら、部屋の記録へ host の行を一行置く
  → 部屋の記録 (building_messages)
      → 画面: チャット履歴の定期的な取り直し (frontend/src/lib/chatPolling.ts) で、行と詳細が出る
      → ペルソナ: 次の Pulse の取り込み処理 (auto_ingest) で記憶へ届く
```

## 置き場所 — `PulseController._execute_unlocked`

確かめる処理は `sea/pulse_controller.py` の `_execute_unlocked` (いま 589-675 行) に一回だけ置く。

- **全部のきっかけがここを通る。** ユーザーの発言・スケジュール・外部イベント・再起動後に拾い直された外部イベントへの応答・処理待ちの列から繰り上がった実行・中断からの再開。拾い直しに使うのは実行の記録 (`execution_ledger`。スケジュールや外部イベントへの応答の実行がどこまで進んだかを残す表で、再起動後にやり残しを拾い直すのに使う)。処理待ちの列の分は、ここ以外では誰も結果を見ていない。
- **自律行動の判断は自然に外れる。** 判断点 (`saiverse/judgment_points.py`。一日の始まりと終わりや外部イベントの時点で、判断の Playbook を走らせる仕組み) の実行は、`submit_meta_judgment` から `_submit_meta_lane` という別の経路を通り、`_execute_unlocked` を通らない。判断の Playbook はそもそも発言しない。
- **「発言が生まれたか」を確かめる材料が既にある。** `sea/runtime_emitters.py` の `last_saved_utterance(persona_id)` は、ペルソナが最後に発言を保存した時刻を持っていて、保存の成功判定を一箇所にまとめた `notify_speak_persisted` だけがこれを更新する。`_execute_unlocked` の開始時刻と比べれば、この実行の中で発言が保存されたかが分かる。中断を知らせる行を置く処理 (`settle_reply_stop`) も同じ記録を参照するが、そちらの起点は `run_meta_user` の中の `_reply_started_at` (`sea/runtime.py:489`) で、`_execute_unlocked` の開始より少し後になる。起点が早い分、今回の確認ではより広い時間を「この実行の中」とみなすので、中断を知らせる行が置かれた回 (保存あり) に今回の行も置く、ということは起きない (上の「この設計で保証すること」の 5)。
- **書き込みは既存の関数を使う。** `sea/runtime_llm.py` の `_record_interruption_notice` が `role: "host"` の行を置いている。この関数に、原因の詳細 (`metadata`) と、記憶へ届ける相手の一覧 (`heard_by`) を渡せるようにして使う (関数名は役目に合わせて改める)。置く部屋は `request.building_id`。

同じ型の先例: ユーザーがチャットから話しかけた経路の「何も届かなかった回」の確認は、入口を数え上げずに `backend_worker` の `finally` に一つだけ置いた ([user_utterance_path_failure_inventory.md](../issues/archive/user_utterance_path_failure_inventory.md) の「束 2 — 無言をなくす (バックエンド)」)。入口を数え切る守り方は必ず漏れる。

### 判定の限界

`last_saved_utterance` はペルソナごとの記録で、実行ごとの記録ではない。同じペルソナの別の実行が、この実行の最中に発言を保存することがある。割り込まれた古い実行の残りや、作業セッション (時間割のコマで、ペルソナが一人で作業する時間。`sea/work_session.py`) の中で唱えた `tell` (宛先を決めて、その場で声をかける Spell) がそれにあたり、[reply_stop_exit.md](reply_stop_exit.md) の「事実の記録」の節も同じ重なりを挙げている。この場合、この実行がエラーで何も残さなかったのに「保存あり」とみなし、行は置かれない。そのときの部屋の記録では、そのペルソナの最後の吹き出しはその別の実行の発言になる。中断を知らせる行と同じ割り切りで、この設計でも受け入れる。

## 何を「エラー」と数えるか

`_execute_unlocked` が受け取る終わり方 (`request.runtime_outcome`) ごとに決める。

| 終わり方 | いまの扱い | この設計での扱い |
|---|---|---|
| `error` (LLMError を含む、Playbook 内の例外すべて) | ログだけ (ユーザーがチャットから話しかけた回は、ブラウザで見ていれば画面のエラー表示) | **置く**。モデルが無い・繋げない回 (`ModelUnavailableError`) も含むかは問い 0 |
| `completed` だが、再試行しても LLM の応答が空だった | `sea/runtime_llm.py:6973-6977` が「空のまま進む」とログに書き、例外を出さずに終わる。外からは意図した沈黙と区別できない | **置く**。ただし `runtime_outcome` は `completed` のまま変えない。「空の応答で終わった」ことを `request` の新しい項目に記録しておき、今回追加する確認の処理でだけ参照する |
| `completed` だが、指定された Playbook が見つからなかった | `sea/runtime.py:439-449` がエラー文の一覧を返し、呼び出し元の多くはそれを捨てる | **置く**。同じく `runtime_outcome` は変えず、`request` の新しい項目に記録する |
| `cancelled` (`interrupted_by="user_stop"`、停止ボタン) | 何も残らない (2026-08-26 の決定) | **置かない** — ユーザー自身の操作で、本人は知っている |
| `cancelled` (`interrupted_by` が `"user"` などの割り込み) | 割り込まれた要求は処理待ちの列に戻って後で走る | **置かない** — 発言はまだ失われていない |
| `cancelled` (`interrupted_by="server_shutdown"`) | 何も残らない。スケジュールは、分類のコード (`saiverse/schedule_manager.py:1058-1059`) から見ると `accepted` として済んだ扱いになり、次の予定時刻へ進んで、その回は失われる (動かして確かめてはいない) | 問い 2 |
| `gate_closed` — このペルソナ宛ての未配送の記録 (`pending`) を配れず、実行を始められなかった (`BeatGateClosedError`)<br>`floor_unmet` — あらすじの最低限の範囲 ([arasuji_levels.md](arasuji_levels.md) §15-5) を用意できず、実行を始められなかった (`WindowFloorUnmetError`) | ユーザーがチャットから話しかけた回は画面のエラー表示。ほかの経路は WARNING / ERROR のログで、スケジュールは 120 秒おきに 3 回まで自動で再実行される | 問い 1 |

空の応答の回と、Playbook が見つからなかった回で `runtime_outcome` を変えない理由: 実行の記録 ([execution_ledger.md](execution_ledger.md) §2.5) に書くとき、`saiverse/schedule_manager.py:1056-1073` の処理は `runtime_outcome` の値で結果を分けている。`completed` は済んだものとして次の予定時刻へ進み、`error` は「どう終わったか分からないので自動で再実行しない」(`unknown`) になる。ここを `error` に変えると、一回きりのスケジュールの扱いまで変わる。今回の目的は「起きたことを残す」で、再実行の方針を変えることではないので、実行の記録の分け方には触らない。

2026-08-26 に「一言も出ないうちに止められた回」を記録しない形へ変えたときの理由は、`sea/pulse_controller.py:623-635` のコメントの原文で「そちらには昔から何も書いておらず、中断だけ機構の声を足すと、そこだけ不揃いになる」だった (「そちら」は返事が生まれなかった回、「機構の声」は host の行のこと)。この設計は、エラーの回についてその前提を変える。停止ボタンの回を記録しない結論は、理由を「ユーザー自身の操作だから」に置き換えて残る。

## あわせて直す不具合 (メティスの提案。まはーの了承待ち — 問い 5)

洗い出しで見つかった、「発言が生まれない」状態を引き起こしている不具合。`_execute_unlocked` で確かめるだけでは塞がらないので、同じ改修に含めたい。

1. **部屋の 1 人目が LLMError で失敗すると、2 人目以降が走らない。** `manager/runtime.py:858-935` で、LLMError を捕まえる try が for ループの外側にある。モデルが無い回 (`ModelUnavailableError`) と同じく、ペルソナごとに捕まえて次のペルソナへ進む形にする。一人の不調で全員を止めない ([persona_model_selection.md](persona_model_selection.md) の決まったこと 2 と同じ理由)。
2. **処理待ちの列から走った実行の例外が、ログにすら入っていない可能性が高い。** 別スレッドの `run()` (`sea/pulse_controller.py:769-772`) が、`_execute_unlocked` がそのまま呼び出し元へ投げ直した `LLMError` を受け止めず、スレッドの未処理例外になる。リポジトリに `excepthook` の設定は無い。`run()` で例外を受け止めてログへ書く (部屋の記録への行の追加は、`_execute_unlocked` の中の確認の処理で行う)。
3. **外部イベントの失敗が、ログ上で成功と記録される。** `inject_persona_event` は失敗時に文字列 `"error: pulse submission failed"` を返すが、`phenomena/manager.py:183` は戻り値を見ずに `completed successfully` を出す。戻り値を見てログを分ける。
4. **再試行しても空だった応答** と **見つからなかった Playbook** を、上の表のとおり `request` の新しい項目に記録する。
5. **会話の長さの上限超過を、`LLMError` のエラーの種類の一つとして分ける。** 今は `InvalidRequestError` に入る。上限超過はよくある失敗で、ユーザーができること (上限の大きいモデルへ切り替える) がはっきりしているので、専用の文面を持たせる。

Discord ゲートウェイの経路 (呼び出しの引数の数が合っていない — `discord_gateway/saiverse_adapter.py:111` は 1 引数、`manager/gateway.py:60-62` の定義は 2 引数) は、[persona_model_selection.md](persona_model_selection.md) の決まったこと 9 で「手を入れないもの」(レガシーで、現在は動作しない見込み) になっているので、この設計でも扱わない。

## この設計の対象外になる失敗

`_execute_unlocked` に届く前に終わる失敗は、そこで確かめられない。

- **書く部屋が決まらない失敗** — スケジュールや外部イベントの対象のペルソナが居ない、現在地が無い回と、ユーザーがチャットから話しかけた経路で会話を始める前提 (ペルソナ・建物・`run_sea_user`) が揃わない回 (`saiverse/user_conversation.py:702-728`)。これは世界の設定の異常で、部屋に書けない。問い 3。
- **部屋は決まっているが、実行に入る前に断られた失敗** — 終了処理中の受付拒否 (`sea/pulse_controller.py:420-427` ほか)、処理待ちの列のあふれ (`:543-549`、10 件超)、終了処理での処理待ちの列の破棄。処理待ちの列のあふれは書く部屋が `request` から分かるので、同じ書き込みの関数をそこからも呼ぶ。終了処理中の二つは問い 2 と同じ扱いにする。

## 画面

- 部屋の記録の `host` の行は、今もシステム通知として表示されている (`frontend/src/app/page.tsx:3920`)。行の `metadata` にある詳細を、チャット履歴の API (`api/routes/chat.py` の `ChatMessage`) に項目を一つ足して画面へ渡し、行の下に出す。「言い切っていない」印 (`ChatMessage.interrupted`) を渡しているのと同じ形。
- 詳細には、`LLMError` とそのエラーの種類 (`llm_clients/exceptions.py`) が持つ `user_message` と、モデルが返したエラーの原文を出す。ユーザー向けの文面を持っているのはこのエラー群だけ ([user_utterance_path_failure_inventory.md](../issues/archive/user_utterance_path_failure_inventory.md) 段 6 の観察)。
- 新しい行を追加しても、再送ボタンを出すかどうかの判定 (`database/building_messages.py` の `_has_assistant_reply_after`) には影響しない。この判定は `assistant` の行だけを応答として扱い、`host` の行は対象外にしている (2026-11-19 にコードで確認)。

## 問いへの答え (2026-11-19 まはー)

## まはーに決めてもらうこと (答えが出る前の記録。答えは上の節)

**問い 0: モデルが無い・繋げない回も含めて書くか。書くなら、届けるのは本人だけか、部屋の全員か。**
上の「既存の決まりとの関係」のとおり、モデルが無い回は「建物の記録にもペルソナの記憶にも書かない」と決まっている。理由は「同じ部屋のペルソナの記憶にまで写る」こと。
メティスの推奨: 含める。そのうえで、行が届くのは発言できなかった本人だけにする (記憶へ届ける相手の一覧 `heard_by` を本人に絞る)。部屋の記録には残るので画面には出る。途中で止められた発言は、他のペルソナも「途中で切れた」ことを目撃しているので、中断を知らせる行は全員に届けている (2026-08-26 のまはーの判断)。一方、一言も出なかった回は、他のペルソナからは何も起きていないように見えるので、目撃したことにならない。これで 9/12 の決まりの理由 (他のペルソナの記憶に写る) は解消し、書き換わるのは「本人の記憶にも書かない」の部分だけになる。

**問い 1: 自動でやり直される失敗 (`gate_closed`・`floor_unmet`) にも、毎回置くか。**
スケジュールはこの二つで失敗すると、120 秒おきに 3 回まで自動で再実行される。毎回置くと、同じスケジュールについて「発言できませんでした」が最大 4 行並ぶ。どちらもスケジュールの指示文を記憶へ書く前に止まる (Playbook も走っていない) ので、ペルソナから見ると「聞いた覚えのないことで失敗した」行になる。実行の記録から拾い直された外部イベントへの応答にも、同じような自動のやり直しがある (`saiverse/autonomy_wiring.py:1461-1483` の `_dispatch_recovered_response_with_retry`)。
メティスの推奨: 自動のやり直しがある経路 (スケジュールと、拾い直された外部イベントへの応答) では、やり直しが尽きたときに一行だけ置く。やり直しが無い、ユーザーがチャットから話しかけた経路では、その場で置く。やり直しの上限に達したかどうかを判定しているのは `ScheduleManager` (`saiverse/schedule_manager.py:909-919`) と `_dispatch_recovered_response_with_retry` (`:1412-1427`) なので、書き込みの関数をそれらの箇所からも呼ぶ。

**問い 2: サーバーを止めたことで生まれなかった発言にも置くか。**
実行中や処理待ちの列にあった発言が、サーバーの停止で失われる回。止めたのはユーザーなのでエラーではないが、ペルソナから見ると、言おうとしたことが黙って消える。途中まで喋っていた回には、サーバーを終了するときの処理で、既に中断を知らせる行が置かれるようになっている。
メティスの推奨: 置く。本文を「(サーバーの停止により、エリスは発言できませんでした)」にして、途中まで喋った回の扱いと揃える (ユーザーの操作による原因なので、「この設計で保証すること」の 2 の例外として本文に書く)。

**問い 3: 書く部屋が決まらない失敗を、どこに出すか。**
ペルソナが居ない・現在地が無いせいでスケジュールが走れなかった回は、部屋の記録に書けない。
メティスの推奨: 画面上部のお知らせのバナー (`GET /api/system/alerts`、`manager.startup_alerts`) に出す。ただしこの仕組みは今、起動時に積んだお知らせを、画面がバックエンドに繋がったときに一度だけ取りに行く作り (`frontend/src/components/SystemAlertBanner.tsx:77-79`) で、次の起動で消える。実行中に積んだお知らせを出すには、画面が取り直すきっかけを足す改修が要る。

**問い 4: ユーザーがチャットから話しかけて失敗したとき、今の画面のエラー表示と新しい行が両方出てよいか。**
ブラウザで見ている間に失敗すると、今の画面のエラー表示 (再送ボタンへの案内つき、次の操作で消える) と、新しい部屋の記録の行が同時に出る。
メティスの推奨: 両方出す。画面のエラー表示は「いま何ができるか」の案内で次の操作で消え、部屋の記録の行は「何が起きたか」の記録で残る。役目が違う。

**問い 5: 「あわせて直す不具合」の 5 件を、同じ改修に含めてよいか。**
メティスの推奨: 含める。どれも「発言が生まれない」状態を作っている箇所で、別々に直すと、今回の確認の置き場所と同じ判断が二箇所に分かれる。
