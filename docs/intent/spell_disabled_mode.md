# Intent Document: スペル不使用モード

**ステータス**: 検証待ち (2026-09-14 起草・同日実装、実機検証待ち)
**出発点**: ユーザーからの実測報告 — アップデート後、会話 1 回のトークン数が 15,000〜30,000 から 65,000〜71,000 に跳ね上がった（[head_prompt_followups.md](../issues/head_prompt_followups.md) の 2026-09-09 追記と同系の報告）。スペルを一切使わないユーザーにとって、スペルのスキーマ全部と、スペルが前提の説明（アイテム・Playbook・URI・記憶操作）は毎ターン送られる純粋な無駄になっている。

**設計の最優先はユーザーにとっての分かりやすさ（2026-09-14 オーナー裁定）**: UI では「スペル不使用モード」という名前のモードとしてはっきり見せ、切り替えは保存した時点で即反映する。キャッシュ効率の作法（作り直しの契機を増やさない）よりもこちらが優先 — 切り替えのコストは注意書きで正直に伝える。データベース上の実体は既存の `AI.SPELL_ENABLED` 列で、新しい列や内部概念は増やさない（§4-1）。

**効果の届き方に注意**: 本変更は「スペル 無効」に**切り替えたペルソナ**のトークンを減らす。既定は有効なので、報告者のトークンは本人が設定を切り替えて初めて減る。有効のまま使うペルソナ向けの軽量化は別件（[head_prompt_followups.md](../issues/head_prompt_followups.md) のスペル一覧ダイエット）が担う — 同じ報告に対する別々の処方で、どちらか一方では解決しない。

---

## 1. 芯（専門用語なしの要約）

ペルソナ設定に「スペル不使用モード」を用意する。選ぶと、スペルの使い方・道具の一覧・アイテムの説明など「スペルがあるから意味を持つ文章」がシステムプロンプトから全部消え、会話だけのペルソナは以前の軽いトークン消費に戻る。切り替えは保存した時点ですぐ反映される。切り替えるとそのペルソナのプロンプトキャッシュは積み直しになるので、UI にその注意を明示する。

## 2. 全体像（誰が何に頼れるか）

- **ユーザー**: 会話専用のペルソナは「スペル 無効」にすれば安く運用できる、に頼れる。切り替えのコスト（キャッシュ積み直し）が UI に書いてあることに頼れる。
- **ペルソナ**: 自分のシステムプロンプトに「実際には使えない能力の説明」が載らないことに頼れる。使えないスペルの説明を読んで /spell を唱えて空振りする、という自己像の混乱が起きない。
- **スペル有効のペルソナとそのユーザー**: 本変更で何も変わらないことに頼れる — システムプロンプトの文章は 1 バイトも変わらず、キャッシュも切れない（§4-2）。
- **保守者**: 「スペルが使えるか」の判定が一つの実装に集約されていて、節（section）ごとに判定がばらけないことに頼れる。

### 経路の全体

```
SettingsModal（スペルを使う/使わない） → AI.SPELL_ENABLED (DB)
  → 保存で値が変わったら SPELL_TOGGLED を発火（manager/admin.py の update_ai →
     saiverse/dynamic_state.py の on_spell_toggled → head pipeline）
  → gate を持つ section が一斉に再 capture = その場で反映（判定結果は capture の
     時点で snapshot に焼き込まれる）
  → 会話
  → 取りこぼした Session（別モデルの head）は次の Metabolism で揃う
実行側: spell loop / realtime spell は _spell_enabled の判定で既に止まる（W10 監査 =
  2026-08-16 のスペル残穴監査、docs/handoff/2026-08-16_w10_spell_audit_remnants_handoff.md）
  → 残っていた抜け穴 = pre_spells（チャット UI「ツール指定」・スケジュール由来）を本変更で止める
```

## 3. 現状と欠陥

`AI.SPELL_ENABLED` は既に存在し、無効にするとスペル一覧（スキーマ込み）は 2 行の断り書きに縮む。実行側も spell loop・realtime spell は `_spell_enabled` の判定で止まる。しかし**説明の側**が残っている:

| 場所 | 無効でも残っている文章 | 分量の目安 |
|---|---|---|
| common.txt (`CommonPromptSection`) | 能力（スペルとPlaybook）/ SAIVerse URI / 記憶のスペル操作・URI 一覧 / アイテムシステム / building_move の一文 | 約 2,300 字 |
| `AvailablePlaybooksSection` | 「## 利用可能なPlaybook」全一覧（run_playbook スペルで起動、と書いてある） | Playbook 数に比例 |
| `AutonomyModesSection` | 「## モード」（メインモード/分身モード。分身は run_playbook 前提） | 約 450 字 |
| `MemopediaIndexSection` | 「memory_read で読んでください」の指示文 | 1 文 |
| `DeskSection` | ページが開いているとき「自分で memory_open して〜 memory_close で棚に戻せます」の指示文（ページは UI からも開けるので、スペル無効でも空とは限らない） | 2 文 |
| 実行経路の抜け穴 | `pre_spells`（ツール指定モード・スケジュール・inject_persona_event 由来）は `_spell_enabled` を見ずに実行される | — |

使えない道具の説明はトークンの無駄であると同時に、ペルソナに「持っていない能力を持っている」と読ませる人格上の害でもある（autonomy_modes が 2026-09-01 に「存在しない機能の説明を外した」のと同じ理由）。

## 4. 設計

### 4-1. UI では名前のあるモード、内部では既存の列

UI はこの状態を「スペル不使用モード」という名前で見せる（オーナー命名、2026-09-14）。ユーザーが「これを選べば会話専用で安くなる」と一目で分かることが要件。内部の実体は既存の `AI.SPELL_ENABLED=false` で、新しい DB 列・内部概念は増やさない — 変更は「無効時に消えるものを、実態に合わせて全部にする」ことと「見せ方と反映を分かりやすくする」こと。

### 4-2. キャッシュへの影響

**最重要の不変条件: スペル有効のペルソナのシステムプロンプトは、本変更の前後で 1 バイトも変わらない。** common.txt への変更はマーカー行の挿入だけで、既存行の文言・移動・分割は一切行わない（「同じ意味」では足りない — 1 バイトでも変われば、リリースの瞬間に有効ペルソナ全員のキャッシュが積み直しになる）。§7 にこの検算を置く。

- **切り替え（平常運用）**: **保存した時点で即反映**（2026-09-14 オーナー裁定 — 「次の記憶整理で反映」はユーザーには意味が取れないため、分かりやすさを優先して却下された）。保存時に切り替え専用の作り直しイベント（SPELL_TOGGLED）を発火し、gate を持つ全 section（§4-5 の表 + スペル一覧）が**一斉に**作り直される。その瞬間にプロンプトの先頭（common_prompt）から文章が変わるため、そのペルソナの全ラインのプロンプトキャッシュは積み直しになる — モード切り替えの本質的なコストで、UI の注意書きが伝える（§4-8）。頻繁な切り替えを機構で防ぐことはしない。設定値が変わらない保存では発火しない。
- **一斉であることが要**: 反映契機は SPELL_TOGGLED（即時）と Metabolism（全 section 再構築）の二つだけで、どちらも gate を持つ全 section を同時に作り直す。「一部の section だけ先に変わった中途半端なプロンプト先頭部」は生じない。SYSTEM_PROMPT_EDITED / ADDON_LOADED / ADDON_UNLOADED のイベント宣言は存在するが、いずれも現在発火元が無いことを確認済み（dispatch は building_entered と metabolism のみ）。
- **リリース適用の初回だけの過渡期**: builtin common.txt のファイルが変わると、テンプレートの指紋比較で common_prompt だけが次の head 構築時に先に作り直される（欠損補充の仕組みは欠けた section だけを埋める）。スペル**有効**のペルソナは作り直しても文章が同一バイトなので、キャッシュもプロンプトも何も変わらない。リリース前から既にスペル無効にしてあったペルソナだけ、①適用直後に common.txt 由来の説明が消え（ここでキャッシュ積み直し 1 回目）、②次の Metabolism で Playbook 一覧・モード解説などが消える（2 回目）、という二段階になる。①と②の間はスペル説明の消え方が不揃いだが、一度きりの過渡期として許容する（§6）。リリース後にモードを切り替えた場合は SPELL_TOGGLED が一斉に反映するので、この不揃いは起きない。

### 4-3. 判定の一本化

`AI.SPELL_ENABLED` を DB から引く実装は現在 `SpellListSection._resolve_enabled` と `SEARuntime._is_spell_enabled_for_persona` にある。head 側は**共有ヘルパー 1 本**（`sea/head_pipeline/spell_gate.py`）に集約し、判定を使う全 section が同じものを使う（節ごとに判定を書き写すと、片方だけ直した日に食い違う）。

### 4-4. common.txt の条件ブロック

テンプレートに行単位の条件マーカーを導入する。**両方向**:

```
{if_spell_enabled}
（スペルが使えるときだけ載る行）
{end_if_spell_enabled}
{if_spell_disabled}
（スペルが使えないときだけ載る行）
{end_if_spell_disabled}
```

- マーカー行は単独行。`CommonPromptSection` の capture 処理が spell_enabled を解決し、該当しない側のブロックをまるごと削除、該当する側はマーカー行だけ削除して中身を残す。
- **対応が取れていない（開きっぱなし・閉じだけ・入れ子・交差）マーカーは fail-safe**: 中身を全部残してマーカー行だけ落とし、警告ログを出す。人格を担う文章を、テンプレートの書き損じで黙って落とさないため。
- マーカーを含まない既存のユーザー上書きテンプレート（user_data/prompts/common.txt）は挙動が一切変わらない（全文が両方の設定で載る）。裏返すと、上書きしているユーザーには本変更の節約が届かない（§6）。
- 無効側ブロックが要るのは「記憶」の節だけ（下記 3）。有効側の行を 1 バイトも動かさずに、無効ペルソナにも通じる導入文を与えるには、共通の文を無効側ブロックに書き直して置くしかない（数文の重複を許容 — §6）。

builtin の common.txt への変更（**すべてマーカー行の挿入のみ**）:

1. 「## 能力（スペルとPlaybook）」全体を有効側ブロックで囲う
2. 「## SAIVerse URI」全体を有効側ブロックで囲う
3. 「## 記憶」: 見出し行は共通のまま。本文の全行（スペルで想起する指示・URI 一覧・地図帳の動詞・コア記憶の節を含む現在の全部）を有効側ブロックで囲い、無効側ブロックを追加してこう書く:
   - 「あなたを形づくるのは、あなたの過去すべての体験です。ただし、いまこのコンテキストに載っているのはそのごく一部にすぎません。それらしい内容をでっち上げて覚えているフリをすることは厳禁です。思い出せないときは、思い出せないと正直に伝えてください。」
   - 「会話に関連する記憶は「ふと浮かんだ記憶」として自動的に意識に上ってきます。無理に思い出そうとしなくても、必要な断片は勝手に浮かんできます。」
   （= でっち上げ禁止と自動想起はスペルが無くても真なので、無効ペルソナにも残す。コア記憶の定義文は消えるが、コア記憶がある個体には head の「## コア記憶（自分で選んで刻んだ、常に携えている知識）」見出しが役割を自己説明する）
4. 「## アイテムシステム」全体を有効側ブロックで囲う
5. 「## Buildingシステム」の「建物間の移動は `building_move` Playbookで行います。」の一文だけ有効側ブロックで囲う

### 4-5. section の gate（capture で焼く）

head の設計原則（cached_head_architecture.md: render は snapshot のみを見る。ペルソナごとの状態は capture の時点で snapshot に書き込む）に従う。`SpellListSection` が既にやっている形と同じ。なお autonomy_modes のコード内コメント「ここにゲート（条件分岐）を足してはならない」は、render 時の動的分岐と用途別の出し分けを禁じたもの — capture 時にペルソナ単位の DB 設定を snapshot に焼き込む形は (persona, model) 固定を壊さず、禁止の対象ではない。実装時にこのコメント自体を射程が分かる文に書き直す。

| Section | 無効時の挙動 | 備考 |
|---|---|---|
| `CommonPromptSection` | §4-4 のブロック処理を capture 時に適用 | snapshot は展開済みテキストなので型は不変 |
| `AvailablePlaybooksSection` | capture 処理では一覧取得を行わず、空を snapshot に書く → render は None | snapshot に `spell_enabled` を追加（旧 snapshot は有効扱いで互換） |
| `AutonomyModesSection` | 「## モード」の代わりに、スペルと無関係な事実だけを残した短い定数を出す: 「## 発言の扱い」— 発言は Building 内に発声され UI に表示される / 同席ペルソナに知覚される、の 2 文（メインモード解説から機械的に抜き出した文。分身モードは run_playbook 前提なので丸ごと消す） | snapshot に `spell_enabled` を追加。deserialize 処理では本文を定数から組み直す現行方針のまま、フラグだけ保存値を使う（旧 payload は有効扱い） |
| `MemopediaIndexSection` | 「ページの本文まで読みたい場合は memory_read で読んでください。」の一文を落とす（目次自体は自動想起の手掛かりとして残す） | snapshot に `spell_enabled` を追加 |
| `DeskSection` | 見出しとページ本文は残し、「自分で memory_open して〜 memory_close で棚に戻せます。」の指示文だけ「机が溢れると自動的に棚へ戻る」旨の文に差し替える。ページを消さないのは、ページが UI からも開けるものであり（API 経由の机操作は SPELL_ENABLED を見ない）、内容はペルソナの記憶だから | snapshot に `spell_enabled` を追加 |
| `SpellListSection` | **変更なし**（無効時の 2 行の断り書き「スペルは現在使用できません。/spell コマンドを使用しないでください。」を維持） | 過去履歴に /spell がある個体の模倣を抑える現役の安全装置。約 40 トークンで、節約目的に対して無視できる |

### 4-6. 切り替え時の通知はスペル一覧 section が一手に担う

切り替えの通知（「スペル機構が無効になりました / 有効になりました」）は `SpellListSection.diff_to_notifications` に既に実装されている。他の gate 付き section は **有効/無効の反転そのものでは差分通知を出さない**:

- `AvailablePlaybooksSection`: old と new の `spell_enabled` が異なるときは空を返す（さもないと全 Playbook 分の「使えなくなりました」が一度に並ぶ。実際に起きたことは「スペル機構ごと無効になった」の一言で尽きている）。このとき通知済みの基準（last_notified）は切り替え前の snapshot のまま据え置かれるが、それが正しい — 基準は配送だけが進める（cached_head_architecture.md §C8）。再有効化のときに、無効の間に起きた Playbook の増減が切り替え前との比較でまとめて通知される。
- `CommonPromptSection`: 差分通知の比較は**展開済みテキストのみ**にする（テンプレート指紋を含む snapshot 全体の比較のままだと、文章が同一バイトのリリースでも全ペルソナに「前提情報が更新されました」が飛ぶ）。切り替えでテキストが実際に変わったときに一度出るのは許容（現行挙動のまま）。
- `AutonomyModesSection` / `MemopediaIndexSection` / `DeskSection`: 元々反転を通知しない設計を維持する。

### 4-7. 実行経路の抜け穴を止める（pre_spells）

`lg_llm_node` の pre_spells 実行を `state["_spell_enabled"]` の判定で止める。無効ペルソナでは、チャット UI「ツール指定」・スケジュール・inject_persona_event どの経路から積まれた pre_spells も実行しない。黙って握り潰さない — 警告ログを出し、event_callback があれば status イベントで「スペル無効のためスキップ」を流す（ツール指定を選んだユーザーが「実行されたはず」と思い込む形を作らない）。

### 4-8. UI

**スペル欄（SettingsModal）はモードとして見せる** — 現在の「スペル 有効/無効」のチェックボックスを、名前のある二択に置き換える:

- **使用する（標準）** — 従来どおり
- **使用しない — スペル不使用モード** — 会話専用の軽量運用

説明文（実装時に微調整可。現行の「ツール定義を使わないため、キャッシュ効率に影響しません」は function calling でなくテキスト詠唱だという別の話なので置き換える）:

> スペル不使用モード: ペルソナがスペル（/spell）・Playbook・アイテム操作を一切使わない、会話専用の軽量モードです。スペルの説明やツール一覧がシステムプロンプトから全て外れるため、1 回の会話に使うトークンが大きく減ります。切り替えは保存するとすぐ反映されます。
> ⚠️ 切り替えるたびにこのペルソナのコンテキストが作り直され、プロンプトキャッシュが積み直しになります（モードの間でキャッシュは共用できません）。頻繁に切り替えると、節約どころか逆に費用が高くつくことがあります。

**事前実行スペル欄への注意（同じ画面の隣）** — スペル無効のペルソナでは事前実行スペル（realtime spell）は走らない（実装済みの挙動）が、設定画面は何も言わずに設定だけできてしまう。SettingsModal の事前実行スペル欄に、スペル不使用モードのときだけ「スペル不使用モードのため、事前実行スペルは実行されません。」の注意を表示する。Building 側の設定画面（BuildingSettingsModal）は対象ペルソナが定まらないので、説明文に「スペルが無効のペルソナには実行されません。」の一文を常設で足す。

## 5. 対象外と、その理由

- **`FacilitiesSection`（行ける場所）・部屋のアイテム知覚**: 変更しない。ペルソナはユーザー操作で移動させられるし、部屋に何があるかは世界の知覚であって、スペルの説明ではない。
- **`CoreMemorySection` / `MemoryWeaveSection`（ふと浮かんだ記憶）**: 変更しない。どちらも中身は記憶そのもので、スペル無しでも成立する。
- **実行側の既存の判定（spell loop / realtime / work_session）**: 既に `_spell_enabled` で止まっている（W10 監査）。変更しない。
- **チャット UI の「ツール指定」セレクタの出し分け**: 今回はしない。セレクタは会話単位で、建物には有効/無効のペルソナが混在しうる。実行側の判定（§4-7）と status イベントで実害を防ぐ。出し分けが要るかは実運用を見て判断。

## 6. 局所修正で残る課題

- 切り替えは即反映のため、頻繁に切り替えるユーザーはそのたびにキャッシュを捨てることになる。機構では止めず、UI の注意書きだけで伝える（分かりやすさ優先の裁定とセットのコスト）。
- 保存とまったく同じ瞬間に別の契機（Metabolism 等）の撮り直しが走っていた場合、旧設定を読んで始まった撮り直しが後から書き込まれ、即反映が一回空振りする数秒の窓が理屈上ある（2026-09-14 の敵対レビュー指摘）。これは head の撮り直し全般が元々持つ性質で本変更が作ったものではなく、起きても次の撮り直しで自己回復する。世代番号で直列化する処方は複雑さが釣り合わないため採らない。切り替えの瞬間の撮り直しが DB 障害等で失敗した場合も同じ扱い — head の仕組み全体が「失敗時は直近の正しい姿のまま走り、次の撮り直しで直す」を選んでいる（cached_head_architecture.md §C7）ので、切り替えだけを止まる側（fail-closed）へ倒す処方も採らない。
- **即反映が届くのは、そのペルソナの標準モデルのコンテキストだけ**。head は (ペルソナ, モデル) ごとに一つあり、切り替えイベントの配送も一つの (ペルソナ, モデル) を宛先にする（`HeadPipeline.dispatch_event` は `ctx.model_key` の行しか撮り直さない）。保存は Pulse の外の出来事で実行モデルが定まらないため、入室の hook と同じく標準モデルへ送っている。軽量モデルなど別モデルの head は、次の Metabolism か anchor の TTL 切れで揃う。全モデルへ一斉に届けるには、pipeline に「このペルソナの (ペルソナ, モデル) を列挙する」公開口が要る（`advance_last_notified` が持っている走査の形）。実運用で不揃いが問題になったらそこを足す。宛先が標準モデルである以上、同じ保存でモデルも変えた場合は**新しいモデルが確定してから**切り替えを発火する必要がある（発火は `update_ai` のモデル当てはめの後・モデル設定のロックの外に置いてある。当てはめの前だと旧モデルの head を撮り直して、新モデルの head に旧モードの説明が残る）。当てはめが例外で転んだ回はモデルが変わっていないので、その時点の標準モデルへ発火してよい（commit 済みなら例外経路でも発火する — 落とすと、同じ値を保存し直しても「値が変わっていない」ので二度と発火しない）。
- リリース適用の初回、リリース前から既にスペル無効だったペルソナだけ反映が二段階になる（§4-2）。過渡期の head にはスペル説明が部分的に残るが、次の Metabolism で揃う。
- common.txt を独自に上書きしているユーザーには本変更の節約が届かない（マーカーが無いテンプレートは全文が載り続ける）。マーカー構文の利用者向けの説明は現状この intent にしかない — 利用者向けのプロンプトカスタマイズ文書ができたときに移す。
- 「記憶」の節の共通 3 文（体験の一部しか載っていない・でっち上げ禁止・自動想起）が、有効側ブロックと無効側ブロックに別の形で二重に存在する。片方だけ直すと食い違う。common.txt を編集するときはこの節の両ブロックを見比べること。
- スペルが有効だったころの会話履歴に残る /spell 行・スペル結果は消えない（履歴は改変しない — 送信済みコンテキストの途中を書き換えない原則）。まねて唱えることの抑止はスペル一覧 section の断り書き 2 行が担う。

## 7. 検証手順

1. **有効側 1 バイト不変の検算**: 変更後の common.txt からマーカー行と無効側ブロックを取り除いた結果が、変更前（git の直前版）の common.txt と完全一致することを比較で確認する（検収時に実施）。テストとしては「有効側の展開結果に、マーカー文字列と無効側ブロックの文が現れないこと」「マーカー無しテンプレートが素通しであること」を恒常化する。
2. 隔離環境（隔離 SAIVERSE_HOME + 合成ペルソナ、LLM 不要）で SPELL_ENABLED=true / false それぞれの head を実際に描画し、**組み上がったシステムプロンプト全文を読者として読む**（false 側にスペル・Playbook・アイテム・URI の説明が一切残っていないこと、true 側が現状と同一であることを目で確認）。
3. 単体テスト: マーカー処理（両方向・fail-safe・上書きテンプレート互換）/ 各 section の gate と snapshot 互換（旧 payload = 有効扱い）/ 反転時の通知抑制と common_prompt のテキストのみ比較 / pre_spells の gate / desk・autonomy_modes の無効時文面 / 切り替え保存で gate を持つ全 section が一斉に作り直されること（値が変わらない保存では作り直されないこと）。
4. 実機（まはー検証）: 実ペルソナで無効化 → Metabolism 後のコンテキストプレビューでスペル関連の説明が消えていること、トークン数の実測差。
