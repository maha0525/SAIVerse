# 返事が途中で止まった回の出口 — 最後の発言に「続きの生成」を付ける

ステータス: 検証待ち (2026-09-25 起草・同日まはー裁定・同日実装。フルスイート緑、敵対レビュー一巡 + 当て直し検証の消し込み済み。隔離環境のブラウザで場面 A〜D — スペル後の失敗・続きの生成で二言目・スペル無しの切断・スペル後の切断 — をメティスが目視確認済み。残 = まはーの実機確認。裁定の記録は末尾)

## この文書が守る約束 (要件)

前提になる裁定は二つ。

- 2026-08-25 (`docs/issues/archive/user_utterance_path_failure_inventory.md` §④⑤): 途中まで生成された言葉は常に残す。続きは自動で打たず、追加の課金は必ずユーザーのボタンの一押しの後ろに置く。
- 2026-09-24 (同 issue 追記と `docs/handoff/2026-09-25_spell_stop_continue_handoff.md` の記録): スペルのあとで返事が止まったとき、ユーザーが欲しいのは二言目であって、自分の発言の再送ではない — 既存の「続きの生成」に載せる。

この二つから、世界が保障することは次の五つ。

1. **話した言葉は消えない。** 返事がスペルの周回で複数の発言を保存した後に止まっても、保存済みの発言は全部残る。まだ保存していない言いかけが手元にあれば、止まる前に保存する。
2. **「続きの生成」は、そのペルソナが最後に保存した発言に出る。** エラーの直後の画面でも、開き直した画面でも、同じ発言に出る。押せば、その続きをペルソナが話す。
3. **その発言の部屋の記録に、中断の通告が一枚入る。** これでペルソナは次の生成で中断を知り、続きの生成のプロンプトの末尾がユーザー側の行になるので、モデル発話の続きを受け付けない Gemini 系でも続きが通る。通告が運ぶ内容は「§通告の内容」で確定済み (2026-09-25 まはー裁定)。
4. **エラー札 (画面に出るエラーの知らせ) には、出口までの案内を載せる。** 同じ部屋なら「ペルソナの発言の『続きの生成』を押してください」。スペルでペルソナが別の部屋へ移って、移った先の発言で止まった回は、部屋の名前を出して「その部屋へ行って押してください」。「返事の部屋」とは、ユーザーがその発言を送った部屋 (エラー札が出る画面の部屋) を指す。
5. **印と通告は一回の中断に一つずつ。** 二枚目の通告や二つ目の印は、どの経路を通っても生まれない。

出力例 (要件 4、モデルが安全性フィルターで拒んだ回のエラー札):

> 安全性フィルターによりブロックされました（PROHIBITED_CONTENT）。このモデルでは通らない内容でも、別のモデルなら通ることがあります。別のモデルに切り替えてから、ペルソナの発言に表示されている「続きの生成」ボタンを押してください。

## 全体の流れ

ユーザーが発言する → ペルソナの返事が生成される。この途中に、スペルの周回 (一周ごとに発言が保存されうる)、スペルによる部屋の移動、スペルが起こす別の生成が挟まりうる。別の生成のうち、サブライン (`run_playbook`) は返事の pulse_id を引き継ぐが、`tell` スペルは自分用の pulse_id を新しく作って発言を建物に書く (`builtin_data/tools/tell.py`) → どこかで失敗して止まる → 【後始末】 → エラー札が画面に出る → ユーザーが「続きの生成」を押す → 普段の返事と同じ生成が空の入力で走り、部屋の記録の通告を読んだペルソナが続きを話す。

「続きの生成」の口はこの設計で変えない: `POST /api/chat/continue` が建物の行の `metadata["_interrupted"]` (「言い切っていない」印) を関所にし、普段の会話 Pulse をそのまま起こす (`manager/runtime.py` `continue_persona_message_stream`)。

## 設計の芯 — 事実の記録は一箇所、後始末は返事につき一回

前の実装が迷子になった構造的な原因は、**止まった場所ごとに後始末 (印と通告) をしていた**こと。スペルの内側で止まった回は、内側の後始末が印と通告を置いた後に、外側の後始末が溜めていた本文を書くため順序が狂う。それを直すために、通告を取り下げて付け替える機構、例外オブジェクトに起点を載せて運ぶ仕組み、状態キー 6 個が積み上がった。救済が本体を覆った (CLAUDE.md 把握可能性の制約)。

作り直しでは、役割を二つに分ける。

### 1. 事実の記録 — 保存完了の信号の一本化点で

ペルソナの発言が建物の行に**本文つきで**保存されるたび、「このペルソナが最後に保存した発言 = (message_id, building_id, 保存時刻)」をメモリ内の記録 (ペルソナ単位、DB には書かない) に上書きする。書く場所は、保存の成功判定が既に一本化されている `sea/runtime_emitters.py` の `notify_speak_persisted` の位置 — この関数の docstring 自身が「保存経路は複数あり、経路ごとに書き分けると必ず漏れるので判定をここに一本化する」と定めており、本文が空の行を弾く判定も既にここにある。記録の書き込みは、画面に繋がっていない保存 (event_callback が無い回) でも行う。

- 記録を**ペルソナ単位**にするのは、`tell` スペルが自分用の pulse_id で発言を書くため、pulse_id で切ると取りこぼすから。
- ペルソナ単位の記録には混線の可能性が残る (割り込みの新旧の実行は一時的に重なる。作業セッションは PulseController の外で走り、その中の `tell` は会話中でも発言を書ける — 整合性検査 2026-09-25 の指摘)。これを、後始末側の**時間窓** (返事の実行の開始時刻より後に保存された発言だけを対象にする) で受ける。窓の中に別の実行の発言が混ざった場合は最後の一件が対象になるが、それはユーザーの画面でも実際に最後の吹き出しであり、「最後に保存した発言に続きを出す」という要件の側から見て誤りではない。

### 2. 後始末 — 返事の実行につき一回、すべての書き込みの後で

返事の実行が言い切らずに終わるとき (エラーで閉じる回と、サーバーがストリームを途中で切ったが部分文が残った回)、後始末を**返事につき一回だけ**行う。

1. まだ保存していない言いかけが手元にあれば、発言として保存する (要件 1)。この保存は今までどおり記憶にも「言い切っていない」印つきで書く。
2. 記録にある最後の発言の建物の行に「言い切っていない」印 (`metadata["_interrupted"]`) を付ける。**既に保存済みの発言の記憶側の行は書き換えない** — エラーの後片付けが記憶を書き換える口になるのは危うい (2026-08-25 裁定)。ペルソナに中断を知らせる仕事は、記憶の印ではなく次の通告が担う。
3. その発言の部屋に中断の通告を一枚置く (既存の `_record_interruption_notice` の経路を使う。内容は「§通告の内容」の 4 分類 × 原因 2 通り)。
4. エラーで閉じた回は、エラー札のイベントにその発言の id と (返事の部屋と違うときは) 部屋の id・表示名を載せる。サーバー切断で部分文が残った回は、今までどおりエラー札ではなく情報の知らせのままとし、そこに同じ案内を載せる。

これは新しい関数の発明ではなく、既存の後始末 (`_settle_interrupted_utterance` と、その呼び出し元 4 箇所 — Beat の死・ストリーム途中の停止・締めの Beat に本文が無い回・サーバー切断) を**置き換える**工事になる。呼び出し元が複数あっても、後始末の実行は返事につき一回に守られ (既存の `pipeline_finalized` の印と同じ型)、スペルの内側・サブライン・周回の途中といった**内側の経路は後始末を呼ばない** — 失敗をそのまま上へ投げるだけにする。置く者が一人になるので、取り下げも二枚目も原理的に起きない。既存の後始末が担っている隣の仕事 (Beat の死んだ回の記憶の補填 `_backfill_memory_on_beat_death` — 2026-08-27 裁定の穴 3) は、この置き換えで消さずに引き継ぐ。

サーバー切断の後始末は、いまはスペルが一つも走らなかった回の完了の道にしか無く、それが issue `spell_round_stream_cut_is_not_detected.md` の供給源になっている。一本化では、切断の申告の消費を後始末の側に移し、スペルの周回の途中の切断 (次の周が発話を続けるので自己回復する) と最終周の切断 (発言が途切れたまま確定する) を区別して、後者にだけ印と通告を付ける。

### 通告の内容 (2026-09-25 まはー裁定 — 設計対話で確定)

通告はペルソナに読ませる文で、ペルソナが「次に自分はどうすればいいか」を推理なしで選べる情報を運ばなければならない。中断の事実だけでは足りない — スペルや Playbook は「正常に動き切って結果が渡される」前提で説明を省いており、「起こらなかった」場面ではペルソナは何が起こるはずだったのかを知りようがない (まはーの提示した要件)。かといって「何が起こるはずだったか」を機構が書くのは Playbook 一般では原理的に不可能なので、**機構が実際に知っている事実の結論をそのまま書く**。

本文は、後始末が状況から選ぶ 4 通り:

| # | 状況 | 本文 (原案 — 文面の調整は後から自由) |
|---|---|---|
| ① | 発言の途中で切られた (言いかけが残る) | ここで発言が中断されました |
| ② | スペルの実行が終わる前に切られた (結果は来ていない) | 発言の後に唱えたスペルは、実行が終わる前に中断されました。結果は届いておらず、どこまで実行されたかは不明です |
| ③ | スペルの結果を受け取った後、それを受けて話す前に切られた | スペルの結果を受け取った後、続きの発言の前に中断されました |
| ④ | 言い切った後、続きが始まる前に切られた (スペルが絡まない一般の受け皿) | この発言の後、続きが始まる前に中断されました |

原因の句はこの頭に付く: ユーザーの停止なら「ユーザーの操作により、」、事故なら無印 (2026-08-26/27 裁定の出し分けを継承)。書く部品は 2 + 4 の 6 個。

この分類を支える判断:

- **①と④を見た目に頼らず書き分ける**: 切れた発言は言い切った短い発言と見分けがつかない — それがこの機能一式の存在理由なので、通告が明示的に区別を運ぶ。
- **②は不確定を正直に言う**: スペルの途中の死では、副作用 (部屋の移動、tell の発言、外部呼び出し) がどこまで効いたかは機構自身にも分からないことがある (外部呼び出しは送信後に切れると顛末を知る術がない)。「実行されていません」と断定するとペルソナが安心して唱え直し、二重に効く。「分からない」と書くのは、ユーザー側の出口 7 (顛末が確定しない回は「分かりません」と正直に言う — 2026-08-25 裁定) と同じ原則。
- **③が書けるのは、受け取り済みの結果が必ず行に残っているときだけ**: 後始末の一手目 (未保存分の保存) は、言いかけの本文だけでなく受け取り済みのスペル結果まで含めて行へ残す。スペル群で一つ目の結果が来てから二つ目で死んだ回は、一つ目の結果が行に残り、通告は②になる — 「結果が付いているものは来た、最後のは不明」と記録が語る。
- **指示は書かない**: 同じ一行を「続きの生成」の文脈でも、普通に会話が続いた文脈でも読むため、「唱え直してください」の形にはしない。事実 (結果は来ていない / 結果は受け取った) が書いてあれば、行動は文脈から自然に決まる。
- **エラーの中身 (安全性フィルター・利用制限・タイムアウトの別) はペルソナに渡さない**: それはユーザー向けのエラー札の仕事。特に安全性フィルターの理由を記憶に書くと「自分の発言は禁止内容と判定された」という自己像を植え付ける (誤検知も多い)。
- **スペルの名前・存在に触れるのは問題ない**: 他のペルソナの記憶にも、スペルの詳細は隠されるが「[スペル名(引数)]」の形で唱えた事実は最初から伝わっている (`docs/intent/voice_tts_pipeline_streaming.md` 論点 4)。

### 画面への届け方

- 保存完了の信号 `speak_persisted` は、保存された行の message_id を既に画面まで運んでいる (HEAD 時点で画面側に受け手が無いだけ)。画面はこれを拾って吹き出しに行の id を持たせ、エラー札のイベントに載る id と突き合わせて「続きの生成」を出す。**新しいイベントの種類は足さない。** 開き直した画面は履歴 API の `interrupted` で同じ状態に戻る。
- エラー札の案内文と i18n の文言 (`app.page.continue*` / `app.page.movedContinue*`) は、前の実装で書いた下書きを流用する。ただし画面ではまだ一度も確認していない文面であり、検収は作り直しの検証で行う。既知の不揃い: 部屋の移動が絡む側 (`movedContinue*`) には支払い・認証のエラーの文面があるが、同じ部屋の側 (`continue*`) には無い — 実装時に揃える。

## 前の実装から外すもの

- **通告の取り下げ・付け替えの機構** — 後始末が返事につき一回になったので、問いごと消える (2026-09-25 のハンドオフの判断待ち 1 は、この設計で解消)。
- **例外に起点と通告を載せて運ぶ仕組み** (`LLMError.continue_point` / `continue_notice` ほか) — 記録がペルソナ単位の一箇所にあるので、運ぶ必要が無い。
- **保存 (確定) の失敗時の救済を広げた部分** — HEAD には既に、スペルの周の確定に失敗した本文を建物へ直接書き直す救済 (`_write_beat_body_directly`) が一箇所ある。これは残す。前の実装はこれを締めくくり・普段の返事・中断時の確定へ広げ、同じ発言が二度配信されるのを防ぐ仕掛け (`SpeakFinalizeResult.delivered_to_gateway` ほか、intent `addon_speak_hooks.md` に足した不変条件 8) を併設した。この拡張一式は二言目の出口とは独立した工事なので本件から外し、別 issue に切り出す (未決 2)。

## 不変条件

1. 追加の推論・課金は、必ずユーザーの一押しの後ろにある (2026-08-25 裁定の再掲)。後始末は保存と印と通告だけを行い、LLM を呼ばない。
2. 印と通告は必ず対で、本文の残る発言にだけ付く。印だけが立つと、続きの生成は通るのにプロンプトの末尾がモデル発話のままになり、Gemini 系で失敗する。
3. 中断の通告は建物の記録に置かれ、取り込みを通じて在室ペルソナの記憶へ写る。これは意図された経路である (2026-08-26/27 裁定) — 通告の文面・内容を変えるときは「ペルソナに読ませてよいか」を先に問う (今回の内容は 2026-09-25 に設計対話で裁定済み)。
4. 後始末の実行は返事の実行につき一回。内側の経路 (スペルの周回・サブライン) は後始末を呼ばず、失敗をそのまま上へ投げる。新しい失敗の経路を足すときも、足すのは事実の記録と例外の伝播だけ。
5. **行に残るものは、現実に起きたところまでと一致する。** 受け取り済みのスペル結果は、後始末の保存で必ず行に残す。逆に、来ていない結果・確定していない実行を「済んだ」とも「起きていない」とも書かない — 通告が断定してよいのは機構が確定を知っている事実だけで、不確定は不確定と書く (§通告の内容 ②)。プロセスごと落ちた回だけは後始末自体が走れないため守れない (今と同じ割り切り)。

## 検証の計画

- 隔離環境 (隔離 SAIVERSE_HOME + 合成ペルソナ + 偽 LLM) で、止まり方の場面の列 (スペル無し / スペル一周後 / `tell` の発言の後 / 部屋の移動後 / ストリーム切断の最終周と途中の周 / 非ストリーミング) を実際に通し、画面に「続きの生成」と案内が出るところまで**私がブラウザで見る**。前の実装はここを一度もやらないまま差分が育った。
- 「続きの生成」を押したとき、続きの生成の中でスペルが再発火するかは既存挙動の確認事項として残っている (続き専用のスペル抑止はコード上存在しない)。隔離環境で台本つきの偽 LLM を使って観察する。
- この設計で直さない既知の穴 (どれも既存 issue / 既知の形のまま): 印の書き込み自体が DB の混雑で失敗し続けた回は、エラー札だけが出て「続きの生成」も「再送」も出ない (まれ)。続きの生成を連打すると、印の検査と生成の開始の間の隙間で二重生成が起きうる (issue `continue_has_toctou_between_check_and_generation.md`)。ユーザーが返事の途中で自分が部屋を移動した回の、案内の部屋の判定は扱わない。

## 設計が選んだ割り切り (2026-09-25 レビューで確認した境界)

どれも「後始末を一箇所に保つ」ことと引き換えに受け入れた形で、直すには後始末の多重化 (作り直しの原因) へ戻る必要がある。

- **割り込みが重なった回の原因の句**: 新しい返事が古い返事を割り込みで止め、古い返事の最後の発言が新しい返事の失敗の後始末に拾われると、原因の句 (ユーザーの操作 / 事故) が新しい返事の側の原因で書かれることがある。対象の発言は画面でも実際に最後の吹き出しなので、「続きの生成」の出口としては正しい。
- **言い切った直後の後段の失敗にも ④ が付く**: 発言を言い切った後、記録などの後段の処理で返事が死んだ回も、その発言に ④ と「続きの生成」が付く。返事に続きが予定されていたかは機構に分からないため、④ の文面は「続きが始まる前に切られた」という位置の事実だけを述べる。押せば続きは普通に生成される (課金はユーザーの一押しの後ろ)。
- **返事が止まらず続いた回の、途中の切れた発言**: サブラインの発言が途中で切れても、その失敗がスペルの結果文字列に変換されて返事自体は続いた回は、返事は止まっていないので後始末は走らず、切れた発言は印も通告も無いまま残る。前の形はここで返事の途中に通告を書いていて、それが順序の狂いと取り下げ機構の温床だった。
- **プロセスやサーバーの停止 (asyncio の取り消し) の回**: 後始末は走らない (走れない)。今までと同じ。
- **スペルの `tell` の行の id が、生成中の吹き出しに一瞬付くことがある**: 画面の描き直しで消える一過性の表示で、保存された記録には影響しない。

## 経緯 — なぜ作り直すか (2026-09-25)
