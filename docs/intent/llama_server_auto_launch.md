# llama.cpp サーバー自動起動

**ステータス**: 検証待ち — host/port 分離を実装、develop へマージ済み・実機確認待ち。既存の busy 判定は実機検証済み。

## 目的

llama.cpp をサーバーモード (`openai_compat` プロトコル) で使う場合、サーバーの手動起動が必要だった。モデル設定に起動情報を持たせることで、サーバーが立っていなければ自動で起動し、使い終わったら SAIVerse 終了時に自動で停止する。

## 接続先ごとの所有境界 (2026-10-02 改修)

利用者は、複数マシンで同じポート番号を使っても、ある接続先へのリクエストが別の接続先の停止・再起動・idle 時計に干渉しないことを頼りにする。

モデル設定の `base_url` → factory / `OpenAIClient` の生存確認 → リクエストと `LlamaCachedClient` の restore〜save を覆う貸出札 → idle 判定 → 停止・再起動・終了時の回収まで、所有境界は一貫して **`(host, port)`** とする。`LlamaServerManager` が台帳・札・外部確認・警告抑止を所有し、呼び出し側で補正しない。札は同じ接続先の世代交代を跨ぐが、別 host の現職には届かない。

帳簿の host は DNS を引かず、`localhost` / `localhost.localdomain` / 127.0.0.0/8 / `::1` / `0.0.0.0` / `::` を一つのローカル鍵へ正規化する。接続・起動・bind に使う host は元の URL のまま保持し、遠隔 host や DNS 別名は統合しない。HTTP の健全性確認・起動コマンド・LAN bind の既存仕様は変えず、遠隔プロセスを起動する機構も追加しない。

検証は合成プロセスと HTTP / SDK の置換を使い、同ポート別 host の台帳分離、lease 返却、idle 停止、再起動、警告、shutdown、およびクライアントからの呼び出しを横断する。本番ペルソナ・実サーバー起動・実推論・実ネットワーク接続は検証しない。

## 2つの起動モード

### コマンドモード

既存の起動スクリプト (.bat / .sh) をそのまま使う。JSON には `command` だけ書けばいい。

```json
"llama_server": {
    "command": "C:/path/to/start_model.bat"
}
```

- `llama_server_binary`, `model_path`, `extra_args` 等は全て無視される
- .bat ファイルの場合、末尾の `pause` は自動除外して実行される
- バイナリやモデルの変更はスクリプト側で行う

### ビルドアップモード

スクリプトがない場合、個別フィールドからコマンドラインを組み立てる。

```json
"llama_server": {
    "model_path": "~/models/model.gguf",
    "n_gpu_layers": -1,
    "parallel": 2,
    "extra_args": ["--mmproj", "~/models/mmproj.gguf", "--jinja"]
}
```

## 設計判断

### なぜプロバイダ + モデルの二層設定か

- **バイナリパス** (`llama_server_binary`) はプロバイダレベル。同じ llama-server バイナリを複数モデルで共有するため
- **起動パラメータ** (`llama_server`) はモデルレベル。GGUF パス・GPU レイヤー数・並列スロット数はモデル固有

`_INHERITABLE_FIELDS` により、プロバイダの `llama_server_binary` がモデル設定に自動継承される。ビルドアップモードのみ使用。

### なぜ管理下/管理外を区別するか

ポートに既にサーバーが応答している場合、それがユーザーが手動で立てたものかもしれない。管理下プロセス (自分が起動したもの) だけ再起動対象とし、管理外プロセスには触れない。

### 設定変更の検知

管理下プロセスの identity (コマンドモード: スクリプトパス、ビルドアップモード: model_path) を保持し、設定と一致しなければ再起動する。

### idle 自動停止と busy 判定 (2026-08-03 改修)

管理下サーバーは放置されると自動停止する (VRAM/RAM を占有し続けないため)。

- `llama_server.idle_timeout` — 最後の利用からこの秒数で停止 (既定 600)。**`0` で自動停止を丸ごと無効化** — busy_deadline の強制停止も含めて一切止めなくなる (82GB 級などロードし直しが高くつくモデル向け)
- `llama_server.busy_deadline` — 処理中と**証明された**サーバーでも、この秒数を超えたら強制停止 (既定 3600)。起算は「idle checker が最初に busy を目撃した時刻」で、idle_timeout 経過後にしか評価されないため、idle_timeout 未満の値は起動時に idle_timeout へ丸めて警告する

**貸出札 (request_lease) と活動時刻**: リクエストは送信前の ensure_running に加えて、送信〜後処理 (ストリーム完走・KV slot save) の全体を**貸出札**で覆う。札は**接続先 `(host, port)` に付く** (サーバー世代ではなく) — 貸出中に世代交代しても同じ接続先の現職を守り続け、別 host の時計や停止条件には触れない。札が出ている間、idle checker はそのサーバーを停止できない — `/slots` は応答受信直後や save 中 (数 GB のディスク書き込みで数秒) も「暇」を返すため、札なしでは保存中のサーバーを撃てる (2026-08-03 十巡目レビューで検出)。札は try/finally で返却されるため例外・ストリーム中断でも漏れず、**返却時に last_activity を更新する** = idle_timeout の起算は完了時刻から (idle_timeout 超の長時間推論の完了直後に停止が発火しない)。idle checker が busy を目撃したときも時計を巻き直す (札の経路が届かない外部クライアント向けの下支え)。busy_deadline の起算は busy 初観測時刻 (busy_since) で、idle 観測・札の返却でクリアされる。

**状態判定の契約 (三値)**: 停止前に `/slots` エンドポイント (llama-server 既定で有効) の `is_processing` で状態を確定する。**`/health` を busy 判定に使ってはならない** — `/health` は生存確認専用で、スロットが推論中でも 200 を返す (b10229 実測)。2026-08-03、旧実装 (`/health` の status != 200 を busy とみなす) が常に「暇」と答え、プロンプト処理 39% のサーバーを idle 停止で二度殺した実害がある。

- **idle** (全スロット暇と証明) — 停止してよい。kill 直前にロック内で `/slots` を再確認する
- **busy** (処理中と証明) — busy_deadline 超過でのみ強制停止
- **unknown** (証明不能: `--no-slots`・応答が想定形でない・生存中なのに接続不能) — **決して止めない**。busy_deadline の強制停止にも使わない。そのサーバーの自動停止は事実上無効になり、リソースを握ったまま無言にならないよう警告を 30 分ごとに繰り返す。誤って残すコストより、証明の無い kill のほうが高い
- プロセスが死んでいる場合だけは接続不能でも idle 扱い (掃除経路を塞がない)

停止の実行は「候補観測時と同一世代 (同一オブジェクト) で、last_activity 再確認後も idle 条件を満たす」ときだけ。接続先 host は `ManagedServer.host` (base_url 由来) を使い、loopback 固定にしない。`busy_deadline < idle_timeout` は実現不能 (候補になるのが idle_timeout 経過後のため) なので起動時に idle_timeout へ丸めて警告する。

**リクエスト前の生存確認 (2026-08-03)**: `llama_server` 付きモデルの `OpenAIClient` は `bind_llama_server` で紐付けられ、**リクエスト送信のたびに** `ensure_running` を通る (slot キャッシュの restore を送る `LlamaCachedClient` は restore より先に `ensure_backend` を呼ぶ)。これが二つの穴を同時に塞ぐ: ① idle 停止後もキャッシュ済みクライアントが自動で再起動経路を持つ (以前は停止済みポートへ送信し続けて失敗した)。② ensure_running の last_activity 更新は停止判定と同じロックの中なので、先に名乗ったリクエストを idle 停止が撃つ競合が閉じる。SAIVerse を経由しない外部リクエスト (手動 curl 等) はこの保護の外— そこだけが残る既知の限界。

毎リクエスト経路になったため、ensure_running は**高速経路と低速経路**を分ける: 管理下プロセスが生存 + identity 一致なら HTTP を打たず activity 申告だけ (ロック保持はマイクロ秒)。/health の一時不調 (高負荷時のタイムアウト等) で生存中のサーバーを二重起動しないための構造でもある — 健康確認と起動・置換は、プロセスが消えているときだけの低速経路に隔離。低速経路では「管理下プロセスは死亡・ポートは応答」を外部再利用とみなして起動せず (ポート衝突防止)、外部管理サーバーの確認は (host, port) 単位で 30 秒間隔に間引き、自分の古い失敗観測より他スレッドの新しい外部確認を優先する。起動はロック保持のまま = 巨大モデルの同時多重起動を構造的に防ぐ。

**受け入れた限界 (2026-08-03 判断、いずれも「複雑さを買ってまで塞がない」と決めたもの)**:

> **裁定 (2026-08-31 まはー)**: 8 項のうち **4 (同一ポートの多 host) だけは受け入れず issue 化** ([llama_server_registry_ignores_host](../issues/llama_server_registry_ignores_host.md)) — 別ホスト同ポートは多マシン運用 (NEBULA 時代) で普通にある形のため。**他 7 項は受理で確定** (いずれも保守側にしか誤らず有界、または「ポートを分ける」運用で発生自体を消せる)。

1. **ハングした生存プロセスは自動復旧しない。** 高速経路はプロセスの存在だけを見るので、プロセスは生きているが HTTP が固まったサーバーは、リクエスト失敗が続いても自動再起動されない。運用シグナルは二つ: リクエスト自体のタイムアウトエラーと、idle checker の「busy 判定不能」警告 (30 分ごと)。自動復旧 (suspect 状態機械) を入れるより、明示的な再起動に委ねる。旧実装はこのケースで健康確認失敗→上書き起動 = 二重起動していたので、退行ではない
2. **起動中はグローバルロックを最大 120 秒保持する。** 別ポートのサーバーへの高速経路も待たされる。ポート単位のロック分割はしない — この環境の常用は「巨大モデル 1 本」で、複数巨大モデルの同時起動を待たせるのは RAM/VRAM 保護としてむしろ望ましい
3. **起動途中 (503) の外部サーバーは検出できない。** /health が通らないポートには起動を試みる (旧実装と同じ)。外部サーバーと管理下サーバーを同じポートに共存させる運用自体を避けるのが前提
4. **同一ポートの多 host 混線は改修の検証待ち。** [issue](../issues/llama_server_registry_ignores_host.md) の修正で管理台帳・貸出札・警告抑止を `(host, port)` 単位に統一した。別 host の利用は互いの activity・停止・再起動に干渉しない。ループバック・wildcard の既知の別名は一つの帳簿に載せる (上記「接続先ごとの所有境界」)。旧挙動は末尾の経緯に保存。
5. **外部確認の順序判定は保守側に誤りうる。** 自分の失敗観測の開始後に完了した外部確認を優先するため、「確認直後に外部が消えた」スケジュールでは正当な起動が最大 30 秒 (再確認間隔) 遅れる。誤る方向が「起動しない」側であり自己回復するので受け入れる
6. **同一接続先で複数モデルを並行に使う構成はサポート外。** 貸出札は接続先単位のカウンタなので世代交代を跨いで現職を守るが、設定変更による再起動が別クライアントのリクエストと同時に走ると、リクエストが新世代 (別モデル) に届く競合は本改修以前から存在し、塞いでいない。モデルごとにポートを分けること
7. **札の返却は busy 時計を無条件に消すため、ハング回収が有界に先送りされうる。** 別リクエストや旧世代の札の返却が、ハング中のサーバーの busy 時計を消す並びがある (並行スロット・強制停止後の新世代・キュー待ちクライアントのタイムアウト返却)。ただし時計は次の busy 観測 (idle 周期ごと) で再確立するので、回収の遅れは有界 (idle 周期 1〜2 回ぶん)。逆向き (時計を世代・リクエスト単位で厳密管理) は札に世代トークンと実行中/待機中の分離を要求する状態機械で、有界な遅延のために買う複雑さではないと判断した。方向は常に保守側 (健康な仕事を殺す側には倒れない)
8. **強制停止後、旧世代でハングしたリクエストの札が新世代の idle 停止を遅らせる。** 札は接続先単位なので、旧リクエストのクライアントタイムアウトで返却されるまで (最長でモデル設定の timeout 秒) 新世代は idle 停止されない。方向は保守側 (止めない) で有界

## 不変条件

1. `llama_server` 設定がないモデルには一切影響しない (回帰なし)
2. 管理外プロセスを kill / restart しない
3. SAIVerse 終了時に管理下プロセスを全て停止する
4. ヘルスチェック待ちは最大 120 秒 (大型モデルのロード時間を考慮)
5. サーバーログはセッションログディレクトリに `llama_server_{port}.log` として出力
6. `command` 指定時、ビルドアップ用フィールドは全て無視 (排他)
7. **処理中のサーバーを idle 停止しない** — 暇と証明できたときだけ止める (busy 判定は `/slots`、証明不能なら止めない)
8. **旧世代の「警告済み」記録が新世代を黙らせない。** 警告の抑止表はサーバーオブジェクトより長生きするので、鍵には接続先とサーバー個体を指す単調増加の世代番号を使う。`id()` は回収されたアドレスを次の個体へ再利用するため、この用途には使えない (2026-08-16 に実害: 抑止が別個体へ漏れ、並列テストで稀に露見した)
9. **別 host の同ポートは別の接続先として扱う。** 管理台帳・貸出札・外部確認・警告の世代記録を接続先単位で所有し、他の接続先の停止・再起動・活動時刻を変更しない。

## 経緯: busy 判定修正の実機検証 (2026-08-31 合格)

gemma4 E4B (Vulkan) を自動起動管理下で走らせて検証した。

- **busy 中に殺さない**: 3 分 37 秒の生成 (prompt 処理 167 秒 + 生成 50 秒、実測ログ) が、60 秒級の idle 判定周期を複数回跨いで完走した。旧実装 (/health ベース) なら射殺されていた長さ。
- **暇になったら止まる**: 完走の 620 秒後に `idle for 620s (timeout=600s), stopping` が発火し、正常停止した。
- 検証中の学び: 外部が先に立てたサーバーは「externally managed」となり管理対象外 (idle 停止は適用されない) — 検証は必ず SAIVerse 自身に起動させること。
- 副産物 issue 二つ: [設定スナップショットの鮮度](../issues/llama_server_config_snapshot_staleness.md) (idle_timeout の編集が作成済みクライアントの起動に反映されない — 検証時に設定した 60 が効かず既定 600 で動いた理由)、[LLM エラー時の再送ボタン欠落](../issues/llm_error_reply_offers_no_retry.md)。

**全残件決着 (2026-08-31)**: 限界 8 項は裁定済み (7 項受理・1 項 issue 化 — 上の囲み)。止血の `idle_timeout: 0` は「まはーの環境の値であり触らない」で確定。builtin テンプレの `idle_timeout: 600` の焼き込みは除去済み (任意項目の案内コメント化、`0c40d6cc`)。本件は完了 — 台帳から降ろした。


## 経緯: host/port 分離 (2026-10-02、PR レビュー待ち)

- 旧限界 4 は「同一ポートの多 host はサポート外」とし、host 不一致でも応答中なら既存プロセスを残す一方、その activity を更新していた。まはーが 2026-08-31 にこの限界だけを受け入れず、issue 化した。
- 修正前に、遠隔接続先の lease 返却がローカルの last_activity / busy_since を変更すること、および遠隔の健康確認がローカルの last_activity を変更することを隔離テストで再現した。
- 管理台帳・lease・停止/再起動・警告を `(host, port)` に統一し、旧 host 不一致の救済分岐を撤去した。既存の起動コマンド・非 loopback bind・ポート別ログファイル名は維持する。
- 合成プロセス、HTTP / SDK の置換を使う回帰検証まで。実サーバー・本番ペルソナ・推論・永続履歴には触れていない。実機確認までは issue を未解決に残す。


## 経緯: ローカル別名の保護回復 (2026-10-03)

- 技術原因: URL の host をそのまま帳簿の鍵にして、同じローカルプロセスへの札が別管理になった。判断の誤り: 別マシン分離だけを不変条件とし、既存のローカル別名保護を運用上の制約に変更した。検出漏れの条件: 別名を分離するテストが期待値を固定し、起動競合と札を持つ別名利用を検証していなかった。
- 帳簿の鍵を管理者で一括正規化し、接続先・bind は変更しない。DNS は引かない。IPv6 の health / slots URL は角括弧付きにする。
- 回帰検証は「異なる表記の同一資源」と「同じ番号の異なる資源」を対にする。別名 lease による idle 停止阻止と二スレッド同時起動の一回性を確認した。この境界テストの型はファイルの別名による所有権と、DB の別表現による重複更新にも適用できるが、それらの領域は今回未変更・未検証。
