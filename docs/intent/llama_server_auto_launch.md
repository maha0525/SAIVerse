# llama.cpp サーバー自動起動

## 目的

llama.cpp をサーバーモード (`openai_compat` プロトコル) で使う場合、サーバーの手動起動が必要だった。モデル設定に起動情報を持たせることで、サーバーが立っていなければ自動で起動し、使い終わったら SAIVerse 終了時に自動で停止する。

## 2つの起動モード

### コマンドモード

既存の起動スクリプト (.bat / .sh) をそのまま使う。JSON には `command` だけ書けばいい。

```json
"llama_server": {
    "command": "C:/path/to/start_model.bat"
}
```

- `llama_server_binary`, `model_path`, `extra_args` 等は全て無視される
- .bat ファイルの場合、末尾の `pause` は自動除外して実行される
- バイナリやモデルの変更はスクリプト側で行う

### ビルドアップモード

スクリプトがない場合、個別フィールドからコマンドラインを組み立てる。

```json
"llama_server": {
    "model_path": "~/models/model.gguf",
    "n_gpu_layers": -1,
    "parallel": 2,
    "extra_args": ["--mmproj", "~/models/mmproj.gguf", "--jinja"]
}
```

## 設計判断

### なぜプロバイダ + モデルの二層設定か

- **バイナリパス** (`llama_server_binary`) はプロバイダレベル。同じ llama-server バイナリを複数モデルで共有するため
- **起動パラメータ** (`llama_server`) はモデルレベル。GGUF パス・GPU レイヤー数・並列スロット数はモデル固有

`_INHERITABLE_FIELDS` により、プロバイダの `llama_server_binary` がモデル設定に自動継承される。ビルドアップモードのみ使用。

### なぜ管理下/管理外を区別するか

ポートに既にサーバーが応答している場合、それがユーザーが手動で立てたものかもしれない。管理下プロセス (自分が起動したもの) だけ再起動対象とし、管理外プロセスには触れない。

### 設定変更の検知

管理下プロセスの identity (コマンドモード: スクリプトパス、ビルドアップモード: model_path) を保持し、設定と一致しなければ再起動する。

### idle 自動停止と busy 判定 (2026-08-03 改修)

管理下サーバーは放置されると自動停止する (VRAM/RAM を占有し続けないため)。

- `llama_server.idle_timeout` — 最後の利用からこの秒数で停止 (既定 600)。**`0` で自動停止を丸ごと無効化** — busy_deadline の強制停止も含めて一切止めなくなる (82GB 級などロードし直しが高くつくモデル向け)
- `llama_server.busy_deadline` — 処理中と**証明された**サーバーでも、この秒数を超えたら強制停止 (既定 3600)。起算は「idle checker が最初に busy を目撃した時刻」で、idle_timeout 経過後にしか評価されないため、idle_timeout 未満の値は起動時に idle_timeout へ丸めて警告する

**貸出札 (request_lease) と活動時刻**: リクエストは送信前の ensure_running に加えて、送信〜後処理 (ストリーム完走・KV slot save) の全体を**貸出札**で覆う。札は**ポートに付く** (サーバー世代ではなく) — リクエストはポートへ飛ぶので、貸出中に世代交代してもそのポートの現職を守り続ける。札が出ている間、idle checker はそのサーバーを停止できない — `/slots` は応答受信直後や save 中 (数 GB のディスク書き込みで数秒) も「暇」を返すため、札なしでは保存中のサーバーを撃てる (2026-08-03 十巡目レビューで検出)。札は try/finally で返却されるため例外・ストリーム中断でも漏れず、**返却時に last_activity を更新する** = idle_timeout の起算は完了時刻から (idle_timeout 超の長時間推論の完了直後に停止が発火しない)。idle checker が busy を目撃したときも時計を巻き直す (札の経路が届かない外部クライアント向けの下支え)。busy_deadline の起算は busy 初観測時刻 (busy_since) で、idle 観測・札の返却でクリアされる。

**状態判定の契約 (三値)**: 停止前に `/slots` エンドポイント (llama-server 既定で有効) の `is_processing` で状態を確定する。**`/health` を busy 判定に使ってはならない** — `/health` は生存確認専用で、スロットが推論中でも 200 を返す (b10229 実測)。2026-08-03、旧実装 (`/health` の status != 200 を busy とみなす) が常に「暇」と答え、プロンプト処理 39% のサーバーを idle 停止で二度殺した実害がある。

- **idle** (全スロット暇と証明) — 停止してよい。kill 直前にロック内で `/slots` を再確認する
- **busy** (処理中と証明) — busy_deadline 超過でのみ強制停止
- **unknown** (証明不能: `--no-slots`・応答が想定形でない・生存中なのに接続不能) — **決して止めない**。busy_deadline の強制停止にも使わない。そのサーバーの自動停止は事実上無効になり、リソースを握ったまま無言にならないよう警告を 30 分ごとに繰り返す。誤って残すコストより、証明の無い kill のほうが高い
- プロセスが死んでいる場合だけは接続不能でも idle 扱い (掃除経路を塞がない)

停止の実行は「候補観測時と同一世代 (同一オブジェクト) で、last_activity 再確認後も idle 条件を満たす」ときだけ。接続先 host は `ManagedServer.host` (base_url 由来) を使い、loopback 固定にしない。`busy_deadline < idle_timeout` は実現不能 (候補になるのが idle_timeout 経過後のため) なので起動時に idle_timeout へ丸めて警告する。

**リクエスト前の生存確認 (2026-08-03)**: `llama_server` 付きモデルの `OpenAIClient` は `bind_llama_server` で紐付けられ、**リクエスト送信のたびに** `ensure_running` を通る (slot キャッシュの restore を送る `LlamaCachedClient` は restore より先に `ensure_backend` を呼ぶ)。これが二つの穴を同時に塞ぐ: ① idle 停止後もキャッシュ済みクライアントが自動で再起動経路を持つ (以前は停止済みポートへ送信し続けて失敗した)。② ensure_running の last_activity 更新は停止判定と同じロックの中なので、先に名乗ったリクエストを idle 停止が撃つ競合が閉じる。SAIVerse を経由しない外部リクエスト (手動 curl 等) はこの保護の外— そこだけが残る既知の限界。

毎リクエスト経路になったため、ensure_running は**高速経路と低速経路**を分ける: 管理下プロセスが生存 + identity 一致なら HTTP を打たず activity 申告だけ (ロック保持はマイクロ秒)。/health の一時不調 (高負荷時のタイムアウト等) で生存中のサーバーを二重起動しないための構造でもある — 健康確認と起動・置換は、プロセスが消えているときだけの低速経路に隔離。低速経路では「管理下プロセスは死亡・ポートは応答」を外部再利用とみなして起動せず (ポート衝突防止)、外部管理サーバーの確認は (host, port) 単位で 30 秒間隔に間引き、自分の古い失敗観測より他スレッドの新しい外部確認を優先する。起動はロック保持のまま = 巨大モデルの同時多重起動を構造的に防ぐ。

**受け入れた限界 (2026-08-03 判断、いずれも「複雑さを買ってまで塞がない」と決めたもの)**:

1. **ハングした生存プロセスは自動復旧しない。** 高速経路はプロセスの存在だけを見るので、プロセスは生きているが HTTP が固まったサーバーは、リクエスト失敗が続いても自動再起動されない。運用シグナルは二つ: リクエスト自体のタイムアウトエラーと、idle checker の「busy 判定不能」警告 (30 分ごと)。自動復旧 (suspect 状態機械) を入れるより、明示的な再起動に委ねる。旧実装はこのケースで健康確認失敗→上書き起動 = 二重起動していたので、退行ではない
2. **起動中はグローバルロックを最大 120 秒保持する。** 別ポートのサーバーへの高速経路も待たされる。ポート単位のロック分割はしない — この環境の常用は「巨大モデル 1 本」で、複数巨大モデルの同時起動を待たせるのは RAM/VRAM 保護としてむしろ望ましい
3. **起動途中 (503) の外部サーバーは検出できない。** /health が通らないポートには起動を試みる (旧実装と同じ)。外部サーバーと管理下サーバーを同じポートに共存させる運用自体を避けるのが前提
4. **同一ポートの多 host 構成はサポート外。** host 不一致でターゲット endpoint が応答している場合、応答者が管理下プロセス (別 host に bind) か外部かは証明できないため、壊さず・上書き起動もせず、警告して現状を使う (管理下プロセスの活動時刻も更新し、idle 停止の誤射も防ぐ)。使い分けたい場合はポートを分けること
5. **外部確認の順序判定は保守側に誤りうる。** 自分の失敗観測の開始後に完了した外部確認を優先するため、「確認直後に外部が消えた」スケジュールでは正当な起動が最大 30 秒 (再確認間隔) 遅れる。誤る方向が「起動しない」側であり自己回復するので受け入れる
6. **同一ポートで複数モデルを並行に使う構成はサポート外。** 貸出札はポート単位のカウンタなので世代交代を跨いで現職を守るが、設定変更による再起動が別クライアントのリクエストと同時に走ると、リクエストが新世代 (別モデル) に届く競合は本改修以前から存在し、塞いでいない。モデルごとにポートを分けること
7. **札の返却は busy 時計を無条件に消すため、ハング回収が有界に先送りされうる。** 別リクエストや旧世代の札の返却が、ハング中のサーバーの busy 時計を消す並びがある (並行スロット・強制停止後の新世代・キュー待ちクライアントのタイムアウト返却)。ただし時計は次の busy 観測 (idle 周期ごと) で再確立するので、回収の遅れは有界 (idle 周期 1〜2 回ぶん)。逆向き (時計を世代・リクエスト単位で厳密管理) は札に世代トークンと実行中/待機中の分離を要求する状態機械で、有界な遅延のために買う複雑さではないと判断した。方向は常に保守側 (健康な仕事を殺す側には倒れない)
8. **強制停止後、旧世代でハングしたリクエストの札が新世代の idle 停止を遅らせる。** 札はポート単位なので、旧リクエストのクライアントタイムアウトで返却されるまで (最長でモデル設定の timeout 秒) 新世代は idle 停止されない。方向は保守側 (止めない) で有界

## 不変条件

1. `llama_server` 設定がないモデルには一切影響しない (回帰なし)
2. 管理外プロセスを kill / restart しない
3. SAIVerse 終了時に管理下プロセスを全て停止する
4. ヘルスチェック待ちは最大 120 秒 (大型モデルのロード時間を考慮)
5. サーバーログはセッションログディレクトリに `llama_server_{port}.log` として出力
6. `command` 指定時、ビルドアップ用フィールドは全て無視 (排他)
7. **処理中のサーバーを idle 停止しない** — 暇と証明できたときだけ止める (busy 判定は `/slots`、証明不能なら止めない)

## 設定例

### コマンドモード (既存スクリプト活用)

```json
{
  "model": "gemma4-31b",
  "provider_ref": "llama_cpp_server",
  "context_length": 128000,
  "llama_server": {
    "command": "C:/Users/user/llama/start_gemma4_31B.bat"
  }
}
```

### ビルドアップモード (フルスペック指定)

プロバイダ:
```json
{
  "id": "llama_cpp_server",
  "display_name": "llama.cpp Server",
  "protocol": "openai_compat",
  "base_url": "http://127.0.0.1:8080/v1",
  "llama_server_binary": "/path/to/llama-server"
}
```

モデル:
```json
{
  "model": "qwen2.5-72b-q8",
  "display_name": "Qwen 2.5 72B Q8 (llama.cpp)",
  "provider_ref": "llama_cpp_server",
  "context_length": 32768,
  "llama_server": {
    "model_path": "~/models/qwen2.5-72b-q8.gguf",
    "n_gpu_layers": -1,
    "parallel": 2,
    "extra_args": ["--slot-save-path", "~/.saiverse/llama_cache"]
  }
}
```

## バイナリ解決順 (ビルドアップモードのみ)

1. `llama_server.binary` (モデル設定内)
2. `llama_server_binary` (プロバイダから継承)
3. 環境変数 `LLAMA_SERVER_BINARY`
4. PATH 上の `llama-server`
