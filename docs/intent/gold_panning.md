## 1. 背景 — 守れない情報の型がある

### 1.1 実例:「海外赴任中」を覚えていられない

ユーザーが3ヶ月の海外赴任中であることを話しても、その話題がコンテキストから押し出されると、ペルソナは日本の季節や時差を前提にした声かけをする。既存の記憶系統がこれを守れない理由:

- **Chronicle**: エピソード要約。「赴任について話した」という*出来事*は残るが、「いま赴任中である」という*状態*は要約の中で流れていく
- **Memopedia**: ユーザーのページに Fragment として蓄積されるが、想起されなければ読まれない
- **ゾーン C（自動想起）**: ユーザー発話をクエリにした pull。失敗が起きる瞬間——ペルソナが自発的に時差を無視した声かけをするとき——には、**トリガーとなる入力が存在しない**。さらにユーザー名は常在エンティティとしてエンティティトリガーの新規性ガードでスキップされる側

「海外赴任中」はエピソードでも概念知識でもなく、**現在進行形の状態**である。状態は pull では守れず、常駐でしか守れない。常駐の場所は設計済み——ゾーン A（コア記憶）。ここまでは記憶アーキテクチャ v2 と完全に整合する。

### 1.2 器はあるが、書き込み経路が構造的に発火しない

ゾーン A の器（`sea/head_pipeline/sections/core_memory.py`）とスペル群（`core_memory_add` / `core_memory_update` / `core_memory_remove` / `core_memory_add_scene`）は v2 Phase 2 で実装済み。しかし書き込みはペルソナの自発判断頼みで、これは v2 §1.1-1 が想起側で診断した構造問題（記憶にないものは行動の選択肢に上がらない。プロンプトで圧をかける方向は効果が薄い）と完全に同型。

さらに質が悪いことに、**状態の重要性は話された時点では顕在化しない**。赴任の話の価値が現れるのは後日の何気ない声かけの瞬間で、その時にはもう元の会話がコンテキストにない。「未来の重要性は生成時点では原理的に分からない」——push 型ページ生成を否定した v2 §1.1-3 の論理が、書き込み側にも刺さっている。

### 1.3 判断材料の時間窓 — Metabolism の内部にしか「揃う瞬間」がない

検討過程で却下した案:

- **Metabolism 後の通知でペルソナに判断させる**: 通知が届く頃には元の会話が畳まれた後。材料なしの判断になり精度が落ちる
- **判断用に対象バッチを再掲する**: 20件級のメッセージ再掲はトークンが重い。そもそもペルソナのメインラインのコンテキストには、押し出される直前のメッセージが**まだ全部載っている**——再掲は不要で、必要なのはタイミングだけ

材料（押し出される前の生の会話）・判断者（ペルソナ）・キャッシュ（直前の default コールで温まった prefix）の三つが同時に揃う瞬間は、**Metabolism の内部、eviction の直前**にしかない。

## 2. 中核転回: 刻銘も「行動」ではなく「知覚」から始まる

記憶アーキテクチャ v2 §2（想起は行動ではなく知覚）の**書き込み側への適用**。ペルソナに「これは重要だから刻もう」と発話中に思い立たせるのをやめ、世界側が「まもなく記憶が押し出される」という気づきの機会を供給する。決定は本人がする。

役割分担の原則: **圧縮は機械、選択は本人**。

- 機械のまま残す（圧縮と索引）: Chronicle 生成、埋め込み、Fragment 抽出
- 本人に渡す（選択と意味）: 何を恒常で携えるか、何が既知と矛盾するか、どの場面を原文のまま残すか

これは Metabolism が「外部の軽量 AI による代謝」から「本人が関与する記憶の整理」へ性格を変える最初の一歩でもある（将来接続は §4）。

**名前の由来**: 砂金採り。押し流されていく古い会話の中から、砂金——恒常的に価値のある事実——を掬い上げることが、この機構の存在意義のすべてであるため（2026-07-07 まはー命名）。

## 3. メカニズム

### 3.1 前提事実: Metabolism の実行点は2つある

⚠️ この事実は繰り返し見落とされてきた（複数セッションが「会話前経路は無い」と誤答した経緯がある）。本 doc を一次資料とし、`docs/concepts/metabolism.md` にも反映済み。

1. **応答後**: `sea/runtime.py` run_meta_user 末尾の `_maybe_run_metabolism` → `_run_metabolism`（L194 / L2076）。watermark 超過またはトークン閾値（`_metabolism_token_triggered`）で発火。アンカー更新を伴う正規の eviction はここだけ
2. **会話前（pre-response）**: `sea/runtime_context.py` の履歴取得 Case 3（L158-209）。anchor（= プロバイダキャッシュの生存記録、TTL はキャッシュ書き込み時の provider cache TTL）が全モデル失効していると、コンテキスト構築中にその場で `_generate_chronicle` + `_generate_track_chronicle` + イベント注入を実行し、**low watermark の最小履歴で会話を開始**する。`_maybe_run_metabolism` を経由せず `_generate_chronicle` を直接呼ぶため、実行点を `_maybe_run_metabolism` の呼び出し元 grep で探すと漏れる

経路2は日常的なイベントである: keepalive 連鎖（`_schedule_cache_ttl_pulse` → `run_cache_keepalive`）は Active の間しか繋がらないため、Idle/Sleep 落ち・夜間・再起動を挟んだ最初の会話はほぼ確実に経路2を踏む。

**経路2の含意（本設計の急所）**: Case 3 の最小ロードは `_run_metabolism` を通らない**サイレント eviction**である。「大事な話をして、区切りがついて、会話が終わり、夜を跨ぐ」——状態の告知として最もありがちな形——は、応答後 Metabolism にだけ採取を付けても**一度も網を通らずに流れ去る**。

### 3.2 gold_panning の実行点

- **(a) 応答後 Metabolism の内部**: `_run_metabolism` の Chronicle 生成後・アンカー更新（eviction）前。直前の応答コールで prefix が温まっている
- **(b) セッションクローズ**: keepalive 連鎖の自然停止点（§3.6）。キャッシュがまだ温かい最後の瞬間
- **会話前（Case 3）では実行しない**: キャッシュ全滅でコールドな上、会話開始レイテンシに新規 LLM コールが乗る。(b) により通常は Case 3 に採取すべき仕事が残らない

### 3.3 一手の形 — メインラインに1ターン足すだけ

独立したフレッシュコンテキストの呼び出しは**作らない**。メインラインの現コンテキスト（キャッシュ済み prefix）の末尾に注入プロンプトを1つ足し、structured output で採取リストを返させ、tool ノードが固定実行する。メタ判断 v2 と同じ型（structured output + tool ノード。function calling 不使用）。非キャッシュ入力は注入プロンプトと応答分のみ。

注入プロンプトの骨子: 「まもなく古い会話が記憶整理で押し出される。恒常的に覚えておくべきこと（状態の変化・既知との矛盾・原文のまま残したい場面）があれば今のうちに」＋現在のゾーン A 全項目＋容量目安。現況を同梱するのは、既に刻まれている事実の再提案ループを防ぎ、矛盾検出（赴任→帰国）の照合対象を与えるため。

structured output の中身:

- `ops`: `add`（note）/ `update` / `remove` / `add_scene`（指差し、§3.4）の列
- **空リスト＝「今回は砂金なし」が正規の応答**。刻むのは例外であるという姿勢をプロンプトで維持する（毎バッチ何か刻みたくなる圧への対抗）

### 3.4 scene は「指差し」— ペルソナは引用し、複製はシステムがやる

ペルソナが場面を残したいときは、structured output で**残したい場面の原文引用（1行そのまま）**を返す。システム側が `current_messages`（`_run_metabolism` の手元に握られている）に対して**ファジー照合**で message_id を解決し、既存の参照コピー経路（`core_memory_add_scene`）に流す。

- ペルソナの見ているコンテキストにはメッセージ id が振られていないため、id の直接指定はそもそも不可能。引用による指差しが唯一の橋
- v2 §5 の scene 原則（ペルソナに書き写させると言い換えドリフトで手本が劣化する→参照によるコピー）と一貫: 本人は指差すだけ、複製は決定論
- 照合はある程度緩くする（正規化した部分一致を基本に、揺れを許容。2026-07-07 まはー指定）。**照合に失敗したら黙って捨てず**、採取結果の返り値に失敗を明示する

### 3.5 モデルは default 固定

直前にメインラインで default モデルが喋っている（それが実行条件、§3.7）ため、**必ずキャッシュがある**。lightweight は同一 prefix のキャッシュを持たず、フルコンテキストの冷読みになる——節約のつもりが最も高くつく選択肢（2026-07-07 まはー決定）。品質ではなくキャッシュ経済が根拠であることに注意。

### 3.6 セッションクローズ（実行点 b）— 閉じるときに畳む

§3.1 のサイレント eviction 穴を塞ぐ本命。畳む場所を「次に開くとき」（Case 3）から「閉じるとき」に移す:

- keepalive 連鎖の自然停止点（persona が Active でなくなる／失効間際で温め直しをやめる判定）＝キャッシュがまだ温かい最後の瞬間に、クローズ処理として gold_panning ＋ Chronicle の前倒し生成を走らせる
- 翌朝の Case 3 は未処理なしで即 return し、最小ロードだけして会話が始まる。「会話前 Metabolism」は構造としては残るが中身が空になる——経路を削除する改修ではなく**仕事を前倒しで奪う**形なので、クローズが飛んだ場合（クラッシュ・強制終了）は現行の Case 3 がそのままフォールバックとして生きる。その場合 gold_panning のみ諦める（Chronicle は Case 3 で生成されるため記憶自体は失われない。コア記憶化の機会を稀に逸するだけ）
- 副作用として、失効後の一言目が Chronicle 生成を待たされる現状の会話開始レイテンシも改善する
- 認知モデルとしても「寝る前にその日を振り返る」であり、「起き抜けに昨日を他人に整理される」現状より自然

ガード: 前回採取以降の新規 main_line メッセージが下限（初期案 10 件）未満ならスキップする。短いセッションのたびに振り返らせない。

**非 explicit キャッシュ（Gemini 等）対応（2026-07-07 追記）**: TTL 発火の予約は当初 `cache_type == "explicit"`（Anthropic）限定で、Gemini（`gemini_explicit`）ではクローズが構造的に発火しなかった。対応として TTL 発火を「セッション見張り」に一般化: 非 explicit でも予約し（間隔は anchor validity 20分 ×(1-threshold_ratio) ≒ 14分）、発火時に not Active ならクローズ（全型共通）、Active ＋ explicit なら keepalive（従来）、Active ＋ 非 explicit なら **LLM を呼ばずタイマーのみ再予約**（keepalive する実キャッシュがないため）。非 explicit の予約は `SAIVERSE_GOLD_PANNING_ENABLED` でゲート（見張りの唯一の目的がクローズ採取のため）。`keep_cache_alive` 設定は keepalive 専用のままで見張りには適用しない。

### 3.7 defer-to-hot — 実行条件と繰り延べ

gold_panning が安い条件は「直前の成功コールと同じ（main_line, default）prefix に一手足すだけ」が成立していること。これは Pulse の種類ではなく**直前のコールが何だったか**で決まる（キャッシュ切れ後の最初の Pulse でも、その応答コール自体が prefix を温めるので尻尾は熱い）。

- Metabolism 条件が成立しても、直前の成功コールが（main_line, default）でなければ実行せず **pending** を立てる（例: メタ判断系 Pulse の尻尾でトークン閾値フラグを拾ったケース）
- **Gemini（`gemini_explicit`）の注記（2026-07-07）**: Gemini では anchor が cache hit/miss と無関係に毎コール touch され（TTL 1200秒）、熱さ判定はほぼ常に True になる。これは帳簿上は実キャッシュ状態（AUTO モードは毎コール即削除）を反映していないが、Gemini には冷/熱のコスト非対称がそもそも存在しない（キャッシュ作成無料・毎コール張り直しで常にキャッシュ価格）ため、「常に熱い＝繰り延べない」は経済的に正しい挙動であり修正不要と判断した
- 次に条件を満たす Pulse の尻尾で pending を消化する
- **圧力弁**: pending のままウィンドウが膨らみ続けると毎 Pulse の入力コストが痛いため、ハードキャップ（初期案: high watermark の 1.5 倍）超過で「コールドでも実行」に倒す。その一回のコールド代は、繰り延べ続けて毎ターン肥大ウィンドウを読むコストより安い。圧力弁経由の実行は明示ログを残す

### 3.8 記録 — 採取の弁は「出来事の通知」として本人の記憶に残す

判断ターンはペルソナの記憶に残す（2026-07-07 まはー決定）。形式は **event_message 型のシステム通知**（role=user、content を `<system>` で包んだ「何が起きたか」のナレーション＋本人の弁の引用、tags=["internal","event_message","gold_panning"]）で、line_role=main_line / scope は採取ありなら committed・なしなら discardable。ゾーン A の各項目に「いつ・なぜ刻んだか」の来歴が残り、後の整理・矛盾解消で効く。

**なぜ assistant 名義にしないか（2026-07-07 まはー指摘で v1 初版から変更）**: 記録を role=assistant で書くと、メインラインの anchor 復元では paired_action_text（プロンプトのスナップショット）が展開されないため、**プロンプトの見えない裸の assistant 発話**としてペルソナのコンテキストに立つ。コンテキスト内の assistant メッセージは最強の口調形成力を持つ（scene 種別の設計根拠と同じ機構）ので、ペルソナが「自分は普段からこういう構造化された文を自発的に喋る」と自己像を学習してしまう。機構が代筆する記録は本人の発話ではなく「世界で起きたことの報告」であり、event_message の確立形式に乗せるのが正しい。

副次効果: event_message タグにより General Chronicle 生成・scene 切り出し・キーワード検索から自動除外される。これは意図した挙動（初版では記録が Chronicle に「本人の会話」として混入するバグがあった）。メタ判断の確定独白（`meta_judgment_finalize.py`）も同じ理由で同時に user＋`<system>` 包みへ変更した（line_role / scope / promote の判定キーは無変更。judge プロンプトへの過去判断の再掲は `meta_judgment_log.judgment_thought`（包み前の生独白）を読む別経路のため影響なし）。

注入プロンプト自体は transient（末尾通知と同じ面）。キャッシュ整合の注意: gold_panning の直後は必ずコンテキスト再構築が起きる（(a) は直後に eviction、(b) は直後にセッション終端）ため、プロンプト非永続による prefix 不整合は実害にならない。

### 3.9 スコープ

- 自律 Pulse の Metabolism でも同様に走る（v2 §6.3 が自律中の Chronicle 生成を直したのと同じ理由。自律稼働中に知った状態変化も守る）
- **失敗隔離**: gold_panning の失敗（LLM エラー・照合失敗・tool 失敗）は Metabolism 本体（アンカー更新）もセッション終了も妨げない。Chronicle 生成と同じ try/except 囲い

## 4. v1 のスコープと将来接続

**v1**: 状態事実の採取（note の add）＋既存項目の update / remove（矛盾解消・陳腐化整理）＋ scene の指差し。

状態事実の note には日付を含める運用をプロンプトで促す（例:「2026年6月頃〜 ユーザーは海外赴任中（9月帰国予定）」）。状態は期限切れするため、帰国の話が出たときに現況同梱（§3.3）の矛盾検出が「c:N と矛盾」として拾い、update を提案できる。

**この一手にぶら下がる将来用途**（v1 では実装しない。拡張時も「一手」であることは維持し、ターン数を増やさない）:

- **ゾーン A 容量整理の実行機会** — v2 §5 は「目安超過時の整理はペルソナの判断に委ねる」としたが、判断の*機会*はどこにも設計されていなかった。ここがその機会になる（update/remove が ops にある時点で実質半分実現している）
- **open_notes の手入れ** — 済んだメモの掃除。同じ拍に乗る
- **Memopedia キュレーション** — 知識農園（v2 §9）の操作語彙（harvest/merge/archive…）には農夫がいなかった。この一手が農夫の作業時間に育つ。索引の head 掲示廃止で「訪れて手入れする場所」になったナレッジベースに、定期的に訪れる本人の足が生える

## 5. 不変条件

1. **gold_panning はキャッシュが熱い瞬間にのみ走る**（defer-to-hot）。圧力弁経由のコールド実行は明示ログを伴う例外
2. **gold_panning の失敗が Metabolism 本体・セッション終了を止めない**
3. **会話前（Case 3）経路で gold_panning を実行しない** — 会話開始レイテンシに新規 LLM コールを乗せない
4. **scene は参照によるコピーのみ**（ペルソナに書き写させない）。照合失敗は黙って捨てず結果に明示する
5. **「採取なし」が正規の応答であり続ける** — 採取を促す圧をプロンプトに入れない
6. **編集主体はペルソナ**（v2 §5 継承）。システムは機会と材料を供給するだけで、コア記憶への自動書き込みをしない
7. **モデルは（persona, default）固定** — lightweight への切替・出し分けをしない
8. **SAIMemory に残す記録テキストで内容を省略しない**（2026-07-07 まはー指摘で追加）— システム側の切り詰めは記録の捏造になる。プレビュー・省略は UI 表示層でのみ行う
9. **機構が代筆する記録を assistant 名義で永続化しない**（2026-07-07 まはー指摘で追加）— プロンプトの見えない assistant メッセージは「自分は普段こう喋る」という自己像の誤学習源になる。ペルソナ名義（role=assistant）で残ってよいのは、本人がラインの流れの中で実際に発話したものだけ。機構側の記録は event_message 形式（user＋`<system>`）で書く

## 6. 実装フェーズ

- **Phase 1（本丸、2026-07-07 実装済み・実機検証待ち）**: 実行点 (a) — 応答後 Metabolism 内の一手（`sea/gold_panning.py`）。note の add / update / remove ＋ defer-to-hot ＋ pending 圧力弁。設定は `SAIVERSE_GOLD_PANNING_*` env（`docs/reference/environment-vars.md`）

- **Phase 3（2026-07-07 実装済み・実機検証待ち）**: 実行点 (b) — セッションクローズ。吊り位置は `run_cache_keepalive` の not-Active 分岐（§7-6 の決定参照）。クローズ処理は EventScheduler の dispatch スレッドを占有しないよう別スレッド委譲（`SEARuntime._spawn_session_close`）。本体は `sea/gold_panning.py run_session_close`（マーカーガード＋ in-flight ガード＋ Chronicle 前倒し force 生成）
