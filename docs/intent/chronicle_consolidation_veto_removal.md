用語 (この文書で使う既存語彙): **束ね** = 未統合の一次あらすじたちを 1 本の上位あらすじへ
統合すること (親を足すだけで、子の本文は書き換えない)。**帯** = 毎回の会話の頭に載る
Chronicle 枠 (予算 2 万字)。⚠️ landscape §「あらすじのレベル制」の「帯 (同じ次数の
ノード列)」とは別物 — あちらは束ねの内部の並びで、この文書では使わない。**窓** =
モデルごとの提示コンテキスト (起点 anchor 以降の生ログ − 畳んだ範囲 + その位置の
digest)。**窓の記録** = (ペルソナ, モデル) ごとに窓の状態を持つ DB のレコード
(`session_anchor` テーブル、キャッシュ TTL と最終使用時刻を持つ)。**節目** = そのモデルの
頭 (帯を含む凍結スナップショット) が組み直される瞬間。主な契機は Metabolism 実行と
窓の記録のキャッシュ TTL 失効の二つで、他にも読み戻し直後・補修ジョブ後などの組み直しが
ある (cached_head_architecture)。**吸収** = あらすじにならなかった端数を、隣のあらすじを
開き直して合体させる補修。こちらは**本文を書き換える** (正確には「新しい id で作り直して
古い方を消す」— absorption.py の generate-then-swap)。

## 原則 (この設計の芯)

**共有の記憶の整理は、自分の規則だけで前進する。提示 (各モデルの窓と帯) は視点であり、
視点は共有の記録に拒否権を持たない。見え方の帳尻は、モデルごとの帯の組み直し (節目) で合わせる。**

これまでの設計は逆向きだった — 束ねの発火判定が全モデルの窓の記録を照会し、どれか
一つでも提示中なら止まった。拒否権の持ち主は死んでも (使わなくなったモデルの窓の
記録にも掃除が無く) 拒否権が残り、現役でモデルを切り替える利用者では拒否が実質常時
かかる。止めることで守られる品質は無く (下の「なぜ壊れないか」)、束ねの停止 = 帯の
肥大 = 利用者の API 料金だけが実在した。[chronicle_coverage_gaps.md](chronicle_coverage_gaps.md)
の「穴は統合を止めない」(2026-09-08) と同じ仕分けの、提示への適用。

**除外の出典の検査 (2026-09-27 整合性レビューで判明)**: この除外の由来は旧
chronicle_consolidation.md §3 の「提示中のものを上へ畳まない (experience_structure §4-1)
の帰結」だが、experience_structure §4 にその規則は無い。それどころか §4-4 の 2026-07-25
明確化は「圧縮区間の一次あらすじは未束ねのまま列にいるので、通常の列のあふれで
二次あらすじへ束ねられる — 道は最初からあった」と、**提示中の一次あらすじを上へ束ねる
ことを機構の本体として明言している**。撤去する柵は、出典の無い導出だった。

## 全体の見立て (whole-system)

- **誰が何に頼れるべきか**: 利用者は「モデルをいくつ・どう切り替えても、記憶の整理が
  止まらず、送信量が設計どおりの水位に収まる」ことに。ペルソナは「提示中の記憶の
  文面が、自分のモデルの節目以外で裏から変わらない」ことに。機構は「束ねの発火と
  対象が、提示状態という自分の外の状態に依存しない」ことに頼れる。
- **旅の全体**: 生ログ → (退場) → 一次あらすじ → (束ね) → 上位あらすじ → 各モデルの
  帯として提示。窓と帯はモデルごとの視点で、記憶の木 (あらすじの階層) はペルソナ
  共通の一本。本設計は「木の成長」と「視点の帳尻合わせ」の責任を分離する。
- **不変条件と所有権**:
  1. **束ねは子の本文を書き換えない (親の追加と統合済み印だけ)** — これはコードの現在の
     性質であって、正典に宣言された不変条件では**なかった** (由来は廃止済みの旧
     chronicle_consolidation.md 不変条件 5。2026-09-27 整合性レビューで、現行正典の
     どこにも宣言が無いことを確認)。本設計の土台なので、**本 intent で不変条件として
     明文化し、回帰テストで固定する**。所有は bands (束ね・繋ぎ直しの帳簿操作)。
  2. **提示中の digest のバイト列は、そのモデルの節目以外で変わらない** — 束ねは 1 に
     より自動成立。機構の経路でこれを破りうるのは吸収 (本文の作り直し) だけなので、
     吸収の拒否権は「キャッシュが生きている窓の記録」に限定して**残す** (機構 C)。
     ユーザー自身の操作 (あらすじの本文編集・再生成・削除) は例外として容認する —
     利用者の権利であり、削除には既存の道連れ処理がある。
  3. **帯は、窓が見せている期間を二重に見せない** — 現行の束ねの停止でも、これは
     支えきれていなかった: 畳みへの引き当て照会 (`get_entries_covering_messages`) は
     統合済みを絞らないため、読み戻し・被覆の印の経路では統合済みの一次あらすじが
     畳みに載り、その**親**は今日の除外名簿 (id の単純一致) では抜けず二重提示になる。
     機構 B はこの既存の欠陥も一緒に直す。所有は帯の組み立て (降下規則)。
- **変更の置き場**: 症状の現場は束ねの発火判定だが、修正の置き場は「拒否権の構造」
  そのもの。発火判定に例外 (TTL・現役判定) を足す案を二度検討して捨てた — どちらも
  拒否権の持ち主を減らすだけで、持ち主が二人以上いる限り機能不全の期間が残る (会話の
  標準モデルと裏方の軽量モデルは、別々の窓の記録を独立に持つ —
  [tests/test_session_anchor_rows.py](../../tests/test_session_anchor_rows.py) の
  `test_touch_routes_to_actual_usage_model` が touch の行き先の分離を固定している。
  二本が常に同時に温かいことまでは固定していないが、なかみつさんの Gemini/Gemma の
  日常切り替えだけで持ち主は複数になる)。
- **帰結 (これが完全に働いても残るもの)**: 節目の間、新しくできた親は帯に現れない
  (頭は凍結スナップショットなので従来どおり)。降下規則で開いた部分木は予算ガードでは
  畳めないため、**fold が窓に居る間、帯は予算を超えうる** (超過分の上限は、開いた親の
  子孫のうち窓の外の分の字数。窓が前進して fold が退けば解消する)。超過の発生は
  WARNING で観測する。モデルごとに帯の見え方が違うのは既存の容認 (arasuji_levels
  §15-4「モデルごとのばらつきは容認」— あちらは「どこまで生で見ているか」の割れの
  話で、帯の見え方の違いまで広げるのは本設計の判断) のまま。

## なぜ拒否権を消しても壊れないか (検算の記録)

束ねの拒否権が防ぐとされたのは「提示中のあらすじを上へ畳むと、同じ期間が窓の digest と
帯の親の両方に出る」の一点だけ。時系列で追う:

1. モデル A の窓があらすじ X を digest 提示中に、束ねが X を親 P へ畳む。
2. X の本文は変わらない (不変条件 1)。A の窓の描画は digest 解決 (entry id → 本文) で
   行われるため、**一バイトも変わらない**。キャッシュ無傷。
3. A の帯は節目まで凍結スナップショットのまま。P は凍結後に生まれたので載っていない。
   二重提示はこの間、起きない。
4. A の節目で帯を組み直す。ここで初めて P が候補になる — このときだけ「P は X の期間を
   含む」問題が現れる。機構 B (降下規則) がここで受ける。

つまり二重提示は「束ねを止めるべき理由」ではなく「節目の帯の組み方の問題」だった。

## 機構

### A. 束ねの拒否権を撤去する

束ね (発火の勘定・畳み対象・境界) から提示中 digest の除外を全廃する。

- `bands.py` の excluded (字数の勘定から外す / 畳み対象から外す / 畳み範囲が跨げない
  境界①) を撤去。arasuji_levels §3-2 の境界①「提示中の圧縮区間」を同じコミットで
  廃止改訂する。境界②「未統合の下位レベルノードが間に居る」は木の形の問題なので残す。
- **勘定の主語の変更を明文にする** (数値の契約には主語がある): excluded が消えることで、
  レベル別の並びの発火上限 (5,000 字) と残す量 (2,500 字) の勘定は「窓が digest で
  見せている分も**含む**」へ主語が変わる。残す量の目的は「いちばん新しい体験を細かい
  まま保つ」ことであり、新しさは木と時間の性質で提示状態の性質ではないので、この主語が
  正しい。窓で提示中の直近の一次あらすじが残す量の枠を使うのは意図どおり (帯からは
  除外名簿で抜けるので二重にはならない)。この主語をテストで固定する。
- 束ね経路 (`session_lifecycle.py` の Metabolism 側) から全モデル fold 集約の参照を
  外す。「照会に失敗したら束ねを見送る」という安全側の扱いも、束ねについては照会ごと
  消えるので不要になる。
- **見積もり (生成コスト確認モーダル、`api/routes/people/arasuji.py`) の扱い**: 束ねの
  コール数見積もりからは除外を外す (実行と同じく除外なし)。吸収の見積もりには従来
  どおりの集合 (第一段では全モデル集約のまま) を渡し続ける — 表示と実走が違う数を
  言ってはならない (arasuji_levels §16-2)。第二段で吸収側の集合が変わるときに、
  見積もりも同じ判定関数へ揃える。
- **既存データへの一斉適用の検査 (実装時)**: 除外で長く取り残された一次あらすじは、
  両隣が先に別の親へ束ねられていることがある。解放後にそれが上位の被覆期間と**内包**の
  関係になる場合は既存の繋ぎ直し (coverage_gaps 機構 C) が回収する。**交差 (内包でなく
  跨ぎ)** になる形が実データに存在するかを、なかみつさんの診断の形 (解放される Lv1 の
  期間 × 既存上位の期間) で検査してから出荷する — 一次あらすじの束ねには隣接の壁が
  無い (`bands.py` の level≦1 早期 return) ため、交差があるなら境界の要否をそこで
  判断する。

### B. 帯の降下規則 — 窓が見せている子を含む親は、子に降りる

帯の組み立て (`sai_memory/arasuji/context.py` `get_episode_context` の除外フィルタ、
現行は階層を辿らない id の単純一致) を再帰の降下に変える:

> 候補エントリの子孫 (source_ids を辿った集合) に、除外名簿 (いま組んでいるモデルの
> 窓が digest 提示中のエントリ id) のものが含まれるなら、そのエントリは見せず子に
> 降りる。降りた先で、除外名簿のものは抜き、残りを見せる。子孫に含まれなければ
> 従来どおりそのまま見せる。

- 判定は id の包含だけで済む — 窓の期間 (時刻) を組み立て側へ新たに渡す必要はない。
  親→子リンク (source_ids) は組み立て地点で全エントリ分ロード済み。除外名簿が空
  (単一モデルの平常時・畳みの無い窓) なら降下は一度も起きず、**現行と完全に同じ出力**になる。
- **実装の形は「降下後の一覧を先に作る」**: 除外名簿と交わる祖先をエントリ一覧から
  除き、代わりに降下先の子たちを置いた一覧を作ってから、既存の選定 (質量の累積規則)
  と予算ガード (`_compress_within_budget`) に渡す。予算ガードは渡された一覧からしか
  親を引かないので、「降下で開いた側から親を再導入して二重提示が復活する」経路が
  構造的に閉じる (親昇格の例外条件を予算ガードに書き足す形は採らない — 例外は漏れる)。
- 除外名簿の読み取りは従来どおり、いま組んでいるモデルの窓の記録だけ
  (`memory_weave.py` capture)。変更なし。

### C. 【第二段】補修 (吸収・開き直し) も同じ構造にする — 書き直しは新版を作り、旧版は見ている窓が手放すまで残す

**第一段では補修の拒否権に触らない — 現状 (全モデル集約) のまま残す。** 現状維持
なので退行は無く、なかみつさんの症状 (束ねの停止と帯の肥大) は A・B だけで解決する。

第二段の形は 2026-09-27 のまはーの指摘「根本的には束ねと同じ話」で確定した。当初案
(拒否権をキャッシュの生きている窓に絞って残す — 温度判定) は、拒否権の持ち主を減らす
だけの手当てで、①②と同族だった。同じ構造にするとこうなる:

> 補修は**拒否権ゼロでいつでも進む**。あらすじを書き直すときは新しい版 (新 id) を
> 作るだけで、**旧版は、それを digest 提示中の窓が一つでもある間は消さない**。
> 各モデルの窓は自分の節目 (キャッシュがどうせ組み直る瞬間 = その窓の次の Metabolism)
> で畳みの参照を新版へ付け替え、どの窓からも参照されなくなった旧版をそこで消す。

- これで不変条件 2 (提示中の digest のバイト列は、そのモデルの節目以外で変わらない) は
  **補修についても書き換えではなく構造で成立する**。キャッシュと「ペルソナが見た文面」の
  両方が守られるため、保護の目的が (a) キャッシュか (b) 体験かという確認は**問いごと
  消滅**した (両方守られる)。温度判定 (`_anchor_entry_is_hot` の共有) も不要になる。
- 旧版の帳簿: エントリに「新版への差し替え先」(superseded 参照) を持たせる。連鎖
  (旧→新→さらに新) は最新版まで辿る。掃除 (どの窓からも参照されなくなった旧版の削除)
  の判定には全モデルの畳み集約 (`collect_folded_chronicle_entry_ids`) を使う — 拒否権の
  供給口だった関数が、掃除の目印に格下げされて存続する。
- **帯の除外名簿の拡張が要る**: 窓が旧版の digest を見せている間、その差し替え先
  (新版) も帯に出さない (出すと同じ期間が新旧二重に載る)。除外名簿の展開時に
  superseded 連鎖を辿って新版の id も名簿へ足す — B の降下規則と同じ場所で処理できる。
- 旧版は差し替え先が付いた時点で束ね・補修の対象からは外れる (木の現役は最新版だけ)。
- ユーザー操作の手動削除との交差 (旧版を見せている最中に新版が消される等) は実装時に
  既存の道連れ (`remove_folds_referencing_entry`) と突き合わせて詰める。
- 「照会に失敗したら (None)、その回の補修は見送る」という安全側の扱いは掃除の判定に
  そのまま残す (待つのは常に安全)。

### D. 窓の記録の掃除は不要になった (やらない)

A・C が揃うと、使われなくなったモデルの窓の記録はどの経路にも拒否権を持たない無害な
状態記録になる。当初案の掃除 (日数 → TTL の二転) は、この構造では手当てする対象を
失うため実施しない。容量が気になる規模になったら別件として起こす。C が保留の間、
使われなくなったモデルの畳みは吸収だけを止め続ける (現状どおり) — それでも束ね・帯は
止まらないので、掃除を先行させる理由にはならない。

## 第一段の設計確認 (まはーへ)

2026-09-27 の裁定は「拒否権の構造ごと撤去」の方向まで。第一段の中身 2 つ — 束ねの
拒否権の全廃 (A) と、帯の降下規則「窓が見せている子を含む親は、親を見せず子に降りる」
(B)、掃除をやらない (D) — は本文が初出なので、この intent の確認をもって承認とする。

## 第二段の位置づけ (2026-09-27)

第二段 (機構 C) の方向は同日中に確定した — 温度で拒否権を絞る当初案に対し、まはーが
「根本的には束ねと同じ話」と指摘し、旧版保持 + 節目乗り換えの形 (機構 C の本文) に
差し替えた。これで当初添えていた確認 1 点 (「書き換え禁止が守るのはキャッシュか
体験か」) は、両方守られる構造になったため問いごと消滅した。残る第二段の設計詳細は
旧版の帳簿・掃除・手動削除との交差で、実装計画は第一段の出荷後に詰める。

## 検証の旅

- **純関数の回帰テスト**: 降下規則 (親子 3 階層 × 除外の位置の組み合わせ、除外が空
  なら現行と同一出力の golden)、降下後の一覧に祖先が居ないこと (予算ガード経由の
  再導入が起きない構造の確認)、温度判定の共有 (生存・失効・NULL)、勘定の主語
  (発火上限と残す量が提示中の分を含む) の固定、不変条件 1 (束ね・繋ぎ直しが子の本文に
  触れない) の固定。
- **補修の旧版保持 (第二段)**: 補修後、(a) 旧版が提示中の窓の digest はバイト列不変、
