# 作成直後の文書と登録失敗の後始末

> **ステータス**: 検証待ち (2026-10-02、文書側の実装・隔離回帰済み、PR レビュー待ち)
> **関連**: [元 issue](../issues/media_files_orphaned_when_item_creation_fails.md)、[部屋のアイテム表示](room_item_display_cap.md)、[メディア入力](multimodal_input_pipeline.md)

## 全体と所有権

文書の作成は、本文の保存 → 要約の保存 → Item と置き場所の DB 登録 → キャッシュ・部屋通知 → 文書参照の返却を通る。失敗の後始末はこの一連の作成が持ち、読み手や次回起動の掃除に委ねない。ユーザーとペルソナの既存の物、履歴から読める添付、登録済みの物を傷つけず、登録前に拒否された文書だけを残さない。

- `document_create` の本文と要約は、まだ公開されていない同じ作成の新規ファイル。新規作成を排他的に成功させたファイルだけを控える。パスを受け取ったこと、名前が似ていること、DB に見つからないことを所有権の証明にしない。
- `generate_image` は Item 登録に失敗しても、生成画像の path・URI・履歴用 snippet を返す。生成には課金もあり、この成果物は単なる孤児ではない。現状の返却を保持する。捨てるか、登録の再試行口を作るかは別の仕様判断であり、この修正で決めない。
- チャットの画像・文書・音声・動画添付も Item 登録とは独立して会話 metadata に残る。既存 URI から動画を登録する経路、管理画面の任意の FILE_PATH、`create_*_item_for_user` / `create_picture_item` に渡されたパスも所有権を引き渡していないので消さない。

## 不変条件と実装位置

1. 文書作成の失敗時、当該呼び出しが排他的に作成した本文・要約だけを削除する。既存ファイルは上書きも削除もしない。後始末時の検査で別ファイルへの差し替えやハードリンク共有が判明したものも保持する。
2. DB の書き込みを明示的に flush してから commit へ進む。commit を一度も試していない失敗だけが後始末の対象。commit 呼び出しが例外を返した場合は、永続化の成否を断定できないので全ファイルを保持する。rollback 成功や別接続での非存在確認を commit 不成立の証拠にしない。
3. commit 後のキャッシュ更新・部屋更新・履歴通知の失敗はファイルを削除しない。
4. 削除失敗はログに残し、元の失敗を隠さない。広範囲の走査や既存の孤児掃除はしない。
5. 対象は通常の作成呼び出しがまだ公開していない UUID 名の文書だけ。同じパスを並行 writer に渡してはならない。所有権の検査と削除の間へ外部プロセスが割り込んで差し替えるケースを原子的に防ぐ仕組みではない。任意の共有ファイルの掃除には使わない。
6. ファイルを作る `media_utils` が排他的な新規作成を記録し、`ItemService.create_document_item` が保存から DB 登録までの寿命を管理する。要約側も同じ所有権へ参加し、サイドカーだけ取り残さない。

## 検証の旅程

隔離 SAIVERSE_HOME と一時 SQLite、合成ペルソナで、実物の本文保存・要約生成・Item/ItemLocation 登録を通す。保存失敗、要約失敗、DB の add/flush、commit の直前/直後の例外、通知失敗を注入し、DB と本文・要約を照合する。既存ファイルの衝突、複数の所有ファイル、差し替え・共有ファイル、unlink 失敗も確認する。

画像 API はモックだけを使い、登録失敗でも返却した画像が読めることを固定する。アップロードや管理画面の既存パスは登録側から削除しない契約を確認する。本番ペルソナ・本番 DB・有料 API は使わない。commit 成否不明時に残るファイルと既存の孤児掃除は未解決のまま明示する。

## 隔離検証の結果 (2026-10-02)

- 新規の所有権・失敗注入テストは 35 件。関連メディア・アイテム・チャット・Gemini ヘルパーの 10 ファイルは 172 passed / 30 subtests passed。
- LLM client も含めた別の広域チェックは 259 passed / 33 subtests passed、既存 11 件が環境の DNS 解決不可 (`openrouter.ai` / `integrate.api.nvidia.com`) で失敗。provider の安全検査は変更しない。
- 変更 Python の ruff、`git diff --check`、台帳の検査は通過。全スイート・実機・有料 API は未実施。
- 独立レビューで通常の公開前 UUID 文書の writer を再照合し、commit 前にパスを公開・共有する経路は無いことを確認。要約 LLM は本文だけを受け取り、キャッシュと通知は commit 後、文書編集は登録済み Item を前提にする。この適用範囲では追加指摘なし。外部プロセスによる検査直後の同名パス交換を原子的に防ぐ仕組みとは扱わない。
