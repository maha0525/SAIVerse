# Physical Ear — ウェイクワード無しの常時リッスン音声入力

ウェイクワードを言わなくても、声で話しかければペルソナが応えてくれる。その「常に開いた耳」を SAIVerse に据えるための設計指針。**Fixture** (`docs/intent/observer.md`) の存在論を共有する、Observer の兄弟にあたる新種の Fixture であり、マイクを持つ物理デバイス (ｽﾀｯｸﾁｬﾝ / PC マイク / スマホ / USB マイク) を Building に設置された「耳」として扱う。

> **本書のステータス: ドラフト (v0.2, 2026-07-09) — 設計中**。Web 版 Claude との壁打ち (VAD ベースの発話セグメンテーション + 判断層 + 応答生成の三段構成) を受けてまはーが起こしを依頼。2026-07-09 のインタビューで骨子確定 — **Observer の子ではなく別 Fixture タイプとして切り出す** / 応答者は設置 Building の occupant 全員 / transport は案 A (セグメント POST) / Ear 自身は永続蓄積しない (§決定事項記録)。残る論点 (continue セッション管理・判断層 E4B の実行環境・応答中の耳の扱い等) は末尾「未解決の論点」。

## これは何か

- **Physical Ear (物理耳)**: Building に固定設置された、マイク入力を常時聴き続ける新種の Fixture。ユーザーの発話を捉え、ウェイクワード無しで「これは応答すべき発話か」を判断し、応答すべきなら発話音声をペルソナの会話経路に注入して応答を引き出す。Observer (蓄積型 Fixture) とは兄弟で、Fixture という存在論 (Building 固定設置物) だけを共有し、下流は別物 (§Observer との関係)。
- **三段パイプライン**:
  1. **発話セグメンテーション (VAD)**: マイク音声を常時 VAD (Voice Activity Detection) にかけ、無音区間で発話を塊として切り出す。固定 10 秒窓ではなく、発話が 3 秒でも 40 秒でも「一つの完結した発話」として区切る。
  2. **応答判断 (判断層 / 軽量マルチモーダル)**: 切り出した発話音声を軽量モデル (NPU で動く Gemma 系マルチモーダル E4B を想定) に渡し、`ignore` / `respond` / `continue` の三値で「応答すべきか」を判断する。判断基準はシステムプロンプトで設定でき、声だけでなく大きな物音などにも反応させる、といった調整ができる。
  3. **応答生成 (大モデル)**: `respond` 判定時のみ、発話音声を大きめのマルチモーダルモデル (Gemini 3.5 Flash を想定) に渡す。既存の「音声でペルソナに話しかける」会話経路 (ｽﾀｯｸﾁｬﾝで実績あり) を再利用し、ペルソナが応答する。
- **入力源に依存しない耳**: マイクは ｽﾀｯｸﾁｬﾝ に限らない。PC の内蔵/USB マイク、スマホ、Bluetooth マイクなど、どこから来た音声でも同じ「耳」として扱えるよう、入力源と SAIVerse 本体の境界を分ける。

## これは何でないか

- **文字起こし前提ではない**。判断層・応答生成ともに音声を直接マルチモーダルモデルに渡す。Web 版 Claude は判断層の前に軽量 ASR (whisper.cpp 等) を置く案を出したが、想定する Gemma 系 E4B は軽量ながら音声を直接聴けるマルチモーダル性能を持つため、文字起こし層を挟まず一貫して音声で通す。固有名詞の多い SAIVerse では、音声解釈に事前知識を効かせられる音声直入力の利点が大きい。
- **Observer ではない (兄弟の別 Fixture)**。既存 Observer (SGP30 / ウェアラブル) は「観測値を `observer_metrics` に溜め、閾値超過で通知する」蓄積型 Fixture。Physical Ear の下流は根本的に違い、**発話をペルソナの会話に注入して応答を生成する** うえ、**何も永続蓄積しない**。Fixture という *存在論 (Building 固定設置物)* だけを Observer と共有し、Observer の子 (`EXEC_KIND` 拡張) ではなく別 Fixture タイプとして立てる (§Observer との関係)。
- **リアルタイム常時接続 API ではない**。Gemini Live / OpenAI Realtime のようなサーバ側 VAD・ターン検出に丸投げする構成は採らない。常時接続はコストと「話しかけていないのに反応する」問題を持つため、ローカルの VAD + 判断層でゲートしてから大モデルを叩くハイブリッドにする。
- **ペルソナの自律行動 (pulse) ではない**。Physical Ear は環境側の設備 (Fixture) であり主体ではない。捉える・判断する・会話に渡す、までが仕事で、応答内容の生成はペルソナ側の既存経路が担う。

## なぜ必要か

### 1. ウェイクワードの摩擦を消す

「〇〇、〜して」と毎回呼びかけるのは、そこに *いる* 相手への話しかけ方ではない。ｽﾀｯｸﾁｬﾝが机の上にいて、こちらが独り言まじりに話しかけたら振り向く——その体験には常時リッスンが要る。ウェイクワードは「呼び出しボタン」であって「同居する存在」の応答様式ではない。

### 2. 10 秒問題を VAD で構造的に解く

まはーの当初案「10 秒ごとに音声を切って判断」では、発話が 10 秒を跨いだときに発話完了を待って全音声を繋ぐ制御が難しい。VAD で「無音が一定時間続いたら発話終了」とすれば、発話長に関わらず完結した塊が切り出され、固定窓の制約自体が消える。切り出し → ラベル付け → 必要なら大モデル、が綺麗に完結する。

### 3. respond 条件を設定可能にする = 耳の性格を持たせる

判断層のシステムプロンプトを設定可能にすると、同じ機構で「声にだけ反応する耳」「大きな物音にも反応する耳」「特定ユーザーの声だけに反応する耳」を作り分けられる。ユーザーやペルソナの希望次第で耳の感度・対象を変えられる。これは既存 Observer の `NOTIFY_RULES_JSON` (数値閾値) の音声版にあたる、意味的なゲート設定である。

### 4. 知覚型 Observer 一族の足場になる

NPU で軽量マルチモーダル E4B を常時回して環境を知覚する、という形は音声に限らない。アイディア帳の「NPU で Gemma E4B カメラモニタリング」(視覚の常時知覚) は Physical Ear の兄弟であり、「10 秒ごとにカメラを見て内容を記録」も同じ *知覚 → 判断 → (記録 or 通知 or 会話注入)* の構造に乗る。Physical Ear はこの一族の最初の実装であり、抽象の妥当性を検証するケースになる。

## 概念モデル

```
Fixture   … 持ち運べない固定設置物 (Building 直結)
  ├─ Observer … 受けた観測値を observer_metrics に蓄積し閾値で通知する「蓄積型」Fixture
  │     例: SGP30 (pull), ウェアラブル (push)
  └─ Physical Ear … マイク入力を判断層で選別し respond ならペルソナ会話へ流す
        「知覚→会話型」Fixture。何も永続蓄積しない (本書)
        (兄弟候補: カメラ知覚 Fixture = 視覚版。同じ「知覚→判断→ディスパッチ」構造)
```

Observer と Physical Ear は **親子ではなく兄弟** — どちらも Fixture (Building 固定設置物) だが、片方は蓄積、片方は判断してディスパッチする。将来のカメラ知覚 Fixture も、Observer に無理に載せず、この兄弟列に並べる。

Physical Ear は「Building に設置された耳」という Fixture であり、その耳がどのマイクデバイスに繋がっているか (ｽﾀｯｸﾁｬﾝ / PC / スマホ) は入力源の違いにすぎない。耳の *設置先 Building* が、誰の声を誰に届けるか (どのペルソナが応答するか) の文脈を決める。

## 三段パイプラインの担当分界 (edge / core)

「常時・重い・リアルタイム」な部分を入力源の近く (edge) に置き、「設定・ペルソナ紐付け・モデル呼び出し」を SAIVerse 本体 (core) に置く。境界は **完結した発話音声セグメント** の受け渡し。

```
[edge = 捕捉クライアント]                    [core = SAIVerse 本体]
マイク所有                                    Physical Ear Observer
  → リングバッファ (発火 0.5s 前から保持)       → セグメント連結バッファ
  → VAD (Silero 等) で発話区間検出              → 判断層 (E4B, プロンプトは config)
  → 無音エンドポインティングで塊に切り出し   ──▶   ├ ignore → 破棄
  → 完結セグメントを core へ送出                 ├ continue → バッファ保持、次セグメントを待つ
                                               └ respond → 発話音声をペルソナ会話経路へ注入
                                                            (大モデル = ペルソナの通常応答)
```

- **なぜ VAD は edge か**: VAD は連続音声を絶えず処理する軽量リアルタイム処理で、マイクの至近に置くのが自然。ｽﾀｯｸﾁｬﾝ (ESP32) は VAD を回すには非力なため、ｽﾀｯｸﾁｬﾝの場合だけは「生 PCM を母艦へ流し、母艦側の捕捉クライアントが VAD する」中継形にする (§transport 参照)。PC マイクなら捕捉クライアントは母艦上で動き localhost 完結、スマホならアプリ内で VAD する。
- **なぜ判断層 (E4B) は core か**: (1) 判断基準のシステムプロンプトは Physical Ear の config として core が持つ、(2) NPU は母艦上にあり core と同居する、(3) どの入力源から来た発話も同じ判断層・同じ設定で選別したい。ゆえに判断層は入力源に依存しない core 側に一元化する。境界を跨ぐのは *セグメント化された発話* だけで、連続音声そのものは (localhost の PC マイクを除き) 境界を越えない。
- **`continue` (意味的エンドポインティング)**: 無音区切りだけだと「えーっと…」で考え込む沈黙に割り込む。判断層が「文として未完」と見たら `continue` を返し、core はバッファを閉じず次の VAD セグメントを連結する。ただし `continue` が続くと永遠に応答しないため、**連結合計が上限 (例: 60 秒) を超えたら強制 `respond`** の脱出条件を置く。

## Observer との関係 (兄弟 Fixture として切り出す)

| 観点 | Observer (蓄積型 Fixture) | Physical Ear (知覚→会話型 Fixture) |
|---|---|---|
| 上位存在論 | Fixture (Building 固定設置物) | ✅ Fixture (同じ存在論を共有) |
| 入力の受け口 | pull (EventScheduler) / push (metric JSON HTTP) | **セグメント音声 POST** (新経路) |
| 判断 | `NOTIFY_RULES_JSON` の数値閾値 | 判断層モデル (E4B) + 設定プロンプト |
| 永続蓄積 | `observer_metrics` (客観データ) | **なし** (ignore=破棄 / respond=会話文脈へ) |
| 下流アクション | Building 通知 (`add_building_event`) | ペルソナ応答の生成 (`respond` 時) |
| テーブル | `fixture` + `observer_config` + `observer_metrics` | `fixture` (TYPE=`ear`) + 専用 config (別テーブル) |

**決定 (2026-07-09)**: Physical Ear は `observer_config` の `EXEC_KIND` 拡張ではなく、**別 Fixture タイプ (`fixture.TYPE="ear"`) + 専用 config テーブル** として切り出す。決め手は **Physical Ear が何も永続蓄積しない** こと — Observer の背骨は `observer_metrics` の時系列蓄積と閾値通知であり、溜めるものが無い Ear をそこに押し込むと器 (Observer) の方が歪む。Fixture の *配置・登録・入力源非依存* だけを共有し、下流 (判断層・会話注入) は Ear 独自に持つ。これで Observer を「受けて蓄積する Fixture」として純化したまま保てる。

## マイク音声をどう core に流すか (transport 提案)

まはーからの主要な問い。入力源が複数ありうる (ｽﾀｯｸﾁｬﾝ以外も) 前提で、**入力源ごとに捕捉クライアントを差し替え、core への受け口を一本化する**構成を提案する。共通の受け口は「完結セグメントの送出」で、既存 push endpoint の Bearer token 認証パターンを流用する。

### 入力源別の捕捉クライアント

| 入力源 | VAD をどこで | core への transport | 備考 |
|---|---|---|---|
| **PC 内蔵/USB マイク** | 母艦上の捕捉プロセス | localhost | Python の `sounddevice` 等でマイクを掴み、Silero VAD で区切って core に POST。母艦完結なので最も単純。**最初の実装候補**。 |
| **ｽﾀｯｸﾁｬﾝ (ESP32)** | 母艦側 (ESP32 は非力) | ESP32 → gateway (WebSocket) で生 PCM ストリーム → 母艦の捕捉クライアントが VAD | 既存 gateway 経路の延長。ｽﾀｯｸﾁｬﾝは「マイクを流すだけ」でデバイス負荷ほぼゼロ。 |
| **スマホ** | アプリ内 (on-device VAD) | アプリ → Tailscale 経由で core へ POST | ウェアラブルコンパニオンアプリ (`temp/saiverse-wearable-companion-handoff.md`) と同型の「edge で捕捉、SAIVerse で判断」パターン。 |
| **Bluetooth/その他マイク** | 母艦上の捕捉プロセス | localhost | PC マイクと同じ捕捉クライアントで OS 経由入力として扱える。 |

### core 側の受け口 (二案)

- **案 A: セグメント POST (push endpoint の音声版)**
  捕捉クライアントが VAD で切った *完結セグメント* を、1 発話 = 1 リクエストで core に POST する (音声は multipart or base64)。既存 `/api/observer/{id}/push` の認証・冪等の作法をそのまま音声に拡張。core はセグメント受信ごとに連結バッファ更新 → 判断層 → ゲート。
  - 利点: 受け口が離散的で既存 push モデルと形が揃う。実装が最も軽い。edge が VAD を持つ前提と綺麗に一致。
  - 難点: `continue` の連結が「複数 POST を core 側で束ねる」形になり、セッション (どの発話列が一続きか) の管理が要る。
- **案 B: 音声ストリーム受信 (WebSocket)**
  core が WebSocket で連続音声を受け、VAD も判断も core 側で回す。edge はマイクを流すだけ。
  - 利点: ｽﾀｯｸﾁｬﾝ中継形と自然に一致。VAD/判断/連結が全部 core 側で一元化され `continue` 制御が単純。
  - 難点: 常時ストリームが core に流れ込む (PC/スマホでは帯域と常時接続負荷)。VAD を core が全入力源ぶん背負う。

**現時点の推し (要まはー判断)**: 入力源で VAD の置き場が割れる (PC=母艦捕捉プロセス、ｽﾀｯｸﾁｬﾝ=母艦中継、スマホ=on-device) 以上、**受け口は案 A (セグメント POST) に寄せ、ｽﾀｯｸﾁｬﾝだけ「gateway で生 PCM を母艦に流し、母艦の捕捉クライアントが VAD して案 A の POST に合流させる」**のが、入力源を跨いで受け口を一本化できて素直だと考える。案 B の常時ストリームは全入力源に強いるには重い。ただし `continue` のセッション管理コストは案 A の負担なので、そこを詰めてから確定したい。

### 最初の実装ターゲット

**PC/USB マイク + 母艦上の捕捉クライアント (案 A・localhost)** を最初の検証ケースにする。入力源として最も単純 (gateway もアプリも要らず母艦完結) で、VAD・判断層・respond → ペルソナ会話注入の三段を最短で通せる。ここが通れば ｽﾀｯｸﾁｬﾝ中継・スマホは transport の差し替えだけで乗る。

## 守るべき不変条件

### 1. ローカルでゲートしてから大モデルを叩く

VAD と判断層は完全ローカル (母艦 / edge) で回し、大モデル (Gemini 3.5 Flash 等) の API 呼び出しは `respond` 判定時のみに絞る。常時回る部分に課金経路を置かない。これが「常時リッスンなのにコストが応答時だけ」を成立させる核心。

### 2. respond 条件は設定であってコード埋め込みではない

判断層のシステムプロンプト (何に反応するか) と VAD パラメータ (無音判定閾値・終了無音時間・語頭プリロール) は Physical Ear の config として持ち、UI/設定から変えられる。マイクや話し方に合わせた実測調整が必ず入るため、これらをコードに焼き込まない。

### 3. 応答生成は既存のペルソナ会話経路を再利用する

`respond` 時の発話音声は、既存の「音声でペルソナに話しかける」会話エントリ (ｽﾀｯｸﾁｬﾝで実績のある経路) にユーザー入力として注入する。Physical Ear 専用の応答生成ロジックを新設しない。発話は最終的にそのペルソナの SAIMemory 会話文脈に、ユーザー発話として正しいタグで入る (メトリクスとして `observer_metrics` に閉じ込めない)。

### 4. 判断層は入力源に依存しない一点に置く

どのマイク (ｽﾀｯｸﾁｬﾝ / PC / スマホ) から来た発話も、同じ判断層・同じ設定プロンプトで選別する。判断層を入力源ごとに分散させない。境界を跨ぐのはセグメント化された発話であり、判断は core に一元化する。

### 5. 発話者の同定と誤反応の抑止は体験品質を決める

判断層のプロンプトには「独り言・テレビ音声・他人同士の会話は ignore」の例示を入れる。ここの精度が「話しかけていないのに反応する」問題を左右し、体験の質をほぼ決める。将来的に話者識別 (誰の声か) まで踏み込むかは論点だが、初版でも最低限の誤反応抑止をプロンプトに持たせる。

## スコープ (初版)

**含む**:
- Physical Ear を Observer の兄弟 Fixture として立てる (`fixture.TYPE="ear"` + 専用 config テーブル)
- 母艦上の捕捉クライアント (PC/USB マイク + Silero 系 VAD + セグメント切り出し)
- core 側のセグメント受け口 (案 A) + 連結バッファ + `continue` セッション管理
- 判断層 (E4B マルチモーダル) の呼び出しと `ignore`/`respond`/`continue` 三値判定
- 判断プロンプト・VAD パラメータの config 化
- `respond` → 既存ペルソナ音声会話経路への注入 (設置 Building の occupant 全員が対象)
- PC/USB マイクを最初の検証ケースとして end-to-end で通す

**含まない (将来)**:
- ｽﾀｯｸﾁｬﾝ生 PCM 中継 (gateway 経由) — transport 差し替えとして次段
- スマホ捕捉アプリ — transport 差し替えとして次段
- 話者識別 (誰の声か) による宛先/フィルタリング
- 大きな物音・環境音への反応 (判断プロンプト設定で原理上可能だが検証は初版外)
- カメラ知覚 Fixture (視覚の兄弟) — 抽象が固まってから
- **「蓄音機 Observer」連携** (耳が聞いた/無視したログを別 Fixture へ送る) — 優先度低。Fixture 間の情報授受プロトコルが別途要るため本書では想定だけ (§将来拡張)
- 複数ペルソナが同室のときの応答者選択の高度化 (初版は occupant 全員という単純ルール)

## 将来拡張: 「蓄音機 Observer」連携 (優先度低)

Ear 自身は蓄積しないが、将来「耳がいつ誰の声を聞いた / 何を無視した」のログが欲しくなる筋はある。その場合は **蓄音機 Observer** (蓄積型 Fixture) を別に Building へ置き、**Ear が respond でペルソナに喋るのと並行して蓄音機にログを送る** イメージ。蓄積能力を Ear 自身に持たせず、蓄積は蓄積型 Fixture (Observer) の仕事のまま保つ設計。

ただしこれは **Fixture 間の情報授受** を要し、その汎用プロトコル定義は大きめの別案件になる。本書では「拡張するならこの形」という想定だけ置き、初版スコープには含めない。

2. **判断層モデルの実行環境**: NPU 上の Gemma E4B をどう呼ぶか (ローカル推論経路)。既存 `llm_clients/` に乗るか、専用の推論プロセスか。

## 決定事項記録

### 2026-07-09 起草時インタビューで確定

- **別 Fixture タイプとして切り出す**: Observer の子 (`EXEC_KIND` 拡張) ではなく、`fixture.TYPE="ear"` + 専用 config テーブルの兄弟 Fixture として立てる。決め手は Physical Ear が何も永続蓄積しない点 — 蓄積が背骨の Observer に押し込むと器が歪む。Observer は「受けて蓄積する Fixture」のまま純化して保つ。
- **応答者は occupant 全員**: 設置 Building に複数ペルソナがいたら全員が応答する (ユーザーがその Building で喋ったときの現行挙動と揃える)。特定ペルソナ紐付けは初版では持たない。
- **transport は案 A (セグメント POST)**: 捕捉クライアントが VAD で切った完結セグメントを 1 発話 = 1 リクエストで POST。案 B (WebSocket 常時ストリーム) は全入力源に強いるには重いため採らない。ｽﾀｯｸﾁｬﾝだけは gateway で生 PCM を母艦へ流し、母艦の捕捉クライアントが VAD して案 A に合流させる。
- **判断層は入力源非依存で core に一元化**: どのマイクから来た発話も同じ判断層・同じ設定プロンプトで選別する。
- **文字起こしを挟まず一貫音声**: 判断層・応答生成とも音声を直接マルチモーダルモデルに渡す (E4B の音声マルチモーダル性能に依拠)。
- **Ear は蓄積しない**: 将来ログが要る場合は「蓄音機 Observer」を別置し Ear が送る想定 (§将来拡張)。Fixture 間情報授受プロトコルは別案件・優先度低。
