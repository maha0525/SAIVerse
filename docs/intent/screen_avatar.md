## 一言で

チャット画面に枠を一つ作り、いまいる Building の内装と、そこにいるペルソナの姿を映す。この枠の名前は「ルームビュー」(2026-11-22 にまはーが選んだ。経緯は「まはーが決めること」)。ルームビューの脇には、その部屋に置かれているアイテムが並ぶ。ペルソナが 3D のアバター (VRM) を持っていれば、ブラウザがそれを描く。空間の中を歩くことと VR は Godot の役目で、この文書は扱わない。

## 全体像 — 誰に何を約束するか

- **ユーザー**: チャットをしながら、ペルソナが部屋に「居る」ことが目で分かる。何も追加で入れていなくても、内装画像と立ち絵でルームビューが出る。VRM を入れたペルソナは 3D で出る。そのために Godot を入れる必要は無い。
- **ユーザー (アイテムについて)**: 自分の画面に並ぶアイテムと、ペルソナに見えているアイテムが、同じ範囲になる。今は、ペルソナには最近触られた上位だけが見え、ユーザーの画面には全部が並んでいる。
- **ペルソナ**: 姿 (見た目の画像と VRM) は自分の持ち物で、どの Building に行っても付いていく。ルームビューを表示しても、ペルソナの発話・記憶・ペルソナに送る文章は変わらない。
- **Godot を使う利用者**: VRM の指定が本体の一か所になる。ブラウザ用と Godot 用に二度設定しない。
- **保守**: 「どのアイテムがペルソナに見えているか」を決める処理が一つになる。3D を描く仕組みは、ブラウザ用 (three-vrm) と空間用 (Godot) の二つで、役割が重ならない。

## 今の作り (2026-11-22 にコードで確認。段階 1 の実装より前の状態)

- 右サイドバー (`frontend/src/components/RightSidebar.tsx`) には、上から Building の名前と説明、内装画像 (`image_path`)、部屋にいるユーザー、部屋にいるペルソナ、アイテム、設置物 (Fixture) が並んでいる。画面の幅が 768px 以下のとき、右サイドバーは画面の端から引き出す形になる。
- アイテムの一覧は、`GET /api/info/details` (`api/routes/info.py`) が返す全件を、ID の順にそのまま並べている。ペルソナ向けにどのアイテムを見せるかを選ぶ関数 `_select_displayed_items` (`builtin_data/tools/get_visual_context.py`) は、この API では使われていない。入れ物 (Bag) について、API は中身の全件を返しているが、画面は中身の個数だけを出している。
- ペルソナの画像は二つある。小さなアイコン (`AI.AVATAR_IMAGE`、256px) と、ペルソナ本人に自分の見た目として渡している画像 (`AI.APPEARANCE_IMAGE_PATH`)。
- VRM の指定は、Godot のアドオンのペルソナ別設定 `avatar_vrm_path` にだけある。値は Godot を動かす PC の上のパスで、本体は VRM のファイルを持たず、VRM を返す API も無い。
- 画面には 3D を描くライブラリが入っていない。
- 声を鳴らす場所は二つある。自動で鳴る声は `frontend/src/lib/clientActions/playAudio.ts` の一つの audio 要素で鳴る。吹き出しの「音声を再生」ボタンは、`frontend/src/components/AddonBubbleButtons.tsx` の中で別に作られる Audio を使って鳴る。
- 自律で動いているペルソナが「いま何をしているか」を画面へ通知する仕組みは無い。返事を待つ間の表示は、ユーザーが送ったメッセージへの返事の間だけ、送った本人の画面に出る。部屋にいるペルソナの「いま何をしているか」の欄は 2026-08-22 に取り除いてあり、作り直しは「暮らしの窓」として、自律行動を実際に動かす部分 (autonomous_behavior_v3.md が「運転」と呼んでいる、これから作る部分) と一緒に予定されている (同 §9-9、§11)。
- 発話に身振りを付ける書き方 `{"body_emote": "smile"}` (9 種類) は、Godot のアドオンの中に実装されている。ペルソナへの案内は、Godot の Building にいる間だけ出る。ブラウザでは、この書き方が小さな灰色の `(smile)` として表示されるだけで、何も動かない。embodied_expression.md に書かれている `/emote` の形は下書きのままで、本体に実装は無い。

## 設計

この節のうち、「決まったこと」に発言の記録があるもの以外は、メティスがその決定を具体にした案になる。まはーの確認が要ると考えたものは七つの問いとして出し、呼び名以外の六つは 2026-11-22 に了承された (「まはーが決めること」)。

### 1. ルームビューの置き場所 (画面の幅ごと)

ルームビューの置き場所は、画面の幅で三通りに分かれる (2026-10-05 にまはーが 4K と 1080p、全画面と半分のスクリーンショットを比べて決めた)。

- **チャットの左右に余白がある幅** (4K の全画面): ルームビューを、チャットの横の独立した縦のUI区画として置く。
- **余白は無いが右サイドバーを出せる幅** (4K の半分、1080p の全画面): 右サイドバーの内装画像の枠 (Building の名前と説明のすぐ下) を、ルームビューに育てる。何もどけずに済む。
- **右サイドバーを出せない幅** (1080p の半分、スマホ): ログとルームビューを切り替える。ペルソナが喋っている間だけ自動でルームビューに切り替え、終わればログに戻す。

狭い幅での自動切り替えについて、まはーが確定した三点 (2026-10-05):

1. ルームビューからログへ戻るのは、読み上げの音声があれば音声が終わったとき、無ければ文字が流れ終わって一呼吸置いたとき。
2. 利用者がメッセージを入力している最中と、過去のログを遡って読んでいる最中は切り替えない。「喋っています」の小さな印だけを出し、印を押せば手動でルームビューに切り替えられる。
3. ログとルームビューを両方出せる広い画面では、切り替え自体をしない。

三つの幅の境目の具体的な数値は、実装のときに実際の画面で決める。今のコードにある境目は 768px の一つだけ。

### 2. ルームビューの中身は三通り

ルームビューは「3D を映す枠」ではなく、「その Building とペルソナが持っている一番豊かな見た目を映す枠」として作る。Building がこれから自動で増えていく構想では、増えた Building に 3D のシーンは付いてこない。内装画像は画像生成ですぐ作れるので、内装画像が全部の Building に共通の見た目になる。

- **内装画像と立ち絵** (全員に出る): 内装画像を背景に、ペルソナの 2D の画像を立ち絵として出す。立ち絵は新しい種類の画像ではない。使うのは、ペルソナ本人に見た目として渡している既にある画像 (`APPEARANCE_IMAGE_PATH`) で、無ければアイコンを使う。既にある画像と同じものを使うので、ルームビューのために別の見た目の設定を増やさない。
- **ブラウザが描く 3D アバター**: VRM を持っていて、3D の表示を入にしてあるペルソナは、立ち絵の代わりに 3D アバターが内装画像の前に立つ。空間は持たない (位置も歩行も無い)。
- **Godot の 3D 空間**: この文書の外 (virtual_embodiment_godot.md)。Godot が描いた映像をルームビューの枠へ流す案は、流し続ける負荷を測っていないので、やるとしても後にする。日常の会話は上の二つで足りる。

中身の選び方は次のとおり。

- 3D を出すかどうかは、ペルソナごとの設定で選ぶ。VRM を入れていないペルソナには、その設定自体を出さない。
- VRM の読み込みに失敗したら立ち絵に戻し、失敗した理由を画面に出す。黙って立ち絵に替えない。
- 同じ部屋にペルソナが複数いるとき、ルームビューに出るのは一人にする。喋っているペルソナが出て、誰も喋っていなければ最後に喋ったペルソナが残る。部屋にいるペルソナの一覧から選んで切り替えられる (メティスの案。2026-11-22 にまはーが了承)。

ルームビューの中身は、将来ほかの種類を足せる形にしておく。候補は、絵一枚から作る 2D の動くアバター (アイディア帳の「Mesh Avatar Studio」) と、Live2D (ライセンスの審査が要るので一番後回し — 2026-10-05 のまはーの決定)。

### 3. ブラウザの 3D アバター

- 描画には three.js と `@pixiv/three-vrm` (どちらも MIT ライセンス) を使い、アドオンではなく本体のフロントエンドに入れる。これまでアドオンに分けてきた理由は、大きな追加のソフト (GPU 用のものや Python のパッケージ) が要ること、ライセンスの都合、特定のハードが要ることだった。three-vrm はブラウザの中だけで動き、サーバー側に何も足さないので、どれも当てはまらない。
- 3D のライブラリは、VRM を持つペルソナのルームビューを開いたときにだけ読み込む。3D アバターを入れていない利用者の画面は重くならない。
- three-vrm を使って描くのは、VRM の標準の描き方 (MToon)、表情、まばたき、視線、髪や服の揺れ。
- **口パク**: 鳴っている声の音量を取り、口の開きに写す。声を鳴らす場所は二つあるので (「今の作り」)、どちらの声でも口が動くようにする。声の無い発話では、文字が流れている間だけ口を動かす (Godot 側の「字幕だけなら時間で開閉する」と同じ扱い)。
- **動き**: 最初は立ち姿 (呼吸・まばたき・視線) だけにする。全身の動き (キーボードを打つ姿など) は設計 6 で足す。
- 採らなかったもの:
  - Godot をそのままブラウザで動かす道 (Godot の Web 書き出し)。ブラウザでは Compatibility という軽い描画方式しか使えない (Godot 4.7 の公式ドキュメント「Exporting for the Web」)。Godot の VRM アドオンで髪や服を揺らす拡張 (`vrm_physics.gdextension`) には、ブラウザで動く版が入っていない。VRM が一体 25〜150MB ある。
  - [three-liltoon](https://github.com/mochiya-labs/three-liltoon)。lilToon (VRChat 向けのアバターでよく使われる、MToon とは別の描き方) を Three.js 用に翻訳したもので、Unity から専用のツールで書き出し直した VRM にだけ効く。手元のアバターは全員 MToon なので、需要が小さい (2026-11-22 まはー)。
  - [aituber-kit](https://github.com/tegnike/aituber-kit) のコード。v2.0.0 以降カスタムライセンスなので流用しない。

### 4. VRM の持ち主と置き場所

- VRM はペルソナの持ち物にする。本体のペルソナ設定 (見た目の画像を変えるのと同じ画面) で指定し、ファイルは本体のユーザーデータの下に置く。
- 本体が VRM をブラウザへ返す。返す相手は、その SAIVerse の画面を開ける人に限る (今の画像と同じ範囲)。再配布を禁じている VRM があるので、リポジトリには入れず、外から誰でも取れる場所にも置かない。
- Godot のアドオンは、VRM を本体から取得する。Godot が SAIVerse と同じ PC で動いていても別の PC で動いていても、同じ方法で取得する。
- アドオンの `avatar_vrm_path` はなくす。VRM の設定が二か所にある期間を作らない。既に `avatar_vrm_path` を設定してある利用者のために、アドオンを更新するとき、本体から読める場所にあるファイルは本体へ一度だけ写す。写せなかったペルソナ (Godot のプロジェクトの中のパスや、別の PC のパス) は、どのペルソナの VRM を入れ直す必要があるかを画面に出す (メティスの案。2026-11-22 にまはーが了承)。
- Godot だけが使うもの (表情のプロファイル、動きの好み、Godot と SAIVerse を繋ぐときの認証の情報) は、アドオンに残す。

**vessel.md (2026-07-21 の下書き) との食い違い**: vessel.md には、アバターの実物のデータはアドオンの側で管理し、本体の側では保存場所だけを記録する、と書かれている (アバターの見た目のデータの一覧を扱う「Avatar Asset レジストリ」の節と、同文書が必ず守ることとして挙げている「不変条件」4)。また同文書では、画面のアバターを Vessel の一種として位置づけている。種類の名前は `ambient` で、どの Building にも結び付かず、ペルソナがどこにいても使える身体、という意味になる。そのうえで、身体を動かすスペル (`body_gesture` など。今は Godot のアドオンにある) を受ける側に置いている。2026-11-22 の決定は、この二点と逆向きになる。VRM の実物を本体の側で持ち、ブラウザのアバターは姿を映すだけで、身体を動かすスペルを受けない。逆向きにした理由は三つある。ブラウザが VRM を描くには、本体が VRM を返せなければならない。アドオンのフォルダにある利用者のファイルはアンインストールで消えるので、ユーザーデータ側へ移したい、という方針が 2026-09-29 にまはーから出ている (アイディア帳「Godot Vessel のユーザー由来ファイルをユーザーデータ側へ引っ越す」)。vessel.md は下書きで、該当の部分は実装されていない。2026-11-22 にまはーが了承したので、この文書の決定を正とし、vessel.md を詰めるときにそちらを直す。

### 5. 置かれたアイテムの並びと、埋もれたアイテムの山

- ルームビューの脇に、Building に直接置かれているアイテムを並べる。絵は縮小した絵そのもの、それ以外は種類の印と名前を出す。押すと、今と同じアイテムの画面が開く。今の右サイドバーのアイテム一覧の描き方を変えるだけで、アイテムの新しい置き場は作らない。設置物 (Fixture) は対象外で、今と同じ別の欄に出す。
- 並べるのは、ペルソナに見える範囲だけにする。範囲は room_item_display_cap.md の決まりそのもの (建物に直接置かれたアイテムのうち、最近触られた順の上位。初期値は 10 個で、Building の設定で変えられる)。
- 残りは山一つにまとめ、「ほかに N 個のアイテムが埋もれています」と添える。押すと残りが見える。ペルソナが読んでいる一行 (「ほかに N 個のアイテムがありますが、埋もれていて見えません。スペル『埋もれたアイテムを見る』でめくって見られます」) と同じ「埋もれて」という語を使うが、一字一句同じにはしない (スペルの案内はユーザーには要らない)。箱の絵にしないのは、片付け用の入れ物 (Bag) と見分けにくくなるため。Bag は誰かがしまったアイテムで、埋もれたアイテムは散らかって見えなくなっているだけ。
- **どれが埋もれているかを、画面の側では数え直さない。** `/api/info/details` が、ペルソナ向けの部屋の様子と同じ関数 `_select_displayed_items` を通した結果 (見えるアイテムと、埋もれたアイテム) を返し、画面の側は受け取った結果をそのまま描く。選ぶ処理が二か所にあると、いつか食い違って、今と同じ見え方の食い違いがまた生まれる。スペル「埋もれたアイテムを見る」(`buried_items_view.py`) は、入れ物の中身まで含めた全部のアイテムを一本の順に並べてページに分ける、別の役割の処理なので、この関数にはまとめない (「最近触られた」の時刻を決める処理には、今も両方で同じ関数 `_touched_epoch` を使っている)。
- 画面での並び順は、最近触られた順 (先頭が一番新しい) にする。ペルソナに渡す部屋の様子の中の並び順は変えない (room_item_display_cap.md の「不変条件」6)。
- この文書で「触る」と書くのは、room_item_display_cap.md の決まりで順位が上がる操作のこと。アイテムの中身や説明の書き換え、開け閉め、置き場所の移動がそれに当たる。読むだけでは順位は上がらない。
- **食い違いうる所**: ペルソナが実際に読んでいる部屋の様子は、部屋に入ったときの全文と、その後に変わった部分の積み重ねでできている。画面に出るのは「いま選び直した結果」なので、ユーザーがアイテムを触った直後などに、一時的に食い違うことがある。画面が示しているのは、「次に部屋の様子が組まれたときにペルソナに見える範囲」になる。
- 開いた入れ物 (Bag) の中身にも同じ決まり (上位 10 件) がある。画面で中身を見せる形にするときは、同じ山の描き方を使う。最初の段階では、今と同じ個数だけの表示のままでよい。
- room_item_display_cap.md の「不変条件」1 にある「ユーザー画面の一覧は無傷」は、「山にまとまるが、押せば全部に届く」へ、実装と同じ変更で書き直す。

### 6. 喋っている間と、作業している間

ルームビューのアバターは、ペルソナが何をしているかで姿を変える。姿は数個に限る。

- **喋っている間**: 口パクをする。狭い画面では、設計 1 のとおりルームビューへ自動で切り替える。
- **返事を書いている間、スペルを実行している間** (ユーザーとの会話の中): 作業の姿になる。会話の中では、返事を待つ間の表示に使っている画面への通知 (chat_progress_display.md) が既にあるので、それを使う。
- **自律で作業している間**: 作業の姿になり、触っているアイテムが並びの先頭に出てきて、印が付く。

自律で作業している間の表示には、「いま何のスペルを実行していて、どのアイテムを触っているか」を画面へ通知する仕組みが要る。この仕組みは今は無い。もとになる自律行動を実際に動かす部分そのものが、これから作られる (autonomous_behavior_v3.md §11)。だから、この表示は自律行動を動かす部分と一緒に作る。

autonomous_behavior_v3.md §9-9 で「暮らしの窓」に出すと決めてある一行の中身は、ペルソナがいま取り組んでいる一件の名前と、自律行動の入・切だけで、実行中のスペルと触っているアイテムは含まれていない。ルームビューにはこの二つが要るので、自律行動を動かす部分の設計のときに、取り出す場所を一つ決め、暮らしの窓とルームビューが同じ所から受け取る形にする。同じ事実を取り出す場所を、画面ごとに別々に作らない。

**原則: ルームビューに出す「いま何をしているか」は、事実だけから決める。** 使うのは、実行中のスペルと、触っているアイテム。ペルソナの気持ちや意図を、機械が推測して姿に出さない。autonomous_behavior_v3.md §9-9 の「スペルの表示は解釈ではなく事実の翻訳」と同じ線引きになる。

- 作業の姿は、立ち姿・キーボードを打つ姿・絵を描く姿のような、決まった数個にする。どのスペルがどの姿になるかの対応表は、本体のフロントエンドに置く。対応の無いスペルは、汎用の「作業している」姿になる。
- 触っているアイテムが並びの先頭に出てくるのは、新しい仕組みではない。「最近触られた順」は、アイテムの中身が書き換えられると順位が上がる決まりなので、山に埋もれていたアイテムをペルソナが書き足すと、そのアイテムは山から出て先頭に並ぶ。読んでいるだけのアイテムは順位が上がらないので、先頭には出てこない。まはーが 3D について言った「使うときにアバターをそこへ向かわせる」は、Godot の中では歩いて向かう形になり、ブラウザのルームビューではアイテムのほうが前に出てくる形になる。
- 狭い画面では、自律の作業中に自動でルームビューへ切り替えない。「作業しています」の小さな印だけを出し、押せばルームビューが見える (メティスの案。2026-11-22 にまはーが了承)。ユーザーに話しかけているわけではないので、ログを読む手を止めさせない。2026-10-05 の決定は「喋っている瞬間以外のペルソナは事実上眠っている」を前提にしていたので、ここはその前提が変わる所になる。

### 7. 発話中の身振り (後の段階)

- 書き方は、既に動いている `{"body_emote": "smile"}` (9 種類) を使い、新しい書き方を作らない。9 種類はどれも全身の動きとして表す、というのが既存の決まりなので (virtual_embodiment_godot.md「発話位置に同期する全身エモートと口パク」— 表情だけの動作にはしない)、ブラウザのアバターでも全身の動きとして表す。だから、ブラウザで全身の動きを再生できること (設計 6) が前提になる。
- 今は、この書き方の案内が Godot の Building にいるペルソナにしか出ていない。ブラウザのアバターのために案内の範囲を広げると、ペルソナが読む文章が変わる。これは見た目の話ではなくペルソナへの働きかけなので、広げるかどうかは、段階 4 に入るときに決める (この先送りを 2026-11-22 にまはーが了承)。
- v0.3 までの下書きには、embodied_expression.md の `/emote` の形を使うと書かれていた。実際に作られたのは `body_emote` の形なので、この文書は動いているほうに合わせる。embodied_expression.md の側の整理は、この文書の範囲の外に置く。

### 8. Godot と同時に動いているとき

- ブラウザのアバターは姿を映すだけで、位置の情報を持たない。ペルソナがどの Building にいるかは Building の在室の記録にあり、空間の中の位置は Godot の中にある。だから、Godot の中のアバターとブラウザのアバターが、二つの身体として食い違うことは無い。
- Godot の Building にペルソナがいて Godot が繋がっている間、声は Godot の中のアバターからだけ鳴る (virtual_embodiment_godot.md の既存の決まり)。この間、ブラウザには口パクに使う声が無いので、口は文字に合わせて動く。

## 必ず守ること

1. **何も入れていない利用者にもルームビューが出る。** 内装画像と立ち絵が土台で、3D はその上に載る追加。
2. **ペルソナに見えるアイテムの範囲を決める処理は一つ。** 画面の側では数え直さず、受け取った結果をそのまま描く。
3. **アイテムは消えない。** 山にまとまったアイテムにも、押せば届く。
4. **ルームビューを表示しても、ペルソナの発話・記憶・ペルソナに送る文章は変わらない。** 設計 7 の案内の範囲を広げるかどうかは、別の決定として扱う。
5. **「いま何をしているか」は事実だけから出す。** 実行中のスペルと触っているアイテムから決め、気持ちや意図を推測して姿にしない。
6. **VRM の設定は本体の一か所。**
7. **ブラウザのアバターは空間を持たない。** 位置・歩行・アイテムとの距離を持たせたくなったら、それは Godot の役目。
8. **狭い画面で、ログを読んでいる・入力している利用者の画面を勝手に切り替えない。**
9. **3D のライブラリは、VRM を持つペルソナのルームビューを開くまで読み込まない。**

1. **枠と、置かれたアイテム**: ルームビューの枠 (三つの幅)、内装画像と立ち絵、狭い画面の自動切り替え、アイテムの並びと山 (設計 1、設計 2 の「内装画像と立ち絵」、設計 5)。3D を入れていない利用者にも届く部分を先に作る。

4. **発話中の身振り**: 設計 7。

## 段階 1 で作ったもの (2026-11-22)

段階 1 は実装が済み、メティスが本番と分けたテスト環境で確かめた。まはーの実機での確認はこれから。この節は、設計に書いていなかった具体の数値と、実装のときにメティスが決めたことを記録する。上の「今の作り」は、この実装より前の状態の記録として残してある。

- **「UI区画」という言葉 (2026-11-22 まはー)**: 幅の広い画面で、チャットの横にルームビューを置く場所を、この文書とコードの説明書きでは「UI区画」と呼ぶ。起草のときは「区画」と書いていて、言葉づかいの検査が「エリア」を勧めた。まはーの決定は「「UI区画」にして。どちらもそれ単体で言われても何の話か分からない一般語だから。」。「経緯」の 2026-10-05 の記録に出てくる「区画」は、当時の文のまま残してある。
- **幅の境目**: 2000px 以上で独立したUI区画、それ未満は右サイドバーの中。4K の全画面は、OS の拡大率が 100% でも 150% でも 2000px を超える。4K の半分と 1080p の全画面は超えない。数値は `frontend/src/lib/roomViewPlacement.ts` に置いてある。
- **ログとルームビューを切り替える形になる条件**: 幅が 1100px 未満で、右サイドバーがチャットの横に出ていないとき。右サイドバーを横に出している間は、ルームビューが右サイドバーの中に見えているので、切り替えない (設計 1 の三点目)。幅 1100px 以上で右サイドバーを閉じている画面も、切り替えない。
- **UI区画を置く位置 (2026-11-22 まはー、実機を見て)**: UI区画はチャットのすぐ右にくっつけ、チャットとUI区画を合わせて、左右のサイドバーの間の中央に揃える。最初の実装は、チャットだけを中央に置いて、UI区画を右サイドバーの側に寄せていた。まはーの指摘は「喋ってる最中って当たり前だけどチャットUI見てるはずなんだよ。だから広い時のルームビューはチャットUIの方にくっつけるべきだと思う。二つ合わさって中央に揃う感じかな。」。
- **UI区画の中のルームビューの形**: 幅 3・高さ 4 の比にして、UI区画の上下の中央に置く。UI区画いっぱいに縦へ広げると、横長の内装画像 (保存のときに長辺 768px へ縮めてある) が大きく引き伸ばされ、部屋の一部しか映らないため。
- **立ち絵**: 使うのはペルソナ設定の「外見画像」(この文書の前半で「見た目の画像」と書いているもの。無ければアイコン) で、背景の透けていない絵なので、角を丸めたカードとして内装画像の手前に置き、下にペルソナの名前を表示する。
- **喋っている間の決め方**: 返事の文字が流れている間 (考えている途中の表示だけの間は数えない) と、読み上げの音声が鳴っている間。音声は、いま見ているログの発言のものだけを数える。吹き出しの「音声を再生」ボタンで利用者が自分で鳴らした音声は数えない。
- **ログへ戻るまでの待ち**: その発話の間に音声が鳴っていたら 0.4 秒、文字だけなら 1.5 秒。
- **過去のログを遡って読んでいる最中の決め方**: 利用者自身の操作 (ホイール、指でのスクロール、スクロールバーのドラッグ、スクロールのキー) で、一番下から 200px より上へ動かしている間。メッセージが届いたときに画面が自動で下へ動く分は数えない。最初の実装では、自動で動く分まで利用者の操作として扱っていて、利用者が何もしていないのに切り替わらなかった。テスト環境で見つけて直した。
- **字幕 (設計に無かったもの。メティスが足した)**: ログに重ねてルームビューを出している間、いま喋っている発言の本文を、ルームビューの下側に出す。読み上げの音声を使っていない利用者は、ログが隠れると返事を読めなくなるため。本文は切り詰めず、字幕の欄の中でスクロールする。
- **アイテムの個数の設定をどこから読むか**: 部屋の様子に出す個数 (`item_display_limit`) を読む処理を `_read_item_display_limit` (`builtin_data/tools/get_visual_context.py`) の一つにまとめ、ペルソナ向けの部屋の様子を作る処理でも画面向けの API でも、設定画面で保存したときに書き込まれるデータ (`manager.building_map`) から読むようにした。それまでペルソナ向けの処理では、ペルソナが起動時に受け取った Building のコピー (`persona.buildings`) から読んでいたので、Building やペルソナを作った後に変えた個数が反映されなかった。同じコピーの古さは Building の名前とシステムプロンプトにもあり、こちらは直していない ([issue](../issues/entity_creation_has_no_transactional_boundary.md))。
- **確かめたこと**: テスト用に作ったペルソナへ発言を送り、テスト用の LLM が受け取った文面に載っていたアイテム 10 個と、画面に並んだ 10 個が一致した。埋もれたアイテムの「AI コンテキストに含める」を切り替えると、そのアイテムが並びの先頭に出て、一番古い一つが埋もれた側に入った。幅 375px・960px・1280px・2560px で置き場所を見た。960px で、喋り始めると自動で切り替わること、喋り終わるとログに戻ること、入力中は切り替わらず「喋っています」の表示が出ること、その表示を押すと切り替わることを見た。
- **確かめていないこと**: 読み上げの音声を使ったときの切り替え (テスト環境には音声のアドオンが無い)。文字が流れ終わってから音声が始まるまでが 1.5 秒より長いと、いったんログに戻ってからもう一度切り替わる。スマホの実機での、指を離した後も流れ続けるスクロールの扱い。Chrome 以外のブラウザ。これらは、まはーの実機確認で見る。
- **入れ物 (Bag) の中身**: 最初の段階の予定どおり、個数だけの表示のまま。

## 段階 2 で作ったもの (2026-11-22、作っている途中)

段階 2 は四つに分けて進める。(1) VRM を本体のペルソナ設定に置き、ブラウザで描く。喋っている間の口は、時間で開け閉めする。(2) 口の開きを、鳴っている声の音量に合わせる。(3) Godot のアドオンが本体から VRM を取得できるようにし、アドオンの設定 `avatar_vrm_path` をなくす。(4) (1)〜(3) が揃ってからリリースに入れる。VRM の設定が本体とアドオンの二か所にあるリリースを作らないため (必ず守ること 6)。(2) を (1) と分けたのは、音量を取るために声を鳴らす処理に手を入れるので、失敗すると声そのものが鳴らなくなりうるため。まはーの実機で、声が鳴ることを確かめながら進める。

この節は、いま済んでいる (1) について、設計に書いていなかった細かい決まりと、実装のときにメティスが決めたことを記録する。

**VRM の置き場所と受け渡し (バックエンド)**

- **置き場所**: `<SAIVERSE_HOME>/personas/<ペルソナの ID>/avatar/` に、ペルソナ一人につき一つだけ置く。ペルソナの記憶 (`memory.db`) と同じフォルダの下なので、ペルソナの持ち物として一緒に動く。DB の `AI.AVATAR_VRM_PATH` には、`SAIVERSE_HOME` からの相対パスを入れる。データのフォルダごと別の PC へ移しても読めるようにするため。置き場所の決まりは `saiverse/persona_avatar_vrm.py` に集めてある。
- **受け取り**: `POST /api/people/{persona_id}/avatar-vrm`。受け取るのは、名前が `.vrm` で終わり、ファイルの先頭に、glTF という形式のファイルであることを示す 4 文字 (`glTF`) が入っていて、300MB までのファイル (VRM は glTF 形式のファイルの一種)。手元の VRM は一体 25〜150MB なので、その倍を上限にした。ファイルを受け取るときは、まず別の名前のファイルへ書き込み、上の条件を確かめ終わってから、本来の名前へ付け替える。途中で失敗しても、前の VRM は残る。入れ替えたときは、前のファイルを消す。
- **返す**: `GET /api/people/{persona_id}/avatar-vrm`。届く範囲は、ペルソナのアイコンや外見画像と同じ (その SAIVerse の画面を開ける人)。DB の値がそのペルソナの `avatar/` フォルダの外を指しているときは、返さない。
- **3D を出すかどうかの切り替え**: `AI.AVATAR_3D_ENABLED`。値が無いときは「出す」として扱う。VRM を入れたらそのまま 3D で出るのが、利用者の期待に合うため。VRM を入れたまま、ルームビューを立ち絵 (外見画像のカード) に戻したい利用者のために、切り替えを残した。
- **部屋の詳細 (`GET /api/info/details`)**: 在室のペルソナごとに `avatar_vrm_url` を返す。返すのは、VRM があり、3D を出す設定で、ファイルが実際にあるときだけ。画面の側では、この値があるかどうかだけで、3D を出すか立ち絵を出すかを切り替える。
- **ペルソナを消すとき**: `avatar/` フォルダの中のファイルを消す。
- **ペルソナまるごとパック**: 書き出しに `avatar/` フォルダと `AVATAR_VRM_PATH` を入れない (「まはーが決めること」の六つ目の、初期設定の側)。利用者が選んだときに入れる部分は、まだ作っていない。

**ブラウザで描く部分 (フロントエンド)**

- **ライブラリ**: 3D を描くための three 0.187.0 と、VRM を読むための `@pixiv/three-vrm` 3.5.5。フロントエンドが使うライブラリを書き並べたファイル (`frontend/package.json`) には、「このバージョン以上」のような範囲ではなく、このバージョンそのものを書く。three は小さなバージョンの更新でも動きが変わることがあるので、更新は確かめてから行う。
- **読み込むのは必要になってから**: three を読み込む処理は `frontend/src/lib/vrmAvatarEngine.ts` だけにまとめてあり、このファイルは、VRM を持つペルソナのルームビューが画面に見えたときに初めて読み込まれる (必ず守ること 9)。
- **VRM は画面に一体だけ**: 幅によっては、ルームビューが画面に二つある (右サイドバーの中と、ログに重ねる側)。VRM は一体 25〜150MB あるので、読み込んだ VRM と、3D を描く領域 (canvas) は一組だけにして、見えているほうのルームビューへ canvas を移す。ルームビューが見えなくなっても 3 分は VRM を持ったままにする。狭い画面では喋るたびにルームビューが出たり消えたりするので、そのたびに読み直さないため。
- **読み込めなかったとき**: 立ち絵のカードに戻し、理由を小さく添える (ブラウザが 3D を描く機能 (WebGL) を使えない、ファイルが見つからない、壊れている、VRM の情報が無い、など)。同じファイルは、ページを開き直すまで読み直さない。喋るたびに 100MB を読み直して、同じ失敗を繰り返さないため。
- **VRM を送っている途中でペルソナ設定を閉じたとき**: 送るのは止めず、最後まで送る。入った VRM は、閉じた後でもルームビューに出る。閉じた後に送るのが失敗したときは、画面に知らせが出ない (前の VRM がそのまま残り、ペルソナ設定を開き直すと今の状態が見える)。同じ PC や家の中の通信では、送るのは数秒で終わるので、知らせを出す仕組みは足していない。
- **立ち姿**: VRM は読み込んだままだと両腕を横に伸ばした姿 (T ポーズ) なので、両腕を下ろす。呼吸の小さな揺れと、不規則な間隔のまばたきを付け、視線はカメラへ向ける。
- **口**: 喋っている間 (段階 1 の「喋っている間の決め方」と同じ) だけ、時間で開け閉めする。声の音量に合わせるのは (2)。
- **構図**: 右サイドバーの中と、ログに重ねる置き方では、腰から上を映す。UI区画では全身を映す。3D を描く範囲はルームビューの枠の全体で、内装画像がアバターの後ろに見える。ペルソナの名前の表示と字幕は、アバターの上に重ねて出す。
- **服や髪が、体とは別の骨格に付いている VRM** (2026-11-22、まはーが実機ではなくテスト環境の絵を見て気づいた): VRM の中には、体の骨格 (骨をひとまとめにしたもの。armature) とは別に、服や髪飾り用の armature が入っているものがある。別の armature の中には、体と同じ名前の骨 (`Hips`、`Chest`、`upper_armL` など) がもう一揃い入っていて、服の形のデータ (メッシュ) はそちらの骨に付いている。体の腕だけを下ろすと、腕は下りるのに袖が横に伸びたまま残る。最初の実装はこの形で、メティスは「腕の骨は回っているのに絵は T ポーズ」と読み違えて、描画の側を調べていた。まはーの指摘は「そのTポーズとってるのは服！よく見ると腕は降りてて、袖だけ上がってる。服の方の骨だけ動いてないんじゃない？」。Godot のアドオンには、同じ問題への手当てが既に入っていた (`sai-vr/scripts/avatar_skeleton_followers.gd`)。ブラウザの側も同じやり方にした: 体の骨と同じ名前で、動かす前の位置が 10cm 以内にある骨を、別の armature の中から探してペアにし、体の骨の姿勢を、動かす前の互いの位置関係を保ったまま、画面を描き直す一コマごと (毎フレーム) に、ペアの相手の骨へ写す。体と関係の無い小物を取り違えないよう、腰の骨がペアになっていて、ペアが三つ以上ある armature だけを対象にする。条件は Godot の側と揃えてある。同じ VRM が、Godot とブラウザで違う姿にならないようにするため。骨の名前は、末尾の `_数字` を落としてから比べる。メティスは最初、「VRM の中では体と服の骨が同じ名前で、ブラウザのライブラリが読み込むときに `_2` を付ける」と思い込んで、ファイルの中の名前どうしを比べる形で実装を頼んだ。実物の VRM を調べると、ファイルの中の名前がもう `Hips` と `Hips_2` になっていて、ペアが一つもできなかった。Godot のアドオンの処理では、最初から `_数字` を落として比べるようになっていた。

**確かめたこと (メティスが、本番と分けたテスト環境で、テスト用に作ったペルソナに VRM を入れて画面を開いた)**

- VRM 三体で見た。服が体と同じ armature に付いているもの (`air.vrm`、59MB)、服と髪飾りが別の armature 二つに付いているもの (`erys_skimmia_VRM1_0.2.3_50MB.vrm`、30MB。骨のペアは 30 個)、一番大きいもの (`quon_misaki_VRM1.vrm`、150MB。骨のペアは 29 個)。三体とも、腕と袖が一緒に下りた姿で出た。150MB の VRM は、ページを開いてから 3D が出るまで 17 秒ほどかかった。
- 三つの置き場所で見た。右サイドバーの中 (幅 1280px) は腰から上が枠いっぱいに出て、体は枠のいちばん下で切れる。ログに重ねる置き方 (幅 960px で右サイドバーを閉じた状態) は、喋り始めると切り替わり、字幕がアバターの下の部分に重なって出る。UI区画 (幅 2560px) は全身が出て、足がペルソナの名前の表示より上に来る。どの幅でも、canvas は画面に一つだけだった。
- 喋っている間、口が開け閉めされた。
- 壊れたファイル (先頭の 4 文字 `glTF` だけ正しく、その後ろがでたらめなもの) を入れると、立ち絵のカードに戻り、「VRM のファイルが壊れているか、読めない形式です。」と出た。先頭の 4 文字が違うファイルは、受け取りの時点で受け付けられなかった。
- 「ルームビューに 3D アバターを出す」のチェックを外して保存すると立ち絵に戻ること、VRM を入れ替えると前のファイルが消えること。

**確かめていないこと**

- **VRM 0.x の VRM。** 手元の VRM は全部 VRM 1.0 だった。VRM 0.x では、腕を下ろす向きが逆になる (VRM 0.x 用の処理は書いてあるが、実物では動かしていない)。VRM 0.x のファイルが手に入ったときに見る。
- **動きの滑らかさ。** メティスが使った確認用のブラウザは、描画が一秒に一枚ほどに抑えられていた。口の開け閉め・まばたき・揺れが自然に見えるかは、まはーの実機で見る。
- **スマホでの重さ** (「まだ確かめていないこと」の二つ目)。
- **服の armature の目の骨。** 目の骨まで別の armature に持っている VRM (`quon_misaki_VRM1.vrm` がそう) では、視線の動きだけ、服の側の目の骨に一コマ遅れて写る。見た目で分かる差は確認用のブラウザでは見えなかった。

## まだ確かめていないこと (確かめ方)

- **全身の動きをブラウザで再生できるか。** three-vrm 自体には動きの再生が入っていない。候補は `@pixiv/three-vrm-animation` (VRM 用の動きのファイル `.vrma` を再生するライブラリ、MIT ライセンス)。Godot 用の動きは ARDY (文章から身体の動きを作るモデル) で作ってあるので、そのデータをブラウザでも使えるかを、段階 3 の最初に、本番と分けたテスト環境で一体の VRM を使って試す。
- **スマホでの重さ。** VRM は一体 25〜150MB ある。段階 2 の確認で、スマホの実機で読み込みの時間と動きの滑らかさを測る。重すぎたときの手当ては、その結果を見てから決める。
- **Godot が、本体から取得した VRM を、動かしている最中に読めるか。** Godot のエディタから動かす形では、今も動かしている最中にファイルのパスから VRM を読んでいる。配布用に書き出した Godot で外部の VRM を読めるかは、virtual_embodiment_godot.md の「最初に潰す技術リスク」に「実行時VRMロード」として挙がったままで、まだ確かめられていない。段階 2 の最初に確かめる。
- **本体とアドオンの更新が同時でない場合。** アドオンは別のリポジトリなので、新しいアドオンと古い本体の組み合わせが起こりうる。アドオンのカタログの登録情報には、必要な本体のバージョンを書く欄 `min_saiverse_version` があり、導入と更新のときに検査されている (`saiverse/addon_registry.py`、`saiverse/addon_installer.py`)。新しいアドオンのこの欄に必要な本体のバージョンを書いておけば、導入と更新のときの検査で足りるかを、段階 2 の設計で確かめる。
- **自律行動を動かす部分から、実行中のスペルと触っているアイテムを取り出せるか。** 段階 3 の自律の部分は、その部分の設計と一緒に詰める。
