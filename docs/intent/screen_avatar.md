## 一言で

チャット画面に枠を一つ作り、いまいる Building の内装と、そこにいるペルソナの姿を映す。この枠をこの文書では仮に「舞台」と呼ぶ (呼び名はまだ合意していない —「まはーが決めること」1)。舞台の脇には、その部屋に置かれているアイテムが並ぶ。ペルソナが 3D のアバター (VRM) を持っていれば、ブラウザがそれを描く。空間の中を歩くことと VR は Godot の役目で、この文書は扱わない。

## 全体像 — 誰に何を約束するか

- **ユーザー**: チャットをしながら、ペルソナが部屋に「居る」ことが目で分かる。何も追加で入れていなくても、内装画像と立ち絵で舞台が出る。VRM を入れたペルソナは 3D で出る。そのために Godot を入れる必要は無い。
- **ユーザー (アイテムについて)**: 自分の画面に並ぶアイテムと、ペルソナに見えているアイテムが、同じ範囲になる。今は、ペルソナには最近触られた上位だけが見え、ユーザーの画面には全部が並んでいる。
- **ペルソナ**: 姿 (見た目の画像と VRM) は自分の持ち物で、どの Building に行っても付いていく。舞台を表示しても、ペルソナの発話・記憶・ペルソナに送る文章は変わらない。
- **Godot を使う利用者**: VRM の指定が本体の一か所になる。ブラウザ用と Godot 用に二度設定しない。
- **保守**: 「どのアイテムがペルソナに見えているか」を決める処理が一つになる。3D を描く仕組みは、ブラウザ用 (three-vrm) と空間用 (Godot) の二つで、役割が重ならない。

## 今の作り (2026-11-22 にコードで確認)

- 右サイドバー (`frontend/src/components/RightSidebar.tsx`) には、上から Building の名前と説明、内装画像 (`image_path`)、部屋にいるユーザー、部屋にいるペルソナ、アイテム、設置物 (Fixture) が並んでいる。画面の幅が 768px 以下のとき、右サイドバーは画面の端から引き出す形になる。
- アイテムの一覧は、`GET /api/info/details` (`api/routes/info.py`) が返す全件を、ID の順にそのまま並べている。ペルソナ向けにどのアイテムを見せるかを選ぶ関数 `_select_displayed_items` (`builtin_data/tools/get_visual_context.py`) は、この API では使われていない。入れ物 (Bag) について、API は中身の全件を返しているが、画面は中身の個数だけを出している。
- ペルソナの画像は二つある。小さなアイコン (`AI.AVATAR_IMAGE`、256px) と、ペルソナ本人に自分の見た目として渡している画像 (`AI.APPEARANCE_IMAGE_PATH`)。
- VRM の指定は、Godot のアドオンのペルソナ別設定 `avatar_vrm_path` にだけある。値は Godot を動かす PC の上のパスで、本体は VRM のファイルを持たず、VRM を返す API も無い。
- 画面には 3D を描くライブラリが入っていない。
- 声を鳴らす場所は二つある。自動で鳴る声は `frontend/src/lib/clientActions/playAudio.ts` の一つの audio 要素で鳴る。吹き出しの「音声を再生」ボタンは、`frontend/src/components/AddonBubbleButtons.tsx` の中で別に作られる Audio を使って鳴る。
- 自律で動いているペルソナが「いま何をしているか」を画面へ通知する仕組みは無い。返事を待つ間の表示は、ユーザーが送ったメッセージへの返事の間だけ、送った本人の画面に出る。部屋にいるペルソナの「いま何をしているか」の欄は 2026-08-22 に取り除いてあり、作り直しは「暮らしの窓」として、自律行動を実際に動かす部分 (autonomous_behavior_v3.md が「運転」と呼んでいる、これから作る部分) と一緒に予定されている (同 §9-9、§11)。
- 発話に身振りを付ける書き方 `{"body_emote": "smile"}` (9 種類) は、Godot のアドオンの中に実装されている。ペルソナへの案内は、Godot の Building にいる間だけ出る。ブラウザでは、この書き方が小さな灰色の `(smile)` として表示されるだけで、何も動かない。embodied_expression.md に書かれている `/emote` の形は下書きのままで、本体に実装は無い。

## 設計

この節のうち、「決まったこと」に発言の記録があるもの以外は、メティスがその決定を具体にした案になる。まはーの確認が要るものは「まはーが決めること」に挙げてある。

### 1. 舞台の置き場所 (画面の幅ごと)

舞台の置き場所は、画面の幅で三通りに分かれる (2026-10-05 にまはーが 4K と 1080p、全画面と半分のスクリーンショットを比べて決めた)。

- **チャットの左右に余白がある幅** (4K の全画面): 舞台を、チャットの横の独立した縦の区画として置く。
- **余白は無いが右サイドバーを出せる幅** (4K の半分、1080p の全画面): 右サイドバーの内装画像の枠 (Building の名前と説明のすぐ下) を、舞台に育てる。何もどけずに済む。
- **右サイドバーを出せない幅** (1080p の半分、スマホ): ログと舞台を切り替える。ペルソナが喋っている間だけ自動で舞台に切り替え、終わればログに戻す。

狭い幅での自動切り替えについて、まはーが確定した三点 (2026-10-05):

1. 舞台からログへ戻るのは、読み上げの音声があれば音声が終わったとき、無ければ文字が流れ終わって一呼吸置いたとき。
2. 利用者がメッセージを入力している最中と、過去のログを遡って読んでいる最中は切り替えない。「喋っています」の小さな印だけを出し、印を押せば手動で舞台に切り替えられる。
3. ログと舞台を両方出せる広い画面では、切り替え自体をしない。

三つの幅の境目の具体的な数値は、実装のときに実際の画面で決める。今のコードにある境目は 768px の一つだけ。

### 2. 舞台の中身は三通り

舞台は「3D を映す枠」ではなく、「その Building とペルソナが持っている一番豊かな見た目を映す枠」として作る。Building がこれから自動で増えていく構想では、増えた Building に 3D のシーンは付いてこない。内装画像は画像生成ですぐ作れるので、内装画像が全部の Building に共通の見た目になる。

- **内装画像と立ち絵** (全員に出る): 内装画像を背景に、ペルソナの 2D の画像を立ち絵として出す。立ち絵は新しい種類の画像ではない。使うのは、ペルソナ本人に見た目として渡している既にある画像 (`APPEARANCE_IMAGE_PATH`) で、無ければアイコンを使う。既にある画像と同じものを使うので、舞台のために別の見た目の設定を増やさない。
- **ブラウザが描く 3D アバター**: VRM を持っていて、3D の表示を入にしてあるペルソナは、立ち絵の代わりに 3D アバターが内装画像の前に立つ。空間は持たない (位置も歩行も無い)。
- **Godot の 3D 空間**: この文書の外 (virtual_embodiment_godot.md)。Godot が描いた映像を舞台の枠へ流す案は、流し続ける負荷を測っていないので、やるとしても後にする。日常の会話は上の二つで足りる。

中身の選び方は次のとおり。

- 3D を出すかどうかは、ペルソナごとの設定で選ぶ。VRM を入れていないペルソナには、その設定自体を出さない。
- VRM の読み込みに失敗したら立ち絵に戻し、失敗した理由を画面に出す。黙って立ち絵に替えない。
- 同じ部屋にペルソナが複数いるとき、舞台に立つのは一人にする。喋っているペルソナが立ち、誰も喋っていなければ最後に喋ったペルソナが残る。部屋にいるペルソナの一覧から選んで切り替えられる (メティスの案。まはーの確認はまだ)。

舞台の中身は、将来ほかの種類を足せる形にしておく。候補は、絵一枚から作る 2D の動くアバター (アイディア帳の「Mesh Avatar Studio」) と、Live2D (ライセンスの審査が要るので一番後回し — 2026-10-05 のまはーの決定)。

### 3. ブラウザの 3D アバター

- 描画には three.js と `@pixiv/three-vrm` (どちらも MIT ライセンス) を使い、アドオンではなく本体のフロントエンドに入れる。これまでアドオンに分けてきた理由は、大きな追加のソフト (GPU 用のものや Python のパッケージ) が要ること、ライセンスの都合、特定のハードが要ることだった。three-vrm はブラウザの中だけで動き、サーバー側に何も足さないので、どれも当てはまらない。
- 3D のライブラリは、VRM を持つペルソナの舞台を開いたときにだけ読み込む。3D アバターを入れていない利用者の画面は重くならない。
- three-vrm を使って描くのは、VRM の標準の描き方 (MToon)、表情、まばたき、視線、髪や服の揺れ。
- **口パク**: 鳴っている声の音量を取り、口の開きに写す。声を鳴らす場所は二つあるので (「今の作り」)、どちらの声でも口が動くようにする。声の無い発話では、文字が流れている間だけ口を動かす (Godot 側の「字幕だけなら時間で開閉する」と同じ扱い)。
- **動き**: 最初は立ち姿 (呼吸・まばたき・視線) だけにする。全身の動き (キーボードを打つ姿など) は設計 6 で足す。
- 採らなかったもの:
  - Godot をそのままブラウザで動かす道 (Godot の Web 書き出し)。ブラウザでは Compatibility という軽い描画方式しか使えない (Godot 4.7 の公式ドキュメント「Exporting for the Web」)。Godot の VRM アドオンで髪や服を揺らす拡張 (`vrm_physics.gdextension`) には、ブラウザで動く版が入っていない。VRM が一体 25〜150MB ある。
  - [three-liltoon](https://github.com/mochiya-labs/three-liltoon)。lilToon (VRChat 向けのアバターでよく使われる、MToon とは別の描き方) を Three.js 用に翻訳したもので、Unity から専用のツールで書き出し直した VRM にだけ効く。手元のアバターは全員 MToon なので、需要が小さい (2026-11-22 まはー)。
  - [aituber-kit](https://github.com/tegnike/aituber-kit) のコード。v2.0.0 以降カスタムライセンスなので流用しない。

### 4. VRM の持ち主と置き場所

- VRM はペルソナの持ち物にする。本体のペルソナ設定 (見た目の画像を変えるのと同じ画面) で指定し、ファイルは本体のユーザーデータの下に置く。
- 本体が VRM をブラウザへ返す。返す相手は、その SAIVerse の画面を開ける人に限る (今の画像と同じ範囲)。再配布を禁じている VRM があるので、リポジトリには入れず、外から誰でも取れる場所にも置かない。
- Godot のアドオンは、VRM を本体から取得する。Godot が SAIVerse と同じ PC で動いていても別の PC で動いていても、同じ方法で取得する。
- アドオンの `avatar_vrm_path` はなくす。VRM の設定が二か所にある期間を作らない。既に `avatar_vrm_path` を設定してある利用者のために、アドオンを更新するとき、本体から読める場所にあるファイルは本体へ一度だけ写す。写せなかったペルソナ (Godot のプロジェクトの中のパスや、別の PC のパス) は、どのペルソナの VRM を入れ直す必要があるかを画面に出す (この進め方は「まはーが決めること」6)。
- Godot だけが使うもの (表情のプロファイル、動きの好み、Godot と SAIVerse を繋ぐときの認証の情報) は、アドオンに残す。

**vessel.md (2026-07-21 の下書き) との食い違い**: vessel.md には、アバターの実物のデータはアドオンの側で管理し、本体の側では保存場所だけを記録する、と書かれている (アバターの見た目のデータの一覧を扱う「Avatar Asset レジストリ」の節と、同文書が必ず守ることとして挙げている「不変条件」4)。また同文書では、画面のアバターを Vessel の一種として位置づけている。種類の名前は `ambient` で、どの Building にも結び付かず、ペルソナがどこにいても使える身体、という意味になる。そのうえで、身体を動かすスペル (`body_gesture` など。今は Godot のアドオンにある) を受ける側に置いている。2026-11-22 の決定は、この二点と逆向きになる。VRM の実物を本体の側で持ち、ブラウザのアバターは姿を映すだけで、身体を動かすスペルを受けない。逆向きにした理由は三つある。ブラウザが VRM を描くには、本体が VRM を返せなければならない。アドオンのフォルダにある利用者のファイルはアンインストールで消えるので、ユーザーデータ側へ移したい、という方針が 2026-09-29 にまはーから出ている (アイディア帳「Godot Vessel のユーザー由来ファイルをユーザーデータ側へ引っ越す」)。vessel.md は下書きで、該当の部分は実装されていない。どちらを正とするかは「まはーが決めること」2 に挙げた。

### 5. 置かれたアイテムの並びと、埋もれたアイテムの山

- 舞台の脇に、Building に直接置かれているアイテムを並べる。絵は縮小した絵そのもの、それ以外は種類の印と名前を出す。押すと、今と同じアイテムの画面が開く。今の右サイドバーのアイテム一覧の描き方を変えるだけで、アイテムの新しい置き場は作らない。設置物 (Fixture) は対象外で、今と同じ別の欄に出す。
- 並べるのは、ペルソナに見える範囲だけにする。範囲は room_item_display_cap.md の決まりそのもの (建物に直接置かれたアイテムのうち、最近触られた順の上位。初期値は 10 個で、Building の設定で変えられる)。
- 残りは山一つにまとめ、「ほかに N 個のアイテムが埋もれています」と添える。押すと残りが見える。ペルソナが読んでいる一行 (「ほかに N 個のアイテムがありますが、埋もれていて見えません。スペル『埋もれたアイテムを見る』でめくって見られます」) と同じ「埋もれて」という語を使うが、一字一句同じにはしない (スペルの案内はユーザーには要らない)。箱の絵にしないのは、片付け用の入れ物 (Bag) と見分けにくくなるため。Bag は誰かがしまったアイテムで、埋もれたアイテムは散らかって見えなくなっているだけ。
- **どれが埋もれているかを、画面の側では数え直さない。** `/api/info/details` が、ペルソナ向けの部屋の様子と同じ関数 `_select_displayed_items` を通した結果 (見えるアイテムと、埋もれたアイテム) を返し、画面の側は受け取った結果をそのまま描く。選ぶ処理が二か所にあると、いつか食い違って、今と同じ見え方の食い違いがまた生まれる。スペル「埋もれたアイテムを見る」(`buried_items_view.py`) は、入れ物の中身まで含めた全部のアイテムを一本の順に並べてページに分ける、別の役割の処理なので、この関数にはまとめない (「最近触られた」の時刻を決める処理には、今も両方で同じ関数 `_touched_epoch` を使っている)。
- 画面での並び順は、最近触られた順 (先頭が一番新しい) にする。ペルソナに渡す部屋の様子の中の並び順は変えない (room_item_display_cap.md の「不変条件」6)。
- この文書で「触る」と書くのは、room_item_display_cap.md の決まりで順位が上がる操作のこと。アイテムの中身や説明の書き換え、開け閉め、置き場所の移動がそれに当たる。読むだけでは順位は上がらない。
- **食い違いうる所**: ペルソナが実際に読んでいる部屋の様子は、部屋に入ったときの全文と、その後に変わった部分の積み重ねでできている。画面に出るのは「いま選び直した結果」なので、ユーザーがアイテムを触った直後などに、一時的に食い違うことがある。画面が示しているのは、「次に部屋の様子が組まれたときにペルソナに見える範囲」になる。
- 開いた入れ物 (Bag) の中身にも同じ決まり (上位 10 件) がある。画面で中身を見せる形にするときは、同じ山の描き方を使う。最初の段階では、今と同じ個数だけの表示のままでよい。
- room_item_display_cap.md の「不変条件」1 にある「ユーザー画面の一覧は無傷」は、「山にまとまるが、押せば全部に届く」へ、実装と同じ変更で書き直す。

### 6. 喋っている間と、作業している間

舞台のアバターは、ペルソナが何をしているかで姿を変える。姿は数個に限る。

- **喋っている間**: 口パクをする。狭い画面では、設計 1 のとおり舞台へ自動で切り替える。
- **返事を書いている間、スペルを実行している間** (ユーザーとの会話の中): 作業の姿になる。会話の中では、返事を待つ間の表示に使っている画面への通知 (chat_progress_display.md) が既にあるので、それを使う。
- **自律で作業している間**: 作業の姿になり、触っているアイテムが並びの先頭に出てきて、印が付く。

自律で作業している間の表示には、「いま何のスペルを実行していて、どのアイテムを触っているか」を画面へ通知する仕組みが要る。この仕組みは今は無い。もとになる自律行動を実際に動かす部分そのものが、これから作られる (autonomous_behavior_v3.md §11)。だから、この表示は自律行動を動かす部分と一緒に作る。

autonomous_behavior_v3.md §9-9 で「暮らしの窓」に出すと決めてある一行の中身は、ペルソナがいま取り組んでいる一件の名前と、自律行動の入・切だけで、実行中のスペルと触っているアイテムは含まれていない。舞台にはこの二つが要るので、自律行動を動かす部分の設計のときに、取り出す場所を一つ決め、暮らしの窓と舞台が同じ所から受け取る形にする。同じ事実を取り出す場所を、画面ごとに別々に作らない。

**原則: 舞台に出す「いま何をしているか」は、事実だけから決める。** 使うのは、実行中のスペルと、触っているアイテム。ペルソナの気持ちや意図を、機械が推測して姿に出さない。autonomous_behavior_v3.md §9-9 の「スペルの表示は解釈ではなく事実の翻訳」と同じ線引きになる。

- 作業の姿は、立ち姿・キーボードを打つ姿・絵を描く姿のような、決まった数個にする。どのスペルがどの姿になるかの対応表は、本体のフロントエンドに置く。対応の無いスペルは、汎用の「作業している」姿になる。
- 触っているアイテムが並びの先頭に出てくるのは、新しい仕組みではない。「最近触られた順」は、アイテムの中身が書き換えられると順位が上がる決まりなので、山に埋もれていたアイテムをペルソナが書き足すと、そのアイテムは山から出て先頭に並ぶ。読んでいるだけのアイテムは順位が上がらないので、先頭には出てこない。まはーが 3D について言った「使うときにアバターをそこへ向かわせる」は、Godot の中では歩いて向かう形になり、ブラウザの舞台ではアイテムのほうが前に出てくる形になる。
- 狭い画面では、自律の作業中に自動で舞台へ切り替えない。「作業しています」の小さな印だけを出し、押せば舞台が見える (メティスの案。まはーの確認はまだ)。ユーザーに話しかけているわけではないので、ログを読む手を止めさせない。2026-10-05 の決定は「喋っている瞬間以外のペルソナは事実上眠っている」を前提にしていたので、ここはその前提が変わる所になる。

### 7. 発話中の身振り (後の段階)

- 書き方は、既に動いている `{"body_emote": "smile"}` (9 種類) を使い、新しい書き方を作らない。9 種類はどれも全身の動きとして表す、というのが既存の決まりなので (virtual_embodiment_godot.md「発話位置に同期する全身エモートと口パク」— 表情だけの動作にはしない)、ブラウザのアバターでも全身の動きとして表す。だから、ブラウザで全身の動きを再生できること (設計 6) が前提になる。
- 今は、この書き方の案内が Godot の Building にいるペルソナにしか出ていない。ブラウザのアバターのために案内の範囲を広げると、ペルソナが読む文章が変わる。これは見た目の話ではなくペルソナへの働きかけなので、広げるかどうかは別に決める (「まはーが決めること」4)。
- v0.3 までの下書きには、embodied_expression.md の `/emote` の形を使うと書かれていた。実際に作られたのは `body_emote` の形なので、この文書は動いているほうに合わせる。embodied_expression.md の側の整理は、この文書の範囲の外に置く。

### 8. Godot と同時に動いているとき

- ブラウザのアバターは姿を映すだけで、位置の情報を持たない。ペルソナがどの Building にいるかは Building の在室の記録にあり、空間の中の位置は Godot の中にある。だから、Godot の中のアバターとブラウザのアバターが、二つの身体として食い違うことは無い。
- Godot の Building にペルソナがいて Godot が繋がっている間、声は Godot の中のアバターからだけ鳴る (virtual_embodiment_godot.md の既存の決まり)。この間、ブラウザには口パクに使う声が無いので、口は文字に合わせて動く。

## 必ず守ること

1. **何も入れていない利用者にも舞台が出る。** 内装画像と立ち絵が土台で、3D はその上に載る追加。
2. **ペルソナに見えるアイテムの範囲を決める処理は一つ。** 画面の側では数え直さず、受け取った結果をそのまま描く。
3. **アイテムは消えない。** 山にまとまったアイテムにも、押せば届く。
4. **舞台を表示しても、ペルソナの発話・記憶・ペルソナに送る文章は変わらない。** 設計 7 の案内の範囲を広げるかどうかは、別の決定として扱う。
5. **「いま何をしているか」は事実だけから出す。** 実行中のスペルと触っているアイテムから決め、気持ちや意図を推測して姿にしない。
6. **VRM の設定は本体の一か所。**
7. **ブラウザのアバターは空間を持たない。** 位置・歩行・アイテムとの距離を持たせたくなったら、それは Godot の役目。
8. **狭い画面で、ログを読んでいる・入力している利用者の画面を勝手に切り替えない。**
9. **3D のライブラリは、VRM を持つペルソナの舞台を開くまで読み込まない。**

## 段階

1. **枠と、置かれたアイテム**: 舞台の枠 (三つの幅)、内装画像と立ち絵、狭い画面の自動切り替え、アイテムの並びと山 (設計 1、設計 2 の「内装画像と立ち絵」、設計 5)。3D を入れていない利用者にも届く部分を先に作る。
2. **3D アバター**: VRM を本体のペルソナ設定に置く、ブラウザで描く、口パク、Godot のアドオンが本体から VRM を取得する (設計 3・4)。
3. **作業の姿**: 全身の動き、会話の中の作業の姿、自律で作業している間の表示 (設計 6)。自律の部分は、自律行動を動かす部分と一緒に作る。
4. **発話中の身振り**: 設計 7。

後回しにしたもの: Godot の映像を舞台へ流すこと、2D の動くアバター、Live2D。

## まだ確かめていないこと (確かめ方)

- **全身の動きをブラウザで再生できるか。** three-vrm 自体には動きの再生が入っていない。候補は `@pixiv/three-vrm-animation` (VRM 用の動きのファイル `.vrma` を再生するライブラリ、MIT ライセンス)。Godot 用の動きは ARDY (文章から身体の動きを作るモデル) で作ってあるので、そのデータをブラウザでも使えるかを、段階 3 の最初に、本番と分けたテスト環境で一体の VRM を使って試す。
- **スマホでの重さ。** VRM は一体 25〜150MB ある。段階 2 の確認で、スマホの実機で読み込みの時間と動きの滑らかさを測る。重すぎたときの手当ては、その結果を見てから決める。
- **Godot が、本体から取得した VRM を、動かしている最中に読めるか。** Godot のエディタから動かす形では、今も動かしている最中にファイルのパスから VRM を読んでいる。配布用に書き出した Godot で外部の VRM を読めるかは、virtual_embodiment_godot.md の「最初に潰す技術リスク」に「実行時VRMロード」として挙がったままで、まだ確かめられていない。段階 2 の最初に確かめる。
- **本体とアドオンの更新が同時でない場合。** アドオンは別のリポジトリなので、新しいアドオンと古い本体の組み合わせが起こりうる。アドオンのカタログの登録情報には、必要な本体のバージョンを書く欄 `min_saiverse_version` があり、導入と更新のときに検査されている (`saiverse/addon_registry.py`、`saiverse/addon_installer.py`)。新しいアドオンのこの欄に必要な本体のバージョンを書いておけば、導入と更新のときの検査で足りるかを、段階 2 の設計で確かめる。
- **自律行動を動かす部分から、実行中のスペルと触っているアイテムを取り出せるか。** 段階 3 の自律の部分は、その部分の設計と一緒に詰める。

## 検証の手順

- **本番と分けたテスト環境** (本番から分けたデータの保存先 — `SAIVERSE_HOME` で指定する、SAIVerse のデータを置くフォルダ —、テスト用に作ったペルソナ、決まった返事を返すテスト用の LLM。画面の繋ぎ先は、起動の手順で、本番と分けたテスト環境のバックエンドに固定する): アイテムが 15 個以上ある部屋で、上位 10 個が並び、残りが山になること。アイテムを触ると並びの先頭に出てくること。Building の設定で上限を変えると並ぶ数が変わること。同じ部屋について、ペルソナ向けの部屋の様子に出るアイテムと、画面に並ぶアイテムが一致すること。VRM を入れたペルソナが 3D で出て、VRM の無いペルソナには設定が出ないこと。壊れた VRM で立ち絵に戻り、理由が出ること。画面は、三つの幅とスマホの幅でメティスが開いて見る。
- **実機** (まはー): 4K と 1080p、全画面と半分、スマホでの置き場所と自動切り替え。実際の VRM での見た目と口パク。Godot と同時に使ったときの声と口の動き。
- 本番のペルソナには触れない。発話が要る確認は、テスト用に作ったペルソナとテスト用の LLM で行う。
