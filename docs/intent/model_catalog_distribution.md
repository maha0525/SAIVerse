# Intent: モデル定義の外部配布とカタログ

**ステータス**: 設計中 (v0.1, 2026-07-23)。段階1〜2 は設計確定・実装待ち。段階3以降はまはーレビュー待ち。

前提となる既存設計: [モデル＆プロバイダ管理 UI](model_provider_management.md)

## これは何か

新しい LLM モデルが出るたびに SAIVerse 本体を更新しなくても、モデル定義だけを外部から取り込めるようにする。同じ定義を SAIVerse Lite からも使えるようにして、両実装が同じモデル知識を共有する。

ただし **接続先とAPIキーの指定は絶対に外部から持ち込ませない**。持ち込ませると、外部リポジトリが乗っ取られたときに「どこへプロンプトとAPIキーを送るか」を攻撃者が決められるため。

## なぜ必要か

### 問題1: モデルを1つ足すのに本体の更新が要る

モデル定義は `builtin_data/models/*.json` にあり、リポジトリの一部として配布されている。新しいモデルが出た日に使い始めるには、本体を更新するしかない。モデルの世代交代は速く (2026-07-21 に Gemini 3.6 Flash が出て、その2日後に 3.5 Flash が終日 503 を返した)、本体の更新周期より短い。

### 問題2: SAIVerse Lite が同じ知識をゼロから作り直した

2026-07-23、Lite で丸一日かけて解いた問題が本体に全部あった。thought signature の差し戻し、429/5xx の再試行、無料枠の存在、キャッシュの最小トークン数、そして推奨モデル名。Lite は独立に同じ数字へ到達した上に、再試行対象から HTTP 408 が抜けた劣化版になっていた。

Lite の推奨モデルは `gemini-3.5-flash` のまま固定されており、それが新規ペルソナへ複写され続けていた。本体側の定義は更新されていたので、**同じ知識が2箇所にあり、片方だけ古くなった**。

この2つは同じ根から出ている。モデル定義が特定のリポジトリの中に埋まっていて、外から参照する手段がない。

## 全体像

### 誰が何を頼りにするか

- **まはー / ユーザー**: 新しいモデルを、本体を更新せずに使い始められる。更新が止まっても、いま動いているものは動き続ける
- **SAIVerse Lite**: 本体と同じモデル知識を持つ。context_length、料金、利用制限、キャッシュ条件を自前で持たない
- **将来の保守者**: まはーがいなくなった後も、カタログの配布元を引き継げる。引き継がれなくても本体は動く

### 不変条件

1. **同梱した定義だけで完全に動く。** カタログは足すか上書きするだけで、無くても機能は落ちない。カタログが消えて止まるのは「新しいモデルが自動で増えること」だけ
2. **接続情報は外部から来ない。** `base_url` / `api_key_env` / `protocol` は、本体が同梱するプロバイダ定義か、まはー自身が自分の端末で書いたものだけを正とする。カタログ由来の定義がこれらを持っていたら、読み込み時に落とす
3. **カタログの配布元を差し替えられる。** リポジトリが消えたら、誰かが fork して設定でそちらを向ける。依存を無くすのではなく、引き継げる形にする
4. **更新が止まった状態を異常として扱わない。** 更新必須の関門を作らない。期限を切らない。催促しない。古いカタログのまま動き続けるのが通常の状態

不変条件2が設計全体を決めている。これが守れないなら、外部配布そのものをやらない。

### 所有者

| 情報 | 持ち主 | 置き場 |
|---|---|---|
| プロトコル / 接続先 / APIキーの環境変数名 | **本体（同梱）** | `builtin_data/providers/*.json` |
| モデルID / 表示名 / context_length / 料金 / 利用制限 / キャッシュ条件 / 対応メディア | カタログ（外部でよい） | 後述のカタログ置き場 |
| 上記すべての上書き | まはー自身 | `~/.saiverse/user_data/` |

## 現状の事実 (2026-07-23 時点の実測)

プロバイダ定義とモデル定義を分ける仕組みは既にある (`saiverse/model_configs.py` の `_resolve_provider_ref`)。ただし移行がほとんど進んでいない。

| | 件数 |
|---|---|
| モデル定義の総数 | 128 |
| `provider_ref` を使っているもの | **4** |
| `base_url` を直接持つもの | 55 |
| `api_key_env` を直接持つもの | 61 |

`_resolve_provider_ref` の解決順は「モデル側の直接フィールドが常に優先」。つまり現状のままカタログを外部化すると、カタログのモデル定義が `base_url` を書くだけで接続先を乗っ取れる。**不変条件2は今は成立していない。**

直接持っている61件の接続先は3種類しかない。

| 接続先 | 件数 | 移行先 | プロバイダ定義 |
|---|---|---|---|
| `https://openrouter.ai/api/v1` | 39 | `provider_ref: openrouter` | **新規に作る必要がある** |
| `https://integrate.api.nvidia.com/v1` | 16 | `provider_ref: nvidia_nim` | 既にあり、base_url も一致 |
| (xAI、base_url なし・`XAI_API_KEY` のみ) | 6 | `provider_ref: xai` | 既にある |

プロバイダ定義を1つ足せば、128件すべてから接続情報を消せる。

## 段階

### 段階1: `openrouter` のプロバイダ定義を追加

`builtin_data/providers/openrouter.json` を作る。`protocol` は `openai_compat`、`base_url` は `https://openrouter.ai/api/v1`、`api_key_env` は既存モデルが使っている環境変数名に合わせる。

### 段階2: 61件を `provider_ref` へ移行

各モデル定義から `base_url` / `api_key_env` / `provider` を削り、`provider_ref` を1行入れる。機械的な書き換えなので、移行前後で `get_model_config()` の解決結果が全モデルで一致することを検査しながら回せる。

**段階1〜2 は、カタログを作るかどうかと独立して価値がある。** 外部配布をやらないと決めても、既に設計されて3%しか進んでいない移行が完了して128件が一貫した形になるだけで、無駄にならない。だから判断を先送りにしたまま着手できる。

### 段階3: カタログの置き場と、出所による制限

カタログは `~/.saiverse/catalog/` に置く。`expansion_data/` とは別にする理由は、拡張パックが今も `git clone` で自由に足せる枠であり、そこに接続情報の禁止をかけると既存の用途を狭めるため。カタログは信頼の水準が違うので、枠ごと分ける。

読み込み優先度は既存の3層に1つ挟む形になる。

| 優先度 | 出所 | 接続情報 |
|---|---|---|
| 最優先 | `~/.saiverse/user_data/models/` | 書いてよい（まはー自身が自分の端末で書いたもの） |
| 2 | `expansion_data/<pack>/models/` | 現状維持 |
| 3 | `~/.saiverse/catalog/models/` | **禁止。読み込み時に落とす** |
| 最低 | `builtin_data/models/` | 書いてよい（同梱） |

制限は**フィールド**ではなく**出所**にかける。`saiverse/data_paths.py` の `iter_files()` はどのディレクトリから読んだかを知っているので、そこで判定できる。

段階2が済んでいれば、同梱のモデル定義も接続情報を持たなくなっているので、この禁止を入れても何も壊れない。

### 段階4: 外部カタログの取得

カタログの配布元リポジトリを決め、取得する手段を用意する。取得先URLは設定可能にする（不変条件3）。取得は任意で、失敗しても起動を妨げない。

### 段階5: SAIVerse Lite 側

Lite はブラウザで動きファイルシステムを持たないので、同じ3層を別の器で作る。

| 優先度 | 本体 | Lite |
|---|---|---|
| 最優先 | `~/.saiverse/user_data/models/` | ユーザーが端末で編集した定義 (IndexedDB) |
| 中 | `~/.saiverse/catalog/models/` | 取得したカタログ (IndexedDB) |
| 最低 | `builtin_data/models/` | ビルド時に同梱した TypeScript モジュール |

Lite 側でも不変条件2は同じで、むしろ深刻になる。APIキーがブラウザの中にあるため、接続先を書き換えられると直接そこへ送られる。Lite の接続先は同梱定義に固定し、カタログからは変更できないようにする。

Lite のパートナー画面のモデル指定は、自由入力からカタログ選択に変わる。OpenAI 互換エンドポイントだけは自由入力を残す（アプリ側が何のモデルを持つか知りようがないため）。

## 検証

- 段階2: 移行前後で全128件の `get_model_config()` の解決結果が一致すること。実際にモデルを呼ぶ必要はない
- 段階3: `~/.saiverse/catalog/models/` に `base_url` を含む定義を置き、それが無視され、警告が出ること
- 段階4: カタログの取得先を到達不能なURLにしても、起動と会話が通常どおり動くこと（不変条件1）
- 段階5: Lite でカタログを空にしても、同梱定義だけで会話が成立すること

不変条件1と2は、正常系の確認では守られているか分からない。**カタログを壊した状態・悪意ある内容を置いた状態で検証する。**

## 未決事項

- カタログの配布元を独立したリポジトリにするか。まはーの当初の動機（本体を更新せずにモデルを足す）は独立リポジトリにしか無いので、私は独立を推している
- カタログのスキーマを本体のモデル定義とそのまま同じにするか、接続情報を持てない別スキーマとして定義するか。同じにすると段階3の「読み込み時に落とす」で守り、別スキーマにすると構造的に書けなくなる
- 取得の頻度と、まはーへの提示の仕方（黙って更新するか、差分を見せて承認を取るか）

## 経緯

2026-07-23、SAIVerse Lite の不具合調査から派生。Lite が本体の既存解決を参照せずに再実装していた件をまはーが指摘し、「モデル定義を別の場所に置いて自動取得できないか、ただしそれは『まはーがいなくなっても SAIVerse は使い続けられる』という思想に面倒を持ち込む」という懸念とともに議論した。

不変条件2（接続情報を外部から持ち込ませない）は、この議論の中で私が挙げた乗っ取り時のリスクに対して、まはーが「もともと分かれているプロバイダとモデルのうち、モデルだけを外部から持ってくる形にすれば改修が小さい」と応じたことで形が決まった。
