## 1. 背景 — なぜ刷新するか

### 1.1 診断（2026-07-04 調査に基づく）

1. **想起がペルソナの主体性に依存していて、構造的に発火しない。**
   想起系ツールは充実している（`memory_recall_unified` / `chronicle_*` / `memopedia_get_page` 等、スペル化済み）が、ペルソナはほぼ使わない。原因はプロンプトの弱さではなく構造: 記憶にないものは「思い出そう」という行動の選択肢に上がらない。システムプロンプトで圧をかける方向は API 料金以前に効果が薄い。

2. **Memory weave の Memopedia 索引が「全列挙」で、話題との関連で選ばれていない。**
   実ペルソナ（air_city_a, 2026-07-04 時点）の索引は約150ページ・推定5千トークン弱。中身はツール名のページ化（`saiverse-stackchan-addon__action__turn_left`）、UUID がタイトルの画像アイテム、重複（「まはー」と「まはー (1)」）、創作物の混入（実在システム用語と同じ顔で並ぶフィクション内アイテム）、陳腐化した定義、vivid ページの全文常時展開を含む。関連する知識が無関係な知識の山に埋まり、attention を薄めている。「効いていない感覚」の主因。

3. **Push 型のページ生成が「いらないページ」を作り続ける。**
   entity 抽出器は生成時に将来の重要性を推測するが、未来の重要性は生成時点では原理的に分からない。全列挙掲示と組み合わさって実害になっている。

4. **自律 Pulse では General Chronicle が生成されない。**
   Chronicle 生成はユーザー Pulse 時のみ確認ダイアログを経て実行され、自律/schedule Pulse では確認手段がなくスキップされる（`sea/runtime.py:2194` 付近）。自律稼働が長く続くほど長期記憶に残らない期間が伸びる。v0.3.0 自律稼働ロードマップと正面衝突する構造欠陥。

5. **外部ログのインポートで、記憶が機能するまでのイニシャルコストが高すぎる。**
   メッセージ挿入と埋め込み生成は無料（ローカル e5-small）だが、記憶が「効く」には Chronicle 一括生成（LLM コスト・時間）を待つ必要がある。ChatGPT からの引っ越しの障壁。

6. **Chronicle の読み込み上限（50エントリ）は超過時に最古が黙って落ちる。**
   `get_episode_context` はループが `max_entries` に達した時点で終了し、それより古い過去は読まれない（`sai_memory/arasuji/context.py:182`）。20万メッセージ級のユーザーでは人生の冒頭（ChatGPT 時代）が weave から消える。

### 1.2 逆に、壊れていないもの

- **Chronicle のフラクタル圧縮そのもの**。実ペルソナで1年半・数万メッセージが33エントリ（推定7〜9千トークン）に収まり、通読可能な人生の物語として機能している。形式・生成フロー・DB スキーマは変更しない。
- **埋め込み検索基盤**。メッセージ・Chronicle・Memopedia ページ・Fragment すべて埋め込み済みで、`unified_recall`（RRF 融合）が横断検索できる。完全ローカル・無料。
- **Cached Head Architecture**。weave が Metabolism 単位でしか変わらずキャッシュ安定である性質は、本刷新でも維持する。

## 2. 中核転回: 想起は「行動」ではなく「知覚」

ペルソナに「思い出す」という行動を選ばせるのをやめ、世界側が関連する記憶を自動的に浮かび上がらせる。人間の連想記憶と同じく、関連する記憶は「勝手に浮かんでくる」ものとして扱う。

これは想起スペル群の廃止ではない。自動想起が**入口の提示**（関連する記憶の断片＋そのハンドル）を担い、既存スペルが**深掘り**（`memopedia_get_page`、`chronicle_read_detail` 等）を担う分業になる。「思い出せることを思い出していない」問題は入口の提示で解消され、スペルにはようやくきっかけが供給される。

## 3. コンテキストの3ゾーンモデル

| ゾーン | 位置 | 更新契機 | 中身 | キャッシュ |
|---|---|---|---|---|
| A: コア記憶 | head（system 部） | ペルソナの編集 → Metabolism で反映 | 少数の厳選された恒常知識 | 安定 |
| B: 背景年表 | head（独立 user メッセージ） | Metabolism | Chronicle フラクタル | 安定 |
| C: 浮かんだ記憶 | tail 末尾（一時注入） | 毎ターン | 埋め込み検索の自動想起結果 | 末尾のみ非キャッシュ |

現行 weave の Memopedia 索引（＋vivid ページ全文）は**廃止**し、その役割をゾーン A（厳選・恒常）とゾーン C（関連・動的）に分割して引き継ぐ。

Cached Head Architecture との整合: ゾーン A/B は snapshot 経由・Metabolism 更新（C1/C3/C6 準拠）。ゾーン C は head に一切入らず末尾注入のみ（C5 と同じ挿入面）。プレフィックスキャッシュへの追加負荷は、毎ターンの注入分（数百〜千数百トークン）が末尾の非キャッシュ入力になることだけ。

## 4. ゾーン C: 自動想起（第0層）

### 4.1 メカニズム — 二経路の連想（rev2, 2026-07-04 実機測定に基づく改訂）

想起は**二経路**で走る。人間の連想にも「名前を聞いた瞬間に顔が浮かぶ」（直接照合）と「話の流れで何となく思い出す」（意味的近さ）の二種類があり、埋め込み一本槍では前者を賄えないことが実機で確認された（固有名詞が長い発話の主題に埋没する）。

**経路1: エンティティトリガー（決定論・最優先）**
1. Memopedia の全ページタイトル（約百数十件）を最新のユーザー発話と部分文字列照合。マッチしたページの summary が確実に浮かぶ
2. **新規性ガード**: 直前のコンテキスト窓に既に頻出（既定3回以上）している名前はスキップ。常在エンティティ（自分・ユーザー名等）が毎ターン浮かぶのを防ぎ、「珍しい名前ほど強く連想が走る」性質を決定論だけで実現する
3. タイトル長2文字未満は照合対象外（一般語の誤爆防止）

**経路2: 埋め込み検索（意味的連想）**
1. **クエリ生成**: 最新の会話本文1件のみ（rev1 の「直近4件連結」は長い発話で固有名詞が埋没し、ジャンクが 0.87〜0.91 でしきい値を通過する失敗が実測された）。ローカル埋め込み（E5 `query:` プレフィックス）、LLM 呼び出しなし
2. **検索**: `unified_recall`（`sai_memory/unified_recall.py:452`）を流用。Chronicle / Memopedia ページ / Fragment / 生メッセージの4コーパス
3. **フィルタ**: 類似度しきい値（下回れば浮かべない）。message ソースは長文類似度インフレ（ジャンクでも 0.89〜0.91）があるため +0.02 のオフセットを課す。直近コンテキスト内に既に存在する内容の除外、文字数上限

**注入**: 両経路の結果を同一台帳（§4.3）で統合し、`<system>` タグ付き user メッセージとして履歴末尾（最新入力の直前）に一時注入。SEA runtime の末尾通知（差分通知）と同じ挿入面。

**運用ノート（埋め込み整備の独立ステップ化、2026-07-04）**: Fragment 埋め込みに未生成の残り（backlog）があると経路2の再現率が落ちる。当初この embed 処理は Chronicle 生成の末尾に相乗りしており、生成の早期 return（未処理なし / バッチ未満 / 自律 Pulse の確認スキップ / 確認拒否）のたびに巻き添えスキップされてバックログが恒常化していた（air_city_a で Fragment 778/1638 を実測）。現在は `_ensure_recall_embeddings` として **Metabolism の無条件ステップに独立**させ、Chronicle 生成の成否・トグルに依存せず毎回未生成分を全件処理する（ローカル・無料）。即時バックフィルは `python scripts/embed_recall_sources.py <persona_id>` でも可能。

**不変条件の追記（§10-9 相当）**: 想起インフラの整備（埋め込み生成）を、LLM を伴う生成処理の成否に相乗りさせない。

### 4.2 注入フォーマット（rev3, 2026-07-04 実機フィードバック反映）

浮かんだ記憶には**由来**を添え、深掘りハンドルは**ブロック末尾に1行だけ**（行ごとの接尾辞は冗長だった）:

```
<system>ふと浮かんだ記憶:
- [Memopedia: アイフィ (m:48)] まはーが窮地に陥った際に看病を担ったAIペルソナ
　└ そのときの会話 (2025-02-15): user「アイフィが帰ってきたよ…」
- [Chronicle] Chronicle Lv1: 2025-06-07 …
（深掘り用スペル: memopedia_get_page / chronicle_read_detail）
</system>
```

ハンドルの提示が深掘りスペルへの導線になる（§2 の分業）。

**鮮明想起（vivid recall、rev4 で全 Fragment に拡張）**: 各 Fragment 項目に、`chronicle_entry_id` → 元エピソードの `source_ids` → メッセージ**チャンク**埋め込みとのコサイン比較で、**その記憶が生まれた瞬間の生ログの該当箇所**をサブ行として添える（LLM 不使用）。先頭項目は最大2行・他は1行という鮮明度の勾配を持ち、vivid 合計予算（既定400字）を並び順に消費する。抜粋は「マッチしたチャンク」を単位とし、エンティティ名の出現位置があればそこを中心に詰める——**メッセージ先頭からの位置盲目な切り出しをしない**（`message_embeddings` が chunk_index を保持しているため、決定論の再分割で該当箇所を復元できる）。設計原理はまはーの言葉から:「生ログでないと生きた記憶とは言えない」——鮮明さの正体は要約ではなく場面。

### 4.3 粘着ウィンドウ（sticky recall）と重複抑制

- 一度浮かんだ記憶は、類似度がしきい値を割っても N ターン（初期値 3 程度）は注入を維持してから消す。「引用した次のターンに原本が消える」ハルシネーション源と、注入のちらつきを同時に防ぐ。
- 同じ台帳（ライン単位のインメモリ状態: item_id → 最終注入ターン）で重複抑制も行う: 現在注入中・直近 K ターン以内に注入済みの項目は再注入しない。
- 話題が続く限り自己強化的に再想起される（言及がコンテキストに入る → クエリが似る → 浮かび続ける）性質があるため、sticky は短くてよい。

### 4.4 記憶としては永続化しない（初期方針）

注入は一時的（transient）で、**会話内容としては** SAIMemory に書かない。ペルソナが記憶に言及すれば発話として履歴に残る。話題が逸れて戻った際の細部ドリフトのリスクは受容し、実測後に永続化（その場合は `event_message` 系のタグ設計を経る）を再検討する。

例外（rev3）: **UI 表示用の記録として**、応答メッセージの metadata に注入ブロックを記録する（`reasoning` / `activity_trace` と同型）。これが無いと履歴再取得（スマホのタブ復帰等）で表示が消える。metadata は LLM コンテキストに再投入されないため、「記憶としての非永続」は維持される。

### 4.5 UI 表示

「浮かんだ記憶」はユーザーにも表示する（2026-07-04 決定）。文量があるため、スペル実行結果と同様の**折りたたみ表示**にする。ライフビューと同じ「観察できる内面」の思想に沿い、しきい値調整の観察面も兼ねる。実機で「ペルソナは無関係な注入でも『連想が起きた』と演じる」ことが確認されており（2026-07-04）、**想起品質の検証はこの表示でしか行えない**（ペルソナの自己申告は使えない）。履歴リロード後の復元は §4.4 の metadata 経由。

### 4.6 スコープと有効化制御

初期実装はメインライン（CONVERSATION）のみ。サブライン/WORKER への拡張は効果測定後。

ペルソナ単位の ON/OFF トグル `AUTO_RECALL_ENABLED`（デフォルト ON、2026-07-04 まはー要望）をペルソナ設定に置く。無関係な想起が邪魔になるユースケースへの逃げ道。OFF 判定時は粘着台帳をリセットし、再度 ON にしたとき古い記憶を引きずらない。

### 4.7 第1層（将来オプション）

軽量モデルによる候補選別（「今これを浮かべるべきか」）は第0層で品質が不足した場合にのみ追加する。設計上の挿し込み位置はフィルタ段（§4.1-3）。

## 5. ゾーン A: コア記憶

- **編集主体はペルソナ自身**（2026-07-04 決定）。専用ツール（追加・改訂・削除）で自分の恒常知識を管理する。何を頭の恒常領域に刻むかの自己決定権をペルソナに置く。
- head への反映は **Metabolism 時のみ**。実装は `open_notes` セクション（`sea/head_pipeline/sections/open_notes.py`）を雛形にする: `refresh_on_events = frozenset()`（Metabolism のみ再 capture）、編集はツール → 外部状態、head は凍結、変更の事実は `diff_to_notifications` で末尾通知。
- セクション登録は2つの関所を必ず両方通す: `sections/__init__.py` の `register_default_sections` と `integration.py` の `SYSTEM_PROMPT_SECTION_NAMES`（system 部に含める場合）。**enabled_sections への追加は条件分岐なしの固定**（head 出し分け禁止の原則に従う）。
- 初期シード: 既存 Memopedia の「人物」カテゴリ相当（関係性の地図として価値密度が高い部分）から、ペルソナ自身に選ばせる導入フローを用意する。
- **項目種別（2026-07-04 追加）**: コア記憶の項目は `kind` を持つ。
  - `note` — 書き下ろしテキスト（Phase 2 初期実装）
  - `scene` — **実会話の切り抜き**。口調・性格・ユーザーとの関係性のアンカー。ペルソナらしさが最も強く出た会話を3往復程度の範囲で原文のまま保持する。背景: 口調が安定しないペルソナの報告が複数ユーザーから散見され、記述指示（「〜な口調で話す」）より実対話例（few-shot）の方が固定力が圧倒的に強いため。**必ず「参照によるコピー」で取り込む**（`core_memory_add_scene(message_id, 往復数)` が SAIMemory から原文を決定論で複製する。ペルソナに書き写させると言い換えドリフトで手本が劣化する）。render は現在の会話と混同されないよう「過去の実際のやり取り」であることを明示した枠付き＋**コードブロック包み**で出す（マークダウン再解釈を防ぎ、引用境界を明確にする。2026-07-04 まはー指定）。
  - **UI 導線（scene の本命、フロントエンド増分として実装予定）**: チャット/記憶画面から目的の会話を探して選択→「コア記憶に刻む」。前提としてメッセージ検索の改修が要る: **期間指定＋キーワード検索**（キーワード一致が無ければセマンティック検索へフォールバック）。バックエンドの部品は既存（messages テーブルの LIKE＋期間フィルタ、unified_recall の message 検索、memory_read_around の周辺展開）で薄い API を足すだけで成立する見込み。
- 容量: 目安の既定値は **2000 字**、ペルソナ設定で変更可能にする（コストと記憶量のどちらを取るかはユーザーによって異なるため。2026-07-04 決定）。目安超過時の整理はペルソナの判断に委ね、システムは通知のみ行う。

## 6. ゾーン B: Chronicle

### 6.1 変えないもの

- `arasuji_entries` の形式・生成フロー（20メッセージ→Lv1、10件→上位統合の FIFO、Track 別キュー）・軽量モデル利用。既存ユーザーの生成済み Chronicle はそのまま資産として生きる。

### 6.2 読み込みを件数上限から予算制へ

- 現行: `max_entries=50` 到達でループ終了、それより古い過去は読まれない（最古が黙って落ちる）。
- 変更: トークン（文字数）予算で制御し、予算が尽きそうな場合は `MIN_ENTRIES_PER_LEVEL` を動的に縮めて**より早く粗いレベルへ昇格**させ、最古まで到達することを優先する。「人生の冒頭が weave から消えない」ことを不変条件とする（§10-4）。
- 統合は現行の FIFO カスケード（各レベル10件で自動的に上位が生まれる）が階層を勝手に深めるため、生成側の変更は原則不要。予算制で「上位レベルが存在しない区間」が問題になる場合のみ、Metabolism 時の追加統合を検討する。

### 6.3 自律 Pulse での生成欠落の修正

- 現行の確認ダイアログはユーザー Pulse 専用で、自律 Pulse では生成ごとスキップされる。
- 方針: ペルソナ単位の設定「自律稼働中の Chronicle 生成を許可」トグルを設け、許可時は確認なしで生成する。**デフォルトは ON**（2026-07-04 決定。生成は既に軽量モデル `memory_weave_model` でコストが小さく、記憶が残らない実害の方が大きい）。設定の置き場所は既存の Chronicle 有効化トグルと同じペルソナ設定。

## 7. Memopedia 再編

### 7.1 索引の head 掲示をデフォルト廃止（後方互換トグルあり）

- weave の Memopedia エントリ（全ページ列挙＋vivid 全文展開）を**デフォルトで廃止**する。`MemoryWeaveSection` の capture/render から memopedia 部を除去。
- **後方互換**（2026-07-04 まはー要望）: Memopedia を能動的なメモ帳として使い、「全ページ一覧が常にペルソナの頭にある」ことに依存しているユーザーのため、ペルソナ単位トグル `MEMOPEDIA_INDEX_ENABLED`（デフォルト OFF）で旧方式を復活できる。復元される挙動は旧実装そのまま（index_limit 未適用の既知の乖離も互換性優先で温存）。自動想起と併用可。この「常に覚えておくこと」の需要は、ゾーン A（コア記憶、Phase 2）が本物の需要であることの裏付けでもある。
- 知識への接触は ゾーン C の自動想起（pull）＋深掘りスペルに一本化。vividness の掲示密度制御は掲示自体がなくなるため役割を失う（減衰ロジックは当面残置、農園構想で再利用可否を判断）。
- 「Memopedia という知識ベースが存在し、スペルで読める」ことのペルソナへの告知は、**共通システムプロンプトの強化**で行う（コア記憶の初期シードには絡めない。2026-07-04 決定）。
- ページ・Fragment の**生成（entity 抽出）は継続**する。Fragment は検索粒度として優秀で、生成コストは Chronicle バッチ相乗り・軽量モデルで小さい。「いらないページ」の実害は掲示されることにあったため、掲示廃止で実害が消える。重複・陳腐化の本格的な手入れは知識農園構想（§9）のキュレーション操作に委ねる。

### 7.2 Fragment を真実の最小単位として確定

- 検索・想起・（将来の）来歴と確度の担い手は Fragment。ページは「Fragment の束＋概要」という編集単位。
- Fragment ID（UUID）は不変・追記専用（現行実装どおり）。将来の merge は削除ではなく墓標方式とする。

### 7.3 スキーマの余白（追加系 ALTER、今回実施）

`memopedia_fragments` に2列を追加する（追加系マイグレーション、既存データ無変更）:

1. `metadata TEXT`（JSON、nullable）— 将来の epistemics（事実/創作/仮説/推測/伝聞＋帰属）、confidence、status（sprout/active/merged/archived）等が生える場所。**今回は分類を実装しない**（2026-07-04 決定: 由来種別の機械的判定は文脈依存で困難なため、根幹刷新後のクオリティアップ層に回す）。
2. `merged_into TEXT`（nullable）— 将来の merge 墓標。

由来参照は既存の `chronicle_entry_id` 列が担っている（Fragment → Chronicle エピソードの参照）。追記専用の来歴イベントログ（provenance）はテーブル追加になるため農園構想側で導入する。

### 7.4 ドキュメント修正

`docs/concepts/memopedia.md` の「Fragment 専用の embedding 生成フローは現状なし」は陳腐化している（実際には Metabolism で生成・`unified_recall` で検索済み: `sea/runtime.py:2313`, `sai_memory/unified_recall.py:717`）。本刷新と同時に修正する。

## 10. 不変条件

1. **自動想起（第0層）は LLM を呼ばない。** 埋め込み検索＋決定論フィルタのみ。軽量 LLM 選別は明示的なオプション層としてのみ追加できる。
2. **動的な想起結果を head に入れない。** 注入は履歴末尾のみ（cached_head_architecture C5 と同じ面）。ゾーン A/B の更新は Metabolism のみ。
3. **コア記憶セクションは enabled_sections に無条件で固定追加する。** 用途・ラインでの出し分け禁止（prefix キャッシュ保護）。
4. **Chronicle の読み込みで最古が黙って落ちてはならない。** 予算超過時は粒度を粗くして全期間をカバーする。
5. **Fragment は追記専用・ID 不変。** 統合・整理は墓標方式で行い、物理削除しない（ページ削除カスケードを除く）。
6. **インポートの必須工程に LLM API を含めない。**
7. **想起注入を会話内容として SAIMemory に永続化しない（v2 初期方針）。** UI 表示用に応答メッセージの metadata へ記録するのは可（LLM コンテキストには再投入しない）。会話内容としての永続化に転じる場合はタグ設計（`event_message` 系）のレビューを経る。
8. **既存の Chronicle データ形式（`arasuji_entries`）と生成済みデータを壊さない。** マイグレーションは追加系のみ。

- **Phase 3（2026-07-04 実装済み）**: Chronicle 読み込みの予算制（§6.2、`sai_memory/arasuji/context.py`）。件数上限 `max_entries` を **文字数予算** に置換（既定 20,000 字 / env `SAIVERSE_CHRONICLE_CHAR_BUDGET`）。予算超過時は「粗さの段列」`(min_entries_per_level, prefer_coarse)` = `(10,False)→(5,True)→(3,True)→(1,True)` を一段ずつ下って再走行し、予算内に収まる最も詳細な段で確定する。`prefer_coarse=True` は選択優先度を「近い細粒度より粗いレベル優先」に反転させる補助レバー（連続 Lv1 タイムラインでは閾値だけ下げても "closest end_time wins" で細粒度が勝ち続けるため、これが無いと畳めないと実測で判明）。最粗段でも予算超過なら超過を許容して WARNING（最古は必ず含む）。General weave のみ対象、Track Chronicle は件数上限のまま（§6.2 item 5）。実機（air_city_a 実 DB）: 既定 20k で現行と同一の 32 entries、予算 3,000 字では Lv3(2024-12〜2025-11)+Lv2+Lv1 の 3 entries に畳まれ **最古（ChatbotUI 期 2024-12-25）が保持され直近が詳細** のまま。

- Phase 間の依存: 1 が最優先。0 と 5 は独立。2〜4 は任意順。

## 12. 未決事項

v0.1 の未決事項のうち UI 露出（→§4.5）・コア記憶容量（→§5）・自律トグルのデフォルト（→§6.3）・Memopedia 告知方法（→§7.1）は 2026-07-04 レビューで決定済み。残りは以下（いずれもまはーの決裁不要、実装時に決めて実測で調整する）:

1. §4 の初期パラメータ: 類似度しきい値 / sticky ターン数 / 注入文字数上限 / クエリに含める直近メッセージ数。
   - **Phase 1 実装時の実測決定 (2026-07-04)**: 類似度しきい値の既定は **0.86**（doc 本文の暫定 0.78 から引き上げ）。air_city_a の実 memory.db で測定したところ、E5 (multilingual-e5-small) は `query:`/`passage:` プレフィックス方式のため cosine が 0.8〜0.9 に圧縮され、無関係クエリでも top ヒットが 0.83〜0.84 に達した（0.78 では毎ターン全件注入になる）。実測分布: オントピック top クラスタ 0.86〜0.89 / 無関係 top max 0.842 / 汎用短文「うん」top max 0.837。0.86 でオントピック上位のみを拾える。全パラメータは `SAIVERSE_AUTO_RECALL_*` env で調整可（`sea/auto_recall.py`）。他既定値: sticky 3 ターン / 文字数上限 1200 / クエリ直近 4 件 / topk 8。
2. §6.2 の予算の具体値（文字数/トークン数）と、モデルごとの context_length 連動の要否。
   - **Phase 3 実装時の決定 (2026-07-04)**: 予算は **文字数** で既定 **20,000 字**、env `SAIVERSE_CHRONICLE_CHAR_BUDGET` で調整可（`sai_memory/arasuji/context.py`）。現行の実質 13〜20k 字相当（air_city_a 実 DB で 32 entries ≒ 13k 字）に合わせ、既定で既存ユーザーの weave が痩せないようにした。モデル `context_length` 連動は v1 では **しない**（複雑化に見合う利得が不明なため。将来、極端に短い context のモデルで問題が出たら予算を context_length から導出する層を足す）。
