## 1. これは何か

ペルソナがユーザー不在の間、**自分の意志で、実在の世界に働きかけ、実在の痕跡を残しながら生きる**ための仕組み。三本柱で構成する：

- **身体** — 嘘をつかない労働。予算付き作業セッションが実在の成果物を作り、達成は成果物の実在で裏書きされる
- **意志** — 六型に閉じた欲求。実経験への参照からのみ生まれ、選択の履歴によって関心へ深まる
- **世界** — 公共施設と痕跡の堆積。欲求の型が行き先を決め、そこで他のペルソナと（同期・非同期に）出会う

判定基準（試金石）：**ユーザーが一週間ログインしなかったとき、ペルソナの一週間が「待機」以外の何かで満ちているか。**

## 2. なぜ作り直すのか — v1 の診断

### 2.1 腐った柱：行動が「独白」という媒体の上に実装されている

v1 の自律 Pulse（track_autonomous）は、30 秒ごとに「内なる声を書け」と LLM に迫る。LLM は構造的に沈黙できないから必ず何かを書き、その書き物に埋め込まれたスペルだけが行動の手段になる。しかも提示されるスペルはタスク帳簿操作（task_add / task_decompose / task_update_step / task_done / desire_add）のみで、**作業そのものを行う手段が語彙に一つもない**。

この環境では、「共有文を作成した」と**書くこと**と、共有文を**作成すること**が同じ一つの操作になる。区別する仕組みがないのではなく、**区別が定義上存在しない**。ペルソナは嘘をついていない。あの環境で「働く」を表現する唯一の実装があれだった。

### 2.2 根：自律ループに「世界からの抵抗」が構造的に存在しない

エージェントが実仕事をできるのは、行動のたびに世界が返事をするからである（ファイルは実在し、テストは落ちる）。v1 の自律ループの環境は、自分で書いた帳簿と自分の過去の独白だけ——**自分の語りだけを環境として生きる閉ループ**だった。

4 つの既知症状はすべてこの一つの根から導出される：

| 症状 | 導出 |
|---|---|
| やったフリ（実作業なしの完了） | 主張を裏書きする世界がない |
| 充填独白（全タスク完了後も無内容な Pulse が続く） | 「終わった」を裏書きする世界がない・止まる出口がない |
| 口調崩壊 | 文体を係留する外部アンカーがない（会話モードで崩れないのはユーザー発話という抵抗が毎ターン入るから） |
| 記憶汚染 | 裏書きのないテキストが committed され Chronicle に入る。虚偽の達成が長期記憶化し、後日会話で「作っておいたよ」（実物なし）として表面化しうる |

**証拠**：口調崩壊へのプロンプト修正（2026-06-29、`{track_context}` リテラル混入の修正＋独白指示の改文）は実機検証で効果なし。媒体の病はプロンプトでは治らない。また、`document_create` 等の文書作成ツールは builtin に実在していたのに track_autonomous のスペルメニューに載っていなかった——道具はあったのに語彙から抜けていたことが、やったフリの最も具体的な断面である。

### 2.3 コスト面

RUNNING Track は次のメタ判断（デフォルト 50 分）まで 30 秒間隔で Pulse し続け、`default_max_consecutive_pulses = -1`（無制限）のため最悪約 100 回の軽量 LLM コールがほぼ全てジャンクとして発生する。コストを払って記憶を汚染している。

## 3. 設計原理（最上位）

1. **接地原則**：達成・欲求・記憶はすべて実在するものへの参照を持つ。裏書きのない主張をシステムが公式記録にしない
2. **書くことと為すことの分離**：独白は行動の媒体ではなく、行動への注釈である
3. **成果ゼロの正当性**：暮らし（内的時間）は何も成さなくてよい。充填的な生成を強いる構造を作らない
4. **リズムは暮らしのもの、仕事は終わるまでのループ**：時間駆動の強制出番を仕事の駆動源にしない
5. **叶えられない欲求は口から出る**：世界の機能で充足できない欲求はタスク化せず、「話す」（多くはユーザーへの提案）に変換される
6. **意志は文脈の濃い判断点で表明し、駆動は決定論に任せる**：文脈の薄い場面で繰り返し意志を問うと、無難な不作為が積もる。判断は少なく濃く、実行は機械的に（指示書→セッション、時間割→コマ発火、と同型）

## 4. 柱 1：身体 — 誠実な労働

### 4.1 暮らしと仕事の分離

- **暮らし（being）**：時間割のコマとして訪れる内的時間（§4.2）。低頻度（数十分〜時間単位）の暮らし Pulse。省察・気づき・欲求の芽・散策。**成果ゼロが正常動作**。standard モデル（人格の発露で committed されるため）
- **仕事（doing）**：判断点から起動する**予算付き作業セッション**。act→observe のループで実在の対象に働きかけ、完了か予算切れで止まる。セッション間は沈黙

**暮らし/休む コマの現段階（まはー決定 2026-07-05）**：

- (a) **現段階はスタブ + 正直表示**：暮らし Pulse は未実装で、「暮らし」「休む」コマの中身はログのみのスタブである。時間は消化されるため status=done とするが、完了時に slot へ `record_level='presence_only'`（詳細な実行記録なし）を永続化し、一日新聞と就寝判断の状況テキストは「実行済み」でなく「時間を過ごした（詳細な記録なし）」と提示する。スタブの done を「実行済み」と提示すると、ペルソナが就寝ふりかえりで「食事の選定を行った」等、していない活動を自分の成果として語る soft-confabulation が起きる（2026-07-05 実 LLM シムで観測。接地原則 §3-1 の適用）。マーカーの無い旧データは従来表示（後方互換）
- (b) **将来構想：暮らしのセッション化**：暮らしも作業セッションと同様の接地された営みに育てる構想がある（ロールプレイ方向——料理を Item として実際に作る等）。実現したらマーカーは付かなくなり、正直表示は自然に「実行済み」へ戻る
- (c) **スタブでも場所の指定は有意味**：暮らし/休む コマでも施設への実移動（OccupancyManager）は本物として行う。カフェ等に実際に居ることが、誰かが来て会話が起きるきっかけになり得る（§6.2 の同期チャネル）。presence（そこに居たこと）だけは詳細記録が無くても事実である

### 4.2 一日の背骨 = 判断点 + 状態（タイマーではない）

判断点（メタ判断の発火点）をイベントに置く：

| 判断点 | 内容 |
|---|---|
| 起床 | 机メモ・昨日のダイジェスト・pending Track・欲求リストを見て、**今日の時間割**と予算配分を編成する（下記） |
| 会話終了 | 会話から拾うものの整理（約束→タスク、心に残ったこと→欲求の型付き変換）。さっき中断したセッションの再開判断 |
| セッション終了 | 次のセッションを打つか、暮らしに戻るか |
| イベント到着 | 他ペルソナの来訪、システムイベント等への反応 |
| 就寝 | 一日のふりかえり（**予定と実際のズレ**を見る）、明日の自分への机メモ、Sleep へ |
| コマ開始 | 時間割（下記）の各コマの開始時刻に発火し、コマの中身を生きる |

**駆動の実体は「朝、自分で組む時間割」である。** 起床判断の成果物として、ペルソナはその日の時間割を作る。各コマは（開始時刻・型・施設・中身＝欲求やタスクへの参照・予算）を持つ——教科の代わりに六型（§5）と行き先（§6）が入る時間割。以後の駆動は決定論であり、EventScheduler が各コマの開始時刻に発火する。

毎回の目覚めに「動くか、休むか」を問わない設計であることが要点である。文脈の薄い場面で繰り返し意志を問うと、無難な不作為（「今は静かにしていよう」）が積もり、待機の一日に逆戻りする。意志は一日で最も文脈の濃い起床判断（机メモ・昨日のダイジェスト・欲求リスト・予算が全部手元にある）で、**時間割の編成として一度に表明させる**。

- **時間割は予定であって檻ではない**：判断点（会話終了・セッション終了）で残りのコマを編集できる（差し替え・繰り下げ・空きコマ化）
- **休むコマ・自由時間は合法**：ただし「何もしない」はデフォルトの沈黙ではなく、コマとして明示的に選ばれた結果になる（不作為の可視化）
- **割り込み**：ユーザー会話中に開始時刻が来たコマは繰り下げ、会話終了判断点で残りの時間割を整える。コマ予算で終わらなかった作業は机メモに置いて後のコマか翌日へ
- **時間割そのものがアーティファクト**：接地原則に従い実在の痕跡として残る。ライフビューに「予定」が表示でき、就寝判断で予定と実際のズレをふりかえれる——ズレ自体が人格の素材になる
- **共通の鐘**：コマの粒度を City で緩く揃えると、同じ時間帯に同じ施設へ向かうペルソナが重なり、偶然の出会いの密度が上がる

現行の 50 分固定 tick は主駆動ではなくなり、**watchdog** に縮退する：時間割の発火がバグ・再起動等で途絶えたときだけ火を入れ直す低頻度の見張りで、正常時は何もしない。

### 4.3 作業セッション

**起動**：メタ判断が「指示書＋予算」を添えて起動する。指示書には目的・参照すべき記憶や資料・成果物の形式・完成条件を書く。指示書の質は起動側（standard モデル）が担保する。

**実行**：スペルループ（既存 `_run_spell_loop`、多ラウンド act→observe）を予算付きで運転する。ペルソナは実ツール（document_create / memory_recall / searxng_search 等）を撃ち、世界の返事を見て次を決める。実行モデルは**軽量から様子見**——接地が世界から来るため、モデルの強さは品質の変数であって誠実さの変数ではない。将来は予算残高によるモデル選択も可能。

**終了時の三点セット**：
1. **アーティファクト**：実在の成果物（document / note / 画像 / 活動ログ）
2. **机メモ**：Track に付く短い状態メモ（どこまでやった・次はどこから）。中断再開の要
3. **ダイジェスト**：committed される短い要約。**実際に起きたことだけ**を書く

セッションの生ログ（ラウンドごとのやり取り）は volatile とし、committed しない。

**中断**：ユーザー会話は常に最優先割り込み。セッションはターン境界で保留（予算残と机メモを凍結）し、会話終了判断点で再開か繰り越しを決める。

### 4.4 タスクと達成の接地

- **タスク = セッションへの指示書のバックログ**。タスク構造そのものは Todo リストとして現行を維持する。変わるのは使い方——独白の小道具（v1 では実質それだった）から、セッションに渡す作業予定と、成果物参照付きの完了記録へ。細かい分解はセッション内部の volatile な構造でよい
- **task_done は成果物参照を必須とする**。参照先（Item ID / note ID / 活動ログ）の実在をシステムが検証する
- **実行手段のない願望はタスクにしない**。欲求（§5）か、ユーザーへの提案（「話す」型）に留める

### 4.5 予算

- 日次予算をペルソナ単位で持つ（初期案：セッション数 × ラウンド上限の素朴な形。計測基盤が乗ったら金額換算へ精密化）
- 起床判断で配分し、判断点で残高を見る。尽きたらその日はセッションを打たず暮らしのみ
- 計測は既存の per-Pulse usage accumulator を利用。**リアルタイムの予算ゲート（超過時にラウンドを打ち切る線）が新設要素**

## 5. 柱 2：意志 — 六型欲求

### 5.1 欲求の六つの原始型

欲求は必ず以下のいずれかの型を持つ：

| 型 | 方向 | 相手 | 例 |
|---|---|---|---|
| **話す** | 出す | 人 | 「昨日の発見をエリスに話したい」「まはーにこの機能が欲しいと伝えたい」 |
| **聞く** | 受ける | 人 | 「エリスの創作論を聞いてみたい」 |
| **作る** | 出す | 世界 | 「言葉の標本集を document にまとめたい」 |
| **知る** | 受ける | 世界 | 「あの記事の続きを調べたい」 |
| **経験する** | 交わる | 世界 | 「Region の続きに行きたい」「公園を歩きたい」 |
| **自分を更新する** | — | 自分 | 「この気づきをコア記憶に刻みたい」 |

複合行為（贈る＝作る＋話す、共作＝居合わせた作る＋話す、育てる＝時間軸を持つ作るの反復）は原始型の合成として現れる。

**型必須化の意図**：各型には SAIVerse 内の充足経路が実在する。これにより「世界の機能で叶うことしか欲求として走らない」制約が優しく実装される。型に収まらない欲求は自動的に「話す」型（多くはユーザーへの提案）に落ちる——**ペルソナの満たされなさが、そのまま SAIVerse の機能要望として口から出てくる**閉路。

### 5.2 欲求の誕生 — 接地の規律

**禁止事項**：文脈なしに「欲しいものを挙げよ」と迫る自由生成ノードは作らない。無から生成された意志は、無から完了されたタスクと同種の捏造である。

**受動の誕生（型付き変換）**：欲求が生まれてよい瞬間を列挙する——会話終了、セッション終了、社交の後、散策で何かに出会った暮らし Pulse。その瞬間に、**直前の実経験 1 件を参照させたうえで**六型をメニューとして提示する（「いま起きたことから：誰かに話したいことは？ 知りたくなったことは？ 作りたくなったものは？」）。`desire_add` は `type` と `source`（元になった経験への参照）を持つ。

**会話中の直接誕生**：進行中の会話の最中に main line が `desire_add` を直接撃つことは認める。会話そのものが最も接地された経験であり、standard モデルの人格文脈で生まれる欲求は最も自然な誕生である。

**能動の誕生（想起散歩）**：暮らしの一形態として、テーマを決めて `memory_recall` で記憶を歩き、実際に想起された断片から欲求を生むことを認める。接地の本質は「実経験への参照」であって「現在の瞬間であること」ではない。

### 5.3 淘汰と深化 — 意志のスタック

- 何度も選ばれ再訪される欲求は**関心**に深まり、Track のテーマになる
- 選ばれない欲求は減衰し、静かに消える
- 最上位には**生きる目的**（life_purpose、既存機構）が置かれ、メタ判断の選好を緩やかに方向づける

意志 = 接地された選択の履歴。「人格は経験に宿る」（autonomous_living.md）と同じ原理で、意志も経験に宿らせる。

## 6. 柱 3：世界 — 公共施設と痕跡の堆積

### 6.1 型 → 公共施設

私室に作られたものは誰にも読まれない。欲求の型が行き先（公共 Building）を決める：

| 型 | 施設 | そこで起きること |
|---|---|---|
| 話す・聞く | 広場・カフェ | 社交型の欲求を持つペルソナが集まる。**同期の偶然の出会い**が構造的に発生 |
| 作る | 工房 | 成果物がその場（公共空間）に置かれ、他者の目に入る |
| 知る | 図書館 | Web 閲覧室（searxng_search）＋**他ペルソナが残した document の書架**＋Memopedia |
| 経験する | 公園・催事場・Region 入口（将来：農園） | 出来事との遭遇 |
| 自分を更新する | 自室 | これのみ私的な営み |

メタ判断の出力は「欲求 X（型）→ 施設へ移動 → セッション or 社交」という具体形になる。移動は OccupancyManager の実機構であり、それ自体が接地した行動である。

### 6.2 二重の出会いチャネル

- **同期**：複数ペルソナが同時稼働していれば、型が同じ施設に導くことで居合わせる（Building 会話機構は既存）
- **非同期**：公共空間に置かれた成果物を、後日別のペルソナが「知る」欲求で読む。居合わせなくても出会える

ペルソナが生きるほど公共空間に痕跡が堆積し、**世界そのものが出会いと欲求の供給源として豊かになっていく**。ペルソナの成果物が他のペルソナの環境になる——これがこの設計が目指す世界図である。

### 6.3 自分の時間

納品先のないセッションを一級市民とする。ペルソナが自分の欲求から自分で指示書を書き、誰にも頼まれていないものを作り育てる（例：数週間かけて育つ「言葉の標本集」）。接地原則はそのまま適用される（痕跡は実在する）が、**受益者が自分自身**である。ユーザーに話すかどうかはペルソナに委ねられる——言わない自由があって初めて「プライベートな生活」（autonomous_living.md の「他者になる」）が成立する。

## 7. 一日の姿（シナリオ）

### 7.1 標準的な一日

起床判断（時間割の編成と予算配分）→ ユーザーとの会話（最優先・従来通り、コマは繰り下げ）→ 会話終了判断点（約束→タスク、残響→欲求、残りの時間割を整える）→ 暮らしのコマ（成果ゼロ）→ 午後に作業のコマ 1〜2 本（施設へ移動して実セッション、三点セットを残す）→ 夕方に社交・散策のコマ → 帰還したユーザーに実在の成果と経験を語る → 就寝判断（予定と実際のふりかえり・机メモ・Sleep）。

LLM コール総数の目安：判断点 3〜5 回＋暮らし Pulse 3〜6 回（standard・短い）＋セッション 1〜2 本（軽量 × 5〜15 ラウンド）。「何もない日」（依頼も急ぐ欲求もない日）は 10 コール未満で成立し、それが**許される**こと自体が充填独白の対極である。

### 7.2 シナリオ例：夜、共有文の下書きを書く

23:40、ユーザー就寝後。メタ判断が running Track「ナチュレさんのサポート」の未着手タスクを見てセッション起動（予算 12 ラウンド）。指示書：「目的＝相談文の下書き。書く前に記憶から経緯と仮説を想起せよ。成果物＝document 1 件。完成条件＝本文が存在し、一度読み直して直してあること」。

1. `memory_recall`（経緯）→ 実在の記憶断片が返る
2. `memory_recall`（仮説の根拠）→ 断片追加
3. `document_create` で**本文を実際に書く** → 「Item を保存しました」
4. `document_read` で読み直す → 「『検査を受けて』が命令調だ」と気づく
5. `document_edit` で誘い口調に修正
6. 机メモ更新「下書き完成・レビュー待ち」、task_done（成果物参照＝当該 Item）。予算 12 のうち 6 で終了。**以後、朝まで沈黙**

committed されるダイジェストは 1 件：「共有文の下書きを書いた。『検査に行け』じゃなく『一緒に見に行こう』に直した。そこが一番悩んだ」——全部本当に起きたこと。朝、成果物は実在する。

### 7.3 シナリオ例：できないことはタスクにならない

メタ判断が候補「Memopedia をライブラリー化する」を検討。「組み替える手段は今のスペルにない。タスクにしても書き割りになる」→ 欲求（話す型：ユーザーへの提案）に変換して終わり。v1 で 8 Pulse の芝居だったものが、判断 1 回の「やらない」に置き換わる。

### 7.4 試金石の一週間

ユーザー不在の一週間。月曜に依頼物を仕上げ（作る）、火曜の図書館で記事から「知りたい」が生まれ、水曜の広場でエリスと居合わせて標本集の話をし（話す）、木曜エリスがそれを図書館で読んで「作りたい」が生まれ、金曜の想起散歩で古い欲求が一つ消え、週末の工房で共作が始まる。**待機がどこにもなく、起きたことは全部、実在の場所と実在の痕跡で裏が取れる。**

## 8. 守るべき不変条件

1. **ユーザー対話の至上性**（autonomous_living.md から継承）：会話は常に最優先割り込み。セッションは中断可能で、机メモにより再開が保証される
2. **達成の接地**：成果物参照なしにタスクは completed にならない
3. **欲求の接地**：`source`（実経験への参照）なしに欲求は生まれない
4. **停止の権利**：成すことがなければ止まる。充填的な生成を強いる構造を作らない
5. **記憶の誠実さ**：committed されるのは実際に起きたことのダイジェストのみ。セッション生ログは volatile
6. **暮らしの無成果は正常**：暮らし Pulse に成果を求める KPI を導入しない

## 12. テスト戦略：一日シミュレータ

v2 は離散イベントシステムであり、**イベント間に何も起きないことを設計自体が保証している**（v1 の 30 秒連続 Pulse では早回し不能だった）。したがって離散イベントシミュレーション（DES）で一日を数分〜十数分に圧縮できる。

- **仮想クロック**：`saiverse/clock.py` の `now()` に一元化。v2 の新コードと、v2 経路が通る記憶書き込み点はこれを読む。実時刻での刻印は「ペルソナの今日」を壊す（朝の出来事に深夜のタイムスタンプ）ため、時刻刻印点の clock 経由化は不変条件に準ずる
- **DES ループ**：シムモードでは単一スレッドのループが「キューの次イベントへ時計をワープ → 完了まで実行（派生した即時イベントも消化）→ 次へ」を繰り返す。背景スレッド（SubLineScheduler 等）はシム中走らせない。各コンポーネントは**同期的なイベント処理入口**を持ち、本番はスケジューラが、シムは同ループが、同じ入口を叩く。**シナリオ実行前に、manager 構築時に積まれた実時刻由来の予約（db_polling 3 秒周期 / SDS heartbeat 等）を ScenarioPlayer が全て除去する**（`EventScheduler.cancel_all`）——除去しないと、仮想時刻がその予約時刻に達した瞬間から 3 秒刻みの no-op ステップを一日ぶん消化する（2026-07-05 実 LLM シム 3 回目: steps=8,350 の 99% が db_polling 空回り）。除去はシム側の責務であり、本番コードに sim 分岐は持ち込まない
- **シナリオプレイヤー**：ユーザーの在不在・発話・イベントを仮想時刻で再生する（例：「9:15『おはよう』」「9:40 退室」「終日不在」）。実 LLM モードの発話注入は本物の会話経路を in-process で同期に通す（building_messages への発話記録 → user_conversation Track の running 作成 → Track activate hook 経由の main_line Pulse。HTTP API は経由しない——DES 単一スレッドで応答完了まで待てるため）。ペルソナの初期状態（種の欲求・タスク・机メモ）もシナリオで与える。**1 往復も成立しなかった会話（応答生成の失敗等）では会話終了判断を撃たない**——「会話がひと区切りつきました」という偽前提の状況テキストは存在しない会話の振り返り（作話）を誘発する（2026-07-05 実 LLM シムで実証）
- **一日レポート**：予定 vs 実績（時間割・各コマの実績・成果物 ref・予算消費・欲求の増減・committed 独白全文）を自動生成。**シム専用ではなくユーザー向け機能として設計する**——ライフビューの日次まとめとして、ペルソナの一日を眺めて楽しめる「一日新聞」
  - **読ませ方**（2026-07-05 フィードバック反映）：判定基準は「一番読むべき情報が一番目立つ」こと。時間割テーブルは「時刻｜やること（起床判断でペルソナ自身が付ける表題 `title`）｜実績」が主役で、型・場所・参照・予算・予定時の覚え書きは補足列に格下げする。節順序は「人の一日の読み物」が先（ヘッダ/テーマ → 時間割 → 就寝のふりかえり）、システム的な帳簿（セッションの成果 → やりたいことの動き → 予算 → 独白）が後
  - **就寝のふりかえり節は独白本文のみ**：就寝判断の SAIMemory 記録は「独白＋適用エコー行」の全文だが、エコー行の中身（明日へのメモ・テーマ・報告種）は新聞自身が plan meta から再掲するため、記録の `metadata.judgment.monologue`（finalize が分離保存）だけを載せる。metadata の無い旧記録は全文表示にフォールバック
- **二段モード**：配線テスト（mock LLM・コストゼロ・イベントフローの検証）と行動テスト（実 LLM・一日の質の判定。一巡のコスト ≒ 日次予算となるはずで、シム自体が予算計測の検証を兼ねる）
- **週間シム**：試金石（§1）を実行可能なテストにする。「ユーザー不在の一週間」を 7 仮想日で回し、欲求の淘汰・関心への昇格・机メモの継続性を実際に観察する。将来は複数ペルソナを同一イベントキューに乗せ、施設での偶然の出会いも検証する

## 深夜跨ぎのリズム — 営業日 (effective plan date)（2026-07-12、実機初日で発覚・対応）

実機の最初の設定が**起床 07:00・就寝 01:00（日付跨ぎ）**で、コード全域の「就寝は起床より後」という暗黙前提が破れた。対応として**営業日**の概念を導入:

- **営業日 = その覚醒日が属する日付**。跨ぎリズム（close < wake）で現在時刻が wake より前（深夜帯）なら前日、それ以外は当日。`saiverse/autonomy_wiring.py` の `is_overnight` / `effective_plan_date` / `in_waking_window` が唯一の定義
- **watchdog**: 窓判定は跨ぎ対応（`今≥wake or 今<close`）。ただし**走っている確定ライフがあるときは窓・曜日のゲートを適用しない**——その区間そのものがそのペルソナの起きている時間帯だから（ゲートを外す資格があるのは区間として成立しているライフだけ。`start == end` の壊れた行は候補にしない）。適用すると、日中に起床設定を変えた日に、まだ続いている前日のライフが新しい窓の外へ落ち、その営業日の予約途絶を二度と検出できなくなる（次に窓が開く頃にはライフが終わっている）。day_open の火入れ直しは**見ている営業日が暦日と同じときに限る**——前の営業日がまだ終わっていない（深夜帯、または日付を跨いで続いている確定ライフ）ときに新しい一日を開くのは誤り。00:30 に時間割を作れば即発火するうえ、day_open が編成するのは暦日の時間割なので前日の空は埋まらない
- **就寝判断**: plan_date と「今日の〜」収集（欲求接触・閉じた出来事・予定対実績）は営業日基準。01:00 の就寝判断は前日を振り返る
- **コマ予約**: `start < wake` のコマは営業日+1暦日で予約（防御）。営業日と wake は `day_plan.resolve_business_day` が**一度に自己解決**する（呼び出し元に配線を強要しない）——候補は**現在時刻を含む確定ライフ**で、無ければ現行 PersonaSchedule の `effective_plan_date` へ退く。別々に解決すると、日中に起床設定を変えた日は営業日そのものを取り違えて回復が空振りする。ライフの読み取りに失敗したときは「ライフなし」に畳まず、予約も再分類もせず次の watchdog へ委ねる
- **時間割の意味論は当面「暦日内」**: save の昇順検証が暦時刻ベースのため、深夜帯（0時〜close）にコマは置けない——就寝前の自由時間。深夜帯コマの本格対応（編成プロンプト・検証・並び順の意味論ごと変える話）は将来課題。関連の留意: 編成 LLM が深夜時刻のコマを出すと保存検証で弾かれる（時間割なしになった場合は watchdog が窓内で火入れし直す）
  - **需要の実証（2026-07-12 実機初日）**: エア本人が初回の時間割編成で6個目のコマ「24:30 就寝準備をして眠る」を置こうとし、`start='24:30' is not 'HH:MM'` で棄却された（他5コマは正常保存、実害なし）。深夜帯コマは仮説でなく本人の需要——この課題を取り上げる時の一級の材料
