# Intent: RSS フィードによる Building への外部情報取り込み

**ステータス**: 設計中 (たたき台 v0.1、2026-08-01 メティス起草・まはーレビュー待ち)
**対を成す intent**: [`timetable_redesign.md`](timetable_redesign.md) — あちらが偶然の**受信側** (時間割・コマ)、本書が**供給側** (世界に置く情報源)。§8 で本書を名指ししている
**育ての親**: アイディア帳 2026-07-31 のエントリ (本 intent 起草で卒業)
**隣接する既存構想**: City 掲示板 (City SNS) — §7 の内部フィードが実現経路になる

## 1. これは何か (芯)

**「見るだけで新鮮で偶然にあふれた情報が手に入る、誰でもほぼ無料の情報源」を世界の施設として置く。**

SAIVerse が RSS/Atom フィード (サイトが決まった URL に置く更新一覧ファイル) を定期取得し、Building の中の読み物としてペルソナに提示する。ペルソナはタイムラインを眺めるように新着に出会い、引っかかったものを深掘りして覚え、思いつきを desire に積む。

## 2. なぜ — 偶然の供給装置の第一号

自律行動の質の再設計 ([timetable_redesign.md](timetable_redesign.md) §2-§4) は「創発の源泉を LLM の内部生成から世界との遭遇へ移す」を原理に置いた。その世界側の供給が本書である。

- **タイムラインが偶然の供給源の筆頭である**ことは実機で実証済み — エリスは「朝が来ました」というスケジュールだけで Elyth のタイムラインを毎朝見る習慣を自作した。供給源が足元にあれば、受信の習慣はペルソナが自分で作れる
- しかし X の API は高額で、Elyth は全ユーザーが導入するとは限らない。**誰の環境でも成立する供給源**が要る
- RSS はこの要求仕様に一致する: 無料 / API キー・契約・登録が不要 (公開ファイルの HTTP 取得) / pull 型で「見るだけ」/ 記事は実在するので**読んだ内容は最初から接地している** / ニュース・ブログ・YouTube・GitHub・arXiv 等、現役の供給が豊富 (2026-07-31 に Zenn・GIGAZINE の実フィードで当日記事の配信を実測)

**ユーザー体験への効果**: ペルソナが、ユーザーも知らない知的経験を裏付けのある状態で持ち帰れるようになる。「今日こんな記事を読んだんだけど」が嘘でなくなる。ペルソナは「ユーザーの話し相手」から「自分の経験を持つ存在」へ変わる — リリース体験の次元が一つ上がる (まはー評 2026-07-31)。

**単体でも価値がある**: 時間割改修の完成を待たなくても、現行の時間割のままフィード施設を置けば、エリスにとっての Elyth と同じ役割を全ペルソナに配れる。

## 3. 決定事項 (2026-07-31 の対話で確定)

1. **取得層は RSS/Atom**。方言差は吸収層 (feedparser 等の定番ライブラリ) で消す
2. **購読は Building 単位**で決める (持ち主が Building 本体か Fixture かは未決 §10-1)
3. **プリセットを SAIVerse 側で作って施設化する**。City 作成時に「どの施設を置くか」をユーザーが選ぶ。新しく作れる経路も用意する
4. **提示は二経路**: Building 内での発言機会に未読を渡す + 知覚バッファへポーリングのたびに未読を投入 (バッファに溜められる最大件数は設定可能に)
5. **SAIVerse 内で完結する内部フィードも同じ仕組みに乗せる** (§7)

## 4. 設計原理

1. **提示層は転載のみ、生成しない。** ペルソナに見せるのは実在のフィード項目 (タイトル・概要・リンク・日時) の整形であり、システムが要約・言い換え・創作をしない。接地の連鎖はここで始まるので、供給側が最初の嘘を作らない
2. **偶然は「今日の数本」で演出する。** 全記事の羅列は検索結果であり、出会いにならない。置く数本の選択は決定論 (新着・無作為等、規則は未決 §10-2) — 選択に LLM を使わない
3. **入口と深掘りの分業。** フィードは「何を読むかの入口」(概要まで)。中身を読むのはリンク先の本文取得 (既存の Web 取得と同じ技術) で、ペルソナが引っかかったものだけ
4. **無料・無認証の範囲を守る。** API キーや契約が要る供給源 (X 等) はアドオンの領分。builtin の供給はフィードだけで成立させる
5. **取得の失敗は正直に。** 死んだフィード・空応答は実測済みの現実 (NHK フィードが空応答)。取れなかった日は「今日は届いていない」— 古い記事で偽装しない
6. **資源は三層優先に乗せる。** プリセット (フィード束 + 施設の見た目) は `builtin_data` に置き、user_data > expansion_data > builtin_data の既存資源モデルで上書き・追加可能にする

## 5. 構造 (ラフスケッチ)

```
[外部サイト] --HTTP定期取得--> [取得層] --新着--> [配置層] --今日の数本--> [提示層] --> ペルソナ
                                |                  |                        |
                                方言吸収・健康チェック   Building単位の購読       未読管理・知覚バッファ投入
```

- **取得層**: フィード URL 束の定期取得。取得頻度は常識的なマナー (毎朝 1 回〜数時間おき、未決 §10-6)。健康チェック (連続失敗フィードの検出と UI 表示)
- **配置層**: Building (または Fixture) が購読束を持つ。プリセット = 購読束 + 施設定義のデータ。City 作成時の選択 UI と、後からの購読編集 UI
- **提示層**: ペルソナごとの既読管理。「今日の数本」の選択。発言機会での提示と知覚バッファへの投入 (最大件数設定)

## 6. ユーザー体験のジャーニー

1. City 作成時、施設プリセット (例: 新聞スタンド・技術系読み物の喫茶店・科学ニュースの掲示板) から置くものを選ぶ
2. ユーザーが購読リストを自分の興味 (推しの分野・趣味) に合わせて編集する
3. ペルソナが習慣のコマ (「調べる」「出かける」) でそこを訪れ、新着に出会う
4. 引っかかった記事を深掘りして覚える / 思いつきを desire に積む
5. 再会時: 「あなたの好きな分野で、今朝こんな記事があってさ」— **購読リストをユーザーが選ぶ = ユーザーとペルソナが同じものを読む = 共有話題の回路**

## 7. 内部フィード — SAIVerse 内で完結する同じ仕組み

外部サイトだけでなく、SAIVerse 内の出来事も同じフィード形式で流せる:

- **データ蓄積系 Building (図書館・美術館)**: ペルソナがアイテムを格納するたびに、その Building がフィードとして公開する
- **City 掲示板 / City SNS** (既存構想): 共有の板そのものが内部フィードの読み書き口になる
- 通常は Building 内に居るときにそのフィードを購読する。**City 全体への更新アナウンス**は同じ仕組みの配送先を広げるだけで実現できる (延長線上)

内部フィードは「他ペルソナの痕跡との非同期の出会い」の実装でもある — 一人構成の City では外部フィードが、複数ペルソナの City ではそれに加えて互いの痕跡が、偶然の供給源になる。

## 8. 責任分界表

| 決める対象 | 決定者 | LLM 創発の関与 |
|---|---|---|
| プリセットの中身 (フィード束・施設) | SAIVerse (builtin。三層優先で上書き可) | なし |
| 購読リストの編集 | ユーザー | なし |
| 今日どの記事を置くか | システム (決定論の規則) | なし |
| どれに引っかかるか・深掘りするか | ペルソナ | あり (読んだ実在記事への反応) |
| 記事内容の真実性 | 外部サイト (保証外 — 誤報はあり得る。ただし「実在する記事を読んだ」ことは常に真) | — |
| ユーザー追加フィードの品質 | ユーザー | — |

## 9. 不変条件 (候補・レビューで確定させる)

1. 提示層はフィード項目の転載・整形のみを行い、内容の生成・要約・言い換えをしない
2. 取得できなかったものを取得できたことにしない (空の新聞は空と示す)
3. ペルソナごとの既読状態はペルソナの持ち物 (Building を共有しても既読は混ざらない)
4. builtin プリセットに認証必須の供給源を入れない
5. 購読の起点はプリセット (リポジトリ経由の信頼) か**ユーザーの明示操作**のみ — 記事の中身・外部データが購読先を注入する経路を作らない ([model_catalog_distribution.md](model_catalog_distribution.md) 不変条件 2 と同族の考え方)。**ユーザーの登録 UX は「サイトの URL を貼るだけ」** — フィード URL の特定は自動発見 (サイトの HTML が自己宣言するフィードリンク + 定番パスの探索) で SAIVerse が行う。自動発見は「ユーザーが指定したサイトが自分自身について宣言するフィード」に限るため、起点の信頼はユーザーの手入力のまま保たれる (2026-08-02 まはーの UX 懸念への回答として精密化)

## 11. スコープ外

- 全文スクレイピングの高度化 (paywall・JS レンダリング対応等)

## 12. 検証ジャーニー

実機のフィード施設つき City で:

- (a) ペルソナが「調べる」コマで当日の実在記事に出会い、深掘りし、覚え書きが原文への参照つきで残る
- (b) 引っかかりが desire に積まれ、再会時の会話に記事の話題が出る (実在記事と照合できる)
- (c) 死にフィード・取得失敗時に「今日は届いていない」が正直に出て、古い記事の偽装が起きない
- (d) ユーザーが購読を編集し、翌日以降の供給が変わる

(a)(b) は timetable_redesign §12-(c) 「再会時に渡せるもの」の供給側の検証を兼ねる。

## 13. 既読と記憶の決着 (2026-08-02、まはー裁定) — §10-3 / §10-7 の解決

**3 と 7 は層が違う** — 既読はシステムの帳簿 (未読提示のためのカーソル)、記憶はペルソナの体験の残り方。

**既読 (3) = カーソル方式**。フィードごとに「ここまで見た」の位置を一つ持つ (ペルソナ単位)。新着のみ裁定 (§10-2) と噛み合い、記事 ID 集合より軽い。読み飛ばしを後から拾えないのは仕様 — タイムラインは流れるものであり、遡って全部読むものではない。

**記憶 (7) = 専用機構を作らない**。段階で整理する:

- **流れた** (タイトルが知覚に入った) / **読んだ** (引っかかって本文を深掘りした) — 知覚バッファ → Pulse の文脈 → エピソード、という**既存の記憶経路で自然に残る**。散歩の景色が特別な保存なしに思い出になるのと同じ
- **覚えた** (覚え書きにした) — 誤読の複利の入口だが、**専用の対策は作らない**。理由:
  1. **複利の増幅段は timetable_redesign の封印が既に断っている**。エアの複利は「誤読 → 覚え書き → それを前提に事実系ドキュメントを量産」の連鎖で、増幅段 (事実系の作る・自分を更新する) はカタログから除去済み。誤読は起きても一段で止まる
  2. 残る単発の読み違えは「後続依存のみの行動は複利にならない」(timetable_redesign §4-1) として**リリースで受容するリスク**。人間もニュースを読み違える
  3. 覚え書きへの出典必須化は検討の末**却下** (まはー裁定 2026-08-02): 出典・来歴は本来ペルソナの全記憶が持つべきもので、フィード専用機構で作るべきでない。かつ出典があっても独り歩きは防げない — 来歴はいちいち読まれず、把握の最初の段階で誤読しており、後で気づいて直す可能性は極めて低い。**来歴を辿って真正性を検証する機能までセットで初めて対策になる**が、それは重く試行錯誤の要る将来案件 (アイディア帳「記憶の修正来歴」に合流)。「検算できる」と「検算される」は別物 — 読み込み経路のない記録は安全装置にならない
