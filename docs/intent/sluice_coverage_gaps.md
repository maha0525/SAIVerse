# スルースの被覆の穴 — 会話を止めない採取と、後から拾える記録

**ステータス**: 実装中 (2026-09-08 起草・文書レビュー 2 種反映・未決 4 点をまはーが裁可して確定。第一段を実装中)

**発端**: 稟乃さんの報告 (2026-09-07〜08)。v0.2 時代の記憶 DB を持つペルソナに話しかけると返事が一度も来ず、翌朝「APIの利用制限に達しました」が出た。診断で確定した実体は下の「出自」節。

用語 (この文書で使う既存語彙): **スルース** = 窓から押し出される会話を本人の目で
読み返し、コア記憶・手帳のメモ・約束を拾う処理。**パンマーカー** = スルースが
最後に見た位置の記録 (persona ごとに一つ)。**退場** = 窓の起点を前進させ、古い
会話を提示から外すこと (行は消えない。起点は model ごと)。**読み戻し** = 窓の
会話が「残す量」を下回ったとき、起点より古い会話を読み足す処理。**非常畳み** =
話しかけた時点で窓が高水位を超えていたときの、応答より前の回復措置。

## 原則 (chronicle_coverage_gaps と同じ芯)

**保証できない品質は、確定を装わない。装えない部分はユーザーに返す。**

これまでの設計は「全ての経験は退場の前に必ず一度、本人の目を通る」を、退場を
止めることで守ってきた (v3 §13.3「確実に通るゲート」)。この保証は温かい定常運転
では安く守れるが、冷たい大量読み (アップデート直後・インポート直後) では守る
費用が「会話が一度も成立しない」に化けた。スルースを通っていない記憶が一部ある
ことで人格は崩れない — Chronicle の穴と同じで、できるだけ防ぎたいものではあるが、
普通の会話を妨げてまで守るのは本末転倒である (2026-09-08 まはー、下の「決定」に
原文)。

## 出自 (実例 — 稟乃さんの実機。証拠: `D:\Download\rate_diag_20260908_201055.txt`、まはーの手元)

- ペルソナ BerrienCliane_city_a、モデル gpt-5.1-instant (OpenAI)。v0.2 時代の
  記憶 DB を v0.3.10 へ更新した直後。Chronicle は 2026-03-30 で止まっており、
  それ以降の 3,744 通が未編纂・スルース未通過。
- 起動直後の読み戻しで **2,128,052 字** (v0.2 時代の履歴ほぼ全部) が窓に開かれた。
  これは 2026-09-05 の決定どおりの動き (arasuji_levels §15-5: 開いた結果が上限を
  超えていても保ち、WARNING のみ — 「記憶を開き直さないくらいなら超過を受け
  入れる」)。ログの「次の非常畳みが整理する前提で開いたままにする」はその決定の
  文面で、今回の実例は**その前提の整理 (非常畳み) が下で潰れる**ことを示した。
- 話しかけると非常畳みが始まり、スルースの LLM 呼び出しにその窓全体が**一度に**
  載る形になった。OpenAI は 1 分あたりのトークン上限超過として 429 を返したが、
  その本文 "Request too large …" が、コンテキスト超過判定の文字列一覧
  (`sea/sluice.py` `_CONTEXT_OVERFLOW_MARKERS` の `"request too large"`) に一致
  したため、**レート制限が「入りきらない」と誤分類され**、§13.5-1 の後退方式
  「直近の 1〜2 通を外して再試行」が繰り返された。212 万字に対して 2 通ずつ
  なので実質終わらない。1 周約 21 秒、**夜通しで 429 が 14,475 回**。返事は一度も
  生成されず、朝の発話が受けた 429 だけが「APIの利用制限に達しました」として
  画面に出た (スルースの失敗は画面に出ない)。
- 費用は発生していない見込み (429 で拒否されたリクエストは処理前に弾かれる。
  残高が減っていない報告と一致)。

## 決定 (2026-09-08 まはー — 原文つき)

1. **スルースを通っていない記憶があっても人格は崩れない。** 原文: 「一部分
   スルース通ってないところがあったとして、それで人格が崩れるわけないでしょ？
   これも Chronicle の穴とかと同じでさ、できるだけ防ぎたいものだけど、普通の
   会話を妨げるようなことして守るのは本末転倒なんだよ」。
2. **冷たいときのスルースは走らせないのが既定。通っていない範囲は後から通せる
   ようにする。** 原文: 「もう思い切ってキャッシュ冷えてる時のスルースはやらない
   をデフォルトにして、スルース通ってない範囲に関しては後から通せる仕組みを
   作る、で対応すべきなんじゃない？　それが一番透明性高いと思う」。
3. **後から通す操作は明示の操作なので、使用モデルや文脈の組み方が通常の会話と
   違ってよい。** 原文: 「後から手動で通すんだったら使用モデルとかコンテキストの
   構築方法が違っても割と自然ではあるし」。
4. **スルースという仕組みが生まれる前の時代の記憶に、遡ってスルースを義務づけ
   ない。** 原文: 「スルースが無い時代の記憶を必ずスルース通さないといけない、
   って謎の思想なんだよ」。
5. (前提の確認として) スルースの本来の姿は発言直後の温かいキャッシュに相乗りする
   軽い処理であり、冷たい大量読みは次善の策 — 原文: 「そもそも理想は発言後の
   キャッシュ暖かい状態で呼ぶべきもののはずなのね。…今走ってるその処理は次善の
   策だという認識」。

この決定から導かれる実装上の操作のうち、過去の決定を反転するものは起草レビューで
「未決」として分離し、同日中にまはーが個別に裁可した — 下の「追加の決定」節。

## 全体の見立て (whole-system)

- **書き換わる約束**: v3 §13.3 の「全ての経験は退場の前に必ず一度、本人の目を
  通る」は、「**温かい定常運転では従来どおり相乗いで通す (既定)。冷たいときは
  通さずに退場し、通っていない範囲を記録として残し、ユーザーはいつでも後から
  通せる**」に改まる。生ログと想起は退場後も残るので、これは忘却ではない —
  採取 (コア記憶・手帳・約束) の時期が本人の自動処理からユーザーの意思へ移る
  だけ。
- **誰が何に頼れるか**: ユーザーは「話しかければ必ず会話が成立する」ことと
  「採取が済んでいない範囲を見て、選んで実行できる」ことに頼れる。ペルソナは
  定常運転の採取 (従来どおり) に頼れる。機構は「巨大な窓が来ても詰まらない」
  ことに頼れる。
- **通っていない範囲は、飛ばした瞬間に明示の記録として残す**: 当初案の
  「パンマーカーと起点の差から導出する」は成立しない — パンマーカーは persona に
  一つで起点は model ごとなので差が一意に決まらず、さらに飛ばした後に最初の
  温かいスルースが成功するとマーカーが窓の末尾へ進み、飛ばした範囲の左端が
  消える (整合性レビュー c-2・c-3)。だから第一段から、飛ばすたびに範囲
  (開始・終了のメッセージ ID と日時) を memory.db に一行書く。第二段の期間選択
  もこの記録を読む。
- **帰結**: 冷たい復帰の直後、ペルソナは「最近の窓 + Chronicle の物語」で喋り、
  その間の採取は済んでいない。会話の品質への影響は Chronicle の穴と同種の近似で、
  残余リスクは観測で追う。

## 第一段 (稟乃さんの救出 — v0.3.11 に同梱)

### A. 冷たいときはスルースを飛ばす

run_metabolism のスルース実行を**量**の条件つきにする: **担当範囲 (パンマーカー
からいま話している窓の末尾まで) の字数が、一発のスルースの呼び出しに入る量の
ときだけ走らせる**。入らない量のときは走らせず、飛ばした範囲を記録して
(全体の見立て参照)、退場はそのまま進める。ログと context-status にも残す。

- 判定は位置 (マーカーが窓の中に居るか) ではなく量で引く — 位置で引くと、
  一度飛ばした後にマーカーが永久に窓の外となり、スルースが二度と走らなくなる
  (整合性レビュー c-1)。飛ばした後の温かい回は、現行コードの規則どおり
  「マーカーが窓に無ければ窓全体が担当範囲」で普通に走る — 窓は普通の大きさ
  なので量の条件を満たす。
- 閾値は「§13.5-1 の後退方式が要らない量」— 入りきらない事態を復旧するのでは
  なく、入りきる回だけ走らせる。具体値はモデルのコンテキスト長から導く
  (実装時に確定)。
- v3 §13.5-1 の後退方式 (直近の組を外して再試行) は**廃止**。「1 組だけはみ
  出した」ための設計で、30 倍の超過には無力なまま 429 の連打だけを生んだ
  (出自)。あわせて `_CONTEXT_OVERFLOW_MARKERS` の `"request too large"` を外し、
  レート制限をコンテキスト超過と誤分類する経路を塞ぐ (出自の近因)。
- **起点前進のパンマーカー頭打ちは撤去する** (追加の決定 1 で裁可済み)。撤去は設計書 3 箇所
  (arasuji_levels §14-2 の見出しつき不変条件・concepts/metabolism.md・
  gold_panning.md) と回帰テスト 3 本 (`tests/test_session_anchor_rows.py` の
  頭打ち系) の改訂を伴う — 文書だけでなくテストが旧仕様を固定している。

### B. 通っていない範囲を後から通す — 判断の主体 (2026-09-08 夜、まはーと再設計)

最初の実装 (コミット 3bfd0919) は「本人のシステムプロンプトだけ着せた器」に過去を
読ませており、まはーのレビューで棄却された — **当時の本人でも今の本人でもない、
第三の主体をでっち上げて「本人の目」と呼んでいた** (「そもそもそれだけでペルソナの
人格そのままの判断ができると思ってるのがダメ」「過去なのに現在の情報を込みで判断
させるのはおかしい」)。判断の主体の候補は三つあり (まはー整理)、次のとおり決めた:

1. **機構** — 誰でもない機構がその範囲だけを見て抽出する。Chronicle の生成と同じ型
   で、最も簡素で安い。本人の会話ログには何も載らない。**採用** — ただし機構は
   コア記憶・手帳へ代筆できない (本人の言葉の器) ので、出力は**候補**止まり:
   「機構が拾った候補」の印付きで置き、本人かユーザーが後から採用する
   (chronicle_coverage_gaps 第二段の「仮の印と事後承認」と同じ形)。
2. **過去の本人** — その時点以降の情報を全て捨て、当時のコンテキスト (手帳・
   Chronicle・コア記憶をその時点以前だけにフィルタ) を再構成して問う。この世界の
   存在論では当時の本人そのものに最も近いが、**コア記憶は上書きで育つ器で当時の
   状態が残っておらず、今日の道具立てでは建たない**。記録の置き場の問題もある。
   **将来の扉として書き残す** (コア記憶に履歴が付いたら開く)。
3. **現在の本人** — いまの本人に、読み返しだと明示して対象の会話を渡し、判断して
   もらう。人間が昔の日記を読み返すのと同じで、主体が「読み返している現在の自分」
   だと明確なら現在の知識で読むのは正しく、古い状態を現在として書き込む事故も
   主体が現在を知っているから起きない。**採用** — 記録の肥大は既存の作業セッション
   の型で解く: 読み返しは脇のセッションで行い、本人の会話の本線にはダイジェスト
   一行だけが立つ (長期記憶への入口は一本、の規則どおり)。

第二段の期間選択 UI は、この二つ (機構に候補を拾わせる / 本人に読んでもらう) を
**ユーザーの選択肢として並べる**。どの期間が本人にとって大事かはユーザーが知って
いるから、選ぶ権利ごと渡す。

### B-2. 拾われた記録の時刻と由来 (2026-09-08 まはー)

どちらの主体で拾っても、書き込まれた記録は次を満たす:

- **二つの時刻を持つ**: 作成日時 (いつ書かれたか) と、**できごとの日時** (採取元の
  会話の時刻 — 本人に申告させず、範囲のメッセージから機械が刻印する。範囲 ID の
  刻印と同じ原理)。
- **普段の提示とソートはできごとの日時**。一括の読み返しで当日作の記録が大量に
  生まれても、過去由来の記録は時間軸の本来の場所に並び、**現在の手帳の内容が
  過去からの想起で押し流されない** (まはー: 「作成日時とは別に採取元になった
  できごとの日時をタイムスタンプとして持っておいて、普段はそいつでソートしとく
  必要が有る」)。
- **由来の印**を持ち、後から読んだ時に過去の経験由来だと把握できる (機構の候補
  なら機構の印、本人の読み返しなら読み返しの印)。
- 手帳のスキーマは v3 §13.6 (まはー承認の正典) なので、時刻と由来の欄の追加は
  §13.6 の改訂と同じコミットで行う。

### C. 安全装置 (決定と独立に、どの経路にも)

1. **レート制限の連続失敗で走行を止め、ペルソナ単位で小休止を置く**: 同じ走行の
   中で 429 起因の失敗が続いたら (OpenAI クライアントの再試行一巡 = 3 回で尽きた
   時点)、その走行を失敗として閉じる。さらに同じペルソナの Metabolism の LLM
   呼び出しを一定時間 (例: 10 分) 見送る — 走行単位で止めるだけだと、自律の
   Pulse ごとに 3 回ずつの 429 が続く (整合性レビュー c-4)。これで夜通しの連打は
   「10 分に 3 回」まで落ちる。ゼロにする最後の受け皿は既存構想の送信量の安全弁
   (docs/overview/ideas.md「モデルへの送信最大文字数」) で、本設計の範囲外。
2. **読み戻しの規則の適用** (追加の決定 2): あらすじに覆われた圧縮区間は従来
   どおり丸ごと開く。生の未編纂のメッセージは後ろから必要な分 (残す量) まで
   読んだら終わり — 塊として一括で開かない。窓の外に残る未編纂は §16-1 の
   不変条件の例外として記帳し、Chronicle 補修 (手動発火) の領分に渡す —
   補修の入口のバナーが件数を出すので、ユーザーには見えている。

## 第二段 (期間を選べる UI — 実装は第一段の後、同じ設計書で続ける)

Chronicle タブに、ペルソナの歴史を期間の一覧で見せる画面を足す。

- 各期間に二種類の欠けを別々の印で出す: 「あらすじになっていない会話が N 件」
  (Chronicle の穴) と「覚えておくことを拾えていない会話が N 件」(スルースの穴)。
- 欠けている期間を**選んで**、その期間だけ実行できる: 「この期間をあらすじに
  する」「この期間から覚えておくことを拾う」。実行前にその期間ぶんの費用
  見積もり。どこが欠けているか次第で重要度が全く違う (2026-09-08 まはー) —
  全部やるか放置するかの二択にしない。
- 従来の「全部まとめて」も残す。
- モデル選択 (本人のモデル / 軽量) をここに置く。
- chronicle_coverage_gaps の第二段 (仮のあらすじと事後承認・断絶の可視化) と
  同じ画面群になる見込み — 起草時に統合を検討する。

## 追加の決定 (2026-09-08 まはー — 起草レビュー後の裁可)

1. **8/23 の「起点はパンマーカーを越えない」は撤回する。** 代わりの制約条件:
   「**スルースを通っていない範囲はユーザーに分かる状態で明示する。かつ UI 操作で
   後から通せるようにする**」(原文ほぼそのまま)。守る対象が「越えさせない」から

2. **読み戻しの規則**: 丸ごと開くか開かないかの単位があるのは、あらすじに覆われた
   圧縮区間だけ (9/5 の決定と §15-2 はそのまま)。**生の未編纂のメッセージに単位の
   概念は無い — 後ろ (新しい側) から、必要な分 (残す量) まで取ったら終わり**。
   原文: 「未編纂の物に開くとかそういう概念ないんだから後ろから見てってほしい分
   までとったら終わりでいいでしょ」。出自の 212 万字がどの経路でこの規則から
   外れたかは実装時にコードで特定して塞ぐ。

4. B の前置きの文面例は実装の検収時に見せる (実装前の追加判断は無し)。
