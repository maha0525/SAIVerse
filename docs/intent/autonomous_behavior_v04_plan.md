## 1. 芯 (一言で)

**v0.4 の自律行動の工事は四段。① 古い v2 の運転 (時間割) を止めて片付ける → ② ティック一回ぶんの部品を作る → ③ ティックを回して一日を運転する → ④ やることの実行と画面を仕上げる。** 各段の終わりに「動いて確かめられる状態」を置き、まはーの実機検証は段 3 の後に最初の大きい一回が来る。

## 2. 全体像 — 終わったとき世界はこうなる

- **ペルソナの一日**: ライフ中、最後に標準モデルを呼んでから T 分たつとティックが打たれ、本人が動く — 中身は、期限の近い一件と機械からの依頼が先に機械的に割り当てられ、何も無い回だけ本人が自由に選ぶ。アラームは定時に鳴り、ルーチンはライフの始めと終わりに走る。起床・就寝は機械の帳簿処理だけで、LLM の義務判断は無い。
- **ユーザー**: ペルソナごとの管理画面で、起床・就寝の時刻、自律の ON/OFF、T (ティックの間隔)、ルーチンとアラーム (別物として表示) を設定できる。ティックで考えたことはチャットには出ず、デバッグは Pulse タイムラインで見る (2026-10-09 まはー決定)。自律 OFF でもアラームは鳴る (同決定)。
- **記憶**: 記憶の手入れ (記憶ページの再編・メモのページ化の採否) は、スルース (会話の記憶が整理で畳まれる直前に必ず通る、本人の一手) に相乗りして、自律の ON/OFF と無関係に全ペルソナへ届く (同決定)。
- **v0.3 のユーザー**: 何も変わらない。この工事は develop-v0.4 の中だけで進み、配布はアーリーアクセスの線から始まる。
- **移行の不変条件**: v2 の時間割の運転とティックの運転が同時に生きている瞬間を作らない — 両方から LLM が呼ばれると課金が二重になる (C1。だから撤去が第一段)。

## 4. 決定の記録 (2026-10-09 まはー)

1. **ティックの出力はチャット画面に出さない。** 記録は本人の記憶のメインラインだけ。観察は Pulse タイムラインの表示を復活させて行う。行動全体を俯瞰する専用 UI は神モード UI の件と合わせて別途。
2. **自律 OFF でもアラームは鳴る。** OFF にして止まるのはティックと判断 (自発の行動)。ルーチンはライフのティックに乗るので一緒に止まり、鳴り続けるのは定時のアラームだけ。
3. **記憶の手入れの採否の置き場はスルースへの相乗り** (v3 §6 に収録済み)。
4. **ペルソナのアラーム用スペル (schedule_add / schedule_delete) は残す。** 塞ぐのは判断点 Playbook を指定できる穴だけ (起床・就寝の行をペルソナが作れてしまう件、C9)。塞ぎ方は単純な拒否でよい — 本人が起床・就寝を動かせる機能は、将来欲しくなったら改めて作る (まはー: 後で再度できるようにするのは簡単)。
5. **アラームとルーチンは、ユーザーに見える概念として別物。** 保存の器が同じでも、UI では同じものとして扱わない。
6. **外から届く刺激の ID は、全供給源に一意な ID を義務として持たせる** (同日追記)。受け取り口での代理採番や合わせ技ではなく、供給源が自分の永続 ID (フィード記事の ID・Discord のメッセージ ID・発話のメッセージ行の ID 等) を渡すことを入口で必須にする。入口は一つではなく三系統 (現象の封筒 TriggerEvent / ユーザー発話の取り込み / Discord の受け口) で、それぞれに欄を義務化する (段 1-3 の調査で確定 — 当初「封筒一本」とした見立ては誤りだった)。v0.3→v0.4 は大きく変えるブランチなので先送りしない。
7. **ID の照合の記録は、行ごとに受け取った時刻を持ち、保持期間を過ぎた行だけを個別に消す** (同日追記)。記録全体を丸ごと消す瞬間を作らない — 掃除と供給が前後しても、新しい行は残る。古さの判定は実時間。本文のハッシュでの同一視はしない。
8. **メモのページ化の提案は段 1 で休止** (同日追記)。検知の材料 (目的の木) が段 1 で撤去されるため。記憶ページの再編の提案は全ペルソナに届き続ける。新しい材料 (手帳のメモの蓄積) からの検知の作り直しは段 4 以降。
9. **ティックの時間の本人向けの呼び名は「自律モード」** (2026-10-10 まはー)。メインモード・分身モードに並ぶ一語で、退役する「自律制御モード」「自律作業モード」の後継。候補 5 件は Antigravity が出し、既存用語との衝突検査 (「自由モード」はキャッシュ運転の均等/自由モードと衝突するため除外) を経て、Antigravity・私・まはーの三者で「自律モード」に一致した。設定の「自律 ON/OFF」と本人の体験が一対一で繋がるのが決め手。実際の改名 (mode_spell_permissions の表・ペルソナに見える文言) は段 2-4 の一括語彙改名の便 (v3 §9-7) で行う。

## 5. 工程

### 段 1 — v2 の運転の撤去と、起床・就寝の機械化

**目的**: 放っておいて LLM を呼ぶ自律の動きを無くす。この段のあとに LLM を呼ぶのは、ユーザー起点の会話、会話に相乗りするスルース、定時のアラーム、実イベント到着時の on_event 判断の四つだけになる。ティックを入れる前に v2 の運転を消し、二系統の同時課金を構造的に不可能にする (C1・依存 9)。

作業 (順序は依存のとおり):

1. **記憶の手入れの採否をスルースへ移設** (C7・依存 7 — 就寝判断の LLM を消すより先)。候補の検知はそのまま、採否の欄をスルースの構造化出力に足し、適用経路を就寝から外す。メモのページ化の提案は休止する (決定 8)。欄の形は v3 §13.6 の型の規律 (数値の欄を置かない等) と同梱量の管理 (§13.5-6) に従って私が設計し、v3 §13.6 へ追記する。提示は業務日に一回までとし、見送った提案を同じ日に再提示しない。承認後の実行の起動点 (今は就寝判断の適用の直後) もスルースの確定の後へ移す。ペルソナに見える文言は新名 (記憶ページの再編 / メモのページ化) に揃える — ただし文言が会話の head に載る形になるなら、その部分は段 2 の改名の束へ移す (v3 §9-7)。
   → **済**。欄の形は v3 §13.6 の「記憶の手入れの欄 `page_reviews`」に追記した。提示の文言はスルースの一手の中だけに載り、head には載らない。
2. **ライフ確定と境界処理を判断経路から機械の帳簿処理へ切り出す** (依存 5)。ライフの保存先は時間割の行から独立させる (依存 6 — 置き場は実装時に私が決める。keep-alive・営業日の判定・画面表示がこの値を読む)。
   → **済**。置き場は新テーブル `persona_life` (旧 `persona_day_plan.meta_json.lives` は前日分の互換のための読み取り専用)。判断 Playbook を経由しなくなったので、Playbook が取り込まれていない環境でもライフは確定する。
3. **on_event (唯一残る判断点) の選択肢を作り直す** (依存 8 — 時間割の撤去より先)。時間割に積む選択肢 (insert_slot) はタスク帳に積む形へ。刺激の ID は全供給源に義務化し (決定 6)、on_event の冪等キーに使う。照合の記録は行単位の期限掃除 (決定 7)。issue `on_event_judgment_has_no_idempotency_key` はこれで閉じる。
   → **済**。選択肢は engage_now / add_task (タスク帳のシステムタスクとして一件積む) / note_only (判断の記録に覚え書きを載せるだけ) / ignore。実装で確定した点は三つ:
   - **受領の照合 (`stimulus_receipt` テーブル、保持 7 日) は現象の入口 (`inject_persona_event`) に置いた** — イベントの記録 (persona_event_log) にも、判断経由・直接応対のどちらの経路にも入る前に止めないと、二度目でもペルソナが同じイベントを二度読むか二度反応するため。ユーザー発話と Discord の再送は、発話の保存 (building_messages の `client_message_id` の一意制約) が入口で止めるので、受領の照合は通さない。
   - **ID の無いユーザー発話は会話を落とさない** — 別の活動中に届いた発話に ID が付いていなければ (配線の誤り)、ERROR を残して仲裁を経ずに直接会話を始める。ID の無い現象の封筒は ERROR で落とす (供給源の義務違反)。
   - **Discord の人間の発話の受け口の引数の食い違いを修復した** (本番では使われていない経路だったことを確認済み)。Discord のメッセージ ID は `client_message_id = "discord:<id>"` として保存まで運び、ID の無い発言は落とす。
4. **起床・就寝の LLM 判断を退役**し、時間割一式 (日次編成・コマ・繰り下げ・習慣テンプレート)・作業セッション・コマの締め・セッション終了判断・ダイジェスト配送を撤去 (v3 §8)。目的の木の配線 9 モジュールと episodes テーブルを読む残りのコードも一緒に落とす (C12)。作業セッションの撤去で issue `work_session_gate_closed_consumes_slot` は対象消滅として閉じる。予算 (回数) の設定と記録はここでは触らず、T が入る段 3 で退役させる (依存 4)。
   → **済**。予算ゲート・一日シミュレータ・一日新聞 (day_report) も同便で撤去した。テーブル定義 (`persona_day_plan` / `persona_task*` / `episodes` ほか) は既存データの残置として維持。watchdog はライフの張り直しだけになった。
5. **schedule_add の穴塞ぎ** (決定 4)。ペルソナが自分のライフの窓を決める行 (起床・就寝) や判断点 Playbook 付きの行を作れる経路を拒否し、アラーム用途はそのまま。
   → **済**。schedule_add / schedule_delete は起床・就寝の行と判断点 Playbook の行を作れず、消せない。REST API (ユーザーの操作) には制限をかけていない。

検証: フルスイート + 隔離環境 (隔離 SAIVERSE_HOME・合成ペルソナ) でサーバーを実時間で数時間立てる (一日の早回しの道具は段 3 で整うため、ここでは実時間)。自律 ON のペルソナで、上の四つ以外の LLM 呼び出し (時間割の編成・コマ・作業セッション・起床就寝の判断) が llm_io.log に一件も無いことと、アラームが従来どおり鳴ること (器の修正は段 4) を確認。スルースの出力に手入れの採否が載り、適用されることを私が読者として読む。

### 段 2 — ティックの器 (まだ回さない)

**目的**: ティック一回ぶんの部品が、手で起動して正しく動く状態を作る。

作業:

1. **Pulse 並列の洗い出し** (依存 3・v3 §9-3)。並走しうる組を数え上げること自体が作業の中身 (少なくとも 会話×ティック / ティック×アラーム / ティック×on_event 判断 / スルース×会話 / スルース×ティック / 投げっぱなし×各種)。組ごとに「防ぐ / 耐える」を表にして本書へ追記する。EventScheduler のスレッドの形 (C11) と「別の活動中か」の判定の作り直しもここで決める — ユーザー発話の仲裁を残すかは未決 10 で、v3 §4 の「ユーザー発話は最強・常に最優先」を上位の制約として表と一緒に決める (C10)。issue `judgment_seat_contention_and_event_loss` (実装済み・実機検証待ち) の検証は、この表の検証と同じ便で行う。

2. **ティックの器**: 標準モデル・メインライン・出力は記憶のみ (決定 1) のアスペクトと Playbook (C2)。
   → **済** (933a92fa)。新アスペクトは作らず、**AUTONOMOUS の tier を軽量から標準へ変えた** (未決 1 の決着 — 死んでいた席を v3 §5 の定義どおりに作り直した。tier のフォールバックも表から引く形に一本化)。器は Playbook `tick` 一枚 (出力は本人の記憶のメインライン committed にだけ残り、建物にもチャットにも出ない)。入口は `SAIVerseManager.fire_tick` / `POST /api/people/{persona_id}/tick` (手で一発打つ口。間隔の運転は段 3)。あわせて、自律の発言を次の提示で機構の報告文に包み直す古い変換 (`_reframe_autonomous_messages`) を撤去した (5dfcb100) — 軽量モデルの口調感染対策で、前提が消えたうえ「本人の言葉があるところでは本人の言葉を出す」に反していた。
3. **単発制御**: スペルを撃ちっぱなしにして 1 Beat で閉じる新設機構 (v3 §5)。
   → **済** (933a92fa)。LLM ノードの新しい欄 `single_beat`: 最初の生成のスペルを従来どおりテキスト順に一巡だけ実行し、結果を続きの生成に回さず Beat を閉じる。**帰結は成功も失敗も一括して、機構名義の知覚 ([システム通知]、本人名義の文は書かない) として次の標準 Pulse の頭に届く** — 唱えた行ごとに「正規化したスペル行 → 結果の文面」を一通にまとめ、失敗した行には印を添える。どの結果が世界に記録されるかの分類はせず、全部届ける一本の規則にする (成功した tell の「◯◯に声をかけました。」も届く)。結果の文面は長くても切り詰めない。発動したスペルと結果は Pulse タイムライン (pulse_logs) にも全部残る。経緯: 未決 2 の最初の決着は「成功の帰結は世界の記録 (建物ログ・台帳・生成物) が運び、失敗だけが知覚で届く」だったが、帰結が戻り値にしか無い読む系スペル (memory_read・検索・read_url_content・run_playbook の報告) では本人が結果を一度も読めないまま終わると 2026-10-10 の Codex 敵対レビュー 2 巡目で実証され、v3 §5「帰結は次のティックの頭 (知覚消費・台帳・報告) が読む」の知覚消費の経路として全件配送へ改めた。同じ便で、ツールが宣言した論理的な失敗 (`meta.error`) を周の記録の成否に写し、スペル行に挟まれた散文を記憶・Pulse ログ・建物の記録から落とさない組み立てに直し、器の Playbook が取れないティックを completed と記帳しない (API は `executed=false`・`outcome=error`) ようにした。宣言を持たないツール側の棚卸しは issue `tool_logical_failures_lack_error_meta`。事前実行スペルは既存の pre_spells をそのまま使う (対象の指定方法は段 4 の差し込み設計で)。
4. **tell の引数式化と標準文脈限定** (C3・C4・依存 2)。ペルソナに見える語彙の改名はこの便に束ねる (v3 §9-7)。
   → **済** (cc5b5bf2)。`tell(target, message)` — 唱えた本人の言葉がそのまま届く。軽量文脈 (分身モード) からは拒否。投函は唱えた Pulse の内側の仕事になり、**本人の記憶への別の発話行は書かない** (言葉は唱えた本文のスペル行として既に残る — 二重に自分の言葉を作らない)。改名の束: モード名は META / AUTONOMOUS とも「自律モード」(決定 9)、ペルソナに見える「スケジュール」の残り文言はアラームへ。gold_panning→sluice のコード改名は調査の結果**対象消滅** — 識別子は既に全部 sluice で、残りは永続値の互換読み (env 変数・記憶の印) と歴史の記述だけ。仲裁の退役 (§8 決定 B) も同便で実装 — 台帳に残る旧仲裁行は回収時に判断を撃たず席を放棄する。

検証: 隔離環境で合成ペルソナにティックを手で一発打たせ、(a) 出力がメインラインに記録されチャットに出ない (b) スペルが一回で閉じる (c) tell で建物へ声が出る、の三つを私が読者として読む。

### 段 3 — ティックの運転

**目的**: ライフ中、T 分間隔でティックが自動で打たれ、一日が回る。まはーの実機検証の最初の大きい一回。

作業:

## 8. Pulse 並列の洗い出し (段 2-1 の成果、2026-10-10)

v3 §9-3 の上位原則 (「個別の競合を潰すのではなく、Pulse の並列走行そのものを設計対象にする」) に従い、並走しうる組を数え上げて組ごとに「防ぐ / 耐える」を確認した。

### 8.1 土台 — 直列化の三つの仕組み (現行コードの事実)

並列の安全はこの三つが持っており、組ごとの表はこの上に立つ:

1. **Beat ロック** (`sea/beat_gate.py`): ペルソナごとの再入可能ロック。ペルソナの記憶に書く可能性のある生成 (会話・判断・自律・Metabolism・スルース) は、全部このロックを取ってから走る。だから「二つの生成が同時に走って記憶が混ざる」事故は構造的に無い。ロックの順序は MetaLayer Lock → Beat ロックの一方向で、逆順の経路を新設しないことが不変条件。
2. **席** (`sea/pulse_controller.py`): ペルソナごとにメインの席が一つ。優先度は user (会話) > schedule (アラーム) > auto (自律) で、上位が来ると走行中の Pulse に取り消しを要求する。取り消しは Beat の切れ目でだけ効く — 走行中の Beat は完走する (課金と生成の保護、2026-07-16 まはー裁定)。席を失った schedule は待ち列に並び直し (wait)、auto は消える (skip — 次の機会が来るから)。判断 (メタ判断) は席の体系の外で、中断せず中断されない。
3. **実行台帳の claim**: 同じ発火 (同じ occurrence) を二人が拾っても、台帳の席取り (CAS) で一人しか実行しない。段 1 で入れた刺激の ID と受領の照合が、判断の側の二重を止める。

一つだけ、土台そのものに欠陥がある — **発火装置 (`saiverse/event_scheduler.py`) は単一スレッドで、予約の callback をそのスレッド上で同期実行する**。今はアラームの LLM 実行 (数十秒〜数分) がこのスレッドを占有し、その間、全ペルソナの全予約 (他のアラーム・keep-alive・会話の沈黙タイマー・回復の見回り) が発火できない。ペルソナが一人なら実害が見えないが、ティックが入って複数ペルソナが T 分ごとに発火する世界では致命傷になる (C11)。

### 8.2 決定 2 件 (段 2-1 で私が決めた)

**決定 A (C11 — 発火装置のスレッドの形): 発火装置のスレッドでは LLM に届く仕事をしない。** 発火の callback の本体 (台帳の claim から Pulse の submit まで) は発火ごとのワーカースレッドへ手渡し、発火装置は「時刻が来たら手渡す」だけに戻す。ペルソナ内の直列性は席と Beat ロックが既に持っているので、ワーカーが増えても記憶は混ざらず、二重発火は台帳の claim が止める。実装は段 3-1 (ティックスケジューラと同じ便) — ただし今日のアラームにも効く修正なので、段 2 の器の検証で邪魔になったら前倒してよい。

**決定 B (C10・未決 10 — 「別の活動中か」とユーザー発話の仲裁): 仲裁は退役。ユーザー発話は常に直接応答する。** v3 §4 の「ユーザー発話は最強・常に最優先」が答えそのもので、ティック走行中に発話が届いたら席の優先度 (user > auto) が取り消しで応える — 「応えるべきか」を LLM に聞く席は要らない。「別の活動中」という概念は席の優先度が置き換えたので、作り直さない。`handle_user_utterance_conflict` と `user_conversation.py` の第三経路 (v0.3 では判定が常に None で発火しない死に枝) は段 2 で撤去する。on_event 判断は外から届く実イベント (現象の封筒・Discord) 専用に残り、issue `judgment_seat_contention_and_event_loss` の検証はその側で本表の検証と同じ便で行う。

### 8.3 組ごとの表

| 並走しうる組 | 方針 | 中身 |
|---|---|---|
| 会話 × ティック | 防ぐ + 耐える | 防ぐ: 空きティックは会話中は打たない (発火前に会話が開いているかを見る — 段 3)。すり抜けても耐える: 席で user が auto を取り消す。ティックは 1 Beat なので実際には完走して退き、skip で消える (次のティックが来るから再開は要らない) |
| ティック × アラーム | 耐える | 同じ席で schedule > auto。アラームが勝ち、ティックは skip。逆順 (アラーム走行中のティック) も席が止める。二重発火は台帳の claim が止める |
| ティック × on_event 判断 | 耐える | 判断は席の外 (メタレーン) で、Beat ロックの切れ目に挟まって直列に走る。判断の出力 (add_task) はタスク帳経由で次のティックが読む — 席の取り合いが無い |
| 会話 × on_event 判断 | 耐える (段 1 で済) | 実イベントへの判断と会話は Beat ロックで直列。同じイベントの二重は受領の照合 (stimulus_receipt) と冪等キーが止める |
| スルース × 会話 / スルース × ティック | 耐える (既存) | スルースはその Pulse 自身の Metabolism の中 (同じスレッド・同じ Beat ロックの内側) で走る — 並走ではなく同じ列の一部。承認済みの計画の実行 (curation batch) だけ別スレッドだが、Beat ロックとペルソナごとの実行中ガードで直列 |
| 投げっぱなし × 各種 | 耐える (新設の規律) | 子の Playbook は別スレッドの別 Beat として走り、記憶に書く瞬間だけ Beat ロックの列に並ぶ。**本人の席 (メインの席) は取らない** — 会話もティックも邪魔しない。報告は本人の記憶へ直接書かず「次のティックが読む置き場」に置く (届け方の具体は段 4-3。候補: 知覚の送信トレイ)。ライフ終了・自律 OFF の後に届いた報告は置き場に残り、次のライフが読む |
| keep-alive × 各種 | 耐える (既存) | keep-alive は Beat ロックの外・記憶に書かない読みだけの保温。発火の時刻がティックと競る件 (C6) は並列ではなく予約時刻の設計の問題 — 段 3-3 |
| ティック × ティック | 防ぐ | 予約キーはペルソナごとに一枚 (発火したら次を張り直す) — 同時に二枚の予約が存在しない。再起動の回復は「無ければ張る」(schedule_if_absent) で、生きている予約を上書きしない |

### 8.4 残した欠陥 (受容)

- 発火装置の単一スレッド占有 (§8.1 の欠陥) は決定 A の実装 (段 3-1) まで残る。段 2 の検証は手でティックを打つ形なので踏まない。
- 席の取り消しが Beat の切れ目でしか効かない以上、「ユーザー発話への応答開始が、走行中の Beat 一つぶん (最大で LLM 一呼び出し) 遅れる」のは仕様 — 課金と生成の保護を優先する既存の裁定のまま。
