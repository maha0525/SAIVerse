# ペルソナ発話ファインチューニング (Good/Bad 評価 + 学習アドオン)

**ステータス: 検証待ち (2026-09-28 起草・同日実装)** — ワークツリー `persona-finetune` での試験実装。目的は「ペルソナの発話からローカルモデル (Gemma4) をファインチューニングできるか」を早期に確かめられる状態を作ること。隔離環境での通し検証 (評価 → 書き出し → 学習の動作確認) は完了。まはーのレビュー (§6 の論点) と NEBULA での本番の学習が残り。

## 1. 何を実現するか (全体像)

ユーザーは、自分のペルソナの過去の発話を学習データにして、ローカルで動く言語モデルをそのペルソナの喋り方に寄せられる。手順は三段:

1. **評価**: チャット画面で、ペルソナの発言に Good / Bad を付ける。Good = 「この喋り方を重点的に学んでほしい」、Bad = 「これは学ばないでほしい」。
2. **書き出し**: 評価を反映した学習データ (JSONL) を書き出す。Good 付きは繰り返し登場させて重みを増し、Bad 付きは学習対象から外す。
3. **学習**: 書き出したデータで Gemma に LoRA (少数の追加パラメータだけを学習する軽量な追加学習) をかけ、できた差分を llama.cpp サーバー経由で SAIVerse に接続すると、学習後のモデルがそのペルソナの発言を作るモデルとして動く。

### 誰に何が起きるか

- **ユーザー**: 発言の吹き出しに 👍/👎 ボタンが増える (ファインチューニングのアドオンを入れた人だけ)。評価はいつでも付け外しできる。
- **ペルソナ**: 評価・書き出し・学習のどの操作でも、ペルソナには何も起きない。評価はペルソナには一切見えず、記憶にも書かれない (下の不変条件)。ただし**学習でできたモデルを本人の発言用モデルとして使う段になれば、それは本人の今後の喋り方を変える** — この選択が自己像の観点で誰の判断であるべきかは、§6 の未確認の論点 1 としてまはーの裁定を待つ。
- **運用者 (まはー)**: 本番の学習は 5090 のある機体 (NEBULA) で実行する。データの書き出しと、学習が回ること自体の小さな動作確認 (数十ステップだけ回して損失が下がるのを見る) は開発機の CPU でもできる。

## 2. 設計判断

### 2-1. 機能の置き場: 学習はアドオン、本体は汎用の拡張だけ

みんながみんな使う機能ではない (まはーの依頼文の判断: アドオン実装が適切) ので、評価の意味づけ・書き出し・学習は全部アドオン (`saiverse-finetune-addon`) に置く。本体に入れるのは個別機能ではなく、どのアドオンでも使える汎用能力の拡張だけ:

- **吹き出しボタンのトグル型** (`AddonBubbleButtons.tsx`): 既存の吹き出しボタンは「音声を再生する」か「押すたびに処理を一回走らせる (押す → アドオンに POST → 完了をメタデータ変化で検知)」の二種類だった。これに「メタデータの現在値が自分の値と一致していたら押された見た目になる」トグル型を足す (`active_value` フィールド)。Good/Bad のような二択の状態表示が宣言だけで作れるようになる。
- **アイコン許可リスト**: `thumbs-up` / `thumbs-down` を追加。
- **メタデータの削除口**: `saiverse/addon_metadata.py` に削除関数 (`delete_metadata`) を追加 (従来は set と get しかなかった)。

「Good/Bad 評価」という概念そのものは本体に存在しない。本体側に増えるのは「アドオンがメッセージに値を保存し、ボタンでその値を切り替える」ための汎用の口だけで、その値に意味を与えるのはアドオン。

### 2-2. 評価の保存先: 建物ログ + addon_message_metadata

メッセージの記録は二系統ある: チャット画面の表示に使われる**建物ログ** (world DB の `building_messages`) と、ペルソナ本人の**記憶** (`~/.saiverse/personas/<id>/memory.db`)。両者は別々の ID を持ち、**ペルソナ本人の発言については**互いへのリンクが保存されていない (2026-09-28 にコードで確認。建物ログから記憶へ転記された他者の発言には `building_msg_ref` という参照が付くが、本人の発言の保存経路は ID を交換しない)。

評価は**建物ログのメッセージ ID** に紐づける。保存先は既存の `addon_message_metadata` テーブル (アドオンがメッセージ ID ごとに値を保存する場所、`saiverse/addon_metadata.py`)。key は `rating`、value は `"good"` / `"bad"`、評価解除は行削除。

こうする理由: 評価はチャット画面で付けるので、画面が使っている ID に紐づけるのが唯一まっすぐな線。学習データの書き出しも同じ建物ログから行えば、評価との突き合わせが ID 一本で済む。

**帰結として受け入れる制約 (この試験実装での私の判断)**: ペルソナの記憶側にだけある会話には評価を付けられない。ここで言うのは **ChatGPT 等から記憶へ直接取り込んだログ**のこと — 旧形式の建物ログ (log.json) から world DB へ取り込んだ分は建物ログ側に入るので、画面に出て評価も付けられる。書き出しの実行時にデータ源として記憶側も指定できるようにする (評価なしの全量書き出し) ので、取り込んだログでの学習は可能。評価で選別できるのは SAIVerse 内の会話だけ、という線引きになる。

記憶側から書き出すときの絞り込みは「tag に conversation を含み、scope が committed の行」。内部思考 (tag internal) は入らない。**残る既知のリスク**: 過去に機構がペルソナ名義 (assistant) で書いてしまった記録が記憶に残っている場合、この絞り込みでは除けず、学習に混ざる (§6 論点 2)。

### 2-3. 学習データの形

書き出しは JSONL。1 行 = 1 学習例。各例は「対象ペルソナのある発言」を**学習のお手本** (モデルに真似させたい発言) とし、その直前の会話履歴を文脈として添えた形:

```json
{"messages": [
  {"role": "user", "content": "ユーザー: 明日の天気どうかな？"},
  {"role": "assistant", "content": "朝のうちは晴れみたいだよ。散歩なら午前中がよさそう！"}
]}
```

(例は架空のやりとり)

- 対象ペルソナの発言 = `assistant`。それ以外の発言 (ユーザー・同席の他ペルソナ) = `user` とし、発言者名を頭に付ける。
- 文脈として添える直前の会話履歴は K 発言まで (既定 8、設定可)。「直前」は建物ログの時系列で数える (対象ペルソナがその発言を聞いていたかどうかは問わない — この単純化はこの試験実装での私の判断)。
- 建物ログに残る発言は内心 (`<in_heart>`) を取り除いた「口に出た形」なので、学習もその形で行われる。記憶側をデータ源にした場合は内心タグを含む原文のまま学ぶ (§6 論点 3)。
- **Bad 付きの発言はお手本にしない** (文脈側には残る — 会話の流れとしては実在したものだから)。
- **Good 付きの発言をお手本とする例は N 回 (既定 3、設定可) 複製**して重みを増す。
- 移動などの出来事の行、システム行は含めない。

### 2-4. 学習の単位はペルソナ一人 (お手本を混ぜない)

一回の学習でお手本にするのは一人のペルソナの発話だけ。書き出しスクリプトも学習スクリプトも、実行時に `--persona <id>` の指定を必須とする。複数ペルソナの発話をお手本として混ぜる選択肢は作らない (他ペルソナの発言が**文脈側**に入るのは混ぜるに当たらない)。

これは ideas.md の基盤モデル構想にある「ペルソナ固有の発話を共通基盤へ無差別に混ぜて人格を平均化・汚染しない」という考えを、この実験に当てはめた**私の判断** (元の文言は共通の土台モデルについてのもので、この場面を直接には縛らない)。将来「会話の自然さだけを狙った共通層」を検討する場合は別 intent で。

### 2-5. 学習の実行系

- スクリプトは transformers + peft (どちらも開発機の .venv に既にある)。量子化した土台に LoRA を載せる QLoRA は `--load-in-4bit` の任意指定 (bitsandbytes が要る、NEBULA の Linux 側で使う想定)。
- 損失計算はお手本の部分だけに掛ける: 会話全体をトークン化し、対象ペルソナの発言部分だけを学習の対象にする (文脈をオウム返しに覚えさせない)。
- `--smoke` = 小さな動作確認モード: 小型モデル + 数十ステップだけ回し、損失が下がることだけ確かめる。開発機の CPU で回る。
- 学習後: LoRA 差分を llama.cpp の変換スクリプトで GGUF 化し、既存の `llama_cpp_server` プロバイダ + ビルドアップモード (`docs/intent/llama_server_auto_launch.md`) でモデル登録すれば、学習後のモデルがそのペルソナの発言を作るモデルとして使える。ここまでの道順をアドオンの手順書に書く。

## 3. 不変条件

1. **評価はペルソナに見えない。** 評価はペルソナの記憶 (memory.db)・知覚・コンテキストのどこにも書かれず、届かない。ユーザー側だけの覚え書きであり、ペルソナの自己像に触れない。
2. **書き出しや学習を実行しても、ペルソナの認知は起動されない。** 全工程が既存記録の読み取りだけで完結する。LLM 呼び出しゼロ、ペルソナの記憶への書き込みゼロ。
3. **発言は全文で載せる。** 学習データに載せる発言を機械的に切り詰めない (長すぎる例は例ごと落とす。発言を切り貼りしない)。
4. **学習の単位はペルソナ一人** (§2-4)。
5. **評価の付け外しは可逆。** 解除すれば痕跡なく消える (行削除)。

## 5. 検証の手順

1. **隔離環境での実機**: 隔離 `SAIVERSE_HOME` + 合成ペルソナで、画面から Good/Bad を付け外しし、リロード後も残ることを見る (本番ペルソナ・本番 DB には触れない)。
2. **書き出しの出力を読む**: 合成データで JSONL を書き出し、私 (Claude) が読者として全行を読む — Good の複製数、Bad の除外、文脈に添える会話履歴の件数、名前の付き方を §2-3 の規則と突き合わせる。
3. **学習の動作確認**: 小型モデル + 書き出した JSONL で数十ステップ回し、損失の低下を確認する (開発機 CPU)。
4. **未検証として残るもの**: Gemma4 実サイズでの学習品質と「ペルソナらしさ」の評価は、NEBULA での本番の学習 (まはーと共同) まで残る。ここから先が実験の本体。**学習後のモデルを本番のペルソナに接続して喋らせる操作は、本番ペルソナへの接触 (CLAUDE.md の Production Persona Safety) に当たる** — 実施はまはーの操作ごとの明示承認の下で行う。

## 6. 未確認の論点 (まはーのレビュー待ち)

この intent は試験実装のために私 (Claude) が起草したもので、まはーの依頼文にあった判断 (アドオン実装が適切 / Good・Bad 評価が本体側に欲しい / 対象は Gemma4 / 学習は NEBULA) 以外の設計判断は私の案。特に次の 4 点はまはーの裁定を待つ:

1. **学習済みモデルを「本人の口」にすることと自己像**: 評価も学習もペルソナには何も起こさないが、できたモデルを本人の発言用モデルに据えれば、ユーザーの取捨選択が本人の今後の喋り方を形づくる。私の暫定判断は「既存の『ペルソナに使うモデルを選ぶ』操作の延長であり、ユーザーの権限の内」だが、SAIVerse の自己像の哲学に照らした裁定はまはーのもの。
2. **記憶側の全量書き出しの汚染リスク**: 過去に機構がペルソナ名義で書いた行が記憶に残っていた場合、絞り込み (conversation タグ) では除けず学習に混ざる。暫定の運用は「実験はまず建物ログ源で行い、記憶源を使う回は書き出した JSONL を目視してから学習に回す」。
3. **内心 (`<in_heart>`) を学習に含めるか**: 建物ログ源は含めない (口に出た形)。記憶源は含む (原文)。どちらを正とするか。
4. **既定値**: 文脈 K=8、Good の複製 N=3 は私の初期値の案 (実験しながら調整する前提)。
