# Intent Document: 依存関係の管理 (lock ファイルと「上げる / 止める」の裁定簿)

**ステータス**: 完了 (2026-09-03。実装・レビュー 3 巡・lock だけの venv でのフルスイート・本番 venv の同期と再起動 (まはー、エリスと会話・声あり)・OpenAI / Anthropic / xAI の実 API 一回ずつ (隔離環境、下記 §5) まで済。残るのは develop へのマージとリリース発行、それと報告者の macOS で LLM 呼び出しが通ることの確認 (リリース後))。2026-09-11 に、アドオンの setup の `platform_script` / `python_script` の step で実行されるスクリプトの中の pip が constraints の外にあり、§2-2 で数え漏れていたと分かった。[addon_setup_scripts_bypass_lock_constraints.md](../issues/addon_setup_scripts_bypass_lock_constraints.md) で追跡している

## 概要

SAIVerse が使う Python の部品 (ライブラリ) について、**「意図した範囲」と「実際に検証した組み合わせ」を別のファイルで持ち、セットアップと更新は後者から入れる**ようにする。あわせて、いま古いまま止まっている部品を「上げる / 理由を書いて止める」に仕分け、止めるものには必ず理由を残す。

芯を専門用語なしで言うと: **「動くと確かめた部品の版の一覧」を配布物に含め、ユーザーの手元にはその一覧どおりに入れる。** いまは「この版以上なら何でも」という指定が混ざっていて、入れる日によって違う組み合わせが入る。

## 1. なぜ必要か (解決する問題)

### 1-1. 起きた実害 (2026-09-02)

ペルソナの声が 9/1 04:18 から出なくなっていた。原因は、更新経路の `pip install -r requirements.txt` が NumPy を 2.5.2 へ上げたこと。requirements.txt の NumPy は `>=1.26.0` (下限だけ) なので pip はこれを合法と見なす。一方、音声合成アドオン (voice-tts) が使う numba 0.65 は NumPy 2.4 までしか受け付けず、以後の全発話が「部品を読み込めない」で無音になった。backend.log には表層のエラーしか出ず、根因は `voice_tts_worker.log` にしか写らなかったので、丸一日以上気づかれなかった。

### 1-2. 構造の問題 (実害の供給源)

1. **requirements.txt が二種類の書き方を混ぜている。** `fastapi==0.116.1` のような「この版ちょうど」と、`anthropic>=0.42.0` のような「下限だけ」。前者は何年でも動かず (openai は 1.97 で最新 3.7、メジャー二段遅れ)、後者は pip の都合で動く。どちらも「決めていない」の別の顔。
2. **lock ファイルが無い。** 開発機とユーザーの手元で入っている版が違いうるし、`update.bat` を叩いた日によっても違う。棚卸しをしても翌月には崩れる。
3. **アドオンの部品が本体と同じ venv に入り、互いを動かせる。** 本体の pip install がアドオンの部品 (numba) を壊した。逆 (アドオンが本体の部品を動かす) も起きうる。アドオンの requirements は `numpy>=1.24` で numba の上限を知らない。
4. **Python の推奨版が現実とずれている。** README は 3.12.10 推奨、開発機は 3.13.2。まはー裁定 (2026-09-02): **3.13 を推奨に上げる** (開発機で見ている版を推奨にする)。

## 2. 全体像 (末端から末端まで)

### 2-1. 誰が何に依存できなければならないか

- **ユーザー**: `setup.bat` / `setup.sh` / `update.bat` を叩けば、開発機で検証したのと同じ部品の組み合わせが入る。入れる日によって違うものが入らない。
- **アドオンの利用者**: アドオンを入れても本体が壊れない。本体を更新してもアドオンが黙って壊れない (壊れるなら入れる時点で失敗して理由が出る)。
- **開発者 (まはー・私)**: 部品を上げるときは lock を作り直してテストし、その結果がそのまま配布物になる。「止めている部品」には理由が書いてあり、読めば外してよい条件が分かる。

### 2-2. 部品の版が決まる経路 (現状)

| 経路 | 何を読むか | 誰が叩くか |
|---|---|---|
| `setup.bat` / `setup.sh` | `pip install -r requirements.txt` | 新規ユーザー |
| `scripts/update_engine.py update_dependencies` | 同上 | `update.bat` / `start.bat` の更新続行 |
| `scripts/update_engine.py completion_fingerprint` | requirements.txt の sha256 | 更新完了マーカーの照合 |
| `scripts/update_engine.py missing_dependencies` | requirements.txt を読んで不足を判定 | 起動時の「更新が要るか」判定 |
| `saiverse/addon_installer.py` (`pip_install` step) | アドオンの requirements | アドオン導入 |
| `.github/workflows/discord_gateway.yml` | `discord_gateway/requirements-dev.txt` (中で `-r ../requirements.txt`) | CI (Python 3.11) |
| `docs/getting-started/installation.md` | 手動手順に `pip install -r requirements.txt` | 手で入れる人 |

lock を導入するなら、この **7 箇所すべて**が lock を読むように揃える。一箇所でも requirements.txt を直接読む経路が残ると、その経路だけ違う組み合わせが入る (入口の検査ではなく境界の保証として、読む側を数え切る)。**2026-09-11 に数え漏れが一つ見つかった**: アドオンの setup の `platform_script` / `python_script` の step で実行されるスクリプトの中の pip (たとえば voice-tts の `scripts/install_backends.py`) は、上の表のどれにも当たらず、requirements.lock も constraints として渡らない ([addon_setup_scripts_bypass_lock_constraints.md](../issues/addon_setup_scripts_bypass_lock_constraints.md))。

### 2-3. 変更後の形

```
requirements.txt      ← 意図の範囲 (人が書く。下限と、理由つきの上限)
requirements.lock     ← 全部品の版を固定した一覧 (機械が作る。人は編集しない)
```

- **requirements.txt** は「本体が直接 import する部品」だけを、**下限 + 理由つきの上限**で書く。`==` は使わない (釘を打つのは lock の仕事)。上限を書くときは必ず一行の理由を添える (mcp<2 の書き方が手本)。
- **requirements.lock** は `requirements.txt` から機械生成する。全部品 (間接依存も含む) が `==` で並び、プラットフォーム差 (Windows / macOS / Linux、Python 3.11〜3.13) は環境マーカーで一枚に収める。ユーザー側は素の pip で読める形式 (`pip install -r requirements.lock`) に限る — ユーザーに新しい道具を入れさせない。
- 生成の道具は開発者だけが使う。`uv pip compile --universal` を第一候補とする (開発機に導入済み、pip 互換の出力、プラットフォーム横断の一枚を作れる)。ユーザーの手元では uv は不要。
- **アドオンの pip install には lock を constraints として渡す** (`pip install -r <addon>/requirements.txt -c requirements.lock`)。アドオンは本体が固定した部品を動かせなくなり、動かす必要があるなら導入時に失敗して理由が出る (黙って壊れる代わりに)。2026-09-11 の時点で実際に渡しているのは、setup の `pip_install` の step だけ (§2-2 の数え漏れ)。**例外 (2026-10-05)**: アドオン専用の Python 環境で実行する step (`env` の付いた step) には渡さない — 本体の venv に何も入れないので、本体の部品は動かない ([addon_catalog_management.md](addon_catalog_management.md) の不変条件 7)。

### 2-4. 不変条件と持ち主

| 不変条件 | 持ち主 (真実の源) |
|---|---|
| ユーザーの手元に入る部品の版は lock と一致する | `requirements.lock` |
| lock は requirements.txt の範囲の中にある | 生成の道具 (compile が保証) |
| 止めている部品には理由がある | `requirements.txt` のコメント行 |
| アドオンは本体の部品を動かせない | `addon_installer.py` が constraints を渡す。**2026-09-11 時点で渡しているのは `pip_install` の step だけで、`platform_script` / `python_script` の step で実行されるスクリプトの中の pip には渡っていない** ([addon_setup_scripts_bypass_lock_constraints.md](../issues/addon_setup_scripts_bypass_lock_constraints.md))。アドオン専用の Python 環境で実行する step (`env` 付き、2026-10-05) は constraints の対象外 — 本体の venv に入れないことを、専用の環境の Python・pip・環境変数で起動する形で守る ([addon_catalog_management.md](addon_catalog_management.md) の不変条件 7) |
| 更新完了マーカーは lock の内容と結びつく | `update_engine.completion_fingerprint` (lock の sha256 を含める) |

### 2-5. 移行

- 既存ユーザー: 次の `update.bat` で lock どおりに入れ直される。上げる部品 (§3) があるので、入れ替えは起きる。requirements.txt の sha が変わるので更新完了マーカーは自然に「要更新」になる。
- 開発機: 同じ。ただし voice-tts などアドオンの部品は lock の外にあるので、constraints と衝突するものがあれば導入し直しで判明する。
- lock の無い版 (v0.3.3 以前) から最初の lock 版へ上げる途中で pip / npm が失敗したとき: 巻き戻しは古い版に `git reset` したあと、その版に lock が無いので、その版自身の `requirements.txt` から入れ直す (`update_engine._rollback_code_and_dependencies` だけがこの経路を選び、WARNING で記録する。通常の更新経路は lock が無ければそのまま失敗する)。

### 2-6. portable Node.js (`.node`) の版 (2026-10-22 追加)

Python の部品と同じ問いが Node.js 本体にもある。Windows の setup.bat は、Node.js が PC に無く winget も使えないとき、`scripts/install_node_portable.ps1` でリポジトリ直下の `.node` に Node.js の ZIP 版 (portable) を入れる。start.bat / start-dev.bat は `.node` があると PATH の先頭に足すので、画面のサーバーはこの Node.js で動く。

**何が問題だったか**: Node.js の版を決めているのは `install_node_portable.ps1` の中の `$NodeVersion` だが、このスクリプトは `.node\node.exe` があると何もせずに終わっていた。だから版を上げても届くのは新しく setup する人だけで、既に `.node` を持っている人は更新しても setup.bat をやり直しても古い版のままだった。2026-10-21 の Node.js のセキュリティ更新 (24.22.1) を受けて固定を 24.13.1 から上げたとき、この穴が見つかった。

**変更後の形**:

- `install_node_portable.ps1` は、`.node\node.exe --version` が固定版と違えば (動かない `node.exe` も「違う」に数える) 入れ替える。nodejs.org から ZIP を取り、スクリプトに書いた sha256 (nodejs.org の `SHASUMS256.txt` の値) と照合し、`.node` の隣の `.node.new` に展開して、展開した `node.exe` が固定版を名乗ることを確かめてから、名前の付け替え (`.node` → `.node.old`、新しいもの → `.node`) で差し替える。同じボリュームの中のフォルダの名前の付け替えなので、`.node` が書きかけになる瞬間は無い。
- 取得・照合・展開・付け替えのどれかが失敗したら、元の `.node` には一切触れずに exit 1 で終わる。`.node` の中のものが動いている (画面のサーバーや MCP サーバー) と付け替えが断られるが、これも同じ扱いになる。
- 付け替えには `[System.IO.Directory]::Move` を使い、PowerShell の `Move-Item` は使わない。`Move-Item` は付け替えを断られると一つずつのファイルの移動に切り替え、使用中のファイルで止まるので、それより前のファイルが `.node` から抜けた状態が残る (2026-10-22 にテストで見つけた。`node.exe` が使用中なら npm 一式が抜けた `.node` になる)。
- 呼ぶ場所は二つ。`scripts/update_engine.py` の `refresh_portable_node` は、`update_dependencies` の最初 (`npm ci` の前) に呼ぶ (Windows で `.node\node.exe` があるときだけ)。`update_dependencies` は、更新でコードが動いたあとに、取ってきたばかりのディスク上の `update_engine.py` の子プロセス (`--install-dependencies`) が実行するので、入れ替えの手順もいつも新しいコードのものになる (2026-10-23、[update_completes_with_new_code.md](update_completes_with_new_code.md))。setup.bat は `.node\node.exe` があれば、PC の Node.js を探すより先にこれを呼ぶ (start.bat が `.node` を優先するのと揃える)。どちらも、`.node` が無く `.node.old\node.exe` だけがある (付け替えの二つの名前変更の間で処理が死んだ) ときにも呼ぶ。スクリプトは最初に `.node.old` を `.node` へ戻す。
- `node.exe --version` の読み取りは、その関数の中だけ `$ErrorActionPreference = "Continue"` にする。Windows PowerShell 5.1 は `Stop` のもとでは、ネイティブのコマンドが標準エラーに一行でも書くと (`2>$null` で捨てていても) 止まる扱いにするので、警告を一行出すだけの正常な Node.js が「読めない」と判定され、更新のたびに取り直しになってしまう。
- 更新の `npm ci` と `npm run build` は `.node` の npm を優先し (PC にも npm があっても)、npm のフォルダを PATH の先頭に置いて動かす。npm のスクリプトや `next build` は `node` を名前で呼ぶので、update.bat のように PATH に `.node` が無い入口でも、画面のサーバーと同じ Node.js で部品が入る。

**何もしない場合**: PC に入っている Node.js (winget や nodejs.org のインストーラで入れたもの) は利用者が管理するもので、触らない。macOS / Linux には portable の経路が無いので何もしない。

**入れ替えに失敗したときの扱い — 更新は止めず、警告して続ける**: `_restore_previous_version` の流儀は「更新の途中で失敗したら、前のバージョンに戻して動く状態にする」で、守っているのは「動かない SAIVerse を残さない」こと。Node.js の入れ替えの失敗は、この意味で SAIVerse を壊さない。スクリプトは失敗したとき元の `.node` をそのまま残すので、更新は前と同じ動く Node.js で `npm ci` へ進める。逆に失敗を更新全体の失敗にすると、nodejs.org に届かない (一時的な障害、社内の制限) だけでコードの更新が全部止まり、コードの側に入っている修正 (セキュリティ修正を含む) まで届かなくなる。だから `refresh_portable_node` は例外を出さず、更新ログに WARNING を残して続ける。ただし失敗はログだけにせず、パッケージの入れ替えを済ませた記録を書かないまま失敗の記録を書くので、画面のバナーに出て、次の start.bat の `--check-complete` で入れ替えがやり直される。つながるようになれば、そこで入れ替わる ([update_completes_with_new_code.md](update_completes_with_new_code.md) §3)。

**巻き戻しでは Node.js を戻さない**: 更新の後半で失敗してコードを前の版に戻すとき、`.node` は新しい版のまま残す。前の版のコードも新しい Node.js で動く (固定の変更は同じメジャー版の中の修正版を想定している)。戻すと、セキュリティ修正のために離れた版をわざわざ入れ直すことになる。メジャー版を上げるときは、この前提を見直す。巻き戻しは前の版の `update_dependencies` を子プロセスで実行するので、子に `--keep-portable-node` を渡して入れ替えを飛ばさせる。この指定を知らない子 (v0.3.25 以前の `update_engine.py`) には渡さない。そういう版の `update_dependencies` はもともと Node.js を入れ替えないので、渡す必要もない。

**古い更新処理で更新された回は、次の start.bat で一度だけやり直す**: `refresh_portable_node` を `update_dependencies` に移す前の版 (v0.3.25 以前) の更新プログラムで更新した回は、その回の入れ替えが古い手順で行われる。2026-10-22 から 2026-10-23 までは、start.bat / start-dev.bat が起動のたびに `install_node_portable.ps1` を呼んで版を見比べることでこれを補っていた。いまは、start.bat / start.sh の `--check-complete` が「古い更新処理で更新された」と分かった環境で `update_dependencies` を一度だけやり直す処理に、Node.js の入れ替えも含めている ([update_completes_with_new_code.md](update_completes_with_new_code.md) §3)。そのため起動のたびの版の見比べは取り除いた。start.bat / start-dev.bat に残しているのは、`.node` が無く `.node.old\node.exe` だけがあるとき (入れ替えの二つの名前変更の間で処理が死んだとき) に `.node.old` の名前を `.node` へ戻す処理だけ。これが無いと、次の更新まで画面のサーバーが Node.js を見つけられない。start-dev.bat は `--check-complete` を呼ばないので、start-dev.bat だけで起動している環境では、古い更新処理で漏れた入れ替えは次の更新で行われる。

| 不変条件 | 持ち主 |
|---|---|
| `.node` の Node.js は、そのコードが固定する版と一致する (取得できなかったときは前の版のまま) | `scripts/install_node_portable.ps1` の `$NodeVersion` / `$ExpectedSha256` |
| 入れ替えの途中で `.node` が書きかけや空にならない | 同スクリプト (`.node` の隣で展開し、名前の付け替えで差し替える) |
| 入れ替えは、いつもディスク上の新しいコードの手順で行う | `update_engine.update_dependencies` (子プロセス `--install-dependencies` が実行する) |
| 入れ替えの途中で止まって `.node.old` だけが残っても、次の起動で `.node` に戻る | start.bat / start-dev.bat の `.node.old` を戻す処理 |
| 更新の npm は画面のサーバーと同じ Node.js で動く | `update_engine._find_npm` (`.node` 優先) と `_env_with_npm_on_path` |
| Node.js の入れ替えの失敗で更新は止まらない | `update_engine.refresh_portable_node` |

### 2-7. setup が Python 3.13 を名指しする / アドオン専用の環境の自動の作り直し (2026-10-23 追加)

**まはーの裁定 (2026-10-23)**: Python 3.11 / 3.12 は非推奨にする。python.org の Windows 用インストーラーが 3.12.10 / 3.11.9 で止まり、普通の利用者にはこの二つの系列の修正版 (セキュリティ修正を含む) を入れる手段が無いため。動作確認は 3.13 系だけで行う (README などは同日に直した)。3.14 以降は非対応のまま。目標は、3.11 / 3.12 から移る人の手順を「3.13.17 を入れる → SAIVerse を更新する → setup をもう一度実行する」だけにすること。

**何が問題だったか**: `.venv` は作ったときの Python の系列に固定される。`.venv/pyvenv.cfg` の `home` がその系列のフォルダを指し、中のパッケージはその系列専用のファイル (`cp312` など) になる。だから 3.13 を入れても `.venv` は古い系列のまま動き続ける。さらに setup.bat は PATH の先頭の `python` で `.venv` を作り、既にある `.venv` は (壊れていなければ) そのまま使っていたので、setup をやり直しても系列は変わらなかった。アドオン専用の Python 環境 (`addon_install/<id>/envs/<name>/`) も作ったときの本体の Python の系列に固定され、本体の系列が変わると `get_addon_env_python` が使うのを断る。作り直しの入口はアドオン管理の選択肢の確定のやり直しだけで、利用者はそれを知らない。

**変更後の形**:

- setup.bat は、レジストリの `HKCU\Software\Python\PythonCore\3.13\InstallPath`、無ければ `HKLM\...` の既定値 (python.org のインストーラーも miniconda も書く) のフォルダの `python.exe` を使う。PATH の並び順に左右されない。見つけた python が 3.13 として動くことも確かめる。既定値の行の名前は Windows の言語で変わる (`(既定)` / `(Default)`) ので、フォルダは `REG_SZ` の後ろから取る。setup.sh は `python3.13` コマンドを使う。選んだ python の場所 (`PYTHON_EXE` / `PYTHON_BIN`) は、`.venv` を有効にする前のすべての処理 (`.venv` の作成、`scripts/setup_venv.py`) に使う。

- 新しい `.venv` にパッケージが入ったあと、setup は `.venv` の python で `scripts/rebuild_addon_envs.py` を実行する。これは `saiverse.addon_installer.rebuild_unusable_addon_envs` を呼び、導入済みのアドオンの専用の環境のうち、フォルダがあって、いまの Python で使えないもの (記録の Python の major.minor が違う・記録が無い・python が無い。`_env_needs_full_run` と同じ判定) を作り直す。走らせるのは、保存された答え (無い質問は既定値) と OS で選ばれる step のうち、その環境を使うもの全部 (`plan_env_rebuild`。環境は空の venv から作り直されるので、`plan_options_apply` と同じ理由で全部要る)。アドオンのバージョン (checkout)・保存された答え・アドオンのデータは変えない (答えは保存し直さない — 既定値で埋めた答えを書くと保存された答えが変わる)。フォルダの無い環境 (一度も作られていない) は作らない。使えない環境が無ければ何もしない。setup が毎回呼ぶのは、系列が変わるのは `.venv` を作り直したときだけだが、前の回の作り直しの失敗をやり直せるようにするため。 **更新も同じスクリプトを呼ぶ (2026-10-23、まはー「setupをしない場合にはどう？」の点検で見つかった)**: v0.3.26 より前の setup (専用の環境を作り直さなかった) や手で `.venv` を 3.13 で作り直した環境では、専用の環境が古い系列のまま残り、次の setup まで直らなかった。そこで `update_dependencies` の最後に `scripts/update_engine.py` の `rebuild_addon_envs` が `.venv` の python で `rebuild_addon_envs.py` を `--core-venv-recreated` なしで実行する。作り直すのは使えないと判定された環境だけで、使える環境には触らない (まはー「必要な時だけやるってことでいい？毎回やってたんじゃ特にTTSはモデルのダウンロードが重くて」)。失敗はスクリプトが同じ記録に書いてバナーに出る (スクリプトが落ちたときも書く) ので、更新の側が失敗 (`addon_envs`) として返すのは、スクリプトを起動できなかったときと、記録を残さずにエラーで終わったとき (落ちたときの記録を書く処理より前、import で止まった場合など) だけ。スクリプトが無い checkout (古いリビジョンへの巻き戻し) では何もしない。voice-tts の Irodori-TTS はモデルの重みを専用の環境の中 (`<専用の環境>/hf_cache/`) に置いているので、その環境の作り直しでは重みも取り直しになる (GPT-SoVITS の重みはアドオンのフォルダの中なので残る)。
- 一つのアドオンの作り直しが失敗しても、次のアドオンへ進み、setup は止めない (SAIVerse 本体は動く)。専用の環境の記録 (`saiverse_env.json`、いまの Python で作った印) は、その環境を使う step を含む全部の step が成功したあとにだけ書く (2026-10-23 に変えた。`_execute_steps` が最後に `_write_env_records` を呼び、`_ensure_addon_env` は作った環境を覚えるだけ)。以前は venv を作った直後に書いていたので、後の step の失敗や中断 (Ctrl+C は失敗の記録の処理にも届かない) で、記録の付いたパッケージの欠けた環境が残り、`get_addon_env_python` が通してしまっていた。記録の無い環境は、`get_addon_env_python` が「setup をやり直して」と断り、次の setup の作り直しと、アドオン管理の導入・更新・選択肢の確定のやり直しが作り直す (全部の経路が `_execute_steps` を通る)。同じ実行の中で後の step が同じ環境を使うときは、作ったばかりの環境をそのまま使う。作り直しを始めた環境が失敗で終わると、やりかけの記録 (上) が残り、次の実行がその環境を作り直す。setup の画面には、どのアドオンが失敗したか、setup をもう一度実行するか、アドオン管理でそのアドオンを入れ直す (アンインストールしてもう一度インストール。データは残る) ことを日本語と英語で出す。
- **本体の `.venv` に入れる step の入れ直し**: アドオンの setup の step には、専用の環境ではなく本体の `.venv` にパッケージを入れるものがある (voice-tts の `env` の無い `pip_install` は、本体用の `requirements.txt` を本体の `.venv` に入れる)。新しい `.venv` には requirements.lock の部品しか入らず、`plan_env_rebuild` は専用の環境を使う step しか選ばないので、そのままでは setup が成功してもそうしたアドオンは動かない。そこで setup は、`setup_venv.py prepare` が `create` / `renamed` / `resume` を返した回 (新しい `.venv` を作った回と、その続き) にだけ `rebuild_addon_envs.py --core-venv-recreated` と呼び、専用の環境の作り直しの前に `reinstall_core_venv_steps` で、導入済みのアドオン (`expansion_data/<id>/addon.json` があり、導入の途中ではないもの) の step のうち本体の `.venv` に入れるものを、保存された答え (無い質問は既定値) と OS で選んで走らせ直す。`keep` の回は走らせない。対象の step は `env` の無い `pip_install` だけで、既存の導入と同じく requirements.lock を constraints として渡す (`_exec_pip_install`)。`env` の無い `python_script` / `platform_script` も本体の Python・環境変数で動くので中で pip を呼べば本体の `.venv` に入れられるが、対象にしない — そういうアドオンはカタログに載せない ([addon_catalog_management.md](addon_catalog_management.md) の不変条件 7)、スクリプトの中の pip には constraints が渡らないので setup から走らせ直すと本体のパッケージを動かしうる、いまある `env` の無いスクリプト (設定ファイルのひな形の作成、Irodori-TTS の依存の手直し) が残すものは `.venv` の外にあって `.venv` を作り直しても消えない、の三つが理由。アドオンのバージョン・保存された答え・アドオンのデータは変えない。SAIVerse が動いている (か分からない) ときは、専用の環境の作り直しと同じく走らせずに失敗として記録する。失敗しても setup は止めず、画面に失敗したアドオンと step、setup をもう一度実行するかアドオン管理で入れ直すことを出し、専用の環境の作り直しの失敗と一緒に一つの記録に書く (項目の `core_venv` が true)。`.venv` は次の setup では `keep` になるので、記録に `core_venv` が true の項目があれば、`--core-venv-recreated` が無い回でもそのアドオンの入れ直しをやり直す (記録が読めない、またはスクリプト自体が新しい `.venv` の回に落ちた記録 (`addon_id` が `(setup)`) なら全部のアドオン)。
- 失敗の内容は、リポジトリ直下の `.addon_env_rebuild_failures.json` に書く (`record_env_rebuild_failures`。`.gitignore` に入れてある)。本体の `.venv` への入れ直しと専用の環境の作り直しの結果を一度に渡して書くので、片方の成功がもう片方の失敗の記録を消さない。失敗が無ければ消す。形は `{"created_at": ISO 時刻, "python_version": 本体の Python, "failures": [{"addon_id", "envs": [環境の名前 (本体の .venv への入れ直しは空)], "steps": [走らせた step の名前], "error": 失敗の文, "core_venv": 本体の .venv への入れ直しなら true}]}`。起動時に `saiverse/environment_alerts.py` がこの記録を画面のバナー (`startup_alerts`) に出す (`main.py`)。
- 同じアドオンへの同時の操作を防ぐ API の鍵 (`api/routes/addon_catalog.py` の `_get_lock`) は SAIVerse のプロセスの中だけの `threading.Lock` で、別のプロセスの setup からは取れない。だから `rebuild_addon_envs.py` は、SAIVerse が動いている (または動いているか分からない。`saiverse.runtime_marker.marker_status`) ときは作り直さず、作り直しが要るアドオンを失敗として記録して「SAIVerse を閉じて setup をもう一度」と出す。setup の最初の `check-stopped` も同じことを確かめているが、このスクリプトは setup の中で時間が経ってから走るので、自分でもう一度確かめる (改名の成功は、Linux / macOS では「動いていない」の確かめにならない)。

**何もしない場合**: PC に入っている Python は利用者が管理するもので、setup は入れも消しもしない。

**SearXNG の専用の venv (`scripts/.searxng-venv`)**: `searxng_install.py setup` は、venv がいまの Python と別の系列で作られていれば、名前を変えて退避してから作り直す (`set_aside_venv_of_other_series`。使用中で改名が断られたら何も変えずに止まる)。作り直しのどこ (venv の作成・pip・確かめ) で失敗・中断しても、作りかけを消して退避した venv を元の名前に戻してから失敗を返す (2026-10-23。それまでは退避したまま残り、SearXNG が動かなくなっていた)。成功したら退避した方を消す。窓を閉じるなどで後始末の処理そのものが走らずに止まったときのために、退避の前に退避先の名前を SAIVerse のフォルダの `.setup_in_progress/searxng-venv.json` に書き (上の「やりかけの記録」、`SET_ASIDE_ENTRY`)、作り直しが成功するか退避した venv を戻せたら消す。記録が残っている間は、`searxng_install.py check` (`ready`) が通らないので、次の `setup` (setup.bat、更新の `refresh_searxng`、SearXNG の起動の `run_searxng_server`) が、いまの venv の系列にかかわらず入れ直し (いまの venv が別の系列なら消して作る)、失敗したら記録にある退避先を戻す。記録の退避先が無い (改名の前に止まった) ときは記録を捨て、ふつうに系列を見る。退避した方を消すときは、先に `.deleting-<日時>` へ改名して記録を消してから消す (途中まで消えたフォルダを戻し先として名指しする記録が残らないように)。残った `.deleting-*` は次の成功した `setup` が消す。`setup` の失敗は SAIVerse のフォルダの `.searxng_setup_failed.json` に書き、本体が起動時に画面のバナーに出す (`saiverse/environment_alerts.py`。次の `setup` の成功で消える)。setup の窓の警告だけでは、窓を閉じたあとに残らないため。更新の中の `refresh_searxng` から呼ぶときは、失敗を `.update_dependencies_failed.json` に書く側に任せ、この記録は書かない (環境変数 `SAIVERSE_SEARXNG_SKIP_FAILURE_RECORD=1`。同じ失敗を二つのバナーに出さないため)。退避の直後に止まると SearXNG の venv には python が無いので、やりかけの記録がある間は「SearXNG が入っている」と扱い、入れ直しは SAIVerse 本体の Python で動かす (2026-10-23、PR #417 の Codex 六巡目。それまでは python が無いことを「入っていない」と読み、更新・起動前のやり直し・start.bat のどれも入れ直しを呼ばなかった)。更新の `refresh_searxng` は確かめ (`check`) を飛ばし、`update_dependencies` に渡された本体の Python で `setup` を動かす。 **確かめと入れ直しは、いつも本体の Python で動かす (2026-10-23、同じ点検)**: `searxng_install.py check` (`ready`) は、SearXNG の venv の系列 (`pyvenv.cfg`) が、自分を動かしている Python の系列と違えば通らない。更新の `refresh_searxng` と `run_searxng_server.ps1` / `.sh` は、記録の有無にかかわらず本体の `.venv` の python でインストーラーを動かす (setup.bat / setup.sh と同じ)。それまでは SearXNG の venv 自身の python で確かめていたので、venv を自分自身と比べることになり、v0.3.26 より前の setup で `.venv` だけ 3.13 にした環境では、SearXNG が 3.12 のまま次の setup まで残っていた (3.12 を消すと検索が動かなくなり、バナーも出なかった)。`.venv` の python が無いときだけ、SearXNG の venv の python (無ければ PATH の `python`) を使う。start.bat / start.sh の起動前の確かめ (`--check-complete`) は、依存の記録が一致していても、この記録があれば起動前のやり直し (`reinstall_dependencies_once`) に回す。start.bat / start-dev.bat は、この記録があるときも SearXNG の窓を開き、`run_searxng_server.ps1` / `.sh` は、記録があるとき (または venv の python が無いとき) は本体の `.venv` の python で `searxng_install.py` を動かす (start.bat は `.venv` を有効にしないので、PATH の先頭の `python` に頼らない)。新しく導入した環境 (`.update_complete` が無い) では起動前のやり直しを走らせない ([update_completes_with_new_code.md](update_completes_with_new_code.md) §2 の約束 3) ので、この窓の側の入れ直しだけが働く。起動前のやり直しが失敗して記録が残ったときは、同じ起動の SearXNG の窓がもう一度入れ直しを試す。

| onnxruntime | `<1.24` | 1.24 以降は macOS x86_64 (Intel Mac) と macOS 13 の wheel が無く sdist も無い。universal lock が 1.24+ を掴むと Intel Mac では `pip install -r requirements.lock` 自体が失敗する (2026-09-02 Codex レビューで発覚。fastembed 0.8 も Python 3.13 で 1.24.0/1.24.1 を除外。fastembed は 2026-10-12 の埋め込み移行 ([embedding_gemma2_migration](embedding_gemma2_migration.md)) で撤去し、onnxruntime は sai_memory が直接 import する依存になった — 上限の理由はそのまま)。外す条件 = onnxruntime が Intel Mac の wheel を再開する、または Intel Mac 対応を打ち切ると決める。下限 `>=1.23.2` は、固定した埋め込みモデル (ONNX IR 10 / opset 21、4bit の MatMulNBits・GatherBlockQuantized を使う) が 1.23.2 で動くことを確かめ、1.19 では読み込みに失敗することを確かめたため (2026-10-12 埋め込み移行のレビューで引き上げ) |
| cryptography | `<49` | 49.0.0 以降は macOS x86_64 (Intel Mac) の wheel が無く、sdist からのビルド (Rust の道具一式が要る) になる。`check_lock_platforms.py` は sdist のみの pin を WARN で通すので、検査の緑だけでは Intel Mac の利用者が入れられるとは言えない (2026-10-22、脆弱性対応で 50.0.2 を掴んだときに発覚)。48.0.1 が Intel Mac の wheel を持つ最後の版で、同梱 OpenSSL の修正 (GHSA-537c-gmf6-5ccf) を含む。49 / 50 でしか直らない届け出 (CVE-2026-69247 PKCS#7 の復号、CVE-2026-69248 / CVE-2026-69249 x509 の証明書経路の検証) は、SAIVerse のコードが呼ばない機能にある。外す条件 = onnxruntime と同じ (Intel Mac の wheel の再開か、Intel Mac 対応の打ち切り) |

**universal lock の盲点 (2026-09-02 に学んだこと)**: `uv pip compile --universal` は依存関係のメタデータだけで解決し、その版の wheel が各プラットフォーム向けに公開されているかは見ない。Windows で入って全スイートが緑でも、Intel Mac で入らない lock はできる。だから lock を作り直したら `python scripts/check_lock_platforms.py` (各 pin の wheel / sdist の有無を PyPI に問い、対象 4 プラットフォーム × Python 3.11〜3.13 で入らない組合せを exit 1 で返す) を回す。判定は pip と同じ `packaging.tags` で行い、macOS の床は x86_64 が 13 (対応する Intel Mac の最低 OS 版)、arm64 が 14、Linux の床は glibc 2.31 (Ubuntu 20.04 LTS / Debian 11 = 対応すると言う最古の Linux。これより新しい glibc を要求する wheel しか無い pin は Linux では「無い」と数える)。Requires-Python は PyPI が wheel / sdist ごとに持つのでファイル単位で見て、その Python を除外するファイルは候補に数えない (どのファイルも許さなければ FAIL)。yanked (取り下げ) されたファイルも候補に数えず、全ファイルが yanked の pin は FAIL。PyPI の照会に失敗した pin は「入る」と数えず FAIL にする (fail-closed。exit 0 は全 pin を取得して判定できたときだけ)。§5 の 1b。

他に止めるべきものは実装時の compile と全スイートで判明する。**「なんとなく上げない」は禁止** — 上げないなら理由を書く。

### 3-3. 本体の責任ではない (アドオンの部品)

torch / transformers / librosa / numba / gradio / funasr など、venv にある 269 個のうち本体の直接依存 (約 30 個) を除く大半は voice-tts が連れてきたもの。これらは本体の requirements には入っていない (現状で正しい)。本体がやることは **constraints で「本体の部品を動かすな」と言う**ことまで。numba の上限などアドオン自身の部品の整合はアドオン側の requirements の責任 (voice-tts に numba の固定を足すのはアドオンのリポジトリの宿題)。

ただし本体の更新は、壊したことを**その場で見せる**義務は負う。`update_engine.update_dependencies` は lock を入れ、lock から外れた本体の部品 (`RETIRED_CORE_PACKAGES`、§7 の 2026-10-22 の項) を消した直後に `pip check` を回し、lock の外にあるパッケージ (アドオンか手で入れたもの) との衝突を `[deps] pip check: ...` の WARNING として更新ログに残す (2026-09-02 の voice-tts の実害は、翌日まで誰も気づかなかったことが問題だった)。衝突と読むのは `pip check` の exit 1 だけで、それ以外の非ゼロ (2 = pip 自身の使い方の誤りや内部エラー、負数 = シグナル) は「pip check が走らず、衝突は検査できなかった」として stderr と一緒に別の WARNING で残す (pip の落ち方をアドオンの衝突に見せない)。可視化だけで、更新は失敗にしないし巻き戻しもしない — 直すのはアドオン側。

2026-09-11 に、この警告の最後の文の助言 (「該当のアドオンは入れ直す (アドオンを入れ直す) 必要があるかもしれません。」) が当てはまらない衝突が見つかった。voice-tts が入れる GPT-SoVITS の requirements.txt 自体が requirements.lock と両立しない場合で、アドオンを入れ直しても衝突は消えない ([pip_check_warning_reinstall_advice.md](../issues/pip_check_warning_reinstall_advice.md))。

### 3-4. SDK を上げる前に分かっていること (2026-09-02 の下調べ)

- **HTTP の部品が世代交代している。** `httpx` は保守が止まり、Pydantic チームの互換フォーク **`httpx2`** に移った。anthropic 1.0 (2026-08-20) と openai 3.0 (2026-08-12) はどちらも「httpx2 へ移行」が唯一の破壊的変更で、`httpx` はもう自動では入らない。google-genai 2.x と mcp 1.x はまだ `httpx` (<1.0) を使う。**二つは別パッケージとして共存できる**ので、当面は両方が venv に入る。
- SAIVerse 自身が `httpx` を直接使う箇所は 10 ファイル。SDK に渡していたのは `llm_clients/anthropic.py` の `httpx.Timeout(...)` だけで、**2026-09-02 に `httpx2.Timeout` へ切り替えた** (httpx2 は requirements.txt の直接依存に載せた)。下調べでは「旧 httpx の型を渡すと構築時に `TypeError`」と書いていたが、1.3.0 の実物で確かめると **`Timeout` は構築時に拒否されない** — 受け取られたうえで、transport に渡る connect / read / write / pool の各値が数値ではなく Timeout オブジェクトそのものになる (黙って壊れる型)。構築時に `TypeError` になるのは `http_client=` に旧 `httpx.Client` を渡したときだけ。だから `tests/test_llm_clients.py` で「構築されたクライアントの timeout が `httpx2.Timeout`」を実構築経路で固定した。`llm_clients/gemini.py` の `isinstance(err, httpx.ReadTimeout ...)` は google-genai が httpx のままなので変えない。方針: **自分のコードは SDK が使う方の型に合わせる** (anthropic / openai 向けは `httpx2`、genai 向けは `httpx`)。プロセス全体で `import httpx` を httpx2 に差し替える `httpx2.alias_httpx()` は使わない — 起動順に依存し、mcp / genai が期待する型を黙って変える。
- **httpx2 は certifi を同梱しない。** `SSL_CERT_FILE` が立っていればその束、無ければ truststore 経由で OS のストアを信頼元にする (httpx2 2.12 の `_config.create_ssl_context` で確認)。`saiverse/tls_trust.py` が起動時 (`main.py` の import 時、`SAIVerseManager` より前) に `SSL_CERT_FILE` を立てるので、Python が OS のストアを読めない macOS 環境では anthropic 1.x の呼び出しも certifi で検証される。docstring は 2026-09-02 に現状へ合わせた。残る確認: **macOS の実機で anthropic 経由の LLM 呼び出しが通ること**を報告者に確認してもらう (truststore 単体でキーチェーンを読めるかは未確認だが、読めるなら環境変数なしでも通る方向の差)。
- **google-genai 2.0** の破壊的変更は Interactions API だけで、`GenerateContent` は無変更 (公式 CHANGELOG)。SAIVerse は Interactions API を使っていない (`llm_clients/` / `saiverse/llm_router.py` / `persona/emotion_module.py` / `tools/adapters/gemini.py` に参照なし) ので、**上限 `<2.0` は 2026-09-02 に外した** (`google-genai>=2.21.0`)。2.21 への実際の差分で SAIVerse に効いたのは一つだけ: 2.18 から `generate_content` は `automatic_function_calling.disable=True` を明示しない限り「Direct use of AFC ... is not recommended」を WARNING でプロセスごとに一度ログする (tools を渡していなくても)。`llm_clients/gemini.py` は元から無効化していたが、`saiverse/llm_router.py` / `persona/emotion_module.py` / `builtin_data/tools/image_generator.py` の 3 箇所は未指定だったので同じ規則 (SAIVerse は SDK の AFC を使わない) に揃えた。挙動は変わらない (tools が無ければ AFC ループは 1 回で抜ける)。google-genai の HTTP 部品は 2.21 でも `httpx` (<1.0) のまま。
- **anthropic 1.0** は httpx2 の他に、`messages.create()` / `messages.stream()` から `temperature` / `top_p` / `top_k` を撤去 (渡すと `TypeError`。古いモデル向けに要るなら `extra_body`)、`output_format=` にスキーマ dict を渡す形を撤去、`.with_raw_response` の戻りが新クラスに。SAIVerse 側で該当したのは `llm_clients/anthropic_request_builder.py` の `temperature` / `top_p` / `top_k` だけで、**2026-09-02 に `request_params["extra_body"]` へ移した** (SDK が JSON の最上位に合流させるので、API に届く形は以前と同じ。`max_tokens` は今も正規の引数)。`tests/llm_clients/test_anthropic_request_builder.py` で、extra_body に入ること・最上位に残らないこと・その dict が 1.3 の `messages.create()` に `TypeError` なしで束縛され JSON の最上位に届くこと (httpx2 の MockTransport で通線) を固定した。`with_raw_response` / `output_format=` / Text Completions / `HUMAN_PROMPT` / `anthropic.Transport` / `BetaBase64PDFBlockParam` は `llm_clients/anthropic*.py` に無し (grep で確認)。`anthropic_retry_policy.py` は SDK の例外クラス (`APITimeoutError` / `APIConnectionError` / `APIStatusError`) だけを見ていて httpx の型に触れていないので無変更。
- **openai 2.0** は Responses API の function call output の型が広がっただけ (SAIVerse は `chat.completions` しか使わない)、**3.0** は httpx2 のみ。**2026-09-02 に 1.97.0 → 3.7.0 へ上げた。** lock は `--upgrade-package openai` で openai と jiter (0.13 → 0.16) だけ動き、openai 3.x は distro / tqdm / httpx を連れて来なくなった (distro は google-genai、tqdm は fastembed / huggingface_hub、httpx は google-genai / mcp / langgraph-sdk / langsmith と SAIVerse 自身の直接依存として残る)。3.7.0 の実物で確かめたこと: `OpenAI(...)` に SAIVerse が渡す `api_key` / `base_url` / `timeout` (float) / `default_headers` はすべて健在で、`chat.completions.create()` に積む `n` / `tools` / `tool_choice` / `response_format` / `stream` / `stream_options` / `extra_body` / `extra_headers` と `OPENAI_ALLOWED_REQUEST_PARAMS` の 15 個は全部まだ正規の引数 (撤去なし、`extra_body` への移送は不要)。例外クラス (`RateLimitError` / `APIStatusError` / `APITimeoutError` / `APIConnectionError` / `AuthenticationError` / `BadRequestError`) と `openai_errors.py` が読む `.status_code` / `.body` も無変更で、`.response` の型が `httpx2.Response` になっただけ (SAIVerse は httpx の型を `isinstance` していないので影響なし)。streaming の chunk 型 (`choices[0].delta.content` / `.tool_calls[].function.name|arguments` / `finish_reason` / 末尾 chunk の `usage.prompt_tokens_details.cached_tokens`) も 1.x と同形。`builtin_data/tools/image_generator.py` の `images.generate` / `images.edit` (image に file の list) も引数健在。anthropic と違い、openai 3.7.0 は `http_client=` に旧 `httpx.Client` を渡しても構築時に拒否せず MockTransport の往復まで通ってしまう (duck typing) — 型注釈は `httpx2.Client` なので、テストは SDK と同じ側に寄せた。float でない `timeout` に旧 `httpx.Timeout` を渡すと anthropic と同じく黙って壊れる (httpx2 の Timeout が Timeout を包んで各段が数値でなくなる) が、SAIVerse は float しか渡さないので該当なし。`tests/test_llm_clients.py` に、factory 経由で構築した実クライアントの `_client` が `httpx2.Client` で timeout が届いていることを固定する 2 テストを足した。SDK 由来の警告は対象テストで 0 件 (3.7 の `DeprecationWarning` は生 bytes を `body=` に渡す低レベル経路だけで、SAIVerse は使っていない)。
- lock の環境マーカーの癖: `hf-xet` の行のマーカーが `platform_machine == 'amd64'` (小文字) で書かれており、Windows (`AMD64`) では偽になって入らない。huggingface_hub は無くても通常のダウンロードに退避するので実害はないが、上流のマーカーをそのまま写した結果であることを記録しておく。

## 5. 検証 (境界を跨ぐ順に)

1. **compile が通る** — requirements.txt から lock が生成でき、pip check で衝突ゼロ。
   1b. **全プラットフォームで入る** — `python scripts/check_lock_platforms.py` が exit 0 (Windows / Linux / macOS arm64 / macOS x86_64 × Python 3.11〜3.13 の全組合せに wheel か sdist があり、Requires-Python にも除外されず、全 pin を PyPI から取得できた。wheel の適合は `packaging.tags` で判定し、macOS の床は x86_64=13 / arm64=14)。照会に失敗した pin があれば exit 1 (fail-closed)。開発機では確かめられない環境の代理。
2. **素の venv に lock だけで入る** — 開発機の venv ではなく、新しい venv に `pip install -r requirements.lock` して全スイートが緑。これが「ユーザーの手元」の代理。
3. **update 経路** — 隔離環境 (`docs/test_environment.md`) で `update_engine.py --manual` を通し、完了マーカーが lock の sha を持つこと。
4. **アドオン導入** — 隔離環境で voice-tts を `pip_install` step から入れ、constraints が効くこと (本体の部品を動かそうとしたら失敗すること、を一つ作為的に確かめる)。**pip の機構としては 2026-09-02 に確認済み**: lock venv で `pip install --dry-run -r <アドオン風の requirements> -c requirements.lock` を実行すると、マーカー付き行と `# via` コメントを含む lock をそのまま constraints として受け付け、`numpy<2` のような本体の pin と矛盾する要求は `ResolutionImpossible` で止まる。`addon_installer` が `-c` を渡す配線はテストで固定済み。voice-tts の実導入は本番 venv の同期のときに。
5. **SDK の実 API 一回ずつ** — openai / anthropic / gemini / xai を各一回、隔離環境から呼ぶ。**課金が出るので、この段の直前にまはーの承認を取る** (対象・回数・見込み額を示して)。**済 (2026-09-03、まはー承認)**: ペルソナは使わず SAIVerse のクライアントクラス (`get_llm_client` → `generate` / `generate_stream`) を隔離環境 (`SAIVERSE_HOME=test_data/.saiverse`) から直接叩いた。gpt-5.4-nano (generate 4.7s / stream 1.3s)、claude-haiku-4-5 (1.3s / 0.8s — extra_body 経路と messages.stream の両方)、grok-4-1-fast-reasoning (2.8s)、全部 'pong' が返った。Gemini はまはー本人のエリスとの会話 (本番、gemini-3.7-flash-paid、キャッシュ有効) で確認済み。
6. **本番の再起動** — まはーの手で。会話一往復、声、記憶タブ。**済 (2026-09-03 00:11 起動)**: バージョン鎖 0.3.3 で完了、lifespan で addon_events のループ登録 → startup complete、TLS 退避の発火なし、エリスと会話 (LLM 成功・Gemini 明示キャッシュ)、voice-tts は 64 片を enqueue して import 失敗 0・合成失敗 0 (前日まで全滅していた経路)。Traceback は stackchan アドオンの Gemini 関数定義変換の既存 3 件のみ。

「全スイート緑」は 2 と 3 の代理にならない (スイートは開発機の venv で走るため)。
