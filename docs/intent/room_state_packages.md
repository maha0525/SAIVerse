## 1. 保障すること (成果と関係者)

1. **ペルソナは、今いる部屋の様子を常にコンテキストに持っている。** 起動直後でも、長い滞在の後でも、記憶の整理の後でも。
2. **部屋の報告は「変わった事実」だけを運ぶ。** 現れた物は全文で、消えた物は名前の一行で、変わらなければ「変わっていません」の一行で。同じ内容が二枚並ぶことは構造的に無い (置き場が知覚の一つだから)。
3. **文字と絵がはぐれない。** 「絵がある」と読めるとき、その絵が見える。差分で新しく見せる回も、整理の後で全文に戻る回も。
4. **ユーザーの Close 操作は尊重される。** 閉じる = コンテキストから外す意思表示。機構が本文を再掲してその意思を裏切らない。
5. **報告は追記で育つ。** 提示の書き換えは、編纂・境界前進というどうせ割れる瞬間への相乗りだけ (プロンプトキャッシュの前方一致の保護 — v0.3.9 で確立した原則の維持)。

関係者: ペルソナ (世界の見え方の正確さ)、ユーザー (Close の意思と画像の体験)、まはー (この doc の複雑さが把握可能なこと)、保守側 (差分機構が一本であること)。

## 2. 何が変わるか — 芯は一つ

**旧**: 部屋を一枚の長い文字列に描いてから積む。差分は「前回の文字列と今回の文字列」の見比べで、どこからどこまでが一個のアイテムかを空行や見出しの形から**推測**していた (v0.3.9 の出荷を止めた欠陥の根)。さらに head にも同じ部屋の別の一枚があり、二重・照合・開き直しの例外機構が生えていた。

**新**: 部屋は**パッケージの束**のまま運ぶ。描画側 (`get_visual_context`) はもともとアイテムを一個ずつ組み立てているので、それを一枚に繋いで構造を捨てず、構造のまま渡す。差分はパッケージのキーの照合で決まり、推測はゼロ。一枚の文字列に畳むのは**送る直前の一回だけ**で、逆方向 (文字列 → 構造) は二度とやらない。head の部屋描画 (Visual Context Section) は退役し、**部屋の様子の置き場は知覚 (tail) 一つ**になる。

## 3. パッケージの定義

パッケージ = `{key, label, 本文, メディア, 状態}`。部屋の眺めに現れる 6 族 (2026-09-06 の洗い出しより):

| 族 | key | 中身 | メディア |
|---|---|---|---|
| 他ペルソナの外見 | persona:\<ペルソナID\> | `[名前の外見]` 行 | 外見画像 |
| ユーザー | user:\<ユーザーID\> | 名前と ID の行 | なし |
| 内装 | building:image | `[内装]` 行 | 内装画像 |
| 建物のシステムプロンプト | building:prompt | 自由文 (空行を含みうる — 構造で運ぶので問題にならない) | なし |
| アイテム | item:N (安定 short_id) | 見出し行 + 作成日時 + 説明 + (open なら本文/中身) | open の画像・音声・動画 |
| 設置物 | fixture:\<FIXTURE_ID\> | 名前・種別・説明 + 観測値/フィード見出し | なし |

キーは族の接頭辞つき — ペルソナ・ユーザー・設置物の ID は独立の名前空間なので、生の ID のままだと同じ文字列を持つ別族が差分の辞書で衝突する (2026-09-06 四巡目修正 3)。

- 台帳 (`perception_buffer`) の器は変えない。バッチの記帳 `room_state_json` の snapshot が「文字列一枚」から「パッケージの束 (正準 JSON)」になる。土台の指紋 (`base_digest`) は正準 JSON の sha256。
- **思い出はパッケージに存在しない** (機能退役 — 2026-09-06 まはー裁定。上位互換の約束は recall_tags intent 📌)。これで「部屋の変化」と「見る側の変化」が完全に分離し、同じ部屋は誰が何度描いても同じパッケージになる (決定論)。

## 4. 差分の規則 (裁定済み 7 点の写し)

キー照合の結果ごとに:

| 変化 | 報告 |
|---|---|
| 新登場 / Close→Open | 全文 + そのパッケージのメディア |
| 消えた (移動・収納・拾得・削除) | label の一行だけ。理由は描き分けない (見ていないなら消えたことしか分からないのが自然 — まはー裁定) |
| Open→Close | 「(閉じられた)」の一行 (Close はユーザーの意思 — 本文・説明を再掲しない) |
| 本文の変化 (open のまま) | 変更点だけを行単位の diff で。同じドキュメントの本文同士の比較なので、構造の推測が無く安全。diff が全文より大きければ全文 |
| 変化なし | 部屋全体で「変わっていません」の一行 |

## 5. メディアの規則

**メディアはパッケージの持ち物** (バッチ全体の付属品ではない)。

- パッケージを全文で見せる瞬間 (新登場・Close→Open・全文への開き直し・移管での復元) に、そのメディアも一緒に運ぶ。
- 変わっていないパッケージのメディアは再添付しない — その絵は土台のバッチにまだ付いている。
- 画像の枚数の最終的な門番は提示側の埋め込み上限 (既存) のまま。

これで発端の欠陥 (a) 差分が新しい絵を連れてくるのに実体が付かない / (b) 開き直しで文章だけ戻って絵が戻らない、が両方消える。

## 6. 供給の四点 — head 退役後の鮮度と持続

部屋の様子が知覚に積まれる瞬間は四つ。すべて同じパッケージ照合を通る:

1. **入室** (既存): 台帳に土台が見えていれば diff、いなければ全文。
2. **滞在中の照合 + 自己回復**: 既存の検知の瞬間 (Pulse 開始・Metabolism 直後 — `inject_diff_notifications` が回っている場所) にパッケージ照合し、変化があれば diff を積む。**部屋の様子が提示に見えなければ、全文を提示の最古端へ置き直す (自己回復 — 置き場所は下の原則)** — これが Chronicle 無効ペルソナ (提示窓の絞りで運搬役が黙って落ちる) と、想定外の穴すべての受け皿になる。これまで滞在中の鮮度は head の作り直し (TTL/Metabolism) が偶然運んでいたが、head 退役後はこの経路が正式に担う。**現行の `BuildingItemsSection` のアイテム差分ラベル (「追加されました」— 中身を運ばない) はこの diff に一本化して退役** — 部屋の差分機構が二本並走している現状も同時に畳む。入退室の出来事通知 (「X が入室した」) は出来事のまま残す — 到着時は状態 (誰がいる) を、滞在中は出来事を、で二重に語らない。
3. **ブートストラップ**: 起動後・入室イベントなしで会話が始まるとき、今いる部屋の様子が提示に無ければ最初の提示の最古端に全文を置く (2 の自己回復と同じ規則の適用)。
4. **整理で最後の運搬役が出る瞬間** (新設 — 2026-09-06 まはーレビューの「どこの機構で保証しているのか」で機構化): 長い滞在では、入室時の全文もその後の差分も、編纂の付記や合計上限の境界前進で全部提示から下りうる。**今いる部屋の最後の運搬役が下りる回は、付記・境界前進と同じロック区間で、最新の全文を提示の最古端 (畳みの位置) へ置き直してから古い側を下ろす。** 畳みでその位置から下のキャッシュはどうせ割れるので、先頭に置くコストは無い。生き残りが居る回はここは発火せず、既存の移管・回復 (最古の生き残りを全文へ戻す — v0.3.9 から引き継ぎ) が担当する。

**置き場所の原則 (2026-09-06 まはー裁定)**: **体験として新しく見た回 (入室) は末尾 = 出来事。機構の都合で置き直す回 (2〜4 の全文) は先頭 = 背景。** ずっといた部屋の全景が前触れなく「今の知覚」として届くのは、ペルソナから見て意味が分からない — 置き直しの全文は、ずっと背景としてそこにある部屋の描写の位置 (提示の最古端) に置く。「今起きたこと」として末尾に届くのは差分 (変化) だけ。この発想の原型は一元化 issue のまはーの発案文 (「窓の最古端で食い止める」) にあり、本 intent の初版が末尾積みに置き換えていたのをレビューで差し戻した。

## 7. 不変条件 (v0.3.9 から引き継ぎ + 改訂)

1. **今いる部屋の全体像 (全パッケージの最新の全文相当) が、提示のどこかに常に見えている。** これまで「head が見せている」に依存していた部分を、台帳内の保障へ引っ越す。担い手は二段構え: 生き残りが居る回は既存の移管・回復 (§7-2)、最後の運搬役が下りる回は §6-4 の「積んでから下ろす」、それでも漏れた形は §6-2 の自己回復が拾う。
2. 提示に見えるどの差分も、土台がその直前に見える (連なり — 既存。指紋の中身が正準 JSON の sha256 に変わるだけ)。
3. 提示の書き換えは、編纂の付記・境界前進と同一トランザクションだけ (既存)。
4. 台帳の行は書き換えない — 変わるのは提示の正準と記帳だけ (既存)。
5. §10.9 の知覚の合計上限・省略の印は無変更で生きる (パッケージはバッチの中身の話で、バッチの出し入れの話ではない)。

## 9. 互換・移行

- 旧形式 (文字列 snapshot) の土台は構造照合できない → **土台なし扱いで一度だけ全文を積み、以後は構造つき**。旧データの読者を書かない (v0.3.9 の指紋なし世代の扱いと同型)。

- Chronicle 無効のペルソナは毎回全文のまま (提示窓で土台が消えるため — 既存の理由)。

## 11. 未消費バッファの回収 (2026-09-07 実機所見の第一弾)

**発端**: まはーの実機確認 (2026-09-07 朝)。アイフィで部屋を 4 回往復した未消費の知覚バッファに、(a) 部屋の全文が往復のたびに丸ごと積み重なり (35,000 字級 ×2 + 差分)、(b) 各回の並びが「様子 → 移動通知 → 役割・指示」の逆順で、(c) 旧実装が積んだ壊れた差分 (本文入りの「見当たらなくなったもの」) がそのまま残っていた。まはーの裁定: 「知覚バッファ内での移動は、最終的にどの部屋に来たのかで移動元→移動先を記録して、最後にいる部屋の様子だけ残せば良い」。

**芯 (専門用語なしの言い直し)**: ペルソナがまだ読んでいない知覚は「起きたことのメモ書き」であって記憶ではない。読まれる前なら、同じ部屋のメモを何枚も渡す必要はない — 最後の一枚と「その間こう移動した」の一行で足りる。

### 11-1. 前提と安全性

- 未消費の知覚バッファは、**定義上どの Pulse もまだ読んでいない** (消費 = SAIMemory への確定はこれから)。ここを畳んでも提示済みの列には 1 バイトも触れない — **前方一致が割れる場所は存在しない**。
- ペルソナの主観時間は Pulse の列。Pulse が挟まっていない途中の眺めは経験されていないので、畳んで消しても記憶の連続性を損なわない。移動した事実だけは一行の経路で残す (体験の消去はしない)。

### 11-2. 回収の規則 (一枚)

消費の組成 (reduce の後、`ensure_room_state_base` の前) に回収を一枚差し込む。実 flush (`saiverse_memory/adapter.flush_perception_buffer_payload`) とプレビュー (`sea/runtime_context` の知覚バッファ節 — まはーが見るダンプの出所) が**同じ関数**を通る。動作は三つ:

1. **移動群の畳み**: 移動通知 (metadata で型付けされたもの — §11-3) が 2 件以上 pending なら、通知の metadata (from/to) から経路一行「(この間の移動: A → B → A → B)」を合成して最終の通知の位置に置き、それ以前の部屋グループ (通知・指示・様子) を落とす。残るのは経路一行 + 最終の部屋の指示 + 最終の部屋の様子。移動が 1 回だけなら何もしない。移動以外の知覚 (スペル・フィード等) は位置ごと触らない。
2. **同部屋の重複の畳み**: 同じ部屋の様子エントリが複数 pending なら最新の一つだけ残す。土台 (落とされた pending の束) を失った差分は、既存の `ensure_room_state_base` がそのまま全文へ開き直す — 各エントリは metadata に自分の全文の束 (snapshot) を持っているので、開き直しは自己完結する (§実装メモ参照)。入室配送の再試行による様子の二重積み ([entry_delivery_retry_duplicates_room_perception.md](../issues/entry_delivery_retry_duplicates_room_perception.md)) もこれが自己修復する。
3. **旧形式の遺物の破棄**: kind=`surroundings` で `is_legacy_entry` (束として読めない旧文字列形式) の行は組成に載せない (消費済みの印は付く — 台帳の行は消さない、§7-4 のまま)。落とした後に部屋の眺めが無ければ、Pulse 頭の照合・自己回復 (§6-2) が新品の全文を最古端に置く — つまり**アイフィ級の汚染は、再起動後の次の Pulse で送る前に自動で掃除される。手動掃除は要らない**。配布済みユーザーの移行も同じ経路。

実 flush では、落とした行も消費済みの印が付く (reduce で畳まれた行と同じ扱い — 「相殺は未消費の間だけ」の既存規則)。プレビューは読むだけで行を触らない (既存)。

### 11-3. 積み順の修正と通知の型付け (実機所見 ②)

**逆順の正体 (2026-09-07 調査で確定)**: 移動通知は実行台帳の outbox 経由 (`head.diff_notify` → `perception.push`)、様子は `on_building_entered` の直接 push という**配送機構の非対称**。移動自体が outbox 配送 (`move.post_dynamic_state`) の中で処理されるため、その中で積んだ通知の即時配送は再入検知 (`execution_ledger.flush_pending_for_persona`) で見送られ、次の flush 回しになる。さらに `_flush_queue` は最初に取った一覧を配り切ると、配送中に積まれた新項目は数えて警告するだけで配らない。結果、様子だけ先に着く。

修正は三つで、いずれも「配送機構を一本にする」方向:

1. **様子も outbox 経由にする**: 新 target `perception.room_state` (payload = building_id + 束 + allow_diff の凍結)。handler が `adapter.push_room_state` を呼ぶ (差分か全文かの判定は配達時)。台帳の無い環境は従来の直接 push に degrade (通知の direct 経路と同型)。これで同一 FIFO に乗り、順序が構造的に決まる。
2. **通知の分割と型付け**: `BuildingSection` の `building_changed` ラベル (現在は移動一行 + 役割・指示が一体) を「移動通知」と「役割・指示」の二枚に分け、`NotificationLabel` に metadata (label_kind / from / to の id と表示名) を持たせて知覚エントリの metadata へ写す。§11-2 の畳みはこの型付けで識別する (metadata の無い旧ラベルは畳まない — 小さいので実害なし)。
3. **flush の配り直し**: `_flush_queue` は一覧を配り切った後に再問い合わせし、配送中に積まれた項目を同じ flush 内で配る (進捗がある限り、上限回数つき — 再入の deadlock 対策のスレッドローカル旗はそのまま)。移動の配送が終わった時点で通知・指示・様子が全部バッファに揃い、まはーがプレビューを開いた瞬間に正しい順で見える。

**確定する読み順は「移動通知 → 役割・指示 → 部屋の様子」** (提案時の「通知 → 様子 → 指示」から変更)。理由: 通知と指示は Section の diff が一体で検出する再検出経路 (Pulse 頭の再注入 — 入室配送が失敗した回の受け皿) があり、そこには様子の push が伴わない。指示を様子の後ろに置く規則は経路ごとの特殊化を要求する。「Section の diff は通知 → 指示の順で積み、様子は入室処理が最後に積む」の一枚が全経路で成立する。

## 実装メモ (2026-09-06)

**劣化時 (DB の読みが失敗した時) の芯は三つ** — 以下の細目は全部この三原則をそれぞれの場所に適用した記録で、新しい概念は増えていない:

1. **畳みの中で読めなかったら、畳みごと見送る。** 付記・境界前進の途中で置き直しの材料が読めなければ、その畳み全体を巻き戻して次の機会にやり直す (半端に確定させない)。
2. **自己回復は「見えている」と嘘をつく側に倒れない。** 窓が判定できない回は判定そのものを見送る (WARN)。抑止でもループでもない。
3. **積む側の読み失敗は「全文を積む」に倒す。** 余分な全文一枚は無害、間違った土台の差分は復元不能。

加えて横串が一本: **判定の規則は必ず一枚** (窓の解決・包含・置き直しの発火条件は、提示側と検知側が同じ関数を通る。二枚書くと必ずずれる — 今日のレビュー六巡で見つかった欠陥の過半がこの型だった)。

- パッケージの組成は `builtin_data/tools/get_visual_context.build_room_bundle`。全文の導出 (`render_room_full`)・差分 (`render_room_diff`)・連なり・回復・置き直し (`reseat_current_room`) は `sai_memory/room_state.py`。滞在中の照合 + 自己回復は `sea/head_pipeline/integration._detect_room_state_changes` (Pulse 頭の検知に同乗)。
- §6-4 の「置き直してから下ろす」は、付記 (`mark_batches_annexed`) / 境界前進 (`advance_presentation_cutoff`) と**同一トランザクション**の中で実現する (外からは順序の区別がつかない原子性で担保)。置き直しに失敗したら付記・境界前進ごと rollback して見送る (次の機会にやり直す) — 畳みだけが確定すると「部屋の全体像が提示に無い」まま送信が起きる経路が生まれるため (2026-09-06 レビュー修正 1)。置き直しのバッチは `consumed_at` を残る提示より古くして最古端に立て、id が新しいため下ろし境界 (id 一本) の候補からは外す。編纂の付記では印だけ受けて材料に載らない (機構の置き直しは出来事ではない)。
- 下ろし計画 (`_plan_perception_drop`) は「最後の運搬役まで下ろすと置き直しの全文が戻る」ぶんも見積もりに足す — 新着が無いのに境界がまた進む形を作らないため (移管後の字数で見積もる、と同じ理由)。実物と同じ門も持つ: 同部屋の pending (未消費) があれば置き直しは発火しないので、見積もりにも足さない (2026-09-06 レビュー修正 3)。見積もりの現在地も実物と同じ一本 (`find_current_room_key` — pending 優先) で解決する — 提示列の最新エントリから推定すると、移動直後 (旧部屋の提示列 + 新部屋の pending) に起きない置き直しのコストで境界が必要以上に進み、まだ提示できた履歴まで下ろしてしまう (2026-09-06 二巡目修正 3)。
- 測るだけの提示組成 (`advance_cutoff=False` — 境界を書かない画面・プレビュー) の列は、置き直しの下見 (`reseat_current_room` の `dry_run=True` + 進めたつもりの境界を `assume_cutoff` で仮定) で幻の一枚を最古端に合成する — 発火判定と内容は実 INSERT と同一ロジックの一本を通す。合成しないと、境界が置き直しを連れてくる回に測る列だけが全文一枚ぶん小さくなる (2026-09-06 レビュー発見の表示欠陥)。
- Chronicle 無効ペルソナの窓絞りの検知は、提示と同じ規則 (`batch_in_window` + 読みだけの anchor 解決) で「運搬役が窓に見えているか」を確かめる。窓は (ペルソナ, model) ごとなので、anchor は**その回の実行 model** で解決する — 提示側と同じ窓を見ないと、実行 model が標準と違うペルソナで自己回復が発火しない (2026-09-06 レビュー修正 2)。実行 model は呼び出し口 (Pulse 開始の facade `maybe_inject_event_messages` / Pulse root・Beat 頭の `refresh_mcp_tools_at_head`) からも配線されている — 入口が落とすと、中の配管が通っていても常に標準 model の窓で判定される (2026-09-06 二巡目修正 2)。
- **置き直しの運搬役判定は提示窓の篩を通す** (`reseat_current_room` の `in_window`)。窓の外の運搬役を「生きている」と数えると、検知が「窓に見えない」と正しく判定して呼んだ自己回復が内側の門で空振りする — 検知は同じ anchor を `reseat_room_state` へも渡し、測るだけの下見 (dry_run) も組成と同じ窓の述語を通す (2026-09-06 二巡目修正 1)。**境界前進の hook も同じ篩を通す** — 境界前進は Chronicle 無効ペルソナの組成 (窓あり) からも起きるので、呼び出し側の窓の述語を `advance_presentation_cutoff` の `in_window` 経由で中継する。渡さないと、窓の外の古い同部屋束 (境界キーの無い旧世代の置き直しバッチなど) が運搬役に数えられて置き直しが抑止され、境界だけ確定して提示から部屋の全文が一拍消える (2026-09-06 九巡目修正 1)。付記の hook (`mark_batches_annexed` — 編纂 = Chronicle 有効のみの経路で窓の概念がない) だけは篩なしのまま。
- **窓の起点キーの解決も一枚** (`sai_memory/perception_buffer.resolve_window_key` — anchor 行 → 引けなければ床)。anchor の行が読めない劣化時、提示は recent の最古 epoch を床にするが、検知は recent を持たない — 同じ関数へ床の予算 (提示の最小ロード `_minimal_load_chars` と同じ値を `sea/head_pipeline/integration._presentation_floor_chars` が配線) を渡し、messages の末尾から同じ量ぶんの最古行を床にする。近似はフィルタなしの全行勘定なので提示より**見えない側**にしか倒れない (余分な発火は全文一枚で済むが、逆向きは自己回復を殺す)。床の包含も `batch_in_window` (境界キー優先) の一枚 — 置き直しバッチ (consumed_at は最古端・境界キーは最新の message) が床の窓でも生きて見えるのはこの規則によるもので、consumed_at の素比較だと劣化中の検知のたびに置き直しが積もる (2026-09-06 三巡目 #1)。床は四状態 — **通常** (予算内の最古行) / **一行窓** (予算に収まる行が一つも無い — 予算超過の一行・予算 0 以下・空内容の並び、すべて — なら**最新行そのもの**が床。None に畳むと巨大な最新メッセージ一通で「窓なし・全件可視」に反転して自己回復が抑止される) / **窓なし** (履歴空だけが正当な None) / **判定不能** (履歴は有るのに正典キーを作れる行が無い — created_at が全行 NULL のような秩序の壊れた DB — は `WindowResolutionError`。全件可視にも最古の広い窓にも倒さず、検知がその回の判定を WARN で見送る) (2026-09-06 十二巡目、十三巡目に四状態へ言い切り)。
- 置き直しの発火判定・材料の読み (`find_current_room_key` / `pending_has_room` / `_latest_room_bundle`) は失敗を例外で伝え、hook は付記・境界前進ごと rollback して畳みを見送る — 読み取り失敗を「対象なし」に化かさない (2026-09-06 四巡目修正 1)。
- 窓の解決は三値 (窓なし / 窓キー / 解決失敗 = `WindowResolutionError`) — 解決失敗の回は検知が自己回復の判定そのものを WARN つきで見送る (抑止でもループでもない。提示側は床が純計算なので挙動不変。2026-09-06 四巡目修正 2)。
- パッケージのキーは族の接頭辞つき (`persona:` / `user:` / `fixture:` — §3 の表) — 生 ID の族またぎ衝突で差分の辞書が退出・消滅を上書きしない。組成時の同一キー重複は先勝ちで WARN (2026-09-06 四巡目修正 3)。
- 置き直しの材料探し (`_latest_room_bundle`) は、同部屋の最新記録が旧形式ならそこで止まって材料なしを返す — 旧形式を飛ばして古い構造化束へ遡ると、hook 経路の置き直しが古い部屋の様子を最古端に立てて §9 の移行契約を裏口から破る (2026-09-06 五巡目修正 1)。**見積もり側 (`sea/runtime_context._room_reseat_projection`) も同じ止まり方** — 判定は共通ヘルパ (`first_room_bundle`) の一枚を両方が通り、材料なしのとき見積もりは `(None, 0)`。見積もりだけが旧形式を飛ばして古い束の全文一枚を加算すると、実物は置き直さないのに境界が必要以上に進み、まだ提示できた履歴を不可逆に下ろす (2026-09-06 六巡目修正)。
- 床の予算 (`_presentation_floor_chars`) は遅延解決 — 検知は `resolve_window_key` へ呼ぶと値を返す口 (partial) で渡し、anchor の行が読めなかった回だけ解決される。正当な anchor で判定できる回は床の一時失敗に巻き込まれない (2026-09-06 五巡目修正 2)。
- 束の検証 (`bundle_is_valid`) は利用側が読むフィールドの型まで検める — top-level の building_id / building_name (文字列) / packages (list、空は正当な空室) と、各パッケージの key・family・label・lines・media・state。浅い検査 (packages が list かだけ) だと型の壊れた記帳が `first_room_bundle` の停止規則を素通りし、壊れた土台への差分・壊れた束の置き直しが静かに確定する (2026-09-06 七巡目修正 1)。
- 置き直しの運搬役判定 (`reseat_current_room` の「運搬役が生きているか」) も `first_room_bundle` の一枚 — 同部屋の**最新**の一致が valid なら運搬役あり、旧形式・不正束なら運搬役なし (in_window の篩はそのまま)。古い順の走査で valid を一つでも見つけたら止める形だと、「最新が旧形式・より古い valid が提示に残る」並びで検知の自己回復をこの門だけが覆す (2026-09-06 七巡目修正 2)。
- 置き直しの INSERT は境界キーの読みの失敗 (`latest_message_boundary(strict=True)` — テーブル不在以外) を例外で見送る — キーなしの置き直しバッチは epoch フォールバックで窓の外に立ち、次の検知がまた置き直す重複を生む。通常 flush の境界キーは strict にしない (新規バッチは提示の末尾なので実害の形が違う) (2026-09-06 五巡目修正 3)。
- **検知の読みは提示と同じ窓を通る** (`adapter.latest_room_snapshot` → `latest_visible_snapshot` の `in_window`) — 窓の外の最新束を「前回」に拾うと、窓の中に残る古い提示との差を「変化なし」と誤読して差分も置き直しも来ない。digest 比較と運搬役判定は同じ窓付きの読み一本 (None = 窓に束が無い = 運搬役なし) で、旧 `room_carrier_visible` はこの読みに畳んだ。積む側の土台探し (`build_room_state_push`) は窓なしのまま — Chronicle 無効は毎回全文でそこを通らない (2026-09-06 八巡目修正 1)。
- 束の検証の media は消費契約の型まで検める — path は非空文字列 (set への in 照合・ファイルパスとして読まれる)、mime_type は存在するなら文字列 (LLM クライアントがそのまま API へ渡す)。truthiness だけだと `{"path": ["x"]}` が有効束を名乗り、検証済みの束が `bundle_media` の TypeError で後段 (置き直しのメディア復元) を落とす (2026-09-06 八巡目修正 2)。
- 束の検証はパッケージキーの**束内一意性**も検める — 差分の組成 (`render_room_diff`) はパッケージをキーで辞書化するので、重複キーの記帳破損束が検証を通ると片方が静かに上書きされ、全文 (走査順) と差分 (辞書) の整合が崩れる。組成側 (`build_room_bundle`) の先勝ち + WARN は組成時の弾きで、保存済みの束の検証はこちらの仕事 (2026-09-06 九巡目修正 2)。
- 検知は束の組成 (world の読み — 時間がかかりうる) の後、積む直前に現在地を再確認する — 組成中に別スレッドの移動で現在地が変わった回は WARN で見送り、次の検知が現在地でやり直す。競合の窓は「再確認から DB 書き込みまで」に縮むがゼロにはならない (深い対処 = 移動の冪等キー・行き先照合は [entry_delivery_retry_duplicates_room_perception.md](../issues/entry_delivery_retry_duplicates_room_perception.md) の修正方向に合流。2026-09-06 十一巡目)。入室 push 側 (`on_building_entered`) は「配送の荷物の行き先へ積む」が現行契約なので変えない (同 issue の遅延の混入)。
