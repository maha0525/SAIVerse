# Handoff 2026-05-09: 自律稼働中の長期 idle 脱出機構 + Track 最終発話時間の可視化

**親**: [README.md](README.md)
**前回 handoff**: [handoff_2026-05-08.md](handoff_2026-05-08.md) — Phase 3 A 残件 (meta_user 系削除 + スケジュール pre_spells 適用)

このセッションの直前に **Track Chronicle 機構 (v0.32) + ユーザー会話 Track 親スレッド保持機構 (v0.33)** を実装・commit (`96a789c`) した。動作確認の中で「自律稼働中に勝手にユーザー会話 Track が active になり、それ以降メタ判断が止まり自律稼働が継続できない」症状が顕在化したため、その対処として本ハンドオフを起草。

---

## 1. 背景: なぜメタ判断が止まるか

`MetaLayer.should_fire` (`saiverse/meta_layer.py:262-273`) と `on_periodic_tick` (`saiverse/meta_layer.py:392-402`) の両方で、**running Track の Handler が `post_complete_behavior=='wait_response'` ならメタ判断を skip** する仕組みがある。

`UserConversationTrackHandler` がこれに該当 (`post_complete_behavior='wait_response'`、`saiverse/track_handlers/user_conversation_handler.py:79`)。

**設計意図** (intent B v0.8、`02_mechanics.md` より):

> 対ユーザー Track での発話完了直後をメタレイヤー判断のトリガにすると、ユーザーの返答を待たずに次の判断に走る不適切な挙動になる。「ユーザーの返答を待つ」のが基本姿勢。

= ユーザー発話直後にメタ判断で別 Track に切り替えると対話が崩れる、という対話 UX 保護。**この設計判断自体は正しく、抑制ロジックは維持する**。

## 2. 現症状の本質

問題は抑制自体ではなく、**長期 idle 時の脱出経路が無いこと**:

1. ペルソナが自分でメタ判断時に user_conversation Track を `track_activate` する (これは正常な拡張パスで、「自分から話しかける」可能性のために残すべき。元凶を絶つ案 = メタ判断 prompt で activate を禁ずるのは将来の拡張可能性を潰すので NG)
2. activate 後、`post_complete_behavior='wait_response'` 抑制でメタ判断が止まる
3. ユーザー発話 alert が来るまで脱出できない → 自律稼働が完全停止

加えて副次的な問題として:

- **過去のメタ判断ログ独白を真実と誤認**: 数時間前の独白で「Track は running 状態で安定している」と書いた内容を、後の判断時に「現在の事実」として引きずる。実際は pending に落ちていて、最終発話から長時間経過しているのに認識できていない
- **時間経過の客観情報が見えていない**: 各 Track の最終メッセージ時間がメタ判断 prompt に含まれていない。「この Track は 3 時間前で最後だった」という時間感覚が無い

## 3. 次セッションの目標

```
[作業 1] post_complete_behavior='wait_response' Track のタイムアウト自動 pause
   ├─ AI テーブルにペルソナ別タイムアウト設定 (USER_CONV_TIMEOUT_MINUTES) 追加
   ├─ EventScheduler でタイマー予約
   ├─ タイムアウト到達時: pending 落とし → メタ判断発火 → AutonomyManager タイマー再開
   └─ 対象は wait_response 全般 (将来の他 wait_response 系 Track も自動でカバー)

[作業 2] 各 Track の最終メッセージ時間の可視化
   ├─ 取得方法: messages.created_at の MAX (origin_track_id でフィルタ) を Track 別に算出
   ├─ UI (TracksViewer 等) で表示
   └─ メタ判断 prompt 内の Track 一覧に注入 (= ペルソナの判断材料に追加)
```

両方ともユーザー会話 Track 限定ではなく、**`post_complete_behavior='wait_response'` 全般 / 全 Track 一律の機構**として作る。

## 4. 作業 1: タイムアウト自動 pause

### 確定仕様

| 項目 | 値 |
|------|---|
| デフォルトタイムアウト | **30 分** |
| 設定の置き場所 | **AI テーブル (ペルソナ別)** ※環境変数ではない (普段使うモデルにより適切値が変わるため) |
| 対象 Track | `post_complete_behavior='wait_response'` 全般 |
| タイムアウト発火時の挙動 | **pending に落とす + メタ判断発火 + AutonomyManager タイマー再開** |

### 設計判断の根拠

- **ペルソナ別設定**: 軽量モデルと重量級モデルで「自然な対話の間」の長さが違う。環境変数で全ペルソナ一律にすると合わない
- **wait_response 全般**: 同じ構造の問題は将来の他の応答待ち型 Track でも起きる。Track 種別ハードコードでなく属性ベースで判定
- **メタ判断発火 + AutonomyManager タイマー再開**: 単に pending に落とすだけだと自律稼働再開のトリガが無い。タイムアウト = 「今この Track が終わったので次を判断すべき」という能動的な状態変化なので、メタ判断発火で「次に何をするか」決めさせる

### 実装の流れ

1. **DB スキーマ拡張**:
   - `AI` テーブルに `USER_CONV_TIMEOUT_MINUTES` (Integer, nullable, デフォルト 30) カラム追加
   - migration を `database/migrate.py` に追記
   - フロントエンドの SettingsModal で編集可能にする

2. **TrackManager**:
   - `activate(track_id)` 内で、その Track の Handler の `post_complete_behavior` を確認
   - `'wait_response'` だったら EventScheduler に「N 分後に自動 pause」を予約
   - キー例: `f"track_wait_response_timeout:{track_id}"`
   - 同 Track が再度 active 化されたら予約は上書き (= タイマーリセット)

3. **タイムアウト callback**:
   - 該当 Track が今も `running` のまま + 最終メッセージから N 分経過していることを再確認 (race 回避)
   - `track_pause(track_id)` で pending に落とす
   - メタ判断を発火 (`MetaLayer.on_periodic_tick(persona_id, context={"trigger": "wait_response_timeout"})` 相当)
   - AutonomyManager にタイマー再開を要求

4. **既存実装との整合**:
   - `Phase 4-e` で実装済の `EventScheduler` を流用する (`saiverse/event_scheduler.py`)
   - `TrackManager._schedule_waiting_timeout` (waiting Track 廃止予定) と似た構造で実装可能
   - waiting 廃止作業 ([phase_3_lines_playbooks.md §待ち機構の整理](phases/phase_3_lines_playbooks.md)) と並走できる

### 注意点

- ペルソナがそのアクティブ Track の中で、Pulse 完了直後 `wait_response` で停止したまま `last_active_at` も更新されない可能性 → タイマー基準は **`last_active_at` ではなく Track 紐付きメッセージの最新 created_at** で見るのが正しい (= 作業 2 の取得値と同じ)
- 現状の `UserConversationTrackHandler` は user_id 別に Track を持つ可能性 → 全 user_conversation Track が独立にタイマー管理されるべき
- **「ペルソナがメタ判断 spell で track_activate した直後にすぐタイムアウトで自動 pause」される事故を防ぐ**: タイマーは「最終メッセージの created_at」を基準に開始すべき (activate 時刻を基準にすると、過去メッセージしか無い Track が即タイムアウトする)

## 5. 作業 2: Track 最終メッセージ時間の可視化

### 確定仕様

| 項目 | 値 |
|------|---|
| 取得対象 | **(b) 案** = `messages.created_at` の MAX (`origin_track_id=?` でフィルタ) |
| 表示先 | **UI + メタ判断 prompt の両方** |
| 表示形式 | 絶対時刻 + 相対時刻併記が望ましい (例: `2026-05-09 14:23:45 (3 時間前)`) |

### なぜ (b) か

- `last_active_at` は Track 状態遷移の時刻なので「最近 activate された」が出てしまう。「最後にやり取りがあった時刻」とずれる
- `(c)` (= role='user' のみの最新時刻) は「ユーザーの最終発話時刻」だが、ペルソナ自身の独白も時間経過の指標になるので含めてよい
- (b) = 「Track 内の活動の最終時刻」が意味的に綺麗

### 実装の流れ

1. **取得関数** (`saiverse/track_manager.py` 等):
   - `get_track_last_message_time(track_id) -> Optional[datetime]` を実装
   - SQL: `SELECT MAX(created_at) FROM messages WHERE origin_track_id = ?`
   - SAIMemory (per-persona DB) から取得

2. **UI 表示**:
   - `api/routes/people/tracks.py` の Track API レスポンスに `last_message_at` フィールド追加
   - `frontend/src/components/memory/TracksViewer.tsx` に表示行追加

3. **メタ判断 prompt 注入**:
   - メタ判断時に Track 一覧をペルソナに見せる経路を確認 (= `track_list` ツール経由か、context 構築時か)
   - Track 一覧の各エントリに `last_message_at` (絶対 + 相対時刻) を含める
   - 既存の `track_list` ツール (`builtin_data/tools/track_list.py` 想定) があれば、その出力フォーマットを拡張

### 注意点

- メタ判断 prompt 内で「最終メッセージから N 時間経過」が見えていることが、過去独白を真実と誤認する症状の対症療法になる
- 将来的にはメタ判断 prompt 自体の改善 (= 「過去ログより現在の Track 状態を信頼せよ」を明示) も並行して検討すべき (本ハンドオフのスコープ外)
