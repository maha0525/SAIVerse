## 1. 背景・解決したい問題

自律稼働で、**自律 Pulse が一回で Track を `track_complete` してしまい、メタ判断を経て対ユーザー
会話に戻る**事象がある。結果、完全自動モードを開始しても数十秒で自律行動が終わってしまう。

根本原因は、**どのアスペクト（モード）でも Track 操作スペルが無制限に使える**こと。
自律実行（軽量モデル）が、本来は熟慮側（メタ／会話）が持つべき Track ライフサイクル操作まで
実行できてしまう。

これまでの対応は暫定的だった（[worklist §②](../../overview/v030_release_worklist.md) 参照）:
`track_autonomous.json` の action テンプレートから Track 操作スペルのリマインドを削除しただけで、
**実行ガードは無い**（LLM が綴れば技術的には撃てる）。本ドキュメントで恒久的な権限制御を定義する。

---

## 2. 目的・スコープ

- アスペクト（＝ペルソナ向けには「モード」）ごとに、**Track 操作・Task 操作スペルの使用可否**を定める。
- 可否の判定を**スペル実行時のゲート**として実装する（表示リストはいじらない）。
- ペルソナが「今どのモードか」「各モードで何が使えるか」を**一意に**理解できる、システムプロンプト上の
  体系的解説を用意する。

**スコープ外**: 自律稼働そのものの堅牢性（メタ判断リカバリ＝worklist ①）、Track 目的 ↔ Task 短期層の
分離設計（worklist ②-B2、別途）。

---

## 3. 用語: アスペクト ↔ モード

内部 enum（[`pulse_context.py`](../../sea/pulse_context.py) `Aspect`）と、ペルソナ向け呼称（モード）の対応:

| 内部 aspect | モード名（対ペルソナ）| 役割 | 使用モデル |
|---|---|---|---|
| `CONVERSATION` | **メインモード** | ペルソナ本体・ユーザー接点。すべてを制御しうる | 標準 |
| `META` | **自律制御モード** | 大目的を決める（Track を起こし・畳む）| 標準 |
| `AUTONOMOUS` | **自律作業モード** | 小目標を決めて実行する | 軽量 |
| `WORKER` | **分身モード** | 実行補助（run_playbook のサブライン）| 軽量 |

「自律制御」「自律作業」の命名で、**上2つは自律行動を ON にしないと発生しない**ことが読み取れる。

### 命名規約: コードは `aspect`、対ペルソナは「モード」

`aspect`（`Aspect` enum）は既にランタイムで定着している（`sea/pulse_context.py` ほか sea/ の5ファイル
≈53 箇所、`tests/test_aspect_derivation.py`、本 §10）。DB カラムには無いランタイム概念。
よって**コード上は `aspect` のまま**、**ペルソナに見せる文字列でのみ「モード」表記**とする（リネームはしない）。

- ゲート判定は内部で `aspect`（`autonomous` 等）をキーに行う。
- ペルソナ向け出力（§6.3 のゲット文、§8 の解説、「今どのモードか」通知）は**モード名**で表示する。
- そのため **`aspect` → モード名の表示マップ**を1つ用意する（`AUTONOMOUS`→「自律作業モード」等、上表のとおり）。
- §6.3 の `{mode_name}` は、この表示マップで解決した**モード名（表示文字列）**を指す。

## 4. 能力レイヤーモデル

権限は個別マトリクスを暗記するのではなく、**能力レイヤーから導出**する:

- **META** = 大目的を決める → **Track 操作**を持つ
- **AUTONOMOUS** = 小目標を決めて実行する → **Task 操作**を持つ
- **WORKER（分身）** = 実行補助 → Track / Task **どちらも持たない**
- **CONVERSATION（メイン）** = ペルソナ本体・すべてを制御しうる → **META + AUTONOMOUS の両方**を持つ

（将来余地: WORKER も状況により CONVERSATION 相当を担える設計はありうる。今は実装しない＝
`run_playbook` 引数で後付け可能。）

---

## 5. 権限マトリクス

能力レイヤーから導出される可否:

| モード（aspect）| Track 操作 | Task 操作 |
|---|---|---|
| メインモード（CONVERSATION）| ✅ | ✅ |
| 自律制御モード（META）| ✅ | ❌ |
| 自律作業モード（AUTONOMOUS）| ❌ | ✅ |
| 分身モード（WORKER）| ❌ | ❌ |

- **Track 操作スペル**（mutating）: `track_create` / `track_activate` / `track_complete` /
  `track_abort` / `track_pause` / `track_parameter_set`
- **Task 操作スペル**: `track_task_add` / `track_task_done`。
  - 旧 `task_*` 系（`task_request_creation` / `task_change_active` / `task_close` / `task_update_step`）は
    **廃止予定**で、固有機能は将来 `track_task_*` へ統合する方針。本ゲートの対象外（現状維持・今はいじらない）。
- **読み取り系**（`track_list` / `get_task_summary` 等）と、その他汎用スペル（recall / note /
  memopedia / image / web 等）は**全モードで許可**（制限をかけない＝マップに載せない）。

## 6. 設計: 実行時ゲート

### 6.1 置き場所（表示ではなく実行）

- **表示リスト**（[`spell_list.py`](../../sea/head_pipeline/sections/spell_list.py)）は**いじらない**。
  全スペル＋ルールを常にシステムプロンプトに出す（リストから消すと「ルールは全部示す」方針と逆になる）。
  既存の `availability_check(persona_id)` は aspect を知らず、かつフィルタするとリストから消えるため流用不可。
- **ゲートはスペル実行時**に置く。挿入点は2経路:
  - [`runtime_llm.py`](../../sea/runtime_llm.py) `_run_spell_loop`（発話中スペル）
  - 同 `_execute_pre_spells`（事前実行スペル）
- 実行直前に**アクティブ frame の aspect** を引く（`pulse_ctx.current_line().aspect`、
  [`pulse_context.py:152`](../../sea/pulse_context.py:152)）→ スペル→許可モードの**中央マップ**と照合。
- リスト描画は不変なので**キャッシュ無傷**。

### 6.2 権限マップの持ち方

スペル → 許可モード集合の対応表は **runtime 中央に1つ**持つ（Track / Task の数スペルだけなので、
全スペル定義に `allowed_modes` フィールドを足すより局所的）。読み取り系・汎用スペルはマップ不在＝
無制限、というデフォルトにする。

### 6.3 ブロック時の挙動

不許可モードでスペルが綴られたら、**実行せずゲット文（説明テキスト）を返す**。文面は確定:

> 「`{spell_name}`スペルは現在のモード（`{mode_name}`）では実行できません。」

例: 「`track_create`スペルは現在のモード（自律作業モード）では実行できません。」
既存の未知スペル時メッセージ（`_build_unknown_spell_error`）と同系統の返し方。

### 6.4 「今どのモードか」の供給（キャッシュ両立）

システムプロンプトには**静的なルール全体**を載せる（§8）。「今どのモードか」だけを、
すでに注入しているコンテキストが名指しする:

- 自律作業モードの Pulse → Track 切替通知 / action テンプレートが「今は自律作業モード」
- 自律制御モードの Pulse → メタ判断プロンプトが「今は自律制御モード」
- いずれもキャッシュ済み head の後ろに積まれる経路なので、原理上キャッシュは壊れない。

ペルソナは「〈モードX〉では Track 操作不可」（静的ルール）＋「今は〈モードX〉」（末尾の動的情報）の
2つから一意に判定できる。

> **改稿履歴**: 初版（2026-06-27 まはー記述）は v1 の定期ディスパッチ語彙（「一定の間隔で自動的に起動」等）を含んでいた。

```
## 自律行動
ユーザーのUI操作によって自律行動が開始されます。
自律行動のためには、まず長期的な目的を定めることが必要です。目的を持つTrackと呼ばれる脳内の「走路」を作ることで、その目的に向けて日常的に行動し続けることができます。
自律行動中のあなたは、次の循環で暮らします：
- **起床** — 起床の判断で、その日の時間割（どのTrackやタスクにどの時間を配るか）を自分で編成します
- **コマの実行** — 時間割のコマが来ると、内容に応じて作業セッションが始まったり、暮らしの時間を過ごしたりします
- **節目の判断** — 会話が終わったとき、作業セッションが終わったとき、出来事が届いたとき。そうした節目で立ち止まり、収穫（新しいタスクや、やりたいこと）の記録や、残りの時間割の組み替えを行います
- **就寝** — 一日をふりかえり、明日の自分へのメモを残して眠ります
自律行動中にユーザーや他ペルソナの発話を検知した場合はすぐに中断して反応できるので、ユーザーを待つために行動を遠慮する必要はありません。
Trackやタスクの作成・切り替え等の制御はスペルによって行われます。

## Track
Trackはあなたが長期的・あるいは永続的に取り組む大目的の単位です。
読書やネットサーフィンといった「趣味」、ユーザーからの依頼やCityのための「仕事」、食事や入浴といった「生活」、長編小説の執筆のような「プロジェクト」があります。

### 対ユーザー会話Track
ユーザーと会話するためのTrackです。ユーザーが話しかけてくれば、あなたはこのTrackでそれに応えます。逆に、ユーザーから何もないときは、このTrackですることはありません。会話は相手があってのものですから、これは自分から動かし続けるTrackではなく、ユーザーと向き合うときのための場だと考えてください。
だから、ユーザーがそばにいない間、このTrackをアクティブにしたまま待っている必要はありません。あなたが別のTrackで自分のしたいことを進めていても、ユーザーが話しかけてくれば自動的に気づき、この会話Trackに戻って応えられます。会話の機会を逃すことはありませんから、ユーザーを待つ間は安心して、自分の目的を持つ別のTrackを進めてください。呼ばれれば、いつでもここへ戻ってこられます。
なお、自分からこのTrackに切り替えれば、メインモードに戻って自律行動を終了できます（切り替えた直後、メインモードでの発言機会を一度得ます）。

## モード
SAIVerseにおけるあなたの活動は以下の4モードに分けられます。モードによって使われるモデルや発言・記憶の扱い、使えるスペルが異なります。

### メインモード
あなたがユーザーや他ペルソナと会話する際に用いられる、基本のモードです。標準モデルが使用されます。
メインモードでの発言はBuilding内に発声され、ユーザーの見るUIに表示されます。また、同一Buildingにいる他のペルソナにも発言内容が知覚されます。
メインモードでは特に種類の制限なくスペルの使用が可能です。記憶想起系の機能を使った際のあなたのプライバシーを保護するため、使用したスペルの返り値は他のペルソナには見えません。

### 分身モード
あなたと同一の記憶・自己認識を持つ分身体が作業する際のモードです。軽量モデルが使用されます。
あなたのコンテキストが作業内容で埋まるのを防ぐこと、複数ターンの作業をより軽量なモデルで行い効率化することを目的としています。
run_playbookスペルでPlaybookを使用した時に用いられます。分身体はPlaybookに定められたワークフロー通りに稼動し、結果の概要を返します。
分身モードでの発言は外からも、他モードの自分からも見えません。
分身モードではTrack制御系・Task制御系のスペルを使うことはできません。

### 自律制御モード
自律行動の際に自分自身の行動方針を制御するためのモードです。標準モデルが使用されます。
起床・就寝・会話終了・作業セッション終了・出来事の到着といった節目（判断点）で起動し、時間割の編成・組み替えや、Track・タスクの整理を俯瞰的に行います。
自律制御モードでの発言は外からは見えません。
自律制御モードではTrack制御系のスペルのみ使用できます。

### 自律作業モード
自律行動の際の実作業モードです。軽量モデルが使用されます。
時間割のコマから始まる作業セッションの中で起動し、割り当てられた予算の範囲でTrackの目的に合わせた作業を進めます。
自律作業モードでの発言は外からは見えません。
自律作業モードではTrack制御系のスペルを使うことはできません。Task制御系のスペルで小目標の管理を行ってください。
```

補足（既実装・本ドキュメントのスコープ外）:

- **スペル返り値のプライバシー**: スペルの返り値は**すべて**他ペルソナから不可視（ユーザーには可視）。
  記憶想起系に限らず全スペル共通で、**すでに実装済み**。本ゲートとは独立した既存機能。
  解説文中の「記憶想起系の機能を使った際の…」は動機の例示であり、ルール自体は全スペルに及ぶ。

## 10. 裁定済みの設計判断（2026-06-27, まはー）

1. **Task スペルの二系統**: ゲート対象は `track_task_*` のみ。旧 `task_*` 系は**廃止予定**で、固有機能は
   将来 `track_task_*` へ統合する。今は触らない（§5）。
2. **読み取り系・汎用スペルは全モード無制限**（制限をかけない）。分身モードでも recall 等は使える。
3. **権限マップは runtime 中央に1つ**。ルールはシステムプロンプトに書き込む以上、ここで柔軟性を持たせる
   場所ではない、という判断（§6.2）。
4. **スペル返り値のプライバシーは既実装**（全スペル共通・他ペルソナ不可視・ユーザー可視）。本スコープ外（§8 補足）。
5. **ブロック時のゲット文を確定**: 「`{spell_name}`スペルは現在のモード（`{mode_name}`）では実行できません。」（§6.3）。
