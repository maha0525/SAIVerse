### `run_meta_user()` メソッド名について

`run_meta_user()` というメソッド名は紛らわしいが、実体は **すべての pulse 経路 (user / schedule / auto / meta_judgment) の汎用エントリーポイント** で `meta_user` Playbook に依存していない (`pulse_controller.py:343` のコメントで明示)。

**判断**: 本 handoff では **リネームしない**。`meta_user` Playbook 削除と同時にメソッドリネームすると影響範囲が大きい (`pulse_controller`, `meta_layer`, `runtime_context` から全部呼ばれる)。リネームは別タスクで実施 (例: `run_pulse` / `run_meta_pulse` への改名)。docstring とコメントだけ更新して「Playbook 名由来でなく、メタレイヤーから走る Pulse のエントリ」と明示する。

### 起点 (最初の作業)

```
1. ruff check で現状クリーンな状態を確認
2. 4 つの Playbook ファイル削除
3. import_all_playbooks.py --force で DB に prune を反映 (`playbook_sync` が古いレコードを削除)
4. sea/runtime_llm.py:812 のデバッグログ条件削除
5. docstring / コメント整理
6. テストデータ整理
7. 全テスト実行 (pytest)
8. 実機 air_city_a 起動 → ユーザー会話 / 自律 Pulse / meta_judgment 動作確認
```

### 検証方法

- `ruff check .` クリーン
- `pytest` 全パス (特に `tests/test_run_playbook_spell.py`, `tests/test_meta_layer.py`, `tests/test_track_manager.py`)
- 実機シナリオ:
  - ユーザー会話 (普通の往復) → `track_user_conversation` 経由で動く
  - 自律 Pulse (`track_autonomous`) → AutonomyManager 経由
  - メタ判断 alert → `meta_judgment` Playbook (これは別物、削除対象ではない)
  - `/run_playbook` Spell 経由 (例: `/run_playbook(name="generate_image")`)

### ハマりどころ

- **DB に古いレコードが残る可能性**: `import_all_playbooks.py` の prune が走らない設定 (環境変数か?) の場合、DB に `meta_user` 等が残る。`scripts/import_all_playbooks.py --force` で確実に削除させる
- **`_basic_chat_playbook()` (in-memory) は残す**: コード上のフォールバック。`basic_chat.json` ファイルだけ削除し、`runtime.py:2137` の `_basic_chat_playbook()` メソッドは残置
- **docstring 整理時に意味を変えない**: `_choose_playbook` のコメントは「fall back の意図」を保ったまま簡略化する (`basic_chat` も無いから単に `track_user_conversation` 一択、と明記)
- **`meta_user_manual` を削除する根拠**: `pre_spells` 経路で代替されたことを revisions に明記しておく

## 作業 2: スケジュール起動経路への `pre_spells` 適用

### 現状

`saiverse/schedule_manager.py:254-325` `_execute_schedule()`:
- `PersonaSchedule.META_PLAYBOOK` で Playbook 名を hardcode (`schedule_management` 等)
- `PersonaSchedule.PLAYBOOK_PARAMS` で JSON 引数保存
- `submit_schedule()` → `ExecutionRequest` 生成 (**`pre_spells=None`**)

### 置き換え方針

1. `PersonaSchedule.PLAYBOOK_PARAMS` に `"pre_spells": ["/run_playbook(name=\"...\")", ...]` キーを追加できるように
2. `_execute_schedule` で `PLAYBOOK_PARAMS` から `pre_spells` を抽出
3. `submit_schedule()` に `pre_spells` 引数を追加し、`ExecutionRequest.pre_spells` に流す
4. スケジュール作成画面 (frontend) でツール指定できるよう拡張 (UI コンポーネント追加)

### 触るファイル

| ファイル | 何をするか |
|---|---|
| `saiverse/schedule_manager.py:254-325` | `PLAYBOOK_PARAMS` から `pre_spells` 抽出して `submit_schedule` に渡す |
| `sea/pulse_controller.py` (`submit_schedule`) | `pre_spells` 引数を受け取って `ExecutionRequest` に乗せる |
| `frontend/components/schedule/...` | スケジュール作成 UI にツール選択 (チェックボックス or プルダウン) 追加 |
| `api/routes/schedule.py` (もしあれば) | スケジュール作成 API のリクエストに `pre_spells` 追加 |

### 起点

```
1. saiverse/schedule_manager.py を読んで _execute_schedule の現在の実装を把握
2. PLAYBOOK_PARAMS に pre_spells を含めて伝播させる (バックエンドのみ先行実装)
3. 単体テストで動作確認 (PLAYBOOK_PARAMS の JSON に pre_spells を入れて _execute_schedule を呼ぶ)
4. UI 拡張は別 PR でも OK (バックエンドさえ動けばまはーが手動 SQL で試せる)
```

### ハマりどころ

- **既存スケジュールとの後方互換**: `PLAYBOOK_PARAMS` に `pre_spells` キーが無い既存スケジュールは `pre_spells=None` で呼ばれる必要がある (現挙動と同じ)
- **JSON parse エラー**: `PLAYBOOK_PARAMS` のパースが失敗した時の挙動を守る (現状の例外ハンドリングを保持)
- **frontend は後追い OK**: バックエンドが動けば手動でスケジュール DB 行を編集して実機検証できる
