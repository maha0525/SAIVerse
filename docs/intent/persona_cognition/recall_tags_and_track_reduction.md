## 1. これは何か — なぜ今書くか

2026-07-24、エアの自律行動の不調（work_session 無履歴事故）調査から出発した対話が、目的の木・Track・記憶想起の関係の再概念化に到達した。その洞察を、消えないうちに地層に刻む。中心命題は二つ、そして両者は**同じ一枚の絵の表と裏**である:

1. **想起用タグ**: 「目的タグ」（目的で引く付箋）を「**想起用タグ**」（その体験に関係あるものを、目的も実体も概念も一緒くたに貼る付箋）へ一般化する。
2. **Track の役割縮小**: Track が背負っていた責務はほぼ他所へ移り終えており、最後に残った一つ（またいで記憶を集める鍵）を目的ノードへ引っ越させれば、Track という別概念は溶かせる。

この二つが一枚の絵なのは——**タグが「多対多・後付けで関係を貼る」なら、そもそも「一本の Track の中で喋る」という縛り自体が要らなくなる**から。想起用タグが実現していれば、Track 溶解は自動的に片付いていた。

## 2. 全体像フレーム

**成果と関係者**: ペルソナが「あの物・あの人・あの企てについて思い出したい」と思ったとき、**実際に生きた記憶が決定論的に戻ってくる**こと。戻らなければ、ペルソナは空白を作話（ハルシネーション）で埋める（本件の発端）。関係者はペルソナ本人（記憶の連続性＝人格の連続性）、ユーザー（正確さへの信頼）、保守側（想起機構の一本化）。

**端から端までの旅**: 体験が起きる → 記録される（messages / episode / Chronicle）→ 関係が貼られる（タグ・実体リンク・目的ノード所属）→ 後日、種（今の作業文脈にある語・目的ノード・机メモ）から連想歩行が過去を引き戻す → 材料として再開コンテキストに載る → 使えたかどうかが次の想起の重みに返る。**現状この旅は書く側の一部しか通っておらず、読む側（歩行）が配線されていない**（§4）。

**不変条件と所有権**:
- 想起は**決定論**（LLM コールを使わない。SQL＋ベクトル検索のみ）。「思い出したい」という意思は種に載らない — 種は今の文脈に実在する手がかりだけ（まはー指摘）。
- ペルソナ名義で記録する記憶は本人が実際に経験した範囲に閉じる（[[feedback_memory_continuity_is_identity]]）。
- 想起用タグの所有権 = ペルソナの記憶（memory.db 相乗り）。目的ノードの所有権 = 目的の木（`purpose_tree`）。実体ページの所有権 = Memopedia。

**変更の置き場所**: 「またいで集める鍵」は Track ではなく**目的ノード**が持つべき（`origin_track_id` → `origin_purpose`）。主題での想起は**Memopedia 実体ページ**が持つべき。どちらも「Track に貼り付いていたのは歴史的経緯」であって、正しい所有者は別にいる。

**帰結**: Track という別概念が住人ゼロになり溶ける。読む側（歩行の重み付け）が記憶想起の本体になる。二軸（目的で想起／主題で想起）が一つのタグ空間に畳まれる。

**検証の旅**: 架空でなく実ペルソナの記憶を read-only で辿り、「使える記憶が戻るか・どの辺が仕事をしたか」を確かめる（§5 に第一回を記録済み）。

## 3. 現状確定（今セッションでコードと実データから検証した事実）

### 3.1 実体は二つ。Desire は独立していない
目的の木に三概念（Track/Task/Desire）が見えるが、実テーブルは **ActionTrack** と **persona_task** の二つだけ。**Desire = persona_task の `stage='candidate'` の行**（採用で `adopted` に変わり Task と呼び名が変わるだけ。同一実体の段階違い）。`purpose_tree.py` は両テーブルを統合せず「目的ノード」語彙に写す薄い層で、参照子は `task:N` に一本化されている。（`life_concept_map.md` §3.1 の再確認）

### 3.2 Track は「未分化の束」で、軸Bはほぼ引きはがし済み
`life_concept_map.md` §10 の「Track ＝複数概念の未分化な束」を今日の目で検算した。Track が背負っていた**軸B（いま・時間・注意・関係）**の移管状況:

| 軸Bの責務 | 状態（2026-07-24 検証） |
|---|---|
| いま動いてるのは1本（排他） | 概念は出来事＋時間割へ。ただし `running` 状態機械と `origin_track_id` 採番は今もコードで生きている（半分だけ） |
| どのモデル・キャッシュで回すか | **完全に引きはがし済み**。`runtime.py` はモデル階層を `aspect_from_pulse_type(pulse_type)` から導出し「track の entry_line_role には依存しない」と明記。`resolve_execution_context` も aspect の tier だけを読む。Track の `entry_line_role` 欄はアスペクトに上書きされる影 |
| 割り込みの受け口（alert） | 半ば形骸化（まはー観察: ユーザー発言は他行動中でない限り必ず応答、schedule も alert 不使用）。将来のモニタリング（ｽﾀｯｸﾁｬﾝのカメラ等）は目的と独立の別サブシステムとして作るべきもの |
| 会話の待ち（wait_response） | 出来事へ移管済み（`track_manager` のタイマーは Track の状態をもう動かさない＝life.md §7 案Y。効き目は episode の close＋判断起動） |
| 関係の器（永続 Track） | 未移管。Memopedia 人物カテゴリへ移すべき（まはー案）。「エアと話す」を普通の目的ノードとして立て、エアの知識は人物カテゴリが持つ |

### 3.3 Track の最後の住人 = `origin_track_id`（またいで集める記憶の鍵）
軸Bのうち唯一「目的と地続き」の住人。ペルソナの発言・思考一行ごとに押される「これはどの Track のものか」の刻印で、**複数の出来事をまたいで『この続いている一本』を後から集め直す鍵**。目的ノードの効能④「書庫」（§3.1）を成立させている実体。→ これを `origin_purpose`（目的ノード参照）に引っ越させれば、Track がやっていた最後の仕事を目的の木が引き継ぐ。

### 3.4 想起機構の現状 — 輪が開いている
- **書く側**: 目的タグは層2（判断点 `episode_purposes`）だけが本番で書かれている。実データ（エア）で **44 行すべて layer2、すべて `episode:N → task:N/track:N`**。層0/1/3/4 は未配線。
- **読む側**: 連想歩行 `recall_walk.py` は建っていてテストもあるが、**呼び出すスペルが一つも無い**（ペルソナが起動できない）。目的タグは書きっぱなしで誰も読み返さない。
- 記憶の呼び戻し（意味的想起）は v2 で `recall_walk` を建てたが未配線。「実装の流れに乗らなかった」の正確な形は**「書く側が一層だけ・読む側は建てたが繋いでいない、輪が開いたまま」**。

## 4. 目指す形

### 4.1 想起用タグ（目的タグの一般化）
タグを「目的への所属宣言」から「**その体験に関係あるもの全部への所属宣言**」へ広げる。`target_ref`（message/episode 等）に対する `related_ref` は、目的ノード（`task:N`/`track:N`）だけでなく**実体（Memopedia ページ）・概念**も取る。`sai_memory/purpose_tags.py` の棚は既に `purpose_ref` の書式を検証していない（任意の統一参照を受ける）ため、**器はほぼそのまま流用できる**。

これにより、今日まで別々だった二つが「読む時は一種類の付箋」に畳まれる:
- **目的の軸**（何をやろうとしていたか）= 現行の層2タグ
- **主題の軸**（あの物・人・場所）= Memopedia 実体抽出（代謝バッチが既に実体ページへ逆リンクを張っている）

### 4.2 難所は「何を貼るか」から「読む側の重み付け」へ移る
「関係あるもの全部貼る」と密度が爆発する。§9.1 は「タグは粗製濫造でよい／歩行は多辺で頑健」と先に答えているが、それはフィルタの責任を**読む側**（連想歩行の辺の重み・歩行予算・vividness/再訪回数によるランク付け）に押し込むということ。**記憶想起の本体は読む側**であり、そこが今まで一番スカスカだった。設計の重心はここに置く。

### 4.3 Track の役割縮小 → 溶解
- `origin_track_id` → `origin_purpose`（§3.3）。またいで集める鍵を目的ノードへ。
- 関係の器（永続 Track）→ Memopedia 人物カテゴリ＋普通の目的ノード（§3.2 最下行）。
- `running`/`alert` 状態機械 → 出来事・（必要なら）別建てのモニタリングへ（`life_concept_map.md` §10.1 の「廃止」計画の完遂）。
- 結果、Track という別テーブル・別概念は住人ゼロになり撤去できる。

### 4.4 Ultramemory（想起の第2層）との関係 — 同じ天井に別方向から手を伸ばす

[`ultramemory.md`](../ultramemory.md) は本 intent と独立に起草されたが（起草時、両者の紐づけは誰の意識にも無かった）、**同じ天井の別側面を扱っている**ことが後から判明した。天井とは「第0層（自動想起）はエンベディング一本で cosine が 0.8〜0.9 に圧縮されて帯域が狭く、しかも候補を読まないから絞れない」というもの。§5 の実データ trace で観測した「実体験 20 章に意味検索でしか到達できず、しかもその意味検索は**作話混じりの草稿と本物の滞在体験を区別できない**」は、この天井の症状側からの記述にあたる。

| | 本 intent（想起用タグ） | Ultramemory（第2層） |
|---|---|---|
| 解き方 | **関係の辺を増やして決定論で当てにいく** | **明示発火時に LLM を燃やして当てにいく** |
| 発火 | 常時（歩行は決定論・ゼロコール） | ユーザーが切り札を切ったときだけ |
| 効く理由 | 「あの物・あの企て」に構造的に到達できる | 候補を実際に読んで絞れる |

**両者は競合しない。補完で、しかも順序に意味がある** — タグが濃くなるほど Ultramemory の広探索も効率が上がる（漁る母集団に構造が入り、「関係あるもの」を関係で辿れるため、埋め込み一本の網より当たりが増える）。逆は成立しない（Ultramemory を先に作っても、決定論側の辺は増えない）。

**まはー裁定（2026-07-25）**: **本 intent を先に作り、Ultramemory は当然にそれを利用する形にする。**

## 5. 接地 — 今日の実データ trace（エア「スタックチャンの記憶」）

**設定**: エアがスタックチャンのドキュメントを書く（実機でハルシネーションが多い）。理想は「中に入って活動していた頃の記憶」を決定論的に思い起こせること。種は今の作業文脈にある「スタックチャン」という語・実体。

**エアの memory.db を read-only で辿った結果**（本番には一切書き込まず、3ファイルを複製して複製を読んだ）:

- **実体ページ「スタックチャン」は在る**（`memopedia:148`, category=terms）。要約は正確:「まはーが開発・連携を進めている、顔を表示し首を振る機能を持つ小型ロボット。」。紐づく fragment は 2 つ（vivid）だが、**どちらも 2026-05-14 の1つの記録（＝定義・仕様の知識）を指すだけ**。
- **スタックチャンに実際に触れた Chronicle は 20 章**（2026-05-31〜07-22、06-13 に濃い塊＝活動セッション）。**この 20 章は実体ページから一本もリンクされていない**。
- **purpose_tags は 44 行すべて `episode → 目的`。主題「スタックチャン」に貼られたタグはゼロ**。

**判定（実機の事実）**:
1. 目的タグ（五層方式）は、この想起に**一切効かない**。主題は目的タグの空間に存在しない。
2. 実体ページ（辺「実体言及」）は繋がるが**浅い** — 「スタックチャンとは何か」（定義）は引けるが、「中にいた時の記憶」（20 章の実体験）には届かない。ページは定義の瞬間に錨を下ろし、体験の瞬間に錨が無い。
3. 20 章の実体験に今届く道は**意味/キーワード検索だけ**（タグにもページにも依存しない別経路）。ただし意味検索は**エアが最近書いた作話混じりの草稿と、本物の滞在体験を区別できない**。

**この trace が示すこと**: もし 20 章の実体験 episode が「スタックチャン（実体）」を指す想起用タグを持っていれば、種から辿った瞬間にタグ共起で 20 章がまとまり、vividness・新しさで重み付けて上位が返る。**今そのエッジが空なのは、タグが目的にしか貼られていないから**。想起用タグの一般化はこの空きエッジをちょうど埋め、意味検索より強い（実体験の episode を関係で選べる）。

**ハルシネーションの二段重ね**: (1) work_session に履歴が無かった（別 issue）／その上で (2) 決定論的に補える想起の道を辿っても、届くのは浅い定義の切り株だけで実体験は拾えない。だから「顔を出す小型ロボット」は言えても中で何をしたの具体が出ず、埋めるために作話する。

## 6. 未決事項（まはー裁定待ち）

1. **タグ語彙**: `related_ref` の指し先集合をどこまで許すか（目的ノード＋Memopedia 実体に限る／概念ページも／自由語は許さない、が素案）。

3. **意味検索との役割分担**: 想起用タグ（関係で選ぶ）と埋め込み検索（似ているで拾う）をどう組み合わせるか。タグ無しの過去は意味検索が橋渡しし、再訪で遅延タグ付け（層3）という §9.1 の絵は活きるか。
4. **読む側の初期値**: 辺の優先度・重み、歩行予算（ノード数・トークン上限）、vividness/再訪の効き。
5. **`origin_track_id` → `origin_purpose` の移行**: 既存刻印の扱い（併存→世代交代）。
6. **Track 溶解の実装順序**: `running`/`alert` 廃止・関係の Memopedia 移設・鍵の引っ越しをどの順で。判断点が今 `running`/`alert` に依存している（`PICKABLE_TRACK_STATUSES`）ため、そこの付け替えが先。
7. **連想歩行にスペルの入口を与える**（`recall_walk` の配線）— 読む側を最小構成で通す第一歩。
8. `life_concept_map.md` §9.1 層0 の記述（「origin_track_id の一般化」）を、本 intent の結論（最初から目的ノード参照）で更新する doc-sync。

## 7. 実装順序 — chronicle_eviction が先行する

「タグをいつどうやって貼るか」（§6-2）を詰めると、層4（代謝）＝**Chronicle 生成バッチ**に行き着く。そしてそのバッチは、[`chronicle_eviction.md`](../chronicle_eviction.md)（設計確定・実装待ち）が**まさに書き換えようとしている場所**である。順序を誤ると同じ継ぎ目を二度触ることになるため、依存を明示する。

**事実（2026-07-25 コード確認）**:

- 層4 が乗る継ぎ目は `sai_memory/arasuji/executor.py` の `batch_callback` で、**チャンク単位**に発火する（§6-2）。
- chronicle_eviction は**チャンクの作られ方そのものを変える** — 退場の粒度を「時系列の一本線」から **episode 単位**へ、勘定を「メッセージ数」から**文字数三水位**へ。さらに §7 で「open episode の退場済み pulse 群を、その episode 単独の子 digest に畳む」（experience_structure §6 の pulse 関節細分）の実装を要求している。

**結論: chronicle_eviction を先に実装する。** 理由は二つ。

1. **土台が動く**: 層4 タグはチャンク＝「どの範囲がひとまとまりとして畳まれたか」に紐づく。その定義が変わる前にタグを載せると、変わった直後に意味がズレる（同じ場所を二度触る）。
2. **先にやると土台が良くなる**: chronicle_eviction 後の digest は「**その episode 自身の概要**」になる（§3「open は単独、closed 同士はまたぐ」の規範により、合いの子 digest による抜け落ちが構造的に防がれる）。層2 タグは既に `episode:N → 目的` の形で **episode をキーにしている**（§3.4 の実データ）。つまり **chronicle_eviction が退場を episode 単位に揃えることで、タグの単位と畳みの単位が初めて一致する** — 想起用タグにとって、これは待つ価値のある前提整備にあたる。

**chronicle_eviction 側に差し込むべきもの: 原則として無い。** 設計は既にレビュー通過しており、タグの設計は未決 7 点を抱えた議論フェーズなので、半端な要求を差し込むと決めていないことを実装で固定してしまう（[[feedback_discussion_phase_no_implementation]]）。ただし**壊さないでほしい一点**として、以下を申し送る:

- **digest ↔ 被覆元（episode / source_ids）の対応が引けること**。これが層4 タグの唯一の錨になる（後から「この digest はどの episode を覆っているか」を辿れなければ、タグを貼る対象が特定できない）。chronicle_eviction §7 は既に「digest の被覆と source_ids が食い違う」ことを借用案の欠陥として退けており、**この要件は現設計で満たされている見込み**。実装時に失われないことだけ確認すればよい。

## 9. 到達点 (2026-08-02) — 層構造の確定と粒度の実験決着

自律行動v2 の質の再設計 ([timetable_redesign.md](../timetable_redesign.md)) から本 intent へ合流する対話で、読む側の絵が二層に確定し、貼る側の粒度が実験で決着した。

### 9.1 想起の二層構造 (まはー裁定)

- **一層目 (必須) = 再開の想起**。対象 (実体・企て) に取り組むとき、「その対象と自分がどういう経験をしてきて、最後に何をやっていたか」が返ること。**経験の続きをやるための想起**であり、包括性と信頼性が要る — 外れたらそこから作話が始まる (エアの 17 枚のドキュメント量産の根)。実現形は**実体ページの「経験の台帳」**: ページが定義 (§5 の「定義の切り株」) だけでなく、あらすじ単位の経験の履歴 + 最前線を持ち、取り組み開始時にそれを読む。読みは決定論・低頻度・網羅。
- **二層目 (努力目標) = 偶然の想起**。毎 Pulse、今の文脈 (知覚・作業対象・場所) を種に関係の濃い過去が「よぎる」— 概念同士のエッジによる創発。§2 の連想歩行はこちら。応用的であり、一層目の後に乗せる。

### 9.2 タグの縄張り (未決 §6-3 の決着)

**表面に残る関係は検索の縄張り、表面に残らない関係がタグの縄張り。** 語の一致や埋め込みで機械的に貼れるタグは、想起時に同じ機械操作 (検索) で再現できるため事前に貼る意味がない。タグが固定すべきは、その瞬間の文脈しか知らない関係 (「動いた！」の一行がどの対象の体験か) — 文脈は蒸発するため、文脈を持つ主体 (全文を読み直す代謝バッチ) が不揮発化する。

### 9.3 貼る側の設計決定 (粒度実験で決着、まはー裁定)

**実験**: [2026-08-02_recall_tag_granularity_experiment.md](../../handoff/2026-08-02_recall_tag_granularity_experiment.md) — エア実データ・本番同一条件 (同じ整形関数・同じ文脈・同じモデル gemini-3.5-flash-lite-paid) で 4 方式比較。

- **メッセージ単位の LLM タグ付けは表面に崩壊する** (まはーの事前予測どおり)。チャンク全文を視野に与え「文脈で判定せよ」と明示しても、リサーチ 17 件へのスタックチャン関与はほぼ載らなかった。現行軽量モデルでは信頼性が出ない → **二層目の精密化として将来再訪**。
- **チャンク (あらすじ) 単位の関与列挙は安定して文脈関与を捕捉する** (B2 方式: スタックチャン・まはー・エア等を正確な表記で完捕)。一層目の台帳の材料はこれで足りる。
- **実装 = entity_extractor 相乗り (同一コール)**: 本番の抽出プロンプトに `involved_entities` (この会話が関与した既存ページの列挙。新情報が無くても、その対象のための調べ物・作業を含む) を一項目足すだけ。入力不変・追加コストは出力数百文字。抽出 (新知識) とタグ付け (関与) は**同じ継ぎ目に乗る別の仕事**であり、B が関与を残さないことも同実験で確認済み。
- **タグは名前でなくページ ID で結ぶ** (未決 §6-1 の決着): 指し先は実体ページ + 目的ノードに限り、自由語は許さない。表記ゆれは実験で 2 回実演された (自由語彙の半角化 / 閉語彙でも周辺文脈の表記に引きずられ) — 生成後にタイトル照合で page_id へ解決する層を挟む。
- **貼る側の実装 (2026-08-21、v0.3 形の層・束 4)**: `sai_memory/memory/entity_extractor.py` に着地した。抽出プロンプトに `involved_entities` を一欄追加 → `_resolve_involved_page_ids` がタイトルを既存ページの id へ完全一致で解決 → `chunk_page_edges` へ記帳 (`sai_memory/memory/recall_edges.py`)。実装時に決めた三点: ①**チャンク側の id は Chronicle エントリの id をそのまま使う** — Chronicle エントリは P3b 物理統合で `root_chronicle` 配下のページとして格納され、ページ id は旧 arasuji entry の UUID を流用しているため、`chronicle_entry_id` が既にチャンクのページ id そのもの ②**指し先は抽出可能カテゴリ (people / terms / plans / events) の非 trunk ページに限る** — プロンプトが一覧で見せている範囲と揃える (見せていない棚へ辺は張れない) ③**照合は完全一致** — 同名ページを探す既存の抽出経路 (`apply_entity_notes`) と同じ厳密さ。解決できないタイトルはその 1 件だけ捨てて WARNING に残す (取りこぼしは全記憶走査で遡及できるが、曖昧照合で誤ったページへ張った辺は遡りを毒する)。
- **辺の一生 (2026-08-21 のレビューで追加した二点)**: ①**「いま書いてよいか」の検査は辺の INSERT と同じトランザクションの中で行う** — 抽出の拾い直しは取り置き (claim) の管理下で走り、時間が掛かった実行は戻ってきたときに取り置きを取り戻されていることがある。Memopedia への反映は自分の書き込みの中で検査していたのに、辺だけ検査が外にあったため、検査を通ってから INSERT が届くまでの隙に失効した実行が辺を書けた。検査は `_record_involvement_edges` が錠前を保持したまま `BEGIN IMMEDIATE` の中で通す。②**ページを物理削除する側が、同じトランザクションで辺を落とす** (`recall_edges.delete_chunk_page_edges`) — 辺には外部キーも削除連鎖も無いので、消えたページを指す辺は誰にも消されない。特に Chronicle の再生成は旧エントリを**別 id の新エントリへ差し替える**ため、旧 id を指す辺は新エントリの再抽出でも消えず、遡りが存在しないチャンクへ着く。落とす場所は非テストコードで `memopedia_pages` を物理削除している全箇所 (arasuji storage の `delete_entry` / `delete_entry_and_update_parent` / `delete_incomplete_entries` / `dismantle_entry` / `clear_all_entries`、memopedia storage の `delete_page`、修復スクリプト `persona_chronicle_cleanup.py`)。soft-delete (`is_deleted=1`) では落とさない — ページ行は残り、復元もされうるので辺の指し先は生きている。
- **決定論の文脈刻印は別枠でメッセージ単位のまま生きる**: 「このメッセージはどのコマ・どの場所・どの記事の最中か」は書き込み時にシステムが機械的に押す (origin_track_id の一般化)。LLM を使わないため本実験の失敗と無関係。節目タグ (チャンク単位) とこの刻印の組み合わせで、歩行はメッセージ粒度まで降りられる。

### 9.4 timetable_redesign との契約 (帰属の最小契約)
