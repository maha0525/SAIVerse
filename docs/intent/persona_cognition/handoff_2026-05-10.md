# Handoff 2026-05-10: メインライン応答の `origin_track_id` が NULL になる回帰バグ

**親**: [README.md](README.md)
**前回 handoff**: [handoff_2026-05-09.md](handoff_2026-05-09.md) — 自律稼働中の長期 idle 脱出機構
**関連 Intent**: [meta_judgment_structured.md](meta_judgment_structured.md) — メタ判断 v2 実装 (本セッションで完了、その実機検証中に本バグを発見)

このセッションでメタ判断 v2 (構造化出力ベース) の実装一巡 + 関連バグ 2 件修正 (commit `e95fa41`) を完了した直後、メタ判断時の Track 一覧で「最終: 3日前」と表示されるのが不自然 (まはー認識では昨日 5/9 17:59 が最終発話) という指摘から調査を開始し、**メインライン応答の `messages.origin_track_id` カラムに NULL が書き込まれる回帰バグ**を発見した。本ハンドオフはその追跡と修正のための引き継ぎ資料。

5/9 のエアの応答は `line_role=main_line, scope=committed` で**メインライン応答として正しく書き込まれている**が、**`origin_track_id` だけが NULL になっている**。

5/9 のメタ判断系 (line_role=meta_judgment) も全て `origin_track_id=NULL` だが、これは旧仕様の `_record_judgment_log` 経路では仕様的に NULL のまま (Track 横断のメタログ領域)。問題はメインライン応答のほう。

### 「3日前」表示は正しく動いている

- `MAX(created_at) WHERE origin_track_id=c6fa3f2d..` = `1778076329` (5/6 23:05:29、JST)
- 現在 5/10 14:54 から見て差 = **3.66 日** → 表示「3 日前」は正確
- タイムゾーンも `_format_relative` の計算もズレていない
- → 表示変換ではなく、データ側 (`origin_track_id` の埋め漏れ) が原因

調査スクリプト (実行済): `temp/check_track_messages.py` / `temp/check_track_messages2.py`

### 5/7 以降のいつかから NULL になり始めた

- `5/5 23:27` 以前: `origin_track_id` 埋まっている
- `5/6 23:05` まで: 埋まっている
- `5/7 〜 5/8` の範囲は `assistant` role でメインライン応答が無い (メタ判断系のみ)
- `5/9 17:59:52` 以降: メインライン応答が NULL

つまり**境界は 5/6 23:05 〜 5/9 17:59 の間**。この期間に commit されたコード変更が原因の可能性が高い。

## 2. 影響範囲

`origin_track_id` が NULL のままだと連鎖的に複数機能が壊れる:

1. **Track の最終メッセージ時間表示** (本件発覚の入口)
   - `SAIMemoryAdapter.get_track_last_message_times` (`saiverse_memory/adapter.py:1695`) は `WHERE origin_track_id IN (...)` で絞り込んで `MAX(created_at)` を取る。NULL のメッセージは拾われない。
   - `track_list` ツールの `last_message_at` / `last_message_relative` が古い値を返す。
   - メタ判断 v2 の状況テキスト「最終: N日前」が常に誤情報を提示 → ペルソナの判断を歪める。

2. **`wait_response_timeout` の base_time** (`saiverse/track_manager.py:_schedule_wait_response_timeout`)
   - provider が「最終メッセージ時刻」を返す経路で同じ MAX クエリを使っている (`SAIVerseManager` 周辺の provider 実装は要確認)。
   - base_time が古いままになり、本セッションで観測した「activate 直後に即タイムアウト → ループ」の遠因の一つにもなった。本セッションで base_time が過去なら `now()` フォールバックする修正は入れたので、ループ自体は止まる。が、根本は本件。

3. **Track Chronicle 生成範囲** (`sea/runtime.py:_generate_track_chronicle` 周辺)
   - 「Track ごとの未処理メッセージ」の集計が `origin_track_id` ベースのため、NULL 化したメッセージは Chronicle にもならない。
   - 本セッション末にコミットした `incomplete Lv1 のカバー範囲スキップ` 最適化 (commit `4a0a042`) も、このデータが正常な前提で動く。

4. **Track 別履歴フィルタ全般**
   - `messages` テーブルを `origin_track_id` で絞る他の経路 (履歴 UI / 検索 / Stelis 等) も影響を受ける可能性あり。

## 3. 原因のあたり

### 該当コード

`sea/runtime.py:_store_memory` (約 1200-1240 行付近) で `origin_track_id` を埋める:

```python
resolved_track_id = origin_track_id  # 引数からくる場合
if pulse_context is not None and (... resolved_track_id is None):
    meta = pulse_context.current_line_metadata()
    ...
    if resolved_track_id is None:
        resolved_track_id = meta.get("origin_track_id")

message: Dict[str, Any] = {"role": role or "assistant", "content": text}
...
if resolved_track_id is not None:
    message["origin_track_id"] = resolved_track_id  # ← ここが None なら set されない
```

つまり、**`PulseContext.current_line_metadata()` が `origin_track_id` を返してきていない / 引数経由でも来ていない**のが直接の原因。

### 仮説

**仮説 A: LineFrame に `origin_track_id` を登録する経路の漏れ**

`PulseContext._line_stack` / `LineFrame` に `origin_track_id` が乗るタイミングは:
- メインライン Pulse 起動時 (`run_meta_user` / `handle_user_input_stream` 経路)
- サブライン Spell (`/run_playbook`) 起動時
- Track 切り替えスペル発動後の deferred apply 直後

直近 commit のうち以下が容疑者:
- `9f03948 fix(sea): tool ノード結果が後続 LLM ノードに見えないバグを修正 + Phase 3 段階 4-D 完了`
  - context_profile / model_type / exclude_pulse_id / pulse_id タグ併行記録 などを一斉削除した大規模リファクタ。LineFrame の構築経路を整理したときに `origin_track_id` の伝播が一部で抜けた可能性。
- `cf946cd feat(persona): wait_response Track 自動 pause タイマー + Track 最終メッセージ時間の可視化`
  - Track 状態遷移経路を触っているので、activate 後の Pulse-root context 構築で LineFrame に origin_track_id をセットし忘れた可能性。
- `96a789c feat(persona): Track Chronicle 機構 + ユーザー会話 Track 親スレッド保持を実装`
  - ユーザー会話 Track 親スレッド保持 (`saiverse/user_conversation_preserver.py`) で履歴を別経路から流し込むように。この経路で書かれるメッセージに `origin_track_id` を渡し忘れている可能性。

**仮説 B: ユーザー発話の経路で origin_track_id が伝播しない**

5/9 の `role=user` のまはー発話も `origin_track_id=NULL` だった。`manager/runtime.py:handle_user_input_stream` でユーザー発話を SAIMemory に書き込む経路で、当該 Track ID を message dict に乗せていない可能性。

メインライン応答だけでなく**ユーザー発話側も同症状**である点は、書き込み経路全体の根の問題を示唆している。

## 5. 短期しのぎ案 (根本修正に時間がかかる場合)

`SAIMemoryAdapter.get_track_last_message_times` のフォールバック:

```python
# origin_track_id が埋まっている前提のクエリ
SELECT origin_track_id, MAX(created_at) ...

# フォールバック: 永続 user_conversation Track などは「メインライン応答の最新時刻」も拾う
# (origin_track_id NULL でも line_role=main_line なら現行 user_conversation の応答とみなす)
```

ただし、この種のフォールバックは **NULL 状態を許容してしまう設計汚染**になるので推奨しない。**まず根本を直してから、フォールバックは入れない**のが良い。

これらは本件と独立して進めて良いが、「Track 最終メッセージ時刻」がメタ判断の判断材料に乗るので、本件が直らないと実機検証時の Track 一覧表示は誤情報を出し続ける点に注意。
