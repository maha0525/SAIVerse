## 1. 要点 (数行で)

SAIVerse は毎ターン、最新の発言の近くに「リアルタイム情報」(現在時刻・リアルタイムスペルの結果) と「自動想起」(ふと浮かんだ記憶) を差し込み、次のターンには消している。消える物が末尾近くにあると、キャッシュとして保持されている前回の送信の範囲と、今回の送信の先頭が一致しなくなる。

キャッシュの境目をこちらから指定できるモデル (Claude の cache_control、Gemini の継続キャッシュ) なら、消える物の手前を境目にすれば済む。指定できないモデル (Gemini 4 Argon の暗黙キャッシュ) では、消える物そのものを無くすしかない。

そこで、**モデル設定で ON にしたモデルでは、差し込んだリアルタイム情報と自動想起を、送った時点でペルソナのデータに残し、次のターン以降も同じ位置に同じ文面で送る。** 送る中身は毎ターン後ろに足されるだけになり、前回の送信が今回の送信の先頭とそのまま一致する。

## 2. なぜ必要か (実測)

2026-10-14、Gemini 4 Argon の暗黙キャッシュを、SAIVerse を通さない直接の呼び出しで測った。

- Argon の暗黙キャッシュで保持されていたのは二か所だけだった。前回の送信の「末尾から 2,049 トークン手前まで」と「システムプロンプトの終わりまで」。同じ中身を送り直すと、三つの実験すべてで「全体 − 2,049」だけが当たった。
- 2,017 トークンの差し込みを最後の発言の前に置いた場合、次のターンはほぼ全部当たった。3,217 トークンにすると、前に置いても後ろに置いても、システムプロンプトの分しか当たらなかった。
- キャッシュの保持時間は、8 分あけた送り直しでは当たり、11 分半では当たらなかった (各一回の測定)。

アイフィとの実際の会話でも同じ形が出た。画像付きの発言 (画像だけで 1,151 トークン) の次のターンは、9 万トークン中、システムプロンプトの 26,349 トークンしか当たらなかった。当たった回と外れた回で、1 回あたりの費用は約 $0.017 と約 $0.14 で、8 倍違う。

同じ日に、ターンの中で LLM を二回呼ぶ場合も測った。ターン 1 の一回目の呼び出し (24,375 トークン) のあと、ターン内の往復を足した二回目の呼び出しを挟み、ターン 2 ではその往復を別の形 (ツール呼び出しを JSON 本文にし、結果の改行も変えた形) で復元して送った。ターン 2 は 24,466 トークン中 22,417 トークンがキャッシュに当たった (外れたのは末尾の 2,049 トークンで、上の三つの実験と同じ形)。一回目の呼び出しで保持された範囲は、二回目を挟んでも次のターンに効く。だから、この設計が揃えるべきなのはターンの最初の呼び出しどうしで、ターン内の往復の形が次のターンの復元形と違っても、失うのはその往復の分だけになる (不変条件 1)。

「2,049」は公式の数字ではなく実測の値なので、Google が変えれば変わる。この設計はその数字に依存しない (毎ターン後ろに足すだけなら、キャッシュの範囲がどこで切れても、前回の送信は今回の送信の先頭と一致する)。

## 3. 設定

モデル定義の `cache` に `persist_realtime_and_recall` (真偽値、省略時 false) を置く。

```json
"cache": { "type": "implicit", "explicit_supported": false, "persist_realtime_and_recall": true }
```

- ON にするのは、境目を指定できないキャッシュで、かつキャッシュに乗った分の割引が大きいモデル。2026-10 時点の組み込みでは Gemini 4 Argon だけ。
- 境目を指定できるモデル (Claude、明示キャッシュの Gemini) では OFF のままにする。保存したメッセージの分だけ Metabolism (古い会話をあらすじに置き換えて送る量を減らす処理) が早く実行されるのに、得るものが無い。
- llama.cpp は、境目の目印をこちらから渡せるようにするフォークが本来の対応 ([issue](../issues/llama_prompt_cache_full_reprocess_swa_checkpoint.md))。それができるまでのつなぎとして、この設定を ON にすることもできる。

設定値は `saiverse/model_configs.py` の `get_cache_config` で読み、未指定なら false になる。ON かどうかは、送る列を組むときのモデル (`prepare_context` に渡る `model_key`) で決める。組んだ後で別のモデルへ切り替わる経路 (tell の `select_llm_client` など) は、組んだときのモデルの判定に従う。

## 4. ON のモデルで何が変わるか

### 4.1 送る並び

ON のモデルへ送るとき、そのターンのリアルタイム情報と自動想起は、一つのまとまりとして**送る列の一番後ろ** (最新の発言と、そのターンの知覚のまとめの後ろ) に置く。OFF のモデルは今までどおり (最新の発言の直前)。リアルタイム情報のメッセージが無いターンにリアルタイムスペルが自前でメッセージを作る経路も、ON では一番後ろに置く。

一番後ろに置くのは、次のターンにこのまとまりが出る位置 (= 残した時点で最後にあった発言とそのターンの知覚の直後) と、今回送る位置を一致させるため。同じパルスの中で LLM 呼び出しが二回目以降 (スペルの繰り返し) になっても、このまとまりは最初の位置に据え置き、ツールの往復はその後ろに積む。自律パルスのスペルの繰り返しでは、周内の発言を、次のターンに履歴から復元される形 (自律の発言は user ロールの自律記録になる) と同じロール・本文で積む。保存する元の発言は変えない。これは往復の分の一致を増やす直しで、不変条件 1 が約束するのはターンの最初の呼び出しどうしの一致まで (自律の通常のノード間や native tool の往復は揃えていない — [issue](../issues/in_pulse_message_forms_differ_from_restored_history.md))。

一度送ったまとまりは不変にする。初めて送るときに文面・画像・位置を決める発言を固定し、それより後にはまとまりへ何も足さない。ON のモデルでは、リアルタイムスペルの実行済みの状態と、その結果 (本文と画像) を一緒に持ち、親と子の Playbook で共有する。この入れ物はパルスに一つで、パルスの記録 (`PulseContext`) に置く。子の Playbook の入口 (SUBPLAY ノード、`/run_playbook` スペル、スペルの引数を決める `spell_args_decider`、TOOL ノードから呼んだ `run_playbook`) のどれからでも、同じ入れ物に届く。子が写す列の状態 (残すモデルの列か、結果をもう持っているか) は、呼び出し元の列から一つの関数 (`sea/runtime_context.realtime_spell_handover`) を通して渡す。リアルタイムスペルは同じパルスで一度だけ実行し、実行しなかった側 (文脈を組み直す子 = line='main'、親の列を写す子 = line='sub'、どちらが先に走っても) には、同じ結果をその列のそのターンのまとまりに入れて届ける。文脈を組み直す子が、親が保存した後に走ったときは、結果はその子の列に出る保存したメッセージに入っているので、二度は届けない。OFF のモデルの実行の仕方は変えない (Playbook ごとに自分で実行する)。子へ渡す列ではまとまりを辞書ごと写し、親のまとまりを共有しない。それでも送った後に新しい結果が出る経路が残っていれば、その結果は別の末尾のメッセージに置き、保存しない。

### 4.2 保存する

そのまとまりを、送った文面のまま、ペルソナの `memory.db` に一行のメッセージとして保存する (以下「保存したメッセージ」)。保存先は知覚のまとめと同じ表 (`perception_batches`) で、種類の欄で知覚と区別する。保存先を揃える理由は、送る列から外す規則 (Chronicle の付記で外れる)・Metabolism の量の勘定・位置を決める既存の列 (`boundary_created_at` / `boundary_rowid` = 送った列でまとまりより前にある最後の発言) に、前例の仕組みのまま乗れるから。

- **残す時刻**: 生成が正常に完了した (本文または tool call を得た) 後。空応答の打ち切り・本文の無い中断・ユーザー停止では残さない (返事の無いターンに、差し込みだけが残ることを防ぐ)。全文一括の経路 (通常・tools 付き・構造化出力・スペルの繰り返し) でも停止を確かめる。全文一括では、生成の途中で止められても応答を受け取り終えてから戻ってくるので、本文があることだけでは止められていないことにならない。リアルタイムスペルの結果は最初の LLM 呼び出しの直前に足されるので、それより前には文面が確定しない。初めて送ったときに固定した写しを「保存待ち」にし、DB への書き込みが成功したときだけ「保存済み」にする。書き込みが失敗したら、同じパルスの次に生成が完了した地点で、固定した同じ写しを書き直す (どの地点で書けても文面と位置は同じ)。
- **残すパルス**: state の `_pulse_type` が user / auto / schedule のパルスだけ。それ以外 — キャッシュを保つための定期の送信 (keepalive)、Metabolism の前に覚えておくことを採取する処理 (`sea/sluice.py`)、作業セッション (`work_session`)、tell、判断のパルス (meta_judgment) — では差し込みを残さない。作業セッションや tell の実行時にもペルソナの発話は生まれるが、これらは会話の流れとは別に組んだ列で一回ずつ呼ぶ処理で、その列の続きが次のターンに来るわけではないので、残しても前方一致の役に立たない。これらの処理でも、すでに残してある差し込みは送る列に含める (4.3)。その処理自身が組んだ差し込みは、今までどおり次のターンには消える。
- **入れ子の Playbook**: 最初の LLM 呼び出しが入れ子の Playbook (`lg_subplay_node`) の中にあるターンは、子に `_pulse_type` が渡らないので保存されない (会話の既定の `track_user_conversation` は直接の LLM ノードなので該当しない)。そのターンは今までのモデルと同じく、次のターンには差し込みが残らない。
- **一ターン一回**: スペルの繰り返しで LLM 呼び出しが何度あっても、残すのは一回。
- **位置を決める発言が無いターン**: 送った列で、そのターンのまとまりより前に記録の発言が一件も無いターン (ペルソナの最初のパルス、空のスレッドの自律開始。事前スペル・TOOL の結果など、記録に残った行が前にあれば、それが位置を決める発言になる) は残さない。次のターンに出る位置が決まらない (§4.3) ので、残しても送られないため。そのターンのまとまりは今までどおり送る列の一番後ろに置いて送るが、次のターンには残らない (OFF のモデルの差し込みと同じく消える)。判定は保存の一点で行い (`sea/runtime_llm._persist_turn_realtime_and_recall` が発言の id の無いまとまりを書きに行かない。`adapter.record_realtime_and_recall` も、渡された id が記録に一件も無ければ書かない)、境界が NULL の行は生まれない (Codex 八巡目)。
- **出すものが無いターン**: 時刻の項目が両方 OFF でスペルの結果も無く、新しく浮かんだ記憶も無いターンは、まとまり自体を作らず、何も残さない (realtime_info.md 不変条件 3 と同じ)。
- **画像**: リアルタイムスペルが画像を返したときは、その画像も一緒に残す。
- **画像の枚数の上限を使わない**: ON のモデルへ送る列では、送る画像の枚数の上限 (OFF のモデルでは既定 4 枚、新しい順。環境変数・モデル設定の `max_image_embeds`・チャット画面の上書きで変えられる) そのものを使わず、列にある画像をすべて画像のまま送る。ユーザーの画像・知覚の画像・ツールの画像・スペルの画像の区別はしない。上限があると、新しい画像が来るたびに一番古い画像が文字に置き換わって前回の送信の中身が書き換わり、「後ろに足すだけ」という ON の約束と根本でぶつかるため。印は列に一つで、送る列を組むとき (`prepare_context`) に、組んだときのモデルの判定 (§3) で列の先頭のメッセージに付ける (`llm_clients/utils.ATTACHMENT_LIMIT_OFF_KEY`)。各クライアント (Gemini・Anthropic・OpenAI 互換・xAI) と送る量の見積もり (`sea/sluice.py`) は、同じ一つの判定 (`attachment_limit_is_off`) で読む。以前は画像を運ぶメッセージの種類ごとに「上限の数に入れない」印を付けていたが、知覚の画像・MEMORIZE で残したツールの画像に付け漏れが二巡続いた (Codex 四巡目・五巡目) ので、型ごと消した。OFF のモデルの上限は変えない。

### 4.3 次のターン以降の送り方

- 保存したメッセージは、**送った列でまとまりより前にあった最後の発言 (とそのターンの知覚) の直後**に置く。「保存する時点で最後に保存済みの発言」にしないのは、送る列に出ない行 (判断のパルスの記録、別のスレッドの行) がそれに当たると、次のターンに境目が列に無く、二度と送られなくなるため (通常のターンでは両者は同じ発言になる)。位置は既存の境界の列 (`boundary_created_at` / `boundary_rowid`) で決め、時刻の秒では決めない。知覚のまとめは秒単位の時刻の順に並ぶため、同じ秒の前後が区別できない。保存したメッセージは最新の発言と返事のすき間という狭い位置に入るので、秒の丸めで前後が入れ替わる余地がある。同じ発言の直後に並ぶもの同士は、表の id の順に並べる。
- ON のモデルの送る列では、知覚のまとめも境界の発言 (バッチを確定した時点で最後に保存済みだった発言。送る列に無ければ、その手前で送る列にある最後の発言) で位置を決める。発言・知覚・返事・次の発言が同じ秒に並ぶと、秒の順では知覚が返事の後ろへ移り、前回の送信と先頭が一致しなくなるため。境界で位置を決められない知覚のまとめ (境界が NULL の古い行・最初のパルスで消費した行、境界が別のスレッドの発言などで、境界より前の発言が送る列に無い行) は、ON のモデルの送る列では、自分の時刻 (秒) 以上の時刻を持つ最初の発言の直前に置く (= 同じ秒の発言より前。同じ位置に複数並ぶときは表の id 順)。秒の厳密な比較のままだと、後から同じ秒の発言が保存されるたびに知覚が後ろへ動き、前回の送信と先頭が一致しなくなるため (Codex 九巡目)。省略の印も同じ規則で並べる。部屋の様子の置き直しは最古にした時刻で先頭に立つ規則のまま。OFF のモデルは従来の秒の順のまま。送る側と測る側 (Metabolism の勘定・退場計画) は同じ関数を通る。
- 部屋の背景の置き直し (部屋の様子が提示から見えなくなったときに、機構が全文を立て直すバッチ) は境界で動かさず、先頭に置く。このバッチは背景として履歴の先頭に置くために `consumed_at` を意図的に最古にしてあり、境界の列は窓の判定 (見えるかどうか) のためだけに付けている。境界で並べると、背景が最新の発言の直後へ移ってしまう。
- **位置を決める発言を持たない (境界が NULL の) 保存したメッセージ**は送らない。そういう行は残さない (§4.2) ので生まれないが、記録に既にあっても (七巡目の規則で書かれた行など) 送らない。
- **位置を決める発言が送る列に無いとき** (別のスレッドにいる、Chronicle を無効にしたペルソナの窓の外、など) は、その差し込みを送らない。自動想起の台帳を thread ごとに分けた理由 (前のスレッドで浮かんだ記憶を新しいスレッドの冒頭へ出さない — memory_architecture_v2.md §4.3 の 2026-07-12 実装ノート) を、保存したメッセージでも守るため。
- 保存したメッセージを送るのは、送り先のモデルが ON のときだけ。OFF のモデルへ送るときは保存したメッセージを含めず、今までどおりそのターンの差し込みを最新の発言の直前に置く。
  - 例: アイフィが Argon (ON) で 10 ターン話したあと 3.8 Flash (OFF) に切り替えると、3.8 Flash へは保存したメッセージが送られず、毎ターンの差し込みが今までどおり出る。Argon に戻すと、保存したメッセージは元の位置に戻ってくる。
- 保存したメッセージは、Chronicle の付記で送る列から外れる (知覚のまとめと同じ)。
- **あらすじの材料には入れる** (arasuji_levels.md §7-1 のまはー裁定「本人の提示に立った行は、すべて編纂の材料と被覆に入る。意味・種類による仕分けはしない」。編纂 = あらすじ作成、被覆 = あらすじが元の発言のどこまでを要約済みとして受け持つかの範囲)。材料では、想起を含む差し込みに【想起 (過去の再提示)】のラベルを付け、生成プロンプトの既存の注記 (過去の出来事の再提示であり、この期間の新しい出来事として語らない) に乗せる。想起を含まない差し込み (時刻とスペルの結果だけ) は【通知】のラベルにする。長さは機構名義の行と同じ規則 (閾値を超えたら、LLM を使わず本文と metadata から機械的に作る一行に縮めて材料に渡す) に従う。材料の中の位置は、位置を決める発言が材料にあれば、その発言の後ろ、次の発言の前に収める (その間に先に出た知覚のまとめとは時刻順 — 送る列と同じく「発言 → 知覚 → 差し込み → 返事」)。保存の時刻は最初の LLM 呼び出しが終わった時刻で、返事の保存と同じ秒になりやすく、秒の順だけで並べると「発言 → 返事 → 差し込み」と実際の順 (発言 → 差し込み → 返事) が入れ替わるため。位置を決める発言が材料に無い・記録に無いときは、知覚のまとめと同じ秒の順 (同じ秒は発言が先) に戻る。知覚のまとめの材料の並びは変えない。
- 知覚のキーワード検索 (記憶検索 API の `search_perceptions`) には入れない。

### 4.4 自動想起の出し方

ON のモデルでは、想起は「新しく浮かんだ分だけ」を出して残す。

- 今の自動想起の仕様では、一度浮かんだ記憶を「粘着」させ、話題から外れて 3 ターン経つまで毎ターン全件を出し直す。ON のモデルでそのまま残すと、同じ記憶が毎ターン積み重なる。
- ON のモデルでは、**いま送る列にある保存したメッセージに入っている記憶を、候補を集める段階で除外する** (採用した後で捨てると、候補の枠が既出の記憶で埋まったまま件数だけ減る — auto_recall_jev_rerank.md の詰まり 1 と同じ理由)。そのために、保存したメッセージには、出した記憶の識別子 (種類と id) を構造化して持たせる。
- 「新しく浮かんだ」の基準は、粘着の台帳ではなく保存したメッセージにする。台帳の記録は keepalive や作業セッションの呼び出しでも更新されるので、台帳を基準にすると、それらの呼び出しで最初に浮かんだ記憶が二度と残らなくなる。
- 一度出た記憶は、Metabolism で送る列から外れるまで、ペルソナの目に入り続ける (粘着の「しばらくしたら引っ込める」は、ON のモデルでは働かない — 2026-10-14 まはー了承)。
- 画面に出す想起 (UI の表示と、返事に付ける想起の記録) も、残したのと同じ「新しく浮かんだ分」にする。
- 新しく浮かんだ記憶が一つも無いターンは、想起を出さない (リアルタイム情報があればそれだけを残す)。

### 4.5 自動想起のきっかけにしない

保存したメッセージは、知覚のまとめとは別の印を付け、自動想起のきっかけ (検索に使う文。このターンに新しく目に入った物) と Jev に渡す観察 (`_trailing_perception_blocks` / `_is_conversational_message` / `_latest_user_message` が集める物) から明示的に外す。同じ印にすると、ユーザーの発言の無いターン (自律の思考) で、保存したメッセージが想起のきっかけになり、思い出したことをまた思い出す循環が起きる。

### 4.6 リアルタイム情報

ON のモデルでは、毎ターンの「現在時刻」の行が残っていく。ペルソナには会話の各ターンの時刻が残ることになる。「前回発言」の行は、OFF と同じくペルソナ設定のトグルに従う。

## 5. 守ること (不変条件)

1. **前回の送信は、今回の送信の先頭そのもの** — ON のモデルで、あるターンの最初の LLM 呼び出しで送った列は、次のターンの最初の呼び出しの列の先頭と、保存したメッセージまで含めて一字一句同じになる。ターン内の二回目以降の呼び出し (スペルの繰り返し・native tool の往復・自律パルスの複数の LLM ノード) で積んだ往復の形が、次のターンで履歴から復元される形と違うことは、この設計の範囲外 (§2 の実測のとおり、損はその往復の分だけで、ON/OFF を問わない既存の性質。[issue](../issues/in_pulse_message_forms_differ_from_restored_history.md))。スペルの結果の文面を復元形に揃えた直し (不変条件 2) と、ON のモデルの自律パルスでスペルの繰り返しの周内の発言を復元形で送る直し (§4.1) は、往復の分の一致を増やす直しとして残す。例外は、Metabolism・head の作り直しが起きたターンと、履歴が空の最初のターン (位置を決める発言が無いターン — §4.2) の次のターン (そのターンのまとまりは残さないので、次のターンの列には出ない)。画像の枚数の上限で古い画像が文字に置き換わる崩れ方は、ON のモデルでは上限そのものを使わないので起きない (§4.2)。最初の呼び出しの前に記録に書かれたもの (事前スペルの結果・TOOL ノードの結果・ツールの中で書かれる記録・MEMORIZE の行など) は、送る直前に送る列を記録から読み直した並びに揃えることで、次のターンに復元されるのと同じ文面と順序で送る。揃えた後の列を読み直した並びと機械で比べ、食い違いがあれば WARN を出す (この節の末尾の「最初の呼び出しの前に足すもの」と「機械検査」)。これがこの設計の存在理由で、検収で最も重く見る点。
2. **OFF のモデルは何も変わらない** — 送る並びも、残すかどうかも、自動想起の出し方も、今までと同じ。ただし、スペルの結果と事前スペルの結果を、送るときから履歴の復元形と同じ文面にする直しは、全モデル共通 (前回の送信との一致を増やす方向の修正で、送る並びは変えない)。結果の画像を記録に残すのは ON のモデルだけで、OFF のモデルの履歴は今までどおり画像を持たない (残すと、OFF のモデルでも画像が後のターンへ送られ続け、画像の枚数の上限でユーザーの古い画像が文字に置き換わる時期が早まるため。2026-10-14 メティス裁定)。結果の本文は復元形の `<system>\n…\n</system>` で送る。/quick_spell の失敗時に注入する説明文は記録しない約束 (quick_spell.md 不変条件 5) なので、結果のメッセージとは別の、保存しないメッセージとして結果の直前に置く (この回だけは次のターンの列と一致しない)。
3. **保存したメッセージは機構の名義** — `<system>` タグ付きの user ロールで残し、ペルソナの発言としては残さない。想起のきっかけにも、知覚のキーワード検索の対象にもならない。あらすじの材料には §7-1 どおり入り、ラベルで機構の物と分かるようにする。
4. **一ターン一行** — `_pulse_type` が user / auto / schedule のパルスで、生成が正常に完了したターンにつき一行。失敗したターン・返事の無いターン (空応答の打ち切り・本文の無い中断・ユーザー停止)・keepalive・Metabolism の前の採取・作業セッション・tell・判断のパルスでは残さない。

**最初の呼び出しの前に足すもの**: ON のモデルの、残すパルス (user / auto / schedule) のトップレベルの列で、ターンの最初の LLM 呼び出しを送る直前に一度だけ、送る列の「最後の記録済みの発言 (境界) より後ろ」を、記録 (SAIMemory) から読み直した並びに揃える (`sea/runtime_llm._align_first_send_with_record` → `sea/runtime_context.align_first_send_with_record`)。境界は `prepare_context` が組んだ履歴の部分で最後に id を持つ発言。読み直しは、次のターンの `prepare_context` が履歴を復元するのと同じ関数 (`_append_history` — 取り出し・知覚のまとめのマージ・添付の注記・時刻の目安・自律の発言の変換まで同じ一枚) を、組んだときの建物・指定・モデルで、このパルスの id を渡さずに通す (`reread_recorded_history`。リアルタイム情報・自動想起・head は組み直さない)。境界より後ろの記録済みの行 (同じ発言の id・同じ台帳 id のもの、知覚のまとめ・時刻の目安) は読み直した並びに置き換え、記録に残らないもの (そのターンのまとまり、記録に残らない差し込み) はその後ろに元の順で置く。送る列と Playbook の列 (`state["_messages"]`) の両方を揃える。そのターンのまとまりは記録済みの行の後ろ (列の一番後ろ側) になり、送る直前の固定がその直前の記録済みの行を位置を決める発言にするので、次のターンも同じ位置に出る。

揃えられた列では、**前駆刻印の材料** (返事の metadata の `predecessor_message_id` = その生成が実際に見ていた最後の発言。材料は state の `_presented_message_ids`、sea/message_stamp.py) を、送信のたびに、実際に送る列にある記録の行 id から作り直す (`sea/runtime_llm._refresh_presented_ids_for_aligned_send`)。揃えで送る列に入った行 (事前スペルの結果・TOOL の結果・MEMORIZE の行・状況変化の記録) を返事が実際に見ているのに、組成時点の材料のままではユーザーの発言が前駆として残るため (Codex 七巡目)。前駆の材料は、子の Playbook の中継 (SUBPLAY) が落とす (子の本文に親の前駆を刻まないため) が、その後の親の送信でも同じく送る列から作り直す。そのために、この列では親が保存に成功した返事 (memorize と important の二重書き) とスペルの周の発言に、返された保存 id を送る列のその行にも持たせる (`sea/runtime_llm._keep_stored_id_in_list`)。持たせないと、作り直した材料が保存済みの返事を飛ばして古いユーザーの発言を前駆にする (Codex 八巡目)。`id` の欄は LLM へ送る中身には入らない (履歴から組んだ行がもともと持っている欄)。揃えが走らない列 (OFF のモデル・入れ子の Playbook・揃えに失敗した列) は今までどおり (組成時点の材料に、スペルの周の行を足していく。送る列の行に id も持たせない)。

これにより、最初の呼び出しの前に記録に書かれるもの — 事前スペルの結果、TOOL ノードの結果とエラー、ツールの中で書かれる記録 (`get_situation_snapshot` の状況変化など)、MEMORIZE の行、子の Playbook が残した行、今後足されるもの — を、差し込み口ごとに送る列へ同期しなくてよい (以前は一つずつ同期していて、巡ごとに付け漏れが出た — Codex 四巡目〜六巡目)。ただし記録に残らないものは読み直しに出ないので、送る列へ足すものを記録に残す規則は残る: 事前スペルの結果 (全モデル共通で記録に残る) と同じく、TOOL ノードの結果とエラーの結果も、この間は system ロールの記録に残し、その id を持たせ、記録が復元されるのと同じ文面 (`<system>\n…\n</system>`) で足す (`sea/runtime_engine._append_tool_message`。Codex 五巡目)。揃えられない (材料が無い・読み直しに失敗した・境界が列に無い・履歴はあるのに id を持つ発言が無い) ときは列を変えず WARN を出す。OFF のモデルの列と入れ子の Playbook (`_pulse_type` を持たない) では何もしない。最初の呼び出しより後に足すもの (ターン内の往復) は今までどおり記録に残さない。

**機械検査**: 揃えた直後に、送る列の境界より後ろ (そのターンのまとまりを除く) と、記録から読み直した並びを、LLM へ届く中身 (役割・本文・画像・tool call) で順に比べる (`sea/runtime_context.find_unrecorded_messages`)。食い違いは二種類で、送る列にだけあるもの (記録に残らない差し込み) と、読み直した並びにだけあるもの (記録に書かれたのに送る列のその位置に無い行)。どちらも役割と先頭の文字を WARN で出す (送信は止めない)。以前の検査は「id か決まった印を持つか」だけを見ていたので、送った行の保存は確かめても、次のターンの復元で間に入る行 (状況変化の記録・MEMORIZE の行) を見落とした (Codex 六巡目)。この検査は、そのターンのまとまりがまだ保存されていない時点で走るので、「保存したまとまりが次のターンに出ない」は拾えない。そこで二つ目の検査として、まとまりを保存した直後に同じ関数で記録から読み直し、保存したまとまりがその並びに出なければ WARN を出す (`sea/runtime_llm._check_kept_block_comes_back` → `sea/runtime_context.kept_block_comes_back`。Codex 七巡目。残すのは境界のあるまとまりだけなので、この検査も境界のある保存にだけ働く)。2026-10-14 時点で検査が拾うと分かっているのは、トップレベルの Playbook の最初の LLM ノードに action の指示文がある場合と、SUBPLAY の `report_to_parent` が最初の呼び出しの前に親の列へ足される場合 (どちらも記録に残らない。揃えた後はそのターンのまとまりの後ろに並ぶので、外れるのはその差し込みの分だけ。会話の既定の Playbook には当てはまらない)。

## 6. 全体の流れ (時間順)

```
パルスの頭: 知覚を消費してバッチにする (今まで通り)
  ↓
prepare_context: head + 履歴 + 知覚のまとめ
                 + [ON なら 保存したメッセージを、位置を決める発言の直後へ (発言が無ければ送らない)]
                 + そのターンのリアルタイム情報・自動想起
                   [ON なら 既出の記憶を候補から外し、送る列の一番後ろ / OFF なら 最新の発言の直前]
  ↓
最初の LLM ノード: リアルタイムスペルの結果を足す
                 → [ON・トップレベルなら 送る列の境界より後ろを記録から読み直した並びに揃え、検査する]
                 → [送る直前に まとまりを固定 (保存待ち)] → LLM 呼び出し
  ↓ 生成が正常に完了 (本文または tool call を得た)
[ON かつ user/auto/schedule なら 固定した写しを一行残す。書けなければ同じパルスの次の完了地点で書き直す]
  ↓
返事を保存 (今まで通り)
  ↓ 次のターン
prepare_context: 保存したメッセージは「残した時点で最後の発言」の直後に出る → 前回の送信と一致
```

## 7. 置き場所の理由

- **なぜ残すのか (境目の指定でなく)**: Argon は境目を指定できず、キャッシュの範囲も Google が決める。直せるのは「末尾に消える物を置かない」ことだけ。
- **なぜモデルごとか**: 境目を指定できるモデルには得が無く、保存したメッセージの分だけ Metabolism が早まる損だけが残る。
- **なぜ知覚のまとめと同じ保存先か**: 送る列から外す規則・Metabolism の量の勘定・位置を決める境界の列・あらすじの材料への引き渡しを、新しく作らずに済む (別の表にすると、付記で外す仕組みと勘定への参加を自前で作ることになり、作り漏れで保存したメッセージが送られ続けるか、勘定から漏れる)。前例と違うところ (想起のきっかけから外す・キーワード検索から外す・モデルで送り分ける・材料のラベル) は、種類の欄で分岐させる。

## 8. 残る結果

- ON のモデルでは、保存したメッセージの分だけ会話が速く伸び、Metabolism が早い段階で実行されるようになる。Metabolism を実行したターンはキャッシュが一度外れる。Argon のようにキャッシュに乗った分が 1/20 のモデルでは、保存したメッセージを送り続ける費用より、毎ターン外れる費用の方がずっと大きいので、差し引きで得になる。
- キャッシュの保持時間 (実測で 8〜11 分) を超えて間があいたターンは、この設計でも外れる。明示キャッシュの無いモデルでは手の打ちようがない。
- 新しいペルソナの最初の一ターン (と、空のスレッドで自律パルスが始まったターン) は、そのターンのリアルタイム情報と自動想起を残さない (§4.2)。だから次のターンではキャッシュが一度外れ、その一ターンの時刻が後からペルソナに見えない (その一ターンで浮かんだ記憶は、次のターンにまた浮かびうる)。一回きりの場面のために、位置を決める発言の無い行を置く例外規則を持つより、残さない方を選んだ (Codex 八巡目)。
- 自動想起の「粘着」が ON のモデルでは働かなくなる (4.4)。
- ON から OFF に切り替えると、ON のときの返事が引用した想起の原本が、OFF のモデルには見えなくなる (粘着が防いでいた「引用した次のターンに原本が消える」形が、切り替えの瞬間にだけ起きる)。
- 送る列の最後が `<system>` の差し込みになる (返事を求める最新の発言の後ろに機構の文が来る)。返事が想起の方へ引っ張られないか、またペルソナが `<system>` の形を真似て偽の通知を書かないか (memory `feedback_no_assistant_impersonation_in_memory` の逆方向の事故) は、まはーの実機で確かめる。
- ユーザーの画像が 5 枚目に達するたびに一番古い画像が文字に置き換わって先頭の一致が崩れる問題は、ON のモデルでは上限を使わないので起きない。代わりに、会話が畳まれる (Metabolism) まで過去の画像が画像のまま送られ続ける (画像 1 枚 1,000 トークン強、キャッシュに乗れば 1/20)。

## 9. 検証

- **一字一句の一致 (不変条件 1)**: 隔離環境で、ON のモデル設定・合成ペルソナ・偽の LLM を使い、二ターン続けて送る列を取り出して、一ターン目の最初の呼び出しの列が二ターン目の最初の呼び出しの列の先頭と完全に一致することを、SAIVerse の列と Gemini の送信形式の両方で確かめる。リアルタイムスペル付き (画像あり)・自動想起の新規採用あり/なし・同じ秒に発言と残す時刻が並ぶ場合・同じ秒に発言・知覚・返事・次の発言が並ぶ場合・スペルの繰り返しがある場合 (画像付きのスペル結果を含む)・`/run_playbook` スペルで子を起動した場合・ユーザーの画像を使わず知覚・ツール・スペルの画像だけで上限 (OFF の既定 4 枚) を超える場合・ユーザーの画像が 5 枚目に達する場合 (どちらも画像が一枚も文字に置き換わらないこと)・トップレベルの TOOL → LLM (結果とエラーの結果) の場合、状況変化を記録する TOOL (本物の `get_situation_snapshot`、`detect_changes=True`) → LLM の場合、TOOL → MEMORIZE → TOOL → LLM の場合、履歴が一行も無い最初のパルスの TOOL → LLM の場合を含める。履歴が一行も無い最初の自律パルス (TOOL なし — 位置を決める発言が無い) では、保存したメッセージが増えないこと、そのまとまりが次のターンに残らないこと、二ターン目の最初の送信が三ターン目の最初の送信の先頭と一致すること (時刻の目安の位置も含めて) を、通常・Chronicle を無効にしたペルソナ・保存の一回目が失敗する DB の三つで確かめ、あらすじの吸収の材料集めで残した行が漏れないことも確かめる。返事の `predecessor_message_id` が、送った列の最後の記録の行と一致すること (TOOL・MEMORIZE を挟む TOOL・事前スペル・状況変化・子の Playbook の後の親の生成・返事を残した親の LLM → 子の Playbook → 親の LLM・スペルの周を挟んだ後の子の Playbook → 親の LLM) も確かめる。送る直前の機械検査が、通常・事前スペル・TOOL → LLM・状況変化・TOOL → MEMORIZE → TOOL・リアルタイムスペル・自動想起・知覚・自律パルスの各場面で食い違い無しを返し、記録に残らない差し込みがあれば WARN を出すこと、揃えを止めた列では状況変化と MEMORIZE の行を「送る列に無い記録の行」として見つけることも確かめる。OFF のモデルでは、5 枚目のユーザーの画像で一番古い画像が今までどおり文字に置き換わること、TOOL の結果が今までどおり記録に残らないことを確かめる。スペルの繰り返しがある場合は、往復の分の一致を増やした直しの回帰として、一ターン目の最後の呼び出しの列も二ターン目の最初の呼び出しの列の先頭と一致することを確かめる (不変条件 1 の外)。
- **OFF の不変 (不変条件 2)**: 同じ手順を OFF のモデルで行い、送る列が変更前と同じであることを確かめる。
- **切り替え**: ON → OFF → ON で、保存したメッセージが送られなくなり、また戻ること。
- **残さない処理**: keepalive・Metabolism の前の採取・作業セッション・tell・判断のパルスで行が増えないこと。失敗したターン、空応答の打ち切り・本文の無い中断・ユーザー停止のターン (通常と tools 付きの両方) で行が増えないこと。初回だけ失敗する DB で、同じパルスの次の完了地点で同じ写しが書かれること。ON のモデルで、子の Playbook (line='main' / 'sub'、親が先・子が先、実際の `/run_playbook` スペルの入口を通した子を含む) がリアルタイムスペルを二度実行せず、親のまとまりを書き換えず、パルス内の各送信に同じ結果が載ること。OFF のモデルの親子の送信が一巡目の修正前と同じであること。
- **想起**: 既出の記憶が候補の段階で外れ、新しい記憶が枠に入ること。保存したメッセージが自動想起のきっかけと Jev の観察に入らないこと。
- **あらすじ**: 付記で送る列から外れ、材料には【想起 (過去の再提示)】/【通知】のラベル付きで入ること。発言と返事が同じ秒に並ぶときも、材料の中で位置を決める発言と先に出た知覚の後ろ、返事の前に並ぶこと。
- **実機**: まはーが Argon のペルソナと続けて話し、画像付きの発言の次のターンもキャッシュが当たることをログで見る (`[DEBUG] Usage recorded: ... cached=`)。
