# 自動想起の Jev 選別層 (実験)

**ステータス: 検証待ち (2026-09-18 に拾い上げの拡張を追加。実験ブランチ feature/jev-auto-recall-rerank。まはーの実機再評価待ち)**

## これは何か

自動想起 (`sea/auto_recall.py`) が「どの記憶をペルソナの頭に浮かばせるか」を決めるとき、
埋め込み類似度のしきい値 (既定 0.86) だけで判定している現行方式に、外部の判断専用モデル
**Jev (TypeSafe 社の System One モデル)** による関連度判定を重ねる実験。

Jev は文章を生成しない。状況 (state) と型付きの質問を渡すと、質問ごとに確率を返す。
ここでは候補記憶 1 件につき「この記憶は今の会話の流れで自然に浮かぶべきか」という
はい/いいえの確率 (Noul) を 1 問ずつ、**1 リクエストにまとめて**問う。

`docs/intent/memory_architecture_v2.md` §10-1 の不変条件は「自動想起は LLM を呼ばない。
**軽量 LLM 選別は明示的なオプション層としてのみ追加できる**」であり、本実験はその
オプション層の最初の実装にあたる。

## 全体像 (どこで何が変わるか)

- **影響を受ける人**: 自動想起を使う全ペルソナ。浮かぶ記憶の選別精度が変わる。
  オプション OFF (既定) では**一切の挙動が変わらない**。
- **旅程**: 会話ターン → `run_auto_recall` → `unified_recall` が候補を返す →
  【新設】Jev に候補一括判定 → 通過した候補だけが粘着台帳に入り末尾注入される。
- **費用**: ON のとき、会話ターンごとに TypeSafe API 呼び出しが 1 回発生する
  (入力 $0.042/100万トークン、出力無料。1 ターンあたり概算 0.01 円未満)。
- **プライバシー**: 直近の会話本文 (1 件あたり 500 字まで) と、候補記憶の**本文抜粋**
  (1 件あたり 200 字。過去の会話メッセージの抜粋と、その発話者ロール・時刻を含む) が
  TypeSafe API へ送られる。要約ではなく本文の一部がそのまま出る点に注意。既存の
  クラウド LLM プロバイダ (Gemini 等) と同等の外部送信であり、ON にするのは
  ユーザーの明示操作 (env 設定) のみ。
- **検証の旅程**: 隔離 SAIVERSE_HOME + 合成 memory.db で実 API を通した確認まで
  実施済みにしてから、まはーの実機 (本番ワールド) での体感評価に渡す。
  **未検証の境界**: 締切超過のときの切断 (close) が実際に通信を止めることは、
  モック環境 (`httpx.MockTransport`) では確かめられていない。テストで確認できたのは
  「会話が締切で戻ること」と「置き去りワーカーが終わるときに枠を返すこと」までで、
  実ソケットに対して close がどこまで効くかは実 API を通した確認に残っている。

## なぜ埋め込みしきい値だけでは足りないか

実測 (memory_architecture_v2 §12-1) で判明している構造的な弱さ:

- E5 埋め込みは cosine が 0.8〜0.9 に圧縮され、無関係クエリでも 0.83〜0.84 に達する。
  しきい値 0.86 は「オントピック上位だけ通す」ぎりぎりの線で、0.86 近傍の
  当落は実質ノイズ。
- message ソースは長文類似度インフレのため +0.02 の底上げ補正を別途持っている
  (対症療法であることが `get_message_threshold_offset` の docstring に明記されている)。
- 類似度は「意味が近い」しか測れず、「今この場面で浮かぶべきか」(会話の流れ・
  相手・状況との関係) を測れない。

Jev 層はこの「浮かぶべきか」を直接問う。TypeSafe 公式の再ランキング実例では
検索単体に対し Top-1 正解率 5%→18% の改善が報告されているが、**この数字は法律文書
での実測であり、SAIVerse の日本語会話データでの効果は本実験で測る**。

## 設計

### 判定の流れ (ON のとき)

1. `unified_recall` の候補 (topk=8) のうち、`embed_score >= JEV_FLOOR` (既定 0.78)
   のものを候補集合とする。0.78 は intent doc の当初案の値 — cosine 単独では
   ノイズが多すぎて 0.86 へ引き上げた経緯があるが、Jev が後段で選別するため
   広めに拾い直せる。**Jev 層の狙いは、0.86 一本では拾えなかった正解 (0.78〜0.86 帯)
   を拾い、0.86 を超えるノイズを落とす、の両方向。**
2. 候補全件を 1 リクエストで Jev に渡す。state = 直近 N 件 (既定 6) の会話本文 +
   候補記憶の一覧。質問 = 候補ごとの Noul 1 問。メディア想起 (`SAIVERSE_MEDIA_RECALL_ENABLED`)
   が ON のときは、検索クエリに足すのと同じ最新添付 (画像/音声/動画) の概要も state に入る
   — 写真をきっかけに検索が拾ってきた候補を、写真を知らない Jev が落とすのを防ぐため。
3. `noul >= JEV_THRESHOLD` (既定 0.5) の候補だけを採用し、既存の粘着台帳処理へ
   そのまま流す (台帳・注入・鮮明想起は無改変)。
4. message ソースの +0.02 底上げは Jev 経路では適用しない (インフレ対策の対症療法を
   Jev の直接判定が置き換えるため)。

### 拾い上げの拡張 (ON のときだけ)

Jev をどれだけ賢くしても、候補に入っていない記憶は選びようがない。実機評価で、
候補を作る `unified_recall` の側が狭すぎて、拾われるべき過去の会話が Jev の手前に
届いていないと分かった。実測で見つかった詰まりは 3 つある。

**1. ユーザーが今言った発話が message 枠を毎ターン占領していた。** `unified_recall` は
ソース種別ごとの枠で結果を選ぶ (fragment 5 / memopedia 1 / message 1)。message の
1 席は、直前に memory.db へ永続化されたばかりの「ユーザーの今の発話」が必ず取る —
検索クエリと同一のテキストなので類似度が 0.92 前後で常に 1 位になる。その 1 件は
後段で「既にコンテキストにある」として捨てられるので、**過去の会話が浮かぶ経路は
実質毎ターン死んでいた**。対処として、コンテキスト窓に載っている message を
`unified_recall` の**収集段階**で外す (`exclude_message_ids`)。選抜後に捨てると
枠を食い潰したまま件数だけ減るので、外すのは選ぶ前でなければならない。

**2. message の枠が 1 席しかなかった。** ON のときだけ枠を
`{"fragment": 5, "memopedia": 1, "message": 3}` に上書きし、過去の会話が複数件
浮かべる余地を作る (`source_allocations`)。合計は 9 になるが `topk=8` の天井は
そのままで、枠は「上限」であって「確保」ではない。

**3. キーワード検索が日本語では死んでいた。** `unified_recall` のキーワードは
`query.split()` (空白区切り) で作られるため、空白の無い日本語文ではクエリ全文が
1 個の巨大キーワードになり、何にもマッチしない。キーワード一致数はランキングの
第一ソートキー (RRF より優先) なので、ここが死んでいると「字面が一致する過去の
会話」を上位へ持ち上げる手段が丸ごと失われる。実測では、クエリ
「ねーエリス、十条まで歩いてみた日のこと覚えてる？」に対して、拾われるべき過去の
会話 (「十条」を字面に含む) が message ソース 9,075 件中 **164 位** (cosine 0.839)
にいた。埋め込み類似度の順位では `topk` をいくら広げても届かない。

対処として、ON のときだけクエリから内容語 (カタカナ連・漢字連・英数連) を正規表現で
抜き、`keywords` として渡す。抜いた語のうち、memory.db の messages での出現件数が
**50 件以下**のものだけを、**出現件数の少ない順に最大 4 個**使う。ありふれた語を
捨てるのはエンティティトリガーの ambient ガードと同じ思想で、「珍しい名前ほど連想が
走る」。実例では「十条」は 11 件で残り、「エリス」は 4,053 件で落ちる。50 と 4 は
実験値であり、**env には出さない** — 実験の一部として調整する数字で、利用者が触る
設定ではないから。語が 1 つも残らないターンは `keywords` を渡さず、従来の
`query.split()` 挙動に戻る。

あわせて `unified_recall` 側で、キーワードで拾われたヒットにも埋め込み全件スキャンで
計算済みの cosine を `embed_score` として付けるようにした。従来は「埋め込み上位
`topk*2` 件に双子が居た場合だけ」補完しており、164 位のような候補はキーワードで
拾えても `embed_score` が `None` のまま = 自動想起の採否判定から落ちていた。
この補完は**拾い上げの 3 引数のいずれかを渡した呼び出しだけ**で効く — 補完自体は
意味的にはどの経路でも正しい (`None` の本来の意味は「埋め込みが無くて比較して
いない」) が、既定引数の呼び出しの返り値を 1 ビットも変えないという OFF 不変の
約束を優先した (2026-09-18 裁定)。

**4. 部屋の様子や通知が、ユーザーの発言からクエリの種を奪っていた (ON/OFF を問わない
バグ修正)。** 自動想起の検索クエリは「一番新しい会話文 1 件」を種にする。ところが
部屋の様子と通知は、送信直前に履歴へ時刻順で差し込まれる知覚ブロック (発言者の欄は
user、本文は `<system>` で包まれ、目印を metadata に持つ) として入るため、ユーザーの
発言より後ろに挟まると、そちらが「一番新しい会話文」に化けて**ユーザーが今言った
ことではなく部屋の様子で記憶を探していた**。本番実測で確認 (2026-09-18 21:28 の
ターン)。原因は 2026-09-06 に部屋の描画が head の合成メッセージからこの知覚ブロックへ
引っ越したとき、自動想起側の除外リストが追従しなかったこと。

**これは Jev の ON/OFF を問わず効く挙動修正 (バグ修正) で、この節で唯一 OFF にも
効く変更**。知覚ブロックを会話文から外し、クエリの種の優先順位を 3 段にした:

1. **このターンのユーザー発言** — あればこれが種。後ろに何枚ブロックが挟まっても
   動かない。
2. **直近の通知・部屋の様子** — このターンに新しいユーザー発言が無いとき
   (会話文の末尾が assistant の自律ターンなど) は、末尾の知覚ブロックの本文が種。
   「見たものに対して想起が走る」経路は残す (従来挙動の保存)。
3. **直近の assistant 発言** — 発言もブロックも無ければ従来どおり。

目印を持たない `<system>` 通知 (「スケジュールの実行時刻です…」など) は知覚ブロック
ではなく普通の user メッセージとして履歴に入るので、この修正の影響を受けず従来どおり
種になる。除外は会話文の判定そのものを直したので、エンティティトリガーの「最新
ユーザー発話」・ambient カウント・コンテキスト内除外の ID 集合・添付概要の取得元にも
同時に効く (添付概要は特に重要 — 知覚ブロックはメディアを持ちうるので、外さないと
「今添付されたもの」の取得元まで部屋の様子に乗っ取られる)。

**「いま見えたもの」は脇道から参加する (ON のときだけ)。** ユーザーの発言が種に
なったターンでも、その発言より後ろにある知覚ブロック = このターンで新しく目に
入ったものは捨てない。(a) 字面検索のキーワード抽出の対象にクエリ本文と並べて渡し
(珍しさの判定も上限 4 個の枠も共通。同数ならクエリ本文の語が先)、(b) Jev の state に
`observations` として別枠で渡す (1 件 500 字で切り、最新側から最大 3 件。無いときは
キー自体を入れない — `attachments` と同じ流儀)。見えたものを知らない Jev が、
見えたものに紐づく候補を落とす非対称を避けるため。

### 変えないもの

- エンティティトリガー経路 (決定論) — Jev を通さない。
- 粘着ウィンドウの台帳・注入ブロック組み立て・鮮明想起 — 無改変。
- OFF 時の全挙動 — **ただしクエリの種の修正 (知覚ブロックによる乗っ取りのバグ修正)
  だけは例外で、OFF にも効く**。あれはオプションの効果ではなく、2026-09-06 の引っ越し
  で壊れたままだった挙動を直すもの。OFF の自動想起も、ユーザーが発言したターンは
  その発言を種に検索するようになる。OFF では判定経路に入らず、拾い上げの 3 つの引数
  (`keywords` / `exclude_message_ids` / `source_allocations`) も `unified_recall` へ
  渡さないので、検索は従来とまったく同じ引数で走る。外部 API 用モジュール
  (`saiverse/typesafe_client.py`、httpx) も import されない (`run_auto_recall` の
  `is_jev_rerank_enabled()` 分岐で、採否判定は旧コードの else 側をそのまま通る)。
  既存テスト (`tests/test_auto_recall.py`) は OFF 時の挙動を件数・内容の表明で
  固定しているが、注入文面のバイト単位の完全一致までは検査していない。
- `embed_score` の全件補完も、拾い上げの 3 引数を渡さない既定呼び出し (= OFF の
  自動想起と、Memory タブ検索・スペル等の既存の呼び出し元すべて) では効かせない。
  返り値は従来と同一になる。

**Jev は入場の門であって、退場の門ではない。** Jev が決めるのは「その記憶が新たに
浮かぶか」だけで、一度台帳に入った記憶の退場は既存の粘着仕様がそのまま握る —
しきい値を割っても `sticky_turns` (既定 3) の間は注入され続け、その後に消える。
すでに台帳にある記憶を Jev が「今回は浮かばない」と判定した場合も同じ扱いで、
その場で消えるのではなく粘着ウィンドウの分だけ薄れてから消える (従来方式で
cosine しきい値を割ったときとまったく同じ経路)。記憶が急に消えず数ターンかけて
薄れるのは §4.3 の設計意図そのものなので、Jev 層はここに触らない。
回帰テストは `tests/test_auto_recall_jev.py::test_jev_rejection_does_not_evict_sticky_item`。

### 失敗時の振る舞い

TypeSafe API の失敗 (キー無し・タイムアウト・非 200・不正応答) は **そのターンだけ
既存の cosine しきい値方式に静かに戻る** (WARNING ログ 1 行)。自動想起は会話の
同期経路にあり、外部 API の障害がペルソナの返事を止めてはならない。タイムアウトは
既定 2.5 秒 (env 調整可)。

エラー時の規範は「止めるのではなく、記録し、明示し、選択してもらう」— ここでは
フォールバックが「止めない」、WARNING ログが「記録・明示」にあたる。

締切で打ち切ったあとに残るもの: 打ち切りは通信の切断 (close) で行うが、まだ接続を
確立している最中 (TCP 接続・TLS ハンドシェイク) の通信は切断が効かず、会話が
フォールバックして進んだあとに判定リクエストが 1 回だけ遅れて送られることがある。
その応答は誰も読まずに捨てられ、費用は 1 判定ぶん (0.01 円未満) が余分にかかる。
会話は締切で必ず戻るので待たされることはなく、置き去りの通信の本数は**同時 4 本の
上限**で有界になる (締切を超えた呼び出しは通信を切断 (close) してワーカーを終わらせ、
終わったワーカーが枠を返す)。実験層では、これを完全に無くすための通信基盤の
非同期化 (完全キャンセル) はコストに見合わないと裁定した (2026-09-17)。
恒久機能へ昇格させる場合は再検討する。

同時 4 本の上限は**プロセス全体で共有**される。複数ペルソナが同時にターンを回す
賑やかな時間帯は、5 本目以降のターンが Jev を通らずそのまま従来の cosine 方式で
判定される。これは障害ではなく平常動作であり (会話の同期経路でキュー待ちさせない
ための設計)、下の効果測定はこの条件込みで読むこと — 「Jev が効いていないターンが
混ざる」のは、同時実行が混んだ結果でありうる。

### 設定 (すべて env、読み取りは毎ターン)

| env | 既定 | 意味 |
|---|---|---|
| `SAIVERSE_AUTO_RECALL_JEV` | (空) = OFF | `1/true/yes` かつ `TYPESAFE_API_KEY` があるときだけ ON |
| `TYPESAFE_API_KEY` | (空) | TypeSafe API キー |
| `SAIVERSE_AUTO_RECALL_JEV_FLOOR` | 0.78 | Jev に渡す候補の embed_score 下限 |
| `SAIVERSE_AUTO_RECALL_JEV_THRESHOLD` | 0.5 | 採用に必要な Noul 確率 |
| `SAIVERSE_AUTO_RECALL_JEV_TIMEOUT` | 2.5 | API タイムアウト (秒) |
| `SAIVERSE_AUTO_RECALL_JEV_CONTEXT_MESSAGES` | 6 | state に入れる直近会話メッセージ数 |

既定 OFF は「旧経路を flag で残す」判定 (feedback_no_dead_code_via_flags) には
該当しない — §10-1 が「明示的なオプション層」を要求しており、cosine 方式は
置き換え対象ではなくフォールバックとして恒久に残る本体だから。

### 置き場所

- `saiverse/typesafe_client.py` — 薄い HTTP クライアント (httpx 使用、依存追加なし)。
  Jev の判定口は今後ツール選択・自律判断の実験でも使う想定があるため、
  auto_recall 内へ埋め込まず独立モジュールにする。
- `sea/auto_recall.py` — 候補の絞り込みと採否判定の差し込みのみ。

## 効果測定 (実験の合否判定)

DEBUG ログに候補ごとの `embed_score` / `noul` / 採否を出す。まはーの実機評価の観点:

1. 0.86 一本のときに浮かばなかった記憶が、適切な場面で浮かぶようになったか
2. 無関係な記憶の注入 (ノイズ) が減ったか
3. 会話の体感遅延が許容範囲か (追加レイテンシは API 1 往復ぶん)

ダメなら env を OFF に戻すだけで完全に元の挙動へ戻る。
