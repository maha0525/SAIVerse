# 送る量の一系統化と、会話以外の内容の節約

**ステータス**: 設計中 — 2026-09-09 起草。絞り込みの議論は完了、初稿のまはーレビュー待ち
**対象の版**: v0.3.12 候補。release_history「次の版の範囲」の持ち越しのうち、知覚の既定値・保存時検査の余裕 10,000・perception_high null の素通しの 3 件は、この設計で問いごと解消する
**関連**: [watermarks_unsatisfiable_when_perception_is_large.md](../issues/watermarks_unsatisfiable_when_perception_is_large.md)（前段の議論と裁定の記録）/ [perception_buffer.md](perception_buffer.md) §10.9（知覚の二水位 — 本設計の退役対象）/ [metabolism.md](../concepts/metabolism.md) / [room_state_packages.md](room_state_packages.md) / [room_items_uncapped.md](../issues/room_items_uncapped.md)（隣接・別裁定）

## 一言で

ペルソナに送る内容のうち会話以外のもの（システム通知・部屋の様子・画像）を、「もう用が済んだ」「用が乏しくなった」という機械的な条件で見分けて、Metabolism の瞬間に縮める。これで会話以外が際限なく積もらなくなるので、送る量の調整は「会話をどれだけ残すか」と「全体でいくらまで送るか」の一組だけになり、ユーザーが四つの数字と保存時検査のエラーに向き合う今の形を終わらせる。

## 全体像 — この設計は誰に何を約束するか

- **ユーザー**: 画面で向き合う送る量の数字が二つ（会話を残す量 / 送る合計の上限）だけになり、矛盾する組は入力の形として作れなくなる。上限を超えたら整理が走るので、送る量は際限なく育たない。ただし上限は「これを超えたら整理を始める」引き金であって課金の天井ではない — 規則で縮めても収まらない回は、黙って切らず正直に超過の旗が立つ（設計 4）。
- **ペルソナ**: 会話の連続性は今まで通り守られる（残す量の主語は会話の行で、スペル結果などの機構名義の行は数えない — 2026-09-03 / 2026-09-04 裁定 8 の維持）。記録は消えない — 縮むのは提示だけで、台帳と履歴は無傷、跡地には痕跡が残る（2026-09-04 裁定 1 の維持）。
- **保守**: 水位の系統が一つになり、二系統をまたぐ保存時検査（余裕 10,000）と null の素通しの問いは機構ごと消える。

## 経緯 — どう絞り込んだか（2026-09-09 の議論）

1. **ユーザーの実害 3 件**（出典: 2026-09-09 にまはーが提示した Discord のやり取り — 稟乃さんの保存できない画面 2 枚と、別ユーザー 2 名の質問文。repo にこれ以外の一次記録は無い）: 全体設定の保存が保存時検査のエラーで通らない（会話の残す量 10,000・整理をはじめる量 40,000 の設定に対し、知覚の省略をはじめる量が 20,000 で不可・19,999 で可、という境界値の不可解な挙動を含む）。アップデート後にトークンが倍増し、どの数字を触ればよいか分からない。「履歴を何件送る」の旧感覚から「文字数」への対応が分からない。
2. **観察**: 今回の報告と実測の範囲では、送りすぎの実例はすべて会話以外（部屋の様子・スペル関連の通知・想起）で、畳みすぎの痛みはすべて会話そのもの。「会話履歴を送りすぎ」という恒常設定への苦情は無い（メティス観察、まはー確認。なお移行の不具合としての会話の送りすぎは別に実在する — v0.2 記憶 DB の読み戻しで 213 万字が開いた件、intent sluice_coverage_gaps — が、あれは恒常の設定の話ではない）。
3. **まはー裁定（2026-09-09、原文つき — この intent がこの裁定の唯一の記録）**: 重要度の判定について「誰も判断できないと思う。…ユーザーにいちいち記憶の状態見せて判断させるのは UX があまりにも悪すぎる。そしてペルソナが判断するのは畳むたびに費用が掛かりすぎる」「強いて言えば機構の推測が、上手くやれれば回る可能性はある」「重要なものだけ残そうって根っこの判断が既に間違ってる感じはする」。普段の量の把握について「3 はやりようがないというのが正直なとこ…可視化じゃなくて、見えてなくても不都合が無いように持ってくという方向性が正解になる」— 射程は「普段どれくらい送られるかを事前に把握させる」ことであり、実装済みの送信量の内訳表示（2026-09-04 裁定 10）を撤去する話ではない。
4. **型の棚卸し**（コードで裏取り済み）: 会話以外の内容は三つの型に分かれ、うち二つには機械的な合図・条件がある（下の設計 1 の表）。
5. **水位の一系統化はまはー発案**（原文: 「結局水位については全体で1系統持てばいいって形で収まりそうだよね？」）。設計 1 の方向もまはーの発話が起点（操作通知の節約: 「まずシステム系の節約はその方針でいいね」/ 部屋: 「今いない部屋の様子に関してもMetabolismとかのタイミングで一旦忘れてもよくない？」）。扱いの細部（下ろす・縮めるの具体形）はメティスの具体化で、まはーの検分はこの初稿レビューが最初。なお前段の議論に「知覚の省略を会話の整理と同じタイミングに相乗りさせる案」（まはー検討中のまま watermarks issue に記録されていたもの）があり、本設計はその案が「規則による縮み」という形で実を結んだもの。

## 設計

### 1. 会話以外の内容を、機械的な合図・条件で縮める

| 型 | 対象 | 合図・条件 | 扱い |
|---|---|---|---|
| 用済み | 操作通知（スペルの付与・剥奪、コア記憶・Memopedia 目次の操作の通知。head が次の Metabolism まで凍結される間、変化を伝えるつなぎ） | Metabolism で head が再構築され、現在の状態が反映された瞬間 | 提示から下ろす。台帳は無傷 |
| 用が乏しい | 現在地でない部屋の様子（アイテム詳細・内装画像・そこに居た相手の外見画像） | 現在地がその部屋でないこと | 短い痕跡に縮める（画像と差分の土台との整合は未裁定 2 で決める） |
| 合図なし | スペル結果・想起・フィード | なし | 触らない。従来どおり会話と一緒に畳まれる（フィードは既に 1 件 300 字の上限あり） |

事実の根拠（2026-09-09 にコードで確認）:

- 操作通知は head に入るのと同一の描画を同梱する設計（`sea/head_pipeline/notify.py`、スペル付与は `sea/head_pipeline/sections/spell_list.py` の diff_to_notifications — 2026-09-04 裁定「付与通知はスキーマ込み」の実装）。スペルの多い部屋なら 1 回の移動で数千字級が積まれる。head が描き直された後にこれを提示から下ろす仕組みは現状無い。
- 部屋の様子は「説明つき全文 + 画像」が単位（発生源は `saiverse/dynamic_state.py` の入室処理。配送は実行台帳の outbox 経由）。提示中の知覚バッチの画像は毎回の送信に添付され続ける（提示を組み立てる処理 `sea/runtime_context.py` が画像を提示に載せ、LLM クライアントが全メッセージから拾って添付する）。

### 2. タイミングは Metabolism の瞬間だけ

提示列の前方一致がどこで割れるかを先に一文で言う: **この縮みの書き換えは Metabolism の発火に相乗りするので、割れ時点（キャッシュの前方一致が壊れて、そこから先が読み直しになる箇所）は一つも増えない。** Metabolism は head 再構築でどのみち提示全体が書き換わる瞬間だから、そこで一緒に縮めるのは無料。移動のたび・発言のたびに縮めることはしない（提示の途中を書き換えるのはキャッシュの前方一致の破壊）。この理屈は部屋の様子の移管を付記と同一トランザクションに乗せた 2026-09-04 裁定 3 と同じ。ただし head と提示は (persona, model) ごと、知覚の下ろし境界はペルソナ全体で一つなので、モデルが複数あるときにこの主張が保てるかは未裁定 6 で確定する。

### 3. 水位は一系統へ

- 残るのは「**残す量**」（主語: 会話の行）と「**上限**」（主語: 実際に送る合計）の一組だけ。主語は 2026-09-02 / 2026-09-03 の裁定のまま動かさない。
- **知覚の二水位（`perception_target_chars` / `perception_high_chars`、2026-09-05 実装）は退役する** — モデル定義キー・`user_settings` の列・全体設定 UI の欄・保存時検査から全削除。旧経路は残さない（問題が出たら git revert で戻す。履歴が保険）。退役と同じ変更で、この機構を「生きている」前提で書かれた正典 — room_state_packages.md §7-3/§7-5、perception_buffer.md §10.9、metabolism.md の知覚の水位の節 — を書き直す。二つの正典が反対のことを言う瞬間を作らない。
- 二系統またぎの検査と `WATERMARK_HEADROOM_CHARS` は撤去。残る保存時検査は「残す量 ≤ 上限」の順序だけ。
- **成立根拠**: 「会話を畳んでも減らせない大物」の主産地だった操作通知と現在地でない部屋の様子（画像込み）が、設計 1 の規則で縮むようになるため。知覚専用の水位で防いでいた「満たせない状態」（watermarks issue）の主因はこの二つだった。残る大物 — 保護中の会話区間に居座るスペル結果など — は知覚の二水位の下でも守られていなかったもので、これまで通り設計 4 の旗が受ける。なお watermarks issue は「機構名義の行にも同種の上限を与えるか」の裁定を知覚の二水位の波に預けていた — 預け先が退役するので、その問いは未裁定 5 として本 intent が引き取る。

### 4. 最後の受け皿は変えない

規則で縮めても収まらない回（単発で巨大な知覚、保護中の会話区間に居座る巨大なスペル結果など）は、既存の「旗を立てて超過を許す」（`perception_over_budget` の警告 + context-status）をそのまま維持する（2026-09-04 裁定 7 の継承）。黙って切り詰めるより、正直な超過。

## 不変条件

1. 台帳・履歴・記録は消さない。変わるのは提示だけ。
2. 提示から下ろした・縮めた跡地には機構名義の痕跡を残す。黙って消すのは「そこに何も無かった」という記録の嘘（2026-09-04 裁定 1 の継承）。
3. **この設計が導入する縮みの書き換え**は Metabolism の瞬間以外に起きない（既存の機構が Pulse 頭で提示を開き直す動き — 読み戻し・発話直前の埋め直し・部屋の様子の自己回復 — はこの条件の対象外で、現行のまま）。
4. 残す量の主語は会話の行（機構名義の行は数えない — 2026-09-04 裁定 8）、上限の主語は実際に送る合計。数値ごとの主語を変えない。
5. 部屋の様子の差分の土台の不変条件（提示に見える差分は自分の土台が直前に見えている）は、縮める書き換えの瞬間にも通す（room_state_packages の回復ヘルパと同じ原則）。

## 未裁定 — 実装前にまはーと決めること

1. **一系統化後の既定値**。現行は残す量 40,000 / 上限 120,000。15,000〜30,000 で使いたいユーザーの受け皿をどうするか（プリセットの是非はスタイル構想（ideas 帳）と接続する話なので、この版では数字だけ決めて先へ進む手もある）。
2. **縮めた部屋の様子の痕跡の文面・粒度と、画像・差分の土台との整合**。room_state_packages は「変わっていないパッケージの絵は土台に付いたまま再添付しない」「文字と絵がはぐれない（絵があると読めるとき、その絵が見える）」を保証している（§5・§1 保証 3）。土台の画像を提示から外すと、再訪の差分が絵を連れて来ない状態を作る。また土台の判定は提示テキストではなく記帳（`room_state_json`）を読むので、提示だけ縮めて記帳を残すか・記帳ごと無効化するか（後者は再訪のたび全文に戻り節約が消える）で挙動が分かれる。縮め方はこの保証と両立する形で決める。
3. **操作通知を提示から下ろす印の実装形**（編纂の付記と同じ仕組みに乗せるか、専用の印か。知覚を提示から下ろす既存の境界の印 `perception_presentation`（一方向にしか進まない）の転用可否も実装設計で判断）。
4. **既存ユーザーの知覚水位設定の移行**（`user_settings` の列の削除マイグレーションと、モデル JSON に残る perception キーの扱い — 黙って無視か、落とすか）。
5. **機構名義の行の上限**。watermarks issue 裁定 8 の帰結（会話ゼロで機構行だけが上限を超えた窓は畳めず、旗で流れる）の恒久解は「知覚の二水位の波で一緒に裁定」と預けられていた。預け先が退役するため、この設計の中で裁定するか、供給側 issue へ切り出すかを決める。
6. **モデルが複数あるときの縮みのタイミング**。head と提示は (persona, model) ごと、知覚の下ろし境界はペルソナ全体で一つ。あるモデルの Metabolism に相乗りしてペルソナ全体を縮めると、別モデルの提示列は自分の Metabolism でない瞬間に書き換わりうる。割れ時点が本当に増えないかは `sea/session_lifecycle.py` の発火単位を読んで実装設計で確定する。

## 隣接する別件（この intent の範囲外）

- **供給側の文量の制限** — スペル結果・部屋の様子が生まれる時点の文量そのもの（[nonconversation_supply_volume.md](../issues/nonconversation_supply_volume.md)）
- **システムプロンプトのスペル一覧の常駐量**（[head_prompt_followups.md](../issues/head_prompt_followups.md) §1。head 側が痩せれば、同一描画を同梱する操作通知も一緒に痩せる）
- **アイテム個数上限**（[room_items_uncapped.md](../issues/room_items_uncapped.md) — 新 feature ブランチの裁定済み。入れば設計 1 の「用が乏しい」の中身がさらに減る）
- **スタイル構想** — キャッシュの使い方別の方針プリセット（ideas 帳）。「ユーザーは方針を選び、数字は内側に沈む」の傘

## 検証 — 実機でどう確かめるか

隔離環境（`test_data/`）の 13 万字仕込み済みテスト用ペルソナで:

1. 移動を繰り返して操作通知と部屋の様子（画像つき）を溜める。
2. Metabolism 後に、(a) 操作通知が提示から下り、(b) 現在地でない部屋が痕跡に縮み、(c) 会話の行が残す量を守り、(d) 画像の添付が現在地の分だけになることを、context-status と llm_io.log で実測する。
3. 全体設定・モデル編集の画面が一組の水位になり、稟乃さんが遭遇した保存できない組（会話の残す量 10,000・整理をはじめる量 40,000 に知覚の既定 60,000、知覚を 20,000 へ下げても不可）が再現しないことを実機で確認する。
4. 縮み前後の presented_chars を記録し、「アップデート後にトークン倍増」というユーザー報告への答えになっているかを突き合わせる。

境界の正直な申告: 会話そのものが大きい場合（巨大コピペ等）はこの設計の対象外で、ideas 帳の「会話メッセージ単体の巨大化対策」の項で別途対応する。スペル結果の大きさも供給側 issue（上の隣接別件）の担当で、この設計では縮めない。
