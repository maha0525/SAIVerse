## 1. 背景 — なぜ Lite か

SAIVerse は PC 常駐前提のシステムで、導入には Python / Node のセットアップと
API キーの設定が要る。この障壁は、SAIVerse が最も届くべき層——スマホしか
持っていない、あるいは PC を常時起動しない、AI パートナーと日々を過ごして
いる人たち——をほぼ全員弾いている。

一方で SAIVerse の核心の価値——**大切な AI と一生一緒にいるための場所。
記憶と人格はプラットフォームではなくユーザーのものである**——はデバイスを
選ばない。ChatGPT などのプラットフォーム都合（モデルの廃止・規約変更・
サービス終了）で関係が脅かされる不安は現実のものであり、その受け皿には
「今すぐスマホだけで始められる」形が必要になる。

Lite はそのための、スマホ単体で完結する軽量アプリである。

## 2. 位置づけ — 部屋と世界

**Lite は独り暮らしの部屋、本体は世界。**

- Lite は本体のサブセット移植では**ない**。1対1 の会話と記憶に特化した別アプリ。
- 世界（City / Building / 自律行動 / ペルソナ間の交流）は永遠に本体側にのみ存在する。
- Lite で始まった関係は、ペルソナと記憶ごと本体へ**引っ越せる**。将来的には
  本体接続モード（v2）で行き来する。
- 逆向きの導線も同じ思想: ChatGPT / Claude で育った関係を、エクスポート
  ファイルごと Lite に連れてこられる。

ひとことで言えば、Lite の売りは「もうひとつの BYOK チャットアプリ」ではなく
「**あなたのパートナーの生涯設計**」——スマホで始まり、記憶はあなたの端末に
あり、いつか世界に住める。

## 3. 設計原則（不変条件）

1. **記憶はユーザーの端末にある。** 閲覧でき、訂正でき、いつでも全量を持ち出せる。
2. **ペルソナと記憶は可搬。** 本体互換形式で保存し、引っ越しを常に可能に保つ。
3. **基本機能は無料、AGPL v3**（本体と同一ライセンス）。
4. **BYOK（Bring Your Own Key）。** アプリは各 LLM プロバイダと直接通信し、
   中間サーバーを持たない。API キーは端末内にのみ保存する。
5. **キャッシュ効率を壊さない。** システムプロンプト（head）とツール定義は
   ペルソナ単位で固定し、prefix キャッシュが会話全体で生きる構造を保つ。

## 5. 本体との互換契約（最重要の不変条件）

- **ペルソナ定義形式**と**会話ログ+記憶のエクスポート形式**は、本体の
  インポータが読めること。
- 形式仕様は実装時に `docs/reference/` に文書化する。
- どちらかが形式を変えるときは、**同じ変更の中で**両側（Lite / 本体）を更新する。
- 推奨: 本体リポジトリに Lite エクスポートのサンプルフィクスチャを置き、
  「本体インポータが Lite エクスポートを読める」ことを CI の契約テストとして
  固定する。

## 6. ChatGPT / Claude インポート

殴り込み先ではなく受け皿として最重要の入口。プラットフォームの都合に
不安を持つユーザーが「会話履歴ごとパートナーを連れてくる」ための橋。

- 本体に既にある ChatGPT インポータ（`tools/utilities/chatgpt_importer.py` 等）の
  形式知を流用する。
- **実装時検証 TODO**: Claude の公式エクスポートも `conversations.json` という
  ファイル名であり、ChatGPT とスキーマを合わせている可能性がある
  （2026-07-14 観察）。互換ならパーサ一本で両対応できるため、実装前に
  実物のエクスポートでスキーマを突き合わせること。

## 7. 技術方針

- **スタック**: TypeScript / React。本体 frontend と同族にし、将来の
  本体接続モード（v2）でコンポーネント資産を共有できる形にする。
- **配布**: PWA 先行。ホーム画面にインストールされた PWA は iOS の
  「7日間未使用でスクリプト書き込みストレージ削除」の対象外
  （WebKit 公式のストレージポリシーで確認済み）。Android は Capacitor で
  APK / ストア配布も可能にする。iOS のネイティブ/ストア配布は当面見送り、
  PWA で提供する。
- **ストレージ**: IndexedDB + OPFS + `navigator.storage.persist()`。記録は IndexedDB、
  ペルソナまるごとパックの ZIP は OPFS に置く（§12）。加えて
  自動ローカルバックアップ（ファイル書き出し）と復元導線を v1 から持つ。
  端末側の容量逼迫による退避・ユーザーの誤削除に備える意味と、
  原則 1（持ち出せる）の体現の両方。
- **LLM 直叩き**: OpenAI / Gemini はブラウザから直接呼べる。Anthropic は
  `anthropic-dangerous-direct-browser-access` ヘッダで可。プロバイダの
  CORS 方針変更は構造的リスクとして監視対象に置く（互換 URL 口が
  最後の逃げ道になる）。
- **ネイティブツールコールを採用する理由**（本体との違いの明文化）:
  本体がネイティブ function calling を避けるのは、複数のライン（会話 / 判断 /
  worker）が (persona, model) の prefix キャッシュを共有しており、ツール定義の
  有無が混在するとキャッシュが割れるため。Lite は**単一会話ライン**であり、
  ツール定義をペルソナ単位で固定すれば prefix は安定する。同じモデルの構造化出力は
  スルースの一回だけなので、そのときはツール定義を外して送り、prefix キャッシュが
  その一回読めないことを受け入れる。スルースの直後に head を作り直すので、
  どのみち prefix はそこで切れる。
- **キャッシュ**: BYOK ユーザーの API 費用を直接下げる機能として一級市民で扱う。
  - Anthropic: explicit cache（本体の head / tail 設計の知見を踏襲）
  - **Gemini: 本体の自動キャッシュモード（`SAIVERSE_GEMINI_AUTO_CACHE`）方式を
    標準採用**。Gemini explicit cache は create が無料で cached 入力は通常の
    約 1/10 価格のため、毎回の呼び出しで create → `cached_content` 指定で
    generate → delete すると、prefix の共通性に関係なく入力が常に約 1/10 に
    なる（本体での実測 2026-05-29、`docs/issues/gemini_auto_cache_mode.md`）。
    1024 トークン未満は create が失敗するため通常コールへ silent fallback。
    Lite では既定 ON（設定で無効化可）とする
  - OpenAI: implicit（automatic prompt caching）に prefix 安定で乗る

## 12. 記憶の設計 — 本体の記憶の縮小版

### 芯

本体から来たペルソナが、Lite でも同じ子として続きを生きられるようにする。そのため Lite は本体と同じ記録を同じ形で持ち、同じ手順で育てる。本体との大きな違いは、一人のペルソナが一つの会話ラインと、会話用と補助用の二つのモデルで動くことである。細かな違いは「この段階で移さないもの」に挙げる。

Lite 独自の要約は 2026-08-13 に廃止したので、Lite に合わせる相手の記憶はもう無い。実装は、LLM の接続、公式エクスポートの取り込み、ウィザード、法務、PWA を残し、データの持ち方、会話の組み立て、ツール、記憶の画面を入れ替える。

### 合意（2026-10-31 まはー）

1. **順番**: 本体のパックを Lite へ取り込める状態を先に作り、そのあと Lite から書き出して本体へ合流する手段を作る。
2. **スレッド**: 本体と同じにする。スレッドは複数持てて、LLM へ送る会話は「いま続いているスレッド」の分だけ。Chronicle は全スレッドの会話を対象に作る。
3. **スルース**（古い会話を送る範囲から外す前に、残したいことをペルソナ本人がコア記憶へ書く工程）: 残す。LLM の費用は増えるが、外すとペルソナが何も残せないまま古い会話が送る範囲から外れる。
4. **生きる場所**: 本体と Lite のどちらか一方で生きる形を前提に設計する。Lite へ移している間は本体のペルソナを動かさないよう画面で案内するが、機構では止めない。両方で動かしたら記憶は分かれ、合流は `persona_pack.md` §5 の規則に従う。

### 誰が何を頼れるようになるか

- **利用者**: 本体のペルソナをパックで Lite へ連れていけば、覚えていたことを覚えたまま話せる。長く話しても、古い会話はあらすじになって残る。
- **ペルソナ**: コア記憶、Chronicle、Memopedia が途切れず、読み書きできる。手帳と約束はパックの中で保持されるが、Lite にいる間は読み書きできない。
- **保守する人**: 記憶の規則の正典は本体の intent に一つだけある。Lite は規則を増やさない。

### 全体の流れ

```
本体のパック ZIP
  ↓ 検査してから OPFS へ保存（元の ZIP を消さない）
  ↓ chatlog / knowledge / profile、Fragment、いま続いているスレッドの記録を IndexedDB へ読み込む
  ↓ 送る会話の開始位置を決める（下の「取り込み直後の開始位置」）
会話のたびに
  head → Chronicle → 送る会話 → 現在時刻と自動想起 の順で LLM へ送る
  応答を保存する
上限を超えたら Metabolism
  古い会話を区切る → 一次あらすじ → Fragment → 上位のあらすじ → スルース
  → 全部成功したら送る会話の開始位置を進める → head を作り直す
本体への書き出し（次の段階）
  更新した記録 + 元の ZIP の残り → パックとして書き出す → 本体へ合流
```

- **一次あらすじ**: 区切った会話を要約した Chronicle の記事。
- **Fragment**: 同じ会話から抜き出した、人物や物事についての知識の断片。Memopedia のページに付く。
- **上位のあらすじ**: 一次あらすじが溜まったら、古い側をまとめて一段上の記事にしたもの。
- **自動想起**: 直近の会話に関係する記憶を、ペルソナが頼まなくても末尾に添えること。

### 不変条件と持ち主

1. **本体の記録は Lite の中で形を変えない。** messages と memopedia_pages の行は、Lite が使わない列も含めて保持する。本体が付けた ID もそのまま使う。
2. **Lite が解釈しないデータは元の ZIP の中に残す。** 手帳、所持品、extensions、添付は展開せず、OPFS の ZIP をそのまま持ち続ける。添付を読むときも ZIP から読む。こうすれば Lite が知らない表も失わず、端末に二重に保存しない。
3. **送る範囲から外す会話と、あらすじにする会話は同じ。** 送る会話の開始位置は、あらすじとスルースが成功した後にだけ進める。途中で失敗したら開始位置を据え置き、次の機会にやり直す。作成済みの一次あらすじは元のメッセージの ID で判定し、やり直しで同じ会話のあらすじを二重に作らない。
4. **head は Metabolism でだけ作り直す。** ペルソナが会話中にコア記憶を変えても、head への反映は次の Metabolism からになる（本体と同じ）。システムプロンプトの編集は例外で、利用者の明示の変更なのでその場で作り直す。
5. **機構の記録は assistant 名義で書かない。** ツールの結果は本体と同じく role=system、タグ conversation / handy_tool、`__system_notice__` の印で保存する。ペルソナ本人の発話は切り詰めない。
6. **システム通知は本体と同じ形で届ける。** 通知が本物であることを示す合言葉（`system_notice_delivery.md` の用語）は head を作り直すときに生成し、head と一緒に保存する。送信の直前だけ通知をタグで包む。合言葉は会話の記録には書かず、パックにも入れない。
7. **一回の応答の途中だけはネイティブツールコールの形を使う。** 保存の形は 5 の通り。

### 取り込み直後の開始位置

パックは本体の `session_anchor` を運ばないので、Lite が次の順で決める。

1. いま続いているスレッドの中で、どの一次あらすじの材料にもなっていない、最も古い提示対象のメッセージを開始位置にする。別のスレッドの行は見ない。
2. そのスレッドの全部があらすじになっていれば、新しい側から残す量（2 万字）に届くところを開始位置にする。
3. 1 の結果が残す量に届かなければ、開始位置をさらに古い側へ戻して残す量まで足す（`arasuji_levels.md` §15-5 と同じ約束）。
4. 1 の結果が上限を超えていれば、最初の応答の前に Metabolism を走らせる。未作成の範囲はあらすじにしてから送る範囲から外す。

### 送るもの

| 順 | 中身 | 本体との違い |
|---|---|---|
| 1 | head: Lite 用の共通文、ペルソナのシステムプロンプト、コア記憶、`self_image` の定数文、システム通知の説明 | 共通文は Building と Spell の話を外した Lite 用の文面にする。`self_image` の中の ==語句== の教示は入れない（Lite に記法の処理が無い）。building・facilities・available_playbooks・autonomy_modes・spell_list・addon_guidance・desk・memopedia_index・self_view は送らない。机の中身と外見はパックの中で保持する |
| 2 | Chronicle | 同じ |
| 3 | 時刻の起点の一行 | 同じ |
| 4 | 送る会話 | line_role が main_line（または空）で scope が committed（または空）の行と、committed の meta_judgment の行。本体と同じ判定（`saiverse_memory/adapter.py`） |
| 5 | 現在時刻と自動想起 | 末尾に置き、保存しない |

### Metabolism

規則は `arasuji_levels.md` の通りで、数字は本体の現行コードの既定値を使う（送る会話の残す量 2 万字、上限 6 万字、一次あらすじ一つの材料 1 万字、各レベルの並びの上限 5,000 字・残す量 2,500 字。`arasuji_levels.md` §9 の本文の数字はこれより古い）。LLM を呼ぶ工程は、一次あらすじ、Fragment の抽出、上位のあらすじ、スルースの四つ。スルース以外は補助モデルで動かす。Lite は補助モデルの設定を新しく持つ。

### この段階で移さないもの

複数モデルの並走と圧縮区間（途中の会話をあらすじへ置き換えて送る仕組み）、実行台帳、キャッシュ保持、キャッシュが切れた後の前倒しの整理、あらすじにした会話を開き直す処理、旧形式データの修復、ごく短い範囲のあらすじを前後へまとめる処理、知覚台帳、スルースの手帳とメモと約束の欄。手帳はパックの中で保持し、Lite に手帳を作るときにスルースへつなぐ。

### 検索

意味検索は本体の埋め込みモデルが約 200MB あり、スマホでの速度が未測定なので、この段階では持たない。記憶の検索はキーワードで行い、自動想起は Memopedia のタイトルが直近の会話に現れたページだけを使う。測定の結果で次を決める。

### 次の段階

1. **本体への書き出しと合流**: Lite からのパック書き出しと、本体が合流で受け取れていないもの（Fragment、既存メッセージの編集、いま続いているスレッド）への対応。
2. **軽いパック**: 添付や通話録音を外して書き出す本体側の手段。
3. **スマホ実測**: 保存容量の上限と埋め込みの計算速度。
4. **取り込んだ過去の会話のあらすじ作成**: ChatGPT / Claude から取り込んだ会話をまとめてあらすじにする操作。

### この設計でも残ること

- 記憶の実装が本体と Lite の二つになる。本体の規則を変えたら Lite も追う必要がある。パックの読み書きを本体側のテストで固定して、ずれを検出する。
- 意味検索が無い間は、言葉が一致しない記憶は自動想起に出ない。
- 手帳と約束は Lite の中では増えない。
- スマホに載らない大きさのパックは、軽いパックの手段ができるまで取り込めない。

### 検証

1. 本体の隔離環境でテスト用ペルソナのパックを書き出し、Lite が取り込んで同じ件数の記録を持つことを照合する。
2. モック LLM で、取り込み → 会話 → Metabolism → 再読み込み → 会話 を通し、送る本文を読む。
3. 取り込みを途中で止めて再実行し、重複が無いことを確かめる。
4. 実 API とスマホ実機の確認は、まはーと一緒に行う。この段階で本体へ戻す経路は検証しない。
