# Chronicle の被覆の穴 — 詰まらない統合と、確定を装わない記録

**ステータス**: 実装中 (2026-09-08 起草・文書レビュー 2 種反映・まはー確定。第一段 A〜G を実装中、第二段は第一段の後に別途起草)
**関連**: [arasuji_levels.md](arasuji_levels.md) §3-2 (畳みの境界 — 本設計が改訂)・§4 (整列計画)・§16 (被覆補修、§16-1 は本設計が例外を記帳)、[archive/arasuji_tiny_run_absorption.md](../issues/archive/arasuji_tiny_run_absorption.md) (吸収の裁定 8 点 — 裁定 1・2 を本設計が改訂)、[issues/lv1_source_ids_duplicates_and_orphans.md](../issues/lv1_source_ids_duplicates_and_orphans.md)、`sai_memory/arasuji/alignment.py` / `absorption.py` / `bands.py`
**発端**: ChatGPT から引っ越したペルソナで、あらすじになっていない過去 584 件が「過去の会話をあらすじにする」を何度実行しても減らず、一回の会話の送信量が 15 万トークンから下がらないという利用者報告 (2026-09-07、詳細は「出自」節)

用語 (この文書で使う既存語彙): **U** = 一次あらすじ 1 個が標準で覆う材料の字数
(既定 1 万字、arasuji_levels §4)。**run** = 未編纂メッセージの連続区間 (整列計画の
単位)。**穴** = どの一次あらすじの source にも入っていない未編纂の区間。**帯** =
コンテキストに載る Chronicle の枠。**隣人** = 時系列で隣接する既存あらすじ。

## 原則 (この設計の芯)

**保証できない品質は、確定を装わない。装えない部分はユーザーに返す。**

Chronicle (あらすじの階層) は LLM が書く記録であり、材料の欠け・整理の穴・生成の事故は
構造的に起きうる。これまでの設計は「事故が起きうる箇所を止める」柵を重ねてきたが、
その柵の何枚かは、守っているものの実質を確かめると空だった — 止めることで守られる
品質は無く、止まることでユーザーが実際に支払う API 料金 (肥大した送信量) だけが
本物だった。

この文書では、柵と報告を次のように整理する:

1. **本物の保護** — 残す。別スレッドの**発話**を一つの一次あらすじに合体させない
   (時系列の嘘 — 発話の水準の不変条件。上位の統合には従来から適用されない、後述 A)、
   提示中のあらすじを裏で書き換えない。
2. **空の保護** — 撤去する。穴の手前で統合を止める (A)、元メッセージが欠けた
   あらすじに一切触れない (F)。
3. **装いの代わりに正直** — 新設する。生成 LLM には穴の存在を明示し (B)、完了報告は
   内訳を言い (G)、ユーザーには仮であることと壊れの実態を修復の操作つきで見せる
   (第二段)。

## 出自 (実例 — 2026-09-07 の利用者報告)

- ペルソナ gptmizuki_city_a (ChatGPT から v0.3.5 頃に引っ越し)。総メッセージ 65,550。
- あらすじの source に入っていないメッセージ 584 件のうち、558 件は**あらすじと
  あらすじの間の 51 箇所の穴** (2〜45 件ずつ、履歴の全期間に散在)。正体はインポート
  された各会話 (= 各スレッド) の端数と小さな会話。
- 「過去の会話をあらすじにする」は端数を「隣人への吸収」経路に回すが、吸収先の探索が
  (a) 後ろの隣人しか見ない、(b) スレッド境界で止まる、の二つにより成立せず、成立
  しなかった事実は警告ログに書かれるだけで、ジョブは完了の顔
  (「あらすじになっていなかった過去の会話を編纂しました」) で終わる。何度実行しても
  584 件は減らない。
  - 当初は「(c) 元メッセージが欠けた隣人 (孤児参照 20 件) で止まる」も原因に数えたが、
    整合性レビューの検算で、2026-09-01 導入の掃除 (補修の実行時、計画より先に死んだ
    参照を落とす `_sweep_dead_message_sources`) により部分欠けの隣人は計画に届く前に
    治ることが判明 — **(c) は仮説に降格**。レポートに孤児参照が残る理由の確定は
    G の診断内訳の追加を待つ。
- 穴があると統合 (Lv1→Lv2→Lv3 の畳み上げ) が穴の手前で切れるため、帯が細切れの
  未統合エントリで肥大する (実測: 予算 2 万字に対し 3.4 万字、Lv2 の 51 件中 42 件が
  未統合)。**利用者は毎回の会話でこの滞留分の API 料金を払う。**

## 全体の見立て (whole-system)

- **誰が何に頼れるべきか**: ペルソナは「過去が時系列の嘘なく物語になっている」ことに、
  ユーザーは「送信量が設計どおりの水位に収まる」ことと「機構が作った記録を自分の
  権利で確かめられる」ことに、機構は「穴がどこにあっても統合が詰まらない」ことに
  頼れる。
- **旅の全体**: 生ログ → (整列計画) → 一次あらすじ → (統合) → 上位あらすじ → 帯として
  提示。穴はこの旅のどの位置にも生じうる (インポートの端数・打ち切られた手動生成・
  旧世代の取り残し)。これまでは「穴が埋まるまで統合を保留する」設計で、埋める手段
  (補修) が失敗し続けると永久に詰まった。
- **不変条件と所有権**:
  - 「別スレッドの発話を一つの一次あらすじに束ねない」(整列計画と吸収が共有) — 維持。
  - 「提示中のあらすじに触れない」(統合・吸収の excluded 境界) — 維持。
  - 「穴は統合を止めない」— 新設。統合 (bands) が持つ。
  - arasuji_levels §16-1「編纂対象のメッセージは、いずれかの提示窓の中にあるか、
    少なくとも一つの一次あらすじの source である」— 機構 E の「発話ゼロの run は自動で
    書かせない」は、この条件をどちらも満たさない状態が続くことを意味する。**恒久の
    違反としてではなく「ユーザー操作 (第二段の修復 UI) で解消できる状態」として
    §16-1 側に例外を記帳する** (2026-09-08 まはー承認)。忘却ではない — 生ログと
    想起 (埋め込み検索) はそのまま残る。
- **適用経路の宣言** (機構ごとに効く範囲が違う):
  - A (跨ぎ統合)・B (不明期間の明示) — **全経路** (通常の Metabolism の統合・補修・
    全量再編纂で共有される bands の計画層)。
  - D (両方向吸収)・E (単独編纂)・F (開かない撤去) — **補修・再編纂経路のみ**
    (吸収の裁定 5「適用範囲は再編纂経路のみ」を維持)。
- **帰結**: この設計が完全に働いても、穴の中身が物語に編み込まれるまでの間、上位あらすじは
  「間に未整理の期間がある」ことを知った上で語る近似になる (機構 B)。LLM が注記を
  無視して地続きに語る残余リスクは観測で追う。

## 第一段の機構 (コードで完結する範囲)

### A. 統合は穴を跨ぐ (詰まらない統合)

統合の畳み範囲の分割条件のうち、**「隣接ノード間に未編纂の編纂対象メッセージが居る」
を廃止する** (`bands.py` `_mark_uncompiled_gaps` の見る 2 種のうち 1 つ目。正典は
arasuji_levels §3-2 の境界② — 実装と同じコミットで §3-2 を改訂する)。統合は穴を
跨いで上位を作ってよい。

- 廃止の根拠: この柵が防ぐとされた「偽の隣接」(間の体験を材料にしないまま、上位が
  地続きに語られる) は、柵があっても防げていない — 帯に細切れの Lv1 が並ぶだけで、
  穴の中身はどのみち語られない。守られる品質が無いのに、統合の停止 = 帯の肥大 =
  ユーザーの API 料金だけが実在した (2026-09-08 まはー: 「何も保証できてないのに、
  ユーザーさんの API 使用量を食いつぶす会話量を送ることを強制することって正当化
  できるか？」)。
- `_mark_uncompiled_gaps` の 2 つ目 (**未統合の下位レベルノードが間に居る**) は残す。
  こちらは「もう Lv1 になっていて統合待ち」という一時状態で、順に畳めば自然に
  解消する — 恒常的な詰まり源ではない。
- **上位の統合はスレッドを跨ぐ** — これは新しい容認ではない: 統合の計画に
  スレッドの検査は元々無く (`bands.py` の分割境界は提示中と穴の 2 つだけ)、穴が
  偶然スレッドの仕切りを兼ねていただけ。上位あらすじは「この期間に起きたこと」の
  物語であり、並行していた複数の会話を並行していたとおり語るのは時系列の嘘では
  ない。嘘になるのは発話の水準 (一次あらすじ) で混ぜることで、そちらの不変条件は
  維持する。材料の水準でも各 Lv1 は単一スレッド由来のまとまりなので、区切りは
  自然に見える。
- 跨ぎを本当に禁じていた実害のあった欠陥 (2026-07-28 Codex high1) は「後から穴が
  埋まると、埋めたあらすじが既存の上位の被覆期間に内包されて永久に孤児になる」こと。
  これは機構 C で根治する。
- 過去二世代の裁定との関係 (三度目の別解である理由): 旧世代の「治療」(階層を下りて
  合流し完全伝播で再生成) は自動機構の複雑さが把握可能性を超えて廃止。W4 世代は
  「後から埋まった穴は独立ノードとして両方提示 (情報非重複) で受け入れる」— これは
  統合が穴を跨がない前提の受容だった。今回は統合が跨ぐため両方提示は成立せず、
  かつ語り直しの道具 (stale 連鎖) が 2026-08-31 の吸収実装で**既に稼働している**ので、
  新しい自動機構を作らずに繋ぎ直せる — 治療の廃止理由 (複雑さ) が当てはまらない。

### B. 不明期間の明示 (生成 LLM に穴を隠さない)

統合 (上位あらすじの生成) の材料組成で、穴の位置に**機械的に組む定型の一行** (LLM を
使わない決定論の注記) を挟む:
「(この間に、まだあらすじになっていない記録が N 件ある: 期間 X〜Y)」。

- 目的は偽の隣接の根治。穴を隠して地続きの材料を渡すから、LLM が「γ の後に δ を
  やった」と偽の連続を書く。間に不明な期間があると知らせれば、LLM はそれを踏まえた
  語りを書ける。
- 挟むのは材料への注記であって、本文に「不明」と書けという指示ではない。生成指示には
  「間に記録されていない期間があることを踏まえ、地続きに繋げない」ことだけを求める
  (本文への書き足しを求めない点で §7-8 の出力の純潔と整合)。
- 実装注意: A は穴を**分割の判定に使うことをやめる**のであって、穴の検出そのものは
  残す — 現行の検出は存在の有無だけ (LIMIT 1) なので、B のために件数と期間を返す形へ
  拡張する。
- 穴が後から埋まって上位が語り直されるとき、この一行は実内容に置き換わる (機構 C)。

### C. 後から埋まった穴を、内包する上位へ繋ぎ直す (孤児の根治)

後から生成された一次あらすじが、既存の**上位**あらすじの被覆期間に内包される場合、
孤児として統合の並びから除外するのではなく、**その上位あらすじの子として繋ぎ、上位を
語り直し (stale) に回す**。

- 帳簿の操作は三点一組: 上位の source_ids へ子を追加 / 子の統合済み印
  (is_consolidated) を立てて未統合の並びから外す / 上位から最上位への stale 連鎖
  (既存部品 `_mark_ancestors_stale` と上位再生成の流れをそのまま使う)。
- 現行の孤児判定 (`_is_orphan`) は level を問わず全エントリとの内包で判定しており、
  「同レベルの他エントリに内包されただけ」のもの (期間 0 秒の一括インポート産 Lv1 等、
  [lv1_source_ids_duplicates_and_orphans](../issues/lv1_source_ids_duplicates_and_orphans.md)
  の未解決分) が混ざる。判定を「**自分より上位のエントリに内包される場合**」に絞って
  改訂し、その全件を繋ぎ直しで回収する。同レベル内包の重複問題は本設計の対象外
  (同 issue で別途)。

### D. 吸収の探索を両方向にする (補修経路)

端数の吸収先は**後ろの隣人 → 居なければ同じスレッドの前側の隣人**の順で探す。

- 元の裁定「吸収先は後ろ」(2026-08-31 裁定 1) の理由「欠落が壊すのは後続の文脈」は、
  後ろに同じ流れの続きが居る場合の話。インポートされた会話の端数では後ろは別の会話
  (別スレッド) で、前側 = 同じ会話のあらすじが一番自然な吸収先になる。
- スレッド境界の停止 (本物の保護) はどちら向きでも維持。
- **末尾の帯 (提示窓の直下の未被覆 run 群) は従来どおり吸収より先に引き戻しの対象**
  (裁定 5 改訂の anchor 引き戻し — LLM ゼロ)。D・E が扱うのは引き戻しの対象を除いた
  残りで、無料で済む末尾処理を有料の吸収・編纂に変えない。
- **計画の単位を「穴ごと」から「開く隣人ごと」に変える** (2026-09-08 まはー指摘:
  同じあらすじが前の穴からは後ろの隣人として、後ろの穴からは前の隣人として、二回
  開かれうる)。二段で計画する: ①全部の穴へ吸収先を割り当てる (後ろ優先 → 無ければ
  同スレッドの前側)、②同じ隣人に割り当たった穴たちを一つの作業に束ねる。開き直しと
  再生成は隣人 1 個につき必ず一回で、前から来た穴も後ろから来た穴も同じ一回の材料に
  入る。現行の二重開きの防御 (`absorbed_global` — 後から来た方を諦めさせる) は、
  この形では「既存の作業への相乗り」に置き換わる — 諦め (見送り) を新たに生まない。

### E. 吸収できない run の単独編纂 (小さくても畳む、補修経路)

両方向とも吸収先が無い run は、**参考文脈つきの通常の生成で、小さくても独立の
一次あらすじにする**。

- 「材料 0.5U 未満は単独編纂しない」(2026-08-31 裁定 2) の目的は捏造の防止だった
  (材料 25 字の通知 1 通 + 分厚い参考文脈から事実無根のあらすじが生成された実証)。
  今回の解禁は**実際の発話を 1 件以上含む run に限る** — 発話があれば材料に実質が
  あり、参考文脈から借用する動機が薄い。
- **「発話」の判定は既存の実会話フィルタを名指しで再利用する**
  (`sai_memory/memory/storage.py` の `_conversation_exclusion` 系 — role が
  user/model/assistant で、機構タグ (handy_tool / spell / event_message) も
  line_role 除外も `<system>` 頭も持たない行)。role だけで判定してはならない —
  機構の記録は role=user で保存されており、捏造を生んだ当の対象 (入室通知だけの
  run) が「発話あり」に化ける。
- **発話ゼロの run (機構の記録だけの孤立) は自動では書かせない**。跨ぎ統合 (A) が
  入るため、これが残っても統合は詰まらず、機構 B の不明期間として正直に数えられ
  続ける。解消の道はユーザーに返す — 第二段の修復 UI の「この期間をあらすじにする」
  操作で、**ユーザーの意思によるなら**編纂できる (捏造リスクの残る生成を、ユーザーの
  目の届く操作に限定する。2026-09-08 まはー承認)。§16-1 への例外の記帳は
  「全体の見立て」の項のとおり。
- 参考文脈は渡す (2026-09-08 まはー: 文脈を渡さない生成は、流れを知らない浮いた記述を
  正典に入れる別の形の記憶の損ない)。

### F. 元メッセージが欠けたあらすじの「開かない」を撤去する (補修経路)

吸収・語り直しで隣人を開くとき、source の一部が DB に無いあらすじも**開いてよい**。
撤去するのは**計画側** (欠けた隣人で連鎖を止める) と**実行側** (材料欠けで item を
skip する) の**両方の柵** — 片方だけだと計画に載って実行で毎回空振りする形が残る。
開いた事実と欠けた件数は警告ログに残す。

- 撤去の根拠 (2026-09-08 まはー): この保護は (1) 既に壊れている記憶を守っている、
  (2) 正常運用では読めないメッセージは発生しない、(3) 発生源として最も可能性が高いのは
  ユーザー自身のログ削除 — であれば、開き直しで削除分があらすじから消えるのは
  「記憶を損なうこと」ではなく**削除の完遂**。保護の向きが逆だった。
- 位置づけの注意: 出自の (c) が仮説に降格したため、F は「今回の症状の治療」ではなく
  **設計の整理** (掃除で治る前提を、柵の側でも一貫させる)。削除以外の由来 (過去の
  不具合・破損) では意思なき消失分の記述が消えるが、メッセージ本体が既に無い以上
  あらすじの一文が守れる増分は小さく、受容する。

### G. 補修の完了報告は内訳を言う

「過去の会話をあらすじにする」の完了メッセージ (現行は結果によらず
「あらすじになっていなかった過去の会話を編纂しました」) に、**編纂 N 件 / 吸収 M 件 /
残り K 件 (理由つき)** の内訳を出す。残りがあるのに完了の顔だけで終わらない。

2026-09-08 の実機検証での追記が二つ。完了文の内訳には束ねの実数 (「まとめ N 件」)
も載せ、編纂ゼロで束ねだけの走行は「編纂しました」ではなく「あらすじを大きな流れに
まとめました」と言う。また補修の入口 (バナーと確認モーダル) は、未編纂がゼロでも
**束ねの残りが 1 回分以上あれば開く** — 束ねだけが残った状態 (予算枯渇の欠陥の
後遺症や、将来の中断の後) の正常化の経路が会話しか無い、という穴を実機で踏んだため。

診断ツール (Chronicle 診断レポート) には孤児参照のエントリ単位の内訳
(何本のあらすじに散っているか・全滅か部分欠けか) を追加する。今回の調査で
「参照が 20 個」までしか分からず、(c) の真偽も確定できなかった不足の解消。

## 第二段の範囲宣言 (UI — 別途起草)

1. **仮のあらすじと事後承認**: 全あらすじに「機構の下書き」である印を持たせ、ユーザーが
   いつでも承認・却下・編集できる (コア記憶の未確認バッジと同思想。承認を求めるのでは
   なく、できる — 未承認でも通常どおり使われる)。
2. **断絶の可視化と修復の委任**: 穴・孤児参照・孤児あらすじを、修復の操作つきで
   Chronicle タブに見せる (「この期間をあらすじにする」「作り直す」「削除する」)。
   操作の無い警告は出さない。発話ゼロの run の解消口はここ (機構 E)。

## 検証の旅

- 整列計画・吸収計画・統合分割は純関数なので、穴 51 個の合成データで回帰テストを組む
  (跨ぎ統合 / 両方向吸収 / 発話ゼロの線引き (実会話フィルタ経由) / 不明期間の一行 /
  上位への繋ぎ直し / 末尾の引き戻しとの優先順位)。
- 実利用者の形の再現: 「複数スレッド + 各スレッドに端数 + 孤児参照」の隔離 DB で
  補修の一気通貫テスト (mock LLM) — 実行後に未被覆が発話ゼロ分だけになること・
  内訳報告の文面まで確かめる。
- 実機: 報告者に配布し、(a) 584 件が発話ゼロ分を除いて消えること、(b) 帯が予算内に
  収まること、(c) 一回の会話の送信量の再測定。送信量が下がり切らなければ別要因として
  追加調査。
- 正典の同時改訂: arasuji_levels §3-2 (境界②の廃止)・§16-1 (発話ゼロの例外の記帳)・
  吸収 issue の裁定 1・2 への改訂注記を、実装と同じコミットで行う。
