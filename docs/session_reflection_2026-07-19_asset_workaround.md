# Session reflection: 根因未確認のランタイム材質補正

## 事故

Godot Vesselの`player.vrm`が白く描画された際、VRM内でbase textureが生存し、MToonのshade textureがなくshade colorが白いことまでは確認した。しかし制作元のUnity材質と変換工程を調べる前に、Vesselの汎用avatar loaderでbase textureをshade textureへ代入する処理を実装し、「白化を修正した」と報告した。

## 何が誤りだったか

- MToon仕様ではshade texture未指定時に白を使うため、Godotはartifactを正しく描画していた。仕様どおりの出力をruntime側で上書きした。
- Unity元材質はUTS 2.09からMToon10へshader参照だけが切り替わり、UTS固有parameterがMToon側へ移植されていなかった。shadeだけでなくnormal、emission、matcapも欠落していた。
- 見た目が改善したことを、根因が直った証拠として扱った。実際には編集可能な上流変換不備を一症状だけ隠した。
- 公式の旧VRM移行規則に似た処理が存在することを、今回のVRMにも適用してよい根拠と混同した。今回のartifactは最初からVRM 1.0であり、旧形式移行対象だとは確認できなかった。

## 根因

技術上の根因はUTS→MToon材質parameter移植の欠落。作業上の根因は、調査範囲を`serialized artifact → importer → renderer`に限定し、`authoring source → converter/exporter`まで遡らないまま実装へ移ったこと。

ただし、これを「外部artifactでは制作元まで遡る」という専用手順にした最初の再発防止策も不十分だった。問題の本質はartifact調査の不足ではなく、成功条件を目の前の出力へ縮め、担当中のcomponentだけを安全に見せ、原因・負債・検証を別工程と未来の作業者へ移す**早すぎる局所化**にある。外部artifact専用の因果chainは、今回と同じ事故にしか効かない二つ目のその場しのぎだった。

## 恒久的な判断規範

問題を実装箇所へ狭める前に、次の四層を順に定義する。

1. 最終的にユーザーまたはペルソナへ何が成立すべきか。
2. その結果を作る端から端までの工程とライフサイクルは何か。
3. 各境界で誰がどの不変条件を所有するか。
4. その上で、いま観測している局所症状はどこに位置するか。

修正案には「この変更が局所的に完全成功しても、全体のどこに誤り・曖昧さ・後始末が残るか」を必ず問う。失敗後は原因を、直接の技術原因、誤った判断を生んだ思考、判断を通過させた工程・検証構造の三層に分ける。再発防止は後二者まで変えなければならない。

また、再発防止策を正典化する前に、現在の固有名詞を使わず、無関係な二領域へ適用する転用テストを行う。転用できない規則は恒久策と呼ばない。

## 転用テスト

### 外部APIの再試行

局所症状だけなら「失敗したHTTP callを再試行する」で閉じる。しかし全工程を見ると、課金・外部副作用・内部台帳・ユーザーへの結果配送が一つの旅であり、callだけの成功は重複実行を生む。所有すべき不変条件は「一つの意図に一つの外部副作用と追跡可能な結果」で、execution ledgerやidempotency境界へ修正を置く必要がある。本規範は、HTTP client内の局所retryで隠す判断を止める。

### 記憶表示UIの不整合

局所症状だけなら「画面上で重複行をfilterする」で見た目は直る。しかし全工程を見ると、生成・永続化・検索・context投入・表示が同じ記憶を消費し、DBの重複はペルソナの次の思考にも入る。所有すべき不変条件は永続化または配送境界の一意性であり、UI filterへ負債を移してはいけない。本規範は、最終画面だけ合わせる判断を止める。

この二例はVRM、Unity、Godot、材質という固有語を使わず、今回と同じ「局所出力の成功で全体の破綻を覆う」判断を検出できる。

## 今回から残す具体的教訓

1. 外部artifactの不具合は`制作元→変換→artifact→import→runtime`の全段を追う。
2. 仕様準拠かどうかを公式仕様で先に確認する。
3. 正常な比較対象がある場合は、生成ツールの版だけでなく入力parameterを比較する。
4. 上流を編集できるならruntime補正を入れない。
5. 出力差だけを根拠に「修正」と報告しない。
6. 互換shimが必要なら、実装前に上流修正不能の理由と意味変更を明示し、一回の承認を得る。

これらは本件へ適用した具体例であり、一般規範そのものではない。一般規範は`CLAUDE.md`の「Whole-system correction and recurrence prevention」に正典化した。
