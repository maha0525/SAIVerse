# 自動想起しきい値の再測定 (EmbeddingGemma 2 q4 ONNX)

計測日: 2026-10-12。仕様は docs/intent/embedding_gemma2_migration.md の「設計 §3 しきい値の再測定」。
この文書は、測った事実 (1〜3 節) と、そこから導いた既定値とその根拠 (4 節) を分けて書く。

## 結論 (導いた値)

| 値 | e5 時代 | 新しい既定 | 出自 | 状態 |
|---|---|---|---|---|
| 採用しきい値 `SAIVERSE_AUTO_RECALL_THRESHOLD` | 0.86 | **0.78** | 分布 (この測定) | 合成データでの導出。実会話での採否の確認は隔離検証フェーズに残る |
| message の上乗せ `SAIVERSE_AUTO_RECALL_MSG_THRESHOLD_OFFSET` | 0.02 | **0** | 分布 (この測定) | 同上 |

新しい採用しきい値 0.78 が、e5 時代の反射判断の下限と同じ数字になったのは偶然 (e5 の分布で決めた 0.78 と、EmbeddingGemma 2 の分布で決めた 0.78 は別の量の上の値)。

## 1. 測定の方法

0.86 を決めたときの手順 (sea/auto_recall.py の旧コメント: 話題に沿ったクエリ / 無関係なクエリ / 「うん」のような短文、それぞれでの top ヒット) を、合成データの上で再現した。

### データ (すべてこの測定のために書いた架空の文、実在のペルソナの記憶は不使用)

部品は `corpus_data.py`、組み立ては `measure.py` (乱数 seed 20261012 固定)。

- **message 層 300 本** (122〜479 字、中央値 310 字): 会話メッセージ風。話題 18 種 (料理・天気・ゲーム・引っ越し・猫・映画・音楽・旅行・作業相談/プログラミング・体調・読書・植物・買い物・散歩・友人・掃除・星空・自転車) の文を組み合わせ、話題を問わない会話の地の文 (「書き残しておかないと、すぐ忘れてしまいそう。」など 16 文) を約 3 割の確率で混ぜた。うち 30 本は、特定の出来事 (例: カレーにりんごジャムを入れて甘くなりすぎた) を 1 文含む「正解のメッセージ」。文書プロンプト `title: none | text: ` で埋め込む (本番の message ソースと同じ: 本文のチャンクを `is_query=False`)。
- **要約層 100 本** (30〜67 字、中央値 44.5 字): Memopedia / Fragment の埋め込み形式 (`タイトル: 本文`、sai_memory/unified_recall.py の embed_memopedia_pages / embed_memopedia_fragments と同じ形)。うち 30 本は上の出来事の要約 (正解の要約)、70 本は話題ごとの要約。半分程度に要約の結び (「本人はそのことを笑いながら話していた。」など 12 文) を付けて長さを散らした。Chronicle は本番の自動想起の対象外 (`search_chronicle=False`) なので入れていない。
- **クエリ 60 本** (クエリプロンプト `task: search result | query: `): ① 話題に沿ったクエリ 30 本 (各 1 つの出来事を指す最新発話。正解は message 1 本 + 要約 1 本で、作成時に記録)、② 無関係なクエリ 20 本 (コーパスに無い話題 15 本 + 意味のない文字列 5 本)、③ 短い相づち 10 本 (「うん」「そうだね」「なるほど」「わかった」など)。

### 測った量

各クエリについて、層ごとのコーパス全体に対する cosine の最大値 (top)。① は正解との cosine と、正解以外の最高も。層をまたいだ上位 8 件 (自動想起の topk 既定) も保存した。

### モデル

- **gemma_q4**: 本番の `sai_memory.memory.recall.Embedder` をそのまま (sbert/embeddinggemma-2-q4、CPU、onnxruntime の既定スレッド)。
- **e5_small** (較正用): 移行前の経路と同じ組み方 (fastembed 0.7.4 の custom model、mean pooling、正規化、`query: ` / `passage: `、sbert/multilingual-e5-small の onnx/model.onnx)。同じ合成データの上で e5 を測り、(a) 合成データが元の実データの測定を再現できているか、(b) 反射判断の下限の相対位置、の二つに使う。スレッド数は 4 に絞った。

## 4. 値の導出

### 採用しきい値 0.78

しきい値ごとの通過数 (derive.py の出力、正解 = message・要約のどちらかの層で正解が通ったクエリ数):

| 設定 | 正解 (どちらかの層) | 正解 message | 正解 要約 | 正解以外の最高が通過 (message / 要約) | ノイズ (② ③ の 30 本) の通過 |
|---|---|---|---|---|---|
| e5 0.86 + message 0.02 (参考) | 29/30 | 16 | 29 | 9 / 8 | 0/30 |
| gemma 0.76 | 29/30 | 20 | 29 | 8 / 2 | 1/30 |
| gemma 0.77 | 29/30 | 15 | 29 | 5 / 2 | 0/30 |
| **gemma 0.78** | **29/30** | **12** | **29** | **3 / 1** | **0/30** |
| gemma 0.79 | 26/30 | 11 | 26 | 2 / 0 | 0/30 |
| gemma 0.80 | 25/30 | 9 | 25 | 1 / 0 | 0/30 |

根拠: 現行の決め方 (無関係と相づちの top の最大より上、話題に沿ったクエリの top の帯の下端) を踏襲すると、ノイズの最大 0.761 と、話題の帯の下端 0.784 (離れた 1 本 0.720 を除く) の間に置くことになる。0.78 はこの隙間の上寄りで、ノイズの最大に対する余裕 0.019 は、e5 の 0.86 が元の実測のノイズ最大 0.842 に対して持っていた余裕 0.018 とほぼ同じ。正解の通過 29/30・ノイズの通過 0/30 は、同じデータの上での e5 の現行設定と同じ結果になる。0.79 にすると話題の帯の下端を割って正解が 3 本落ち、0.77 では余裕が 0.009 に縮む。

### message の上乗せ 0

根拠: 上乗せが対処していた「message 層のノイズが要約層より高く出る」性質が gemma では逆転している (3 節: ノイズの最大は message の方が 0.014 / 0.022 低い)。0.78 だけでノイズの通過は 0/30 なので、上乗せで落とせるノイズは無く、上乗せ 0.02 を残すと正解の message の通過が 12/30 → 9/30 に減るだけになる。負の上乗せ (message を緩める) は、ノイズの p50 では message の方が高い群 (無関係 +0.010) もあるので入れない。

### 反射判断の候補の下限 0.62 (暫定)

0.78 は e5 の上で Jev の実験 (2026-09) によって調整された値で、分布だけでは決められない。そこで「現行の帯 (下限 0.78〜採用しきい値 0.86) が e5 の分布の中で占めた相対位置」を新しい分布の上で保存する。

- まず百分位の位置そのもの (下限が正解ヒット分布の何 % 点にあるか) で移すことを試したが、**0.78 は e5 の正解ヒット分布の全体より下** (合成データの e5 の正解は最小 0.823、JSQuAD の e5 の正解も p10 が 0.844) で、どの基準でも 0 % 点になって写像が決まらない。「正解をすべて下回る位置にある」という点だけは保存でき、0.62 も gemma の正解の最小 (0.700) より下にある。
- そこで、帯の幅 (0.86 − 0.78 = 0.08) を **正解ヒット分布の p10〜p90 幅の何倍か** で表し、その倍率を gemma の分布の上で保存した。

| 正解ヒット分布の基準 | e5 の p10〜p90 幅 | 倍率 (0.08 / 幅) | gemma の幅 | 導いた下限 (0.78 − 倍率 × 幅) |
|---|---|---|---|---|
| 合成: どちらかの層の正解の良い方 | 0.0370 | 2.164 | 0.0761 | 0.615 |
| 合成: 要約層の正解 | 0.0370 | 2.164 | 0.0761 | 0.615 |
| 合成: message 層の正解 | 0.0454 | 1.764 | 0.0927 | 0.616 |
| 合成: 両層をまとめた 60 値 | 0.0482 | 1.661 | 0.1153 | 0.589 |
| JSQuAD (results.md B 節 e5 / C 節 q4) | 0.0861 | 0.929 | 0.1349 | 0.655 |

- 照合 (判断に回る件数の保存): 上位 8 件のうち下限以上の候補の平均件数は、e5 の 0.78 で 7.67 件 (話題 8.00 / 無関係 7.00 / 相づち 8.00)。gemma で同じ件数になる下限は約 0.595。gemma の 0.62 では 6.82 件 (話題 8.00 / 無関係 4.45 / 相づち 8.00)。

根拠: 同じ合成データの正解分布を基準にした 3 通りが 0.615〜0.616 で一致したので、これを丸めて 0.62 とした。JSQuAD の分布で同じ計算をすると 0.65 (高め)、判断に回る件数を揃えると 0.60 (低め) で、0.62 はその間にある。0.62 < 0.78 なので、下限が採用しきい値を超えたときの逆転警告 (sea/auto_recall.py の `_REFLEX_FLOOR > accept_threshold`) は既定の組では出ない。

**暫定である範囲**: 下限 0.62 は「e5 の上で合格した帯の相対位置」を移しただけで、反射判断を通した採否が Jev の合格時と同等であることは確かめていない。docs/intent/auto_recall_jev_rerank.md の合否手順の縮小再実行は、移行の隔離検証フェーズ (intent の検証手順 2) に残る。

## 5. 再現性

同じ seed で 2 回走らせ (`results/run1.json` と `results/run2.json`)、`measure.py --compare` で照合した: コーパスは同一、クエリごとの全スコアの差の最大は 0 (完全一致)、top の文書も全クエリで一致。

## 6. 計測上の妥協・注意点

- **合成データでの測定**。元の 0.86 は実データ (air_city_a) で決めたが、今回は本番データに触れていない (intent §3 の既定)。代表性は e5 での較正 (2 節) で確かめたが、実会話の語彙の広さ・長さの分布・コーパスの規模 (実データは数千〜数万チャンク) までは再現していない。コーパスが大きいほどノイズの top の最大は上がる方向に動くはず (未確認)。
- 同じ話題の message は同じ文の部品を共有するので、① の「正解以外の最高」(特に message 層) は実データより高く出ている可能性がある。導出にはこの系列を使っていない。
- 要約層の長さは 30〜67 字で、仕様の範囲 (30〜120 字) の短い側に寄っている。
- クエリは各群 20〜30 本で、百分位は粗い (p10 は下から 3 本目付近)。
- 上位 8 件は cosine の単純な順位で取った。本番の unified_recall はソースごとの枠と順位の融合 (RRF) を通すので、判断に回る件数の照合は近似。
- JSQuAD の分布で見ると、gemma の 0.78 は正解の分布のおよそ p39 にあたり (p10 0.720 と p50 0.802 の線形補間)、e5 の 0.86 (およそ p23) より相対的に厳しい。JSQuAD は質問と百科事典の段落の検索で、自動想起の「ノイズを落とす」位置づけとは課題が違うので導出には使っていないが、実会話で message の想起が e5 より渋く感じられる可能性はある (合成データでも正解の message の通過は e5 16/30 に対して 12/30)。隔離検証で見る点として残す。
- 計測は 1 台 (Ryzen AI 9 HX 370、CPU のみ)。gemma の 400 本の埋め込みは約 39 秒、e5 は約 25 秒。

## 再現の手順

作業ツリーのルートから:

```
python -X utf8 experiments/embeddinggemma2_bench/threshold/measure.py --models gemma,e5 --out results/run1.json
python -X utf8 experiments/embeddinggemma2_bench/threshold/measure.py --models gemma,e5 --out results/run2.json
python -X utf8 experiments/embeddinggemma2_bench/threshold/measure.py --compare results/run1.json results/run2.json
python -X utf8 experiments/embeddinggemma2_bench/threshold/derive.py results/run1.json
```

`--models` の既定は gemma だけ。e5 の較正は任意の測定で、fastembed (移行で本体の依存から外れた) と sbert/multilingual-e5-small が要る (既定の置き場はリポジトリの `sbert/multilingual-e5-small`、別の場所なら `--e5-dir` で指す。移行後のリポジトリには無い)。derive.py は e5 の結果を使うので、上の手順は e5 込みで測っている。gemma の分布だけを見るなら `--models` を付けずに回せばよい。
